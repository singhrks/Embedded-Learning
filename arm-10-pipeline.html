How an instruction executes

CA chapter 11 covered pipelining in general. This chapter follows one AArch64 instruction through a real core, showing where the MMU, the caches and the exception machinery each enter the picture — and what can go wrong at each point.

The pipeline, concretely

A processor does not execute one instruction at a time from start to finish. It has many in flight at once, at different stages, and almost every performance effect in this track comes from something disturbing that flow.

   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
   │ FETCH  │→│ DECODE │→│ RENAME │→│ ISSUE  │→│EXECUTE │→│ RETIRE │
   │        │ │        │ │        │ │        │ │ MEMORY │ │        │
   └────────┘ └────────┘ └────────┘ └────────┘ └────────┘ └────────┘
        ▲          ▲                     ▲          ▲          ▲
        │          │                     │          │          │
   branch      fixed 32-bit         scheduler   MMU + caches  in ORDER,
   predictor   encoding makes       picks ready              architectural
   + I-TLB     this cheap and       instructions             state updates
   + I-cache   parallel                                      HERE ONLY

  Depth varies enormously by core:
     Cortex-A53     8 stages, in-order, 2-wide
     Cortex-A78    13 stages, out-of-order, 4-wide fetch/6-wide issue
     Neoverse V2   deeper still, 8-wide

Fetch: where translation begins

Before an instruction can be decoded it has to be fetched, and fetching means an address translation and a cache lookup. That is why instruction-side misses and TLB pressure are real performance problems and not just a data-side concern.

/* The PC is a VIRTUAL address. Before any instruction bytes can be
   read, it must be translated.                                */

   PC → I-TLB lookup
          hit  → physical address in ~1 cycle
          miss → hardware page table walk (chapter 13)
                 walk fails → INSTRUCTION ABORT
                              ESR.EC = 0x20 (lower EL) or 0x21
        → L1 instruction cache
          hit  → up to 4-8 instructions returned
          miss → L2 → interconnect → DRAM

/* In parallel, the branch predictor is already producing the NEXT
   fetch address, so the front end never waits for decode to
   discover that an instruction was a branch (CA chapter 12).  */

/* Three things can go wrong here:
     · translation fault      → instruction abort
     · permission fault       → the page is XN (execute-never)
     · the page is Device     → instruction fetch from Device
                                memory is UNPREDICTABLE. Never
                                execute from an MMIO mapping.  */

Decode and rename

Decoding turns instruction bits into work for the execution units, and on an out-of-order core it also renames registers — which is what allows instructions to execute in a different order without producing wrong answers.

/* Fixed 32-bit encodings mean the decoder can split N instructions
   simultaneously with no serial dependency — the single biggest
   front-end advantage of the ISA (chapter 03).               */

/* Two things happen that software cannot see but must understand: */

/* 1. CRACKING — some instructions become several micro-operations */
        ldp     x0, x1, [x2]        // may become two loads
        stp     x0, x1, [x2, #16]!  // store + address update

/* 2. REGISTER RENAMING — architectural registers are mapped onto
      a much larger physical register file.                    */

        add     x0, x1, x2      // x0 → physical reg p37
        ldr     x0, [x3]        // x0 → physical reg p52  (a NEW one)
        add     x4, x0, #1      //         reads p52

/* Renaming removes WAR and WAW hazards entirely: the second write
   to x0 does not have to wait for the first, because they are
   different physical registers. Only TRUE dependencies (RAW)
   remain, and those are the ones you can attack in source code
   with multiple accumulators (CA chapter 19).               */

The memory stage, in detail

Loads and stores are the most complicated stage, because a load may hit, miss, or need to wait for an earlier store to the same address. This is where most stalls in real code actually originate.

This is where most of the interesting failures live.

   effective address computed (base + offset, or base + index<<s)
        │
        ▼

        Device memory: ANY unaligned access faults

Out-of-order execution and its limits

Out-of-order execution hides latency by running later instructions while an earlier one waits. It is powerful and finite, and knowing what limits it tells you which stalls the hardware can absorb and which it cannot.

/* Instructions EXECUTE when their operands are ready, in any
   order. They RETIRE strictly in program order.             */

        ldr     x0, [x1]        // L2 miss: 40 cycles
        add     x2, x3, x4      // independent — executes NOW
        add     x5, x6, x7      // independent — executes NOW
        add     x8, x0, #1      // DEPENDENT on x0 — must wait

/* The reorder buffer holds results until retirement. Two
   properties follow, and both matter:                      */

/* 1. PRECISE EXCEPTIONS. If the load faults, everything after it
      is discarded before retiring, so the architectural state
      looks exactly as if execution stopped at the load. That is
      what makes demand paging possible: the OS fixes the mapping
      and the SAME instruction re-executes (OS chapter 12).  */

/* 2. SPECULATIVE state is NOT rolled back. Caches, TLBs and
      predictor tables were already changed. This is the entire
      basis of Spectre (CA chapter 12), and the reason ARM added
      CSDB, SB and SSBS.                                     */

/* What LIMITS the reordering window:
     · reorder buffer size (~100-500 entries)
     · load/store queue depth
     · physical register file size
     · a full BARRIER, which drains it deliberately (chapter 21) */

Where stalls come from

A pipelined core's steady-state throughput of "roughly one instruction per cycle" is a best case, not a guarantee, and every row here is a different reason an instruction has to wait rather than issue immediately. They fall into two kinds worth telling apart: the first five rows are the pipeline waiting on memory or prediction — the data or the next instruction simply is not ready yet — and no amount of code restructuring removes the miss, it can only make misses less frequent or hide their latency behind other work. The last three rows are different: they are the cost of correctness mechanisms — barriers, atomics — that exist to make concurrent code behave predictably, and the fix there is usually to use a weaker, cheaper mechanism rather than to eliminate the need for one entirely.

/* The dependency chain is the one you control most directly: */

/* 4-cycle FP add latency, serialised — 4 cycles per element */
for (i = 0; i < n; i++) sum += a[i];

/* four independent chains — the latencies overlap */
for (i = 0; i < n; i += 4) {
        s0 += a[i];   s1 += a[i+1];
        s2 += a[i+2]; s3 += a[i+3];
}
sum = (s0 + s1) + (s2 + s3);
/* Typically ~4x faster with an UNCHANGED instruction count. The
   compiler will not do this for floats without -ffast-math,
   because it changes the rounding (CA chapter 03).         */

Measuring what the pipeline is doing

All of the above is measurable. The performance monitoring unit counts exactly these events in hardware, which turns a theory about why code is slow into a number.

# the top-down view: where are the issue slots going?
perf stat -e cycles,instructions,stall_frontend,stall_backend ./prog

#   stall_frontend high → INSTRUCTION supply
#        I-cache misses, branch mispredicts, ITLB misses
#        fix: code layout, PGO, fewer/predictable branches
#
#   stall_backend high  → DATA supply or execution
#        D-cache misses, dependency chains, divides
#        fix: data layout, more parallelism, better algorithms

# drill down
perf stat -e l1d_cache_refill,l2d_cache_refill,ll_cache_miss_rd \
          -e dtlb_walk,itlb_walk \
          -e br_mis_pred_retired,br_retired \
          -e inst_spec,inst_retired ./prog

#   inst_spec vs inst_retired = how much work was SPECULATED and
#   thrown away. A large gap means heavy mispredict waste.

# which instruction?
perf record -e l1d_cache_refill ./prog && perf annotate

# ARM's own tooling gives a full top-down breakdown
#   topdown-tool (from Arm's telemetry solution)
#   Arm Streamline, Arm MAP
IPC is the first number to look at

Instructions per cycle tells you immediately which world you are in. Below ~0.5 on a wide core means you are stalled — find out on what. Above ~2 means the core is busy and further gains must come from doing less work, i.e. a better algorithm. Between the two, look at the stall counters. This one number saves a great deal of misdirected optimisation.

Where exceptions fit

An exception has to appear to happen at a precise instruction, even though dozens are in flight. How the pipeline achieves that explains why some faults are recoverable and others are not.

   Any stage can raise an exception:

     FETCH    instruction abort — translation or permission
     DECODE   undefined instruction; trapped by a higher EL
     EXECUTE  FP exception, divide-by-zero (where trapped)
     MEMORY   data abort, alignment fault, external abort
     any      IRQ/FIQ arriving asynchronously
     any      SError — an imprecise external abort, often from
              a write posted long ago

   SYNCHRONOUS exceptions are precise: the instruction is
   identified exactly, and ELR points at it (or past it, for SVC).

   ASYNCHRONOUS ones are taken between instructions, at a point
   the hardware chooses.

   SError is the awkward case: the reported PC has NOTHING to do
   with the cause, because the failing transaction retired long
   before the error came back. This is why external aborts from a
   bus firewall (security chapter 20) are so hard to attribute,
   and why an ESB (Error Synchronization Barrier) is used to
   contain them at known points.

   Chapter 28 covers the entry sequence; chapter 29 covers
   decoding what happened.
