One page: the whole track, for revision

Twenty chapters of isolation mechanisms compressed to what you actually need in your head. Nothing here teaches a concept for the first time — every line is a reminder with a chapter number attached. Read it before a security review, before a bring-up, or whenever you need to answer "is this actually isolated?" without re-reading the track.

The seven rules that decide whether isolation is real

Each has been the single missing step in a shipped product
  1. Name the adversary before claiming security. "Secure" without "against whom" is not a claim that can be evaluated, let alone tested (ch. 01).
  2. The CPU's MMU does not constrain devices. Every bus master reaches memory independently, and without an SMMU nothing checks it (ch. 02).
  3. A boundary you cannot demonstrate is not a boundary. Attempt the forbidden access and confirm it is denied — assumption is not verification (ch. 19).
  4. Lock the configuration once it is set. Protection that later, less-trusted software can reconfigure protects nothing (ch. 18).
  5. Everything crossing a trust boundary is attacker-controlled — contents, size, and whether it changes while you read it. Copy, then validate (ch. 12, 16).
  6. Signatures prove authenticity, never freshness. Without anti-rollback an attacker installs a genuine, signed, vulnerable old version (ch. 14).
  7. Debug bypasses all of it. If the authentication signals are asserted on a production part, the rest of this track is decoration (ch. 10).

The table to fix first: four mechanisms, four questions

A modern SoC has several independent isolation mechanisms, and they are routinely confused with one another. Each answers a different question about a different kind of access — and a design that relies on one where another was needed has a gap rather than defence in depth.

MechanismAnswersEnforced atCh.
MMUMay this software touch this memory?The processorARM 12–14
SMMU / IOMMUMay this device touch this memory?In front of the device03–07

The gap each one leaves

The MMU says nothing about devices. The SMMU says nothing about which peripherals a master may reach. The NS bit says nothing about separating two non-secure masters from each other. Access control units say nothing about memory contents. They are complementary rather than alternative, and the interesting question in any review is which of the four is absent.

The DMA problem, and what actually closes it

The single largest idea in the track, reduced to a before-and-after. If you can draw this and name what the SMMU still does not cover, you have the substance of chapters 2 through 7.

   THE GAP:
        CPU  ──► MMU ──► memory        checked
        device ─────────► memory       NOT checked

   THE FIX:
        device ──► SMMU ──► memory     checked

   WHAT THE SMMU NEEDS TO DO ITS JOB:
        StreamID        which device is this?      (ch. 03)
        Stream table    per-device configuration   (ch. 04)
        Context desc.   which address space        (ch. 04)
        Stage 1 / 2     who owns each translation  (ch. 05)
        Event queue     what it blocked and why    (ch. 06)

   WHAT IT STILL DOES NOT COVER:
        · masters not behind an SMMU at all
        · devices grouped together and indistinguishable
        · peripheral register access (that is an XPU job)
        · anything with ATS, which moves trust INTO the device

   THE DRIVER-FACING VIEW is the DMA API (ch. 07), which
   hides all of the above - and whose four rules exist
   precisely because the hardware underneath is real.

TrustZone in one picture

TrustZone reduced to its structure: one bit, two worlds, four levels, and the hardware blocks without which the bit means nothing.

   ONE BIT, CARRIED WITH EVERY TRANSACTION, enforced by
   hardware blocks that must all be present:

     NON-SECURE                 SECURE
     ──────────                 ──────
     EL0  applications          S-EL0  trusted apps
     EL1  the OS kernel         S-EL1  trusted OS
     EL2  hypervisor            S-EL2  partition mgr (opt.)
     ─────────────── EL3: the monitor ───────────────
                     the only level that sees both

   THE ENFORCEMENT BLOCKS (ch. 10) - a platform missing any
   of these has a weaker boundary than the architecture
   implies:

     TZASC    partitions DRAM
     TZPC     partitions peripherals
     caches   tagged by security state
     GIC      interrupt groups per state
     SMMU     device transactions carry the bit too
     debug    gated separately - and bypasses everything

   CROSSING IT costs a full context switch through the most
   privileged software on the chip, twice - microseconds,
   not nanoseconds (ch. 11).

The security review checklist

  • The adversary and the assets are both written down.
  • Every bus master is enumerated, and you know which are behind an SMMU and which are not.
  • Device groups that cannot be separated are identified and treated as one unit.
  • The access-control matrix exists explicitly, and no entry is permissive "just in case".
  • Every protection unit's configuration is locked before untrusted software runs.
  • Denials are tested deliberately, not assumed.
  • Secure-world code validates every parameter, and copies before validating.
  • The secure world contains as little as the design allows.
  • The boot chain is unbroken from immutable ROM to the OS, with anti-rollback.
  • Debug authentication is deasserted on production parts, and that is verified.
If you remember only one sentence from this track

Isolation is a property of hardware that has been configured, locked and tested — never of software that intends well. Every mechanism here fails silently when misconfigured, which is precisely why demonstrating a denial matters more than reading the code that was supposed to produce one.
