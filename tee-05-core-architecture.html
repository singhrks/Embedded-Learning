OP-TEE OS architecture

OP-TEE is a small preemptible kernel with a fixed pool of threads, its own MMU regime, a demand pager, and a strict rule that it never runs unless the normal world asked it to. Those four properties explain almost every behaviour you will observe, including the deadlock in the last section.

The shape of it

The trusted OS has the same concerns as any kernel — memory, threads, entry points — solved differently because of where it runs and what it must guarantee.

   S-EL0    TA        TA        TA
            |         |         |
            |  SVC (the GP Internal API is a syscall
            |       interface, exactly like Linux's)
            v
   +-----------------------------------------------------+

   |   crypto          libtomcrypt / mbedTLS, plus       |

   EL3      TF-A BL31

   Things OP-TEE deliberately does NOT have:

     no scheduler of its own in the usual sense - the NORMAL
       world schedules it, by choosing when to make an SMC
     no interrupts it services on its own behalf, except its
       own timer and secure interrupts
     no dynamic memory beyond fixed pools
     no filesystem - it asks the normal world (chapter 9)
     no network, no USB, no display, unless a platform adds one

   It is closer to a very careful library with an MMU than to
   an operating system, and that is deliberate: a small
   trusted computing base is the entire product.

The thread pool

The secure world has a small, fixed number of execution contexts rather than a scheduler creating them on demand. That limit is a design decision with consequences the normal world can feel.

/* OP-TEE has a FIXED number of threads, set at build time:   */

    CFG_NUM_THREADS = 8      /* typical; sometimes 2 or 4      */

/* One thread is occupied for the ENTIRE duration of a normal-
   world call. From the SMC that enters OP-TEE until the SMC
   that returns, that thread belongs to that caller.          */

  normal world calls in       -> a thread is allocated
     TA runs
     TA does secure storage   -> RPC out to tee-supplicant.
                                 THE THREAD IS STILL HELD - it
                                 is suspended waiting for the
                                 normal world to answer.
     TA finishes
  return to normal world      -> thread freed

/* Consequences:

   1. At most CFG_NUM_THREADS concurrent TA invocations,
      system-wide. The 9th caller gets
      TEEC_ERROR_BUSY / OPTEE_SMC_RETURN_ETHREAD_LIMIT and
      libteec retries.

   2. A TA that blocks holds a thread. A TA that blocks
      FOR EVER holds it for ever.

   3. Thread stacks are statically allocated:
        CFG_STACK_THREAD_SIZE   default 8192 bytes
        CFG_STACK_TMP_SIZE      the temporary/abort stack
      8 threads x 8 KB is 64 KB of your secure memory budget,
      before any TA runs.

   4. TA stack size is separate and per-TA:
        TA_STACK_SIZE in the TA's user_ta_header_defines.h    */
The thread-exhaustion deadlock

All CFG_NUM_THREADS threads are inside OP-TEE, each waiting on an RPC to tee-supplicant. tee-supplicant is a normal-world process; to service any of them it must be scheduled by Linux. If tee-supplicant itself needs to enter OP-TEE — or if the Linux thread that would run it is itself blocked in an OP-TEE call — nothing can make progress. The system hangs with no error anywhere.

Avoid it by: never calling into the TEE from a thread that services the TEE; keeping RPC use out of hot paths; and raising CFG_NUM_THREADS so transient bursts do not saturate the pool. It is a design constraint, not a bug to be fixed later.

How a call enters

Every call into the secure world arrives at a defined entry point, and following one from the SMC to the trusted application's code shows how the layers connect.

/* core/arch/arm/kernel/thread_spmc.c and entry_a64.S       */

  BL31 ERETs into OP-TEE's vector table at one of:

    fast_smc_entry        a "fast" call - runs to completion
                          with interrupts masked, on the
                          temporary stack, no thread allocated.
                          Used for: version queries, memory
                          config, cache maintenance requests.

    std_smc_entry         a "standard" call - allocates a
                          THREAD, can be preempted by a
                          non-secure interrupt, can make RPCs.
                          Used for: everything that runs a TA.

    fiq_entry             a secure interrupt arrived while the
                          normal world was running

    cpu_on/off/suspend/resume_entry
                          PSCI events forwarded by BL31 so
                          OP-TEE can save and restore per-CPU
                          state

/* The distinction matters. A fast call cannot:
     - allocate memory
     - call a TA
     - make an RPC
     - be interrupted
   It must be short and self-contained. Trying to do real work
   in a fast call is a classic porting mistake and produces
   hangs with interrupts masked.                             */

/* Foreign (non-secure) interrupt handling: while a standard
   call is running, an interrupt destined for the NORMAL world
   causes OP-TEE to save the thread's state and return to the
   normal world with OPTEE_SMC_RETURN_RPC_FOREIGN_INTR. Linux
   services the interrupt, then RESUMES the same thread. The TA
   never notices. This is why a long-running TA does not block
   Linux's timekeeping.                                       */

Memory layout

How the trusted OS lays out memory determines what is isolated from what, and it must account for memory shared with an untrusted world.

   TEE_RAM  - OP-TEE's own memory. Secure, and never mapped
              into any TA.
      TEE_RAM_RX   code, read+execute
      TEE_RAM_RW   data, heap, thread stacks
      TEE_RAM_RO

   TA_RAM   - the pool TA memory is allocated from. Each TA
              gets its own mapping; TAs cannot see each other.

   SHM      - non-secure shared memory. The ONLY region both
              worlds can touch. Chapter 7.

   +------------------------------------------------+
   |  TEE_RAM      core code + data      SECURE     |
   +------------------------------------------------+
   |  TA_RAM       TA code + data        SECURE     |
   +------------------------------------------------+
   |  SHM          shared buffers        NON-SECURE |
   +------------------------------------------------+

   Each TA runs at S-EL0 with its own translation tables. A TA
   cannot:
     read another TA's memory
     read TEE_RAM
     read normal-world memory except a buffer explicitly
       passed to it
     execute anything it did not bring

   The isolation between TAs is exactly the isolation between
   Linux processes, implemented by the same hardware. That is
   the point of running TAs at S-EL0 rather than linking them
   into the core.

The pager

Secure memory is scarce, so a trusted OS may page parts of itself in and out — with integrity and confidentiality maintained, since the backing store is not trusted.

/* CFG_WITH_PAGER=y makes OP-TEE demand-page its own code.   */

  Why: secure on-chip SRAM is small - often 128-256 KB - and
  OP-TEE plus crypto plus drivers does not fit. But external
  DRAM is not trustworthy: an attacker with bus access could
  read or modify it.

  Solution: keep a small resident part in SRAM, and page the
  rest in from DRAM, where it is stored ENCRYPTED and
  AUTHENTICATED.

     +---------------------------+
     |  SRAM (secure, on-chip)   |
     |    unpaged core           |
     |    the pager itself       |
     |    page tables            |
     |    a pool of page frames  |
     +---------------------------+
              ^  page fault
              |  decrypt + verify + map
              v
     +---------------------------+
     |  DRAM                     |
     |    encrypted pages, each  |
     |    with an authentication |
     |    tag                    |
     +---------------------------+

  Cost: a page fault inside OP-TEE now involves AES and a MAC
  check. Measurable, and worth it when the alternative is not
  fitting.

  On QEMU there is plenty of secure DRAM, so the pager is
  usually off. On real SoCs with small secure SRAM it is
  essential. tee-pager_v2.bin and tee-pageable_v2.bin in the
  FIP (chapter 2) are exactly this split.                    */

Default to a user-mode TA. A pseudo TA runs with the trusted OS's full privilege and no memory isolation; the only good reasons are needing a core API that is not exposed to S-EL0, or needing to run before the normal world can load anything. Chapter 18 covers the cases where it is genuinely right.
