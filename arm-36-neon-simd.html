Advanced SIMD and floating point

Chapter 4 showed that a second, wider register file exists alongside the integer one and left it there. This chapter is what it is for: how one instruction operates on many values at once, what the floating-point control registers actually change, why the whole register file has to be enabled before it can be used at all, and what it costs a kernel on every context switch.

One register, many values

The idea behind Advanced SIMD — universally called NEON — is that a 128-bit register need not hold one 128-bit number. It can hold sixteen bytes, or eight 16-bit values, or four 32-bit values, and a single instruction operates on all of them simultaneously and independently.

   THE SAME 128 BITS, INTERPRETED FOUR WAYS:

   V0.16B   ┌─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┐  16 x  8-bit
            └─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┘
   V0.8H    ┌───┬───┬───┬───┬───┬───┬───┬───┐   8 x 16-bit
            └───┴───┴───┴───┴───┴───┴───┴───┘
   V0.4S    ┌───────┬───────┬───────┬───────┐   4 x 32-bit
            └───────┴───────┴───────┴───────┘
   V0.2D    ┌───────────────┬───────────────┐   2 x 64-bit
            └───────────────┴───────────────┘

   THE SUFFIX IS PART OF THE INSTRUCTION, not a property of
   the register. The SAME register V0 is addressed as .16B in
   one instruction and .4S in the next, and the hardware does
   not track which you "meant" - the bits are simply
   reinterpreted.

     ADD  V2.4S, V0.4S, V1.4S

   performs FOUR independent 32-bit additions. Lane 0 of V0
   plus lane 0 of V1 goes to lane 0 of V2, and so on. There
   is NO carry between lanes - that independence is the whole
   point, and it is what lets the hardware do all four at
   once.

   THE NARROWER NAMES from chapter 4 - Q, D, S, H, B - are
   the SCALAR view of the same registers, used when you want
   one value rather than a vector. Qn is the full 128 bits;
   Dn is the low 64; Sn the low 32; Hn the low 16.
Writing a narrow register zeroes the rest — always

This mirrors the integer rule from chapter 4, where writing W0 zeroes the top half of X0. Writing S0 or D0 zeroes every bit above it in V0. It is not a merge. Code that assumes the upper lanes survived a scalar operation is reading zeros, and this is one of the most common mistakes when hand-writing NEON — particularly when mixing scalar floating-point with vector code in the same routine.

The operation classes worth recognising

The instruction set is large, but it is not arbitrary — nearly everything falls into a handful of shapes, and recognising the shape tells you what an unfamiliar mnemonic does without looking it up.

/* --- ELEMENTWISE: lane N op lane N -> lane N ------------- */
        ADD   V2.4S, V0.4S, V1.4S
        FMUL  V2.4S, V0.4S, V1.4S      /* F prefix = float  */
        FMLA  V2.4S, V0.4S, V1.4S      /* multiply-ACCUMULATE
                                          into the destination -
                                          the workhorse of any
                                          dot product or filter */

/* --- WIDENING and NARROWING: the lane count changes ------ */
        UADDL V2.8H, V0.8B, V1.8B      /* 8x8-bit -> 8x16-bit,
                                          so the sum cannot
                                          overflow             */
        XTN   V2.8B, V0.8H             /* back down, truncating */
        SQXTN V2.8B, V0.8H             /* back down, SATURATING */

/* --- SATURATING: clamp instead of wrap ------------------- */
        SQADD V2.8B, V0.8B, V1.8B
/* Q = saturating. 250 + 10 gives 255, not 4. This is the
   behaviour audio and image code wants, and getting it for
   free is a large part of why SIMD suits those domains. */

/* --- REDUCTION: many lanes -> one value ------------------ */
        ADDV  S0, V1.4S                /* sum of all lanes     */
        UMAXV B0, V1.16B               /* largest lane         */
/* Reductions are comparatively EXPENSIVE and they break the
   independence that makes SIMD fast. Do them once at the end
   of a loop, never inside it. */

/* --- PERMUTE: move data between lanes -------------------- */
        ZIP1  V2.4S, V0.4S, V1.4S      /* interleave           */
        TBL   V2.16B, {V0.16B}, V1.16B /* arbitrary shuffle -
                                          a 16-entry lookup    */

/* --- STRUCTURED LOAD/STORE: de-interleave in the load ---- */
        LD2   {V0.16B, V1.16B}, [x0]
/* Loads 32 bytes and SPLITS them: even-numbered bytes into
   V0, odd into V1. For interleaved data - stereo audio,
   RGB pixels - this de-interleaves for free, which is often
   worth more than the arithmetic instructions. LD3 and LD4
   do the same for three- and four-way interleaving. */

Floating point: the control and status registers

Scalar floating point uses the same register file, and its behaviour is governed by two registers that most programmers never touch and that change results when they are touched. They matter to a kernel because they are part of a thread's context.

Register / fieldControlsWhy it matters
FPCR.RModeRounding mode — nearest-even, toward zero, up, downChanging it changes results; a library that sets it and does not restore it corrupts every later calculation in that thread
FPCR.FZFlush-to-zero: treat denormals as zeroSubstantially faster on some implementations, and not IEEE-conformant — a deliberate accuracy trade, not a free win
FPCR exception enablesWhether invalid, divide-by-zero, overflow and inexact trapUntrapped by default: you get a default result and a sticky flag rather than an exception
FPSR cumulative flagsSticky record that an exception condition occurred They accumulate and are never cleared by hardware — you must clear them before a check means anything
FPSR.QCSticky flag that a saturating instruction actually saturatedThe only way to detect that a SIMD result was clamped rather than exact
These registers are per-thread state, and that has two consequences

First, a kernel must save and restore them on a context switch along with the vector registers — omitting them means one thread's rounding mode silently leaks into another's arithmetic. Second, because the flags are sticky and never self-clear, testing FPSR to find out whether your calculation overflowed requires clearing it first; otherwise you are reading the accumulated history of everything that ran on that thread beforehand.

The register file must be switched on first

This is the detail that turns a working user-space program into a kernel that crashes at boot, and it has no equivalent on the integer side: access to the whole SIMD and floating-point register file is trappable, and on reset it is trapped.

/* CPACR_EL1.FPEN controls whether EL0 and EL1 may execute
   any FP or SIMD instruction at all.

     00  trapped at both EL0 and EL1
     01  trapped at EL0 only
     10  trapped at both          (reserved-ish; see the ARM)
     11  not trapped

   AFTER RESET IT IS TRAPPING. An FP instruction executed
   before this is configured takes an exception with

        ESR_ELx.EC = 0b000111   (access to SVE/SIMD/FP
                                 trapped)

   which is chapter 29's syndrome decoding, and it is a
   classic early-boot failure: the C compiler emitted a
   floating-point or SIMD instruction into code you did not
   think used floating point at all - a struct copy compiled
   into vector loads, say - and the kernel dies before the
   console is up.                                            */

        MRS     x0, CPACR_EL1
        ORR     x0, x0, #(3 << 20)      /* FPEN = 0b11 */
        MSR     CPACR_EL1, x0
        ISB                             /* chapter 21: the
                                           change is not in
                                           effect until this
                                           retires            */

/* THE SAME CONTROL EXISTS AT HIGHER LEVELS:
     CPTR_EL2.TFP    traps FP/SIMD from EL1 and EL0 to EL2
     CPTR_EL3.TFP    traps it to EL3
   A hypervisor uses this deliberately - see below.

   AND THIS IS WHY KERNELS FORBID FP IN KERNEL CODE:
   it is not superstition. Kernel code runs with the user
   thread's FP state loaded, so using FP would corrupt it
   unless the kernel saves and restores around every use.
   Linux therefore builds with -mgeneral-regs-only, which
   makes the compiler refuse to emit FP or SIMD at all, and
   provides explicit kernel_neon_begin()/end() for the rare
   code - crypto, RAID checksums - that genuinely wants it. */

Lazy context switching, and why the trap is deliberate

The trap described above is not only a safety check for unconfigured systems. Kernels keep it armed deliberately, as the mechanism behind an optimisation that makes the large register file affordable.

   THE VECTOR REGISTER FILE IS 32 x 128 BITS = 512 BYTES,
   plus FPCR and FPSR. Saving and restoring that on EVERY
   context switch would be a significant cost - and most
   threads never touch it.

   SO KERNELS DO IT LAZILY:

     1. On context switch, do NOT restore the new thread's
        FP state. Instead, TRAP FP access (CPACR_EL1.FPEN)
        and record that the registers currently belong to
        some other thread.

     2. If the new thread never uses FP - the common case -
        nothing is ever saved or restored. Cost: zero.

     3. The moment it DOES execute an FP instruction, the
        trap fires. The handler:
             - saves the register file to whichever thread
               owns it right now
             - loads this thread's saved state
             - clears the trap
             - RETURNS TO RE-EXECUTE the faulting instruction

   THE COST MOVED, IT DID NOT VANISH: a thread that uses FP
   pays one trap the first time it does so after each switch.
   For a thread that uses FP constantly this is pure loss,
   which is why some kernels track usage and switch to eager
   saving for such threads.

   THIS IS ALSO A SECURITY BOUNDARY. If step 3 restores the
   registers but a path exists that clears the trap WITHOUT
   restoring, a thread reads another thread's vector
   registers - which may hold key material from a crypto
   routine. That exact class of bug has been found in real
   kernels more than once.

Getting SIMD into your code

There are four ways to reach these instructions, and they trade control against portability and effort in a way that makes the choice reasonably clear-cut in practice.

ApproachControlWhen it is the right answer
Auto-vectorisation — let the compiler do itNoneAlways try first. Costs nothing, and modern compilers vectorise simple loops well
Intrinsics — vaddq_u32() and friendsHigh; the compiler still allocates registers and schedulesThe usual answer when auto-vectorisation fails. Portable across compilers, and debuggable
Inline assemblyTotalRarely. You take over register allocation and scheduling, and usually lose to the compiler
A library — Ne10, or your BLASNoneFor standard operations, someone has already tuned this per microarchitecture
 
/* CHECK WHETHER THE COMPILER ALREADY DID IT before writing
   anything by hand - this is the step people skip:        */

$ gcc -O3 -march=armv8-a -fopt-info-vec-optimized -c loop.c
loop.c:7:3: optimized: loop vectorized using 16 byte vectors

/* AND WHEN IT REFUSES, IT USUALLY TELLS YOU WHY: */
$ gcc -O3 -fopt-info-vec-missed -c loop.c
loop.c:7:3: missed: couldn't vectorize loop
loop.c:8:12: missed: possible alias between data refs

/* "possible alias" is the commonest reason, and it is
   fixable: the compiler cannot prove the input and output
   arrays do not overlap, so it must assume they might.
   `restrict` (C chapter 04) is the promise that they do
   not:                                                     */

void scale(float * restrict out,
           const float * restrict in, size_t n)
{
        for (size_t i = 0; i < n; i++)
                out[i] = in[i] * 2.0f;
}
/* Now it vectorises. One keyword, four times the throughput,
   and no intrinsics written.                                */

/* INTRINSICS, when you do need them: */
#include <arm_neon.h>

void scale_neon(float *out, const float *in, size_t n)
{
        float32x4_t two = vdupq_n_f32(2.0f);

        for (size_t i = 0; i + 4 <= n; i += 4) {
                float32x4_t v = vld1q_f32(in + i);
                vst1q_f32(out + i, vmulq_f32(v, two));
        }
        /* AND THE TAIL. n is rarely a multiple of 4, and
           forgetting this is the single most common NEON
           bug - it silently leaves the last few elements
           unprocessed.                                     */
        for (size_t i = n & ~(size_t)3; i < n; i++)
                out[i] = in[i] * 2.0f;
}
Where SVE differs, in one paragraph

Advanced SIMD has a fixed 128-bit width baked into every instruction, which means code must be rewritten to exploit wider hardware. The Scalable Vector Extension removes that: the same binary runs on implementations with different vector lengths, because the length is read at run time and loops are controlled by predicate registers rather than by a trip count you computed. That also removes the tail problem above entirely. SVE uses its own register file (Z0–Z31, with the NEON V registers aliased into their low 128 bits) and its own enable bit alongside FPEN — so everything in this chapter about trapping, lazy switching and context size applies to it too, with a larger and implementation-dependent amount of state to save.
