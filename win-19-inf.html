INF files and installation

The INF tells Windows which hardware your driver serves, what to copy, and what registry state to create. It plays the role the device tree plays on Linux — describing this particular device — but applied once at install time rather than parsed at every boot.

Anatomy of an INF

An INF file is how Windows learns that your driver exists and which hardware it serves. It is a plain text file with a rigid structure, and most installation problems are INF problems rather than driver problems — so it repays reading carefully once.

;
; mydriver.inf - Vendor MyDevice
;

[Version]
Signature   = "$WINDOWS NT$"
Class       = System                  ; or a custom class
ClassGuid   = {4d36e97d-e325-11ce-bfc1-08002be10318}
Provider    = %ManufacturerName%
CatalogFile = mydriver.cat            ; the signature catalog
DriverVer   = 03/15/2026,1.0.0.0      ; DATE,VERSION
PnpLockdown = 1                       ; REQUIRED on modern
                                      ; Windows - protects the
                                      ; driver's files

[DestinationDirs]
DefaultDestDir = 13                   ; 13 = the DRIVER STORE.
                                      ; Not System32\drivers.

[SourceDisksNames]
1 = %DiskName%,,,""

[SourceDisksFiles]
mydriver.sys = 1,,

; ---- which hardware, on which architectures ----

[Manufacturer]
%ManufacturerName% = Standard,NTamd64,NTarm64

[Standard.NTamd64]
%MyDevice.DeviceDesc% = MyDevice_Install, PCI\VEN_1234&DEV_5678

[Standard.NTarm64]
%MyDevice.DeviceDesc% = MyDevice_Install, ACPI\VEN0001

; ---- what to install ----

[MyDevice_Install.NT]
CopyFiles = MyDevice_CopyFiles

[MyDevice_CopyFiles]
mydriver.sys

[MyDevice_Install.NT.Services]
AddService = mydriver, 0x00000002, MyDevice_Service
             ;         ^ SPSVCINST_ASSOCSERVICE - this is the
             ;           FUNCTION driver for the device

[MyDevice_Service]
DisplayName   = %MyDevice.SvcDesc%
ServiceType   = 1                     ; SERVICE_KERNEL_DRIVER
StartType     = 3                     ; SERVICE_DEMAND_START
ErrorControl  = 1                     ; SERVICE_ERROR_NORMAL
ServiceBinary = %13%\mydriver.sys

; ---- KMDF version binding (chapter 13) ----

[MyDevice_Install.NT.Wdf]
KmdfService = mydriver, MyDevice_wdfsect

[MyDevice_wdfsect]
KmdfLibraryVersion = 1.15

; ---- registry: device configuration ----

[MyDevice_Install.NT.HW]
AddReg = MyDevice_AddReg

[MyDevice_AddReg]
; per-device parameters your driver reads (chapter 01)
HKR,,FifoDepth,0x00010001,32          ; REG_DWORD 32
HKR,,SampleRate,0x00010001,48000
HKR,,DeviceMode,,"normal"             ; REG_SZ

; SECURITY: who may open this device (chapter 04)
HKR,,DeviceCharacteristics,0x10001,0x0100   ; SECURE_OPEN
HKR,,Security,,"D:P(A;;GA;;;SY)(A;;GA;;;BA)"

; MSI support (chapter 18)
HKR,"Interrupt Management",,0x00000010
HKR,"Interrupt Management\MessageSignaledInterruptProperties",,0x00000010
HKR,"Interrupt Management\MessageSignaledInterruptProperties",\
    MSISupported,0x00010001,1
HKR,"Interrupt Management\MessageSignaledInterruptProperties",\
    MessageNumberLimit,0x00010001,4

; ---- strings, localisable ----

[Strings]
ManufacturerName    = "Vendor Corporation"
DiskName            = "MyDevice Installation Disk"
MyDevice.DeviceDesc = "Vendor MyDevice Controller"
MyDevice.SvcDesc    = "Vendor MyDevice Driver"
Destination 13 is not optional

DefaultDestDir = 13 means the driver store, and it is required for a modern, universal INF. Copying to %windir%\System32\drivers (destination 12) directly is the legacy pattern; it breaks driver store integrity, prevents proper rollback, and fails certification. Let Windows manage the files.

Hardware IDs and ranking

The device reports identifiers; your INF claims some of them. When several drivers claim the same device, Windows ranks the matches and picks the most specific — which is why a generic driver does not displace your specialised one.

The PnP manager asks the bus driver for a list of IDs, most
specific first, and picks the BEST-RANKED matching INF.

  For a PCI device, the bus reports:

    HARDWARE IDs, most specific first:
      PCI\VEN_1234&DEV_5678&SUBSYS_9ABCDEF0&REV_01
      PCI\VEN_1234&DEV_5678&SUBSYS_9ABCDEF0
      PCI\VEN_1234&DEV_5678&REV_01
      PCI\VEN_1234&DEV_5678
    COMPATIBLE IDs, less specific:
      PCI\VEN_1234&DEV_5678&CC_010601
      PCI\VEN_1234&CC_0106
      PCI\CC_010601

  RANK, lower is better:
    0x0000  a signed INF matching a HARDWARE id
    0x1000  a signed INF matching a COMPATIBLE id
    0x8000+ unsigned equivalents

  So a driver matching the full subsystem ID beats a generic
  class driver - which is how a vendor driver replaces
  Microsoft's inbox one, and how a generic driver still works
  when no vendor driver is installed.

  THE PRACTICAL RULE: match the MOST SPECIFIC id your driver
  genuinely supports. Matching PCI\VEN_1234&DEV_5678 claims
  every board with that chip, including ones with different
  wiring - and if yours behaves differently, use the SUBSYS
  form.

  FIND THE IDs: Device Manager -> Properties -> Details ->
  "Hardware Ids". Copy them exactly; a single wrong character
  means Code 28 and no explanation.

Universal INFs

Modern Windows requires INFs to work across editions and form factors, which rules out a number of things older INFs did freely. Following the universal rules is not optional if you intend to ship.

; A "universal" (or "declarative") INF is required for
; Windows 10+ certification and for anything shipping on
; Windows on ARM, HoloLens or IoT Core. The rules:

; MUST:
;   · DefaultDestDir = 13 (the driver store)
;   · use only DECLARATIVE directives - no co-installers, no
;     RunOnce, no custom setup code
;   · AddReg only under HKR (relative) - no absolute HKLM
;     paths
;   · no [DDInstall.CoInstallers] section
;   · no calls out to external programs

; MUST NOT:
;   · RegisterDlls, UnregisterDlls
;   · AddService for a user-mode service that runs setup code
;   · absolute file paths
;   · legacy WDF co-installers (WdfCoInstaller*.dll) -
;     modern KMDF is inbox and needs none

; CHECK IT:
    InfVerif.exe /u mydriver.inf
    ; /u = universal check. Also:
    InfVerif.exe /v /w mydriver.inf

; The Windows Driver Kit's build already runs InfVerif in
; recent versions. Failures here block certification, so fix
; them as you write rather than at submission time.

; IF YOU NEED SETUP LOGIC - to install a user-mode service or
; a control panel applet - ship it as a separate DCH-compliant
; component package or a Windows app, not as a co-installer.
; That separation is the whole point of the universal model:
; the driver package is pure data.

Installing and testing

Installing a driver during development is not the same as shipping one. These are the commands to stage, install, update and remove a package on a test machine without leaving debris behind.

# --- Prepare a test machine (chapter 01) ---
    bcdedit /set testsigning on
    shutdown /r /t 0

# --- Install ---
    pnputil /add-driver mydriver.inf /install
    ; /install also updates matching devices

    ; or, the older tool, still useful for testing:
    devcon install mydriver.inf "PCI\VEN_1234&DEV_5678"

    ; for a device with no physical hardware - a software
    ; device or a test device:
    devcon install mydriver.inf "root\mydevice"

# --- Inspect ---
    pnputil /enum-drivers                ; every third-party
                                         ; driver in the store
    pnputil /enum-devices /connected
    devcon status "PCI\VEN_1234*"
    devcon driverfiles "PCI\VEN_1234*"

# --- Update and remove ---
    pnputil /add-driver mydriver.inf /install    ; upgrade
    devcon update mydriver.inf "PCI\VEN_1234&DEV_5678"

    pnputil /delete-driver oem12.inf /uninstall /force
    devcon remove "PCI\VEN_1234&DEV_5678"
    devcon rescan

# --- The development loop ---
    devcon disable "PCI\VEN_1234*"
    pnputil /delete-driver oem12.inf /uninstall
    ; rebuild
    pnputil /add-driver mydriver.inf /install
    devcon enable "PCI\VEN_1234*"

# Script this. You will run it several hundred times.

setupapi.dev.log

When an install goes wrong, the answer is almost always already written down. This log is the definitive record of what setup decided and why, and it is the file most people never think to open.

# THE FILE THAT ANSWERS "why did my driver not install":
    C:\Windows\INF\setupapi.dev.log

# It records every INF considered, its rank, and the decision:

  >>>  [Device Install (Hardware initiated) - PCI\VEN_1234&DEV_5678\...]
  >>>  Section start 2026/03/15 10:23:45.123
      dvi: Searching for hardware ID(s):
      dvi:     pci\ven_1234&dev_5678&subsys_9abcdef0&rev_01
      dvi:     pci\ven_1234&dev_5678&subsys_9abcdef0
      dvi:     pci\ven_1234&dev_5678&rev_01
      dvi:     pci\ven_1234&dev_5678
      dvi: Selected driver installs from section
           [MyDevice_Install] in 'c:\windows\system32\
           driverstore\filerepository\mydriver.inf_amd64_.../
           mydriver.inf'
      dvi: Class GUID of device changed to: {4d36e97d-...}
      dvi: Set selected driver complete.
      ...
      !!!  dvi: Device not started: Device has problem: 0x0a
           (CM_PROB_FAILED_START)

# READ IT TOP-DOWN:
#   "Searching for hardware ID(s)"  -> what the bus reported.
#      Compare against your INF character by character.
#   "Selected driver installs from" -> which INF won.
#      If it names someone else's, your rank was worse.
#   "No matching drivers found"     -> Code 28. Your IDs do
#      not match.
#   "Device has problem: 0x0a"      -> the INF matched and the
#      driver loaded, but START_DEVICE failed. Now it is a
#      driver bug, not an installation one (chapter 15).

# THIS DISTINCTION - install problem versus start problem - is
# the first thing to establish, and this log settles it in
# thirty seconds.

Reading your settings

The INF is also how per-device settings reach your driver: values written at install time appear under the device's own registry key, where your driver reads them at start-up.

/* What the INF's HKR entries wrote, read back at probe time
   (chapter 01):                                            */

NTSTATUS
MyReadDeviceParameters(_In_ WDFDEVICE Device)
{
        PMY_CONTEXT ctx = MyGetContext(Device);
        WDFKEY key;
        ULONG value;
        NTSTATUS status;

        DECLARE_CONST_UNICODE_STRING(fifoName, L"FifoDepth");
        DECLARE_CONST_UNICODE_STRING(rateName, L"SampleRate");

        PAGED_CODE();

        status = WdfDeviceOpenRegistryKey(Device,
                        PLUGPLAY_REGKEY_DEVICE,
                        KEY_READ,
                        WDF_NO_OBJECT_ATTRIBUTES,
                        &key);
        if (!NT_SUCCESS(status)) {
                /* NOT FATAL - use defaults */
                ctx->FifoDepth  = MY_DEFAULT_FIFO;
                ctx->SampleRate = MY_DEFAULT_RATE;
                return STATUS_SUCCESS;
        }

        status = WdfRegistryQueryULong(key, &fifoName, &value);
        ctx->FifoDepth = NT_SUCCESS(status) ? value
                                            : MY_DEFAULT_FIFO;

        status = WdfRegistryQueryULong(key, &rateName, &value);
        ctx->SampleRate = NT_SUCCESS(status) ? value
                                             : MY_DEFAULT_RATE;

        WdfRegistryClose(key);

        /* VALIDATE - the registry is user-writable by an
           administrator, so treat the values as input       */
        if (ctx->FifoDepth == 0 || ctx->FifoDepth > MY_MAX_FIFO)
                ctx->FifoDepth = MY_DEFAULT_FIFO;

        return STATUS_SUCCESS;
}

/* THE TWO KEYS:
     PLUGPLAY_REGKEY_DEVICE  the device's "Device Parameters"
                             subkey - per-instance settings.
                             THIS is where HKR from the .HW
                             section lands.
     PLUGPLAY_REGKEY_DRIVER  the driver's software key -
                             per-driver settings.

/* ALWAYS HAVE A DEFAULT. A missing value must not be fatal -
   the driver may be loaded on a device whose INF section did
   not run, or the value may have been deleted.          */
