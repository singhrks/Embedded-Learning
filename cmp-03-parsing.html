Grammars and parsing

Turning a flat stream of tokens into a tree that reflects the structure of the program. This is where operator precedence comes from, why C's declaration syntax is famously awkward, and how a compiler decides what your code means.

Grammars

A GRAMMAR is a set of rules that generate a language. Written
in BNF or EBNF:

   expr    -> expr '+' term
            | expr '-' term
            | term

   term    -> term '*' factor
            | term '/' factor
            | factor

   factor  -> NUMBER
            | IDENT
            | '(' expr ')'

  TERMINALS are tokens: '+', NUMBER, IDENT.
  NON-TERMINALS are the named rules: expr, term, factor.

  THE STRUCTURE ENCODES PRECEDENCE. Because `term` appears
  inside `expr`, multiplication binds tighter than addition:
  the only way to derive `1 + 2 * 3` is with `2 * 3` as one
  term. Precedence is not a table bolted on afterwards - it is
  the SHAPE of the grammar.

  AND ASSOCIATIVITY comes from the recursion side:

     expr -> expr '+' term      LEFT recursive  -> left assoc
                                (a+b)+c
     expr -> term '+' expr      RIGHT recursive -> right assoc
                                a+(b+c)

  So `a - b - c` means `(a-b)-c` because the grammar is
  left-recursive, and `a = b = c` means `a = (b = c)` because
  assignment's rule is right-recursive.

Ambiguity

/* A grammar is AMBIGUOUS if some input has more than one
   parse tree. The classic:                                */

        stmt -> 'if' '(' expr ')' stmt
              | 'if' '(' expr ')' stmt 'else' stmt
              | ...

        if (a) if (b) x(); else y();

/* Two readings:
     if (a) { if (b) x(); else y(); }     <-- the rule
     if (a) { if (b) x(); } else y();

   THE DANGLING ELSE. Every C-family language resolves it the
   same way: an `else` binds to the NEAREST unmatched `if`.
   That is a disambiguation rule imposed on top of an
   ambiguous grammar, not something the grammar itself
   expresses.

   AND IT IS WHY braces are worth writing even for
   single statements - not because the rule is unclear, but
   because the reader has to apply it.                     */

/* THE OTHER AMBIGUITY C HAS: the typedef problem
   (chapter 02).                                            */
        (foo)(bar);
/* a cast of `bar` to type `foo`, or a call of function `foo`
   with argument `bar`? Only the symbol table knows.      */

/* AND C++ ADDS the "most vexing parse": */
        Widget w(Gadget());
/* Declares a FUNCTION `w` taking a pointer-to-function
   returning Gadget, and returning Widget. Almost never what
   was meant. C++11's brace initialisation exists partly to
   escape it:                                              */
        Widget w{Gadget{}};

Recursive descent

/* One function per grammar rule. Readable, debuggable, gives
   excellent error messages - which is why GCC, Clang and most
   production compilers use it despite the theory favouring
   generated parsers.                                       */

static Node *parse_expr(Parser *p);

static Node *parse_primary(Parser *p)
{
        if (match(p, TOK_NUMBER))
                return make_number(previous(p));

        if (match(p, TOK_IDENT))
                return make_ident(previous(p));

        if (match(p, TOK_LPAREN)) {
                Node *e = parse_expr(p);
                expect(p, TOK_RPAREN, "expected ')'");
                return e;
        }

        error(p, "expected an expression");
        return NULL;
}

static Node *parse_unary(Parser *p)
{
        if (match(p, TOK_MINUS) || match(p, TOK_BANG)) {
                Token op = previous(p);
                Node *operand = parse_unary(p);   /* RIGHT
                                                     assoc  */
                return make_unary(op, operand);
        }
        return parse_primary(p);
}

static Node *parse_term(Parser *p)
{
        Node *left = parse_unary(p);

        /* LEFT associativity via a LOOP, not recursion -
           left-recursive grammar rules cannot be written
           directly in recursive descent because they would
           recurse forever.                                */
        while (match(p, TOK_STAR) || match(p, TOK_SLASH)) {
                Token op = previous(p);
                Node *right = parse_unary(p);
                left = make_binary(left, op, right);
        }
        return left;
}

static Node *parse_expr(Parser *p)
{
        Node *left = parse_term(p);

        while (match(p, TOK_PLUS) || match(p, TOK_MINUS)) {
                Token op = previous(p);
                Node *right = parse_term(p);
                left = make_binary(left, op, right);
        }
        return left;
}

/* THE PATTERN: each precedence level is a function that calls
   the NEXT TIGHTER level, then loops on its own operators.
   Add a level by adding a function in the chain.

   THE LEFT-RECURSION RULE is the one thing to remember:
   rewrite `expr -> expr op term` as a loop.              */

Precedence climbing

/* C has fifteen precedence levels. Fifteen near-identical
   functions is tedious and slow. Pratt parsing (precedence
   climbing) collapses them into one loop driven by a table. */

static int precedence_of(TokenKind k)
{
        switch (k) {
        case TOK_OROR:   return 1;
        case TOK_ANDAND: return 2;
        case TOK_OR:     return 3;
        case TOK_XOR:    return 4;
        case TOK_AND:    return 5;
        case TOK_EQEQ: case TOK_NEQ:  return 6;
        case TOK_LT: case TOK_GT:
        case TOK_LE: case TOK_GE:     return 7;
        case TOK_SHL: case TOK_SHR:   return 8;
        case TOK_PLUS: case TOK_MINUS: return 9;
        case TOK_STAR: case TOK_SLASH:
        case TOK_PERCENT:              return 10;
        default: return 0;      /* not a binary operator */
        }
}

static Node *parse_binary(Parser *p, int min_prec)
{
        Node *left = parse_unary(p);

        for (;;) {
                int prec = precedence_of(peek(p).kind);

                if (prec == 0 || prec < min_prec)
                        break;

                Token op = advance(p);

                /* LEFT associative: the right operand may only
                   contain operators of HIGHER precedence, so
                   pass prec + 1.
                   For a RIGHT associative operator, pass prec
                   instead.                                 */
                Node *right = parse_binary(p, prec + 1);

                left = make_binary(left, op, right);
        }
        return left;
}

        /* the whole expression grammar: */
        Node *e = parse_binary(p, 1);

/* ONE FUNCTION, one table. Adding an operator is a table
   entry. This is what most modern hand-written parsers use,
   and it is worth understanding because the `prec + 1` versus
   `prec` distinction is exactly where associativity lives. */
Precedence and associativity are grammar, not convention

When you wonder why a & b == c means a & (b == c) — a genuine C wart that has caused real bugs — the answer is that == sits at a higher precedence level than & in the grammar C inherited from B. It is not a rule someone can change; it is the shape of the language. Parenthesise bitwise operators.

LR parsing and generators

/* The other family: BOTTOM-UP. Instead of predicting which
   rule applies, shift tokens onto a stack and REDUCE when the
   top of the stack matches a rule's right-hand side.       */

   Parsing `1 + 2 * 3`:

     stack                   input          action
     (empty)                 1 + 2 * 3      shift
     1                       + 2 * 3        reduce factor
     factor                  + 2 * 3        reduce term
     term                    + 2 * 3        reduce expr
     expr                    + 2 * 3        shift
     expr +                  2 * 3          shift
     expr + 2                * 3            reduce factor,term
     expr + term             * 3            SHIFT (not reduce!)
     expr + term *           3              shift
     expr + term * 3         (end)          reduce factor
     expr + term * factor    (end)          reduce term
     expr + term             (end)          reduce expr
     expr                    (end)          ACCEPT

   THE INTERESTING STEP is `expr + term` with `*` next: the
   parser could reduce `expr + term` to `expr`, or shift the
   `*`. It shifts, because `*` binds tighter. That decision -
   SHIFT/REDUCE - is what a precedence declaration resolves in
   a generator.

/* yacc / bison: */
%left  '+' '-'
%left  '*' '/'          /* later = tighter */
%right UMINUS

%%
expr : expr '+' expr    { $$ = mk(ADD, $1, $3); }
     | expr '-' expr    { $$ = mk(SUB, $1, $3); }
     | expr '*' expr    { $$ = mk(MUL, $1, $3); }
     | expr '/' expr    { $$ = mk(DIV, $1, $3); }
     | '-' expr %prec UMINUS { $$ = mk(NEG, $2); }
     | '(' expr ')'     { $$ = $2; }
     | NUMBER           { $$ = mk_num($1); }
     ;

/* THE GRAMMAR IS AMBIGUOUS as written - and the %left
   declarations resolve every conflict. That is the appeal:
   the grammar reads like the language reference.

   THE CONFLICTS YOU WILL SEE:
     shift/reduce   usually benign; bison shifts by default,
                    which is correct for dangling-else
     reduce/reduce  ALWAYS a real ambiguity. Fix the grammar.

   Run `bison -Wcounterexamples` - it prints an actual input
   that triggers each conflict, which turns a cryptic warning
   into a concrete problem.                               */

/* WHY PRODUCTION COMPILERS STILL USE RECURSIVE DESCENT:
     · error messages: a hand-written parser knows what it
       expected and can suggest a fix
     · error RECOVERY: continuing sensibly after a mistake
     · context sensitivity: C's typedef problem
     · incremental re-parsing, for IDEs
   GCC moved from bison to recursive descent for C++ in 2004
   for exactly these reasons.                             */

C declaration syntax

/* C's declarations follow the "declaration mirrors use"
   principle, which makes complex ones hard to read.       */

        int    *p;              /* *p is an int             */
        int    a[10];           /* a[i] is an int           */
        int    f(void);         /* f() is an int            */
        int   *f(void);         /* *f() is an int -> f
                                   returns int*             */
        int  (*f)(void);        /* (*f)() is an int -> f is a
                                   pointer to function      */
        int   *a[10];           /* array of 10 int*         */
        int  (*a)[10];          /* pointer to array of 10    */
        int (*f[10])(void);     /* array of 10 function
                                   pointers                 */
        int (*(*f)(void))[10];  /* pointer to function
                                   returning pointer to
                                   array of 10 int          */

/* THE READING RULE - "spiral" or "right-left":
     1. start at the identifier
     2. go RIGHT while you can: [] means array, () means
        function
     3. then go LEFT: * means pointer
     4. parentheses override, innermost first             */

        int (*f[10])(void);
             ^ f
              [10]     -> array of 10
            *          -> pointers to
                (void) -> functions taking void
        int            -> returning int

/* THE TOOL: */
        cdecl> explain int (*(*f)(void))[10]
        declare f as pointer to function (void) returning
        pointer to array 10 of int

/* THE PRACTICAL ADVICE: use typedefs. */
        typedef int (*handler_fn)(void);
        handler_fn table[10];        /* obviously an array of
                                        10 handlers          */

/* WHY IT IS LIKE THIS: Dennis Ritchie chose it so that a
   declaration looks like the expression that uses the
   variable. It is internally consistent, and it composes
   badly - which is why every later language (Go, Rust, even
   C++'s trailing return types) spells declarations
   differently.                                             */

Error recovery

/* A compiler that stops at the first error is unusable. Good
   parsers RECOVER and keep going, without producing a
   cascade of bogus follow-on errors.                      */

/* PANIC MODE - the standard technique: */
static void synchronise(Parser *p)
{
        advance(p);

        while (!at_end(p)) {
                /* a semicolon ends a statement - resume there */
                if (previous(p).kind == TOK_SEMI)
                        return;

                /* or at a token that clearly STARTS something */
                switch (peek(p).kind) {
                case TOK_IF: case TOK_WHILE: case TOK_FOR:
                case TOK_RETURN: case TOK_STRUCT:
                case TOK_RBRACE:
                        return;
                default:
                        advance(p);
                }
        }
}

/* AND SUPPRESS CASCADES: after reporting an error, do not
   report another until the parser has successfully consumed
   something. Otherwise one missing brace produces two hundred
   messages and the real error scrolls off the screen.

/* GOOD ERROR MESSAGES, which Clang made the standard:
     · point at the exact column, with a caret
     · say what was EXPECTED, not just what was found
     · suggest a FIX when the situation is unambiguous
     · show the relevant note - "to match this '(' here"

     error: expected ';' after expression
        x = y + 1
                 ^
                 ;

   Compare "parse error before '}'" - which was normal in
   1998 and tells the reader almost nothing.             */
