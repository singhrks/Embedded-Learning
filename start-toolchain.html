Setting up your workbench

Every exercise and project on this site runs without buying hardware. This page gets you a cross-compiler, an emulated ARM machine, a kernel-development host and a Windows driver target — in about an hour.

What you are building

  YOUR MACHINE (any OS)
    │
    ├── a Linux environment            ← native, VM, or WSL2
    │     ├── native gcc + gdb          for C, C++, compiler exercises
    │     ├── aarch64 cross-compiler    for ARM assembly and bare metal
    │     ├── QEMU (system + user)      an emulated ARM64 machine
    │     └── kernel headers + build    for the Linux driver track
    │
    ├── a disposable Windows VM        ← only for the Windows track
    │     ├── test signing enabled
    │     └── kernel debugging to the host
    │
    └── optional: one real board       ← after you have done the emulated work

What the naming means

A cross-compiler is <arch>-<vendor>-<os>-<abi>-gcc. aarch64-linux-gnu- targets 64-bit ARM running Linux with glibc. aarch64-none-elf- targets 64-bit ARM with no OS — bare metal. arm-none-eabi- is the 32-bit Cortex-M standard. Picking the wrong one produces link errors about missing _start or a libc that should not exist.

An emulated ARM64 machine

QEMU's virt machine is a synthetic ARM64 platform with a GIC, PCIe, an SMMU and virtio devices. It is where you will run kernels, examine exception levels, and single-step boot code.

# boot a kernel you built (Linux track, chapter 16)
qemu-system-aarch64 \
  -M virt -cpu cortex-a57 -smp 2 -m 1024 \
  -kernel arch/arm64/boot/Image \
  -initrd rootfs.cpio.gz \
  -append "console=ttyAMA0 earlycon" \
  -nographic

# add an emulated SMMU (security track)
  -M virt,iommu=smmuv3

# start at EL3 with firmware, rather than jumping straight to the kernel
  -M virt,secure=on,virtualization=on

# wait for a debugger before executing the first instruction
  -s -S
# then, in another terminal:
aarch64-linux-gnu-gdb vmlinux -ex 'target remote :1234' -ex 'hbreak start_kernel'
-nographic and how to get out

-nographic puts the guest serial console on your terminal. To quit, press Ctrl-A then x. Ctrl-C goes to the guest, not to QEMU — this catches everyone once.

QEMU has a track of its own

The lines above are enough to get started. When you need to know what -M virt actually builds, how to wire a device onto a bus, why your guest has no network, or how to debug firmware and kernel together through one GDB session, the QEMU track covers it properly — including building a root filesystem, writing your own device model, and a ready-made command line for every track on this site.

Bare metal without an OS

For the ARM assembly chapters you want to run a handful of instructions with nothing underneath. This is the smallest possible setup.

boot.S — prints a character and halts, on QEMU virt
    .section .text
    .global _start
_start:
    ldr     x0, =0x09000000     // QEMU virt PL011 UART data register
    mov     w1, #'A'
    str     w1, [x0]            // memory-mapped I/O: one store = one character
1:  wfi                         // wait for interrupt = park the core
    b       1b
link.ld and the build
ENTRY(_start)
SECTIONS { . = 0x40000000; .text : { *(.text) } }
aarch64-none-elf-as boot.S -o boot.o        # or aarch64-linux-gnu-as
aarch64-none-elf-ld -T link.ld boot.o -o boot.elf
qemu-system-aarch64 -M virt -cpu cortex-a57 -nographic -kernel boot.elf
#   A

# inspect what you built
aarch64-none-elf-objdump -d boot.elf
aarch64-none-elf-readelf -S boot.elf

That is a complete embedded system: reset vector, memory-mapped I/O, and a parked core. Every chapter in the ARM track is an expansion of one of those three ideas.

A Windows driver target

Only needed for the Windows track. Two machines: a host with the tools, and a disposable VM that you will bug-check repeatedly.

  1. On the host: Visual Studio 2022 with "Desktop development with C++", then the Windows SDK, then the WDK — in that order, matching versions. The WDK adds the driver project templates.
  2. Install WinDbg: winget install Microsoft.WinDbg
  3. Create the test VM (Hyper-V, VMware or VirtualBox) and take a snapshot immediately. You will restore it often.
  4. On the VM, enable test signing and kernel debugging, then reboot.
on the TEST VM, elevated
bcdedit /set testsigning on
bcdedit /debug on
bcdedit /dbgsettings net hostip:192.168.1.10 port:50000 key:1.2.3.4
shutdown /r /t 0
on the HOST
windbg -k net:port=50000,key=1.2.3.4
.sympath srv*C:\symbols*https://msdl.microsoft.com/download/symbols;C:\myproject\x64\Debug
.reload /f
Test signing is a development-only setting

It puts a watermark on the desktop and weakens the machine's driver integrity guarantees. Enable it only on a disposable VM, never on a machine you rely on.

Ready when

  • aarch64-linux-gnu-gcc compiles a hello-world and qemu-aarch64-static runs it.
  • The bare-metal boot.S above prints A under qemu-system-aarch64.
  • ls /lib/modules/$(uname -r)/build shows a directory (Linux track only).
  • WinDbg connects to your test VM and .reload /f succeeds (Windows track only).
  • You can jump to the definition of kmalloc in a kernel tree in under five seconds.
