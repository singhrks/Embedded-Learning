Searching: binary search done correctly

Everyone knows the idea. Almost nobody writes it without an off-by-one on the first attempt. This chapter gives you one template you can trust, and the discipline that makes the boundary cases obvious rather than guessed.

The pattern

Nearly everyone knows binary search and nearly everyone states its precondition wrongly. Getting that statement right is what unlocks the half of the applications that have no sorted array anywhere in sight.

   HALVE THE SEARCH SPACE EVERY STEP. n candidates become 1
   in log2(n) steps: a million-element array is 20 steps.

   THE PRECONDITION IS NOT "SORTED". It is:

     THE ARRAY CAN BE SPLIT BY SOME PREDICATE INTO A FALSE
     REGION FOLLOWED BY A TRUE REGION.

     [ F, F, F, F, T, T, T, T ]
                   ^
                   the boundary — what you are looking for

   Sortedness is just the most common way to get that
   property. Once you see binary search as FINDING A
   BOUNDARY rather than FINDING A VALUE, the rotated-array
   and search-on-answer variants stop being separate tricks.

   THE BUG EVERYONE WRITES:

     mid = (lo + hi) / 2        // OVERFLOWS in C++/Java
                                // when lo+hi > 2^31
     mid = lo + (hi - lo) / 2   // correct everywhere

   In JavaScript numbers are doubles so overflow is not a
   practical concern, but write the safe form anyway — the
   interviewer is watching, and you will write C++ one day.

   THE THREE DECISIONS THAT DETERMINE CORRECTNESS:

     1. IS hi AN INDEX (n-1) OR A BOUND (n)?
     2. IS THE LOOP `lo <= hi` OR `lo < hi`?
     3. DO YOU MOVE TO mid OR mid±1?

   MIXING CONVENTIONS IS WHAT CAUSES INFINITE LOOPS AND
   MISSED ELEMENTS. Pick one and never deviate.

   THE TERMINATION ARGUMENT, worth being able to state:
   the interval must strictly shrink every iteration. If a
   branch can leave [lo, hi] unchanged, the loop hangs.
   With `lo < hi` and `mid = lo + (hi-lo)/2`, mid can equal
   lo but never hi, so `hi = mid` shrinks and `lo = mid+1`
   shrinks. That is why the halves are asymmetric.

Two templates, and only two

Rather than re-deriving the loop bounds under pressure, learn two templates and know which question each answers. Everything else in this chapter is one of these two with a different predicate.

/* ===== TEMPLATE A: EXACT MATCH =====
   "Is this value present, and where?"                    */
function find(a, target) {
    let lo = 0, hi = a.length - 1;          // hi is an INDEX
    while (lo <= hi) {                      // <= : lo==hi is
                                            //      still valid
        const mid = lo + ((hi - lo) >> 1);
        if (a[mid] === target) return mid;
        if (a[mid] < target) lo = mid + 1;  // EXCLUDE mid
        else                 hi = mid - 1;  // EXCLUDE mid
    }
    return -1;
}

/* ===== TEMPLATE B: FIND THE BOUNDARY =====
   "First index where predicate(i) is true."
   USE THIS ONE FOR EVERYTHING THAT IS NOT AN EXACT MATCH. */
function firstTrue(lo, hi, pred) {          // hi is a BOUND
    while (lo < hi) {                       // < : stop when
                                            //     they meet
        const mid = lo + ((hi - lo) >> 1);
        if (pred(mid)) hi = mid;            // KEEP mid — it
                                            // might be the
                                            // answer
        else           lo = mid + 1;        // mid is false,
                                            // discard it
    }
    return lo;          // == hi; equals `hi` if nothing is true
}

/* TEMPLATE B SOLVES ALL OF THESE, by changing only pred: */
    lowerBound(a, t)   // first index with a[i] >= t
      = firstTrue(0, a.length, i => a[i] >= t)
    upperBound(a, t)   // first index with a[i] >  t
      = firstTrue(0, a.length, i => a[i] >  t)
    countOf(a, t)      = upperBound(a,t) - lowerBound(a,t)
    insertPosition     = lowerBound(a, t)
    firstBadVersion    = firstTrue(1, n+1, v => isBad(v))

/* AND THE STANDARD LIBRARY EQUIVALENTS, worth knowing:
     C++     std::lower_bound / std::upper_bound
     Python  bisect.bisect_left / bisect.bisect_right
     Java    Arrays.binarySearch (returns -(insertion)-1
             when absent — read that signature carefully)

   THE DISCIPLINE THAT REMOVES THE BUGS:
     · state the INVARIANT before writing the loop:
       "the answer is always inside [lo, hi]"
     · every branch must SHRINK the interval
     · after the loop, say what lo and hi mean
     · TEST WITH: empty, one element, target smaller than
       everything, larger than everything, and duplicates  */

Problems

How it shows up

SymptomCause
Infinite loopA branch that does not shrink the interval — usually lo = mid with lo < hi
Misses the target at index 0 or n−1Mixed conventions: hi = n with lo <= hi
Overflow in C++/Java(lo + hi) / 2 — use lo + (hi - lo) / 2
Returns any duplicate, not the firstExact-match template returns on the first hit — use lower bound
Off by one on the insert positionConfusing lower bound with upper bound
Works on odd sizes, fails on evenMid rounding — check whether you need the upper mid
Fails on the rotated array at the pivotComparing against the wrong endpoint when deciding which half is sorted
Correct value, wrong index with duplicatesRotated search is not O(log n) when duplicates are allowed
