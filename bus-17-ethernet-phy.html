Ethernet, the MAC/PHY boundary and MDIO

Ethernet on a microcontroller is three separate things that must all work: a MAC inside the chip, a PHY outside it, and a management bus connecting them. Most bring-up problems are at one of the two boundaries, and knowing which one you are looking at is most of the diagnosis.

MAC and PHY

   +-------------------------------------------------+
   |  MICROCONTROLLER                                |
   |                                                 |
   |   TCP/IP stack (lwIP)                           |
   |        |                                        |
   |   +----+-----+                                  |
   |   |   MAC    |  frames, addresses, CRC, DMA     |
   |   +----+-----+                                  |
   |        |                                        |
   +--------|----------------+----------------------+
            | RMII/MII       | MDIO (2 wires)
            | (7 or 18 wires)|
   +--------+----------------+----------------------+
   |   PHY  (external chip)                         |
   |   encoding, analog drive, link negotiation     |
   +--------+---------------------------------------+
            |
        [magnetics]      transformer - isolation and
            |            common-mode rejection
          RJ45

   THE DIVISION OF LABOUR:

   MAC (in the MCU)     frame assembly, source/destination
                        addresses, CRC, collision handling,
                        DMA descriptors

   PHY (external)       4B/5B or similar line coding,
                        analog line driving, auto-
                        negotiation of speed and duplex,
                        link detection

   MDIO/MDC             a tiny two-wire management bus so
                        the MAC can read and write the PHY's
                        registers. Essentially I2C's job,
                        with its own protocol.

   MAGNETICS            galvanic isolation to 1.5 kV, and
                        common-mode rejection. NOT optional -
                        omitting them is a real design error
                        that works on a bench and destroys
                        ports in the field.

MII versus RMII

   MII    18 wires, 25 MHz clock, 4 bits per direction
   RMII    7 wires, 50 MHz clock, 2 bits per direction
   RGMII  12 wires, 125 MHz DDR, for gigabit

   RMII is what you will use on a microcontroller: half the
   pins for the same 100 Mbit/s.

   RMII SIGNALS:
     REF_CLK    50 MHz, SHARED by MAC and PHY
     TXD0, TXD1
     TX_EN
     RXD0, RXD1
     CRS_DV     carrier sense / data valid

   THE REF_CLK IS THE CLASSIC BRING-UP PROBLEM. Both ends
   must use the SAME 50 MHz clock, and there are two valid
   topologies:

     A) A 50 MHz oscillator feeds both the PHY and the MCU's
        REF_CLK input. Simple and robust.

     B) The MCU outputs 50 MHz on its MCO pin to the PHY,
        derived from its own PLL.

   Topology B requires that the MCU's clock configuration
   produce EXACTLY 50 MHz, and it must be running before the
   PHY is released from reset. Getting this wrong gives a
   PHY that never establishes a link, or a link that comes
   up and passes no traffic - and neither symptom points at
   the clock.

   MEASURE REF_CLK WITH A SCOPE during bring-up. It is one
   probe and it eliminates the most likely cause first.

MDIO: reading the PHY

/* MDIO is a 2-wire bus: MDC (clock, up to 2.5 MHz) and
   MDIO (bidirectional data). The MAC has a register pair
   that drives it for you.                                 */

static uint16_t phy_read(uint8_t phy_addr, uint8_t reg)
{
    ETH->MACMIIAR = (phy_addr << 11) | (reg << 6)
                  | ETH_MACMIIAR_CR_Div42 | ETH_MACMIIAR_MB;
    while (ETH->MACMIIAR & ETH_MACMIIAR_MB) { }   /* + timeout! */
    return (uint16_t) ETH->MACMIIDR;
}

/* THE STANDARD REGISTERS - IEEE 802.3 defines 0-15
   identically for every PHY ever made, which means this
   code works with any of them:                            */

/*  0  BMCR    control: reset, speed, duplex, autoneg
    1  BMSR    status: LINK UP, autoneg complete
    2  PHYIDR1 |  OUI and model - identifies the chip
    3  PHYIDR2 |
    4  ANAR    what we advertise
    5  ANLPAR  what the link partner advertises
   16+ vendor specific - including, annoyingly, the
       resolved speed and duplex on most PHYs           */

int phy_link_status(uint8_t addr, int *speed, int *full_duplex)
{
    /* BMSR bit 2 is LATCHING LOW: it reports "link has been
       down since the last read". Read it TWICE to get the
       current state - a genuine and very commonly missed
       detail.                                             */
    (void) phy_read(addr, 1);
    uint16_t bmsr = phy_read(addr, 1);

    if (!(bmsr & (1u << 2))) { return 0; }        /* down    */
    if (!(bmsr & (1u << 5))) { return 0; }        /* autoneg
                                                    not done */

    /* Resolved speed/duplex is vendor-specific. For the
       common LAN8742 it is register 31.                    */
    uint16_t sr = phy_read(addr, 31);
    *speed       = ((sr >> 2) & 3u) <= 1 ? 10 : 100;
    *full_duplex = (sr >> 4) & 1u;
    return 1;
}

/* FINDING THE PHY ADDRESS: it is set by strapping pins and
   is usually 0 or 1, but vendors vary. Scan for it - the
   same approach as an I2C scan (chapter 06):              */
int phy_scan(void)
{
    for (uint8_t a = 0; a < 32; a++) {
        uint16_t id = phy_read(a, 2);
        if (id != 0xFFFF && id != 0x0000) { return a; }
    }
    return -1;      /* nothing responded: check MDC, the
                       PHY's reset pin, and its supply     */
}
The bring-up order that isolates faults

Check them in this sequence and each step rules out a layer: 1. Is REF_CLK present and 50 MHz? 2. Does an MDIO scan find the PHY? 3. Does the PHY report link up and auto-negotiation complete? 4. Does the MAC receive any frames at all (check the receive descriptor count, not the IP stack)? 5. Does a broadcast ARP appear? Only then look at lwIP. Debugging from the TCP layer downward is why Ethernet bring-up has a reputation for taking days.

Descriptors and buffers

/* The MAC does not have registers you write frames into.
   It walks a RING of DESCRIPTORS in memory, each pointing
   at a buffer - the same pattern as any high-throughput
   DMA engine (mcu chapter 12).                            */

typedef struct {
    volatile uint32_t status;      /* OWN bit + flags      */
    uint32_t          ctrl_len;
    uint32_t          buf1_addr;
    uint32_t          next_desc;
} eth_desc_t;

#define DESC_OWN  (1u << 31)       /* 1 = DMA owns it      */

/* THE OWNERSHIP BIT IS THE WHOLE PROTOCOL:
     OWN = 1  the DMA engine may use this descriptor
     OWN = 0  software owns it

   RX: software clears OWN after processing, handing the
       buffer back. FORGET THIS AND RECEPTION STOPS after
       exactly as many frames as you have descriptors -
       a very recognisable symptom.

   TX: software sets OWN to hand the frame over.          */

static eth_desc_t rx_desc[4] __attribute__((aligned(4)));
static uint8_t    rx_buf[4][1524] __attribute__((aligned(4)));

void eth_rx_poll(void)
{
    eth_desc_t *d = &rx_desc[rx_index];
    if (d->status & DESC_OWN) { return; }      /* DMA still
                                                  owns it   */
    uint16_t len = (uint16_t)((d->status >> 16) & 0x3FFF);
    lwip_input(rx_buf[rx_index], len - 4u);    /* strip CRC  */

    d->status = DESC_OWN;                      /* GIVE IT BACK */
    rx_index = (rx_index + 1u) & 3u;
    ETH->DMARPDR = 0;                          /* poll demand */
}

/* MEMORY PLACEMENT MATTERS, exactly as in mcu chapter 12:
   - descriptors and buffers must be in RAM the Ethernet
     DMA can reach. On STM32F7/H7 the default SRAM often is
     NOT reachable - use a specific region and place it in
     the linker script.
   - on Cortex-M7, either mark that region non-cacheable in
     the MPU, or do explicit cache maintenance around every
     descriptor access. Getting this wrong produces an
     Ethernet port that works for a few seconds and then
     stops, which is a memorably frustrating bug.          */
