Memory ordering and happens-before

Your program's memory operations do not happen in the order you wrote them. The compiler reorders, the CPU reorders, and the cache system makes writes visible to different cores at different times. A memory model is the contract that says which of those reorderings you are allowed to notice — and happens-before is the only relation in it that matters.

Three layers of reordering

Your memory accesses do not happen in the order you wrote them, and three separate agents are entitled to rearrange them. Knowing which three is what makes the fixes later in the chapter make sense.

   YOU WROTE                 WHAT ACTUALLY RUNS

     a = 1;                    the COMPILER may:
     b = 2;                      reorder independent stores
     x = c;                      keep a value in a register
                                 delete a "redundant" load
                                 hoist a load out of a loop
                                 merge two stores into one

                              the CPU may:
                                execute out of order
                                speculate past a branch
                                buffer stores and drain later
                                prefetch loads early

                              the MEMORY SYSTEM may:
                                make your store visible to
                                core 2 before core 3 sees it

   NONE of this is a bug. All of it is required for
   performance, and all of it is invisible in single-threaded
   code because each layer preserves the illusion for the
   thread doing the work.

   Concurrency is where the illusion leaks - and the memory
   model is the exact specification of how much it may leak.

Happens-before is the whole model

Reasoning about concurrent code informally does not work. The formal relationship the languages define — what is guaranteed to be visible to whom, and when — is the only reliable basis, and it is simpler than its reputation.

   The C, C++, Rust, Java and Go memory models all say the
   same thing:

     If A happens-before B, then B sees A's effects.
     If neither happens-before the other AND one is a write,
     that is a DATA RACE - undefined behaviour.

   HOW YOU ESTABLISH HAPPENS-BEFORE - and there are only four
   ways:

   1. PROGRAM ORDER, within one thread.
        a = 1; b = 2;      -> a=1 happens-before b=2
        (as OBSERVED by that thread. Others may disagree.)

   2. RELEASE / ACQUIRE on the same variable.
        thread A:  ... writes ...
                   atomic_store(&flag, 1, release);
        thread B:  while (!atomic_load(&flag, acquire)) ;
                   ... reads ...
        -> everything before A's store happens-before
           everything after B's load. THIS IS THE ONE YOU USE.

   3. THREAD CREATION AND JOIN.
        everything before pthread_create happens-before the
        new thread's first instruction.
        everything in a thread happens-before pthread_join
        returns.

   4. MUTEX UNLOCK / LOCK on the same mutex.
        which is just case 2 with nicer syntax - unlock is a
        release, lock is an acquire.

   TRANSITIVITY: happens-before chains. If A hb B and B hb C
   then A hb C. That is what makes a mutex work across three
   threads.

   AND NOTHING ELSE ESTABLISHES IT. Not "thread B started
   later". Not "the sleep was long enough". Not "it is only
   one byte".

The six orderings

Every atomic operation takes an ordering argument, and the default is the strongest and most expensive. Choosing a weaker one correctly requires knowing precisely what each guarantees rather than what it sounds like.

/* From weakest to strongest. */

memory_order_relaxed
        Atomicity only. No ordering with anything.
        USE FOR: counters nobody makes decisions on, and the
        increment side of a refcount.
        DO NOT USE FOR: publishing anything.

memory_order_acquire        (loads, and RMW)
        Nothing after this in program order may be reordered
        BEFORE it. Pairs with a release on the same variable
        to give you everything the releaser wrote.
        THINK: "I am picking up the data."

memory_order_release        (stores, and RMW)
        Nothing before this in program order may be reordered
        AFTER it.
        THINK: "I am handing over the data."

memory_order_acq_rel        (RMW only)
        Both. For a read-modify-write that both consumes and
        publishes - a CAS in a lock-free stack, a refcount
        decrement.

memory_order_seq_cst        (the default)
        Acquire+release PLUS a single total order that ALL
        seq_cst operations agree on, across all variables.
        The only one that gives you the naive mental model.
        Costs a full barrier (DMB ISH on ARM, MFENCE-ish on
        x86 for stores).

memory_order_consume
        Intended as a cheaper acquire for pointer chasing.
        Every real compiler promotes it to acquire because
        the specification is unimplementable as written.
        DO NOT USE IT. It is being deprecated.
The default is seq_cst, and that is the right default

Write atomic_load(&x) and you get sequential consistency. It is the slowest ordering and the only one that behaves the way you expect. Start there. Weaken an ordering only when a profile shows the barrier costs you and you can write down the happens-before chain that still holds. Code littered with relaxed written by someone who could not articulate why is the least reviewable code in existence.

The publication pattern

The most common pattern in all of concurrent programming: fully initialise something, then make it visible. Getting this right is release-acquire, and getting it wrong is how other threads see a half-built object.

/* This is 90% of the memory ordering you will ever need. */

struct config *cfg;                     /* the payload         */
atomic_bool ready = false;

/* PUBLISHER */
void publish(void)
{
        struct config *c = malloc(sizeof *c);
        c->timeout = 30;                /* (1) */
        c->retries = 3;                 /* (2) */
        cfg = c;                        /* (3) */

        atomic_store_explicit(&ready, true, memory_order_release);
        /* RELEASE: (1),(2),(3) cannot move after this line, and
           are guaranteed visible to anyone who ACQUIRES `ready`
           and sees true.                                      */
}

/* CONSUMER */
void consume(void)
{
        if (atomic_load_explicit(&ready, memory_order_acquire)) {
                /* ACQUIRE: nothing below may move above. Having
                   seen `true`, we are guaranteed to see (1),(2)
                   and (3).                                     */
                use(cfg->timeout, cfg->retries);   /* safe      */
        }
}

/* WHAT GOES WRONG WITH relaxed

        atomic_store_explicit(&ready, true, memory_order_relaxed);

   The store to `ready` may become visible BEFORE the stores to
   c->timeout, c->retries, or even before `cfg` itself. The
   consumer sees ready==true, dereferences a pointer that is
   still null or points at uninitialised memory, and crashes.

   ON x86 this almost never happens, because TSO does not
   reorder store-store. ON ARM it happens immediately. That
   asymmetry is why this bug reaches production: it is written
   on a laptop and found on a phone.                          */

The one x86 also gets wrong

One reordering is fundamentally more expensive to prevent than the others, and it is the reason sequential consistency costs what it does. It is also the one behind the classic litmus test that surprises everyone.

/* Store-Load is reordered even on x86. This is Dekker's
   pattern, and it is the classic demonstration.            */

atomic_int x = 0, y = 0;
int r1, r2;

/* thread A */              /* thread B */
x = 1;                      y = 1;
r1 = y;                     r2 = x;

/* CAN r1 == 0 && r2 == 0 ?

   With sequential consistency: NO. Someone stored first, and
   the other thread must see it.

   In reality: YES, on every real CPU including x86.

   Both stores sit in their core's store buffer. Both loads
   read from L1, which has not seen the other core's store
   yet. Both read 0.

   This is the ONLY reordering x86 permits, and it is enough
   to break hand-rolled synchronisation. It is why
   seq_cst STORES are expensive on x86 - the compiler must
   emit an MFENCE or use XCHG to drain the store buffer.

   THE FIX: use seq_cst on both (the default), or insert
   atomic_thread_fence(memory_order_seq_cst) between the store
   and the load in each thread.                              */

What it compiles to

Ultimately these orderings become instructions. Looking at what the compiler actually emitted on your target turns an abstract argument about ordering into something you can verify.

/* ARM64 - the orderings map to distinct instructions, which
   is why the choice actually costs something.              */

  relaxed load        LDR   x0, [x1]
  acquire load        LDAR  x0, [x1]          ; load-acquire
  seq_cst load        LDAR  x0, [x1]          ; same

  relaxed store       STR   x0, [x1]
  release store       STLR  x0, [x1]          ; store-release
  seq_cst store       STLR  x0, [x1]          ; same
                      (with -moutline-atomics or older targets
                       you may instead see DMB ISH + STR)

  fence(acquire)      DMB ISHLD
  fence(release)      DMB ISH
  fence(seq_cst)      DMB ISH

  relaxed fetch_add   LDXR/ADD/STXR loop, or LDADD  (LSE)
  acq_rel fetch_add   LDAXR/ADD/STLXR,   or LDADDAL (LSE)

/* x86-64 - almost everything is free, which is the trap. */

  relaxed load        MOV
  acquire load        MOV                     ; free!
  seq_cst load        MOV                     ; free!

  relaxed store       MOV
  release store       MOV                     ; free!
  seq_cst store       XCHG  (or MOV + MFENCE) ; NOT free

/* Read that x86 column again. Acquire and release cost
   NOTHING on x86 - so code that omits them behaves
   identically. The bug is not merely hidden; it is
   unobservable, on that machine, for ever.                 */
Test on weak hardware, or you have not tested

An arm64 machine — a Raspberry Pi, an Apple Silicon Mac, a Graviton instance — will surface ordering bugs that x86 physically cannot exhibit. If your product ships on ARM and your CI is x86-only, your CI is not testing the memory model at all. Add one weak-ordered runner; it is the highest-value CI change a concurrent codebase can make.
