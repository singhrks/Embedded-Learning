GPIO and pinmux from the register level

A pin is the only part of a microcontroller that touches the physical world, and it is massively multiplexed: one ball of solder, a dozen possible functions, and a set of electrical properties you must configure or regret. This is the simplest peripheral and the one worth understanding exactly.

What is behind a pin

                          VDD
                           |
                        [pull-up]  <- PUPDR
                           |
     alt.fn out --+        |        +---> IDR (input data)
     ODR ---------+-->[ P-MOS ]     |
                  |    output    +--+---> alt.fn in
                  |    driver    |  |
     MODER -------+-->[ N-MOS ]--+--+---> ADC (analog)
                           |         [Schmitt trigger]
                        [pull-down] <- PUPDR
                           |
                          GND
                           |
                        === PIN ===

   FIVE independent decisions per pin:

   MODER    input / output / alternate function / analog
   OTYPER   push-pull (drives both rails) or open-drain
            (drives low only; needs a pull-up for high)
   OSPEEDR  slew rate - how fast the edge is
   PUPDR    internal pull-up, pull-down, or neither
   AFR      WHICH alternate function, when MODER says AF

   Getting MODER right and the other four wrong is the
   normal failure mode: the pin half-works.

Configuring a pin properly

/* PA5 as a push-pull output - the LED case. */

RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;
(void) RCC->AHB1ENR;                  /* read back (ch 09)  */

/* Two bits per pin: clear then set. Never just OR - the
   reset value for some pins is not 00, notably the SWD
   pins PA13/PA14 which come up as alternate function.     */
GPIOA->MODER   &= ~(3u << (5 * 2));
GPIOA->MODER   |=  (1u << (5 * 2));   /* 01 = output       */

GPIOA->OTYPER  &= ~(1u << 5);         /* 0 = push-pull     */

GPIOA->OSPEEDR &= ~(3u << (5 * 2));   /* 00 = low speed    */
                                       /* for an LED this is */
                                       /* the RIGHT choice   */
GPIOA->PUPDR   &= ~(3u << (5 * 2));   /* 00 = no pull      */

/* PA9 as USART1_TX - an alternate function. */
GPIOA->MODER   &= ~(3u << (9 * 2));
GPIOA->MODER   |=  (2u << (9 * 2));   /* 10 = alt function */
GPIOA->OSPEEDR |=  (3u << (9 * 2));   /* fast edges for a  */
                                       /* real signal        */
/* AFR[0] covers pins 0-7, AFR[1] covers 8-15, 4 bits each. */
GPIOA->AFR[1]  &= ~(0xFu << ((9 - 8) * 4));
GPIOA->AFR[1]  |=  (7u   << ((9 - 8) * 4));  /* AF7=USART1 */

/* WHICH AF number? Not guessable. It is a table in the
   DATASHEET (not the reference manual) called "Alternate
   function mapping". Every pin has a different mapping, and
   a given peripheral appears on only a few pins. This table
   is what pin-planning tools automate.                     */
Slew rate is an EMC decision, not a performance one

A fast edge radiates. Setting every pin to maximum speed "to be safe" is how boards fail radiated-emissions testing, and the fix at that stage costs a respin or a pile of series resistors. Use the slowest setting that meets the timing requirement: low speed for LEDs and slow logic, high speed only for a clock or a bus running near its limit. Chapter bus-19 covers the physics.

BSRR: setting pins without a race

/* The obvious way is wrong in the presence of interrupts: */

GPIOA->ODR |=  (1u << 5);      /* read, modify, write      */

/* If an interrupt fires between the read and the write and
   changes another pin in the same port, that change is lost
   when this write completes. A classic lost-update race,
   and it produces LEDs that occasionally stay on and relays
   that occasionally do not fire.                           */

/* BSRR is a WRITE-ONLY register with set bits in the low
   half and reset bits in the high half. One store, no read,
   no race - and it affects only the bits you name.         */

GPIOA->BSRR = (1u << 5);           /* set PA5              */
GPIOA->BSRR = (1u << (5 + 16));    /* clear PA5            */
GPIOA->BSRR = (1u << 5) | (1u << (6 + 16));  /* both, in
                                      the same instant     */

/* If both the set and reset bit for one pin are written,
   SET WINS. Documented, and occasionally useful.

   This is the same set/clear idiom as the NVIC's ISER/ICER
   (chapter 07). Recognising it is a general skill: when a
   peripheral offers a write-1-to-act register, use it and
   delete your critical section.                            */

/* Reading is unambiguous - IDR always reflects the PIN,
   even when the pin is configured as an output. That is
   how you detect a short: drive high, read low.            */
if (!(GPIOA->IDR & (1u << 5))) {
    fault_log(FAULT_LED_SHORTED);
}

Push-pull versus open-drain

   PUSH-PULL                     OPEN-DRAIN

     VDD                           VDD
      |                             |
   [P-MOS]  drives HIGH          [external pull-up]
      |                             |
      +---- PIN                     +---- PIN
      |                             |
   [N-MOS]  drives LOW           [N-MOS]  drives LOW only
      |                             |
     GND                           GND

   Two push-pull outputs tied     Any number of open-drain
   together, one high and one     outputs can share a wire.
   low, are a SHORT. Amps flow.   Whoever pulls low wins;
                                  otherwise the pull-up
                                  makes it high.

   USE PUSH-PULL FOR: LEDs, chip selects, anything you
   drive alone. Faster edges, no external parts.

   USE OPEN-DRAIN FOR:
     - I2C, always. The protocol REQUIRES it: clock
       stretching and arbitration both depend on any device
       being able to hold the line low (chapter bus-07).
     - Shared interrupt lines from several sensors.
     - Level shifting to a lower-voltage part, with the
       pull-up to the LOWER rail.
     - Any bus where two masters might drive at once.

   The internal pull-ups (~40 kO) are too weak for I2C at
   400 kHz. Fit external 2.2-4.7 kO resistors; relying on
   the internal ones gives you rounded edges and marginal
   timing that fails on long traces or hot days.

Pins as interrupt sources

/* EXTI: external interrupt lines. The mux is per PIN NUMBER
   across ports, and that constraint bites.                 */

/* Route PC13 to EXTI line 13. */
RCC->APB2ENR |= RCC_APB2ENR_SYSCFGEN;
SYSCFG->EXTICR[13 / 4] &= ~(0xFu << ((13 % 4) * 4));
SYSCFG->EXTICR[13 / 4] |=  (2u   << ((13 % 4) * 4));  /* port C */

EXTI->IMR  |=  (1u << 13);      /* unmask                   */
EXTI->FTSR |=  (1u << 13);      /* falling edge             */
EXTI->RTSR &= ~(1u << 13);      /* not rising               */

NVIC_SetPriority(EXTI15_10_IRQn, 10);
NVIC_EnableIRQ(EXTI15_10_IRQn);

/* THE CONSTRAINT: EXTI line N serves pin N of exactly ONE
   port. You can use PA0 or PB0 or PC0 as an interrupt - but
   not two of them at once. Discovering this after the PCB
   is made is a genuinely common and expensive mistake, and
   it is why pin assignment happens before layout.

   Note also that lines 5-9 and 10-15 SHARE a single NVIC
   vector, so the handler must demultiplex:                 */

void EXTI15_10_IRQHandler(void)
{
    if (EXTI->PR & (1u << 13)) {
        EXTI->PR = (1u << 13);   /* write 1 to CLEAR */
        button_pressed();
    }
    if (EXTI->PR & (1u << 14)) {
        EXTI->PR = (1u << 14);
        lid_switch_changed();
    }
}

/* "Write 1 to clear" is a third register idiom, alongside
   read-modify-write and set/clear pairs. Writing 0 does
   nothing; writing ~0 clears everything, which is a
   convenient bug when you meant to clear one flag.         */
Debouncing belongs in software, and not in the ISR

A mechanical switch bounces for 1–20 ms, producing dozens of edges. An EXTI handler that increments a counter will see all of them. The standard fix is to have the ISR disable its own EXTI line and start a one-shot timer; the timer's handler samples the pin once, acts, and re-enables EXTI. That gives you exactly one event per press, costs no polling, and keeps the ISR short. A for-loop delay inside the handler "works" and blocks every other interrupt for 20 ms — an eternity.
