Concurrency and shared state in a design

Every variable touched by two contexts is a design decision, and in a design round you should be able to point at each one and say who writes it, who reads it, and what protects it. Most concurrency bugs are not subtle races — they are shared state nobody wrote down.

Name the contexts first

   "Two threads" is not enough detail. On an embedded
   system the contexts have different capabilities, and
   the right mechanism depends on which pair you have.

   TASK <-> TASK        both can block. Mutexes, queues,
                        semaphores all available.

   ISR -> TASK          the ISR CANNOT block. Only
                        ISR-safe, non-blocking primitives.
                        The common case.

   ISR <-> ISR          different priorities can preempt
                        each other. Same priority cannot.
                        Only interrupt masking or atomics.

   CPU <-> DMA          DMA is not a thread and obeys no
                        lock. Ownership must be by
                        protocol, plus barriers and cache
                        maintenance.

   CORE <-> CORE        real parallelism. Now you need
                        actual atomics and barriers, not
                        just interrupt masking - disabling
                        interrupts on one core does NOT
                        stop the other.

   THE LAST ONE CATCHES PEOPLE. A critical section
   implemented as "disable interrupts" is correct on a
   single core and useless on a dual-core part. If the
   design has two cores, every such critical section is a
   bug.

Write the sharing table

FOR EVERY PIECE OF SHARED STATE, three columns. Producing
this table in a design round is worth more than describing
any individual mechanism.

  state              writer      reader     protection
  ------------------ ----------- ---------- ---------------
  rx_ring[]          UART ISR    comms task SPSC, no lock
  rx_head            UART ISR    comms task published after
                                            data; single
                                            writer
  rx_tail            comms task  UART ISR   single writer
  adc_sample         ADC ISR     ctrl task  volatile u32,
                                            atomic on ARM
  setpoint           comms task  ctrl task  double buffer
                                            + atomic index
  motor_state        ctrl task   all        mutex, PI on
  error_counters     several     diag task  atomic add
  config             comms task  all        RCU-style: swap
                                            a pointer
  dma_buffer[]       DMA         proc task  ownership flag
                                            + cache maint

THE PATTERNS, from cheapest to most expensive:

  1. DON'T SHARE. Pass ownership through a queue. The
     data belongs to exactly one context at a time and
     there is nothing to protect. This is the right answer
     far more often than people assume.

  2. SINGLE WRITER, ALIGNED WORD. On ARM a naturally
     aligned 32-bit load or store is atomic, so one writer
     and any number of readers needs only volatile.

  3. SPSC RING BUFFER. One producer, one consumer, power-
     of-two size, publish the index AFTER the data. No
     lock at all.

  4. DOUBLE BUFFER + ATOMIC INDEX SWAP. Writer fills the
     inactive buffer, then atomically swaps which is
     active. Readers always see a consistent snapshot.

  5. ATOMIC READ-MODIFY-WRITE. Counters, flags, simple
     state machines.

  6. INTERRUPT MASKING. Short critical sections, and the
     only option when an ISR is involved. Single core only.

  7. MUTEX WITH PRIORITY INHERITANCE. Task-to-task
     exclusion over anything non-trivial.

REACH DOWN THE LIST, NOT UP. A design that uses a mutex
for something a queue would have solved has added a
blocking point and an inversion risk for nothing.
The strongest answer to "how do you handle shared state?"

"I try not to have any." Passing ownership through a queue — the producer fills a buffer, hands it over, and never touches it again — eliminates the class of bug rather than managing it. Every lock you do not have is a deadlock you cannot have, a priority inversion you cannot suffer, and a critical section that cannot delay an interrupt. Reaching for a mutex should be the fallback, not the default, and saying so demonstrates that you understand what locks actually cost.

The failure modes, and how to design them out

   RACE CONDITION
     Two contexts touch the same state without ordering.
     DESIGN OUT: the sharing table. If every row has a
     protection column, you have at least considered each.

   DEADLOCK
     Two contexts each hold what the other wants.
     DESIGN OUT: a global LOCK ORDER, documented, and never
     taken out of order. Two locks is where this starts;
     three is where it becomes likely.

   PRIORITY INVERSION
     A high-priority task blocked behind a low one, with a
     medium one preventing progress. Unbounded.
     DESIGN OUT: mutexes (not semaphores) with inheritance
     enabled; short critical sections; and no lock shared
     between a real-time task and a best-effort one.

   LOST WAKEUP
     A signal arrives between the check and the wait.
     DESIGN OUT: use the kernel primitive rather than
     rolling your own; on bare metal, the disable-then-WFI
     pattern (WFI wakes on a pending interrupt even when
     PRIMASK masks it).

   TORN READ
     A 64-bit value read as two 32-bit halves while it
     changes.
     DESIGN OUT: keep shared values word-sized, or use a
     seqlock, or a critical section.

   ABA / STALE POINTER
     A pointer swapped and freed while another context
     still holds it.
     DESIGN OUT: never free while a reader might hold it -
     use a pool with generation counts, or defer
     reclamation.

   THE ONE THAT ACTUALLY BITES MOST OFTEN in embedded
   systems is not any of these - it is an ISR touching a
   structure that a task is halfway through updating,
   because nobody wrote down that the structure was
   shared.

Questions

An ISR and a task share a data structure. Walk me through your options.Mid

First: the ISR cannot block, so mutexes are off the table entirely — there is no owner to record and nothing to switch to.

Then, cheapest first. If it is a single aligned word with one writer, a volatile read/write is atomic on ARM and needs nothing else. If it is a stream, use a single-producer/single-consumer ring buffer: the ISR writes data then publishes the head index; the task reads the tail. No lock, and correct because each index has exactly one writer. If it is a structure that must be updated as a unit, either double-buffer it (the ISR fills the inactive one and swaps an index atomically, so the task always sees a consistent snapshot) or have the task disable interrupts briefly around its access — acceptable for a few instructions, and the only option that works both ways. If the RTOS provides a queue, use it: xQueueSendFromISR copies the data, handles the wake, and removes the problem.

And the ISR must signal the task that there is work — with the yield-from-ISR call, or the woken task waits until the next tick for no reason.

Listening forRuling out mutexes immediately with the reason, and reaching for a queue rather than inventing a lock.
Why is a single-producer, single-consumer ring buffer safe without a lock?Mid

Three properties together. Each index has exactly one writer — the producer owns head, the consumer owns tail — so neither is ever the subject of a lost update. Both indices are single aligned words, so reads and writes are atomic on ARM. The producer publishes the head index after writing the data, so a consumer that sees a new head is guaranteed the corresponding byte is already stored.

The third point is the one with a caveat: it relies on the writes not being reordered. On Cortex-M's largely in-order model that holds; on a weakly-ordered multicore system you need a release barrier before publishing the index and an acquire barrier after reading it — which is exactly what C11's atomic_store_explicit(..., memory_order_release) expresses.

Also: use a power-of-two size so the wrap is a mask rather than a modulo, and treat "full" as next == tail, which wastes one slot but avoids needing a separate count that both sides would write.

Listening forAll three properties, and the ordering caveat for multicore.
How do you prevent deadlock in a design with several locks?Mid

Define a global lock ordering and never violate it. Number the locks, document the order, and require that any code holding lock N may only acquire locks numbered above N. This makes a cycle impossible by construction, which is stronger than testing for it.

Supporting practices: hold as few locks at once as possible — ideally one; never call out of a subsystem while holding its lock, because you cannot know what the callee will take; use timeouts on acquisition so a deadlock becomes a detectable, reportable error rather than a silent hang; and prefer designs that do not need multiple locks at all — passing ownership through a queue avoids the problem entirely.

For verification: Linux's lockdep (CONFIG_PROVE_LOCKING) proves the ordering at runtime and reports violations even when no deadlock actually occurred, which catches the bug before it manifests. It is worth enabling for driver work.

Listening forLock ordering as a design rule rather than a testing problem, and "never call out while holding a lock".
A design has two cores. What changes about your critical sections?Senior

Disabling interrupts stops preemption on your core and does nothing to the other one, so every critical section implemented that way becomes a bug. You now need real atomics — load-exclusive/store-exclusive or LSE instructions — and real barriers, because the two cores' views of memory can genuinely differ.

You also need to think about which memory is shared and how it is mapped: shared data must be in a region marked as inner-shareable so the coherency protocol covers it, and if one core has a cache the other does not snoop, you need explicit maintenance.

The other change is architectural. Two cores are often used asymmetrically — a Cortex-A running Linux and a Cortex-M in the same package, for instance — in which case the right pattern is usually not shared locks at all but a message-passing interface over a mailbox and a shared ring buffer, with ownership passed explicitly. That avoids needing a coherency story for arbitrary data structures and confines the hard part to one well-tested channel.

Listening forThe interrupt-disabling failure specifically, and message passing as the preferred architecture rather than shared-memory locking.
How does a task safely read a value that a DMA controller is writing?Senior

DMA is not a thread and obeys no lock, so the protection has to be a protocol: at any moment, the buffer belongs either to the DMA or to the CPU, and ownership transfers only at defined points.

The standard shape is double buffering: DMA fills buffer A while the task processes buffer B; at the transfer-complete interrupt they swap. The task never touches the buffer DMA owns. For a circular receive, the half-transfer and transfer-complete interrupts define the same boundary.

Two mechanisms on top of the protocol. Barriers: the completion flag must not become visible before the data writes, so a DMB sits between them; and volatile is required so the compiler actually re-reads the flag. Cache maintenance on parts with a D-cache: clean before a memory-to-peripheral transfer so the DMA sees your data, invalidate after a peripheral-to-memory transfer so the CPU does not read stale lines — with buffers aligned and padded to the cache line size, or the invalidate will discard a neighbouring variable's cached value.

And the buffer must be in DMA-reachable memory and never on the stack.

Listening for"Ownership protocol, not a lock" as the framing, then barriers and cache maintenance as the mechanisms.
Where would you use a double buffer rather than a lock?Mid

Whenever a reader needs a consistent snapshot of a multi-field structure and must not block — which describes most real-time readers. The writer fills the inactive buffer at its leisure, then atomically swaps an index; the reader reads whichever index is currently active and always sees a complete, coherent set of values.

Concrete cases: a control loop reading a setpoint structure updated by a comms task; a display reading a frame of sensor values; a task reading calibration data that is occasionally recomputed.

What it buys over a mutex: the reader never blocks, so a high-priority task cannot be delayed by a low-priority writer — the priority inversion is designed out rather than mitigated. The cost is double the memory and the fact that the reader may get slightly stale data, which for a control loop is almost always preferable to being late.

The detail that matters: the index swap must be genuinely atomic, and the reader must latch the index once at the start of its read rather than re-reading it, or it can read across a swap.

Listening for"The reader never blocks" as the motivation, and latching the index once.
What is a lost wakeup and how do you avoid it?Mid

A signal that arrives between the moment you test a condition and the moment you go to sleep, so the sleep never ends. The classic bare-metal form:

while (!work_pending) {
    __WFI();      /* interrupt fires HERE: sets the flag,
                     returns - then we sleep anyway */
}

The symptom is a device that hangs roughly once a day and never reproduces on the bench.

The fix on Cortex-M relies on an architectural guarantee: WFI wakes on a pending interrupt even when PRIMASK masks it. So you disable interrupts, test the condition, and WFI inside the masked region — the interrupt cannot run to set the flag, and if it is already pending the WFI returns immediately.

With an RTOS you avoid rolling your own: a semaphore, queue or task notification handles the check-and-sleep atomically inside the kernel, which is exactly why those primitives exist.

Two tasks both need the SPI bus for different devices. How do you arrange that?Mid

A bus mutex held across the whole transaction — from asserting chip select to deasserting it — because the bus configuration (mode, clock rate) and the chip select are shared state that must not change mid-transfer. Each device carries its own configuration, and the transaction function reconfigures the controller, drives CS, transfers, waits for the shift register to empty, releases CS, and gives the mutex back.

The mutex must have priority inheritance and a timeout — never wait forever on a bus, because a wedged device then blocks a task permanently.

The alternative that scales better: a single bus-owner task with a request queue. Other tasks post a transaction descriptor and wait for completion; only the owner touches the hardware. That serialises access by construction, makes DMA easy to use, and removes the mutex entirely — which is exactly what Linux's SPI subsystem does with its message queue and per-device spi_device structs.

The failure without either: two tasks interleave, the mode changes mid-transaction, two chip selects go low at once, and you get corruption that appears only when both devices are used concurrently — that is, only in the integrated system and never in a unit test.

Listening forHolding the lock across the whole transaction including CS, and the bus-owner-task alternative.
How do you test concurrency in an embedded system?Senior

Deliberately, because ordinary testing exercises one interleaving out of millions and the bug lives in a rare one.

Make races more likely: run at higher event rates than the product will see; add randomised delays at context-switch points; run on a faster or slower clock to change the timing; deliberately fire interrupts during critical sections.

Use tooling that reasons rather than samples: ThreadSanitizer on a host build (if the code is portable enough to run there — which is a good reason to write it that way); lockdep in kernel code, which proves lock ordering rather than testing it; static analysers that check for missing locks.

Instrument for evidence: record a trace of task switches, ISR entries and lock acquisitions — SystemView or Tracealyzer — so that when something does go wrong you can see the interleaving rather than guessing. This is also how you see priority inversion rather than inferring it.

And design so there is less to test: the sharing table, ownership passing, single-writer patterns. The most reliable way to pass a concurrency test is to have less concurrency.

Listening forAmplification and tracing as concrete techniques, and the closing point that design beats testing here.
A field unit hangs once every few weeks with no crash log. Where do you look?Senior

The absence of a crash log is itself information: the CPU is probably still executing, so this is a hang rather than a fault. That points at a deadlock, a lost wakeup, or a task blocked forever on something that never arrives.

What I would want in place beforehand — and would add if not: a watchdog fed only from the place that proves real progress (a watchdog fed by a timer would keep a deadlocked system alive indefinitely); a record of which task was running and which were blocked, written to .noinit before the watchdog reset; the reset cause read at boot and reported; and per-task counters so a stalled task is visible as one whose counter stopped.

Given those, the watchdog reset dumps the task states and the answer is usually immediate: a task blocked on a queue that no longer receives, or two tasks each holding what the other wants.

The systematic causes to check in the code: any portMAX_DELAY without a recovery path — a lost signal then blocks a task permanently; any acquisition without a timeout; and any lock taken in two different orders anywhere.

Listening forInferring "hang not fault" from the missing log, and the watchdog petting rule as the thing that makes the diagnosis possible.
