The block layer: bio, request_queue and blk-mq

Chapter 42 ended with writeback pushing dirty pages down to "the underlying storage" without saying how they actually get there. This chapter is that path: the layer between a filesystem and a physical disk that turns page-cache-sized I/O into requests a device can execute, and that gives a spinning disk, an SSD and an NVMe drive the same interface to sit behind.

The bio: one I/O operation, described structurally

Between a filesystem and a storage driver, an I/O request travels as a data structure rather than a function call. Understanding what that structure contains explains how one request can gather data from pages scattered all over memory.

   A struct bio (BLOCK I/O) DESCRIBES ONE I/O OPERATION AS
   DATA, not as a function call: which device, which
   direction (read or write), which sectors, and a list of
   the actual memory pages involved. Filesystems and the page
   cache build bios and hand them to the block layer; they
   never talk to a disk driver directly.

     struct bio {
        bi_bdev      -> which block device
        bi_opf        -> REQ_OP_READ / REQ_OP_WRITE / ...
        bi_iter       -> current position: sector, size
        bi_io_vec[]   -> a list of (page, offset, length) -
                         the ACTUAL PHYSICAL MEMORY this I/O
                         reads into or writes from, which may
                         be SEVERAL NON-CONTIGUOUS PAGES for
                         one logical I/O (this is a "vector"
                         of I/O the same way readv()/writev()
                         are - a single bio can gather or
                         scatter across many pages, which is
                         exactly what makes a page-cache-
                         backed write of many separate pages
                         into one efficient bio possible)
        bi_end_io     -> a callback invoked when the I/O
                         COMPLETES - block I/O is fundamentally
                         ASYNCHRONOUS; nothing blocks waiting
                         for a bio synchronously except by
                         explicitly choosing to
     }

From a bio to a completed I/O: the pipeline

A request does not go straight from the filesystem to the device. It passes through several stages that combine it with other pending requests, order them sensibly, and hand them to the hardware in parallel — each of which exists to compensate for a real limitation of storage devices.

   FILESYSTEM / PAGE CACHE
        |  builds a bio: "write these 4 pages to sector N"
        v
   THE REQUEST QUEUE  (per block device)
        |  MERGING: a bio adjacent to one already queued gets
        |  COMBINED into a single, larger request - writing
        |  sectors 100-107 right after queuing sectors 108-115
        |  becomes ONE 100-115 request, because one larger
        |  operation is cheaper for the device than two small
        |  ones, especially on a spinning disk where seek time
        |  dominates
        |
        |  SCHEDULING: multiple pending requests are ordered
        |  by an I/O SCHEDULER (below) before being issued
        v
   blk-mq  (multi-queue block layer)
        |  DISPATCHES requests onto PER-CPU SOFTWARE QUEUES,
        |  which map onto the device's OWN HARDWARE QUEUES -
        |  modern NVMe devices expose dozens to thousands of
        |  independent hardware queues specifically so that
        |  many CPUs can submit I/O in parallel with NO shared
        |  lock between them, the single biggest reason blk-mq
        |  replaced the older single-queue block layer: a
        |  single queue with one lock became the actual
        |  bottleneck once devices got fast enough that the
        |  LOCK, not the storage medium, was the slowest part
        |  of the path
        v
   THE DEVICE DRIVER submits the request to hardware and,
   later, an INTERRUPT (chapter 16) signals completion
        |
        v
   bi_end_io() RUNS, and whoever issued the original bio
   (the filesystem, direct I/O, page-cache writeback) is
   notified the operation is done.

I/O schedulers: reordering requests on purpose

SchedulerOptimises forBest fit
noneNo reordering — issue in submission orderNVMe, where the device's own many hardware queues already parallelise better than software reordering could help
mq-deadlineBounding worst-case latency — every request gets a deadline it must be serviced byGeneral-purpose SSDs and spinning disks; the sensible embedded default
bfqFairness between processes issuing I/O, and interactive responsiveness Desktop-like workloads where one background I/O hog should not starve interactive reads
kyberLatency targets, tuned automatically at runtimeFast SSDs under mixed read/write load

The right scheduler follows directly from what the underlying device actually needs help with: a spinning disk benefits enormously from reordering requests to minimise seek distance, which is the entire reason I/O schedulers were invented in the first place, while an NVMe SSD has no seek penalty at all and enough parallel hardware queues that software reordering usually only adds latency without buying anything back — which is exactly why none is the typical default there.

# See and change the scheduler for a device:
cat /sys/block/nvme0n1/queue/scheduler
    [none] mq-deadline
cat /sys/block/sda/queue/scheduler
    mq-deadline [bfq] none

echo mq-deadline > /sys/block/sda/queue/scheduler

# Merging and queue depth, live:
cat /sys/block/sda/queue/nr_requests
cat /sys/block/sda/queue/max_sectors_kb

A minimal block driver's shape

Most engineers never write a block driver, but seeing its shape completes the picture: it is the same driver-core pattern as everything else in this track, with one callback that turns a queued request into hardware activity.

/* A block driver's central job is implementing ONE callback
   that turns a REQUEST (already merged and scheduled) into
   actual hardware activity: */

static blk_status_t my_queue_rq(struct blk_mq_hw_ctx *hctx,
                                 const struct blk_mq_queue_data *bd)
{
        struct request *rq = bd->rq;

        blk_mq_start_request(rq);

        /* Walk the request's bios/segments, program the
           hardware's DMA descriptors (chapter 30's DMA API)
           to move data to/from the addresses described, kick
           the device off.                                   */

        return BLK_STS_OK;
        /* Completion, later, from an interrupt handler:
                blk_mq_end_request(rq, BLK_STS_OK);           */
}

static const struct blk_mq_ops my_mq_ops = {
        .queue_rq = my_queue_rq,
};

/* Registration, roughly: */
disk = blk_mq_alloc_disk(&tag_set, NULL);
disk->fops = &my_block_fops;      /* open/release/ioctl, the
                                     block-device equivalent of
                                     chapter 22's char device
                                     file_operations            */
set_capacity(disk, nr_sectors);
device_add_disk(dev, disk, NULL);
Why most driver authors never write this directly

A genuinely new block driver is rare compared with character and platform drivers, because most storage hardware (NVMe, SCSI, MMC/SD, USB mass storage) already has a generic upstream driver that talks to the block layer correctly, and a new piece of hardware usually just needs a thin transport-specific layer underneath one of those, not a fresh blk_mq_ops implementation from scratch. Understanding this pipeline matters anyway, because every filesystem operation, every fsync() from the previous chapter, and every I/O-latency number you will ever be asked to explain passes through exactly this path.

How it shows up

SymptomCause
Many small, adjacent writes show up as fewer, larger I/Os in iostatExpected — request-queue merging combined them before dispatch
Switching an NVMe drive's scheduler from none to mq-deadline hurts throughputExpected — software reordering adds overhead a device with many hardware queues does not need
A background dd makes interactive disk access sluggishThe current scheduler is not prioritising fairness — try bfq
I/O completion happens long after the driver's submit function returnsExpected — block I/O is asynchronous; completion arrives later via bi_end_io / blk_mq_end_request from an interrupt
A new storage chip needs only a small driver, not a full block driverLikely correct — it can probably sit under an existing generic driver (NVMe, SCSI, MMC) instead of implementing blk_mq_ops directly
Per-CPU I/O submission scales well on a fast NVMe device but not on an older SATA SSDExpected — the benefit of multi-queue dispatch is bounded by how many hardware queues the device itself actually exposes
