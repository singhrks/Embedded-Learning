Box, Rc, RefCell and interior mutability

When the ownership rules from chapters 02 and 03 are too rigid for the design, these types relax them — some at compile time, some by moving the check to run time. Knowing which is which is the whole chapter.

Box

The simplest smart pointer, and the one that makes recursive types and trait objects possible. On embedded targets its requirement is the interesting part.

    let b = Box::new(42);       // one value, on the heap
    let v = *b;                 // deref

/* THE SAME THING AS std::unique_ptr (C++ chapter 10): one
   owner, freed on drop, zero overhead beyond the allocation
   itself. sizeof(Box<T>) == sizeof(&T).

/* THE THREE REASONS TO USE IT:

/* 1. A RECURSIVE TYPE, which otherwise has infinite size: */
    enum List { Cons(i32, Box<List>), Nil }
    // without Box: "recursive type has infinite size"

/* 2. A TRAIT OBJECT that must be owned: */
    let sensors: Vec<Box<dyn Sensor>> = vec![
        Box::new(Thermistor::new(0)),
        Box::new(Photodiode::new(1)),
    ];

/* 3. MOVING A LARGE VALUE cheaply - moving a Box moves one
      pointer, not the payload.

/* AND THE CONVERSIONS that matter for FFI (chapter 15): */
    let raw: *mut T = Box::into_raw(b);  // give up ownership
    let b = unsafe { Box::from_raw(raw) };// take it back
/* into_raw LEAKS unless something later calls from_raw. That
   is exactly how you hand a Rust-allocated object to C and
   get it back.                                            */

Interior mutability

This is how you mutate through a shared reference without breaking the borrow rule — by moving the check from compile time to run time, which is a trade with consequences worth understanding.

   THE PROBLEM: sometimes you need to mutate through a shared
   reference. A cache, a refcount, a peripheral behind a
   global.

   THE RULE (chapter 03) says &T means no mutation. Interior
   mutability types are the sanctioned exception: they
   provide `fn set(&self, ...)` and uphold the aliasing
   guarantee some other way.

     UnsafeCell<T>   the PRIMITIVE. The only legal way to get
                     &mut from &. Everything below is built
                     on it.
     Cell<T>         get/set by VALUE for Copy types. No
                     references handed out, so no aliasing
                     question. Zero cost.
     RefCell<T>      hands out &T and &mut T, with the
                     borrow rule checked AT RUN TIME.
                     PANICS on violation.
     Mutex<T>        the same, across threads, by blocking.
     RwLock<T>       many readers or one writer, across
                     threads.
     Atomic*         lock-free single values.

   THE PATTERN: the compile-time check is moved to run time,
   or to a lock. You pay either a panic risk or a
   synchronisation cost, and you get flexibility.

   THE CHOICE, in one line:
     Copy value, single thread    -> Cell
     needs references, single
       thread                     -> RefCell
     across threads               -> Mutex, RwLock or Atomic
     performance-critical single
       value                      -> Atomic
/* --- Cell: no borrows, so no possible failure --- */
    use core::cell::Cell;

    struct Counter { count: Cell<u32> }

    impl Counter {
        fn increment(&self) {           // note: &self, not
                                        // &mut self
            self.count.set(self.count.get() + 1);
        }
    }
/* Cell::get COPIES the value out; set replaces it. No
   reference to the interior ever exists, so there is nothing
   to alias. Zero cost - it compiles to a plain load and
   store.

/* --- RefCell: borrows, checked at run time --- */
    use core::cell::RefCell;

    let c = RefCell::new(vec![1, 2, 3]);

    {
        let r = c.borrow();             // Ref<Vec<i32>>
        println!("{}", r.len());
    }                                   // released here

    c.borrow_mut().push(4);             // RefMut

    let a = c.borrow();
    let b = c.borrow_mut();             // PANIC: already
                                        // borrowed

    // the non-panicking forms:
    if let Ok(mut m) = c.try_borrow_mut() { m.push(5); }

/* RefCell KEEPS A COUNTER of active borrows and panics if
   the rule is violated. So the guarantee is preserved - you
   just find out at run time instead of compile time.

   COST: one usize per RefCell, and a check per borrow.

   ON EMBEDDED: a panic in a RefCell is a bug that reaches
   the field. Prefer designs where the compiler can check;
   use try_borrow when a runtime failure is genuinely
   possible.                                              */
UnsafeCell is the only legal route

Obtaining &mut T from &T by any other means — a pointer cast, transmute — is undefined behaviour, because the compiler emits noalias on shared references and will optimise on that assumption. UnsafeCell is the marker that tells it not to. Every safe interior-mutability type wraps one, and any unsafe code of your own that mutates through a shared reference must too.

Rc and Arc

Reference counting for when a single owner genuinely will not do. The two variants differ in one respect, and choosing wrongly is either a performance cost or a compile error.

    use std::rc::Rc;            // single-threaded
    use std::sync::Arc;         // Atomic - across threads

    let a = Rc::new(vec![1, 2, 3]);
    let b = Rc::clone(&a);      // refcount 2 - NOT a deep
                                // copy
    println!("{}", Rc::strong_count(&a));   // 2

/* SHARED OWNERSHIP: the value lives until the last Rc drops.
   The same as std::shared_ptr (C++ chapter 10), with the
   same caveats:

     · Rc is NOT thread-safe (no atomics) - and the compiler
       enforces that, because Rc is not Send (chapter 16).
       Arc is, and pays for atomic refcounting.
     · CYCLES LEAK. Two Rcs pointing at each other never
       reach zero.
     · Rc gives you &T only. For mutation you need
       Rc<RefCell<T>> - which is the shape most "I need
       shared mutable state" designs end up in, and which
       should prompt you to reconsider the design.

/* BREAKING A CYCLE with Weak: */
    use std::rc::{Rc, Weak};

    struct Node {
        children: RefCell<Vec<Rc<Node>>>,
        parent: RefCell<Weak<Node>>,    // NOT Rc
    }

    if let Some(p) = node.parent.borrow().upgrade() {
        // Weak::upgrade returns Option<Rc<T>> - None if the
        // target is gone
    }

/* ON EMBEDDED: Rc and Arc need `alloc`, and the atomic
   refcounting in Arc is a real cost. Ask first whether:
     · one clear owner plus borrowed references works
     · a static arena with indices works (chapter 04)
     · the sharing is actually needed
   Reaching for Rc<RefCell<T>> is usually a sign the
   ownership design has not been decided.               */

Globals on embedded

Global mutable state is the normal way to write firmware and the thing Rust makes hardest. These are the patterns that resolve that tension safely.

/* THE PROBLEM: a peripheral is a global, and an interrupt
   handler needs to reach it. `static mut` is unsafe to
   touch, and as of Rust 2024 taking a reference to one is a
   hard error.                                            */

/* --- THE OLD WAY, now forbidden --- */
    static mut UART: Option<Uart> = None;
    unsafe { UART.as_mut().unwrap().write(b"x"); }
                                // undefined behaviour if an
                                // interrupt races

/* --- 1. Mutex<RefCell<T>> with a critical section --- */
    use cortex_m::interrupt::{self, Mutex};
    use core::cell::RefCell;

    static UART: Mutex<RefCell<Option<Uart>>> =
        Mutex::new(RefCell::new(None));

    fn init(uart: Uart) {
        interrupt::free(|cs| {
            UART.borrow(cs).replace(Some(uart));
        });
    }

    #[interrupt]
    fn USART1() {
        interrupt::free(|cs| {
            if let Some(u) = UART.borrow(cs).borrow_mut()
                                 .as_mut() {
                u.handle_irq();
            }
        });
    }

/* `cortex_m::interrupt::Mutex` is NOT a blocking mutex - it
   requires a CriticalSection token, proving interrupts are
   disabled. So access is sound by construction, and the
   token costs nothing at run time. This is the standard
   pattern in the embedded ecosystem.

/* --- 2. StaticCell: initialise once, get &'static mut --- */
    use static_cell::StaticCell;

    static BUFFER: StaticCell<[u8; 1024]> = StaticCell::new();

    let buf: &'static mut [u8; 1024] = BUFFER.init([0; 1024]);
/* Panics if called twice. Gives you a 'static mutable
   reference without a heap - which is exactly what a DMA
   buffer or a network stack needs (chapter 20).

/* --- 3. Atomics, for simple flags and counters --- */
    use core::sync::atomic::{AtomicU32, AtomicBool, Ordering};

    static COUNT: AtomicU32 = AtomicU32::new(0);
    static READY: AtomicBool = AtomicBool::new(false);

    #[interrupt]
    fn TIMER() {
        COUNT.fetch_add(1, Ordering::Relaxed);
        READY.store(true, Ordering::Release);
    }

    fn main_loop() {
        if READY.load(Ordering::Acquire) {
            // sees everything the ISR wrote before the store
            // (chapter 16)
        }
    }
/* No critical section, no panic risk, no allocation. For a
   flag or a counter this is strictly the best option.

/* --- 4. RTIC, which removes the question entirely --- */
    #[app(device = stm32f4xx_hal::pac)]
    mod app {
        #[shared] struct Shared { uart: Uart }
        #[task(binds = USART1, shared = [uart])]
        fn on_uart(mut cx: on_uart::Context) {
            cx.shared.uart.lock(|u| u.handle_irq());
        }
    }
/* RTIC computes the required critical sections at COMPILE
   time from the priority ceiling, so the lock is often free
   (chapter 20).                                          */

Deref and custom smart pointers

The trait that makes smart pointers feel like the thing they point at, and the coercion rules that follow from it.

    use core::ops::{Deref, DerefMut};

    struct Guard<'a, T> { inner: &'a mut T }

    impl<T> Deref for Guard<'_, T> {
        type Target = T;
        fn deref(&self) -> &T { self.inner }
    }
    impl<T> DerefMut for Guard<'_, T> {
        fn deref_mut(&mut self) -> &mut T { self.inner }
    }

    impl<T> Drop for Guard<'_, T> {
        fn drop(&mut self) { release_hardware(); }
    }

    let g = acquire();          // returns a Guard
    g.method();                 // DEREF COERCION - calls
                                // T::method
                                // released when g drops

/* DEREF COERCION is why `&String` works where `&str` is
   wanted, and `&Vec<T>` where `&[T]` is - and why you should
   take the slice types in parameters (chapter 03).

/* THE RULE FOR IMPLEMENTING Deref: only for types that ARE a
   pointer or a guard. Using it to fake inheritance produces
   confusing method resolution, exactly as in C++
   (C++ chapter 06).

/* THE GUARD PATTERN IS THE USEFUL ONE, and it is how Mutex
   works: lock() returns a guard, the guard derefs to the
   data, and dropping it unlocks. RAII plus Deref gives you
   an API that cannot be used without holding the lock.  */

Choosing

Five types that overlap enough to be confusing and differ enough to matter. Working down from what you actually need is faster than reasoning about what each one offers.

NeedUseCost
One owner, heapBox<T>The allocation
Mutate a Copy value through &Cell<T>None
Mutate anything through &, one threadRefCell<T>A counter, and a panic risk
Shared ownership, one threadRc<T>Refcount, cycles leak
Shared ownership, threadsArc<T>Atomic refcount
Shared mutable, threadsArc<Mutex<T>>Allocation + locking
A flag or counter, ISR-sharedAtomic*Near zero
A peripheral, ISR-sharedMutex<RefCell<T>> + critical sectionInterrupt latency
