Access control: designing a policy

Knowing how to program an XPU is the easy half. The hard half is deciding what the policy should be — and doing it as engineering rather than as a guess, on a chip with sixty bus masters and a memory map nobody has ever written down in one place.

The method

Writing an access-control policy is a design exercise before it is a programming one, and doing it ad hoc produces a policy that is both permissive and unmaintainable. This is a method that scales.

   1. ENUMERATE every bus master. All of them.
   2. ENUMERATE every protected resource.
   3. Build the ACCESS MATRIX: who needs what, and why.
   4. Group masters into DOMAINS to fit the hardware's limits.
   5. Lay out the MEMORY MAP to match the region granularity.
   6. Express the policy as DATA, in one place.
   7. GENERATE the firmware tables and the device tree from it.
   8. TEST the negative cases.
   9. REVIEW, with people who did not write it.

  Steps 1 and 2 take a week and feel like clerical work. They
  are the whole job. Every failure of a real policy traces back
  to a master nobody listed or a resource nobody classified.

Step 1: enumerate the masters

Step one is knowing every master on the SoC that can issue transactions. That list is longer than most teams expect and is where the surprises live.

/* "Every block that can issue a bus transaction." Far more
   than people expect. On a mid-range application SoC:      */

   CPU cluster(s)          often several, with different IDs
                           per core or per cluster
   GPU                     usually several masters: shader,
                           command processor, ...
   display controller      one per pipe
   camera ISP              plus its own DMA
   video encoder/decoder
   audio DSP               and its DMA

                           dedicated port

   crypto engine

   trace funnel writing to memory (ETR)

/* FOR EACH ONE, record:

     what is its master ID, or ID range?
     is the ID fixed, or programmable by that master?
     is it behind an SMMU? which one? which StreamIDs?
     is it behind an XPU? which one?
     what security state does it issue in? fixed or dynamic?
     who controls its firmware, and how is that firmware
       verified?
     when is it released from reset, relative to the XPU
       configuration?

/* SOURCES: the SoC TRM's master ID table, the interconnect
   configuration, the SMMU StreamID mapping, the DT, and -
   this one matters - ASKING THE SoC INTEGRATION TEAM. The
   documentation is routinely incomplete. Blocks get added
   late.

/* AND THEN VERIFY EMPIRICALLY: program a deny-all XPU, run the
   system, and collect the faults. Every master that faults is
   one you now know about. Masters that never appear are either
   idle or not covered - and telling those two apart is the
   point of the exercise.                                    */
The master you did not list is your vulnerability

A debug block that can write DRAM. A power-management microcontroller running unsigned vendor firmware with full bus access. A PCIe endpoint that arrives with the user's plug-in card. An audio DSP whose firmware is loaded from the normal-world filesystem. Each of these has been the path around an otherwise sound TrustZone design on shipping hardware. The policy is defined by its completeness, not by how carefully you wrote the entries you thought of.

Step 3: the access matrix

With both lists, the policy is a grid — and filling it in explicitly is what surfaces the permissions nobody could justify but everybody assumed were needed.

# One row per resource, one column per domain, and a REASON

                                                            nothing reads it

# READ THE EMPTY CELLS. They are the security properties:
#   modem cannot see the framebuffer
#   media cannot see modem memory
#   nothing but secure code reads the fuses
#   the AP cannot read protected video back
#
# Each empty cell should survive the question "what breaks if
# we fill this in?" - and if the answer is "nothing", it is a
# property worth keeping.
Three principles, applied concretely
  • Least privilege. Start from all-deny and add only what a demonstrated failure requires. Never start from all-allow and subtract.
  • Directionality. Read and write are separate questions. A display controller reads; it never writes. A video encoder writes a protected buffer; nothing reads it back. Half the value of a good matrix is in the cells that say r or w rather than rw.
  • Justify every allow. A cell without a reason is a cell nobody can safely remove later, which means it will still be there in five years' worth of derived products.

Step 5: laying out memory to fit

Turning the matrix into hardware configuration is mechanical once the matrix exists, which is precisely why the matrix is worth producing first.

The XPU has 16 regions and a 1 MB granule. Your matrix has 24
distinct resource classes. Something has to give - and the
right thing to give is the ADDRESS MAP, decided early.

  BAD LAYOUT - interleaved, needs a region per buffer:

     0x8000_0000  kernel
     0x8010_0000  modem shared
     0x8020_0000  kernel
     0x8030_0000  sensor
     0x8040_0000  kernel
     ...                      -> 20 regions, 4 KB apart,
                                 impossible to express

  GOOD LAYOUT - grouped by DOMAIN, aligned to the granule:

     0x8000_0000  +----------------------+
                  | AP DRAM              |  1 region
                  | 768 MB               |
     0xB000_0000  +----------------------+
                  | AP/modem shared 4 MB |  1 region
     0xB040_0000  +----------------------+
                  | AP/sensor shared 1 MB|  1 region
     0xB050_0000  +----------------------+
                  | (gap - denied)       |
     0xC000_0000  +----------------------+
                  | modem private 128 MB |  1 region
     0xC800_0000  +----------------------+
                  | protected media 64 MB|  1 region
     0xCC00_0000  +----------------------+
                  | secure world 32 MB   |  1 region
     0xCE00_0000  +----------------------+

  Six regions instead of twenty. And note the GAPS: address
  space that matches no region and is therefore denied to
  everyone. Gaps are free - use them as guard bands between
  domains, so an off-by-a-little DMA lands in a fault rather
  than in the neighbour's memory.

  THE RULE: group by WHO MAY TOUCH IT, not by what it is for.
  All AP memory contiguous, all modem memory contiguous, each
  sharing window its own aligned block.

  This decision is made at SoC memory-map definition time,
  which is roughly 18 months before anyone writes the XPU
  driver. Bring the security requirements to that meeting or
  you will spend the project working around its output.

Steps 6 and 7: one source of truth

A policy with a single overly-permissive entry can undo the rest of it. These are the patterns that quietly do that.

# The same policy must appear in at least four places:
#   the firmware's XPU tables
#   the firmware's TZASC/TZC configuration
#   the device tree's reserved-memory nodes
#   the SMMU stream table setup
# and often a fifth: the modem or DSP's own linker script.
#
# Hand-maintaining four copies guarantees they will drift. So
# write the policy ONCE, as data, and generate.

# platform_policy.yaml
domains:
  secure:  { masters: [cpu_s, crypto] }
  ap:      { masters: [cpu_ns, dma0, dma1, usb, ufs] }
  modem:   { masters: [mdsp, mdma] }
  media:   { masters: [gpu, display, venc, vdec] }
  sensor:  { masters: [shub] }

regions:
  - name: ns_dram
    base: 0x80000000
    size: 0x30000000
    access: { ap: rw, media: rw, secure: rw }
    dt_node: false                 # the kernel owns it
  - name: ap_modem_shm
    base: 0xB0000000
    size: 0x00400000
    access: { ap: rw, modem: rw, secure: rw }
    dt_node: { name: modem_shm, no_map: false }
  - name: modem_priv
    base: 0xC0000000
    size: 0x08000000
    access: { modem: rw, secure: rw }
    dt_node: { name: modem_mem, no_map: true }
  - name: secure_dram
    base: 0xCE000000
    size: 0x02000000
    access: { secure: rw }
    dt_node: { name: secure_mem, no_map: true }
    lock: true

# Then one generator emits:
#   xpu_policy.c        the firmware table
#   tzc_regions.c       the TZASC configuration
#   reserved-memory.dtsi  the DT nodes
#   policy_test.c       the negative-test list
#   policy.md           a human-readable matrix for review
#
# Now a change is made in ONE place, and the four artifacts
# cannot disagree. This is the single highest-value thing in
# this chapter, and it is a two-hundred-line Python script.

Step 8: test the negatives

A policy is only real if denials actually happen. Testing that requires deliberately attempting forbidden accesses, which is a step most projects skip.

/* Positive tests - "the driver works" - happen anyway. They
   tell you nothing about the policy, because a policy of
   "allow everything" passes all of them.

   NEGATIVE tests are the only ones that measure isolation. */

struct denial_test {
        const char *name;
        uint32_t    master;
        uint64_t    addr;
        bool        write;
};

static const struct denial_test must_fail[] = {
  { "AP reads secure DRAM",        M_CPU_NS, SECURE_DRAM,   false },
  { "AP writes secure DRAM",       M_CPU_NS, SECURE_DRAM,   true  },
  { "AP reads modem private",      M_CPU_NS, MODEM_PRIV,    false },
  { "modem reads AP DRAM",         M_MODEM,  NS_DRAM,       false },
  { "modem reads framebuffer",     M_MODEM,  FRAMEBUFFER,   false },
  { "media writes secure DRAM",    M_GPU,    SECURE_DRAM,   true  },
  { "AP reads protected video",    M_CPU_NS, PROT_VIDEO,    false },
  { "AP writes fuse controller",   M_CPU_NS, FUSE_CTRL,     true  },
  { "AP writes XPU config",        M_CPU_NS, XPU_BASE,      true  },
  { "sensor reads AP DRAM",        M_SHUB,   NS_DRAM,       false },
  { "display writes DRAM",         M_DISPLAY,NS_DRAM,       true  },
  { "unlisted addr, any master",   M_CPU_NS, UNMAPPED_GAP,  false },
};

/* HOW to issue a transaction as a non-CPU master: program that
   master's own DMA to do a small transfer, and check for the
   error. Most subsystems have a test or loopback mode; if not,
   the smallest real operation will do. This is genuine work to
   build, and it is the part that separates a policy you HAVE
   from a policy you KNOW.                                   */

/* RUN THESE:
     · in CI, on real silicon, every night
     · on the FINAL lifecycle state, not a dev part
     · after every firmware change
     · after every DT change
     · and specifically after any "temporary" bring-up widening

   A denial test that starts passing when it should fail is the
   highest-priority bug in the build. Wire it to fail the
   pipeline.                                                */

Step 9: review

What a reviewer should be able to ask
  • "Show me the master list, and how you know it is complete."
  • "Which masters are not behind any SMMU or XPU, and why is that acceptable?"
  • "Point at the reason for this rw. What breaks if it becomes r?"
  • "Which regions are unlocked at runtime, who can change them, and what stops the normal world asking?"
  • "Where is the window between reset and enforcement, and which masters run inside it?"
  • "Show me the negative test for this empty cell, and the CI run where it passed."
  • "Which of these four artifacts is generated, and which is hand-written?"

If any of those questions has no answer, that is the finding — not a comment on the code.

Living with a policy

Policies must survive new firmware, new peripherals and new chip revisions, so how they are expressed and reviewed matters as much as what they contain.

/* Policies rot. Specifically:

   · BRING-UP WIDENING. Someone opens a region to make a new
     block work at 2 a.m., intending to narrow it later.
     -> require every widening to carry an expiry and a ticket;
        fail the build after the date.

   · DERIVED PRODUCTS. A cheaper variant drops the modem, and
     nobody removes its domain - leaving an allow for a master
     that no longer exists, or worse, whose ID has been reused
     by a different block.
     -> regenerate from the policy file per product; never copy
        the generated C.

   · NEW MASTERS mid-project. A block is added; the policy is
     not updated; it works because the default was never
     tightened.
     -> that is why the default is DENY. A new master that
        nobody told you about fails loudly on day one.

   · DEBUG BUILDS diverging. The dev configuration is permissive
     and the production one is not, so the negative tests only
     ever run against the permissive one.
     -> run the denial suite against the PRODUCTION policy on
        production silicon.                                  */

How it shows up

SymptomCause
A new subsystem faults on everythingIts master ID is not in any region — correct behaviour of a deny-by-default policy
Policy needs more regions than the hardware hasMemory map not grouped by domain; regroup, do not compromise the policy
Buffers fail only at certain sizes or addressesCrossing a region boundary; alignment does not match the granule
Firmware and DT disagree after a changeHand-maintained copies — generate them
Isolation works on the dev board, not on productionDifferent policy build, or lifecycle state differences
An allow nobody can explainBring-up widening that was never removed
A master reaches memory the matrix forbidsMaster ID shared or remapped — the matrix is describing something the hardware cannot distinguish
Negative tests all pass, but so does everythingThe XPU was never enabled — verify XPU_CTRL
Corruption during early boot onlyA master released from reset before enforcement began

Check yourself

  • List the nine steps and say which two are usually skipped.
  • Enumerate the bus masters of a device you have worked on — all of them.
  • Explain why an unlisted master defeats the policy regardless of its quality.
  • Build an access matrix with a reason in every cell, and read its empty cells aloud as security properties.
  • Explain why read and write must be separate decisions, with an example of each.
  • Redesign an interleaved memory map so it fits sixteen regions.
  • Explain why gaps between domains are worth keeping.
  • Name the four artifacts that must agree, and how to make them agree by construction.
  • Write ten negative tests for a system you know, and say how you would issue each one.
  • List four ways a policy rots and the control that stops each.
