Ownership

One value, one owner, dropped exactly once. This is C++'s RAII with the loopholes closed — and it is the rule from which use-after-free, double-free and leaks all become impossible rather than merely unlikely.

The three rules

Three rules, stated in about thirty words, from which the entire memory model follows. They are worth learning verbatim because every later error message is one of them being enforced.

   1. Every value has exactly ONE OWNER.
   2. There can be only one owner at a time.
   3. When the owner goes out of scope, the value is DROPPED.

   {
        let s = String::from("hello");  // s owns the heap
                                        // buffer
        use(&s);
   }                                    // s dropped here.
                                        // The buffer is
                                        // freed. Exactly
                                        // once, on every
                                        // path.

   COMPARE C++ (chapter 03 of that track):
        std::string s = "hello";        // same
        std::string t = s;              // a COPY - two
                                        // buffers
   COMPARE RUST:
        let s = String::from("hello");
        let t = s;                      // a MOVE - one
                                        // buffer, and `s` is
                                        // dead

   THE DIFFERENCE IS THE DEFAULT. C++ copies unless you say
   move; Rust moves unless the type opts into Copy. So the
   accidental deep copy and the accidental shallow copy - the
   two classic C++ bugs - are both eliminated by the same
   choice.

Moves

Assignment in Rust does something different from assignment in C or C++, and this is the single biggest adjustment for a systems programmer. Once it clicks, most borrow-checker errors stop being surprising.

    let s1 = String::from("hello");
    let s2 = s1;                        // MOVE
    println!("{s1}");                   // ERROR:
                                        // borrow of moved value

/* THE ERROR MESSAGE, which is genuinely helpful:

     error[E0382]: borrow of moved value: `s1`
       --> src/main.rs:3:20
        |
      1 |     let s1 = String::from("hello");
        |         -- move occurs because `s1` has type
        |            `String`, which does not implement the
        |            `Copy` trait
      2 |     let s2 = s1;
        |              -- value moved here
      3 |     println!("{s1}");
        |               ^^^^ value borrowed here after move
        |
      help: consider cloning the value
        |
      2 |     let s2 = s1.clone();

/* MOVES HAPPEN ON:
     assignment            let b = a;
     passing by value      f(a);
     returning             return a;
     pushing into a
       collection          v.push(a);
     pattern matching by
       value               match a { ... }

/* WHAT A MOVE COSTS: a memcpy of the value itself - for a
   String that is three words (pointer, length, capacity).
   THE HEAP BUFFER IS NOT COPIED. And the compiler usually
   elides even the memcpy.

/* THE MOVED-FROM VALUE IS GONE, not "valid but unspecified"
   as in C++ - the compiler prevents you from touching it at
   all. That is strictly stronger.                        */

/* PASSING TO A FUNCTION MOVES: */
    fn consume(s: String) { }           // takes OWNERSHIP

    let s = String::from("hi");
    consume(s);
    println!("{s}");                    // ERROR

/* SO IF THE CALLER NEEDS IT AFTERWARDS, borrow instead
   (chapter 03): */
    fn inspect(s: &String) { }          // BORROWS
    inspect(&s);
    println!("{s}");                    // fine

/* OR RETURN IT BACK - the pattern before borrowing existed,
   and still occasionally useful: */
    fn transform(mut s: String) -> String { s.push('!'); s }
    let s = transform(s);

Copy types

Not every assignment moves, and the rule for which ones do not is simple and worth knowing precisely — it explains why integers behave the way you expect and String does not.

    let x = 5;
    let y = x;                          // COPIED, not moved
    println!("{x}");                    // fine - x is still
                                        // valid

/* TYPES THAT IMPLEMENT `Copy` are duplicated bitwise instead
   of moved. The rule: a type may be Copy only if every part
   of it is Copy and it has no Drop implementation.

   COPY TYPES:
     all integers, floats, bool, char
     &T (shared references)
     raw pointers
     arrays and tuples of Copy types
     any struct you derive Copy on

   NOT COPY:
     String, Vec<T>, Box<T>      - they own a resource
     &mut T                      - copying it would create
                                   two exclusive references
     anything with a Drop impl   - copying would double-drop

/* DERIVING IT: */
    #[derive(Copy, Clone, Debug, PartialEq)]
    struct Point { x: i32, y: i32 }

    let p = Point { x: 1, y: 2 };
    let q = p;                          // copied
    println!("{p:?} {q:?}");            // both usable

/* Copy REQUIRES Clone - Copy is "Clone, and it is a bitwise
   memcpy". You always derive both together.

/* WHEN TO DERIVE Copy: for small, plain-data types - a
   register value, a coordinate, an enum of states, a message
   header. It makes them behave like C values, which is what
   you want.
   WHEN NOT TO: anything large (a copy becomes implicit and
   invisible), or anything that owns a resource.

/* AND `Clone` FOR EXPLICIT DEEP COPIES: */
    let s2 = s1.clone();                // explicit,
                                        // potentially
                                        // expensive, VISIBLE
/* The visibility is the point: in C++ a deep copy can happen
   in a function call you did not look at. In Rust it says
   `.clone()`.                                             */
The .clone() escape hatch

When the borrow checker refuses, cloning usually makes it compile. That is fine while learning — but treat a .clone() you added to silence an error as a note to revisit. Frequently the real fix is to borrow instead of own, or to restructure so one function owns the data and the others take references. Reaching for clone reflexively produces Rust that works and performs like a garbage-collected language.

Drop

Destruction in Rust is deterministic and tied to scope, which will be familiar from C++ RAII. The differences from C++ are small in number and significant in effect.

    struct Uart { base: usize }

    impl Drop for Uart {
        fn drop(&mut self) {
            // called automatically when the owner goes out of
            // scope
            unsafe { write_reg(self.base + CTRL, 0); }
        }
    }

    {
        let uart = Uart { base: 0x4000_0000 };
        uart.write(b"hello");
    }   // drop() runs HERE, on every path

/* DROP ORDER:
     · local variables in REVERSE declaration order
     · struct fields in DECLARATION order
     · the outer value's drop() runs BEFORE its fields are
       dropped

    struct Device {
        clock: ClockGate,       // dropped SECOND
        uart:  Uart,            // dropped FIRST
    }
/* Wait - fields drop in declaration order, so `clock` drops
   first. If the UART needs the clock enabled to be shut down
   cleanly, declare it the other way round:              */
    struct Device {
        uart:  Uart,            // dropped first - good
        clock: ClockGate,       // dropped second
    }

/* YOU CANNOT CALL drop() DIRECTLY: */
    uart.drop();                        // ERROR
    drop(uart);                         // this instead - it
                                        // MOVES the value
                                        // into a function
                                        // that does nothing,
                                        // so it drops there

/* AND `std::mem::forget` LEAKS DELIBERATELY: */
    std::mem::forget(uart);             // drop is NOT called
/* Which is SAFE Rust - leaking is not a memory-safety
   violation. It matters for FFI: when you hand ownership to
   C, you forget the Rust value so it is not dropped twice
   (chapter 15).

/* A TYPE WITH Drop CANNOT BE Copy - which the compiler
   enforces, because a bitwise copy followed by two drops is
   exactly the C++ double-free (C++ chapter 03).        */

Ownership of hardware

This is where ownership stops being a language feature and starts being useful to an embedded engineer: a peripheral is a resource that must have exactly one owner, and the compiler can enforce that.

/* THE EMBEDDED APPLICATION: make a peripheral a value that
   can only be owned once. Then "two drivers configured the
   same UART" is a compile error.                         */

    pub struct Uart0 { _private: () }   // cannot be
                                        // constructed outside
                                        // this module

    pub struct Peripherals {
        pub uart0: Uart0,
        pub spi1:  Spi1,
        pub gpio:  Gpio,
    }

    static TAKEN: AtomicBool = AtomicBool::new(false);

    impl Peripherals {
        pub fn take() -> Option<Self> {
            if TAKEN.swap(true, Ordering::SeqCst) {
                None                    // ALREADY TAKEN
            } else {
                Some(unsafe { Self::steal() })
            }
        }
    }

    fn main() -> ! {
        let p = Peripherals::take().unwrap();

        let uart = UartDriver::new(p.uart0);   // MOVES the
                                               // token in
        // p.uart0 is now gone - nobody else can construct a
        // second UartDriver for it, at all.
        loop { }
    }

/* THIS IS THE SINGLETON PATTERN the whole embedded Rust
   ecosystem is built on (chapter 20). The peripheral token
   is a zero-sized type - it occupies no memory and generates
   no code - and moving it expresses exclusive access in a way
   the compiler checks.

/* AND TYPE-STATE, taking it further: encode the CONFIGURATION
   in the type, so an unconfigured pin cannot be used.    */

    struct Pin<MODE> { pin: u8, _mode: PhantomData<MODE> }
    struct Input;
    struct Output;

    impl Pin<Input> {
        fn into_output(self) -> Pin<Output> {
            configure_as_output(self.pin);
            Pin { pin: self.pin, _mode: PhantomData }
        }
        fn read(&self) -> bool { read_pin(self.pin) }
    }

    impl Pin<Output> {
        fn set_high(&mut self) { write_pin(self.pin, true); }
        // NO read() - an output pin cannot be read
    }

    let pin: Pin<Input> = ...;
    pin.set_high();             // COMPILE ERROR
    let mut pin = pin.into_output();
    pin.set_high();             // fine

/* PhantomData IS ZERO-SIZED, so Pin<Input> and Pin<Output>
   are both one byte and generate identical code. The
   distinction exists only at compile time - which is the
   definition of a zero-cost abstraction (C++ chapter 14, the
   same idea).                                            */

Scopes and shadowing

Scopes determine when values are dropped, and shadowing is a Rust idiom that looks like a mistake to anyone coming from C. Both are small; both cause confusion early.

    let x = 5;
    let x = x + 1;              // SHADOWING - a new variable,
    let x = x * 2;              // same name. Not mutation.
    println!("{x}");            // 12

/* SHADOWING lets you change the TYPE, which mutation cannot:
*/
    let input = "42";                   // &str
    let input: u32 = input.parse()?;    // now u32

/* IDIOMATIC AND USEFUL - it avoids `input_str` and
   `input_num`. Distinct from `mut`, which keeps one variable
   and changes its value.

/* BLOCKS ARE EXPRESSIONS: */
    let y = {
        let a = compute();
        a * 2                   // no semicolon = the block's
                                // value
    };

/* WHICH IS WHY: */
    let max = if a > b { a } else { b };
    let msg = match code {
        0 => "ok",
        _ => "error",
    };
/* `if` and `match` are expressions, so there is no ternary
   operator and no need for one.

/* AND THE SEMICOLON RULE, which trips everyone once: */
    fn f() -> i32 { 5 }         // returns 5
    fn g() -> i32 { 5; }        // ERROR - `5;` is a
                                // STATEMENT, and the block's
                                // value is () - the unit
                                // type

A mental model

The model that makes ownership feel obvious rather than restrictive, once you have it. It is worth reading this even if the rules above already made sense.

   WHEN THE BORROW CHECKER REJECTS SOMETHING, ask in order:

   1. Does this function need to OWN the value, or only READ
      it?
         -> if only read, take &T (chapter 03)

   2. Does it need to MODIFY it in place?
         -> take &mut T

   3. Does it need to KEEP it beyond the call?
         -> take T by value; the caller gives it up

   4. Do TWO parts of the program genuinely need to own it?
         -> they cannot. Either
              · one owns and the other borrows, or
              · restructure so there is a clear owner, or
              · use Rc/Arc for genuinely shared ownership
                (chapter 10) - which is the C++ shared_ptr
                answer, with the same caveats

   5. Am I fighting a design problem rather than the
      compiler?
         -> frequently yes. "Who owns this?" is a question C
            lets you avoid answering and Rust does not, and
            answering it usually improves the design.

   THE COMMONEST BEGINNER SHAPE that fights the checker:
   a struct holding references to other parts of the same
   structure. Rust makes self-referential structures hard on
   purpose, because they are exactly what goes wrong when
   something moves. Use indices into an arena instead - which
   is the same advice as the generational-handle pattern in
   C++ chapter 10.

How it shows up

ErrorMeaning and fix
"use of moved value"You gave it away. Borrow, clone, or return it back
"cannot move out of borrowed content"You have &T and tried to take ownership — clone, or take T
"cannot move out of index"Moving one element out of a Vec — use swap_remove, take, or clone
"cannot move out of `self`"The method takes &self; it needs self
"the trait Copy is not implemented"The type owns a resource — that is why it moves
"cannot implement Copy for a type with Drop"Correct — that combination is a double free
Value dropped earlier than expectedField or variable declaration order
Resource not releasedmem::forget, an Rc cycle, or an early drop you did not intend
