Real-time operating systems and latency

Real-time means predictable, not fast. An RTOS trades throughput, memory efficiency and flexibility for one property: a bounded worst case. This chapter covers what that bound costs, how to measure it, and when Linux can deliver it instead.

What real-time means

The distinction

A system is real-time if correctness depends on when a result is produced, not only on the result itself. A motor controller that computes the right current 2 ms late has failed, however correct the number.

The metric is therefore the worst case, never the average. A system with 5 µs average latency and one 8 ms outlier per hour is not real-time; one with a guaranteed 200 µs bound is.

ClassMissing a deadline meansExamples
HardSystem failure. Possibly injury or loss of life.Airbag deployment, flight control, engine timing, medical infusion
FirmThe result becomes worthless, but no damageVideo frame rendering, a missed radar sweep
SoftQuality degrades proportionallyAudio glitches, UI stutter, VoIP jitter

Where latency comes from

"Real-time" does not mean fast; it means predictable. The distinction matters because a system with excellent average performance can be entirely unsuitable, and one that is slower can be exactly right.

How an RTOS achieves a bound

A real-time kernel achieves its bound by making specific design choices that a general-purpose kernel deliberately avoids. Each one trades throughput or flexibility for predictability.

/* A typical RTOS scheduler decision, in constant time: */
static uint32_t ready_bitmap;              /* one bit per priority */

static inline int highest_ready(void)
{
        return 31 - __builtin_clz(ready_bitmap);   /* ONE instruction */
}

The RTOS programming model

The most widely deployed of them, and small enough to read in an afternoon — which makes it the best way to see the concepts above in actual code rather than in the abstract.

/* FreeRTOS — the shape is essentially the same in every RTOS */

void sensor_task(void *arg)
{
        TickType_t next = xTaskGetTickCount();
        for (;;) {
                read_sensor();
                process();
                /* absolute deadline — no drift accumulation */
                vTaskDelayUntil(&next, pdMS_TO_TICKS(10));
        }
}

xTaskCreate(sensor_task, "sensor",
            256,            /* stack in WORDS — sized per task */
            NULL,
            3,              /* priority: higher number = higher */
            &handle);
vTaskStartScheduler();      /* never returns */

/* ISR → task communication. Note the FromISR suffix: separate
   entry points that never block, and that request a context
   switch on return.                                           */
void UART_IRQHandler(void)
{
        BaseType_t woken = pdFALSE;
        xQueueSendFromISR(rx_queue, &byte, &woken);
        portYIELD_FROM_ISR(woken);      /* switch immediately if a
                                           higher-priority task woke */
}

/* Calling the blocking variant from an ISR is the classic RTOS
   bug: it asserts, or silently corrupts the scheduler state. */
Per-task stacks are the memory problem

Every task needs its own stack, sized for its worst-case call depth plus any interrupt frame that can nest on it. Twenty tasks at 1 KB each is 20 KB — often more than the application's data. Undersize one and you get silent corruption of the neighbouring task's stack, which presents as impossible behaviour far from the cause.

Use uxTaskGetStackHighWaterMark(), enable stack-overflow checking during development, and fill stacks with a known pattern so you can measure real usage rather than guess.

Worst-case execution time

Guaranteeing a deadline requires knowing the worst-case execution time, which is far harder to establish than the average and is complicated by exactly the features that make modern processors fast.

Hard real-time requires a PROVEN upper bound on execution time —
not a measured maximum. That is genuinely hard, because modern
hardware is designed to make the AVERAGE case fast:

  caches            a miss is 100x a hit. WCET must assume misses.
  branch prediction a mispredict costs 15+ cycles. Assume worst.
  out-of-order      timing depends on surrounding instructions
  DRAM refresh      periodic stalls outside your control
  shared buses      another master can delay you
  SMT / big.LITTLE  a sibling thread steals resources; cores differ
  DVFS              the clock itself varies

  Approaches:
    STATIC ANALYSIS   model the pipeline and caches, prove a bound
                      (aiT, Bound-T). Sound, pessimistic, expensive.
    MEASUREMENT       run many times, take the max, add margin.
                      Practical, and NOT a proof.
    HYBRID            measure segments, compose analytically.

  Simplifying for analysability is usually cheaper than analysing
  complexity: disable caches on the critical path, lock cache ways,
  use TCM/scratchpad memory, pin to one core, avoid dynamic
  dispatch, and forbid recursion and unbounded loops.

Will the task set meet its deadlines?

Given a set of tasks with periods and deadlines, there is a mathematical question of whether any schedule can meet them all. The answer is computable, which turns a design question into arithmetic.

/* RATE MONOTONIC — static priorities, shorter period = higher
   priority. Optimal among fixed-priority schemes.            */

   Sufficient condition (Liu & Layland):
        U = Σ (Cᵢ / Tᵢ)  ≤  n(2^(1/n) − 1)

        n=1  → 1.000      n=3  → 0.780
        n=2  → 0.828      n→∞  → 0.693

   Worked example, three periodic tasks:
        T1: C=1 ms,  T=4 ms   → 0.250
        T2: C=2 ms,  T=8 ms   → 0.250
        T3: C=4 ms,  T=16 ms  → 0.250
        U = 0.75  ≤  0.780    → schedulable, guaranteed.

/* EARLIEST DEADLINE FIRST — dynamic priorities.
        schedulable iff  U ≤ 1.0
   Strictly better utilisation, but behaves badly on overload:
   under RM the low-priority tasks fail first and predictably;
   under EDF a transient overload can cause a cascade of misses.

   Linux's SCHED_DEADLINE implements EDF with a constant-bandwidth
   server and an ADMISSION TEST, so requesting more than the system
   can guarantee FAILS at setup rather than silently missing
   deadlines later (OS chapter 06).                          */

Real-time Linux

Linux can be made to approach real-time behaviour, and the work required to do it shows precisely which parts of a general-purpose kernel are the obstacles.

# PREEMPT_RT, merged into mainline in 6.12. What it changes:
#   · most spinlocks become sleeping rt_mutexes
#   · interrupt handlers become kernel threads by default
#   · priority inheritance everywhere
#   · bounded interrupt-disable regions throughout
#   Result: typical worst case in the tens of microseconds,
#   at roughly 10-30% throughput cost.

# The full recipe for low latency on Linux:

# 1. kernel command line — isolate cores completely
isolcpus=2,3 nohz_full=2,3 rcu_nocbs=2,3 irqaffinity=0,1 \
    intel_pstate=disable processor.max_cstate=1 idle=poll

# 2. keep interrupts off the RT cores
for i in /proc/irq/*/smp_affinity_list; do echo 0-1 > $i 2>/dev/null; done
systemctl stop irqbalance

# 3. fix the clock, disable deep idle
cpupower frequency-set -g performance

# 4. in the application
mlockall(MCL_CURRENT | MCL_FUTURE);        /* no page faults    */
sched_setscheduler(0, SCHED_FIFO, &param); /* priority 80-90    */
CPU_SET(2, &mask); sched_setaffinity(...); /* pin to an isolated core */
/* pre-fault and pre-allocate EVERYTHING before the real-time loop */

# 5. measure — the only step that proves anything
cyclictest -t2 -p 90 -a 2,3 -i 200 -m -D 24h
#   report the MAX column. Run for hours, under representative load.

Mixed criticality

Many real systems need both a rich operating system and hard real-time guarantees. Several architectures achieve that simultaneously, with different isolation properties.

Modern SoCs run real-time and general-purpose workloads together.
Four ways to combine them, in increasing order of isolation:

  1. SEPARATE CORES on one SoC (AMP)
       Cortex-A runs Linux, Cortex-M/R runs the RTOS.
       Communication via shared memory + mailbox (RPMsg, OpenAMP).
       Very common: motor control beside a Linux HMI.

  2. HYPERVISOR PARTITIONING
       Xen/Jailhouse/Hafnium gives each guest dedicated cores,
       memory and devices. Strong spatial isolation.

  3. PREEMPT_RT alone
       One kernel, RT priorities plus core isolation.
       Simplest; isolation is only as good as the kernel.

  4. DUAL KERNEL (Xenomai, RTAI)
       A tiny RT co-kernel takes interrupts FIRST and runs Linux
       as its lowest-priority task. Best Linux-hosted latency;
       a separate API and real maintenance cost.

  In all four, the hard part is shared HARDWARE: the memory
  controller, caches, the interconnect. A Linux core saturating
  DRAM bandwidth can inflate the RT core's WCET even with perfect
  logical isolation. Cache partitioning and memory bandwidth
  regulation exist for exactly this.
