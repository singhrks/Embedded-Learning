The Client API in depth

Eleven functions, defined by GlobalPlatform, implemented by libteec, and identical across every compliant TEE. Learn them here and your client code moves to Kinibi or QSEE unchanged. This chapter is the complete surface, with the lifecycle rules that the specification states and everyone violates anyway.

The whole API

The whole API is small enough to hold in your head, which is unusual and deliberate: a small interface is easier to implement consistently across TEE vendors.

FunctionDoes
TEEC_InitializeContextConnect to a TEE. Opens /dev/tee0
TEEC_FinalizeContextDisconnect
TEEC_OpenSessionStart talking to a TA, identified by UUID
TEEC_CloseSessionStop
TEEC_InvokeCommandAsk the TA to do something
TEEC_RequestCancellationAsk for an in-flight operation to stop
TEEC_RegisterSharedMemoryGive the TEE memory you already own
TEEC_AllocateSharedMemoryHave the TEE allocate it
TEEC_ReleaseSharedMemoryGive it back
TEEC_RegisterSharedMemoryFileDescriptorOP-TEE extension: share a dmabuf
TEEC_PARAM_TYPESA macro that packs four parameter types into one word

The lifecycle, and what it costs

The client API has a strict object lifecycle — context, session, operation — and each level must be opened and closed in order. Most client-side bugs are a mismatch in that nesting.

   TEEC_InitializeContext
      opens /dev/tee0, queries the driver
      COST: an open() and an ioctl. Cheap-ish.
      |
      v
   TEEC_OpenSession
      -> SMC -> OP-TEE looks up the UUID
      -> if the TA is not resident: RPC to tee-supplicant to
         read the .ta file, then VERIFY ITS SIGNATURE, then
         allocate TA_RAM, map it, run TA_CreateEntryPoint
      -> then TA_OpenSessionEntryPoint
      COST: THE EXPENSIVE ONE. Several milliseconds the first
      time - signature verification of a 100 KB binary is real
      work.
      |
      v
   TEEC_InvokeCommand    (many times)
      -> SMC -> TA_InvokeCommandEntryPoint
      COST: two world switches plus your TA's work. Tens of
      microseconds of overhead.
      |
      v
   TEEC_CloseSession
      -> TA_CloseSessionEntryPoint
      -> if this was the LAST session: TA_DestroyEntryPoint,
         and the TA is unloaded from TA_RAM (unless it is a
         singleton that keeps its instance alive)
      |
      v
   TEEC_FinalizeContext

   THE PERFORMANCE RULE THAT FOLLOWS:

     open the session ONCE, at start-up, and keep it.

   A client that opens and closes a session around every
   operation pays the load-and-verify cost every time. This is
   the single most common OP-TEE performance mistake, and it
   can be a 100x difference.

A complete, correct client

A complete client program, short enough to read in one pass, showing the lifecycle applied end to end.

/* keystore_client.c - the error handling and cleanup are the
   point. Copy this shape.                                    */

#include <err.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <tee_client_api.h>

#define TA_UUID { 0x8aaaf200, 0x2450, 0x11e4, \
        { 0xab, 0xe2, 0x00, 0x02, 0xa5, 0xd5, 0xc5, 0x1b } }

#define CMD_SIGN   0

struct tee_ctx {
        TEEC_Context      ctx;
        TEEC_Session      sess;
        TEEC_SharedMemory io;
        int               have_ctx, have_sess, have_shm;
};

static const char *origin_str(uint32_t o)
{
        switch (o) {
        case TEEC_ORIGIN_API:         return "API";
        case TEEC_ORIGIN_COMMS:       return "COMMS";
        case TEEC_ORIGIN_TEE:         return "TEE";
        case TEEC_ORIGIN_TRUSTED_APP: return "TA";
        default:                      return "?";
        }
}

static void tee_fini(struct tee_ctx *t)
{
        if (t->have_shm)  TEEC_ReleaseSharedMemory(&t->io);
        if (t->have_sess) TEEC_CloseSession(&t->sess);
        if (t->have_ctx)  TEEC_FinalizeContext(&t->ctx);
        memset(t, 0, sizeof *t);
}

static int tee_init(struct tee_ctx *t, size_t bufsz)
{
        TEEC_UUID   uuid = TA_UUID;
        uint32_t    origin;
        TEEC_Result res;

        memset(t, 0, sizeof *t);

        res = TEEC_InitializeContext(NULL, &t->ctx);
        if (res != TEEC_SUCCESS) {
                warnx("InitializeContext: 0x%08x", res);
                return -1;
        }
        t->have_ctx = 1;

        res = TEEC_OpenSession(&t->ctx, &t->sess, &uuid,
                               TEEC_LOGIN_PUBLIC, NULL, NULL,
                               &origin);
        if (res != TEEC_SUCCESS) {
                warnx("OpenSession: 0x%08x origin %s",
                      res, origin_str(origin));
                goto fail;
        }
        t->have_sess = 1;

        /* Allocate ONCE and reuse - see the note below. */
        t->io.size  = bufsz;
        t->io.flags = TEEC_MEM_INPUT | TEEC_MEM_OUTPUT;
        res = TEEC_AllocateSharedMemory(&t->ctx, &t->io);
        if (res != TEEC_SUCCESS) {
                warnx("AllocateSharedMemory: 0x%08x", res);
                goto fail;
        }
        t->have_shm = 1;
        return 0;
fail:
        tee_fini(t);
        return -1;
}

static int tee_sign(struct tee_ctx *t, const void *msg, size_t len,
                    void *sig, size_t *siglen)
{
        TEEC_Operation op;
        uint32_t       origin;
        TEEC_Result    res;

        if (len > t->io.size)
                return -1;
        memcpy(t->io.buffer, msg, len);

        memset(&op, 0, sizeof op);
        op.paramTypes = TEEC_PARAM_TYPES(TEEC_MEMREF_PARTIAL_INPUT,
                                         TEEC_MEMREF_PARTIAL_OUTPUT,
                                         TEEC_NONE, TEEC_NONE);
        op.params[0].memref.parent = &t->io;
        op.params[0].memref.offset = 0;
        op.params[0].memref.size   = len;
        op.params[1].memref.parent = &t->io;
        op.params[1].memref.offset = 2048;      /* second half   */
        op.params[1].memref.size   = *siglen;

        res = TEEC_InvokeCommand(&t->sess, CMD_SIGN, &op, &origin);

        /* THE SHORT-BUFFER RETRY. Every real client needs it. */
        if (res == TEEC_ERROR_SHORT_BUFFER) {
                warnx("need %u bytes, had %zu",
                      op.params[1].memref.size, *siglen);
                *siglen = op.params[1].memref.size;
                return -2;      /* caller reallocates, retries  */
        }
        if (res != TEEC_SUCCESS) {
                warnx("InvokeCommand: 0x%08x origin %s",
                      res, origin_str(origin));
                return -1;
        }

        *siglen = op.params[1].memref.size;
        memcpy(sig, (char *)t->io.buffer + 2048, *siglen);
        return 0;
}

int main(void)
{
        struct tee_ctx t;
        uint8_t sig[512];
        size_t  siglen = sizeof sig;

        if (tee_init(&t, 4096))
                return 1;

        /* Many invocations, ONE session. */
        for (int i = 0; i < 1000; i++) {
                if (tee_sign(&t, "hello", 5, sig, &siglen) < 0)
                        break;
                siglen = sizeof sig;
        }

        tee_fini(&t);
        return 0;
}
Allocate shared memory once

TEEC_AllocateSharedMemory is not free — it goes to the kernel and possibly to OP-TEE. Allocating a buffer per invocation, in a loop, doubles your overhead for no benefit. Allocate one buffer at start-up, big enough for your largest transfer, and use TEEC_MEMREF_PARTIAL_INPUT/OUTPUT with offsets to carve it up.

Login types and connection data

The TEE can be told something about who is calling, which lets a trusted application distinguish a request from the kernel from one from an arbitrary user process.

/* The fifth argument to TEEC_OpenSession says WHO is calling.
   The TA can see it, and OP-TEE derives per-caller storage
   keys from it (chapter 15).                                */

  TEEC_LOGIN_PUBLIC        no identity claimed. Anyone.
  TEEC_LOGIN_USER          the caller's uid, hashed in by the
                           kernel driver - the client CANNOT
                           forge it
  TEEC_LOGIN_GROUP         a gid, supplied in connectionData
  TEEC_LOGIN_APPLICATION   an application identity
  TEEC_LOGIN_USER_APPLICATION
  TEEC_LOGIN_GROUP_APPLICATION
  TEEC_LOGIN_REE_KERNEL    the caller is the kernel (ch. 10)

    uint32_t gid = 1000;
    res = TEEC_OpenSession(&ctx, &sess, &uuid,
                           TEEC_LOGIN_GROUP, &gid,
                           NULL, &origin);

/* Why it matters: with LOGIN_USER, two different users opening
   sessions to the same TA get DIFFERENT secure storage. The
   TA writes to "my key" and each caller gets their own. That
   separation is enforced by OP-TEE, using an identity the
   client cannot choose.

   With LOGIN_PUBLIC there is one shared storage space for
   everyone. For a multi-user or multi-app system that is
   almost certainly wrong.                                   */

Cancellation

A long-running secure operation may need to be cancelled, and doing so is cooperative rather than forced — the trusted application must be written to notice.

/* A long-running TA operation can be asked to stop. It is
   COOPERATIVE - the TA must check.                          */

/* Client, from another thread: */
    TEEC_RequestCancellation(&op);

/* TA side: */
    if (TEE_GetCancellationFlag()) {
            cleanup();
            return TEE_ERROR_CANCEL;
    }

    /* A TA can also mask cancellation while in a critical
       section, and must restore it: */
    bool old = TEE_MaskCancellation();
    do_something_uninterruptible();
    if (old) TEE_MaskCancellation(); else TEE_UnmaskCancellation();

/* Uses:
     a watchdog thread that cancels after a timeout
     a UI "cancel" button on a slow key generation
     shutdown

   Limits:
     the TA must poll the flag. A TA blocked in an RPC will
     not see it until the RPC returns.
     There is NO way to forcibly kill a TA invocation. If your
     TA can loop for ever, you have created an unkillable
     thread (chapter 5).                                     */

Thread safety

Because the secure world has a limited number of contexts, a multi-threaded client can exhaust them. The rules about concurrent sessions follow from that limit.

/* The GlobalPlatform rules, which OP-TEE follows:

   TEEC_Context   may be shared between threads.
   TEEC_Session   may be shared, BUT concurrent
                  TEEC_InvokeCommand calls on ONE session are
                  serialised by the TA's own instance/session
                  flags (chapter 13). Whether they run
                  concurrently depends on TA_FLAG_*.
   TEEC_Operation must NOT be shared. One per in-flight call.
   TEEC_SharedMemory may be shared, but you are responsible
                  for not having two calls write the same
                  region.

   The practical pattern for a multithreaded client:

     one TEEC_Context           process-wide
     one TEEC_Session           process-wide, if the TA is
                                multi-session capable
     one TEEC_Operation         per call, on the stack
     one TEEC_SharedMemory      per thread, allocated once

   If the TA is TA_FLAG_SINGLE_INSTANCE without
   TA_FLAG_MULTI_SESSION, your threads will serialise inside
   OP-TEE no matter what the client does. Know which your TA
   is.                                                        */

How it shows up

SymptomCause
Every operation takes millisecondsSession opened and closed per call — the TA is being loaded and verified each time
TEEC_ERROR_ITEM_NOT_FOUND on OpenSessionTA not installed, or tee-supplicant not running
TEEC_ERROR_BUSY intermittentlyThread pool exhausted; libteec retries but concurrency is capped
Corruption with multiple threadsA TEEC_Operation or a shared buffer used by two calls at once
Client cannot cancel a stuck TACancellation is cooperative; the TA is not polling the flag
Two users see each other's stored dataTEEC_LOGIN_PUBLIC where LOGIN_USER was needed
Retry loop on SHORT_BUFFER never endsThe TA does not set memref.size to the required length
Memory grows over timeShared memory or sessions not released on the error path
Works alone, fails under concurrencyTA flags serialise sessions; see chapter 13
