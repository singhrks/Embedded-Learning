What ARM is: architecture versus microarchitecture

Arm Ltd does not make chips. It writes a specification and licenses core designs that implement it. Keeping those two things apart is the first thing to get right, because it tells you which of your bugs are portable and which are specific to the silicon in front of you.

Why this matters when you are debugging

Ask which one you are fighting.

Architectural problems are portable: if your code violates the memory model, it is wrong on every ARM implementation, and the fix is in your code. Microarchitectural surprises — timing, cache line effects, an erratum — are specific to one core, and the fix may be a workaround, a different compiler flag, or a kernel quirk.

A useful test: would this still be a bug on a hypothetical, perfectly simple in-order implementation of the same architecture? If yes, it is architectural and it is your problem to fix properly.

The architecture licence is why Apple's cores are dramatically faster than a Cortex core of the same generation while running identical binaries: same contract, very different implementation. It is also why "ARM performance" is a meaningless phrase — you must name the core.

One architecture, many implementations, all running your binary:

What the architecture actually specifies

  • The instruction set — encodings and precise semantics.
  • The register file — what exists and what each register means.
  • The memory model — what reorderings are permitted, and what barriers guarantee (ch. 20).
  • The exception model — exception levels, vectors, what hardware saves (ch. 26).
  • Address translation — page table formats, descriptor bits, TLB maintenance (ch. 13).
  • System registers — names, fields, and which level may access them.
  • Required behaviour on reset, and what is IMPLEMENTATION DEFINED.
IMPLEMENTATION DEFINED is a formal term

The ARM ARM uses precise vocabulary that is worth learning, because it tells you exactly how much you may rely on something:

  • IMPLEMENTATION DEFINED — the implementer chooses and must document it. Cache size, number of breakpoints, whether a feature exists.
  • UNPREDICTABLE — behaviour is not specified, but must not be a security hole or hang the machine. Never write code that relies on it.
  • CONSTRAINED UNPREDICTABLE — one of a specified, enumerated set of behaviours. Still do not rely on it.
  • RES0 / RES1 — reserved bits you must write as zero or one respectively, so that future architecture versions can use them without breaking your code. Ignoring this is why some old firmware fails on new silicon.

Never assume — ask the CPU

"ARM" names a family with enormous internal variation, so almost nothing is safe to assume about the chip in front of you. Fortunately the processor can be asked directly — every AArch64 core carries a set of registers describing exactly what it implements.

/* The architecture provides ID registers describing exactly which
   optional features this implementation has. Software must query
   them rather than assume, because the SAME architecture version
   allows different feature sets.                              */

MIDR_EL1          /* implementer, part number, revision — "who am I" */
MPIDR_EL1         /* affinity: which core in which cluster           */
ID_AA64ISAR0_EL1  /* atomics (LSE), CRC32, crypto, SHA               */
ID_AA64ISAR1_EL1  /* pointer authentication, JSCVT, DPB              */
ID_AA64MMFR0_EL1  /* physical address size, granule sizes supported  */
ID_AA64MMFR1_EL1  /* VHE, hardware access/dirty bit management       */
ID_AA64PFR0_EL1   /* which exception levels exist, SVE, FP           */
CTR_EL0           /* cache line sizes — readable from EL0            */

/* Example: does this core have the Large System Extensions? */
static bool has_lse(void)
{
        uint64_t isar0;
        asm volatile("mrs %0, id_aa64isar0_el1" : "=r"(isar0));
        return ((isar0 >> 20) & 0xF) >= 2;   /* Atomic field */
}
/* Linux and Windows both do exactly this at boot and PATCH the
   binary — replacing an LDXR/STXR loop with a single LDADD where
   the hardware supports it. One kernel image, optimal on each. */
# see what your machine reports
cat /proc/cpuinfo
#   CPU implementer : 0x41        (0x41 = 'A' = Arm Ltd; 0x61 = Apple)
#   CPU architecture: 8
#   CPU variant     : 0x1
#   CPU part        : 0xd0b       (0xd0b = Cortex-A76)
#   Features        : fp asimd atomics crc32 sha1 sha2 ...
#                     ^^^^^^^ "atomics" means LSE is present

lscpu
cat /sys/devices/system/cpu/cpu0/regs/identification/midr_el1

Errata

Read the errata document. Always.

Every core has documented hardware bugs, published as an errata notice, each with a software workaround. They are not rare and they are not theoretical — the Linux kernel contains hundreds of them, gated by MIDR checks so the workaround applies only on affected revisions.

grep -rn "ARM64_WORKAROUND" arch/arm64/kernel/cpu_errata.c | head
cat /sys/devices/system/cpu/vulnerabilities/*

/* A real example: Cortex-A53 erratum 843419 — a specific sequence
   of ADRP plus a load can compute the wrong address. The fix is a
   LINKER workaround (--fix-cortex-a53-843419), which is why some
   toolchains pass it by default for that core.

   The lesson: when hardware behaves impossibly, check the errata
   before assuming your code is at fault. And when bringing up new
   silicon, read the whole document once, up front.          */

Why ARM ended up everywhere

None of these properties is individually decisive — x86 is also an ecosystem, and other RISC architectures were also power-efficient. What made ARM dominant is that the licensing model turned every other advantage into something a competitor could exploit without ARM Ltd having to compete on chip design at all. A company that wanted a phone SoC did not need to design a CPU core, tape out silicon at their own risk, or build a compiler and OS ecosystem from scratch — they licensed a core, and Linux, Android and the toolchains already worked. That economic structure, more than any instruction encoding decision, is why the same instruction set runs a smart thermostat and a fifty-thousand-core Graviton cluster.

Using the ARM ARM

The architecture reference manual runs to several thousand pages, which makes it useless to read and invaluable to search. Knowing how it is organised turns it from an obstacle into the fastest way to settle a question definitively.

It is over 12,000 pages. It is a REFERENCE, not a textbook, and
reading it linearly is a mistake beginners make once.

  How to use it:
    · start from a QUESTION ("what does ESR_EL1 bit 24 mean?")
    · search the PDF, or use developer.arm.com's HTML version
    · the register descriptions (section D) are the most-used part
    · pseudocode in the manual is NORMATIVE — when prose and
      pseudocode disagree, the pseudocode wins

  Start instead with:
    "Arm Cortex-A Series Programmer's Guide for ARMv8-A"
      — a few hundred readable pages, written as a tutorial
    "Learn the architecture" guides on developer.arm.com
      — short, topic-focused, and genuinely good

  Then use the ARM ARM to answer the questions those raise.
