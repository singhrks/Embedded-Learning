Processes, threads and task_struct

Linux has no separate notion of a process and a thread. There is one structure, task_struct, and everything else is a question of what two tasks choose to share — which turns out to be a much cleaner model than the one most textbooks describe.

One structure for both

Linux does not have separate machinery for processes and threads. There is exactly one structure describing something the scheduler can run, and whether you call a given instance a process or a thread depends only on how much it shares with its neighbours.

A "process" with three threads is really THREE task_structs
that share most of their pointers:

   task_struct (tid 100)      task_struct (tid 101)
   +------------------+       +------------------+
   | pid   = 100      |       | pid   = 100      |  <- SAME
   | tid   = 100      |       | tid   = 101      |  <- differs
   | mm    = ---------+---+---+ mm    =          |
   | files = ---------+-+ |   | files =          |
   | fs    = ...      | | |   | fs    =          |
   | signal= ...      | | |   | signal=          |
   | stack = 0xffff.. | | |   | stack = 0xffff.. |  <- OWN
   +------------------+ | |   +------------------+
                        | |
                        | +--> struct mm_struct   the address
                        |      (page tables, VMAs) space
                        |
                        +----> struct files_struct  the fd table

  WHAT IS ALWAYS PRIVATE:
     the kernel stack, the register state, the tid,
     the scheduler state, pending signals

  WHAT MAY BE SHARED, decided at clone() time:
     CLONE_VM       the address space   -> "threads"
     CLONE_FILES    the fd table
     CLONE_FS       cwd, root, umask
     CLONE_SIGHAND  signal handlers
     CLONE_THREAD   the thread group (same pid)
     CLONE_NEWNS/NEWPID/NEWNET/...  namespaces -> containers

  fork()   = clone(SIGCHLD)                    shares nothing
  pthread  = clone(CLONE_VM|CLONE_FILES|CLONE_FS|
                   CLONE_SIGHAND|CLONE_THREAD|...)
  container= clone(... | CLONE_NEWPID | CLONE_NEWNET | ...)

  So processes, threads and containers are three points on one
  continuum, not three mechanisms.

pid, tid, and the naming trap

This is one of the genuinely confusing corners of Linux, because the words mean different things inside the kernel than they do to a user-space programmer — and the mismatch is exactly backwards from what most people assume.

/* The kernel's names are the OPPOSITE of what userspace calls
   them, and this confuses everyone once.                    */

   task->pid       the THREAD id.  Unique per task.
                   Userspace calls this the TID.
   task->tgid      the THREAD GROUP id. Shared by all threads
                   in a process. Userspace calls this the PID.

/* So: */
        getpid()  in userspace  returns  task->tgid
        gettid()  in userspace  returns  task->pid

/* In kernel code: */
        current->pid            /* this THREAD */
        current->tgid           /* the process */
        task_pid_nr(current)    /* pid in the INIT namespace */
        task_tgid_nr(current)
        task_pid_vnr(current)   /* pid as the task's own
                                   namespace sees it - what a
                                   containerised process
                                   believes its pid to be    */

/* WHICH TO USE when identifying a caller in a driver:
     for logging          -> current->pid and current->comm
     for ownership        -> the struct file, NOT the pid.
                             A pid can be reused after exit.
     across a namespace   -> think hard; a pid means nothing
                             outside the namespace that
                             created it                      */

current

Kernel code frequently needs to know which task it is running on behalf of. Rather than passing that around everywhere, the kernel provides a single expression that always evaluates to the current task — and understanding how it works explains why it is safe in some contexts and meaningless in others.

#include <linux/sched.h>

        current             /* the task_struct running NOW */
        current->pid
        current->comm       /* the command name, 16 bytes */
        current->mm         /* NULL for a kernel thread! */
        current->flags

/* On arm64 `current` is SP_EL0, repurposed: the kernel keeps
   the current task_struct pointer there while running at EL1,
   so reading it is a single register read, not a lookup.
   (arch/arm64/include/asm/current.h)                        */

/* USEFUL IN A DRIVER: */
        dev_dbg(dev, "ioctl from %s[%d]\n",
                current->comm, current->pid);

/* AND THE TRAPS:

   1. `current` is only meaningful in PROCESS CONTEXT. In an
      interrupt handler it points at whatever task was
      unluckily interrupted - which has nothing to do with the
      device. Never attribute interrupt work to `current`.

   2. current->mm is NULL for KERNEL THREADS. Code that
      assumes an address space exists will crash when called
      from a kthread or a workqueue.

           if (!current->mm)
                   return -EINVAL;      /* kernel thread */

   3. Do not store `current` and use it later. The task can
      exit. If you need a reference, take one:
           get_task_struct(task);
           ...
           put_task_struct(task);                            */

Task states

Every task's state answers the scheduler's one question — is this task runnable right now — but the distinctions within "not runnable" matter enormously for anyone debugging a hung system, since they determine whether a stuck process can be interrupted, signalled, or killed at all.

StatepsMeaning
TASK_RUNNINGRRunning, or on a runqueue ready to run
TASK_INTERRUPTIBLESSleeping; signals wake it
TASK_UNINTERRUPTIBLEDSleeping; signals do not wake it
TASK_KILLABLEDUninterruptible except by a fatal signal — usually the right choice
__TASK_STOPPEDTStopped by SIGSTOP
EXIT_ZOMBIEZExited, not yet reaped by its parent
TASK_IDLEIUninterruptible but not counted in load average — for kthreads
The D state is a driver's fault more often than not

A process stuck in D cannot be killed, not even with SIGKILL, and it drives the load average up. It is almost always waiting on I/O in a driver that used wait_event() — the uninterruptible form — instead of wait_event_interruptible(). Use the interruptible or killable variants unless you can state exactly why a signal must not interrupt this wait; and if the hardware genuinely cannot be abandoned mid-operation, use a timeout so the wait is at least bounded.

Sleeping and waking, correctly

Waiting is the operation drivers get wrong most often. A driver that spins waiting for hardware burns a CPU; one that sleeps incorrectly misses its wake-up and hangs forever. There is a correct pattern, and it is worth learning as a pattern rather than reconstructing it each time.

/* THE PATTERN every blocking driver uses. */

struct my_dev {
        wait_queue_head_t  wq;
        bool               data_ready;
        spinlock_t         lock;
};

        init_waitqueue_head(&d->wq);

/* --- the reader: wait for data --------------------------- */
static ssize_t my_read(struct file *f, char __user *buf,
                       size_t count, loff_t *ppos)
{
        struct my_dev *d = f->private_data;
        int ret;

        /* non-blocking mode must be honoured */
        if (f->f_flags & O_NONBLOCK) {
                if (!d->data_ready)
                        return -EAGAIN;
        } else {
                ret = wait_event_interruptible(d->wq,
                                               d->data_ready);
                if (ret)
                        return -ERESTARTSYS;   /* a signal:
                                                  let libc
                                                  restart it */
        }
        ...
}

/* --- the interrupt handler: wake it ---------------------- */
static irqreturn_t my_isr(int irq, void *dev_id)
{
        struct my_dev *d = dev_id;

        d->data_ready = true;
        wake_up_interruptible(&d->wq);
        return IRQ_HANDLED;
}

/* WHY wait_event_* IS A MACRO AND NOT A FUNCTION:
   it expands to the correct sleep sequence, which is subtle:

        for (;;) {
                prepare_to_wait(&wq, &entry, TASK_INTERRUPTIBLE);
                if (condition)         <-- re-check AFTER
                        break;             being queued
                if (signal_pending(current)) { ret = -ERESTARTSYS;
                                               break; }
                schedule();
        }
        finish_wait(&wq, &entry);

   The ORDER is what matters: queue yourself FIRST, then check
   the condition. Check first and a wakeup arriving in between
   is lost, and you sleep forever. This is the lost-wakeup
   race, and it is why you use the macro rather than writing
   it out.                                                  */

/* THE VARIANTS: */
        wait_event(wq, cond);                    /* D state  */
        wait_event_interruptible(wq, cond);      /* S state  */
        wait_event_killable(wq, cond);           /* SIGKILL  */
        wait_event_timeout(wq, cond, HZ);        /* bounded  */
        wait_event_interruptible_timeout(wq, cond, HZ);

/* AND THE RETURN VALUES DIFFER - a classic bug: */
        ret = wait_event_interruptible_timeout(wq, cond, HZ);
        if (ret == 0)   return -ETIMEDOUT;   /* timed out    */
        if (ret < 0)    return ret;          /* interrupted  */
        /* ret > 0: condition true, jiffies remaining        */

Kernel threads

Sometimes a driver needs work done in the background, in a context where it is allowed to sleep, without any user process being involved. A kernel thread is a task with no user-space side at all — it exists only to run kernel code.

#include <linux/kthread.h>

static int my_thread_fn(void *data)
{
        struct my_dev *d = data;

        while (!kthread_should_stop()) {
                wait_event_interruptible(d->wq,
                        d->work_pending || kthread_should_stop());
                if (kthread_should_stop())
                        break;
                do_the_work(d);
        }
        return 0;
}

        d->task = kthread_run(my_thread_fn, d, "my_worker/%d", id);
        if (IS_ERR(d->task))
                return PTR_ERR(d->task);
        ...
        kthread_stop(d->task);   /* sets the flag, wakes it,
                                    WAITS for it to return   */

/* PROPERTIES:
     · runs in process context - CAN SLEEP
     · current->mm is NULL - no user address space
     · appears in ps in [square brackets]
     · schedulable, so it can be niced and affined
     · kthread_should_stop() must be checked, AND the thread
       must be woken for it to notice - hence the condition
       above includes it

   WHEN TO USE ONE:
     you need a long-running, sleeping loop of your own.

   WHEN NOT TO - which is most of the time:
     for short deferred work, use a WORKQUEUE (chapter 15).
     A workqueue shares worker threads across the whole
     kernel; a dedicated kthread per device costs memory and
     scheduler entries. Reach for a kthread only when you
     genuinely need a private, long-lived, sleeping context -
     a polling loop, or a thread servicing a hardware queue.  */

Signals in the kernel

Signals are a user-space concept, but they reach into the kernel: they are what allows a blocked process to be interrupted, and a driver that waits without accounting for them is the reason processes get stuck unkillable.

/* A driver rarely handles signals, but it must react to them
   correctly when interrupted.                              */

        if (signal_pending(current))
                return -ERESTARTSYS;

/* THE ERROR CODES, and the difference matters to userspace:

     -EINTR         "your syscall was interrupted". Userspace
                    sees EINTR and must retry itself.

     -ERESTARTSYS   "restart the syscall automatically, IF the
                    handler was installed with SA_RESTART".
                    Never reaches userspace as-is; the signal
                    machinery converts it to EINTR or restarts
                    the call. THIS IS USUALLY WHAT YOU WANT
                    from a wait that made no progress.

     -ERESTARTNOINTR  always restart, regardless of SA_RESTART

   THE RULE: if the operation made NO observable progress,
   return -ERESTARTSYS. If it partially completed - you copied
   some bytes - return the count you completed instead, and
   let the caller resume from there. Returning -ERESTARTSYS
   after partial progress causes the work to be done twice. */

        if (copied > 0)
                return copied;          /* partial success */
        if (signal_pending(current))
                return -ERESTARTSYS;    /* nothing done */

Looking at tasks

Every task is visible from user space, along with what it is currently waiting on. When something is hung, these are the first places to look, and they usually identify the responsible driver directly.

# From userspace:
    ps -eLf                 # -L shows THREADS, not just
                            # processes: LWP is the tid
    cat /proc/$PID/status   # Tgid, Pid, Threads, State, ...
    cat /proc/$PID/task/*/  # one directory per thread
    cat /proc/$PID/stack    # kernel backtrace - where is it
                            # blocked? THE tool for a D state
    cat /proc/$PID/wchan    # the function it is sleeping in
    cat /proc/$PID/maps     # the address space

# Finding what a D-state process is stuck on:
    ps -eo pid,stat,comm | awk '$2 ~ /D/'
    sudo cat /proc/1234/stack
      [<0>] my_driver_read+0x120/0x2a0     <-- there it is
      [<0>] vfs_read+0xb4/0x1e0
      ...

# Or the whole system's blocked tasks, from the kernel:
    echo w > /proc/sysrq-trigger
    dmesg                   # "Showing all locks held" and
                            # blocked task backtraces

# The hung task detector will do it for you automatically:
    CONFIG_DETECT_HUNG_TASK=y
    # prints a backtrace for any task in D state for 120s
