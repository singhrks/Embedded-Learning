The threat model of a modern SoC

Before any mechanism makes sense you need to know what it defends against. This chapter sets out who the adversaries are, what they can reach, and why a chip needs four independent isolation layers rather than one good one.

What is worth protecting

Before defences, decide what is actually worth defending. Most designs protect the obvious secrets and forget something that turns out to be equally valuable, which is why writing this list explicitly matters.

Who you are defending against

"Secure" is meaningless without saying against whom. These adversaries differ enormously in what they can do — remote, local, physically present, or holding the chip in a lab — and a design that stops one may not slow another at all.

Ordered by capability. Each level can do everything below it.

  1. REMOTE ATTACKER
       sends network traffic, malicious files, malformed input
       defeated by: memory safety, input validation, sandboxing

  2. LOCAL UNPRIVILEGED CODE
       an app on the device, or a compromised process
       defeated by: the MMU, process isolation, seccomp, SELinux

  3. LOCAL PRIVILEGED CODE  (root / EL1 compromise)
       full control of the OS kernel
       THIS is where the security track begins. Everything up to
       here is the OS's job; from here on the OS is ASSUMED
       COMPROMISED.
       defeated by: TrustZone, the SMMU, interconnect firewalls

  4. MALICIOUS OR BUGGY PERIPHERAL
       a DMA-capable device programmed to read anywhere
       defeated by: the SMMU / IOMMU

  5. PHYSICAL ATTACKER, non-invasive
       JTAG probe, bus probing, cold-boot RAM extraction,
       glitching the clock or voltage
       defeated by: fused-off debug, memory encryption, glitch
       detectors, redundant checks

  6. PHYSICAL ATTACKER, invasive
       decapping the die, microprobing, focused ion beam
       defeated by: shields, sensors, and ultimately economics.
       You raise the cost; you do not eliminate the threat.

MOST embedded security work targets levels 3 and 4. Those are
where a mechanism can give a hard guarantee.
The assumption that defines this track

Assume the rich OS will be compromised. Linux is tens of millions of lines with a continuous stream of CVEs. Designing as though a kernel compromise is impossible is designing for a world that does not exist.

So the question becomes: what still holds when EL1 is fully attacker-controlled? Everything in this track answers that question, and it is why the mechanisms live in hardware, below the kernel, rather than in it.

Four independent layers

A modern SoC has several independent protection mechanisms, each answering a different question about a different kind of access. Knowing which layer catches what is how you tell a defence-in-depth design from one with a single point of failure.

   +--------------------------------------------------------+
   | 1. MMU — per-process isolation                          |
   |    constrains: CPU accesses                             |
   |    configured by: the OS kernel                         |
   |    defeated by: a kernel compromise                     |
   |    see: ARM chapters 12-16                              |
   +--------------------------------------------------------+
   | 2. SMMU / IOMMU — per-device isolation                  |
   |    constrains: DMA from peripherals                     |
   |    configured by: the OS, or a hypervisor               |
   |    defeated by: whoever owns the tables                 |
   |    see: chapters 02-07                                  |
   +--------------------------------------------------------+
   | 3. TrustZone — world isolation                          |
   |    constrains: EVERYTHING, by security state            |
   |    configured by: EL3 firmware, before the OS runs      |
   |    survives: a full kernel compromise                   |
   |    see: chapters 08-16                                  |
   +--------------------------------------------------------+
   | 4. XPU / interconnect firewall                          |
   |    constrains: every transaction on the bus             |
   |    configured by: firmware, then LOCKED until reset     |
   |    survives: even a compromised secure world            |
   |    see: chapters 17-20                                  |
   +--------------------------------------------------------+

WHY FOUR? Each has a different failure mode:

   · the MMU is configured by software you may not trust
   · the SMMU only sees transactions that pass through it, and
     some masters have no SMMU at all
   · TrustZone splits into two worlds, but everything inside one
     world is mutually trusting
   · the XPU is the last checkpoint and can be locked, but it is
     coarse-grained

No single layer covers everything. That is not redundancy — it is
coverage of disjoint threats.

Enumerate every master

The CPU is one master among many

A modern SoC has a dozen or more agents that issue memory transactions independently. Every one is a potential path to your assets, and the ones people forget are the dangerous ones.

   +------+ +------+ +------+ +------+ +------+ +------+
   | CPU  | | GPU  | | DSP  | | NPU  | | DMA  | | USB  |
   +------+ +------+ +------+ +------+ +------+ +------+
   +------+ +------+ +------+ +------+ +------+ +------+
   |Video | |Camera| |Crypto| | PCIe | | WiFi | |Sensor|
   |codec | |  ISP | |engine| |      | |modem | | hub  |
   +------+ +------+ +------+ +------+ +------+ +------+
   +----------------+ +-------------+ +------------------+
   | Power mgmt MCU | | Debug / JTAG| | Test / DFT ports |
   +----------------+ +-------------+ +------------------+
     ^^^ THE ONES PEOPLE FORGET — often with no SMMU in front
         of them, and full access to memory.

  For each master, ask three questions:
     1. What can it address?
     2. Who programs it, and from which security state?
     3. Is there an SMMU or firewall between it and memory?

  A single "no" to question 3, on a master a compromised kernel
  can program, bypasses everything above it.

The trusted computing base

TCB: everything that must be correct for security to hold

If any component has a bug, the guarantee fails. So the discipline is simple to state and hard to follow: make the TCB as small as possible, and be honest about what is in it.

A typical TCB for "the disk encryption key stays secret":

   boot ROM                   ~10 KB, immutable, unauditable
   BL2 trusted boot firmware  ~100 KB
   BL31 EL3 monitor (TF-A)    ~50 KB, RESIDENT forever
   trusted OS (OP-TEE)        ~300 KB
   the trusted application    ~10 KB
   the hardware               fuses, crypto engine, TZASC,
                              the SMMU, the interconnect
   ---------------------------------------------------------
   TOTAL                      ~500 KB of code

  NOT in the TCB: Linux, Android, every app, every driver.
  Tens of millions of lines that can be fully compromised
  without exposing the key.

  That ratio — 500 KB versus 30 M lines — IS the value of
  TrustZone. And it is why the design principle is:

     EVERY BYTE added to the secure world enlarges the attack
     surface of the most privileged code on the chip. A
     vulnerability in a trusted application is WORSE than one in
     the kernel.

  So a TEE should do as little as possible: hold keys, perform
  one operation, return a result. Not parse untrusted formats.
  Not implement a filesystem. Not run a network stack.

Design principles that actually help

A handful of design principles predate all of this hardware and still decide whether a system holds up. Each is violated routinely, and each violation shows up later as a specific class of vulnerability.

PrincipleIn practice
Least privilegeEvery master gets the minimum access it needs; every trusted app gets one capability
Fail closedThe default rule denies. Anything you forgot to configure is refused, not permitted.
Complete mediationEvery access checked, every time. No cached "already allowed" decisions.
Defence in depthThe four layers above. Assume any one will be bypassed.
Economy of mechanismA small TCB you can audit beats a large one you cannot
Open designSecurity from the key, not from secrecy of the mechanism
Separation of dutiesThe code that verifies is not the code that executes
Lock what will not changeConfiguration set before the OS starts should be immutable afterwards

Device lifecycle states

A device's security posture is not fixed — it changes between manufacture, provisioning, deployment and decommissioning. Several real compromises happened in a state the designers had not thought about.

Silicon moves through fuse-controlled states, each disabling more
capability. This is why "it works on my dev board" is not
evidence that it works on a production part.

   BLANK / VIRGIN
      no keys fused, debug fully open, secure boot OFF
      for silicon bring-up

   DEVELOPMENT
      test keys fused, debug open, secure boot may run with
      development keys

   SECURED / PRODUCTION
      production key hash fused, secure boot ENFORCED,
      SECURE DEBUG DISABLED, test ports closed
      this is what ships

   RMA / RETURN
      a controlled path to re-enable debug for failure analysis,
      usually requiring a SIGNED unlock token and often
      destroying the device keys first

  Transitions are ONE-WAY, enforced by one-time-programmable
  fuses. You cannot go back.

  CONSEQUENCES you will meet:
     · JTAG stops working on production silicon
     · a peripheral readable on the dev board aborts in the field
     · timing changes because a debug path was removed
     · firmware that worked now fails signature checks

  Always test on a part in the FINAL lifecycle state before
  shipping.

What these mechanisms do not do

Be honest about the limits
  • TrustZone does not stop physical attacks. An attacker with the die and a probe station reads the bus directly.
  • A TEE is not a secure element. It shares the CPU, caches and DRAM with the normal world, so it inherits every side channel. A separate secure element with its own die is a stronger — and slower, and more expensive — guarantee.
  • Secure boot does not protect a running system. It verifies what loads; it says nothing about what happens afterwards. Runtime attestation is a separate mechanism.
  • An SMMU does not help if it is not configured. Devices left in bypass are unprotected, and this is a very common misconfiguration.
  • None of this fixes bugs. A buffer overflow in a trusted application is still a buffer overflow — with more privilege.

Stating the limits precisely is not pessimism; it is what lets you pick the right mechanism for the actual threat.
