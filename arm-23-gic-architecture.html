The GIC: architecture

A separate hardware block that collects interrupt signals from every peripheral, prioritises them, decides which core should handle each, and enforces the secure/non-secure split. Understanding its structure is what makes interrupt routing, affinity and virtualisation comprehensible.

Why a dedicated block

With many cores and hundreds of interrupt sources, deciding which core handles what — and in which order — is too complex to leave to the cores themselves. The GIC is the dedicated block that does it.

A CPU core has ONE interrupt input (two, counting FIQ). A SoC has
hundreds of interrupt sources and several cores. Something must:

   · multiplex hundreds of sources onto a few core inputs
   · PRIORITISE — a timer tick must not delay a critical fault
   · ROUTE — decide which core handles which interrupt
   · MASK selectively, per source and per priority
   · handle EDGE versus LEVEL signalling per source
   · enforce SECURITY — keep secure interrupts away from the
     normal world (security track)
   · support VIRTUALISATION — inject interrupts into a guest
     without a hypervisor trap on every one

That block is the Generic Interrupt Controller. It is architected
by Arm, so the programming model is the same across every SoC —
which is why one Linux driver serves them all.

The move from MMIO to system registers in GICv3 matters: acknowledging an interrupt becomes an MRS rather than a device read, which is dramatically faster and removes the barriers that MMIO access requires (chapter 11).

The components

The GIC is not one unit but several, split by what they are responsible for and where they physically sit. Knowing which piece owns which registers is most of what you need to program it.

Interrupt ID ranges

The GIC partitions its interrupt ID space by scope — who the interrupt belongs to — and that partition is baked into the number itself, so you can tell a great deal about an interrupt just from its ID without looking anything else up. SGIs and PPIs are per-core: each core has its own instance of IDs 0–31, so "IPI number 3" or "the timer PPI" means something different, privately, on every core simultaneously. SPIs and LPIs are global: there is exactly one interrupt 45 in the whole system, shared across all cores, which is why an SPI needs the routing and affinity mechanism the rest of this chapter describes — something has to decide which core actually takes it. LPIs exist because SPIs are a scarce, statically-configured resource, and a modern SoC with hundreds of MSI-capable PCIe and platform devices needed an ID space that scales past the low-thousands limit of the SPI range.

Affinity routing

Routing an interrupt to a specific core in a large system needs a way to name that core. The hierarchical scheme used here also appears in other parts of the architecture.

/* GICv3 identifies cores by their MPIDR affinity hierarchy rather
   than by a bitmask — which is what allows more than 8 cores. */

        mrs     x0, mpidr_el1
/*  MPIDR_EL1:
       Aff0 [7:0]    core within a cluster (or thread)
       Aff1 [15:8]   cluster
       Aff2 [23:16]  group of clusters
       Aff3 [39:32]  higher level still                        */

/* An SPI's target is written to GICD_IROUTER<n>: */
        GICD_IROUTER(intid) = (aff3 << 32) | (aff2 << 16) |
                              (aff1 << 8)  |  aff0;
/* or with bit 31 set (Interrupt_Routing_Mode = 1) it means
   "any participating core" — 1-of-N delivery, which lets the
   GIC pick an idle core.                                     */

/* Sending an SGI is a SYSTEM REGISTER write, not MMIO: */
        msr     ICC_SGI1R_EL1, x0
/*  x0 encodes: the target affinity, a 16-bit target list within
    the cluster, and the SGI number. That is how Linux sends a
    reschedule IPI or a TLB shootdown request.                */
# control affinity from userspace
cat /proc/irq/24/smp_affinity_list
echo 2 > /proc/irq/24/smp_affinity_list        # pin to CPU2
echo 3 > /proc/irq/24/smp_affinity             # bitmask form

# irqbalance moves them automatically — and is usually wrong for
# latency-sensitive work. Disable and pin by hand:
systemctl stop irqbalance

# keep interrupts entirely off the real-time cores
# kernel cmdline: irqaffinity=0,1 isolcpus=2,3

Security groups

Interrupts are partitioned by security state, so that secure-world interrupts cannot be taken, masked or observed by non-secure software. This is the interrupt half of TrustZone.

Every interrupt belongs to a GROUP, and the group determines
which exception level receives it and as which signal:

   Group 0          → FIQ, always taken to EL3
                      Secure firmware's interrupts

   Secure Group 1   → IRQ when in the secure world,
                      FIQ when in the non-secure world
                      Trusted OS interrupts

   Non-secure Group 1 → IRQ
                        Ordinary OS interrupts

  THE CONSEQUENCE that matters: a Non-secure OS clearing PSTATE.I
  cannot mask secure interrupts, because they arrive as FIQ and
  are routed to EL3. The secure world can always preempt the
  normal world — which is what makes a TEE's timing guarantees
  meaningful (security track).

  Configured in GICD_IGROUPR / GICD_IGRPMODR, and only writable
  from the secure world.

Priority and preemption

Priority decides not only which pending interrupt is taken first, but whether an arriving interrupt can preempt one already being handled. That second question is what makes real-time behaviour possible.

/* 8-bit priority values, and LOWER NUMBER = HIGHER PRIORITY.
   (This trips people up constantly.)                         */

        GICD_IPRIORITYR(intid) = 0x80;     /* mid priority */

/* Not all 8 bits are necessarily implemented — write 0xFF and
   read back to discover how many are: */
static unsigned priority_bits(void)
{
        writeb(0xFF, GICD_IPRIORITYR(0));
        return 8 - __builtin_ctz(readb(GICD_IPRIORITYR(0)));
        /* commonly 4 or 5 bits → 16 or 32 usable levels */
}

/* THREE registers control what gets through: */

   ICC_PMR_EL1      Priority Mask: interrupts with priority
                    NUMERICALLY >= this value are blocked.
                    0xFF = allow everything, 0x00 = block all.

   ICC_BPR1_EL1     Binary Point: splits the priority field into
                    a GROUP part and a SUB-priority part. Only the
                    group part participates in PREEMPTION, so this
                    controls how much nesting you allow.

   ICC_RPR_EL1      Running Priority: the priority of the
                    interrupt currently being handled. A new
                    interrupt preempts only if its group priority
                    is higher.

/* Linux uses PMR for "pseudo-NMI": rather than masking with
   PSTATE.I (which blocks everything), it raises PMR so that
   ordinary interrupts are blocked but a high-priority NMI still
   gets through. That is how arm64 gets NMIs without hardware
   NMI support.                                               */

The ITS and MSIs

Message-signalled interrupts arrive as memory writes rather than wires, which scales far better and allows vast numbers of them. Translating those messages into interrupts is a dedicated unit's whole job.

A PCIe device signals an interrupt by WRITING to an address —
there is no wire. The GIC must turn that write into an interrupt
for a specific core.

   device writes (DeviceID, EventID) to GITS_TRANSLATER
        │
   ┌────▼────────────────────────────────────────┐
   │  ITS — Interrupt Translation Service         │
   │                                              │
   │  Device Table:  DeviceID → an ITT            │
   │  ITT:           EventID  → (LPI ID, Collection) │
   │  Collection Table: Collection → Redistributor│
   └────┬────────────────────────────────────────┘
        ▼
   the LPI is made pending in the target redistributor's
   PENDING TABLE (in memory), and the core is signalled

  Two levels of indirection, both table-driven, because there can
  be tens of thousands of LPIs and they must be redirected when
  a VM migrates between cores.

  Software configures it with COMMANDS in a queue, exactly like
  the SMMU (security track):
     MAPD    map a DeviceID to an ITT
     MAPTI   map an EventID to an LPI and collection
     MOVI    move an LPI to a different collection (core)
     INV     invalidate cached configuration
     SYNC    wait for completion

  GICv4 adds direct injection: a VM's LPI is delivered to the
  guest WITHOUT a hypervisor exit at all.

Virtualisation support

A guest operating system needs to program an interrupt controller, but must not be allowed to program the real one. The GIC provides a virtual interface for exactly this.

/* Without hardware help, every guest interrupt would need a
   hypervisor trap: take the interrupt at EL2, work out that it
   belongs to a guest, and inject it. The GIC provides a LIST
   REGISTER mechanism to avoid that.                         */

   ICH_LR<n>_EL2      List Registers — the hypervisor writes a
                      virtual interrupt here, and the GIC delivers
                      it to the guest DIRECTLY. The guest
                      acknowledges and EOIs it with its own
                      ICC_* registers, with NO exit.

   ICH_HCR_EL2        hypervisor control: enable virtual
                      interfaces, request maintenance interrupts

   ICH_VMCR_EL2       the guest's virtual control state

   ICV_*_EL1          the guest's view — when HCR_EL2.IMO is set,
                      the guest's ICC_* accesses are REDIRECTED
                      to these virtual registers

/* Cost: the hypervisor must still populate the list registers on
   entry and read back state on exit, and there are only a few
   (typically 4-16). A guest with many pending interrupts causes
   MAINTENANCE INTERRUPTS to refill them.

   GICv4's direct injection removes even that for LPIs.      */

Initialising the GIC

Bringing the GIC up is a defined sequence, and the ordering matters. This is what a bootloader or an early kernel actually does.

/* Distributor — once, globally */
        GICD_CTLR = 0;                          /* disable while
                                                   configuring */
        for each SPI:
                GICD_ICENABLER = all;           /* disable      */
                GICD_ICPENDR   = all;           /* clear pending */
                GICD_IPRIORITYR = 0xA0;         /* default prio  */
                GICD_ICFGR     = level or edge;
                GICD_IGROUPR   = 1;             /* NS Group 1    */
                GICD_IROUTER   = target affinity;
        GICD_CTLR = ARE_NS | EnableGrp1NS;      /* affinity routing
                                                   + enable       */

/* Redistributor — per core */
        GICR_WAKER &= ~ProcessorSleep;          /* wake it        */
        wait until (GICR_WAKER & ChildrenAsleep) == 0;
        configure SGIs and PPIs in GICR_SGI_base

/* CPU interface — per core, SYSTEM REGISTERS */
        msr     ICC_SRE_EL1, #1        /* enable system register
                                          access — MUST be first  */
        isb
        msr     ICC_PMR_EL1, #0xFF     /* unmask all priorities   */
        msr     ICC_BPR1_EL1, #0
        msr     ICC_IGRPEN1_EL1, #1    /* enable Group 1          */
        isb

/* The GICR_WAKER dance is a common bring-up trap: a
   redistributor comes out of reset ASLEEP and delivers nothing
   until woken, with no error to indicate why.               */

Device tree description

Linux does not probe the GIC's configuration; it is described in the device tree. Reading that description is often the quickest way to understand an unfamiliar system's interrupt topology.

gic: interrupt-controller@2f000000 {
        compatible = "arm,gic-v3";
        #interrupt-cells = <3>;
        interrupt-controller;
        reg = <0x0 0x2f000000 0x0 0x10000>,     /* GICD  */
              <0x0 0x2f100000 0x0 0x200000>;    /* GICR  */
        interrupts = <GIC_PPI 9 IRQ_TYPE_LEVEL_HIGH>;  /* maintenance */

        its: msi-controller@2f020000 {
                compatible = "arm,gic-v3-its";
                msi-controller;
                reg = <0x0 0x2f020000 0x0 0x20000>;
        };
};

/* And a device referencing it: */
        interrupts = <GIC_SPI 56 IRQ_TYPE_LEVEL_HIGH>;
/*                    ^type    ^number  ^trigger
   Note the SPI number here is RELATIVE to 32: SPI 56 is INTID 88.
   Mixing these up is a very common device tree error, and the
   symptom is an interrupt that never fires.              */
