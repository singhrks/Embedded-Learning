Diffie–Hellman and key exchange

Two parties who have never met agree on a shared secret over a channel an attacker is reading. The most surprising result in cryptography, and the foundation of every modern secure channel.

The basic exchange

Two parties who have never met, communicating over a channel an attacker can read, can still agree on a shared secret. That result is genuinely surprising the first time, and it underpins essentially all secure communication.

   PUBLIC PARAMETERS: a large prime p, a generator g.
   Both are known to everyone, including the attacker.

     ALICE                                    BOB
     a = random secret                        b = random secret
     A = g^a mod p        ---- A ---->
                          <---- B ----        B = g^b mod p

     s = B^a mod p                            s = A^b mod p
       = (g^b)^a                                = (g^a)^b
       = g^(a*b) mod p    ===== SAME =====      = g^(a*b) mod p

   THE EAVESDROPPER SEES p, g, A and B.
   To compute s they must find a from g^a - the DISCRETE
   LOGARITHM PROBLEM (chapter 11). No efficient classical
   algorithm is known.

   THE SHARED SECRET IS NOT A KEY YET. g^(a*b) mod p is a
   structured group element, not uniform bits. RUN IT THROUGH
   A KDF:

       k_enc = HKDF(s, salt, "protocol v1 encryption")
       k_mac = HKDF(s, salt, "protocol v1 mac")

   Using the raw DH output as an AES key is a real and common
   bug (chapter 10).

   WHAT THIS BUYS AND WHAT IT DOES NOT:
     · a shared secret over a public channel        YES
     · secrecy against a PASSIVE eavesdropper       YES
     · FORWARD SECRECY, if a and b are ephemeral    YES
     · protection against an ACTIVE attacker        NO
     · authentication of who you are talking to     NO
     · a usable symmetric key without a KDF         NO

The man in the middle

Key exchange alone protects against eavesdropping and not against an attacker who sits in the middle and talks to both sides. Closing that gap requires authentication, which is a separate problem.

/* UNAUTHENTICATED DH IS COMPLETELY BROKEN AGAINST AN ACTIVE
   ATTACKER, and this is not a subtle failure.            */

    ALICE          MALLORY          BOB
      A  ------->   (drops A)
                     M1  ------->
                     <-------  B    (drops B)
      <-------  M2

    Alice and Mallory share s1 = g^(a*m1).
    Mallory and Bob   share s2 = g^(m2*b).
    Mallory decrypts everything from Alice, reads it, and
    re-encrypts it to Bob. NEITHER SIDE SEES ANYTHING WRONG.

/* THE FIX IS ALWAYS AUTHENTICATION - proving that the public
   value you received belongs to the party you intended to
   talk to. The options:

   1. SIGN THE EPHEMERAL PUBLIC VALUES with a long-term key
      whose certificate chains to a trusted root. This is
      TLS's ECDHE + certificate (chapters 16, 17).

   2. STATIC-EPHEMERAL DH: one side's key is long-term and
      already known (e.g. burned into the device at
      manufacture), the other's is ephemeral.

   3. A PASSWORD-AUTHENTICATED KEY EXCHANGE (PAKE) - SPAKE2,
      OPAQUE, or the CPace family. Both sides prove knowledge
      of a shared low-entropy secret WITHOUT it being
      brute-forceable offline. This is how a device pairs
      with a phone using a 6-digit code.

   4. OUT-OF-BAND VERIFICATION: derive a short fingerprint
      from the transcript and have humans compare it. The
      "safety number" in a messaging app, or the SSH host key
      fingerprint you were supposed to check.

   5. TOFU - trust on first use. Remember the peer's key and
      alarm if it ever changes. SSH's known_hosts. Weak on
      the first connection, strong afterwards.

/* FOR EMBEDDED DEVICES the usual answer is a
   FACTORY-PROVISIONED IDENTITY: a device key pair generated
   at manufacture, its private half in a secure element, and
   a certificate signed by the vendor CA. The device then
   authenticates every exchange with it (chapter 18).     */
Forward secrecy

Use a fresh, ephemeral a and b for every session and destroy them afterwards. An attacker who records all the traffic today and steals the device's long-term key in five years still cannot decrypt those recordings — the ephemeral secrets are gone. This is the "E" in ECDHE, and it is the single most valuable property a protocol design can have. A protocol that encrypts a session key to a long-term key (RSA key transport, chapter 12) has no forward secrecy at all, which is why TLS 1.3 removed it.

ECDH and X25519

The elliptic-curve form, which achieves the same result with far smaller keys and less computation. It is what modern protocols actually use.

/* The same protocol, in an elliptic curve group instead of
   the integers mod p (chapter 14). Same maths, far smaller
   numbers.                                                */

    private:  a random scalar d
    public:   the point  Q = d * G
    shared:   d_A * Q_B = d_A * d_B * G = d_B * Q_A

/* SIZES, and this is the whole reason ECC won:
     finite-field DH, 128-bit security:  3072-bit p
                                         -> 384-byte messages
     ECDH P-256, 128-bit security:       -> 32-64 bytes
     X25519:                             -> 32 bytes exactly

/* --- X25519: the one to use --- */
    #include <sodium.h>

    /* each side */
    unsigned char sk[crypto_kx_SECRETKEYBYTES];
    unsigned char pk[crypto_kx_PUBLICKEYBYTES];
    crypto_kx_keypair(pk, sk);

    /* exchange pk over the wire (32 bytes), then: */
    unsigned char rx[crypto_kx_SESSIONKEYBYTES];
    unsigned char tx[crypto_kx_SESSIONKEYBYTES];
    if (crypto_kx_client_session_keys(rx, tx, pk, sk,
                                      server_pk) != 0)
            return BAD_PEER_KEY;

    /* NOTE: SEPARATE rx AND tx KEYS, derived for you. That
       is the key-separation rule from chapter 08 built into
       the API.                                            */

/* THE LOW-LEVEL FORM, when you need the raw shared value: */
    unsigned char q[crypto_scalarmult_BYTES];
    if (crypto_scalarmult(q, my_sk, their_pk) != 0)
            return BAD_PEER_KEY;    /* all-zero output:
                                       a small-order point */

    /* AND THEN ALWAYS: */
    crypto_generichash_state h;
    crypto_generichash_init(&h, NULL, 32, 32);
    crypto_generichash_update(&h, q, 32);
    crypto_generichash_update(&h, client_pk, 32);
    crypto_generichash_update(&h, server_pk, 32);
    crypto_generichash_final(&h, session_key, 32);

/* HASHING BOTH PUBLIC KEYS ALONGSIDE THE SHARED SECRET binds
   the key to the specific exchange. Without it, some
   protocols admit key-reuse and unknown-key-share attacks.

/* WHY X25519 IS THE DEFAULT RECOMMENDATION:
     · every 32-byte string is a valid public key - no point
       validation code to get wrong
     · the Montgomery ladder is naturally constant time
     · clamping removes the small-subgroup problem
     · fast: ~100 microseconds on a Cortex-M4
     · no patents, no NIST-curve provenance questions
     · one function, no parameter choices to get wrong

   USE P-256 INSTEAD ONLY WHEN a standard, a certificate
   profile, or a hardware accelerator requires it.       */

Where key exchange goes wrong

The mathematics is sound and the implementations fail in specific, recurring ways — mostly by omitting validation of what the other party sent.

/* --- 1. NO AUTHENTICATION --- */
    Covered above. The most common failure in home-grown
    protocols, and it is total.

/* --- 2. NOT VALIDATING THE PEER'S PUBLIC VALUE --- */
    Finite-field DH: reject y <= 1, y >= p-1, and check
    y^q ≡ 1 mod p for the subgroup order q. Otherwise:
    small-subgroup confinement (chapter 11).

    ECDH on a NIST curve: verify the point is ON THE CURVE.
    An INVALID CURVE ATTACK sends a point on a different,
    weaker curve; the scalar multiplication still "works" and
    leaks the private key a few bits at a time. This broke
    several TLS libraries and a Bluetooth implementation.

    X25519: the output being all zeros means a small-order
    input. Check it, or use a library that does.

/* --- 3. REUSING EPHEMERAL KEYS --- */
    Caching a "temporary" key across sessions - usually done
    for performance on a slow MCU - DESTROYS FORWARD SECRECY
    and enables key-recovery attacks against unvalidated
    implementations. If you must cache, cache for seconds,
    not for the device's lifetime.

/* --- 4. USING THE RAW SHARED SECRET AS A KEY --- */
    Always through a KDF, always with a context string.

/* --- 5. NOT BINDING THE TRANSCRIPT --- */
    Authenticate the ENTIRE HANDSHAKE - every message, in
    order, including the negotiated parameters. Otherwise a
    DOWNGRADE ATTACK works: the attacker strips the strong
    ciphersuites from the client's offer and both sides
    happily negotiate the weak one, each believing the other
    only supported it. LOGJAM downgraded TLS to 512-bit
    export DH this way; FREAK did the same to export RSA.

/* --- 6. WEAK OR SHARED PARAMETERS --- */
    LOGJAM again: a huge fraction of the internet used the
    SAME 1024-bit DH group. Precomputation against one group
    - expensive but feasible for a state actor - then breaks
    every connection using it. Use named, modern groups
    (RFC 7919) or, better, use a curve.

/* --- 7. TIMING LEAKS IN THE SCALAR MULTIPLY --- */
    Chapter 19. Use a constant-time implementation; X25519's
    ladder is one by construction.

/* --- 8. NO REPLAY PROTECTION ON 0-RTT DATA --- */
    TLS 1.3's early data can be replayed by an attacker. Only
    send idempotent requests in it.                       */

Real handshake patterns

Real protocols combine key exchange with authentication in a few established patterns, each making different assumptions about what the parties already know about each other.

/* --- TLS 1.3, simplified (chapter 17) --- */
    ClientHello:  key_share = ephemeral X25519 or P-256 pk
    ServerHello:  key_share = server's ephemeral pk
      -> both derive the handshake secret immediately, so
         the REST OF THE HANDSHAKE IS ENCRYPTED
    Certificate + CertificateVerify: the server SIGNS the
      transcript, authenticating the exchange
    Finished (both sides): a MAC over the whole transcript,
      closing the downgrade hole
    One round trip. Forward secret. Authenticated.

/* --- NOISE PROTOCOL FRAMEWORK --- */
    A construction kit for DH handshakes with a formal naming
    scheme. Used by WireGuard, WhatsApp, Lightning.

      Noise_NN   neither party authenticated
      Noise_NK   the responder's static key is known to the
                 initiator     <-- typical for a device
                                    talking to a known server
      Noise_XX   both authenticate during the handshake
      Noise_IK   initiator knows the responder's static key
                 and sends its own immediately

    EACH PATTERN IS A SHORT SEQUENCE OF DH OPERATIONS, mixed
    into a running hash. WireGuard's whole handshake is about
    150 lines. FOR AN EMBEDDED PROTOCOL, PICKING A NOISE
    PATTERN IS ALMOST ALWAYS BETTER THAN DESIGNING ONE.

/* --- THE DEVICE PROVISIONING PATTERN --- */
    factory:  generate a device key pair inside the secure
              element; the private half NEVER LEAVES
              (chapter 18)
              vendor CA signs the public half -> device cert
    field:    device does ECDHE with the server
              device signs the transcript with its device key
              server validates the cert chain to the vendor
              root and checks the device is not revoked
              server signs its side; device validates against
              a root PINNED IN FIRMWARE

    NOTE THE PINNING. A device that trusts the general
    public CA list can be attacked by any compromised CA in
    the world. Pin your own root (chapter 16).           */
