Mutual exclusion from first principles

Before you can use a mutex well you have to know what one is made of. This chapter builds mutual exclusion up from nothing — the software-only algorithms that almost work, the hardware instruction that makes it possible, and the futex trick that makes it fast.

What we are trying to buy

Before any implementation, it is worth stating what a correct mutual-exclusion mechanism must actually guarantee. Several plausible-looking schemes fail one of these, and knowing the list is how you spot that.

   A correct mutual-exclusion protocol needs four properties.
   Dropping any one of them is a real bug with a real name.

   1. MUTUAL EXCLUSION
        at most one thread in the critical section at a time.
        Without it: the thing you were trying to prevent.

   2. PROGRESS  (deadlock freedom)
        if nobody is in the critical section and somebody
        wants in, somebody gets in.
        Without it: deadlock (chapter 14).

   3. BOUNDED WAITING  (starvation freedom)
        a thread that wants in gets in after a bounded number
        of other entries.
        Without it: starvation - a thread waits for ever
        while others take turns ahead of it.

   4. NO ASSUMPTIONS ABOUT SPEED
        correctness must not depend on relative thread speeds,
        core counts, or the scheduler.
        Without it: works on your laptop.

   Note what is NOT on the list: fairness in the FIFO sense,
   and performance. Most real mutexes deliberately give up
   strict fairness to go faster (see barging, below).

Software-only: interesting, and not what you use

Mutual exclusion can be built from ordinary loads and stores alone, which is a genuinely surprising result. These algorithms are impractical today and worth seeing once, because they show exactly what the hardware instructions later replace.

/* PETERSON'S ALGORITHM - two threads, no special instruction.
   Correct on a sequentially consistent machine.            */

atomic_bool want[2] = { false, false };
atomic_int  turn    = 0;

void lock(int me)
{
        int other = 1 - me;
        want[me] = true;        /* I want in                  */
        turn = other;           /* but you go first           */
        while (want[other] && turn == other)
                ;               /* spin                       */
}

void unlock(int me) { want[me] = false; }

/* WHY IT WORKS: the `turn` write is a deliberate deference.
   If both threads arrive together, both set turn, and the
   LAST write wins - so exactly one of them sees turn pointing
   away from itself and proceeds.

   WHY YOU WILL NEVER USE IT:

   1. It is for exactly two threads. Extending it (Lamport's
      bakery algorithm) needs O(n) storage and O(n) scanning
      per acquisition.

   2. It spins. Every waiter burns a core.

   3. THE REAL KILLER: it is only correct under sequential
      consistency, and no real CPU provides that. On ARM or
      x86 the store to `want[me]` and the load of
      `want[other]` can be reordered, and both threads enter.
      Making it correct needs full barriers in both places -
      at which point you are paying more than a real mutex
      costs.

   It is on the exam because it proves mutual exclusion is
   possible without hardware help. It is not in your code
   because hardware help is cheaper.                        */

The instruction that changes everything

Every practical lock rests on an instruction the hardware guarantees is indivisible. There are a few such primitives, and they differ in what they promise under contention.

/* What we need is one indivisible read-modify-write. Every
   architecture provides one; they differ in shape.        */

/* x86: exchange, with an implicit lock prefix. */
        xchg    eax, [lock]        ; atomically swap

/* x86: compare-and-swap, the general form. */
        lock cmpxchg [ptr], ebx    ; if [ptr]==eax, [ptr]=ebx

/* ARM: LOAD-LINKED / STORE-CONDITIONAL. No single atomic RMW -
   instead a pair, where the store FAILS if anyone touched the
   line in between.                                          */
retry:  ldaxr   w1, [x0]           ; load-acquire exclusive
        cmp     w1, #0
        b.ne    retry              ; already locked, spin
        mov     w2, #1
        stlxr   w3, w2, [x0]       ; store-release exclusive
        cbnz    w3, retry          ; w3 != 0 means we lost the
                                   ; reservation - try again

/* ARMv8.1-A LSE adds true single-instruction atomics, which
   scale far better under contention because they can be done
   at the point of coherency instead of bouncing the line:   */
        swpal   w1, w2, [x0]       ; swap
        casal   w1, w2, [x0]       ; compare-and-swap
        ldaddal w1, w2, [x0]       ; atomic add

/* In C, you write none of this: */
        while (atomic_exchange_explicit(&lock, 1,
                                        memory_order_acquire))
                ;                          /* spin lock       */
        /* critical section */
        atomic_store_explicit(&lock, 0, memory_order_release);
Why acquire and release, specifically

The lock is not just about exclusion — it is about visibility. Acquiring with memory_order_acquire guarantees that everything the previous holder did before releasing is visible to you afterwards. Releasing with memory_order_release guarantees your writes are visible to the next acquirer. A "mutex" that excluded correctly but gave no ordering guarantee would still let you read stale data. Chapter 12 is this idea in full.

A spinlock, properly written

The simplest usable lock busy-waits rather than sleeping. That is the right trade only under specific conditions, and the naive implementation performs badly on a multiprocessor for reasons worth understanding.

/* The naive version, and why each fix matters. */

/* v1: correct, and terrible under contention. */
void lock_v1(atomic_flag *l) {
        while (atomic_flag_test_and_set_explicit(l, memory_order_acquire))
                ;
}
/* Every waiter hammers the cache line with an atomic RMW.
   With 16 waiters the line ping-pongs 16 ways and the HOLDER
   cannot even write its own data. Contention makes it slower
   the more threads you add.                                */

/* v2: test-and-test-and-set. Spin on a plain LOAD, which can
   sit in the local cache in Shared state and generate no bus
   traffic at all. Only attempt the expensive RMW when it
   looks free.                                              */
void lock_v2(atomic_bool *l) {
        for (;;) {
                if (!atomic_exchange_explicit(l, true,
                                              memory_order_acquire))
                        return;
                while (atomic_load_explicit(l, memory_order_relaxed))
                        cpu_relax();          /* pause / yield  */
        }
}

/* v3: add back-off, so the thundering herd on release does not
   all collide at once. */
void lock_v3(atomic_bool *l) {
        unsigned backoff = 1;
        for (;;) {
                if (!atomic_exchange_explicit(l, true,
                                              memory_order_acquire))
                        return;
                while (atomic_load_explicit(l, memory_order_relaxed)) {
                        for (unsigned i = 0; i < backoff; i++)
                                cpu_relax();
                        if (backoff < 1024) backoff *= 2;
                }
        }
}

/* v4: give up and sleep, because spinning past a few hundred
   cycles is worse than a context switch. That is a MUTEX. */

/* And note none of v1-v3 is FAIR: a thread that just released
   can immediately re-acquire while an older waiter is still
   backing off. A TICKET LOCK fixes that:                   */

struct ticket { atomic_uint next, now_serving; };

void ticket_lock(struct ticket *t) {
        unsigned me = atomic_fetch_add_explicit(&t->next, 1,
                                        memory_order_relaxed);
        while (atomic_load_explicit(&t->now_serving,
                                    memory_order_acquire) != me)
                cpu_relax();
}
void ticket_unlock(struct ticket *t) {
        atomic_fetch_add_explicit(&t->now_serving, 1,
                                  memory_order_release);
}
/* Strict FIFO, and every waiter still spins on one shared
   line. MCS and CLH locks fix that too by giving each waiter
   its own line to spin on - which is what the kernel uses for
   contended spinlocks.                                     */
Never spin where you can be preempted

A spinlock assumes the holder is running and will release shortly. If the holder is descheduled — because you are in user space, or in a VM whose vCPU was taken away (virtualisation chapter 08) — every waiter burns a full timeslice waiting for a thread that cannot run. This is lock-holder preemption, and it is why spinlocks belong in the kernel with preemption disabled, not in application code.

The futex: spin a little, then sleep

A mutex that always entered the kernel would be far too slow, and one that never did could not block. The solution is a hybrid that stays in user space when uncontended and calls the kernel only when a thread must actually wait.

   A real mutex wants both: no syscall in the fast path, and
   no spinning in the slow one. Linux's futex gives exactly
   that by making the KERNEL involved only on contention.

   state: 0 = free, 1 = locked, 2 = locked and someone waits

   LOCK
     CAS 0 -> 1 succeeds?          done. NO SYSCALL AT ALL.
                                   This is the common case and
                                   it costs ~20 ns.
     otherwise:
       spin briefly (adaptive)
       still locked?
         set state to 2  ("I am going to sleep")
         futex(FUTEX_WAIT, addr, 2)
           kernel: "is *addr still 2? then queue me and sleep"
           - the recheck inside the kernel is what closes the
             race between deciding to sleep and sleeping

   UNLOCK
     if state was 1:  store 0.     NO SYSCALL.
     if state was 2:  store 0, then
                      futex(FUTEX_WAKE, addr, 1)

   THE WHOLE TRICK is that "2" records the existence of
   waiters, so the unlock path knows whether a syscall is
   needed. An uncontended mutex never enters the kernel in
   either direction.

   Windows: WaitOnAddress / WakeByAddressSingle.
   macOS:   __ulock_wait / os_unfair_lock.
   Same idea everywhere.

How it shows up

SymptomCause
Hand-rolled lock works on x86, fails on ARMMissing barriers; the algorithm assumed sequential consistency
Spinlock gets slower as threads are addedTest-and-set hammering one cache line — needs test-and-test-and-set
One thread never acquires while others cycleBarging; the lock is unfair. Use a ticket lock
A core is pinned at 100% doing nothingSpinning on a lock whose holder is descheduled
