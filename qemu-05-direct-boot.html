Booting a kernel directly

-kernel lets you skip the bootloader entirely: QEMU loads your image, synthesises the handoff a bootloader would have performed, and jumps to it. It turns a five-minute build-flash-boot cycle into a two-second one, and it is how you should develop everything until the boot chain itself is the thing you are testing.

What -kernel actually does

   Normally, on real hardware:

     ROM -> BL1 -> BL2 -> BL31 (EL3) -> U-Boot (EL2/EL1)
                                          |
                                          | reads a device tree
                                          | loads Image + initrd
                                          | sets x0 = DTB address
                                          | jumps to the kernel
                                          v
                                        Linux

   With -kernel, QEMU IS the bootloader:

     1. Parse the image. An arm64 "Image" has a 64-byte header:
            0x00  code0, code1        (branch instructions)
            0x08  text_offset         (where to load, relative
                                       to the start of RAM)
            0x10  image_size
            0x18  flags
            0x38  magic "ARM\x64"
        QEMU reads text_offset and image_size and places the
        image accordingly - usually 0x4008_0000.

     2. Load the initrd, if given, somewhere above the kernel,
        and record its address and size.

     3. GENERATE the device tree (chapter 4), then PATCH it:
            /chosen/bootargs        = your -append string
            /chosen/linux,initrd-start
            /chosen/linux,initrd-end
        and write it into guest RAM.

     4. Write a tiny boot stub at the start of RAM that:
            sets x0 = DTB address
            x1 = x2 = x3 = 0
            branches to the kernel entry point
        For -smp N, secondary CPUs park in a PSCI-compatible
        wait loop.

     5. Release the CPU at the stub.

   The kernel cannot tell the difference, which is the point.

The smallest thing that boots

# You need three things: a kernel, a console, and a root
# filesystem. Start with only the first two.

$ qemu-system-aarch64 \
    -M virt -cpu cortex-a57 -m 512M -nographic \
    -kernel Image \
    -append "console=ttyAMA0 earlycon"

# It boots, prints, and panics with "No working init found",
# because there is no root filesystem. That panic is SUCCESS:
# it means the kernel ran to the end of its own initialisation.

# Now add an initramfs and you have a usable system:
$ qemu-system-aarch64 \
    -M virt -cpu cortex-a57 -m 512M -nographic \
    -kernel Image -initrd initramfs.cpio.gz \
    -append "console=ttyAMA0 earlycon rdinit=/bin/sh"

# Exit with Ctrl-A x.  (Ctrl-A c switches to the monitor.)

# The four arguments that matter, and why:
#
#   console=ttyAMA0   the PL011 at 0x09000000. WITHOUT THIS you
#                     see nothing after the kernel takes over
#                     its own console. It is the single most
#                     common "it hangs" cause.
#
#   earlycon          console output BEFORE the driver probes.
#                     On virt, the kernel finds the address in
#                     /chosen/stdout-path, so plain "earlycon"
#                     works with no arguments.
#
#   rdinit=/bin/sh    run a shell from the initramfs instead of
#                     looking for /sbin/init.
#
#   -nographic        no window; serial to your terminal.
#                     Implies -serial mon:stdio.
Always add earlycon while bringing something up

Without it, the window between "kernel entered" and "console driver probed" is silent — and that window contains the MMU setup, the memory-map parse and the device-tree parse, which is exactly where early boot failures live. With it, you see Booting Linux on physical CPU 0x0 almost immediately, and a hang after that is a much smaller problem than a hang before it.

Building a kernel worth booting

$ git clone --depth=1 -b v6.8 \
    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git
$ cd linux

$ export ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-
$ make defconfig

# defconfig already includes virtio, PL011 and the GIC. Add the
# things you will want for this site's tracks:
$ scripts/config --enable  DEBUG_INFO_DWARF5 \
                 --enable  GDB_SCRIPTS \
                 --enable  DEBUG_KERNEL \
                 --enable  DYNAMIC_DEBUG \
                 --enable  MAGIC_SYSRQ \
                 --enable  KGDB \
                 --enable  FTRACE \
                 --enable  FUNCTION_TRACER \
                 --enable  KPROBES \
                 --enable  TEE \
                 --enable  OPTEE \
                 --enable  BLK_DEV_INITRD \
                 --set-val CONFIG_RANDOMIZE_BASE n
$ make olddefconfig
$ make -j$(nproc) Image modules

# Result: arch/arm64/boot/Image   (uncompressed - what -kernel
#                                  wants)
#         arch/arm64/boot/Image.gz (what a real board uses)
#         vmlinux                  (with symbols - what GDB
#                                   wants, chapter 11)

# RANDOMIZE_BASE off is deliberate: KASLR moves the kernel
# every boot, and then your GDB symbols are at the wrong
# addresses. Turn it off for debugging, on for realism.
# Alternatively pass "nokaslr" in -append.

A root filesystem in thirty seconds

# Option 1: busybox, statically linked. Smallest and fastest.

$ wget https://busybox.net/downloads/busybox-1.36.1.tar.bz2
$ tar xf busybox-1.36.1.tar.bz2 && cd busybox-1.36.1
$ make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
$ sed -i 's/# CONFIG_STATIC is not set/CONFIG_STATIC=y/' .config
$ make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)
$ make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
       CONFIG_PREFIX=../rootfs install

$ cd ../rootfs
$ mkdir -p proc sys dev etc/init.d
$ cat > init <<'EOF'
#!/bin/sh
mount -t proc  none /proc
mount -t sysfs none /sys
mount -t devtmpfs none /dev
echo "=== up ==="
exec /bin/sh
EOF
$ chmod +x init
$ find . | cpio -o -H newc | gzip > ../initramfs.cpio.gz

# Boot it:
$ qemu-system-aarch64 -M virt -cpu cortex-a57 -m 512M -nographic \
    -kernel Image -initrd initramfs.cpio.gz \
    -append "console=ttyAMA0 earlycon"

# Option 2: use the host's own aarch64 container image
$ docker create --platform linux/arm64 --name x arm64v8/alpine
$ docker export x | (mkdir -p rootfs && cd rootfs && tar xf -)
$ docker rm x
# ...then cpio it as above, or make it a disk image (chapter 6).

Supplying your own device tree

# Sometimes you want to modify what QEMU generated - to add a
# node for a device model you are writing, or to change a
# property. The workflow is: dump, edit, feed back.

$ qemu-system-aarch64 -M virt,dumpdtb=virt.dtb -m 1G -smp 2
$ dtc -I dtb -O dts virt.dtb -o virt.dts

# Edit virt.dts - add your node:
#     my-device@c000000 {
#         compatible = "acme,widget";
#         reg = <0x0 0x0c000000 0x0 0x1000>;
#         interrupts = <0x0 0x30 0x4>;
#     };

$ dtc -I dts -O dtb virt.dts -o virt-mod.dtb
$ qemu-system-aarch64 -M virt -m 1G -smp 2 -nographic \
    -kernel Image -dtb virt-mod.dtb -append "console=ttyAMA0"

# CAUTION: -dtb REPLACES the generated tree entirely. If you
# then change -m or -smp, the tree no longer matches the
# machine and the guest will see the OLD memory size. Regenerate
# after any machine change. This causes hours of confusion, so
# script it:

$ cat > boot.sh <<'EOF'
#!/bin/sh
set -e
MEM=${MEM:-1G}; SMP=${SMP:-2}
qemu-system-aarch64 -M virt,dumpdtb=/tmp/base.dtb -m $MEM -smp $SMP
dtc -I dtb -O dts /tmp/base.dtb -o /tmp/base.dts 2>/dev/null
python3 add_my_node.py /tmp/base.dts /tmp/final.dts
dtc -I dts -O dtb /tmp/final.dts -o /tmp/final.dtb 2>/dev/null
exec qemu-system-aarch64 -M virt -m $MEM -smp $SMP -nographic \
    -kernel Image -dtb /tmp/final.dtb -append "console=ttyAMA0 earlycon"
EOF
$ chmod +x boot.sh

Choosing the exception level you land at

# -kernel normally enters at EL1 (or EL2 with virtualization=on).
# For bare-metal work you often want something else.

# Land at EL2, so you can write a hypervisor:
$ qemu-system-aarch64 -M virt,virtualization=on -cpu max \
    -kernel my-el2-payload.bin -nographic
# Confirm from inside: mrs x0, CurrentEL  -> 0x8 means EL2

# Land at EL3, for firmware work:
$ qemu-system-aarch64 -M virt,secure=on -cpu max \
    -bios my-el3-firmware.bin -nographic
# NOTE: -bios, not -kernel. -bios loads at address 0 and starts
# there with no stub, no device tree patching and no PSCI - you
# are the firmware now.

# Load a raw ELF anywhere, with full control:
$ qemu-system-aarch64 -M virt -cpu max -nographic \
    -device loader,file=payload.elf \
    -device loader,addr=0x40100000,cpu-num=0
# The second loader sets the PC of CPU 0.

# Load several blobs at chosen addresses - the pattern the
# OP-TEE track uses for TF-A + OP-TEE + U-Boot:
$ qemu-system-aarch64 -M virt,secure=on -cpu max -nographic \
    -bios bl1.bin \
    -device loader,file=fip.bin,addr=0x40100000 \
    -semihosting-config enable=on,target=native
-kernel versus -bios

-kernel means "you are an OS; I will act as your bootloader". -bios means "you are the firmware; here is a bare machine". With -bios you get no device tree, no -append, no initrd loading and no PSCI implementation — QEMU stops helping. Mixing them up produces a payload that runs but finds x0 pointing at nothing.

How it shows up

SymptomCause
Completely silent, no output everMissing console=ttyAMA0, or -nographic omitted so output went to a window
Prints "Booting Linux" then stopsConsole handed over from earlycon to the real driver and the real console is wrong
Hangs before any output at allAdd earlycon; if still silent, the image is loaded at the wrong address or is the wrong format
No working init foundNo initrd, or no /init in it, or it is not executable, or it is dynamically linked with no libraries
Guest sees the wrong memory sizeA stale -dtb from a different -m
Secondary CPUs never come upPSCI conduit mismatch, or -bios used so there is no PSCI at all
GDB symbols are all wrongKASLR — add nokaslr or disable RANDOMIZE_BASE
Image rejected or garbage executedPassed Image.gz or vmlinux to -kernel instead of Image
Works with -kernel, fails with -biosExpected — no boot stub, no DTB, no PSCI
initramfs unpacks but binaries fail with "not found"Dynamically linked busybox without its loader; build static
