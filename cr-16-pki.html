Certificates and PKI

A signature proves a message came from a key. A certificate is the machinery that tells you whose key it is — and getting that binding wrong is how otherwise-correct cryptography ends up protecting nothing.

The binding problem

Signatures prove a message came from the holder of a key. They say nothing about who that is. Bridging that gap — binding a key to an identity — is the entire purpose of a public key infrastructure.

   You verified a signature with public key Q. Excellent.
   WHO OWNS Q?

   Without an answer, an attacker just generates their own
   key pair, signs whatever they like, and hands you their
   public key. Everything verifies.

   A CERTIFICATE is a signed statement:

        "The key Q belongs to <identity>,
         valid from <date> to <date>,
         and may be used for <purposes>."
                              -- signed, some issuer

   THE RECURSION: how do you trust the ISSUER's key?
   Answer: another certificate. Until you reach a
   SELF-SIGNED ROOT that you trust because it was PUT THERE
   OUT OF BAND - shipped in your OS, burned into your OTP
   fuses, compiled into your firmware.

   THE CHAIN:

     ROOT CA (self-signed, in your trust store)
        |  signs
        v
     INTERMEDIATE CA
        |  signs
        v
     END-ENTITY CERT  ("device-4711", or
                        "api.example.com")

   INTERMEDIATES EXIST so the root's private key can stay
   OFFLINE, in a safe, powered off. If an intermediate is
   compromised, it is revoked and replaced. If the root is
   compromised, every device that trusts it must be
   physically updated - which for embedded hardware may mean
   never.

   THE TRUST MODEL IS THE WEAK PART: with the public web PKI
   you are trusting ~150 organisations worldwide, ANY OF
   WHICH can issue a certificate for ANY name. Several have
   been compromised or have misissued. DigiNotar (2011) was
   used to intercept Gmail for 300,000 Iranian users, and the
   CA went bankrupt.

Inside an X.509 certificate

The certificate format everything uses, with a structure and an encoding that are both more complicated than the problem requires and which have produced a long history of parsing vulnerabilities.

Certificate:
  Data:
    Version: 3 (0x2)
    Serial Number: 04:1a:...              /* unique per CA;
                                             must be random
                                             (see below) */
    Signature Algorithm: ecdsa-with-SHA256
    Issuer:  C=US, O=Example CA, CN=Example Issuing CA
    Validity
      Not Before: Jun  1 00:00:00 2026 GMT
      Not After : Aug 30 23:59:59 2026 GMT
    Subject: CN=api.example.com
    Subject Public Key Info:
      Public Key Algorithm: id-ecPublicKey
        NIST CURVE: P-256
        pub: 04:8f:...
    X509v3 extensions:
      X509v3 Basic Constraints: critical
        CA:FALSE                     <-- THE IMPORTANT ONE
      X509v3 Key Usage: critical
        Digital Signature
      X509v3 Extended Key Usage:
        TLS Web Server Authentication
      X509v3 Subject Alternative Name:
        DNS:api.example.com, DNS:www.example.com
                                     <-- THE NAME THAT
                                         COUNTS
      X509v3 Authority Key Identifier: keyid:...
      X509v3 CRL Distribution Points: URI:http://...
      Authority Information Access:
        OCSP - URI:http://ocsp.example.com
  Signature Algorithm: ecdsa-with-SHA256
  Signature Value: 30:45:02:20:...

/* THE FIELDS THAT ACTUALLY MATTER FOR SECURITY:

   BASIC CONSTRAINTS / CA:FALSE
     Says this certificate may NOT sign other certificates.
     A verifier that ignores it lets ANY certificate holder
     become a CA and issue a cert for any name. This was a
     REAL BUG in Internet Explorer, in the iPhone, and in
     several embedded stacks. It is the single most important
     extension.

   KEY USAGE / EXTENDED KEY USAGE
     What the key may do. A certificate issued for code
     signing should not authenticate a TLS server.

   SUBJECT ALTERNATIVE NAME
     THE NAMES THE CERT IS VALID FOR. The Subject CN is
     LEGACY and modern verifiers ignore it. Wildcards match
     ONE label: *.example.com covers a.example.com but NOT
     a.b.example.com and NOT example.com itself.

   VALIDITY DATES
     Which means the device NEEDS A CORRECT CLOCK - see
     below, because on embedded hardware it usually does
     not have one.

   PATH LENGTH CONSTRAINT
     How many intermediates may appear below this CA.

/* AND A NOTE ON ENCODING: all of this is DER-encoded ASN.1 -
   nested tag-length-value structures. X.509 PARSERS ARE A
   HISTORIC SOURCE OF MEMORY-SAFETY BUGS, because the parser
   runs on ATTACKER-CONTROLLED INPUT BEFORE any signature has
   been checked. If you are choosing a TLS library for a
   device, the quality of its ASN.1 parser matters more than
   its cipher performance.                               */

Verifying a chain, correctly

Verifying a certificate is not one check but a chain of them, and skipping any single one invalidates the whole. Most real-world failures are an omitted step rather than a broken signature.

/* THE FULL PROCEDURE. Skipping any step has broken real
   software.                                              */

  FOR EACH certificate from the leaf up to a trusted root:

   1. SIGNATURE: verify it with the ISSUER's public key.

   2. VALIDITY DATES: now is within [notBefore, notAfter].

   3. ISSUER/SUBJECT CHAINING: this cert's Issuer matches
      the next cert's Subject, byte for byte.

   4. FOR EVERY NON-LEAF: BASIC CONSTRAINTS says CA:TRUE.
      <-- THE STEP PEOPLE SKIP

   5. FOR EVERY NON-LEAF: KEY USAGE includes keyCertSign.

   6. PATH LENGTH within the constraint.

   7. NAME CONSTRAINTS, if the CA has any, are satisfied.

   8. CRITICAL EXTENSIONS you do not understand -> REJECT.
      That is what "critical" means.

   9. REVOCATION: not on a CRL, or OCSP says good.

  AND THEN, SEPARATELY, ON THE LEAF:

  10. NAME MATCHING: the SAN contains the name YOU INTENDED
      to connect to - not the name in the certificate, and
      not the name the server told you.

  11. EXTENDED KEY USAGE matches your purpose.

  12. THE CHAIN ENDS AT A ROOT IN YOUR TRUST STORE.

/* THE FAMOUS FAILURES:
     · Apple's "goto fail" (2014): a duplicated goto
       statement skipped the signature check entirely.
     · GnuTLS (2014): a return-value confusion made invalid
       certificates verify.
     · Countless mobile apps: implementing a custom
       TrustManager that returns "valid" unconditionally, to
       make a self-signed test certificate work - and
       shipping it.
     · Basic-constraints omissions in at least four major
       stacks.

   THE PATTERN: THE FAILURE IS ALWAYS "ACCEPTS WHAT IT
   SHOULD REJECT", AND IT IS INVISIBLE IN TESTING, because
   the happy path still works perfectly.

/* SO: TEST YOUR VERIFIER WITH BAD CERTIFICATES.
     - expired
     - wrong name
     - self-signed
     - signed by a non-CA leaf
     - a valid chain to an untrusted root
     - a revoked certificate
     - a truncated / malformed DER blob
   If all seven are rejected, you have a verifier. If you
   only ever tested the good certificate, you have nothing.
   openssl s_server plus a small script generates all of
   these in a few minutes, and badssl.com hosts them
   publicly.                                              */
Never disable certificate verification "temporarily"

curl -k, verify=False, MBEDTLS_SSL_VERIFY_NONE, a custom TrustManager that always returns success — every one of these has shipped to production in a real product. If a self-signed development certificate is inconvenient, add it to the device's trust store for development builds. Make the insecure path impossible to compile into a release build, not merely discouraged.

Revocation, and why it barely works

A compromised key must be repudiated before its certificate expires, and every mechanism for doing so has significant practical problems. This is the weakest part of the system in practice.

/* A certificate is valid until it expires. If the private
   key is stolen before then, you need to say so. All the
   mechanisms are unsatisfying.                            */

/* --- CRL: certificate revocation list --- */
    A signed list of revoked serial numbers, published by the
    CA.
    PROBLEMS: it grows without bound (megabytes); it is
    cached, so revocation is delayed by hours or days; and
    fetching it needs network access at exactly the moment a
    connection is being established.

/* --- OCSP: online status protocol --- */
    Ask the CA about one certificate.
    PROBLEMS: a PRIVACY LEAK (the CA learns every site you
    visit); a latency cost on every connection; and the fatal
    one - MOST CLIENTS SOFT-FAIL. If the OCSP responder is
    unreachable, they proceed anyway. An attacker who can
    intercept your traffic can also block OCSP, so revocation
    checking provides no security against the attacker it
    was designed to stop.

/* --- OCSP STAPLING --- */
    The SERVER fetches its own signed OCSP response and
    includes it in the handshake. Fixes the privacy and
    latency problems. Still soft-fails unless the
    certificate carries the "must-staple" extension.

/* --- SHORT-LIVED CERTIFICATES: the practical answer --- */
    Issue for 90 days, or 7, or 1. Revocation becomes
    expiry. This is why ACME/Let's Encrypt automation
    exists, and the industry is moving toward 47-day
    maximum lifetimes.

/* --- FOR EMBEDDED DEVICES, be realistic --- */
    A device may be offline, may have no clock, and may live
    for fifteen years. The web PKI's assumptions do not hold.
    WHAT WORKS INSTEAD:

      · YOUR OWN CA, not the public one. You control issuance
        and you can make the certificates last as long as the
        hardware.
      · PINNING: the device trusts EXACTLY ONE root, whose
        hash is in OTP. No public CA can attack it.
      · A REVOCATION LIST DELIVERED WITH FIRMWARE UPDATES,
        signed, with a monotonic version.
      · A DEVICE IDENTITY THAT CANNOT BE STOLEN: the private
        key generated inside a secure element and never
        exported (chapter 18).
      · AND FOR THE CLOCK PROBLEM: either accept that
        notBefore/notAfter cannot be checked and rely on
        pinning plus revocation, or seed the clock from a
        SIGNED time source before doing any validation.
        Do not let an attacker set your clock to 2035 and
        use an expired certificate.                       */

Device PKI in practice

Embedded devices have a harder version of this problem: no user to click through warnings, clocks that may be wrong, and certificates that must outlive the product's support period.

/* --- THE HIERARCHY --- */
      Vendor Root CA          offline, in an HSM, in a safe.
        |                     30-year validity. Its PUBLIC
        |                     KEY HASH goes into every
        |                     device's OTP.
        +-- Manufacturing CA  signs device certificates on
        |                     the production line
        +-- Firmware CA       signs firmware manifests
        |                     (chapter 15)
        +-- Service CA        signs the cloud endpoints the
                              device connects to

    SEPARATE INTERMEDIATES PER PURPOSE. A compromise of the
    factory does not let an attacker sign firmware.

/* --- PROVISIONING, on the line --- */
    1. the secure element GENERATES ITS OWN key pair; the
       private half never exists outside it
    2. it emits a CSR (certificate signing request) - the
       public key plus a self-signature proving possession
    3. the factory HSM signs it, embedding a DEVICE SERIAL
       and a PRODUCT CLASS
    4. the certificate is written back to the device (it is
       public; it needs no protection)
    5. the (serial -> certificate) mapping goes into the
       vendor's inventory database

    THE PRIVATE KEY IS NEVER TRANSPORTED, NEVER BACKED UP,
    AND NEVER KNOWN TO ANYONE. A compromised factory database
    leaks nothing secret.

/* --- MUTUAL TLS IN THE FIELD --- */
    device -> cloud:  presents its device certificate,
                      proves possession via the handshake
                      signature
    cloud  -> device: presents a service certificate, which
                      the device validates against its
                      PINNED vendor root

    The cloud additionally checks the device serial against
    its inventory: is this device registered, activated, not
    reported stolen, and running a firmware version we still
    accept?

/* --- WHAT TO PUT IN OTP --- */
    NOT the root certificate - it is too big for fuses.
    THE SHA-256 HASH of the root public key. 32 bytes.
    The certificate itself lives in flash, and the boot code
    hashes it and compares before trusting it. That way the
    fuse cost is fixed and small, and the certificate can be
    re-encoded or re-formatted without burning new fuses.

/* --- AND PLAN FOR ROTATION --- */
    Fifteen-year devices outlive algorithms. Provision
    SEVERAL root key slots in OTP, with a fuse indicating
    which are active, so a root can be retired without
    bricking the fleet. This costs a few hundred fuse bits
    and it is the difference between a recoverable incident
    and a recall.                                        */
