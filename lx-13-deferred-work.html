Deferred work: softirqs, tasklets and workqueues

An interrupt handler must be short. Everything it cannot do goes somewhere else — and Linux offers four somewhere-elses, differing in whether they can sleep, how soon they run, and how much they cost. Choosing is easy once you know the trade.

The top half / bottom half split

An interrupt handler runs with that interrupt — and often others — disabled, so every microsecond it spends is added directly to the worst-case latency of the entire machine. The universal solution is to do the bare minimum in the handler and push the real work somewhere it can take its time.

   device raises IRQ
        |
        v
   TOP HALF (hard IRQ handler)
        · interrupts may be disabled
        · MUST BE FAST - microseconds
        · CANNOT SLEEP
        · do only: acknowledge the device, stop it
          re-interrupting, grab the minimum state
        |
        +--> schedule the bottom half
        |
        v
   return IRQ_HANDLED
        ...
        |
        v
   BOTTOM HALF, later
        · the actual work: parse the data, wake readers,
          submit the next transfer, log the error
        · may or may not sleep, depending which kind

  WHY: while your handler runs, that interrupt is masked, and
  on many systems others are too. Every microsecond spent in a
  top half is added directly to the worst-case interrupt
  latency of the WHOLE SYSTEM (chapter 11).

The four mechanisms

All four exist to move work out of the interrupt top half described above, but they differ on the one property that decides which a driver author is actually allowed to reach for: whether the deferred work can sleep, since anything that needs to allocate with GFP_KERNEL, take a mutex, or wait on hardware cannot run in the two non-sleeping mechanisms at all.

Can sleepRuns onLatencyVerdict
SoftirqNoThe CPU that raised itVery lowCore subsystems only — you cannot add one
TaskletNoThe CPU that scheduled itLowDeprecated. Do not use in new code
WorkqueueYesAny CPU, a kworker threadScheduler-dependentThe default choice
Threaded IRQYesA dedicated thread per IRQLow, and prioritisableBest for device work
The short answer

For work arising from an interrupt on your device: use a threaded IRQ. For work arising from anywhere else — a timer, a syscall path that must not block, a retry — use a workqueue. You will almost never need anything else, and tasklets are actively being removed from the kernel.

Threaded interrupts

This is the mechanism most driver work should use, and it is the easiest to get right: the kernel runs the second half of your handler in an ordinary kernel thread, so it may sleep, take mutexes, and talk to slow buses — none of which is possible in a hard interrupt handler.

/* The modern pattern, and the one to reach for first. */

static irqreturn_t my_hardirq(int irq, void *dev_id)
{
        struct my_dev *d = dev_id;
        u32 status;

        status = readl(d->base + REG_STATUS);
        if (!(status & INT_PENDING))
                return IRQ_NONE;        /* not ours - important
                                           on a shared line   */

        /* acknowledge and mask, so it stops asserting */
        writel(status, d->base + REG_STATUS);

        d->pending_status = status;     /* hand it over */

        return IRQ_WAKE_THREAD;         /* run the thread fn */
}

static irqreturn_t my_thread_fn(int irq, void *dev_id)
{
        struct my_dev *d = dev_id;

        /* PROCESS CONTEXT. We may sleep here: */
        mutex_lock(&d->lock);
        process_data(d, d->pending_status);   /* can be slow  */
        mutex_unlock(&d->lock);

        wake_up_interruptible(&d->wq);

        return IRQ_HANDLED;
}

        ret = devm_request_threaded_irq(&pdev->dev, irq,
                                        my_hardirq,
                                        my_thread_fn,
                                        IRQF_ONESHOT,
                                        dev_name(&pdev->dev),
                                        d);

/* IRQF_ONESHOT keeps the interrupt MASKED until the thread
   function finishes. Essential for level-triggered interrupts
   and for slow buses - without it a device that keeps
   asserting will re-interrupt immediately and livelock the
   CPU.

/* THE DEGENERATE CASE, and it is very common - pass NULL for
   the hard handler and the core provides one that just wakes
   the thread: */
        devm_request_threaded_irq(dev, irq, NULL, my_thread_fn,
                                  IRQF_ONESHOT, name, d);
/* This is exactly right for I2C and SPI devices, where you
   cannot even READ the status register without sleeping.  */

/* WHY THREADED IRQs ARE BETTER THAN A WORKQUEUE HERE:
     · one thread per interrupt, so no sharing with unrelated
       work
     · it can be given a real-time priority and pinned
     · on PREEMPT_RT this is the default for ALL interrupts,
       so your driver already matches the model
     · the masking is handled for you                       */

Workqueues

When work is not tied to an interrupt at all — a retry, a delayed poll, a slow initialisation — a workqueue is the general-purpose way to run it in a context that may sleep. It is the default answer for "do this later, properly."

#include <linux/workqueue.h>

/* --- simple: use the shared system queue ----------------- */
struct my_dev {
        struct work_struct  work;
        ...
};

static void my_work_fn(struct work_struct *w)
{
        struct my_dev *d = container_of(w, struct my_dev, work);

        /* process context - CAN SLEEP */
        mutex_lock(&d->lock);
        do_slow_thing(d);
        mutex_unlock(&d->lock);
}

        INIT_WORK(&d->work, my_work_fn);
        schedule_work(&d->work);        /* queue it */

/* --- delayed work ---------------------------------------- */
        struct delayed_work poll_work;

        INIT_DELAYED_WORK(&d->poll_work, poll_fn);
        schedule_delayed_work(&d->poll_work,
                              msecs_to_jiffies(100));
        /* and to re-arm from inside poll_fn, for a poller: */
        schedule_delayed_work(&d->poll_work, HZ);

/* --- your own workqueue, when you need control ----------- */
        d->wq = alloc_workqueue("my_dev_wq",
                                WQ_UNBOUND | WQ_MEM_RECLAIM,
                                1);           /* max_active */
        if (!d->wq)
                return -ENOMEM;

        queue_work(d->wq, &d->work);
        ...
        destroy_workqueue(d->wq);    /* drains first */

/* THE FLAGS THAT MATTER:
     WQ_MEM_RECLAIM   guarantees a rescuer thread, so the queue
                      can make progress under memory pressure.
                      REQUIRED if your work is on a memory
                      reclaim path (a storage or swap driver).
     WQ_UNBOUND       not tied to a CPU; the scheduler places
                      it. Better for long-running work.
     WQ_HIGHPRI       runs ahead of normal work
     WQ_FREEZABLE     stops during suspend
     max_active = 1   serialises - only one work item at a
                      time, which often replaces a lock

/* CANCELLING - and this is where drivers leak or crash: */
        cancel_work_sync(&d->work);           /* WAITS */
        cancel_delayed_work_sync(&d->poll_work);
        flush_workqueue(d->wq);

/* In remove(), you MUST use the _sync forms. cancel_work()
   without _sync returns immediately, the work may still be
   running, and it will touch your freed device structure
   moments later.                                           */
The teardown ordering bug 
static void my_remove(struct platform_device *pdev)
{
        struct my_dev *d = platform_get_drvdata(pdev);

        /* 1. STOP THE SOURCE first - no new work can arrive */
        free_irq(d->irq, d);            /* or devm handles it */
        writel(0, d->base + REG_INT_ENABLE);

        /* 2. THEN cancel what is already queued, and WAIT   */
        cancel_delayed_work_sync(&d->poll_work);
        cancel_work_sync(&d->work);
        del_timer_sync(&d->timer);

        /* 3. ONLY NOW is it safe to free anything          */
}

Reverse steps 1 and 2 and the interrupt re-queues the work after you cancelled it. Skip the _sync and the work runs against freed memory. Both produce crashes minutes later, in unrelated code, and both are found instantly by KASAN.

Timers

Sometimes the trigger is time rather than an event: poll again in 500 ms, give up if the device has not answered in two seconds. Linux offers two timer mechanisms with very different resolutions and very different costs, and picking the wrong one gives you either jitter or wasted CPU.

/* --- timer_list: jiffy-resolution, runs in SOFTIRQ ------- */
#include <linux/timer.h>

static void my_timer_fn(struct timer_list *t)
{
        struct my_dev *d = from_timer(d, t, timer);
        /* SOFTIRQ CONTEXT - cannot sleep */
        schedule_work(&d->work);        /* punt if you must */
}

        timer_setup(&d->timer, my_timer_fn, 0);
        mod_timer(&d->timer, jiffies + msecs_to_jiffies(500));
        ...
        del_timer_sync(&d->timer);      /* _sync, always */

/* Resolution is one jiffy = 1/CONFIG_HZ, typically 1-10 ms,
   and timers fire LATE, never early. Fine for timeouts and
   watchdogs; useless for precise periods.                 */

/* --- hrtimer: nanosecond resolution ---------------------- */
#include <linux/hrtimer.h>

static enum hrtimer_restart my_hr_fn(struct hrtimer *t)
{
        struct my_dev *d = container_of(t, struct my_dev, hrt);

        /* HARD IRQ context by default - be quick */
        do_sample(d);

        hrtimer_forward_now(t, ns_to_ktime(1000000));  /* 1 ms */
        return HRTIMER_RESTART;
}

        hrtimer_init(&d->hrt, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
        d->hrt.function = my_hr_fn;
        hrtimer_start(&d->hrt, ns_to_ktime(1000000),
                      HRTIMER_MODE_REL);
        ...
        hrtimer_cancel(&d->hrt);

/* Use hrtimer_forward_now() to re-arm a PERIODIC timer -
   it advances from the scheduled time, so the period does not
   drift with handler latency. Re-arming from "now" instead
   accumulates error, which is the classic sampling-rate
   bug.                                                     */

/* --- short delays, no timer at all ----------------------- */
        udelay(10);          /* BUSY-WAITS. atomic-safe.
                                Under ~10us only.           */
        ndelay(100);
        mdelay(5);           /* busy-waits MILLISECONDS -
                                almost always wrong          */

        usleep_range(100, 200);   /* SLEEPS. process context.
                                     Give a range so the
                                     kernel can coalesce it.  */
        msleep(20);               /* sleeps, coarse           */

/* NEVER mdelay() in a driver unless a datasheet demands a
   busy-wait. It burns a CPU for the whole duration with
   preemption implications for everything else.            */

Tasklets, and why not

You will meet tasklets constantly in existing drivers and in older tutorials, so it is worth knowing what they are — and equally worth knowing that they are on their way out and should not appear in anything you write today.

/* You will see these in existing drivers: */
        DECLARE_TASKLET(my_tasklet, my_tasklet_fn);
        tasklet_schedule(&my_tasklet);

/* THEY ARE DEPRECATED. Reasons:
     · they run in softirq context, so they cannot sleep -
       yet they are used for work that wants to
     · a tasklet cannot be preempted, so a long one is a
       latency bug that nothing reports
     · the same tasklet never runs concurrently on two CPUs,
       which sounds helpful but hides races that appear the
       moment someone converts it
     · they are being actively removed from the tree

   IF YOU ARE MAINTAINING ONE, convert it:
        tasklet doing work that can sleep -> threaded IRQ
        tasklet doing quick work          -> the hard IRQ
                                             handler itself
        tasklet used for deferral         -> workqueue      */

Choosing

With four mechanisms available the decision can feel arbitrary, but in practice it collapses to one question — may this work sleep — followed by how urgent it is.

   Work arises from MY DEVICE'S INTERRUPT?
        |
        +-- and it can sleep, or takes more than ~10 us
        |      -> THREADED IRQ
        |
        +-- and it is a few register writes
               -> do it in the hard handler. Deferring it
                  costs more than doing it.

   Work arises from ELSEWHERE?
        |
        +-- must run periodically, precise timing
        |      -> hrtimer (+ workqueue if it must sleep)
        |
        +-- must run periodically, approximate
        |      -> delayed_work, re-armed
        |
        +-- must run once, soon, and may sleep
        |      -> workqueue
        |
        +-- must run once, after a delay
               -> delayed_work, or timer_list for a timeout

   And on a memory-reclaim path (storage, swap):
        -> a dedicated workqueue with WQ_MEM_RECLAIM

Observing

Deferred work is easy to get subtly wrong in ways that only show up as latency. All of these mechanisms are visible from user space, so you can confirm what actually ran, how often, and how long it took rather than assuming.

# Softirq activity:
    cat /proc/softirqs
    # HI, TIMER, NET_TX, NET_RX, BLOCK, TASKLET, SCHED,
    # HRTIMER, RCU - per CPU

# ksoftirqd busy = softirq load so high it was pushed to a
# thread. On an embedded system that usually means network or
# timer pressure:
    top -H | grep ksoftirq

# Workqueue state:
    ls /sys/bus/workqueue/devices/
    cat /sys/bus/workqueue/devices/my_dev_wq/max_active
    # and with CONFIG_WQ_WATCH:
    dmesg | grep "workqueue.*hogged CPU"

# Tracing - the useful one:
    trace-cmd record -e workqueue -e irq -e timer
    trace-cmd report
    # shows workqueue_queue_work / execute_start / execute_end,
    # so you can measure how long each item took and how long
    # it waited

# Stuck work is reported automatically:
    BUG: workqueue lockup - pool cpus=0 flags=0x0 nice=0
         stuck for 32s!
# Means a work item blocked forever, starving everything else
# on that queue. Common cause: work item A waiting on work
# item B, both on the same single-threaded queue.
