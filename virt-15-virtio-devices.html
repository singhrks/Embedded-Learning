virtio device families and vhost

One queue mechanism, thirty device types, and three places the device implementation can live: in the VMM process, in the host kernel, or in a separate process entirely. Which you choose decides your throughput, your latency and your blast radius when the device model has a bug.

Which ones matter on an embedded target

virtio-blk, virtio-net, virtio-console and virtio-rng give you a fully functional Linux guest on QEMU's virt machine with four command-line options. Everything else is specialisation. Start there, and see the recipes in QEMU chapter 15.

Three places a device can live

The same device specification can be implemented in three different places, and the choice determines the performance and the failure modes far more than the device type does.

   1. IN THE VMM (userspace, e.g. QEMU)

      guest  --notify-->  KVM  --exit-->  QEMU thread
                                            |
                                          host syscall
      Latency:  ~15-30 us per batch
      Pros:     easy to write, debug and sandbox; full access
                to files, sockets, image formats (qcow2)
      Cons:     two context switches per batch

   2. IN THE HOST KERNEL (vhost)

      guest  --notify(ioeventfd)-->  KVM  --wake--> vhost-net
                                                    kernel thread
                                                       |
                                                    net stack
      Latency:  close to host-native
      Pros:     no userspace round trip; the kernel already has
                the socket/block layer right there
      Cons:     device model is kernel code - a bug is a host
                kernel bug. Only exists for net, blk (vhost-blk,
                out of tree), scsi, vsock.

      QEMU still does SETUP: feature negotiation, queue
      addresses, and it hands vhost the memory map and the
      eventfds. Only the DATA PATH moves.

   3. IN ANOTHER PROCESS (vhost-user / vhost-vdpa)

      guest  --notify-->  KVM  --> a separate daemon
                                   (DPDK, SPDK, virtiofsd,
                                    a rust-vmm device)
      Latency:  can be the best of all - a polling DPDK thread
                never sleeps, so there is no wake-up at all
      Pros:     device crash does not take down the VMM or the
                host kernel; can be written in Rust; can be
                updated independently
      Cons:     the daemon must map ALL of guest memory, so it
                is inside the trust boundary for confidentiality

      The daemon learns the guest memory layout over a UNIX
      socket (the vhost-user protocol) and then accesses the
      rings directly.

virtio-net in detail

The networking device is the one with the most features and the most tuning knobs, and the interesting ones are all about avoiding copies and notifications.

/* Feature bits worth knowing, because they decide performance
   far more than the ring implementation does.              */

  VIRTIO_NET_F_CSUM            device handles checksums; the
                               guest can send unchecksummed
                               packets. Saves a pass over data.
  VIRTIO_NET_F_GUEST_CSUM      the guest will accept them.
  VIRTIO_NET_F_HOST_TSO4/6     device will segment; the guest
                               may send 64 KB "packets".
                               THE big win - one descriptor
                               chain instead of forty.
  VIRTIO_NET_F_GUEST_TSO4/6    guest accepts big receives (GRO).
  VIRTIO_NET_F_MRG_RXBUF       merge several receive buffers
                               into one packet - needed for
                               large receives without wasting
                               memory on small ones.
  VIRTIO_NET_F_MQ              multiqueue: one RX/TX pair per
                               vCPU, so no cross-CPU contention.
  VIRTIO_NET_F_CTRL_VQ         a control queue for MAC filters,
                               VLANs, offload changes.
  VIRTIO_NET_F_MTU             device tells the guest the MTU.

/* The header prepended to every packet: */

struct virtio_net_hdr_v1 {
        __u8  flags;            /* NEEDS_CSUM, DATA_VALID       */
        __u8  gso_type;         /* NONE, TCPV4, UDP, TCPV6      */
        __le16 hdr_len;
        __le16 gso_size;        /* MSS for segmentation         */
        __le16 csum_start;      /* where the checksum field is  */
        __le16 csum_offset;
        __le16 num_buffers;     /* MRG_RXBUF: how many buffers
                                   this packet occupies         */
};

/* Descriptor chain for one transmitted packet:

     desc[0]  the header above          (device reads)
     desc[1]  the packet data           (device reads)
     ...      more fragments if scattered

   For a receive:

     desc[0]  a buffer the DEVICE WRITES, big enough for header
              plus data. With MRG_RXBUF, several such buffers
              may be consumed for one large packet, and
              num_buffers says how many.                     */
# Turn the knobs and watch what happens.

# Multiqueue, 4 pairs, with vhost:
$ qemu-system-aarch64 -M virt -accel kvm \
   -netdev tap,id=n0,vhost=on,queues=4 \
   -device virtio-net-pci,netdev=n0,mq=on,vectors=10

# vectors = 2*queues + 2 (one per queue direction, plus config
# and control). Too few and the guest silently falls back to
# fewer queues.

# In the guest, confirm:
$ ethtool -l eth0
Channels: Combined: 4

# Which offloads did the guest actually get?
$ ethtool -k eth0 | grep -E 'tx-checksum|tso|gro|gso'
tx-checksumming: on
tcp-segmentation-offload: on
generic-receive-offload: on

# Turning TSO off is the single fastest way to prove it matters:
$ ethtool -K eth0 tso off
$ iperf3 -c host      # expect a large drop

virtio-blk, the one to implement first

Block is the device to implement first: a small command set, an obvious data path, and a specification short enough to read in one sitting.

/* Three descriptors per request. That is the whole protocol. */

struct virtio_blk_outhdr {
        __le32 type;       /* IN=0 read, OUT=1 write,
                              FLUSH=4, GET_ID=8, DISCARD=11,
                              WRITE_ZEROES=13                */
        __le32 reserved;
        __le64 sector;     /* in 512-byte units, ALWAYS,
                              regardless of the logical block
                              size the device advertises     */
};

  desc[0]  -> struct virtio_blk_outhdr   (device reads)
  desc[1]  -> the data buffer            (read: device writes
                                          write: device reads)
  desc[2]  -> a single status byte       (device writes)
                 VIRTIO_BLK_S_OK      0
                 VIRTIO_BLK_S_IOERR   1
                 VIRTIO_BLK_S_UNSUPP  2

/* A device model's whole hot path: */

static void blk_handle_request(struct blkdev *d, struct chain *c)
{
        struct virtio_blk_outhdr *h = c->desc[0].addr;
        void   *buf  = c->desc[1].addr;
        size_t  len  = c->desc[1].len;
        uint8_t *st  = c->desc[2].addr;
        off_t   off  = (off_t)le64toh(h->sector) * 512;

        switch (le32toh(h->type)) {
        case VIRTIO_BLK_T_IN:
                *st = (pread(d->fd, buf, len, off) == (ssize_t)len)
                    ? VIRTIO_BLK_S_OK : VIRTIO_BLK_S_IOERR;
                break;
        case VIRTIO_BLK_T_OUT:
                *st = (pwrite(d->fd, buf, len, off) == (ssize_t)len)
                    ? VIRTIO_BLK_S_OK : VIRTIO_BLK_S_IOERR;
                break;
        case VIRTIO_BLK_T_FLUSH:
                *st = fdatasync(d->fd) == 0
                    ? VIRTIO_BLK_S_OK : VIRTIO_BLK_S_IOERR;
                break;
        default:
                *st = VIRTIO_BLK_S_UNSUPP;
        }
        vq_complete(c, len);
}

/* THE FLUSH IS NOT OPTIONAL. A device model that ignores
   VIRTIO_BLK_T_FLUSH will pass every functional test and lose
   the guest's filesystem on the first host power cut, because
   the guest believed its journal was durable. If you take one
   thing from this chapter, take that.                       */
Cache modes are a durability contract

QEMU's cache= option decides who may lie about durability. cache=writeback (the default) lets the host page cache absorb writes and relies on the guest issuing flushes — correct, and fast, if your flush path works. cache=unsafe discards flushes entirely: excellent for a throwaway build VM, catastrophic for anything you care about. cache=none uses O_DIRECT. Choose deliberately, and never leave unsafe in a script someone else might reuse.

virtio-vsock: the one people forget

A host-to-guest socket that needs no network configuration solves a problem most people work around badly, and it is under-used.

/* Host-guest communication without a network. No IP, no
   firewall, no DHCP, no risk of the guest routing somewhere.
   Addresses are (CID, port).                               */

  CID 0  hypervisor
  CID 1  local (loopback)
  CID 2  the HOST, always
  CID 3+ guests, assigned by the VMM

# QEMU:
$ qemu-system-aarch64 ... -device vhost-vsock-pci,guest-cid=42

# Guest, a server:
$ socat VSOCK-LISTEN:1234,fork -
# Host, a client:
$ socat - VSOCK-CONNECT:42:1234

/* In C, it is just sockets: */
    int s = socket(AF_VSOCK, SOCK_STREAM, 0);
    struct sockaddr_vm a = {
            .svm_family = AF_VSOCK,
            .svm_cid    = VMADDR_CID_HOST,   /* 2              */
            .svm_port   = 1234,
    };
    connect(s, (struct sockaddr *)&a, sizeof a);

/* Use it for: guest agents, log shipping, test harnesses,
   debugging a guest with no network configured, and anything
   where giving the guest a network interface would be a
   security decision you do not want to make.               */

virtiofs and DAX

Sharing a filesystem rather than a block device changes the semantics considerably, and the memory-mapping path is what makes it fast.

# Sharing a host directory with a guest, properly.

# Host: run the daemon (a vhost-user device in its own process)
$ /usr/libexec/virtiofsd --socket-path=/tmp/vfs.sock \
      -o source=/srv/shared -o cache=auto

# QEMU: connect to it, and give it shared memory
$ qemu-system-aarch64 -M virt,memory-backend=mem \
   -object memory-backend-file,id=mem,size=4G,\
mem-path=/dev/shm,share=on \
   -chardev socket,id=vfs,path=/tmp/vfs.sock \
   -device vhost-user-fs-pci,chardev=vfs,tag=myfs

# Guest:
$ mount -t virtiofs myfs /mnt

/* Why "share=on" and a file-backed memory object are
   mandatory: virtiofsd is a SEPARATE PROCESS. It must be able
   to map guest memory to read and write the queues. Anonymous
   private memory cannot be shared, so the VM will start and
   the mount will hang.

   DAX goes further: with a DAX window, the guest maps host
   PAGE CACHE PAGES directly into its own address space. A
   read() becomes a memory access with no copy and no exit at
   all. That is why virtiofs beats 9p by an order of magnitude
   on metadata-heavy workloads like a source tree.          */

How it shows up

SymptomCause
Guest filesystem corrupt after a host crashDevice model ignores VIRTIO_BLK_T_FLUSH, or cache=unsafe
Network throughput a fraction of the host'sTSO/checksum offload not negotiated — every packet is a separate chain
Multiqueue configured but only one queue activeToo few MSI-X vectors, or the guest never sent the control-queue command to enable the pairs
vhost-user device never starts, VM hangs at bootGuest memory not shared (share=on and a file-backed memory object missing)
Guest blocks for a minute early in bootNo virtio-rng; the entropy pool is empty
Large receives dropped or truncatedMRG_RXBUF negotiated but num_buffers not honoured
Guest sees the wrong disk size after resizingConfig-space change not signalled with a configuration-change interrupt
vsock connection refused from the hostWrong CID — the guest must connect to CID 2, not to its own
virtiofs mount hangsDaemon not running, socket path mismatch, or DAX window requested without shared memory
Everything is slow only with -accel tcgNot a virtio problem — emulation is the bottleneck (QEMU chapter 2)
