Why you need a scheduler: the superloop and its limits

Most embedded products ship with no RTOS at all, and that is often the right decision. This chapter covers the architectures between "one loop" and "preemptive kernel", what each costs, and the specific symptom that tells you it is time to move up.

The superloop

/* The architecture behind more shipped firmware than every
   RTOS combined.                                          */

int main(void)
{
    clock_init();
    gpio_init();
    uart_init();

    for (;;) {
        poll_sensors();
        update_control();
        service_comms();
        update_display();
    }
}

/* WHAT IS GOOD ABOUT IT

   - No concurrency. Nothing preempts anything, so there are
     no races between the four functions and no locks. Every
     data-sharing bug you have ever read about is absent by
     construction.
   - Trivially analysable. The worst-case loop time is the
     sum of four numbers.
   - No kernel: no scheduler RAM, no per-task stacks, no
     kernel code. On a part with 8 kB of RAM this is not a
     preference, it is the only option.
   - Nothing to learn or misconfigure.

   WHAT IS BAD ABOUT IT

   - LATENCY IS THE WHOLE LOOP. If update_display() takes
     40 ms, the control loop cannot respond faster than that,
     no matter how urgent.
   - One slow function degrades everything.
   - Any blocking call is fatal to responsiveness.        */
The rule that makes a superloop work

Every function in the loop must return quickly and never block. That single discipline is what keeps the architecture viable, and it is why superloop code is written as state machines rather than sequences. A function that waits — for a UART byte, an I2C transfer, a sensor conversion — has stolen the whole loop's responsiveness. The moment you cannot express something without waiting, you have found the boundary of the architecture.

Non-blocking state machines

/* THE BLOCKING VERSION - 210 ms of the loop, unavailable
   to everything else.                                     */
void read_sensor_blocking(void)
{
    i2c_write(ADDR, CMD_START);
    delay_ms(200);                    /* conversion time    */
    value = i2c_read16(ADDR, REG_DATA);
}

/* THE STATE MACHINE - returns in microseconds, every time. */
typedef enum { S_IDLE, S_WAIT, S_READ } sensor_state_t;

void read_sensor_step(void)
{
    static sensor_state_t st = S_IDLE;
    static uint32_t       t0;

    switch (st) {
    case S_IDLE:
        i2c_write(ADDR, CMD_START);
        t0 = g_ms;
        st = S_WAIT;
        break;

    case S_WAIT:
        if ((int32_t)(g_ms - (t0 + 200)) >= 0) {   /* wrap-safe */
            st = S_READ;
        }
        break;                        /* returns immediately */

    case S_READ:
        value = i2c_read16(ADDR, REG_DATA);
        st = S_IDLE;
        break;
    }
}

/* This is the central skill of superloop design, and it is
   also its central cost: the CONTROL FLOW IS INSIDE OUT.
   The sequence "start, wait, read" is obvious in the
   blocking version and scattered across a switch in the
   non-blocking one. With three such sequences interleaved,
   each with error handling and timeouts, the state count
   multiplies and the code becomes genuinely hard to follow.

   THAT is the real argument for an RTOS. Not performance -
   readability. An RTOS lets you write the blocking version
   and have it be correct, because the kernel switches away
   from a blocked task instead of the whole system waiting. */

The spectrum

   1. SUPERLOOP
      for(;;) { a(); b(); c(); }
      Latency: whole loop.  RAM: one stack.
      Use when: every function is short, few deadlines.

   2. SUPERLOOP + INTERRUPTS  <- most shipped firmware
      ISRs handle urgent work; the loop handles the rest;
      they communicate through flags and ring buffers.
      Latency: microseconds for ISR work, whole loop for
               the rest. RAM: one stack + ISR frames.
      Use when: the urgent work is SHORT. This covers a
               remarkable proportion of real products.

   3. COOPERATIVE SCHEDULER
      Tasks yield explicitly; the scheduler picks the next.
      No preemption, so still no data races between tasks.
      Latency: longest run between yields.
      RAM: one stack per task.
      Use when: you want task structure but cannot afford
               preemption's synchronisation burden.

   4. PREEMPTIVE RTOS
      The kernel switches on a tick or an event; a
      high-priority task runs as soon as it is ready.
      Latency: bounded by the kernel, typically a few us.
      RAM: one stack per task + kernel overhead (2-10 kB).
      Cost: RACES ARE NOW POSSIBLE. Every shared variable
            needs a mutex, a queue, or an atomic.
      Use when: multiple independent deadlines, or blocking
               sequences you want written as sequences.

   Moving from 2 to 4 buys bounded latency and pays for it
   in synchronisation bugs. That is a real trade and the
   step should be deliberate.

The pattern that delays the decision

/* Most "we need an RTOS" moments are actually "we need to
   get work out of the ISR". Deferred processing solves that
   without a kernel.                                       */

static volatile uint8_t  ring[256];
static volatile uint8_t  head, tail;   /* single producer,  */
                                       /* single consumer   */

void USART1_IRQHandler(void)           /* PRODUCER: ISR     */
{
    uint8_t next = (uint8_t)(head + 1);
    if (next != tail) {                /* drop if full      */
        ring[head] = (uint8_t) USART1->RDR;
        head = next;                   /* publish LAST      */
    }
}

void service_comms(void)               /* CONSUMER: loop    */
{
    while (tail != head) {
        parse_byte(ring[tail]);
        tail = (uint8_t)(tail + 1);
    }
}

/* WHY THIS IS SAFE WITHOUT A LOCK:
   - exactly one writer of head (the ISR), one writer of
     tail (the loop);
   - both are single bytes, so reads and writes are atomic
     on Cortex-M;
   - head is published AFTER the data is written, so the
     consumer never sees an index for a byte not yet
     stored. On Cortex-M's ordering this holds; on a weakly
     ordered core you would need a release barrier here,
     which is exactly what the ARM track's barriers chapter
     is about.
   - the size is a power of two, so the wrap is free and
     the index arithmetic cannot go wrong.

   THE ISR IS NOW ~10 CYCLES. All the parsing happens in the
   loop, at whatever rate it manages, and a burst is
   absorbed by the buffer. This single pattern removes the
   need for an RTOS in a large fraction of designs.        */

When to actually move up

SymptomFix
One function occasionally takes 50 ms and everything stuttersSplit it into a state machine first; an RTOS only hides the problem
ISR does too much workDeferred processing with a ring buffer — no kernel needed
Two independent deadlines that cannot both be met by one loopA preemptive RTOS. This is the real reason
Sequential protocols with many wait states become unreadableA preemptive RTOS, for readability
A third-party stack (TCP/IP, BLE, USB) demands oneUse the one it expects — fighting it costs more than it saves
You want "threads" because it feels more professionalNot a reason. The superloop is a legitimate architecture
RAM is under 8 kBYou cannot afford a preemptive kernel; stay with 1 or 2
Safety certification is requiredEither — but the superloop is far easier to argue for, which is why safety-critical code often uses it
An RTOS does not make a slow system fast

If your control loop misses its deadline because the computation takes too long, adding a scheduler adds overhead and changes nothing. An RTOS reallocates latency, letting urgent work preempt unimportant work. It cannot create CPU time. Diagnose which problem you have — measure with the cycle counter from chapter 16 — before assuming a kernel is the answer.
