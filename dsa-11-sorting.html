Sorting: the algorithms and custom comparators

You will rarely implement a sort in an interview, but you will constantly use one — and you will be asked how merge sort and quicksort work, why one is stable, and when sorting is worth its log factor.

The algorithms worth knowing

You will almost never implement a sort in an interview, and you will regularly be asked to choose one and justify it. These are the four worth being able to compare, with the property that actually distinguishes them.

   MERGE SORT — divide and conquer, always n log n
     split in half, sort each half, MERGE the two sorted
     halves with two pointers (chapter 20's merge).
     T(n) = 2T(n/2) + O(n)  ->  O(n log n)

     + STABLE, predictable, parallelises, works on linked
       lists with O(1) extra space
     - needs O(n) scratch space for arrays

   QUICKSORT — partition around a pivot
     choose a pivot, move smaller elements left and larger
     right, recurse on both sides.
     Average O(n log n); WORST O(n^2) when the pivot is
     always extreme (a sorted array with a first-element
     pivot).

     + in place, excellent cache behaviour, fastest in
       practice
     - unstable, and the worst case is real
     FIXES: random pivot, median-of-three, or introsort
     (switch to heapsort once recursion gets too deep) —
     which is what std::sort actually does.

   WHAT YOUR LANGUAGE ACTUALLY USES:
     C++ std::sort        introsort — NOT stable
     C++ stable_sort      merge sort
     Java primitives      dual-pivot quicksort — not stable
     Java objects         TimSort — STABLE
     Python sorted()      TimSort — STABLE
     JavaScript .sort()   STABLE since ES2019

   STABILITY MEANS equal elements keep their original
   relative order. It matters whenever you sort by one key
   and then by another: sort by the SECONDARY key first,
   then STABLY by the primary, and the secondary order
   survives inside each group.

   NON-COMPARISON SORTS beat n log n by not comparing:
     COUNTING SORT  O(n + k) for integers in a small range k
     RADIX SORT     O(d(n + k)) digit by digit
     BUCKET SORT    O(n) for uniformly distributed values
   The n log n lower bound applies only to COMPARISON sorts,
   which is a good thing to say when someone asks whether
   you can beat it.

Comparators — where the bugs are

Comparators cause more wrong answers in this track than any algorithm does, and the reasons are mundane: one language default that surprises everyone, and one contract that is easy to violate without noticing.

/* --- THE JAVASCRIPT TRAP, first of all --- */
[10, 9, 1].sort()                // ["1","10","9"] LEXICOGRAPHIC
[10, 9, 1].sort((a, b) => a - b) // [1, 9, 10]

/* THE CONTRACT: return NEGATIVE if a comes first, POSITIVE
   if b comes first, ZERO if equivalent.                   */

/* --- MULTI-KEY: chain with || --- */
people.sort((a, b) =>
      a.age - b.age            // primary:   age ascending
   || b.score - a.score        // secondary: score DESCENDING
   || a.name.localeCompare(b.name));   // tertiary: name

/* `||` works because 0 is falsy — a tie on one key falls
   through to the next.

/* --- STRINGS --- */
words.sort((a, b) => a.localeCompare(b));   // locale-aware
words.sort((a, b) => (a < b ? -1 : a > b ? 1 : 0));  // by code unit

/* --- THE SUBTRACTION TRAP --- */
    a - b OVERFLOWS in C++/Java when the values are far
    apart. Use explicit comparison instead:
        Integer.compare(a, b)          // Java
        return a < b ? -1 : (a > b);   // C++ — or just a < b
    In JavaScript doubles do not overflow, but the habit is
    worth keeping.

/* --- SORTING PAIRS AND KEEPING INDICES --- */
    const idx = nums.map((v, i) => [v, i])
                    .sort((a, b) => a[0] - b[0]);
    // now idx[j] = [value, ORIGINAL index]
    // this is how you sort when the answer needs the
    // original positions (chapter 14's Two Sum problem)

/* --- SORT BY A COMPUTED KEY, computed ONCE --- */
    // BAD: recomputes the key O(n log n) times
    words.sort((a, b) => score(a) - score(b));
    // GOOD: Schwartzian transform — compute n times
    words.map(w => [score(w), w])
         .sort((x, y) => x[0] - y[0])
         .map(p => p[1]);

/* --- A COMPARATOR MUST BE CONSISTENT --- */
    It must be transitive and antisymmetric. An inconsistent
    comparator (for instance one using a random tiebreak, or
    `a.x > b.x ? 1 : -1` with no zero case) can crash
    Java's TimSort with "Comparison method violates its
    general contract".                                    */
