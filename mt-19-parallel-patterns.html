Parallel patterns and how to decompose work

Almost every parallel program is one of six shapes. Recognising which one you have tells you where the synchronisation goes, what the scaling limit is, and — usually — that you can avoid sharing altogether.

The six

Most parallel programs are one of a handful of shapes. Recognising which shape a problem has is more valuable than any individual technique, because the shape determines the synchronisation you will need.

   1. EMBARRASSINGLY PARALLEL / MAP
        f(x) for every x, independently.
        NO shared state, NO synchronisation, linear scaling
        until you hit memory bandwidth.
        -> image filters, hashing files, per-request work.

   2. REDUCE
        combine N values into one with an associative op.
        Tree-shaped: log N depth, and the only sync is at the
        joins.
        -> sum, max, count, histogram merge.

   3. MAP-REDUCE (scatter-gather)
        map, then reduce. The overwhelmingly common shape.
        -> "count word frequencies", "sum per customer".

   4. PIPELINE
        stage1 -> stage2 -> stage3, each on its own thread,
        items flowing through.
        Throughput = the SLOWEST stage. Latency = the sum.
        -> decode -> filter -> encode; parse -> plan -> exec.

   5. FORK-JOIN / DIVIDE AND CONQUER
        split, recurse in parallel, combine. Naturally
        matches work stealing (chapter 17).
        -> quicksort, mergesort, tree traversal, FFT.

   6. PRODUCER-CONSUMER
        decouple rates with a queue. Not really about speed -
        about smoothing bursts and isolating failure.
        -> logging, request queues, sensor to processor.

   AND THE ONE THAT IS NOT A PATTERN:
      "put a mutex around the shared thing and run it on
      8 threads". That is not a decomposition, it is a hope.

Map, and the mistake in it

The simplest and most valuable pattern: the same independent operation applied to many items. When a problem fits this, parallelising it is nearly free of synchronisation — which is exactly why it should be the first thing you check for.

/* THE OBVIOUS VERSION - and why it is slow. */

std::atomic<long> total{0};

parallel_for(0, n, [&](int i) {
        total += expensive(data[i]);     /* EVERY iteration
                                            writes one atomic  */
});
/* All threads hammer one cache line. Often SLOWER than the
   serial loop (chapter 16).                                 */

/* THE FIX: privatise, then combine. Once. */

struct alignas(64) Partial { long v = 0; };
std::vector<Partial> partial(nthreads);

parallel_for_chunked(0, n, [&](int lo, int hi, int tid) {
        long local = 0;                  /* a REGISTER, not
                                            even memory        */
        for (int i = lo; i < hi; i++)
                local += expensive(data[i]);
        partial[tid].v = local;          /* ONE write, ever    */
});
long total = 0;
for (auto &p : partial) total += p.v;    /* nthreads adds      */

/* The pattern, in one line: ACCUMULATE PRIVATELY, MERGE ONCE.
   It applies to counters, histograms, string builders, output
   buffers, allocators, random number generators - anything
   where the combine is associative.                          */

/* And the libraries already do it: */
        std::reduce(std::execution::par, v.begin(), v.end(), 0L);
        v.par_iter().map(expensive).sum::<i64>();      // Rayon
        #pragma omp parallel for reduction(+:total)    // OpenMP
Granularity is the single biggest lever

Too fine and scheduling overhead dominates: a task that takes 100 ns cannot pay for a 1 µs enqueue. Too coarse and the tail dominates: 8 chunks on 8 cores means one slow chunk leaves 7 cores idle. The usual sweet spot is tasks of roughly 10–100 µs, and 4–8× more chunks than cores so the scheduler can balance. Both numbers are worth measuring rather than trusting.

Pipelines

When work must pass through stages in order, the stages themselves can run concurrently on different items. Throughput is then set by the slowest stage, which makes the optimisation target obvious.

/* Three stages, bounded queues between them. */

BoundedQueue<Raw>     q1(64);
BoundedQueue<Decoded> q2(64);

std::thread reader([&] {
        Raw r;
        while (read_next(&r)) q1.push(r);
        q1.close();                       /* propagate the end  */
});
std::thread decoder([&] {
        Raw r;
        while (q1.pop(&r)) q2.push(decode(r));
        q2.close();
});
std::thread writer([&] {
        Decoded d;
        while (q2.pop(&d)) write_out(d);
});

/* THE PROPERTIES

   throughput = 1 / (slowest stage time)
        adding threads to the FAST stages changes nothing.
        Find the slow stage and parallelise THAT - a pipeline
        where stage 2 is the bottleneck becomes
        stage1 -> [stage2 x 4] -> stage3.

   latency = sum of all stages + queueing
        a pipeline makes throughput better and latency WORSE.
        If you care about latency, this is the wrong pattern.

   BOUNDED queues are mandatory
        an unbounded queue between a fast producer and a slow
        consumer converts backpressure into memory exhaustion,
        far away from the cause.

   CLOSING must propagate
        each stage closes its output when its input closes and
        it has drained. Miss one and shutdown hangs -
        the commonest pipeline bug.

   ORDER is not preserved once you widen a stage.
        If output order matters you need sequence numbers and
        a reorder buffer at the end, which is real work.     */

Fork-join

Recursive problems split into independent sub-problems that are solved in parallel and combined. The important detail is knowing when to stop splitting, because at some size the overhead exceeds the work.

/* Parallel mergesort, with the two details that matter. */

void psort(int *a, int n, int depth)
{
        /* DETAIL 1: a cutoff. Below it, go serial. Without
           this you create a task per ELEMENT and spend all
           your time scheduling. */
        if (n < 4096) { std::sort(a, a + n); return; }

        /* DETAIL 2: bound the depth, or the task count
           explodes. depth 0 means "no more forking". */
        int mid = n / 2;
        if (depth > 0) {
                auto left = std::async(std::launch::async,
                                       [&]{ psort(a, mid, depth-1); });
                psort(a + mid, n - mid, depth - 1);
                left.get();                    /* join */
        } else {
                psort(a, mid, 0);
                psort(a + mid, n - mid, 0);
        }
        std::inplace_merge(a, a + mid, a + n);
}
/* call with depth = log2(hardware_concurrency) + 1 */

/* WITH A WORK-STEALING RUNTIME you can skip the depth bound -
   that is exactly what stealing is for. Rayon: */
        fn psort(a: &mut [i32]) {
            if a.len() < 4096 { a.sort(); return; }
            let mid = a.len() / 2;
            let (l, r) = a.split_at_mut(mid);
            rayon::join(|| psort(l), || psort(r));   /* steals  */
            merge(l, r);
        }
/* rayon::join is nearly free when nobody steals - it pushes
   the right half and runs the left inline. The cutoff is
   still needed; the depth bound is not.                     */

Choosing a decomposition

Before any of the patterns can be applied, the problem must be divided — and how you divide it determines how much synchronisation the result needs. This is where most parallel performance is won or lost.

   THREE WAYS TO CUT A PROBLEM

   BY DATA        each thread gets a slice of the data and
                  runs the same code.
                  + scales with data size
                  + easy to balance
                  - needs the data to be splittable
                  -> the default. Try this first.

   BY TASK        each thread runs different code.
                  + suits heterogeneous work
                  - scales to the NUMBER OF TASKS, not cores
                  - balancing is manual and usually wrong
                  -> pipelines, and GUI-plus-worker.

   BY PIPELINE    each thread is a stage.
                  + good for streaming, bounded memory
                  - throughput capped by the slowest stage
                  - latency increases

   THE QUESTIONS THAT PICK ONE

     Is the work uniform?        yes -> data
     Is there a natural stream?  yes -> pipeline
     Is the work heterogeneous?  yes -> task
     Does order matter?          if yes, avoid widening stages
     Is state shared?            if yes, can you privatise it?
                                 (usually yes - do that first)
Load imbalance beats almost every other inefficiency

Eight chunks on eight cores where one chunk takes twice as long means seven cores idle for half the run — a 43% loss, invisible in any lock profile. Fix it with more, smaller chunks plus dynamic scheduling (schedule(dynamic) in OpenMP, work stealing elsewhere) rather than by trying to predict chunk costs. Static partitioning is only right when every item genuinely costs the same.
