The kernel source tree and how to navigate it

Forty million lines of C, and you will never read most of it. What you need is the skill of finding the twenty lines that matter in under a minute — which is a learnable, mechanical skill, and the first one to acquire.

Want the picture before the paths?

Chapter 03 is a single diagram of every layer and subsystem in the kernel, with each one mapped to the directory it lives in. If you prefer to see the whole shape before learning to navigate it, read that first and come back here — the two chapters are designed to be read in either order.

Getting it

Everything in this track assumes you have the source to hand. It is a large download but it is the reference you will consult constantly — far more often than any book — so it is worth setting up properly once.

# The mainline tree, full history. ~4 GB, worth having.
git clone https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux

# Shallow, if you only want to read one version:
git clone --depth 1 --branch v6.12 \
    https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

# The trees you will care about in embedded work:
#   torvalds/linux          mainline - where everything lands
#   stable/linux-stable     the -stable branches, v6.12.y etc.
#   next/linux-next         everything queued for the NEXT merge
#                           window; check here before writing
#                           something that already exists
#   soc/soc                 the arm-soc tree
#   <vendor>/<board>        the BSP you actually ship, usually
#                           an old LTS plus 3,000 patches

# THE VERSION SCHEME:
#   6.12        a mainline release, roughly every 9-10 weeks
#   6.12.34     a stable update: fixes only, no features
#   6.12-rc3    a release candidate
#   LTS         one release a year, maintained ~2-6 years.
#               6.1, 6.6, 6.12... - this is what products ship.

The layout

The top level of the tree has about twenty directories, and their names are terse but entirely logical. Learning what lives where takes ten minutes and saves you from searching the whole tree every time you need something.

linux/

      arm64/boot/dts/       DEVICE TREES live here
      arm64/kernel/         entry.S, setup.c, the exception

      arm64/mm/             page table code
      arm64/include/asm/    architecture headers

                 you think. Documentation/driver-api/,
                 Documentation/devicetree/bindings/ ...

  drivers/       ~70% of the tree. Where your code goes.

      gpio/  i2c/  spi/  pci/  usb/  net/  mmc/  tty/

  mm/            memory management: page_alloc.c, slub.c,
                 vmalloc.c, mmap.c

  security/      LSMs: SELinux, AppArmor, IMA

  virt/          KVM
Three directories carry most of your work

For embedded driver development it is drivers/ for the code, include/linux/ for the API you are calling, and Documentation/ for why. arch/arm64/boot/dts/ joins them the moment you touch hardware description. Everything else you visit occasionally.

Finding things — the actual skill

Nobody reads the kernel; people search it. The difference between someone who finds the relevant twenty lines in a minute and someone who spends an afternoon lost is almost entirely a matter of knowing which tool to point at which question.

# SET UP ONE OF THESE ON DAY ONE. Grepping 40 million lines
# interactively does not scale.

# cscope + ctags, the classic:
make ARCH=arm64 cscope tags
#   vim -t symbol_name        jump to a definition
#   Ctrl-]                    follow
#   :cs find c func           who CALLS this?

# Or the modern option, and the better one:
#   clangd + compile_commands.json
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)
./scripts/clang-tools/gen_compile_commands.py
# now any LSP editor gives you real go-to-definition,
# find-references, and call hierarchies - CONFIG-aware, which
# grep is not.

# Or the web: https://elixir.bootlin.com/linux/latest/source
# Cross-referenced, version-switchable, no setup. Use it when
# you are away from your build machine. It is excellent.

# git grep is fast enough for a lot:
git grep -n "devm_platform_ioremap_resource" -- drivers/ | head
git grep -n "EXPORT_SYMBOL_GPL(dma_alloc_attrs)"
git grep -W "static int spi_probe"        # -W = whole function

# Restrict by directory, always:
git grep -n "regmap_write" -- drivers/iio/

The five questions, and how to answer each

In practice, almost everything you need to look up is one of five recurring questions. Each has a reliable mechanical answer, and knowing the answer turns "I don't know where to start" into a specific command.

# 1. "WHAT DOES THIS FUNCTION DO?"
     git grep -n "^\(static \)\?[a-z_ *]*\bfunc_name\b *(" -- '*.c'
   The DEFINITION is what you want, not the 200 call sites.
   Then read the kernel-doc comment above it - most exported
   functions have one, and it is usually accurate.

# 2. "HOW DO I USE THIS API?"
     Find an EXISTING DRIVER that uses it, and copy its shape.
     git grep -l "devm_request_threaded_irq" -- drivers/ | head
   This is the single most effective kernel technique. The tree
   is its own best documentation, because every user compiles
   and most were reviewed.
     Prefer a RECENT, SIMPLE driver: check `git log --oneline -3`
   on the file. Old drivers use deprecated patterns.

# 3. "WHY IS IT LIKE THIS?"
     git log -p --follow drivers/foo/bar.c
     git log -S "the_exact_string" -- drivers/foo/
     git blame drivers/foo/bar.c
   Kernel commit messages are unusually good. The one that
   introduced the odd-looking line usually explains the bug it
   fixed, with the reproducer.

# 4. "WHO CALLS THIS?"
     LSP find-references, or cscope, or:
     git grep -n "\bfunc_name\b" -- '*.c' '*.h'
   Watch for indirect calls through ops structures - grep finds
   `.probe = my_probe` but not the core code that invokes it.
   For those, search for the STRUCT MEMBER name instead:
     git grep -n "->probe(" -- drivers/base/

# 5. "IS THIS CODE EVEN COMPILED?"
     The most common wasted hour. Find the Makefile:
     cat drivers/foo/Makefile
       obj-$(CONFIG_FOO) += foo.o
     then check your .config:
     grep CONFIG_FOO .config
   And check the #ifdefs. Half the file may be behind
   CONFIG_PM or CONFIG_OF. Reading code that your build never
   compiles is a genuinely common failure mode - which is why
   an LSP with your real compile_commands.json beats grep.
Read a subsystem in this order
  1. Documentation/ for the subsystem — the design intent.
  2. include/linux/<subsys>.h — the public API and the key structs. This is the contract.
  3. The smallest, newest driver in that subsystem — the shape of a real user.
  4. The core file — only now, and only the paths your driver touches.

Going straight to the core file is the mistake everyone makes once. You will read 4,000 lines of generic machinery before learning what it is for.

Conventions that decode the code

Kernel source relies on a set of naming and annotation conventions that carry real semantic weight — a prefix or macro here is not decoration, it is the kernel telling you a rule that will not be enforced any other way. Reading unfamiliar driver code fluently means recognising these on sight, the same way a fluent reader of any language stops noticing punctuation as separate work.

You seeIt means
__initUsed only at boot; freed afterwards. Calling it later is a bug.
__exitOnly in a module unload path; discarded if built in.
__userA user-space pointer. Never dereference (ch. 09). Checked by sparse.
__iomemAn MMIO pointer. Use readl/writel, not *p (ch. 26).
__percpu, __rcuAccess only through the matching accessors.
__must_checkIgnoring the return value is a warning — and usually a bug.
staticFile-local. Most driver functions are. If it is not static, ask why.
EXPORT_SYMBOL_GPLAvailable to GPL modules only. The absence of an export is a deliberate boundary.
devm_*Device-managed: freed automatically on unbind (ch. 33). Prefer these.
__weakA default that an architecture or driver may override.
likely(), unlikely()Branch hints. unlikely almost always marks an error path.
ERR_PTR, IS_ERR, PTR_ERRAn error code smuggled inside a pointer. Check with IS_ERR, never against NULL.
A trailing _locked or __ prefixThe caller must already hold the relevant lock.

Kconfig: how code is selected

Not all of the source is built. Which files end up in your kernel is decided by a configuration system, and understanding how a file gets selected explains both how to enable something and why an option you want sometimes cannot be turned on at all.

# drivers/foo/Kconfig
config FOO_DRIVER
        tristate "Foo device support"      # tristate: y/m/n
        depends on ARCH_MYSOC && OF        # only offered if...
        select REGMAP_MMIO                 # force this on
        default n
        help
          Say Y here if you have a Foo device.

# drivers/foo/Makefile
obj-$(CONFIG_FOO_DRIVER) += foo.o          # y -> built in
                                           # m -> a module
foo-objs := foo-core.o foo-hw.o            # multi-file module

# THE THREE STATES, and they matter:
#   y  compiled into vmlinux. Available at boot. No unload.
#   m  a .ko module. Loadable, unloadable, and therefore
#      exercisable - which makes development far faster.
#   n  not compiled at all.

# depends on   the option is HIDDEN unless the dependency is met
# select       forcibly enables another option - use sparingly,
#              it bypasses that option's own dependencies and is
#              a classic source of unbuildable configs

# FINDING WHY AN OPTION IS UNAVAILABLE:
make ARCH=arm64 menuconfig
#   press '/' and search for the symbol. It shows the full
#   dependency chain and what you must enable first. This one
#   keystroke answers 90% of "why can't I turn this on".

Where the real answers are

The kernel's own source tree tells you what the code does, but not why it does it that way — the reasoning, the rejected alternatives, and the arguments over a design almost always live outside the repository, in the mailing-list threads that produced it. Knowing which of these resources to reach for saves the hours otherwise spent reverse-engineering intent from a diff alone.

ResourceUse
elixir.bootlin.comCross-referenced source, any version. Best browser.
lore.kernel.orgEvery mailing list, searchable. The design discussion behind any patch.
LWN.netThe best writing about kernel development anywhere. Read the merge-window summaries.
Documentation/process/How to submit, how to report bugs, the coding style.
scripts/get_maintainer.plWho owns this file and which list to ask.
git logUnderrated. The answer to "why" is usually in a commit message.
 
# Who maintains the code you are about to change?
./scripts/get_maintainer.pl -f drivers/tee/optee/core.c

# What has changed in this file recently, and by whom?
git log --oneline -20 -- drivers/tee/optee/

# Has someone already proposed what I am about to write?
#   search lore.kernel.org, and check linux-next.
# This takes five minutes and occasionally saves a month.

Check yourself

  • Name what lives in drivers/, include/linux/, include/uapi/, arch/arm64/ and Documentation/.
  • Set up cscope/ctags or clangd against a configured tree, and jump to a definition.
  • Answer all five questions for a function you have never seen.
  • Explain why finding an existing user beats reading the core implementation first.
  • Decode __init, __user, __iomem, devm_ and ERR_PTR on sight.
  • Read a Kconfig entry and say what it takes to enable it.
  • Explain the difference between y and m, and why m is better during development.
  • Use get_maintainer.pl and find the discussion behind a commit on lore.
