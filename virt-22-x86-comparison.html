The other architecture: VT-x, VMCS and EPT

Everything so far has been ARM. Most hypervisor source you will read was written for x86 first, and almost every concept transfers with a different name — except one structural difference, which turns out to explain why ARM needed VHE and x86 never did.

Why this chapter exists

You do not need x86 to write an ARM hypervisor. You do need it to read KVM, Xen, or almost any paper or mailing-list thread about virtualisation, because the vocabulary is x86's and the ARM support was added afterwards.

   THE PRACTICAL REASONS TO KNOW BOTH:

     · KVM's common code is shaped by x86. Reading
       virt/kvm/*.c means reading x86 assumptions
       (chapter 18).
     · Papers, CVEs and conference talks use x86 terms.
       "EPT violation" and "VMCS" appear constantly.
     · Server and automotive work frequently spans both.
     · The differences are instructive: where the two
       architectures diverge, there is usually a design
       argument worth understanding.

   THE STRUCTURE OF THIS CHAPTER: the translation table
   first, then the ONE genuine structural difference, then
   the places where the mapping breaks down.

The one structural difference that matters

If you take one thing from this chapter, take this. ARM made EL2 a privilege level; x86 made root mode a parallel universe. That single choice explains several things that otherwise look arbitrary.

   ARM, ORIGINALLY:

     EL2  hypervisor        a DIFFERENT exception level,
                            with its OWN register names
                            (TTBR0_EL2, TCR_EL2 ...) and a
                            different layout from EL1
     EL1  guest kernel
     EL0  guest user

   A HOST KERNEL WANTING TO BE A HYPERVISOR had a problem:
   it is written for EL1, but the hypervisor must be at EL2.
   KVM's answer was to SPLIT - most of Linux stays at EL1, a
   small stub lives at EL2, and they call each other. That
   split is why nVHE exists, and why the world switch has
   the shape it does (chapter 09).

   ---------------------------------------------------------

   x86, FROM THE START:

     ROOT MODE          ring 0   hypervisor
                        ring 3   the VMM's user-space half
     NON-ROOT MODE      ring 0   guest kernel
                        ring 3   guest user

   ROOT/NON-ROOT IS ORTHOGONAL TO RINGS. The hypervisor runs
   in ring 0 - the SAME ring the kernel always ran in, with
   the SAME registers. Linux did not need to be rewritten to
   host guests; it just enters root mode and carries on.

   ---------------------------------------------------------

   SO: x86 NEVER NEEDED VHE, because it never had the
   problem VHE solves. ARMv8.1 added VHE to give EL2 an
   EL1-compatible register layout - which is, in effect,
   retrofitting x86's property onto ARM.

   THIS IS THE SINGLE MOST USEFUL THING TO CARRY FROM THIS
   CHAPTER: when you read that VHE "lets the host kernel run
   at EL2 unmodified", the x86 comparison tells you exactly
   what was being fixed.

The VMCS, and why it is not just a struct

The second real difference is smaller but bites immediately when reading code: on Intel you cannot simply dereference the guest context. It is an opaque structure with its own access instructions.

/* ARM: the vCPU context is ordinary memory. You read it. */
u64 far = vcpu->arch.fault.far_el2;
vcpu->arch.ctxt.regs.pc += 4;

/* INTEL: the VMCS has an IMPLEMENTATION-DEFINED layout.
   The processor may keep parts of it in internal caches, so
   it is reached only through two instructions.            */
u64 qual;
vmread(EXIT_QUALIFICATION, &qual);      /* not a load  */
vmwrite(GUEST_RIP, rip + len);          /* not a store */

/* WHY: it lets the processor cache hot fields internally
   and arrange the rest however it likes. The cost is that
   every field access is an instruction with real latency,
   which is why x86 hypervisors cache VMCS fields in
   software and batch their writes.

   AMD DID THE OPPOSITE. The VMCB is an architecturally
   defined structure in ordinary memory, read and written
   with ordinary loads and stores - much more like ARM. When
   you see KVM code with an svm/ and a vmx/ directory doing
   the same job very differently, this is usually why.   */

/* AND THE TRAP POLICY, compared:

     ARM     one register, HCR_EL2, plus a few friends.
             Readable in one page (chapter 04).

     INTEL   pin-based controls, primary processor-based
             controls, secondary controls, tertiary
             controls, an MSR bitmap, an I/O bitmap, and an
             exception bitmap - all VMCS fields, added in
             layers as the architecture grew.

   SAME IDEA, accumulated differently. ARM had the advantage
   of designing it once, after watching x86 do it.        */

Where the mapping breaks down

The analogy is good but not total, and the places it fails are worth knowing before you assume an x86 technique transfers.

DifferenceConsequence
x86 has no architectural equivalent of the SMC / secure-world splitTrustZone, S-EL2 and FF-A (chapter 20) have no direct counterpart; SMM is a different thing with a different purpose
x86 instruction encoding is variable-length and complexEmulating a faulting instruction requires a full decoder — a large, historically bug-prone body of code. ARM's fixed-width encoding and syndrome register hand the hypervisor most of what it needs
x86 has legacy modes (real, protected, v8086)A hypervisor must handle guests that switch modes during boot; ARM guests start in one place and stay there
ARM's system-register space is vast and trapped per-registerTrap policy is finer grained, and there are many more registers to save and restore
ARM implementations vary enormouslyFeature detection is mandatory (chapter 03); x86 is comparatively uniform
ARM platform devices are not discoverableDevice tree is required where x86 has PCI enumeration and ACPI (chapter 14)
Memory attributes combine differentlyARM's stage-1/stage-2 combining rule (chapter 07) has no close x86 analogue; EPT memory types work another way
The instruction-decoder difference is bigger than it looks

When an ARM guest faults on an MMIO access, ESR_EL2 usually tells the hypervisor the access size, the direction, and which register was involved — so the device model can be driven without ever looking at the instruction. On x86 the exit qualification frequently does not, and the hypervisor must fetch and decode the faulting instruction itself. That decoder has to handle prefixes, ModRM, SIB, and the full legacy encoding space, and it has historically been a rich source of escapes and correctness bugs. It is a good illustration of a general point: a syndrome register that reports what the instruction was trying to do, rather than leaving the hypervisor to work it out, removes an entire class of vulnerability.
