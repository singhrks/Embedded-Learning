Borrowing and references

Access without ownership, governed by one rule: many readers or one writer, never both. That single constraint eliminates data races, iterator invalidation and aliasing bugs simultaneously — because all three are the same problem.

The rule

One rule governs references, and the whole borrow checker is its enforcement. Like the ownership rules, it is short enough to memorise and worth memorising.

   AT ANY GIVEN TIME, for any given value, you may have
   EITHER:

     · any number of SHARED references    &T
     · exactly one EXCLUSIVE reference    &mut T

   but never both, and never two exclusive ones.

   AND every reference must be VALID for its whole lifetime -
   it cannot outlive what it points to (chapter 04).

        let mut v = vec![1, 2, 3];

        let a = &v;             // shared
        let b = &v;             // another shared - FINE
        println!("{a:?} {b:?}");

        let m = &mut v;         // exclusive - fine, because
                                // a and b are no longer USED
        m.push(4);

        println!("{a:?}");      // ERROR if this came after
                                // the &mut

   NON-LEXICAL LIFETIMES: a borrow ends at its LAST USE, not
   at the end of the scope. So this compiles:

        let a = &v;
        println!("{a:?}");      // a's last use
        let m = &mut v;         // fine - a is dead
        m.push(4);

   which is why modern Rust is far less irritating than the
   2015-era descriptions suggest.

   THE NAMES: `&T` is often called "immutable" and `&mut T`
   "mutable", but SHARED and EXCLUSIVE are the accurate
   words - the real distinction is aliasing, not mutation.
   Cell and Mutex allow mutation through &T (chapter 10),
   which is only confusing if you learned the wrong names.

What it eliminates

The rule looks restrictive until you see the specific bug classes it makes impossible — several of which you will recognise from debugging C.

/* --- 1. ITERATOR INVALIDATION --- */
    let mut v = vec![1, 2, 3];
    for x in &v {               // v is borrowed SHARED here
        v.push(*x);             // ERROR - push needs &mut
    }
/* THE C++ EQUIVALENT compiles, runs, and corrupts memory
   when the vector reallocates (C++ chapter 08). Here it is a
   compile error, and the error message says exactly why.

/* --- 2. USE AFTER FREE --- */
    let r;
    {
        let x = 5;
        r = &x;
    }
    println!("{r}");            // ERROR: `x` does not live
                                // long enough

/* --- 3. DATA RACES --- */
    let mut data = vec![1, 2, 3];
    thread::spawn(|| data.push(4));     // ERROR - the closure
    data.push(5);                       // would need &mut
                                        // while main also
                                        // has it
/* The SAME RULE that prevents iterator invalidation prevents
   data races, because they are the same shape: two paths to
   one value, one of them writing.

/* --- 4. ALIASING BUGS --- */
    fn f(a: &mut i32, b: &mut i32) { *a = 1; *b = 2; }
    let mut x = 0;
    f(&mut x, &mut x);          // ERROR - two exclusive
                                // borrows
/* In C this is legal, and the compiler must assume a and b
   may alias - which prevents optimisation. Rust's guarantee
   is why rustc emits LLVM's `noalias` on &mut parameters,
   and why Rust sometimes optimises BETTER than the
   equivalent C.                                          */

Borrowing in functions

Passing references to functions is where borrowing meets everyday code, and the choice between the three forms is a design decision you make constantly.

    fn read(v: &Vec<i32>) -> i32 { v[0] }       // shared
    fn modify(v: &mut Vec<i32>) { v.push(4); }  // exclusive
    fn consume(v: Vec<i32>) { }                 // takes
                                                // ownership

    let mut v = vec![1, 2, 3];
    read(&v);
    modify(&mut v);
    println!("{v:?}");          // still usable
    consume(v);
    println!("{v:?}");          // ERROR - moved

/* THE PARAMETER RULE, and it is the whole design decision:
     need to READ it              -> &T
     need to MODIFY it in place   -> &mut T
     need to KEEP it              -> T
   Exactly the C++ const-ref / ref / value decision
   (C++ chapter 04), but enforced.

/* PREFER SLICES TO CONCRETE TYPES: */
    fn sum(v: &Vec<i32>) -> i32 { ... }         // narrow
    fn sum(v: &[i32])    -> i32 { ... }         // BETTER

    sum(&vec);                  // Vec derefs to a slice
    sum(&array);                // arrays too
    sum(&vec[1..3]);            // and sub-slices

    fn greet(s: &String) { }    // narrow
    fn greet(s: &str)    { }    // BETTER - accepts String,
                                // &str and literals
/* This is exactly the std::span / std::string_view advice
   from C++ chapter 08, and for the same reason.

/* METHODS take self in one of four ways: */
    impl Buffer {
        fn len(&self) -> usize { ... }          // read
        fn push(&mut self, b: u8) { ... }       // modify
        fn into_vec(self) -> Vec<u8> { ... }    // CONSUMES
        fn new() -> Self { ... }                // no self -
                                                // an
                                                // associated
                                                // function
    }
/* `into_*` by convention means "consumes self". `as_*` means
   a cheap borrowed view. `to_*` means an expensive
   conversion producing an owned value. Following those
   conventions makes an API readable at a glance.        */
The mutability is on the binding, not the type 
let v = vec![1];        // immutable binding
v.push(2);              // ERROR
let mut v = vec![1];    // mutable binding
v.push(2);              // fine

fn f(v: &mut Vec<i32>)  // an exclusive reference
let mut r = &v;         // a MUTABLE BINDING holding a
                        // SHARED reference - r can be
                        // reassigned, *r cannot be written

mut in a let and mut in &mut are different things, and reading them as one is a common early confusion.

Working with the checker

When the checker refuses something you know is correct, there is usually a standard restructuring that expresses the same thing in a form it can verify. These are the ones worth knowing.

/* --- 1. TWO FIELDS OF ONE STRUCT: fine --- */
    struct S { a: Vec<i32>, b: Vec<i32> }
    let ra = &mut s.a;
    let rb = &mut s.b;          // FINE - disjoint fields
/* The compiler tracks fields separately. But NOT through a
   method: */
    let ra = s.get_a_mut();     // borrows ALL of s
    let rb = s.get_b_mut();     // ERROR
/* Fix by having one method return both, or by borrowing the
   fields directly.

/* --- 2. SPLITTING A SLICE --- */
    let (left, right) = v.split_at_mut(mid);
    // two &mut into DISJOINT halves - the standard library
    // provides this because it needs unsafe internally, and
    // it is proved correct once so you never need to.

    for chunk in v.chunks_mut(64) { ... }
    let [a, b] = v.get_disjoint_mut([0, 5]).unwrap();  // 1.86

/* --- 3. A LOOP THAT MODIFIES WHAT IT ITERATES --- */
    // WRONG:
    for x in &v { if bad(x) { v.remove(...); } }
    // RIGHT:
    v.retain(|x| !bad(x));
    // or collect the indices first, or iterate mutably:
    for x in &mut v { *x += 1; }
    // or drain:
    let removed: Vec<_> = v.drain(..).filter(keep).collect();

/* --- 4. RETURNING A REFERENCE INTO A LOCAL: impossible --- */
    fn f() -> &str {
        let s = String::from("hi");
        &s                      // ERROR
    }
    fn f() -> String { String::from("hi") }     // return the
                                                // value

/* --- 5. THE SELF-REFERENTIAL STRUCT: do not --- */
    struct Bad<'a> { data: Vec<u8>, slice: &'a [u8] }
/* If `slice` points into `data`, moving the struct
   invalidates it. Rust makes this hard on purpose. Use
   INDICES instead:                                        */
    struct Good { data: Vec<u8>, range: Range<usize> }
/* which is the arena/handle pattern again.

/* --- 6. WHEN YOU GENUINELY NEED SHARED MUTATION --- */
    RefCell<T>      runtime-checked borrows, single-threaded
    Cell<T>         get/set of Copy values, no borrows at all
    Mutex<T>        across threads
    RwLock<T>       many readers or one writer, across
                    threads
/* All four are "interior mutability" - mutation through &T,
   with the aliasing rule enforced at RUN TIME instead of
   compile time (chapter 10).                             */

Reborrowing

Reborrowing is a mechanism you use constantly without noticing, and understanding it explains several errors that otherwise look arbitrary.

/* A `&mut` can be temporarily lent out. The compiler does
   this implicitly, and knowing it explains several
   otherwise-confusing errors.                            */

    fn f(v: &mut Vec<i32>) {
        g(v);                   // implicitly REBORROWS:
                                // g(&mut *v)
        v.push(1);              // v is usable again after g
                                // returns
    }
    fn g(v: &mut Vec<i32>) { }

/* WITHOUT reborrowing this would MOVE the &mut into g and v
   would be unusable afterwards - which is what happens when
   the type is not obviously a reference:               */

    fn h<T>(x: T) { }
    fn f(v: &mut Vec<i32>) {
        h(v);                   // MOVES - T is inferred as
                                // &mut Vec, no reborrow
        v.push(1);              // ERROR
    }
    // fix: h(&mut *v);         // explicit reborrow

/* AND IN A LOOP, the classic: */
    let mut current = &mut head;
    loop {
        current = &mut current.next;     // moves out of
                                         // current
    }
/* Linked-list traversal with &mut is genuinely awkward, and
   is one of the shapes where an index-based arena is simply
   better in Rust.                                        */

The optimisation payoff

The borrow rules are not only about safety — they hand the optimiser a guarantee C cannot express, and the difference is visible in the generated code.

/* Rust's aliasing guarantee is stronger than C's, and LLVM
   uses it.                                                */

    // C: the compiler CANNOT assume a and b are distinct
    void add(int *a, const int *b, int n) {
            for (int i = 0; i < n; i++)
                    a[i] += b[i];   // must reload b[i] in
                                    // case a[i] aliased it
    }
    // which is why `restrict` exists (compilers chapter 07).

    // Rust: &mut is UNIQUE by construction
    fn add(a: &mut [i32], b: &[i32]) {
        for i in 0..a.len().min(b.len()) {
            a[i] += b[i];
        }
    }
/* rustc emits `noalias` on the &mut parameter, so LLVM knows
   they are disjoint and vectorises without a runtime alias
   check - the same code C gets only with `restrict`, and
   without the risk of the promise being false.

/* CHECK IT: */
    cargo asm --rust my_crate::add
    # or paste into godbolt with the Rust compiler selected

/* THE BOUNDS CHECK QUESTION, which everyone asks:
     a[i] IS bounds-checked. But:
       · the check is a compare and a branch, predicted
         perfectly
       · LLVM removes it whenever it can prove the index is in
         range - which iterators always can
       · so idiomatic Rust (iterators, chapter 08) usually has
         NO bounds checks at all:                          */
    for (x, y) in a.iter_mut().zip(b.iter()) { *x += *y; }
/* -> no bounds checks, vectorised, identical to the C with
   restrict.

   THE RULE: write iterator chains, not index loops, and the
   bounds-check cost disappears along with the aliasing
   question.                                              */

ErrorMeaning and fix
"cannot borrow as mutable because it is also borrowed as immutable"A shared borrow is still live — shorten it, or restructure
"cannot borrow as mutable more than once"Two &mut — split the data, or use split_at_mut
"cannot borrow as mutable, not declared as mutable"Missing mut on the let
"cannot assign to `*x` which is behind a `&` reference"You have a shared reference; you need &mut
"cannot move out of borrowed content"Clone, or take ownership instead of borrowing
