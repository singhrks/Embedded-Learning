Undefined, unspecified and implementation-defined behaviour

Three categories that sound similar and differ enormously. One is a portability note, one is a harmless choice, and one means the standard imposes no requirements at all — and modern optimisers act on that fact in ways that delete your safety checks.

The three categories

CategoryMeaningMust be documented?Example
Implementation-definedThe implementation chooses, and must document its choice. Behaviour is consistent.YesSize of int; whether plain char is signed; right shift of a negative value
UnspecifiedThe implementation chooses from several valid options, and need not document or be consistent.NoOrder of evaluation of function arguments; padding byte contents
UndefinedThe standard imposes no requirements whatsoever. Anything may happen, including nothing, including time travel.NoSigned overflow, null dereference, out-of-bounds access, data race
Why UB is not "whatever the hardware does"

The common intuition — "signed overflow wraps, because the CPU wraps" — is wrong, and dangerously so. The compiler does not translate your code to instructions; it reasons about your code assuming undefined behaviour never occurs, and uses that assumption to justify transformations. If UB does occur, the assumptions were false, and the conclusions drawn from them can be arbitrary.

Crucially, the effects are not local. UB can cause code before the offending statement to misbehave, because the optimiser propagates the assumption backwards.

Optimisations that delete your code

This is the part people find hardest to accept: the compiler may assume undefined behaviour never happens, and therefore delete the check you wrote to prevent it. The examples below are real, not hypothetical.

/* 1. The overflow check that vanishes */
bool check(int a, int b) { return a + b < a; }
/* Signed overflow is UB, so the compiler assumes a + b never
   overflows. If it never overflows, a + b < a is equivalent to
   b < 0. And with -fstrict-overflow it may simplify further.
   GCC compiles the classic form `a + b < a` to `b < 0` — which
   is not the check you wrote.                                  */

/* 2. The null check that vanishes  (Linux CVE-2009-1897) */
struct tun *tun = ptr;
struct sock *sk = tun->sk;          /* dereference implies non-NULL */
if (!tun)                            /* ...so this is dead code     */
        return -EINVAL;              /* DELETED by the optimiser    */
/* Result: a null dereference that the author had explicitly
   guarded against. Order matters: check FIRST, then dereference. */

/* 3. The infinite loop that vanishes */
while (1) { }
/* A loop with no side effects and no exit is UB in C11 (6.8.5p6).
   The compiler may assume it terminates and delete it, letting
   control fall through to whatever follows.                     */

/* 4. The bounds check that vanishes */
int f(int *p, int i)
{
        int x = p[i];                /* implies i is in bounds...  */
        if (i < 0 || i >= 10)        /* ...so this is redundant    */
                return -1;
        return x;
}

/* 5. Unreachable code becomes reachable */
int f(int x)
{
        if (x > 0) return 1;
        if (x < 0) return -1;
        if (x == 0) return 0;
        /* no return here — falling off the end of a non-void
           function is UB, so the compiler may emit anything,
           including running into the NEXT function.            */
}

Strict aliasing

The rule

An object may only be accessed through an lvalue of a compatible type, a signed/unsigned variant of it, a qualified version, an aggregate containing it, or any character type. Accessing an object through an incompatible pointer type is undefined.

The rule exists so the compiler can assume that a float * and an int * never refer to the same storage — which allows it to keep values in registers across stores. Without it, every store through any pointer would invalidate every cached load.

/* The classic violation — "type punning" through a pointer cast */
float f = 1.0f;
uint32_t bits = *(uint32_t *)&f;      /* UNDEFINED */

/* At -O2 this may read a stale register, or reorder relative to the
   store to f, and it genuinely misbehaves on real compilers.     */

/* CORRECT 1: memcpy. Compiles to zero instructions at -O2 — the
   compiler recognises the idiom.                                */
uint32_t bits;
memcpy(&bits, &f, sizeof bits);

/* CORRECT 2: a union. Legal in C (since C99 TC3), NOT in C++. */
union { float f; uint32_t u; } cvt = { .f = 1.0f };
uint32_t bits = cvt.u;

/* CORRECT 3: character types may alias anything — this is how
   serialisation code is allowed to work at all.               */
unsigned char *bytes = (unsigned char *)&f;
for (size_t i = 0; i < sizeof f; i++) put(bytes[i]);

/* An escape hatch, if you have inherited code you cannot fix: */
gcc -fno-strict-aliasing      /* the Linux kernel builds with this */

/* But note it costs real performance, and it is a workaround, not
   a fix. New code should be alias-correct.                      */

Alignment travels with aliasing

/* This is a second, independent bug in the same line of code */
uint8_t buf[100];
uint32_t v = *(uint32_t *)(buf + 1);    /* misaligned AND aliasing */

/* On ARM with strict alignment this faults; on x86 it is merely
   slow; and either way the compiler may assume 4-byte alignment
   and emit an instruction that requires it.                    */

/* Correct: */
uint32_t v;
memcpy(&v, buf + 1, sizeof v);          /* alignment-safe, alias-safe,
                                           and compiles to one unaligned
                                           load where the target allows */

Finding UB

Undefined behaviour by definition produces no required diagnostic, so finding it means using tools that deliberately look. These are the ones that work, and they find different things.

# UndefinedBehaviorSanitizer — the single most valuable tool here.
# Reports the exact file, line and values at the moment it happens.
gcc -fsanitize=undefined -fno-sanitize-recover=all -g prog.c

# individual checks, if you want them separately
-fsanitize=signed-integer-overflow
-fsanitize=shift
-fsanitize=bounds
-fsanitize=alignment
-fsanitize=null
-fsanitize=object-size
-fsanitize=bool,enum
-fsanitize=float-cast-overflow

# combine with ASan for memory UB
gcc -fsanitize=address,undefined -g prog.c

# compile-time help
gcc -Wall -Wextra -Wstrict-aliasing=3 -Wcast-align \
    -Wstrict-overflow=5 -Wsequence-point -Wreturn-type \
    -Wuninitialized -Wnull-dereference -fanalyzer

# make some UB defined, where you must
-fwrapv               # signed overflow wraps (kills the optimisation
                      # AND the check-deletion behaviour)
-fno-strict-aliasing  # disable the aliasing assumption
-fno-delete-null-pointer-checks
# The Linux kernel uses all three. They are a pragmatic choice for
# a huge legacy codebase — not a licence to write UB in new code.
Run your entire test suite under UBSan and ASan

This is the highest-value habit in this chapter. UB is invisible until the day an optimiser or a compiler upgrade exposes it, and by then it is a production incident. Sanitizers cost a few times the runtime in CI and find these bugs the day they are written. Both are in GCC and Clang; there is no reason not to.

Unspecified behaviour worth knowing

Three terms are used almost interchangeably in conversation and mean genuinely different things in the standard. The distinction matters because only one of them permits the compiler to do literally anything.

/* Legal, but the choice is not documented and may vary. */

f(g(), h());              /* order of g and h: unspecified        */
a[i++] = i;               /* actually UNDEFINED — unsequenced      */
p1 < p2                   /* comparing pointers into different
                             objects: unspecified                  */
padding bytes             /* contents are unspecified — which is
                             why memcmp on structs is wrong
                             (chapter 07)                          */
malloc(0)                 /* may return NULL or a unique pointer   */

/* Do not write code that depends on any of these, but note that
   unlike UB, they cannot make unrelated code misbehave.        */

Implementation-defined behaviour is not undefined: the compiler must pick a behaviour and document it. These are the ones you will actually encounter, and knowing your platform's choices is part of writing portable code deliberately.

How to think about it

Undefined behaviour is often presented as compiler writers being hostile. It is more usefully understood as a bargain — and knowing what the language bought with it explains why it will not be removed.

The bargain C makes:

  The standard leaves things undefined so implementations can be
  FAST on wildly different hardware — one's-complement machines,
  word-addressed machines, machines that trap on overflow. The
  optimiser gets to assume the programmer stayed inside the lines.

  The programmer's side of the bargain is to STAY INSIDE THE LINES.

  What makes this hard in practice:
    · UB is silent — no warning by default
    · effects are non-local and can appear far from the cause
    · behaviour can change with optimisation level, compiler
      version, inlining decisions, or unrelated edits
    · "it worked before" is evidence of nothing

  The practical response is not to memorise the standard. It is:
    1. enable the sanitizers, in CI, on every test
    2. enable the warnings, and treat them as errors
    3. learn the ~15 UB cases in the table above by heart
    4. when something behaves differently at -O2 than at -O0,
       suspect UB FIRST, not a compiler bug
