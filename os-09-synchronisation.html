Synchronisation primitives

Shared mutable state plus concurrency equals corruption, unless something enforces order. This chapter covers the primitives, what each one is actually for, and — the part that matters most in kernel work — which are legal in which execution context.

The problem, precisely

Start with the failure itself. A pair of operations that look atomic in source code are not, and seeing exactly where another thread can interleave is what makes every mechanism that follows obviously necessary.

/* A shared counter, incremented by two threads. */
counter++;

/* which is really three operations (C chapter 01, CA chapter 09) */
        ldr  w1, [x0]        /* LOAD  */
        add  w1, w1, #1      /* MODIFY */
        str  w1, [x0]        /* STORE */

/* Interleaved:
     T1: load  → 5
     T2: load  → 5
     T1: add   → 6
     T2: add   → 6
     T1: store → 6
     T2: store → 6          one increment LOST                 */
Three properties you may need, and they are separate
  • Atomicity — the operation completes indivisibly. Nothing observes a half-done state.
  • Mutual exclusion — at most one thread in a region at a time.
  • Ordering — other threads observe operations in the intended order (CA ch. 15).

Atomics give atomicity and, with the right memory order, ordering. Locks give all three. Neither is a substitute for the other, and the classic mistake is assuming that "atomic" implies "correct".

Atomic operations

The hardware provides operations that cannot be interrupted partway through. Everything else in this chapter is built on them, and for simple cases they are sufficient on their own.

#include <stdatomic.h>

atomic_int counter = 0;
atomic_fetch_add(&counter, 1);              /* indivisible */

/* the primitive everything else is built from */
int expected = old;
if (atomic_compare_exchange_strong(&v, &expected, desired)) {
        /* v was `old`, now it is `desired` */
} else {
        /* v was not `old`; expected now holds the actual value */
}

/* the CAS loop — the shape of every lock-free algorithm */
int old, new;
do {
        old = atomic_load(&v);
        new = f(old);                       /* any computation */
} while (!atomic_compare_exchange_weak(&v, &old, new));
/* _weak may fail spuriously but is cheaper in a loop; _strong
   does not, and is right when there is no loop.              */

/* Check what is actually lock-free on your target: */
atomic_is_lock_free(&obj);
ATOMIC_INT_LOCK_FREE            /* 2 = always, 1 = sometimes, 0 = never */
/* A "lock-free" atomic on a large struct may be implemented with a
   hidden mutex — which is a correctness surprise in a signal
   handler or an interrupt context.                            */

Mutexes

The default answer for protecting shared data: one holder at a time, with everyone else waiting. Its cost is not the lock itself but what happens when the lock is contended.

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

pthread_mutex_lock(&m);
        /* critical section */
pthread_mutex_unlock(&m);

/* Properties that matter:
     · OWNERSHIP — only the locker may unlock. This is what allows
       priority inheritance and deadlock detection.
     · SLEEPS on contention (via futex — OS chapter 08)
     · uncontended cost ~20 ns; contended cost ~1-5 µs        */

/* Types */
PTHREAD_MUTEX_NORMAL        /* self-deadlock on recursive lock   */
PTHREAD_MUTEX_ERRORCHECK    /* returns EDEADLK instead — use in
                               debug builds                      */
PTHREAD_MUTEX_RECURSIVE     /* same thread may relock. Usually a
                               design smell: it hides unclear
                               ownership of the invariant.       */
PTHREAD_MUTEX_ADAPTIVE_NP   /* spin briefly, then sleep          */
/* Always release on every path. In C, the goto ladder or the
   cleanup attribute (C chapters 11 and 14):                   */
static inline void unlock_p(pthread_mutex_t **m) { pthread_mutex_unlock(*m); }
#define LOCKED(mp) \
        pthread_mutex_t *_l __attribute__((cleanup(unlock_p))) = (mp); \
        pthread_mutex_lock(_l)

void f(void)
{
        LOCKED(&m);
        if (error) return;          /* unlocked automatically */
        ...
}                                   /* unlocked automatically */

/* Linux kernel 6.5+ has the same idea, type-safe: */
guard(mutex)(&lock);
scoped_guard(spinlock_irqsave, &lock) { ... }

Reader-writer locks

When reads vastly outnumber writes, forcing readers to exclude each other wastes parallelism. This variant lets them proceed together — and is a worse answer more often than people expect.

pthread_rwlock_t rw = PTHREAD_RWLOCK_INITIALIZER;

pthread_rwlock_rdlock(&rw);     /* many readers concurrently */
pthread_rwlock_unlock(&rw);

pthread_rwlock_wrlock(&rw);     /* exclusive */
pthread_rwlock_unlock(&rw);
Reader-writer locks are usually slower than you expect

They are only a win when reads are both frequent and long. For short critical sections the extra bookkeeping — and the cache-line contention on the shared reader count, which every reader must write — often costs more than a plain mutex. They also introduce a writer-starvation policy question that the implementation answers for you, usually badly.

Measure before choosing one. If reads dominate and are short, RCU or a seqlock is almost always the better answer.

Condition variables

Waiting for a condition rather than for a lock requires a mechanism that atomically releases the lock and sleeps. The canonical usage has a loop in it, and the loop is not optional.

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cv = PTHREAD_COND_INITIALIZER;
bool ready = false;

/* WAITER — note the loop, which is not optional */
pthread_mutex_lock(&m);
while (!ready)                          /* while, NEVER if */
        pthread_cond_wait(&cv, &m);     /* atomically unlocks m,
                                           sleeps, relocks on wake */
consume();
pthread_mutex_unlock(&m);

/* SIGNALLER */
pthread_mutex_lock(&m);
ready = true;
pthread_mutex_unlock(&m);
pthread_cond_signal(&cv);               /* or _broadcast for all */
Always while, never if

Three independent reasons the predicate can be false after a wake-up:

  1. Spurious wake-ups are explicitly permitted by POSIX and do occur.
  2. Another waiter got there first and consumed the item — with broadcast, all waiters wake but only one can proceed.
  3. The condition changed again between the signal and your reacquiring the mutex.

Using if produces a bug that appears under load, months later, and is nearly impossible to reproduce.

/* The three rules for condition variables:
     1. always associated with a mutex, and the predicate is
        protected by that mutex
     2. wait in a while loop on the predicate
     3. hold the mutex when changing the predicate

   Signal inside or outside the lock? Either is correct.
   Inside is simpler to reason about; outside avoids the waiter
   waking and immediately blocking on the mutex you still hold.
   Modern implementations optimise both cases.                */

Semaphores

A counter with waiting built in, which makes it the natural fit for a pool of limited resources rather than for mutual exclusion — despite being usable for both.

#include <semaphore.h>
sem_t s;
sem_init(&s, 0, 3);             /* 0 = threads only, 3 permits */

sem_wait(&s);                   /* take a permit, or block */
        /* at most 3 threads here */
sem_post(&s);                   /* return a permit */

/* Unlike a mutex, a semaphore has NO OWNER: any thread may post.
   That makes it the right tool for:
     · limiting concurrency to N (a resource pool)
     · signalling between threads (post from one, wait in another)
     · counting available items in a producer/consumer queue

   And the wrong tool for mutual exclusion — a mutex's ownership
   is what enables priority inheritance and error checking.    */

/* sem_post IS async-signal-safe, which makes semaphores the one
   correct way to wake a thread from a signal handler.        */

Kernel context: the rule that dominates

Can this code sleep?

Everything about kernel synchronisation follows from this one question. If you are in a context that cannot sleep — an interrupt handler, holding a spinlock, or above DISPATCH_LEVEL on Windows — then any primitive that might block is a bug. It will deadlock, or trigger "scheduling while atomic".

   Does this code need to sleep while holding the lock?
   (kmalloc(GFP_KERNEL), copy_to_user, I/O, another mutex)
        │
        ├── YES ──► MUTEX  (Linux)  /  FAST_MUTEX, ERESOURCE (Windows)
        │           process context only; never in an ISR
        │
        └── NO ───► is the data ALSO touched by an interrupt handler?
                       │
                       ├── NO ──► spin_lock()
                       │
                       └── YES ─► spin_lock_irqsave()
                                  disables interrupts on THIS core, so
                                  the handler cannot deadlock against you

   Special cases:
     read-mostly, rare writes    → RCU
     a simple counter or flag    → atomic_t, no lock at all
     waiting for an event        → wait_event() + wake_up()
     one-shot completion         → struct completion
     read-mostly, short reads    → seqlock
/* Linux */
spinlock_t lock;
unsigned long flags;

spin_lock_irqsave(&lock, flags);        /* save, disable, lock   */
        /* short, non-sleeping critical section ONLY */
spin_unlock_irqrestore(&lock, flags);   /* unlock, restore state */

/* Why save-and-restore rather than plain disable/enable: if
   interrupts were ALREADY disabled by an outer critical section,
   unconditionally re-enabling them at the inner unlock is a
   serious bug.                                                */

/* Windows equivalents */
KIRQL old;
KeAcquireSpinLock(&lock, &old);          /* raises to DISPATCH_LEVEL */
KeReleaseSpinLock(&lock, old);
KeAcquireSpinLockAtDpcLevel(&lock);      /* already at DISPATCH     */

RCU and seqlocks

For data read constantly and written rarely, even an uncontended lock is too expensive. This technique makes reads genuinely free by deferring cleanup until every possible reader has finished.

/* RCU: Read-Copy-Update. Readers pay ZERO synchronisation cost —
   no atomics, no cache-line contention, no barriers on most
   architectures. Writers do all the work.                     */

/* reader */
rcu_read_lock();                       /* just disables preemption */
struct foo *p = rcu_dereference(gp);
if (p) use(p->field);
rcu_read_unlock();

/* writer */
struct foo *new = kmalloc(...);
*new = *old;                            /* COPY */
new->field = value;                     /* UPDATE the copy */
rcu_assign_pointer(gp, new);            /* publish, with a release */
synchronize_rcu();                      /* wait until every pre-existing
                                           reader has finished       */
kfree(old);                             /* now provably safe */

/* The insight: instead of preventing readers from seeing a torn
   update, never modify in place. Readers see either the old
   object or the new one, both consistent. Reclamation is
   deferred until no reader can hold a reference.

   Ideal for: routing tables, module lists, configuration —
   anything read constantly and updated rarely.
   Bad for: frequent writes (each one allocates and waits).   */
/* Seqlock: readers retry if a write occurred during their read.
   Very cheap reads, but readers must be side-effect free.     */

/* reader */
unsigned seq;
do {
        seq = read_seqbegin(&sl);
        a = shared.x;  b = shared.y;    /* may read a torn pair */
} while (read_seqretry(&sl, seq));      /* ...and retry if so   */

/* writer */
write_seqlock(&sl);
shared.x = 1;  shared.y = 2;
write_sequnlock(&sl);

/* Used for timekeeping: readers vastly outnumber writers and must
   never block a writer. Note readers can starve under constant
   writing, and must not have side effects since they may run
   several times.                                              */

Rules that prevent most bugs

Most synchronisation bugs violate one of a short list of rules. Following them mechanically prevents far more problems than reasoning carefully about each case.

RulePrevents
Document what each lock protects, next to its declarationAmbiguous ownership — the root of most locking bugs
Acquire multiple locks in one global order, alwaysDeadlock (ch. 10)
Keep critical sections shortContention, and latency spikes
Never call unknown code holding a lockLock-order inversion via a callback
Never sleep holding a spinlockDeadlock, "scheduling while atomic"
Never return from a function holding a lock it acquiredUnbalanced locking; use scope guards
Prefer no sharing, then immutable sharing, then locksThe whole problem class
One lock per data structure, not per functionLocks that protect nothing coherent

Finding synchronisation bugs

Race conditions do not reproduce on demand. These tools find them by instrumenting every memory access and checking the rules, rather than waiting for the failure to occur naturally.

# ThreadSanitizer — finds races that have not yet manifested.
# The highest-value tool in this chapter.
gcc -fsanitize=thread -g prog.c && ./prog

# lock order and race detection without rebuilding
valgrind --tool=helgrind ./prog
valgrind --tool=drd ./prog

# contention
perf lock record ./prog && perf lock report
mutrace ./prog

# a hang: get every thread's stack
gdb -p PID -batch -ex 'thread apply all bt'

# kernel
CONFIG_PROVE_LOCKING=y          # lockdep: proves lock ORDER correctness
                                # across the whole kernel, and reports a
                                # potential deadlock the FIRST time an
                                # inconsistent order is observed —
                                # before it ever deadlocks
CONFIG_DEBUG_ATOMIC_SLEEP=y     # catches sleeping in atomic context
CONFIG_KCSAN=y                  # data race detector
lockdep is the single best thing about kernel development

It builds a graph of every lock acquisition order observed at runtime and reports a cycle the first time one appears — even if the deadlock did not actually occur. A potential deadlock that would surface once a year in production becomes a splat in dmesg on your first test run. Always develop with it enabled.
