ESR: decoding any fault

One register tells you exactly why the last exception happened. Learn its layout and you can read any crash — a kernel oops, a bare-metal hang, a hypervisor trap — and know within seconds what went wrong and where to look next.

The register

When an exception is taken, one register describes precisely what happened. Learning to read it is the single highest-value diagnostic skill in this track — it converts a crash into a specific statement about the instruction that failed.

 31    26 25 24                                                    0
┌────────┬──┬─────────────────────────────────────────────────────┐
│   EC   │IL│                       ISS                            │
└────────┴──┴─────────────────────────────────────────────────────┘

   EC  [31:26]   Exception Class — WHAT KIND of exception
   IL  [25]      Instruction Length: 1 = 32-bit, 0 = 16-bit (T32)
   ISS [24:0]    Instruction Specific Syndrome — the details.
                 Its meaning depends entirely on EC.

  Read EC FIRST. It tells you how to interpret everything else.

  Companion registers:
     FAR_ELx    the faulting virtual address (aborts, watchpoints)
     HPFAR_EL2  the faulting IPA, for stage-2 faults (chapter 16)
     ELR_ELx    the faulting or returning instruction

The pairing rule

Notice 0x20/0x21 and 0x24/0x25. The lower value means the exception came from a lower exception level; the higher means it came from the same level. So EC = 0x24 in a Linux oops means userspace faulted; 0x25 means the kernel did. That single bit tells you immediately whether you are looking at a user bug or a kernel bug.

Data abort ISS

Data aborts are the most common exception you will have to diagnose, and their syndrome field is correspondingly rich: it tells you the access size, direction, and the exact stage and level of the translation that failed.

EC = 0x24 or 0x25. The ISS layout:

┌──┬─────┬──┬──┬────────┬──┬─────┬──┬──┬──┬──┬──┬──┬──┬────────┐
│ISV│SAS │SSE│SRT      │SF│AR│VNCR│  │ │EA│CM│S1PTW│WnR│ DFSC │

   DFSC  [5:0]   Fault Status Code — THE key field
   WnR   [6]     0 = read, 1 = write

   CM    [8]     the fault was on a cache maintenance instruction
   EA    [9]     external abort type

   SET   [12:11] synchronous error type
   AR    [14]    the access was acquire/release
   SF    [15]    64-bit register width

Fault status codes

0b0101LLExternal abort on a table walkThe page table memory itself is unreachable
0b011000Synchronous parity/ECC errorMemory corruption detected by hardware

The four-way triage
  • Translation fault — the address is simply not mapped. Null pointer, use-after-free, a missing ioremap, or a stale pointer.
  • Permission fault — it is mapped, just not for this operation. Writing to read-only, executing no-execute, EL0 touching an EL1 page, or PAN blocking a kernel access to user memory.
  • Access flag fault — the AF bit was clear. Normal in an OS that uses AF for page aging; a bug in hand-written table code.
  • External abort — translation succeeded and the transaction went out on the bus, and something out there refused it. This is a hardware or platform problem, not a page table one: an unclocked peripheral, a powered-down domain, a wrong address, or an access-control block denying you.

That one distinction — page tables versus the bus — sends you to completely different parts of the system, and it is why reading DFSC first saves hours.

A decoder worth keeping

Rather than looking fields up each time, this is a compact reference you can apply directly to a value from a real dump.

drop this into any bare-metal or kernel fault handler
static const char *dfsc_name(unsigned dfsc)
{
        switch (dfsc & 0x3C) {
        case 0x00: return "address size fault";
        case 0x04: return "TRANSLATION fault (not mapped)";
        case 0x08: return "access flag fault (AF clear)";
        case 0x0C: return "PERMISSION fault (mapped, wrong perms)";
        }
        switch (dfsc) {
        case 0x10: return "EXTERNAL ABORT (bus refused it)";
        case 0x18: return "parity/ECC error";
        case 0x21: return "ALIGNMENT fault";
        case 0x30: return "TLB conflict (break-before-make bug)";
        default:   return "unknown";
        }
}

void dump_fault(void)
{
        uint64_t esr, far, elr;
        asm volatile("mrs %0, esr_el1" : "=r"(esr));
        asm volatile("mrs %0, far_el1" : "=r"(far));
        asm volatile("mrs %0, elr_el1" : "=r"(elr));

        unsigned ec  = (esr >> 26) & 0x3F;
        unsigned iss =  esr & 0x1FFFFFF;

        printf("ESR=%016llx  EC=0x%02x  FAR=%016llx  ELR=%016llx\n",
               esr, ec, far, elr);

        switch (ec) {
        case 0x15:
                printf("  SVC #%u — a system call\n", iss & 0xFFFF);
                break;

        case 0x20: case 0x21:
                printf("  INSTRUCTION abort at %s EL: %s, level %u\n",
                       ec == 0x20 ? "lower" : "same",
                       dfsc_name(iss & 0x3F), (iss & 3));
                printf("  → fetching from %016llx failed\n", far);
                break;

        case 0x24: case 0x25: {
                unsigned dfsc = iss & 0x3F;
                printf("  DATA abort at %s EL on %s of %016llx\n",
                       ec == 0x24 ? "lower" : "same",
                       (iss & (1u << 6)) ? "WRITE" : "READ", far);
                printf("  %s, level %u\n", dfsc_name(dfsc), dfsc & 3);

                if (iss & (1u << 7))
                        printf("  S1PTW: the PAGE TABLE WALK itself faulted\n");
                if (iss & (1u << 10))
                        printf("  FnV: FAR is NOT valid\n");
                if (iss & (1u << 24))
                        printf("  size=%u bytes, dest reg x%u\n",
                               1u << ((iss >> 22) & 3), (iss >> 16) & 0x1F);
                break;
        }

        case 0x18:
                printf("  trapped MSR/MRS — a higher EL is watching\n");
                break;

        case 0x26:
                printf("  SP ALIGNMENT fault — SP was not 16-byte aligned\n");
                break;

        case 0x2F:
                printf("  SError — IMPRECISE. ELR is NOT the cause.\n");
                break;

        default:
                printf("  EC 0x%02x — look it up in the ARM ARM, D17.2.37\n", ec);
        }
}

Worked examples

Decoding a real value end to end is what makes the preceding tables stick. Work through these before trusting that you can do it under pressure.

/* ESR = 0x96000004, FAR = 0x0000000000000000 */
   EC   = 0x96000004 >> 26 = 0x25   data abort, SAME EL (kernel)
   ISS  = 0x000004
   DFSC = 0x04 = 0b000100          translation fault, level 0
   WnR  = 0                        a READ
   FAR  = 0                        address zero
   → A KERNEL NULL POINTER DEREFERENCE, on a read.
     Level 0 because nothing at all is mapped at address 0.

/* ESR = 0x9200004F, FAR = 0x0000ffff8a3c1000 */
   EC   = 0x24                     data abort, LOWER EL (user)
   DFSC = 0x0F = 0b001111          permission fault, level 3
   WnR  = 1                        a WRITE
   → Userspace wrote to a read-only page. A .rodata write, or a
     copy-on-write page that has not yet been copied (OS ch. 13).

/* ESR = 0x96000010, FAR = 0x0000000040001000 */
   EC   = 0x25                     kernel
   DFSC = 0x10                     EXTERNAL ABORT
   → Translation SUCCEEDED. The bus refused it. Check: is the
     peripheral clocked? Powered? Is an XPU denying access?
     This is NOT a page table problem.

/* ESR = 0x86000007, FAR = 0x0000000000401234 */
   EC   = 0x21                     INSTRUCTION abort, same EL
   DFSC = 0x07 = 0b000111          translation fault, level 3
   → Tried to FETCH from an unmapped page. A corrupted function
     pointer, or a jump into freed memory.

/* ESR = 0x56000000 */
   EC   = 0x15                     SVC from AArch64
   ISS  = 0                        svc #0
   → A normal system call. Not an error at all.

SError: the hard one

Most exceptions are precise — they name the instruction responsible. SErrors are not, which makes them the hardest class to diagnose and the one where the usual approach does not apply.

/* EC = 0x2F. The ISS layout is different again: */
   IDS  [24]     IMPLEMENTATION DEFINED syndrome
   AET  [12:10]  Asynchronous Error Type
                   0 = uncontainable
                   1 = unrecoverable
                   2 = restartable
                   3 = recoverable
                   6 = corrected
   EA   [9]      external abort
   DFSC [5:0]    0x00 = uncategorised, 0x11 = asynchronous SError

/* The problem: an SError is reported at an arbitrary later
   instruction. ELR points at whatever was executing when the
   error was finally taken — which has NOTHING to do with the
   transaction that failed.

   Typical causes:
     · a POSTED WRITE rejected by an access-control block long
       after the store retired (chapter 25, security ch. 20)
     · an ECC error discovered on a writeback
     · a device signalling an error asynchronously

   How to narrow it down:
     1. ESB (Error Synchronization Barrier) at known points
        confines an SError to a bounded region, so you can
        bisect where it originates:
              esb
        Place them around suspect code and see which region
        produces it.
     2. The RAS extension adds ERR<n>STATUS records describing
        exactly which node reported the error.
     3. Vendor-specific error registers in the interconnect —
        an XPU usually LATCHES the offending address and master
        ID even when the CPU cannot attribute it.

   Linux prints these when it can:
        dmesg | grep -i 'SError\|RAS\|EDAC'                */

Reading a Linux oops

A Linux oops prints this register, already partly decoded. Knowing which parts the kernel decoded for you, and which you must decode yourself, is what makes the dump fully readable.

Unable to handle kernel NULL pointer dereference at virtual address 0000000000000010
Mem abort info:
  ESR = 0x0000000096000006
  EC = 0x25: DABT (current EL), IL = 32 bits
  SET = 0, FnV = 0
  EA = 0, S1PTW = 0
  FSC = 0x06: level 2 translation fault
Data abort info:
  ISV = 0, ISS = 0x00000006
  CM = 0, WnR = 0

pstate: 60400009 (nZCv daif +PAN -UAO)
pc : my_read+0x48/0x120 [mydriver]
lr : vfs_read+0xb4/0x1f0
sp : ffff800009abc000
Call trace:
 my_read+0x48/0x120 [mydriver]
 vfs_read+0xb4/0x1f0
 ksys_read+0x74/0x110
 __arm64_sys_read+0x24/0x30
 el0_svc_common+0x88/0x1a0

/* Reading it in order:
     EC 0x25   → the KERNEL faulted, not userspace
     FSC 0x06  → translation fault at level 2
     WnR 0     → a READ
     FAR 0x10  → address 16 — a NULL pointer plus a 16-byte
                 field offset. So: a null struct pointer, and
                 the field is at offset 0x10.
     pstate +PAN → PAN was on, so this was NOT an attempt to
                 read user memory
     call trace → arrived via a read() syscall from `cat`

   Conclusion: my_read() dereferenced a null pointer and read the
   member at offset 16. Find it: */

scripts/faddr2line vmlinux my_read+0x48
pahole -C my_device mydriver.ko | grep -A2 'offset:.*16'

Stage-2 faults

Under virtualisation the same register reports faults from the second stage of translation, with slightly different meaning — a distinction worth keeping straight when debugging a guest.

/* Taken to EL2, with ESR_EL2. Two extra things to read: */

   HPFAR_EL2      the faulting IPA:  (HPFAR & ~0xF) << 8
   FAR_EL2        the guest VA, when available
   ESR_EL2.S1PTW  set → the GUEST'S PAGE TABLES are in an
                  unmapped IPA. The guest did nothing wrong; the
                  hypervisor has not mapped the memory holding
                  its tables.

/* And ISV/SAS/SRT are what make MMIO emulation possible without
   decoding the instruction (chapter 16):                    */

        if (esr & ESR_ISV) {
                int size = 1 << ((esr >> 22) & 3);
                int reg  = (esr >> 16) & 0x1F;
                bool wr  = esr & (1 << 6);
                emulate(ipa, reg, size, wr);
        } else {
                decode_instruction_slowly();    /* rare */
        }
