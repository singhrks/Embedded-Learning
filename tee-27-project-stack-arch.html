Project: the four-layer stack — architecture and seams

One request, four layers, three trust boundaries: an ordinary application asks for a signature, a kernel driver carries the request into the secure world, a trusted application performs it, and a driver inside the secure world drives the hardware that does the arithmetic. This chapter is the architecture and the contracts at each seam; the next three build every line of it.

The four layers, and why each exists

Each layer below exists because the one above it cannot be trusted with something. Reading the stack as a sequence of trust reductions — rather than as an arbitrary number of hops — is what makes the design decisions in the rest of the project obvious.

   LAYER 1   secsign-cli                    NORMAL WORLD
             an ordinary unprivileged program     EL0
                  │  ioctl(/dev/secsign, ...)
                  │  ── SEAM A: the UAPI ──
                  ▼
   LAYER 2   secsign.ko                     NORMAL WORLD
             a Linux misc-device driver           EL1
             · validates and bounds the request
             · owns the TEE session
             · is the ONLY thing that may talk to the TA
                  │  tee_client_invoke_func()
                  │  ── SEAM B: the TEE client ABI ──
                  │     (ioctl → driver → SMC → EL3 → S-EL1)
                  ▼
   LAYER 3   secsign TA                     SECURE WORLD
             a trusted application               S-EL0
             · holds the private key; it never leaves
             · re-validates EVERYTHING from layer 2
             · asks for a hash, then signs it
                  │  TEE_DigestDoFinal()
                  │  ── SEAM C: OP-TEE crypto dispatch ──
                  ▼
   LAYER 4   hwsha driver                   SECURE WORLD
             an OP-TEE core driver               S-EL1
             · MMIO to a hash accelerator that the
               NORMAL world cannot address at all

   WHAT EACH BOUNDARY BUYS:

     A  process isolation  — the app cannot touch the
                             device or the session directly
     B  world isolation    — the kernel cannot read the key
                             even though it makes the request
     C  privilege + MMIO   — S-EL0 cannot reach the
                             accelerator's registers; only
                             S-EL1 can
Why a kernel driver at all, when an application can open /dev/tee0 directly?

It is a fair question, and for many designs the answer is that you should not add one. A kernel driver earns its place here for three specific reasons. First, policy: the kernel can decide which processes may sign, using credentials the TA cannot see. Second, session ownership: the secure world has a small fixed number of contexts (chapter 5), and one kernel-held session serialising many callers is far more robust than every process opening its own. Third, in-kernel users: once the driver exists, other kernel subsystems — a disk-encryption layer, a firmware-update path — can use the same service without going out to user space and back. If none of those apply to your design, the application should talk to /dev/tee0 itself and you have one less layer to secure.

What the finished thing does

Deliberately one operation, so the plumbing is visible rather than buried. A realistic product would add key management and a richer interface; none of that changes the shape below.

   secsign-cli sign <file>

     1. reads the file into a buffer
     2. ioctl(SECSIGN_IOC_SIGN, { data, len, sig_out })
     3. gets back a 64-byte ECDSA P-256 signature
     4. writes it to <file>.sig

   secsign-cli pubkey

     returns the public key, so anybody can verify the
     signature WITHOUT the secure world being involved -
     which is the whole point of using a signature rather
     than a MAC.

   THE PROPERTY WE ARE BUILDING, stated precisely:

     The private key exists only inside the secure world.
     Neither the application, nor the kernel, nor an attacker
     with root, nor an attacker who has compromised the
     kernel entirely, can extract it. They can ask for
     signatures while they have that access; they cannot
     take the key with them.

   THAT DISTINCTION IS THE ENTIRE VALUE. A compromise becomes
   temporary rather than permanent.

The three seams, and the contract at each

Almost every bug in a stack like this lives at a boundary rather than inside a layer. Writing down what each seam guarantees — and what it explicitly does not — is what makes the validation code in later chapters look necessary rather than paranoid.

SeamMechanismTrust directionWhat the lower side must assume
A app ↔ kernelioctl on a misc deviceKernel does not trust the appPointers are user addresses; lengths are attacker-chosen; the buffer can change under you
B kernel ↔ TATEE client API → SMCTA does not trust the kernelShared memory is normal-world memory; it can change after you validate it
C TA ↔ core driverOP-TEE crypto dispatchBoth sides are secure; the driver still validatesLength and alignment, because a TA bug should not become an MMIO fault
Seam B is the one that matters, and it is the one people get wrong

It is tempting to think the kernel is "more trusted" than the application and therefore that the TA can relax. The opposite is true: the entire reason the secure world exists is that the kernel might be compromised. A TA that trusts its caller because the caller is the kernel has thrown away the property the whole design was built for. Every parameter arriving at layer 3 is attacker-controlled, exactly as chapter 20 insists — and the buffer lives in memory the normal world can still write while you are reading it, which is why layer 3 copies before it validates.

What this design does and does not defend against

Being precise here is what separates a security design from security theatre, and it is worth doing before any code exists rather than after.

AttackerOutcomeWhy
Unprivileged local processBlockedCannot open the device; file permissions and the kernel's policy check
RootCan request signatures; cannot extract the keyThe key never crosses seam B in either direction
Fully compromised kernelSame — signatures while resident, no key World isolation is enforced by hardware, not by the kernel
Attacker who can flash firmwareNot blocked by this designNeeds secure boot and anti-rollback (isolation ch. 14)
Physical attacker with fault injectionNot blockedOut of scope here; see isolation ch. 16
Attacker exploiting a bug in the TA itselfNot blockedWhich is why layer 3 is deliberately tiny and validates everything

/* NOTE THE TWO SHARED HEADERS. Each defines one seam, and
   each is included by exactly the two layers on either side
   of it. A single header shared by all four layers would
   couple the application to the TA's internals, which is
   precisely what the seams exist to prevent.              */

The order to build it in

Building all four layers before testing anything is the reliable way to spend a day not knowing which one is broken. This order gives you a working system at every step.

   1. THE TA ALONE, called by the standard OP-TEE test
      client. Proves the secure world works and your TA
      loads and is signed correctly.        (chapter 28)

   2. THE KERNEL DRIVER, invoking the TA, exercised with a
      throwaway ioctl from a shell. Proves seam B.
                                            (chapter 27)

   3. THE CLI, replacing the throwaway test. Proves seam A.
                                            (chapter 27)

   4. THE CORE DRIVER, replacing the software hash with the
      accelerator. Proves seam C — and note the layers above
      it should not change AT ALL, which is the test that
      your abstraction is right.            (chapter 29)

   5. THE ATTACK TESTS. Only now is there anything to
      attack.                               (chapter 29)

   AT EVERY STEP the thing you just built is exercised before
   the next is started. That is slower to read and very much
   faster to debug.
