SMMU / IOMMU concepts

The MMU protects memory from the CPU. The SMMU protects memory from everything else. This chapter explains why DMA breaks every guarantee the MMU gives you, how the SMMU restores them, and how to debug it when a device faults.

The problem: DMA bypasses the MMU

Recall from chapter 03 that the MMU sits between a CPU core and the interconnect. Every address the CPU emits is translated and permission-checked.

Now consider a network controller doing DMA. You give it a buffer address, it writes packets there directly, with no CPU involvement. Its transactions go straight onto the interconnect. The CPU's MMU is nowhere in that path.

What goes wrong without one

  • No isolation. A firmware bug in the NIC — or a malicious peripheral on a hot-pluggable bus like Thunderbolt/PCIe — can read your disk encryption keys out of kernel memory. This is the classic DMA attack.
  • No virtualisation. You cannot pass a physical device through to a VM. The guest would program the device with guest-physical addresses (IPAs), and the device would use them as real physical addresses, scribbling over the host or another guest.
  • No scatter-gather. Devices needing a large contiguous buffer force the OS to find contiguous physical memory, which fragments and eventually fails. With translation, physically scattered pages can look contiguous to the device.
  • 32-bit devices on 64-bit systems. A legacy device that can only address 4 GB cannot reach a buffer above that line, forcing slow "bounce buffer" copies.
One-sentence definition

An SMMU (Arm's name) / IOMMU (the generic name; Intel VT-d, AMD-Vi are others) is an MMU placed in front of non-CPU bus masters, giving each device its own address space and permission set.

StreamID: how the SMMU knows who is asking

The CPU's MMU serves one core and uses TTBR plus the ASID to pick a translation context. The SMMU serves many different devices through one block, so it needs the transaction to identify its origin. That identifier is the StreamID.

  • The StreamID is derived from interconnect sideband signals — for PCIe it is typically built from the Requester ID (bus:device:function); for on-chip masters the SoC integrator hard-wires it.
  • An optional SubstreamID (SSID, called PASID on PCIe) subdivides one device into multiple contexts — this is what lets a GPU give each user process its own address space.
  • StreamID assignment is a SoC integration decision, documented in the SoC TRM, and surfaced to software through the device tree (iommus = <&smmu 0x800>) or ACPI IORT tables.
Why this is the crux of SMMU debugging

The most common SMMU bring-up failure is a StreamID mismatch: the device tree says StreamID 0x800, the hardware actually emits 0x801, so the SMMU finds no valid stream table entry and aborts every transaction. The fault register will tell you the StreamID it saw — compare it against what you configured.

SMMUv3 data structures

SMMUv3 is entirely table-driven: software builds structures in memory and tells the SMMU where they are. There is no per-device register bank to program (unlike SMMUv2's "context banks").

The lookup, step by step

  1. A transaction arrives carrying StreamID, optional SubstreamID, address, access type and NS state.
  2. The SMMU indexes the Stream Table with the StreamID. (Large StreamID spaces use a two-level stream table so you do not have to allocate an entry for every possible ID.)
  3. The STE says what to do: abort everything, bypass translation entirely, apply stage 1, apply stage 2, or apply both. A missing or invalid STE means abort.
  4. If stage 1 is enabled, the STE points to a Context Descriptor table, indexed by SubstreamID. The CD holds TTB0, TCR, MAIR and the ASID — exactly the CPU's translation context.
  5. The SMMU walks the stage-1 tables to produce an IPA, then (if enabled) walks the stage-2 tables from S2TTB to produce a PA.
  6. Permissions are checked at both stages. The result is cached in the SMMU's own TLBs.
  7. On failure the SMMU writes an event record to the Event Queue and either aborts the transaction or stalls it, depending on configuration.

Programming interface

Key commands you will see in a driver: CMD_CFGI_STE (invalidate a cached stream table entry after you modify one), CMD_CFGI_CD, CMD_TLBI_NH_VA (invalidate a stage-1 TLB entry), CMD_TLBI_S2_IPA, and CMD_SYNC (wait for everything before it to complete — the SMMU's equivalent of DSB).

The invalidation rule

Anything you change in memory — an STE, a CD, a page table entry — is invisible to the SMMU until you issue the matching invalidate command and a CMD_SYNC. This mirrors the CPU's write → DSB → TLBI → DSB → ISB rule, and forgetting it produces exactly the same class of "works sometimes" bug.

Almost no driver author programs an SMMU directly. You use the DMA API, and the IOMMU layer sits underneath it transparently.

the correct DMA idiom in a Linux driver
/* ---- streaming mapping: a buffer used for one transfer ---- */
dma_addr_t dma;
void *buf = kmalloc(SZ_4K, GFP_KERNEL);

dma = dma_map_single(dev, buf, SZ_4K, DMA_TO_DEVICE);
if (dma_mapping_error(dev, dma))
        return -ENOMEM;

writel(lower_32_bits(dma), regs + DMA_ADDR_LO);
writel(upper_32_bits(dma), regs + DMA_ADDR_HI);
writel(SZ_4K,              regs + DMA_LEN);
writel(START,              regs + DMA_CTRL);
/* ... wait for the completion interrupt ... */
dma_unmap_single(dev, dma, SZ_4K, DMA_TO_DEVICE);

/* ---- coherent mapping: a long-lived descriptor ring ---- */
struct desc *ring = dma_alloc_coherent(dev, RING_BYTES, &ring_dma, GFP_KERNEL);
/* no cache maintenance needed on this one - the API guarantees coherency */
dma_free_coherent(dev, RING_BYTES, ring, ring_dma);

/* ---- tell the core what your device can address ---- */
dma_set_mask_and_coherent(dev, DMA_BIT_MASK(48));
Three rules that will save you weeks
  1. Never give a device a pointer from kmalloc directly. It is a virtual address. The device needs the dma_addr_t the API returned.
  2. Never DMA to or from stack memory, and never to memory from vmalloc. Stack buffers may not be cache-line aligned, so a cache invalidate can destroy neighbouring stack data; vmalloc memory is not physically contiguous.
  3. Respect ownership. Between dma_map and dma_unmap, the buffer belongs to the device. Touching it from the CPU without dma_sync_single_for_cpu() gives you stale or corrupted data on non-coherent systems.

Where the SMMU shows up in device tree

        compatible = "arm,smmu-v3";

                     <GIC_SPI 77 IRQ_TYPE_EDGE_RISING>;   /* cmdq-sync */

        #iommu-cells = <1>;                  /* one cell: the StreamID */
};

dma_engine@2c000000 {
        compatible = "vendor,dma-engine";
        reg = <0x0 0x2c000000 0x0 0x1000>;
        iommus = <&smmu 0x42>;               /* this device's StreamID is 0x42 */
        dma-coherent;                        /* it participates in coherency  */
};

Advanced features

SVA — Shared Virtual Addressing

Because the SMMU uses the same descriptor format as the CPU MMU, the OS can point a device's Context Descriptor at a user process's own page tables and give the device the same ASID. The device can then dereference exactly the pointers the application uses — no mapping, no copying, no dma_map. This is how modern GPU and accelerator programming models avoid buffer marshalling. It requires the device to support ATS and PRI, so it can request that swapped-out pages be brought in.

ATS — Address Translation Services

A PCIe device can ask the SMMU to translate an address ahead of time and cache the result in its own ATC (Address Translation Cache), then issue pre-translated transactions. This removes the SMMU from the fast path. The cost is a new correctness obligation: when the OS unmaps a page it must send an ATC invalidate to the device and wait for the response, otherwise the device keeps using a stale translation. This is also a security consideration — you are trusting the device to honour invalidations.

PRI — Page Request Interface

Lets a device take the equivalent of a page fault: instead of aborting on an unmapped address, it sends a page request, the OS pages memory in, and the device retries. Enables demand paging for devices, but needs the SMMU configured to stall rather than terminate faulting transactions.

Secure vs Non-secure streams

SMMUv3 has separate secure and non-secure programming interfaces and separate stream tables. Secure firmware owns the secure side, so a Non-secure OS cannot configure translations for a device operating in the secure world. See chapter 06.

Debugging SMMU faults

A typical Linux fault looks like this:

arm-smmu-v3 2b400000.iommu: event 0x10 received:
arm-smmu-v3 2b400000.iommu: 0x0000004200000010
arm-smmu-v3 2b400000.iommu: 0x0000000000000000
arm-smmu-v3 2b400000.iommu: 0x00000000fffff000
arm-smmu-v3 2b400000.iommu: 0x0000000000000000

Decode it: event type 0x10 is C_BAD_STREAMID, and the StreamID field reads 0x42. The device is emitting StreamID 0x42 and there is no valid stream table entry for it.

Bisecting an SMMU problem

Boot once with iommu.passthrough=1. If the problem disappears, it is a mapping or StreamID issue. If it persists, the bug is in the device programming itself and the SMMU was just the messenger. This one experiment splits the search space in half.
