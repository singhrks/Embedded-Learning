Linux kernel development

Everything you learned about ARM now has a user. This chapter covers how the Linux kernel is organised, how it boots on an ARM SoC, how memory and scheduling work, and the concurrency rules you must obey — because kernel code has no safety net.

How kernel code differs from everything else you have written

User spaceKernel space
A bugSegfault, one process diesOops or panic — the whole machine, possibly filesystem corruption
C libraryAll of libcNone. No printf, malloc, fopen. A separate, smaller API.
Floating pointFree to useEffectively forbidden — FP state is not saved on kernel entry
Stack8 MB, grows automatically16 KB, fixed. No recursion, no big local arrays.
Memory protectionBetween processesNone within the kernel — any pointer bug can corrupt anything
PreemptionAlways preemptibleDepends on context and configuration; some contexts must not sleep
Debugginggdb, printfprintk, ftrace, crash dumps, KGDB, JTAG
The single most important rule

Never sleep in atomic context. Interrupt handlers, code holding a spinlock, and code with preemption disabled must not call anything that can block. Violate this and you get a deadlock or the "scheduling while atomic" bug. Everything in the concurrency section flows from this rule.

How to find anything

Learn one tool well: cscope, ctags, or the web at elixir.bootlin.com, which cross-references every identifier in every kernel version. When you meet an unfamiliar function, look at its callers first — that tells you the context it runs in, which matters more than what it does.

Boot flow on an ARM64 SoC

initcalls — how drivers get started

The kernel does not call driver init functions explicitly. Each driver registers one via a macro, the linker collects them into ordered sections, and do_initcalls() runs them level by level:

early_initcall()        /* level 0 — before most subsystems      */
core_initcall()         /* 1 — core subsystems                   */
postcore_initcall()     /* 2                                     */
arch_initcall()         /* 3 — architecture-specific             */
subsys_initcall()       /* 4 — bus types, classes                */
fs_initcall()           /* 5                                     */
device_initcall()       /* 6 — most drivers. module_init() maps here */
late_initcall()         /* 7 — anything that needs everything else  */

Within a level, order follows link order — which follows the Makefile. Depending on that order is a bug; use proper dependencies (-EPROBE_DEFER, described in chapter 09) instead.

GFP flags — the part people get wrong

FlagMeaningAllowed in
GFP_KERNELNormal allocation; may sleep to reclaim memoryProcess context only
GFP_ATOMICWill not sleep; may fail; dips into emergency reservesInterrupt handlers, spinlock-held code

Using GFP_KERNEL in an interrupt handler

is one of the most common kernel bugs. It may work for months, until memory pressure makes the allocator actually try to sleep — then the machine deadlocks. Rule: if you cannot sleep, you must use GFP_ATOMIC, and you must handle allocation failure.

Talking to user space

/* NEVER dereference a user pointer directly. Always use these. */
copy_to_user(void __user *to, const void *from, unsigned long n);
copy_from_user(void *to, const void __user *from, unsigned long n);
get_user(x, ptr);     put_user(x, ptr);           /* single values */

/* They return the number of bytes NOT copied. Zero means success. */
if (copy_to_user(ubuf, kbuf, len))
        return -EFAULT;

These functions validate that the address really is in user space, and install a fixup so that a fault returns an error instead of oopsing. The __user annotation is checked by sparse (make C=1) — run it.

Processes, threads and scheduling

Linux has no separate thread concept in the kernel. Everything schedulable is a struct task_struct; threads are simply tasks that share an address space. current is a macro giving you the running task.

Task states

   TASK_RUNNING  <-- on a runqueue, running or ready to run
        |  ^
 sleep  |  |  wake_up()
        v  |
   TASK_INTERRUPTIBLE     sleeping; signals will wake it   (use this by default)
   TASK_UNINTERRUPTIBLE   sleeping; signals will NOT       (the "D state" in ps)
        |
        v
   TASK_STOPPED / TASK_TRACED / EXIT_ZOMBIE / EXIT_DEAD

Scheduling classes

ClassPolicyFor
DeadlineSCHED_DEADLINEHard real time: runtime, deadline and period specified explicitly. Highest priority.
Real timeSCHED_FIFO, SCHED_RRPriority 1–99. A FIFO task runs until it blocks or yields — it can starve everything below it.

PREEMPT_RT

The real-time patch set, now largely merged upstream, converts most spinlocks into sleeping mutexes and makes interrupt handlers into threads. This trades throughput for bounded latency and is the standard choice for industrial and audio systems. It changes what "atomic context" means, so RT-correct driver code is stricter than mainline-correct code.

Concurrency — the part that will bite you

The kernel is fully preemptive and runs on many cores. Your driver's functions can be entered simultaneously by different processes, and interrupted by an interrupt handler that touches the same data.

Sources of concurrency

  • Two user processes calling into your driver on two cores.
  • An interrupt arriving while your process-context code holds the data.
  • A timer or workqueue callback firing.
  • Kernel preemption suspending you mid-update.
  • A second CPU seeing your writes out of order (the ARM memory model — chapter 03).

Choosing a lock

  Do I need to sleep while holding it?  (kmalloc(GFP_KERNEL), copy_to_user,
                                         mutex, I/O, msleep...)
        |
        +-- YES --> use a MUTEX (or a semaphore, or an rwsem)
        |             mutex_lock(&d->lock) ... mutex_unlock(&d->lock)
        |             Process context only. Cannot be used in an interrupt.
        |
        +-- NO  --> is the data ALSO touched by an interrupt handler?
                      |
                      +-- NO  --> spin_lock(&d->lock)
                      |
                      +-- YES --> spin_lock_irqsave(&d->lock, flags)
                                  ... spin_unlock_irqrestore(&d->lock, flags)
                                  (disables interrupts on THIS core, so the
                                   handler cannot deadlock against you)

  Is it a simple counter or flag?   -> atomic_t / atomic64_t, no lock needed
  Read-mostly, rarely written?      -> RCU
  Just need to wait for an event?   -> wait_event_interruptible() + wake_up()
  Counting a resource?              -> semaphore, or completion for one-shot
the standard shape of a driver's locking
struct my_device {
        struct mutex      lock;      /* protects process-context state       */
        spinlock_t        irq_lock;  /* protects state shared with the ISR   */
        struct list_head  pending;
        atomic_t          open_count;
        wait_queue_head_t readq;
        bool              data_ready;
};

/* --- process context: may sleep, so a mutex is fine --- */
static ssize_t my_read(struct file *f, char __user *buf, size_t n, loff_t *off)
{
        struct my_device *d = f->private_data;
        int ret;

        if (mutex_lock_interruptible(&d->lock))
                return -ERESTARTSYS;          /* woken by a signal */

        while (!d->data_ready) {
                mutex_unlock(&d->lock);       /* never sleep holding the lock */
                if (f->f_flags & O_NONBLOCK)
                        return -EAGAIN;
                if (wait_event_interruptible(d->readq, d->data_ready))
                        return -ERESTARTSYS;
                if (mutex_lock_interruptible(&d->lock))
                        return -ERESTARTSYS;
        }

        ret = copy_to_user(buf, /* ... */ NULL, 0) ? -EFAULT : 0;
        mutex_unlock(&d->lock);
        return ret;
}

/* --- interrupt context: cannot sleep, must use a spinlock --- */
static irqreturn_t my_isr(int irq, void *dev_id)
{
        struct my_device *d = dev_id;
        unsigned long flags;

        spin_lock_irqsave(&d->irq_lock, flags);
        d->data_ready = true;
        spin_unlock_irqrestore(&d->irq_lock, flags);

        wake_up_interruptible(&d->readq);     /* safe from interrupt context */
        return IRQ_HANDLED;
}

Deferred work

Interrupt handlers must be short. Anything slow is deferred:

MechanismContextCan sleep?Use for
SoftirqAtomicNoNetworking, block I/O. Statically defined; you almost never add one.
TaskletAtomicNoLegacy; being removed. Use a workqueue or a threaded IRQ instead.
WorkqueueProcess (kernel thread)YesThe usual answer. schedule_work(), or your own alloc_workqueue().
Threaded IRQProcess (dedicated thread)YesBest for most drivers: a tiny hard handler acknowledges, the thread does the work.
 
/* threaded IRQ: the modern default */
ret = devm_request_threaded_irq(dev, irq,
                                my_hard_isr,   /* atomic: ack the device, return */
                                my_thread_fn,  /* process ctx: may sleep         */
                                IRQF_ONESHOT, "mydev", d);

static irqreturn_t my_hard_isr(int irq, void *p)
{
        struct my_device *d = p;
        u32 status = readl(d->regs + STATUS);
        if (!(status & IRQ_PENDING))
                return IRQ_NONE;            /* not ours — essential for shared IRQs */
        writel(status, d->regs + STATUS);   /* clear at the device */
        return IRQ_WAKE_THREAD;
}

Building and booting your own kernel

# get the source
git clone --depth=1 https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git
cd linux

export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-

# start from a known-good configuration
make defconfig                 # generic arm64
# or:  make your_board_defconfig
make menuconfig                # tweak; / searches for a symbol by name

# build (Image is the arm64 kernel binary; dtbs are the device trees)
make -j$(nproc) Image modules dtbs

# install modules into a staging rootfs
make INSTALL_MOD_PATH=/path/to/rootfs modules_install

# artefacts
#   arch/arm64/boot/Image
#   arch/arm64/boot/dts/vendor/board.dtb

Try it with no hardware at all

qemu-system-aarch64 \
  -M virt -cpu cortex-a57 -smp 2 -m 1024 \
  -kernel arch/arm64/boot/Image \
  -initrd rootfs.cpio.gz \
  -append "console=ttyAMA0 earlycon" \
  -nographic

# add  -s -S  to wait for a debugger, then:
aarch64-linux-gnu-gdb vmlinux -ex 'target remote :1234'
Debug options worth enabling while you learn

CONFIG_DEBUG_KERNEL, CONFIG_DEBUG_ATOMIC_SLEEP (catches sleeping in atomic context — turn this on), CONFIG_PROVE_LOCKING (lockdep: finds deadlocks before they happen), CONFIG_DEBUG_OBJECTS, CONFIG_KASAN (use-after-free and buffer overflow detection), CONFIG_DEBUG_INFO, CONFIG_FTRACE, CONFIG_DYNAMIC_DEBUG. They cost performance and are worth every cycle during development.

Kernel modules

#include <linux/module.h>
#include <linux/init.h>

static int __init my_init(void)
{
        pr_info("hello, kernel\n");
        return 0;                 /* non-zero aborts loading */
}

static void __exit my_exit(void)
{
        pr_info("goodbye\n");
}

module_init(my_init);
module_exit(my_exit);

MODULE_LICENSE("GPL");            /* not "GPL" -> tainted kernel, no GPL symbols */
MODULE_AUTHOR("You");
MODULE_DESCRIPTION("Example");
obj-m += hello.o
all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
sudo insmod hello.ko            # load
lsmod | grep hello              # list
modinfo hello.ko                # metadata
sudo rmmod hello                # unload
dmesg | tail                    # see the output
sudo modprobe hello             # load with dependency resolution (needs install)
There is no stable in-kernel ABI

A module built against 6.6 will not load on 6.7. This is deliberate: it forces drivers upstream, where they are maintained alongside the API. Out-of-tree drivers are a permanent maintenance cost — plan for it, or upstream your driver.

Everything you learned in chapter 04 applies directly: decode the ESR, note read vs write, then use the call trace to find which pointer was null.

Kernel coding style and culture

  • Tabs, 8 wide. 80 columns is a soft limit. Read Documentation/process/coding-style.rst.
  • Run scripts/checkpatch.pl --strict before you show anyone your code.
  • Return 0 for success and a negative errno for failure. Never invent your own error codes.
  • Use goto for unwinding on error paths — it is idiomatic here, not a code smell.
  • Prefer devm_* functions so cleanup happens automatically.
  • Never add a new user-space ABI without thinking hard: include/uapi/ is forever.
  • One logical change per patch. Commit messages explain why, not what.

Chapter checklist

  • You can explain three ways kernel code differs from user code and why each matters.
  • You can describe the boot flow from BL1 to /sbin/init.
  • You can choose between kmalloc, vmalloc, devm_kzalloc and dma_alloc_coherent and justify the choice.
  • You can pick the right lock given a description of who touches the data.
  • You can explain why GFP_KERNEL in an ISR is a bug.
  • You can build a kernel, boot it under QEMU, and load a module into it.
  • You can read an oops and name the faulting function and the access type.
