Windows kernel development

Windows solves the same problems as Linux with a different vocabulary and a much stronger emphasis on formal contracts. This chapter covers the NT architecture, IRQL — the concept with no Linux equivalent — objects, the I/O model, and how to set up a working kernel development environment.

IRQL — the central concept

Interrupt Request Level is a per-processor value that determines which interrupts can preempt the currently running code. Every kernel routine documents the IRQL it may be called at, and violating that is the most common cause of a bug check.

HIGH_LEVEL      31  ┐  machine checks, bug checks
POWER_LEVEL     30  │
IPI_LEVEL       29  │  inter-processor interrupts
CLOCK_LEVEL     28  │  the scheduler clock
PROFILE_LEVEL   27  │
                    │
DIRQL         3-26  │  DEVICE interrupt levels — your ISR runs here
                    │
DISPATCH_LEVEL   2  │  the scheduler itself runs here. DPCs run here.
                    │  *** CANNOT PAGE FAULT. CANNOT WAIT. ***
APC_LEVEL        1  │  asynchronous procedure calls
PASSIVE_LEVEL    0  ┘  normal thread execution. Everything is allowed.

Rule: code running at IRQL N can only be interrupted by something at IRQL > N.
      Raising IRQL is how you block interference; it is Windows' spinlock mechanism.
The rule that generates most BSODs

At DISPATCH_LEVEL and above:

  • You cannot touch pageable memory. A page fault requires the scheduler, and the scheduler runs at DISPATCH_LEVEL — it cannot preempt itself. Result: IRQL_NOT_LESS_OR_EQUAL (bug check 0xA) or PAGE_FAULT_IN_NONPAGED_AREA (0x50).
  • You cannot wait on any dispatcher object with a non-zero timeout. No KeWaitForSingleObject, no mutex. Result: DRIVER_IRQL_NOT_LESS_OR_EQUAL or a hang.
  • You cannot allocate from paged pool. Use NonPagedPoolNx.

This is the same rule as Linux's "never sleep in atomic context", made explicit and checkable. KeGetCurrentIrql() tells you where you are; PAGED_CODE() asserts you are at PASSIVE_LEVEL.

You are atWhenYou may
PASSIVE_LEVELMost dispatch routines, DriverEntry, work itemsEverything: wait, page, allocate from paged pool, call into other drivers
APC_LEVELInside some file-system paths, when APCs are disabledAlmost everything except waiting on certain objects
DISPATCH_LEVELDPCs, timer callbacks, holding a spin lockNon-paged memory only, no waiting, brief work only
DIRQLYour interrupt service routineVery little. Acknowledge the device, queue a DPC, return.

The object manager

Nearly everything in the NT kernel is an object with a type, a name, a security descriptor and a reference count: processes, threads, files, events, devices, registry keys.

// User mode gets a HANDLE, which is an index into a per-process handle table.
HANDLE h = CreateFile(L"\\\\.\\MyDevice", ...);

// Kernel mode can convert a handle to the object pointer, taking a reference.
PFILE_OBJECT fileObj;
status = ObReferenceObjectByHandle(h, FILE_READ_DATA, *IoFileObjectType,
                                   UserMode, (PVOID *)&fileObj, NULL);
// ... use it ...
ObDereferenceObject(fileObj);   // ALWAYS pair these

Named objects live in a hierarchical namespace you can browse with the WinObj tool:

\                          the object namespace root
├── Device\               device objects created by drivers
│   ├── HarddiskVolume1
│   └── MyDevice          <- what your driver creates
├── DosDevices\  (== \??\) symbolic links visible to Win32
│   ├── C:      -> \Device\HarddiskVolume2
│   └── MyDevice -> \Device\MyDevice     <- what CreateFile("\\\\.\\MyDevice") finds
├── Driver\               loaded drivers
├── BaseNamedObjects\     user-mode events, mutexes, sections
└── KernelObjects\

The I/O model and IRPs

Every I/O operation in Windows is an IRP — I/O Request Packet — a structure the I/O manager creates and passes down a stack of drivers.

Major function codes

CodeTriggered by
IRP_MJ_CREATECreateFile() — a handle is being opened
IRP_MJ_CLOSE / IRP_MJ_CLEANUPHandle closed / last handle for a file object closed
IRP_MJ_READ / IRP_MJ_WRITEReadFile() / WriteFile()
IRP_MJ_DEVICE_CONTROLDeviceIoControl() — the main custom interface
IRP_MJ_INTERNAL_DEVICE_CONTROLDriver-to-driver IOCTLs, not callable from user mode
IRP_MJ_PNPPlug and Play: start, stop, remove, query capabilities
IRP_MJ_POWERSystem or device power state transitions
IRP_MJ_SYSTEM_CONTROLWMI requests
WDF handles almost all of this for you

Everything above describes WDM, the original model. In modern development you use WDF (KMDF/UMDF), which manages IRPs, PnP and power internally and hands you callbacks. You still need the WDM model in your head to read documentation and to debug — but you should not write it by hand. Chapter 12 covers WDF.

Four characters identifying your driver. With Driver Verifier's pool tracking, or !poolused in WinDbg, you can see exactly how much memory your driver has outstanding and find leaks in minutes rather than days.

Accessing user buffers safely

Windows offers three buffering methods, chosen per device or per IOCTL. This is a genuine design choice you must make, unlike Linux where copy_to_user is the only answer.

MethodHowBest forTrade-off
Buffered (METHOD_BUFFERED)The I/O manager allocates a kernel buffer and copies in and outSmall transfers, IOCTLsSafe and simple; a copy in each direction
Direct (METHOD_IN_DIRECT/OUT_DIRECT)The user pages are probed and locked; you get an MDLLarge transfers, DMANo copy; you must map the MDL and handle failures
Neither (METHOD_NEITHER)You get the raw user pointerAlmost nothingDangerous. You must ProbeForRead/Write inside a __try/__except, in the caller's context. Avoid.
 
// METHOD_NEITHER done correctly — note how much work it is, and prefer not to
__try {
        ProbeForRead(userPtr, length, __alignof(UCHAR));
        RtlCopyMemory(kernelBuf, userPtr, length);
} __except (EXCEPTION_EXECUTE_HANDLER) {
        return GetExceptionCode();
}

MDLs

A Memory Descriptor List describes the physical pages backing a virtual buffer — the Windows equivalent of a scatter-gather list:

PMDL mdl = IoAllocateMdl(buffer, length, FALSE, FALSE, NULL);
MmProbeAndLockPages(mdl, KernelMode, IoReadAccess);   // pin the pages
PVOID sysAddr = MmGetSystemAddressForMdlSafe(mdl, NormalPagePriority);
// ... device DMA can now use the physical addresses in the MDL ...
MmUnlockPages(mdl);
IoFreeMdl(mdl);

Interrupts and DPCs

Windows splits interrupt handling into two mandatory halves, and the split is enforced by IRQL:

  device raises an interrupt
        |
        v
  ISR runs at DIRQL — very high
        - the ONLY things you should do here:
             read the status register, confirm it is your device,
             acknowledge/clear it, capture anything volatile,
             queue a DPC
        - return TRUE if it was yours, FALSE if not (shared lines)
        |
        v
  IRQL drops below DISPATCH_LEVEL
        |
        v
  DPC runs at DISPATCH_LEVEL
        - the real work: process the data, complete IRPs,
          start the next transfer
        - still cannot page or wait
        |
        v
  need to page, wait, or call something at PASSIVE_LEVEL?
        queue a WORK ITEM -> runs on a system worker thread at PASSIVE_LEVEL
Mapping to Linux

ISR → the hard IRQ handler. DPC → softirq/tasklet. Work item → workqueue. The concepts are identical; Windows simply makes the constraint explicit through IRQL instead of leaving it as a convention you must remember.

Processes, threads and scheduling

  • 32 priority levels. 0 is the zero-page thread; 1–15 are dynamic (normal); 16–31 are real time and never have their priority boosted or decayed.
  • Threads are the scheduling unit, as in Linux, but Windows also has explicit priority boosting: a thread that completes I/O or is woken from a wait receives a temporary boost so interactive work stays responsive.
  • Quantum is shorter on client SKUs and longer on servers — the same kernel, tuned by a registry setting.
  • System threads (PsCreateSystemThread) are the Windows equivalent of kernel threads. They run at PASSIVE_LEVEL and may wait.
// Sleeping (PASSIVE_LEVEL only)
LARGE_INTEGER delay;
delay.QuadPart = -10 * 1000 * 100;      // negative = relative, in 100 ns units
                                        // this is 100 ms
KeDelayExecutionThread(KernelMode, FALSE, &delay);

// Busy-wait, safe at any IRQL, but only for very short waits
KeStallExecutionProcessor(50);          // microseconds

Setting up a development environment

  1. Install Visual Studio 2022 with the "Desktop development with C++" workload.
  2. Install the Windows SDK, then the WDK (Windows Driver Kit) — in that order, and the versions must match. The WDK installer adds driver project templates to Visual Studio.
  3. Create a test VM. Never develop drivers on your working machine. Hyper-V, VMware or VirtualBox all work. Take a snapshot before every test — you will bug-check it constantly.
  4. Enable test signing on the VM so unsigned drivers load.
  5. Set up kernel debugging between the host and the VM.
on the TEST VM, in an elevated prompt
:: allow unsigned (test-signed) drivers
bcdedit /set testsigning on

:: enable kernel debugging over a network connection
bcdedit /debug on
bcdedit /dbgsettings net hostip:192.168.1.10 port:50000 key:1.2.3.4

:: ...or over a serial port / named pipe for a VM
bcdedit /dbgsettings serial debugport:1 baudrate:115200

:: useful while developing
bcdedit /set nointegritychecks on
bcdedit /set disable_integrity_checks on

shutdown /r /t 0
on the HOST
:: install WinDbg (the modern one)
winget install Microsoft.WinDbg

:: connect to the target using the key from dbgsettings
windbg -k net:port=50000,key=1.2.3.4

:: point it at Microsoft's symbols plus your own build output
.sympath srv*C:\symbols*https://msdl.microsoft.com/download/symbols;C:\myproject\x64\Debug
.reload /f
Test signing is a development-only setting

testsigning on shows a desktop watermark and weakens the machine's driver integrity guarantees. Only ever enable it on a disposable VM. Production drivers must be signed through the Microsoft Partner Center attestation or WHQL process — covered in chapter 12.

Driver Verifier — use it from day one

Verifier instruments your driver at runtime to catch the bugs that would otherwise appear randomly in the field. Turning it on is the single highest-value thing you can do while developing.

:: interactive configuration
verifier /standard /driver mydriver.sys

:: or specify checks explicitly
verifier /flags 0x209BB /driver mydriver.sys

:: check status, then turn it off
verifier /querysettings
verifier /reset

shutdown /r /t 0

Chapter checklist

  • You can explain IRQL and list three things you cannot do at DISPATCH_LEVEL.
  • You can describe an IRP's path down and back up a device stack.
  • You can choose between buffered, direct and neither buffering, with a reason.
  • You can map ISR/DPC/work item onto their Linux equivalents.
  • You have a test VM with test signing and a kernel debugger attached.
  • You can run !analyze -v on a crash dump and identify the faulting driver.
