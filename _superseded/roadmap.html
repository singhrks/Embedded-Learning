Learning roadmap: zero to expert

Embedded is a wide field and the classic mistake is to wander. This is a concrete order of study, with the honest time cost of each stage and a test you can apply to know when you have actually learned it.

The skill tree

Skills here are stacked: the ones lower down are load-bearing for everything above them. You can read out of order, but you cannot understand out of order.

Six phases

Phase 0 — Prerequisites (2–4 weeks, skip if you have them)

  • C, seriously. Pointers to pointers, function pointers, struct layout and padding, volatile, const placement, the preprocessor, linkage.
  • A Linux shell. You will live in one, even for Windows driver work (for git and cross-builds).
  • Build tooling. make, compiler flags, what a linker actually does, what an object file contains.
  • Number systems. Hex fluency. You should read 0x4001_0080 and think "offset 0x80 in the block at 0x40010000" without pausing.

Readiness test: write a program that packs and unpacks a bitfield struct by hand with shifts and masks, and explain why the compiler might reorder your two writes to a hardware register.

Phase 1 — Foundations and the ARM core (3–5 weeks)

Chapters 02 and 03. This is the biggest single jump in the whole course. Do not rush it.

  • Register file, program flow, load/store architecture.
  • The memory map: what "an address" means before and after the MMU is on.
  • The translation walk, drawn out by hand at least once.
  • Caches, cache coherency, and why volatile is not a memory barrier.

Readiness test: given a 48-bit VA and a set of table base registers, trace by hand which bits index which level of the page table, and say what happens on a miss.

Phase 2 — The exception model (2–3 weeks)

Chapter 04. Short chapter, huge payoff — this is the vocabulary that all system software shares.

Readiness test: describe, register by register, what the hardware does between a user process executing svc #0 and the kernel's C handler running.

Phase 3 — Isolation and security (3–4 weeks)

Chapters 05, 06, 07. This is the part most self-taught engineers never reach, and it is what separates a "driver writer" from a "platform engineer".

Readiness test: a device DMAs to an address and gets a fault. List five distinct layers that could have produced that fault, and name the register you would read in each case.

Phase 4 — Operating system internals + drivers (8–12 weeks)

Chapters 08–10 and/or 11–13. Pick a primary OS. Build the project. Break it deliberately and fix it.

Readiness test: your driver deadlocks under load. Explain the tools and the order in which you would use them, without touching a debugger first.

Phase 5 — Depth (ongoing, forever)

  • Read real driver source in drivers/ — pick a small subsystem and read it end to end.
  • Bring up a real board: U-Boot, device tree, defconfig, rootfs.
  • Contribute a patch. Even a one-line fix teaches you the review culture.
  • Read the errata documents for a SoC you use. This is where the real world lives.

Common traps

Trap 1 — collecting boards

Buying a Raspberry Pi, a BeagleBone and three dev kits is not learning. One board, used until you have broken and recovered it ten times, teaches more than five untouched ones.

Trap 2 — reading the ARM ARM cover to cover

It is a reference, not a textbook — over 10,000 pages. Use it to answer a question you already have. Learning is question-driven; the manual is the answer key.

Trap 3 — skipping the memory model

Barriers, cache maintenance and coherency feel like optional detail until the day you have a bug that only reproduces on a four-core build under load. That bug will cost you a week. The chapter costs a day.

Trap 4 — writing drivers without reading drivers

The kernel already contains a near-exact template for whatever you are writing. Professionals find it and adapt it. Search drivers/ before you start typing.

Self-assessment checkpoints

You are ready to call yourself intermediate when you can answer all of these without looking anything up:

  • Why does a load from a device register need volatile, and why is that still not enough?
  • What is the difference between an IPA and a PA, and who owns the mapping between them?
  • What actually changes in the CPU when an interrupt is taken at EL1?
  • Why can a device not simply use the same page tables as the CPU?
  • What does the NS bit do, and where is it physically checked?
  • In your OS of choice, what is the difference between the code that runs in an interrupt handler and the code that runs in a work item — and why does it matter?

You are approaching expert when you can look at an unfamiliar SoC's technical reference manual and, within an hour, identify its interconnect topology, its DMA masters, its isolation blocks and its boot flow.
