ARM architecture, in depth

This is the load-bearing chapter of the whole site. By the end you should be able to follow a single instruction from fetch, through address translation, through the cache hierarchy, out onto the interconnect — and explain what could go wrong at each step.

What ARM is, and what it is not

Arm Ltd does not make chips. It designs and licenses two things:

  • An architecture — a specification of what a processor must do: instructions, registers, memory model, exception behaviour. This is the ARM Architecture Reference Manual (the "ARM ARM"). It is a contract, not an implementation.
  • Micro-architectures — actual core designs implementing that contract (Cortex-A78, Cortex-M4, Neoverse N2). Apple, Qualcomm and others take an architecture licence and build their own.
Why this distinction matters

Architecture defines correctness: if you write architecturally correct code it works on every implementation. Micro-architecture defines performance: cache sizes, pipeline depth, prefetchers. When you are debugging, ask yourself which one you are fighting. Architectural bugs are portable; micro-architectural surprises (timing, cache line effects, errata) are chip-specific.

  • ARMv7-A — 32-bit only. Modes (User, FIQ, IRQ, Supervisor, Abort, Undefined, System, Monitor, Hyp), banked registers, CP15 coprocessor for system control.
  • ARMv8-A — introduced AArch64: 64-bit registers, a clean new instruction set (A64), 31 general-purpose registers, and the exception-level model (EL0–EL3) that replaced processor modes. AArch32 is retained as a compatibility execution state.
  • ARMv9-A — builds on v8: SVE2 vectors, Realm Management Extension (CCA — a fourth security state), Branch Target Identification and Memory Tagging as mainline features.

Everything below is AArch64 unless stated otherwise, because that is what modern application processors run.

Load/store architecture — the core principle

ARM is a RISC design. The single most important consequence:

The rule

Only LDR and STR family instructions touch memory. Every arithmetic and logic instruction operates only on registers. There is no ADD [addr], #1.

So counter++ on a global becomes three instructions, and that fact is the root of an entire class of concurrency bugs:

    adrp    x0, counter          // form page address of the symbol
    add     x0, x0, :lo12:counter // add the low 12 bits -> full address
    ldr     w1, [x0]             // LOAD  from memory into a register
    add     w1, w1, #1           // MODIFY in the register
    str     w1, [x0]             // STORE back to memory

Two cores executing that sequence at the same time can both read the same old value and both write back the same new value — one increment is lost. Fixing this needs the atomic instructions covered in the atomics section.

The procedure call standard (AAPCS64)

You need this to read stack traces and to write assembly that C can call.

  • Integer arguments 1–8 in X0–X7; further arguments on the stack.
  • Return value in X0 (and X1 for 128-bit); large structs via a hidden pointer in X8.
  • Floating point / vector arguments in V0–V7.
  • X19–X28 are callee-saved: if you use them, save and restore them.
  • The stack pointer must be 16-byte aligned at every public interface. Getting this wrong produces alignment faults that look like random corruption.
// A typical function prologue / epilogue
my_func:
    stp     x29, x30, [sp, #-32]!   // push FP and LR, pre-decrement SP by 32
    mov     x29, sp                 // establish the frame pointer
    stp     x19, x20, [sp, #16]     // save the callee-saved regs we will use
    ...
    ldp     x19, x20, [sp, #16]     // restore
    ldp     x29, x30, [sp], #32     // pop FP and LR, post-increment SP
    ret                             // branch to X30

How an instruction actually executes

A classic in-order pipeline; modern cores are wider and out-of-order but the stages are the same names.

  1. Fetch. The PC is a virtual address. It goes through the instruction TLB, hits the L1 instruction cache, and returns up to several instructions. In parallel, the branch predictor guesses where execution goes next so fetch never stalls.
  2. Decode. The fixed 32-bit encoding is split into operation, registers and immediates. An unrecognised encoding raises an Undefined Instruction exception.
  3. Issue / register read. Operands are read; on out-of-order cores registers are renamed and the instruction waits in a scheduler until its inputs are ready.
  4. Execute. The ALU, multiplier, FPU or vector unit does the work.
  5. Memory. Only for loads/stores. The virtual address goes to the data TLB; on a miss the hardware walks the page tables. Permission and memory-type checks happen here. Then the data cache is probed, and on a miss the request goes out to the interconnect.
  6. Writeback. The result is committed to the architectural register file. Only at this point is the instruction architecturally "done" — everything before it can still be squashed by a mispredicted branch or an exception.

Memory types: Normal vs Device

Before translation, understand that ARM tags every region with a memory type, and this tag changes what the hardware is allowed to do with accesses to it. Choosing the wrong one is one of the most common driver bugs.

Normal memoryDevice memory
Used forRAM, code, data, DMA buffersPeripheral registers (MMIO)
ReorderingAllowed freely by the CPUNot reordered relative to other Device accesses
Speculative accessAllowed — the CPU may read addresses you never asked forNever speculated
Merging / splitting writesAllowedDepends on sub-type (see below)
Unaligned accessAllowedAlways faults
CacheableYes (write-back, write-through, or non-cacheable)Never

Device memory has sub-types, written Device-nGnRnE etc., where each letter is a permission:

  • G / nG — Gathering: may separate accesses be merged into one bigger one?
  • R / nR — Reordering: may accesses to different addresses in this region be reordered?
  • E / nE — Early write acknowledgement: may a write be acknowledged before it reaches the endpoint?

Device-nGnRnE is the strictest — no gathering, no reordering, no early ack — and is what you use for control registers where every write must land in order. Device-GRE is the most relaxed and is used for things like framebuffers.

Classic bug

Mapping a peripheral as Normal Cacheable "because it was faster". The CPU then speculatively reads a FIFO register — draining data that no one asked for — and caches control registers so your writes never reach the device. Symptom: works in a debugger, fails at speed. Always map MMIO as Device.

The MMU and the translation walk

The MMU turns a virtual address into a physical address, while checking permissions and attaching memory attributes. It exists for four reasons: isolation between processes, giving each process the same layout, letting physically scattered pages look contiguous, and enforcing read/write/execute permissions.

The address space split

AArch64, 48-bit VA (bits [63:48] must be all 0s or all 1s)

  0xFFFF_FFFF_FFFF_FFFF  +---------------------------+
                         |  kernel space             |  TTBR1_EL1 translates these
                         |  (top of the range)       |
  0xFFFF_0000_0000_0000  +---------------------------+
                         |     non-canonical hole    |  faults if accessed
  0x0000_FFFF_FFFF_FFFF  +---------------------------+
                         |  user space               |  TTBR0_EL1 translates these
                         |  (bottom of the range)    |
  0x0000_0000_0000_0000  +---------------------------+

Two translation table base registers is an elegant trick: the kernel mapping lives in TTBR1_EL1 and never changes, while a context switch only has to swap TTBR0_EL1. The kernel stays mapped, so a syscall does not need a full table change.

Page table structure

Building a mapping by hand

a minimal identity-map setup, the kind that lives in bare-metal boot code
#define PTE_VALID       (1UL << 0)
#define PTE_TABLE       (1UL << 1)   /* at L0-L2: entry points to another table */
#define PTE_PAGE        (1UL << 1)   /* at L3:    entry is a 4 KB page          */
#define PTE_AF          (1UL << 10)  /* access flag - forget this and you fault  */
#define PTE_SH_INNER    (3UL << 8)
#define PTE_AP_RW_EL1   (0UL << 6)
#define PTE_UXN         (1UL << 54)
#define PTE_ATTR(i)     ((unsigned long)(i) << 2)

#define MAIR_IDX_NORMAL 0
#define MAIR_IDX_DEVICE 1

static uint64_t l1[512] __attribute__((aligned(4096)));
static uint64_t l2[512] __attribute__((aligned(4096)));

void mmu_init(void)
{
    /* MAIR: slot 0 = Normal write-back, slot 1 = Device-nGnRnE */
    uint64_t mair = (0xFFUL << (8 * MAIR_IDX_NORMAL)) |
                    (0x00UL << (8 * MAIR_IDX_DEVICE));
    asm volatile("msr mair_el1, %0" :: "r"(mair));

    /* L1[0] points at our L2 table (covers VA 0 - 1 GB) */
    l1[0] = (uint64_t)l2 | PTE_VALID | PTE_TABLE;

    /* L2: map 512 x 2 MB blocks, identity mapped */
    for (int i = 0; i < 512; i++) {
        uint64_t pa = (uint64_t)i << 21;               /* 2 MB blocks */
        int is_device = (pa >= 0x40000000UL);          /* peripherals up here */
        l2[i] = pa | PTE_VALID                         /* block: bit1 = 0 */
                   | PTE_AF | PTE_AP_RW_EL1
                   | (is_device ? PTE_ATTR(MAIR_IDX_DEVICE) | PTE_UXN
                                : PTE_ATTR(MAIR_IDX_NORMAL) | PTE_SH_INNER);
    }

    asm volatile("msr ttbr0_el1, %0" :: "r"((uint64_t)l1));

    /* TCR: 48-bit VA (T0SZ=16), 4 KB granule, inner-shareable walks */
    uint64_t tcr = (16UL << 0) | (1UL << 8) | (1UL << 10) | (3UL << 12);
    asm volatile("msr tcr_el1, %0" :: "r"(tcr));

    asm volatile("dsb ish; isb");                      /* tables visible first */

    uint64_t sctlr;
    asm volatile("mrs %0, sctlr_el1" : "=r"(sctlr));
    sctlr |= (1UL << 0) | (1UL << 2) | (1UL << 12);    /* M | C | I */
    asm volatile("msr sctlr_el1, %0" :: "r"(sctlr));
    asm volatile("isb");                               /* MMU is on from here */
}
Read that code twice

If you understand every line above — MAIR, the block descriptor, TCR's T0SZ, and why the dsb/isb pair is there — you understand the ARM MMU. Everything else is detail.

TLBs and ASIDs

The TLB caches completed translations. Because a full walk costs up to four memory accesses, a TLB miss is expensive and a TLB that must be flushed on every context switch is a disaster. Two mechanisms avoid that:

  • ASID (Address Space ID) — an 8- or 16-bit tag stored in TTBR0_EL1[63:48] and attached to every non-Global TLB entry. Two processes' entries can coexist in the TLB. A context switch changes the ASID rather than invalidating everything.
  • Global entries (nG=0) — kernel mappings match regardless of ASID.
  • VMID — the same idea one level up, tagging entries per virtual machine.

When you change a page table you must invalidate the stale TLB entry yourself. The hardware will not notice:

    dsb ishst              // make the table write visible to the walkers
    tlbi vae1is, x0        // invalidate VA in x0, EL1, Inner Shareable (all cores)
    dsb ish                // wait for the invalidate to complete everywhere
    isb                    // flush the pipeline so nothing stale is in flight
The number one MMU bug

Updating a descriptor and forgetting the TLBI, or getting the barrier order wrong. Symptom: the change works on one core and not another, or works after an unrelated context switch. The sequence above is write-table → DSB → TLBI → DSB → ISB, and it is not optional.

Two-stage translation

Under a hypervisor, translation happens twice:

  Guest VA  --[ stage 1, guest owns it ]-->  IPA  --[ stage 2, hypervisor owns it ]-->  PA
            TTBR0/1_EL1                            VTTBR_EL2

  IPA = Intermediate Physical Address = "what the guest believes is physical"

A stage-1 walk that itself needs stage-2 translation for each of its table accesses can therefore cost many more memory accesses. This is why hypervisors care so much about TLB behaviour, and it is exactly the structure the SMMU reuses — see chapter 05.

Caches and coherency

DRAM is roughly 100× slower than a register. Caches hide that, and understanding them is the difference between a driver that works and a driver that works sometimes.

   Core 0                  Core 1
  +--------+              +--------+

  +--------+--+-------+   +--------+--+-------+

  +-----------+           +-----------+
  |    L2     |           |    L2     |            ~256KB-1MB, ~15 cycles
  +-----------+           +-----------+
        |                       |
        +-----------+-----------+

             +-------------+
             | L3 / SLC    |                       shared, ~4-32 MB, ~40 cycles

             +-------------+
             |    DRAM     |                       ~100-200 cycles

Terms that matter

  • Cache line — the unit of transfer, almost always 64 bytes on ARM. You never fetch 4 bytes from DRAM; you fetch the whole line. This causes false sharing: two cores writing to different variables in the same line ping-pong that line between them and destroy performance.
  • Write-back — a store updates the cache and marks the line dirty; DRAM is updated later. Write-through — every store also goes to the next level. Write-back is the default.
  • PIPT / VIPT — how a cache is indexed and tagged. AArch64 data caches behave as Physically Indexed, Physically Tagged from software's point of view, which means you do not have to worry about virtual aliasing for data (instruction caches still need explicit maintenance).
  • Shareability domain — Inner Shareable is typically "all the cores in this cluster/system that are coherent"; Outer Shareable extends further. It determines how far a barrier or a TLBI propagates.

Hardware coherency

Between CPU cores, coherency is automatic: the interconnect implements a protocol (MESI/MOESI, carried over AMBA ACE or CHI) so that if core 0 writes a line, core 1's copy is invalidated before it can read stale data. You do not need cache maintenance between coherent cores.

But DMA may not be coherent

Whether a DMA master participates in coherency is a property of the SoC. If it does not:

  • Before a device reads your buffer you must clean (flush) the cache, or the device reads stale DRAM while your data sits dirty in L1.
  • Before you read a buffer the device wrote you must invalidate the cache, or you read a stale cached copy and never see the new data.

This is the single most common DMA bug in the field. In Linux the DMA API (dma_map_single(), dma_sync_single_for_cpu()) does this for you — which is exactly why you must never hand a device a raw kmalloc pointer.

Memory ordering and barriers

ARM has a weakly ordered memory model. Unless you say otherwise, the CPU may execute your loads and stores to Normal memory in any order that preserves single-threaded correctness, and other observers may see them in a different order than you wrote them.

The canonical failure:

// Producer (core 0)              // Consumer (core 1)
buffer[0] = 42;                   while (flag == 0)
flag      = 1;                        ;
                                  use(buffer[0]);   // may read garbage!

The producer's two stores can become visible in the opposite order. The consumer sees flag == 1 and reads a buffer that has not been written yet. This is not a compiler bug and not a race in the usual sense — it is the memory model working as specified.

BarrierGuaranteeUse when
DMB — Data Memory BarrierMemory accesses before it are observed before accesses after it. Does not stall non-memory work.Ordering two data accesses. The common case.
DSB — Data Synchronization BarrierStronger: execution stops until all prior memory accesses and cache/TLB maintenance have completed.After TLBI/DC, before starting DMA, before WFI.
ISB — Instruction Synchronization BarrierFlushes the pipeline; instructions after it are re-fetched. Makes system register changes take effect.After enabling the MMU, changing SCTLR, or modifying code.

Each takes a domain and direction suffix: ish (Inner Shareable), osh (Outer), sy (full system), optionally st (stores only) or ld (loads only). dmb ishst is the cheap "make my prior stores visible to the other cores" barrier.

// Fixed producer
buffer[0] = 42;
dmb ishst;            // all prior stores visible before the next one
flag = 1;

// Fixed consumer
while (flag == 0) ;
dmb ishld;            // do not let the load of buffer float above the flag load
use(buffer[0]);

The modern way: acquire/release

ARMv8 added ordered load/store instructions that are cheaper than a standalone barrier because the ordering is attached to the access itself:

  • LDAR — load-acquire: no later access may be reordered before it.
  • STLR — store-release: no earlier access may be reordered after it.

Together they give exactly the release/acquire pairing that C11 <stdatomic.h>, Linux's smp_store_release()/smp_load_acquire(), and Windows' InterlockedExchangeRelease compile down to. Prefer these over raw barriers in new code.

Atomic operations

Because ARM is load/store, atomicity needs dedicated instructions. Two generations exist:

Load-exclusive / store-exclusive (all of ARMv8)

// atomic increment of the 32-bit word at [x0]
1:  ldaxr   w1, [x0]        // load-acquire exclusive: marks the address as "monitored"
    add     w1, w1, #1
    stlxr   w2, w1, [x0]    // store-release exclusive: w2 = 0 on success, 1 on failure
    cbnz    w2, 1b          // another core touched it -> retry the whole sequence

The exclusive monitor in hardware watches the address. If any other master writes it between the LDXR and the STXR, the store fails and you loop. Keep the loop body tiny — a memory access or an exception inside it can clear the monitor and cause livelock.

Large System Extensions (ARMv8.1+)

Single-instruction atomics that the interconnect can execute near memory, scaling far better under contention:

    ldadd   w1, w2, [x0]      // atomic add,  returns the old value in w2
    ldeor   w1, w2, [x0]      // atomic XOR
    ldset   w1, w2, [x0]      // atomic OR (set bits)
    swp     w1, w2, [x0]      // atomic swap
    cas     w1, w2, [x0]      // compare-and-swap

Linux and Windows both patch between the two forms at boot depending on what the CPU reports in ID_AA64ISAR0_EL1.

Interrupts and the GIC

The Generic Interrupt Controller is a separate hardware block that collects interrupt signals from every peripheral, prioritises them, and delivers one to a specific core. Since GICv3 the CPU interface is accessed through system registers (ICC_*_EL1) rather than MMIO.

Interrupt delivery flow

  1. A peripheral asserts its interrupt line, or writes a doorbell register for an MSI.
  2. The distributor marks the INTID pending, checks it is enabled, and compares its priority against what the target core is currently running.
  3. If it wins, the GIC asserts the IRQ (or FIQ) signal to that core.
  4. The core takes the exception if PSTATE.I is clear — see chapter 04 for the exact hardware sequence.
  5. The handler reads ICC_IAR1_EL1 to acknowledge. This returns the INTID and moves the interrupt to active, so it will not be re-signalled.
  6. The handler services the device — crucially, it must clear the interrupt condition at the device, not just at the GIC, or a level-triggered interrupt fires again immediately.
  7. The handler writes the INTID to ICC_EOIR1_EL1 to signal End Of Interrupt, dropping the running priority and allowing lower-priority interrupts through.
  8. ERET returns to the interrupted code.
Interrupt storm

If you EOI without clearing the condition at the device, a level-triggered interrupt re-asserts immediately and the core does nothing but enter and exit the handler forever. The system appears hung with 100% CPU in the handler. Always clear at the source first, then EOI.

The interconnect: AMBA

AMBA is Arm's family of on-chip bus specifications. Which one a block uses tells you a lot about it.

What travels with an AXI transaction

This list is the key to chapters 05, 06 and 07 — these sideband signals are what the isolation hardware inspects:

  • AxADDR — the physical address.
  • AxID — the master's transaction ID, from which the SoC derives a master ID or StreamID identifying who is asking.
  • AxPROT[1] — the NS bit: is this a Secure or Non-secure access? This one bit is the entirety of TrustZone's bus-level enforcement.
  • AxPROT[0] — privileged or unprivileged. AxPROT[2] — instruction or data.
  • AxCACHE — cacheability and bufferability hints, derived from the page-table attributes.
  • AxLEN, AxSIZE, AxBURST — burst shape.
Tie it together

A page table entry's NS and AttrIndx fields are not abstractions. They are literally converted into wires on the bus — AxPROT[1] and AxCACHE — and hardware downstream makes decisions based on them. When you set a bit in a descriptor you are setting a signal on the interconnect.

Putting it all together: one load instruction, end to end

        ldr  x1, [x0]        with x0 = 0xFFFF_0000_C0DE_1234

  1. FETCH        PC -> I-TLB -> L1 I-cache -> instruction word
                  (branch predictor already guessed the next PC)

  2. DECODE       recognised as a 64-bit load, base x0, offset 0

  3. EXECUTE      compute the effective address = x0 + 0

  4. TRANSLATE    VA[63] == 1  -> use TTBR1_EL1
                  D-TLB lookup, tagged by ASID
                     hit  -> PA + attributes in ~1 cycle
                     miss -> hardware walks L0->L1->L2->L3
                             any invalid descriptor -> TRANSLATION FAULT
                                 ESR_EL1 = fault code, FAR_EL1 = 0xFFFF...1234
                                 -> exception to EL1, OS decides: fix or SIGSEGV

  5. PERMISSION   AP bits vs current EL and access type
                  UXN/PXN for instruction fetches
                  PAN: is EL1 allowed to touch EL0 memory right now?
                     fail -> PERMISSION FAULT (same reporting path)

  6. STAGE 2      only if EL2 is active for this world:
                  IPA -> PA via VTTBR_EL2, second set of permission checks
                     fail -> exception to EL2, not EL1

  7. CACHE        attributes from MAIR say Normal-WB-Inner-Shareable
                  L1 D-cache probe -> miss -> L2 -> miss -> interconnect

  8. INTERCONNECT AXI read: ADDR=PA, PROT[1]=NS bit, CACHE=attrs, ID=master id
                  --> SMMU?      only for non-CPU masters (ch. 05)
                  --> XPU check: is this master allowed at this PA in this
                      security state?  no -> error response (ch. 07)
                  --> memory controller -> DRAM

  9. RETURN       64-byte line fills L2 and L1, x1 gets the requested 8 bytes

 10. WRITEBACK    x1 architecturally updated; the instruction retires

Every fault type in an OS crash log maps to one of those steps. When you learn to read a kernel oops or a bugcheck, you are really identifying which of these ten steps failed.

Performance features worth knowing

  • Branch prediction — a mispredict costs 10–20 cycles of squashed work. Branchless code via CSEL can win in hot loops.
  • Out-of-order execution and speculation — the CPU runs ahead. This is also the root of Spectre-class vulnerabilities, and why CSDB, SB and array-index masking exist.
  • Prefetching — hardware detects strides and pulls lines in early. Sequential access patterns can be several times faster than random ones for the same amount of data.
  • NEON / SVE — SIMD. NEON is fixed 128-bit; SVE is vector-length agnostic, so the same binary runs optimally on different vector widths.
  • PMU — the Performance Monitor Unit counts cycles, cache misses, TLB misses, mispredicts. This is what perf stat reads. Learn to use it before optimising anything.
  • big.LITTLE / DynamIQ — heterogeneous cores with identical ISA but different performance and power. The scheduler migrates threads between them; this occasionally surprises code that assumed a fixed clock rate.
