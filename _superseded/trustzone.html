ARM TrustZone & the secure world

TrustZone splits the entire SoC — not just the CPU — into two worlds. It is the mechanism behind secure boot, disk encryption keys, DRM, mobile payments and biometric matching. This chapter builds it from one bit of hardware up to a full trusted OS.

The core idea: one bit, everywhere

Everything about TrustZone follows from a single design decision: add one extra bit to every bus transaction, indicating whether the access comes from the Secure or the Non-secure world, and then teach every piece of hardware in the SoC to respect it.

That bit is AxPROT[1] on the AXI bus, universally called the NS bit (NS = 1 means Non-secure).

The rule

A Non-secure master cannot access Secure resources. A Secure master can access both. This is enforced in hardware at the memory controller, at the peripherals, at the interrupt controller and at the interconnect — not by software checks that could be bypassed.

This is what makes TrustZone different from a hypervisor. A hypervisor is software isolating software. TrustZone is silicon isolating silicon: even a fully compromised kernel with arbitrary code execution at EL1 cannot read a Secure memory region, because the DRAM controller will not return the data.

The two worlds

Why put things in the secure world?

  • The rich OS is too big to trust. Linux is tens of millions of lines. Assume it will be compromised eventually. A trusted OS is tens of thousands of lines and can be audited.
  • Some secrets must survive kernel compromise. Device attestation keys, DRM content keys, full-disk-encryption keys, biometric templates, payment credentials.
  • Some operations need a trusted path. "Confirm this payment" must display on a screen the normal world cannot fake and read a touch input the normal world cannot inject.
  • Boot integrity must be rooted somewhere immutable. Secure boot verification runs before the normal world exists at all.

Hardware enforcement, block by block

TrustZone is not a CPU feature. It is a system-wide contract. Every one of these blocks participates:

BlockWhat it enforcesHow
CPU coreThe current security stateSCR_EL3.NS. Every instruction fetch and data access emits the corresponding NS bit.
MMUPer-page securitySeparate translation regimes for Secure and Non-secure EL1. Descriptors carry an NS bit, so Secure software can create a mapping that issues Non-secure accesses.
CachesNo cross-world leakageCache lines are tagged with the security state; a Non-secure lookup cannot hit a Secure line.
TZASC (TrustZone Address Space Controller)DRAM regionsProgrammable region table: address range → permitted NS states. Non-secure access to a Secure region gets an error response.
TZPC (Protection Controller)Peripheral assignmentMarks each peripheral Secure or Non-secure, often at runtime. This is how a fingerprint sensor becomes invisible to Linux.
GICInterrupt routingEach interrupt is in Group 0 (Secure, delivered as FIQ) or Group 1 (Non-secure, IRQ). A Non-secure OS cannot mask or claim a Group 0 interrupt.
SMMUSecure DMASeparate secure/non-secure programming interfaces and stream tables, so a Non-secure OS cannot retarget a secure device's DMA.
eFuses / OTPRoot keys, lifecycle stateReadable only by Secure masters; often only during early boot.
DebugSecure debug authenticationSPIDEN/SPNIDEN signals gate whether JTAG may inspect the secure world. Disabled on production parts.
Consequence worth internalising

If a peripheral is marked Secure in the TZPC, a Linux driver that ioremap()s its registers will get a bus error, not data — because the access carries NS=1 and the peripheral rejects it. This produces an SError or external abort with no obvious explanation. When a peripheral "reads back all zeros or aborts" on a production board but works on a development board, suspect TrustZone configuration before suspecting your driver.

The world switch: SMC

Switching worlds is not a jump. It is an exception to EL3, and EL3 decides everything.

The SMC instruction

SMC #imm ("Secure Monitor Call") raises a synchronous exception to EL3, exactly like SVC raises one to EL1. Arguments go in X0–X7 per the SMC Calling Convention (SMCCC), with X0 holding the function ID.

The full switch flow

issuing an SMC from a Linux kernel driver
#include <linux/arm-smccc.h>

static int read_secure_counter(u64 *out)
{
        struct arm_smccc_res res;

        /* SiP-specific function ID; the value comes from your SoC's firmware docs */
        arm_smccc_smc(0xC2000001,   /* x0: function ID (SMC64, SiP service) */
                      0, 0, 0,      /* x1-x3: arguments                     */
                      0, 0, 0, 0,   /* x4-x7                                */
                      &res);        /* returns x0-x3                        */

        if ((long)res.a0 < 0)
                return -EIO;        /* firmware returned an error code      */

        *out = res.a1;
        return 0;
}
SMC is expensive and blocking

A round trip costs thousands of cycles and, on most designs, the calling core is unavailable for that whole period. Batch work into a single call rather than making many small ones, and never call from an interrupt handler or with a spinlock held.

Secure boot: the chain of trust

TrustZone is worthless if an attacker can replace the secure world's own code. Secure boot ensures every stage is verified by the stage before it, anchored in something immutable.

Related concepts

  • Anti-rollback — a monotonic counter in fuses prevents an attacker from installing an older, correctly signed, but vulnerable firmware version.
  • HUK (Hardware Unique Key) — a per-device key, readable only by secure hardware, used to derive storage encryption keys. This is why encrypted data cannot be moved to another device.
  • Lifecycle state — chips move through fuse-controlled states (blank → development → secured → RMA), each disabling more debug capability. Secure debug is closed in the secured state.
  • Attestation — the device proves its identity and boot state to a server by signing a challenge with a factory-provisioned key held in the secure world.

Secure memory partitioning in practice

Physical memory as configured by the TZASC at boot

  0x8000_0000  +--------------------------------+
               | Non-secure DRAM                |  NS access permitted
               |   Linux kernel + userspace     |  Secure access also permitted
               |   ~1.9 GB                      |
  0xFC00_0000  +--------------------------------+
               | Shared / non-secure buffer     |  both worlds; how a TEE returns
               |   used for TEE message passing |  results without exposing secrets
  0xFE00_0000  +--------------------------------+
               | Secure DRAM                    |  NS access -> ERROR RESPONSE
               |   OP-TEE OS + TA heap          |  invisible to Linux entirely
  0xFF00_0000  +--------------------------------+
               | EL3 firmware (BL31)            |  Secure only, and often locked
               |                                |  so even S-EL1 cannot write it
  0xFF10_0000  +--------------------------------+
Shared memory is the interesting part

The two worlds must exchange data. The pattern is always: the normal world allocates a buffer in non-secure memory and passes its physical address; the secure world copies data in and out of it. Secure code must never dereference a normal-world pointer without validating that it points entirely inside non-secure memory — otherwise the normal world can trick the secure world into reading or writing secure memory on its behalf. This class of bug (a "confused deputy") is behind many real TEE CVEs.

TrustZone for Cortex-M

Microcontrollers have TrustZone too (ARMv8-M), but it works differently — worth knowing so you do not mix them up:

Attacks and mitigations

AttackMechanismMitigation
Confused deputyNormal world passes a pointer into secure memory; secure code writes to itValidate every incoming address range against the non-secure memory map, before use
TOCTOU on shared memorySecure code validates a value in shared memory, then reads it again — normal world changed it in betweenCopy into secure memory first, then validate the copy. Never validate in place.
Cache / timing side channelsNon-secure code measures cache timing to infer secure key materialConstant-time crypto, cache partitioning, flushing on world switch
Spectre-class speculationSpeculative execution across the security boundary leaves microarchitectural tracesSpeculation barriers (CSDB, SB), index masking in monitor code
Rowhammer / fault injectionVoltage or clock glitching to skip a signature check; DRAM disturbance to flip bitsRedundant checks, randomised delays, glitch detectors, ECC memory
DowngradeFlash an older signed firmware with a known bugFuse-based monotonic anti-rollback counters
Debug port abuseAttach JTAG on a production deviceFuse-disable secure debug; require signed debug-unlock tokens

The design principle

Every byte you add to the secure world enlarges the attack surface of the most privileged code on the chip. A vulnerability in a Trusted Application is worse than a vulnerability in the kernel. Keep the secure world small, keep its interfaces narrow, and treat every input from the normal world as hostile — because eventually it will be.

Hands-on: OP-TEE on QEMU

You can run a complete TrustZone stack — TF-A at EL3, OP-TEE at S-EL1, Linux at EL1 — on your laptop with no hardware. This is the best possible way to make the chapter concrete.

# Build the full OP-TEE + TF-A + Linux stack for QEMU (needs ~30 GB and time)
mkdir optee && cd optee
repo init -u https://github.com/OP-TEE/manifest.git -m qemu_v8.xml
repo sync -j8
cd build
make toolchains -j4
make run -j$(nproc)

# Two consoles appear: the normal world (Linux) and the secure world (OP-TEE log).
# In the Linux console:
xtest                 # run the OP-TEE regression/conformance suite
optee_example_hello_world
optee_example_secure_storage

# Watch the secure console while you run these — you can see the TA load,
# the command dispatch, and the return, live.

Then read optee_examples/hello_world/: it is about 150 lines split between a normal-world client (using the TEE Client API) and a Trusted Application (with TA_InvokeCommandEntryPoint). Tracing one command through both halves teaches more than any amount of reading.
