Exception levels & the exception model

Exception levels are ARM's answer to "who is allowed to do what". Every piece of system software — kernels, hypervisors, secure monitors — is defined by which level it runs at. This chapter covers the model, then walks the exact hardware sequence of taking and returning from an exception.

The four levels

AArch64 replaced ARMv7's processor modes with a clean hierarchy. Higher number means more privilege. Privilege is strictly nested: EL3 can do everything EL2 can, and so on.

What each level actually controls

EL1OS kernel and driversTTBR0/1_EL1, SCTLR_EL1, VBAR_EL1, MMIO, interrupt masks, cache and TLB maintenance.SVC, IRQ, data abort from EL0
EL2HypervisorStage-2 tables (VTTBR_EL2), trap configuration (HCR_EL2), virtual interrupts, guest timers.HVC, trapped EL1 operation

Which levels exist is a design choice

EL2 and EL3 are optional. A simple embedded SoC may implement only EL0 and EL1. A phone implements all four. A server implements all four plus S-EL2. Software must query ID_AA64PFR0_EL1 rather than assume. Note also that a level is only active if firmware enables it — Linux boots at EL2 on most platforms and drops to EL1 unless KVM is in use.

What counts as an exception

ARM uses "exception" as the umbrella term for anything that diverts the flow of execution to a handler. Two families:

Synchronous exceptions

Caused by the instruction currently executing, and reported precisely — you know exactly which instruction did it.

  • SVC / HVC / SMC — deliberate calls to EL1 / EL2 / EL3. This is the system call mechanism.
  • Data abort — a load or store failed translation or permission checks.
  • Instruction abort — the instruction fetch itself failed.
  • Undefined instruction — bad encoding, or an instruction disabled at this level.
  • Alignment fault — unaligned access to Device memory, or with SCTLR.A set.
  • Trapped register access — a higher level configured a trap on this system register.
  • Breakpoint / watchpoint / software step — debug events.

Asynchronous exceptions (interrupts)

Caused by something outside the instruction stream; they are taken between instructions.

  • IRQ — normal interrupt. Masked by PSTATE.I.
  • FIQ — fast interrupt. Masked by PSTATE.F. Conventionally reserved for the secure world in TrustZone designs.
  • SError — System Error. Typically an imprecise external abort, such as an ECC failure or a bus error from a write that was posted long ago. Masked by PSTATE.A. These are the hardest faults to debug because the reported PC is unrelated to the cause.

The vector table

VBAR_ELx holds the base address of a 2 KB table of 16 entries. Each entry is 128 bytes (32 instructions) of code — not an address, actual code. You either handle the exception there or branch out.

VBAR_ELx + offset      exception source                     type

  0x000   Synchronous  ┐
  0x080   IRQ          │  from the CURRENT EL,   using SP_EL0
  0x100   FIQ          │  (SPSel = 0)
  0x180   SError       ┘

  0x200   Synchronous  ┐
  0x280   IRQ          │  from the CURRENT EL,   using SP_ELx
  0x300   FIQ          │  (SPSel = 1)  <-- the normal kernel case
  0x380   SError       ┘

  0x400   Synchronous  ┐
  0x480   IRQ          │  from a LOWER EL,       AArch64
  0x500   FIQ          │  <-- syscalls and user-mode faults land here
  0x580   SError       ┘

  0x600   Synchronous  ┐
  0x680   IRQ          │  from a LOWER EL,       AArch32
  0x700   FIQ          │  (32-bit compatibility)
  0x780   SError       ┘

The four-way split by source is what lets a handler know instantly whether it must switch stacks and save user state, or whether it is a nested kernel-mode exception.

Taking an exception: the exact hardware sequence

This is the single most important flow in system software. When an exception is taken from ELx to ELy (where y ≥ x), the hardware performs all of the following atomically, before your first instruction runs:

Why interrupts are masked on entry

Step 5 masks D, A, I and F. This is essential: ELR_EL1 and SPSR_EL1 are single registers, not a stack. If a second exception were taken before your handler saved them, the return address would be overwritten and you could never get back. Your handler saves them to the kernel stack first, and only then may re-enable interrupts to allow nesting.

What the general-purpose registers do — nothing

Notice what is not in that list: X0–X30 are not saved. AArch64 has no banked general-purpose registers (unlike ARMv7). The handler runs with the interrupted code's register values still live, and it is entirely software's job to save them. That saved set is the trap frame / struct pt_regs.

the entry stub every AArch64 OS has
el0_sync:
    /* SP is now SP_EL1 — the kernel stack for this thread */
    sub     sp, sp, #272                 // room for 31 regs + SP_EL0 + ELR + SPSR
    stp     x0,  x1,  [sp, #16 * 0]
    stp     x2,  x3,  [sp, #16 * 1]
    /* ... x4 through x27 ... */
    stp     x28, x29, [sp, #16 * 14]
    mrs     x21, sp_el0                  // the *user* stack pointer
    mrs     x22, elr_el1                 // where to return
    mrs     x23, spsr_el1                // the PSTATE to restore
    stp     x30, x21, [sp, #16 * 15]
    stp     x22, x23, [sp, #16 * 16]

    mrs     x25, esr_el1                 // why are we here?
    lsr     x24, x25, #26                // EC = exception class, ESR[31:26]
    cmp     x24, #0x15                   // 0x15 = SVC from AArch64
    b.eq    do_syscall
    cmp     x24, #0x24                   // 0x24 = data abort from lower EL
    b.eq    do_mem_abort
    b       do_undefined

do_syscall:
    mov     x0, sp                       // pass the trap frame to C
    bl      handle_syscall               // C code from here on
    b       ret_to_user

ret_to_user:
    ldp     x22, x23, [sp, #16 * 16]
    msr     elr_el1,  x22
    msr     spsr_el1, x23
    ldp     x30, x21, [sp, #16 * 15]
    msr     sp_el0,   x21
    /* ... restore x0 - x29 ... */
    add     sp, sp, #272
    eret                                 // back to EL0

Reading ESR_ELx — how to diagnose any fault

The Exception Syndrome Register tells you exactly what happened. Learn its layout and you can decode any crash.

 31    26 25 24                                                    0
+--------+--+-----------------------------------------------------+
|   EC   |IL|                        ISS                          |
+--------+--+-----------------------------------------------------+
  EC  = Exception Class   — what kind of exception
  IL  = Instruction Length (1 = 32-bit instruction, 0 = 16-bit Thumb)
  ISS = Instruction Specific Syndrome — details, meaning depends on EC

0x00Unknown reason — often a genuinely undefined instruction
0x0EIllegal execution state
0x15SVC from AArch64 — a system call
0x16HVC from AArch64 — hypervisor call
0x17SMC from AArch64 — secure monitor call
0x18Trapped MSR/MRS — a higher EL intercepted a system register access
0x20 / 0x21Instruction abort from lower EL / same EL

Data abort ISS (EC = 0x24 / 0x25)

FieldMeaning
DFSC (ISS[5:0])Fault status code: 0b0001xx translation fault (level in low bits), 0b0011xx access flag fault, 0b0010xx permission fault, 0b010000 external abort, 0b1000xx alignment

a decoder you can drop into any bare-metal or kernel handler
void dump_fault(void)
{
    uint64_t esr, far, elr;
    asm volatile("mrs %0, esr_el1" : "=r"(esr));
    asm volatile("mrs %0, far_el1" : "=r"(far));
    asm volatile("mrs %0, elr_el1" : "=r"(elr));

    unsigned ec  = (esr >> 26) & 0x3F;
    unsigned iss =  esr & 0x1FFFFFF;

    printf("EC=0x%02x ESR=0x%016llx FAR=0x%016llx ELR=0x%016llx\n",
           ec, esr, far, elr);

    if (ec == 0x24 || ec == 0x25) {
        unsigned dfsc = iss & 0x3F;
        printf("  data abort on %s of 0x%llx\n",
               (iss & (1u << 6)) ? "write" : "read", far);
        switch (dfsc & 0x3C) {
        case 0x04: printf("  translation fault, level %u"
                          "  -> address not mapped\n", dfsc & 3); break;
        case 0x08: printf("  access flag fault, level %u"
                          "  -> AF bit clear in the descriptor\n", dfsc & 3); break;
        case 0x0C: printf("  permission fault, level %u"
                          "  -> mapped but AP/XN forbids it\n", dfsc & 3); break;
        case 0x10: printf("  external abort -> the bus rejected it "
                          "(check XPU / device power / clock)\n"); break;
        }
        if (iss & (1u << 7))
            printf("  S1PTW: the page table walk itself faulted\n");
    }
}
Fast triage table
  • Translation fault — the address is simply not mapped. Null pointer, or you forgot to ioremap().
  • Permission fault — it is mapped, but not for this. Writing to a read-only page, executing from a no-execute page, or EL0 touching an EL1-only page.
  • Access flag fault — the descriptor's AF bit was 0. Normal in an OS that uses AF for page-aging; a bug in hand-written table code.
  • External abort — translation succeeded and the transaction went out on the bus, and something out there refused it. This is your XPU denying access, or the peripheral's clock or power domain being off.

Moving between exception levels

DirectionMechanismNotes
Upward (less → more privilege)Only via an exception: SVC, HVC, SMC, an interrupt, or a faultYou can never simply "jump" to a higher EL. The entry point is always the vector table, controlled by the higher level.
Downward (more → less privilege)ERETTarget EL comes from SPSR_ELx.M, target PC from ELR_ELx. This is also how you drop to a lower EL during boot.

Dropping from EL3 to EL1 during boot

how firmware hands control to a kernel
    /* configure the world we are about to enter */
    mov     x0, #(1 << 10)          // RW  = 1: EL2/EL1 below is AArch64
    orr     x0, x0, #(1 << 0)       // NS  = 1: the world below is Non-secure
    msr     scr_el3, x0

    /* the state to install on ERET */
    mov     x0, #0x3C5              // M[3:0]=0b0101 -> EL1h, D/A/I/F masked
    msr     spsr_el3, x0

    ldr     x0, =kernel_entry
    msr     elr_el3, x0

    eret                            // now running at EL1, Non-secure

SPSR.M[3:0] encodes the target: 0b0000 = EL0t, 0b0100 = EL1t, 0b0101 = EL1h, 0b1000 = EL2t, 0b1001 = EL2h. The t/h suffix selects SP_EL0 (thread) or SP_ELx (handler) as the stack pointer.

Trapping and virtualisation

A higher exception level can configure the hardware so that specific operations at a lower level cause an exception instead of executing. This is the entire basis of virtualisation.

RegisterOwnerExample bits
HCR_EL2HypervisorTGE route all EL0 exceptions to EL2 · VM enable stage 2 · IMO/FMO virtualise IRQ/FIQ · TVM trap writes to virtual-memory registers
CPTR_EL2 / CPACR_EL1Hypervisor / kernelTrap FP and SIMD access — used for lazy FPU context switching
SCR_EL3Secure monitorNS security state · IRQ/FIQ/EA routing · SMD disable SMC · HCE enable HVC
MDCR_EL2/EL3Hypervisor / monitorTrap debug and performance-monitor access

  Guest kernel (EL1) does:  writel(1, uart_base + UART_CR)
        |
        | stage 1 translation: guest VA -> IPA   (guest's own tables)
        v
  stage 2 lookup of that IPA in VTTBR_EL2
        |
        | the hypervisor deliberately left this IPA UNMAPPED
        v
  stage-2 data abort  -->  taken to EL2, not EL1
        |
        v
  hypervisor handler reads:
        HPFAR_EL2  -> the faulting IPA           (which device register)
        ESR_EL2.ISS -> ISV/SAS/SRT/WnR           (size, direction, source register)
        |
        v
  hypervisor emulates the UART in software, updates its model,
  advances the guest's ELR_EL2 past the faulting instruction
        |
        v
  ERET back into the guest — which never knew anything happened

This is exactly how QEMU/KVM presents virtual hardware, and it is worth internalising: the guest thinks it did MMIO, but no bus transaction ever occurred.

Common pitfalls

Vector table alignment

VBAR_ELx requires 2 KB alignment and each entry must be exactly 128 bytes. Get either wrong and you take the wrong handler, or execute garbage. Use .align 11 for the table and .align 7 per entry.

Re-enabling interrupts too early

If you unmask IRQs before saving ELR_ELx and SPSR_ELx, a nested interrupt destroys your return path. Save first, then unmask.

Forgetting ISB after a system register write

System register writes are not guaranteed to affect instructions already in the pipeline. Changing SCTLR, VBAR, TTBR or TCR without a following ISB gives behaviour that varies by core and by build.

Using the wrong ELR on return

For SVC, ELR already points past the instruction. For a data abort it points at the faulting instruction so it can be retried after the OS fixes the mapping. If you emulate an instruction you must advance ELR by 4 yourself, or you will loop forever.
