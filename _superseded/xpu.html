Access control: XPU, MPU & bus firewalls

The MMU and SMMU decide what an address means. The access-control hardware decides whether a given master is allowed to reach it at all — the last checkpoint before memory. It is the least documented layer in most SoCs and the source of the most confusing faults.

Why a third layer of protection

You already have two:

  • The MMU constrains the CPU.
  • The SMMU constrains DMA-capable devices.

Both have the same weakness: they are configured by software. Whoever owns the page tables owns the policy. If the OS kernel is compromised, it can map anything. If firmware forgets to program the SMMU, a device roams free. And some masters have no SMMU in front of them at all — small microcontrollers embedded in the SoC, sensor hubs, audio DSPs, the power-management processor.

What an XPU adds

A checkpoint sitting on the interconnect itself, in front of memory and peripherals, configured once by the most privileged software (usually EL3 firmware) and then locked. It asks a different question from the MMU: not "what does this address mean?" but "is this master, in this security state, permitted to touch this physical region?"

One concept, many names

Every vendor names this block differently, which makes it hard to search for. They are all the same idea.

Do not confuse XPU with the ARM MPU

The ARM MPU in Cortex-M and Cortex-R is a core-local unit — a simplified MMU that checks the addresses issued by its own core, with no translation. An XPU is a system-level unit on the interconnect that checks transactions from every master. Both are region-based, which is why the names get muddled. Both are covered below.

The core-local MPU (Cortex-M / R)

Before the system-level story, the simpler cousin. On an MCU with no MMU, the MPU provides protection without translation.

MPU region (ARMv8-M / ARMv7-M)

   RBAR  base address | shareability | access permissions | execute-never
   RLAR  limit address | attribute index | enable

  - typically 8 to 16 regions
  - each region: a contiguous physical range with permissions
  - no address translation: the address is used as-is
  - regions have priority; higher-numbered regions override lower ones
  - an access matching NO enabled region faults (if the background region is off)
configuring an ARMv8-M MPU region
/* Make the .rodata region read-only and execute-never for unprivileged code */
#define MPU_RBAR_XN     (1u << 0)
#define MPU_RBAR_AP_RO  (2u << 1)   /* read-only, any privilege */
#define MPU_RLAR_EN     (1u << 0)

void mpu_setup_region(uint8_t region, uint32_t base, uint32_t limit,
                      uint32_t attrs, uint8_t attr_idx)
{
    MPU->RNR  = region;                                   /* select the region  */
    MPU->RBAR = (base  & 0xFFFFFFE0u) | attrs;            /* 32-byte aligned    */
    MPU->RLAR = (limit & 0xFFFFFFE0u) | (attr_idx << 1) | MPU_RLAR_EN;
}

void mpu_init(void)
{
    MPU->CTRL = 0;                       /* disable while reconfiguring        */
    __DSB(); __ISB();

    mpu_setup_region(0, 0x00000000, 0x0007FFFF, MPU_RBAR_AP_RO, 0);  /* flash  */
    mpu_setup_region(1, 0x20000000, 0x2001FFFF, MPU_RBAR_XN,     0); /* SRAM   */
    mpu_setup_region(2, 0x40000000, 0x4FFFFFFF, MPU_RBAR_XN,     1); /* MMIO   */

    MPU->CTRL = MPU_CTRL_ENABLE_Msk;     /* PRIVDEFENA left off: no background */
    __DSB(); __ISB();                    /* mandatory - see chapter 03         */
}

Typical MPU uses on an MCU: making the stack non-executable, catching stack overflow with an unmapped guard region below the stack, making flash read-only, and giving each RTOS task access only to its own memory.

The system-level XPU model

Every XPU implementation, whatever it is called, has the same conceptual structure:

A region entry (conceptually — exact register names vary by vendor)

  +---------------------------------------------------------------+
  | START ADDRESS   | END ADDRESS (or size)                        |
  +---------------------------------------------------------------+
  | SECURITY:  this region is Secure-only / Non-secure-only / both |
  +---------------------------------------------------------------+
  | PERMITTED MASTERS: a bitmap or list of master IDs              |
  |    e.g. bit 0 = CPU, bit 3 = GPU, bit 7 = audio DSP            |
  +---------------------------------------------------------------+
  | PER-MASTER ACCESS: read / write / execute for each             |
  +---------------------------------------------------------------+
  | PRIVILEGE:  privileged-only, or unprivileged permitted         |
  +---------------------------------------------------------------+
  | LOCK BIT:  once set, this entry cannot be changed until reset  |
  +---------------------------------------------------------------+
  | VIOLATION BEHAVIOUR: return an error / return zeros / interrupt|
  +---------------------------------------------------------------+

The decision flow

  Transaction arrives at the XPU
        |  address = PA, master = ID, ns = NS bit, rw = read/write
        v
  Find region(s) whose address range contains PA
        |
        +-- no region matches
        |        |
        |        +--> is there a default/background rule?
        |               permissive default -> ALLOW   (common on dev silicon)
        |               restrictive default -> DENY   (correct for production)
        |
        +-- one or more match  -> apply the highest-priority match
                 |
                 v
        Does the region's security setting accept this NS value?
                 no  -> DENY
                 yes |
                     v
        Is this master ID in the permitted list?
                 no  -> DENY
                 yes |
                     v
        Does the master have the needed R/W/X permission here?
                 no  -> DENY
                 yes -> ALLOW, forward to the target

  On DENY:
        - return a bus error (becomes an external abort / SError at the CPU)
          or silently return zeros / drop the write, depending on config
        - latch the offending address, master ID and access type into
          fault-status registers
        - optionally raise an interrupt to secure firmware
"Silently return zeros" is why this is so hard to debug

Many XPUs can be configured to swallow a denied write and return 0 on a denied read, rather than signalling an error. The CPU sees no fault at all. Your driver reads a register, gets 0, and concludes the device is broken or unpowered. Always check whether the XPU has a fault-status register you can read — it usually latched exactly what happened.

Programming an XPU

Real register layouts are vendor-specific and often under NDA, but the pattern is consistent. Here is a representative sequence, with the reasoning that matters more than the exact offsets:

representative XPU region configuration (runs in EL3 firmware or a secure driver)
/* Region register block, repeated per region */
#define XPU_BASE            0x01F00000u
#define XPU_RGN(n)          (XPU_BASE + 0x100u + (n) * 0x20u)
#define XPU_RGN_START       0x00u   /* region start address (aligned)     */
#define XPU_RGN_END         0x04u   /* region end address                 */
#define XPU_RGN_MASTERS     0x08u   /* bitmap of permitted master IDs     */
#define XPU_RGN_PERM        0x0Cu   /* R/W/X and privilege bits           */
#define XPU_RGN_CFG         0x10u   /* security state, enable, lock       */

#define CFG_ENABLE          (1u << 0)
#define CFG_SECURE_ONLY     (1u << 1)   /* deny all NS=1 transactions     */
#define CFG_LOCK            (1u << 31)  /* write-once until reset         */

#define PERM_READ           (1u << 0)
#define PERM_WRITE          (1u << 1)
#define PERM_EXEC           (1u << 2)
#define PERM_PRIV_ONLY      (1u << 8)

#define MASTER_CPU          (1u << 0)
#define MASTER_CRYPTO       (1u << 4)
#define MASTER_GPU          (1u << 5)

/*
 * Protect the secure OS image: only the CPU and the crypto engine may
 * touch it, secure accesses only, and the rule is locked so that even
 * compromised secure software cannot widen it before the next reset.
 */
static void xpu_protect_secure_os(void)
{
    unsigned r = 3;   /* region index chosen by the platform memory map */

    mmio_write32(XPU_RGN(r) + XPU_RGN_START,   0xFE000000u);
    mmio_write32(XPU_RGN(r) + XPU_RGN_END,     0xFEFFFFFFu);
    mmio_write32(XPU_RGN(r) + XPU_RGN_MASTERS, MASTER_CPU | MASTER_CRYPTO);
    mmio_write32(XPU_RGN(r) + XPU_RGN_PERM,
                 PERM_READ | PERM_WRITE | PERM_EXEC | PERM_PRIV_ONLY);

    /* enable and lock in one write - order matters, see the note below */
    mmio_write32(XPU_RGN(r) + XPU_RGN_CFG,
                 CFG_ENABLE | CFG_SECURE_ONLY | CFG_LOCK);

    /* make sure the configuration has landed before we rely on it */
    __asm__ volatile("dsb sy" ::: "memory");
}
RuleWhy
Configure regions before enabling themA half-configured enabled region can deny accesses your own code needs, including the code doing the configuring
Never lock a region you have not verifiedLock bits are cleared only by reset. A wrong locked region can brick a board until it is re-flashed — or permanently, if the boot code needs the denied access
Set the default rule to denyFail closed. A permissive default means anything you forgot to cover is wide open
DSB after configurationThe write must reach the XPU before you depend on it
Configure in the most privileged stage possibleUsually BL2/BL31. If Linux could reconfigure the XPU, the XPU protects nothing from a compromised Linux

A worked example: locking down a crypto engine

Requirement: an on-chip crypto accelerator holds device keys. Only the secure world may use it. The GPU and the audio DSP must never reach it. Debug access must be blocked on production parts.

Layered configuration to meet that requirement

  1. TZPC / peripheral security
        mark the crypto engine's register block SECURE
        -> any transaction with NS=1 to 0x4030_0000..0x4030_0FFF is refused

  2. XPU peripheral region
        region: 0x4030_0000 - 0x4030_0FFF
        masters permitted: CPU only  (not GPU, not DSP, not DMA engine)
        security: secure only
        privilege: privileged only
        LOCK

  3. XPU memory region for the key buffer in DRAM
        region: 0xFE80_0000 - 0xFE80_FFFF
        masters permitted: CPU + crypto engine
        security: secure only
        LOCK

  4. SMMU
        crypto engine's StreamID -> secure stream table
        configured by secure firmware, not by Linux

  5. Debug
        fuse: secure debug disabled in the "secured" lifecycle state
        -> JTAG master ID cannot be granted access by any software

  Result: a full compromise of the Linux kernel yields NS=1 transactions,
  which are refused at steps 1 and 2. There is no software path to the keys.

Debugging access-control failures

This is the practical heart of the chapter. XPU faults look like hardware failures, and engineers waste days on them because the symptom points nowhere near the cause.

Symptoms

SymptomLikely XPU cause
Reading a peripheral register returns all 0x00000000 or all 0xFFFFFFFFAccess denied with "return zeros/ones" behaviour configured
Writes to a register have no effect; reads always show the reset valueWrites are being dropped
SError or external abort with no obvious faulting addressA posted write was rejected long after the instruction retired
Data abort with DFSC = 0b010000 (external abort)Translation succeeded, the bus refused the access — see ESR decoding
Works on the development board, fails on production siliconFuses moved the part to the secured lifecycle state, tightening defaults
Works when Linux boots standalone, fails with the full firmware stackFirmware programmed and locked an XPU region that excludes your device
Only DMA fails; MMIO from the CPU worksThe device's master ID is not in the permitted list even though the CPU's is

Triage flow

  Access appears to fail
        |
        v
  1. Is the device actually powered and clocked?
        Rule this out FIRST. An unclocked peripheral also returns zeros or aborts.
        Check the clock and power-domain registers, or `clk_summary` in debugfs.
        |
        v
  2. Is the mapping correct?
        Right base address from the TRM? Mapped as Device-nGnRnE, not Normal?
        Correct size? (ioremap of too few bytes silently truncates)
        |
        v
  3. Read the XPU fault-status registers.
        Almost every XPU latches: faulting address, master ID, read/write,
        NS bit, and which region matched. This is the definitive answer.
        On many SoCs firmware exposes this via an SMC or a log ring.
        |
        v
  4. Compare the latched master ID against what you expect.
        A mismatch means the SoC integration differs from the documentation,
        or the transaction is coming from a different path than you think
        (e.g. through a bridge that re-IDs it).
        |
        v
  5. Check the security state.
        Is your code running Non-secure while the region is Secure-only?
        Was the peripheral assigned to the secure world by the TZPC?
        |
        v
  6. Check whether firmware locked the region.
        If it is locked, no amount of Linux-side configuration will help.
        You need a firmware change and a reboot.
        |
        v
  7. Last resort: boot with the XPU in permissive mode (development parts only).
        If the problem vanishes, it is confirmed to be access control.
        If it persists, the XPU was a red herring — go back to step 1.
The bisect that always works

Get a second master to try the same access. If the CPU can read the register but the DMA engine cannot, the difference is the master ID and the answer is the XPU's permitted-master list. If neither can, it is address, clock or security state. This single experiment eliminates half the possibilities.

What to ask the SoC vendor

When you are blocked, these are the questions that get useful answers:

  • "What is the master ID of <block> as seen by the XPU in front of <target>?"
  • "Which boot stage programs the XPU regions covering <address range>, and are they locked?"
  • "Is there a fault-status register for this XPU, and how do I read it from the normal world?"
  • "Is <peripheral> assigned Secure or Non-secure in the default TZPC configuration?"
  • "Does the production fuse configuration change any XPU defaults?"

Designing an access-control policy

If you are the one deciding the policy, work from principles rather than from the register list:

  1. Enumerate every master. Not just the obvious ones — include the debug port, the power-management microcontroller, the sensor hub, any test/DFT interface. Each is a potential path to memory.
  2. Enumerate every asset. Key storage, secure OS code and data, firmware images in DRAM, fuse controllers, the XPU's own configuration registers, boot-mode straps.
  3. Build the matrix. Masters down one axis, assets across the other. Fill in the minimum access each pairing genuinely requires. Every empty cell is a rule you must enforce.
  4. Default deny. Anything not in the matrix is refused. Verify this by testing the default, not by reading the documentation.
  5. Lock what will not change. Anything configured before the normal world starts, and not needed at runtime, should be locked so a later compromise cannot widen it.
  6. Test the negatives. A policy that has never been tested by attempting a forbidden access is a policy you do not know works. Write deliberate violation tests during bring-up, while debug is still open.
Protect the protector

The XPU's own configuration registers must be covered by an XPU region that only the most privileged master can write, and that region must be locked. An access-control block whose configuration is writable by the software it is meant to constrain provides no protection at all — and this exact mistake has shipped in real products.
