Debugging & bring-up toolkit

Embedded debugging is a discipline, not a set of tools. This chapter is the method — how to narrow a problem systematically — followed by the tools that implement it on both platforms.

The method

Beginners reach for a debugger first. Experienced engineers spend most of their time narrowing the search space and only then attach a tool. The order matters:

  1. Make it reproducible. An intermittent bug is a bug you cannot fix. Find the smallest reliable trigger, even if it takes a day. Everything after this is faster once you have it.
  2. Establish what is known good. Did it ever work? On another board? With another kernel? Under a different load? The difference between working and not working is the bug.
  3. Bisect. In code (git bisect), in configuration (halve the defconfig), in hardware (swap the board), in time (when did it start?). Each bisection halves the space; ten of them reduce a thousand possibilities to one.
  4. Form one falsifiable hypothesis. "The DMA buffer is not being invalidated" is testable. "Something is wrong with the memory" is not.
  5. Test it with the cheapest tool that can. Often a single print, or reading one register.
  6. Change one thing at a time. Two simultaneous changes give you an uninterpretable result and you will have to redo both.
  7. Write down what you learned, including the dead ends. Next time this class of bug appears, that note saves you the week.
The most useful question in embedded debugging

"Is the transaction actually reaching the hardware?" Most bugs that feel mysterious resolve into one of: the write never left the CPU (cache/barrier), the write never reached the device (address, clock, power, firewall), or the device did something other than what you expected (errata, wrong register, wrong order). Establish which of the three you are in, and you have cut the problem down by two-thirds.

        yes |
            v

        dump the buffer before and after. All zeros = it never wrote.
        Garbage = cache coherency. Fault = translation or the SMMU (chapter 05).

Printing changes timing

A print in an interrupt handler can add milliseconds and make a race disappear — the classic "Heisenbug". If the problem vanishes when you add a print, that is information: you have a timing or concurrency bug. Switch to a low-overhead mechanism (ftrace, WPP, a GPIO toggle, or a memory ring buffer you dump later) rather than concluding the print fixed it.

# Linux: enable pr_debug at runtime, no rebuild
echo 'module mydriver +p'                > /sys/kernel/debug/dynamic_debug/control
echo 'file drivers/x/my.c line 100-200 +p' > /sys/kernel/debug/dynamic_debug/control
echo 'func my_probe +p'                  > /sys/kernel/debug/dynamic_debug/control

# raise console verbosity
echo 8 > /proc/sys/kernel/printk
dmesg -w --level=err,warn

Level 0.5: a GPIO and an oscilloscope

When timing matters and printing is too slow, toggle a pin at the points of interest and look at it on a scope or logic analyser. Overhead is a few nanoseconds and you get exact timing, jitter and ordering between cores.

/* the cheapest instrumentation there is */
#define PROBE_HIGH()  writel(BIT(7), gpio_base + GPIO_SET)
#define PROBE_LOW()   writel(BIT(7), gpio_base + GPIO_CLR)

static irqreturn_t my_isr(int irq, void *d)
{
        PROBE_HIGH();          /* rising edge = interrupt entry  */
        ...
        PROBE_LOW();           /* falling edge = interrupt exit  */
        return IRQ_HANDLED;    /* pulse width = handler latency  */
}

This answers questions no software tool can: is the interrupt actually being asserted by the device? How long is the handler really taking, worst case? Are two cores entering the critical section simultaneously?

Level 1: JTAG / SWD hardware debugging

A hardware debug probe halts the core and inspects it directly. It is the only tool that works before any software is running — during bring-up, in the boot ROM, or when the system is hard-hung.

Debug may be fused off

On a production part with secure boot enabled, JTAG for the secure world — and sometimes entirely — is disabled by fuses (see chapter 06). If your probe cannot connect on production silicon but works on a development board, this is why. You need a signed debug-unlock token from the vendor, or a development part.

A board bring-up checklist

New hardware, nothing works yet. Go in this order — each step depends on the previous one:

  1. Power. Measure every rail with a meter. Sequencing errors damage parts. Do not skip this because "it must be fine".
  2. Clocks. Scope the main oscillator and the PLL outputs. A wrong crystal load capacitor produces a system that half-works.
  3. Reset. Confirm reset asserts and releases cleanly, with correct timing.
  4. Boot mode straps. Read the boot-mode pins. Confirm the SoC is trying to boot from what you think.
  5. JTAG connectivity. Can the probe see the core's IDCODE? If not, stop and fix that first — everything downstream is guesswork without it.
  6. The first instruction. Halt at reset; confirm the PC and the reset vector.
  7. UART out. The single most valuable milestone. Getting one character out of a serial port turns the rest of bring-up from blind to sighted.
  8. SRAM. Write and read back patterns (0x00, 0xFF, 0x55, 0xAA, address-as-data). Catches stuck and shorted data/address lines.
  9. DDR. Init and calibrate, then run an extended memory test at temperature. Marginal DDR timing is the source of "random" crashes months later.
  10. Boot media. eMMC / SD / SPI-NOR enumerate and read.
  11. Bootloader. U-Boot prompt.
  12. Kernel. earlycon output, then a full boot.
  13. Rootfs and userspace. A shell prompt.
  14. Peripherals, one at a time, each with a test.

Habits of good debuggers

  • Read the error message. All of it. Twice. It usually says exactly what is wrong.
  • Read the errata before assuming your code is wrong — and read your code before assuming the silicon is.
  • Keep a known-good build to bisect against, always.
  • Version-control your configuration, not just your code. Half of embedded bugs are configuration.
  • When stuck for more than two hours, explain the problem out loud to someone. You will often solve it mid-sentence.
  • When you fix something, understand why the fix works. A fix you cannot explain is a coincidence waiting to reappear.
  • Write the regression test before you move on.
