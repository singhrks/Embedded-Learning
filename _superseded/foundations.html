Embedded foundations & the toolchain

Before any ARM-specific detail, you need the vocabulary that every embedded conversation assumes: what a SoC is made of, what an address really means, how software talks to hardware, and what happens between your .c file and a running instruction.

What "embedded" actually means

An embedded system is a computer built into a product, where the software is written with knowledge of the specific hardware. That knowledge is the whole job. On a PC you call fopen() and never think about the disk controller. In embedded, you are the disk controller.

Three broad tiers, and they demand different skills:

TierExampleSoftware modelWhat you write
Bare metal / MCUCortex-M4, STM32, ESP32No OS, or a small RTOS. One flat address space, no MMU.Everything: startup code, ISRs, drivers, application
RTOSFreeRTOS, Zephyr, ThreadXTasks, priorities, deterministic scheduling. Usually MPU, not MMU.Tasks + drivers, using the RTOS primitives

This site targets the third tier — Cortex-A class application processors — because that is where ARM architecture, exception levels, SMMU, TrustZone and full OS drivers all live. But everything in chapters 02 and 03 applies to all three.

Anatomy of a SoC

A System on Chip is not "a CPU". It is a small city of blocks sharing an interconnect. Recognising the blocks is half of reading a technical reference manual (TRM).

The blocks you must be able to name

  • Master (initiator) — anything that starts a bus transaction: a CPU, a GPU, a DMA engine, a USB controller.
  • Slave (target) — anything that responds: memory, a peripheral's register block.
  • Interconnect / NoC — the fabric routing transactions from masters to slaves. It carries more than address and data: it carries who is asking (master ID) and in what security state (NS bit). Chapters 05 and 07 are entirely about what happens on this fabric.
  • MMU — per-CPU address translation and permission checking.
  • SMMU / IOMMU — the same thing, for non-CPU masters.
  • GIC — the ARM Generic Interrupt Controller: routes peripheral interrupts to cores.
  • Boot ROM — mask-programmed code that runs first. It cannot be changed. It is the root of trust.

The memory map, and what "an address" means

A SoC has one large physical address space, typically 32 to 48 bits wide. The chip designer statically assigns ranges of it to blocks. That assignment is the memory map, and it is the first table you look up in any TRM.

The key idea

Memory and peripherals share one address space. There is no separate "I/O instruction" on ARM. Writing to a UART is the same instruction as writing to RAM — only the address differs. This is called memory-mapped I/O (MMIO), and it is the foundation of every driver you will write.

Reading and writing a register

A peripheral exposes a small block of registers. The TRM gives you a base address and, for each register, an offset, a width, an access type (RW, RO, W1C — "write 1 to clear") and a bitfield layout.

bare-metal MMIO — the shape of every driver ever written
#define UART0_BASE      0x40000000u

/* offsets from the TRM */
#define UART_DR         0x00u   /* data register        RW */
#define UART_FR         0x18u   /* flag register        RO */
#define UART_IBRD       0x24u   /* integer baud divisor RW */
#define UART_CR         0x30u   /* control register     RW */

/* bit positions from the TRM */
#define FR_TXFF         (1u << 5)   /* transmit FIFO full */
#define CR_UARTEN       (1u << 0)
#define CR_TXE          (1u << 8)

static inline void     mmio_write32(uintptr_t a, uint32_t v) { *(volatile uint32_t *)a = v; }
static inline uint32_t mmio_read32 (uintptr_t a)             { return *(volatile uint32_t *)a; }

void uart_init(void)
{
    mmio_write32(UART0_BASE + UART_CR, 0);              /* disable while configuring */
    mmio_write32(UART0_BASE + UART_IBRD, 26);           /* baud rate divisor        */
    mmio_write32(UART0_BASE + UART_CR, CR_UARTEN | CR_TXE);
}

void uart_putc(char c)
{
    /* spin while the TX FIFO is full */
    while (mmio_read32(UART0_BASE + UART_FR) & FR_TXFF)
        ;
    mmio_write32(UART0_BASE + UART_DR, (uint32_t)c);
}
Why volatile is mandatory

Without volatile, the compiler sees while (*(uint32_t*)FR & TXFF);, notices that nothing in the loop changes *FR, hoists the load out of the loop and produces an infinite loop (or removes it entirely). volatile tells the compiler: this location can change behind your back, so re-read it every time and never eliminate the access.

But volatile is not a barrier. It constrains the compiler, not the CPU or the interconnect. It does not guarantee that your write to register A becomes visible to the device before your write to register B. For that you need memory barriers — see chapter 03. In a real OS driver you use writel()/readl() (Linux) or WRITE_REGISTER_ULONG() (Windows), which handle both.

Cross-compilation

You develop on an x86-64 host but the code runs on ARM. A cross-compiler is named <arch>-<vendor>-<os>-<abi>-gcc:

TripletTarget
aarch64-linux-gnu-gcc64-bit ARM, Linux userspace, glibc
aarch64-none-elf-gcc64-bit ARM, bare metal (no OS)
arm-none-eabi-gcc32-bit ARM/Thumb, bare metal — the Cortex-M standard
arm-linux-gnueabihf-gcc32-bit ARM, Linux, hardware float ABI
 
# typical cross-build invocation
export CROSS_COMPILE=aarch64-linux-gnu-
export ARCH=arm64
${CROSS_COMPILE}gcc -march=armv8-a -O2 -c main.c -o main.o

# inspect what you produced
${CROSS_COMPILE}objdump -d main.o        # disassemble
${CROSS_COMPILE}readelf -S program.elf   # section headers and addresses
${CROSS_COMPILE}nm      program.elf      # symbol table
${CROSS_COMPILE}size    program.elf      # text / data / bss sizes

The linker script — where your code lands

On a hosted OS the linker script is invisible. On bare metal you write it, and it is how you say "vectors at 0x0, code in flash, stack at the top of SRAM".

MEMORY {
  FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 512K
  SRAM  (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS {
  .text : { KEEP(*(.vectors)) *(.text*) *(.rodata*) } > FLASH
  .data : { _data_start = .; *(.data*) _data_end = .; } > SRAM AT > FLASH
  .bss  : { _bss_start = .;  *(.bss*) *(COMMON) _bss_end = .; } > SRAM
  _stack_top = ORIGIN(SRAM) + LENGTH(SRAM);
}

Note .data ... > SRAM AT > FLASH: initialised variables must live in RAM but be stored in flash. Startup code copies them across before main() — that copy loop is why your global initialisers work.

Endianness, alignment and padding

  • Endianness — byte order within a multi-byte value. ARM is little-endian in practice (the AArch64 E0E/EE bits can select big-endian, but nobody does). It matters when you parse a network packet or a file format defined as big-endian: use be32_to_cpu() / ntohl() rather than casting.
  • Alignment — a 32-bit load normally requires a 4-byte-aligned address. Unaligned access to Device memory (i.e. MMIO) always faults on ARM, even when it would be allowed on normal memory. This is a classic first bug: casting a byte pointer into a register block.
  • Padding — the compiler inserts holes in structs to keep members aligned. Never assume a struct's binary layout matches a hardware register block unless you have checked, and never memcpy() a struct onto the wire without a packed representation.
struct bad  { uint8_t a; uint32_t b; uint8_t c; };  /* sizeof == 12, not 6 */
struct good { uint32_t b; uint8_t a, c; };          /* sizeof == 8          */

/* register blocks: describe them as a struct of volatile members in order */
struct uart_regs {
    volatile uint32_t DR;      /* 0x00 */
    volatile uint32_t RSR;     /* 0x04 */
    uint32_t reserved0[4];     /* 0x08 - 0x14 gap, must be declared */
    volatile uint32_t FR;      /* 0x18 */
};
#define UART0 ((struct uart_regs *)0x40000000u)

Where this is going

DMA is the reason chapters 05 and 07 exist. The moment a device writes to memory on its own, you have a second entity issuing addresses that the CPU's MMU never sees — and every isolation guarantee you built with page tables has a hole in it unless something else checks those transactions.
