Semaphores, barriers and latches

Three primitives that are not mutexes. A semaphore counts permits; a latch is a one-shot gate; a barrier is a rendezvous. Reaching for the right one turns several pages of condition-variable code into a line, and reaching for the wrong one produces the most durable deadlocks in this track.

Semaphores: counting permits

A semaphore is a counter with waiting built in, which makes it a natural fit for limiting access to a pool of resources rather than for mutual exclusion — even though it can do both.

   A semaphore is an integer with two atomic operations and a
   waiting rule.

     wait / P / acquire / down
         if count > 0:  count--,  proceed
         else:          block until someone posts

     post / V / release / up
         count++,  wake one waiter if any

   THREE DISTINCT USES, and they look nothing alike:

   1. COUNTING A RESOURCE    initial = N
        N identical things (connections, buffers, slots).
        wait = take one, post = give one back.

   2. SIGNALLING             initial = 0
        "an event happened". Producer posts, consumer waits.
        The count IS the number of pending events, so unlike a
        condition variable a semaphore REMEMBERS a post that
        arrives before anyone waits. No lost wake-ups.

   3. MUTUAL EXCLUSION       initial = 1
        A "binary semaphore". Works, and you should not:
        it has no owner, so no priority inheritance, no
        deadlock detection, no error checking, and anyone may
        post a semaphore they never waited on.

   THE KEY DIFFERENCE FROM A CONDITION VARIABLE:
     a condvar is stateless and a signal to nobody is lost.
     a semaphore is stateful and a post to nobody is stored.
   That single property decides which one your problem wants.
/* POSIX */
#include <semaphore.h>

sem_t slots;
sem_init(&slots, 0 /* not process-shared */, 8 /* permits */);

sem_wait(&slots);        /* take one, blocking            */
sem_trywait(&slots);     /* or fail with EAGAIN           */
sem_timedwait(&slots, &abs_timeout);
/* ... use the resource ... */
sem_post(&slots);        /* give it back                  */

/* sem_post is ASYNC-SIGNAL-SAFE - almost uniquely among
   synchronisation primitives. It is the only correct way to
   wake a thread from a signal handler.                     */

/* C++20 */
#include <semaphore>
std::counting_semaphore<8> slots{8};
std::binary_semaphore     signal{0};

slots.acquire();
slots.release();
if (slots.try_acquire_for(std::chrono::milliseconds(10))) { ... }

/* Windows */
HANDLE s = CreateSemaphore(NULL, 8, 8, NULL);
WaitForSingleObject(s, INFINITE);
ReleaseSemaphore(s, 1, NULL);
The rule that catches most semaphore bugs

Wrap it. A raw sem_wait/sem_post pair scattered across a function has exactly the problem manual unlock has, plus no owner to blame. Use a RAII guard, and make the semaphore private to the type that owns the resource it counts — never a global that any code may post.

/* Semaphore as a connection pool - use 1, the good one. */

class Pool {
    std::counting_semaphore<> permits_;
    std::mutex               m_;
    std::vector<Conn>        free_;
public:
    explicit Pool(int n) : permits_(n) { /* fill free_ */ }

    class Lease {                       /* RAII, so a throw or
                                           an early return
                                           cannot leak a permit */
        Pool *p_; Conn c_;
    public:
        Lease(Pool *p, Conn c) : p_(p), c_(std::move(c)) {}
        ~Lease() { if (p_) p_->give_back(std::move(c_)); }
        Lease(Lease&& o) : p_(o.p_), c_(std::move(o.c_))
                          { o.p_ = nullptr; }
        Conn &get() { return c_; }
    };

    Lease take() {
        permits_.acquire();             /* blocks if all N are
                                           out - THIS is the
                                           backpressure         */
        std::lock_guard<std::mutex> g(m_);
        Conn c = std::move(free_.back());
        free_.pop_back();
        return Lease(this, std::move(c));
    }
private:
    void give_back(Conn c) {
        { std::lock_guard<std::mutex> g(m_); free_.push_back(std::move(c)); }
        permits_.release();             /* release AFTER the
                                           object is back in
                                           the list             */
    }
};

Latches: a gate that opens once

Sometimes you need to wait for a set of things to finish exactly once, with no reuse. A latch is that: a one-shot countdown, simpler and harder to misuse than the reusable alternative.

/* A latch counts DOWN to zero and then stays open for ever.
   Single use. Nobody resets it.                            */

#include <latch>                        /* C++20             */

std::latch ready(3);                    /* three participants */

/* worker */
        do_setup();
        ready.count_down();             /* "I am ready"        */
        ready.wait();                   /* wait for the others */
        /* all three are past setup here */

/* or, from a coordinator that does not participate: */
        ready.wait();                   /* until all 3 counted */

/* arrive_and_wait() is count_down() + wait() in one call.  */

/* USES
     - start N workers, wait until all have initialised
     - fan out N requests, wait for all N to complete
     - hold workers at a starting line for a benchmark

   Before C++20, or in C, it is a counter plus a condvar: */

struct latch {
        pthread_mutex_t m;
        pthread_cond_t  cv;
        unsigned        n;
};
void latch_count_down(struct latch *l) {
        pthread_mutex_lock(&l->m);
        if (l->n > 0 && --l->n == 0)
                pthread_cond_broadcast(&l->cv);   /* broadcast:
                                                     everyone is
                                                     released    */
        pthread_mutex_unlock(&l->m);
}
void latch_wait(struct latch *l) {
        pthread_mutex_lock(&l->m);
        while (l->n > 0)
                pthread_cond_wait(&l->cv, &l->m);
        pthread_mutex_unlock(&l->m);
}

Barriers: a rendezvous, repeatedly

A barrier makes every participating thread wait until all have arrived, then releases them together. It is the standard structure for phased parallel computation, and it reuses itself for the next phase.

/* A barrier is a REUSABLE latch. Every participant waits
   until all arrive; then all are released and the barrier
   resets for the next round.                               */

#include <barrier>                      /* C++20             */

std::barrier sync(4, [] {               /* completion function:
        swap_buffers();                    runs ONCE per phase,
        ++generation;                      by one thread, while
});                                        all others wait    */

void worker(int id) {
        for (int step = 0; step < 1000; step++) {
                compute_my_share(id);
                sync.arrive_and_wait();     /* phase boundary  */
                /* every thread's writes from this phase are
                   visible to every thread in the next one    */
        }
}

/* pthread barriers, the same thing: */
pthread_barrier_t b;
pthread_barrier_init(&b, NULL, 4);
int r = pthread_barrier_wait(&b);
if (r == PTHREAD_BARRIER_SERIAL_THREAD) {
        /* exactly ONE thread gets this - do the once-per-phase
           work here */
}

/* WHAT BARRIERS ARE FOR: bulk-synchronous parallelism.
   Iterative solvers, physics steps, image filters, any
   "everyone computes, then everyone exchanges" loop.

   THE COST: every phase runs at the speed of the SLOWEST
   participant. With 16 threads and one that is 10% slow,
   you lose 10% of all 16. Load imbalance is the whole game.

   THE DEADLOCK: if any participant leaves early - returns,
   throws, hits an error path - every other thread waits for
   ever. arrive_and_drop() exists for exactly this, and code
   that can throw between arrivals needs it.               */
The three ways barriers deadlock

1. A participant exits the loop early on an error and never arrives again. 2. The count does not match the number of threads — off by one, or a thread that failed to start. 3. Two barriers used in different orders by different threads. All three present identically: everything hangs, no CPU used, and a stack dump shows every thread in barrier_wait.

Choosing

These three primitives overlap enough that the choice is not obvious from their descriptions. This reduces it to what you are actually trying to express.

You want to…Use
Protect data from concurrent accessMutex — it has an owner
Wait for a state to become trueCondition variable
Limit concurrency to NCounting semaphore
Signal from an interrupt or signal handlerSemaphore — the only async-signal-safe one
Wake a thread for an event that may arrive firstSemaphore, which stores the post
Wait for N things to finish, onceLatch
Synchronise phases of a loop, repeatedlyBarrier
Run something exactly oncecall_once / pthread_once
Deliver a single value to a single waiterfuture / promise

How it shows up

SymptomCause
Pool exhausts and never recoversA permit leaked on an error path — needs RAII
More than N concurrent users of an N-permit resourceSomebody posted without waiting; a semaphore has no owner to stop them
Real-time thread misses deadlines behind a binary semaphoreNo priority inheritance — use a mutex (chapter 15)
Everything hangs at a barrierWrong participant count, or one thread left early
Barrier phase takes as long as the slowest thread every timeWorking as designed — fix load balance, not the barrier
Latch never opensFewer count_down calls than the initial count, often an early return
Deadlock on shutdown with waiters on a semaphoreSemaphores have no "close" — post N times or use a different primitive
Signal handler deadlocks the processIt took a mutex or signalled a condvar; only sem_post is safe there
Counter drifts over daysUnbalanced wait/post, usually one path that returns without releasing
