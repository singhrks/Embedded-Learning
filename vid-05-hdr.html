HDR and wide colour gamut

HDR changes three things at once — the transfer function, the gamut and the bit depth — and most "HDR looks wrong" bugs come from changing one without the others. It also introduces the first transfer function in history that specifies absolute brightness, which breaks a lot of assumptions.

What HDR actually changes

   SDR                          HDR

   peak ~100 nits (cd/m2)       peak 1000-10000 nits
   BT.709 gamut                 BT.2020 container, P3 in
                                practice
   gamma ~2.2, RELATIVE         PQ (absolute) or HLG (relative)
   8-bit                        10-bit minimum, 12 for grading

   "Nits" = candela per square metre. Useful anchors:

     0.005    the darkest a good OLED can show
     1        a lit interior at night
     100      SDR reference white - a paper page, a monitor
     203      HDR "diffuse white" reference (ITU-R BT.2408)
     1000     a typical consumer HDR TV's peak
     4000     a mastering monitor
     10000    the PQ maximum
     1600000  the sun

   THE MISCONCEPTION worth killing early: HDR is not "brighter
   everything". It is a WIDER RANGE. Diffuse white - a shirt,
   a wall, a page of text - should still sit near 100-200
   nits. What HDR adds is HEADROOM for specular highlights,
   the sun, a lightbulb, a reflection - things that were
   previously clipped to the same white as the shirt.

   If an HDR image looks uniformly blinding, someone has
   mapped SDR white to HDR peak. That is the most common
   authoring error.

/* PQ, the ST 2084 EOTF. Note it returns ABSOLUTE nits. */

#define M1 (2610.0 / 16384.0)          /* 0.1593017578125 */
#define M2 (2523.0 / 4096.0 * 128.0)   /* 78.84375        */
#define C1 (3424.0 / 4096.0)           /* 0.8359375       */
#define C2 (2413.0 / 4096.0 * 32.0)    /* 18.8515625      */
#define C3 (2392.0 / 4096.0 * 32.0)    /* 18.6875         */

double pq_to_nits(double e)            /* e in [0,1]      */
{
        double p  = pow(e, 1.0 / M2);
        double num = fmax(p - C1, 0.0);
        double den = C2 - C3 * p;
        return 10000.0 * pow(num / den, 1.0 / M1);
}

double nits_to_pq(double nits)
{
        double y = fmin(fmax(nits / 10000.0, 0.0), 1.0);
        double p = pow(y, M1);
        return pow((C1 + C2 * p) / (1.0 + C3 * p), M2);
}

/* THE CONSEQUENCE OF "ABSOLUTE": a PQ value is a promise
   about photons. It does not adapt. Show 10,000-nit content
   on a 600-nit display and the display MUST tone-map, and the
   quality of that tone map is now a property of the TV, not
   of your content. Hence the metadata below.             */

/* HLG, by contrast, is relative and has a system gamma that
   depends on the display's peak - it degrades gracefully and
   needs no metadata, which is why broadcasters chose it. */
Why HDR needs 10 bits, not as a nicety

PQ spreads its code values over a range 100× wider than SDR. At 8 bits the steps between adjacent codes become visible as banding in gradients — a sky, a wall lit by a lamp — much sooner than in SDR. Ten bits is the practical minimum and it is why HEVC Main10 and AV1 Main (which is 10-bit capable) became the HDR codecs. An "8-bit HDR" file is a red flag.

The metadata

/* PQ content must tell the display what it was mastered on,
   so the display knows how to tone-map. Two levels: */

/* 1. MASTERING DISPLAY COLOUR VOLUME (SMPTE ST 2086)
      static, per title. */
     display_primaries  R, G, B in CIE xy
     white_point        xy
     max_display_mastering_luminance   e.g. 1000 nits
     min_display_mastering_luminance   e.g. 0.005 nits

/* 2. CONTENT LIGHT LEVEL (CTA-861.3)
      also static, and often more useful in practice. */
     MaxCLL   Maximum Content Light Level - the brightest
              single pixel in the whole title
     MaxFALL  Maximum Frame-Average Light Level - the
              brightest frame, averaged. This is what
              protects the panel from being asked to run at
              peak across the whole screen.

/* 3. DYNAMIC METADATA - per scene or per frame.
     HDR10+       SMPTE ST 2094-40, open, royalty-free-ish
     Dolby Vision ST 2094-10, proprietary, licensed, and
                  carries a full colour-volume mapping plus
                  optionally a second enhancement layer

   HDR10 = PQ + BT.2020 + 10-bit + static metadata. It is the
   baseline that everything supports, and the one to target
   unless you have a reason not to.                        */

# Setting it with ffmpeg - the syntax is unpleasant and
# exact. The values are in units of 1/50000 for chromaticity
# and 1/10000 nits for luminance.
$ ffmpeg -i in.mov -c:v libx265 -pix_fmt yuv420p10le \
  -x265-params "hdr-opt=1:repeat-headers=1:\
colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc:\
master-display=G(13250,34500)B(7500,3000)R(34000,16000)\
WP(15635,16450)L(10000000,1):max-cll=1000,400" \
  out.mp4

# Verify - and this is worth doing every time, because a
# silently-dropped side-data block is the usual failure:
$ ffprobe -show_frames -read_intervals "%+#1" \
    -show_entries frame=side_data_list out.mp4
[SIDE_DATA]
side_data_type=Mastering display metadata
red_x=34000/50000 ...
max_luminance=10000000/10000
[/SIDE_DATA]
[SIDE_DATA]
side_data_type=Content light level metadata
max_content=1000
max_average=400
[/SIDE_DATA]
Metadata is the part that gets lost

Remux a file, run it through a filter, transcode it with default settings, or pass it through a player that does not understand side data, and the mastering metadata quietly disappears. The video still decodes, the colour tags may survive, and the display now tone-maps with no idea what it is looking at — producing a washed-out or crushed picture that looks like a decoder bug. When HDR "looks wrong", check the metadata survived before suspecting anything else.

Tone mapping and gamut mapping

   TONE MAPPING: 1000 nits of content, 400 nits of display.

   CLIP                everything above 400 becomes 400.
                       Highlights lose all detail; a sunset
                       becomes a white disc. Cheap, and bad.

   REINHARD            L' = L / (1 + L). Smooth, and it
                       desaturates and flattens the whole
                       image, including the parts that fitted
                       perfectly well.

   ROLL-OFF / BT.2390  linear below a knee, a smooth curve
                       above it. Preserves everything that
                       fits and compresses only the excess.
                       THIS IS THE RIGHT DEFAULT.

   ACES / HABLE        filmic S-curves from film emulation.
                       Popular in games; more of a look than
                       a mapping.

   DYNAMIC             HDR10+/Dolby Vision drive the curve
                       per scene, so a dark scene and a bright
                       one are mapped differently.

   GAMUT MAPPING is the same problem in colour: BT.2020
   content on a P3 display has saturated colours that simply
   do not exist there.

     CLIP        oversaturated colours all become the same
                 boundary colour -> flat patches, lost detail
     COMPRESS    squeeze the whole gamut inward -> everything
                 slightly duller, but relationships preserved
     PERCEPTUAL  preserve hue and lightness, sacrifice
                 saturation. Usually what you want.

   AND THE HARD DIRECTION: HDR -> SDR. You are throwing away
   most of the range. A naive conversion looks grey and flat;
   a good one applies a roll-off AND a saturation boost,
   because desaturation is what makes tone-mapped images look
   washed out.
# Tone map HDR to SDR with something reasonable, in linear
# light (chapter 2 - doing it in PQ space is wrong):
$ ffmpeg -i hdr.mp4 -vf "\
zscale=t=linear:npl=100,\
format=gbrpf32le,\
zscale=p=bt709,\
tonemap=tonemap=bt2390:desat=0,\
zscale=t=bt709:m=bt709:r=tv,\
format=yuv420p" \
  -c:v libx264 -crf 20 sdr.mp4

# The chain, read left to right:
#   zscale t=linear   decode PQ to linear light
#   npl=100           "nominal peak luminance" - the anchor
#   format=gbrpf32le  work in float; 8-bit here would band
#   zscale p=bt709    gamut map BT.2020 -> BT.709
#   tonemap=bt2390    the roll-off curve
#   desat=0           do NOT desaturate; bt2390 handles it
#   zscale t=bt709    encode the SDR transfer function
#   format=yuv420p    back to 8-bit 4:2:0

# Getting the ORDER wrong - tone mapping before linearising,
# or gamut mapping after encoding - produces plausible-looking
# output that is measurably wrong, which is worse than an
# obvious failure.

Check yourself

  • Name the three things HDR changes relative to SDR.
  • Explain why HDR is not "brighter everything", and where diffuse white should sit.
  • Distinguish PQ from HLG in terms of absolute versus relative, and say who uses each.
  • Explain why HDR needs 10 bits.
  • Say what MaxCLL and MaxFALL each describe and why MaxFALL protects the panel.
  • Name the components of HDR10 and say why it is the baseline.
  • Explain why static metadata means two TVs legitimately differ.
  • Compare clipping, Reinhard and BT.2390 roll-off as tone maps.
  • Explain why tone mapping must happen in linear light.
  • Say why naive HDR-to-SDR conversion looks washed out and what fixes it.
