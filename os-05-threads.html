Threads and threading models

A thread is an independent execution context sharing an address space with its siblings. That sharing is the whole point and the whole danger: communication is free, and so is corruption.

What is shared and what is not

A thread is a separate flow of execution sharing its address space with others. That sharing is the whole point and the whole difficulty: communication is free, and so is corrupting each other's data.

   ONE PROCESS, THREE THREADS

   ┌──────────────────────────────────────────────────────┐
   │  SHARED — one copy for the whole process              │
   │    text (code)                                        │
   │    data, bss, heap                                    │
   │    memory mappings                                    │
   │    file descriptor table                              │
   │    cwd, root, umask                                   │
   │    signal HANDLERS (the dispositions)                 │
   │    PID (tgid), UID/GID, namespaces, cgroups           │
   └──────────────────────────────────────────────────────┘
        │                  │                  │
   ┌────▼────┐        ┌────▼────┐        ┌────▼────┐
   │ thread 1│        │ thread 2│        │ thread 3│
   │ PRIVATE:│        │         │        │         │
   │  stack  │        │  stack  │        │  stack  │
   │  regs+PC│        │  regs+PC│        │  regs+PC│
   │  TID    │        │  TID    │        │  TID    │
   │  errno  │        │  errno  │        │  errno  │
   │  TLS    │        │  TLS    │        │  TLS    │
   │  sigmask│        │  sigmask│        │  sigmask│
   │  priority│       │         │        │         │
   └─────────┘        └─────────┘        └─────────┘

Note the asymmetry in signals: the HANDLER is shared, the MASK is
per-thread. That is a genuine source of confusion.
The trade

Threads communicate through ordinary memory — a pointer write is all it takes, at nanosecond cost. Processes must use IPC, which is safe but costs microseconds. Threads buy you cheap communication and pay for it with the entire class of data races, deadlocks and memory-ordering bugs from CA chapter 15.

The Linux model

Linux does not implement threads as a distinct kind of object. They are ordinary tasks that happen to share more than usual, which is a simpler model than most systems use and explains several of its behaviours.

/* In Linux, threads and processes are the SAME KERNEL OBJECT.
   Both are created by clone(); the flags decide what is shared. */

clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND |
      CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS, ...)
      /* ^ a THREAD: shares everything */

clone(SIGCHLD, ...)          /* == fork(): shares nothing */

/* So a "process" is a group of tasks with the same tgid. */
getpid()   /* returns tgid — the same for every thread */
gettid()   /* returns pid  — unique per thread          */

ls /proc/1234/task/          /* one directory per thread */
ps -L -p 1234                /* list threads             */
top -H                       /* per-thread view          */
Why this design

Because the kernel needs one scheduler, one context-switch path and one wait mechanism regardless of how much is shared, the sharing is expressed as flags rather than as a separate object type. Windows takes the other approach — EPROCESS owns ETHREADs — which matches intuition more closely at the cost of duplicating machinery.

Threading models

Threads can be mapped onto kernel-scheduled entities in more than one way, and the choice affects how a blocking call behaves and whether threads can genuinely run in parallel.

ModelMappingProperty
1:1 (kernel threads)Each user thread is one kernel threadTrue parallelism; blocking is fine; context switch costs a syscall. Linux, Windows, macOS all use this.
N:1 (green threads)Many user threads on one kernel threadVery cheap switching; one blocking call stops everything; no multicore. Historical.
M:NM user threads over N kernel threadsBest of both in theory; scheduler interaction is notoriously hard. Go's runtime does this well; Solaris and NPTL abandoned it.
Async / coroutinesCooperative, one OS thread per coreNo preemption, no locks needed within a task, but a blocking call stalls the whole executor
 
Why M:N mostly failed, and where it works

  The kernel scheduler and the user scheduler each make decisions
  without knowing the other's state. Classic failure: a user thread
  blocks in a syscall, taking its kernel thread with it, and the
  user scheduler cannot see that its worker vanished.

  Go succeeds because its runtime OWNS the blocking calls: every
  channel operation, network read and syscall goes through the
  runtime, which can park the goroutine and reuse the OS thread.
  That is only possible in a language with a controlled runtime.

  In C and C++ you get 1:1, and async is a library (io_uring,
  libuv, ASIO) that you must use consistently or not at all.

Creating threads

Creating a thread looks simple and has details that matter — what it runs, what it gets as an argument, how you wait for it, and what happens if you never do.

#include <pthread.h>

static void *worker(void *arg)
{
        int id = *(int *)arg;
        /* ... */
        return (void *)(intptr_t)result;
}

pthread_t t[4];
int ids[4];
for (int i = 0; i < 4; i++) {
        ids[i] = i;                    /* NOT &i — see below */
        if (pthread_create(&t[i], NULL, worker, &ids[i]) != 0)
                return -1;             /* returns errno, does NOT set it */
}
for (int i = 0; i < 4; i++) {
        void *ret;
        pthread_join(t[i], &ret);
}

/* The classic bug: passing &i, the LOOP VARIABLE. Every thread
   receives the same address, and reads whatever value it holds
   when the thread happens to run. Pass a distinct object per
   thread, or pass the value cast to intptr_t.               */
/* C11 threads — standard but thinly supported; pthreads remains
   the practical choice on POSIX.                              */
#include <threads.h>
thrd_create(&t, worker, arg);
thrd_join(t, &res);

/* Windows */
HANDLE h = CreateThread(NULL, 0, ThreadProc, param, 0, &tid);
WaitForSingleObject(h, INFINITE);
CloseHandle(h);
/* Prefer _beginthreadex in C code: it initialises the CRT's
   per-thread state (errno, strtok buffers). Raw CreateThread
   leaks that state and breaks some CRT functions.           */

Detached versus joinable

/* A joinable thread's exit status and stack are retained until
   someone joins it. Never joining leaks — the thread equivalent
   of a zombie process.                                        */

pthread_join(t, &ret);          /* wait and reclaim */

/* Or detach, if you never need the result: */
pthread_detach(t);
/* or at creation */
pthread_attr_t a;
pthread_attr_init(&a);
pthread_attr_setdetachstate(&a, PTHREAD_CREATE_DETACHED);
pthread_attr_setstacksize(&a, 256 * 1024);   /* default is 8 MB! */
pthread_create(&t, &a, worker, arg);
pthread_attr_destroy(&a);

/* Stack size matters: 8 MB of VIRTUAL address space per thread is
   fine on 64-bit, but on 32-bit it caps you at ~380 threads, and
   the guard page plus first-touch cost is real. Size it.      */

Thread-local storage

Sometimes each thread needs its own copy of a variable despite sharing the address space. There are several mechanisms for that, with different costs and different lifetimes.

_Thread_local int counter;          /* C11              */
thread_local int counter;            /* C23 / <threads.h> */
__thread int counter;                /* GCC extension     */
__declspec(thread) int counter;      /* MSVC              */

/* Each thread gets its own instance, with static duration.
   Used for: errno, per-thread caches, random number state,
   the current transaction or request context.            */

/* Dynamic TLS, when the key is not known at compile time: */
pthread_key_t key;
pthread_key_create(&key, destructor);   /* destructor runs at thread exit */
pthread_setspecific(key, ptr);
void *p = pthread_getspecific(key);

/* Cost: a TLS access is a few instructions via a dedicated register
   (TPIDR_EL0 on AArch64). In a shared library with dynamic TLS it
   can require a function call on first access per thread.       */

Thread safety and reentrancy

"Thread-safe" and "reentrant" are used interchangeably and mean different things. The distinction matters because a function can be one without being the other, and signal handlers need the stricter property.

PropertyMeans
Thread-safeCorrect when called concurrently from several threads — usually via internal locking
ReentrantCorrect when interrupted and called again, including from a signal handler. Stricter: implies no locks and no static state.
Async-signal-safeSafe to call from a signal handler. Stricter still — see C ch. 16.
 
/* NOT thread-safe: returns a pointer to static storage */
char *strtok(char *s, const char *d);
struct tm *localtime(const time_t *t);
char *strerror(int e);
struct passwd *getpwnam(const char *n);

/* the _r variants take caller-supplied storage instead */
strtok_r(s, d, &saveptr);
localtime_r(t, &tm_buf);
strerror_r(e, buf, sizeof buf);
getpwnam_r(n, &pwd, buf, sizeof buf, &result);

/* Writing thread-safe code: three strategies, in order of
   preference.                                            */

/* 1. NO SHARED STATE — by far the best. Give each thread its own
      data and combine at the end.                            */
struct alignas(64) partial { long sum; };   /* padded: CA ch. 15 */
struct partial results[NTHREADS];

/* 2. IMMUTABLE SHARED STATE — read-only after construction needs
      no synchronisation at all.                               */
static const struct config *cfg;   /* set once before threads start */

/* 3. EXPLICIT SYNCHRONISATION — locks, atomics, channels.
      Necessary, but every lock is a chance to deadlock.       */

Signals and threads

Signals and threads interact badly, because a signal is delivered to a process but must run on some thread. The rules are precise and the naive approach is almost always wrong.

/* The rules, which are unintuitive:
     · signal HANDLERS are per-PROCESS (shared)
     · signal MASKS are per-THREAD
     · a signal sent to the process is delivered to ANY ONE thread
       that has it unblocked — you do not choose which
     · pthread_kill() targets a specific thread                */

/* The standard pattern: block signals everywhere, handle them in
   one dedicated thread. This removes async-signal-safety from the
   problem entirely.                                            */
sigset_t set;
sigemptyset(&set);
sigaddset(&set, SIGINT);
sigaddset(&set, SIGTERM);
pthread_sigmask(SIG_BLOCK, &set, NULL);   /* BEFORE creating threads,
                                             so all inherit the mask */

/* ...then in one thread: */
int sig;
sigwait(&set, &sig);              /* synchronous, ordinary context —
                                     you may call anything here      */
shutdown_gracefully();

/* Linux alternative: signalfd() turns signals into a readable fd
   you can put in an epoll loop.                                */

Cancellation

Stopping a thread from outside is far harder than starting one, because it may be holding locks or halfway through modifying shared state. The mechanisms reflect that difficulty.

pthread_cancel(t);              /* request cancellation */

/* Deferred (the default): the thread dies at the next CANCELLATION
   POINT — a blocking call such as read, write, sleep, wait.  */
pthread_setcanceltype(PTHREAD_CANCEL_DEFERRED, NULL);

/* Asynchronous: dies immediately, anywhere. Almost never usable —
   it can die holding a lock or half-way through an allocation. */
pthread_setcanceltype(PTHREAD_CANCEL_ASYNCHRONOUS, NULL);

/* Cleanup handlers run on cancellation */
pthread_cleanup_push(unlock_it, &mutex);
        /* ... critical section ... */
pthread_cleanup_pop(1);         /* 1 = also run it on normal exit */
Prefer cooperative shutdown

pthread_cancel is difficult to use correctly: every resource must have a cleanup handler, and a cancellation point can appear inside library code you did not write. In practice, use an atomic flag plus a wakeup mechanism (a pipe, an eventfd, a condition variable) and let the thread exit its own loop. Windows does not offer cancellation at all — TerminateThread is documented as unsafe and should never be used.

Thread pools

Creating a thread per unit of work does not scale. A pool of workers pulling from a queue is the standard answer, and the details that matter are mostly about the queue rather than the threads.

Creating a thread per unit of work does not scale:

   thread creation      ~10-100 µs and ~8 MB of virtual address space
   context switching    grows with thread count
   cache footprint      each thread evicts the others
   scheduler overhead   O(log n) or worse per switch

A POOL fixes the count and queues the work:

   [ task queue ] ──► worker 1
                 ├──► worker 2
                 ├──► worker 3
                 └──► worker 4      (typically nproc, or nproc+1)

Sizing:
   CPU-bound      ≈ number of cores
   I/O-bound      more, since most workers are blocked
   mixed          separate pools, so slow I/O cannot starve compute

Beware of the work-queue lock becoming the bottleneck — that is
what work-stealing deques solve, and why Rayon, TBB and Go's
scheduler all use per-worker queues.

Debugging threaded programs

Threading bugs are timing-dependent and rarely reproduce on demand. These tools find them by checking the rules on every access rather than waiting for the unlucky interleaving.

# ThreadSanitizer — finds data races that have not yet manifested.
# The single most valuable tool here. ~5-15x slowdown.
gcc -fsanitize=thread -g prog.c && ./prog

# Helgrind / DRD — race and lock-order detection, no rebuild needed
valgrind --tool=helgrind ./prog

# gdb
info threads
thread 3
thread apply all bt          # backtrace of EVERY thread — the first
                             # thing to run on a deadlock

# what are the threads doing right now?
top -H -p PID
ps -L -o pid,tid,psr,pcpu,stat,wchan,comm -p PID
cat /proc/PID/task/TID/stack        # kernel-side, for D state

# contention
perf lock record ./prog && perf lock report
perf sched latency
