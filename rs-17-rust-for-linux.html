Rust in the Linux kernel

Since 6.1 the kernel accepts Rust drivers. This chapter is what that actually means: how the abstractions are built, what a Rust driver looks like beside the C one from Linux chapter 21, and an honest account of the state of it.

Why the kernel accepted it

The kernel had rejected new languages before. Understanding what changed is more instructive than the syntax, because the argument was about maintenance rather than elegance.

   THE ARGUMENT, made over several years and finally
   accepted:

     · roughly two thirds of kernel CVEs are memory safety
       issues - use-after-free, buffer overflow, race
       conditions on refcounts
     · drivers are the largest and least-reviewed part of the
       tree, and where most of those bugs live
     · the existing tooling - KASAN, lockdep, sparse, smatch,
       syzkaller (Linux chapter 34) - finds a great deal and
       still misses a great deal
     · a language that makes the class impossible is
       structurally better than one that makes it detectable

   THE CONDITIONS ATTACHED, which shape everything below:

     1. NO REWRITE. C remains the kernel's language; Rust is
        for NEW code, chiefly drivers.
     2. NO SECOND ABI. Rust code calls the existing C
        interfaces through bindings; it does not define a
        parallel kernel API.
     3. C DEVELOPERS ARE NOT REQUIRED TO LEARN RUST. If a C
        change breaks Rust code, fixing it is the Rust
        maintainers' problem.
     4. NO PANICS. A kernel panic is unacceptable; the
        abstractions must return errors instead.
     5. NO IMPLICIT ALLOCATION FAILURE. Kernel allocation can
        fail, so the standard library's infallible
        collections are not usable - the kernel has its own.

   TIMELINE:
     6.1 (2022)   the infrastructure merged
     6.3-6.7      abstractions grow; the first real drivers
     6.8+         Binder, the Nova GPU driver, PHY drivers,
                  null_blk
     6.12+        Rust is production-supported on several
                  architectures

   AND THE REALISTIC STATUS in 2026: several shipping
   drivers, an actively growing abstraction layer, and the
   Android Binder rewrite as the flagship. Not yet routine,
   and no longer experimental.

What differs from ordinary Rust

Kernel Rust is a restricted dialect, and the restrictions follow directly from constraints you already know from the Linux track.

/* --- 1. NO std, NO alloc-as-you-know-it --- */
    #![no_std]
/* The kernel provides its own `kernel` crate, containing the
   allocation types, synchronisation primitives and
   abstractions. `alloc`'s infallible Vec::push is unusable
   because kernel allocation FAILS.                       */

    use kernel::alloc::{flags, KVec};

    let mut v = KVec::new();
    v.push(42, flags::GFP_KERNEL)?;     // FALLIBLE - returns
                                        // Result

/* NOTE the GFP flag as a parameter - the allocation context
   question from Linux chapter 07 is in the type system,
   where the compiler can see it.

/* --- 2. NO PANICS --- */
    v[0]                        // indexing PANICS - avoid
    v.get(0).ok_or(EINVAL)?     // this instead
/* The kernel builds with panic=abort, and an abort is a
   kernel panic. Every abstraction is written to return
   Result rather than panic, and the same discipline applies
   to driver code (chapter 07).

/* --- 3. THE ERROR TYPE IS AN ERRNO --- */
    use kernel::error::{code::*, Result};

    fn probe(...) -> Result {
        if bad { return Err(EINVAL); }
        let p = ioremap(addr).ok_or(ENOMEM)?;
        Ok(())
    }
/* `Result` defaults to `Result<()>` with the kernel's Error
   type, which wraps a negative errno - so it converts
   directly at the C boundary.

/* --- 4. PINNED INITIALISATION --- */
    #[pin_data]
    struct MyDevice {
        #[pin] lock: SpinLock<State>,
        base: IoMem<0x1000>,
    }
/* Kernel objects frequently contain self-referential
   structures - a list_head that points at itself, a lock
   with an address registered with lockdep. They cannot be
   moved after initialisation. The `pin-init` crate makes
   in-place, fallible construction expressible, which is
   machinery ordinary Rust rarely needs (chapter 17's Pin,
   applied).

/* --- 5. NO EXTERNAL CRATES --- */
/* Everything must be in-tree. No crates.io, no Cargo
   dependency resolution - the kernel build system compiles
   the Rust files directly.                               */

A driver, beside the C version

Setting the two versions side by side is the clearest way to see what the safety guarantees actually buy in a real driver, and what they cost in ceremony.

// SPDX-License-Identifier: GPL-2.0
//! A minimal platform driver.

use kernel::{
    c_str, device::Core, of, platform, prelude::*,
    sync::aref::ARef,
};

struct MyDriver {
    pdev: ARef<platform::Device>,
    base: IoMem<0x1000>,
}

kernel::of_device_table!(
    OF_TABLE,
    MODULE_OF_TABLE,
    <MyDriver as platform::Driver>::IdInfo,
    [
        (of::DeviceId::new(c_str!("vendor,my-device")), ()),
    ]
);

impl platform::Driver for MyDriver {
    type IdInfo = ();
    const OF_ID_TABLE: Option<of::IdTable<Self::IdInfo>>
        = Some(&OF_TABLE);

    fn probe(
        pdev: &platform::Device<Core>,
        _info: Option<&Self::IdInfo>,
    ) -> Result<Pin<KBox<Self>>> {
        dev_info!(pdev.as_ref(), "probing\n");

        let base = pdev.io_request_and_map(0, c_str!("mydev"))?;

        let id = base.read32(REG_ID);
        if id != EXPECTED_ID {
            dev_err!(pdev.as_ref(), "bad id {:#x}\n", id);
            return Err(ENODEV);
        }

        KBox::pin_init(
            try_pin_init!(MyDriver {
                pdev: pdev.into(),
                base,
            }),
            GFP_KERNEL,
        )
    }
}

impl Drop for MyDriver {
    fn drop(&mut self) {
        // the equivalent of remove() - runs automatically
        dev_info!(self.pdev.as_ref(), "removing\n");
    }
}

kernel::module_platform_driver! {
    type: MyDriver,
    name: "my_driver",
    author: "Your Name",
    description: "Example platform driver",
    license: "GPL",
}

/* COMPARE THE C VERSION (Linux chapter 21) POINT BY POINT:

   · NO GOTO LADDER. The `?` operator returns early, and Drop
     releases everything acquired so far. The error path
     cannot be wrong because it is not written
     (Linux chapter 33's devm_, but from the language).

   · NO remove() FUNCTION. Drop is the teardown, and it runs
     in reverse construction order, automatically.

   · io_request_and_map RETURNS A TYPE whose Drop unmaps.
     Forgetting is impossible.

   · IoMem<0x1000> CARRIES THE SIZE IN THE TYPE, so
     read32(offset) is bounds-checked at COMPILE TIME where
     the offset is a constant.

   · THE ID TABLE is checked by the macro rather than being a
     hand-written array with a sentinel that can be omitted
     (Linux chapter 19's classic crash).

   · dev_err! is the same dev_err(), with format checking.

   THE C DRIVER IS ABOUT 90 LINES; THE RUST ONE IS ABOUT 60,
   AND THE 30 LINES REMOVED ARE THE ERROR PATHS - which is
   exactly where the bugs were.                          */
What the abstraction layer is doing

Between the Rust driver and the C kernel sits a hand-written layer of unsafe code that wraps each C interface in a safe Rust API — checking null, enforcing lifetimes, tying refcounts to Drop. That layer is the project: writing it correctly, for each subsystem, is most of the work and most of the review. The driver above is safe because someone proved the wrapper's invariants once (chapter 14).

The abstractions

The safe wrappers are where the real work is: each one takes a C API with rules enforced by convention and re-expresses those rules as something the compiler checks.

/* --- SYNCHRONISATION, with the guard pattern --- */
    use kernel::sync::{Mutex, SpinLock, new_mutex};

    #[pin_data]
    struct Shared {
        #[pin] data: Mutex<State>,
    }

    let guard = shared.data.lock();
    guard.field = 5;                    // the guard DEREFS to
                                        // State
    // unlocked when the guard drops - no unlock to forget

/* THE TYPE SYSTEM ENFORCES what lockdep checks at run time
   in C (Linux chapter 12): you cannot touch the data without
   the guard, and the guard cannot outlive the lock.

/* --- REFERENCE COUNTING --- */
    use kernel::sync::aref::ARef;

    let dev: ARef<Device> = pdev.into();
/* ARef is a refcounted reference to a kernel object whose
   Drop calls put_device(). The get/put imbalance that
   leaks a device or frees it early (Windows chapter 04 has
   the same failure mode) is not expressible.

/* --- MMIO --- */
    let base: IoMem<0x1000> = pdev.io_request_and_map(0,
                                        c_str!("mydev"))?;
    let v = base.read32(0x04);          // compile-time bounds
                                        // check
    base.write32(0x08, value);
    base.try_read32(offset)?;           // runtime check, for
                                        // a dynamic offset
/* Volatile by construction, sized by the type, and the
   mapping released on Drop.

/* --- WORK QUEUES, TIMERS, WAIT QUEUES --- */
    use kernel::workqueue::{self, Work, WorkItem};
    use kernel::time::{Delta, Instant};
    use kernel::sync::CondVar;

/* --- CHAR DEVICES and file operations --- */
    use kernel::miscdevice::{MiscDevice, MiscDeviceOptions};

    #[vtable]
    impl MiscDevice for MyDevice {
        type Ptr = Pin<KBox<Self>>;

        fn open(_file: &File, _misc: &MiscDeviceRegistration<Self>)
                -> Result<Self::Ptr> { ... }

        fn ioctl(me: Pin<&Self>, _file: &File,
                 cmd: u32, arg: usize) -> Result<isize> {
            match cmd {
                MY_IOCTL_GET => { ... }
                _ => Err(ENOTTY),
            }
        }
    }

/* --- USER MEMORY, where the type system earns its keep --- */
    use kernel::uaccess::{UserSlice, UserSliceReader};

    fn read_from_user(ptr: UserPtr, len: usize) -> Result<KVec<u8>> {
        let mut reader = UserSlice::new(ptr, len).reader();
        let mut buf = KVec::with_capacity(len, GFP_KERNEL)?;
        reader.read_all(&mut buf, GFP_KERNEL)?;
        Ok(buf)
    }
/* A UserPtr is a DISTINCT TYPE from a kernel pointer. You
   cannot dereference it; you must go through the checked
   readers. The `__user` annotation that sparse checks in C
   (Linux chapter 09) is a real type here, enforced by the
   compiler rather than by an optional static analyser.  */

Building it

Getting a Rust-enabled kernel to build has a few specific requirements, and the version coupling is tighter than most people expect.

# --- PREREQUISITES ---
    rustup override set $(scripts/min-tool-version.sh rustc)
    rustup component add rust-src
    cargo install --locked bindgen-cli
    rustup component add clippy rustfmt

# --- CHECK the toolchain is acceptable ---
    make LLVM=1 rustavailable
    # prints exactly what is missing if anything is

# --- CONFIGURE ---
    make LLVM=1 menuconfig
    #   General setup ---> Rust support   [*]
    #   (needs CONFIG_MODVERSIONS=n on some versions)

# --- BUILD ---
    make LLVM=1 -j$(nproc)
    make LLVM=1 rust-analyzer        # generates
                                     # rust-project.json for
                                     # IDE support

# --- THE SAMPLES, which are the best documentation ---
    samples/rust/rust_minimal.rs
    samples/rust/rust_print.rs
    samples/rust/rust_misc_device.rs
    samples/rust/rust_driver_platform.rs
    samples/rust/rust_driver_pci.rs

# --- THE SOURCE TO READ ---
    rust/kernel/            the abstraction layer
    rust/bindings/          bindgen output for the C headers
    rust/macros/            #[vtable], module!, pin_data
    Documentation/rust/     coding guidelines and the design
                            rationale

# --- WRITING A DRIVER ---
    drivers/foo/foo.rs
    # in the Makefile:
    obj-$(CONFIG_FOO) += foo.o
    # in Kconfig:
    config FOO
        tristate "Foo driver"
        depends on RUST

# LLVM=1 IS EFFECTIVELY REQUIRED: rustc uses LLVM, and mixing
# GCC-compiled C with LLVM-compiled Rust works but is less
# well tested, particularly for LTO.

An honest assessment

An assessment of where this actually stands, separated from both the enthusiasm and the objections — which is harder to find than it should be.

/* WHAT WORKS WELL TODAY:
     · character devices and misc devices
     · platform and PCI drivers
     · the synchronisation abstractions - Mutex, SpinLock,
       CondVar, ARef
     · allocation with proper failure handling
     · Binder (Android's IPC) - the largest Rust component in
       the kernel, and in production on millions of devices
     · the Nova GPU driver and several network PHY drivers

/* WHAT IS STILL THIN:
     · many subsystems have no abstractions yet - writing a
       driver for one means writing the wrapper too, which is
       the hard part
     · filesystems, block layer, and much of networking
     · documentation, compared with the C side
     · the abstraction API changes between releases, so
       out-of-tree Rust drivers churn more than C ones

/* THE POLITICAL SITUATION, stated neutrally: some
   maintainers welcome it and some do not, and the "no C
   developer is required to learn Rust" rule means the Rust
   side absorbs the maintenance cost of C changes. That
   arrangement has produced friction in specific subsystems.
   It has also produced shipping code.

/* WHAT IT MEANS FOR YOU:

     LEARNING IT: worthwhile. The abstractions are a
     well-written example of the safe-wrapper discipline
     (chapter 14), and reading rust/kernel/ teaches both Rust
     and the kernel.

     WRITING A DRIVER TODAY: reasonable IF your subsystem has
     abstractions. Check rust/kernel/ first. If it does not,
     you are writing the abstraction layer, which is a much
     larger project and needs to be upstreamed to be useful.

     FOR A PRODUCT: viable for Android-adjacent work, and
     early for most other things. The C path is still the
     default, and choosing Rust should be a decision with a
     reason rather than a preference.

     AND THE DIRECTION IS CLEAR: the trend across Android,
     Windows, and now Linux is that new systems code in
     memory-unsafe languages increasingly needs
     justification. That is worth positioning for regardless
     of what you write this year.                        */

How it shows up

SymptomCause and fix
make rustavailable failsIt names exactly what is missing — usually the rustc version or rust-src
"Rust support" not offered in menuconfigToolchain check failed, or a conflicting config option
Abstraction does not exist for your subsystemYou must write and upstream it — check rust/kernel/ first
Code breaks on a kernel upgradeThe abstraction API is not stable — expect churn
Allocation compiles but should notUse the kernel's fallible KVec, not alloc's
A panic reaches the kernelAn unwrap or an index — use get and ?
"cannot move out of pinned value"Kernel objects are pinned — use pin_init
Cannot dereference a user pointerCorrect — go through UserSlice
Symbol not found at module loadThe C symbol is not exported, or not bound in rust/bindings
Building with GCC produces odditiesUse LLVM=1

A project that uses all of this

OP-TEE chapter 25 builds a signing service in which every layer is Rust: a user-mode driver, a kernel module of the kind this chapter describes, and a trusted application in the secure world. It is also an honest look at the rough edges — the kernel module has to carry its own FFI bindings, because there is no kernel::tee abstraction upstream, and the MiscDevice and UserSlice APIs used here are still moving between releases.
