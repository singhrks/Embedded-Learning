The serial console, and why you need one

SSH requires a booted kernel, a configured network and a running sshd. The serial console requires none of those, which is precisely why it is the tool you need on the days everything else is broken. Fit it before you need it.

What it gives you that SSH cannot

   WHEN EACH ONE WORKS

                        bootloader  kernel   kernel   userspace
                        messages    early    panic    running
   -----------------------------------------------------------
   HDMI + keyboard         yes       yes      yes       yes
   SSH                      no        no       no       yes
   SERIAL CONSOLE          YES       YES      YES       YES

   The serial console is the ONLY thing in that table that
   is both complete and headless. It sees:

     - the EEPROM bootloader's own diagnostics, before any
       kernel exists (BOOT_UART=1, chapter 03)
     - firmware messages and device tree errors
     - every kernel message from the very first line,
       including the ones that scroll past before rsyslog
       starts and are therefore NOT in journalctl
     - a kernel panic, with the stack trace
     - the point at which a boot HANGS - which is invisible
       by every other means

   AND IT IS BIDIRECTIONAL: you get a login prompt, so a Pi
   with no network at all is still fully usable.

   THE RULE: any time you are about to say "it just does not
   boot and I cannot see why", you needed this an hour ago.

Wiring it

   YOU NEED A 3.3 V USB-TO-SERIAL ADAPTER. CP2102, CH340,
   FT232 - any of them. A 5 V adapter will damage the Pi.

   PI 4 (and Pi 5, if using the 40-pin header):

     Pi pin 6  (GND)  ------- GND on adapter
     Pi pin 8  (GPIO14, TXD) --- RX on adapter
     Pi pin 10 (GPIO15, RXD) --- TX on adapter

   TX GOES TO RX. This is the single most common mistake:
   the Pi's transmit line must reach the adapter's receive
   line. Crossed, not straight through.

   DO NOT CONNECT THE ADAPTER'S 5 V OR 3.3 V PIN. The Pi has
   its own supply; back-feeding it through the serial
   adapter powers the board partially and produces bizarre,
   intermittent failures.

     +-----------+                    +------------+
     |  Pi       |                    |  USB-TTL   |
     |  pin 6  --|--------------------|-- GND      |
     |  pin 8  --|------\    /--------|-- RX       |
     |  pin 10 --|-------\  /---------|-- TX       |
     |           |        \/          |  (5V/3V3   |
     |           |        /\          |   unused)  |
     +-----------+                    +------------+

   PI 5 - use the dedicated UART connector instead. It is a
   3-pin JST-SH header near the USB-C socket, labelled, and
   it does not consume any of your 40-pin GPIO. The Pi 5
   also works with the header wiring above, but the
   dedicated connector is the reason to prefer a Pi 5 for
   this kind of work.

   THE OFFICIAL DEBUG PROBE is a Pi-branded USB adapter with
   both a UART cable and an SWD cable, pre-wired for the Pi 5
   connector. It removes the wiring mistakes entirely and is
   worth the money if you do this often.

Enabling it

# On the boot partition (chapter 03), in config.txt:
enable_uart=1

# On a Pi 4/5 this also pins the core clock, because the
# mini-UART's baud rate is derived from it and would
# otherwise drift as the CPU scales. Setting enable_uart=1
# is what makes the console reliable rather than
# occasionally garbled.

# Check cmdline.txt contains the console directive. It is
# normally there by default:
console=serial0,115200 console=tty1

# "serial0" is an ALIAS the device tree resolves to whichever
# UART is the primary console on this board. Prefer it over
# ttyAMA0 or ttyS0, which differ between models:
$ ls -l /dev/serial*
lrwxrwxrwx 1 root root 7 ... /dev/serial0 -> ttyAMA10
lrwxrwxrwx 1 root root 7 ... /dev/serial1 -> ttyAMA0

# TWO UARTS, and the distinction bites on Pi 4 and earlier:
#
#   PL011  a real UART with a FIFO and its own clock.
#          Reliable at any baud rate.
#   mini-UART  a cut-down block whose baud rate derives from
#          the VPU core clock. Garbles output when the clock
#          scales, unless the clock is pinned.
#
# On Pi 3/4, Bluetooth claims the PL011 by default and the
# console gets the mini-UART. To give the console the good
# UART instead:
dtoverlay=disable-bt           # frees PL011, disables BT
# or
dtoverlay=miniuart-bt          # BT moves to the mini-UART

# Then enable the login service (usually already enabled):
$ sudo systemctl enable --now serial-getty@ttyAMA0.service

# And for the bootloader's own output, set it in the EEPROM
# (chapter 03) - this is separate from anything in Linux:
$ sudo -E rpi-eeprom-config --edit
BOOT_UART=1

Connecting from the host

# The adapter appears as a tty. Find it:
$ ls /dev/ttyUSB* /dev/ttyACM*          # Linux
$ ls /dev/cu.usbserial-*                # macOS
# Windows: Device Manager, or a COMn port

# Add yourself to the group ONCE, then log out and back in.
# Otherwise you will use sudo forever for no reason:
$ sudo usermod -aG dialout $USER

# --- picocom: the best default. Ctrl-A Ctrl-X to exit. ---
$ picocom -b 115200 /dev/ttyUSB0

# --- minicom: more features, awkward defaults ---
$ minicom -D /dev/ttyUSB0 -b 115200

# --- screen: always installed, and traps people ---
$ screen /dev/ttyUSB0 115200
#   exit with Ctrl-A then k, then y. NOT Ctrl-C, which sends
#   the interrupt to the Pi. Closing the terminal window
#   leaves screen holding the port, and the next connection
#   fails with "device is busy" - the classic confusion.

# --- tio: modern, reconnects automatically ---
$ tio -b 115200 /dev/ttyUSB0
#   Reconnects when the Pi reboots and the USB device
#   disappears and returns. For a board you power-cycle
#   constantly this is the nicest of the four.

# ALWAYS LOG THE SESSION. When something scrolls past
# during a failure you want the text, not your memory:
$ picocom -b 115200 -g ~/pi-console-$(date +%F).log /dev/ttyUSB0
$ tio -b 115200 -l -L /dev/ttyUSB0
115200 8N1, no flow control

Those are the settings, and the Pi does not use hardware flow control on the console by default. If you see correctly-timed but garbled characters, the baud rate is wrong or the mini-UART's clock is drifting; if you see nothing at all, it is wiring (TX/RX swapped) or enable_uart=1 missing. Those two symptoms distinguish the two failure classes immediately, which is why bus chapter 02's framing material is worth having read.

What to do with it

# 1. WATCH A BOOT. Attach the console, then power on. You
#    will see, in order: bootloader diagnostics, firmware
#    messages, the kernel's first lines, driver probes, then
#    systemd. The point where it stops is the bug.

# 2. CATCH A PANIC. A kernel oops prints here and nowhere
#    else if the box is wedged. Keep the log.

# 3. BREAK INTO A HUNG SYSTEM with SysRq. Works when the
#    kernel is alive but userspace is unusable:
$ echo 1 | sudo tee /proc/sys/kernel/sysrq      # enable

#    Then over the serial line send a BREAK, followed by
#    the key. In picocom: Ctrl-A Ctrl-\  sends a break.
#      b  reboot immediately
#      s  sync filesystems
#      u  remount read-only
#      e  SIGTERM to everything except init
#      i  SIGKILL to everything except init
#      w  dump blocked tasks   <- the useful one for hangs
#      t  dump all task states
#
#    "Raising Elephants Is So Utterly Boring" - the safe
#    emergency shutdown order: unRaw, tErminate, kIll,
#    Sync, Unmount, reBoot.

# 4. RECOVER A BOARD WITH NO NETWORK. Log in over serial and
#    fix the network configuration you just broke.

# 5. SINGLE-USER MODE for a root filesystem problem. Add to
#    cmdline.txt on the boot partition from your host:
init=/bin/sh
#    You get a shell with no services at all. Remount rw:
#      mount -o remount,rw /

How it shows up

SymptomCause
Nothing at all on the consoleTX/RX not crossed, or enable_uart=1 missing
Garbled characters at the right rateBaud mismatch, or the mini-UART's clock drifting
Output works, typing does nothingOnly one direction wired; check the other line
Console garbles only under CPU loadmini-UART with an unpinned core clock
Bluetooth stopped workingdisable-bt overlay — use miniuart-bt instead
Board behaves oddly, powers partiallyAdapter's 5 V or 3.3 V pin connected — remove it
"Device is busy" on connectA previous screen session still holds the port
Permission denied on /dev/ttyUSB0Not in the dialout group
Kernel messages present, bootloader ones absentBOOT_UART=1 not set in the EEPROM
Ctrl-C kills your terminal instead of the Pi's processUsing screen; its exit key is Ctrl-A k

Check yourself

  • Give three things a serial console shows that SSH cannot.
  • State the three wires and which two must be crossed.
  • Explain why the adapter's power pin must be left unconnected.
  • Say what enable_uart=1 does beyond enabling the UART.
  • Distinguish the PL011 from the mini-UART and say which the console should use.
  • Explain what serial0 is and why it is preferable to ttyAMA0.
  • Give the settings: baud, data bits, parity, stop bits, flow control.
  • Distinguish the symptom of wrong wiring from the symptom of a wrong baud rate.
  • Describe how to dump blocked tasks on a hung system over serial.
  • Explain how to get a shell when the root filesystem will not mount normally.
