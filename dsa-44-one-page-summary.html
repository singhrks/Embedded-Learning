Everything in this track compressed to what you would want in front of you the evening before an interview. If a line here does not immediately make sense, that is the chapter to reopen — and if they all do, close the laptop.

Read the constraints first — they name the algorithm

Before thinking about the problem, look at the input size. It eliminates most of the solution space for free, and it is the single fastest way to know what you are aiming at.

n up toAffordableWhich usually means
10–12O(n!)Permutations — backtracking
15–20O(2ⁿ)Subsets, or bitmask DP
100–500O(n³)Floyd–Warshall, interval DP
2,000–5,000O(n²)DP on two sequences, or all pairs
10⁵–10⁶O(n log n)Sorting, heap, binary search, Fenwick
10⁷ and aboveO(n) or O(log n)One pass, two pointers, or maths

The inference runs both ways. An n of 20 with a "find the minimum cost" question is almost certainly bitmask DP, and an n of 10⁹ with any question at all is binary search on the answer or a closed form — you cannot even read the input.

The templates worth having in muscle memory

Four pieces of code account for a startling share of interview questions, and each has exactly one detail that people get wrong under pressure. Write them until the detail is automatic.

   BINARY SEARCH - the half-open form that cannot loop
   forever:

     let lo = 0, hi = n;            // hi is EXCLUSIVE
     while (lo < hi) {
         const mid = lo + ((hi - lo) >> 1);
         if (ok(mid)) hi = mid;     // keep mid as a candidate
         else         lo = mid + 1; // discard mid
     }
     return lo;                     // first index where ok

   THE DETAIL: every branch must strictly shrink the range.
   `hi = mid` is safe only because the other branch is
   `lo = mid + 1`.

   ---------------------------------------------------------

   SLIDING WINDOW - grow right, shrink left:

     let l = 0;
     for (let r = 0; r < n; r++) {
         add(a[r]);
         while (invalid()) { remove(a[l]); l++; }
         best = Math.max(best, r - l + 1);
     }

   THE DETAIL: `while`, not `if`. One removal may not be
   enough to restore the invariant.

   ---------------------------------------------------------

   BFS ON A GRID - mark when you ENQUEUE:

     const q = [start]; seen.add(start);
     while (q.length) {
         const [x, y] = q.shift();
         for (const [nx, ny] of neighbours(x, y)) {
             if (!inBounds(nx, ny) || seen.has(key)) continue;
             seen.add(key);          // HERE, not on dequeue
             q.push([nx, ny]);
         }
     }

   THE DETAIL: marking on dequeue lets the same cell enter
   the queue many times, and turns O(n) into something much
   worse.

   ---------------------------------------------------------

   BACKTRACKING - choose, recurse, undo:

     path.push(choice);
     recurse(next);
     path.pop();            // the undo is not optional

   THE DETAIL: push a COPY into the results, not the live
   array - otherwise every answer ends up empty.

Ten rules that prevent most wrong answers

These are the failures that show up again and again in the "How it shows up" tables across the track, collected in one place.

RuleBecause
Say the approach out loud before writing anythingThe interviewer is scoring the reasoning, and a wrong plan is cheap to fix before it is code
State the complexity of the brute force firstIt proves you understood the problem, and it sets up why the real solution is better
Check the empty, single and all-equal inputsThey break more submissions than large inputs do
Decide the tie-break before writing the comparatorUnspecified ties are where "correct on small inputs" comes from
Never sort when the answer needs original indicesSorting destroys exactly the information you must return
Copy before mutating a caller's arrayAn invisible side effect that passes your tests and fails theirs
Use lo + ((hi - lo) >> 1) for the midpointIn fixed-width languages (lo + hi) / 2 overflows
Try to break a greedy rule before implementing itTwo minutes now against fifteen wasted
Reduce modular values after every multiplyOverflow happens before the % runs, not after
Say what you would test if you had more timeIt is free marks and almost nobody does it

The last week

Revision at this stage is about retrieval, not coverage. Re-reading is the least effective thing you can do with the time.

   SEVEN DAYS OUT:

     · re-solve, from a blank editor, one problem per
       pattern you feel least sure about. Blank editor is
       the whole point - recognising a solution is not the
       same skill as producing one.
     · write the four templates above from memory, once a
       day, until the details stop needing thought.

   TWO DAYS OUT:

     · do one full mock under time, out loud, with a timer.
       Talking while thinking is a separate skill and it is
       the one that degrades first under stress.
     · re-read only the "How it shows up" tables. They are
       the highest-density revision in this track.

   THE NIGHT BEFORE:

     · this page.
     · sleep. A tired candidate makes exactly the errors in
       the table above, and no amount of extra practice
       compensates.

Check yourself

  • Given n ≤ 20, name the two algorithm families that fit.
  • Given n = 10⁹, say what the solution cannot possibly do.
  • Recite the pattern for "minimum largest value" without hesitating.
  • Write the half-open binary search from memory and say why it terminates.
  • Write the sliding window and explain why the inner loop is a while.
  • Say when a BFS marks a cell as seen, and what breaks otherwise.
  • Give the three lines of backtracking and the copy that must happen.
  • Name five of the ten rules without looking.
  • Give the first move for "wrong only on large inputs".
  • Say what beats a half-finished optimal solution, and why.
