Barriers: DMB, DSB and ISB

Three instructions that constrain what the hardware may reorder. They look interchangeable and are not: each solves a different problem, and choosing the wrong one gives you code that is either incorrect or needlessly slow.

The distinction in one line each

DMB orders. DSB waits. ISB re-fetches.

DMB says "these accesses must become visible in this order" but does not stall the pipeline. DSB says "nothing proceeds until all of this has actually finished". ISB says "throw away everything already fetched and start again", which is what makes a configuration change take effect.

Domain and direction

A barrier instruction takes a qualifier saying how far it applies and to which direction of access. Choosing the narrowest one that is still correct is where most of the available performance in this area lives.

   DMB / DSB  <domain><direction>

   DOMAIN — how far the ordering propagates (chapter 19)
      sy    full system — widest, includes Device memory and
            non-coherent masters
      ish   inner shareable — the SMP default
      osh   outer shareable
      nsh   non-shareable — this PE only

   DIRECTION — which accesses are constrained
      (none)  both loads and stores
      ld      loads only — orders prior LOADS against later
              loads and stores
      st      stores only — orders prior STORES against later
              stores

   Combined:
      dmb ishst    prior stores visible before later stores
                   → the PRODUCER side of a message-passing pattern
      dmb ishld    prior loads complete before later accesses
                   → the CONSUMER side
      dmb ish      full ordering within the inner domain
      dsb sy       everything, everywhere, completed
      dsb nshst    local stores completed — boot code

   Narrower is cheaper. `dmb ishst` is materially faster than
   `dmb sy`, and in a hot path the difference is measurable.

DMB in practice

The most common barrier, and the one to reach for when you need two memory accesses to be observed in a particular order by someone else.

/* The message-passing pattern (chapter 20), fixed with DMB: */

/* producer */                      /* consumer */
buffer[0] = 42;                     while (flag == 0)
dmb ishst;   /* stores ordered */           ;
flag = 1;                           dmb ishld;   /* loads ordered */
                                    use(buffer[0]);

/* Note both sides need one. Ordering the producer's stores does
   not stop the consumer's loads being reordered.            */

/* What DMB does NOT do:
     · it does not FLUSH anything — it constrains ORDER only
     · it does not wait for completion; a store may still be in
       a buffer, just guaranteed to leave before the next one
     · it does not affect instruction fetch
     · it does nothing for Device-memory-to-DMA handoff, where
       you need completion — use DSB                        */

Prefer acquire/release

Rather than placing separate barriers, the architecture lets ordering be attached to the load or store itself. This is both cheaper and harder to get wrong, and it should be your default.

/* Ordering attached to the ACCESS is cheaper than a standalone
   barrier, because the core can keep other work in flight. */

/* with barriers */                 /* with ordered accesses */
str  w1, [x0]                       str  w1, [x0]
dmb  ishst                          stlr w2, [x3]      ← one instruction
str  w2, [x3]

ldr  w1, [x0]                       ldar w1, [x0]      ← one instruction
dmb  ishld
ldr  w2, [x3]                       ldr  w2, [x3]

/* LDAR — load-acquire:  no LATER access may move before it
   STLR — store-release: no EARLIER access may move after it

   These are what C11's memory_order_acquire/release compile to,
   and what Linux's smp_load_acquire/smp_store_release emit.

   Rule of thumb: use acquire/release for synchronisation between
   threads; reserve explicit DMB for cases the ordered accesses
   cannot express, and DSB for completion.                  */

DSB: when you need completion, not order

Where a DMB orders accesses, a DSB waits for them to actually finish. The difference matters whenever the next thing you do depends on the previous operation having completed, not merely being ordered.

/* DSB is required whenever a LATER action depends on a prior
   operation having actually FINISHED — not merely being ordered. */

/* 1. After cache or TLB maintenance (chapters 15, 18) */
        dc      cvac, x0
        dsb     ish              /* the writeback has COMPLETED */
        /* only now is it safe to start the DMA */

        tlbi    vae1is, x0
        dsb     ish              /* the invalidate has completed
                                    on every core */
        isb

/* 2. Before starting DMA */
        /* fill the buffer... */
        dsb     sy               /* the data has reached the point
                                    the device will read from */
        writel(START, regs);

/* 3. Before WFI / WFE */
        dsb     sy               /* outstanding transactions must
                                    complete before we sleep, or
                                    they may never do              */
        wfi

/* 4. Before writing SCTLR to enable the MMU (chapter 12) */
        dsb     ish              /* the page tables must be visible
                                    to the table walker */
        msr     sctlr_el1, x0
        isb

/* 5. Before a reset or power-down */
        dsb     sy
DSB is expensive

It stalls the core until every outstanding memory transaction has completed — which on a large SoC means waiting for the far side of the interconnect. Hundreds of cycles is normal. A dsb sy in a hot loop is a serious performance bug, and using dsb where dmb would do is the most common form of that mistake.

ISB: making changes take effect

Changing how the processor itself behaves — enabling the MMU, switching translation tables — is not visible to instructions already in flight. An ISB is what makes such a change take effect.

/* ISB flushes the pipeline. Instructions after it are re-fetched
   and re-decoded under the CURRENT context.                  */

/* Required after: */

/* 1. Any system register write affecting fetch, translation or
      permissions (chapter 06) */
        msr     sctlr_el1, x0
        isb

        msr     ttbr0_el1, x0
        isb

        msr     vbar_el1, x0
        isb

/* 2. Modifying instructions (chapter 18) */
        dc      cvau, x0
        dsb     ish
        ic      ivau, x0
        dsb     ish
        isb                      /* THIS core may have prefetched
                                    the old bytes */

/* 3. After changing an exception level's configuration and before
      relying on it */

/* ISB does NOT order memory accesses. It is not a substitute for
   DMB, and DMB is not a substitute for it. They constrain
   different machinery: DMB the memory system, ISB the
   instruction pipeline.                                     */

The compiler barrier

Hardware barriers do not stop the compiler reordering your code, and the compiler is perfectly entitled to. Both kinds of barrier are needed, and confusing them produces code that breaks only at higher optimisation levels.

/* Hardware barriers do nothing about COMPILER reordering. A
   compiler that hoists a load out of a loop has already broken
   your code before any instruction executes.               */

#define barrier()  asm volatile("" ::: "memory")

/* The "memory" clobber tells GCC: this statement may read or
   write any memory, so do not cache values in registers across
   it and do not reorder memory accesses past it. It emits NO
   instruction.                                              */

/* Linux's READ_ONCE and WRITE_ONCE are built on this idea: */
#define READ_ONCE(x)      (*(const volatile __typeof__(x) *)&(x))
#define WRITE_ONCE(x, v)  (*(volatile __typeof__(x) *)&(x) = (v))

/* They prevent the compiler from:
     · tearing a single access into several
     · fusing several accesses into one
     · inventing accesses that were not in the source
     · caching the value in a register across a loop

   They emit NO hardware barrier. Every shared variable needs at
   least this, even one you consider "just a flag".         */

/* Every real barrier macro includes the compiler barrier: */
#define smp_mb()   asm volatile("dmb ish" ::: "memory")
/*                                          ^^^^^^^^ essential */

The Linux barrier vocabulary

Linux does not ask driver and kernel code to write raw DMB/DSB instructions with a hand-picked domain — it defines a small set of portable macros named after what you are ordering against, and each architecture backend picks the cheapest instruction sequence that satisfies it. That indirection is why the same driver source compiles correctly on ARM, x86 and RISC-V despite their very different native barrier instructions. Reading the table as three groups helps: smp_* macros order CPU against CPU and compile to the narrow inner-shareable domain from chapter 19; mb()/dma_* macros exist for talking to devices and DMA, and reach further because a device is not necessarily inner-shareable; and smp_store_release/smp_load_acquire are the publish/consume pairing from chapter 20, spelled the way kernel code actually writes it.

MMIO ordering

Device registers have their own ordering requirements, and driver code has conventions for expressing them. These are the patterns that appear throughout real drivers.

/* Device memory accesses are ordered relative to EACH OTHER
   (chapter 11), but NOT relative to Normal memory accesses.
   The DMA handoff is exactly that combination:              */

        memcpy(dma_buf, data, len);     /* Normal memory */
        dsb     sy                       /* MUST complete first */
        writel(START, regs + CTRL);      /* Device memory */

/* Linux's accessors handle this for you: */
        writel(v, addr);          /* includes a barrier before the
                                     write so prior Normal writes
                                     are visible                  */
        readl(addr);              /* includes a barrier after      */

        writel_relaxed(v, addr);  /* NO barrier — use when you have
                                     already ordered things, e.g.
                                     several register writes in a
                                     row where only the last needs
                                     ordering                      */

/* The common optimisation: use _relaxed for a burst of register
   writes, then a single full writel() or an explicit barrier at
   the point where ordering actually matters. This can be a
   significant win in a hot driver path.                     */

/* And the POSTED WRITE trap: a write to Device-nGnRE may be
   acknowledged before it reaches the device. To be certain it
   has landed — before releasing a reset, say — you must READ
   BACK from the same peripheral:                            */
        writel(v, regs + CTRL);
        (void)readl(regs + CTRL);        /* forces completion */

Cost, and choosing

Barriers are not free, and their cost varies by type and by how busy the system is. This is what makes the difference between choosing correctly and choosing defensively.

Approximate, and highly implementation dependent — but the
ORDERING is reliable:

   barrier()            0 cycles      (no instruction)
   ldar / stlr          few cycles    (attached to the access)
   dmb ishst/ishld      ~5-20         (one direction, narrow)
   dmb ish              ~10-30
   dmb sy               ~20-50
   dsb ish              ~20-100       (waits for completion)
   dsb sy               ~50-500+      (waits for the whole system)
   isb                  ~10-30        (pipeline flush)

DECISION PROCEDURE:

   Ordering two data accesses between threads?
        → acquire/release, or the narrowest DMB

   Need something to have COMPLETED before proceeding?
        → DSB, narrowest domain that is correct

   Changed a system register or wrote instructions?
        → ISB

   Only worried about the compiler?
        → barrier(), READ_ONCE, WRITE_ONCE

   Handing a buffer to a device?
        → DSB, and use the DMA API which does it for you
