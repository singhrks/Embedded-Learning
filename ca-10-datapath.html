The datapath and the control unit

This is the chapter where a processor stops being a metaphor. Using only the blocks from chapters 05 and 06, we build a machine that actually executes instructions — and every later idea (pipelining, forwarding, speculation, exceptions) is a modification of this one drawing.

The problem

You have an ALU, a register file, muxes, decoders and memory. You have an instruction encoding from chapter 09. How do you wire them together so that fetching a 32-bit word from memory causes the right thing to happen?

The answer splits cleanly into two halves, and keeping them separate is the single most useful idea here:

Datapath and control

The datapath is where values flow: registers, ALU, memory ports, and the muxes that route between them. It is the plumbing, and it is the same for every instruction.

The control unit decides, for the current instruction, how every mux is set and which units are enabled. It is combinational logic driven by the opcode — the decoder from chapter 05.

The datapath makes everything possible; the control unit makes one thing happen.

A single-cycle datapath

Start with the simplest working design: every instruction completes in exactly one clock cycle.

Walking three instructions through it

1.  ADD X0, X1, X2         register-to-register arithmetic

    PC → I-memory → instruction
    decode: opcode = ADD, Rn = 1, Rm = 2, Rd = 0
    register file: read X1 and X2
    ALU-src mux: select the REGISTER path (not the immediate)
    ALU: op = add
    mem-write: OFF, mem-read: OFF        ← data memory unused
    write-back mux: select the ALU RESULT
    register file: write X0
    next-PC mux: select PC + 4

2.  LDR X0, [X1, #16]      load

    decode: opcode = LDR, Rn = 1, Rd = 0, immediate = 16
    register file: read X1
    ALU-src mux: select the IMMEDIATE
    ALU: op = add           ← the ALU computes the ADDRESS, not a value
    data memory: read at that address
    write-back mux: select the MEMORY DATA
    register file: write X0
    next-PC mux: PC + 4

3.  CBZ X0, label          branch if zero

    decode: opcode = CBZ, Rn = 0, offset = label - PC
    register file: read X0
    ALU: compare against zero → sets the Z flag
    register write: OFF     ← nothing is written back
    next-PC mux: select the BRANCH TARGET if Z, else PC + 4

Notice that the ALU did three different jobs: arithmetic, address computation, and comparison. That reuse is deliberate and is why the ALU sits at the centre of the drawing.

The control unit

For this datapath, the control unit produces roughly eight signals. They are a direct function of the opcode — pure combinational logic, exactly the decoder of chapter 05.

Reading that table row by row tells you what each instruction is, in hardware terms. A store is "a load with the memory direction reversed and no write-back". A compare is "a subtract that does not write its result". These are not analogies — they are literally the same wires with different control bits.

Hardwired versus microcoded control

Hardwired: the control signals are produced by combinational logic directly from the opcode. Fast, small, inflexible. This is the RISC approach and how ARM implements the common instructions.

Microcoded: the opcode indexes a small ROM containing a sequence of control-signal sets, stepped through over several cycles by a microprogram counter. Slower, but it makes complex multi-step instructions possible and lets the manufacturer fix bugs by updating the microcode after shipping — which is exactly how Spectre and Meltdown mitigations were delivered on x86.

Modern chips use both: hardwired for the common cases, microcode for the complex or rare ones.

Why single-cycle is a bad design

It works, and it is easy to reason about. It is also slow, for a reason that follows directly from chapter 07.

The clock period must accommodate the LONGEST instruction path.

  ADD:  I-fetch  reg-read  ALU  reg-write
        250 ps + 150 ps + 200 ps + 100 ps            =  700 ps

  LDR:  I-fetch  reg-read  ALU  D-mem  reg-write
        250 ps + 150 ps + 200 ps + 250 ps + 100 ps   =  950 ps  ← longest

  clock period = 950 ps  →  f_max ≈ 1.05 GHz

Every ADD now takes 950 ps even though it needed only 700 —
250 ps of every arithmetic instruction is spent doing nothing.

Worse: each hardware unit is used for a small slice of the cycle
and sits idle for the rest. The memory port is busy for 250 of
950 ps. That is 74% waste on the most expensive resource.

The multi-cycle detour

One historical fix: break each instruction into several shorter cycles, and let different instructions take different numbers of cycles. ADD takes 4, LDR takes 5. The clock period drops to the longest single step rather than the longest instruction, and units can be reused across steps (one memory port serving both fetch and data access).

This improves clock frequency but not throughput — you are still finishing at most one instruction every 4–5 cycles. The real answer is to overlap instructions, which is chapter 11.

Inside the register file

Worth opening up, because its port count is a constraint that shapes ISAs.

A register file with 2 read ports and 1 write port

   read addr A (5 bits) ──► decoder ──┐
                                      ├──► mux tree ──► read data A
   read addr B (5 bits) ──► decoder ──┤
                                      └──► mux tree ──► read data B

   write addr  (5 bits) ──► decoder ──► enable one register's flip-flops
   write data           ──────────────► all registers' D inputs
   write enable         ──────────────► gates the decoder

Each additional port costs area roughly QUADRATICALLY (more wires
crossing more cells) and adds delay. This is why:

  · most instructions have at most 2 source and 1 destination register
  · LDP/STP (load/store PAIR) are special — they need extra ports,
    and are provided anyway because function prologues use them constantly
  · a wide out-of-order core needs many ports and the register file
    becomes one of the hottest, most area-expensive blocks on the die
An ISA design decision you can now explain

Why does AArch64 have no instruction with three source registers and two destinations? Because the register file ports would cost more than the instruction saves. When you see an ISA restriction, the usual explanation is a port count, a wire, or a decoder — not a lack of imagination.

Where exceptions enter the datapath

Every stage can fail, and the datapath must handle it. This is the hardware behind ARM chapter 28.

StagePossible failureDatapath response
FetchInstruction address faults (unmapped, no-execute)Squash the instruction; force the PC mux to the exception vector
DecodeUndefined encoding, or an instruction not permitted at this privilegeSame; record the reason in a syndrome register
ExecuteDivide by zero, FP exceptionSuppress the register write
MemoryData address faultsSuppress write-back; latch the faulting address
Any timeInterrupt assertedComplete instructions already past the point of no return, squash the rest, redirect the PC

The requirement that makes this hard is precise exceptions: from software's point of view, every instruction before the faulting one must have completed fully, and every instruction after it must have had no effect at all. Getting that guarantee out of a machine that runs instructions out of order and speculatively is one of the central difficulties of processor design — and the reason RISC's "only loads and stores touch memory" rule was such a good idea.
