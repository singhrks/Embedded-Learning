Move semantics and perfect forwarding

Transferring ownership instead of duplicating it. Move semantics is what makes unique_ptr, vector and every other resource-owning type efficient — and perfect forwarding is how a generic wrapper passes arguments on without losing information about them.

The problem it solves

Copying a large object to hand it somewhere else is wasteful when the source is about to be destroyed anyway. Move semantics exists to transfer ownership instead of duplicating — and in systems code that is often the difference between an allocation and none.

/* Before C++11, returning a container copied it: */
        std::vector<int> make() {
                std::vector<int> v(1'000'000);
                fill(v);
                return v;               /* a COPY of a million
                                           ints, then the
                                           original is
                                           destroyed          */
        }

/* The copy is pure waste: the source is about to be
   destroyed. What we want is to STEAL its buffer.

/* WITH MOVE SEMANTICS: */
        vector(vector&& other) noexcept
                : data_(other.data_), size_(other.size_),
                  cap_(other.cap_)
        {
                other.data_ = nullptr;  /* the source no longer
                other.size_ = 0;           owns it - and is
                other.cap_  = 0;           still destructible */
        }

/* THREE POINTER ASSIGNMENTS instead of a million-element
   copy. That is the whole idea.

/* A MOVE IS NOT A SPECIAL OPERATION - it is just an OVERLOAD
   that takes an rvalue reference, and by convention steals
   rather than copies. The language provides the overload
   resolution; the stealing is yours to implement
   (chapter 03).                                            */

std::move

std::move does not move anything. It is a cast that marks a value as safe to steal from, and understanding that precisely prevents a whole class of misuse.

/* std::move does NOT move anything. It is a CAST to an rvalue
   reference, which changes which overload is selected.    */

        template<typename T>
        constexpr std::remove_reference_t<T>&&
        move(T&& t) noexcept
        {
                return static_cast<std::remove_reference_t<T>&&>(t);
        }

/* That is the entire implementation. It compiles to nothing.

/* USING IT: */
        std::vector<int> a = make();
        std::vector<int> b = a;                 /* COPY */
        std::vector<int> c = std::move(a);      /* MOVE - a is
                                                   now empty */

/* WHY IT IS NEEDED even inside a function taking T&&: */
        void sink(std::vector<int>&& v) {
                store(v);                       /* COPIES! v
                                                   HAS A NAME,
                                                   so it is an
                                                   LVALUE
                                                   (ch. 04)  */
                store(std::move(v));            /* moves */
        }
/* This is the single most common misunderstanding. An rvalue
   reference PARAMETER is an lvalue inside the function.

/* THE MOVED-FROM STATE: "valid but unspecified". You may
   destroy it and assign to it; you may not assume its value.
   For the standard containers it is in fact empty, but do not
   rely on that.                                            */
        std::string s = "hello";
        std::string t = std::move(s);
        /* s.size() is unspecified - do not read it */
        s = "new value";        /* fine - assignment is
                                   allowed */

/* WHEN NOT TO USE IT: */
        return std::move(local);        /* WRONG - defeats
                                           NRVO (chapter 03) */
        void f(const T& x) { g(std::move(x)); }
                                        /* USELESS - a const
                                           rvalue still binds
                                           to const T&, so it
                                           COPIES            */
        std::move(trivially_copyable)   /* pointless - no
                                           resources to steal */

Forwarding references

A template parameter declared with a double ampersand does not mean what it appears to — it binds to anything and preserves the value category, which is what makes generic wrappers possible.

/* `T&&` in a DEDUCED context is not an rvalue reference. It
   is a FORWARDING (or "universal") reference, and it binds to
   anything.                                                */

        template<typename T>
        void f(T&& x);          /* FORWARDING reference */

        void g(Widget&& x);     /* rvalue reference - T is not
                                   deduced                   */

        template<typename T>
        void h(std::vector<T>&& v);   /* rvalue reference -
                                         the type is not
                                         exactly T          */

/* THE RULE: `T&&` is a forwarding reference ONLY when T is a
   template parameter of that function being deduced. Also
   `auto&&`.

/* HOW IT BINDS - REFERENCE COLLAPSING: */
        T&  &   -> T&
        T&  &&  -> T&
        T&& &   -> T&
        T&& &&  -> T&&
/* "an lvalue reference wins".

        Widget w;
        f(w);                   /* T = Widget&, so
                                   T&& = Widget& && = Widget& */
        f(Widget{});            /* T = Widget, so
                                   T&& = Widget&&           */

/* SO T ENCODES WHETHER THE ARGUMENT WAS AN LVALUE OR AN
   RVALUE - and std::forward decodes it again.            */

Perfect forwarding

Passing an argument onward without losing its value category requires an explicit step, and omitting it silently turns moves back into copies.

/* THE PROBLEM: a wrapper must pass its arguments on with
   their value category intact.                            */

/* NAIVE - always copies: */
        template<typename T>
        void wrapper(T x) { target(x); }

/* BETTER, still wrong - x has a name, so it is an lvalue: */
        template<typename T>
        void wrapper(T&& x) { target(x); }   /* always copies */

/* CORRECT: */
        template<typename T>
        void wrapper(T&& x) { target(std::forward<T>(x)); }

/* std::forward<T> casts to T&&, which after reference
   collapsing is:
        T = Widget&  -> Widget&   (stays an lvalue)
        T = Widget   -> Widget&&  (becomes an rvalue)
   Exactly preserving what was passed.

/* THE VARIADIC FORM, which is what every factory looks like:
*/
        template<typename T, typename... Args>
        std::unique_ptr<T> make_unique(Args&&... args)
        {
                return std::unique_ptr<T>(
                        new T(std::forward<Args>(args)...));
        }

        auto p = make_unique<Widget>(x, std::move(y), 42);
        /* x is copied into the constructor, y is moved, 42 is
           passed as an rvalue - each correctly                */

/* THE RULE, memorised as a pair:
     std::move     on an rvalue reference - you are done with
                   it
     std::forward  on a forwarding reference - pass on what
                   you were given
   Using move where forward belongs steals from the caller's
   lvalue, which is a real and nasty bug.                 */

/* AND THE PLACE IT MATTERS MOST - emplace: */
        std::vector<Widget> v;
        v.push_back(Widget{1, 2});      /* construct, then MOVE
                                           into the vector    */
        v.emplace_back(1, 2);           /* construct IN PLACE -
                                           no move at all     */
/* emplace_back forwards its arguments to the element's
   constructor. For a type where move is cheap the difference
   is small; for one where it is not, it is the whole cost. */
The forwarding reference trap 
template<typename T>
void f(T&& x);          // matches EVERYTHING
void f(int);            // rarely selected

f(42);                  // T&& wins: an exact match with
                        // T = int, versus a non-template
                        // that also needs no conversion -
                        // and the template's specialisation
                        // is exact for every argument type

A forwarding-reference overload is greedier than almost anything else, and it will silently hijack calls you intended for other overloads — including copy constructors, producing baffling errors. Constrain it with a concept (C++20) or enable_if, or avoid overloading on it at all.

Implementing move correctly

Writing your own move operations is straightforward with one non-obvious requirement: the moved-from object must be left in a state that is safe to destroy.

class Buffer {
        uint8_t *data_ = nullptr;
        size_t   size_ = 0;

public:
        Buffer(Buffer&& o) noexcept
                : data_(std::exchange(o.data_, nullptr)),
                  size_(std::exchange(o.size_, 0))
        {}
        /* std::exchange(obj, newval) sets obj and returns the
           OLD value - exactly the move idiom, in one call. */

        Buffer& operator=(Buffer&& o) noexcept
        {
                if (this != &o) {
                        delete[] data_;         /* release ours */
                        data_ = std::exchange(o.data_, nullptr);
                        size_ = std::exchange(o.size_, 0);
                }
                return *this;
        }
};

/* --- OR THE COPY-AND-SWAP IDIOM, which gives you both
       assignment operators from one function and is
       automatically self-assignment safe: --- */

        Buffer& operator=(Buffer o) noexcept   /* BY VALUE */
        {
                swap(*this, o);
                return *this;
        }                       /* o's destructor releases what
                                   we used to own            */

        friend void swap(Buffer& a, Buffer& b) noexcept
        {
                using std::swap;
                swap(a.data_, b.data_);
                swap(a.size_, b.size_);
        }

/* The by-value parameter is copy-constructed from an lvalue
   argument and move-constructed from an rvalue, so ONE
   operator handles both. Elegant, and slightly less efficient
   than separate operators for the copy case - which is why
   the standard library writes both.

/* --- THE noexcept REQUIREMENT, restated because it matters
       (chapter 03): --- */
        static_assert(std::is_nothrow_move_constructible_v<Buffer>);
/* Put that assertion in your test file. A move constructor
   that silently is not noexcept makes vector reallocation
   copy instead of move.

/* --- AND THE `= default` CASE --- */
        class Widget {
                std::unique_ptr<Impl> p_;
                std::string name_;
        public:
                Widget(Widget&&) noexcept = default;
                Widget& operator=(Widget&&) noexcept = default;
        };
/* Member-wise move, generated correctly. Prefer this to
   writing it by hand whenever every member is itself
   movable - which is the rule of zero again (chapter 03). */

Does it matter on embedded?

Move semantics matters differently in embedded code, where the resource being transferred is more often a hardware handle or a buffer than heap memory.

/* HONESTLY: less than in application code, because the types
   that benefit most - vector, string, shared_ptr - are often
   banned anyway (chapter 01). But it still matters in three
   places:

/* 1. MOVE-ONLY RESOURCE TYPES. This is the big one, and it
      is independent of the heap:                          */
        class DmaChannel {
                int ch_ = -1;
        public:
                explicit DmaChannel(int ch) : ch_(ch)
                        { dma_claim(ch_); }
                ~DmaChannel() { if (ch_ >= 0) dma_release(ch_); }

                DmaChannel(const DmaChannel&) = delete;
                DmaChannel(DmaChannel&& o) noexcept
                        : ch_(std::exchange(o.ch_, -1)) {}
                ...
        };

        DmaChannel acquire_channel();   /* RETURN BY VALUE,
                                           moved out, no
                                           allocation
                                           anywhere         */
        std::optional<DmaChannel> try_acquire();

/* THE OWNERSHIP IS IN THE TYPE. A DmaChannel cannot be
   accidentally copied, cannot be leaked, and can be returned
   from a factory - none of which is expressible in C without
   convention.

/* 2. FIXED-CAPACITY CONTAINERS still benefit: */
        etl::vector<Message, 16> queue;
        queue.push_back(std::move(msg));    /* moves the
                                               element's
                                               members       */

/* 3. std::optional and std::variant use moves internally, and
      both are extremely useful on embedded (chapter 15).

/* WHERE IT DOES NOT MATTER: a trivially copyable struct -
   a Point, a register value, a POD message - has no
   resources, so a move IS a copy. std::move on one is
   harmless and pointless.                                 */

Verifying it happens

Whether a move actually happened is not obvious from the source. These are the ways to confirm it rather than assume it.

/* Instrument a type and watch: */
struct Tracer {
        Tracer()                     { puts("ctor"); }
        Tracer(const Tracer&)        { puts("COPY"); }
        Tracer(Tracer&&) noexcept    { puts("move"); }
        Tracer& operator=(const Tracer&)
                { puts("COPY="); return *this; }
        Tracer& operator=(Tracer&&) noexcept
                { puts("move="); return *this; }
        ~Tracer()                    { puts("dtor"); }
};

        std::vector<Tracer> v;
        v.reserve(4);
        Tracer t;
        v.push_back(t);                 /* COPY */
        v.push_back(std::move(t));      /* move */
        v.emplace_back();               /* ctor - no copy or
                                           move at all      */

/* Drop the reserve() and watch reallocation move (or copy!)
   every element. Remove `noexcept` from the move constructor
   and watch it switch to COPY - that experiment makes the
   rule stick better than any explanation.
