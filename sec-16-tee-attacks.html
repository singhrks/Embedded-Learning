TEE attacks and mitigations

Every mechanism in this track has been broken on real hardware. Knowing how is not pessimism — it is the only way to build something that holds, and to judge honestly what a TEE is and is not worth.

Where attacks land

A trusted execution environment is a boundary, and boundaries get attacked. Framing the attack surface honestly is what separates a design that resists attack from one that merely assumes trust.

   +---------------------------------------------------+
   |  1. THE INTERFACE                                 |
   |     SMC handlers, TA commands, parameter parsing  |
   |     -> by far the most productive target          |
   +---------------------------------------------------+
   |  2. THE TRUSTED CODE ITSELF                       |
   |     memory safety bugs in the TEE or a TA         |
   +---------------------------------------------------+
   |  3. SIDE CHANNELS                                 |
   |     cache timing, power, EM - no bug required     |
   +---------------------------------------------------+
   |  4. FAULT INJECTION                               |
   |     glitch the hardware into skipping the check   |
   +---------------------------------------------------+
   |  5. THE CHAIN OF TRUST                            |
   |     boot ROM parsing, downgrade, key handling     |
   +---------------------------------------------------+
   |  6. THE SYSTEM AROUND IT                          |
   |     DMA, debug, an unprotected peripheral         |
   +---------------------------------------------------+

  Note the ordering. Almost every publicly disclosed TEE
  compromise has been in layer 1 or 2 - ordinary software bugs
  in code that happened to be very privileged. The exotic
  attacks get the conference talks; the boring ones get the
  CVEs.

1. Interface attacks

The interface between the worlds is the primary attack surface, because it is the one place where untrusted input legitimately reaches trusted code. Every parameter is attacker-controlled.

/* THE CONFUSED DEPUTY - the defining TEE vulnerability. */

/* VULNERABLE: */
static TEE_Result cmd_read_key(uint32_t ptypes, TEE_Param p[4])
{
        /* attacker sets p[0].memref.buffer to a SECURE address */
        memcpy(p[0].memref.buffer, secret_key, 32);
        return TEE_SUCCESS;
}
/* The TA has the privilege to write anywhere. The attacker
   supplies the destination. Result: an arbitrary write
   primitive inside the secure world, driven from userspace. */

/* FIXED: */
        if (!tee_buffer_is_non_secure(p[0].memref.buffer,
                                      p[0].memref.size))
                return TEE_ERROR_ACCESS_DENIED;

/* --- MISSING paramTypes CHECK ------------------------------ */
/* If the TA does not verify ptypes, the client passes a VALUE
   where a MEMREF is expected. params[0].memref.buffer is then
   whatever 64-bit number the attacker put in params[0].value.a.
   Same primitive, reached differently.                       */

/* --- INTEGER OVERFLOW IN A SIZE CHECK ---------------------- */
        if (offset + len > buffer_size)     /* WRAPS */
                return TEE_ERROR_BAD_PARAMETERS;
        memcpy(dst + offset, src, len);
/* offset = 0xFFFFFFF0, len = 0x20 -> sum wraps to 0x10, check
   passes, memcpy writes far out of bounds.                  */
        if (offset > buffer_size || len > buffer_size - offset)
                return TEE_ERROR_BAD_PARAMETERS;   /* no wrap */

/* --- TOCTOU ------------------------------------------------ */
        if (validate(shm->cmd))         /* read 1 */
                execute(shm->cmd);      /* read 2 - DIFFERENT */
/* Another CPU rewrote it in between. Copy in ONCE, then
   validate and use only the copy.                           */

/* --- STATE CONFUSION --------------------------------------- */
/* Call sequence: OPEN, then USE. What if the attacker calls
   USE twice? USE after CLOSE? OPEN twice? Two USEs on two CPUs
   at once? A session state machine that assumes the documented
   order is a use-after-free waiting to happen.              */

2. Memory safety in trusted code

Trusted applications are usually written in C and run with substantial privilege, so an ordinary memory-safety bug there is far more valuable to an attacker than the same bug elsewhere.

/* The secure world is C. It has all of C's problems (see the C
   track, chapter 15) with none of the mitigations you get for
   free in Linux userspace.                                  */

   What is usually MISSING in a TEE:
        ASLR             often none, or very coarse
        stack canaries   sometimes; check your build flags
        NX / W^X         usually yes, but verify
        guard pages      often not - the heap is a fixed array
        a hardened allocator   rarely
        CFI              rarely
        MTE / PAC        only on newer parts, and only if enabled

   And the payoff for a bug is total: S-EL1 code owns the keys,
   the fuses, and the ability to lie to the normal world about
   attestation.

/* MITIGATIONS THAT ARE WORTH THE EFFORT: */

   -fstack-protector-strong    cheap, catches real bugs
   -D_FORTIFY_SOURCE=2
   -Wall -Wextra -Werror       and actually fix the warnings
   -fsanitize=... in a HOST harness, not on target

   CFG_TA_ASLR=y               OP-TEE: randomise TA layout
   CFG_CORE_SANITIZE_KADDRESS  debug builds only
   PAC and BTI on Armv8.3+     enable them

   Fuzz the SMC and TA interfaces on the host, with the same
   code compiled natively. Every TEE interface is a parser, and
   parsers are what fuzzers are good at.

   And: KEEP IT SMALL. A 20,000-line trusted OS can be audited.
   A 500,000-line one cannot, no matter how good the process. */

3. Side channels

Secure-world code shares caches, branch predictors and power rails with the normal world, and each of those has been used to extract secrets across the boundary without breaking it.

The two worlds SHARE the microarchitecture: caches, branch
predictors, TLBs, the memory controller, the power rail. Sharing
a resource means measuring one another.

  CACHE TIMING (Prime+Probe, Flush+Reload)
     Normal-world code fills a cache set, lets the secure world
     run, then times its own re-access. Slow = the secure world
     evicted it = it touched that set. Repeat, and the pattern
     of accesses reveals the key - because table-driven AES and
     square-and-multiply RSA access memory in key-dependent
     ways.
     -> TruSpy, ARMageddon, and many since.

  BRANCH PREDICTOR
     Same idea, different shared structure. Secret-dependent
     branches leave traces.

  POWER and EM
     Physical access, an oscilloscope and a probe. DPA on a
     naive AES implementation needs a few thousand traces and
     an afternoon.

  MICROARCHITECTURAL SPECULATION
     Spectre-style: train a predictor, make secure code
     speculatively access secret-dependent addresses, read the
     cache. Applies across the world boundary on affected
     cores.

  MITIGATIONS:
     · CONSTANT-TIME code for anything touching a secret:
          no branch on secret data
          no memory INDEX derived from secret data
          no early exit from a comparison
     · bitsliced or table-free crypto, or a hardware engine
     · masking / blinding - randomise the intermediate values
     · flush or partition caches on world switch (costly)
     · disable SMT on the secure side, or do not use SMT
     · use the crypto accelerator: it is not sharing the cache

  ACCEPT THE LIMIT: a TEE does not defend against an attacker
  with physical access, an oscilloscope and time. It defends
  against a compromised NORMAL WORLD. Say so in your threat
  model rather than pretending otherwise.
/* Constant-time comparison - the smallest example, and the one
   people still get wrong.                                   */

/* LEAKS: returns as soon as it finds a difference, so the time
   reveals how many bytes matched.                           */
int bad_compare(const uint8_t *a, const uint8_t *b, size_t n)
{
        for (size_t i = 0; i < n; i++)
                if (a[i] != b[i])
                        return -1;
        return 0;
}

/* CONSTANT TIME: always touches every byte, no branch on data */
int ct_compare(const uint8_t *a, const uint8_t *b, size_t n)
{
        uint8_t diff = 0;

        for (size_t i = 0; i < n; i++)
                diff |= a[i] ^ b[i];

        return diff;            /* 0 iff equal */
}

/* And the same discipline everywhere: */
        if (secret_flag) x = a; else x = b;     /* leaks       */
        mask = -(uint32_t)!!secret_flag;
        x = (a & mask) | (b & ~mask);           /* does not    */

/* Beware the compiler. It can reintroduce a branch. Check the
   generated assembly for anything genuinely critical, and
   consider a barrier or volatile to pin it down.            */

4. Fault injection

An attacker with physical access can glitch voltage or clock to make a processor skip an instruction — which turns a signature check into an unconditional success. Defending against this is a design discipline, not a library.

Do not break the crypto - break the CHECK.

     if (verify_signature(img) != OK)
             fail();            <-- glitch the branch, skip this
     boot(img);

  Techniques, roughly by cost:
     VOLTAGE GLITCH   drop Vcc for nanoseconds. ~$50 of kit.
     CLOCK GLITCH     an extra or shortened clock edge.
     EM PULSE         a coil over the die. No decapsulation.
     LASER            decapsulated die, single-bit precision.
                      Six figures, and a lab.
     ROWHAMMER        software-only DRAM bit flips - a fault
                      attack with no hardware at all.

  Effects: an instruction skipped, a register corrupted, a
  comparison inverted, a loop counter changed.

  SOFTWARE COUNTERMEASURES - none is sufficient alone, but
  together they raise the cost a great deal:

     · DOUBLE-CHECK critical decisions, with different code
     · use non-trivial constants: a "success" value of
       0x5A3C96C3, never 0 or 1, so a cleared register is not
       automatically a pass
     · random delays before sensitive operations
     · redundant loop counters, verified after the loop
     · verify the result of the operation you just did
     · a "flow counter" incremented at each checkpoint and
       validated at the end - so a skipped stage is detectable

  HARDWARE COUNTERMEASURES: voltage and clock glitch detectors,
  light sensors, redundant logic, error-correcting registers.
  If your threat model includes physical attackers, choose
  silicon that has them - you cannot add them later.
/* Fault-hardened verification, as it is actually written in
   boot ROMs.                                                */

#define FLOW_OK    0x5A3C96C3u
#define FLOW_FAIL  0xA5C36939u

static uint32_t verify_hardened(const image_t *img)
{
        uint32_t r1, r2;
        volatile uint32_t counter = 0;

        r1 = verify_signature(img);
        counter++;

        random_delay();

        r2 = verify_signature(img);     /* again, independently */
        counter++;

        if (r1 != FLOW_OK)  return FLOW_FAIL;
        if (r2 != FLOW_OK)  return FLOW_FAIL;
        if (r1 != r2)       return FLOW_FAIL;
        if (counter != 2)   return FLOW_FAIL;   /* skipped step? */

        return FLOW_OK;
}

        if (verify_hardened(img) == FLOW_OK) {
                if (verify_hardened(img) != FLOW_OK)  /* again */
                        panic();
                boot(img);
        } else {
                panic();
        }

/* Ugly, redundant, and deliberately so. A single glitch must
   not produce a boot. Reviewers should be able to point at
   each redundant check and name the fault it catches.      */

What a TEE is actually worth

An honest threat model

A TEE defends well against: a compromised normal-world OS, malicious applications, an attacker with root, offline extraction of keys from storage, and cloning a device by copying its filesystem.

A TEE defends poorly or not at all against: an attacker with physical access, time and laboratory equipment; side channels, unless the code was written for it; bugs in the trusted code itself; and anything the silicon integration left unprotected.

That is still a great deal of value — it is the difference between "root compromises every device forever" and "root compromises this device's session". Just do not let a datasheet's security bullet points substitute for stating which of the two you are buying.
