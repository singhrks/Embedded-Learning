config.txt and the firmware interface

This one file is the Pi's BIOS, its bootloader configuration and its board-level hardware description all at once. It is read by closed firmware before Linux exists, its syntax resembles nothing else, and a typo in it produces silence rather than an error.

What reads it, and when

   config.txt is parsed by the VIDEOCORE FIRMWARE at boot
   stage 4 (chapter 03), before the ARM cores are released.

   THREE CONSEQUENCES that explain most confusion:

   1. NOTHING IN LINUX READS IT. Changing it and running
      "systemctl daemon-reload" or "modprobe" does nothing.
      Every change needs a REBOOT.

   2. ERRORS ARE SILENT. An unknown key, a misspelled
      overlay, a bad value - the firmware skips the line and
      carries on. There is no error message anywhere unless
      you have the serial console with BOOT_UART=1
      (chapter 05).

   3. IT DESCRIBES HARDWARE, so it is really a device tree
      front-end. dtoverlay= and dtparam= lines are literally
      modifications applied to the device tree before Linux
      sees it (chapter 10).

   WHERE IT LIVES depends on your OS release:
     Bookworm and later:  /boot/firmware/config.txt
     Older releases:      /boot/config.txt

   Check before editing. Writing to the wrong path creates a
   file that is never read, and the symptom is "my change
   did nothing" - which is also the symptom of a typo, so
   you can waste a long time here.
     $ mount | grep boot

The syntax, including the part that surprises

# Plain key=value, one per line, no spaces around '='.
arm_64bit=1
enable_uart=1

# Comments are '#'. There is NO line continuation.

# CONDITIONAL SECTIONS - a filter that applies to every line
# until the next section header. This is the part people
# miss, and it silently changes what your settings do:

[all]              # everything below applies to all boards
                   # ALWAYS END WITH THIS

[pi4]              # only on a Pi 4
arm_boost=1

[pi5]              # only on a Pi 5
dtparam=uart0=on

[cm4]              # Compute Module 4
[board-type=0x11]  # a specific revision
[HDMI:1]           # settings for the second HDMI port
[EDID=...]         # a specific attached monitor
[gpio4=1]          # conditional on a GPIO being high at boot

# THE CLASSIC MISTAKE:
#
#   [pi4]
#   arm_boost=1
#   enable_uart=1        <-- still inside [pi4]!
#
# On a Pi 5 the UART is not enabled and you have no console,
# which is exactly when you need one. Close every
# conditional section with [all] before adding general
# settings.

# ORDER MATTERS for repeated keys: the LAST assignment wins.
# So a stray duplicate further down silently overrides your
# careful earlier line. Grep before adding:
$ grep -n "^enable_uart" /boot/firmware/config.txt

Settings that matter for development

# --- CONSOLE AND DEBUG (chapter 05) ---
enable_uart=1                 # serial console; also pins the
                              # core clock so it stays legible
dtoverlay=disable-bt          # give the console the good UART

# --- INTERFACES (chapter 12) ---
dtparam=i2c_arm=on            # /dev/i2c-1
dtparam=i2c_arm_baudrate=400000
dtparam=spi=on                # /dev/spidev0.0, 0.1
dtparam=i2s=on
enable_uart=1

# raspi-config edits these for you, and is the safer route
# for the common ones:
$ sudo raspi-config nonint do_i2c 0      # 0 = enable
$ sudo raspi-config nonint do_spi 0
$ sudo raspi-config nonint do_serial_hw 0

# --- MEMORY SPLIT ---
gpu_mem=16                    # minimum, for a headless board.
                              # Frees RAM the VideoCore would
                              # otherwise reserve. Do NOT do
                              # this if using the camera or
                              # hardware video (vid track).

# --- BOOT BEHAVIOUR ---
boot_delay=0                  # skip the default 1s wait
disable_splash=1
dtoverlay=disable-wifi        # headless wired board: less
                              # power, fewer surprises

# --- OVERCLOCK / UNDERCLOCK (chapter 18) ---
arm_freq=2000
over_voltage=2
# On a Pi 5 the voltage controls differ; check current
# documentation rather than copying Pi 4 recipes.
# Overclocking sets a permanent bit in OTP on some models -
# read before you type.

# --- CUSTOM KERNEL (chapters 15, 20) ---
kernel=kernel8-custom.img     # boot a different image
device_tree=my-board.dtb
initramfs initramfs8 followkernel   # NOTE: no '=' on this
                                    # one. It is genuinely
                                    # inconsistent syntax.
Always keep a known-good copy on the boot partition

Before editing, sudo cp config.txt config.txt.good. When a change stops the board booting — and one eventually will — you pull the card, mount the FAT partition on any laptop, and copy the good file back. That is a ninety-second recovery instead of a reimage. The same applies to cmdline.txt. This is the single most useful habit in this chapter.

cmdline.txt, the other half

# The kernel command line. ONE line, space-separated, no
# newline anywhere in it. A newline truncates everything
# after it and the usual result is a kernel that cannot find
# its root filesystem.

console=serial0,115200 console=tty1 root=PARTUUID=abcd1234-02 \
  rootfstype=ext4 fsck.repair=yes rootwait

# (shown wrapped for reading - it is ONE line in the file)

# WHAT IS WORTH ADDING DURING DEVELOPMENT:

  loglevel=8              # all kernel messages to console
  ignore_loglevel         # even more
  earlycon                # console output BEFORE the real
                          # driver initialises - catches
                          # crashes that print nothing
                          # otherwise
  initcall_debug          # trace every driver init, with
                          # timings. Excellent for "which
                          # driver is hanging the boot"
  cma=128M                # contiguous memory for camera or
                          # video (vid track)
  isolcpus=3              # keep core 3 free of the
                          # scheduler, for a latency-
                          # sensitive thread
  systemd.unit=rescue.target   # boot to a shell

# WHY earlycon MATTERS: the normal console driver starts
# some way into boot. A panic before that point prints
# nowhere at all. With earlycon you see it. If a Pi hangs
# with no output despite a working serial console, this is
# the first thing to add.

# root=PARTUUID is used rather than /dev/mmcblk0p2 because
# the device name changes if you later boot from USB or
# NVMe. Find it with:
$ sudo blkid

Finding out what the firmware actually did

# config.txt is a request. This is how you check it was
# honoured - which is the step most people skip.

# What the firmware decided, as key=value:
$ vcgencmd get_config int
arm_freq=2400
gpu_mem=76
...
$ vcgencmd get_config str

# Note this shows the RESOLVED values, so it catches a
# setting that was overridden later in the file or that sat
# inside a [pi4] block on a Pi 5.

# Which overlays and parameters were applied:
$ sudo vcdbg log msg 2>&1 | grep -i overlay     # Pi 4
# vcdbg is not available on the Pi 5; use the serial console
# with BOOT_UART=1 instead, which prints the same detail.

# THE AUTHORITATIVE ANSWER - the device tree Linux actually
# received, after all overlays:
$ dtc -I fs -O dts /sys/firmware/devicetree/base > live.dts
$ grep -A5 "i2c@7e804000" live.dts
# status = "okay"  means it was enabled.
# status = "disabled" means your dtparam did not take.

# This one command settles nearly every "did my config
# change work" question, and chapter 10 relies on it
# throughout.

$ cat /proc/cmdline        # the command line as received
$ vcgencmd version         # firmware build date
