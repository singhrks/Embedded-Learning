Debugging a video pipeline

A video bug has a visible signature, and the signature names the layer. Learning to read "green frame", "diagonal skew", "washed out", "judder" as diagnoses rather than symptoms turns a day of guessing into ten minutes of bisection.

Bisect the pipeline, do not stare at the output

A pipeline is capture → encode → mux → transmit → demux → decode → convert → display. The fastest way to localise a bug is to dump the intermediate: write the raw frames after capture, the elementary stream after encode, the decoded frames before display. Whichever dump is the first to look wrong contains the bug. Ten minutes of dumping beats a day of reasoning about which stage is guilty.

Dumping at every stage

# 1. AFTER CAPTURE - raw frames from the device
$ v4l2-ctl -d /dev/video0 \
    --set-fmt-video=width=1920,height=1080,pixelformat=NV12 \
    --stream-mmap --stream-count=30 --stream-to=cap.nv12
$ ffplay -f rawvideo -pixel_format nv12 -video_size 1920x1080 cap.nv12
# Wrong here -> sensor, ISP, or your format assumption.

# 2. AFTER ENCODE - the elementary stream, no container
$ ffmpeg -i input.mp4 -c:v copy -bsf:v h264_mp4toannexb -f h264 es.264
$ ffplay es.264
# Plays -> the codec data is fine and the problem is the
# container or the transport.

# 3. AFTER DECODE - what the decoder actually produced
$ ffmpeg -i input.mp4 -pix_fmt nv12 -f rawvideo dec.nv12
$ ffplay -f rawvideo -pixel_format nv12 -video_size 1920x1080 dec.nv12
# Correct here but wrong on screen -> conversion or display.

# 4. COMPARE two stages numerically rather than by eye
$ ffmpeg -i original.y4m -i decoded.y4m \
    -lavfi "[0:v][1:v]psnr=stats_file=psnr.log" -f null -
$ awk '$0 ~ /psnr_avg/ {print}' psnr.log | sort -t: -k6 -n | head
# The worst frames first. A single terrible frame among good
# ones is a dropped reference; a gradual decline is drift
# (chapter 11).

# 5. VISUAL DIFF, which finds what metrics miss
$ ffmpeg -i a.mp4 -i b.mp4 \
    -lavfi "[0:v][1:v]blend=all_mode=difference,eq=contrast=8" \
    -c:v libx264 -crf 18 diff.mp4
# Black = identical. Anything visible is a real difference,
# amplified 8x.

Inspecting the bitstream itself

# When the pixels are wrong and you suspect the stream.

# Every NAL unit, its type and size:
$ ffmpeg -i in.mp4 -c copy -bsf:v trace_headers -f null - 2>&1 | head -60
[trace_headers] Sequence Parameter Set
[trace_headers] 0           forbidden_zero_bit          0
[trace_headers] 1           nal_ref_idc                11 = 3
[trace_headers] 3           nal_unit_type          00111 = 7
[trace_headers] 8           profile_idc          01100100 = 100
[trace_headers] 16          level_idc            00101000 = 40
[trace_headers] ...         pic_width_in_mbs_minus1   = 119
[trace_headers] ...         pic_height_in_map_units_minus1 = 67
#                                                        ^^ 68
#   68 * 16 = 1088, and frame_cropping tells you it is really
#   1080. This is where you check the crop (chapter 16).

# Frame types, sizes and timestamps in one view:
$ ffprobe -select_streams v -show_entries \
    frame=pict_type,key_frame,pkt_size,pkt_pts_time \
    -of csv=p=0 in.mp4 | head -20

# Bitrate over time - finds spikes and starved regions:
$ ffprobe -select_streams v -show_entries frame=pkt_size \
    -of csv=p=0 in.mp4 | awk '{s+=$1; n++}
      n%30==0 {printf "%d %.0f kbit/s\n", n/30, s*8/1000; s=0}'

# Is the file structurally valid at all?
$ ffmpeg -v error -i in.mp4 -f null -
# Silence = clean. Any output here is a real decode error.

# Deeper conformance:
$ ffmpeg -v verbose -err_detect explode -i in.mp4 -f null -
# Turns warnings that are normally tolerated into failures.

# For MP4 box structure:
$ MP4Box -info in.mp4
$ mp4dump in.mp4 | head -40
# Missing moov, wrong track duration, an edit list you did not
# expect (chapter 15) - all visible here.
"It plays in VLC" proves almost nothing

VLC and ffmpeg are extraordinarily tolerant — they resynchronise after corruption, guess missing metadata, ignore level violations and work around broken muxers. A hardware decoder does none of that. If a file plays in VLC and fails on a device, the file is very likely wrong and VLC is compensating. Test with -err_detect explode, and on the actual target.

Performance, not correctness

# THE FIRST QUESTION: is the hardware path in use at all
# (chapters 16, 19)?

$ sudo intel_gpu_top             # "Video" and "VideoEnhance" rows
$ nvidia-smi dmon -s u           # "dec" and "enc" columns
$ adb shell dumpsys SurfaceFlinger | grep -A5 'Composition'
$ sudo cat /sys/kernel/debug/dri/0/state | grep -c 'format=NV12'
# Zero in any of these = you are on the software path.

# THE SECOND: where is the time going?
$ perf top -p $(pidof myplayer)
# Expect to see, in a healthy software decoder:
#   ff_h264_decode_mb_cabac      entropy   (chapter 8)
#   h264_idct_add8_8_avx         transform
#   ff_h264_filter_mb            deblock   (chapter 12)
#   ff_hscale / yuv2rgb          CONVERSION - if this is high,
#                                you have an unnecessary
#                                format conversion

# THE THIRD: memory bandwidth, which is what actually limits
# embedded pipelines (chapter 16).
$ sudo perf stat -e uncore_imc/data_reads/,uncore_imc/data_writes/ \
    -a sleep 5
# Compare against the theoretical (frame size x fps x copies).
# Much higher than expected = hidden copies.

# LATENCY, end to end, measured rather than estimated:
$ ffmpeg -f lavfi -i "testsrc=size=640x480:rate=60" \
    -vf "drawtext=text='%{pts\\:hms}':fontsize=48:x=10:y=10" \
    -f v4l2 /dev/video1
# Point a camera at the screen showing the timestamp, and
# compare. Crude, and it measures the WHOLE chain including
# the display, which is the number that actually matters.

# GStreamer's built-in latency tracer:
$ GST_DEBUG="GST_TRACER:7" GST_TRACERS="latency" \
    gst-launch-1.0 ... 2>&1 | grep latency

The method

  1. Name the artefact. Use the table above. Half of all video bugs are identified by their appearance alone.
  2. Bisect by dumping. Raw after capture, elementary stream after encode, raw after decode. The first bad dump contains the bug.
  3. Check the metadata before the pixels. Format, stride, colour tags, crop, timestamps. These are cheap to inspect and are the cause far more often than the codec.
  4. Reproduce with ffmpeg alone. If ffmpeg -i in -f null - is clean, the file is fine and your pipeline is not.
  5. Test on the target. Desktop tolerance hides level violations, missing headers and alignment problems that a hardware decoder will not accept.
  6. Separate correctness from performance. They have different tools and different answers, and confusing them wastes the most time.
