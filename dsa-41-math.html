Math: gcd, primes, modular arithmetic and overflow

A small, fixed toolkit that turns up in interviews far more often than its size suggests: Euclid's algorithm, the sieve, fast exponentiation, and the arithmetic rules that stop a correct algorithm returning a wrong number. None of it is deep. All of it is the sort of thing you either know cold or fumble under pressure.

Euclid, and the two facts that follow from it

The greatest common divisor is four lines, and the reason it works explains most of the problems that use it. Learn the identity rather than the code and the applications become obvious.

   THE IDENTITY:   gcd(a, b) = gcd(b, a mod b)

   WHY: any number dividing both a and b also divides
   a - k*b for every k, and a mod b is just a - k*b for the
   right k. So the two pairs have exactly the SAME set of
   common divisors - not merely the same largest one.

     gcd(48, 18)
       = gcd(18, 48 mod 18 = 12)
       = gcd(12, 18 mod 12 = 6)
       = gcd(6,  12 mod 6  = 0)
       = 6

   IT IS FAST. The remainder at least halves every two
   steps, so it is O(log min(a, b)) - fast enough that you
   never need to think about its cost.

   ---------------------------------------------------------

   THE TWO FACTS WORTH CARRYING:

   1. lcm(a, b) = a / gcd(a, b) * b
      DIVIDE FIRST. Writing a * b / gcd overflows for inputs
      that the correct order handles fine.

   2. gcd IS ASSOCIATIVE, so the gcd of a whole array is a
      fold:  arr.reduce(gcd)
      and it collapses fast - usually to 1 within a few
      elements, which you can exploit to exit early.

   ---------------------------------------------------------

   WHERE IT SHOWS UP WHEN NOTHING MENTIONS DIVISORS:

     · reducing a fraction to lowest terms
     · "how many distinct slopes" - store a slope as a
       reduced pair (dy/g, dx/g), never as a float
     · repeating patterns and cycles: two cycles of lengths
       a and b realign after lcm(a, b)
     · "can these strings tile each other" - the answer
       length is gcd of the lengths

The sieve

Trial division is fine for asking about one number. The moment a problem needs every prime below some limit, the sieve is the answer — and the two details in it are the ones people get wrong.

function sieve(n) {
    const isPrime = new Array(n + 1).fill(true);
    isPrime[0] = isPrime[1] = false;

    /* DETAIL 1: stop at sqrt(n). Any composite below n has
       a factor at or below its square root, so a larger i
       has nothing left to cross off.                      */
    for (let i = 2; i * i <= n; i++) {
        if (!isPrime[i]) continue;

        /* DETAIL 2: start at i*i, not 2*i. Every smaller
           multiple of i has a smaller prime factor and was
           already crossed off by it.                      */
        for (let j = i * i; j <= n; j += i) isPrime[j] = false;
    }
    return isPrime;
}

/* COST: O(n log log n), which is very close to linear.
   Quote it as "about n" and do not try to justify the
   log log unless asked - it comes from summing 1/p over
   the primes.                                            */

/* TESTING ONE NUMBER doesn't need a sieve: */
function isPrime(n) {
    if (n < 2) return false;
    if (n % 2 === 0) return n === 2;
    for (let i = 3; i * i <= n; i += 2)
        if (n % i === 0) return false;
    return true;
}

/* FACTORISATION, same shape, and the trailing case is the
   one that gets forgotten: */
function factorise(n) {
    const out = [];
    for (let p = 2; p * p <= n; p++)
        while (n % p === 0) { out.push(p); n /= p; }
    if (n > 1) out.push(n);   /* a leftover prime factor
                                 LARGER than sqrt(original) */
    return out;
}

Fast exponentiation, and why it is not really about numbers

Binary exponentiation computes x^n in O(log n) multiplications. It is worth learning as a shape, because the same shape applies to anything you can multiply associatively.

   THE IDEA: read the exponent in BINARY.

     x^13,  13 = 1101b
          = x^8 * x^4 * x^1

   So: square the base repeatedly, and multiply it into the
   answer whenever the current exponent bit is 1.

     result = 1
     while (n > 0) {
         if (n & 1) result *= x;
         x *= x;
         n >>= 1;
     }

   FOUR MULTIPLICATIONS INSTEAD OF TWELVE, and for n around
   10^9 it is 30 instead of a billion.

   ---------------------------------------------------------

   THE THREE THINGS THAT BREAK IT:

     · NEGATIVE n. Compute x^|n| and take the reciprocal.
       In languages with fixed-width ints, negating the most
       negative value overflows - convert to a wider type
       BEFORE negating.
     · n = 0 must return 1, including 0^0 by convention.
     · x squared overflows quickly. If the problem is modular,
       reduce after EVERY multiply, not at the end.

   ---------------------------------------------------------

   THE SHAPE GENERALISES, which is the real reason to know
   it. Replace "multiply" with any associative operation:

     · matrix multiply  -> the n-th Fibonacci number in
                           O(log n), and linear recurrences
                           generally
     · modular multiply -> modular inverse via Fermat
     · function compose -> "apply this permutation n times"

   IF A PROBLEM HAS AN ABSURD n - 10^18 - AND A SMALL STATE,
   this is almost always the intended route.

Modular arithmetic and overflow

This is the section that actually loses marks. The algorithm is right, the answer is wrong, and the reason is arithmetic rather than logic.

RuleHolds?What to do
(a + b) % mYesReduce each term first if they are large
(a * b) % mYesBut a * b can overflow before the % runs — reduce first, and use a wide type
(a - b) % mYes, butMay be negative; write ((a - b) % m + m) % m
(a / b) % mNoDivision is not defined mod m. Multiply by the modular inverse instead
Comparisons after %NoOrder is destroyed by reduction — never sort or compare reduced values

The division row is the one that catches people, because it looks like it should work. When the modulus is prime — and in interview problems 10^9 + 7 always is — the inverse of b is b^(m-2) mod m by Fermat's little theorem, which is one call to the fast-power function you already wrote. That is the entire reason fast exponentiation and modular arithmetic are taught together.

   AND THE LANGUAGE TRAP, which is not a maths problem:

   JAVASCRIPT has one number type, a 64-bit float. Integers
   are exact only up to 2^53. So:

     (10**9 + 7) * (10**9 + 6)   is WRONG - silently.

   USE BigInt for modular multiplication with a 10^9 modulus,
   or keep the modulus below about 2^26 so products stay
   exact.

   C++ AND JAVA have the opposite problem: int is 32 bits and
   wraps SILENTLY. Cast to long/long long BEFORE multiplying,
   not after:

     (int)(((long long)a * b) % MOD)     correct
     (int)((a * b) % MOD)                already overflowed

   PYTHON has arbitrary-precision integers and none of this
   applies - which is a genuine reason to pick it for a
   maths-heavy question, and worth saying out loud.
