Why C++ for systems, and what to leave out

C++ gives you real safety improvements over C at genuinely zero runtime cost — and also gives you several features that are wrong for embedded work. Knowing which is which is the whole skill, and it matters more here than in any other domain.

What C++ actually buys

C++ in systems work is not the language people write applications in. It is a deliberately chosen subset, adopted for a handful of specific benefits and with several major features switched off entirely — so the first question is what you are actually adopting.

   THE FEATURES THAT COST NOTHING AT RUN TIME AND PREVENT
   REAL BUGS:

     RAII                a resource is released when its owner
                         goes out of scope. No leak, on any
                         path, including exceptions and early
                         returns. This is the single biggest
                         win.
     destructors         deterministic, not garbage collected
     const correctness   enforced by the type system
     references          a pointer that cannot be null and
                         cannot be reseated
     strong typing       no implicit void* conversions; enum
                         class does not decay to int
     templates           one implementation, many types, with
                         no runtime dispatch
     constexpr           computation moved to compile time
     std::array, span    an array that knows its own size
     unique_ptr          ownership expressed in the type
     namespaces          no more my_module_do_thing()
     function overloading and default arguments

   AND THE COST OF EACH, honestly: zero, provided you use them
   as intended. `std::unique_ptr` compiles to exactly the same
   code as a raw pointer plus a manual delete - godbolt it and
   see (chapter 14).

   WHAT IS *NOT* FREE, and needs a decision:
     exceptions          code size, and a hidden control flow
                         path (chapter 12)
     RTTI / dynamic_cast a type-info table per class
     virtual functions   an indirect call and a vtable pointer
                         per object (chapter 11)
     the iostreams       enormous; often 100 KB+ of code
     std::function       a heap allocation and an indirect call
     dynamic allocation  fragmentation and non-determinism
     std::string, vector heap allocation
The honest summary

C++ is a better C for systems work — if you choose a subset deliberately and enforce it. Used without that discipline it produces binaries three times the size with unpredictable timing, which is why some embedded organisations ban it outright. That ban is a reasonable response to the undisciplined case and a poor response to the disciplined one.

Choosing a subset

Embedded and kernel C++ is defined as much by what it excludes as by what it includes. These exclusions are not stylistic preferences; each one has a concrete cost that makes it unacceptable in the environment.

# A configuration that most embedded C++ projects converge on:

    -fno-exceptions             ; chapter 12
    -fno-rtti                   ; no dynamic_cast, no typeid
    -fno-threadsafe-statics     ; if single-threaded init
    -fno-use-cxa-atexit         ; no static destructor
                                ; registration
    -ffunction-sections -fdata-sections
    -Wl,--gc-sections
    -Os or -O2
    -std=c++17 or c++20

# AND THE LIBRARY DECISION:
#   freestanding / no std::     bare metal, tightest control
#   ETL (Embedded Template Library)   fixed-capacity
#                               containers with the STL's
#                               interface
#   the STL, minus the allocating parts
#   full STL                    embedded Linux, where a heap
#                               and megabytes exist

# WHAT TO BAN, and why:
#   iostreams          enormous, and drags in locale
#   std::string        heap; use std::string_view, or a
#                      fixed-size buffer
#   std::function      heap + indirect call; use a function
#                      pointer or a template parameter
#   dynamic_cast       needs RTTI
#   exceptions         see chapter 12
#   new/delete in steady state    preallocate at init
#   std::shared_ptr    atomic refcounts; usually the wrong
#                      ownership model for embedded

# WHAT TO ENCOURAGE:
#   std::array, std::span, std::optional, std::variant
#   constexpr everything that can be
#   enum class
#   RAII wrappers for every hardware resource
#   std::unique_ptr with a custom deleter, for handles
#   templates for compile-time configuration

# WRITE IT DOWN. A one-page "C++ subset" document that says
# what is permitted and why is worth more than any amount of
# individual good judgement, because it survives staff
# changes and makes review objective.

RAII, immediately

This is the single feature that justifies C++ in systems code. Tying a resource's lifetime to an object's scope means cleanup happens on every exit path automatically — including the ones you forgot to write.

/* THE C VERSION, and every error path is a chance to leak: */
        int do_work(void)
        {
                int fd = open("/dev/thing", O_RDWR);
                if (fd < 0) return -1;

                void *buf = malloc(SIZE);
                if (!buf) { close(fd); return -1; }

                if (configure(fd) < 0) {
                        free(buf); close(fd); return -1;
                }
                if (transfer(fd, buf) < 0) {
                        free(buf); close(fd); return -1;
                }

                free(buf);
                close(fd);
                return 0;
        }

/* THE C++ VERSION: */
        class FileDescriptor {
                int fd_;
        public:
                explicit FileDescriptor(const char *path, int flags)
                        : fd_(::open(path, flags)) {}

                ~FileDescriptor() { if (fd_ >= 0) ::close(fd_); }

                /* non-copyable, movable - chapter 03 */
                FileDescriptor(const FileDescriptor&) = delete;
                FileDescriptor& operator=(const FileDescriptor&)
                        = delete;
                FileDescriptor(FileDescriptor&& o) noexcept
                        : fd_(o.fd_) { o.fd_ = -1; }

                bool valid() const { return fd_ >= 0; }
                int  get()   const { return fd_; }
        };

        int do_work()
        {
                FileDescriptor fd("/dev/thing", O_RDWR);
                if (!fd.valid()) return -1;

                std::array<std::byte, SIZE> buf;   /* NO HEAP */

                if (configure(fd.get()) < 0) return -1;
                if (transfer(fd.get(), buf.data()) < 0)
                        return -1;

                return 0;      /* destructor closes fd, on
                                  EVERY path */
        }

/* THE GENERATED CODE IS IDENTICAL to the C version's happy
   path, plus a close in each exit block - which the C version
   also has, written by hand, four times, with one of them
   eventually forgotten.

   THIS IS THE ARGUMENT FOR C++ IN SYSTEMS WORK, and it is
   the same argument as Linux's devm_ (Linux chapter 33) and
   WDF's object parenting (Windows chapter 14): make cleanup
   structural rather than remembered.                      */

Proving the cost

C++ features vary enormously in what they cost at run time, from literally nothing to a hidden allocation. Knowing which is which is what separates a useful adoption from a bloated one.

/* Do not take "zero-cost" on trust. Check it (chapter 14). */

/* --- unique_ptr versus a raw pointer --- */
        void f() {
                auto p = std::make_unique<int>(42);
                use(*p);
        }
/* -O2 aarch64: */
        mov     w0, #4
        bl      operator new(unsigned long)
        mov     w1, #42
        str     w1, [x0]
        ...
        bl      operator delete(void*, unsigned long)
/* EXACTLY new/delete. No overhead, no size cost.

/* --- std::array versus a C array --- */
        int sum(std::array<int, 4> a) {
                return a[0]+a[1]+a[2]+a[3];
        }
/* compiles to the same instructions as the C version, and
   `a.size()` is a compile-time constant.

/* --- a template versus a macro --- */
        template<typename T> T max(T a, T b)
                { return a > b ? a : b; }
/* -> one `csel`, same as the macro, but type-safe and with no
   double-evaluation bug.

/* --- WHERE IT IS *NOT* FREE --- */
        std::function<int(int)> f = [x](int y) { return x + y; };
/* -> possibly a heap allocation, and an indirect call through
   a type-erased interface. Replace with a template parameter
   or a plain lambda passed by value:               */
        template<typename F> void apply(F f) { ... }
/* -> the lambda is inlined completely; zero cost.

/* THE RULE: any abstraction whose type is known at compile
   time is free. Anything that ERASES the type - virtual,
   std::function, dynamic_cast - costs an indirection and
   blocks inlining.                                        */

Static initialisation

C++ runs code before main, to construct global objects. On bare metal that code does not run unless you arrange it, and objects you assumed were initialised simply are not.

/* A C++ global with a non-constant initialiser runs code
   before main (compilers chapter 13). On embedded this needs
   thought.                                                 */

        Device g_device{0x40000000};    /* constructor runs
                                           before main - but
                                           the hardware may
                                           not be initialised
                                           yet!             */

/* THE PROBLEMS:
     1. ORDER across translation units is unspecified
     2. it runs before your clock/PLL setup, potentially
     3. .init_array must be walked by your startup code -
        __libc_init_array() does it, and bare-metal startup
        code must call it
     4. destructors register with __cxa_atexit, which needs
        a heap on some implementations

/* THE FIXES, in order of preference: */

/* (a) make it constexpr - initialised at COMPILE time, ends
       up in .rodata or .data, no code runs:               */
        struct Config { uint32_t rate; uint8_t mode; };
        constexpr Config g_config{48000, 2};

/* (b) construct on first use - ordered by dependency: */
        Device& device() {
                static Device instance{0x40000000};
                return instance;
        }
/* (thread-safe since C++11, via a guard variable and an
   atomic - which is what -fno-threadsafe-statics removes if
   you are single-threaded.)

/* (c) explicit two-phase init - the most common embedded
       pattern: */
        Device g_device;                /* trivially
                                           constructed */
        void system_init() {
                g_device.init(0x40000000);   /* YOU choose
                                                when       */
        }

/* (d) placement new into a static buffer, when you need
       control over both timing and location:              */
        alignas(Device) static std::byte storage[sizeof(Device)];
        Device *dev = new (storage) Device{0x40000000};

/* CHECK WHAT YOU HAVE: */
        readelf -x .init_array prog.elf
        nm prog.elf | grep -i 'global.*ctor\|_GLOBAL__sub_I'
/* An empty .init_array means no static constructors, which is
   the goal for a tightly controlled firmware image.      */

The standard versions

Each standard version added features that matter specifically to systems work, and which one you can use is usually decided by your toolchain rather than by preference.

VersionWhat it added that matters here
C++11auto, move semantics, lambdas, constexpr, nullptr, enum class, unique_ptr, array, <atomic>, the memory model
C++14Relaxed constexpr, generic lambdas, make_unique
C++17string_view, optional, variant, structured bindings, if constexpr, guaranteed copy elision
C++20concepts, ranges, span, consteval, designated initialisers, three-way comparison, modules
C++23expected, mdspan, print, deducing this
 
/* C++17 IS THE PRACTICAL BASELINE for embedded work in 2026:
   universally supported by the toolchains vendors ship, and
   it contains the features that matter most - if constexpr,
   string_view, optional, and guaranteed copy elision.

   C++20's `concepts` and `span` are worth having where the
   toolchain allows; modules are still not practical in most
   embedded toolchains.

   CHECK WHAT YOUR TARGET SUPPORTS before writing the coding
   standard - a vendor GCC 8 in a BSP constrains you to C++17
   partially, and finding that out after writing the code is
   expensive.                                              */
