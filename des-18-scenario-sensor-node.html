Scenario: a battery-powered sensor node

The most common embedded design round there is. Give yourself 45 minutes and a whiteboard before reading past the prompt — the walkthrough is far more useful once you have produced your own answer.

The prompt, as an interviewer would give it

"Design a wireless environmental sensor for commercial buildings. It measures temperature, humidity and CO₂, and reports to a cloud service. It should run for several years without maintenance. Take me through your design."

2 · Budget — and this is where the design is decided

THE CO2 SENSOR IS THE PROBLEM, and finding that quickly is
the point of this scenario.

  An NDIR CO2 sensor draws roughly 30-50 mA while its
  infrared lamp is on, for perhaps 200 ms per measurement.
  Everything else on the board is trivial by comparison.

  PER MEASUREMENT CYCLE:
    CO2 sensor    0.2 s x 40 mA   = 8000 uA-s
    temp/humidity 0.02 s x 0.5 mA =    10 uA-s
    MCU compute   0.01 s x 5 mA   =    50 uA-s
    radio TX      0.1 s x 15 mA   =  1500 uA-s
    ----------------------------------------------
    active total                    9560 uA-s
    sleep                           3 uA continuous

  AT ONE MEASUREMENT PER MINUTE:
    average = 9560/60 + 3 = 159 + 3 = 162 uA
    3000 mAh / 0.162 mA = 18500 h = 2.1 YEARS. Short.

  AT ONE PER 5 MINUTES:
    average = 9560/300 + 3 = 32 + 3 = 35 uA
    3000 / 0.035 = 85700 h = 9.8 years. Comfortable.

  AT ONE PER 15 MINUTES:
    average = 9560/900 + 3 = 10.6 + 3 = 13.6 uA
    -> 25 years, i.e. now limited by the battery's SELF-
       DISCHARGE and shelf life, not by our consumption.

  THE BREAKDOWN AT 5 MINUTES:
    CO2 sensor  84%    radio 16%    everything else ~0%

CONCLUSIONS I WOULD STATE OUT LOUD:
  1. The CO2 sensor dominates completely. Optimising the
     MCU, the sleep current or the radio is pointless
     until that is addressed.
  2. Five-minute reporting meets a 5-year target with
     margin. I would propose that and negotiate.
  3. There is no point going below ~15 minutes: the
     battery's self-discharge becomes the limit.
  4. If one-minute CO2 data is genuinely required, the
     answer is a different sensor technology
     (photoacoustic, or an electrochemical cell) or a
     bigger battery - not firmware optimisation.

MEMORY (chapter 05): BLE stack ~80 kB + app ~50 kB + OTA
slot = ~270 kB flash -> 512 kB part. RAM ~35 kB -> 64 kB.

3 · Partition and architecture

   ONE MCU. There is no hard deadline, no heavy compute and
   no second power domain worth the part - so a second
   processor would be cost with no benefit. Say that
   explicitly: choosing NOT to add something is a decision.

   +---------------------------------------------------+
   |  MCU: Cortex-M4 + BLE, 512 kB flash, 64 kB RAM    |
   |  (an integrated SoC-in-module: pre-certified,      |
   |   removes a part and the RF certification burden)  |
   +---------------------------------------------------+
      |            |              |              |
      | I2C 100k   | I2C          | GPIO         | GPIO
      |            |              |              |
   +--------+  +----------+  +----------+   +----------+
   | T/RH   |  | CO2 NDIR |  | LOAD SW  |   | button + |
   | sensor |  | sensor   |  | for CO2  |   | LED      |
   +--------+  +----------+  +----------+   +----------+
                    ^              |
                    +--------------+
                    power-gated: its sleep current
                    would otherwise exceed our entire
                    budget (chapter 06)

   THE POWER GATE IS THE DETAIL THAT MATTERS. Many NDIR
   sensors draw hundreds of microamps even idle. Gating it
   costs a few cents and is the difference between 5 years
   and 6 months. Note also that the I2C lines must be
   driven low or isolated while it is unpowered, or it
   back-powers through its protection diodes and never
   fully turns off.

   SOFTWARE: a superloop with interrupts, or a very small
   RTOS if the BLE stack requires one (most vendor stacks
   do). There is no real-time requirement, so the
   scheduling is trivial.

     wake on RTC  ->  power up CO2 sensor
                  ->  wait its warm-up time (asleep)
                  ->  read all three sensors
                  ->  power down CO2
                  ->  store reading
                  ->  every Nth cycle: connect, upload
                      batch, disconnect
                  ->  sleep

   BATCHING is worth stating: uploading 12 readings once an
   hour costs one radio session instead of twelve, which
   at 16% of the budget is a further meaningful saving.

5 · Test and manufacture

  DESIGN FOR TEST: SWD and UART on a tag-connect pad; a
  sense resistor in the battery path so the line measures
  sleep current as pass/fail - which on this product is the
  single most valuable production test, because a sleep
  current fault is the difference between 5 years and 6
  months and is invisible functionally.

  PRODUCTION: flash, provision (serial, key, certificate),
  calibrate the CO2 sensor against a reference gas if the
  sensor is not factory-calibrated, exercise both I2C
  devices, verify sleep and active current, lock the
  device.

  FIELD: battery voltage, sleep-current estimate, error
  counters and reset causes all reported as telemetry, so
  a fleet-wide problem is visible before it becomes a
  wave of returns.

  VALIDATION OF THE 5-YEAR CLAIM (chapter 06): measure each
  phase at temperature extremes and at end-of-life battery
  voltage, add self-discharge, then run an accelerated test
  at high duty cycle to confirm the model, plus a long soak
  at the real rate to catch behaviours the model misses -
  a retry storm when the gateway is down, a sensor that
  occasionally fails to sleep.

Follow-up questions

The customer insists on one-minute CO₂ readings. What now?Mid

Present the arithmetic rather than arguing: at one minute the average is about 162 µA giving roughly two years, against about 35 µA and ten years at five minutes. The CO₂ sensor is 84% of that, so no amount of firmware work changes it materially.

Then the options, with costs: a bigger battery — a D-cell Li-SOCl₂ at ~19 Ah gets one-minute reporting to about 13 years, at the cost of size and unit price; a different sensor technology — photoacoustic sensors draw substantially less per measurement, at a higher part cost; a hybrid schedule — measure CO₂ every five minutes normally but switch to one minute when the reading is changing rapidly or above a threshold, which gives the customer responsive data when it matters and costs little on average; mains power where available, with battery as backup.

I would recommend the hybrid schedule, because it usually satisfies the actual need — knowing quickly when CO₂ rises — rather than the stated requirement, and it costs almost nothing.

Listening forAdaptive sampling as a way to satisfy the underlying need, rather than treating the requirement as fixed or impossible.
Why power-gate the CO₂ sensor rather than using its sleep mode?Mid

Because its own sleep current is likely comparable to or larger than our entire budget. At a 35 µA target, a sensor idling at 100 µA makes the design impossible on its own, regardless of what the MCU does. A load switch costs a few cents and takes it to genuinely zero.

The secondary benefit is recovery: an I2C device that has locked the bus can only be reliably recovered by removing its power, so the gate is also the escalation path when bus recovery clocking fails.

The detail that must be got right: with the sensor unpowered but its I2C lines still connected to a powered bus with pull-ups, current flows through its ESD protection diodes and it is partially powered — it may not reset, and it wastes exactly the current you were saving. So either switch the high side, drive the I2C lines low before removing power, or add series resistors sized so the leakage is negligible.

Listening forBack-powering through the I2C lines — the failure that makes a naive power gate ineffective.
How do you handle the CO₂ sensor's warm-up time without wasting energy?Mid

Sleep through it. Power the sensor, set an RTC alarm for its specified warm-up period, and put the MCU into a stop mode — waking only to read the result. The sensor's current is unavoidable; the MCU's is not, and busy-waiting through a 200 ms warm-up at 5 mA would add 1000 µA·s per cycle, comparable to the radio.

The detail: waking from a deep sleep mode costs time and energy itself, and the clock configuration is usually lost, so the wake path must restore it. For a warm-up in the hundreds of milliseconds a deep stop mode is clearly worth it; for a 5 ms wait it may not be, and the crossover is worth computing rather than assuming.

A further optimisation worth mentioning: if the sensor supports a single-shot mode with the lamp on for a shorter period, or a lower-accuracy fast mode, those trade measurement quality for energy directly — and for a building CO₂ trend, lower per-reading accuracy averaged over more readings may be entirely acceptable.

Listening forSleeping through the wait rather than blocking, and the wake-cost crossover.
The gateway is unreachable for two days. What does the device do?Mid

Buffer and back off. Two days at five-minute intervals is 576 readings; at roughly 16 bytes each that is about 9 kB, which fits comfortably in flash or even RAM — so the buffering itself is easy and I would size for considerably longer.

The important behaviours: readings carry their capture timestamp, not the upload time, so the data is still meaningful when it arrives; retries use exponential backoff so the radio does not drain the battery attempting to connect every five minutes for two days; and the backoff has jitter, because when the gateway returns, every device in the building will otherwise reconnect simultaneously and overwhelm it.

When the buffer fills, drop the oldest — for environmental trend data recent readings matter more. But state the choice explicitly, because for an alarm-type product the opposite is right.

And report the outage on reconnection — how long, how many readings lost — so the gap in the data is explained rather than mysterious, and so a fleet-wide gateway problem is visible.

Listening forJitter, capture timestamps, and stating the drop policy as a deliberate choice.
How do you update firmware on a device that is asleep 99.9% of the time?Senior

The device must initiate, since nothing can reach it while it sleeps. On each scheduled upload it asks whether an update is available; if so, it downloads over subsequent connections — in chunks, because a single long radio session is both an energy spike and a failure risk — resuming where it left off if interrupted.

The energy cost must be budgeted: a 200 kB image at BLE throughput is a meaningful fraction of a day's energy, so updates should be rare, compressed, and ideally delta-encoded. It is also worth requesting a faster connection interval for the transfer and restoring the slow one afterwards.

Then the standard protections: verify signature before flashing; A/B slots so an interrupted download cannot brick it; self-confirmation after reboot, where the criterion is "successfully connected and reported version" rather than merely "booted"; and a staged rollout across the fleet, because a bad image that breaks connectivity on a device you can only reach through connectivity is unrecoverable.

That last point deserves emphasis for this product: the device is in a ceiling, non-replaceable battery, five-year life. There is no physical recovery path that is economically viable, so the update mechanism has to be exceptionally conservative.

Listening forChunked resumable download with the energy budgeted, and the recognition that there is no physical fallback.
What would you cut if the BOM had to drop by $3?Senior

I would start from the breakdown: the CO₂ sensor and the radio module are the two large items, and the enclosure is third.

The honest answer is that the biggest single lever is the CO₂ sensor — a cheaper sensing technology, or dropping CO₂ entirely and selling a temperature/humidity-only variant, which is a product decision rather than an engineering one and should be put to the business with the number attached.

Beyond that: move from a pre-certified module to a bare radio chip, which saves several dollars per unit but costs tens of thousands in certification plus RF layout risk — at 50,000 units that is roughly break-even and worth modelling properly. Reduce the battery if the reporting interval can be relaxed further, since we have margin at five minutes. Reduce PCB layers. Use the internal oscillator if the radio does not require a crystal (it usually does, so probably not).

What I would refuse to cut: the load switch on the CO₂ sensor (it is the design), the test pads, and the flash headroom for OTA — because a five-year non-serviceable product without a working update path is a liability that will cost more than $3 a unit.

Listening forNaming the dominant cost item honestly, and refusing the cuts that would compromise the update path.
The interviewer says "now make it work for 10,000 buildings". What changes?Senior

The device barely changes; the system around it changes completely, and recognising that is the point.

Fleet behaviours become emergent: synchronised reconnection after any outage needs jitter; update rollouts must be staged with automatic halt on a falling check-in rate; and telemetry volume becomes a real cost, so what each device reports and how often needs designing rather than defaulting to everything.

Provisioning and identity at scale: per-device keys generated on-device, certificates issued at manufacture, and a revocation path — because with a million devices, some will be stolen, decommissioned or compromised.

Observability: you can no longer investigate individual units. You need fleet-level dashboards — battery distribution, firmware version distribution, error rates by batch and by site — so that a problem affecting 0.5% of devices is visible as a pattern rather than as noise.

Support and logistics: a 0.5% annual failure rate is 50,000 devices; the return process, diagnosis and spares are a business function that must be designed.

And on the device: nothing that requires per-unit human attention can survive at that scale, so provisioning, commissioning and recovery must all be fully automatic.

Listening forThe shift from device design to fleet design, and quantifying what a small failure rate means at scale.
What did you deliberately choose not to do in this design?Senior

No second processor: there is no hard deadline and no heavy compute, so it would be cost and complexity with no benefit. No RTOS beyond whatever the vendor's BLE stack requires: the scheduling is trivial and a superloop with interrupts is simpler to reason about and to certify if that ever becomes relevant.

No secure element: the threat model is a building sensor reporting environmental data, so per-device keys in the MCU's key store with the debug port disabled is proportionate. A secure element would add cost and provisioning complexity for an attacker who gains very little from compromising one sensor.

No local storage beyond a small buffer: there is no requirement to retain data across long outages beyond what fits in flash, and adding external flash would cost a part and pins.

No display, no local UI beyond a button and an LED: every user-facing element is energy and cost, and the product's interface is the cloud service.

I would say all of this out loud, because each is a decision with a reason rather than an omission — and being able to defend what is absent is usually a better signal than adding more.
