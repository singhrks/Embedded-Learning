How an image is represented

An image is a sampled measurement of light, stored as numbers. Every later chapter — colour, compression, drivers — is an argument about which numbers, how many bits each, and in what order in memory. Getting this layer wrong produces green faces, diagonal stripes and off-by-one-row corruption.

A picture is a sampling of a continuous signal

   The world is continuous. A sensor measures it at a grid of
   points, and quantises each measurement to an integer.

     SPATIAL SAMPLING     how many points   -> resolution
     TEMPORAL SAMPLING    how often         -> frame rate
     AMPLITUDE QUANTISING how finely        -> bit depth

   EACH HAS ITS OWN ALIASING ARTEFACT, and naming them is
   half of image work:

     spatial undersampling  -> MOIRE, jagged edges, texture
                               shimmer. Fix: filter BEFORE
                               sampling (an optical low-pass
                               filter, or mipmaps - GPU
                               chapter 9).

     temporal undersampling -> the WAGON-WHEEL effect, judder,
                               strobing. Fix: motion blur, or
                               a higher frame rate.

     amplitude quantising   -> BANDING in gradients. Fix:
                               more bits, or DITHER - adding
                               noise below the quantisation
                               step converts a visible contour
                               into invisible grain.

   Nyquist applies to all three: to represent detail at
   frequency f you must sample at more than 2f. Everything a
   codec does is a controlled violation of this, chosen so the
   error lands where the eye will not look.

Why 8 bits is not enough for a gradient

A smooth sky spanning 100 pixels between two adjacent 8-bit levels produces a visible step — the eye is extremely good at spotting an edge in an otherwise flat area, far better than at judging absolute brightness. This is banding, and it is the single most common visible defect in 8-bit video. Ten bits mostly fixes it; dithering fixes it at 8 bits by trading a contour for noise, which the eye forgives.

Planar, semi-planar and packed

   The same 4 pixels, three ways of arranging them in memory.

   PACKED / INTERLEAVED  - components of one pixel adjacent

     RGBA8:  R0 G0 B0 A0  R1 G1 B1 A1  R2 G2 B2 A2  ...

     + one pointer, one stride
     + perfect for a GPU texture unit reading whole pixels
     - reading only one component wastes bandwidth (GPU
       chapter 4: this is AoS)

   PLANAR - each component in its own contiguous plane

     Y  plane:  Y0 Y1 Y2 Y3 Y4 ...
     Cb plane:  U0 U1 ...
     Cr plane:  V0 V1 ...

     + each plane can have a DIFFERENT RESOLUTION - which is
       the whole point, because chroma is subsampled
       (chapter 3)
     + a filter that only needs luma reads one plane
     - three pointers, three strides, three allocations

   SEMI-PLANAR - luma separate, chroma interleaved

     Y  plane:  Y0 Y1 Y2 Y3 ...
     UV plane:  U0 V0 U1 V1 ...

     + TWO planes, and the chroma pair is fetched in one
       access - which is what hardware codecs and display
       controllers actually want
     -> this is NV12, and it is the most common video pixel
        format in the world.

   THE RULE OF THUMB
     GPUs and image files like PACKED.
     Codecs and display hardware like SEMI-PLANAR.
     Image processing code likes PLANAR.
   Conversions between them are a real cost in every pipeline.

Stride is not width

/* THE SINGLE MOST COMMON BUG IN IMAGE CODE. */

  WIDTH   how many pixels are meaningful in a row
  STRIDE  how many BYTES from the start of one row to the
          start of the next        (also called PITCH)

  stride >= width * bytes_per_pixel,  and often strictly >

  WHY THERE IS PADDING
    * hardware wants each row aligned to 16, 32, 64, 128 or
      256 bytes so a DMA burst or a SIMD load never straddles
    * a 1920-wide NV12 buffer very often has a 1984 or 2048
      byte stride
    * a sub-image (a crop, a tile) has the PARENT's stride

/* WRONG - assumes packed rows. Works on 1920x1080 by luck,
   corrupts on 1922x1080 with a skew that looks like the
   image was sheared. */
for (int i = 0; i < w * h; i++)
        dst[i] = src[i];

/* RIGHT - one row at a time. */
for (int y = 0; y < h; y++)
        memcpy(dst + y * dst_stride,
               src + y * src_stride,
               w * bytes_per_pixel);   /* copy WIDTH, step
                                          STRIDE                */

/* AND FOR CHROMA in a subsampled format, the chroma plane has
   its OWN stride and its own height: */
for (int y = 0; y < h / 2; y++)
        memcpy(dst_uv + y * dst_uv_stride,
               src_uv + y * src_uv_stride,
               w);                     /* NV12: w bytes = w/2
                                          U + w/2 V pairs       */

/* THE DIAGONAL-SKEW SYMPTOM: if an image looks sheared, with
   each row shifted a little further than the last, you have
   used width where stride was needed. The shift per row is
   exactly (stride - width * bpp).                            */
Negative stride is legal and means bottom-up

Windows DIBs, some capture APIs and BMP files store rows bottom-to-top, expressed as a pointer to the last row and a negative stride. Code that computes row * stride handles this automatically; code that computes abs(stride) or assumes the buffer starts at the lowest address produces a vertically flipped image or a buffer underrun. If your image is upside down, check the sign before adding a flip.

Sizing a buffer

/* Get this wrong and you get a heap overflow that shows up as
   corruption in whatever was allocated next. */

size_t plane_size(int stride, int height)   { return (size_t)stride * height; }

/* RGBA8, 1920x1080, 256-byte aligned rows */
        stride = align_up(1920 * 4, 256);        /* 7936        */
        size   = 7936 * 1080;                     /* 8,570,880  */

/* NV12, 1920x1080 */
        y_stride  = align_up(1920, 128);          /* 1920       */
        y_size    = 1920 * 1080;                  /* 2,073,600  */
        uv_stride = y_stride;                     /* same!      */
        uv_size   = uv_stride * (1080 / 2);       /* 1,036,800  */
        total     = y_size + uv_size;             /* 3,110,400  */
                                                  /* = w*h*1.5  */

/* P010 (10-bit NV12), 1920x1080 - each sample is 16 bits with
   the value in the TOP 10, bottom 6 zero. */
        y_stride  = 1920 * 2;                     /* 3840       */
        total     = 3840 * 1080 * 3 / 2;          /* 6,220,800  */

/* THE TRAPS

   1. ODD DIMENSIONS. A 4:2:0 format needs even width and
      height, because chroma is half in each direction.
      1921x1080 either rounds up (and the extra column is
      garbage) or is rejected. Most hardware requires
      multiples of 2, and many require 16.

   2. THE LAST ROW. Some hardware reads a full aligned row
      even for the final line, so the buffer must be a
      multiple of the alignment, not just stride*height.
      Allocators for video usually round the whole thing up.

   3. ALIGNMENT OF THE BASE POINTER, not just the stride.
      A DMA engine may require the buffer itself to be 4 KB
      aligned (Linux chapter 30).                            */

What comes off a sensor

   A camera sensor does NOT produce RGB. Each photosite
   measures one colour, through a BAYER filter:

        R G R G R G          50% green, because the eye is
        G B G B G B          most sensitive to green
        R G R G R G
        G B G B G B

   DEMOSAICING interpolates the two missing components at
   every site. It is the first and most quality-critical step
   of an image pipeline, and it is why a "12 megapixel" camera
   does not have 12 million real RGB measurements.

   THE FULL ISP PIPELINE (SoC chapter on the home page):

     Bayer raw
       -> black level, defective pixel correction
       -> lens shading correction
       -> white balance
       -> DEMOSAIC                    -> now RGB
       -> colour correction matrix    -> a known colour space
       -> gamma / tone curve          -> now non-linear
       -> noise reduction, sharpening
       -> RGB to YCbCr                -> chapter 3
       -> chroma subsampling
       -> to the encoder

   EVERY STAGE IS LOSSY OR OPINIONATED. "Raw" formats
   (DNG, CR2) store the Bayer data so the decisions can be
   made later; JPEG and video store the output, with the
   decisions baked in.
