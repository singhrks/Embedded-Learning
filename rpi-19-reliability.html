Making a Pi survive: read-only root and watchdogs

A Pi on your desk that you reboot daily is one thing. A Pi in a cabinet that must run for two years, lose power without warning, and recover on its own is a different engineering problem — and it is the one that separates a prototype from a product.

What actually kills them

   IN ORDER OF HOW OFTEN IT IS THE CAUSE:

   1. POWER LOSS DURING A WRITE
      The SD card's controller is mid-erase on a block when
      the rail collapses. The block is left indeterminate.
      ext4's journal protects METADATA, not your file's
      contents, and not the FAT boot partition at all.
      -> read-only root, section below

   2. SD CARD WEAR
      Consumer cards are rated in the hundreds of write
      cycles for the cheapest, thousands for good ones.
      Logs, swap and a database will get there.
      -> move writes off the card

   3. UNDER-VOLTAGE (chapter 18)
      Not a distinct failure so much as a cause of 1.

   4. SOFTWARE HANG
      A deadlocked kernel, an OOM storm, a wedged driver.
      The board is powered and unreachable.
      -> watchdog

   5. FILESYSTEM FULL
      Logs grow until nothing can write. Everything fails
      in confusing ways.
      -> log rotation and quotas

   6. HEAT (chapter 18)
      Rarely fatal; commonly the reason a device is slow
      rather than dead.

   NOTE THAT FIVE OF THE SIX ARE STORAGE OR POWER. This is
   why an embedded Linux product spends so much design
   effort on those two things and comparatively little on
   the application.

Read-only root

# The single most effective reliability measure available.
# If nothing writes to the card during normal operation, a
# power cut cannot corrupt it.

# THE EASY ROUTE - Raspberry Pi OS has this built in:
$ sudo raspi-config
#   Performance Options -> Overlay File System -> enable
#   and also set the boot partition read-only

# WHAT IT ACTUALLY DOES: mounts an overlayfs with the SD
# card as a read-only lower layer and a tmpfs as the
# writable upper layer. Writes go to RAM and are DISCARDED
# at reboot. The card is never written.

# THE CONSEQUENCE you must design around: every change is
# lost on reboot. Configuration, logs, state, everything.
# So you need somewhere real for the things that must
# persist.

# --- THE MANUAL VERSION, so you understand what raspi-config
#     did, and can tune it ---

# /etc/fstab
PARTUUID=xxxx-01  /boot/firmware  vfat  ro,noatime          0 2
PARTUUID=xxxx-02  /               ext4  ro,noatime          0 1
tmpfs             /tmp            tmpfs defaults,noatime,size=64M 0 0
tmpfs             /var/log        tmpfs defaults,noatime,size=32M 0 0
tmpfs             /var/tmp        tmpfs defaults,noatime,size=16M 0 0

# noatime matters independently: without it, every READ
# updates an inode timestamp, which is a WRITE. On a
# read-mostly system that is most of your write traffic
# for no benefit.

# A SEPARATE DATA PARTITION for what must survive, mounted
# with the safest options:
PARTUUID=xxxx-03  /data  ext4  rw,noatime,sync,errors=remount-ro  0 2

# sync makes every write hit the card before returning:
# slow, and much harder to corrupt. For a few kilobytes of
# state a day, the cost is irrelevant and the protection is
# real.

# TEMPORARILY WRITABLE, for maintenance:
$ sudo mount -o remount,rw /
$ ... make changes ...
$ sudo mount -o remount,ro /
# Raspberry Pi OS installs `rpi-rw` and `rpi-ro` helpers
# that do exactly this.
Design for "power can be cut at any instant"

Not "power will be cut cleanly", not "the user will shut down properly" — at any instant, including halfway through your write. The test is simple and you should actually run it: pull the plug a hundred times under load and see what happens. Products that survive this were designed for it; products that were not fail in the field at a rate that looks like bad hardware. If your device writes state, write it to a temporary file then rename() — that is atomic on ext4, and it is the whole trick.

Finding and eliminating writes

# Before you can go read-only you need to know what writes.

# Live view of what is writing, per process:
$ sudo apt install iotop
$ sudo iotop -o -a

# Total writes since boot, per device:
$ cat /proc/diskstats
$ vmstat 5

# Catch every write to a path with ftrace (chapter 17):
$ sudo bpftrace -e '
    tracepoint:syscalls:sys_enter_openat
    /str(args->filename) != ""/ {
      @[comm, str(args->filename)] = count();
    }'

# THE USUAL CULPRITS, and their fixes:

#   systemd-journald  -> volatile storage, RAM only
$ sudo mkdir -p /etc/systemd/journald.conf.d
$ printf '[Journal]\nStorage=volatile\nRuntimeMaxUse=16M\n' | \
      sudo tee /etc/systemd/journald.conf.d/volatile.conf

#   rsyslog           -> remove it, or log to tmpfs
#   swap              -> disable entirely on SD
$ sudo systemctl disable --now dphys-swapfile
$ sudo apt purge -y dphys-swapfile

#   man-db, apt, logrotate timers -> disable on an appliance
$ sudo systemctl disable --now man-db.timer apt-daily.timer \
      apt-daily-upgrade.timer

#   dhcpcd / NetworkManager leases -> small, but they exist
#   bash history, .Xauthority, etc -> symlink to /tmp

# MEASURE AGAIN after each change. The goal is zero writes
# to the root device in steady state:
$ awk '/mmcblk0 /{print $10}' /proc/diskstats   # sectors written
# take two readings ten minutes apart; the difference should
# be zero.

The watchdog

# The BCM SoC has a hardware watchdog. If nothing pets it,
# the board resets - which is the only thing that recovers a
# hung kernel.

# Enable the driver, in config.txt if not already present:
dtparam=watchdog=on

$ ls -l /dev/watchdog*
$ dmesg | grep -i watchdog
bcm2835-wdt bcm2835-wdt: Broadcom BCM2835 watchdog timer

# --- THE SIMPLE ROUTE: let systemd own it ---
# /etc/systemd/system.conf
RuntimeWatchdogSec=15
RebootWatchdogSec=2min
ShutdownWatchdogSec=10min

# systemd now pets the hardware watchdog every 7.5s. If
# systemd itself hangs, or the kernel does, the board
# resets. RebootWatchdogSec also catches a shutdown that
# hangs, which is a real and annoying failure.

# --- APPLICATION-LEVEL: the more useful kind ---
# A running kernel with a dead application is the common
# case, and a kernel watchdog will not catch it. Have your
# service tell systemd it is alive:

# myapp.service
[Service]
Type=notify
WatchdogSec=30
Restart=on-failure
NotifyAccess=main

# and in the application:
#include <systemd/sd-daemon.h>
sd_notify(0, "READY=1");
for (;;) {
    do_one_cycle();
    sd_notify(0, "WATCHDOG=1");     /* only if genuinely
                                       healthy - do NOT pet
                                       it from a timer that
                                       runs regardless      */
}

# THE RULE THAT MAKES A WATCHDOG USEFUL: pet it only from
# the place that proves real progress. A watchdog fed by a
# separate thread on a timer will happily keep a completely
# stuck application alive forever, which is worse than no
# watchdog because it hides the fault.

# --- WHY DID IT RESET? ---
$ cat /sys/class/watchdog/watchdog0/bootstatus
$ vcgencmd get_rsts                 # reset source bits
# Record this at boot into your persistent log, or you will
# never know whether a field unit rebooted from a power cut,
# a watchdog, or a clean restart.

Updating in the field

   A read-only, watchdogged appliance still needs updates,
   and "apt upgrade over SSH" is not an update strategy for
   something you cannot reach.

   THE STANDARD PATTERN IS A/B (dual bank):

   +-------------+-------------+-----------+-----------+
   | boot (FAT)  | rootfs A    | rootfs B  |   /data   |
   +-------------+-------------+-----------+-----------+

   1. Running from A. Download the new image, write it to B.
   2. Verify B: checksum, and ideally a signature.
   3. Flip a flag telling the bootloader to try B next.
   4. Reboot.
   5. B boots and must CONFIRM itself within N minutes.
      If it does not, the watchdog resets and the
      bootloader falls back to A.

   Property that matters: a power cut at ANY point leaves a
   bootable system. During step 1 you are still on A; after
   step 4 either B confirms or you fall back to A.

   TOOLS THAT IMPLEMENT THIS - use one rather than writing
   your own, because the failure cases are subtle:
     RAUC, SWUpdate, Mender

   On a Pi the bootloader flip is done with the autoboot
   configuration or by having tryboot select an alternative
   config.txt; the Pi firmware supports a "tryboot" flag
   that boots once from an alternative configuration and
   reverts unless confirmed, which is exactly the primitive
   this pattern needs.

   THE ALTERNATIVE, for a device you can physically reach:
   ship a new SD card. Do not underestimate this - for a
   fleet of ten, it is cheaper than building an update
   system.

How it shows up

SymptomCause
Corruption after a power cutWritable root — go read-only
Card fails after monthsWrite endurance: logs, swap or a database on the card
Config changes lost on rebootWorking as designed with overlayfs — use a data partition
Board powered but unreachableHang with no watchdog enabled
Watchdog enabled, hung app never resetKernel watchdog cannot see a stuck userspace — use WatchdogSec
Watchdog never fires despite a stuck appPetted from a timer rather than from real progress
Reboot loop after an updateNo A/B fallback — the new image is the only image
Cannot tell why a field unit rebootedReset cause not recorded at boot
Filesystem fills up over weeksLogs not rotated or not on tmpfs
Shutdown occasionally hangs foreverNo ShutdownWatchdogSec
