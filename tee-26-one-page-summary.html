One page: the whole track, for revision

Twenty-five chapters of OP-TEE compressed to what you actually need in your head. Nothing here teaches a concept for the first time — every line is a reminder with a chapter number attached. Read it before writing a trusted application, before a port, or whenever you come back to secure-world work after months away.

The eight rules for trusted-world code

Break any of these and the boundary stops meaning anything
  1. Keys never leave the secure world. Not into shared memory, not into a log, not into an error message. Everything else in this track serves this one rule (ch. 16).
  2. Every parameter is attacker-controlled. The framework checks the shape of parameters, not their meaning — and the gap between those is where exploits live (ch. 20).
  3. Copy before you validate. Shared memory can change after your check and before your use, because the normal world still has access to it (ch. 07, 20).
  4. Constant-time comparison for anything secret. An early exit tells the attacker how much of their guess was right (ch. 20).
  5. Clear secrets after use, in a way the compiler cannot remove. It is entitled to delete a write it can prove is never read (ch. 20).
  6. Derive keys from the hardware root; do not store them. Extracting storage should yield nothing usable on another device (ch. 16).
  7. Signatures prove authenticity, never freshness. Rollback needs a counter that the normal world cannot reset (ch. 17).
  8. Replace the default signing key. It ships in the public source tree, so an unmodified build verifies nothing (ch. 14).

The pre-ship checklist

  • The default signing key is replaced, and an unsigned TA is demonstrably rejected.
  • Every parameter from the normal world is validated, after being copied.
  • No secret is ever written to a trace, a log or an error message.
  • Secrets are cleared with a function the compiler may not optimise away.
  • All secret comparisons are constant-time.
  • Keys are derived from the hardware root rather than stored.
  • Rollback protection exists if stored state matters, and RPMB is provisioned if it does.
  • The instance model is chosen deliberately, and state cannot leak between clients.
  • Secure-world context exhaustion has been tested, not assumed impossible.
  • The interface has been fuzzed.
If you remember only one sentence from this track

A trusted execution environment moves a secret somewhere the rest of the device cannot read it — and then hands you an interface through which untrusted code speaks directly to the code holding that secret. Almost every real TEE compromise was not a broken boundary but an ordinary bug in the small amount of code sitting on it.

Check yourself

  • Recite the eight rules without looking.
  • Redraw the stack, placing every component in the correct world and exception level.
  • Trace a client call from the application to the TA and back, naming each layer.
  • Explain why tee-supplicant must be running, and what fails without it.
  • Make each of the six design decisions for a concrete product, and justify it.
  • Explain the difference between the two storage back ends in threat-model terms.
  • Explain why the default signing key makes verification meaningless.
  • Given a symptom, name your first move.
  • Run the pre-ship checklist against a trusted application you have written.
