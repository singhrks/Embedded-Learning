Driver signing

On 64-bit Windows, an unsigned kernel driver does not load. This chapter covers why, the difference between test signing and production signing, and the attestation and HLK paths to a driver that installs on someone else's machine.

Why it is mandatory

A kernel driver runs with complete control of the machine, so being able to load one is equivalent to owning it. Windows therefore refuses to load any kernel driver that is not signed by a key it already trusts — with no exception for correctness or convenience.

A kernel driver runs at ring 0 with full access to memory,
hardware and every other driver. There is no sandbox, no
privilege boundary, and no way to contain a malicious one
after it loads.

  SO WINDOWS ENFORCES CODE INTEGRITY at load time:

     x64 and ARM64        signing REQUIRED, always
     Secure Boot on       the boot chain is verified too
     HVCI enabled         additional requirements: no
                          W+X memory, no dynamic code
     Windows 10 1607+     new kernel drivers must be signed by
                          MICROSOFT, not merely by a
                          certificate you bought

  THAT LAST POINT IS THE ONE THAT SURPRISES PEOPLE. Buying an
  EV code-signing certificate is no longer sufficient by
  itself for a new kernel-mode driver on a clean, Secure-Boot
  system - the driver must carry a Microsoft signature
  obtained through the Partner Center.

  THIS IS THE SAME ARGUMENT as isolation chapter 14's chain of
  trust: the boot ROM verifies firmware, firmware verifies the
  kernel, and the kernel verifies drivers. Break any link and
  the ones above it are decoration.

Test signing

During development you obviously cannot obtain a production signature for every build. Test signing is the supported way round that, and the failure mode when you forget to enable it looks nothing like a signing problem.

# For development, you self-sign and tell the machine to
# accept it.

# --- 1. Enable test mode on the TARGET machine ---
    bcdedit /set testsigning on
    shutdown /r /t 0
# A "Test Mode" watermark appears on the desktop. Expected.

# On a Secure Boot machine you must first DISABLE Secure Boot
# in firmware, or testsigning is refused.

# --- 2. Create a test certificate ---
    makecert -r -pe -ss PrivateCertStore -n "CN=MyTestCert" \
             mytestcert.cer
# The WDK's Visual Studio template does this for you and
# stores it as "WDKTestCert".

# --- 3. Sign the driver and the catalog ---
    inf2cat /driver:. /os:10_x64,10_ARM64
    ; produces mydriver.cat from the INF

    signtool sign /v /s PrivateCertStore /n MyTestCert \
             /t http://timestamp.digicert.com mydriver.cat
    signtool sign /v /s PrivateCertStore /n MyTestCert \
             /t http://timestamp.digicert.com mydriver.sys

# --- 4. Install the certificate on the target ---
    certmgr /add mytestcert.cer /s /r localMachine root
    certmgr /add mytestcert.cer /s /r localMachine \
            trustedpublisher

# --- 5. Verify ---
    signtool verify /v /kp mydriver.sys
    signtool verify /v /c mydriver.cat mydriver.sys

# THE VISUAL STUDIO PROJECT does steps 2, 3 and part of 4
# automatically when "Sign Mode" is set to "Test Sign".
# Configuration Properties -> Driver Signing.

# --- The alternative for quick experiments ---
    bcdedit /set nointegritychecks on
# Disables enforcement entirely. Works, but it also disables
# it for malware, and it masks signature problems you will hit
# later. Prefer test signing.
Never ship a machine in test mode

Test signing disables the guarantee the whole mechanism exists to provide. It is a development convenience on a machine you control. A product that requires testsigning on or nointegritychecks to run is a product with no code integrity, and it will fail every security review it meets.

Production signing

Shipping a driver to real machines means going through Microsoft, not simply signing it yourself. The process has changed several times and the current shape is worth understanding before you plan a release.

   THE MODERN PATH, for a new kernel driver:

   1. GET AN EV CODE SIGNING CERTIFICATE
        from a CA Microsoft recognises (DigiCert, Sectigo,
        GlobalSign...). "EV" means extended validation: a
        hardware token, and identity verification of your
        organisation. Weeks, and a real cost.

   2. REGISTER ON THE MICROSOFT PARTNER CENTER
        for the Hardware Program. The EV certificate is what
        establishes your identity there.

   3. SIGN YOUR PACKAGE with the EV certificate.

   4. SUBMIT IT to the Partner Center as a driver package
        (a .cab or .hlkx).

   5. MICROSOFT SIGNS IT and returns the signed package.
        THAT signature is what makes it load.

   6. OPTIONALLY, distribute via Windows Update.

   TWO SUBMISSION ROUTES:

     ATTESTATION SIGNING
        · you attest that the driver is safe
        · NO test results required
        · fast: often under an hour
        · limited to Windows 10/11, and NOT for drivers that
          need to run on older releases
        · NOT eligible for Windows Update distribution of
          some classes
        -> the right route for most in-house and niche
           hardware

     HLK / WHQL CERTIFICATION
        · run the Hardware Lab Kit test suite
        · produces an .hlkx package with results
        · required for the "Certified for Windows" logo, for
          Windows Update distribution, and for some device
          classes
        · days to weeks of test running and fixing
        -> required for consumer hardware sold at scale

The HLK

Before Microsoft will sign a driver, it must pass an automated test suite that exercises power transitions, removal, stress and correctness. Running it early is far cheaper than discovering the failures at release time.

# The Hardware Lab Kit is the certification test suite. Even
# if you use attestation signing, RUN THE RELEVANT TESTS -
# they find real bugs.

# SETUP:
#   an HLK Controller machine (with SQL Server)
#   an HLK Studio (the UI)
#   one or more TEST SYSTEMS running the HLK Client, with your
#   driver installed
#
# The controller drives the clients, runs tests, and collects
# results into a submission package.

# THE TESTS THAT MATTER MOST for a typical driver:

    Device Fundamentals
      · DF - PNP Disable and Enable
      · DF - PNP Remove and Restart
      · DF - PNP Surprise Remove       <-- chapter 15
      · DF - Sleep and PNP (with IO Before and After)
      · DF - Reboot Restart
      · DF - Concurrent Hardware and Operating System
      · DF - Fuzz tests (IoSpy/IoAttack)  <-- chapter 17
      · DF - Driver Verifier tests        <-- chapter 22

    Static Tools Logo
      · Code Analysis with driver-specific rules
      · Static Driver Verifier              <-- chapter 22
      Both must pass with zero defects.

# RUN THESE EARLY. A driver that fails "PNP Surprise Remove"
# at certification time usually needs architectural changes -
# whereas the same test on day three costs an afternoon.

# THE DEVICE FUNDAMENTALS TESTS ALONE, run with Driver
# Verifier enabled, catch the majority of the bugs this whole
# track has been warning about: IRQL violations, leaked
# resources, unhandled removal, unvalidated IOCTL input.
# They are, in effect, a free test suite for your driver -
# use them as one.

HVCI and additional requirements

On machines with virtualisation-based security enabled, the requirements are stricter still — some coding patterns that load fine elsewhere are rejected outright. This is increasingly the default configuration rather than an exotic one.

/* Hypervisor-protected Code Integrity runs the code integrity
   check inside a VM-isolated environment, so a compromised
   kernel cannot disable it. It is DEFAULT ON for many
   Windows 11 configurations.

   HVCI IMPOSES EXTRA RULES on drivers: */

   1. NO WRITABLE AND EXECUTABLE MEMORY. A driver may not
      allocate memory that is both.
        -> use POOL_FLAG_NON_PAGED, never
           POOL_FLAG_NON_PAGED_EXECUTE unless truly required
        -> no self-modifying code, no dynamically generated
           trampolines

   2. NO SECTION ALIGNMENT SMALLER THAN 4 KB.
        the linker flag /ALIGN:4096, which the WDK templates
        already set

   3. NO EXECUTABLE SECTIONS THAT ARE ALSO WRITABLE.

   4. IMPORT TABLES MUST BE VALID and resolvable.

/* CHECK YOUR DRIVER: */
        Device Guard / HVCI readiness test in the HLK
        DGReadiness.ps1 (the Device Guard readiness tool)

/* THE SYMPTOM if you fail: the driver silently does not load
   on an HVCI system, with an event log entry about code
   integrity. It works perfectly on your development machine
   with HVCI off - which is why testing on an HVCI-enabled
   system is a required part of the matrix, not an
   afterthought.                                            */

/* AND THE DEEPER POINT, which connects to the isolation
   track: HVCI is Windows applying the same reasoning as
   TrustZone (isolation ch. 09) - move the enforcement to a
   more privileged, smaller, separately-verified component,
   so that compromising the large component does not
   compromise the check.                                    */

Verifying a signature

When a driver will not load, the first question is whether the signature is actually valid and trusted on that machine. These commands answer it definitively rather than by inference.

# --- Is this file signed, and by whom? ---
    signtool verify /v /kp mydriver.sys
      Verifying: mydriver.sys
      Signature Index: 0 (Primary Signature)
      Hash of file (sha256): 3A2B...
      Signing Certificate Chain:
          Issued to: Microsoft Windows Third Party Component CA
          ...
      Successfully verified: mydriver.sys

    ; /kp = check against KERNEL POLICY, which is stricter
    ; than the default. Use it - a driver can pass plain
    ; verification and still be refused at load.

# --- Against the catalog ---
    signtool verify /v /c mydriver.cat mydriver.sys

# --- What is actually loaded ---
    WinDbg:  lm                 ; loaded modules
             !chkimg mydriver   ; image integrity
             .imgscan

# --- WHY DID IT NOT LOAD? ---
    Event Viewer ->
      Applications and Services Logs ->
        Microsoft -> Windows -> CodeIntegrity -> Operational

# Event 3004: "Windows is unable to verify the image integrity
# of the file ... because file hash could not be found on the
# system."  -> the catalog is missing or does not cover the
# file.
# Event 3033: "... did not meet the Microsoft signing level
# requirements."  -> signed, but not by an authority this
# policy accepts.

# THESE TWO EVENTS distinguish "no signature" from "wrong
# signature", which is the first thing to establish.

A signing pipeline

Signing is easy to get wrong by hand and easy to automate once. This is the shape of a build that produces a correctly signed package every time without anyone remembering a step.

# What a real build should do, in order:

# 1. BUILD
    msbuild mydriver.sln /p:Configuration=Release \
            /p:Platform=x64

# 2. STATIC ANALYSIS - must be clean before signing
    msbuild /p:RunCodeAnalysis=true
    ; and Static Driver Verifier (chapter 22)

# 3. BUILD THE CATALOG
    inf2cat /driver:.\output /os:10_x64,10_ARM64 /verbose

# 4. VERIFY THE INF
    InfVerif /u .\output\mydriver.inf

# 5. SIGN, with a timestamp
    signtool sign /v /fd sha256 /a \
             /tr http://timestamp.digicert.com /td sha256 \
             .\output\mydriver.cat
    signtool sign /v /fd sha256 /a \
             /tr http://timestamp.digicert.com /td sha256 \
             .\output\mydriver.sys

# THE TIMESTAMP MATTERS: without it, the signature becomes
# invalid when the certificate expires - typically in one to
# three years. With it, the signature remains valid because
# the timestamp proves it was signed while the certificate
# was live. Never sign without /tr.

# 6. VERIFY
    signtool verify /v /kp .\output\mydriver.sys

# 7. PACKAGE for submission
    makecab /f driver.ddf     ; -> mydriver.cab
    ; sign the cab with the EV certificate, then submit

# KEEP THE EV PRIVATE KEY IN ITS HARDWARE TOKEN. It is the
# identity of your organisation to Microsoft; a stolen one
# signs malware in your name, and revoking it invalidates
# every driver you have shipped.
