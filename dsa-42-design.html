Design problems: building a data structure to order

A different genre from everything before it. There is no single return value and no clever insight — you are handed a list of operations and a complexity target for each, and asked to combine two or three structures you already know so that every target is met at once. The skill being tested is composition, and it is entirely learnable.

The method, which is the same every time

Design questions feel open-ended and are not. Working through these five steps out loud is most of the interview, and it reliably produces the intended answer even for a structure you have never seen.

   1. WRITE DOWN THE OPERATIONS AND THEIR TARGETS.
        get(key)     O(1)
        put(key, v)  O(1)
      The targets are the specification. Everything else
      follows from them.

   2. FOR EACH OPERATION, ASK WHAT STRUCTURE GIVES THAT
      COMPLEXITY ON ITS OWN.
        "find by key in O(1)"          -> hash map
        "smallest/largest in O(log n)" -> heap
        "ordered, find predecessor"    -> sorted array + binary
                                          search, or a BST
        "remove from the middle O(1)"  -> doubly linked list
        "random element in O(1)"       -> array

   3. NOTICE THAT NO SINGLE STRUCTURE MEETS ALL OF THEM.
      That is the entire point of the question. If one did,
      it would not be an interview problem.

   4. USE TWO, AND MAKE ONE POINT INTO THE OTHER.
      This is the move. A hash map from key to a NODE inside
      another structure gives you that structure's ordering
      AND O(1) lookup at the same time.

   5. STATE THE INVARIANT THAT KEEPS THEM CONSISTENT,
      then make sure EVERY operation restores it.
      Design bugs are almost never wrong algorithms - they
      are one operation that forgets to update one of the
      two structures.

   ---------------------------------------------------------

   SAY STEP 4 OUT LOUD. "I'll keep a hash map from key to the
   list node, so I get O(1) lookup and O(1) unlink" is the
   sentence the interviewer is waiting for.

The pairings worth memorising

Almost every design question asked in interviews is one of these five combinations. Recognising the pairing turns a twenty-minute puzzle into a five-minute implementation.

RequirementCombinationClassic problem
O(1) lookup and a recency orderHash map → doubly linked list nodeLRU cache
O(1) insert, delete and randomArray + hash map from value to its indexInsert Delete GetRandom
Lookup by key, then search within itHash map → sorted array, binary searchTime-based key-value store
Running median, or top-K under updatesTwo heaps, or a heap plus a lazy-deletion setFind median from a stream
Fixed memory, O(1) push and pop at both endsArray plus two indices, modularCircular buffer

The second row generalises further than it looks: "swap with the last element, then pop" is how you delete from an array in O(1) whenever order does not matter, and it appears well outside design questions.

The LRU cache, drawn

It is the most-asked design question there is, and the only genuinely fiddly part is the list surgery. A picture of the invariant makes the code write itself.

   TWO STRUCTURES, ONE INVARIANT.

   map:   key -> node

   list:  head <-> A <-> B <-> C <-> tail
          ^^^^                       ^^^^
          MOST RECENT          LEAST RECENT

   INVARIANT: the map contains exactly the nodes in the list,
   and the list is ordered by recency.

   get(key):
        node = map[key]; if missing -> -1
        UNLINK node, RELINK at head
        return node.value

   put(key, value):
        if present: update value, move to head
        else:
            create node, link at head, map[key] = node
            if size > capacity:
                victim = tail.prev
                UNLINK victim
                delete map[victim.key]     <- the line people
                                              forget

   ---------------------------------------------------------

   WHY DUMMY head AND tail NODES.

   Without them, every unlink needs "is this the first node?
   is it the last?" and those branches are where the bugs
   live. With two sentinels that never move, unlink is
   unconditional:

        node.prev.next = node.next;
        node.next.prev = node.prev;

   FOUR LINES OF SETUP TO DELETE TWELVE LINES OF SPECIAL
   CASES. This is worth doing every single time.

   ---------------------------------------------------------

   AND THE TWO THINGS TO SAY OUT LOUD:

     · the eviction must delete from BOTH structures, or the
       map grows without bound and you have written a memory
       leak rather than a cache
     · you must store the KEY inside the node, not only the
       value - otherwise you cannot find the map entry to
       delete when you evict. This is the single most common
       bug in the problem.

Check yourself

  • List the five steps of the method, in order.
  • Given "O(1) lookup and an ordering", name the pairing without thinking.
  • Explain what a hash map pointing at a list node buys you.
  • State the LRU invariant and name every operation that must restore it.
  • Say why sentinel nodes are worth the extra setup.
  • Explain why the node must store the key as well as the value.
  • Describe the O(1) array deletion trick and when it is legal.
  • Explain how to distinguish a full ring buffer from an empty one.
  • Say what you would state aloud before writing any code.
