Interrupts, timers and timekeeping

Interrupts are how hardware gets the kernel's attention, and timers are how the kernel gets its own. Both are governed by one constraint: the code that runs in interrupt context is severely restricted, and everything else about the design follows from working around that.

Interrupt context

Code running in response to an interrupt operates under restrictions ordinary code does not. Knowing precisely what those are is the foundation for everything else in this chapter.

The rule everything else follows from

An interrupt handler runs in a borrowed context: on some arbitrary thread's kernel stack, with interrupts partly or fully masked, and with no task to schedule away from. Therefore it cannot sleep. No mutex, no GFP_KERNEL allocation, no copy_to_user, no waiting for I/O. Violating this deadlocks the machine.

Windows expresses the same constraint as IRQL: at DIRQL and DISPATCH_LEVEL you may not touch pageable memory or wait. Linux calls it "atomic context". The concept is identical.

   device asserts its interrupt line, or writes an MSI
        │
   interrupt controller (GIC) prioritises and routes to a core
        │
   CPU takes the exception  (ARM chapters 24, 28)
        │
   ┌────▼──────────────────────────────────────────┐
   │  TOP HALF / ISR — runs with interrupts masked   │
   │    · read status, confirm it is OURS            │
   │    · ACKNOWLEDGE at the DEVICE                  │
   │    · grab anything volatile                     │
   │    · schedule the bottom half                   │
   │    · return                                     │
   │  Must be SHORT. Every microsecond here is       │
   │  added latency for every other interrupt.       │
   └────┬──────────────────────────────────────────┘
        │
   ┌────▼──────────────────────────────────────────┐
   │  BOTTOM HALF — deferred, interrupts enabled     │
   │    the real work                                │
   └───────────────────────────────────────────────┘

  The split exists solely because the top half runs with interrupts
  disabled. Anything you do there delays every other device.

/* Threaded IRQ: a tiny hard handler plus a sleepable thread.
   This is what you should reach for first.                  */
devm_request_threaded_irq(dev, irq,
                          my_hard_isr,   /* atomic: ack, return */
                          my_thread_fn,  /* may sleep           */
                          IRQF_ONESHOT, dev_name(dev), d);

static irqreturn_t my_hard_isr(int irq, void *p)
{
        struct my_dev *d = p;
        u32 st = readl(d->regs + STATUS);

        if (!(st & IRQ_PENDING))
                return IRQ_NONE;        /* not ours — ESSENTIAL on a
                                           shared line, or the core
                                           cannot detect a stuck IRQ */
        writel(st, d->regs + STATUS);   /* W1C: clear at the SOURCE  */
        d->last_status = st;
        return IRQ_WAKE_THREAD;
}

/* PREEMPT_RT makes ALL interrupt handlers threaded by default —
   which is how it achieves bounded latency, at some throughput
   cost.                                                       */
The interrupt storm

Clear the interrupt at the controller but not at the device, and a level-triggered line re-asserts immediately. The core does nothing but enter and leave the handler forever; the system appears hung with 100% CPU in the ISR. Always clear the condition at the source first, then acknowledge upward. Linux's spurious-interrupt detector will eventually disable the line and log "nobody cared" — which is a diagnosis, not a fix.

Edge versus level

An interrupt signals in one of two ways, and the difference is not merely electrical: it determines whether missing one loses it forever or merely delays it, and whether a badly written handler produces a storm.

Level-triggeredEdge-triggered
AssertedWhile the condition holdsOn the transition only
SharingPossible — each handler checks and clears its ownUnsafe: two simultaneous edges register as one
Missed interruptsCannot be missed — the line stays assertedCan be lost if masked during the edge
Failure modeStorm, if never clearedSilent hang, waiting for an event that already happened
 
/* The classic edge-triggered race, and the standard fix: */
static irqreturn_t isr(int irq, void *p)
{
        do {
                status = readl(STATUS);
                handle(status);
                writel(status, STATUS);        /* clear */
        } while (readl(STATUS) & PENDING);     /* RE-CHECK before
                                                  returning — a new
                                                  event may have
                                                  arrived while we
                                                  were handling      */
        return IRQ_HANDLED;
}
/* Without the loop, an event arriving between handle() and return
   produces no new edge and is lost forever. The device then waits
   for a response that never comes.                             */

MSI: interrupts as memory writes

Modern buses signal interrupts by writing to memory rather than asserting a wire, which removes the sharing problems of line-based interrupts and allows far more of them per device.

WIRED interrupt              MESSAGE-SIGNALLED (MSI/MSI-X, ARM LPI)
  a physical line              a WRITE to a special address
  pin-limited → shared         thousands per device, never shared
  needs "is it mine?"          the vector identifies the source
  can arrive BEFORE the DMA    arrives IN ORDER with the DMA data,
  data it announces            because it is the same bus stream

That last point is not a minor detail. With a wired interrupt, a
driver must issue a read (a "PCI posting flush") to guarantee the
DMA data has landed before it reads the buffer. With MSI the
ordering is free, which removes a subtle and common data-corruption
bug.

  cat /proc/interrupts        # PCI-MSI entries vs IO-APIC/GIC-SPI
  lspci -vv | grep -A3 MSI-X

Interrupt routing and affinity

On a multiprocessor machine, which core handles an interrupt is configurable and matters for both latency and cache behaviour — with the usual caveat that manual tuning makes things worse about as often as better.

# which CPU handles which interrupt?
cat /proc/interrupts
#            CPU0    CPU1    CPU2    CPU3
#  24:     102394       0       0       0   GICv3  35 Level  eth0

# all on CPU0 is a scalability problem. Spread them:
cat /proc/irq/24/smp_affinity_list
echo 2 > /proc/irq/24/smp_affinity_list      # pin to CPU2

# irqbalance does this automatically — and is usually wrong for
# latency-sensitive or RT workloads. Disable it and pin by hand:
systemctl stop irqbalance

# keep interrupts OFF your real-time cores entirely
# kernel cmdline: isolcpus=2,3 nohz_full=2,3 irqaffinity=0,1

# network multi-queue: one IRQ per queue, pinned per core, with RSS
# steering flows to queues. This is how a NIC scales past one core.
ethtool -l eth0
ethtool -L eth0 combined 4

/* A good clocksource must be: monotonic, constant-rate (not
   affected by CPU frequency), synchronised across cores, and
   cheap to read. Early x86 TSC failed several of these, which is
   why HPET existed and why "unstable TSC" messages mattered.

   ARM's generic timer is architected: same behaviour on every
   implementation, readable from EL0 without a trap, which is what
   makes the vDSO clock_gettime possible (OS chapter 03).      */

The tick, and doing without it

Traditionally the kernel interrupted itself at a fixed rate to keep time and make scheduling decisions. Modern systems avoid that when idle, which saves substantial power and complicates timekeeping.

PERIODIC TICK — the traditional design
   a timer interrupt every 1/HZ seconds (HZ = 100, 250 or 1000)
   each tick: update jiffies, run expired timers, account CPU
              time, check whether to preempt

   Simple. But it wakes the CPU 1000 times a second even when
   completely idle, preventing deep sleep states (CA chapter 20).

TICKLESS IDLE (NO_HZ_IDLE) — the default
   when a CPU goes idle, program the timer for the NEXT actual
   deadline instead of the next tick. An idle laptop can sleep
   for seconds at a time.

FULL TICKLESS (NO_HZ_FULL)
   suppress the tick even while RUNNING, if only one task is
   runnable on that CPU. Removes ~1000 interruptions per second
   from a latency-critical thread.
      kernel cmdline: nohz_full=2,3 rcu_nocbs=2,3 isolcpus=2,3
   Combined with IRQ affinity and a pinned RT thread, this is the
   standard recipe for microsecond-class latency on Linux.
/* jiffies: the tick counter. Still used, and still a trap. */
unsigned long timeout = jiffies + msecs_to_jiffies(500);

if (time_after(jiffies, timeout))       /* CORRECT               */
if (jiffies > timeout)                  /* WRONG — breaks on the
                                           32-bit wrap, which on a
                                           1000 HZ system happens
                                           every 49.7 days       */
/* time_after/time_before do signed subtraction, which is correct
   across wraparound. Use them always.                          */

Kernel timers

Kernels provide timers at more than one resolution, with quite different costs, and choosing the wrong one gives you either unnecessary overhead or unacceptable jitter.

/* Low resolution — jiffy granularity, very cheap, batched */
struct timer_list t;
timer_setup(&t, callback, 0);
mod_timer(&t, jiffies + msecs_to_jiffies(100));
del_timer_sync(&t);            /* MUST be _sync before freeing —
                                  waits for a running callback   */

/* High resolution — nanosecond, backed by a clockevent */
struct hrtimer h;
hrtimer_init(&h, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
h.function = callback;
hrtimer_start(&h, ms_to_ktime(10), HRTIMER_MODE_REL);
hrtimer_cancel(&h);

/* Short delays, no timer needed */
udelay(50);       /* BUSY-WAIT. Atomic context OK. Keep under
                     ~100 µs — you are burning a CPU.           */
usleep_range(100, 200);   /* SLEEPS. Process context only. The
                             range lets the kernel BATCH your
                             wakeup with others, saving power.  */
msleep(20);

/* Never usleep_range with a zero-width range: it defeats batching
   and wakes the CPU precisely for you alone.                   */

Time in user space

Applications reach all of this through a set of APIs that hide the hardware, and knowing which clock each uses matters as soon as you care whether time can jump backwards.

struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);      /* durations — NEVER jumps */
clock_gettime(CLOCK_REALTIME, &ts);       /* wall clock — CAN jump   */
clock_gettime(CLOCK_BOOTTIME, &ts);       /* monotonic + suspend time */

/* Served by the vDSO: no syscall, ~25 ns. */

/* precise periodic work, without drift */
struct timespec next;
clock_gettime(CLOCK_MONOTONIC, &next);
for (;;) {
        next.tv_nsec += 1000000;                /* +1 ms */
        if (next.tv_nsec >= 1000000000) { next.tv_nsec -= 1000000000; next.tv_sec++; }
        clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);
        do_work();
}
/* ABSOLUTE deadlines. Sleeping for a RELATIVE 1 ms accumulates the
   work time plus wakeup jitter into permanent drift.          */

/* timerfd: a timer as a file descriptor — integrates with epoll */
int tfd = timerfd_create(CLOCK_MONOTONIC, 0);
timerfd_settime(tfd, 0, &spec, NULL);
Never measure durations with CLOCK_REALTIME

NTP steps it, daylight saving changes it, an administrator can set it backwards, and a virtual machine can have it jump on migration. Durations computed from it go negative or enormous. Use CLOCK_MONOTONIC for anything you subtract, and CLOCK_REALTIME only for timestamps a human will read.

Interrupt latency

The delay between a device signalling and your code responding is a sum of several distinct contributions. Knowing what they are is the only way to reduce it deliberately.

   device asserts
        │  ← hardware propagation, GIC arbitration
        │  ← INTERRUPTS DISABLED somewhere in the kernel  ◄── the
        │     (a spinlock, a critical section)                variable
        │  ← exception entry, register save                   part
        │  ← handler dispatch
        ▼
   your ISR's first instruction

  Total latency = hardware + longest interrupts-disabled region
                + entry cost

  The DOMINANT and most variable term is the interrupt-disabled
  time somewhere else in the kernel. This is exactly what
  PREEMPT_RT attacks: it converts most spinlocks to sleeping
  mutexes and threads the handlers, bounding that term.

  Measuring it:
     cyclictest -t4 -p 90 -i 200 -m -D 3600
     → report the MAXIMUM, not the average. The average is
       always fine; the maximum is what breaks deadlines.

     ftrace: irqsoff and preemptoff tracers find the exact
     longest region and its stack trace.
         echo irqsoff > /sys/kernel/debug/tracing/current_tracer
         cat /sys/kernel/debug/tracing/trace
