The monitor, QMP and snapshots

QEMU has a control channel into a running machine that can inspect memory, dump registers, add and remove devices, and freeze the whole system into a file. Two interfaces expose it: one for humans and one for programs. The human one is the fastest debugging tool in this track.

HMP and QMP

   HMP - Human Monitor Protocol
       terse, text, tab-completion, stable enough for daily use
       but NOT a stable API.
       Reach it with:  -monitor stdio
                       Ctrl-A c   (with -nographic)
                       -monitor telnet::4444,server,nowait

   QMP - QEMU Machine Protocol
       JSON, versioned, introspectable, the actual API. libvirt
       speaks this. Scripts should too.
       Reach it with:  -qmp unix:/tmp/qmp.sock,server,nowait
                       -qmp tcp::4444,server,nowait
                       -qmp stdio

   You can have both at once, and usually should:

     -monitor unix:/tmp/hmp.sock,server,nowait \
     -qmp     unix:/tmp/qmp.sock,server,nowait

   And you can run an HMP command through QMP when a QMP
   equivalent does not exist:

     {"execute":"human-monitor-command",
      "arguments":{"command-line":"info mtree"}}

(qemu) dump-guest-memory /tmp/guest.core
$ crash vmlinux /tmp/guest.core
info registers on a hung guest

A guest that stops responding is not a black box. Press Ctrl-A c, type info registers, and you have the PC, the exception syndrome and the exception link register — which is more than a kernel oops would have given you, and you did not need the guest to be healthy enough to print it.

QMP, properly

$ qemu-system-aarch64 -M virt ... \
    -qmp unix:/tmp/qmp.sock,server=on,wait=off

# Talk to it. Every session starts with a greeting, then you
# must leave capabilities negotiation before anything works:
$ socat - UNIX-CONNECT:/tmp/qmp.sock
{"QMP": {"version": {"qemu": {"major": 8, "minor": 2}}, ...}}
{"execute":"qmp_capabilities"}
{"return": {}}
{"execute":"query-status"}
{"return": {"status": "running", "singlestep": false, "running": true}}

# From Python, which is how you should automate it. QEMU ships
# the client library:
$ pip install qemu.qmp
#!/usr/bin/env python3
"""Wait for a guest to boot, snapshot it, and pull stats."""
import asyncio
from qemu.qmp import QMPClient

async def main():
    qmp = QMPClient('vm')
    await qmp.connect('/tmp/qmp.sock')

    # What can this QEMU do?
    cmds = await qmp.execute('query-commands')
    print(len(cmds), 'commands available')

    # Machine state
    print(await qmp.execute('query-status'))
    print(await qmp.execute('query-cpus-fast'))
    print(await qmp.execute('query-block'))

    # Wait for the guest to signal readiness. Events are the
    # right way to synchronise - never sleep and hope.
    await qmp.execute('cont')
    async for event in qmp.events:
        print('EVENT', event['event'])
        if event['event'] == 'RESET':
            break

    # Snapshot the whole machine
    await qmp.execute('human-monitor-command',
                      {'command-line': 'savevm booted'})

    # Add a disk while it runs
    await qmp.execute('blockdev-add', {
        'node-name': 'extra',
        'driver': 'qcow2',
        'file': {'driver': 'file', 'filename': 'extra.qcow2'},
    })
    await qmp.execute('device_add', {
        'driver': 'virtio-blk-pci', 'drive': 'extra', 'id': 'blk1',
    })

    await qmp.disconnect()

asyncio.run(main())

Events: the synchronisation primitive

# QMP pushes events asynchronously. Waiting for one is how a
# test harness knows when to act.

{"event": "RESET",          "data": {"guest": true}, ...}
{"event": "SHUTDOWN",       "data": {"guest": true, "reason": "guest-shutdown"}}
{"event": "STOP"}
{"event": "RESUME"}
{"event": "POWERDOWN"}
{"event": "GUEST_PANICKED",  "data": {"action": "pause"}}
{"event": "DEVICE_TRAY_MOVED"}
{"event": "BLOCK_IO_ERROR",  "data": {"device": "hd0", "operation": "write"}}
{"event": "MIGRATION",       "data": {"status": "completed"}}
{"event": "VSERPORT_CHANGE"}

# A CI harness in eight lines of shell + socat:
$ (echo '{"execute":"qmp_capabilities"}'; cat) \
  | socat - UNIX-CONNECT:/tmp/qmp.sock \
  | while read -r line; do
        case "$line" in
          *GUEST_PANICKED*) echo "FAIL: guest panicked"; exit 1;;
          *SHUTDOWN*)       echo "PASS: clean shutdown";  exit 0;;
        esac
    done

# Make a panic detectable rather than a hang:
$ qemu-system-aarch64 ... -no-reboot \
    -device pvpanic-pci
# The guest's panic handler writes to the pvpanic device, QEMU
# emits GUEST_PANICKED, and your harness fails fast instead of
# waiting for a timeout.

Migration, and its offline uses

# Migration serialises the entire machine. That is useful even
# when you are not moving anything anywhere.

# 1. Save a machine to a file and restore it later:
(qemu) migrate "exec:gzip -c > state.gz"
# start a NEW qemu with identical arguments plus -incoming:
$ qemu-system-aarch64 ...same args... \
    -incoming "exec:gzip -dc state.gz"

# 2. Move a running guest to another machine:
#    destination:
$ qemu-system-aarch64 ...same args... -incoming tcp:0:4444
#    source:
(qemu) migrate -d tcp:dest-host:4444
(qemu) info migrate
capabilities: xbzrle: off  postcopy-ram: off
Migration status: completed
total time: 4213 ms
downtime: 87 ms

# 3. Requirements people trip over:
#    - IDENTICAL command line on both ends, including the
#      versioned machine type (virt-8.2, not virt)
#    - the same QEMU version, or a compatible one
#    - shared or replicated storage, unless you use
#      --copy-storage-all
#    - NO passed-through devices (virt chapter 16)
#    - the same CPU model; -cpu host will refuse across
#      different silicon

# 4. Tuning, when it will not converge:
(qemu) migrate_set_parameter max-bandwidth 1G
(qemu) migrate_set_parameter downtime-limit 300
(qemu) migrate_set_capability auto-converge on   # throttle the
                                                 # guest until
                                                 # it converges
(qemu) migrate_set_capability postcopy-ram on    # switch over
                                                 # first, fault
                                                 # pages after
Snapshot before the hard part

Reproducing a bug that needs ten minutes of setup is the most wasteful thing in embedded debugging. savevm just before the interesting moment turns every subsequent attempt into loadvm plus one second. Combine it with -icount (chapter 2) and the replay is deterministic too.
