Mutexes in practice

The primitive is simple; using it well is a set of habits. What a lock protects, how long you hold it, whether you can take two, and never — under any circumstances — releasing it by hand on an error path.

A lock protects an invariant, not a variable

A lock does not protect a variable; it protects an invariant. Thinking in terms of invariants rather than data is what tells you where the critical section actually begins and ends.

   THE QUESTION THAT PREVENTS MOST LOCK BUGS

     "What is true when this lock is not held?"

   If you cannot answer in one sentence, the lock is
   decoration.

   BAD: "m protects `count`."
        Then what protects the relationship between `count`
        and the buffer it counts? Two locks, two invariants,
        and a window between them.

   GOOD: "m protects the queue: `head`, `tail`, `count` and
          the elements between head and tail are mutually
          consistent whenever m is not held."

   Now every rule follows from the sentence:
     - you may not read `count` without m, because the
       invariant only holds while m is unheld and you are
       observing it mid-update otherwise
     - you must restore ALL of it before unlocking
     - a function that returns a pointer INTO the queue has
       leaked the invariant past the lock, and is wrong

   WRITE THE SENTENCE IN A COMMENT NEXT TO THE LOCK. It is the
   single highest-value comment in concurrent code, and the
   one people never write.
/* What that looks like in a header. */

struct queue {
        /* @lock protects every field below it: head, tail and
         * count are mutually consistent, and elements
         * [head, tail) are initialised, whenever @lock is not
         * held. Callers must not retain pointers to elements
         * after releasing @lock.
         */
        pthread_mutex_t lock;
        struct item    *head, *tail;
        size_t          count;
};

/* The kernel writes this as a lockdep-checkable annotation;
   C++ has an analyser attribute for it:                    */

class Queue {
    std::mutex m_;
    size_t     count_ GUARDED_BY(m_);      /* clang thread
                                              safety analysis */
public:
    size_t size() { std::lock_guard<std::mutex> g(m_);
                    return count_; }
};
/* -Wthread-safety turns "read count_ without m_" into a
   COMPILE ERROR. It is underused and nearly free.          */

Never unlock by hand

Unlocking on every exit path — including exceptions and early returns — is exactly the problem scope-bound resource management solves. In practice this removes the majority of lock-leak bugs structurally.

/* THE BUG, in every codebase that uses manual unlock. */

int process(struct queue *q, int x)
{
        pthread_mutex_lock(&q->lock);

        if (x < 0)
                return -EINVAL;              /* LOCK LEAKED   */

        if (q->count == 0) {
                pthread_mutex_unlock(&q->lock);
                return -EAGAIN;              /* fine, for now */
        }

        do_work(q);                          /* if this throws
                                                or longjmps:
                                                LOCK LEAKED   */
        pthread_mutex_unlock(&q->lock);
        return 0;
}
/* Someone adds a fourth early return in six months, and the
   process deadlocks the next time that path is taken.      */

/* C++: RAII. The destructor cannot be forgotten and runs on
   exceptions too. */
int process(Queue &q, int x)
{
        std::lock_guard<std::mutex> g(q.m);   /* one line     */
        if (x < 0)      return -EINVAL;       /* unlocked      */
        if (q.empty())  return -EAGAIN;       /* unlocked      */
        do_work(q);                           /* throws? still
                                                 unlocked      */
        return 0;
}
/* std::scoped_lock (C++17) is the same and takes N mutexes
   deadlock-free. Prefer it: std::lock_guard has no advantage. */

/* Rust: the data is INSIDE the mutex, so there is no way to
   touch it without locking, and the guard unlocks on drop. */
let q = Mutex::new(Queue::new());
{
    let mut g = q.lock().unwrap();
    g.push(item);
}   // unlocked here, always

/* C, with GCC/Clang: */
static inline void unlock_p(pthread_mutex_t **m) {
        pthread_mutex_unlock(*m);
}
#define LOCKED(mtx) \
        pthread_mutex_t *__l __attribute__((cleanup(unlock_p))) \
                = &(mtx); pthread_mutex_lock(__l)

int process(struct queue *q, int x)
{
        LOCKED(q->lock);
        if (x < 0) return -EINVAL;      /* unlocked correctly */
        ...
}
Rust's real contribution

Other languages give you a lock and a separate piece of data and trust you to pair them. Rust makes Mutex<T> own the T, so accessing the data without holding the lock is not a bug you might make — it is code that does not compile. That single design choice removes the entire "forgot to take the lock" category, which is most of this chapter.

Recursive mutexes are a design smell

They exist so that a function holding a lock can call another function that takes the same lock. That situation means you do not know your own locking structure. The real cost is that the invariant is only guaranteed at the outermost unlock — so the inner function sees the data mid-update and cannot tell. The fix is to split each public function into a locking wrapper and an unlocked _locked worker, which also documents which is which.

/* The pattern that removes the need for recursion. */

static void queue_push_locked(struct queue *q, struct item *i)
{
        /* caller MUST hold q->lock. Name says so. */
        ...
}

void queue_push(struct queue *q, struct item *i)
{
        LOCKED(q->lock);
        queue_push_locked(q, i);
}

void queue_push_many(struct queue *q, struct item **v, size_t n)
{
        LOCKED(q->lock);                    /* taken ONCE     */
        for (size_t k = 0; k < n; k++)
                queue_push_locked(q, v[k]);
}

How much to protect, and for how long

One big lock is simple and serialises everything; many small locks are concurrent and risk deadlock. The choice is a genuine engineering trade-off, and the right answer is usually less fine-grained than people expect.

/* TOO COARSE: one lock for everything.
   Correct, simple, and it serialises your whole program. */

/* TOO FINE: a lock per element.
   More memory than the data, more time in locking than in
   work, and now you can deadlock by taking two. */

/* HOLD TIME is usually the bigger lever than granularity: */

/* BAD - I/O inside the critical section. */
{
        std::lock_guard<std::mutex> g(m);
        auto v = cache[k];
        write_to_disk(v);            /* 10 ms, holding the lock,
                                        blocking every other
                                        thread                 */
}

/* GOOD - copy out, then work. */
Value v;
{
        std::lock_guard<std::mutex> g(m);
        v = cache[k];                /* microseconds          */
}
write_to_disk(v);                    /* nobody is blocked     */

/* THE RULES

   1. Never call into unknown code while holding a lock. A
      callback, a virtual function, an allocator or a logger
      may take another lock and deadlock you (chapter 14).
   2. Never do I/O or sleep while holding a lock.
   3. Never allocate while holding a hot lock if you can
      avoid it - malloc has its own locks.
   4. Copy small things out and release; do not hold a lock
      across expensive work.
   5. If the critical section is one atomic-sized update, use
      an atomic instead (chapter 11).                        */

Measuring contention

Lock contention is invisible in source code and very visible in performance. These are the ways to find out which lock is actually the bottleneck rather than guessing and optimising the wrong one.

# Is the lock actually contended, or are you guessing?

$ perf lock record ./app && perf lock report
 Name   acquired  contended  avg wait    max wait   total wait
 &q->lock  184291      41082   1.42 us   9.81 ms     58.3 ms

$ perf stat -e 'syscalls:sys_enter_futex' -p $(pidof app)
# a large futex count means real contention: the fast path is
# not being taken

# In the kernel:
$ echo 1 > /proc/sys/kernel/lock_stat
$ cat /proc/lock_stat

# The number that matters is CONTENDED / ACQUIRED. Below a few
# percent, leave it alone. Above ten percent, either shrink
# the critical section or split the lock - and measure again,
# because splitting a lock often just moves the queue.
