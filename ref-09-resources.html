Books, manuals and practice environments

Where to go after this site. The primary sources, the books worth owning, and — more importantly — the hardware and exercises that turn reading into competence.

Primary sources

   READ THE SPECIFICATION. Not a blog post about the
   specification.

   This is the single habit that separates engineers who
   can solve novel problems from those who can only apply
   remembered patterns. Secondary sources are for
   orientation; the primary source is where the answer
   actually is, and it is usually free.

   ARM
     ARM Architecture Reference Manual (ARM ARM) for
       Armv8-A / Armv9-A - the definitive text. Enormous.
       Use it for lookup, never linearly.
     Armv8-M Architecture Reference Manual
     Cortex-M Technical Reference Manuals - per-core
     Procedure Call Standard (AAPCS) - the ABI
     ARM Cortex-M Generic User Guide - the practical
       subset, and the right place to start
     TrustZone, SMMU and GIC architecture specifications
     -> developer.arm.com/documentation

   YOUR SILICON VENDOR
     The REFERENCE MANUAL - every register, every bit
     The DATASHEET - electrical, timing, pinout
     The ERRATA SHEET - READ THIS ONE. It explains
       behaviour the reference manual does not.
     Application notes - often excellent and overlooked

   LINUX
     The kernel source itself. Documentation/ is
       substantial and current.
     Documentation/process/ - how to contribute
     lore.kernel.org - mailing list archives, where the
       reasoning lives
     elixir.bootlin.com - the best kernel source browser
       there is
     LWN.net - the best technical journalism in the field.
       Subscribe; it funds the writing.

   WINDOWS
     learn.microsoft.com/windows-hardware/drivers
     The WDK samples on GitHub - genuinely good starting
       points
     The Windows Internals books (below)

   STANDARDS
     ISO C (N3220 for C23 drafts; the drafts are free)
     ISO C++ (eel.is/c++draft, and cppreference.com for
       daily use)
     RFCs - rfc-editor.org. TLS is RFC 8446; ChaCha20-
       Poly1305 is RFC 8439.
     NIST FIPS and SP 800 series for cryptography

Hardware to learn on

/* YOU CANNOT LEARN EMBEDDED SYSTEMS WITHOUT HARDWARE. Buy
   something. The total cost of a genuinely capable bench is
   under three hundred dollars.                          */

/* --- BOARDS, roughly in order of what to get first --- */
    RASPBERRY PI PICO / PICO 2       ~$5
      Dual Cortex-M0+/M33, and the RP2040/RP2350's PIO is a
      genuinely novel and instructive peripheral. Excellent
      documentation. START HERE if you have nothing.

    ST NUCLEO or DISCOVERY           ~$15-30
      Cortex-M0 to M7, ON-BOARD ST-LINK, huge community.
      The most practical general-purpose learning platform.

    NORDIC nRF52840-DK               ~$50
      Bluetooth, TrustZone-M on the nRF5340/nRF54, and
      Zephyr support. For wireless and security work.

    ESP32-S3                         ~$10
      Wi-Fi, Bluetooth, an NPU-ish vector unit, and a
      completely different ecosystem worth seeing.

    RASPBERRY PI 4 or 5              ~$60
      A full Cortex-A Linux machine you can compile kernels
      for and reflash without fear. THE RIGHT PLATFORM FOR
      THE LINUX DRIVER TRACK.

    BEAGLEBONE BLACK / AI-64
      Excellent for device tree, PRU real-time cores, and
      mainline kernel work.

    QEMU                             free
      Boot a kernel, attach GDB, and never brick anything.
      -M virt with a Cortex-A53 runs the Linux track's
      examples, and it is what the PL031 driver project
      targets.

    AN OLD PC or a VM                free
      For the Windows driver track: a second machine or a
      Hyper-V guest for kernel debugging (ref-05).

/* --- INSTRUMENTS, in order of value per dollar --- */
    LOGIC ANALYSER                   $10-400
      A cheap 8-channel clone with sigrok/PulseView is
      $10 and will transform your debugging. A Saleae is
      $400 and better. GET ONE BEFORE YOU GET AN
      OSCILLOSCOPE - most embedded problems are digital
      timing, and a logic analyser decodes I2C, SPI and
      UART for you.

    OSCILLOSCOPE                     $150-400
      Rigol DHO800 or similar. For analogue questions:
      supply ripple, rise times, crystal oscillation
      (ref-07).

    MULTIMETER                       $30
      Continuity, voltage, current. The most-used
      instrument on any bench.

    BENCH SUPPLY WITH CURRENT LIMIT  $60
      The current limit is the feature. It has saved more
      boards than any other tool.

    USB-SERIAL ADAPTER (3.3V)        $5
      Buy several. You will lose them.

    J-LINK EDU                       $60
      For RTT (ref-02) and reliable flashing across
      vendors.

    USB PROTOCOL ANALYSER            $100+
      Only if you do USB work - and if you do, essential.

/* --- AND THE THING PEOPLE SKIP --- */
    A SOLDERING IRON AND SOME FLUX. Being able to fit a
    tag-connect header, tack a wire onto a test point, or
    lift a pin is a genuine debugging capability
    (ref-07).                                            */
The single most valuable purchase

A cheap logic analyser. Ten dollars, and it converts "the driver doesn't work" into "the bytes are going out but the ACK never comes back". Almost every embedded problem is a question about what is actually happening on a wire, and until you can see the wire you are guessing.

Projects that teach

/* READING IS NOT LEARNING. Build these, in roughly this
   order. Each one forces a specific set of chapters to
   become concrete.                                       */

  1. BLINK AN LED WITH NO LIBRARIES.
     Registers only, from the reference manual. Then write
     the startup code and linker script yourself.
     -> the C track, computer architecture, ref-07

  2. A UART DRIVER, polled, then interrupt-driven, then
     with a ring buffer, then DMA.
     -> interrupts, concurrency, ref-02

  3. A BOOTLOADER that verifies and jumps to an
     application image.
     -> linkers, memory maps, and then signatures
        (cr-15)

  4. PORT AN RTOS, or write a cooperative scheduler with a
     context switch in assembly. Writing the context switch
     yourself teaches more than a term of reading.
     -> the OS track

  5. A LINUX CHARACTER DRIVER, then a platform driver with
     device tree, then one with interrupts and DMA.
     -> the Linux track; lx-28 and lx-29 are exactly this

  6. A WINDOWS KMDF DRIVER and its user-mode client.
     -> the Windows track; win-23 and win-24

  7. IMPLEMENT AES AND SHA-256 FROM THE SPECIFICATION.
     Then make them constant time. Then check with dudect.
     -> the cryptography track, cr-19

  8. A TLS CLIENT on an MCU, with a pinned root and a
     device certificate.
     -> cr-16, cr-17, cr-21

  9. A COMPILER for a small language, following Crafting
     Interpreters. Then emit real machine code.
     -> the compilers track

 10. THE TINY TRANSFORMER (ai-28), then shrink it, quantise
     it, and run it on the Pico.
     -> the AI track, end to end

 11. REVERSE-ENGINEER SOMETHING YOU OWN. Dump the firmware
     from a cheap device, find the UART, identify the
     architecture, disassemble it. Legally, on your own
     hardware. This teaches more about how real products
     are built - and how badly - than any number of
     tutorials.

 12. FIX A BUG IN AN OPEN-SOURCE PROJECT, and get the patch
     merged. The review is the education.
     -> lx-30 covers the kernel process specifically

/* --- HOW TO PRACTISE, not just what --- */
    · BUILD SOMETHING YOU WANT. Motivation carries you
      through the tedious parts, and there are many.
    · FINISH THINGS. A finished small project teaches more
      than three abandoned ambitious ones, because the last
      20% is where the real problems live.
    · READ OTHER PEOPLE'S CODE. The kernel, FreeRTOS,
      Zephyr, mbedTLS, llama.cpp. Pick a subsystem and read
      it properly.
    · EXPLAIN IT. Write it down, or teach someone. You will
      discover what you do not actually understand.
    · AND KEEP A LOG. Of bugs you found, and how. It
      compounds.                                        */

/* --- CERTIFICATIONS, honestly --- */
    Largely not valued in this field. A portfolio of things
    you have built, and contributions people can read, are
    worth considerably more. The exceptions are
    domain-specific safety certifications (IEC 61508,
    ISO 26262, DO-178C) where the process qualification
    genuinely matters to employers in those industries.

/* --- AND A CLOSING NOTE ON THIS SITE --- */

    281 chapters is a great deal of reading and none of it
    is a substitute for the work. The tracks were written
    to be a MAP - to tell you what exists, what it is for,
    what the failure modes look like, and where the primary
    source is.

    THE ACTUAL LEARNING HAPPENS WHEN YOU BUILD SOMETHING
    THAT DOES NOT WORK AND YOU FIND OUT WHY.

    Everything in ref-01 through ref-07 exists to make that
    process faster. Everything else exists so you know what
    you are looking at when you get there.

    Go and build something.                             */

Check yourself

  • Name the primary source you would consult for an ARM exception-level question.
  • Say which vendor document explains behaviour the reference manual does not.
  • Name one book per track you intend to read.
  • List the minimum hardware bench and its total cost.
  • Say why a logic analyser comes before an oscilloscope.
  • Explain why a current-limited bench supply matters.
  • Pick three projects from the list and say which chapters each exercises.
  • Give the four rules for how to practise, not just what to build.
  • Say what this site is for, and what it is not a substitute for.
