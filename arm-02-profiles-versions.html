Profiles and architecture versions

"ARM" names a family, not a thing. A Cortex-M0 and a Neoverse V2 share a vendor and very little else. This chapter maps the territory so that when someone says "ARMv8" you know which of several very different machines they mean.

The single distinction that matters most

MMU or no MMU. With one, you get virtual memory, process isolation, demand paging and everything in the OS track. Without one, every address is physical, a wild pointer can corrupt anything, and "protection" means an MPU checking region permissions with no translation. Almost every other difference follows from this one.

M-profile: different enough to surprise you

Everything else in this track assumes an A-profile core. M-profile is a different architecture wearing the same brand, and assuming knowledge carries over is a reliable way to waste a day — these are the differences that actually bite.

Cortex-M is not "a small Cortex-A". Concretely different:

  EXCEPTIONS       the hardware stacks R0-R3, R12, LR, PC, xPSR
                   automatically, so an ISR is a PLAIN C FUNCTION.
                   No vector table of code — a table of ADDRESSES.

  VECTOR TABLE     entry 0 is the initial STACK POINTER, entry 1 is
                   the reset handler. The CPU loads SP from memory
                   before executing anything.

  NVIC             priorities, tail-chaining (skip the unstack/stack
                   between back-to-back interrupts), late arrival.
                   Interrupt latency ~12 cycles, deterministic.

  TWO STACKS       MSP (main, used by handlers) and PSP (process).
                   An RTOS gives each task a PSP and keeps MSP for
                   exceptions.

  BIT-BANDING      (v7-M) an alias region where each word maps to
                   one bit — atomic single-bit access without
                   read-modify-write.

  TRUSTZONE-M      a function CALL across the boundary, not an SMC.
                   Tens of cycles, not thousands (ch. 15 of the
                   security track).

  NO A64           Thumb-2 only: mixed 16- and 32-bit encodings,
                   chosen for code density.

Versions are cumulative and mostly optional

ARMv8.5 includes everything from 8.1 to 8.4. But many individual features remain optional even within a version, which is why software must query the ID registers rather than infer capability from a version number (chapter 01). "This is an ARMv8.2 core" does not tell you whether it has SVE.

Execution states

A single core can execute more than one instruction set, and which one it is in changes at defined moments. This is also where the 32-bit legacy lives, and why a 64-bit chip can still run older code.

ARMv8-A defines TWO execution states, and a core may implement
one or both:

  AArch64                        AArch32
    A64 instruction set            A32 (ARM) + T32 (Thumb)
    31 x 64-bit registers          16 x 32-bit registers
    fixed 32-bit encodings         mixed 16/32-bit (T32)
    EL0-EL3                        modes mapped onto ELs
    no conditional execution       full predication (IT blocks)
    system registers               CP15 coprocessor

  Switching states happens ONLY on an exception boundary:
    · taking an exception can move AArch32 → AArch64
    · ERET can move AArch64 → AArch32
    · a HIGHER EL may be AArch64 while a lower one is AArch32,
      never the reverse

  So a 64-bit kernel can run 32-bit userspace, but a 32-bit kernel
  cannot run 64-bit applications.

  AArch32 support is now commonly OMITTED at EL0 in new cores
  (Cortex-A510 onward, Apple silicon). 32-bit ARM Linux binaries
  simply will not run there — a real migration issue for
  long-lived embedded products.

The security features, briefly

These arrived one at a time, each in response to a specific class of exploit that had become common enough to justify hardware silicon. They are worth knowing as a set because they attack different stages of the same attack chain: PAC and BTI make it hard to redirect control flow even after memory has been corrupted; MTE makes the corruption itself detectable at the moment it happens rather than silently; PAN closes off an entire class of kernel privilege-escalation bug by refusing an accidental user-memory access; and CCA/RME assumes the previous three have all failed and isolates a workload from a compromised hypervisor entirely. None of them is a substitute for correct code — they narrow the window an attacker can exploit once a bug already exists.

# build with the hardening on
gcc -mbranch-protection=standard    # PAC on returns + BTI
gcc -march=armv8.5-a+memtag         # MTE

# MTE is the most interesting of these: it makes ASan-class
# detection cheap enough to run in PRODUCTION. Android ships it.
cat /proc/cpuinfo | grep -o 'paca\|bti\|mte'

Decoding the names

ARM's naming is genuinely confusing because several independent schemes overlap — architecture versions, core names and marketing names all coexist. Decoding them is mostly a matter of knowing which scheme you are looking at.

   Cortex-A78AE
   │      │ │ └── AE = Automotive Enhanced (lockstep, safety)
   │      │ └──── generation number: higher is newer/bigger
   │      └────── profile: A, R or M
   └───────────── Arm's own core family

   Neoverse N2 / V2 / E2
     N = balanced (scale-out cloud)
     V = maximum performance (HPC, high-end server)
     E = efficiency (edge, networking)

   Cortex-M33 / M55 / M85
     M23, M33  → ARMv8-M with TrustZone-M
     M55, M85  → ARMv8.1-M with Helium (M-profile vector extension)

   DynamIQ Shared Unit (DSU)
     the cluster that ties heterogeneous cores together with a
     shared L3 — the successor to big.LITTLE's separate clusters

   Suffixes worth recognising:
     -AE   automotive, functional safety
     -AP   with parity/ECC for safety
     +crypto / +sve / +simd  in compiler -march strings

Telling the compiler what to target

The compiler will happily generate instructions your chip does not implement, and the failure arrives at runtime as an illegal instruction. Telling it exactly what to target is therefore not an optimisation detail but a correctness one.

# architecture version — what INSTRUCTIONS may be emitted
-march=armv8-a
-march=armv8.2-a+crypto+fp16
-march=armv9-a+sve2

# tune for a specific microarchitecture — SAME instructions,
# different scheduling and cost model
-mtune=cortex-a76

# both at once
-mcpu=cortex-a76           # implies -march and -mtune
-mcpu=cortex-a55+crypto

# big.LITTLE: build for the LEAST capable core you must run on,
# tune for the one that matters
-mcpu=cortex-a55 -mtune=cortex-a76

# M-profile
-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard -mthumb

# runtime dispatch instead: build a baseline binary and select
# optimised routines after reading the ID registers. This is what
# glibc's ifunc mechanism and every crypto library do.
gcc -march=armv8-a ... ; if (has_crypto()) use_aes_instructions();
-march=native is a trap in embedded work

It targets the build machine, not the deployment target — and on a big.LITTLE system it may target whichever core the compiler happened to run on. The result runs until it is scheduled onto a LITTLE core lacking a feature, then takes an illegal-instruction fault. Always name the target explicitly.

Which profile for which job

The choice almost always reduces to one question: does the job need an MMU, or does it need a guaranteed response time? Those two requirements are close to mutually exclusive in practice, because the very features that make an MMU useful — page tables, TLBs, demand paging — introduce exactly the kind of latency variance a hard deadline cannot tolerate. So the A profile owns "run a general-purpose OS" and the M and R profiles own "respond in a bounded number of cycles", and a product that needs both genuinely needs two cores rather than one clever core, which is why asymmetric designs pairing an A-profile core with an M-profile core on one SoC are so common.
