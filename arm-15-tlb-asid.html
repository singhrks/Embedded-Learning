TLBs, ASIDs and invalidation

The TLB is a cache with no coherence protocol. Hardware will never notice that you changed a page table, and the invalidation sequence you must write yourself is exact, order-sensitive, and the source of some of the most confusing bugs in system software.

Why the TLB exists

A page walk is several memory accesses, and doing one on every instruction fetch and data access would be ruinous. The TLB caches the results, which means translation is almost free — until something invalidates it.

A four-level walk is up to FOUR memory accesses per translation.
Every load and store needs one. Without caching, memory access
would be five times slower.

   L1 TLB      32-128 entries, fully associative, ~1 cycle
               usually SPLIT: separate iTLB and dTLB
   L2 TLB      1024-2048 entries, set-associative, ~10 cycles
               unified, shared between instruction and data
   miss        → hardware table walker → up to 4 memory accesses,
                 each of which may itself hit or miss in the caches

   WALK CACHES are a third structure worth knowing: they cache
   INTERMEDIATE table descriptors (L0/L1/L2), so a miss on a
   nearby address only needs the final level. This is why
   sequential access has far cheaper TLB misses than random.

TLB REACH = entries × page size
     1024 × 4 KB  =    4 MB     ← easily exceeded
     1024 × 2 MB  =    2 GB     ← why huge pages help so much

A TLB miss on a large random working set can cost more than the
cache miss that follows it.

Why ASIDs matter so much

Without them, every context switch would have to flush the entire TLB, and the incoming process would take hundreds of misses warming it back up. With them, entries from many processes coexist and a switch is a single TTBR0 write.

Kernel mappings are marked Global (nG=0) so they match under any ASID — which is why a system call disturbs the TLB not at all.

/* ASID width is 8 or 16 bits — query it, do not assume: */
        ID_AA64MMFR0_EL1.ASIDBits    /* 0 = 8 bits, 2 = 16 bits */
        TCR_EL1.AS                    /* select 8 or 16 bit ASID */

/* A context switch: */
        ttbr0 = next_mm->pgd_pa | ((uint64_t)next_mm->asid << 48);
        asm volatile("msr ttbr0_el1, %0" :: "r"(ttbr0));
        asm volatile("isb");
/* That is the whole switch. No flush.                        */

/* ASID EXHAUSTION: with 16 bits there are 65536; with 8 bits only
   256. When they run out, Linux bumps a GENERATION counter and
   flushes everything, then reassigns. On a system with very many
   short-lived processes this shows up as a periodic latency
   blip — rare, but real, and worth recognising.             */

The TLB has no coherence protocol

The rule

Caches are kept coherent by hardware (CA ch. 15). TLBs are not. If you modify a translation table entry, every TLB in the system may continue using the old translation indefinitely. Nothing will tell you.

Worse, on a multi-core system you must invalidate on every core that might hold the entry — which is what the Inner Shareable variants of TLBI do, broadcasting the invalidation across the coherency domain.

The TLBI instruction

Changing a page table does not change the TLB, so software must say what is now stale. The instruction for that has many variants, and choosing a broader one than necessary is a real performance cost.

   TLBI <type><level><scope>{, Xt}

   TYPE — what to match
     ALL      everything in this regime
     VMALL    all entries for the current VMID (a whole VM)
     ASID     all entries matching the ASID in Xt
     VA       one VA, matching the ASID in Xt
     VAA      one VA, ALL ASIDs ("VA, All ASID")
     IPAS2    one IPA at stage 2
     RVA      a RANGE of VAs (ARMv8.4+)

   LEVEL — which regime
     E1       EL1&0 regime
     E2       EL2 regime
     E3       EL3 regime
     E1OS     ...outer shareable

   SCOPE
     (none)   this PE only
     IS       Inner Shareable — BROADCAST to all cores in the
              inner domain. This is what SMP needs.
     OS       Outer Shareable — wider still

   Examples:
     tlbi vae1is, x0      one VA, EL1&0, current ASID, broadcast
     tlbi vaae1is, x0     one VA, ALL ASIDs, broadcast
     tlbi aside1is, x0    all entries for one ASID, broadcast
     tlbi vmalle1is       everything in EL1&0, broadcast
     tlbi alle1           everything, this core only
     tlbi vmalls12e1is    both stages, whole VM, broadcast
/* The Xt operand for VA-based operations is NOT a plain address.
   It packs the ASID and the VA, shifted:                     */

        Xt[63:48] = ASID
        Xt[43:0]  = VA[55:12]        /* the page number */

/* So: */
        addr = (va >> 12) | ((uint64_t)asid << 48);
        asm volatile("tlbi vae1is, %0" :: "r"(addr));

/* Passing a raw byte address is a common error. It invalidates
   the wrong entry, silently, and the stale translation stays.  */

The invalidation sequence

Write → DSB → TLBI → DSB → ISB

Every part is load-bearing. Omit any one and you get a bug that appears on one core, under load, or only after an unrelated change.

        /* 1. update the descriptor */
        *pte = new_value;

        /* 2. DSB ISHST — ensure the WRITE is visible to the table
              walkers of every core BEFORE we invalidate. Without
              this, a core could refill its TLB from the OLD value
              after our TLBI but before our store lands.       */
        dsb     ishst

        /* 3. TLBI — invalidate, broadcast to the inner domain */
        tlbi    vae1is, x0

        /* 4. DSB ISH — wait for the invalidation to COMPLETE on
              every core. TLBI is issued asynchronously; without
              this, another core may still be using the old entry
              when we proceed.                                 */
        dsb     ish

        /* 5. ISB — flush THIS core's pipeline, so no instruction
              already in flight uses a stale translation.       */
        isb
/* Linux wraps this. Reading the wrappers is instructive: */

flush_tlb_all()                  /* everything, everywhere      */
flush_tlb_mm(mm)                 /* one address space (by ASID) */
flush_tlb_range(vma, start, end) /* a range                     */
flush_tlb_page(vma, addr)        /* one page                    */
flush_tlb_kernel_range(s, e)     /* kernel mappings             */

/* And there is a threshold: below ~32 pages Linux issues
   individual TLBI VA operations; above it, one TLBI ASID, because
   many individual broadcasts cost more than one bulk flush.
   ARMv8.4's TLBI RVA (range) instructions remove that trade-off
   where available.                                            */

TLB shootdown

On a multiprocessor system, invalidating your own TLB is not enough — other cores may hold the same stale entry. How that is coordinated is one of the genuinely tricky parts of a kernel's memory management.

Invalidating on OTHER cores is the expensive part.

  ARM: TLBI ...IS BROADCASTS in hardware. The instruction issues,
       the interconnect distributes it, and DSB waits for
       completion. No interrupts, no software involvement.

  x86: NO broadcast instruction. The OS must send an
       inter-processor INTERRUPT to every core that might hold the
       entry, and wait for each to acknowledge. Far more expensive.

  This is a genuine architectural advantage for ARM, and it is why
  munmap-heavy and page-migration-heavy workloads scale better
  there.

  But it is not free. On a large system, a broadcast TLBI must
  reach every core in the domain, and the DSB blocks until it has.
  Workloads that constantly change mappings (JITs, garbage
  collectors, heavy mmap/munmap) can spend measurable time here.

  Mitigations:
    · batch invalidations (Linux's mmu_gather does this: it
      collects the pages freed during an unmap and issues ONE
      flush at the end)
    · use TLBI ASID rather than many TLBI VA
    · TLBI RVA range operations (ARMv8.4)
    · avoid unnecessary permission changes on hot mappings

Making permissions less restrictiveNot architecturally required — the fault handler will re-walk. Linux does it anyway on some paths.

Splitting a block into pagesYes, with break-before-make
The "no invalidation needed" case has an exception

Making an invalid entry valid appears safe — how could a TLB cache "not present"? But some implementations do cache negative entries, and more importantly, the walk caches may hold intermediate table descriptors. If you allocate a new L3 table and link it in, a core with a cached L2 entry pointing at the old (invalid) state may not see it. Linux issues an invalidation on these paths for exactly this reason. When in doubt, invalidate — it is cheap relative to a stale-translation bug.

Break-before-make, restated

Changing a live mapping in place can leave the TLB holding two conflicting entries, with architecturally unpredictable results. The safe sequence is fixed, and skipping a step produces faults that are almost impossible to reproduce.

/* Changing a LIVE mapping's address, size or attributes in place
   permits the TLB to hold BOTH translations simultaneously.
   The architecture calls the result UNPREDICTABLE, and real
   hardware may raise a TLB conflict abort or use either
   translation non-deterministically.                         */

        /* BREAK */
        *pte = 0;
        dsb     ishst
        tlbi    vaae1is, x_addr
        dsb     ish
        isb

        /* MAKE */
        *pte = new_descriptor;
        dsb     ishst
        isb

/* This is why splitting a 2 MB block into 4 KB pages — which
   Linux does when a partial mprotect() hits a THP — is not a
   simple table edit. It must break the block, invalidate, build
   the L3 table, and only then install the new L2 pointer.   */

Stage-2 and VMID

Under virtualisation there are two levels of translation to keep coherent, and entries are tagged by virtual machine as well as by address space.

/* A guest's TLB entries are tagged with the VMID from
   VTTBR_EL2[63:48], so several VMs coexist in the TLB just as
   several processes do.                                       */

/* Invalidating guest translations from EL2: */
        tlbi    vmalle1is        /* all stage-1 entries, current VMID */
        tlbi    vmalls12e1is     /* both stages, current VMID         */
        tlbi    ipas2e1is, x0    /* one IPA at stage 2                */

/* Note the ordering rule when changing a stage-2 mapping: you
   must invalidate stage 2 BEFORE stage 1, because a stage-1
   entry may have been formed using the old stage-2 translation:

        tlbi    ipas2e1is, x_ipa
        dsb     ish
        tlbi    vmalle1is
        dsb     ish
        isb

   Getting this backwards leaves combined TLB entries built from
   a mixture of old and new — a hypervisor bug class that is
   very hard to reproduce.                                    */

Measuring TLB behaviour

TLB pressure is invisible in source code and very visible in performance counters. These are the events worth watching when a workload is slower than its cache behaviour alone would explain.

# is the TLB the bottleneck?
perf stat -e dTLB-load-misses,iTLB-load-misses,\
dtlb_walk,itlb_walk,l1d_tlb_refill,l2d_tlb_refill ./prog

#   dtlb_walk counts actual PAGE WALKS — the expensive event.
#   A high ratio of walks to loads means poor TLB reach.

# does the working set fit?
#   time a pointer chase over increasing sizes; the step changes
#   land at the L1 TLB reach, the L2 TLB reach, and the cache
#   capacities.

# try huge pages and measure the difference
echo always > /sys/kernel/mm/transparent_hugepage/enabled
perf stat -e dtlb_walk ./prog        # before and after

# per-process THP usage
grep -E 'AnonHugePages|ShmemPmdMapped' /proc/PID/smaps_rollup

# TLB shootdown cost, system-wide
perf stat -e tlb:tlb_flush -a sleep 10
cat /proc/interrupts | grep -i tlb    # x86 only; ARM broadcasts
