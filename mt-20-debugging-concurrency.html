Finding concurrency bugs on purpose

A test that passes tells you one interleaving worked. The discipline that finds concurrency bugs is not better luck — it is making the rare interleaving common, on hardware that permits it, with tools that see what your eyes cannot.

The method

Concurrency bugs defeat the usual debugging approach, because observing the program changes its timing and the failure may not recur. What works is a different method rather than better tools.

   FIRST: WHICH BUG IS IT?  Ten seconds of observation saves
   an afternoon.

     hung, 0% CPU           -> deadlock (chapter 14)
     hung, 100% CPU         -> livelock, or a spin/CAS loop
     wrong answer, no crash -> race condition or lost update
     crash in random places -> data race, or use-after-free
     one thread never runs  -> starvation
     slow, not wrong        -> contention or false sharing
     fine alone, wrong in
       parallel             -> shared state you forgot about

   THEN, IN THIS ORDER:

   1. Make it reproduce more often   (this chapter)
   2. Run a sanitiser                (finds data races)
   3. Read the code for the invariant, not the syntax
   4. Only then, attach a debugger

   Reaching for gdb first is the classic mistake: a breakpoint
   changes the timing, and the bug you were chasing stops
   happening.

Making it reproduce

The first problem is that the bug happens once a week. These techniques make it happen on demand — which turns an intractable investigation into an ordinary one.

# 1. MORE THREADS THAN CORES. Forces constant preemption,
#    so the interleavings you never see become normal.
$ ./app --threads=64          # on 8 cores

# 2. PIN EVERYTHING TO ONE CORE. Removes true parallelism and
#    maximises preemption at arbitrary instructions. Finds a
#    completely different set of bugs from (1) - run both.
$ taskset -c 0 ./app

# 3. RUN ON WEAK HARDWARE. An arm64 box exhibits reorderings
#    x86 physically cannot (chapter 12). If you ship on ARM
#    and test on x86, you are not testing the memory model.

# 4. SLOW DOWN THE SUSPECT WINDOW. The single highest-value
#    technique in this chapter:
      auto it = cache.find(k);
      if (it != cache.end()) return it->second;
+     std::this_thread::sleep_for(std::chrono::milliseconds(50));
      auto v = compute(k);
#    A gap bug that happened once a week now happens every
#    time. Delete the sleep once you have the fix.

# 5. RANDOMISE SCHEDULING. Inject a yield at every
#    synchronisation point, under a flag:
      #ifdef FUZZ_SCHED
      #define SYNC_POINT() do { if (rand() % 4 == 0) \
                                std::this_thread::yield(); } while (0)
      #else
      #define SYNC_POINT() ((void)0)
      #endif

# 6. STRESS IN A LOOP, and record the seed.
$ for i in $(seq 1 100000); do ./test --seed=$i || \
      { echo "FAILED seed=$i"; break; }; done

# 7. RUN UNDER LOAD. Many races need a competitor:
$ stress-ng --cpu 8 --vm 2 & ./app
Pin to one core and oversubscribe — they find different bugs

One core with many threads gives you frequent, arbitrary preemption: it finds check-then-act gaps, lost updates and non-reentrant code. Many cores give you true simultaneity and memory reordering: it finds publication bugs, false sharing and missing barriers. A bug found by one is often invisible to the other, so a stress suite should do both.

The tools

Several tools find concurrency bugs without needing the bug to occur naturally, by checking the rules on every access. They find different classes of problem, so knowing which to reach for matters.

# rr, when a bug is rare but you caught it once:
$ rr record ./app
$ rr replay
(rr) continue                 # runs to the crash, identically
(rr) reverse-continue         # run BACKWARDS to the previous
(rr) watch -l ptr             # write to that address
# Deterministic replay of a race is close to magic: the
# recording contains the exact interleaving that failed.
Sanitisers do not compose, and they miss race conditions

TSan and ASan cannot be enabled together — build twice. TSan needs the whole program instrumented; an uninstrumented third-party library produces false negatives and sometimes false positives. And most importantly: TSan finds data races, not race conditions (chapter 5). A clean TSan run on properly-locked code that has a gap between two critical sections proves nothing at all.

Designing so the bug cannot happen

The most effective debugging is structural: some designs make whole categories of concurrency bug impossible rather than merely unlikely. These are the choices that pay off most.

/* Cheaper than any tool in the table above. */

/* 1. DON'T SHARE. Per-thread state merged at the end
      (chapter 19). No sharing, no race, nothing to test.

   2. IMMUTABLE AFTER PUBLICATION. Build fully, publish with a
      release store, never mutate. Readers need no lock at all.

   3. OWNERSHIP, NOT LOCKING. One thread owns each object;
      others send messages. Rust enforces this; in C++ you can
      approximate it with move-only types and a queue.

   4. MAKE ILLEGAL STATES UNREPRESENTABLE. Put the data inside
      the mutex so there is no way to touch it unlocked -
      Rust's Mutex<T>, or in C++:                             */

template <class T>
class Guarded {
    std::mutex m_;
    T          v_;
public:
    template <class F>
    auto with(F f) -> decltype(f(v_)) {
        std::lock_guard<std::mutex> g(m_);
        return f(v_);                 /* the ONLY way in       */
    }
};
Guarded<std::map<int,int>> cache;
cache.with([&](auto &m) { m[k] = v; });
/* You cannot forget the lock, because there is no accessor
   that does not take it. The whole class of bug is gone.    */

/* 5. ANNOTATE, and let the compiler check.                  */
class Cache {
    std::mutex m_;
    std::map<int,int> data_ GUARDED_BY(m_);
    int hits_ GUARDED_BY(m_);
public:
    int hits() { return hits_; }   /* -Wthread-safety: ERROR,
                                      reading hits_ without m_ */
};

/* 6. ONE INVARIANT PER LOCK, written down (chapter 7).      */

What to run in CI

Concurrency bugs that reach production were usually not caught because the tests were too short and too uniform. Making automated testing actually likely to find them is mostly a matter of configuration.

# The realistic set, in cost order. Even the first three
# catch most of it.

  every commit:
    -Wthread-safety                       free, compile time
    unit tests under TSan                 slow but bounded
    unit tests with threads=4x cores      finds gap bugs

  nightly:
    the full suite under TSan and under ASan (separate runs)
    the full suite pinned to one core
    the full suite on an ARM64 runner      <-- the highest-value
                                               single addition
    a stress soak, several hours, seeds logged

  before a release:
    Helgrind on the critical paths
    a load test measuring p99.9, not the mean

# And record every intermittent failure with its seed and its
# machine. Three occurrences of "flaky test" with the same
# stack is not flakiness; it is a bug with a low reproduction
# rate, and it will reach production at scale.
Never mark a concurrency test flaky

A test that fails once in fifty runs is telling you the truth about a bug that will happen once in fifty thousand production requests — which, at a thousand requests a second, is once a minute. Retrying the test until it passes converts a caught bug into a shipped one. Quarantine it if you must ship, but track it as a defect, not as noise.
