Cache coherence and memory consistency

Two words that sound like synonyms and are not. Coherence is about one location seen by many caches; consistency is about the order of operations across different locations. Confusing them is the root of most multi-core bugs.

The problem

Give each core its own cache (chapter 13) and you have created a correctness problem: the same location now exists in several places at once, with different values.

   Core 0                      Core 1
   +-----------+               +-----------+
   | L1: x = 5 |               | L1: x = 5 |
   +-----------+               +-----------+
         |                            |
         +------------+---------------+
                 +----------+
                 | DRAM x=5 |
                 +----------+

   Core 0 executes:  x = 7

   +-----------+               +-----------+
   | L1: x = 7 |  dirty        | L1: x = 5 |  <-- STALE
   +-----------+               +-----------+

   Core 1 reads x and gets 5. The program is wrong, and nothing in
   the source code hinted that it could be.

Coherence: one location, many caches

The coherence guarantee

A memory system is coherent if, for any single location:

  1. A read returns the value of the most recent write to that location.
  2. All observers agree on the order of writes to it (write serialisation).

Note what this does not say: nothing about the relative ordering of accesses to different locations. That is consistency, and it is a separate guarantee that hardware does not give you by default.

MESI

Each cache line carries a state. Cores watch — "snoop" — each other's transactions and change state accordingly.

StateMeaningOthers may hold it?Memory current?
M — ModifiedI have it and I changed itNoNo — I must write back
E — ExclusiveI have it, unmodified, and only I have itNoYes
S — SharedI have it, unmodified, others may tooYesYes
I — InvalidNo usable copy——
 
The transitions that matter

  Core 0 reads x, nobody else has it   ->  I -> E
  Core 1 then reads x                  ->  Core 0: E -> S,  Core 1: I -> S
  Core 0 writes x                      ->  broadcast INVALIDATE
                                           Core 1: S -> I
                                           Core 0: S -> M
  Core 1 reads x again                 ->  Core 0 must SUPPLY the data
                                           (or write it back first)
                                           Core 0: M -> S,  Core 1: I -> S

The E state exists purely as an optimisation: if only you hold a clean
line, you may write it without broadcasting anything. Without E, every
first write to a private variable would need a bus transaction.

MOESI adds O (Owned): a dirty line may be shared, with one owner
responsible for eventual write-back. Saves memory traffic.

On ARM this rides the interconnect protocols from chapter 17 — ACE for smaller systems, CHI for large ones. Broadcast snooping does not scale past a modest core count, so large designs use a directory: a structure recording which caches hold which lines, so invalidations go point-to-point instead of to everyone.

False sharing

Coherence operates on lines, not variables. Two unrelated variables in the same 64-byte line are indistinguishable to the protocol.

/* looks perfectly parallel. It is not. */
struct counters {
        uint64_t a;    /* thread 0 increments this */
        uint64_t b;    /* thread 1 increments this */
};                     /* both in ONE cache line   */

/* Thread 0 writes a  -> invalidates the line in thread 1's cache
   Thread 1 writes b  -> invalidates the line in thread 0's cache
   ...forever. The line ping-pongs between cores every iteration.

   Measured effect: often 10-100x SLOWER than one thread doing both
   increments. You added a core and went backwards.               */

/* the fix: give each its own line */
struct counters {
        alignas(64) uint64_t a;
        alignas(64) uint64_t b;
};

/* portable spellings */
_Alignas(64)                                         /* C11           */
alignas(std::hardware_destructive_interference_size) /* C++17         */
____cacheline_aligned                                /* Linux kernel  */
__attribute__((aligned(64)))                         /* GCC / Clang   */
The signature of false sharing

Unmistakable once you know it: throughput gets worse as you add threads, and the working set is tiny. Confirm with perf c2c record / perf c2c report, which names the exact cache lines suffering cross-core contention and the source lines touching them. Usual victims: per-thread statistics arrays, adjacent lock structures, and the head and tail pointers of a ring buffer.

Consistency: many locations, what order?

Coherence is not enough. Consider two different variables:

/* both start at 0 */

/* Core 0 */                    /* Core 1 */
data = 42;                      while (flag == 0)
flag = 1;                               ;
                                use(data);      /* may read 0! */

Every location is coherent. Yet core 1 can observe flag == 1 while still reading data == 0. Coherence never promised anything about ordering between addresses.

Why the reordering happens

SourceWhat it does
CompilerReorders or eliminates accesses it can prove safe single-threaded

Out-of-order executionLoads issue as soon as their address is known, possibly before earlier loads
Cache hierarchyInvalidations reach different cores at different times
InterconnectMessages take different routes and arrive out of order

Memory models, strong to weak

ModelGuaranteeUsed by
Sequential consistencyOne global order consistent with each program's orderNo real hardware — too slow. It is the model beginners assume.
TSO (total store order)Only store→load may be reordered; the store buffer is the sole relaxationx86-64, SPARC
Weak / relaxedAlmost anything may be reordered unless you say otherwiseARM, RISC-V, PowerPC
Why this bites when porting from x86

Lock-free code that ran correctly on x86 for years can fail on ARM. x86's TSO happens to forbid the reorderings naive code depends on; ARM's weak model does not. The code was always wrong — x86 merely hid it. It will not reproduce reliably either: it depends on timing, core count and load, so it surfaces in production rather than in test. This is the most common serious porting bug from x86 to ARM.

Restoring order

Coherence keeps caches consistent, but it does not stop the processor or compiler reordering your accesses. That is a separate problem with a separate fix, and conflating the two is the source of a great deal of broken lock-free code.

Fixed with barriers

  /* Core 0 */                     /* Core 1 */
  data = 42;                       while (flag == 0)
  DMB ISHST;   <- prior stores             ;
  flag = 1;       visible before    DMB ISHLD;  <- no later load may
                  later stores                    float above this
                                    use(data);

Fixed with acquire / release - cheaper, and the modern idiom

  /* Core 0 */                     /* Core 1 */
  data = 42;                       while (LDAR(flag) == 0)   <- acquire
  STLR(flag, 1);   <- release              ;
                                   use(data);

  STLR: no EARLIER access may be reordered after it
  LDAR: no LATER   access may be reordered before it

Together they form a RELEASE-ACQUIRE PAIR: everything core 0 did
before the release is visible to core 1 after the acquire. This is
the fundamental synchronisation building block, and every mutex,
every channel and every lock-free queue is built out of it.
/* portable C11 / C++11 - compiles to LDAR/STLR on ARM, and to plain
   loads and stores on x86, where TSO already provides the ordering  */
#include <stdatomic.h>

_Atomic int flag = 0;
int data = 0;

/* producer */
data = 42;
atomic_store_explicit(&flag, 1, memory_order_release);

/* consumer */
while (atomic_load_explicit(&flag, memory_order_acquire) == 0)
        ;
use(data);                      /* guaranteed to see 42 */

/* Linux kernel spellings of the same idea */
smp_store_release(&flag, 1);
if (smp_load_acquire(&flag)) use(data);
smp_mb();  smp_rmb();  smp_wmb();      /* full / read / write barrier  */
READ_ONCE(x);  WRITE_ONCE(x, v);       /* stop the COMPILER only       */
memory_orderGuaranteeCost on ARM
relaxedAtomicity only, no orderingFree — a plain atomic op
acquireLater accesses cannot move before itLDAR
releaseEarlier accesses cannot move after itSTLR
acq_relBoth, for read-modify-writeLDAXR/STLXR or CAS
seq_cstPlus a single global total orderMost expensive — and the default if you omit the argument

Coherence with devices

Cores are kept coherent by hardware. Devices may not be — and whether they are is a property of the SoC, not something you may assume.

Non-coherent DMA: the two failure modes

  CPU writes a buffer, then starts a device READ
    · the data is dirty in L1; DRAM still holds the old bytes
    · the device reads DRAM -> gets garbage
    -> software must CLEAN (flush) the cache first

  Device WRITES a buffer, then the CPU reads it
    · the CPU may still hold a stale clean copy in L1
    · the CPU reads its cache -> gets old data
    -> software must INVALIDATE the cache first

  On ARM:  DC CVAC (clean), DC IVAC (invalidate), DC CIVAC (both)

Coherent DMA: the device participates in the coherency protocol
(ACE-Lite or CHI; marked `dma-coherent` in the device tree). No
maintenance needed - but never assume it, check.
/* Which is exactly why you NEVER hand a device a raw kmalloc pointer.
   The DMA API knows whether this device is coherent and emits the
   right maintenance - or correctly emits none.                      */

dma_addr_t d = dma_map_single(dev, buf, len, DMA_TO_DEVICE);
/* ... the device owns the buffer here; the CPU must not touch it ... */
dma_unmap_single(dev, d, len, DMA_TO_DEVICE);

/* peek mid-transfer, correctly */
dma_sync_single_for_cpu(dev, d, len, DMA_FROM_DEVICE);
inspect(buf);
dma_sync_single_for_device(dev, d, len, DMA_FROM_DEVICE);

Measuring coherence traffic

Coherence traffic is invisible in source code and very visible in performance. These counters show you when cores are fighting over the same cache lines, which is usually the explanation for a parallel program that gets slower as you add threads.

# find false sharing and cross-core line contention
perf c2c record ./program
perf c2c report --stdio
#   reports HITM (hit-modified) events: a load that hit a line
#   modified in ANOTHER core's cache - the fingerprint of sharing

# ARM PMU events worth watching
perf stat -e mem_access,l2d_cache_wb,bus_access_shared ./program

# quick triage: if throughput DROPS as you add threads and the working
# set is tiny, it is almost certainly false sharing

How it shows up

SymptomCause
Adding threads makes a parallel program slowerFalse sharing; pad to cache-line boundaries

DMA results never become visible to the CPUCache not invalidated after the device write
