Load/store architecture and the RISC philosophy

One design rule shapes everything else about ARM: only load and store instructions touch memory. Everything else operates on registers. This chapter draws out the consequences, several of which are the direct cause of bug classes you will meet for the rest of your career.

The rule

Load/store architecture

Memory is accessed only by the LDR and STR instruction families. Every arithmetic, logical and comparison instruction reads its operands from registers and writes its result to a register. There is no ADD [address], #1.

/* C source */
counter++;

/* AArch64 — three separate instructions, plus address formation */
        adrp    x0, counter               // page address of the symbol
        add     x0, x0, :lo12:counter     // + low 12 bits = full address
        ldr     w1, [x0]                  // LOAD    memory → register
        add     w1, w1, #1                // MODIFY  register only
        str     w1, [x0]                  // STORE   register → memory

/* x86, by contrast, can do it in one instruction: */
        incl    counter(%rip)             // read-modify-write in one op
/* — but note that even on x86 this is NOT atomic without a LOCK
   prefix. The hardware still performs three steps internally.  */

What follows from it

"Load-store architecture" sounds like a classification rather than something that affects you. In fact it shapes every line of ARM assembly you will ever read, because it means arithmetic and memory access can never happen in the same instruction.

1. Read-modify-write is never atomic

   Core 0                    Core 1
   ldr  w1, [x0]   → 5
                             ldr  w1, [x0]   → 5
   add  w1, w1, #1 → 6
                             add  w1, w1, #1 → 6
   str  w1, [x0]   → 6
                             str  w1, [x0]   → 6

   Two increments, one result. This is not an ARM quirk — it is
   the direct, visible consequence of the load/store rule, and it
   is why the atomics of chapter 22 exist as separate instructions
   rather than as a property of ADD.

2. Address formation is explicit

/* A 64-bit address does not fit in a 32-bit instruction, so ARM
   builds addresses from pieces. Three common idioms:          */

/* PC-relative, ±4 GB — how globals are reached in position-
   independent code. ADRP gives the 4 KB PAGE address; the low
   bits come from an ADD or the load's own offset.            */
        adrp    x0, symbol
        add     x0, x0, :lo12:symbol

/* Small immediate offset, folded into the load */
        ldr     x1, [x0, #16]

/* Large constants are built 16 bits at a time */
        movz    x0, #0x1234, lsl #16
        movk    x0, #0x5678

/* This is why disassembly shows ADRP/ADD pairs everywhere, and
   why the linker has relocation types specifically for splitting
   an address across two instructions.                        */

3. Fixed 32-bit instruction width

x86 instructions vary from one byte to fifteen, which means a decoder cannot know where the next instruction starts until it has finished decoding the current one — decoding is inherently serial. Every AArch64 instruction is exactly four bytes, so the decoder can slice the instruction stream into already-known-length chunks and hand several to parallel decode pipelines at once, with no dependency between them. That single property is a large part of why ARM cores can go wide (decode four or more instructions per cycle) far more cheaply than an x86 core can, and it has knock-on effects for disassembly and code size:

ConsequenceEffect
Decode is trivialSeveral instructions can be decoded in parallel with no serial dependency — a major reason ARM cores go wide cheaply
Disassembly is unambiguousYou can start disassembling at any 4-byte-aligned address and be correct. On x86, you cannot.
No unaligned instructionsEvery instruction address is 4-byte aligned; the low two bits of the PC are always zero
Immediates are limitedOnly 12 bits for arithmetic, so large constants need several instructions or a literal pool
Code density is worse than x86Which is exactly why Thumb-2 exists for M-profile, mixing 16- and 32-bit encodings

4. Memory access is visible and countable

/* Because every access is an explicit instruction, you can SEE the
   memory traffic in the disassembly. This makes ARM assembly
   unusually readable for performance work.                    */

objdump -d prog | grep -cE '\b(ldr|ldp|str|stp)'   /* count accesses */

/* And it makes the compiler's decisions visible: if a variable
   stays in a register across a loop, there are no LDRs inside
   the loop. If `volatile` forces a reload, you see one per
   iteration. This is the fastest way to confirm what volatile
   and restrict actually did (C chapters 10 and 18).         */

RISC in practice, not in slogans

Classic RISC claimReality on modern ARM
"Reduced instruction set"AArch64 has well over a thousand instructions. The set is not small.
"One instruction per cycle"Wide superscalar cores retire several per cycle; some instructions take many
"Simple instructions only"FJCVTZS (JavaScript float-to-int), AESE, SHA256H, LD64B — these are not simple
"No microcode"Largely true, and it does matter: decode stays cheap
"Load/store architecture"True, and the one that actually matters
"Fixed-width instructions"True for A64; false for Thumb-2
"Many general-purpose registers"True — 31, versus x86-64's 16
The RISC/CISC distinction has largely dissolved

Modern x86 cores decode complex instructions into RISC-like micro-operations and execute those. Modern ARM cores have complex instructions. What remains genuinely different is the front end: fixed-width, regularly encoded instructions are much cheaper to decode in parallel, which lets ARM cores go wide with less power. That, plus load/store discipline, is the real substance behind the label.

Why 31 registers changes how code looks

Having 31 general-purpose registers rather than a handful is not merely convenient — it changes what the compiler can do. Values that would constantly spill to memory on a register-starved architecture simply stay in registers here.

/* With 16 registers (x86-64), the compiler spills to the stack
   constantly. With 31, most functions keep everything in
   registers. Compare a small function:                        */

/* AArch64 — no memory traffic at all inside the function */
sum4:   add     w0, w0, w1
        add     w0, w0, w2
        add     w0, w0, w3
        ret

/* And the calling convention passes EIGHT arguments in registers
   (chapter 09), so most calls involve no stack traffic either.

   Practical consequence: on AArch64, seeing LDR/STR of stack
   slots inside a hot loop usually means something is wrong —
   an address was taken, aliasing blocked an optimisation, or
   the function is genuinely register-starved.               */

Orthogonality and its limits

The instruction set is regular enough that you can usually guess the form of an instruction you have not met. The exceptions to that regularity are few, deliberate, and worth knowing precisely because they are the ones that surprise you.

/* Most instructions accept any register in any operand position —
   which makes the ISA easy to generate code for. But there are
   real exceptions worth knowing:                             */

/* XZR/WZR — register 31 reads as zero and discards writes.
   This gives you several idioms for free:                    */
        mov     x0, xzr          // x0 = 0
        subs    xzr, x1, x2      // compare, discard the result
                                 //   (this IS how CMP is encoded)
        str     xzr, [x0]        // store zero, no register needed

/* But in SOME encodings, register 31 means the STACK POINTER
   instead of the zero register. Which one depends on the
   instruction:                                               */
        add     x0, sp, #16      // here 31 = SP
        add     x0, x1, xzr      // here 31 = XZR

/* This is a genuine trap when hand-writing or reading assembly,
   and the reason disassemblers print SP and XZR explicitly.  */

No predication — and what replaced it

32-bit ARM let almost any instruction execute conditionally, which was distinctive and is now largely gone. Understanding why it was removed explains a great deal about how modern processors actually execute code.

/* ARMv7 could predicate almost ANY instruction:
        ADDEQ r0, r1, r2      @ execute only if Z is set
   This saved branches, but cost 4 encoding bits on every single
   instruction and complicated out-of-order execution.

   A64 dropped it. Instead there are conditional SELECT
   instructions, which are branchless without needing predication
   everywhere:                                                */

        cmp     w0, w1
        csel    w2, w3, w4, gt      // w2 = (w0 > w1) ? w3 : w4
        cset    w2, eq              // w2 = (Z) ? 1 : 0
        csinc   w2, w3, w4, ne      // w2 = ne ? w3 : w4 + 1
        csinv, csneg, cinc, cneg

/* This is how the compiler turns a small if/else into branchless
   code — and why the branchless idioms in CA chapter 12 and C
   chapter 08 compile so well on AArch64.                     */

int max(int a, int b) { return a > b ? a : b; }
/*      cmp     w0, w1
        csel    w0, w0, w1, gt
        ret                    — no branch, no mispredict      */

Flags are set explicitly

On AArch64 an arithmetic instruction does not update the condition flags unless you ask it to, which is the opposite of what many architectures do. That explicitness is what lets the compiler reorder freely without disturbing a pending comparison.

/* Most instructions do NOT touch the condition flags. You opt in
   with an S suffix. This is the opposite of x86, where nearly
   everything clobbers EFLAGS.                                */

        add     w0, w1, w2       // flags unchanged
        adds    w0, w1, w2       // sets N, Z, C, V
        subs    xzr, x1, x2      // == cmp x1, x2
        ands    wzr, w1, w2      // == tst w1, w2

/* Why it matters: because flags survive across unrelated
   instructions, the compiler can compute a condition early,
   do other work, and branch on it later — which schedules
   better on a deep pipeline. It also means an overflow check
   needs an explicit ADDS, which is exactly what
   __builtin_add_overflow generates (C chapter 02).          */

Reading AArch64 disassembly

Reading disassembly fluently is the single most useful ARM skill, and it is far more learnable than it looks — the syntax is regular, and a handful of patterns account for most of what you will see.

# the fastest way to learn: compile and look
gcc -O2 -S -o - test.c              # assembly source
gcc -O2 -c test.c && objdump -d test.o
objdump -d --source prog            # interleaved with C (needs -g)

# godbolt.org is the fastest iteration loop for this

# what to look for, in order:
#   1. LDR/STR inside loops  → memory traffic; is it necessary?
#   2. B / B.cond            → branches; predictable?
#   3. CSEL / CSET           → the compiler went branchless
#   4. ADRP/ADD pairs        → global variable access
#   5. STP/LDP at entry/exit → the prologue and epilogue
#   6. BL                    → calls that were not inlined
#   7. LD1/ST1/V registers   → it vectorised
The habit worth building

When a performance question comes up, look at the assembly before theorising. AArch64 output is regular enough to read without being an assembly programmer, and it answers questions — did it vectorise, did restrict help, is that load hoisted out of the loop — that no amount of reasoning about the source will settle.
