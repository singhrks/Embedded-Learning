The I/O manager and IRPs

Every I/O operation in Windows is an I/O Request Packet travelling down a stack of drivers. One data structure carries reads, writes, IOCTLs, power transitions and PnP events alike — and understanding its lifecycle is understanding Windows I/O.

What an IRP is

The I/O Request Packet is the unit of work in Windows. Every read, write and IOCTL becomes one, and it travels down through the drivers stacked on a device and back up again — so understanding its shape explains how driver layering works at all.

   +-------------------------------------------+
   |  IRP HEADER                               |
   |    MdlAddress        for DIRECT I/O       |
   |    AssociatedIrp.SystemBuffer  BUFFERED   |
   |    UserBuffer        METHOD_NEITHER       |
   |    IoStatus.Status   the result           |
   |    IoStatus.Information  bytes transferred|
   |    RequestorMode     UserMode / KernelMode|
   |    Cancel, CancelRoutine                  |
   |    CurrentLocation                        |
   +-------------------------------------------+
   |  IO_STACK_LOCATION  [n-1]  bottom driver  |
   |  IO_STACK_LOCATION  [n-2]                 |
   |  ...                                      |
   |  IO_STACK_LOCATION  [0]    top driver     |
   +-------------------------------------------+

  ONE STACK LOCATION PER DRIVER in the device stack. Each
  holds THAT driver's view of the request:

     MajorFunction     IRP_MJ_READ, IRP_MJ_DEVICE_CONTROL, ...
     MinorFunction     for PnP and power
     Parameters        a union: Read, Write, DeviceIoControl,
                       QueryDeviceRelations, Power, ...
     DeviceObject      which device
     FileObject        which open instance
     CompletionRoutine to run when a lower driver finishes

  YOU GET YOURS WITH:
        PIO_STACK_LOCATION sp = IoGetCurrentIrpStackLocation(irp);

  AND THE ONE BELOW YOU WITH:
        IoGetNextIrpStackLocation(irp)

  THE DESIGN IDEA: the IRP is a self-contained request that
  can be queued, cancelled, passed between drivers, and
  completed asynchronously from any context. Linux has no
  single equivalent - it has bio for block, urb for USB, skb
  for network, and ad-hoc structures elsewhere. Windows pays
  more machinery for one uniform mechanism.

CLEANUP versus CLOSE — the distinction that matters

IRP_MJ_CLEANUP arrives when the last handle in a process is closed, while the file object still exists. IRP_MJ_CLOSE arrives when the last reference to the file object goes away, which may be much later. Cancel and complete pending requests in CLEANUP: if you wait for CLOSE, a process that exits with I/O outstanding hangs in termination, because the file object cannot be released while your driver still holds its IRPs.

A dispatch routine

A dispatch routine is what the I/O manager calls when a request of a given type arrives for your device. This is the raw WDM form; KMDF hides most of it later, but the shape underneath is exactly this.

NTSTATUS
MyRead(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp)
{
        PMY_DEVICE_EXTENSION ext = DeviceObject->DeviceExtension;
        PIO_STACK_LOCATION sp = IoGetCurrentIrpStackLocation(Irp);
        ULONG length = sp->Parameters.Read.Length;
        PVOID buffer;
        NTSTATUS status;
        ULONG_PTR info = 0;

        /* For METHOD_BUFFERED the I/O manager already copied
           the user buffer somewhere safe (chapter 08):     */
        buffer = Irp->AssociatedIrp.SystemBuffer;

        if (length < sizeof(ULONG)) {
                status = STATUS_BUFFER_TOO_SMALL;
                goto complete;
        }

        status = MyReadData(ext, buffer, length, &info);

complete:
        Irp->IoStatus.Status = status;
        Irp->IoStatus.Information = info;   /* BYTES
                                               TRANSFERRED  */
        IoCompleteRequest(Irp, IO_NO_INCREMENT);
        return status;
}

/* THREE RULES, and each has a specific consequence:

   1. SET BOTH IoStatus FIELDS. `Information` is what
      ReadFile reports as bytes read. Leaving it uninitialised
      makes userspace read uninitialised stack contents as a
      length - and act on it.

   2. THE RETURN VALUE MUST MATCH IoStatus.Status, except that
      you return STATUS_PENDING when you did not complete it.

   3. ONCE YOU CALL IoCompleteRequest, THE IRP IS GONE.
      Touching it afterwards is a use-after-free. Not "may
      be" - the I/O manager may have freed it before the call
      returns.                                             */

/* IO_NO_INCREMENT vs a priority boost: the second argument
   boosts the waiting thread's priority on completion. Use
   IO_NO_INCREMENT unless the request took long enough that
   the thread deserves to run promptly (IO_DISK_INCREMENT and
   friends). Getting it wrong is a performance issue, not a
   correctness one.                                        */

Asynchronous completion

Hardware is slow, so most drivers cannot finish a request before returning. Saying "not finished yet" correctly is a small protocol with strict rules, and getting it subtly wrong produces hangs and double completions.

/* The interesting case: you cannot complete now, so you queue
   the IRP and return.                                       */

NTSTATUS
MyRead(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp)
{
        PMY_DEVICE_EXTENSION ext = DeviceObject->DeviceExtension;

        /* 1. MARK IT PENDING BEFORE QUEUEING. If you queue it
              first, another thread can complete it before you
              mark it - and marking a completed IRP is a
              use-after-free.                               */
        IoMarkIrpPending(Irp);

        /* 2. set a cancel routine, so the request can be
              abandoned (below)                             */
        IoSetCancelRoutine(Irp, MyCancelRoutine);

        /* 3. queue it */
        ExInterlockedInsertTailList(&ext->PendingIrps,
                                    &Irp->Tail.Overlay.ListEntry,
                                    &ext->QueueLock);

        /* 4. return PENDING. The IRP now belongs to your
              queue; do NOT touch it after this point without
              the queue lock.                               */
        return STATUS_PENDING;
}

/* LATER - in the DPC when the hardware finishes: */
        PIRP irp = DequeueNextIrp(ext);

        if (irp) {
                irp->IoStatus.Status = STATUS_SUCCESS;
                irp->IoStatus.Information = bytesRead;
                IoCompleteRequest(irp, IO_NO_INCREMENT);
        }

/* AND THE USER SEES: ReadFile returns FALSE with
   GetLastError() == ERROR_IO_PENDING if the handle was opened
   with FILE_FLAG_OVERLAPPED, and the OVERLAPPED event is
   signalled at completion. Without FILE_FLAG_OVERLAPPED, the
   I/O manager blocks the thread for them and ReadFile appears
   synchronous.

   THIS IS ALL THE MACHINERY WDF QUEUES REMOVE (chapter 16).
   You should understand it once; you should not write it. */

Cancellation

An application can go away — or time out — while your driver is still holding its request. Cancellation is the mechanism for that, and it is the single hardest part of raw WDM because it races with your own completion path by design.

/* A queued IRP can be cancelled at any moment - the thread
   called CancelIo, the process is exiting, the handle closed.
   Getting this right in raw WDM is genuinely hard.         */

VOID
MyCancelRoutine(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp)
{
        PMY_DEVICE_EXTENSION ext = DeviceObject->DeviceExtension;
        KIRQL oldIrql;

        /* The I/O manager called us holding the GLOBAL cancel
           spinlock, at DISPATCH_LEVEL. RELEASE IT FIRST -
           holding it while taking our own lock is a lock
           ordering violation and a system-wide bottleneck. */
        IoReleaseCancelSpinLock(Irp->CancelIrql);

        KeAcquireSpinLock(&ext->QueueLock, &oldIrql);
        RemoveEntryList(&Irp->Tail.Overlay.ListEntry);
        KeReleaseSpinLock(&ext->QueueLock, oldIrql);

        Irp->IoStatus.Status = STATUS_CANCELLED;
        Irp->IoStatus.Information = 0;
        IoCompleteRequest(Irp, IO_NO_INCREMENT);
}

/* AND THE RACE, which is the whole difficulty:

     the cancel routine can fire at ANY time after
     IoSetCancelRoutine, including WHILE you are dequeuing the
     same IRP to complete it normally.

   THE PROTOCOL: whoever successfully clears the cancel
   routine owns the IRP.

        /* dequeuing normally: */
        KeAcquireSpinLock(&ext->QueueLock, &oldIrql);
        irp = DequeueOne(ext);
        if (irp && IoSetCancelRoutine(irp, NULL) == NULL) {
                /* the cancel routine ALREADY fired and owns
                   this IRP - do not touch it */
                irp = NULL;
        }
        KeReleaseSpinLock(&ext->QueueLock, oldIrql);

   Every raw-WDM driver must get this exactly right, on every
   queue, and most of the historical cancellation bugs in
   Windows drivers are here.                              */
This is the strongest argument for WDF

A WDF queue (chapter 16) handles pending, cancellation, the cancel-routine race, power-state stalling, and per-file-object cleanup — correctly, once, for everyone. The code above exists in this chapter so you can read and debug legacy drivers, and so that you understand what the framework is doing on your behalf. Write new drivers in KMDF.

Passing an IRP down

Most devices are served by several stacked drivers, each with its own view of the same request. Passing a request down means deciding what your layer wants to know about the result, which is what the stack locations and completion routines are for.

/* A filter driver, or any driver with something below it. */

/* --- pass it down and forget about it -------------------- */
NTSTATUS
MyPassThrough(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp)
{
        PMY_DEVICE_EXTENSION ext = DeviceObject->DeviceExtension;

        IoSkipCurrentIrpStackLocation(Irp);   /* reuse OUR slot -
                                                 we want no
                                                 completion
                                                 callback      */
        return IoCallDriver(ext->LowerDevice, Irp);
}

/* --- pass it down and see the result --------------------- */
NTSTATUS
MyFilter(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp)
{
        PMY_DEVICE_EXTENSION ext = DeviceObject->DeviceExtension;

        IoCopyCurrentIrpStackLocationToNext(Irp);
        IoSetCompletionRoutine(Irp, MyCompletion, ext,
                               TRUE,    /* on success */
                               TRUE,    /* on error   */
                               TRUE);   /* on cancel  */
        return IoCallDriver(ext->LowerDevice, Irp);
}

NTSTATUS
MyCompletion(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp,
             _In_ PVOID Context)
{
        /* Runs at <= DISPATCH_LEVEL, in an ARBITRARY thread.
           Do not assume you are in the requesting process. */

        if (Irp->PendingReturned)
                IoMarkIrpPending(Irp);   /* propagate it up -
                                            REQUIRED         */

        /* inspect or modify Irp->IoStatus here */

        return STATUS_CONTINUE_COMPLETION;
        /* or STATUS_MORE_PROCESSING_REQUIRED to STOP the
           completion and take ownership of the IRP - then you
           must complete it yourself later.               */
}

/* THE SKIP vs COPY DISTINCTION:
     IoSkipCurrentIrpStackLocation   reuses your slot for the
                                     next driver. Cheaper. No
                                     completion routine
                                     possible.
     IoCopyCurrentIrpStackLocationToNext  gives the next
                                     driver its own copy, and
                                     leaves yours free for the
                                     completion routine.

   Using Skip and then setting a completion routine corrupts
   the stack - a classic filter-driver bug that bugchecks
   randomly.                                                */

The full lifecycle

With the pieces covered, here is the whole journey in one place — allocation to completion — which is worth reading once end to end before moving on to the framework that automates it.

   ReadFile()
       |
   I/O manager: IoAllocateIrp / IoBuildSynchronousFsdRequest
       |  fills IoStatus, RequestorMode, the buffer fields
       |  sets up stack location [0] for the top driver
       v
   IoCallDriver(top)
       |
   +---v---------------------+
   | top driver              |  IoSkip/IoCopy, IoCallDriver
   +---+---------------------+
       |
   +---v---------------------+
   | function driver (you)   |  complete now, or
   |                         |  IoMarkIrpPending + queue
   +---+---------------------+       |
       |                             | later, from a DPC
       v                             v
   IoCompleteRequest(irp, boost)
       |
       |  walk UP the stack, running each completion routine
       |  bottom-first
       v
   the I/O manager:
       · copies SystemBuffer back to the user buffer
         (METHOD_BUFFERED)
       · unlocks and frees the MDL (DIRECT)
       · sets the OVERLAPPED / event
       · wakes the waiting thread
       · FREES THE IRP
       v
   ReadFile returns

  THE INVARIANT: an IRP is completed EXACTLY ONCE, by exactly
  one driver. Completing twice is a bugcheck; never completing
  it hangs the caller forever.

Debugging IRPs

When a request goes missing, the debugger can show you exactly where it stopped and who is holding it, which is almost always faster than reasoning about the code.

# In WinDbg (chapter 23):

    !irp ffff8a0c12345678
      Irp is active with 3 stacks, 2 is current
       cmd flg cl Device  File   Completion-Context
       [IRP_MJ_READ(3), N/A(0)]
         0  0  ffff8a0c...  ffff8a0c...   00000000-00000000
                \Driver\MyDriver
                Args: 00001000 00000000 00000000 00000000

    !irpfind                    every IRP in the system
    !irpfind -v 0 0 device ffff8a0c12345678
                                IRPs for one device
    !devstack ffff8a0c12345678  the whole device stack
    !devobj ffff8a0c12345678    one device object

# WHY !irpfind IS THE TOOL FOR A HANG: a thread stuck in
# ReadFile has an IRP that nobody completed. Find it, see
# which driver holds the current stack location, and you have
# named the culprit.

# LIVE TRACING: the I/O verifier option in Driver Verifier
# (chapter 22) checks IRP handling rules aggressively - double
# completion, touching a completed IRP, wrong IRQL at
# completion, missing PendingReturned propagation. Turn it on;
# these are exactly the bugs that are otherwise
# unreproducible.
