Rate control and buffer models

Deciding the quantisation parameter for every frame, under a constraint you cannot violate. It is the part of encoding that most affects what viewers actually see, and the part most often configured by copying a command line without understanding which mode it selected.

The modes, and which one you want

ModeYou specifyUse for
CQPA fixed QPTesting and research only. Bitrate varies wildly with content
CRFA quality targetThe default for anything stored. Constant perceptual quality, variable bitrate, one pass
ABR (1-pass)An average bitrateRarely the right answer — it must guess the future, and it guesses badly
2-pass VBRA target bitrate or file sizeWhen the size is a hard requirement. Pass 1 measures complexity, pass 2 spends accordingly
CBRA constant bitrateBroadcast, and links with a fixed capacity. Wastes bits on easy content by padding
Capped CRFCRF plus a maximum bitrateThe right answer for streaming. Quality-driven, but never exceeds what the client can pull
 
# CRF - the one to reach for.
$ ffmpeg -i in.mov -c:v libx264 -crf 23 -preset slow out.mp4

#   x264 CRF 18   visually lossless-ish
#         23      the default; good
#         28      noticeably compressed
#   x265 and AV1 use a similar scale but the numbers are NOT
#   comparable - x265 CRF 28 is roughly x264 CRF 23.
#   +6 CRF is about half the bitrate. -6 is about double.

# CAPPED CRF - quality-driven with a ceiling. This is what
# streaming services actually use:
$ ffmpeg -i in.mov -c:v libx264 -crf 23 \
    -maxrate 6M -bufsize 12M -preset slow out.mp4
#   crf      the quality you want
#   maxrate  the ceiling you must not exceed
#   bufsize  how much short-term variation is allowed
# Easy scenes come out well under 6M; hard scenes are capped.

# 2-PASS, when the SIZE is the requirement:
$ ffmpeg -i in.mov -c:v libx264 -b:v 5M -pass 1 -an -f null /dev/null
$ ffmpeg -i in.mov -c:v libx264 -b:v 5M -pass 2 out.mp4
# Pass 1 writes a stats file recording each frame's
# complexity. Pass 2 distributes the bit budget across the
# whole file, giving hard scenes more and easy ones less.

# CBR - genuinely constant, with padding:
$ ffmpeg -i in.mov -c:v libx264 -b:v 5M -minrate 5M -maxrate 5M \
    -bufsize 5M -x264-params "nal-hrd=cbr" out.ts

# THE MISTAKE PEOPLE MAKE: setting -b:v AND -crf together.
# CRF wins and the bitrate is ignored, so the file comes out
# a completely different size than intended and nobody can
# see why.
CRF is not "constant quality", it is constant effort

CRF adjusts QP per frame using a complexity estimate, deliberately spending fewer bits on frames where the eye will not notice — fast motion, dark scenes, high-detail texture. That is adaptive quantisation, and it is why CRF looks better than fixed QP at the same average bitrate. It also means the measured PSNR varies frame to frame by design, which surprises people benchmarking it.

The buffer model

   A decoder receives bits at some rate and consumes a whole
   frame instantly at each display time. If the buffer runs
   dry, playback stalls. The HRD (Hypothetical Reference
   Decoder) is the model that guarantees it will not.

     buffer
     fullness
        |     /\      /\
        |    /  \    /  \        fills at the bitrate,
   full |---/----\--/----\-----  drains by one frame's bits
        |  /      \/      \      at each frame time
        | /                \
   empty|/------------------\--  <-- UNDERFLOW = a stall
        +----------------------- time

   THE THREE PARAMETERS

     bitrate    the fill rate
     bufsize    the buffer capacity, in bits
     initial    how full before playback starts - this is
                your startup delay

   THE RULE: bufsize / bitrate = the seconds of variation
   allowed.

     bufsize = bitrate      1 second of slack. Tight; forces
                            near-constant frame sizes; costs
                            quality on hard scenes.
     bufsize = 2 x bitrate  the usual streaming choice.
     bufsize = 5 x bitrate  loose. Better quality, but the
                            client needs a bigger buffer and
                            a longer startup delay.

   WHY IT MATTERS
     * a live stream that overflows the client buffer causes
       REBUFFERING - the visible failure viewers actually
       complain about
     * hardware decoders implement the HRD literally, and a
       non-conformant stream can be REJECTED outright even
       though software players accept it
     * broadcast multiplexers allocate a fixed slot; exceeding
       it corrupts the whole multiplex, not just your channel

   AND THE FRAME-SIZE CONSEQUENCE: an I-frame is 10-20x a
   P-frame (chapter 10). With a tight buffer the encoder must
   either shrink the I-frame - hurting the whole GOP that
   predicts from it - or spread the cost over the following
   frames. Both look worse than a bigger buffer.

Adaptive quantisation and lookahead

/* WITHIN a frame, not all blocks deserve the same QP. */

  PSYCHOVISUAL MASKING: the eye cannot see quantisation error
  in a busy, high-contrast region, but sees it immediately in
  a smooth one. So:

     flat areas    -> LOWER QP (finer quantisation)
                      because banding and blocking would show
     detailed areas -> HIGHER QP
                      because the detail masks the error

  This is backwards from what "spend bits where the detail is"
  suggests, and it is measurably better.

    --aq-mode 1    variance-based AQ
    --aq-mode 2    auto-variance
    --aq-mode 3    auto-variance with a dark-scene bias -
                   x264's default, because dark areas show
                   banding badly
    --aq-strength  how aggressive, default 1.0

/* LOOKAHEAD: the encoder buffers N frames before deciding. */

    --rc-lookahead 40      x264's default

  WITH LOOKAHEAD THE ENCODER CAN:
    * see a scene cut coming and not waste bits on the frames
      about to be discarded
    * identify frames that many others will predict from and
      spend MORE on them - MB-tree / macroblock tree, which
      propagates a "how much does this block matter to the
      future" weight backwards
    * distribute the bit budget over an upcoming hard scene
      instead of reacting to it late

  MB-TREE IS WORTH 5-15% ON ITS OWN and is why x264 at
  --preset slow beats a naive encoder at the same bitrate.

  THE COST: latency. 40 frames of lookahead is 1.6 seconds at
  25 fps. Real-time encoding sets --rc-lookahead 0 and
  accepts the loss (chapter 10).                            */
Quality pumping and how to recognise it

If quality visibly oscillates — sharp, then soft, then sharp again on a two-second cycle — rate control is overreacting. Usual causes: bufsize too small for the content, ABR mode trying to hit an average without lookahead, or a GOP whose I-frame consumes so much of the budget that the following frames are starved. The fix is almost always a larger bufsize or switching to capped CRF; it is very rarely a higher bitrate.

Rate control for adaptive streaming

# A streaming ladder is several renditions of the same source,
# and the client switches between them. Constraints:

  1. GOP-ALIGNED. Every rendition must have a keyframe at the
     same timestamps, or switching produces a glitch.
       -x264-params "keyint=48:min-keyint=48:scenecut=0"
     with 48 = 2 seconds at 24 fps. Scene cuts MUST be
     disabled or the alignment breaks (chapter 10).

  2. CAPPED CRF per rung, not fixed bitrate. An easy scene at
     1080p may only need 2 Mbit/s; forcing 6 wastes bandwidth
     and gains nothing.

  3. THE LADDER ITSELF should be per-title. Netflix's
     per-title encoding measures each title's complexity and
     builds a custom ladder - an animated series needs far
     less bitrate at 1080p than a grainy film, and a fixed
     ladder over-serves one and under-serves the other.

# A reasonable fixed ladder, for reference:
#   1920x1080  crf 21  maxrate  6000k  bufsize 12000k
#   1280x720   crf 21  maxrate  3000k  bufsize  6000k
#    854x480   crf 22  maxrate  1500k  bufsize  3000k
#    640x360   crf 23  maxrate   800k  bufsize  1600k
#    426x240   crf 24  maxrate   400k  bufsize   800k

# Segment and package:
$ ffmpeg -i in.mp4 \
  -c:v libx264 -crf 21 -maxrate 6000k -bufsize 12000k \
  -x264-params "keyint=48:min-keyint=48:scenecut=0" \
  -f hls -hls_time 2 -hls_playlist_type vod \
  -hls_segment_filename "1080p_%03d.ts" 1080p.m3u8

# VERIFY THE ALIGNMENT - this is the check people skip:
$ for f in 1080p 720p 480p; do
    echo -n "$f: "
    ffprobe -select_streams v -skip_frame nokey \
      -show_entries frame=pkt_pts_time -of csv=p=0 $f.m3u8 \
      | head -5 | tr '\n' ' '
    echo
  done
1080p: 0 2 4 6 8
720p:  0 2 4 6 8
480p:  0 2 4 6 8        # aligned. If these differ, switching
                        # will glitch.
