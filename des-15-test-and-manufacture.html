Testing, bring-up and manufacturability

This is the stage candidates skip and interviewers use to separate people who have shipped hardware from people who have made one work on a bench. Thirty seconds spent on design for test signals more production experience than anything else you can say.

Design for test

   WHAT MUST EXIST IN THE SCHEMATIC, decided at design time
   because none of it can be added later:

   SWD / JTAG        on a tag-connect or pogo footprint.
                     Without it a board that will not boot
                     teaches you nothing.

   A UART            console during bring-up, diagnostics
                     for a returned unit, and the
                     provisioning channel on the line.

   A SPARE GPIO      brought to a pad, for toggling in an
                     ISR and measuring timing with a scope.
                     Costs one pin and is the single most
                     useful debug tool there is.

   A SENSE RESISTOR  in the battery path, so the production
                     line can MEASURE sleep current as a
                     pass/fail test rather than assuming it.

   TEST POINTS       on every power rail, the reset line,
                     each clock, and each bus.

   A WAY TO ISOLATE  jumpers or DNF resistors so a
                     subsystem can be disconnected during
                     bring-up.

   BOOT MODE ACCESS  the ROM bootloader pin brought to a
                     pad, not tied low permanently. This is
                     the recovery path when a bad firmware
                     disables everything else.

   THE COST is a few pads and perhaps two pins. The cost of
   NOT having them is a board respin or an undiagnosable
   field return - and the counter-consideration, security,
   is handled by disabling the ports in provisioning while
   keeping the pads for factory use (chapter 13).

Bring-up order

NEW BOARD, FIRST POWER-ON. Do this in order; each step
depends on the previous one being sound.

  0. INSPECT. Visual check, then measure resistance from
     each rail to ground BEFORE applying power. A short
     found with a multimeter costs nothing; a short found
     with a power supply costs a board.

  1. POWER. Apply current-limited supply. Check each rail
     for correct voltage AND correct sequence. Measure
     current draw against expectation - wildly wrong means
     stop.

  2. CLOCKS. Scope the crystal. Is it oscillating, at the
     right frequency, with the right amplitude? A crystal
     that does not start is one of the most common new-board
     faults, and everything above it is meaningless.

  3. RESET. Confirm the reset line releases and stays
     released.

  4. DEBUG CONNECTION. Can the probe see the core? If yes,
     you have a functioning processor and most bring-up
     risk is behind you.

  5. CONSOLE. Get a UART printing. From here you are
     debugging software rather than hardware.

  6. PERIPHERALS, ONE AT A TIME. Never enable everything
     at once - a single bad peripheral then makes the whole
     board look dead. Enable, test, commit, move on.

  7. FULL SYSTEM, then thermal and margin testing.

THE PRINCIPLE: change one thing at a time and confirm it
before proceeding. Bring-up goes wrong when several
unknowns are in play simultaneously.
The two questions that reveal production experience

"How is each unit tested on the line, and how long does that take?" — every unit must be tested, the test needs hardware support and a fixture, and its cycle time multiplied by the volume is a real manufacturing cost that can change the design. "How does a unit get its identity and calibration?" — provisioning is a per-unit step that needs a channel, a station, a database and an idempotent, resumable process. Raising either unprompted in a design round is worth more than several minutes of architecture discussion.

The production test

WHAT IT MUST DO TO EVERY UNIT:

  flash firmware
  provision identity: serial number, keys, certificate
  write calibration constants
  exercise every interface and every connector
  verify current in active AND sleep states
  check any analog path against a known stimulus
  record everything against the serial number
  lock the device (debug off, readout protection on) LAST

CONSTRAINTS THAT SHAPE THE DESIGN:

  CYCLE TIME     seconds per unit x millions of units. A
                 30-second key generation may be
                 unacceptable and may drive the part
                 choice.
  FIXTURE        pogo pins need pads with keep-out around
                 them, and a mechanical alignment feature.
  COVERAGE       a test that only checks "does it boot"
                 passes boards with a dry joint on an
                 unused peripheral, which then fails in the
                 field.
  DIAGNOSABILITY when a unit fails the test, the line needs
                 to know WHY, so the test must report a
                 specific fault code, not just "fail".
  IDEMPOTENCE    a unit interrupted mid-provisioning must
                 be re-runnable, or it is scrap.

TWO MORE THINGS WORTH MENTIONING

  TRACEABILITY   which firmware, which component batch,
                 which test results, per serial number. When
                 a field failure pattern emerges, this is
                 what lets you identify the affected units
                 instead of recalling everything.

  GOLDEN UNITS   a known-good board kept aside and run
                 through the test periodically, to detect
                 when the TEST has drifted rather than the
                 product.

Testing the firmware itself

THE LAYERS, and what each can and cannot catch:

  UNIT TESTS on a host. Fast, run on every commit. Require
    the code to be portable - which means hardware access
    behind an interface you can substitute. That
    portability is worth having for its own sake.
    CANNOT catch: anything about real hardware timing,
    electrical behaviour, or the actual peripheral.

  INTEGRATION on real hardware, automated. A bench rig that
    can power-cycle the target, flash it, drive its inputs
    and observe its outputs (see the Raspberry Pi track's
    lab bench project). Runs on every merge.
    CATCHES: the class of bug no host test can - a watchdog
    never wired up, a brown-out that corrupts the
    filesystem, a sensor that NACKs one time in a thousand,
    timing that drifts when the board is warm.

  SOAK TESTS days of realistic load. The only way to find
    leaks, fragmentation, counter wraps and slow drift.

  FAULT INJECTION deliberately cut power mid-write, drop
    the network, disconnect a sensor, corrupt a flash
    block. If you have not tested the failure paths, they
    do not work - they are the least-executed code in the
    product.

  MARGIN TESTING at the temperature, voltage and clock
    extremes, not just at nominal.

THE ONE THAT CATCHES THE MOST BUGS PER HOUR SPENT is fault
injection, because the happy path is exercised constantly
during development and the error paths are exercised
never.

Questions

What would you add to a schematic purely to make the product testable?Mid

SWD or JTAG on a tag-connect footprint; a UART for the console, diagnostics and provisioning; at least one spare GPIO brought to a pad for timing measurement with a scope; a sense resistor in the battery path so the line can measure sleep current as a pass/fail criterion; test points on every rail, the reset line and each clock; jumpers or do-not-fit resistors so subsystems can be isolated during bring-up; and the ROM boot-mode pin brought to a pad rather than tied low, because that is the recovery path when firmware disables everything else.

The cost is a few pads and perhaps two pins. The cost of omitting them is a board respin or a field return nobody can diagnose.

The security tension is real and manageable: the ports get disabled during provisioning as the last step, while the pads remain for factory and repair use behind an authenticated unlock.

Listening forThe sense resistor and the boot-mode pad — both are details only people who have shipped tend to mention.
A new board arrives and does not boot. Walk me through your first hour.Mid

In order, changing one thing at a time. Before power: visual inspection and a resistance check from every rail to ground — a short found with a multimeter is free, a short found with a supply may cost the board.

Power: current-limited supply, check each rail for voltage and sequence, and compare total current against expectation. Wildly wrong means stop and investigate rather than pushing on.

Clocks: scope the crystal. Oscillating? Right frequency? Right amplitude? A crystal that does not start is among the most common new-board faults and nothing above it can work.

Reset: confirm it releases and stays released. Debug: can the probe see the core? If yes, most hardware risk is behind you. Console: get a UART printing — from here it is a software problem.

Then peripherals one at a time. The failure mode to avoid is enabling everything at once, where a single bad peripheral makes the whole board look dead.

Listening forThe resistance check before power, and the clock check before blaming software.
What does the production line have to do to each unit, and how does that affect your design?Senior

Flash firmware; provision a serial number, keys and certificate; write calibration constants; exercise every interface and connector; verify active and sleep current; record everything against the serial number; and lock the device last.

The design effects: every one of those steps needs hardware support that must be in the schematic — a programming and console interface, a fixture-friendly pad layout with mechanical alignment, a current sense, and a way to stimulate and observe each interface. Cycle time is a real cost: a provisioning step taking thirty seconds is unacceptable at a million units and may drive the choice of part or key algorithm. The process must be idempotent, so an interrupted unit can be re-run rather than scrapped. And the locking step is irreversible, so it must be genuinely last and the sequence must be right.

Two additions worth mentioning: traceability, so that when a field pattern emerges you can identify affected units by batch rather than recalling everything; and golden units run periodically through the test to detect drift in the test rather than the product.

Listening forCycle time as a design input, idempotence, and traceability.
How do you test firmware that depends on hardware?Mid

In layers, because each catches a different class of bug.

Host unit tests for logic, with hardware access behind an interface you can substitute. That forces a portable structure which is worth having anyway. Fast enough to run on every commit — but they cannot tell you anything about real timing or electrical behaviour.

Hardware-in-the-loop for everything else: a rig that power-cycles the target, flashes it, drives its inputs and observes its outputs, running automatically on every merge. This catches what no host test can — a watchdog that was never wired up, a brown-out that corrupts storage, a sensor that occasionally NACKs, timing that drifts when the board warms.

Soak tests over days for leaks, fragmentation and counter wraps. Fault injection — cut power mid-write, drop the network, disconnect a sensor — because the error paths are the least-executed code in the product and therefore the least correct. Margin tests at temperature and voltage extremes.

If I could only have one beyond unit tests, it would be fault injection on real hardware: highest bug yield per hour spent.

Listening forThe layering with a clear statement of what each cannot catch, and fault injection prioritised.
Why is a production test that checks "does it boot" insufficient?Mid

Because it passes boards with real defects that only manifest later. A dry solder joint on an unused peripheral, a connector with one bad pin, a sensor with a marginal I2C pull-up, a slightly out-of-spec crystal, a MOSFET installed backwards on a rail that is not exercised — all boot fine and all fail in the field, often after the warranty conversation has already gone badly.

A good test exercises every interface and every connector at least once, checks analog paths against a known stimulus rather than just reading them, verifies current in both active and sleep states (which catches a huge range of assembly faults), and confirms the calibration actually took.

It also has to be diagnosable: when a unit fails, the line needs a specific fault code so the operator knows whether to rework or scrap, and so that a rising rate of one particular failure is visible as a process problem rather than noise.

The trade to acknowledge: more coverage costs cycle time, and cycle time costs money at volume. Where that line sits is a business decision informed by field failure cost.

Listening forSleep current as a broad assembly-fault detector, and the diagnosability requirement.
How do you make firmware testable on a host machine?Mid

Separate logic from hardware access behind a thin interface, so the logic can be compiled and run natively with a substitute implementation. In C that is typically a struct of function pointers, or link-time substitution of a small hardware abstraction layer — not a heavyweight framework.

What that buys beyond testing: the logic can be exercised with fault injection that is impossible on hardware (a sensor returning NaN, a bus that always times out), it runs under sanitizers and Valgrind on the host, and it is fast enough for property-based or fuzz testing — which is extremely effective on protocol parsers, exactly where the security-relevant bugs are.

The discipline it imposes: no direct register access scattered through business logic, no global state reached from anywhere, and time obtained through an interface rather than by reading a hardware counter — which also makes it possible to test time-dependent behaviour by advancing a fake clock instead of waiting.

The honest limit: this tests your logic, not your driver, and not the hardware. It complements hardware-in-the-loop rather than replacing it.

Listening forInjecting time through an interface, and fuzzing parsers as a concrete payoff.
What is a golden unit and why keep one?Senior

A known-good board, characterised and set aside, run through the production test periodically. Its purpose is to distinguish the product has drifted from the test has drifted — because both look identical from the yield data.

Test fixtures wear out: pogo pins lose contact force, cables develop intermittents, a reference instrument goes out of calibration, and a software update to the test station changes a threshold. Any of those produces a rising failure rate that looks like a manufacturing problem and is not. Without a golden unit you can spend weeks investigating the wrong thing, and possibly scrap good product.

Related practices worth mentioning: keep several golden units in case one is damaged; re-characterise them periodically against traceable references; and record the golden-unit results over time, because a slow trend is itself the early warning.

Listening forThe specific insight that failing yield may be a test problem, not a product problem.
How would you test the error paths, given they almost never run?Senior

By forcing them, because they will not occur naturally and untested code does not work. Three mechanisms, in increasing fidelity.

At the interface: if hardware access is behind a substitutable interface, the test can make any call fail — a bus returning a timeout, a flash write reporting an error, an allocation returning null. This is fast, runs on the host, and covers the majority of error handling.

At the hardware: the bench rig physically cuts power mid-write, disconnects a sensor, shorts a bus, drops the network, and brown-outs the supply. This catches the paths that involve the actual device state, which the interface-level test cannot model faithfully.

By construction: compile-time or runtime fault injection built into the firmware — a debug build where a command can make the next flash write fail — so that a specific rare path can be triggered on demand, including in an integration test.

And measure coverage of the error paths specifically, because overall coverage figures are dominated by the happy path and can look healthy while every recovery routine is untouched.

Listening forFault injection at more than one layer, and measuring error-path coverage separately.
A product passes all tests and fails in the field. What was missing?Senior

Almost always one of four things. Margin: tests ran at nominal temperature, voltage and clock; the field runs at extremes, and a design that passes at 25 °C may not at −20 °C or 60 °C. Duration: tests ran for minutes; the field runs for years, so leaks, fragmentation, counter wraps and wear only appear there. Variety: tests ran on a handful of boards from one batch; the field has component tolerance spread, and the failing unit is the one at the limit. Reality: tests ran on the happy path with a clean supply and a good network; the field has brown-outs, dropped connections, vibration, EMI and users doing unexpected things.

The responses: margin testing across the specified environmental range, soak tests measured in days, testing across multiple production batches, and fault injection reproducing field conditions.

And the process response, which matters as much: instrument the fleet so that field failures are diagnosable and their rate is visible, then feed each root cause back into the test suite — so the same failure cannot recur silently. A test suite that only grows when someone remembers to add to it will always lag the field.

Listening forAll four gaps, and closing the loop from field failures back into tests.
What is design for manufacture, in firmware terms?Senior

Making the firmware's requirements compatible with how the product is actually built at volume.

Concretely: a provisioning process that is fast, idempotent and scriptable; a test mode that the line can enter deterministically and that cannot be entered accidentally in the field; calibration that can be performed with the fixture's instruments rather than requiring a lab; fault reporting specific enough for an operator to act on; and a firmware image that is identical across units, with all per-unit variation in a separate data region — so the line flashes one file and writes a small record, rather than building a unique image per device.

Also: supporting multiple hardware variants from one image where possible, reading the variant from a resistor divider or an ID chip, because managing several images through a factory is an error source. And version reporting that the line records, so traceability actually works.

The framing worth stating: the factory is a user of your firmware, with its own requirements, and it is a user nobody consults during design. Asking "what does the line need from this?" during the design phase is what design for manufacture means in practice.

Listening forOne image plus a data region, and treating the factory as a user with requirements.
