Memory architecture and budgeting

Memory is the constraint candidates most often get wrong, because the arithmetic has terms that are easy to forget and consequences that arrive late. A memory budget you can produce on a whiteboard is one of the strongest signals available in a design round.

The budget, with every term

FLASH (or whatever holds the image)

    code (.text)
  + read-only data (.rodata): strings, tables, fonts,
    calibration constants
  + .data INITIALISERS - the values that get copied to RAM
    at boot. This term is counted in BOTH budgets.
  + the OTA SLOT - typically a full second copy of the
    application (chapter 12). THIS IS THE TERM CANDIDATES
    FORGET, and it roughly doubles the requirement.
  + bootloader
  + a configuration / calibration region
  + wear-levelling overhead if you write to it

RAM

    .data      initialised globals
  + .bss       zero-initialised globals
  + STACKS     one per task, each sized from measurement
               plus ~50%, each carrying at least one
               exception frame (32 B, or 104 B with FP)
  + interrupt stack (MSP) sized for worst-case nesting
  + heap, if any
  + DMA buffers - and note these often have alignment and
    placement constraints
  + protocol buffers: a TCP/IP stack wants tens of kB;
    a TLS session wants 20-50 kB for the handshake alone
  + double buffers for anything streaming

WORKED EXAMPLE, a BLE sensor node:
    code                     48 kB
    rodata                    6 kB
    .data initialisers        2 kB
    BLE stack (vendor)       80 kB
    bootloader                8 kB
    ---------------------------------
    app image               144 kB
    OTA slot                144 kB
    config                    4 kB
    ---------------------------------
    FLASH TOTAL             292 kB  -> a 512 kB part, not
                                       the 256 kB one you
                                       would have guessed

    .data + .bss              9 kB
    BLE stack RAM            14 kB
    4 task stacks x 1.5 kB    6 kB
    MSP                       2 kB
    DMA + protocol buffers    4 kB
    ---------------------------------
    RAM TOTAL                35 kB  -> 64 kB part
The three terms candidates forget

The OTA slot — if the device updates in the field with A/B slots, flash is roughly double the application. The .data double-count — initialised globals occupy flash for their initial values and RAM for the variables. The protocol stack — a vendor BLE or TCP/IP stack can be larger than your application, and TLS in particular is a memory monster. Naming all three unprompted is worth real credit.

Where things live, and why it matters

   ON A MICROCONTROLLER, placement is a design decision,
   not an implementation detail.

   FLASH, executed in place
     Code and const data are read directly. Flash is slower
     than the core, so at high clocks you need wait states
     and a prefetch/cache accelerator - and that is why
     enabling the ART accelerator or equivalent can change
     performance by 2x.

   SRAM
     Fast, scarce. Some parts have multiple banks with
     DIFFERENT PROPERTIES: one reachable by DMA, one not
     (CCM RAM on STM32F4 is the classic trap); one tightly
     coupled to the core (TCM) with no wait states.

   THE PLACEMENTS WORTH KNOWING:

     .ramfunc     code copied to RAM at boot. Required for
                  a flash-erase routine, because you cannot
                  execute from the flash you are erasing.

     .noinit      RAM excluded from the startup zeroing, so
                  it SURVIVES a warm reset. This is where a
                  crash log goes so the next boot can
                  report why the last one ended.

     DMA region   a bank the DMA engine can actually reach,
                  aligned to the cache line on parts with a
                  D-cache.

     Backup RAM   a small region in the always-on power
                  domain, retained through deep sleep.

   ON AN APPLICATION PROCESSOR the equivalent decisions are
   CMA size for camera and video buffers, whether the root
   filesystem is in RAM, and how much you reserve for the
   GPU - all of which are boot-time configuration, not code.

Dynamic allocation, and the alternative

WHY malloc IS DISCOURAGED - four distinct problems:

  FRAGMENTATION   after weeks of mixed-size allocations,
                  enough free bytes exist but no contiguous
                  block does. The failure appears only
                  after long uptime, which means it appears
                  in the field and not in test.

  NON-DETERMINISM allocation time is not bounded, so it
                  cannot appear in a real-time path.

  ERROR PATHS     every call needs a failure branch that is
                  hard to test and usually wrong.

  PRIORITY        the allocator has a lock, so a
  INVERSION       high-priority task can block behind a
                  low-priority one inside malloc.

THE ALTERNATIVES, in order of preference:

  1. STATIC ALLOCATION. Everything sized at compile time,
     so the LINKER proves it fits and there is no runtime
     failure mode at all. FreeRTOS supports this fully
     (configSUPPORT_STATIC_ALLOCATION); safety-critical
     projects require it.

  2. POOL ALLOCATORS. Fixed-size blocks from a
     pre-allocated array. O(1), cannot fragment, and
     exhaustion is a countable, testable condition.
     Several pools of different sizes covers most needs.

  3. ALLOCATE-ONLY AT INIT. A heap used during startup and
     never freed. Fragmentation is impossible by
     construction.

  4. A REAL HEAP, if the platform is large and the
     workload genuinely dynamic - which on Linux is
     normal and on an MCU is a decision to justify.

THE LINKER CHECK worth knowing: a section that allocates
your declared minimum stack and heap and therefore makes
the BUILD FAIL if they no longer fit. Trading a runtime
mystery for a compile error is the whole art.

Questions

Produce a flash and RAM budget for a connected sensor node.Mid

Flash: application code, read-only data, the .data initialisers, the vendor protocol stack (BLE or TCP/IP — often larger than your own code), the bootloader, a configuration region, and the OTA slot, which is a second full copy of the application. For a typical BLE node that is roughly 48 + 6 + 2 + 80 + 8 = 144 kB of image, doubled to 288 kB for A/B, plus config — so a 512 kB part, not the 256 kB one the naive sum suggests.

RAM: .data + .bss, the protocol stack's RAM, one stack per task (measured plus 50%), the interrupt stack sized for worst-case nesting, DMA buffers, and any double buffers. Around 35 kB for that example, so a 64 kB part.

Then state the headroom rule: aim to use about half of each on the first working version, because firmware grows and running out late means a respin.

Listening forThe OTA slot and the .data double-count. Getting both is the difference between a rehearsed answer and a real one.
Why is malloc discouraged, and what would you use instead?Mid

Four separate problems: fragmentation (free bytes exist, contiguous block does not — and it appears only after long uptime, i.e. in the field); unbounded allocation time, which breaks real-time paths; an error path per call that is hard to test; and priority inversion through the allocator's lock.

Instead, in order: static allocation, so the linker proves it fits and there is no runtime failure mode; fixed-size pool allocators, which are O(1) and cannot fragment; or a heap used only during initialisation and never freed, which makes fragmentation impossible by construction.

The nuance worth adding: none of this applies with the same force on a Linux system with gigabytes and no hard deadline. The rule is a response to specific constraints, not a superstition — and saying so shows you understand why rather than having memorised it.

Listening forFragmentation and determinism as distinct problems, and knowing the rule's scope.
A DMA transfer completes but the buffer contains zeros. What are your hypotheses?Mid

In order of likelihood. The buffer is in memory the DMA engine cannot reach — many parts have RAM banks outside the DMA's address space (CCM RAM on STM32F4 is the classic), and the transfer completes reporting success while writing nowhere useful. Cache coherency — on a part with a D-cache you did not invalidate after the transfer, so the CPU is reading stale lines rather than the new data. The buffer was a stack local that went out of scope while the transfer was still running. Alignment or width mismatch between peripheral and memory, which some controllers report as an error and some do not.

How to distinguish: check the DMA error flags first, then read the buffer's physical address and compare against the memory map, then try the same transfer into a statically allocated buffer in main SRAM.

Listening forOrdered hypotheses with a way to discriminate between them, not a list.
What is a .noinit section for?Mid

RAM that the startup code deliberately does not zero, so its contents survive a warm reset. The primary use is a crash log: when a fault handler runs, it writes the faulting PC, the fault status registers and the task name into .noinit, then resets. Early in the next boot you check a magic number, report or store the record, and clear it.

That turns a field unit that "just reboots sometimes" into one that tells you the faulting source line — and it costs about forty lines of code. It is impossible to add after deployment, which is why it belongs in the initial design.

Other uses: a boot counter, a flag requesting the bootloader to enter update mode, and state that should persist across a reset but not across a power cycle.

The classic bug: putting the log in an ordinary global, where startup zeroes it before anything can read it.

Listening forThe crash-log use case specifically — it indicates having supported deployed devices.
Why can't you run a flash-erase routine from flash?Mid

Because while a flash bank is being erased or programmed it cannot service instruction fetches — the controller stalls or returns undefined data. If the code doing the erasing lives in that bank, the core stops fetching valid instructions mid-operation and hangs.

The fix is to place the routine in a section that the linker gives a RAM address but a flash load address — the same LMA/VMA trick .data uses — and have startup copy it. GCC's __attribute__((section(".ramfunc"), long_call)) plus a matching linker section does it. The long_call matters because the call now crosses a large address gap.

This matters for any in-application programming: bootloaders, OTA update handlers, and wear-levelling routines. On parts with two independent flash banks you can sometimes execute from one while erasing the other, which avoids the problem — but relying on that is a part-specific decision to document.

Listening forThe LMA/VMA mechanism, not just "put it in RAM".
How much stack does an interrupt need, and where should interrupts run?Mid

Each nesting level costs at least one exception frame — 32 bytes on Cortex-M, or 104 with floating-point context — plus the handler's own locals and any function it calls. Worst case is the maximum nesting depth times that, and nesting depth is bounded by the number of distinct preemption priority levels you have configured.

They should run on the main stack (MSP) while tasks run on the process stack (PSP). That way interrupt nesting is charged once to a single stack you size deliberately, rather than being added to every task's stack. Without the split, each task stack must independently carry the worst-case interrupt depth, which multiplies the cost by the number of tasks.

This is exactly what an RTOS does when it switches tasks to PSP at startup, and it is one of the concrete reasons the two-stack-pointer design exists.

Your firmware fits in flash but the build fails after adding a small feature. What is happening?Junior

Most likely you were already at the limit and the new code crossed it — but the more interesting version of this question is when the increase is disproportionate, say 8 kB of flash for twenty lines of code. That is almost always a library pulled in transitively: adding a printf with %f drags in floating-point formatting; adding an assert can pull in printf; using sprintf where snprintf would do can pull in a different code path entirely.

How to find out: the map file. Pass -Wl,-Map=firmware.map and it records every symbol, its size, and crucially which object pulled it in. nm --size-sort -S ranks symbols by size. Between them you can usually name the culprit in a minute.

The fixes: -specs=nano.specs for newlib-nano, a tiny printf implementation, avoiding float formatting, and -ffunction-sections -fdata-sections with --gc-sections so unused code is actually discarded.

Listening forThe map file as the diagnostic tool — it is the most under-used artefact in embedded builds.
What is different about memory budgeting on a Linux system?Mid

The nature of the problem changes from "does it fit" to "what happens under pressure". You have virtual memory, demand paging, overcommit and an OOM killer, so a process can allocate more than exists and be killed later at an arbitrary point.

What you budget instead: total working set against physical RAM; whether swap exists (on flash storage, usually a mistake because of write endurance); the page cache, which will consume all free memory and is usually fine; reserved regions such as CMA for camera and video buffers, which must be sized at boot and cannot be adjusted later; and per-process limits via cgroups so one leak cannot take down the system.

The failure modes to design for: the OOM killer choosing the wrong process (set oom_score_adj for critical services), and a slow leak that only manifests after weeks. Monitoring RSS over time in the field is the practical defence.

Listening forCMA and the OOM killer — both are Linux-embedded specifics that distinguish real experience.
How do you detect a memory leak on a device that runs for months?Senior

Prevention first: on an MCU, if everything is statically allocated there is no leak to find, which is a strong argument for that discipline. Where a heap exists, instrument it — track allocation count and current bytes in use, expose them as counters, and log the high-water mark. A leak shows as a monotonically rising floor, which is visible long before exhaustion.

For detection during development: on Linux, Valgrind or ASan's leak checker; in the kernel, CONFIG_DEBUG_KMEMLEAK. On an MCU, a pool allocator makes leaks countable per pool, which is far easier than a general heap.

For the field: report the counters as telemetry, or store the high-water mark in non-volatile memory so a returned unit shows its history. And run a soak test — days of realistic load — as a release gate, because a leak of a few bytes per hour will never appear in a functional test.

Listening forInstrumentation and soak testing as the practical answers, rather than only naming tools.
You need a 200 kB buffer on a part with 128 kB of RAM. What are your options?Mid

First challenge the requirement — why 200 kB? Often the answer is "I want the whole frame/message/file in memory", and the real need is to process it, which can be done streaming.

Then, in rough order of preference: process incrementally with a small window (a hash, a filter or a parser almost never needs the whole input); double-buffer and process one half while DMA fills the other, which is the standard answer for audio and sensor streams; compress or decimate before buffering; use external memory — QSPI PSRAM or SDRAM, which costs a part and pins and brings latency; or choose a bigger part, which may well be the cheapest answer once engineering time is counted.

The one to avoid: an external memory added late to rescue a design, because it changes the board, the boot sequence and often the performance characteristics.

Listening forChallenging the requirement first, and naming streaming/double buffering before reaching for hardware.
