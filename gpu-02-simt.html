SIMT: how a GPU really executes

You write code for one thread. The hardware runs thirty-two of them from a single instruction pointer. That gap between the programming model and the execution model is where GPU performance lives, and pretending it is not there is why most first kernels are slow.

SIMD wearing a disguise

   SIMD - what the hardware does
     one instruction, one register file of N lanes, N results.
     The programmer sees vectors and writes vector code.

        vaddps  ymm0, ymm1, ymm2      ; 8 floats at once

   SIMT - what the GPU shows you
     one instruction, N THREADS each with their own registers
     and their own view of memory. The programmer writes
     SCALAR code for one thread.

        c[i] = a[i] + b[i];           // "one thread"

   UNDERNEATH THEY ARE THE SAME MACHINE. The GPU groups your
   threads into WARPS of 32 and issues one instruction for the
   whole warp, every cycle.

     warp = 32 threads
            ONE program counter
            32 sets of registers
            a 32-bit ACTIVE MASK saying which lanes are live

   WHAT SIMT ADDS OVER SIMD

     1. per-lane addressing. Each thread computes its own
        address, so gather and scatter are free at the
        programming level (though not at the memory level -
        chapter 4).
     2. per-lane control flow, via the mask. You may write an
        `if` and it will behave correctly - at a cost
        (chapter 3).

   WHAT IT DOES NOT CHANGE

     the 32 threads still share ONE program counter. They are
     not independent. Anything that makes them want to be in
     different places costs you.
The warp is the unit of everything

Scheduling, instruction issue, memory coalescing, divergence and most synchronisation all operate on warps, not threads. "How many threads" is almost never the useful question; "how many warps, and are their lanes doing the same thing on adjacent data" is. A block of 100 threads occupies four warps and wastes 28 lanes of the fourth — which is why block sizes are always multiples of 32.

Inside an SM

   One Streaming Multiprocessor, roughly (NVIDIA Ampere-ish):

   +-----------------------------------------------------------+
   |  INSTRUCTION CACHE                                        |
   +-----------------------------------------------------------+
   |  WARP SCHEDULERS  x4                                      |
   |    each holds up to 16 resident warps and picks ONE       |
   |    ready warp per cycle to issue                          |
   +-----------------------------------------------------------+
   |  REGISTER FILE   65,536 x 32-bit  =  256 KB               |
   |    partitioned among resident warps. THIS is the budget   |
   |    that decides how many fit (chapter 5).                 |
   +-----------------------------------------------------------+
   |  EXECUTION UNITS                                          |
   |    32x INT32/FP32 lanes    (the main array)               |
   |    16x FP64                (few, on consumer parts)       |
   |     4x SFU     sin, cos, rsqrt - slow, low throughput     |
   |     4x LD/ST   address generation                         |
   |     4x TENSOR  matrix-multiply-accumulate                 |
   +-----------------------------------------------------------+
   |  128 KB, split between L1 CACHE and SHARED MEMORY         |
   |    the split is configurable per kernel                   |
   +-----------------------------------------------------------+

   THE KEY OBSERVATION: there are 32 FP32 lanes and up to 64
   RESIDENT WARPS. The hardware can only execute a few warps
   per cycle, but it KEEPS dozens ready. When one stalls on
   memory, the scheduler issues from another - in the same
   cycle, at no cost, because every warp's registers are
   already live in the file.

   That is latency hiding, and it is why occupancy matters.

One cycle in the life of a scheduler

/* A warp scheduler holds N resident warps. Every cycle it
   picks one that is READY and issues its next instruction. */

  cycle 1:  warp 3  -> LDG   R4, [R2]     ; global load, ~500
                                            cycles. warp 3 is
                                            now STALLED.
  cycle 2:  warp 7  -> FMA   R1, R2, R3   ; ready, issue it
  cycle 3:  warp 12 -> LDG   R8, [R6]     ; stalls too
  cycle 4:  warp 7  -> FMA   R5, R1, R4   ; still ready
  cycle 5:  warp 19 -> IADD  R0, R0, 1
  ...
  cycle 500: warp 3's load returns -> warp 3 is READY again

/* WITH ENOUGH WARPS the ALUs never idle, and the 500-cycle
   memory latency is completely invisible.

   WITH TOO FEW WARPS - say 4 resident - all four issue a load
   and then everyone waits. The SM sits idle for hundreds of
   cycles with nothing to do.

   THE ARITHMETIC:
     to hide 500 cycles of latency with an SM that issues 4
     instructions per cycle, you need roughly
         500 x 4 / (instructions between loads)
     warps in flight. For memory-heavy code that is dozens.

   THIS IS WHY "more parallelism" is the answer to almost
   every GPU performance question, and why a kernel with
   perfect arithmetic and no occupancy is slow.            */

Independent thread scheduling

/* PRE-VOLTA (before 2017): one PC per warp. Threads within a
   warp could NOT make independent progress. This was legal:  */

        /* the "warp-synchronous" idiom - once ubiquitous */
        shared[tid] = value;
        /* no __syncthreads() needed if tid < 32, because the
           warp is in lockstep by construction */
        if (tid < 16) shared[tid] += shared[tid + 16];

/* VOLTA AND LATER: each thread has its own PC and call stack.
   Threads in a warp may diverge and RECONVERGE independently,
   and the hardware may interleave them.

   That broke every warp-synchronous program in existence,
   silently and intermittently.

   THE FIX: state your assumption explicitly. */

        __syncwarp();                    /* barrier the warp    */
        val = __shfl_down_sync(0xffffffff, val, 16);
        /*                     ^^^^^^^^^^ the mask of lanes you
                               are synchronising with. The _sync
                               suffix is mandatory now; the old
                               unsuffixed __shfl is removed.   */

/* WHY THE CHANGE WAS WORTH IT: it makes this correct, which
   it was not before: */

        while (!atomicCAS(&lock, 0, 1)) ;   /* lane 0 wins ...  */
        /* critical section */
        atomicExch(&lock, 0);
/* Pre-Volta, the winning lane could not proceed to release
   the lock while the losing lanes spun - the whole warp
   deadlocked. Per-thread PCs fixed a genuine footgun.       */
Never assume implicit lockstep

If your code relies on threads in a warp being at the same instruction, it is wrong on modern hardware — even though it will usually appear to work. Every intra-warp operation now takes an explicit mask: __shfl_sync, __ballot_sync, __any_sync, __syncwarp. In HLSL and Vulkan the equivalents are the wave intrinsics (WaveActiveSum, WaveReadLaneFirst), which were designed after this lesson and require no mask.

Warp-level operations

/* Because a warp shares an instruction stream, the hardware
   can offer cross-lane operations that cost almost nothing -
   no shared memory, no barrier, just wires in the register
   file. They are the single best optimisation available. */

/* CUDA */
  __shfl_sync(mask, var, srcLane)      /* read another lane   */
  __shfl_down_sync(mask, var, delta)   /* shift within warp   */
  __shfl_xor_sync(mask, var, lanemask) /* butterfly exchange  */
  __ballot_sync(mask, pred)            /* 32-bit vote bitmap  */
  __all_sync / __any_sync(mask, pred)  /* reductions on bools */
  __activemask()                       /* who is live now     */
  __reduce_add_sync(mask, val)         /* Ampere+: one insn   */

/* HLSL / DX12 wave intrinsics (SM 6.0+) */
  WaveActiveSum(v)      WaveActiveMax(v)
  WaveActiveBallot(p)   WaveActiveAllTrue(p)
  WaveGetLaneIndex()    WaveReadLaneFirst(v)
  WavePrefixSum(v)

/* A WARP REDUCTION - 5 instructions, no memory, no barrier: */
__device__ float warp_sum(float v)
{
        for (int off = 16; off > 0; off /= 2)
                v += __shfl_down_sync(0xffffffff, v, off);
        return v;      /* lane 0 holds the total              */
}

/* Compare with the shared-memory version: allocate shared
   memory (which costs occupancy), write, __syncthreads(),
   tree-reduce with more barriers, read back. The warp version
   is several times faster and uses no shared memory at all.

   THE PATTERN FOR A FULL BLOCK REDUCTION:
     1. warp_sum within each warp        (no barrier)
     2. lane 0 of each warp writes to shared    (32 floats max)
     3. __syncthreads()                          (one barrier)
     4. the first warp reduces those 32 values with warp_sum
   Two barriers total, whatever the block size.             */
