Modules, crates and Cargo

Rust's code organisation and build system. After CMake, vendor IDEs and hand-written Makefiles, Cargo is the single feature most likely to make an embedded engineer want to switch — and the module system is where privacy and API boundaries live.

Modules

Rust's module system is not the file-per-translation-unit arrangement C uses, and the mismatch is the most common source of early confusion. Ten minutes on the rules saves a lot of guessing.

/* A module is a namespace and a PRIVACY BOUNDARY. Everything
   is private by default.                                   */

    mod uart {
        pub struct Uart { base: usize }     // the TYPE is
                                            // public
                                            // `base` is not

        impl Uart {
            pub fn new(base: usize) -> Self { Uart { base } }
            pub fn write(&mut self, b: u8) { self.put(b); }
            fn put(&mut self, b: u8) { /* private */ }
        }

        pub(crate) fn debug_dump() { }      // visible in this
                                            // CRATE only
        pub(super) fn helper() { }          // visible to the
                                            // PARENT module
        pub(in crate::drivers) fn x() { }   // a specific path
    }

    use uart::Uart;
    let mut u = Uart::new(0x4000_0000);
    u.write(b'x');
    u.put(b'y');                // ERROR - private

/* PRIVACY IS PER-MODULE, not per-type: a child module can
   see its ancestors' private items. So `mod tests` inside a
   module can test private functions - which is why Rust's
   unit tests live in the file they test.

/* FILE LAYOUT: */
    src/
      main.rs           the binary crate root
      lib.rs            the library crate root
      uart.rs           -> `mod uart;`
      drivers/
        mod.rs          -> `mod drivers;` (older style)
        spi.rs          -> `mod spi;` inside drivers
      drivers.rs        -> the 2018+ style: a sibling file
                           instead of drivers/mod.rs

    // in lib.rs
    mod uart;                   // private module
    pub mod drivers;            // public module
    pub use uart::Uart;         // RE-EXPORT: users write
                                // my_crate::Uart, not
                                // my_crate::uart::Uart

/* THE RE-EXPORT IS THE API DESIGN TOOL: organise the source
   however you like, and present a flat, deliberate public
   surface with `pub use`.

/* PATHS: */
    use crate::drivers::spi::Spi;       // absolute, from the
                                        // crate root
    use super::helper;                  // the parent module
    use self::inner::thing;             // this module
    use core::fmt::Write;               // another crate

    use heapless::{Vec, String};        // grouped
    use embedded_hal::digital::*;       // glob - use
                                        // sparingly, except
                                        // for preludes
    use core::result::Result as R;      // rename

Crates and workspaces

The crate is the unit of compilation and of publication, and the distinction between the two crate kinds determines how a project is laid out.

# A CRATE is a compilation unit: one library or one binary.
# A PACKAGE is one Cargo.toml, containing up to one library
# and any number of binaries.

    my-project/
      Cargo.toml
      src/
        lib.rs            the library crate
        main.rs           a binary crate
        bin/
          tool.rs         another binary: cargo run --bin tool
      tests/              INTEGRATION tests - one crate each
      benches/
      examples/           cargo run --example blink

# A WORKSPACE shares one target directory and one lock file
# across several packages - which is how a real firmware
# project is laid out:

    # Cargo.toml at the root
    [workspace]
    resolver = "2"
    members = ["firmware", "protocol", "hal-ext"]

    [workspace.dependencies]
    heapless = "0.8"
    embedded-hal = "1.0"

    # firmware/Cargo.toml
    [dependencies]
    protocol = { path = "../protocol" }
    heapless.workspace = true

# WHY IT MATTERS ON EMBEDDED: the protocol crate can be
# `no_std` and tested on the HOST with `cargo test`, while
# the firmware crate cross-compiles. That split - testable
# logic in a portable crate, hardware in a target crate - is
# the single most valuable structural decision in an embedded
# Rust project.

Cargo.toml

The manifest is short, declarative, and controls several things that matter a great deal on embedded targets — particularly the release profile.

[package]
name = "firmware"
version = "0.1.0"
edition = "2021"                # 2015/2018/2021/2024 - opt-in
                                # language changes
rust-version = "1.75"           # the MSRV

[dependencies]
cortex-m = "0.7"
cortex-m-rt = "0.7"
embedded-hal = "1.0"
heapless = { version = "0.8", default-features = false }
nb = "1.0"
defmt = "0.3"

[dependencies.stm32f4xx-hal]
version = "0.21"
features = ["stm32f411", "rtic"]

[dev-dependencies]                      # tests and examples
                                        # only
proptest = "1"

[build-dependencies]                    # for build.rs
cc = "1"

[features]
default = ["logging"]
logging = ["dep:defmt"]
debug-uart = []

[profile.release]
opt-level = "z"                 # optimise for SIZE
                                # ("s" is less aggressive)
lto = "fat"                     # link-time optimisation
codegen-units = 1               # one unit - better
                                # optimisation, slower build
panic = "abort"                 # no unwinder (chapter 07)
debug = true                    # KEEP symbols - they cost
                                # nothing in flash, and
                                # defmt/probe-rs need them
overflow-checks = false

[profile.dev]
opt-level = 1                   # -O0 firmware is often too
                                # slow to run at all

# VERSION REQUIREMENTS:
#   "1.0"     ^1.0  - any 1.x, compatible
#   "=1.0.3"  exactly
#   "~1.0.3"  >=1.0.3, <1.1.0
#   "*"       anything - never do this
#
# Cargo.lock records the EXACT resolved versions.
# COMMIT IT for a binary; do NOT for a library.
The release profile is the size lever

opt-level = "z", lto = "fat", codegen-units = 1 and panic = "abort" together typically halve a firmware binary compared with the defaults. Set them before concluding Rust produces large binaries — the default release profile is tuned for server workloads, not for a 256 KB part.

Features

Features are Rust's conditional compilation, and they are how one crate serves both a hosted and a no_std target. They also have a unification rule that surprises people.

    [features]
    default = ["std"]
    std = ["alloc", "serde/std"]
    alloc = []
    logging = ["dep:defmt"]
    hardware-crc = []

    [dependencies]
    defmt = { version = "0.3", optional = true }

/* IN CODE: */
    #[cfg(feature = "logging")]
    fn log(msg: &str) { defmt::info!("{}", msg); }

    #[cfg(not(feature = "logging"))]
    fn log(_: &str) { }

    #[cfg(all(feature = "std", not(feature = "no-alloc")))]
    use std::vec::Vec;

/* AND THE STANDARD no_std SHAPE: */
    #![cfg_attr(not(feature = "std"), no_std)]

/* FEATURES MUST BE ADDITIVE. If two crates depend on yours
   with different features, Cargo UNIFIES them - enabling the
   union. So a feature that REMOVES functionality breaks that
   crate for everyone else in the build. Never write
   `no-floats`; write `floats` and leave it off by default.

/* THE OTHER cfg CONDITIONS: */
    #[cfg(target_arch = "arm")]
    #[cfg(target_os = "none")]
    #[cfg(target_pointer_width = "32")]
    #[cfg(debug_assertions)]
    #[cfg(test)]

/* AND ON THE COMMAND LINE: */
    cargo build --features "logging,hardware-crc"
    cargo build --no-default-features
    cargo build --all-features

The commands

A small set of commands covers everyday work. These are the ones worth having in muscle memory, including two that most people discover embarrassingly late.

# --- DAILY ---
    cargo check                 # TYPE-CHECK only - 5x faster
                                # than build. Use this while
                                # iterating.
    cargo build
    cargo build --release
    cargo run
    cargo test
    cargo clippy -- -D warnings # the linter. Genuinely
                                # excellent - it finds real
                                # bugs, not just style.
    cargo fmt                   # one format, no arguments
    cargo doc --open            # generate and view docs

# --- CROSS-COMPILATION ---
    rustup target add thumbv7em-none-eabihf
    cargo build --target thumbv7em-none-eabihf --release

    # .cargo/config.toml, so you can omit --target:
    [build]
    target = "thumbv7em-none-eabihf"

    [target.thumbv7em-none-eabihf]
    runner = "probe-rs run --chip STM32F411RETx"
    rustflags = ["-C", "link-arg=-Tlink.x"]

    # then `cargo run` FLASHES AND RUNS ON THE TARGET, with
    # defmt output streaming back. That single line of
    # configuration replaces an IDE.

# --- EMBEDDED TOOLING ---
    cargo install probe-rs-tools cargo-binutils cargo-bloat \
                  flip-link cargo-embed
    rustup component add llvm-tools

    cargo size --release -- -A          # section sizes
    cargo bloat --release -n 20         # what is taking space
    cargo nm --release
    cargo objdump --release -- -d
    probe-rs run --chip STM32F411RETx target/.../firmware

# --- MAINTENANCE ---
    cargo update                # update within the
                                # constraints
    cargo tree                  # the dependency graph
    cargo tree -d               # DUPLICATE versions - a
                                # common cause of bloat
    cargo audit                 # known vulnerabilities
    cargo deny check            # licences, bans, advisories
    cargo outdated
    cargo expand                # show macro expansions -
                                # invaluable for debugging
                                # derive macros

Testing

Testing is built into the toolchain rather than bolted on, which changes how much of it gets written. Chapter 12 covers it properly; this is enough to run what you write.

/* UNIT TESTS live beside the code, and can see private
   items: */
    fn parse(s: &str) -> Option<u32> { ... }

    #[cfg(test)]
    mod tests {
        use super::*;

        #[test]
        fn parses_decimal() {
            assert_eq!(parse("42"), Some(42));
        }

        #[test]
        fn rejects_garbage() {
            assert!(parse("x").is_none());
        }

        #[test]
        #[should_panic(expected = "index out of range")]
        fn panics_on_bad_index() { lookup(999); }

        #[test]
        fn returns_result() -> Result<(), Error> {
            let v = fallible()?;         // `?` works in tests
            assert_eq!(v, 1);
            Ok(())
        }
    }

/* DOC TESTS - examples in documentation that are COMPILED
   AND RUN: */
    /// Converts a raw ADC reading to millivolts.
    ///
    /// # Examples
    /// ```
    /// use my_crate::to_mv;
    /// assert_eq!(to_mv(2048), 1650);
    /// ```
    pub fn to_mv(raw: u16) -> u16 { ... }

/* DOCUMENTATION THAT CANNOT GO STALE, because `cargo test`
   runs it. This is one of Rust's genuinely distinctive
   features and it is worth using everywhere.

/* THE EMBEDDED TESTING STRATEGY: */
    1. put the LOGIC in a no_std crate with no hardware
       dependencies - protocol parsing, state machines,
       filters, checksums
    2. `cargo test` it on the HOST, where you have a debugger
       and instant feedback
    3. keep the hardware layer thin, and test it on target
       with defmt-test or embedded-test
    4. use traits (chapter 06) so the logic can be tested
       against a MOCK implementation:

    #[cfg(test)]
    struct MockSpi { written: Vec<u8> }
    impl SpiDevice for MockSpi { ... }

    #[test]
    fn sends_init_sequence() {
        let mut spi = MockSpi::default();
        let mut d = Display::new(&mut spi);
        d.init().unwrap();
        assert_eq!(spi.written, &[0x11, 0x29]);
    }
/* THIS IS THE BIGGEST PRACTICAL WIN in embedded Rust: most
   of your firmware becomes testable on a laptop, in
   milliseconds, without hardware.                        */

build.rs and documentation

Two mechanisms that look peripheral and turn out to be central to embedded work and to FFI: code that runs before your build, and documentation that is compiled and tested.

/* build.rs runs BEFORE compilation - for generated code,
   linker scripts, or compiling C.                         */

    // build.rs
    use std::{env, fs, path::PathBuf};

    fn main() {
        let out = PathBuf::from(env::var("OUT_DIR").unwrap());

        // put the linker script where the linker will find it
        fs::write(out.join("memory.x"),
                  include_bytes!("memory.x")).unwrap();
        println!("cargo:rustc-link-search={}", out.display());
        println!("cargo:rerun-if-changed=memory.x");

        // compile a C file from the vendor SDK (chapter 15)
        cc::Build::new()
            .file("vendor/hal.c")
            .include("vendor/include")
            .compile("vendorhal");
    }

/* THE `cargo:` DIRECTIVES it can emit:
     rustc-link-lib, rustc-link-search, rustc-cfg,
     rustc-env, rerun-if-changed, rerun-if-env-changed,
     warning

/* DOCUMENTATION: */
    //! Crate-level documentation, at the top of lib.rs.

    /// Documentation for the item that follows.
    ///
    /// # Errors
    /// Returns [`Error::Timeout`] if the device does not
    /// respond within 10 ms.
    ///
    /// # Safety
    /// (for unsafe fn) The caller must guarantee ...
    ///
    /// # Panics
    /// Panics if `len` exceeds the buffer capacity.
    pub fn read(&mut self, len: usize) -> Result<&[u8], Error>

    #![deny(missing_docs)]      // require docs on every
                                // public item

    cargo doc --open
/* The generated documentation links types, shows source, and
   runs the examples. `#[deny(missing_docs)]` on a library
   crate is worth adopting from the first commit.        */

How it shows up

SymptomCause and fix
"module not found"Missing mod x; in the parent, or the file is misnamed
"function is private"Add pub, or pub(crate) if it is internal
"unresolved import"Wrong path — remember crate::, super::, self::
A trait method is "not found"The trait is not in scope (ch. 06)
Two versions of the same crate linkedcargo tree -d — align the version requirements
A feature enabled unexpectedlyFeature unification — check cargo tree -f
Disabling a feature breaks another crateThe feature is subtractive — it should be additive
Release binary far larger than expectedDefault profile — set opt-level="z", LTO, panic="abort"
Builds are slowUse cargo check; raise codegen-units in dev
cargo test fails to link on an embedded targetTests need a host target — put logic in a portable crate
Linker script not foundbuild.rs must copy it to OUT_DIR and add a link-search path

Check yourself

  • Explain module privacy, including what a child module can see.
  • Use pub use to design a public API independent of the file layout.
  • Distinguish a crate, a package and a workspace.
  • Lay out a firmware project so the logic is host-testable.
  • Write a release profile tuned for size and say what each setting does.
  • Explain why features must be additive and what happens if they are not.
  • Configure .cargo/config.toml so cargo run flashes the target.
  • Write unit tests, a doc test, and a test using a mock trait implementation.
  • Use cargo size, cargo bloat and cargo tree -d.
  • Write a build.rs that installs a linker script and compiles a C file.
