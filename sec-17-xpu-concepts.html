Access control: XPU concepts

The MMU protects a CPU from itself. The SMMU protects memory from devices that have one. XPUs are the last layer: a firewall in the interconnect that decides, per transaction, whether this master may touch this address — and it is the one nobody teaches.

The gap XPUs fill

The SMMU protects memory from devices and TrustZone splits the system in two. Neither stops one non-secure master from reaching a peripheral it has no business touching — which is the gap this last mechanism fills.

Three protection mechanisms, three different questions:

  MMU     "may this VIRTUAL ADDRESS be accessed by the code
           currently running, at its privilege level?"
          Per-CPU. Translates AND checks.

  SMMU    "may this DEVICE's virtual/IO address be translated,
           and to what?"
          Per-StreamID. Translates AND checks.
          Requires the device to be behind an SMMU.

  XPU     "may THIS MASTER touch THIS PHYSICAL ADDRESS, in
           THIS security state, for READ or WRITE?"
          No translation at all. Pure permission check,
          on physical addresses, in the interconnect.

  WHY THE THIRD ONE IS NECESSARY:

  1. Not every master is behind an SMMU. Small DMA engines,
     sensor hubs, audio DSPs, power-management microcontrollers,
     debug blocks, display pipelines - many are wired straight
     to the interconnect.

  2. The SMMU protects DRAM well. It does nothing about
     PERIPHERAL registers. Which master may write the clock
     controller? The fuse controller? Another CPU's mailbox?

  3. TZASC and TZPC (chapter 10) are two-valued: secure or
     non-secure. Real SoCs have more than two principals - a
     modem, an application processor, a video DSP, a sensor
     hub, all mutually distrusting and all NON-SECURE.

  4. Some masters must be constrained BEFORE the SMMU is
     configured - during boot, when a firmware core is running
     and Linux is not.
The name

"XPU" is a family, not a standard. Qualcomm calls them XPUs (with variants MPU, PPU, VMIDMT). NXP i.MX has the RDC (Resource Domain Controller), the CSU, and TrustZone-aware AIPSTZ. TI has firewalls. Renesas has the Access Window. Xilinx/AMD has XMPU and XPPU. Arm's own is the TZC family. The mechanism is the same everywhere; only the register names and the marketing differ, so learn the model rather than one vendor's manual.

The model

Access control units check transactions at the target rather than at the source, asking whether this particular master may reach this particular resource. That placement is what makes them independent of anything the master itself does.

   MASTER                            SLAVE
   ------                            -----
   CPU cluster    ---+
   GPU            ---+
   display        ---+          +--> DRAM
   video codec    ---+---> XPU -+--> SRAM
   modem DSP      ---+          +--> peripheral registers
   audio DSP      ---+          +--> fuses, crypto, PMU
   sensor hub     ---+
   DMA engine     ---+

  Each transaction on the bus carries:

     ADDRESS        where
     MASTER ID      who   (AxID / AxUSER / a dedicated sideband)
     NS             which world (AxPROT[1])
     PRIVILEGED     AxPROT[0]
     READ / WRITE   direction
     sometimes: a VMID, so one master can be split by which
                virtual machine issued the access

  The XPU holds a table of REGIONS:

     +-------------------------------------------------------+
     | region 3                                              |
     |   base   0x8000_0000   size 64 MB                     |
     |   masters allowed: CPU(rw) GPU(r--) DISPLAY(r--)       |
     |   security: non-secure only                           |
     |   locked: yes                                         |
     +-------------------------------------------------------+

  Transaction arrives -> find the matching region -> look up
  this master's permission -> ALLOW or DENY.

  And critically: what happens when NOTHING matches. That is
  the DEFAULT, and it should be DENY.

Where they sit

PlacementProtectsTrade-off
At the master (a "master-side" or ingress firewall)Constrains one specific device wherever it goesOne instance per master; a master with several ports needs several
At the slave (memory controller, peripheral bridge)Everything reaching that slave, from every masterFewer instances; but the master ID must survive the whole path to get there
In the interconnect fabricWhole subsystems from one anotherCoarse granularity, but catches paths you did not think of
Inside a peripheral (per-register or per-channel)Fine-grained sharing of one deviceOnly where the vendor implemented it
The master ID is only as trustworthy as the wiring

An XPU's entire decision rests on the master ID arriving intact and unforgeable. Real integration problems: IDs remapped by a bridge so the XPU sees the bridge's ID and not the originator's; several masters sharing one ID because the sideband was too narrow; an ID that a master can program. Any of these collapses the policy to "some device did this", which is not a policy. It is exactly the StreamID integrity question from chapter 03, and it has the same answer: verify it empirically, per SoC.

Granularity and its limits

How finely a policy can be expressed — per register, per region, per master, per group — is fixed by the hardware and varies enormously between SoCs. It constrains what policies are expressible at all.

/* Every XPU has hard limits, and they shape your design more
   than any principle does.                                  */

   NUMBER OF REGIONS      typically 8, 16, or 32. Rarely more.
   MINIMUM REGION SIZE    4 KB, 64 KB, or 1 MB depending on
                          the block. Sometimes power-of-two
                          and naturally aligned, sometimes an
                          arbitrary base/limit pair.
   NUMBER OF MASTERS      a bitmap of 8-32 entries, or a list
                          of ID + mask pairs.
   PERMISSION GRANULARITY read/write, sometimes execute,
                          sometimes secure/non-secure
                          independently.

/* CONSEQUENCES you will hit:

   · you cannot give every master a private region - there are
     not enough regions. You will group masters into DOMAINS.

   · buffers must be laid out to MATCH the alignment the XPU
     can express. A 1 MB minimum region means a 4 KB secure
     buffer wastes 1 MB, or worse, cannot be isolated at all
     without moving everything around it.

   · this is a MEMORY MAP DESIGN constraint, decided very early
     in a project. Retrofitting it after the address map is
     frozen is painful and is usually done by giving up on
     some isolation.

   · ID masking lets one entry cover a group:
          match: id & 0xF0 == 0x20
     which is efficient, and also means an accidental grouping
     if the masks are chosen carelessly.                    */

What happens on a denial

Blocking an access is not the end of the decision: what the hardware does next — abort, return zero, or stall — has consequences for whether a fault is diagnosable or merely mysterious.

Three possible behaviours, and which one you get changes how
hard debugging is by an order of magnitude:

  1. ERROR RESPONSE
        the bus returns SLVERR or DECERR.
        the master sees an abort. For a CPU that is a
        synchronous or asynchronous external abort
        (ARM ch. 29). For a DMA engine, a channel error.
        BEST: something visibly fails, close to the cause.

  2. RAZ/WI - read as zero, write ignored
        the transaction "succeeds" and does nothing.
        WORST: no error anywhere. A driver reads 0x00000000
        from its ID register and reports "device not present".
        Days are lost to this (chapter 20).

  3. INTERRUPT + LOG, transaction dropped or errored
        the XPU records address, master ID, security state and
        direction in fault registers and raises an interrupt to
        a monitor.
        BEST FOR DEBUGGING, if someone wired the interrupt up
        and someone else wrote the handler.

  ALWAYS configure error responses and the fault interrupt in
  development builds, even if production chooses to be quiet.
  A silent policy is an untestable policy.

XPU versus SMMU: choosing

SMMUXPU
Translates addressesYes — scatter-gather, virtual DMANo
Per-context (per-process, per-VM)Yes — thousands of contextsNo — a handful of static regions
Dynamic remappingYes, per DMA mappingRarely, and expensively
Protects peripheral registersNot usuallyYes
Works before the OS bootsNeeds setup and tablesYes — a few register writes
Cost in siliconLarge: TLBs, page walkers, queuesSmall: comparators
LatencyTLB hit is fast; a walk is notFixed, small
Fault reportingRich — event queue with full contextBasic — often one fault register

They are complements, not alternatives. A well-built SoC uses the SMMU for masters that need scatter-gather DMA into user or guest memory, and XPUs for the static, coarse questions: which subsystem owns which DRAM carve-out, and who may write the clock and fuse controllers. Where both cover a path, both must allow the transaction — and that intersection is itself a defence, since a mistake in one is caught by the other.

Domains: the usable abstraction

Masters are usually grouped into domains rather than listed individually, because a policy with one entry per master does not scale and does not survive a chip revision.

/* With 16 regions and 20 masters you cannot enumerate pairs.
   So group masters into DOMAINS and write the policy in terms
   of domains.                                               */

   DOMAIN_SECURE     EL3 firmware, the trusted OS, the crypto
                     engine when claimed
   DOMAIN_AP         the application processor and everything
                     Linux drives directly
   DOMAIN_MODEM      the cellular subsystem: its DSP, its own
                     DMA, its dedicated peripherals
   DOMAIN_MEDIA      GPU, display, video codec, camera
   DOMAIN_SENSOR     the always-on sensor hub
   DOMAIN_DEBUG      CoreSight, the debug access port

/* Then the policy is a MATRIX - domains against resources: */

                  secure  AP     modem  media  sensor
   secure DRAM      rw     -      -      -      -
   AP DRAM          rw     rw     -      r      -
   modem DRAM       rw     -      rw     -      -
   shared AP/modem  rw     rw     rw     -      -
   framebuffer      rw     rw     -      rw     -
   fuses            r      -      -      -      -
   clock controller rw     rw     -      -      -
   sensor SRAM      rw     r      -      -      rw

/* This matrix IS the security architecture of the SoC. It
   belongs in a design document, reviewed by people who did not
   write it, and it should be MECHANICALLY DERIVED into the
   register settings rather than hand-written twice
   (chapter 19).

   Note what the matrix makes obvious that prose does not: the
   modem cannot see the framebuffer; the sensor hub cannot see
   AP memory; nothing but secure code reads the fuses. Those
   are decisions. Write them down and they can be argued with. */

Why this matters beyond security

The best argument for XPUs is not security — it is debugging

A rogue DMA write into another subsystem's memory produces a crash somewhere else, much later, in code that is entirely innocent. It is the hardest class of bug on an SoC: no stack trace points at the culprit, and the symptom moves whenever anything is recompiled.

An XPU converts that into an immediate fault at the moment of the bad access, with the offending master's ID in a register. That turns a two-week bug into a two-hour one, and it is why teams that adopt XPU policies for security keep them enabled for reasons that have nothing to do with attackers.
