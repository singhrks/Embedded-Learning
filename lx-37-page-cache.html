The page cache and writeback

Chapter 41 showed how read() reaches a filesystem's own code through the VFS. This chapter is what actually sits between that call and the disk: the page cache, which is why a second read of the same file is nearly free, why "free" memory on a healthy Linux box is usually a lie, and why a write can succeed and still be lost on a power cut.

Reads and writes go through memory, not straight to disk

Reading a file does not usually touch the disk, and writing one almost never does — not immediately. Between your program and the storage sits a cache of file contents in RAM, and nearly every surprising thing about file I/O performance follows from it.

   read(fd, buf, count) DOES NOT, IN THE COMMON CASE, TOUCH
   THE DISK AT ALL:

     read() call
        |
        v
     PAGE CACHE - is this file's data already resident in a
                  page of RAM, indexed by (inode, offset)?
        |
        +-- YES: copy straight out of RAM into buf. Done.
        |        No disk I/O whatsoever. This is why reading
        |        the same file twice in a row is dramatically
        |        faster the second time.
        |
        +-- NO:  read the page from the underlying block
                 device INTO the page cache first, THEN copy
                 out of it - so every subsequent read of that
                 same page is now a cache hit.

   write() WORKS THE SAME WAY IN REVERSE: by default, a
   write() just modifies the page IN THE CACHE and marks it
   DIRTY. It does NOT wait for the disk. The syscall returns
   successfully long before the data is actually durable on
   storage - see the writeback section below for why that
   matters.
"Free" memory on a healthy Linux system is a misleading number

The page cache uses whatever RAM is not otherwise needed — free -h's "available" column, not its "free" column, is the number that actually matters, because the kernel will happily reclaim clean (non-dirty) cache pages instantly under memory pressure with zero cost, since their content can always be re-read from disk. A Linux system reporting a few hundred megabytes "free" and many gigabytes cached is not low on memory — the opposite reading, jumping to add more RAM because "free" looks small, is one of the most common and unnecessary reactions to a completely healthy system.

Dirty pages: memory the disk does not yet agree with

When you write to a file the data goes into that cache and is marked as changed but not yet saved. The kernel then decides when to actually write it out, and the gap between those two moments is where both the performance win and the risk of data loss live.

   A DIRTY PAGE is one that has been WRITTEN in the page
   cache but not yet flushed to the underlying storage. The
   kernel deliberately BATCHES and DELAYS this flush - called
   WRITEBACK - rather than writing synchronously on every
   write() call, because:

     · combining many small writes into fewer, larger disk
       operations is dramatically more efficient
     · a page written multiple times in quick succession only
       needs to reach disk ONCE, with its final content
     · deferring the actual I/O off the calling thread's
       critical path is most of why write() feels instant

   WRITEBACK IS TRIGGERED BY THREE THINGS:
     1. TIME - a dirty page older than dirty_expire_centisecs
        (default 30s) gets flushed on the next writeback pass
     2. VOLUME - total dirty memory crossing
        vm.dirty_background_ratio triggers background
        writeback quietly, in a kernel thread
     3. PRESSURE - crossing vm.dirty_ratio forces the WRITING
        PROCESS ITSELF to block and do writeback synchronously
        - this is the mechanism behind a write() call that
        suddenly, visibly stalls under heavy I/O load
# See dirty memory right now:
grep -i dirty /proc/meminfo
    Dirty:            18432 kB
    Writeback:          512 kB    /* currently being flushed */

# The two thresholds, as a percentage of available memory:
cat /proc/sys/vm/dirty_background_ratio    # quiet flushing starts
cat /proc/sys/vm/dirty_ratio                # writers start blocking

# Force ALL dirty pages to disk right now, synchronously:
sync
# Force just one file's dirty pages and metadata to disk,
# and BLOCK until the device confirms it is durable:
fsync(fd);       /* the ONLY way to know data actually
                     survived a crash - write() alone never
                     guarantees this                          */
fdatasync(fd);   /* like fsync, but skips flushing metadata
                     that does not affect reading the data back
                     (e.g. access time) - slightly cheaper     */
A successful write() is not a durability guarantee

write() returning success means the data reached the page cache — nothing more. If the machine loses power before writeback runs, every dirty page not yet flushed is gone, even though the application already received a success return value and may have told a user, or another system, that the data was saved. Any program with a real durability requirement — a database committing a transaction, a logger recording an event before acknowledging it — must call fsync() (or open the file with O_DSYNC) and treat that call's success, not write()'s, as the actual durability guarantee.

mmap: the page cache visible directly, with no copy at all

Instead of copying data out of the cache into your buffer, a program can ask for the cache pages themselves to appear in its address space. There is then exactly one copy of the data in memory, shared by everyone touching that file.

void *p = mmap(NULL, length, PROT_READ | PROT_WRITE,
               MAP_SHARED, fd, 0);
/* This does NOT read the file into a separate buffer. It
   maps the file's PAGE CACHE PAGES directly into the
   process's address space - touching p[100] for the first
   time takes a page fault (the same mechanism chapter 39's
   copy-on-write section used, here reading from disk instead
   of copying a page), which pulls that one page of the file
   into the cache and maps it in, on demand.

   WITH MAP_SHARED, a write to p[100] dirties the SAME PAGE
   CACHE PAGE that read()/write() on this file would use -
   there is exactly one copy of the file's data in memory,
   regardless of whether it is accessed through mmap or
   through ordinary read()/write() calls, and the two views
   stay consistent because they are, literally, the same
   physical pages.

   THIS IS WHY mmap CAN BE FASTER FOR LARGE, RANDOMLY-ACCESSED
   FILES: no copy from kernel buffer to user buffer at all,
   just a page-table entry pointing straight at the cache
   page - avoiding exactly the copy chapter 09's user-copy
   chapter otherwise describes as unavoidable for read().    */

Readahead: prefetching before you ask

If you are reading a file from start to finish, the kernel can see that pattern and fetch the next part before you ask for it — so the data is already in memory by the time you need it. This is why sequential reads often outrun the drive's own latency.

   THE KERNEL WATCHES A FILE'S ACCESS PATTERN. If reads are
   SEQUENTIAL, it starts speculatively reading FURTHER AHEAD
   than what was actually requested, so that by the time the
   application asks for the next chunk, it is often already
   sitting in the page cache.

     Application reads offset 0-4KB
     Kernel notices a sequential pattern, and prefetches
     offset 4KB-132KB in the background while the app is
     still processing the first chunk

     Application reads offset 4KB-8KB
        -> ALREADY IN CACHE. No disk wait at all.

   THIS IS WHY SEQUENTIAL FILE READS ARE OFTEN FASTER THAN THE
   RAW DEVICE THROUGHPUT WOULD SUGGEST, AND WHY RANDOM ACCESS
   PATTERNS DO NOT BENEFIT: readahead's entire value depends on
   correctly guessing what comes next, which a sequential scan
   makes easy and a random-access workload makes actively
   counterproductive - which is exactly why `posix_fadvise()`
   lets an application override the guess in either direction:

        posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL);
        posix_fadvise(fd, 0, 0, POSIX_FADV_RANDOM);  /* disables
                                                          readahead */

How it shows up

SymptomCause
"Free" memory looks nearly exhausted, system runs fineExpected — most of it is reclaimable page cache; check "available," not "free"
Data is lost after a power cut despite a successful write()The page was dirty and had not yet been flushed — the application needed fsync() for a durability guarantee
A write() call occasionally stalls noticeably under heavy I/ODirty memory crossed vm.dirty_ratio and the calling process is now doing synchronous writeback itself
Reading a file a second time is dramatically faster than the firstExpected — the page cache served it from RAM with no disk I/O
Two processes see each other's writes to a shared mmap region instantlyExpected — both map the same underlying page cache pages, not separate copies
Sequential file reads run faster than the raw device's rated throughputReadahead is prefetching ahead of the application, hiding the latency
A random-access workload benefits from disabling readaheadExpected — readahead's speculative reads are wasted work when the access pattern is not sequential
