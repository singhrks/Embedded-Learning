KVM/arm64 internals

Everything in this track so far exists in one directory of the Linux source tree. This chapter is the map: where each mechanism lives, what the ioctl interface looks like from the outside, and how to build a working hypervisor in about two hundred lines so that the abstractions stop being abstract.

The source map

Knowing where things live in the source tree is most of the battle when reading KVM, and the layout follows the architecture closely.

   arch/arm64/kvm/
   |
   +-- arm.c              VM and vCPU lifecycle, the run loop.
   |                      kvm_arch_vcpu_ioctl_run() is the
   |                      function everything passes through.
   +-- handle_exit.c      the exit dispatch table, keyed on
   |                      ESR_EL2.EC. Start reading here.
   +-- sys_regs.c         the emulated system register table -
   |                      one entry per trapped register, with
   |                      its access function and reset value.
   |                      Enormous, and mechanical.
   +-- mmu.c              stage-2: memslots, user_mem_abort(),
   |                      page table management, dirty logging.
   +-- pkvm.c             protected-KVM setup.
   +-- psci.c             PSCI: CPU_ON/OFF/SUSPEND, SYSTEM_RESET.
   +-- pmu.c pmu-emul.c   virtual PMU.
   +-- arch_timer.c       CNTVOFF, the timer save/restore and
   |                      the hrtimer used while descheduled.
   +-- vgic/
   |    +-- vgic-init.c   creation, from the KVM device API
   |    +-- vgic-mmio*.c  the emulated distributor/redistributor
   |    +-- vgic-v3.c     list registers, the hardware side
   |    +-- vgic-its.c    the emulated ITS
   |    +-- vgic-v4.c     direct injection
   +-- hyp/
        +-- nvhe/         code that runs at EL2 in nVHE mode.
        |                 Compiled separately, its own linker
        |                 script, cannot call ordinary kernel
        |                 functions.
        +-- vhe/          the VHE variants
        +-- include/      shared switch code

   virt/kvm/              architecture-independent core:
                          kvm_main.c, eventfd.c (irqfd,
                          ioeventfd), the memslot machinery.

   READING ORDER that works:
     1. handle_exit.c  - see every exit reason in one table
     2. arm.c          - the loop around it
     3. mmu.c          - user_mem_abort(), the single most
                         important function in the file
     4. sys_regs.c     - pick one register and follow it
     5. vgic/          - only when you need it

The ioctl interface, in order

The interface between a VMM and KVM is a small number of ioctls used in a fixed order, and seeing that order makes the next section readable.

/* This is the entire contract between a VMM and KVM. Every
   VMM - QEMU, crosvm, firecracker, cloud-hypervisor - makes
   these calls in this order.                               */

  int kvm = open("/dev/kvm", O_RDWR);

  ioctl(kvm, KVM_GET_API_VERSION);              /* must be 12  */
  ioctl(kvm, KVM_CHECK_EXTENSION, KVM_CAP_ARM_VM_IPA_SIZE);

  int vm = ioctl(kvm, KVM_CREATE_VM, 40);       /* 40-bit IPA  */

  /* Memory: tell KVM which host memory backs which guest
     physical range. Anything not covered is MMIO.            */
  ioctl(vm, KVM_SET_USER_MEMORY_REGION,
        &(struct kvm_userspace_memory_region){
            .slot            = 0,
            .guest_phys_addr = 0x40000000,
            .memory_size     = 1UL << 30,
            .userspace_addr  = (uint64_t)mmap(...),
        });

  /* The interrupt controller is a "KVM device".              */
  int gic = ioctl(vm, KVM_CREATE_DEVICE,
        &(struct kvm_create_device){
            .type = KVM_DEV_TYPE_ARM_VGIC_V3 });
  ioctl(gic, KVM_SET_DEVICE_ATTR, ...);   /* base addresses    */

  /* vCPUs.                                                    */
  int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);

  struct kvm_vcpu_init init = {};
  ioctl(vm, KVM_ARM_PREFERRED_TARGET, &init);
  init.features[0] |= 1 << KVM_ARM_VCPU_PSCI_0_2;
  ioctl(vcpu, KVM_ARM_VCPU_INIT, &init);

  /* The shared communication page.                            */
  size_t mmap_sz = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
  struct kvm_run *run = mmap(NULL, mmap_sz, PROT_READ|PROT_WRITE,
                             MAP_SHARED, vcpu, 0);

  /* Registers are set through a generic ID-based interface.   */
  ioctl(vcpu, KVM_SET_ONE_REG, &(struct kvm_one_reg){
            .id   = ARM64_CORE_REG(regs.pc),
            .addr = (uint64_t)&entry_point });

  /* And then, forever:                                        */
  for (;;) {
          ioctl(vcpu, KVM_RUN, 0);
          switch (run->exit_reason) { ... }
  }

A hypervisor in two hundred lines

A working hypervisor is far shorter than expected, and writing one is the fastest way to understand what the kernel is and is not doing for you.

/* Runs a tiny AArch64 payload that writes to a UART address we
   model, then halts. Build:
       aarch64-linux-gnu-gcc -static -o tinyvmm tinyvmm.c
   Run on an arm64 host with /dev/kvm.                       */

#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <linux/kvm.h>

#define GUEST_RAM   0x40000000UL
#define RAM_SIZE    (2UL * 1024 * 1024)
#define UART_BASE   0x09000000UL

/* The guest program, assembled by hand:

     mov  x1, #0x09000000        // UART base
     mov  w2, #'K'
     str  w2, [x1]
     mov  w2, #'V'
     str  w2, [x1]
     mov  w2, #'M'
     str  w2, [x1]
     mov  w2, #'\n'
     str  w2, [x1]
   1: wfi
     b    1b
*/
static const uint32_t guest_code[] = {
        0xd2a12001,  /* mov x1, #0x09000000                   */
        0x52800962,  /* mov w2, #0x4b  'K'                    */
        0xb9000022,  /* str w2, [x1]                          */
        0x52800ac2,  /* mov w2, #0x56  'V'                    */
        0xb9000022,
        0x528009a2,  /* mov w2, #0x4d  'M'                    */
        0xb9000022,
        0x52800142,  /* mov w2, #0x0a  '\n'                   */
        0xb9000022,
        0xd503207f,  /* wfi                                   */
        0x17ffffff,  /* b .-4                                 */
};

#define ARM64_CORE_REG(x) \
        (KVM_REG_ARM64 | KVM_REG_SIZE_U64 | KVM_REG_ARM_CORE | \
         (offsetof(struct kvm_regs, x) / sizeof(__u32)))

int main(void)
{
        int kvmfd = open("/dev/kvm", O_RDWR | O_CLOEXEC);
        if (kvmfd < 0) { perror("/dev/kvm"); return 1; }

        int vmfd = ioctl(kvmfd, KVM_CREATE_VM, 0);

        /* Guest RAM. */
        void *ram = mmap(NULL, RAM_SIZE, PROT_READ | PROT_WRITE,
                         MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE,
                         -1, 0);
        memcpy(ram, guest_code, sizeof guest_code);

        struct kvm_userspace_memory_region region = {
                .slot            = 0,
                .guest_phys_addr = GUEST_RAM,
                .memory_size     = RAM_SIZE,
                .userspace_addr  = (uint64_t)ram,
        };
        ioctl(vmfd, KVM_SET_USER_MEMORY_REGION, &region);

        /* One vCPU. */
        int vcpufd = ioctl(vmfd, KVM_CREATE_VCPU, 0);

        struct kvm_vcpu_init init = {};
        ioctl(vmfd, KVM_ARM_PREFERRED_TARGET, &init);
        ioctl(vcpufd, KVM_ARM_VCPU_INIT, &init);

        size_t run_size = ioctl(kvmfd, KVM_GET_VCPU_MMAP_SIZE, 0);
        struct kvm_run *run = mmap(NULL, run_size,
                                   PROT_READ | PROT_WRITE,
                                   MAP_SHARED, vcpufd, 0);

        /* PC = start of our code, PSTATE = EL1h, interrupts
           masked.                                            */
        uint64_t pc = GUEST_RAM;
        uint64_t pstate = 0x3c5;   /* D,A,I,F masked, EL1h     */
        struct kvm_one_reg r;

        r = (struct kvm_one_reg){ .id = ARM64_CORE_REG(regs.pc),
                                  .addr = (uint64_t)&pc };
        ioctl(vcpufd, KVM_SET_ONE_REG, &r);
        r = (struct kvm_one_reg){ .id = ARM64_CORE_REG(regs.pstate),
                                  .addr = (uint64_t)&pstate };
        ioctl(vcpufd, KVM_SET_ONE_REG, &r);

        /* The loop. */
        for (;;) {
                if (ioctl(vcpufd, KVM_RUN, 0) < 0) {
                        perror("KVM_RUN");
                        return 1;
                }

                switch (run->exit_reason) {
                case KVM_EXIT_MMIO:
                        if (run->mmio.phys_addr == UART_BASE &&
                            run->mmio.is_write) {
                                putchar(run->mmio.data[0]);
                                fflush(stdout);
                        }
                        break;

                case KVM_EXIT_SYSTEM_EVENT:
                        printf("\n[system event %u]\n",
                               run->system_event.type);
                        return 0;

                case KVM_EXIT_FAIL_ENTRY:
                        fprintf(stderr, "entry failed: 0x%llx\n",
                                run->fail_entry.hardware_entry_failure_reason);
                        return 1;

                default:
                        fprintf(stderr, "exit reason %u\n",
                                run->exit_reason);
                        return 1;
                }
        }
}

What this proves

KVM does not "run virtual machines". It provides a CPU in a box and tells you when the box needs something. Every device, every address-space decision, every piece of firmware and every policy is user space's problem. That is why there are half a dozen VMMs with wildly different characters — firecracker boots in 100 ms because it declines to implement almost everything QEMU does.

The VMMs, and what they optimise for

The user-space half varies widely in size and philosophy, and the choice determines your attack surface and your boot time more than your throughput.

VMMLanguageOptimises forNotes
QEMUCCompletenessEvery device, every architecture, TCG as well as KVM. The reference
FirecrackerRustBoot time and attack surface~5 devices, no PCI, no BIOS. Used for AWS Lambda
crosvmRustSandboxingEach device in its own process with seccomp; the basis of ChromeOS and Android VMs

rust-vmmRustBeing a libraryThe shared crates the above are built from; the fastest way to write your own

Instrumenting KVM

KVM is unusually well instrumented, and knowing which counters and tracepoints exist turns performance questions into measurements.

# Per-VM statistics (modern kernels expose them per-fd):
$ sudo ls /sys/kernel/debug/kvm/
$ sudo grep . /sys/kernel/debug/kvm/*/vcpu0/stat/* 2>/dev/null

# Tracepoints - the useful ones:
$ sudo ls /sys/kernel/debug/tracing/events/kvm/
kvm_entry  kvm_exit  kvm_guest_fault  kvm_mmio  kvm_set_irq
kvm_wfx_arm64  kvm_hvc_arm64  kvm_arm_setup_debug  ...

$ sudo perf record -e 'kvm:*' -a -- sleep 5
$ sudo perf script | awk '{print $5}' | sort | uniq -c | sort -rn

# Live summary:
$ sudo perf kvm --host stat live

# Function-level, when you are changing KVM itself:
$ sudo trace-cmd record -p function_graph \
      -g kvm_arch_vcpu_ioctl_run -O nofuncgraph-irqs
$ trace-cmd report | head -50

# Building a KVM with your own printk:
#   CONFIG_KVM=y (not =m, if you are changing hyp code)
#   CONFIG_DEBUG_INFO=y
# Note: in nVHE mode, code under arch/arm64/kvm/hyp/nvhe/
# CANNOT printk. Use the trace buffer or a magic register value
# you read after the exit. In VHE mode, ordinary printk works -
# one more reason VHE made KVM development pleasant.
