Addressing modes

Since only loads and stores touch memory, how they compute an address is where a surprising amount of performance lives. Array indexing, struct access, stack frames and pointer walking each map onto a specific mode, and recognising them makes disassembly readable.

The modes

Every one of these exists to make one specific C pattern compile to a single instruction rather than a separate address calculation followed by a load. The base-plus-immediate form covers a struct field at a fixed offset; the base-plus-scaled-register form covers array indexing, where the index must be multiplied by the element size before it is added; and the pre/post-index forms fold the pointer's own update into the same instruction that dereferences it, which is exactly what a pointer walk or a stack push does. Reading down the "compiles from" column right to left is often the fastest way to understand a mode you have not memorised.

Pre-index versus post-index — the distinction that trips people up

   PRE-INDEX   [x0, #8]!      "update, then use"
        x0 = x0 + 8
        access [x0]

   POST-INDEX  [x0], #8       "use, then update"
        access [x0]
        x0 = x0 + 8

  Mnemonic: the ! is where the update happens relative to the
  bracket. Inside the bracket → before. After the bracket → after.

  This is exactly *++p versus *p++ in C, and it is why a linked-
  list walk or a memcpy loop needs no separate ADD instruction.

The scaled index, and why it matters

Indexing an array is so common that the architecture folds the multiply into the load itself. That single feature removes an instruction from the inner loop of an enormous amount of real code.

/* Array indexing is ONE instruction, because the shift is free —
   it happens in the address generation unit, not the ALU.   */

long a[100];
long f(long *a, int i) { return a[i]; }
/*      ldr     x0, [x0, w1, sxtw #3]     // x0 + (sign-ext w1)*8
        ret                                                   */

/* The shift amount matches the element size:
        #0  → 1-byte elements       #2  → 4-byte (int, float)
        #1  → 2-byte                #3  → 8-byte (long, pointer)
        #4  → 16-byte (Q registers)

   Note SXTW: a signed 32-bit index must be sign-extended to 64
   bits. If you index with a size_t (unsigned 64-bit) instead,
   the extension disappears:                                 */

long g(long *a, size_t i) { return a[i]; }
/*      ldr     x0, [x0, x1, lsl #3]      // no extension needed */

/* This is a real, if small, reason to prefer size_t for indices
   in hot loops — and it also removes the signed-overflow UB
   from the index arithmetic (C chapter 15).                */

Immediate offset ranges

The offset you can encode in a load or store is limited, and the limit depends on the access size in a way that looks arbitrary until you see the encoding. It explains why the compiler sometimes materialises an address separately.

The encodable range depends on the ACCESS SIZE, because the
offset is scaled by it:

   LDRB/STRB    unsigned imm12, scaled by 1   →  0 .. 4095
   LDRH/STRH    unsigned imm12, scaled by 2   →  0 .. 8190,  even
   LDR/STR (W)  unsigned imm12, scaled by 4   →  0 .. 16380, mult of 4
   LDR/STR (X)  unsigned imm12, scaled by 8   →  0 .. 32760, mult of 8

   Unscaled signed form (LDUR/STUR): -256 .. 255, any alignment.
   The assembler picks it automatically when needed.

   LDP/STP      signed imm7, scaled          →  -512 .. 504 for X

WHY THIS MATTERS IN PRACTICE:

  · a struct field at offset 32760 is one instruction; at 32768
    it needs an extra ADD. Very large structs cost more to access.

  · this is why the compiler sometimes rebases a pointer into the
    middle of a large structure — to bring fields into range.

  · stack frames larger than ~32 KB generate extra address
    arithmetic on every local variable access. Another reason
    large stack arrays are a bad idea (C chapter 09).

Load and store pair

Moving two registers in one instruction halves the instruction count of every function prologue and epilogue in the system. It is also why ARM stack frames look the way they do.

/* LDP/STP move TWO registers in ONE instruction. This is why
   prologues save registers in pairs and why the stack moves in
   multiples of 16 bytes.                                     */

        stp     x29, x30, [sp, #-32]!   // push both, pre-decrement
        stp     x19, x20, [sp, #16]
        ...
        ldp     x19, x20, [sp, #16]
        ldp     x29, x30, [sp], #32     // pop both, post-increment

/* Also used for bulk copies — a 16-byte-at-a-time memcpy: */
1:      ldp     x2, x3, [x1], #16
        stp     x2, x3, [x0], #16
        subs    x4, x4, #16
        b.ne    1b

/* And with Q registers, 32 bytes at a time: */
        ldp     q0, q1, [x1], #32
        stp     q0, q1, [x0], #32

/* Constraint: both registers must be the same size, and the
   offset is a signed 7-bit value scaled by the access size —
   a much narrower range than a single LDR.                  */

PC-relative addressing

Position-independent code needs to refer to data without knowing where it will be loaded. PC-relative addressing is how that works, and it is the basis of shared libraries, ASLR and most modern binaries.

        adr     x0, label        // PC ± 1 MB, byte granular
        adrp    x0, symbol       // PC ± 4 GB, PAGE granular (4 KB)

/* ADRP gives the address of the 4 KB PAGE containing the symbol,
   with the low 12 bits ZEROED. The low bits are supplied
   separately:                                                */

        adrp    x0, my_global
        add     x0, x0, :lo12:my_global     // full address
        ldr     w1, [x0]

/* Or folded into the load's own offset — one instruction fewer: */
        adrp    x0, my_global
        ldr     w1, [x0, :lo12:my_global]

/* Why the split: a single 32-bit instruction cannot encode a
   ±4 GB byte offset. Splitting it into a page offset (21 bits)
   plus a 12-bit low part covers the full range.

   This is also why the LINKER has relocation types specifically
   for the two halves (R_AARCH64_ADR_PREL_PG_HI21 and
   R_AARCH64_ADD_ABS_LO12_NC), and why an ADRP/ADD pair must not
   be separated by the compiler — Cortex-A53 erratum 843419 is
   precisely a bug in that sequence (chapter 01).           */

/* LITERAL POOLS: a PC-relative load of a constant stored in the
   code stream. The assembler's = syntax generates one:      */
        ldr     x0, =0x123456789abcdef0
/*  becomes:
        ldr     x0, .Lpool
        ...
    .Lpool: .quad 0x123456789abcdef0                          */

Access sizes and extension

A load can move one, two, four or eight bytes, and when it moves fewer than eight there is a question of what fills the rest of the register. Getting the signed and unsigned forms confused produces values that are wildly wrong rather than slightly wrong.

        ldrb    w0, [x1]        // load byte,  ZERO-extend to 32
        ldrh    w0, [x1]        // load half,  zero-extend
        ldr     w0, [x1]        // load word   (upper 32 of x0 zeroed)
        ldr     x0, [x1]        // load 64 bits

        ldrsb   w0, [x1]        // load byte,  SIGN-extend to 32
        ldrsb   x0, [x1]        // ...to 64
        ldrsh   x0, [x1]
        ldrsw   x0, [x1]        // load word, sign-extend to 64
                                //   — very common for int → long

        strb    w0, [x1]        // store the low 8 bits
        strh    w0, [x1]
        str     w0, [x1]        // store 32
        str     x0, [x1]        // store 64

/* Note there is no STRSB: sign extension is a property of
   LOADING, not storing. And remember that writing Wn zeroes the
   top half of Xn (chapter 04), so LDR Wn is implicitly a
   zero-extending 64-bit write.                             */

Ordered, exclusive and non-temporal

A plain LDR/STR says nothing about ordering, atomicity, or cache behaviour beyond the memory type it targets — it just moves data. Each row below adds exactly one of those properties on top of an ordinary load or store, and they combine: LDAXR is simultaneously exclusive (for building an atomic read-modify-write) and acquire-ordered (so nothing after it can be reordered before it completes). You reach for these only when the plain form is provably not enough — for synchronisation primitives, for crossing the user/kernel boundary safely, or for streaming data you know you will not reuse.

FormMeaningChapter
LDAR / STLRLoad-acquire / store-release — ordering attached to the access21
LDXR / STXRExclusive, for atomic sequences22
LDAXR / STLXRBoth: exclusive and ordered22
LDNP / STNPNon-temporal pair — a hint not to pollute the cache17
LDTR / STTRUnprivileged — behaves as an EL0 access even when executed at EL1. Used by copy_to_user.05
PRFMPrefetch hint: PLDL1KEEP, PSTL2STRM…CA 13
 
/* LDTR/STTR are worth understanding: they let kernel code access
   user memory with USER permissions, so a malicious pointer
   pointing at kernel memory faults rather than succeeding. That
   is how copy_from_user enforces the boundary in hardware
   rather than by checking the address (OS chapter 03).      */

/* Non-temporal, for streaming through data you will not reuse: */
1:      ldnp    q0, q1, [x1], #32
        stnp    q0, q1, [x0], #32
        subs    x2, x2, #32
        b.ne    1b
/* Avoids evicting the working set for a bulk copy — the same
   idea as MADV_DONTNEED at a different level.               */

Reading addressing in disassembly

Addressing modes are where disassembly looks most alien to someone used to high-level code. The notation is consistent, and once decoded it tells you a great deal about the data structure being accessed.

/* Each pattern tells you what the source code was doing: */

  ldr  x0, [x1]                  *p
  ldr  x0, [x1, #24]             p->field  (at offset 24)
  ldr  x0, [x1, x2, lsl #3]      a[i]      (8-byte elements)
  ldr  x0, [x1], #8              *p++      (pointer walk)
  ldr  x0, [x1, #8]!             *++p
  ldp  x0, x1, [x2, #16]         two adjacent fields, one instruction
  ldr  x0, [sp, #40]             a local variable, or a spilled reg
  adrp x0, sym / add x0,x0,:lo12: a global
  ldr  w0, [x1, w2, sxtw #2]     a[i] with an int index

/* And the absence of loads inside a loop tells you the compiler
   kept everything in registers — which is the goal.        */
The addressing mode reveals the data structure

When reverse-engineering or reviewing generated code, the addressing mode is the strongest clue about the underlying type. A constant offset means a struct field; a scaled register offset means an array; post-index means a sequential walk; an indirect BLR after a load means a function pointer or vtable (C ch. 12). Reading these patterns is a large part of what makes disassembly useful rather than opaque.
