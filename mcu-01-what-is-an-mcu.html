What a microcontroller is, and how it differs

Everything else on this site so far has assumed a processor with an MMU, hundreds of megabytes of DRAM and an operating system underneath you. A microcontroller has none of those. This chapter establishes what you actually get, because every technique in this track follows from the constraints.

One chip, one program

A microcontroller is a complete computer on a single die: a CPU core, its memory, and the peripherals that connect it to the outside world. It boots from its own on-chip flash into your code, and your code is the only code. There is no bootloader chain to negotiate with, no kernel to ask permission from, and no other process competing for the CPU — unless you write one.

   A TYPICAL CORTEX-M MICROCONTROLLER

   +--------------------------------------------------+
   |                                                  |
   |   +----------+        +---------------------+    |
   |   | Cortex-M |========| FLASH   256 kB      |    |
   |   |   core   |        | (your program, XIP) |    |
   |   |          |        +---------------------+    |
   |   |  NVIC    |                                   |
   |   |  SysTick |        +---------------------+    |
   |   |  MPU     |========| SRAM     64 kB      |    |
   |   +----------+        | (stack, heap, data) |    |
   |        ||             +---------------------+    |
   |   =====++=====  bus matrix  ==================   |
   |     ||     ||      ||      ||      ||       ||   |
   |   +----+ +----+ +-----+ +-----+ +-----+ +------+ |
   |   |GPIO| |UART| | SPI | | I2C | |Timer| | ADC  | |
   |   +----+ +----+ +-----+ +-----+ +-----+ +------+ |

         ||     ||      ||      ||               ||
        pins   pins    pins    pins            analog

   Everything inside the box is one chip, one package,
   often under two dollars. The CPU, the memory and the
   peripherals share a bus matrix; a peripheral register
   is just an address you write to.

The consequence that matters most: there is no virtual memory. A pointer holds a physical address. Address 0x40020000 is not "wherever the kernel decided to map the GPIO block" — it is the GPIO block, permanently, as documented in the reference manual. This makes the machine dramatically easier to reason about and dramatically less forgiving, in exactly the ways you would expect.

The trade is determinism against capability

A Cortex-A core is faster in every benchmark and worse at every deadline. Its caches, branch predictors, MMU and scheduler all improve average performance by introducing variance. A Cortex-M has no cache to miss, no TLB to walk and no scheduler to preempt you, so the time between an electrical edge on a pin and the first instruction of your handler is a number you can look up and rely on. When the requirement is "the motor commutates within 5 µs, every time, for ten years", that number is the whole product.

Execute in place, and why RAM is precious

Your program is not loaded into RAM. The CPU fetches instructions directly from flash over a dedicated bus — execute in place, XIP. Flash is comparatively plentiful and slow; SRAM is fast and scarce. That inverts habits learned on a desktop:

/* On a microcontroller these two lines have completely
   different costs.                                        */

const char msg[] = "sensor fault";       /* Ideally: flash. */
char       buf[] = "sensor fault";       /* Always: SRAM,   */
                                         /* AND a copy of   */
                                         /* the initialiser */
                                         /* in flash too.   */

/* The second costs 13 bytes of your 64 kB of SRAM, plus 13
   bytes of flash for the initialiser that startup code
   copies into it (chapter 06). If it does not need to be
   written, it must be const - that is not a style rule
   here, it is a memory budget.

   Toolchains will place const data in flash only if you let
   them. On AVR and some others you need an explicit
   attribute; on Cortex-M, const alone is enough.           */

const char *p = msg;    /* p is 4 bytes of SRAM pointing at flash */

A 64 kB SRAM budget sounds generous until you count: every task's stack, every DMA buffer, every driver's ring buffer, the heap if you have one, and every non-const global. Running out is not an ENOMEM you can handle — it is a stack that silently grows into your variables. Chapter 20 is about making that impossible rather than unlikely.

A peripheral is an address

On Linux you request a GPIO from a subsystem that arbitrates between drivers. Here, you write to a register. The entire abstraction is a struct overlaid on a fixed address:

/* Memory-mapped I/O, the whole idea in one block. */

#include <stdint.h>

typedef struct {
    volatile uint32_t MODER;    /* 0x00  mode: in/out/alt/analog */
    volatile uint32_t OTYPER;   /* 0x04  push-pull or open-drain */
    volatile uint32_t OSPEEDR;  /* 0x08  slew rate                */
    volatile uint32_t PUPDR;    /* 0x0C  pull-up / pull-down      */
    volatile uint32_t IDR;      /* 0x10  input data   (read-only) */
    volatile uint32_t ODR;      /* 0x14  output data              */
    volatile uint32_t BSRR;     /* 0x18  atomic set/reset         */
} GPIO_TypeDef;

#define GPIOA ((GPIO_TypeDef *) 0x40020000UL)

/* Set PA5 high. One store. No system call, no driver, no
   lock, and roughly two clock cycles.                      */
GPIOA->BSRR = (1U << 5);

/* volatile is mandatory, not decorative. Without it the
   compiler may cache the value in a register, reorder the
   access, or delete it entirely - all legal, because C's
   abstract machine has no concept of a wire attached to
   memory. See the C track, chapter 10.                     */
volatile is necessary but not sufficient

It stops the compiler reordering and eliding accesses. It says nothing to the hardware about write buffers or bus ordering, and nothing about atomicity. Two volatile writes to different peripherals can still land out of order at the far side of a bus bridge. On Cortex-M that is rare enough to ignore for GPIO and common enough to matter when you are clearing an interrupt flag and returning from the handler — a case we return to in chapter 15.

Nothing underneath you

The most disorienting part of moving from Linux to bare metal is how much simply is not there.

   WHAT YOU LOSE                  WHAT YOU GAIN

   printf to a console       ->   a UART you configure first
                                  (chapter 16 has cheaper options)

   malloc that works         ->   a heap you must justify,
                                  size, and usually avoid

   "segmentation fault"      ->   silent corruption, or a
                                  HardFault you must decode
                                  yourself (chapter 15)

   a scheduler               ->   a superloop, until you write
                                  one (chapters 17-18)

   drivers for everything    ->   the reference manual and
                                  1200 pages of register tables

   process isolation         ->   one address space; any bug
                                  can reach any byte

   time from the OS          ->   a timer you configure, whose
                                  accuracy is your crystal's

   The trade is total visibility. There is no layer between
   your code and the silicon that you cannot read, single-step,
   and change. Every problem is ultimately findable, because
   there is nowhere for it to hide.

Choosing between them

The decision is usually made for you by three constraints, in this order:

  • Power. If the product runs from a coin cell for a year, it is a microcontroller. No application processor idles in the microamp range. This one constraint decides more designs than any other.
  • Determinism. If missing a deadline is a safety event rather than a dropped frame, you want a core with no cache and no scheduler — or a system that has both, with an MCU beside it doing the part that must not miss.
  • What the software needs. A TCP/IP stack, a filesystem and a display fit on a modern MCU. A web browser, a camera pipeline and a package manager do not. If you need Linux's driver ecosystem, you need Linux, and you have chosen an application processor.

Plenty of real products contain both: an application processor for the interface and connectivity, and a microcontroller for the real-time control loop and power management, talking over SPI or I2C. Knowing both sides of that link, and why the split exists, is most of what this track and the next one are for.
