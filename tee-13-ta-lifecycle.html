TA lifecycle, properties and flags

Four flags in a header file decide whether your TA can serve several clients at once, whether it keeps state between them, and whether the kernel can see it. Choosing them wrongly produces bugs that only appear under concurrency, which is the worst kind to find late.

The header that configures everything

Every trusted application carries a header describing what it is and how it should be run. The loader reads it before any of your code executes.

/* ta/include/user_ta_header_defines.h - every TA has one.   */

#ifndef USER_TA_HEADER_DEFINES_H
#define USER_TA_HEADER_DEFINES_H

#include "my_ta.h"      /* where TA_MY_UUID is defined        */

#define TA_UUID  TA_MY_UUID

#define TA_FLAGS            (TA_FLAG_SINGLE_INSTANCE | \
                             TA_FLAG_MULTI_SESSION | \
                             TA_FLAG_INSTANCE_KEEP_ALIVE)

#define TA_STACK_SIZE       (2 * 1024)      /* per session     */
#define TA_DATA_SIZE        (32 * 1024)     /* the TA's heap   */

#define TA_CURRENT_TA_EXT_PROPERTIES \
    { "gp.ta.description", USER_TA_PROP_TYPE_STRING, \
      "My example TA" }, \
    { "gp.ta.version", USER_TA_PROP_TYPE_U32, &(const uint32_t){ 0x0100 } }

#endif

The flags

A handful of flags change the execution model substantially — whether instances are shared between clients, whether they persist, whether they may be multi-threaded.

FlagMeaningConsequence
TA_FLAG_SINGLE_INSTANCEOne copy of the TA serves all clientsGlobal state is shared between sessions. Without it, each client gets its own instance and its own globals
TA_FLAG_MULTI_SESSIONThe instance accepts more than one session at a timeWithout it, a second client waits until the first closes
TA_FLAG_INSTANCE_KEEP_ALIVEThe instance survives when the last session closesGlobal state and TA_CreateEntryPoint work persist. Costs TA_RAM permanently
TA_FLAG_DEVICE_ENUMAdvertise this TA to the Linux TEE busRequired for a kernel driver to bind (chapter 10)
TA_FLAG_SECURE_DATA_PATHMay receive secure-memory buffersFor media pipelines
TA_FLAG_CACHE_MAINTENANCEMay call TEE_Cache*Only with CFG_CACHE_API=y
 
   The four combinations that matter, and what each is for.

   1. SINGLE_INSTANCE | MULTI_SESSION | KEEP_ALIVE
      One instance, always resident, many concurrent clients,
      shared global state.
      -> A SERVICE. The fTPM is exactly this: one TPM, whose
         PCRs and NV storage are global, serving anyone.
      -> You are now responsible for thread safety of your own
         globals. OP-TEE does NOT serialise for you.

   2. SINGLE_INSTANCE | MULTI_SESSION       (no keep-alive)
      Same, but unloaded when idle. Saves TA_RAM; pays the
      load-and-verify cost on the next first session.
      -> A frequently-but-not-constantly used service.

   3. SINGLE_INSTANCE only
      One instance, ONE session at a time. Clients serialise.
      -> The safe default when you have shared state and do
         not want to think about locking. Simple and slow.

   4. neither SINGLE_INSTANCE nor MULTI_SESSION
      A fresh instance per client, each with its own globals
      and its own TA_RAM allocation.
      -> Perfect isolation between clients, at the cost of
         memory. Good for a per-application key handler.

   THE TRAP: combination 1 with global variables and no
   locking. Two clients invoke concurrently, both touch a
   global, and you have a data race inside the secure world.
   It will not show up in testing with one client.
MULTI_SESSION means you must lock

With SINGLE_INSTANCE | MULTI_SESSION, OP-TEE will run two TA_InvokeCommandEntryPoint calls concurrently on different threads, in the same address space, over the same globals. There is no implicit mutex. If your TA has mutable global state — a PCR bank, a key cache, a counter — you must protect it yourself. If you would rather not, drop MULTI_SESSION and accept serialisation.

Where state lives

What survives between calls, between sessions and across a reboot is decided by those flags, and getting the model wrong produces state leaking between mutually distrusting clients.

   THREE scopes, three lifetimes.

   GLOBAL VARIABLES
       lifetime: from TA_CreateEntryPoint to
                 TA_DestroyEntryPoint
       shared:   between all sessions, IF SINGLE_INSTANCE
       lost on:  TA unload (unless KEEP_ALIVE), reboot
       use for:  a service's shared state; caches

   SESSION CONTEXT (*sess_ctx)
       lifetime: TA_OpenSessionEntryPoint to
                 TA_CloseSessionEntryPoint
       shared:   only within that session
       lost on:  session close, TA panic, client death
       use for:  per-client keys, cursors, in-progress
                 operations

   PERSISTENT OBJECTS
       lifetime: until explicitly deleted
       shared:   per-TA, and per-client if the login type
                 scopes it (chapter 15)
       lost on:  explicit delete, factory reset, or a normal
                 world that deletes the backing file
       use for:  keys, counters, anything that must survive
                 reboot

   A common design error: keeping a key in a global "for
   performance" in a SINGLE_INSTANCE TA, so that client B can
   use the key client A loaded. Put per-client material in the
   session context.

A TA with all three

Following the flags through a concrete sequence of client calls is what makes the abstract model concrete.

#include <tee_internal_api.h>
#include <tee_internal_api_extensions.h>
#include <string.h>
#include "my_ta.h"

/* --- GLOBAL: shared, needs locking under MULTI_SESSION --- */
static uint32_t g_invocations;
static bool     g_initialised;

/* --- SESSION: per client --- */
struct session {
        TEE_ObjectHandle key;     /* this client's key         */
        uint32_t         counter;
        uint8_t          nonce[12];
};

TEE_Result TA_CreateEntryPoint(void)
{
        DMSG("TA loaded");
        g_invocations = 0;
        g_initialised = true;
        return TEE_SUCCESS;
}

void TA_DestroyEntryPoint(void)
{
        DMSG("TA unloaded after %u invocations", g_invocations);
        g_initialised = false;
}

TEE_Result TA_OpenSessionEntryPoint(uint32_t ptypes,
                                    TEE_Param params[4],
                                    void **sess_ctx)
{
        struct session *s;

        /* Even here, check the types. */
        if (ptypes != TEE_PARAM_TYPES(TEE_PARAM_TYPE_NONE,
                                      TEE_PARAM_TYPE_NONE,
                                      TEE_PARAM_TYPE_NONE,
                                      TEE_PARAM_TYPE_NONE))
                return TEE_ERROR_BAD_PARAMETERS;

        s = TEE_Malloc(sizeof *s, TEE_MALLOC_FILL_ZERO);
        if (!s)
                return TEE_ERROR_OUT_OF_MEMORY;

        s->key = TEE_HANDLE_NULL;
        TEE_GenerateRandom(s->nonce, sizeof s->nonce);

        /* Who is calling? */
        {
                TEE_Identity id;
                TEE_Result r = TEE_GetPropertyAsIdentity(
                        TEE_PROPSET_CURRENT_CLIENT,
                        "gpd.client.identity", &id);
                if (r == TEE_SUCCESS)
                        DMSG("client login type 0x%08x", id.login);
        }

        *sess_ctx = s;
        return TEE_SUCCESS;
}

void TA_CloseSessionEntryPoint(void *sess_ctx)
{
        struct session *s = sess_ctx;

        if (!s)
                return;
        if (s->key != TEE_HANDLE_NULL)
                TEE_FreeTransientObject(s->key);
        /* Wipe before freeing - the heap is reused. */
        TEE_MemFill(s, 0, sizeof *s);
        TEE_Free(s);
}

TEE_Result TA_InvokeCommandEntryPoint(void *sess_ctx,
                                      uint32_t cmd,
                                      uint32_t ptypes,
                                      TEE_Param params[4])
{
        struct session *s = sess_ctx;

        /* Global mutation. Under MULTI_SESSION this is a race.
           OP-TEE has no user-space mutex API for TAs, so
           either drop MULTI_SESSION, or make the update
           genuinely atomic, or keep the counter per session. */
        g_invocations++;

        s->counter++;

        switch (cmd) {
        case TA_CMD_LOAD_KEY:   return load_key(s, ptypes, params);
        case TA_CMD_SIGN:       return sign(s, ptypes, params);
        case TA_CMD_STATS:
                if (ptypes != TEE_PARAM_TYPES(
                                TEE_PARAM_TYPE_VALUE_OUTPUT,
                                TEE_PARAM_TYPE_NONE,
                                TEE_PARAM_TYPE_NONE,
                                TEE_PARAM_TYPE_NONE))
                        return TEE_ERROR_BAD_PARAMETERS;
                params[0].value.a = s->counter;   /* per session */
                params[0].value.b = g_invocations;/* global      */
                return TEE_SUCCESS;
        default:
                return TEE_ERROR_NOT_SUPPORTED;
        }
}

Sizing stack and heap

Stack and heap sizes are declared statically, because the secure world cannot grow them on demand. Getting them wrong produces a panic rather than a slowdown.

#define TA_STACK_SIZE  (2 * 1024)    /* PER SESSION            */
#define TA_DATA_SIZE   (32 * 1024)   /* the TA's whole heap    */

/* TA_STACK_SIZE: the C stack for TA code. 2 KB is the common
   default and it is small. Things that overflow it:
       - a large local buffer  (uint8_t buf[4096];)
       - deep recursion
       - a crypto call chain with its own locals
   Symptom: a panic with a stack dump, often in an unrelated
   function, and often only for large inputs.

   Do not put big buffers on the stack. TEE_Malloc them, or
   raise TA_STACK_SIZE deliberately.                          */

/* TA_DATA_SIZE: everything TEE_Malloc returns, plus the
   internal allocations OP-TEE makes on the TA's behalf -
   operation handles, object handles, key material.
   Symptom of running out: TEE_ERROR_OUT_OF_MEMORY, usually
   after a leak rather than a genuine shortage.              */

/* Measuring: build with CFG_TA_STATS=y and ask.             */
$ xtest --stats
TA stats:
  <uuid>
    Heap: allocated 8192, max allocated 20480, size 32768
    Stack: max used 1152, size 2048

/* "max used" is the number that matters. 1152 of 2048 is
   comfortable; 1900 of 2048 is a crash waiting for a longer
   input.                                                     */

Properties

Properties are the configuration mechanism, readable by the trusted application at run time and fixed at build time — which is what makes them trustworthy.

/* Declared in the header, readable by the TA and, for some,
   by the client.                                            */

#define TA_CURRENT_TA_EXT_PROPERTIES \
    { "gp.ta.description", USER_TA_PROP_TYPE_STRING, \
      "Secure key store" }, \
    { "gp.ta.version", USER_TA_PROP_TYPE_U32, \
      &(const uint32_t){ 0x0102 } }, \
    { "com.example.max-keys", USER_TA_PROP_TYPE_U32, \
      &(const uint32_t){ 16 } }

/* Read them: */
    uint32_t maxkeys;
    TEE_GetPropertyAsU32(TEE_PROPSET_CURRENT_TA,
                         "com.example.max-keys", &maxkeys);

/* Standard properties every TA has: */
    gpd.ta.appID            this TA's UUID
    gpd.ta.singleInstance   bool, from the flags
    gpd.ta.multiSession     bool
    gpd.ta.instanceKeepAlive bool
    gpd.ta.dataSize         TA_DATA_SIZE
    gpd.ta.stackSize        TA_STACK_SIZE

/* About the TEE itself: */
    gpd.tee.apiversion
    gpd.tee.internalCore.version
    gpd.tee.trustedos.implementation.version
    gpd.tee.deviceID        a per-device identifier derived
                            from the hardware unique key -
                            useful, and privacy-sensitive

/* About the caller: */
    gpd.client.identity     login type + uuid (chapter 12)
