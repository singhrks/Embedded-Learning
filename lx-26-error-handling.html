Error handling patterns and devm

The kernel has no exceptions and no destructors, so unwinding is manual — and error paths are the least-tested code in any driver. Two disciplines make them reliable: the goto ladder, and letting the device model free things for you.

The goto ladder

Kernel C uses goto for error handling, which is startling if you were taught it is always wrong. In a function that acquires several resources in sequence, it produces the only readable structure that unwinds them correctly — and the alternative, repeating cleanup at every exit, is what actually causes bugs.

/* This is idiomatic kernel C, not a code smell. Every label
   undoes exactly one step, in reverse order.               */

static int mydev_probe(struct platform_device *pdev)
{
        struct mydev *d;
        int ret;

        d = kzalloc(sizeof(*d), GFP_KERNEL);
        if (!d)
                return -ENOMEM;

        ret = regulator_enable(d->vdd);
        if (ret)
                goto err_free;

        ret = clk_prepare_enable(d->clk);
        if (ret)
                goto err_reg;

        ret = mydev_hw_init(d);
        if (ret)
                goto err_clk;

        ret = request_irq(d->irq, mydev_isr, 0, "mydev", d);
        if (ret)
                goto err_hw;

        return 0;

err_hw:
        mydev_hw_shutdown(d);
err_clk:
        clk_disable_unprepare(d->clk);
err_reg:
        regulator_disable(d->vdd);
err_free:
        kfree(d);
        return ret;
}

/* WHY IT BEATS THE ALTERNATIVES:

   · nested ifs get unreadable past three levels, and the
     cleanup is duplicated at each depth
   · a single "cleanup everything" function must guess how far
     you got, which means tracking state - more code, more
     bugs
   · early returns duplicate the unwind at every exit

   THE RULE THAT MAKES IT WORK: label names say WHAT THEY
   UNDO, not where they came from. `err_clk` disables the
   clock. Add a step in the middle and you insert one label
   and one goto - nothing else changes.

   NAME THEM AFTER THE THING BEING UNDONE, never err1, err2,
   err3 - those force a renumber every time the order
   changes, and renumbering is where the mistakes creep in. */

devm: managed resources

Most of the ladder above can be deleted. Managed allocations register themselves against the device, and the driver core releases them automatically — in the right order — whether probe fails halfway through or the device is unbound years later.

/* The device model can free things automatically when the
   device unbinds - which deletes most of the ladder.       */

static int mydev_probe(struct platform_device *pdev)
{
        struct device *dev = &pdev->dev;
        struct mydev *d;

        d = devm_kzalloc(dev, sizeof(*d), GFP_KERNEL);
        if (!d)
                return -ENOMEM;

        d->base = devm_platform_ioremap_resource(pdev, 0);
        if (IS_ERR(d->base))
                return PTR_ERR(d->base);

        d->clk = devm_clk_get_enabled(dev, NULL);
        if (IS_ERR(d->clk))
                return PTR_ERR(d->clk);

        d->irq = platform_get_irq(pdev, 0);
        if (d->irq < 0)
                return d->irq;

        ret = devm_request_irq(dev, d->irq, mydev_isr, 0,
                               "mydev", d);
        if (ret)
                return ret;

        return 0;      /* no labels, no unwind, no leaks */
}

/* HOW IT WORKS: each devm_ call appends an entry to a list on
   the struct device. When the device unbinds - whether
   because probe failed, remove ran, or the module unloaded -
   the core walks that list IN REVERSE and calls each release
   function.

   So the unwinding order is automatically correct, and it is
   correct on the failure path too, without you writing it.

/* THE COMMON ONES: */
        devm_kzalloc, devm_kcalloc, devm_kstrdup
        devm_ioremap, devm_platform_ioremap_resource
        devm_clk_get, devm_clk_get_enabled, devm_clk_bulk_get
        devm_regulator_get, devm_regulator_bulk_get
        devm_reset_control_get
        devm_gpiod_get, devm_gpiod_get_optional
        devm_request_irq, devm_request_threaded_irq
        devm_regmap_init_mmio
        devm_pm_runtime_enable
        devm_add_action_or_reset   /* <-- the general one */
What devm does not do

devm_clk_get() releases the clock reference — it does not disable the clock. devm_regulator_get() does not disable the regulator. devm_gpiod_get() does not restore the pin state. Anything you enabled by hand, you must disable by hand in remove. Use devm_clk_get_enabled() and the bulk enable helpers where they exist; for the rest, the pattern below closes the gap.

devm_add_action_or_reset

devm_ covers the resources the kernel knows about. When you need to undo something it has no concept of — quiescing hardware, freeing a third-party handle — you can register your own cleanup function to run at the same time.

/* Register YOUR OWN cleanup with the device, so anything can
   participate in managed unwinding.                        */

static void mydev_disable_vdd(void *data)
{
        regulator_disable(data);
}

        ret = regulator_enable(d->vdd);
        if (ret)
                return ret;

        ret = devm_add_action_or_reset(dev, mydev_disable_vdd,
                                       d->vdd);
        if (ret)
                return ret;
        /* from here on, the regulator is disabled
           automatically on unbind - and if the registration
           itself failed, _or_reset already called the action,
           so there is nothing to unwind.                    */

/* THE "_or_reset" SUFFIX IS THE POINT: plain
   devm_add_action() leaves you holding the resource if the
   registration fails, so you would need an error path for the
   error path. _or_reset calls the action immediately on
   failure, so `return ret;` is always correct.

   ALWAYS USE _or_reset. There is no good reason for the
   plain form in new code.                                   */

/* THIS PATTERN GENERALISES to anything: */
static void mydev_hw_off(void *data)
{
        mydev_hw_shutdown(data);
}
        ret = mydev_hw_init(d);
        if (ret)
                return ret;
        ret = devm_add_action_or_reset(dev, mydev_hw_off, d);
        if (ret)
                return ret;

/* Now even hardware shutdown is managed, and remove() can be
   empty - which is the goal: a driver whose teardown cannot
   be wrong because there is no teardown code to get wrong. */

ERR_PTR and error returns

Kernel functions returning a pointer need a way to report why they failed, not just that they did. Rather than an out-parameter, the kernel encodes an error code into the pointer itself — which is why testing these returns against NULL is a bug.

/* Kernel convention: functions returning a pointer encode
   errors IN the pointer, using the top page of the address
   space, which no valid pointer occupies.                  */

        void *p = some_function();

        if (IS_ERR(p))
                return PTR_ERR(p);      /* extract the errno */

/* NOT: */
        if (!p)                          /* WRONG - an error
                                            pointer is NOT
                                            NULL              */

/* WRITING one: */
struct mydev *mydev_find(int id)
{
        if (id < 0)
                return ERR_PTR(-EINVAL);
        if (!exists(id))
                return ERR_PTR(-ENODEV);
        return &devices[id];
}

/* THE THREE-WAY CASE - can return NULL, an error, or a valid
   pointer (optional resources do this): */
        if (IS_ERR_OR_NULL(p))
                ...
        /* or, more precisely: */
        if (IS_ERR(p))
                return PTR_ERR(p);      /* a real error */
        if (!p)
                /* legitimately absent - the optional case */

/* PRINTING one: */
        dev_err(dev, "failed: %pe\n", p);
                -> "failed: -ENOMEM"

/* AND THE ERRNO CODES that matter in drivers: */
        -ENOMEM         out of memory
        -EINVAL         bad argument from a caller
        -ENODEV         no such device / not present
        -EIO            hardware failed
        -EBUSY          in use, try later
        -ETIMEDOUT      hardware did not respond
        -EPROBE_DEFER   a supplier is not ready yet
        -ENOTSUPP       this hardware cannot do that
        -ENOTTY         no such ioctl
        -EAGAIN         nothing available right now
        -ERESTARTSYS    interrupted, please restart

/* PICK THE SPECIFIC ONE. -EINVAL for everything makes a
   userspace program's diagnostics useless, and yours too. */

dev_err_probe

Nearly every failure in probe() wants to do the same three things: log a message, avoid shouting about a deferred probe, and return the code. One helper does all three, which is why modern probe functions are so much shorter than older ones.

/* Every resource acquisition in probe should use it: */

        d->clk = devm_clk_get(dev, "core");
        if (IS_ERR(d->clk))
                return dev_err_probe(dev, PTR_ERR(d->clk),
                                     "failed to get core clock\n");

/* IT DOES FOUR THINGS:
     1. logs with the device name prefixed
     2. for -EPROBE_DEFER, logs at DEBUG level instead of
        ERROR - so normal boot is not flooded with messages
        about deferrals that resolve
     3. records the deferral reason, visible in
        /sys/kernel/debug/devices_deferred
     4. returns the error code, so `return` composes

   THE ALTERNATIVE people write: */
        if (IS_ERR(d->clk)) {
                dev_err(dev, "no clock\n");      /* spams on
                                                    every retry */
                return PTR_ERR(d->clk);
        }
/* which works but floods the log during normal deferred
   probe, and loses the deferral reason.                    */

Scope-based cleanup

The newest addition to kernel C borrows an idea from C++ and Rust: variables that clean themselves up when they go out of scope. It removes whole classes of leak, and you will increasingly see it in new code.

/* Newer kernels have __cleanup__-based helpers, borrowed from
   C++ RAII. They release on EVERY exit from the scope,
   including returns and gotos.                             */

#include <linux/cleanup.h>

/* LOCKS: */
static int mydev_do_thing(struct mydev *d)
{
        guard(mutex)(&d->lock);       /* held until return */

        if (!d->ready)
                return -EAGAIN;        /* unlocked correctly */

        return mydev_thing(d);         /* and here too */
}

/* a narrower scope: */
        scoped_guard(spinlock_irqsave, &d->lock) {
                d->count++;
        }

/* MEMORY: */
        char *buf __free(kfree) = kmalloc(len, GFP_KERNEL);
        if (!buf)
                return -ENOMEM;
        ...
        return 0;              /* buf freed automatically */

/* REFERENCE COUNTS: */
        struct device_node *np __free(device_node) =
                of_parse_phandle(dev->of_node, "partner", 0);

/* WHERE THIS HELPS MOST: functions with many early returns
   under a lock, which is exactly where forgotten unlocks
   live. It does not replace the goto ladder for probe -
   ordered hardware teardown still needs explicit sequencing -
   but it removes a whole class of lock leaks.

   Check whether your target kernel has it before relying on
   it; it landed in 6.4 and later.                          */

Testing error paths

Error paths are the least-tested code in any driver, because they only run when something goes wrong — which in normal testing is never. These techniques make failures happen deliberately, so the paths get exercised before a customer finds them.

# Error paths are the least-executed and least-tested code in
# any driver. Force them.

# 1. FAULT INJECTION on allocations:
    CONFIG_FAILSLAB=y
    CONFIG_FAULT_INJECTION_DEBUG_FS=y
    echo 10   > /sys/kernel/debug/failslab/probability
    echo 100  > /sys/kernel/debug/failslab/times
    echo 1    > /sys/kernel/debug/failslab/verbose
    # then load your driver repeatedly. 10% of allocations
    # fail; anything that crashes is an unchecked return.

# 2. REMOVE RESOURCES from the device tree, one at a time:
#      delete the clocks property   -> probe must fail cleanly
#      delete the interrupt         -> same
#      point reg at a bad address   -> the ID check must catch it

# 3. BIND/UNBIND in a loop, under KASAN:
    for i in $(seq 100); do
      echo 1c000000.my-device > .../unbind
      echo 1c000000.my-device > .../bind
    done
    dmesg | grep -i -e kasan -e "warn" -e "bug"

# 4. CHECK FOR LEAKS after a failed probe:
    cat /proc/iomem      | grep 1c000000    # should be gone
    cat /proc/interrupts | grep my-device   # should be gone
    cat /sys/kernel/debug/kmemleak

# EVERY ONE of these finds real bugs in drivers that pass
# their functional tests. The fault-injection run in
# particular usually finds two or three unchecked returns the
# first time it is used on a driver.
The rule that prevents most of it

Whenever you write a line that acquires something, write the line that releases it in the same edit — the goto label, the devm_add_action_or_reset, or the __free annotation. Deferring "I will add the cleanup later" is how leaks are born, because later never has the full context of what order things were acquired in.

How it shows up

SymptomCause
Crash when a NULL check "passed"Checked for NULL where IS_ERR was needed
Resource leak after a failed probeMissing unwind step, or an early return past the ladder
Region still in /proc/iomem after unbindBare ioremap instead of the devm/resource form
Clock stays on after unbinddevm_clk_get does not disable — use devm_clk_get_enabled
Regulator refcount imbalance warningsregulator_enable without a matching disable path
Second bind fails after a successful unbindState left behind — something not released
Log flooded with "failed to get clock" at bootdev_err instead of dev_err_probe on a deferral
Deadlock on an error pathEarly return under a lock — guard() prevents this class
Crash only under memory pressureUnchecked allocation — fault injection finds it in minutes
Unwind order wrong, hardware left in a bad stateManual cleanup function that guessed how far setup got
