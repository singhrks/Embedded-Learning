Shaders and the programmable stages

A shader is a small program run millions of times a frame with no memory of the last invocation. Learning the language takes an afternoon; learning what it may and may not do — and how it gets from source to silicon — is the part that matters.

The languages, and the IRs beneath them

   HLSL   ---> DXBC        DX11 and earlier
          ---> DXIL        DX12 Shader Model 6+, LLVM-based
          ---> SPIR-V      via DXC, for Vulkan

   GLSL   ---> SPIR-V      OpenGL 4.6, Vulkan
   MSL    ---> AIR         Metal
   WGSL   ---> whatever    WebGPU
   Slang  ---> all of them a newer language that targets
                           everything; increasingly common

   THE TWO-STAGE COMPILE, and it explains a lot:

     OFFLINE     your HLSL -> DXIL/SPIR-V.  Portable IR, but
                 still not machine code. Ships in your app.
     AT RUNTIME  the DRIVER compiles IR -> the actual ISA of
                 the installed GPU.

   CONSEQUENCES

     * you cannot ship machine code: the ISA differs per
       vendor, per generation, and is often undocumented.
     * the FIRST use of a shader triggers a driver compile,
       which is why games stutter on new effects and why
       "shader pre-caching" screens exist.
     * a driver update can change your shader's performance
       without you rebuilding anything.
     * two GPUs disagreeing about your shader is usually two
       different back-end compilers, not a spec violation.

   PIPELINE STATE OBJECTS (chapter 15) exist largely to give
   the driver everything it needs to do this compile ONCE, at
   a time you choose, instead of mid-frame.
// HLSL, the whole language you need for a first shader.

cbuffer PerObject : register(b0)      // constant buffer
{
    float4x4 WorldViewProj;
    float4   Tint;
};

Texture2D    Albedo  : register(t0);  // SRV
SamplerState Linear  : register(s0);  // sampler

struct VSIn {
    float3 pos    : POSITION;         // SEMANTICS bind these
    float3 normal : NORMAL;           // to vertex buffer
    float2 uv     : TEXCOORD0;        // elements
};

struct VSOut {
    float4 pos    : SV_Position;      // SV_ = SYSTEM VALUE,
    float3 normal : NORMAL;           // meaningful to the
    float2 uv     : TEXCOORD0;        // fixed-function stages
};

VSOut VSMain(VSIn i)
{
    VSOut o;
    o.pos    = mul(float4(i.pos, 1.0), WorldViewProj);
    o.normal = i.normal;
    o.uv     = i.uv;
    return o;
}

float4 PSMain(VSOut i) : SV_Target       // -> render target 0
{
    float3 n = normalize(i.normal);      // renormalise: linear
                                         // interpolation of
                                         // unit vectors does
                                         // NOT preserve length
    float  ndl = saturate(dot(n, float3(0, 1, 0)));
    float4 base = Albedo.Sample(Linear, i.uv);
    return base * Tint * (ndl * 0.8 + 0.2);
}
Semantics are the wiring

There are no linkers between shader stages. TEXCOORD0 out of the vertex shader connects to TEXCOORD0 in the pixel shader by name, and the input layout binds POSITION to a byte offset in the vertex buffer by name. A mismatched or missing semantic is the commonest reason a mesh renders as garbage, and it usually produces no error — just wrong data.

/* Things that are slower than they look. */

  a / b            -> reciprocal + multiply. Fine.
  a % b   (int)    -> genuinely slow. If b is a power of two,
                      use a & (b-1).
  a / b   (int)    -> same. Use a >> log2(b).
  pow(x, 2)        -> use x * x. The compiler often catches
                      this; do not rely on it.
  length(v) < r    -> compare SQUARED lengths and skip the
                      sqrt entirely: dot(v,v) < r*r
  sin/cos of the
    same angle     -> sincos(x, s, c) computes both at once

/* Things that are faster than they look. */

  saturate(x)      -> FREE. It is an output modifier on the
                      preceding instruction, not an operation.
                      Prefer it to clamp(x, 0, 1).
  mad / fma        -> a*b+c is ONE instruction. Write your
                      arithmetic so it factors that way.
  lerp(a, b, t)    -> one mad.
  swizzles         -> free. v.xyzw, v.wwww, v.xz cost nothing.
  abs and negate   -> free input modifiers.

/* The general rule: the ALU is nearly free; MEMORY and
   DIVERGENCE are what cost. Optimising arithmetic in a shader
   that is texture-bound is wasted effort - measure first. */

What a shader may not do

   NO recursion            the stack is finite and tiny.
                           (Ray-tracing shaders are the one
                           exception, with a bounded depth.)

   NO function pointers    everything is inlined. There is no
                           call in the final ISA.

   NO dynamic allocation   no malloc, no new. All storage is
                           declared up front.

   NO pointers, mostly     buffers are indexed, not chased.
                           (DX12 has descriptor indexing, and
                           newer models add buffer pointers.)

   NO cross-invocation
     communication         except within a wave (chapter 2) or
                           a compute workgroup via groupshared.
                           Two pixels cannot talk.

   NO guaranteed order     pixel shader invocations complete in
                           any order. Blending is ordered by
                           fixed-function hardware, not by you.

   LOOPS must be bounded   or the compiler unrolls until it
                           gives up. An unbounded while loop
                           driven by a texture value will
                           either fail to compile or produce a
                           multi-megabyte shader.

   [loop]     forces a real loop (smaller code, more
              divergence)
   [unroll]   forces unrolling (bigger code, more registers,
              often much faster)
   [branch]   real branch
   [flatten]  evaluate both sides and select

   These attributes matter: a [unroll] on a 4-iteration loop
   is usually a clear win, and a missing [loop] on a long one
   can blow your register budget and destroy occupancy
   (chapter 5).

Derivatives, and why pixels come in quads

/* The rasteriser ALWAYS shades 2x2 quads, even for a triangle
   covering one pixel. The other three lanes are "helper
   invocations": they run, they compute, their output is
   discarded.

   WHY: mip level selection needs to know how fast the texture
   coordinate is changing across the screen, and the only way
   to know that is to compare with your neighbour.          */

        float2 dx = ddx(uv);       /* difference with the pixel
                                      to the right             */
        float2 dy = ddy(uv);       /* ... and below            */
        /* Texture.Sample() calls these implicitly to pick a
           mip level.                                         */

/* THREE CONSEQUENCES

   1. SMALL TRIANGLES ARE EXPENSIVE. A triangle covering one
      pixel still costs four pixel-shader invocations - 4x
      the shading for the same coverage. This is why dense
      meshes tank performance long before the vertex cost
      matters, and the main problem meshlets and variable-rate
      shading exist to address.

   2. YOU CANNOT SAMPLE WITH IMPLICIT MIPS IN DIVERGENT FLOW.
      If half the quad took the other branch, its derivative
      is undefined. The compiler will either hoist the sample
      out of the branch or warn you. Use SampleLevel() or
      SampleGrad() to supply the mip yourself:              */
        if (someCondition)
                c = tex.Sample(s, uv);         /* UNDEFINED    */
        c = tex.SampleLevel(s, uv, 0);         /* fine anywhere */

   3. DERIVATIVES ARE PER-QUAD, so ddx of a value that varies
      per-pixel is a 2x2 approximation, not a true gradient.
      Screen-space effects built on ddx are blocky at 2x2
      granularity by construction.                          */
The dense-mesh trap

Quad overshading means a mesh tessellated to sub-pixel triangles can cost four times the pixel shading of the same silhouette drawn with larger triangles — while every profiler tells you the pixel shader is the bottleneck, which it is, for a reason that has nothing to do with the shader. Check triangle size before optimising shader code on a highly detailed asset.
