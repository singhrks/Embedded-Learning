Memory-mapped files and copy-on-write

Two applications of the same trick: make the page tables lie, and let a fault fix things up on demand. Together they explain why fork() is cheap, why shared libraries cost one copy of memory system-wide, and why mmap is sometimes far faster than read and sometimes much slower.

Mapping a file into memory

Mapping a file into memory replaces read and write calls with ordinary memory access, and removes a copy in the process. It is the mechanism behind program loading, shared libraries and most high-performance I/O.

int fd = open("data.bin", O_RDONLY);
struct stat st;
fstat(fd, &st);

void *p = mmap(NULL,            /* let the kernel choose the address */
               st.st_size,      /* length                            */
               PROT_READ,       /* protection                        */
               MAP_PRIVATE,     /* private (COW) or MAP_SHARED       */
               fd, 0);          /* file and offset (page-aligned)    */
close(fd);                      /* the MAPPING keeps the file alive  */

/* the file's bytes are now simply memory */
uint32_t magic = *(uint32_t *)p;
for (size_t i = 0; i < st.st_size; i++)
        checksum += ((uint8_t *)p)[i];

munmap(p, st.st_size);
What actually happened:

  mmap() created a VMA and returned. NO data was read.
  Every page is marked invalid in the page tables.

  The first access to each page faults:
     · kernel looks up the VMA → this is file-backed at offset N
     · finds the page in the PAGE CACHE, or reads it from disk
     · installs a PTE pointing at that page-cache page
     · retries the instruction

  Consequences:
     · the mapping is the SAME physical memory as the page cache,
       so no copy is made
     · two processes mapping the same file share those frames
     · a 100 GB file can be mapped on a machine with 8 GB of RAM
     · reading sequentially triggers readahead, exactly as read()
       would

The four combinations

A mapping is described by two independent choices, giving four combinations with genuinely different behaviour. Picking the wrong one produces changes that silently go nowhere.

File-backedAnonymous
MAP_PRIVATECopy-on-write view of a file. Writes are private and never reach disk. Used for: executables, shared libraries.Ordinary private memory. Used for: malloc of large blocks, thread stacks.
MAP_SHAREDWrites go to the file and are visible to every other mapper. Used for: databases, IPC over a file.Shared memory between related processes. Used for: fork-based IPC (ch. 08).
 
/* MAP_PRIVATE on a file is where the two ideas meet: */
void *p = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_PRIVATE, fd, 0);
p[0] = 'X';
/* The page was shared read-only with the page cache. Writing it
   triggers a COW fault: the kernel allocates a fresh frame, copies
   the contents, and remaps THIS process's PTE to the copy.
   The file on disk is untouched. Other mappers see the original. */

Copy-on-write

Copy-on-write lets two processes share pages until one writes, at which point it gets a private copy. It is what makes process creation fast and shared libraries cheap.

   BEFORE fork()
   parent PTEs ──────►  [ page A ]  [ page B ]  [ page C ]
                          rw           rw          rw

   AFTER fork() — no data copied, only page TABLES
   parent PTEs ──┐
                 ├────►  [ page A ]  [ page B ]  [ page C ]
   child  PTEs ──┘         RO,cow      RO,cow     RO,cow
                           refcount 2  refcount 2 refcount 2

   Both mappings are marked READ-ONLY, with a flag saying "this is
   COW, not genuinely read-only".

   CHILD WRITES page B
        │ write to a read-only page → PAGE FAULT
        ▼
   kernel: the VMA says writable, and the PTE says COW
        · allocate a new frame
        · copy page B into it
        · point the CHILD's PTE at the copy, mark it rw
        · decrement the original's refcount to 1
        · since only the parent now maps it, restore ITS PTE to rw
        · retry the instruction

   parent PTEs ──────►  [ page A ]  [ page B  ]  [ page C ]
                          RO,cow       rw          RO,cow
   child  PTEs ──────►  [ page A ]  [ page B' ]  [ page C ]
                          RO,cow       rw          RO,cow

  Only the pages actually written are ever duplicated. A process
  that forks and immediately execs copies almost nothing.

The fork memory-accounting confusion

After fork(), ps shows both processes with the same RSS — but they share almost all of it, so the machine's real usage barely changed. RSS double-counts shared pages. Use PSS (Proportional Set Size), which divides each shared page's size by the number of sharers:

grep -H '^Pss:' /proc/*/smaps_rollup | sort -k2 -n -r | head
smem -k -s pss                    # per-process, sorted by PSS
/* PSS is the only per-process number that sums to something
   meaningful across all processes.                          */

Why COW is security-sensitive

A famous vulnerability in exactly this mechanism, worth studying because it shows how a subtle race in something this fundamental becomes a complete privilege escalation.

/* Dirty COW (CVE-2016-5195) — a race between the COW fault handler
   and madvise(MADV_DONTNEED), exploitable to write to a read-only
   file mapping, giving local root on essentially every Linux
   system for nine years.

   The lesson is general: COW is a place where the page tables
   deliberately disagree with the VMA's stated permissions, and
   the window between fault and fixup is a race that must be
   handled with great care. Several later CVEs (Dirty Pipe,
   CVE-2022-0847) follow the same shape.                      */

The honest summary

mmap is a win for random access to large files and for sharing. It is frequently a loss for sequential streaming, because a page fault every 4 KB costs more than one read() of 1 MB. Linus Torvalds has made this point repeatedly, and benchmarks bear it out. Use mmap when you would otherwise be seeking; use read with a large buffer when you are streaming.

/* If you do use mmap, tell the kernel your access pattern */
madvise(p, len, MADV_SEQUENTIAL);   /* aggressive readahead, drop behind */
madvise(p, len, MADV_RANDOM);       /* disable readahead                 */
madvise(p, len, MADV_WILLNEED);     /* prefault now                      */
mmap(..., MAP_POPULATE, ...);       /* prefault the whole mapping        */

/* Handling SIGBUS is genuinely awkward: it fires on a truncated
   file or an I/O error, from anywhere the mapping is touched. In
   robust code, either avoid mmap for untrusted files, or install
   a handler and use siglongjmp — which is its own problem.    */

Zero-copy I/O

Moving data without copying it is the goal of several distinct mechanisms, each suited to a different shape of problem — and each removing a copy that read and write would have made.

/* The general goal: avoid copying data through user space at all. */

/* sendfile: file → socket, entirely in the kernel */
sendfile(out_fd, in_fd, &offset, count);
/* saves two copies and two context switches versus read+write.
   This is how static web servers serve files.                */

/* splice: move data between fds via a pipe, without copying */
splice(fd_in, NULL, pipefd[1], NULL, len, SPLICE_F_MOVE);
splice(pipefd[0], NULL, fd_out, NULL, len, SPLICE_F_MOVE);

/* vmsplice: map user pages into a pipe */
/* copy_file_range: server-side copy, may be offloaded to the
   filesystem or even the storage device (reflink on btrfs/XFS) */
copy_file_range(fd_in, &off_in, fd_out, &off_out, len, 0);

/* io_uring: registered buffers plus fixed files remove even the
   per-operation syscall (OS chapter 08).                      */

Direct access and persistent memory

When storage is byte-addressable and nearly as fast as memory, the page cache becomes an unnecessary intermediate copy. Bypassing it entirely is what this mode does.

/* DAX: for byte-addressable persistent memory, the page cache is
   pointless — map the device's pages directly.                */
mount -o dax /dev/pmem0 /mnt

/* A store instruction now writes persistent storage. Which raises
   a genuinely new problem: ordering and durability at CPU cache
   granularity. You need explicit flushes:                     */
    dc cvap, x0        /* clean to point of persistence (ARM)   */
    clwb               /* cache line write back (x86)           */
    sfence
/* Getting this wrong gives torn, non-atomic updates that survive
   a power cut — a corruption class that did not exist before. */

Observing mappings

Everything about a process's mappings is visible from outside, which turns questions about what is mapped, shared or resident into a single command.

cat /proc/PID/maps               # all VMAs
cat /proc/PID/smaps              # per-VMA detail:
#   Rss, Pss, Shared_Clean/Dirty, Private_Clean/Dirty,
#   Referenced, Anonymous, Swap, THPeligible
cat /proc/PID/smaps_rollup       # totals — much cheaper to parse

pmap -x PID                      # readable summary
pmap -XX PID                     # everything

# is this page shared, and with whom?
sudo ./page-types -p PID         # from linux/tools/vm

# how much of the page cache does a file occupy?
vmtouch -v /path/to/file
fincore /path/to/file

# force a file out of the cache, for cold benchmarking
dd of=/path/to/file oflag=nocache conv=notrunc,fdatasync count=0
