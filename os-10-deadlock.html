Classic concurrency problems and deadlock

Deadlock has exactly four necessary conditions, and breaking any one of them prevents it. The classic textbook problems are not academic exercises — each is a real pattern you will meet, and each has a standard solution worth knowing by name.

The four conditions

Coffman's conditions — all four must hold simultaneously
  1. Mutual exclusion — a resource is held exclusively.
  2. Hold and wait — a thread holds one resource while waiting for another.
  3. No preemption — a resource cannot be forcibly taken away.
  4. Circular wait — a cycle exists in the wait-for graph.

Break any one and deadlock becomes impossible. Every prevention technique below is an attack on one of these four.

   Thread A                        Thread B
   ─────────                       ─────────
   lock(mutex1)   ────────────►    lock(mutex2)
        │                               │
   lock(mutex2)   ◄──── waits ────  lock(mutex1)
        │                               │
      blocked                        blocked

   wait-for graph:      A ──► mutex2 (held by B)
                        B ──► mutex1 (held by A)
                        ↑                       │
                        └───────────────────────┘   a CYCLE

  Note this deadlocks only when the interleaving is unlucky. It can
  pass ten thousand tests and hang in production — which is exactly
  why static order rules and lockdep matter more than testing.

Breaking each condition

Deadlock needs four conditions to hold simultaneously, which is useful because breaking any one of them is sufficient. Each break has a different cost, and one of them is the standard answer in practice.

AttackTechniquePracticality
Mutual exclusionLock-free structures, immutable data, per-thread copiesBest when applicable — removes the problem entirely
Hold and waitAcquire all locks at once, or none. Release everything before retrying.Often impractical: you rarely know the full set in advance
No preemptiontrylock + back off, releasing what you holdWorkable, but risks livelock without randomised backoff
Circular waitA global lock order, obeyed everywhereThe standard solution in real systems
 
/* LOCK ORDERING — the practical answer. Define a total order and
   document it where the locks are declared.                    */

/*
 * Lock order (acquire in this order, release in reverse):
 *      1. device->config_lock
 *      2. device->queue_lock
 *      3. buffer->lock
 */

/* When the order is dynamic — two objects of the same type — order
   by ADDRESS. Any consistent total order works.               */
void transfer(struct account *a, struct account *b, int amount)
{
        struct account *first  = (a < b) ? a : b;
        struct account *second = (a < b) ? b : a;

        if (a == b) return;              /* do not self-deadlock */

        pthread_mutex_lock(&first->lock);
        pthread_mutex_lock(&second->lock);
        a->balance -= amount;
        b->balance += amount;
        pthread_mutex_unlock(&second->lock);
        pthread_mutex_unlock(&first->lock);
}
/* Ordering by address is the standard trick; the kernel's
   double_lock_balance() and Linux's inode locking both do it.  */
/* TRYLOCK AND BACK OFF — when ordering is impossible */
for (;;) {
        pthread_mutex_lock(&m1);
        if (pthread_mutex_trylock(&m2) == 0)
                break;                          /* got both      */
        pthread_mutex_unlock(&m1);              /* release ALL   */
        usleep(rand() % 100);                    /* random backoff */
}
/* The random backoff is not optional: without it, two threads can
   repeatedly grab and release in lockstep forever — LIVELOCK.
   They are running, consuming CPU, and making no progress.    */

Detection and recovery

Rather than preventing deadlock, a system can detect it after the fact and recover. Databases do this routinely; operating systems mostly do not, and the reason is worth understanding.

/* Rather than preventing deadlock, detect it and break the cycle. */

/* 1. Timeouts — crude but effective in application code */
struct timespec ts;
clock_gettime(CLOCK_REALTIME, &ts);
ts.tv_sec += 5;
if (pthread_mutex_timedlock(&m, &ts) == ETIMEDOUT) {
        release_everything();
        return -EAGAIN;                  /* retry from the top */
}

/* 2. Error-checking mutexes catch self-deadlock immediately */
pthread_mutexattr_settype(&a, PTHREAD_MUTEX_ERRORCHECK);
if (pthread_mutex_lock(&m) == EDEADLK) ...

/* 3. lockdep (kernel) — builds the lock-order graph at runtime and
      reports a cycle the FIRST time an inconsistent order is seen,
      whether or not it deadlocked. This is the gold standard.   */

/* Databases do full cycle detection in the wait-for graph and
   abort one transaction as the "victim" — which is why you must
   handle deadlock-retry errors in any transactional code.     */

Livelock and starvation

A system can be completely stuck without any thread being blocked — everyone busy, nothing progressing. It is rarer than deadlock and considerably harder to recognise.

DeadlockLivelockStarvation
Threads areBlockedRunningRunning or blocked
CPU usageZeroHighNormal
ProgressNone, everNone, everSome threads progress; one never does
CauseCircular waitRepeated mutual back-offUnfair scheduling or lock policy
FixLock orderingRandomised backoff, or a queueFair/ticket locks, aging, priority boost
 
/* Starvation from an unfair lock: a thread on the same core keeps
   reacquiring before a waiter on another core is scheduled.  */

/* A TICKET LOCK gives strict FIFO fairness: */
typedef struct { atomic_uint next, now; } ticket_lock_t;

void lock(ticket_lock_t *l) {
        unsigned my = atomic_fetch_add(&l->next, 1);
        while (atomic_load_explicit(&l->now, memory_order_acquire) != my)
                cpu_relax();
}
void unlock(ticket_lock_t *l) {
        atomic_fetch_add_explicit(&l->now, 1, memory_order_release);
}
/* Fair, but every waiter spins on the SAME cache line — the
   coherence traffic scales badly (CA chapter 15). MCS and qspinlock
   fix that by giving each waiter its own line to spin on; Linux
   uses qspinlock for exactly this reason.                    */

Producer–consumer

The most common concurrent structure there is, and the one most often implemented subtly wrongly. Getting the empty and full cases right is the whole problem.

/* The most common real pattern: one side generates, the other
   consumes, with a bounded buffer in between.                */

#define N 16
struct item buf[N];
size_t head, tail, count;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_full  = PTHREAD_COND_INITIALIZER;
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;

void produce(struct item it)
{
        pthread_mutex_lock(&m);
        while (count == N)                       /* while, not if */
                pthread_cond_wait(&not_full, &m);
        buf[head] = it;
        head = (head + 1) % N;
        count++;
        pthread_mutex_unlock(&m);
        pthread_cond_signal(&not_empty);
}

struct item consume(void)
{
        pthread_mutex_lock(&m);
        while (count == 0)
                pthread_cond_wait(&not_empty, &m);
        struct item it = buf[tail];
        tail = (tail + 1) % N;
        count--;
        pthread_mutex_unlock(&m);
        pthread_cond_signal(&not_full);
        return it;
}

/* TWO condition variables, not one. With a single cv and
   broadcast, a producer can wake another producer, which finds
   the buffer still full and sleeps again — wasted wake-ups, and
   in the signal (non-broadcast) case, a lost wake-up that hangs
   the system.                                                 */

Readers–writers

Allowing concurrent readers but exclusive writers raises a fairness question the simple implementation answers badly — writers can be starved indefinitely.

Three policies, and the trade-off is unavoidable:

  READER PREFERENCE    a new reader may enter while others read
                       → maximum read throughput
                       → WRITERS CAN STARVE indefinitely

  WRITER PREFERENCE    a waiting writer blocks new readers
                       → writers always progress
                       → readers can starve under heavy writing

  FAIR (queued)        requests served in arrival order
                       → nobody starves
                       → lower throughput than reader preference

  glibc's pthread_rwlock defaults to reader preference; the
  PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP attribute changes it.
  Knowing which you have matters: a monitoring thread reading a
  structure in a tight loop can permanently block the writer.

Dining philosophers

The classic illustration of deadlock, and worth working through because the several distinct solutions map exactly onto the prevention strategies above.

   Five philosophers, five forks, each needs both neighbours' forks.

        P0
     F4    F0
   P4        P1
     F3    F1
        P2  F2  P3

  Naive: everyone picks up their LEFT fork, then their RIGHT.
  If all five do it simultaneously, each holds one fork and waits
  forever. All four Coffman conditions, in five lines of code.

  SOLUTIONS, each attacking a different condition:

  1. RESOURCE ORDERING     number the forks; always take the
                           lower-numbered one first.
                           → breaks circular wait. THE standard fix.

  2. LIMIT CONCURRENCY     a semaphore allowing only 4 diners at once.
                           → at least one can always get both forks;
                             breaks hold-and-wait in effect.

  3. ASYMMETRY             odd philosophers take left first,
                           even take right first.
                           → breaks the cycle. Same idea as (1).

  4. ATOMIC ACQUISITION    take both forks or neither, under a
                           global lock.
                           → breaks hold-and-wait. Simple, but
                             serialises everything.

  The point of the problem: it is the minimal example of resource
  ordering, and (1) is what you will actually use.

ABBA deadlock across layers

The most common deadlock in real code: two locks taken in different orders by different threads. It is trivially avoidable by convention and detected automatically by tooling.

/* The dangerous version in real systems: the cycle spans two
   subsystems, and neither author can see the other's order.  */

/* Path A: filesystem operation */
lock(inode->i_mutex);
        lock(page->lock);        /* fs → mm */

/* Path B: memory reclaim */
lock(page->lock);
        lock(inode->i_mutex);    /* mm → fs */

/* Neither file's code looks wrong in isolation. This is why:
     · lock ordering must be documented GLOBALLY, not per-module
     · callbacks are dangerous: calling unknown code while holding
       a lock lets the callee acquire locks you did not expect
     · lockdep finds these, and almost nothing else does      */

/* The general rule: NEVER call into another subsystem, or into a
   caller-supplied callback, while holding a lock.            */

Priority inversion, again

Covered in chapter 06, but it belongs in the deadlock family: a high-priority thread is blocked indefinitely, not by a cycle but by a scheduling interaction. The fix — priority inheritance — is a property of the lock, which is why an RTOS mutex differs from a plain one, and why PTHREAD_PRIO_INHERIT exists.

Avoiding locks entirely

Data structures that avoid locks entirely cannot deadlock, which is a strong guarantee bought at a steep price in difficulty. The trade is worth making far less often than it is attempted.

GuaranteeMeaning
BlockingA suspended thread can block others indefinitely
Obstruction-freeA thread running alone completes
Lock-freeSome thread always makes progress — no deadlock possible
Wait-freeEvery thread completes in bounded steps — the strongest, and rarest
 
/* A lock-free stack push */
void push(struct node *n)
{
        struct node *old;
        do {
                old = atomic_load(&head);
                n->next = old;
        } while (!atomic_compare_exchange_weak(&head, &old, n));
}

/* Pop is much harder — the ABA problem: between reading head and
   the CAS, another thread could pop A, pop B, and push A back.
   Your CAS succeeds because the pointer matches, but the list
   behind it is now wrong.

   Solutions: tagged pointers (a counter in the unused bits),
   hazard pointers, epoch-based reclamation, or RCU.

   The lesson: lock-free code is genuinely hard and easy to get
   subtly wrong. Use a reviewed library, or RCU, unless you have
   measured that lock contention is the actual bottleneck.   */

Debugging a hang

A deadlocked system is not crashed — it is stopped, which means the evidence is all still there. Extracting it is a matter of knowing which commands show what each thread is waiting on.

# 1. Is it deadlock or livelock? Look at CPU usage.
top -H -p PID          # 0% = deadlock;  100% = livelock or spin

# 2. Get every thread's stack. This usually answers it outright.
gdb -p PID -batch -ex 'thread apply all bt'
eu-stack -p PID
py-spy dump --pid PID              # Python
jstack PID                          # Java — reports deadlocks directly

# 3. What is each thread waiting on?
cat /proc/PID/task/*/stack          # kernel side
cat /proc/PID/task/*/wchan
ls -l /proc/PID/task/*/status | head

# 4. Reproduce it deliberately
valgrind --tool=helgrind ./prog     # lock order violations
gcc -fsanitize=thread               # races and some lock issues

# 5. Kernel
dmesg | grep -A40 'possible circular locking dependency'
# lockdep prints the exact two acquisition orders and the stacks
# that established them. It is nearly always sufficient.
The first command to run on any hang

thread apply all bt. Two threads blocked in pthread_mutex_lock on different mutexes, each holding the other's, is unmistakable in the output. Most hangs are diagnosed in under a minute by that one command — before reaching for any specialised tool.
