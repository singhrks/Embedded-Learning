Graphs: union-find

A structure that tracks "are these two things in the same group?" while groups keep merging. Thirty lines of code, effectively constant time, and the right answer whenever connectivity arrives incrementally.

The pattern

Union-find answers "are these two things in the same group" under merging, and does it in effectively constant time. The structure is about twenty lines; the two optimisations are what make the complexity claim true.

   DISJOINT SET UNION (DSU). Each group is a tree; the root
   identifies the group.

     find(x)      which group is x in?  (returns the root)
     union(a, b)  merge the two groups
     connected(a, b)  find(a) === find(b)

   NAIVE VERSION: parent[] pointers, find walks to the root.
   Without optimisation the trees degenerate into chains and
   find becomes O(n).

   TWO OPTIMISATIONS MAKE IT NEARLY O(1). Use BOTH.

   1. PATH COMPRESSION — flatten as you search
        function find(x) {
            while (parent[x] !== x) {
                parent[x] = parent[parent[x]];  // point at
                x = parent[x];                  // grandparent
            }
            return x;
        }
      Every node on the path ends up much closer to the root.

   2. UNION BY SIZE (or rank) — attach the SMALLER tree to
      the LARGER, so depth grows slowly.
        if (size[ra] < size[rb]) swap(ra, rb);
        parent[rb] = ra;
        size[ra] += size[rb];

   TOGETHER: O(α(n)) amortised per operation, where α is the
   inverse Ackermann function. α(n) < 5 for any n you will
   ever see, so treat it as constant — but say "amortised
   near-constant", not "O(1)".

   ---------------------------------------------------------
   WHEN UNION-FIND BEATS DFS

     DFS/BFS need the WHOLE graph before they can answer.
     Union-find answers connectivity queries INCREMENTALLY,
     as edges arrive, and supports interleaved queries.

     use DFS        one static graph, need paths or order
     use UNION-FIND edges arriving over time, only need
                    "same group?", or you need a component
                    COUNT that updates as you merge

   ---------------------------------------------------------
   THE COMPONENT-COUNT TRICK

     Start with count = n (every node its own group).
     DECREMENT ONLY WHEN A UNION ACTUALLY MERGES:

       function union(a, b) {
           const ra = find(a), rb = find(b);
           if (ra === rb) return false;   // ALREADY together
           ...attach...
           count--;
           return true;                    // a real merge
       }

     THE BOOLEAN RETURN IS THE USEFUL PART. `false` means the
     edge closed a CYCLE — which is how you detect cycles in
     an undirected graph, and how Kruskal rejects edges
     (chapter 34).

When to reach for it

Connected components, incrementally

Number of provinces, friend circles, accounts merge.

Cycle detection, undirected

An edge whose endpoints already share a root closes a cycle.

"Is this a valid tree?"

Exactly n−1 edges, no cycle, one component.

Kruskal's MST

Sort edges, add any that merges two groups (ch. 34).

Redundant connection

The first edge that fails to merge is the answer.

Equations / equivalence classes

Group things declared equal, then test the inequalities.

Problems

How it shows up

SymptomCause
Operations degrade to O(n)No path compression, or no union by size
Component count too lowDecremented on every union, not only on real merges
Cycle never detectedIgnored the find(a) === find(b) case
Union attaches roots to non-rootsMust call find on both before attaching
Wrong groups after many unionsCompared parent[a] === parent[b] instead of roots
Stack overflow in findRecursive compression on a deep chain — use the iterative form
Cannot recover the actual pathUnion-find tracks membership only — use DFS if you need paths
