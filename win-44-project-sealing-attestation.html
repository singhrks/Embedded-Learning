Project: layer 4 — sealing, the secure kernel and attestation

The key so far dies with the process. This chapter makes it survive a reboot without ever becoming readable: the enclave asks securekernel.exe to seal it, VTL1 ring 0 does the work against a platform-rooted secret, and the resulting blob is stored on ordinary disk where anybody may read it and nobody may use it. Then the whole stack is run end to end and attacked.

What the fourth layer actually is

In the OP-TEE project layer 4 was a driver you wrote. Here it is code you cannot write, and the interesting question becomes what you are allowed to ask it for — which turns out to be a more useful question anyway.

   THE CALL:  EnclaveSealData(...)          VTL1, ring 3
                     │                       your enclave
                     ▼
              securekernel.exe               VTL1, ring 0
                     │  derives a key from:
                     │    · a platform secret, rooted in the
                     │      TPM and established at boot
                     │    · the IDENTITY of the caller, per
                     │      the policy you pass in
                     ▼
              an opaque blob, handed back to you

   YOU NEVER SEE THE SEALING KEY. You cannot ask for it, and
   there is no API that returns it. The only thing you can do
   with it is seal and unseal - which is the same arrangement
   as an OP-TEE TA and its HUK-derived storage key.

   WHY THIS IS A REAL LAYER AND NOT A LIBRARY CALL:

     the work happens at a HIGHER PRIVILEGE than the caller,
     using a secret the caller cannot reach, against hardware
     the caller cannot address.

   That sentence is also the definition of layer 4 in the
   OP-TEE project. The mechanism is completely different; the
   structure is identical.

The sealing policy is the interesting parameter

Sealing binds a blob to an identity, and you choose how tightly. This single argument decides whether your next build can still read yesterday's key — which is a product decision disguised as an enum.

PolicyCan unsealCosts you
Exact codeOnly a byte-identical enclave imageEvery rebuild, including a one-character fix, loses the key
Same imageAny version of the same enclave image identityA compromised later version can read earlier secrets
Same familyAny enclave in the declared familyYou must actually control the whole family
Same authorAnything signed by the same authorThe broadest, and the easiest to regret after an acquisition or a key rotation

For a signing key the right answer is usually "same image": a rebuild must not silently destroy the user's identity, but nothing signed by an unrelated team of yours should be able to sign on its behalf. The wrong answer is to pick the loosest policy because the tight one made testing annoying, which is the decision this table exists to interrupt.

The enclave, with persistence

Three functions replace the throwaway EnsureKey from chapter 42. Note what is not here: no decision about where the file lives, and no attempt to protect it. The blob is designed to be public.

/* enclave/winsign_enclave.c - LAYER 3 calling LAYER 4 */

/* The enclave has no file access of its own. It hands the
   sealed blob out to the host, which stores it - and that
   is fine, because a sealed blob is not a secret.        */

static NTSTATUS SealKey(unsigned char *blobOut, ULONG cap,
                        ULONG *blobLen)
{
    unsigned char raw[256];
    ULONG rawLen = 0;
    NTSTATUS status;

    /* Export the private key INSIDE the enclave. This is the
       only moment it exists in a buffer, and it is in
       enclave memory the whole time.                      */
    status = BCryptExportKey(g_key, NULL,
                 BCRYPT_ECCPRIVATE_BLOB, raw, sizeof(raw),
                 &rawLen, 0);
    if (!NT_OK(status))
        return status;

    /* THE CALL INTO LAYER 4. The identity policy is the
       argument that matters; see the table above.         */
    status = EnclaveSealData(raw, rawLen,
                 ENCLAVE_IDENTITY_POLICY_SEAL_SAME_IMAGE,
                 0,                 /* runtime policy      */
                 blobOut, cap, blobLen);

    SecureZeroMemory(raw, sizeof(raw));
    return status;
}

static NTSTATUS UnsealKey(const unsigned char *blob,
                          ULONG blobLen)
{
    BCRYPT_ALG_HANDLE alg = NULL;
    unsigned char raw[256];
    ULONG rawLen = 0;
    ENCLAVE_IDENTITY id = {};
    ULONG idFlags = 0;
    NTSTATUS status;

    /* blob came from VTL0. Its LENGTH is attacker-chosen and
       its CONTENT is attacker-chosen; neither matters,
       because unsealing authenticates it. A wrong blob
       fails, it does not produce a wrong key.            */
    if (blobLen == 0 || blobLen > 4096)
        return STATUS_INVALID_PARAMETER;

    status = EnclaveUnsealData(blob, blobLen,
                 raw, sizeof(raw), &rawLen,
                 &id, &idFlags);
    if (!NT_OK(status))
        return status;

    status = BCryptOpenAlgorithmProvider(&alg,
                 BCRYPT_ECDSA_P256_ALGORITHM, NULL, 0);
    if (NT_OK(status)) {
        status = BCryptImportKeyPair(alg, NULL,
                     BCRYPT_ECCPRIVATE_BLOB, &g_key,
                     raw, rawLen, 0);
        BCryptCloseAlgorithmProvider(alg, 0);
    }

    SecureZeroMemory(raw, sizeof(raw));
    return status;
}

/* Replaces EnsureKey. The host passes in whatever blob it
   found on disk, or nothing on the very first run.       */
static NTSTATUS LoadOrCreateKey(const unsigned char *blob,
                                ULONG blobLen,
                                unsigned char *newBlob,
                                ULONG cap, ULONG *newLen)
{
    NTSTATUS status;

    *newLen = 0;
    if (g_key != NULL)
        return 0;

    if (blob != NULL && blobLen > 0) {
        status = UnsealKey(blob, blobLen);
        if (NT_OK(status))
            return 0;
        /* Deliberately NOT falling through to "generate a
           new one" on failure. A blob that will not unseal
           means something changed - a rebuild under an
           exact-code policy, a different machine, or
           tampering. Silently minting a new identity would
           turn all three into a confusing non-event.     */
        return status;
    }

    status = GenerateKey();     /* the generate half of
                                   chapter 42's EnsureKey */
    if (!NT_OK(status))
        return status;

    return SealKey(newBlob, cap, newLen);
}
Why refusing to regenerate is the right behaviour

Falling back to generating a fresh key when unsealing fails makes the first run and the compromised run look identical, and it makes a failed upgrade look like a successful one. Every signature made afterwards verifies against a public key nobody expected, and the failure surfaces days later as "verification stopped working" with no trace of when. Failing loudly at the point of unsealing costs one confusing error message the first time you rebuild, and saves the investigation.

Attestation: proving it to someone else

Sealing convinces you. A report signed by the platform is what convinces a server on the other side of a network that the public key it is about to trust really came from an enclave, on a machine with VBS actually running, rather than from a convincing program on a laptop.

/* Ask layer 4 for a report over data of our choosing. The
   report binds that data to the enclave's identity and the
   platform's state.                                       */
static NTSTATUS MakeAttestation(const unsigned char *pubkey,
                                ULONG pubLen,
                                unsigned char *report,
                                ULONG cap, ULONG *reportLen)
{
    /* BIND THE PUBLIC KEY INTO THE REPORT. A report over
       nothing proves only that some enclave exists; a report
       over this key proves THIS enclave holds it. That
       binding is the entire value.                       */
    return EnclaveGetAttestationReport(pubkey,
               report, cap, reportLen);
}

/* On the RELYING PARTY - a server, or a provisioning tool -
   the report is checked before the key is trusted:

     EnclaveVerifyAttestationReport(ENCLAVE_TYPE_VBS,
                                    report, reportLen);

   and then the caller must STILL check the identity in the
   report is the enclave it expected. Verifying the signature
   only proves SOME enclave produced it - including an
   attacker's own, on their own machine. Checking the image
   identity is the step people forget, and it is the step
   that does the work.                                    */

Running the whole thing

Every piece from chapters 40 to 43, started in dependency order. The first run generates and seals; every run afterwards unseals, and the difference between those two paths is visible in one command.

# 1. The driver (installed in chapter 41):
sc query winsign

# 2. The host. It creates the enclave, loads any blob it
#    finds, and registers with the driver:
winsignhost.exe
# first run:
#   no sealed key found - generating
#   sealed 121 bytes to C:\ProgramData\winsign\key.blob
# later runs:
#   unsealed key from C:\ProgramData\winsign\key.blob

# 3. The application, unchanged since chapter 41:
winsign pubkey
04a3f1...        <- 64 hex bytes

winsign sign C:\test.txt
wrote C:\test.txt.sig (64 bytes)

# 4. THE TEST THAT PROVES LAYER 4 DID ANYTHING:
#    reboot, then ask again.
shutdown /r /t 0
winsign pubkey
04a3f1...        <- THE SAME KEY

#    Before this chapter it was different every run. That
#    one line of identical output is the whole of layer 4.

Verifying from outside

A signature only this stack can check proves nothing at all. This verifies it with tooling that knows nothing about enclaves, drivers or VBS.

# tools/verify.ps1
param([string]$File, [string]$Sig, [string]$PubHex)

# The app prints x||y; rebuild a standard public key object.
$pub  = [byte[]] -split ($PubHex -replace '..', '$& ')
$ec   = [System.Security.Cryptography.ECDsa]::Create()
$parm = [System.Security.Cryptography.ECParameters]::new()
$parm.Curve = [System.Security.Cryptography.ECCurve]::
              CreateFromFriendlyName('nistP256')
$parm.Q.X = $pub[0..31]
$parm.Q.Y = $pub[32..63]
$ec.ImportParameters($parm)

$data = [IO.File]::ReadAllBytes($File)
$sg   = [IO.File]::ReadAllBytes($Sig)

# BCryptSignHash emits r||s, which is exactly the format
# .NET calls IeeeP1363 - no DER conversion needed here,
# unlike the OpenSSL path in the OP-TEE project.
$ok = $ec.VerifyData($data, $sg,
        [System.Security.Cryptography.HashAlgorithmName]::SHA256,
        [System.Security.Cryptography.DSASignatureFormat]::
          IeeeP1363FixedFieldConcatenation)

if ($ok) { "Verified OK" } else { "VERIFICATION FAILED" }

Attacking it

These are the tests that decide whether the four layers are a security design or an elaborate way to call BCrypt. Write them before you believe the result — and expect test 4 to be the uncomfortable one.

# 1. Can an unprivileged user sign?
C:\> winsign sign test.txt
winsign: CreateFile 5                    (ACCESS_DENIED)
#    Blocked by the interface SDDL. POLICY only - an
#    administrator defeats it, by design.

# 2. Can an administrator read the key out of the host?
C:\> procdump -ma winsignhost.exe dump.dmp
C:\> strings dump.dmp | findstr /i <key bytes>
#    Nothing. The enclave range is not in the dump at all -
#    the kernel cannot read it either, so it cannot write
#    it out. THIS IS THE TEST THE WHOLE PROJECT EXISTS FOR.

# 3. Is the sealed blob useful on another machine?
C:\> copy key.blob \\other\C$\ProgramData\winsign\
#    On the other machine:
#    EnclaveUnsealData failed 0xc000000d
#    Rooted in THIS platform. Copying it achieves nothing.

# 4. Can a debugger read the key?
C:\> windbg -p <winsignhost pid>
0:000> dq <enclave base>
#    ??????????  - unreadable, on a NON-DEBUG enclave.
#    NOW REBUILD WITH ENCLAVE_VBS_FLAG_DEBUG AND REPEAT.
#    The key is right there. Do this once, deliberately,
#    so you never ship a debug enclave by accident.

# 5. Can a second host steal requests?
C:\> winsignhost.exe        (while one is already running)
register: 1010 - another host already running?
#    One host. A second could answer requests it never
#    received, with signatures over data of its choosing.

# 6. Can a hostile host forge a result for another client?
C:\> evilhost --answer-id 999 --sig 00000...
#    Dropped: STATUS_NOT_FOUND. The driver matches on the
#    id IT assigned. Remove that check and this succeeds -
#    which is why the id is in the contract.

# 7. Does an over-long input get refused at every layer?
C:\> fsutil file createnew big.bin 2000000
C:\> winsign sign big.bin
input must be 1..1048576 bytes
#    Layer 1 refuses. Remove that and confirm layer 2
#    refuses. Remove THAT and confirm the enclave refuses.
#    Defence in depth is only real if each layer
#    independently says no.

# IF TEST 2 OR TEST 3 SUCCEEDS, STOP. The design does not
# do what this chapter claims.
Test 2 is the one to run first, and the one to re-run after every change

It is the only test that directly demonstrates the property the entire four-layer structure exists to provide: an administrator, with a full memory dump of the very process hosting the key, cannot find it. Every other test checks a policy, a contract or a convenience. If a refactor ever makes test 2 fail — a key accidentally copied into a VTL0 buffer to be logged, an export added for debugging, a debug-flagged build shipped — the stack still works perfectly and has stopped being worth anything.

How it shows up

SymptomCause
EnclaveSealData fails with invalid parameterAn identity policy the enclave's own identity cannot satisfy, or an output buffer too small
Unsealing fails after every rebuildExact-code policy, working as documented — choose same-image if that is wrong for you
Unsealing fails after a Windows feature updateThe platform identity changed; plan a rewrap path before shipping
The public key changes silently one dayA regenerate-on-failure fallback somebody added back in
Verification fails with a correct-looking signatureSignature format — r||s being handed to a DER-expecting verifier
Attestation verifies but the identity is wrongThe relying party checked the signature and not the identity — the common and serious mistake
The blob is readable by everyoneExpected. It is designed to be public; if that feels wrong, re-read what sealing does
Test 2 finds the key in a dumpThe key reached a VTL0 buffer somewhere, or the enclave is a debug build
