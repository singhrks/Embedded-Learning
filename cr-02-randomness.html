Randomness and entropy

Every key, nonce, IV and salt depends on unpredictable numbers, and on an embedded device at first boot there is almost nothing unpredictable available. This is the most common single cause of real cryptographic failure in shipped products.

Three kinds of random

"Random" means three quite different things in computing, and only one of them is safe for keys. Using the wrong one is among the most common and most catastrophic crypto failures, because the result looks perfectly random in testing.

   PRNG          deterministic from a seed. Fast, repeatable,
   (non-crypto)  and PREDICTABLE. rand(), Mersenne Twister,
                 xorshift, LCG.
                 -> simulations, games, test data.
                 -> NEVER for anything security-relevant.

   CSPRNG        deterministic from a seed, but
                 computationally infeasible to predict
                 without it. ChaCha20-based, HMAC-DRBG,
                 CTR-DRBG, AES-CTR.
                 -> ALL cryptographic use.
                 -> still needs a good seed.

   TRNG          a physical entropy source: thermal noise, a
                 ring oscillator's jitter, avalanche noise,
                 radioactive decay.
                 -> seeding the CSPRNG, and nothing else -
                    they are slow, and their raw output is
                    usually biased.

   THE STANDARD ARCHITECTURE, and the one you should use:

        physical noise source (TRNG)
              |
        health tests, de-biasing (von Neumann, or a hash)
              |
        SEED (256 bits of real entropy)
              |
        CSPRNG  --> unlimited output, fast
              ^
              |
        periodic RESEEDING from the noise source

   THE CSPRNG DOES THE WORK; the TRNG only ever provides the
   seed. Reading a TRNG directly for every byte is slow and,
   because raw output is biased, often worse.

The provisioning rule

An embedded device must not generate its long-term keys at first boot. Inject them during manufacturing, from a source with real entropy — an HSM on the production line — and burn the device-unique secret into fuses (isolation chapter 10). A device that generates its own identity before it has entropy is a device whose identity is predictable, and no amount of later reseeding fixes a key that has already been created.

Entropy sources

Randomness has to come from somewhere physical. Where an operating system gets it, and what happens when it does not have enough yet, is the difference between a secure key and a predictable one.

Using a CSPRNG

A cryptographically secure generator stretches a small amount of real entropy into an unlimited stream that is computationally indistinguishable from random. The properties it must have are stricter than they first appear.

/* A ChaCha20-based CSPRNG - the modern standard construction,
   and what Linux, BSD and libsodium all use.             */

    struct Csprng {
        uint8_t key[32];
        uint64_t counter;
    };

    void csprng_seed(struct Csprng *r, const uint8_t seed[32])
    {
        memcpy(r->key, seed, 32);
        r->counter = 0;
    }

    void csprng_bytes(struct Csprng *r, uint8_t *out, size_t n)
    {
        uint8_t block[64];

        while (n) {
            chacha20_block(r->key, r->counter++, block);
            size_t take = n < 64 ? n : 64;
            memcpy(out, block, take);
            out += take; n -= take;
        }
        /* FAST KEY ERASURE: replace the key with fresh
           output, so a later compromise cannot recover
           earlier output. FORWARD SECRECY for the RNG.  */
        chacha20_block(r->key, r->counter++, block);
        memcpy(r->key, block, 32);
        secure_zero(block, sizeof block);
    }

/* THE FAST KEY ERASURE STEP is what makes this construction
   better than a plain counter mode: an attacker who reads
   the state cannot compute what you generated before.

/* THE OTHER STANDARD CONSTRUCTIONS (NIST SP 800-90A):
     HMAC-DRBG     conservative, easy to implement, slow
     CTR-DRBG      AES-CTR based; fast with an AES
                   accelerator
     Hash-DRBG
     (and Dual_EC_DRBG, which was withdrawn after evidence
      of a deliberate back door - a useful reminder that
      "standardised" is not the same as "trustworthy", and
      that public analysis is what matters)

/* RESEEDING: mix in fresh entropy periodically, and always
   after a fork, a restore from snapshot, or a VM clone -
   because all three duplicate the state, and a duplicated
   CSPRNG produces duplicated keys.                       */

Testing randomness

Statistical tests can show that a generator is bad; they can never show it is good. Understanding that asymmetry prevents a common and dangerous conclusion.

# --- STATISTICAL TEST SUITES ---
    dieharder -a -g 201 -f random.bin
    ent random.bin              # entropy, chi-square, mean
    NIST STS                    # SP 800-22
    PractRand                   # the most sensitive; catches
                                # what dieharder misses
    TestU01 BigCrush

# --- WHAT THEY CAN AND CANNOT TELL YOU ---
#   THEY DETECT: bias, short periods, correlations, stuck
#                bits, obviously broken sources
#   THEY DO NOT DETECT: a perfectly uniform but PREDICTABLE
#                sequence. AES-CTR with a key the attacker
#                knows passes every test.
#
#   SO: passing is necessary, not sufficient. It tells you
#   the source is not obviously broken; it says nothing about
#   whether it is secret.

# --- THE HEALTH TESTS THAT BELONG IN THE PRODUCT ---
    · REPETITION COUNT: fail if the same value repeats too
      often (SP 800-90B)
    · ADAPTIVE PROPORTION: fail if one value dominates a
      window
    · continuous self-test on every read from the hardware
      RNG
    · a startup test at boot, before generating anything
    · FAIL CLOSED: if the RNG fails its health test, refuse
      to operate. Do not fall back to a weaker source.

# --- ESTIMATING ENTROPY ---
#   min-entropy H∞ = -log2(max probability)
#   This is the conservative measure and the one that matters
#   for key generation - Shannon entropy overestimates when
#   the distribution is skewed.
#   A source producing 0 with probability 0.6 has 0.97 bits
#   of Shannon entropy and only 0.74 bits of min-entropy.
#   Collect enough raw bits that the CONDITIONED output has a
#   full 256 bits of min-entropy - typically several times
#   as many raw bits as you need.

# --- ON LINUX, CHECK THE POOL ---
    cat /proc/sys/kernel/random/entropy_avail
    dmesg | grep -i random
      random: crng init done      # this line is what you
                                  # need to see before
                                  # generating keys

The embedded checklist

An embedded device often has no keyboard, no disk timing and no network at first boot — precisely the sources a desktop uses for entropy. This is what to do instead, and it needs deciding at design time rather than discovering later.

QuestionRight answer
Does the part have a TRNG?Check the TRM, and check its conditions — some need a peripheral active
Where do long-term keys come from?Injected at manufacture, not generated on device
Is there a device-unique secret in fuses?There should be — it is the root of everything else
Is the RNG health-tested at boot?Yes, and it must fail closed
Is a seed persisted across reboots?Yes, in secure storage, and mixed with fresh entropy
Are GCM nonces counters or random?Counters, persisted, with key rotation on reset
Are keys wiped after use?With explicit_bzero, not memset
What happens if the RNG fails?Refuse to operate — never a weaker fallback
Is every device's key different?Yes — one compromise must not be fleet-wide
Has the source been characterised?Min-entropy measured on real hardware, across temperature and voltage
