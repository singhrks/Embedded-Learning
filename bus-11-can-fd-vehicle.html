CAN FD, and CAN in a vehicle

Classical CAN carries 8 bytes at 500 kbit/s, which was generous in 1991 and is not now. CAN FD raises both limits without giving up arbitration — and the higher-layer protocols built on top are where an embedded engineer actually works.

What CAN FD changes

   TWO CHANGES, and the first is the clever one.

   1. DUAL BIT RATE. Arbitration happens at the classical
      rate; the data phase switches to a faster one.

      |<-- arbitration -->|<--- data --->|<-- ack -->|
      |     500 kbit/s    |   2-8 Mbit/s  | 500 kbit/s|
      +-------------------+---------------+-----------+
       ID, RTR, control    DATA + CRC      ACK, EOF

      WHY THIS WORKS: the round-trip constraint (chapter 09)
      applies only while several nodes might be driving at
      once - during arbitration. Once one node has won, it
      is alone on the bus and no round trip is needed, so
      the bit time can shrink to whatever the physical layer
      supports.

      A genuinely elegant piece of protocol design: it
      removes the bandwidth limit without touching the
      property that made CAN worth using.

   2. LONGER FRAMES. Up to 64 bytes rather than 8. DLC
      values above 8 are encoded non-linearly:
        9-15 mean 12, 16, 20, 24, 32, 48, 64 bytes.
      So the jump is 8, 12, 16, 20, 24, 32, 48, 64 - you
      cannot ask for 40.

   ALSO: a stronger CRC (17 or 21 bit), and no RTR frames.

   THROUGHPUT: 8 bytes at 500 kbit/s is about 3.6 kB/s of
   payload after overhead. 64 bytes with a 2 Mbit/s data
   phase is roughly 25x that, and it means a firmware
   update over CAN goes from hours to minutes.
Classical and FD nodes cannot share a bus

A classical CAN controller sees an FD frame's control bits as a form error and transmits an error frame, destroying it — so one legacy node makes FD traffic impossible. Some transceivers and controllers support "CAN FD tolerant" mode, where classical nodes ignore FD frames instead of objecting, but this must be supported by every node on the bus. In practice a vehicle migrates one whole bus segment at a time, with a gateway translating between them.

The higher-layer protocols

   Raw CAN gives you 8 (or 64) bytes with an identifier.
   Everything else is a protocol on top, and you will
   almost always be implementing one of these:

   ISO-TP (ISO 15765-2) - TRANSPORT
     Segments messages longer than one frame, up to 4095
     bytes, with flow control. The foundation of diagnostics.

       SINGLE FRAME    [0x0n][ up to 7 bytes ]
       FIRST FRAME     [0x1L][LL][ 6 bytes ]
       FLOW CONTROL    [0x30][BS][STmin]     <- receiver
       CONSECUTIVE     [0x2n][ 7 bytes ]        controls
                                                the rate

     The receiver dictates block size and minimum separation
     time, so a slow ECU can throttle a fast tester. This is
     the piece people re-implement badly; use a library.

   UDS (ISO 14229) - DIAGNOSTICS
     Request/response services over ISO-TP. Read fault
     codes, read data by identifier, flash firmware, run
     routines. Service 0x22 (ReadDataByIdentifier) and 0x2E
     (WriteDataByIdentifier) are most of what a tool does.

   J1939 - HEAVY VEHICLES
     29-bit IDs carrying structured meaning: priority,
     PGN (parameter group number), source address. Standard
     PGNs mean engine speed is the same message on every
     truck, regardless of manufacturer.

   CANopen - INDUSTRIAL
     Object dictionary, PDOs for real-time data, SDOs for
     configuration, standard device profiles. Common in
     motion control and industrial automation.

   AUTOSAR - AUTOMOTIVE SOFTWARE ARCHITECTURE
     Not a CAN protocol as such, but the framework most
     automotive ECU software is written inside, with CAN as
     one of its communication stacks.

ISO-TP, because you will meet it

/* Receiving a multi-frame message. The state machine is
   small; the timeouts are what make it correct.           */

typedef enum { TP_IDLE, TP_RECEIVING } tp_state_t;

typedef struct {
    tp_state_t state;
    uint8_t    buf[4095];
    uint16_t   expected, received;
    uint8_t    next_sn;          /* sequence number 0-15   */
    uint32_t   last_frame_ms;
} tp_rx_t;

void tp_on_frame(tp_rx_t *tp, const uint8_t *d, uint8_t len)
{
    uint8_t type = d[0] >> 4;

    switch (type) {
    case 0x0:                                  /* SINGLE   */
        deliver(&d[1], d[0] & 0x0F);
        tp->state = TP_IDLE;
        break;

    case 0x1:                                  /* FIRST    */
        tp->expected = (uint16_t)(((d[0] & 0x0F) << 8) | d[1]);
        if (tp->expected > sizeof(tp->buf)) {
            tp_send_fc_overflow();             /* refuse    */
            return;
        }
        memcpy(tp->buf, &d[2], 6);
        tp->received = 6;
        tp->next_sn  = 1;
        tp->state    = TP_RECEIVING;
        tp->last_frame_ms = g_ms;
        tp_send_flow_control(0 /* BS: unlimited */, 0 /* STmin */);
        break;

    case 0x2: {                                /* CONSEC   */
        if (tp->state != TP_RECEIVING) { return; }  /* stray */

        uint8_t sn = d[0] & 0x0F;
        if (sn != tp->next_sn) {
            /* A frame was LOST. The sequence number exists
               precisely to detect this; abort rather than
               deliver a message with a hole in it.        */
            stats.tp_sequence_errors++;
            tp->state = TP_IDLE;
            return;
        }
        tp->next_sn = (uint8_t)((sn + 1u) & 0x0F);

        uint16_t n = tp->expected - tp->received;
        if (n > 7) { n = 7; }
        memcpy(&tp->buf[tp->received], &d[1], n);
        tp->received += n;
        tp->last_frame_ms = g_ms;

        if (tp->received >= tp->expected) {
            deliver(tp->buf, tp->expected);
            tp->state = TP_IDLE;
        }
        break;
    }
    default:
        break;
    }
}

/* THE TIMEOUT IS NOT OPTIONAL. If the sender dies mid
   message, this state machine waits forever holding a 4 kB
   buffer. ISO 15765-2 specifies N_Cr = 1000 ms between
   consecutive frames.                                     */
void tp_poll(tp_rx_t *tp)
{
    if (tp->state == TP_RECEIVING &&
        (int32_t)(g_ms - tp->last_frame_ms - 1000) >= 0) {
        stats.tp_timeouts++;
        tp->state = TP_IDLE;
    }
}

What a vehicle bus actually looks like

   A car has SEVERAL buses, segregated by criticality, with
   a gateway between them.

   +----------------------------------------------------+
   |                     GATEWAY ECU                     |
   +--+--------------+--------------+-------------+-----+
      |              |              |             |
   POWERTRAIN     CHASSIS         BODY         DIAGNOSTIC
   500 kbit/s     500 kbit/s      125 kbit/s   OBD-II port
   or CAN FD                      or LIN
      |              |              |
   engine ECU     ABS            doors, lights
   transmission   steering       climate, seats
                  airbag

   WHY SEGREGATED:
     - a fault on the body bus must not affect braking
     - bandwidth: the powertrain bus carries 10 ms cyclic
       messages; the body bus can be far slower and cheaper
     - SECURITY: the OBD-II port is physically accessible
       to anyone, so the gateway is a firewall. The famous
       2015 Jeep Cherokee remote attack pivoted from the
       infotainment system onto the CAN bus - after which
       the protocol offers no defence at all, because CAN
       has NO AUTHENTICATION WHATSOEVER.

   THIS IS THE SECURITY REALITY OF CAN: any node can
   transmit any identifier. There is no source
   authentication, no encryption, and no way for a receiver
   to know a frame is genuine. Security must come from:
     - segmentation and a gateway that filters
     - SecOC (AUTOSAR Secure Onboard Communication), which
       adds a truncated MAC and a freshness counter to
       critical messages
     - physical access control

   If you are designing a CAN system today and it carries
   anything that matters, assume the bus is hostile and
   authenticate at the application layer. The cryptography
   track's MAC chapter is directly relevant.
