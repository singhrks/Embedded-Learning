Defensive C: MISRA, assertions and static analysis

C gives you no safety net, so the profession built one out of process: coding standards, static analysis, assertions and review discipline. This chapter is what actually works in production, and what is theatre.

Defence in depth

No single technique makes C safe. What works is a series of independent layers, each catching what the previous one missed — and the cost of adding them is almost entirely at the start of a project rather than throughout it.

Each layer catches what the one before it missed. Cost rises,
and so does the cost of the bugs each one prevents.

  1. LANGUAGE DISCIPLINE     free       consistent idioms, small
                                        functions, clear ownership
  2. COMPILER WARNINGS       free       -Wall -Wextra -Werror
  3. STATIC ANALYSIS         cheap      -fanalyzer, clang-tidy,
                                        cppcheck, commercial tools
  4. CODING STANDARD         process    MISRA, CERT C, kernel style
  5. ASSERTIONS              cheap      invariants checked at runtime
  6. SANITIZERS              CI time    ASan, UBSan, TSan, MSan
  7. UNIT + PROPERTY TESTS   effort     including fuzzing
  8. CODE REVIEW             effort     the only layer that catches
                                        DESIGN errors
  9. FORMAL METHODS          expensive  Frama-C, CBMC — for the code
                                        that must not fail

Most teams do 1, 2 and 8, and skip 3, 5 and 6 — which is precisely
where the cheapest wins are.

Warnings are the cheapest layer

The compiler already knows about a large fraction of the bugs in your code and says nothing unless asked. This is the set worth enabling, and the argument for treating them as errors rather than suggestions.

# the baseline every C project should have
-Wall -Wextra -Wpedantic -Werror

# and the ones -Wall does not include but should
-Wshadow                  # a local hiding an outer name
-Wconversion              # implicit narrowing
-Wsign-conversion
-Wcast-align              # casting to a stricter alignment
-Wcast-qual               # casting away const
-Wpointer-arith
-Wstrict-prototypes       # int f() with no parameter list
-Wmissing-prototypes      # a non-static function with no prototype
-Wold-style-definition
-Wredundant-decls
-Wwrite-strings           # string literals become const char[]
-Wnull-dereference
-Wdouble-promotion        # accidental float->double on an MCU
-Wformat=2 -Wformat-security
-Wvla                     # variable-length arrays (chapter 05)
-Wswitch-enum             # a switch missing an enum value

# Treat warnings as errors in CI from day one. A codebase with
# 400 warnings has zero warnings, because nobody reads them.
Adopting -Werror on an existing codebase

Do not try to fix everything at once. Enable -Werror only for new files, or use -Werror= for individual warnings you have already cleaned (-Werror=return-type -Werror=implicit-function-declaration). Ratchet forward: every warning you clear becomes an error so it can never come back. This converts an impossible cleanup into a steady one.

Static analysis

Static analysers reason about paths through your code that testing may never take, which is how they find errors that only occur on a rare combination of conditions. They differ substantially in what they catch.

gcc -fanalyzer -Wall -Wextra -c src/*.c
scan-build make
clang-tidy src/*.c -- -Iinclude
cppcheck --enable=all --inconclusive --std=c11 src/

# kernel
make C=1 CHECK=sparse
make C=2 CF=-D__CHECK_ENDIAN__

# with a NARROW comment and a REASON, and never with a blanket

MISRA C

A coding standard for safety-related systems, originating in automotive and now used in medical, industrial and aerospace work. MISRA C:2012 has roughly 175 rules and directives, classified as mandatory, required or advisory.

Representative ruleRationale
No dynamic memory (21.3)Fragmentation and non-determinism (ch. 14)
No recursion (17.2)Stack usage cannot be bounded statically
No goto (15.1, advisory)Control-flow analysability
Single exit per function (15.5, advisory)Simplifies reasoning; widely disputed
Every if/else if chain ends in else (15.7)Forces you to consider the default case
Every switch has a default (16.4)Same
All bodies are compound statements (15.6)Prevents the dangling-else and "goto fail" class
No implicit conversions that change signedness or width (10.x)The bug class in chapter 02
Function return values must be used or explicitly discarded (17.7)Ignored error codes
No #undef, restricted #include forms (20.x)Preprocessor predictability
An honest assessment

MISRA's genuinely valuable rules are the ones about implicit conversion, uninitialised data, unused return values and undefined behaviour — they encode real bug classes. The controversial ones (single exit, no goto) can make error handling worse in C, since the goto cleanup ladder (ch. 14) is the clearest way to release resources in reverse order.

MISRA is a deviation-based process: you are expected to violate rules where justified, and to document why. A team that treats it as an absolute prohibition ends up writing worse code to satisfy a checker. If you are not in a certified domain, adopt the conversion and initialisation rules and skip the structural dogma.

CERT C is the security-focused alternative, organised by vulnerability class rather than by language feature, and is generally a better fit for non-certified projects.

Assertions that earn their place

An assertion turns an assumption into a check. The decisions worth making deliberately are which assumptions to check, and whether the check should survive into the shipped build.

/* The distinction that matters: */
assert(...)      /* PROGRAMMER error — an invariant that must hold
                    if this code is correct. May be compiled out.  */
if (...) return -EINVAL;
                 /* EXTERNAL error — bad input, missing hardware,
                    resource exhaustion. Must ALWAYS be handled.   */

/* Assert on: */
assert(index < ARRAY_SIZE(table));     /* internal index          */
assert(state == STATE_READY);          /* state machine invariant */
assert(mutex_is_held(&lock));          /* locking discipline      */
assert(p != NULL);                     /* internal contract       */

/* Never assert on: user input, file contents, network data,
   hardware responses, or malloc results.                       */
/* In production embedded systems, assert() calling abort() is often
   wrong — you cannot just stop a motor controller. Define your own: */

#ifdef NDEBUG
#  define ASSERT(c) ((void)0)
#else
#  define ASSERT(c) ((c) ? (void)0 : assert_failed(__FILE__, __LINE__))
#endif

void assert_failed(const char *file, int line)
{
        enter_safe_state();            /* outputs off, brakes on   */
        log_persistent(file, line);    /* survive the reset        */
        system_reset();                /* recover, do not hang     */
}

/* The kernel's spectrum, and when to use each: */
BUILD_BUG_ON(cond);      /* compile time — always prefer this      */
WARN_ON(cond);           /* log a stack trace and CONTINUE — the
                            default choice for a recoverable
                            invariant violation                    */
WARN_ON_ONCE(cond);      /* ...but do not spam the log             */
BUG_ON(cond);            /* panic. Reserve for "continuing would
                            corrupt data". Rarely justified.       */

Design by contract

Stating what a function requires and guarantees — in comments, in assertions or in attributes — is what lets both humans and tools catch a caller that violates it.

/**
 * ring_write() - append bytes to the ring buffer
 * @r:    ring buffer, must be non-NULL and initialised
 * @data: source buffer, must be non-NULL if @len > 0
 * @len:  number of bytes, must be <= ring_space(r)
 *
 * Context: caller must hold r->lock.
 * Return: number of bytes written, or a negative errno.
 */
ssize_t ring_write(struct ring *r, const void *data, size_t len)
{
        ASSERT(r != NULL);
        ASSERT(data != NULL || len == 0);
        ASSERT(lockdep_held(&r->lock));
        ...
}

/* Write the precondition, then assert it. The comment documents;
   the assertion enforces. Either alone is half a contract.     */

/* Let the compiler help where it can: */
void f(int *p) __attribute__((nonnull(1)));
int  g(void)   __attribute__((warn_unused_result));

/* warn_unused_result is enormously valuable on anything that can
   fail. Ignored return values are a top-tier bug source.       */

Defensive patterns

Some ways of writing C are simply harder to get wrong than others. These are the habits that eliminate whole categories of bug structurally, rather than by being careful.

/* Validate at the trust boundary, once, thoroughly. Do not
   re-validate everywhere internally — that hides which layer owns
   the check and produces inconsistent behaviour.              */

int api_entry(const struct request *req)
{
        /* THE boundary: everything after this point may assume
           the request is well-formed.                          */
        if (!req)                       return -EINVAL;
        if (req->len > MAX_LEN)         return -EMSGSIZE;
        if (req->type >= TYPE_COUNT)    return -EINVAL;
        if (req->len > 0 && !req->data) return -EINVAL;

        return handle(req);             /* internal: asserts only */
}

/* Initialise everything at declaration */
struct config cfg = {0};      /* not: struct config cfg; */
int  ret = -EINVAL;
char *buf = NULL;

/* Const everything you do not modify — it is free documentation
   that the compiler checks.                                    */
static int compute(const struct input *in, struct output *out);

/* Fail closed, not open */
switch (mode) {
case MODE_A: return handle_a();
case MODE_B: return handle_b();
default:     return -EINVAL;      /* not: fall through to A */
}

/* Bound every loop that waits on hardware */
int timeout = 10000;
while (!(readl(base + STATUS) & READY))
        if (--timeout < 0)
                return -ETIMEDOUT;

/* Make illegal states unrepresentable where you can */
typedef struct { int v; } celsius_t;    /* not interchangeable with */
typedef struct { int v; } fahrenheit_t; /* an int, or each other    */

Testing C

Testing C has its own difficulties — no reflection, no easy mocking, and failures that corrupt the test harness itself. These are the approaches that work in practice.

# unit test frameworks that work well in C
#   Unity + CMock  — designed for embedded, no dynamic allocation
#   Check, cmocka, greatest, µnit
#   Criterion      — modern, nice output

# run everything under sanitizers in CI
gcc -fsanitize=address,undefined -g -O1 test.c -o test && ./test

# coverage — measure what the tests actually reach
gcc --coverage test.c && ./test && gcov test.c
lcov --capture --directory . --output-file cov.info
genhtml cov.info --output-directory out
# Aim for branch coverage on error paths specifically. Error paths
# are where the untested bugs live, by definition.

# FUZZING is the highest-value testing for any C code that parses
# input. It routinely finds bugs that unit tests never will.
clang -fsanitize=fuzzer,address parser_fuzz.c -o fuzz
./fuzz corpus/ -max_total_time=600
/* A libFuzzer harness is four lines. There is no excuse not to
   have one for every parser you write.                        */
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)
{
        struct msg m;
        parse_message(data, size, &m);    /* must never crash */
        return 0;
}

What review is for

Tools find defects; review finds wrong designs. Focus review on what no tool can check:

  • Is the ownership of every allocation clear and documented?
  • Is every error path correct, and does it release what it acquired?
  • Are the locking rules stated, and does this code follow them?
  • What happens on the second call? On a concurrent call? On failure halfway through?
  • Is the trust boundary explicit, and is validation on the right side of it?
  • Are the integer types right, and can any arithmetic overflow?
  • Does the API make misuse difficult, or merely document it?
  • Will this be understandable in two years by someone who was not in this conversation?
