The memory manager: VADs, working sets and page faults

Chapter 07 covered what a driver author needs — pool types, allocation calls, IRQL rules. This chapter is the mechanism underneath all of it: how a page fault is actually resolved, what the paging file is really for, and why the answer to "how much memory does this process use" is a genuinely ambiguous question with at least four different correct numbers.

Resolving a page fault, step by step

A page fault is not an error; it is the normal mechanism by which memory becomes available. What matters is which of four very different things just happened, because only one of them involves the disk and only one is a genuine bug.

   A THREAD TOUCHES AN ADDRESS THE HARDWARE HAS NO VALID
   PAGE-TABLE ENTRY FOR. The CPU raises a page fault, which
   lands in the memory manager's MmAccessFault - and from
   there, every fault takes one of four paths:

   1. NO VAD COVERS THIS ADDRESS AT ALL
        -> genuine access violation. STATUS_ACCESS_VIOLATION,
           and in user mode this is the seed of an unhandled
           exception; a driver hitting this in kernel mode is
           a bugcheck.

   2. A VAD COVERS IT, BUT THE PAGE IS SHARE-BACKED AND
      ALREADY RESIDENT SOMEWHERE (a DLL another process has
      mapped, the same physical page)
        -> SOFT FAULT. The memory manager just adds a page-
           table entry pointing at the already-resident
           physical page. No disk I/O. Microseconds.

   3. A VAD COVERS IT, THE PAGE WAS RESIDENT BUT TRIMMED TO
      THE STANDBY OR MODIFIED LIST (chapter 28's working-set
      trimming)
        -> ALSO a soft fault - the physical page is still
           sitting there, just not currently mapped into
           this process. Reclaim it, remap it, done.

   4. THE PAGE MUST BE READ FROM DISK - either a file-backed
      mapping being touched for the first time, or a
      genuinely paged-out private page
        -> HARD FAULT. Real disk I/O, real latency (though
           an SSD narrows the gap enormously compared to the
           spinning-disk era this terminology comes from).

   THE NUMBER THAT ACTUALLY MATTERS FOR PERFORMANCE is hard
   faults per second, visible directly in Task Manager's
   Performance tab and in Process Explorer per-process. A
   system with thousands of soft faults a second is doing
   completely normal, cheap bookkeeping; a system with a
   sustained high hard-fault rate is thrashing.

What the paging file is actually for

The common belief that the page file exists to let a system with "too little RAM" pretend to have more is only part of the picture, and arguably not even the most important part on a modern system. Every private, committed page in every process needs somewhere the memory manager can promise to put it if physical memory becomes scarce — that promise is what "commit charge" tracks (chapter 28's VAD discussion). The page file is that backing store for private memory the way the original executable and DLL files are already the natural backing store for their own code and read-only data — a code page never needs to go to the page file at all, because it can always be re-read from the binary it came from. This is why a system with generous RAM can still benefit from a page file even when it is rarely, if ever, actually read from under normal operation: it exists to make the commit-charge promise honourable, not primarily to be read.

Memory compression: an intermediate step before the page file

Since Windows 10, the memory manager added a compression store that sits between "resident in RAM" and "on the page file" — cold private pages are compressed in place, in RAM, before ever being written to disk. This trades a small amount of CPU time for a large reduction in both memory pressure and page-file I/O, and it is why the classic advice to disable the page file entirely on a machine with abundant RAM is now actively counterproductive: the modern memory manager already avoids most disk I/O on its own, and removing the page file removes the commit-charge safety valve without meaningfully improving performance.

Prototype PTEs: how one physical page serves many processes

When ten processes load the same DLL, its code exists once in physical memory rather than ten times. The mechanism that makes that work — without every process's page tables needing to be updated together — is worth understanding because it explains most memory-accounting confusion.

   WHEN A DLL IS LOADED BY TEN DIFFERENT PROCESSES, its
   code pages exist ONCE in physical memory, not ten times.
   The mechanism that makes this work without every
   process's page tables needing to be updated together is
   the PROTOTYPE PTE.

   THE SECTION OBJECT (created once, when the file is first
   mapped by anyone) owns an array of prototype PTEs - one
   per page of the mapped file, describing where that page
   currently lives (in memory, on disk, or in the page
   file).

   EACH PROCESS mapping that section gets its own real
   page-table entries, but instead of describing the page
   directly, they point at the CORRESPONDING PROTOTYPE PTE.

     Process A's PTE  -->  prototype PTE #42  <--  Process B's PTE
                                   |
                                   v
                          the ONE physical page

   Now trimming, paging out, or re-fetching that page
   happens ONCE, at the prototype PTE, and is instantly
   correct for every process sharing it - nobody needs to
   walk every process's page tables to keep them consistent.
   This is the mechanism, not just the marketing description,
   behind why shared DLLs are cheap: the sharing is enforced
   structurally, at the data-structure level, not by a
   convention that trusts every process to behave.

Reserve, commit, and why the distinction is not pedantry

Windows separates claiming an address range from actually backing it with memory, and the distinction is not pedantry: it is what makes a sparse multi-gigabyte structure cheap, and what causes a puzzling access violation when you forget it.

/* Three distinct states, and conflating them is a genuinely
   common source of confusing bugs. */

void *p = VirtualAlloc(NULL, 1ull << 34,      /* 16 GB */
                       MEM_RESERVE, PAGE_NOACCESS);
/* RESERVED: address range claimed, so nothing else can be
   allocated there. NO backing store guaranteed. NO physical
   memory used. Touching this memory right now FAULTS.     */

VirtualAlloc(p, 4096, MEM_COMMIT, PAGE_READWRITE);
/* COMMITTED (this one page only): the memory manager has
   now promised backing store exists somewhere - RAM, the
   page file, or the compression store - for this page.
   Touching it succeeds; the memory manager satisfies the
   resulting fault with a freshly zeroed page (chapter 05's
   MDL chapter touches on why zeroing matters for security -
   never hand a process pages that might contain another
   process's leftover data).                               */

/* Touching page 2 of the SAME reservation, still only
   reserved, still faults - MEM_COMMIT is per-range, and the
   memory manager does not implicitly commit more than you
   asked for.                                                */

/* THIS THREE-STATE MODEL IS WHY A SPARSE, MULTI-GIGABYTE
   HASH TABLE OR ARENA ALLOCATOR IS CHEAP TO RESERVE UP
   FRONT AND COMMIT INCREMENTALLY: you pay only for what you
   actually touch, while still getting a single, contiguous,
   never-reused address range for the whole structure - a
   pattern used throughout Windows itself, including inside
   the memory manager's own internal allocators.            */

Four different correct answers to "how much memory"

MetricWhat it actually measuresTask Manager column
Commit sizeBacking-store promise made across all committed private pages — may never all be resident at onceCommit size
Working setPages currently resident and mapped for this process specificallyMemory (active private working set)
Private bytesCommitted memory this process does not share with any other — the number that best represents "cost of this process existing"Memory (private working set), roughly
Working set — sharedResident pages this process shares with others (DLL code, mapped files)Not usually shown directly

The gap between these numbers is not measurement error — it is the whole point of the sharing and paging mechanisms described above doing their job. A process can legitimately show a large working set and a small private-bytes figure precisely because most of what it has resident is shared code it did not pay for uniquely; conflating the two when hunting for a "memory leak" is one of the most common false alarms in performance investigation, and Process Explorer deliberately exposes all of these separately for exactly this reason.
