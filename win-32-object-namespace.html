The object manager: namespace, directories and security

Chapter 04 covered handles from a driver's point of view — creating an object, referencing it, closing it. This chapter is the object manager as a general-purpose subsystem: the single namespace almost everything in Windows lives in, how \Device, \?? and C:\ all fit together, and why an access check happens at open time rather than every time a handle is used afterward.

Almost everything nameable in Windows is an object manager object

Chapter 04 covered handles from a driver's point of view. This is the same machinery seen whole: one implementation of naming, reference counting and security serving every kind of object in the system.

   Processes, threads, files, events, mutexes, sections
   (memory-mapped regions), semaphores, ALPC ports,
   symbolic links, device objects, drivers, even the object
   TYPES themselves - all are OBJECT MANAGER OBJECTS,
   created via the same underlying primitives
   (ObCreateObject) and referenced the same way
   (ObReferenceObject / ObDereferenceObject).

   This uniformity is deliberate: it means one reference-
   counting mechanism, one security-checking mechanism, and
   one naming mechanism serve the ENTIRE kernel, rather than
   each subsystem inventing its own. A driver author who
   understands how a MUTEX is referenced and named already
   understands most of how a FILE or a SECTION works too.

One namespace, organised as directories

Named objects live in a real, browsable hierarchy that has nothing to do with the drive letters you see in Explorer. Learning its shape explains where your device object actually lives and why C:\ is not what it appears to be.

   THE ROOT OF EVERYTHING:  \

   \Device                every device object a driver's
                           AddDevice or IoCreateDevice
                           created lives here, named or
                           anonymous
   \Driver                one entry per loaded driver
   \GLOBAL??               (often just shown as \??) - DOS
                           drive letters and many Win32
                           symbolic device names live here:
                           \??\C: is a SYMBOLIC LINK, not a
                           real object, pointing at the
                           actual device
   \BaseNamedObjects       where Win32's CreateEvent,
                           CreateMutex etc. put their named
                           objects by default
   \Sessions\0\...         SESSION 0 gets its OWN private
                           BaseNamedObjects, Windows, and
                           DosDevices - the mechanism behind
                           Session 0 isolation (chapter 34)
   \RPC Control            named pipes and ports RPC uses
   \Callback               kernel notification callback
                           objects

   NAVIGATE IT LIVE with WinObj (a Sysinternals tool) or, in
   WinDbg:
     kd> !object \Device
     kd> !object \Driver\mydriver

   This is a REAL, browsable directory hierarchy, exactly
   the way a filesystem is - the object manager's
   "directory object" type is a genuine container that
   other objects are inserted into by name, and it supports
   the same kind of enumeration a folder does.
Why C:\ is a symbolic link, and why that matters

Win32 code never sees \Device\HarddiskVolume3 — it sees C:\Windows\System32. The translation happens because \??\C: is a symbolic link object pointing at the real device object, and the Win32 subsystem's I/O functions prepend \??\ before handing a path to the native API. This indirection is precisely what lets subst, drive-letter reassignment, and per-session drive mappings (\Sessions\1\DosDevices\C:, giving a Remote Desktop session its own private drive letters) work without the underlying device names ever changing. A driver author who creates a symbolic link from a friendly name to a raw device object — the standard pattern for exposing a device to user mode — is using exactly this same mechanism.

The object header: what every object carries regardless of type

Every object, whatever its type, carries the same small header before its body. That header is where naming, security and the two reference counts live — and those two counts are why an object can outlive every handle to it.

   Every object manager object has a small, FIXED header
   immediately preceding its type-specific body:

   +----------------------------------+
   | OBJECT_HEADER                    |
   |   PointerCount   (references via  |
   |                   a raw pointer,  |
   |                   e.g. from       |
   |                   another kernel  |
   |                   structure)      |
   |   HandleCount    (references via  |
   |                   an open handle  |
   |                   from some       |
   |                   process)        |
   |   Type           -> points at the |
   |                   OBJECT_TYPE     |
   |                   descriptor for  |
   |                   this kind of    |
   |                   object          |
   |   SecurityDescriptor (below)      |
   |   NameInfoOffset (if it has a     |
   |                   name at all -   |
   |                   many objects,   |
   |                   like most       |
   |                   events, do not) |
   +----------------------------------+
   | THE OBJECT BODY - EVENT, MUTEX,   |
   | FILE_OBJECT, DEVICE_OBJECT...     |
   | (type-specific layout)            |
   +----------------------------------+

   THE OBJECT IS FREED ONLY WHEN BOTH COUNTS REACH ZERO -
   which is precisely why a driver must be scrupulous about
   pairing every ObReferenceObject with an
   ObDereferenceObject: a leaked reference does not crash
   anything immediately, it just means the object outlives
   every handle to it, silently, until the leak eventually
   exhausts memory or - worse - the object holds a reference
   to something else that then cannot be cleaned up either.

Access checks happen once, at open time

Every named, securable object carries a security descriptor — an owner, a group, and a discretionary access control list (DACL) of access-control entries, each naming a security identifier (SID) and the access rights it is allowed or denied. The crucial design decision, and the one that surprises people coming from simpler permission models, is when that check happens: the Security Reference Monitor evaluates the caller's token against the object's DACL exactly once, at the moment a handle is opened (chapter 36 covers tokens and DACLs in depth), and the resulting handle is stamped with whichever subset of the requested rights was actually granted. Every subsequent operation through that handle checks only against the rights already granted to that handle — the DACL is never re-consulted for the lifetime of the handle.

The practical consequence: revoking access does not affect open handles

If you change a file's or a registry key's DACL to remove a user's access, any process that already holds a handle opened before the change keeps whatever rights that handle was granted — the change only affects future open attempts. This is not a bug; it follows directly from access checks happening at open time rather than per-operation, and it is why revoking access to something sensitive in real time generally requires also closing or invalidating existing handles, not merely editing the ACL.

The handle table: per-process, and why handle values are not pointers

A handle is a small integer, not a pointer, and it means something only inside the process that owns it. That single fact explains why handles cannot simply be passed between processes and what has to happen instead.

/* A HANDLE is an opaque, small integer - NOT a pointer,
   and not directly usable across process boundaries, even
   though the underlying kernel object might be shared.   */

kd> !handle 0 f fffffa80`03a2b7f0
Handle table at fffff8a0`... with 340 entries in use

  0004: Object: fffffa80`0439a4a0  GrantedAccess: 001f0001
        Type: File
  0008: Object: fffffa80`0439b010  GrantedAccess: 00100020
        Type: Event

/* EACH PROCESS HAS ITS OWN HANDLE TABLE - a per-process
   array (implemented as a small trie for scalability at
   large handle counts) mapping small integers to pointers
   at OBJECT HEADERS. Handle value 0x4 in process A and
   handle value 0x4 in process B are almost certainly
   pointing at completely different objects.

   THIS IS WHY YOU CANNOT PASS A RAW HANDLE VALUE TO
   ANOTHER PROCESS AND HAVE IT MEAN ANYTHING - the value is
   an index into THIS process's table. DuplicateHandle
   exists specifically to solve this: it inserts a new
   entry into the TARGET process's table pointing at the
   SAME underlying object, and hands back the (necessarily
   different) handle value that entry got in that table.

   The GrantedAccess field is exactly the "rights checked
   once, stamped on the handle" value described above - it
   never changes for the life of this handle, regardless of
   what happens to the object's ACL afterward.            */
