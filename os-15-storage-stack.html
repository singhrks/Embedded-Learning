The block layer and the storage stack

Between a filesystem's "read block 12345" and a device actually moving data sits a stack whose job is to merge, reorder, queue and account for requests. Understanding it explains most storage performance behaviour, and all storage latency surprises.

The stack

Between a write call and a platter or flash cell sit half a dozen layers, each capable of buffering, reordering or merging your request. Knowing the layers is what lets you reason about latency and durability at all.

   application:  read(fd, buf, 4096)
        │
   ┌────▼──────────────────────────────────────────┐
   │  VFS / page cache                              │  cache hit? done.
   └────┬──────────────────────────────────────────┘
   ┌────▼──────────────────────────────────────────┐
   │  filesystem (ext4)                             │  file offset →
   │                                                │  block numbers
   └────┬──────────────────────────────────────────┘
   ┌────▼──────────────────────────────────────────┐
   │  BLOCK LAYER                                   │
   │    struct bio  →  struct request               │
   │    merging, I/O scheduler, per-CPU queues      │
   └────┬──────────────────────────────────────────┘
   ┌────▼──────────────────────────────────────────┐
   │  device mapper / MD  (optional)                │  LVM, RAID,
   │                                                │  dm-crypt
   └────┬──────────────────────────────────────────┘
   ┌────▼──────────────────────────────────────────┐
   │  SCSI / NVMe / MMC driver                      │  build commands

        ▼
     device

Each layer can transform, split, merge or delay the request. That is
why the I/O your application issues rarely resembles the I/O the
device sees.

bio and request

Requests travel through the storage stack as data structures rather than function calls, which is what allows them to be queued, merged and completed asynchronously.

/* A `bio` is the unit of I/O submitted to the block layer: a
   target device, a starting sector, and a scatter-gather list of
   memory pages.                                                */

struct bio {
        struct block_device *bi_bdev;
        blk_opf_t            bi_opf;      /* READ, WRITE, FLUSH,
                                             DISCARD, ZONE_APPEND */
        struct bvec_iter     bi_iter;     /* sector, size, index  */
        struct bio_vec      *bi_io_vec;   /* page, offset, len[]  */
        bio_end_io_t        *bi_end_io;   /* completion callback  */
};

/* Note the scatter-gather list: the pages need not be contiguous
   in physical memory. The device's DMA engine walks the list.
   This is why the DMA API and the SMMU matter here — see the
   security track.                                             */

/* A `request` is one or more merged bios, ready for a driver. */

Merging and scheduling

Adjacent small requests are combined into fewer larger ones before reaching the device, because the cost of an operation is dominated by fixed overhead rather than by size.

The block layer's two big optimisations:

  MERGING — adjacent requests become one
     read sectors 100-107    ┐
     read sectors 108-115    ├─► one request, sectors 100-131
     read sectors 116-123    │
     read sectors 124-131    ┘
     · front merge, back merge, or a completely new request
     · limited by max_sectors_kb and max_segments

  SORTING / SCHEDULING — reorder to suit the device
     on a rotational disk, seeking is 5-10 ms and sequential
     access is ~1000x faster, so ordering by sector is decisive.
     On an SSD, "seeking" is free and the scheduler mostly gets
     out of the way.

  This is why `iostat` often shows fewer, larger requests reaching
  the device than the application issued — and why an application
  doing 4 KB sequential writes can still achieve full bandwidth.

blk-mq: why the old design broke

A single request queue with one lock became the bottleneck once devices got fast enough. The multi-queue design removes that by giving each processor its own path to the hardware.

SINGLE-QUEUE (pre-2013)
   all CPUs ──► one request queue, one spinlock ──► device
   Fine at 200 IOPS. At 1,000,000 IOPS the lock IS the bottleneck,
   and every submission bounces a cache line between sockets.

MULTI-QUEUE (blk-mq)
   CPU0 ─► software queue 0 ┐
   CPU1 ─► software queue 1 ├─► hardware queue 0 ─► device
   CPU2 ─► software queue 2 ├─► hardware queue 1 ─► (NVMe has up
   CPU3 ─► software queue 3 ┘                        to 64K queues)

   · per-CPU submission: no shared lock on the fast path
   · completion interrupts are steered back to the submitting CPU,
     so the completion finds the data cache-warm
   · maps naturally onto NVMe, which was designed with the same model

  This is the same insight as per-CPU runqueues in the scheduler
  (OS chapter 06): at scale, the shared structure is the problem.

The inversion

On a hard disk, software overhead was irrelevant — a 10 µs kernel path next to a 10 ms seek. On NVMe the device responds in 20 µs and the kernel path can be a comparable fraction of that. This is why io_uring, polled I/O and SPDK exist: at these speeds the operating system itself is the thing to optimise away.

# polled I/O: spin instead of taking a completion interrupt.
# Burns CPU, removes interrupt and context-switch latency.
echo 1 > /sys/block/nvme0n1/queue/io_poll
# with io_uring: IORING_SETUP_IOPOLL

Queue depth and Little's Law

How many requests are outstanding at once determines whether a device is kept busy — and past a point, adds latency without adding throughput. The right value is measurable rather than guessable.

   throughput = queue_depth / latency          (Little's Law)

   NVMe device: 80 µs latency per operation

     QD = 1    →  1 / 80µs   =    12,500 IOPS
     QD = 32   →  32 / 80µs  =   400,000 IOPS
     QD = 128  →  128 / 80µs = 1,600,000 IOPS (until saturation)

  A single-threaded, synchronous application can NEVER exceed
  QD=1 performance, no matter how fast the device is. This is the
  single most common storage benchmarking mistake — measuring a
  million-IOPS drive with `dd` and concluding it does 12,500.

  To get depth you need: async I/O (io_uring, libaio), multiple
  threads, or readahead doing it for you.

  But depth costs LATENCY: at QD=128 each request waits behind 127
  others. Throughput and latency trade off exactly as in CA
  chapter 18.
# measure properly, with depth and parallelism
fio --name=randread --ioengine=io_uring --direct=1 \
    --rw=randread --bs=4k --iodepth=32 --numjobs=4 \
    --size=4G --runtime=60 --group_reporting

# --direct=1 bypasses the page cache. Without it you are
# benchmarking RAM, which is the second most common mistake.

Direct I/O

Bypassing the page cache entirely gives an application complete control over its own buffering, which is what databases want and what most other programs should not use.

int fd = open("file", O_RDWR | O_DIRECT);
/* Bypasses the page cache entirely. Requires that the buffer,
   the file offset and the length are all aligned to the device's
   logical block size — usually 512 or 4096 bytes.            */

void *buf;
posix_memalign(&buf, 4096, size);      /* aligned allocation */
pread(fd, buf, 4096, offset);          /* all three aligned  */

/* Use O_DIRECT when:
     · the application has its own cache (databases)
     · the data will not be re-read, and caching it would evict
       something useful
     · you are benchmarking the device

   Do NOT use it as a general speed-up. It removes readahead and
   write coalescing, so naive sequential access gets SLOWER.  */

Device mapper and RAID

Block devices can be stacked, with one presenting a virtual device backed by others — which is how RAID, encryption, snapshots and logical volumes are all implemented on the same mechanism.

/* RAID 5's write hole: a partial stripe update that is
   interrupted by power loss leaves data and parity inconsistent,
   and the inconsistency is invisible until a later rebuild
   reconstructs wrong data. Journals, battery-backed cache or a
   COW filesystem (btrfs/ZFS RAID) address it.               */

I/O control and isolation

When several workloads share one device, something must arbitrate, or one of them will monopolise it. I/O control groups are how a system bounds that.

# cgroup v2 io controller — limit or weight a container's I/O
echo "259:0 rbps=10485760 wbps=5242880 riops=1000 wiops=500" \
     > /sys/fs/cgroup/mygroup/io.max
echo "default 100" > /sys/fs/cgroup/mygroup/io.weight

# io.latency: guarantee a latency target for a priority group,
# throttling others when it is exceeded
echo "259:0 target=10000" > /sys/fs/cgroup/critical/io.latency

# per-process I/O priority (works with BFQ / CFQ-style schedulers)
ionice -c 3 -p PID             # idle class
ionice -c 2 -n 7 ./backup      # best-effort, lowest priority

Observing

Storage problems are almost always diagnosable from counters rather than guesswork. These are the ones that distinguish a slow device from a badly-shaped workload.

iostat -xz 1
#  Device  r/s   w/s  rkB/s  wkB/s  rareq-sz  aqu-sz  r_await w_await %util
#                                             ^depth  ^latency        ^busy
#  %util is MISLEADING on SSDs: a device that can serve 32 requests
#  in parallel shows 100% "utilisation" while nearly idle. Use
#  aqu-sz and await instead.

iotop -o                        # which processes are doing I/O
pidstat -d 1

# per-request tracing
blktrace -d /dev/sda -o - | blkparse -i -
btt -i trace.bin                # latency breakdown by stage:
                                # Q2G queue→get, G2I insert,
                                # I2D issue→device, D2C device→complete
                                # This tells you WHICH LAYER is slow.

# eBPF one-liners
biolatency-bpfcc                # latency histogram
biosnoop-bpfcc                  # every I/O with process and latency
biotop-bpfcc

# where is the time going overall?
cat /proc/pressure/io           # PSI — stall percentage
Diagnosing "the disk is slow"

Work down the stack. iostat await high but aqu-sz low means the device is slow. aqu-sz high means you are queueing — the device is saturated, or the scheduler is holding requests. If application latency is high but await is low, the problem is above the block layer: filesystem metadata, fsync, or the page cache. btt resolves this precisely by breaking one request's life into stages.
