The AArch64 register file

Thirty-one general-purpose registers, a stack pointer per exception level, a zero register that is also sometimes the stack pointer, and a vector file that may be 128 or 2048 bits wide. This chapter is the map you will refer back to constantly.

General-purpose registers

The register file is the first thing to fix in your head, because every instruction refers to it and every calling convention is expressed in terms of it. The naming has one wrinkle that confuses newcomers immediately.

   X0 ─ X30      31 registers, 64 bits each
   W0 ─ W30      the LOW 32 BITS of the same registers

   ┌─────────────────────────────────────────────────┐
   │                     X0  (64 bits)                │
   │                 ┌────────────────────────────────┤
   │  upper 32       │        W0  (32 bits)           │
   └─────────────────┴────────────────────────────────┘

   CRITICAL RULE: writing Wn ZEROES the upper 32 bits of Xn.
                  There is no way to write only the low half.

        mov     x0, #0xFFFFFFFFFFFFFFFF
        mov     w0, #1                    // x0 is now 0x1, NOT
                                          // 0xFFFFFFFF00000001

   This is a deliberate design choice: it removes the partial-
   register dependency stalls that plague x86, where writing EAX
   must merge with the old RAX. It also means 32-bit arithmetic is
   free — no sign or zero extension needed afterwards.

X18 is a portability trap

The ABI says "platform register" and each OS decides. Windows uses it for TLS; Android's kernel uses it for the shadow call stack; some RTOSes leave it general. Hand-written assembly or a compiler configured with the wrong -ffixed-x18 setting produces corruption that only appears on one platform. If you write assembly that must be portable, do not touch X18.

The special registers

A few registers are not general-purpose at all: they have fixed architectural meanings, and one of them is a register whose number means two different things depending on the instruction.

/* XZR / WZR — register encoding 31, in most contexts */
        mov     x0, xzr           // x0 = 0, no immediate needed
        str     xzr, [x1]         // store 64 bits of zero
        subs    xzr, x1, x2       // compare: this IS how CMP encodes
        ands    wzr, w1, w2       // test:    this IS how TST encodes

/* SP — register encoding 31, in OTHER contexts */
        add     x0, sp, #16       // 31 here means SP
        mov     x0, sp            // encoded as `add x0, sp, #0`
        sub     sp, sp, #64       // allocate stack

/* The SAME encoding means two different things depending on the
   instruction. This is why disassemblers print them explicitly,
   and why hand-written assembly gets it wrong.               */

/* PC — the program counter is NOT a general register in AArch64.
   You cannot write it directly (unlike ARMv7, where R15 was the
   PC and `mov pc, lr` was a return). It changes only via
   branches, and it can be READ only PC-relatively:          */
        adr     x0, .              // address of this instruction
        adrp    x0, symbol         // page address, ±4 GB range

Stack pointers per exception level

There is not one stack pointer but several, one per exception level, and the processor switches between them automatically. This is what stops an exception handler from running on a stack the faulting code controlled.

   SP_EL0    used by EL0, and optionally by higher ELs
   SP_EL1    the kernel's stack
   SP_EL2    the hypervisor's stack
   SP_EL3    the secure monitor's stack

   PSTATE.SPSel selects which one "SP" refers to at the current EL:
        SPSel = 0  →  always SP_EL0        (called "t", thread)
        SPSel = 1  →  SP_ELx for this EL   (called "h", handler)

   This is why exception return states are written EL1t and EL1h,
   and why the vector table has separate entries for exceptions
   taken with SP_EL0 versus SP_ELx (chapter 27).

   WHY IT EXISTS: on exception entry the hardware switches to the
   handler's own stack automatically. Without this, a user process
   with a corrupt SP would take the kernel down with it — the
   kernel would try to save state onto an invalid stack.

   Linux reads `current` from SP_EL0 while running at EL1, using
   the otherwise-unused register as a per-CPU pointer to the
   current task_struct. That is why `current` is one register
   read rather than a lookup (OS chapter 04).

SIMD and floating-point registers

Alongside the integer registers sits a completely separate, wider register file used for floating point and vector work. Knowing it exists — and that it must be saved separately — matters even if you never write vector code.

   V0 ─ V31      32 registers, 128 bits each

   The SAME register, named by the width you are using:

   ┌────────────────────────────────────────┐
   │              Q0   (128 bits)            │
   │                    ┌────────────────────┤
   │                    │    D0  (64 bits)   │
   │                    │          ┌─────────┤
   │                    │          │ S0 (32) │
   │                    │          │    ┌────┤
   │                    │          │    │H0  │ (16)
   │                    │          │    │  ┌─┤
   │                    │          │    │  │B0│ (8)
   └────────────────────┴──────────┴────┴──┴─┘

   Bn  8-bit    Hn 16-bit    Sn 32-bit (float)
   Dn 64-bit (double)        Qn 128-bit (full vector)

   Or as VECTORS with a lane specifier:
        V0.16B   16 bytes        V0.8H   8 half-words
        V0.4S    4 words         V0.2D   2 double-words

   Writing Sn or Dn ZEROES the upper bits of Vn — the same rule
   as W registers.

   FPCR / FPSR   control and status: rounding mode, exception
                 flags, flush-to-zero. Note these are NOT in
                 PSTATE and are saved separately.

SVE: registers whose width is unknown at compile time

/* The Scalable Vector Extension changes the model fundamentally: */

   Z0 - Z31     vector registers, 128 to 2048 bits — the width is
                an IMPLEMENTATION CHOICE, not known when you compile
   P0 - P15     predicate registers, one bit per vector byte
   FFR          first-fault register, for speculative loads

/* Vector-length-agnostic code: the same binary runs optimally on
   any width, because the loop asks the hardware how wide it is:  */

        whilelo p0.s, x0, x1        // predicate = lanes still in range
1:      ld1w    z0.s, p0/z, [x2, x0, lsl #2]
        ld1w    z1.s, p0/z, [x3, x0, lsl #2]
        fadd    z0.s, z0.s, z1.s
        st1w    z0.s, p0,   [x4, x0, lsl #2]
        incw    x0                   // advance by the ACTUAL width
        whilelo p0.s, x0, x1         // recompute the predicate
        b.first 1b

/* No scalar tail loop is needed — the predicate handles the
   remainder. Compare with NEON, which needs an epilogue for
   elements that do not fill a full 128-bit vector.          */

/* Z0-Z31 ALIAS V0-V31: the low 128 bits of Zn IS Vn. */

System registers are not general registers

System registers are a different thing again: they are not addressed by number in ordinary instructions, they control the processor's behaviour rather than holding your data, and reaching them needs dedicated instructions.

/* Configuration lives in SYSTEM registers, which are a separate
   namespace and are accessed only with MRS and MSR (chapter 06). */

        mrs     x0, sctlr_el1        // System register → general
        msr     sctlr_el1, x0        // General → System register

/* They are named REG_ELx where x is the LOWEST exception level
   that may access them. SCTLR_EL1 is accessible at EL1, EL2 and
   EL3 — but not EL0.

   You cannot use a system register as an operand to ADD. You must
   move it to a general register first. This is a common early
   mistake when hand-writing boot code.                       */

No banked general registers

The most consequential difference from ARMv7

ARMv7 banked several registers per processor mode: entering IRQ mode gave you a private R13 and R14 automatically. AArch64 does not bank X0–X30 at all.

When an exception is taken, the handler begins executing with the interrupted code's register values still live. Nothing is saved for you except ELR, SPSR and the syndrome registers. Saving and restoring the general registers is entirely software's job — and that saved set is struct pt_regs in Linux, the trap frame in Windows.

This is why every AArch64 exception vector begins with thirty-odd store instructions (chapter 28), and why getting that stub wrong corrupts the interrupted program in ways that are extremely hard to diagnose.

Register conventions in practice

Which registers a function may freely use, and which it must preserve, is not enforced by hardware — it is an agreement. Breaking it produces failures that look like memory corruption rather than a calling error.

/* A standard prologue and epilogue — read this until it is
   instantly recognisable in any disassembly.                */

my_func:
        stp     x29, x30, [sp, #-32]!   // push FP,LR; pre-decrement SP
        mov     x29, sp                 // establish the frame pointer
        stp     x19, x20, [sp, #16]     // save the callee-saved regs
                                        //   this function will use
        ...
        ldp     x19, x20, [sp, #16]     // restore
        ldp     x29, x30, [sp], #32     // pop FP,LR; post-increment SP
        ret                             // == BR X30, with a hint

/* STP/LDP move TWO registers in one instruction — which is why
   prologues save in pairs, and why the stack is always adjusted
   in multiples of 16 (chapter 09 covers the alignment rule). */

/* A LEAF function — one that calls nothing — needs no prologue
   at all, because LR is not clobbered:                       */
square: mul     w0, w0, w0
        ret

Inspecting registers

Every register above is visible in a debugger, and reading them is how a register dump in a crash report becomes a diagnosis rather than a wall of hexadecimal.

# gdb
info registers                 # X0-X30, SP, PC, PSTATE
info registers x0 x1 sp
info all-registers             # including V0-V31 and system regs
p/x $x0                        # one register, in hex
p $sp
info frame                     # the current frame's saved registers

# vector registers
p $v0.d                        # as two doubles
p $v0.s                        # as four floats
p/x $v0.b                      # as sixteen bytes

# system registers, where the target exposes them
p/x $SCTLR_EL1
p/x $CPSR                      # PSTATE, on some gdb versions

# in a core dump or an oops, Linux prints them all:
dmesg | grep -A20 'pc :'
#   pc : ffff800008123456
#   lr : ffff8000081234ab
#   sp : ffff800009abc000
#   x29: ...  x28: ...  x27: ...
