Trap-and-emulate and the Popek-Goldberg conditions

In 1974 two researchers wrote down the exact property an instruction set must have to be virtualisable. For thirty years most popular architectures failed the test, and the industry built increasingly baroque workarounds. Understanding the test tells you precisely what EL2 was added to fix.

The mechanism, stripped down

Classical virtualisation is one idea: run the guest at a privilege level lower than it thinks it has, and catch it when it notices.

   Guest kernel BELIEVES it runs at the highest privilege.
   It ACTUALLY runs de-privileged.

   guest executes an ordinary instruction
        |
        |  ADD, LDR to its own memory, B, ...
        v
   runs at full speed on real silicon.  No hypervisor involvement.
   This is most instructions, and it is why virtualisation is fast.


   guest executes a PRIVILEGED instruction
        |
        |  "write TTBR0", "disable interrupts", "read the timer"
        v
   the CPU refuses at this privilege level  ->  TRAP
        |
        v
   +---------------------------------------------+
   |  hypervisor's exception handler             |
   |   1. decode: what did the guest try to do?  |
   |   2. is it allowed, in the guest's own      |
   |      virtual world?                          |
   |   3. perform the EQUIVALENT operation on    |
   |      the guest's shadow state               |
   |   4. advance the guest's PC past it         |
   |   5. return                                  |
   +---------------------------------------------+
        |
        v
   guest resumes, having observed nothing unusual.

   Cost: steps 1-5 are perhaps 1000-2000 cycles.
   Correctness: step 3 must be indistinguishable from the real thing.
The invariant

The guest must not be able to tell. Not "must not be able to escape" — must not be able to tell. Any observable difference between running natively and running virtualised is a bug, and historically most of them were also security holes.

Popek and Goldberg's instruction classes

The 1974 paper divides every instruction into categories based on two questions: does it touch privileged state, and does its behaviour depend on privileged state?

ClassDefinitionAArch64 examples
PrivilegedTraps when executed in user mode, works in supervisor modeMSR TTBR0_EL1, TLBI, AT, ERET
Sensitive — controlChanges the configuration of resources: memory mapping, privilege, interrupt stateMSR SCTLR_EL1, MSR DAIFSet, MSR VBAR_EL1
Sensitive — behaviourIts result depends on the privilege level or on real resource configurationMRS CurrentEL, MRS MIDR_EL1, reading a physical counter
InnocuousEverything elseADD, LDR, B, floating point
 
   THE THEOREM

     A machine is efficiently virtualisable if
     the set of SENSITIVE instructions is a SUBSET
     of the set of PRIVILEGED instructions.

   In words: every instruction that could betray the illusion
   must TRAP when executed by a de-privileged guest.

     +---------------------------------+
     |         all instructions        |
     |   +-------------------------+   |
     |   |      privileged         |   |    GOOD: sensitive fits
     |   |   +---------------+     |   |    entirely inside
     |   |   |  sensitive    |     |   |    privileged. Everything
     |   |   +---------------+     |   |    dangerous traps.
     |   +-------------------------+   |
     +---------------------------------+

     +---------------------------------+
     |   +-------------+               |
     |   | privileged  |               |    BAD: sensitive
     |   +------+------+               |    instructions exist
     |   +------|-----------+          |    OUTSIDE privileged.
     |   |   sensitive      |          |    They silently do the
     |   +------------------+          |    WRONG THING instead
     +---------------------------------+    of trapping.

   The instructions in that overhang are called CRITICAL
   instructions. They are the entire problem.

Where architectures failed

x86 before VT-x had 17 critical instructions. The canonical one is POPF, which pops the flags register. In kernel mode it can change the interrupt-enable flag; in user mode it silently ignores that bit rather than faulting. A de-privileged guest kernel executing POPF to disable interrupts would get no trap and no effect. The hypervisor never learns the guest wanted interrupts off, and the guest never learns it failed.

Classic ARM (ARMv7-A without the Virtualization Extensions) had its own version of the problem, and it is worth knowing because you meet it on old parts:

/* ARMv7-A, no VE. The guest kernel is de-privileged to USR mode. */

    MRS  r0, CPSR        /* reads the mode field. In USR mode the
                            mode bits read back as USR - so a guest
                            that inspects its own mode discovers it
                            is not in SVC. It can TELL. */

    MSR  CPSR_c, #0xD3   /* attempt to switch to SVC and mask IRQs.
                            In USR mode: silently ignored. No trap.
                            The guest believes interrupts are off.
                            They are not. */

    LDM  sp, {r0-r14}^   /* the "^" form accesses USR-mode banked
                            registers - meaningless and unfaulting
                            when you are already in USR mode. */

/* Three sensitive-but-not-privileged instructions, and therefore
   three ways for the illusion to break silently. This is why Xen
   on ARMv7 required PARAVIRTUALISATION: you had to patch the guest
   kernel to replace every critical instruction with a hypercall.  */

The three historical workarounds

ApproachHow it dodges critical instructionsPrice

ParavirtualisationChange the guest source so it never emits a critical instruction — it calls the hypervisor insteadEvery guest OS must be ported and maintained; closed guests cannot run at all

Why "shadow page tables" were the real pain

Even with the instruction problem solved, memory remained hard. The guest builds page tables mapping guest-virtual to guest-physical addresses, but the MMU consumes host-physical. Pre-hardware solutions had the hypervisor maintain a hidden shadow table composing the two, write-protect the guest's tables to detect edits, and rebuild on every change. It worked, and it cost a fortune on fork-heavy workloads. Stage-2 translation (chapter 05) is the hardware answer, and it is the single biggest reason modern virtualisation is cheap.

How ARMv8-A passes the test

ARM did not try to make EL1 instructions trap by de-privileging the guest into EL0. That was the ARMv7 mistake. Instead it added a higher level, EL2, and made trapping configurable: the guest genuinely runs at EL1, with real EL1 registers, and the hypervisor selects which EL1 operations should divert to EL2.

   ARMv7 approach (broken)        ARMv8 approach (works)

   EL0  app                       EL0  app
        guest kernel  <- squashed
                          in here  EL1  guest kernel, genuinely at EL1
   SVC  hypervisor                      with its own SCTLR_EL1, TTBR0_EL1,
                                        VBAR_EL1 ... all real registers

                                  EL2  hypervisor, and it holds the
                                       CONTROL: HCR_EL2 says which
                                       EL1 operations trap up to here

   Consequence: the guest is NOT de-privileged, so it cannot
   detect de-privileging. Sensitive instructions do not need to
   be privileged - they need to be TRAPPABLE, and HCR_EL2 makes
   almost all of them trappable on demand.

   MRS CurrentEL in a guest reads "EL1" - which is TRUE.
   The lie is not about privilege. The lie is about being alone.

This is the key architectural insight of the ARM virtualisation extensions, and it is why HCR_EL2 is the register this whole track revolves around. Popek and Goldberg asked for sensitive ⊆ privileged. ARM instead offered sensitive ⊆ configurably trappable, which is strictly more useful: the hypervisor traps what it must emulate and lets the rest run at full speed.

Selective trapping in practice

The theory says trap on sensitive instructions. Real hypervisors trap on far fewer than they are permitted to, and the reason is entirely about cost.

/* Not everything should trap. The art is choosing.        */

  TRAP IT when the guest must not see real hardware state, or
  when you must maintain shadow state:

    guest writes to the GIC distributor      -> trap, emulate
    guest reads the physical counter         -> trap or offset
    guest executes WFI                       -> trap, so you can
                                                schedule another vCPU
    guest reads ID registers (MIDR, ID_AA64*)-> trap, present a
                                                sanitised view
    guest does SMC / HVC                     -> always to EL2/EL3

  DO NOT TRAP when the hardware already isolates it, because a
  trap you did not need is pure cost:

    guest writes TTBR0_EL1, TCR_EL1          -> let it. Stage-2
                                                already constrains
                                                the result.
    guest issues TLBI VAE1                   -> let it. VMID tags
                                                the entries.
    guest takes its own EL0 syscall          -> let it. Never
                                                involves EL2.
    guest sets DAIF                          -> let it, unless you
                                                are virtualising
                                                interrupts strictly.

   execute BILLIONS of instructions between exits. A badly
   configured one exits thousands of times a second doing the
   same work.                                                */
