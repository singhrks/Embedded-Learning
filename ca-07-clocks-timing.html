Clocks, timing and metastability

The clock is the heartbeat that makes a machine of gates behave predictably. This chapter explains what limits its speed, why crossing between two clocks is genuinely dangerous, and why so many driver bugs turn out to be "the block was not clocked".

The problem

From chapter 06, a flip-flop captures its input on a clock edge. But a real flip-flop is not instantaneous. It needs its input to be stable for a while before the edge and to stay stable for a while after. Violate either window and the captured value is not merely wrong — it may be neither 0 nor 1 for a time.

Setup and hold

A flip-flop cannot capture a value that is still changing. It needs the input to be stable for a short window before the clock edge and a short window after it, and those two requirements are what ultimately limit how fast any chip can run.

                    ┌──────────
   clock  ──────────┘
                    ▲
                    │ capture instant
        ──►│setup│◄─┼─►│hold│◄──
           │      │  │  │    │
   data  ──┴──────┴──┴──┴────┴────
           must be stable through BOTH windows

  t_setup : input must be stable this long BEFORE the edge
  t_hold  : input must remain stable this long AFTER the edge

Violate either → the flip-flop may enter a METASTABLE state:
its output hovers between logic levels for an unbounded time
before resolving randomly to 0 or 1.

The maximum-frequency equation

   ┌──────┐   combinational logic   ┌──────┐
   │ FF A │──────────────────────►  │ FF B │
   └──────┘                         └──────┘
       ▲                                ▲
       └────────── clock ───────────────┘

  T_clock  ≥  t_clk→q  +  t_logic  +  t_setup  +  t_skew

    t_clk→q : delay from the edge to A's output being valid
    t_logic : propagation through the combinational cloud  ← the big one
    t_setup : B's setup requirement
    t_skew  : difference in clock arrival time between A and B

  f_max = 1 / T_clock

The path with the largest t_logic — the CRITICAL PATH — sets f_max
for the entire chip. One slow path anywhere limits everything.
The three ways to go faster
  1. Shorten the logic. Better adders, fewer levels of gates.
  2. Cut the path in two with a register. Each half now settles in half the time, so the clock can roughly double — at the cost of an extra cycle of latency. This is pipelining.
  3. Do more per cycle instead. Wider issue, SIMD, more cores — chapter 19.

Frequency scaling stopped around 2005 because of power (chapter 20), which is why options 2 and 3 dominate every design since.

Clock distribution

A clock must reach millions of flip-flops at very nearly the same instant. It does not arrive by magic: it is driven through a large buffered tree that is among the most carefully engineered structures on the die.

                       PLL
                        │
                   ┌────┴────┐
              ┌────┴───┐ ┌───┴────┐          an H-tree: every leaf is
           ┌──┴──┐  ┌──┴─┴─┐   ┌──┴──┐       the same wire distance
          ┌┴┐   ┌┴┐┌┴┐   ┌┴┐ ┌┴┐   ┌┴┐      from the root, so all
          FF    FF FF    FF  FF    FF       edges arrive together

  SKEW   : difference in arrival time between two endpoints (spatial)
  JITTER : cycle-to-cycle variation at one endpoint (temporal)

Both eat into the timing budget, and the clock tree can consume
20-40% of a chip's total dynamic power — which is why unused blocks
are CLOCK GATED rather than left running.

The number one bring-up bug

A peripheral whose clock is not enabled reads back as all zeros, all ones, or aborts the access entirely — indistinguishable from a wrong address or a firewall denial. Always verify the clock before debugging anything else. On Linux, cat /sys/kernel/debug/clk/clk_summary shows every clock's rate and enable count. In a driver, this is what clk_prepare_enable() is for, and why it comes before the first register read in every probe() function.

Clock domain crossing

A real SoC has dozens of independent clocks: CPU, DDR, USB, audio, a slow always-on domain. When a signal passes from one to another, the receiving flip-flop's setup and hold windows are violated eventually and unavoidably, because the two clocks have no fixed phase relationship.

   domain A (200 MHz)          domain B (48 MHz)
   ┌──────┐                    ┌──────┐
   │ FF A │───────signal──────►│ FF B │   ← setup/hold WILL be violated
   └──────┘                    └──────┘
       ▲                           ▲
      clkA                        clkB     (unrelated phase)

Result: FF B goes metastable. Its output sits between valid levels for
an unpredictable time, then resolves randomly. Downstream logic may
read different values from the same signal — a design that fails once
every few hours, which is the worst possible failure rate to debug.

The standard fixes

TechniqueForHow
Two-flop synchroniserA single control bitChain two flip-flops in the destination domain. The first may go metastable; it is given a full clock period to resolve before the second samples it. Reduces failure probability to once in years.
Gray-coded countersMulti-bit countersOnly one bit changes per increment, so a mid-transition sample yields either the old or the new value — never a nonsense combination
Asynchronous FIFOData streamsDual-port memory with Gray-coded read/write pointers, each synchronised into the other domain
HandshakeOccasional transfersRequest/acknowledge, each synchronised — slow but simple and robust
Why a software engineer should care

Three reasons this is not just hardware trivia. First, it explains why some status registers must be read twice and compared, or why a datasheet says "this field is valid two cycles after the write" — you are seeing a synchroniser's latency. Second, the two-flop synchroniser is conceptually identical to a memory barrier: both are mechanisms for safely passing information between two things that do not share a timebase. Third, the "read a wide counter twice and retry if it changed" idiom in timer drivers exists precisely because the counter crosses a clock domain.

/* reading a 64-bit counter that updates in another clock domain */
do {
        hi1 = readl(base + CNT_HI);
        lo  = readl(base + CNT_LO);
        hi2 = readl(base + CNT_HI);
} while (hi1 != hi2);          /* retry if the low half wrapped mid-read */

Clock gating and dynamic scaling

Dynamic power is proportional to C·V²·f — capacitance, voltage squared, frequency. Two consequences shape every modern SoC:

  • Clock gating. Stop the clock to an idle block and its dynamic power goes to essentially zero. This is what a peripheral's "clock enable" bit does, and why disabling it makes the block's registers unreadable — there is no clock to capture the access.
  • DVFS (dynamic voltage and frequency scaling). Lower frequency permits lower voltage, and because of the square term the energy saving is superlinear. This is what a CPU governor manipulates, and why a benchmark run at a low governor setting is not comparable to one at another.
Typical SoC clock hierarchy as software sees it

  crystal 24 MHz
      │
      ├─► PLL0 ──► 1.8 GHz ──► CPU cluster        [DVFS: 400 MHz - 1.8 GHz]
      │
      ├─► PLL1 ──► 800 MHz ──► DDR controller
      │
      └─► PLL2 ──► 480 MHz ──┬─► /4  → 120 MHz ──► AXI interconnect
                             ├─► /10 →  48 MHz ──► USB      [gateable]
                             └─► /30 →  16 MHz ──► APB ──┬─► UART  [gateable]
                                                         ├─► I2C   [gateable]
                                                         └─► SPI   [gateable]

Every "gateable" leaf is a clk_prepare_enable() call in some driver.
