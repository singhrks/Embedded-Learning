The memory hierarchy and locality

The gap between processor speed and memory speed is the dominant fact of modern computing. This chapter explains the illusion built to hide it, and why data layout beats almost every other optimisation you can make.

The problem

You want memory that is large, fast and cheap. Physics permits any two.

Put those numbers on a human scale. Scale one CPU cycle to one second:

  L1 cache hit         4 cycles     →  4 seconds
  L2 cache hit        12 cycles     →  12 seconds
  L3 cache hit        40 cycles     →  40 seconds
  DRAM               200 cycles     →  3 minutes 20 seconds
  SSD read       ~200,000 cycles    →  2.5 days
  Disk seek   ~20,000,000 cycles    →  8 months

A DRAM access is not "a bit slower". Relative to the core, it is a
coffee break. Everything in this chapter exists to avoid taking it.

Locality: the property that makes caching work

A cache is only useful if past accesses predict future ones. Real programs oblige, in two distinct ways:

The two localities

Temporal locality — if you accessed an address, you will probably access it again soon. Loop counters, the stack top, a hot data structure, function code inside a loop.

Spatial locality — if you accessed an address, you will probably access a nearby one soon. Array traversal, struct field access, sequential instruction fetch.

Caches exploit temporal locality by keeping recently used data, and spatial locality by fetching a whole line rather than a single word. Code with neither gets no benefit at all — which is why a random-access hash table over a large working set can be slower than a linear scan of an array containing the same data.

/* excellent locality — this is nearly free */
for (i = 0; i < n; i++)
        sum += a[i];        /* spatial: consecutive addresses
                               temporal: sum and i stay in registers */

/* terrible locality */
for (i = 0; i < n; i++)
        sum += a[perm[i]];  /* random order: every access a likely miss */

/* the classic demonstration: same work, 10x difference */
for (i = 0; i < N; i++)          for (j = 0; j < N; j++)
  for (j = 0; j < N; j++)          for (i = 0; i < N; i++)
    total += m[i][j];                total += m[i][j];

/* left: row-major, walks memory sequentially — one miss per 16 elements
   right: strides by a whole row — one miss per ELEMENT               */

The hierarchy

There is no single memory technology that is simultaneously fast, large and affordable, so every machine uses several at once and moves data between them automatically. The numbers below are the entire reason the rest of this chapter exists.

                    ┌──────────┐
                    │registers │   ~1 KB      1 cycle
                    └────┬─────┘
                   ┌─────┴──────┐
                   │ L1 I / L1 D│   32-64 KB   ~4 cycles      per core
                   └─────┬──────┘
                  ┌──────┴───────┐
                  │      L2      │   256KB-2MB  ~12 cycles    per core
                  └──────┬───────┘              or per cluster
                 ┌───────┴────────┐
                 │   L3 / SLC     │   4-64 MB    ~40 cycles   shared
                 └───────┬────────┘
                ┌────────┴─────────┐
                │      DRAM        │   GBs        ~200 cycles
                └────────┬─────────┘
               ┌─────────┴──────────┐
               │   SSD (swap/files) │   TBs        ~200,000 cycles
               └────────────────────┘

Each level is a CACHE for the level below it, and each is roughly
10x larger and 3-5x slower than the one above.

The same principle appears again at every scale: the page cache caches
the disk, a CDN caches an origin server, a TLB caches page table walks.
Once you see the pattern you will find it everywhere in systems.

Quantifying it

"Cache misses are slow" is not actionable. This formula turns hit rates and latencies into one number, which is what lets you predict whether a change will actually help before making it.

Average Memory Access Time

  AMAT = hit_time + miss_rate × miss_penalty

  With a hierarchy, recurse:

  AMAT = t_L1 + m_L1 × (t_L2 + m_L2 × (t_L3 + m_L3 × t_DRAM))

  Worked example:
      t_L1 = 4,   m_L1 = 5%
      t_L2 = 12,  m_L2 = 40%     (of L1 misses)
      t_L3 = 40,  m_L3 = 50%     (of L2 misses)
      t_DRAM = 200

  AMAT = 4 + 0.05 × (12 + 0.40 × (40 + 0.50 × 200))
       = 4 + 0.05 × (12 + 0.40 × 140)
       = 4 + 0.05 × 68
       = 7.4 cycles

  Now halve the L1 miss rate to 2.5% (better data layout):
  AMAT = 4 + 0.025 × 68 = 5.7 cycles — a 23% improvement in ALL
  memory access time, from changing nothing but how data is arranged.
Why the miss rate matters more than the hit time

Look at the leverage in that equation. Reducing L1 hit time from 4 to 3 cycles is a heroic hardware change worth ~13%. Halving the miss rate is often a source-level change worth ~23%. This is the arithmetic behind the rule of thumb that data layout beats instruction-level optimisation — and it is why profiling tools report cache misses so prominently.

The three kinds of miss

Compulsory (cold)First ever access to a line — nothing could have been cachedPrefetching; larger lines. Unavoidable in principle.

A fourth appears on multi-core: coherence misses, where another core invalidated your line. Covered in chapter 15.

Prefetching

A miss costs 200 cycles only if you wait for it. If the line arrives before you ask, the cost is zero.

KindMechanismCatches
Next-lineFetch line N+1 whenever N is fetchedSequential scans, instruction fetch
StrideDetect a constant stride and extrapolateArray walks, matrix rows, struct arrays
SoftwarePRFM PLDL1KEEP, [addr] — an explicit hintPointer chasing, irregular patterns the hardware cannot see
 
/* software prefetch: useful when you know the future and hardware does not */
for (n = list; n; n = n->next) {
        __builtin_prefetch(n->next);    /* start fetching the NEXT node   */
        process(n->data);               /* while we work on this one      */
}

/* prefetch distance matters — too close and it has not arrived,
   too far and it is evicted before use. Tune by measurement.        */
#define DIST 8
for (i = 0; i < n; i++) {
        __builtin_prefetch(&a[i + DIST]);
        heavy_work(a[i]);
}
Prefetching is not free

Every prefetch consumes memory bandwidth and a cache line's worth of capacity. Aggressive prefetching on a bandwidth-saturated system makes things worse by evicting useful data and competing for the memory controller. Measure; do not assume. On modern cores the hardware stride prefetcher already handles regular patterns better than you will by hand — reserve software prefetch for genuinely irregular access.

Designing for the hierarchy

You cannot control the cache directly, but you have complete control over the order in which your program touches memory — and that is most of what determines whether the cache helps you or not.

Structure of arrays versus array of structures

/* AoS — natural to write, poor for scanning one field */
struct particle { float x, y, z, vx, vy, vz; int id; float mass; };
struct particle p[100000];              /* 32 bytes each               */

for (i = 0; i < n; i++) p[i].x += p[i].vx;
/* each 64-byte line holds 2 particles, and you use 8 of its 64 bytes.
   87% of every line fetched is wasted bandwidth. */

/* SoA — awkward to write, excellent for scanning */
struct particles {
        float x[100000], y[100000], z[100000];
        float vx[100000], vy[100000], vz[100000];
};
for (i = 0; i < n; i++) ps.x[i] += ps.vx[i];
/* every byte of every fetched line is used, and it VECTORISES —
   the compiler can now emit NEON/SVE operating on 4-8 elements at once */

Blocking (tiling)

/* naive matrix multiply: B is walked column-wise — a miss per element */
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++)
    for (k = 0; k < N; k++)
      C[i][j] += A[i][k] * B[k][j];

/* blocked: work on tiles small enough that A, B and C tiles all fit
   in L1 simultaneously. Same arithmetic, dramatically fewer misses. */
for (ii = 0; ii < N; ii += BS)
 for (jj = 0; jj < N; jj += BS)
  for (kk = 0; kk < N; kk += BS)
   for (i = ii; i < ii+BS; i++)
    for (j = jj; j < jj+BS; j++)
     for (k = kk; k < kk+BS; k++)
      C[i][j] += A[i][k] * B[k][j];

/* choose BS so 3 * BS * BS * sizeof(float) < L1 size.
   For 32 KB L1 and floats: BS ≈ 50, so 32 or 48 in practice.
   This is the single most important optimisation in dense linear
   algebra, and therefore in machine learning kernels — see AI ch. 04. */

Hot/cold splitting

/* before: rarely-used fields evict useful data from every line */
struct conn {
        int fd;  int state;  uint64_t bytes;      /* hot: touched per packet */
        char peer_name[64]; time_t created;       /* cold: touched on error  */
        struct sockaddr_storage addr;             /* cold                    */
};

/* after: the hot struct is small, so more connections fit per line */
struct conn {
        int fd;  int state;  uint64_t bytes;
        struct conn_cold *cold;                   /* one pointer            */
};

Measuring it

None of this needs to be guessed at. Modern processors count cache hits and misses in hardware, and reading those counters turns a theory about your program's memory behaviour into a measurement.

perf stat -e cache-references,cache-misses,\
L1-dcache-loads,L1-dcache-load-misses,\
LLC-loads,LLC-load-misses,dTLB-load-misses ./program

perf record -e cache-misses ./program && perf report   # which line misses?

# on ARM, the PMU exposes the same counters by architectural name
perf list | grep -i cache

# a quick empirical map of your machine's hierarchy: time a pointer
# chase over increasing working-set sizes and look for the step changes.
# The steps land exactly at your L1, L2 and L3 capacities.
