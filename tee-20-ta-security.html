Writing a TA that resists its own client

The client is the attacker. Not "might be" — the entire reason your TA exists is that the normal world may be compromised, so you must write every entry point assuming the caller is hostile, competent and patient. This chapter is the checklist, ordered by how often each mistake appears in real audits.

The mental shift

Before the specific rules, the mental model: everything crossing into your trusted application is attacker-controlled, including things that look like framework guarantees.

   ORDINARY LIBRARY               TRUSTED APPLICATION

   caller is your own code        caller is an attacker
   arguments are well-formed      arguments are chosen to break
                                    you
   a crash is a bug               a crash is a denial of
                                    service, and a controlled
                                    crash may be an exploit
   memory is stable               shared memory CHANGES WHILE
                                    YOU READ IT
   an error message helps         an error message may leak the
                                    secret
   timing does not matter         timing IS a channel

   Every parameter, every length, every index, every pointer.
   There is no trusted input.

1. Check parameter types. Always.

Validate every parameter, every time. The framework checks the shape of the parameters, not their meaning, and the difference is where exploits live.

TEE_Result TA_InvokeCommandEntryPoint(void *sess, uint32_t cmd,
                                      uint32_t ptypes,
                                      TEE_Param params[4])
{
        const uint32_t exp =
                TEE_PARAM_TYPES(TEE_PARAM_TYPE_MEMREF_INPUT,
                                TEE_PARAM_TYPE_MEMREF_OUTPUT,
                                TEE_PARAM_TYPE_NONE,
                                TEE_PARAM_TYPE_NONE);

        if (ptypes != exp) {
                EMSG("ptypes 0x%08x expected 0x%08x", ptypes, exp);
                return TEE_ERROR_BAD_PARAMETERS;
        }
        ...
}

/* WITHOUT this, a client passes VALUE where you expect MEMREF.
   You then read params[0].memref.buffer - which is now an
   arbitrary 64-bit number the attacker chose - and
   dereference it with secure privilege.

   This is the number one OP-TEE TA vulnerability class. It is
   four lines. Check EVERY command, and check it in
   TA_OpenSessionEntryPoint too.                            */

2. Never read shared memory twice

A buffer in shared memory can change after you validate it and before you use it, because the normal world still has access to it. Copy before checking.

/* WRONG - the classic double fetch. */

static TEE_Result bad(TEE_Param params[4])
{
        struct hdr *h = params[0].memref.buffer;

        if (h->len > MAX)                 /* fetch 1: check    */
                return TEE_ERROR_BAD_PARAMETERS;

        /* the client's other thread changes h->len HERE */

        memcpy(dst, h->data, h->len);     /* fetch 2: use      */
        /* h->len is now 0xFFFFFFFF. Heap overflow, in the
           secure world, with attacker-controlled data.      */
}

/* RIGHT - copy once, then work only on the copy. */

static TEE_Result good(TEE_Param params[4])
{
        struct hdr local;
        uint8_t    buf[MAX];

        if (params[0].memref.size < sizeof local)
                return TEE_ERROR_BAD_PARAMETERS;

        /* ONE read of the shared region. */
        TEE_MemMove(&local, params[0].memref.buffer, sizeof local);

        /* Validate the COPY. It cannot change now. */
        if (local.len > MAX ||
            local.len > params[0].memref.size - sizeof local)
                return TEE_ERROR_BAD_PARAMETERS;

        TEE_MemMove(buf,
                    (uint8_t *)params[0].memref.buffer + sizeof local,
                    local.len);

        return process(buf, local.len);
}

/* The rule, stated once: SHARED MEMORY IS A NETWORK
   CONNECTION. You read from it once, into your own storage,
   and everything after that operates on your storage.     */
This is the bug that gets CVEs

Search any TEE vendor's advisory list and the double fetch appears again and again, because the code looks correct — the check is right there, immediately above the use. The window is a few instructions wide and an attacker with another thread will hit it. There is no defence except never fetching twice.

3. Validate every length and index

Memory safety errors in C are ordinary bugs in ordinary code and privilege escalations here, because of where this code runs and what it can reach.

/* Integer overflow in a bounds check is the second-commonest
   finding.                                                 */

    /* WRONG: offset + len can wrap */
    if (offset + len > buffer_size)
            return TEE_ERROR_BAD_PARAMETERS;
    /* offset = 0xFFFFFFF0, len = 0x20  ->  sum wraps to 0x10,
       check passes, and you read far outside the buffer.  */

    /* RIGHT: rearrange so nothing can overflow */
    if (offset > buffer_size || len > buffer_size - offset)
            return TEE_ERROR_BAD_PARAMETERS;

    /* Also wrong: */
    uint32_t total = count * sizeof(struct item);   /* wraps  */
    /* Right: */
    if (count > UINT32_MAX / sizeof(struct item))
            return TEE_ERROR_OVERFLOW;

    /* Signedness: */
    int idx = params[0].value.a;      /* a uint32_t from the
                                         client              */
    if (idx < n)                      /* -1 < n is TRUE       */
            table[idx] = ...;         /* writes before the
                                         table                */
    /* Use unsigned types for anything that indexes. */

    /* And check ranges explicitly, not implicitly: */
    if (params[0].value.a >= ARRAY_SIZE(g_slots))
            return TEE_ERROR_BAD_PARAMETERS;

4. Validate pointers with the API

Secrets must be cleared after use, and the compiler is entitled to remove the code that clears them if it can prove the value is never read again.

    res = TEE_CheckMemoryAccessRights(
                TEE_MEMORY_ACCESS_READ |
                TEE_MEMORY_ACCESS_ANY_OWNER,
                params[0].memref.buffer,
                params[0].memref.size);
    if (res != TEE_SUCCESS)
            return res;

/* This asks OP-TEE whether that pointer, for that length, is
   really memory this session was given. It catches a client
   that registered a 4 KB buffer and then claimed 4 MB.

   It does NOT catch a double fetch - the memory is legitimate,
   it just changes. Both checks are needed.               */

/* When your TA is called BY ANOTHER TA (chapter 18), the
   buffer may be secure memory:
      TEE_MEMORY_ACCESS_SECURE      it must be secure
      TEE_MEMORY_ACCESS_NONSECURE   it must not be
   Being explicit about which you expect stops a confused
   deputy.                                                 */

5. Write output once, on success only

Comparing secrets must take constant time, or the comparison itself leaks how much of the secret was correct.

/* WRONG - leaks intermediate state on the error path. */
    memcpy(out, partial_result, n);      /* client can see this */
    if (verify_something() != OK)
            return TEE_ERROR_SECURITY;   /* too late            */

/* RIGHT */
    uint8_t local_out[MAX];

    res = compute(local_out, &n);
    if (res != TEE_SUCCESS)
            return res;                  /* client sees nothing */

    if (params[1].memref.size < n) {
            params[1].memref.size = n;   /* the ONE allowed
                                            early write         */
            return TEE_ERROR_SHORT_BUFFER;
    }
    TEE_MemMove(params[1].memref.buffer, local_out, n);
    params[1].memref.size = n;
    return TEE_SUCCESS;

/* For a crypto TA the intermediate state often IS the secret -
   a partially decrypted block, a key schedule, an unverified
   plaintext. Compute in private memory, publish at the end. */

6. Constant time where it matters

Error messages that distinguish failure causes can hand an attacker exactly the oracle they need, which is why secure-world errors are deliberately uninformative.

/* Comparison, of anything secret: */

    /* WRONG - returns as soon as bytes differ */
    if (TEE_MemCompare(mac, expected, 32) == 0) ...
    if (memcmp(pin, stored, 4) == 0) ...

    /* RIGHT */
    static bool ct_equal(const uint8_t *a, const uint8_t *b, size_t n)
    {
            uint8_t d = 0;
            for (size_t i = 0; i < n; i++)
                    d |= a[i] ^ b[i];
            return d == 0;
    }
    /* or, for MACs, the API does it: */
    TEE_MACCompareFinal(op, msg, len, mac, maclen);

/* Branching on secrets: */

    /* WRONG - the branch is observable */
    if (key[0] & 1)
            do_a();
    else
            do_b();

    /* Table lookups indexed by secrets are also observable,
       through the cache. This is how AES T-table
       implementations were broken. Use the hardware
       accelerator, or an implementation written to be
       constant time - do not write your own.              */

/* Error messages that distinguish cases: */

    /* WRONG - an oracle */
    if (!user_exists(u)) return TEE_ERROR_ITEM_NOT_FOUND;
    if (!pin_matches(p)) return TEE_ERROR_ACCESS_DENIED;

    /* RIGHT - one answer, one timing */
    bool ok = user_exists(u);
    ok &= pin_matches(p);          /* NOT &&: always evaluate */
    return ok ? TEE_SUCCESS : TEE_ERROR_ACCESS_DENIED;

7. Fail closed, and rate limit

State shared between sessions can leak from one client to another unless the instance model is chosen deliberately — which is the flag discussion from chapter 13 seen as a security matter.

    /* Default to refusal, not permission. */
    TEE_Result res = TEE_ERROR_ACCESS_DENIED;   /* not SUCCESS */
    ...
    if (everything_checked_out)
            res = TEE_SUCCESS;
    return res;

    /* A missing case in a switch must deny: */
    switch (cmd) {
    case CMD_A: return do_a(...);
    case CMD_B: return do_b(...);
    default:    return TEE_ERROR_NOT_SUPPORTED;   /* never
                                                     fall
                                                     through */
    }

    /* Anything guessable needs a counter, and the counter
       needs rollback protection (chapter 17): */
    if (state.failures >= MAX_FAILURES)
            return TEE_ERROR_ACCESS_DENIED;

    state.failures++;
    write_protected_state(&state);      /* BEFORE checking -
                                           so a power cut
                                           during the attempt
                                           counts against the
                                           attacker           */
    if (check_pin(pin)) {
            state.failures = 0;
            write_protected_state(&state);
            return TEE_SUCCESS;
    }
    return TEE_ERROR_ACCESS_DENIED;

8. Clean up on every path

Counting and limiting resource use matters because a trusted application that exhausts secure-world contexts denies service to everything else on the device.

static TEE_Result do_work(TEE_Param params[4])
{
        TEE_OperationHandle op  = TEE_HANDLE_NULL;
        TEE_ObjectHandle    key = TEE_HANDLE_NULL;
        uint8_t             secret[32] = {0};
        TEE_Result          res;

        res = TEE_AllocateOperation(&op, ...);
        if (res) goto out;

        res = TEE_AllocateTransientObject(&key, ...);
        if (res) goto out;

        res = actually_do_it(op, key, secret);
out:
        /* Wipe secrets BEFORE freeing - the heap is reused
           and OP-TEE does not zero on free.               */
        TEE_MemFill(secret, 0, sizeof secret);
        TEE_FreeOperation(op);          /* NULL-safe          */
        TEE_FreeTransientObject(key);   /* NULL-safe          */
        return res;
}

/* A leak here is not merely untidy: TA_DATA_SIZE is small
   (chapter 13), so a leak on an error path that an attacker
   can trigger repeatedly is a denial of service against the
   whole TA.                                               */

14No untrusted parsingASN.1, protobuf, JSON, X.509 inside the TA
Row 14 deserves emphasis

A parser for a complex, attacker-controlled format is the largest single source of memory-safety bugs in any codebase, and putting one inside the secure world concentrates the risk exactly where it hurts most. Parse in Linux; pass the TA a fixed-size, fully validated struct. If the TA genuinely must parse — a certificate, a TPM command — keep the parser small, total, and fuzzed.

Testing hostilely

The interface is small, well-defined and takes attacker-controlled input, which makes it an unusually good fuzzing target — and fuzzing it is far cheaper than an audit.

Check yourself

  • State the assumption you must make about every client.
  • Write the paramTypes check and explain the attack it prevents.
  • Explain the double fetch with a concrete example and give the rule that prevents it.
  • Rewrite offset + len > size so it cannot overflow.
  • Say what TEE_CheckMemoryAccessRights catches and what it does not.
  • Explain why output must be written once, at the end.
  • Write a constant-time comparison and say why TEE_MemCompare is unsuitable.
  • Give two ways an error path can become an oracle.
  • Explain why a leak on an error path is a security bug in a TA.
  • Explain why untrusted parsing does not belong in the secure world.
  • Design a hostile test client covering at least four of the checklist rows.
