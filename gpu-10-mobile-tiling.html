Tile-based rendering on mobile GPUs

Every phone, tablet and Apple Silicon GPU renders in a fundamentally different order from a desktop card. It is not a minor variation — it inverts which operations are cheap, and a renderer tuned for one architecture can be several times slower on the other.

Bandwidth is the whole reason

   A desktop GPU has 500-3000 GB/s of dedicated GDDR/HBM and
   a 300 W power budget.

   A phone has ~50 GB/s of LPDDR, SHARED with the CPU, and
   about 3 W for the whole SoC.

   THE PHYSICS: moving a byte off-chip costs roughly 100x the
   energy of an arithmetic operation. On a phone, DRAM traffic
   IS the power budget, and power is the thermal budget, and
   thermal is your sustained frame rate.

   IMMEDIATE MODE (desktop) - what it costs

     for each triangle:
             rasterise
             for each fragment:
                     READ depth from DRAM
                     test, shade
                     WRITE depth to DRAM
                     READ colour, blend, WRITE colour

     Every fragment touches off-chip memory several times.
     Fine at 3 TB/s. Impossible at 50 GB/s.

   TILE-BASED DEFERRED RENDERING (mobile) - the fix

     PHASE 1 - BINNING
       run ALL vertex shaders for the whole frame.
       sort the resulting primitives into screen TILES
       (typically 16x16 or 32x32 pixels).
       write the per-tile primitive lists to memory.

     PHASE 2 - for each tile, independently:
       the tile's colour+depth live in ON-CHIP TILE MEMORY -
       a few tens of KB, single-cycle access
       rasterise and shade every primitive in that tile
       ... all depth and blending traffic stays ON CHIP ...
       finally, WRITE THE FINISHED TILE to DRAM. Once.

   RESULT: the colour buffer is written exactly once per
   frame, and the depth buffer need never be written at all.
   Bandwidth drops by an order of magnitude.
The consequence that matters most

On a tiler, the entire frame's geometry is processed before any pixel is shaded. Vertex output for the whole frame must be stored to memory and read back — which means vertex data and the number of draw calls cost more on mobile, while overdraw, blending and MSAA cost dramatically less. Every performance intuition from desktop needs re-examining.

Load and store actions: the one thing to get right

/* Because a tile is loaded, worked on, and stored, you must
   tell the driver what to do at each boundary. Getting this
   wrong is the single biggest mobile performance mistake. */

  AT TILE LOAD (start of a render pass)
    CLEAR      cheapest. No read from DRAM at all - the tile
               is simply initialised on chip.
    LOAD       read the previous contents from DRAM. Costs
               full bandwidth.
    DONT_CARE  cheapest, when you will overwrite everything.

  AT TILE STORE (end of a render pass)
    STORE      write the tile to DRAM.
    DONT_CARE  discard it. FREE.

/* THE DEPTH BUFFER should almost always be:
       load  = CLEAR
       store = DONT_CARE
   You need depth during the pass and never afterwards, so
   there is no reason to spend bandwidth writing it out.
   Many engines write depth to DRAM every frame for no reason
   and lose 20-30% of their bandwidth budget to it.        */

/* Vulkan makes it explicit: */
   VkAttachmentDescription depth = {
        .loadOp         = VK_ATTACHMENT_LOAD_OP_CLEAR,
        .storeOp        = VK_ATTACHMENT_STORE_OP_DONT_CARE,
        .stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE,
        .stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE,
   };

/* Metal, the same: */
   pass.depthAttachment.loadAction  = MTLLoadActionClear;
   pass.depthAttachment.storeAction = MTLStoreActionDontCare;

/* GLES, via an extension that is easy to forget: */
   glInvalidateFramebuffer(GL_FRAMEBUFFER, 1,
                           (GLenum[]){GL_DEPTH_ATTACHMENT});

/* AND THE ANTI-PATTERN: a partial clear, or a draw that
   covers only part of the screen, forces a LOAD of the whole
   render target so the untouched parts survive. Clear the
   whole thing, or use DONT_CARE and cover it.             */

Keeping data on chip

/* Deferred shading writes a G-buffer, then reads it back.
   On a tiler that is a full round trip to DRAM and back -
   exactly what tiling exists to avoid.

   THE FIX: tell the API that the second pass reads the same
   TILE, not the same TEXTURE. Then the data never leaves
   chip.                                                    */

/* Vulkan SUBPASSES with input attachments: */
   /* subpass 0: write G-buffer attachments
      subpass 1: read them as INPUT ATTACHMENTS
      dependency: BY_REGION                                */
   VkSubpassDependency dep = {
        .srcSubpass    = 0,
        .dstSubpass    = 1,
        .srcStageMask  = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT,
        .dstStageMask  = VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT,
        .dependencyFlags = VK_DEPENDENCY_BY_REGION_BIT,  /* <-- */
   };
   /* BY_REGION is the promise that pixel (x,y) in subpass 1
      only reads pixel (x,y) from subpass 0. That is what lets
      the driver keep everything in tile memory.           */

   /* In the shader: */
   layout(input_attachment_index = 0, set = 0, binding = 0)
        uniform subpassInput gbufferAlbedo;
   vec4 albedo = subpassLoad(gbufferAlbedo);

/* Metal: programmable blending - just read the colour
   attachment directly in the fragment shader: */
   fragment float4 lighting(GBuffer gbuf [[color(0)]]) { ... }

/* GLES: GL_EXT_shader_framebuffer_fetch */
   gl_LastFragData[0]

/* This is why "just port the desktop deferred renderer" goes
   badly on mobile, and why mobile engines favour
   FORWARD+ / CLUSTERED FORWARD instead: one pass, no
   G-buffer, lights culled per tile on the CPU or in a
   compute pass.                                            */
The render-target ping-pong

Post-processing chains that bounce between two full-screen targets — blur horizontal, blur vertical, tonemap, bloom — cost one full flush and reload per pass on a tiler. Four post passes at 1080p RGBA8 is roughly 66 MB of traffic per frame, at 60 Hz nearly 4 GB/s, on a device with 50 GB/s total. Merge post passes aggressively, work at reduced resolution, and prefer compute with groupshared memory over repeated full-screen draws.

The landscape, and what "deferred" means here

GPUStyleNote
Imagination PowerVRTBDRInvented it. Full hidden-surface removal per tile — opaque overdraw is essentially free
AppleTBDRPowerVR lineage; the same on iPhone and on Apple Silicon Macs
ARM MaliTBRTiled, plus "forward pixel kill" rather than full HSR
Qualcomm AdrenoHybrid"FlexRender" — chooses tiled or immediate mode per render pass based on heuristics
NVIDIA (Maxwell+)Tiled cachingImmediate-mode API semantics, but bins into tiles internally to save bandwidth. Invisible to you
AMD (Vega+)DSBRSame idea, also transparent

Note the vocabulary trap: tile-based deferred rendering is a hardware architecture — deferring rasterisation until the geometry is binned. Deferred shading is a software technique — deferring lighting until after a G-buffer is filled. They are unrelated, and deferred shading is the technique that fits TBDR hardware worst.
