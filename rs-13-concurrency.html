Fearless concurrency: Send, Sync, threads and channels

Rust's data-race guarantee comes from two marker traits and the borrow checker. That is the whole mechanism — and it means a program that compiles cannot have a data race, which is a guarantee no other systems language offers.

Send and Sync

Two traits carry the entire thread-safety story, and they are inferred rather than written. Understanding what each one means turns "fearless concurrency" from a slogan into a mechanism.

   Send    it is safe to MOVE this type to another thread
   Sync    it is safe to SHARE &T with another thread
           (equivalently: &T is Send)

   BOTH ARE AUTO TRAITS: the compiler implements them
   automatically for any type whose components all implement
   them. You almost never write them.

   WHAT IS NOT Send:
     Rc<T>           - a non-atomic refcount
     *const T, *mut T - raw pointers, conservatively
     MutexGuard      - some platforms require unlock on the
                       locking thread

   WHAT IS NOT Sync:
     Cell<T>, RefCell<T>  - unsynchronised interior
                            mutability
     Rc<T>
     raw pointers

   WHAT IS BOTH: almost everything else. i32, String,
   Vec<T> (if T is), Arc<T> (if T is Send+Sync), Mutex<T>
   (if T is Send), atomics.

   AND THE COMBINATION THAT MATTERS:
        Mutex<T>   is Sync if T: Send
   because the mutex provides the synchronisation, so sharing
   a reference to it is safe as long as the contents can move
   between threads.

   THE ENFORCEMENT IS AUTOMATIC:

        let rc = Rc::new(5);
        thread::spawn(move || { println!("{rc}"); });
        // error: `Rc<i32>` cannot be sent between threads
        //        safely
        //        required because it appears within the type
        //        of the closure

   You did not annotate anything. The compiler worked out
   that the closure captures an Rc, that Rc is not Send, and
   that spawn requires Send. THAT is the whole data-race
   guarantee.

Threads

Spawning a thread is ordinary, and the compiler's insistence about what may cross into it is where the data-race guarantee actually lives.

    use std::thread;

    let h = thread::spawn(|| {
        expensive_work()
    });
    let result = h.join().unwrap();     // Result - Err if it
                                        // panicked

/* THE SIGNATURE explains the constraints: */
    pub fn spawn<F, T>(f: F) -> JoinHandle<T>
    where
        F: FnOnce() -> T + Send + 'static,
        T: Send + 'static;

/*   Send      the closure moves to another thread
     'static   the thread may outlive this scope, so the
               closure must not borrow anything local
               (chapter 04)

/* WHICH IS WHY `move` IS USUALLY REQUIRED: */
    let data = vec![1, 2, 3];
    thread::spawn(move || println!("{data:?}"));   // data
                                                   // MOVED in

/* SCOPED THREADS lift the 'static requirement, because the
   scope guarantees they are joined before it ends: */
    let data = vec![1, 2, 3];
    thread::scope(|s| {
        s.spawn(|| println!("{data:?}"));   // BORROWS - no
                                            // move, no clone
        s.spawn(|| println!("{}", data.len()));
    });                                     // both joined
                                            // here
    println!("{data:?}");                   // still usable

/* Two shared borrows in two threads - allowed, because
   neither mutates. The borrow checker's rule extends across
   threads with no extra machinery.                       */

Sharing data

The standard combination for shared mutable state, and why the type system makes the lock impossible to forget — which is the difference from every C API you have used.

    use std::sync::{Arc, Mutex, RwLock};

/* --- Arc<Mutex<T>>: the standard shape --- */
    let counter = Arc::new(Mutex::new(0));

    let mut handles = vec![];
    for _ in 0..10 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut n = c.lock().unwrap();
            *n += 1;
        }));                    // the GUARD drops here,
                                // unlocking
    }
    for h in handles { h.join().unwrap(); }
    println!("{}", *counter.lock().unwrap());   // 10

/* THE GUARD IS THE POINT: `lock()` returns a
   MutexGuard<T> which Derefs to T and unlocks on Drop
   (chapter 10). YOU CANNOT ACCESS THE DATA WITHOUT HOLDING
   THE LOCK - the API makes it impossible, rather than
   documenting it.

   Compare C++ (C++ chapter 13), where std::mutex and the
   data it protects are separate objects and nothing connects
   them. Rust's Mutex<T> CONTAINS the data.

/* POISONING: if a thread panics while holding the lock, the
   mutex is poisoned and later lock() calls return Err -
   because the data may be in a half-updated state.       */
    match m.lock() {
        Ok(g) => use(g),
        Err(poisoned) => {
            let g = poisoned.into_inner();  // use it anyway
            recover(g);
        }
    }

/* RwLock, for read-heavy data: */
    let cfg = Arc::new(RwLock::new(Config::default()));
    { let r = cfg.read().unwrap(); use(&r); }   // many
    { let mut w = cfg.write().unwrap(); w.rate = 48000; }
                                                // one

/* ATOMICS, for single values (C++ chapter 13 covers the
   memory model, which is the SAME model): */
    use std::sync::atomic::{AtomicU32, AtomicBool, Ordering};

    static COUNT: AtomicU32 = AtomicU32::new(0);
    COUNT.fetch_add(1, Ordering::Relaxed);

    READY.store(true, Ordering::Release);
    if READY.load(Ordering::Acquire) { /* sees prior writes */ }

    let ok = FLAG.compare_exchange(false, true,
                                   Ordering::AcqRel,
                                   Ordering::Acquire).is_ok();

/* THE ORDERINGS AND THEIR ARM INSTRUCTIONS are identical to
   C++'s (C++ chapter 13, ARM chapter 21): Relaxed is a plain
   access, Acquire is ldar, Release is stlr, SeqCst adds a
   barrier. Use SeqCst unless you have measured a reason.  */
Why "fearless" is not marketing

In C or C++, a data race is undefined behaviour you discover through corruption months later, and ThreadSanitizer finds only races your tests happen to execute. In Rust, the same mistake is a compile error with a message naming the type that is not Send. The class of bug does not become easier to debug — it becomes impossible to write outside unsafe.

Channels

Message passing as the alternative to shared state, and the ownership transfer that makes it cheap.

    use std::sync::mpsc;

    let (tx, rx) = mpsc::channel();     // unbounded, multi-
                                        // producer,
                                        // single-consumer

    for i in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(format!("from {i}")).unwrap();
        });
    }
    drop(tx);                   // drop the ORIGINAL, or rx
                                // never sees a disconnect

    for msg in rx {             // iterates until every sender
        println!("{msg}");      // is dropped
    }

    let (tx, rx) = mpsc::sync_channel(4);   // BOUNDED - send
                                            // blocks when
                                            // full

    rx.recv()                   // blocks; Err when all
                                // senders drop
    rx.try_recv()               // non-blocking
    rx.recv_timeout(dur)

/* CHANNELS TRANSFER OWNERSHIP. `send(v)` moves v; the
   receiver owns it afterwards. No sharing, therefore no
   locking, therefore no race - which is why "share memory by
   communicating" works so cleanly here.

/* AND THE BETTER CRATE: */
    use crossbeam_channel as chan;
    let (tx, rx) = chan::bounded(16);
    chan::select! {                     // wait on several
        recv(rx1) -> msg => handle(msg),
        recv(rx2) -> msg => handle(msg),
        default(Duration::from_millis(10)) => timeout(),
    }
/* crossbeam adds multi-CONSUMER, select, and better
   performance. It is what most production code uses.    */

Concurrency without an OS

Without an OS there are no threads, and the concurrency is between an interrupt and main. The problem is real and the tools are different.

/* On bare metal there are no threads - there are interrupts,
   and possibly several cores. Send and Sync still apply, and
   the ecosystem uses them.                               */

/* --- 1. ATOMICS, for flags and counters --- */
    use core::sync::atomic::{AtomicU32, Ordering};

    static TICKS: AtomicU32 = AtomicU32::new(0);

    #[interrupt]
    fn SysTick() { TICKS.fetch_add(1, Ordering::Relaxed); }

    fn now() -> u32 { TICKS.load(Ordering::Relaxed) }

/* NOTE: not every target has atomics. Cortex-M0 lacks
   LDREX/STREX, so `portable-atomic` provides them via
   critical sections:                                     */
    use portable_atomic::AtomicU64;     // works everywhere

/* --- 2. CRITICAL SECTIONS, for compound state --- */
    use critical_section::Mutex;
    use core::cell::RefCell;

    static SHARED: Mutex<RefCell<State>> =
        Mutex::new(RefCell::new(State::new()));

    #[interrupt]
    fn TIM2() {
        critical_section::with(|cs| {
            SHARED.borrow(cs).borrow_mut().tick();
        });
    }
/* `critical_section::Mutex` is not a blocking lock - it
   requires a token proving interrupts are disabled
   (chapter 10). Zero cost, and sound by construction.

/* --- 3. A LOCK-FREE SPSC QUEUE, ISR to main --- */
    use heapless::spsc::{Queue, Producer, Consumer};

    static mut Q: Queue<Event, 16> = Queue::new();

    // in init, once:
    let (mut prod, mut cons) = unsafe { Q.split() };
    // `prod` goes to the ISR, `cons` to the main loop -
    // and the TYPES enforce that only one end does each

    #[interrupt]
    fn EXTI0() {
        PRODUCER.enqueue(Event::Button).ok();   // never
                                                // blocks
    }
    fn main_loop() {
        while let Some(ev) = CONSUMER.dequeue() { handle(ev); }
    }
/* Single-producer single-consumer needs no lock at all - the
   same design as the C++ ring in C++ chapter 13, with the
   producer and consumer halves as distinct TYPES so the
   invariant cannot be violated.

/* --- 4. RTIC: priorities and resources, checked at compile
       time --- */
    #[app(device = pac, peripherals = true)]
    mod app {
        #[shared] struct Shared { counter: u32 }
        #[local]  struct Local  { led: Led }

        #[task(binds = TIM2, shared = [counter], priority = 2)]
        fn timer(mut cx: timer::Context) {
            cx.shared.counter.lock(|c| *c += 1);
        }

        #[idle(shared = [counter])]
        fn idle(mut cx: idle::Context) -> ! {
            loop {
                let n = cx.shared.counter.lock(|c| *c);
                ...
            }
        }
    }
/* RTIC applies the STACK RESOURCE POLICY: it computes each
   resource's priority ceiling at compile time and raises
   BASEPRI only as far as needed - so a resource shared only
   between equal-priority tasks needs NO critical section at
   all. Deadlock is impossible by construction, and the
   analysis is done by the macro, not at run time
   (chapter 20).                                          */

Implementing Send and Sync

Occasionally you must assert thread-safety the compiler cannot infer. This is the correct way to do it and the obligation you take on by doing so.

/* Occasionally you must assert it yourself - almost always
   because a raw pointer made the type conservatively
   non-Send.                                              */

    pub struct Uart { base: *mut u32 }

    // SAFETY: `base` points to a memory-mapped peripheral.
    // The Uart is created once via a token that guarantees
    // exclusive ownership, so moving it between contexts
    // cannot create aliasing.
    unsafe impl Send for Uart {}

    // NOT Sync: two &Uart in two contexts could interleave
    // register writes. Callers must wrap it in a Mutex.

/* THE DISCIPLINE: `unsafe impl Send` and `unsafe impl Sync`
   are promises the compiler cannot check (chapter 14).
   Write the SAFETY comment, and state which of the two you
   are NOT implementing and why - that second half is what
   readers need.

/* AND THE OPPOSITE - explicitly opting OUT: */
    use core::marker::PhantomData;
    pub struct NotSync {
        data: u32,
        _marker: PhantomData<*const ()>,    // raw pointer:
                                            // not Send, not
                                            // Sync
    }
/* PhantomData with a chosen type is how you control auto
   traits without any runtime cost. `PhantomData<&'a T>`
   also expresses a lifetime relationship for a type that
   holds no reference - which is what type-state patterns
   need (chapter 02).                                     */

How it shows up

ErrorMeaning and fix
"Rc<T> cannot be sent between threads safely"Use Arc
"RefCell<T> cannot be shared between threads"Use Mutex or RwLock
"*mut T cannot be sent"Wrap it and unsafe impl Send, with a justification
"closure may outlive the current function"Add move, or use a scoped thread
"borrowed data escapes outside of function"The 'static bound — own the data or scope the thread
lock() returns ErrPoisoned — a previous holder panicked
DeadlockRust does not prevent this — establish a lock order
Receiver never terminatesA sender clone was not dropped
fetch_add unavailable on Cortex-M0No LDREX — use portable-atomic
Corruption between an ISR and mainNo critical section, or the wrong atomic ordering
RTIC reports a priority errorThe analysis found a real ceiling violation at compile time
