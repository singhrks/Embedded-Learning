Stack sizing, priority assignment and inversion

Two numbers per task decide whether a system is reliable: how much stack it gets and what priority it runs at. Both are usually guessed. This chapter replaces the guessing with measurement for one and a theorem for the other.

Why stack sizing is hard here

   ON LINUX                      ON AN MCU

   8 MB default stack            512 bytes to 4 kB
   Guard page: overflow          Nothing. The stack grows
   traps immediately             into the next task's data
   Grows on demand               Fixed at creation
   One bad recursion = crash     One bad recursion = a
                                 variable changes somewhere
                                 else, hours later

   WHAT CONSUMES A TASK'S STACK:

     local variables in every frame of the deepest call path
   + saved registers at each call (up to 32 bytes)
   + compiler temporaries and spills
   + ONE EXCEPTION FRAME if an interrupt lands while this
     task runs (32 bytes, or 104 with FP state)
   + the nesting depth of interrupts, IF they run on the
     task stack

   That last point is why PSP matters (chapter 03): with
   tasks on PSP and interrupts on MSP, interrupt nesting is
   charged to ONE main stack you size once, rather than to
   every task stack separately. Without the split, every
   task stack must carry the worst-case interrupt depth.

Measuring, three ways

/* 1. WATERMARKING - the standard technique. Fill the stack
      with a pattern at creation; later, count how much is
      still intact.                                        */

void stack_fill(uint32_t *base, size_t words)
{
    for (size_t i = 0; i < words; i++) {
        base[i] = 0xA5A5A5A5u;
    }
}

size_t stack_unused_words(const uint32_t *base, size_t words)
{
    size_t i = 0;
    while (i < words && base[i] == 0xA5A5A5A5u) {
        i++;
    }
    return i;      /* words never touched */
}

/* FreeRTOS does this for you:
     uxTaskGetStackHighWaterMark(handle)
   returns the minimum free WORDS ever observed. Print it
   for every task after a long soak test under peak load.

   THE TRAP: this reports the worst case SEEN, not the
   worst case POSSIBLE. If the error path that calls
   snprintf never ran during your test, its 200 bytes are
   not in the number. Exercise error paths deliberately
   before trusting a watermark.                            */

/* 2. STATIC ANALYSIS - the only way to bound the worst
      case rather than sample it.                          */

/*   $ arm-none-eabi-gcc -fstack-usage ...
     produces a .su file per translation unit:

       i2c.c:142:5:i2c_read    48   static
       parse.c:88:1:parse_msg  120  dynamic,bounded

     Combine with the call graph and you get a true maximum.
     Tools: puncover, StackAnalyzer, or a script over the
     .su files plus objdump's call graph.

     "dynamic" entries - alloca, VLAs, recursion - cannot be
     bounded. That is the real reason those constructs are
     banned in embedded coding standards, MISRA included.  */

/* 3. THE MPU GUARD - not a measurement, a safety net.
      A no-access region below each stack (chapter 14)
      converts overflow into an immediate, attributable
      fault. Use it alongside watermarking, not instead:
      watermarking tells you how close you are, the guard
      catches the day you are wrong.                       */
A practical procedure

Start every task at 1 kB. Run the system under peak load, including every error path you can provoke, for long enough to see the rare cases. Read the high-water marks. Set each stack to the observed maximum plus 50%, rounded up to a sensible boundary. Add an MPU guard region. Re-check the watermarks in every release. This is not elegant, but it is what reliable products actually do, and it beats both guessing and the false confidence of a single short test run.

Assigning priorities: rate-monotonic

/* There IS a right answer for periodic tasks, and it is a
   theorem rather than an opinion.

   RATE-MONOTONIC: the shorter the period, the higher the
   priority. Not "the more important" - the more FREQUENT.

   Liu and Layland proved this is OPTIMAL among fixed-
   priority schemes: if any fixed-priority assignment can
   meet all deadlines, rate-monotonic can.

   SCHEDULABILITY TEST:

     U = sum(Ci / Ti)          C = worst-case compute time
                               T = period

     Schedulable if U <= n(2^(1/n) - 1)

       n=1  100%      n=4  75.7%
       n=2  82.8%     n=5  74.3%
       n=3  78.0%     n->inf  69.3%   (ln 2)

   WORKED EXAMPLE:

     control loop   T=10 ms   C=2 ms   ->  0.200
     sensor read    T=50 ms   C=5 ms   ->  0.100
     comms          T=100 ms  C=20 ms  ->  0.200
     display        T=200 ms  C=30 ms  ->  0.150
                                            -----
                                     U =    0.650

     n=4 bound is 0.757, and 0.650 <= 0.757, so ALL
     deadlines are met with priorities in period order:
     control > sensor > comms > display.

   The bound is SUFFICIENT, not necessary: above it a system
   may still be schedulable, but you must then do exact
   response-time analysis rather than the simple test.

   THIS IS WHY 69% IS A FAMOUS NUMBER. A fixed-priority
   real-time system that must always meet deadlines cannot
   safely be planned above roughly 70% CPU utilisation.
   Designing for 95% is designing for missed deadlines.   */

Priority inversion, in miniature

   The concurrency track covers this fully (chapter 15).
   The MCU-specific points:

   1. USE A MUTEX, NOT A SEMAPHORE, for mutual exclusion.
      Only a mutex has an owner, so only a mutex can
      implement priority inheritance (chapter 19).

   2. CHECK IT IS ENABLED.
        configUSE_MUTEXES = 1
      Without it xSemaphoreCreateMutex is compiled out and
      you silently get a binary semaphore.

   3. THE ISR IS ALWAYS HIGHEST.
      Any interrupt outranks every task, always. A long ISR
      delays your most urgent task no matter what priority
      you gave it. Interrupt duration is therefore part of
      your schedulability arithmetic, not separate from it:

        U = sum(Ci/Ti) for tasks
          + sum(Ei/Pi) for INTERRUPTS

      A 20 us ISR at 10 kHz is 20% utilisation before any
      task runs. This is routinely forgotten, and it is
      why a system that analyses as 65% utilised misses
      deadlines at 85%.

   4. MEASURE C, DO NOT ESTIMATE IT.
      Use the DWT cycle counter (chapter 16) and record the
      MAXIMUM, not the average. A deadline cares only about
      the worst case, and the worst case is often 5-10x the
      typical one because of a cache miss, a flash wait
      state, or an error path.

RuleWhy
Fewer tasks is betterEach costs a stack, a TCB and a synchronisation surface. Two tasks that always run together should be one
