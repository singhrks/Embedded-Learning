Virtual memory as an architectural idea

Every address your program uses is a lie the hardware maintains. This chapter covers why that indirection exists and how it works in general; ARM chapter 12 and OS chapter 12 cover the specific mechanics.

The problem

Before virtual memory, a program's addresses were physical addresses. Four consequences, all bad:

ProblemConsequence
No protectionAny program can read or write any other program's memory, and the OS's. One bug takes down everything.
No relocationA program compiled to load at 0x10000 must load there. Two such programs cannot coexist.
FragmentationFree memory exists but not contiguously, so a large allocation fails while plenty is free.
Hard capacity limitThe working set must fit in physical RAM. No overcommit, no demand loading, no swap.
The idea

Insert a hardware translation step between the address a program emits and the address that reaches memory. Software sees virtual addresses; the memory system sees physical addresses; a per-process mapping table, controlled by the OS and consulted by hardware, connects them. Every problem above dissolves at once.

                              (per process, OS-owned)
                                  page tables
                                       |
   ┌──────┐   virtual addr   ┌─────────▼────────┐   physical addr   ┌──────┐
   │ CPU  │ ───────────────► │       MMU        │ ────────────────► │ DRAM │
   └──────┘                  └──────────────────┘                   └──────┘
                                       │
                                  translation
                                     fault
                                       ▼
                                 OS exception handler
                                 (map it, or kill it)

The MMU sits inside the core, in the memory stage of the pipeline
(chapter 11). Every load, store and instruction fetch goes through it.

Pages: the unit of mapping

Mapping every byte individually would need a table larger than memory. So the address space is divided into fixed-size pages, and only the page number is translated.

   virtual address                     physical address
  ┌────────────────┬──────────┐       ┌────────────────┬──────────┐
  │  page number   │  offset  │       │  frame number  │  offset  │
  └───────┬────────┴──────────┘       └───────▲────────┴─────▲────┘
          │                                   │              │
          └──── translated by the MMU ────────┘              │
                                                             │
                          offset passes through UNCHANGED ───┘

Page size 4 KB  -> offset is 12 bits
Page size 16 KB -> offset is 14 bits
Page size 64 KB -> offset is 16 bits

Because the offset is untranslated, the low bits of a virtual and a
physical address are IDENTICAL. This single fact is what makes VIPT
caches possible (chapter 14) - the cache can start its lookup before
translation finishes.

Choosing a page size

Small pages (4 KB)Large pages (2 MB, 1 GB)
Internal fragmentationLow — little waste per allocationHigh — a 1-byte allocation can pin 2 MB
Page table sizeLarge — many entriesSmall
TLB reachPoor — 1024 entries cover 4 MBExcellent — 1024 entries cover 2 GB
Fault granularityFine — demand paging works wellCoarse — one fault pulls in 2 MB
Typical useGeneral purposeDatabases, VMs, the kernel's own linear map, ML workloads

Most systems support several sizes simultaneously — Linux calls the large ones huge pages, ARM calls the intermediate levels blocks. The trade-off is always fragmentation against TLB reach.

Page tables

A flat array indexed by page number is the obvious design and is immediately impossible:

  48-bit address space, 4 KB pages
      2^48 / 2^12 = 2^36 pages = 68,719,476,736 entries
      x 8 bytes each = 512 GB of page table.  Per process.

The fix: exploit sparseness. Almost all of that space is unmapped, so
use a MULTI-LEVEL tree and simply omit the empty subtrees.

  VA[47:39] -> L0 entry -> points to an L1 table  (or is INVALID)
  VA[38:30] -> L1 entry -> points to an L2 table
  VA[29:21] -> L2 entry -> points to an L3 table
  VA[20:12] -> L3 entry -> the physical frame + permissions
  VA[11:0]  -> offset within the frame

A process using 8 MB needs only a handful of tables, not 512 GB.
An INVALID entry at any level prunes an entire subtree in one step.
StructureHow it worksTrade-off
Multi-level (radix) treeFixed fan-out per level, indexed by address bitsThe universal choice: x86-64, ARM, RISC-V. Cost is one memory access per level on a miss.
Inverted page tableOne entry per physical frame, hashed by VASize proportional to RAM, not address space. Awkward for shared memory. Used historically on PowerPC.

What an entry carries besides an address

A translation entry is not just a pointer. The permission and attribute bits are where most of the architecture's power lives:

FieldPurposeWhat it enables
ValidIs this mapping present?Demand paging, swap, lazy allocation
Read / WriteAccess permissionRead-only data, copy-on-write
Execute-neverMay instructions be fetched here?W^X — the single most effective anti-exploit measure
PrivilegeUser-accessible, or kernel only?The user/kernel boundary itself
Accessed / DirtyHas it been read? written?Page replacement policy; knowing what must be written back
Memory attributesCacheable? Device? Shareable?MMIO correctness, DMA buffers (ARM ch. 11)
Global / ASIDShared across processes, or taggedAvoiding a full TLB flush on context switch
The insight worth carrying forward

Protection and translation are the same mechanism. The hardware must consult the table on every access to find the physical address, so checking permissions at the same time is free. That is why virtual memory is the foundation of process isolation rather than a separate feature — and why a system without an MMU (a Cortex-M) needs an entirely different protection scheme, the MPU.

The TLB

A four-level walk costs four memory accesses. Doing that on every load would make every access five times slower. So translations are cached in the Translation Lookaside Buffer.

  Typical structure

    L1 TLB    32-64 entries, fully associative, ~1 cycle
              often split: separate iTLB and dTLB
    L2 TLB    1024-2048 entries, set-associative, ~10 cycles
    miss      -> hardware page table walker -> up to 4 memory accesses
                 (each of which may itself hit or miss in the caches)

  TLB reach = entries x page size
    1024 entries x 4 KB  =   4 MB   <- easily exceeded
    1024 entries x 2 MB  =   2 GB   <- why huge pages help so much

  A TLB miss on a workload with a large random working set can cost
  more than the cache miss that follows it.

Context switches and tagging

Each process has its own mapping, so naively a context switch invalidates every TLB entry — and the new process then takes hundreds of misses warming it back up. Two mechanisms avoid this:

  • Address space identifiers. Tag each entry with the owning process (ARM calls it ASID, x86 calls it PCID). Entries from several processes coexist; a switch just changes the current tag.
  • Global entries. Kernel mappings are identical in every process, so they are marked global and match regardless of tag — no reload after a system call.
Software must invalidate; hardware will not notice

The TLB is a cache with no coherence protocol. If you modify a page table entry, the stale translation lives on until you explicitly invalidate it. On a multi-core system you must invalidate on every core that might hold it — a "TLB shootdown", which on ARM is a broadcast TLBI and on x86 requires an inter-processor interrupt. Forgetting this produces the classic "works on one core, fails on four" bug, and shootdown cost is a real scalability limit for munmap-heavy workloads.

Page faults: the useful exception

A translation failure traps to the OS, which decides what it means. Most faults are not errors — they are how features get implemented.

FaultOS responseFeature it implements
Valid bit clear, page is on diskRead it in, update the entry, retryDemand paging and swap
Valid bit clear, never touchedAllocate a zero page nowLazy allocation — why malloc of 1 GB is instant
Write to a read-only shared pageCopy it, make the copy writable, retryCopy-on-write — why fork() is cheap
Access flag clearSet it and retryTracking which pages are in use, for replacement
Write to a clean pageSet dirty, retryKnowing which pages need writing back
Genuinely unmapped, or permission violationSIGSEGV / bug checkProtection — catching the actual bug
 
The demand-paging round trip

  1. Instruction issues a load             VA -> MMU
  2. TLB miss -> page table walk
  3. Entry invalid -> PAGE FAULT exception, precise
  4. Hardware saves the faulting address and cause, enters the OS
  5. OS looks up its own record of what SHOULD be at that address
  6. Allocates a frame, reads from disk if needed, writes the entry
  7. Invalidates the stale TLB entry
  8. Returns from the exception
  9. The SAME instruction re-executes, and now succeeds

Step 9 is why the exception must be PRECISE (chapter 11). The core
must be able to restart the faulting instruction as though nothing
had happened - which constrains the whole out-of-order design.

What the indirection buys, beyond protection

Protection is the reason virtual memory was invented, but it turned out to enable a series of other things that would otherwise be impossible or expensive. Each row below is a feature you have almost certainly used without realising it was the MMU doing the work.

CapabilityMechanism
Shared librariesOne physical copy of libc mapped into every process at whatever address suits it
Memory-mapped filesFile pages mapped directly; reads become faults, writes become dirty pages
Guard pagesAn unmapped page below each stack turns overflow into a clean fault instead of silent corruption
ASLRRandomised mapping addresses make exploit gadget locations unpredictable
Contiguity from fragmentsPhysically scattered frames appear as one contiguous buffer
OvercommitPromise more address space than you have RAM, back it only on use
VirtualisationA second translation stage under the first (ARM ch. 16)
Device isolationThe same idea applied to DMA — the IOMMU (security ch. 02)

And what it costs

  • Latency on every access, hidden by the TLB but never zero.
  • Memory for the tables themselves, plus the walker's own cache pressure.
  • Determinism. A page fault can take microseconds to milliseconds. This is why hard real-time systems lock pages (mlockall) or avoid an MMU entirely — see OS chapter 19.
  • Shootdown cost on many-core systems.
  • A side channel. Timing differences between mapped and unmapped pages leak layout information, which is what defeats naive ASLR.

Seeing it on a real system

Virtual memory is easy to treat as an abstraction you never see. In fact the mapping is fully visible from user space, and looking at a real process's memory map makes the mechanism concrete in a way no diagram does.

# the virtual layout of a running process
cat /proc/self/maps
#   aaaab7c40000-aaaab7c48000 r-xp 00000000 fe:01 1234  /usr/bin/cat
#   aaaab7c57000-aaaab7c58000 r--p 00007000 fe:01 1234  /usr/bin/cat
#   ffff9c7f0000-ffff9c811000 r-xp 00000000 fe:01 5678  /lib/ld-linux.so
#   ffffe3d21000-ffffe3d42000 rw-p 00000000 00:00 0     [stack]
#              ^ permissions: r/w/x and p=private or s=shared

# per-page physical detail
cat /proc/self/smaps            # Rss, Pss, dirty pages, huge pages per mapping

# fault counts: minor = no disk, major = disk read required
/usr/bin/time -v ./program 2>&1 | grep -i fault
ps -o min_flt,maj_flt -p $$

# TLB pressure
perf stat -e dTLB-load-misses,iTLB-load-misses,dtlb_walk,itlb_walk ./program
