QEMU with KVM on real hardware

Switching from TCG to KVM changes one flag and everything else: speed goes up a hundredfold, timing becomes meaningful, and every debugging tool that depended on QEMU seeing each instruction stops working. This chapter covers the switch, what you gain, what you lose, and how to set up a machine that serves both.

Making the switch

# The requirement: guest architecture == host architecture, and
# the CPU must have reached EL2 at boot (virt chapter 3).

$ ls -l /dev/kvm
crw-rw---- 1 root kvm 10, 232 /dev/kvm
$ sudo usermod -aG kvm $USER      # then log out and back in

$ dmesg | grep -i kvm
[    0.512430] kvm [1]: Hyp mode initialized successfully
[    0.512461] kvm [1]: VHE mode initialized successfully

# TCG, for reference:
$ qemu-system-aarch64 -M virt -cpu cortex-a57 -m 2G -nographic \
    -kernel Image -append "console=ttyAMA0"

# KVM. Three changes:
$ qemu-system-aarch64 -M virt,gic-version=host -cpu host \
    -accel kvm -smp 4 -m 2G -nographic \
    -kernel Image -append "console=ttyAMA0"

#   -accel kvm            use the hardware
#   -cpu host             pass the real CPU through. Any other
#                         -cpu value under KVM either fails or
#                         silently gives you the host CPU anyway
#                         - KVM cannot emulate a different core.
#   gic-version=host      match the real interrupt controller.
#                         A mismatch fails at startup.

# Fall back automatically, for a script that must work on both:
-accel kvm -accel tcg
# QEMU tries them in order and uses the first that initialises.

What you gain and lose

TCGKVM
Speed10–50x slower than nativeNear native
Cross-architectureYesNo
-d in_asm, -d exec, -d cpuWorksNothing — QEMU never sees the instructions
TCG pluginsWorksUnavailable
-icount, record/replay, reverse debuggingWorksUnavailable
GDB stubFullWorks, but breakpoints use hardware debug registers and are limited in number
WatchpointsUnlimited, softwareLimited to the CPU's watchpoint registers
-d int, -d mmuFull detailOnly what KVM traps
--trace on device modelsWorksWorks — device models still run in QEMU
Monitor info registers, x, savevmWorksWorks
Timing realismMeaninglessRoughly meaningful
Race reproductionPoor — ordering is too strongReal
Emulated CPU features-cpu max gives you anythingOnly what the silicon has
Use both, deliberately

Develop under TCG on your laptop, where -d exec, plugins and reverse debugging exist and where you can pretend to have an SoC that does not. Validate under KVM on real arm64 hardware, where timing is real and races reproduce. A bug found only under KVM is a timing bug; a bug found only under TCG is usually a logic bug you got lucky about on hardware. Both are worth finding.

Setting up an arm64 host

# Options, cheapest first:
#   Raspberry Pi 5 / Orange Pi 5 - works, slow-ish, ~$80
#   Apple silicon Mac + Asahi Linux or a Linux VM under
#      Virtualization.framework (nested, see below)
#   An Ampere/Graviton cloud instance - the easiest path;
#      c7g/t4g on AWS, or Oracle's free-tier Ampere
#   Any arm64 server board

# 1. Confirm EL2. THIS IS THE ONE THAT FAILS.
$ dmesg | grep -i 'CPU.*started at'
[    0.000000] CPU: All CPU(s) started at EL2       # good
[    0.000000] CPU: All CPU(s) started at EL1       # no KVM,
                                                    # ever
# On a Raspberry Pi, EL2 requires:
$ grep -q '^arm_64bit=1' /boot/firmware/config.txt
$ echo 'arm_control=0x200' | sudo tee -a /boot/firmware/config.txt
# (older firmwares; newer ones start at EL2 by default)

# 2. Packages
$ sudo apt install qemu-system-arm qemu-utils \
      bridge-utils libvirt-daemon-system virtinst

# 3. Permissions
$ sudo usermod -aG kvm,libvirt $USER

# 4. Hugepages, worth doing (virt chapter 21)
$ echo 2048 | sudo tee /proc/sys/vm/nr_hugepages
$ echo 'vm.nr_hugepages=2048' | sudo tee -a /etc/sysctl.conf

# 5. Memlock limit, needed for passthrough
$ sudo tee /etc/security/limits.d/kvm.conf <<'EOF'
@kvm  soft  memlock  unlimited
@kvm  hard  memlock  unlimited
EOF

# 6. Verify end to end
$ qemu-system-aarch64 -M virt,gic-version=host -cpu host \
    -accel kvm -smp 2 -m 1G -nographic \
    -kernel Image -append "console=ttyAMA0"
# Kernel boot in under a second = KVM is working. Twenty
# seconds = you are still on TCG.

Nesting, so you can develop hypervisors

# To run KVM INSIDE a guest (virt chapter 20), the guest needs
# EL2:

$ qemu-system-aarch64 -M virt,virtualization=on \
    -cpu host,el2=on -accel kvm -smp 4 -m 4G ...

# Inside that guest:
$ dmesg | grep -i 'started at'
[    0.000000] CPU: All CPU(s) started at EL2
$ ls /dev/kvm
# ...and you can run a third-level VM.

# On the HOST, nested support must be enabled:
#   kernel command line: kvm-arm.mode=nested
# and the hardware needs FEAT_NV2 for it to be usable rather
# than merely possible.

# Under TCG there is no such restriction - -cpu max always has
# EL2, and nested virtualisation "works" at TCG speed. That is
# often the right way to develop a hypervisor: correctness
# under TCG with full tracing, performance under KVM later.

$ qemu-system-aarch64 -M virt,virtualization=on,secure=on \
    -cpu max -accel tcg -smp 2 -m 2G -nographic \
    -kernel my-hypervisor.elf -s -S
# EL3, EL2, S-EL2, single-steppable, fully traceable, on a
# laptop. No hardware in the world gives you that.

libvirt, when you have more than a couple of VMs

# Hand-written command lines stop scaling around the third VM.
# libvirt gives you persistence, autostart, networking and a
# stable API - and it is just generating the same QEMU command
# line underneath.

$ virt-install \
    --name test-arm64 \
    --memory 2048 --vcpus 4 \
    --arch aarch64 --machine virt \
    --cpu host-passthrough \
    --boot uefi \
    --disk path=/var/lib/libvirt/images/test.qcow2,size=20 \
    --network network=default,model=virtio \
    --graphics none --console pty,target_type=serial \
    --os-variant debian12 \
    --location http://deb.debian.org/debian/dists/bookworm/main/installer-arm64/

$ virsh list --all
$ virsh start test-arm64
$ virsh console test-arm64          # Ctrl-] to leave
$ virsh edit test-arm64             # the XML
$ virsh dumpxml test-arm64

# See the command line libvirt actually built - useful when you
# need to reproduce something by hand:
$ virsh domxml-to-native qemu-argv --domain test-arm64

# Pin vCPUs, for latency work:
$ virsh vcpupin test-arm64 0 4
$ virsh emulatorpin test-arm64 8-11

# Hugepages, in the XML:
#   <memoryBacking><hugepages/></memoryBacking>

Confirming you are actually getting KVM speed

# The three-second check: boot time.
$ time qemu-system-aarch64 -M virt,gic-version=host -cpu host \
    -accel kvm -smp 4 -m 2G -nographic -kernel Image \
    -append "console=ttyAMA0 panic=1" -no-reboot
# under a second to userspace = KVM

# Confirm from inside the guest:
$ dmesg | grep -i 'paravirt\|hypervisor\|KVM'
$ lscpu | grep -i hypervisor
Hypervisor vendor:  KVM

# Exit rate - the number that predicts performance (virt
# chapter 21):
$ sudo perf kvm --host stat live

# Compare like for like:
$ sysbench cpu --threads=4 run          # in the guest
$ sysbench cpu --threads=4 run          # on the host
# Within 5% = KVM working properly. 50x slower = TCG.

# The most common cause of "KVM is slow": it is not KVM.
$ ps aux | grep qemu | grep -o 'accel [a-z]*'
Migration and -cpu host

-cpu host exposes the exact silicon, so a VM started on one CPU model cannot migrate to another. If migration matters, choose a named CPU model that both machines support and accept the lost features. If it does not — which is the case for all development work — use host and get everything.

How it shows up

SymptomCause
Could not access KVM kernel module: Permission deniedNot in the kvm group, or you did not log out after being added
KVM not supported for this targetGuest and host architectures differ
kvm [1]: HYP mode not availableBooted at EL1; firmware consumed EL2

Guest is slow despite -accel kvmCheck it actually initialised; QEMU may have fallen back to TCG if you listed both

Too many breakpointsKVM uses hardware debug registers; there are only a handful
Guest cannot see a CPU featureUnder KVM you get the real silicon only; use TCG with -cpu max
