The A64 instruction set

You do not need to memorise a thousand instructions. You need to recognise the dozen families, know the idioms the compiler emits constantly, and be able to look up the rest. This chapter is the working subset.

The families

This is a reference table, not something to memorise in order — the point of laying it out this way is to show that AArch64's several hundred mnemonics are actually a small number of operations (move, compute, branch, load/store, synchronise) repeated across a few data types and addressing variants. Once you recognise a family, an unfamiliar mnemonic inside it is usually guessable: UBFX extracts an unsigned bitfield the way SBFX extracts a signed one, and CSINC behaves like CSEL with an increment folded in. The chapters linked in the notes column go deep on the families that have real subtlety; the rest you can look up when you meet them in disassembly.

Building constants

A 64-bit constant does not fit in a 32-bit instruction, so getting one into a register takes more thought than it appears. The architecture offers several mechanisms, and which the compiler picks tells you something about the value.

/* A 32-bit instruction cannot hold a 64-bit immediate, so large
   constants are assembled from 16-bit pieces.                */

        movz    x0, #0x1234, lsl #48    // zero the rest, set bits 63:48
        movk    x0, #0x5678, lsl #32    // keep the rest, set bits 47:32
        movk    x0, #0x9abc, lsl #16
        movk    x0, #0xdef0             // x0 = 0x123456789abcdef0

        movn    x0, #0                  // MOVe Negated: x0 = ~0 = -1

/* The assembler's `MOV Xd, #imm` picks whichever of MOVZ, MOVN or
   an ORR-with-bitmask-immediate encodes the value, or emits
   several instructions if none does.                         */

/* BITMASK IMMEDIATES are a genuinely clever encoding: logical
   instructions can take any value that is a repeating pattern of
   set bits. So these are ONE instruction each:               */
        and     x0, x0, #0xFFFFFFFF     // repeating pattern ✓
        orr     x0, x0, #0x0F0F0F0F0F0F0F0F
        and     x0, x0, #0xFFF          // ✓
/* ...but this needs a MOV first, because 0x12345 is not a
   repeating pattern:                                          */
        mov     x1, #0x12345
        and     x0, x0, x1

/* This is why some masks compile to one instruction and visually
   similar ones compile to two. It is not arbitrary.          */

Branches

The variety here exists because branches are the instructions where range and flag dependency both cost something real: a wider range needs more encoding bits, and testing flags before every branch means an extra instruction when the condition is something as simple as "is this pointer NULL". CBZ and TBZ exist specifically to remove that extra compare for the two most common cases — testing a whole register against zero, and testing one bit — at the cost of a much shorter reach than a conditional branch. The range column is the thing to actually pay attention to: a linker error about a branch being out of range is almost always this table in disguise.

CBZ/CBNZ Xn, labelCompare with zero and branch — no flags needed±1 MB

/* CBZ and TBZ are very common because they need no CMP first: */
        cbz     x0, is_null              // if (p == NULL) goto...
        tbnz    w1, #5, bit_set          // if (flags & (1 << 5)) goto...

/* RET is BR X30 with a hint. The hint matters: it tells the
   return-address stack predictor to POP, which is why using
   BR X30 instead of RET degrades prediction (CA chapter 12). */

/* The ±128 MB limit on B/BL is why LINKER VENEERS exist: if a
   call target is further away, the linker inserts a trampoline
   that loads the full address into X16 and does BR X16. That is
   what X16/X17 are reserved for (chapter 04).                */

Conditional select: the branchless workhorse

Since predication was removed, the architecture needs another way to avoid branching on simple decisions. Conditional select is that way, and it is one of the most common instructions in optimised ARM code for a reason worth understanding.

        csel    Xd, Xn, Xm, cond    // Xd = cond ? Xn : Xm
        csinc   Xd, Xn, Xm, cond    // Xd = cond ? Xn : Xm + 1
        csinv   Xd, Xn, Xm, cond    // Xd = cond ? Xn : ~Xm
        csneg   Xd, Xn, Xm, cond    // Xd = cond ? Xn : -Xm

/* And their aliases, which are what you usually see: */
        cset    Xd, cond            // Xd = cond ? 1 : 0
        csetm   Xd, cond            // Xd = cond ? -1 : 0   ← a MASK
        cinc    Xd, Xn, cond        // Xd = cond ? Xn+1 : Xn
        cneg, cinv

/* Source and result: */
int max(int a, int b) { return a > b ? a : b; }
/*      cmp     w0, w1
        csel    w0, w0, w1, gt
        ret                                                  */

int sign(int x) { return (x > 0) - (x < 0); }
/*      cmp     w0, #0
        cset    w1, gt
        csinv   w0, w1, wzr, ge      // clever: -1 when negative
        ret                                                  */

/* CSETM is exactly the mask idiom from C chapter 08:
        mask = -(unsigned)cond;   → csetm
   which is why branchless C compiles so cleanly here.      */

Bitfield instructions

Extracting and inserting bitfields is so common in systems code that the architecture provides dedicated instructions for it. They have famously cryptic names, and recognising what they actually do makes a lot of disassembly suddenly readable.

/* ARM does field extract and insert in ONE instruction, which is
   why the mask-and-shift idioms of C chapter 08 are cheap.  */

        ubfx    w0, w1, #4, #3       // w0 = (w1 >> 4) & 0x7  (unsigned)
        sbfx    w0, w1, #4, #3       // ...sign-extended
        bfi     w0, w1, #4, #3       // insert w1's low 3 bits at 4
        bfxil   w0, w1, #4, #3       // extract and insert low
        ubfiz   w0, w1, #4, #3       // extract, insert, zero the rest

/* Extensions are also bitfield ops: */
        uxtb    w0, w1               // zero-extend byte
        sxtw    x0, w1               // sign-extend word to 64
        lsl     x0, x1, #3           // alias of UBFM

/* Bit counting and reversal, all single instructions: */
        clz     x0, x1               // count leading zeros
        rbit    x0, x1               // reverse bit order
        rev     x0, x1               // reverse BYTE order (endian swap)
        rev16, rev32
        cnt     v0.8b, v1.8b         // popcount, per byte (SIMD)

/* __builtin_clz → CLZ.  __builtin_bswap32 → REV.
   __builtin_ctz → RBIT then CLZ. This is why those builtins are
   free on ARM and you should always prefer them (C ch. 08). */

Arithmetic worth knowing

Beyond add and subtract, a handful of arithmetic instructions appear constantly in compiled code. Each exists because it collapses a sequence that would otherwise take several instructions.

/* Multiply-accumulate in one instruction — the basis of every
   DSP and matrix kernel:                                     */
        madd    x0, x1, x2, x3       // x0 = x3 + x1 * x2
        msub    x0, x1, x2, x3       // x0 = x3 - x1 * x2
        mneg    x0, x1, x2           // x0 = -(x1 * x2)

/* Widening multiply: 32x32 → 64, no overflow */
        umull   x0, w1, w2
        smull   x0, w1, w2
        umulh   x0, x1, x2           // HIGH 64 bits of a 64x64 product
        smulh   x0, x1, x2

/* Division is NOT cheap — roughly 10-20 cycles, and there is no
   remainder instruction. `a % b` becomes:                    */
        sdiv    x2, x0, x1
        msub    x2, x2, x1, x0       // x2 = x0 - (x0/x1)*x1

/* Which is why dividing by a constant compiles to a multiply by
   a magic reciprocal plus shifts, and why power-of-two divisors
   become a single shift.                                     */

/* Shifted register operands are free — folded into the ALU: */
        add     x0, x1, x2, lsl #3   // x0 = x1 + (x2 << 3)
        sub     x0, x1, x2, asr #2
/* This is how array indexing compiles: base + index*8 is ONE
   instruction, not two.                                      */

System instructions

Everything above this point works identically whether you are writing a userspace program or a kernel. This group is different: these are the instructions that exist because software sometimes needs to talk to the architecture itself rather than to data — asking to enter a more privileged level (SVC/HVC/SMC), asking to leave one (ERET), asking the core to stop doing anything until something interesting happens (WFI/WFE), or asking it to deliberately trap (BRK/UDF). Most application code never executes any of them directly; a kernel, hypervisor or debugger uses most of this table constantly.

YIELDA hint that this thread is spinning; useful on SMT

/* The WFE/SEV spinlock idiom — spin without burning power: */
1:      ldaxr   w1, [x0]
        cbnz    w1, 2f              // locked? go wait
        stxr    w2, w3, [x0]
        cbnz    w2, 1b
        ...                          // got it
2:      wfe                          // sleep until an event
        b       1b
/* The unlock does SEV (or a store-release, which generates an
   event on the exclusive monitor). This is why ARM spinlocks
   consume far less power than a naive busy loop.            */

Compiler idioms you will see constantly

Compilers emit a small vocabulary of recurring instruction sequences. Learning to recognise them means you stop decoding disassembly instruction by instruction and start reading it in phrases.

Learn to recognise these on sight — they cover most disassembly:

  stp x29, x30, [sp, #-N]!     function prologue
  mov x29, sp
  ldp x29, x30, [sp], #N       epilogue
  ret

  adrp x0, sym                 global variable access
  add  x0, x0, :lo12:sym       (or the offset folded into the LDR)

  cmp  w0, w1                  comparison + branchless select
  csel w0, w0, w1, gt

  ldr  x0, [x1, x2, lsl #3]    array[i] for 8-byte elements

  cbz  x0, .Lnull              null check

  bl   memcpy                  a struct copy the compiler lowered

  ld1 {v0.4s}, [x0], #16       vectorised loop body
  fadd v0.4s, v0.4s, v1.4s
  st1 {v0.4s}, [x1], #16

  nop                          a patch point: static keys, ftrace,
                               or alternative instruction patching

Looking things up

Nobody remembers the whole instruction set. What matters is being able to find the exact definition of an instruction quickly and trust what you find.

# the fastest reference loop
#   godbolt.org — paste C, see the assembly, hover for docs
#   developer.arm.com/documentation — searchable A64 ISA guide

# locally
aarch64-linux-gnu-objdump -d prog | less
gcc -O2 -S -o - test.c

# decode a single instruction word
echo '.word 0xd65f03c0' > t.s && as -o t.o t.s && objdump -d t.o
#   d65f03c0  →  ret

# the ARM ARM's index of instructions by encoding is section C6.
# When you meet an unfamiliar mnemonic, search there rather than
# guessing from the name — several are aliases of something else.
