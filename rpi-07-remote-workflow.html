A remote development workflow that scales

Editing over SSH in vi works for one file and collapses at ten. The goal is an edit-build-run loop measured in seconds, where your editor and version control live on your laptop and the code executes on the board — without you thinking about the gap.

Four workflows, and when each fits

WorkflowEditBuildGood for
Edit on Pi over SSHPiPiOne-file fixes, emergencies, a board with no network path to your host
Sync then build remotelyHostPiThe default for this track. Simple, robust, no sysroot
Editor remote modeHost UI, Pi filesPiComfortable, full IDE features, one dependency on the editor
Cross-build then deployHostHostKernels, CI, large C++ (chapter 06)
Version control lives on the host, always

Whichever workflow you pick, the git repository belongs on your laptop and the Pi holds a working copy that you can destroy without a thought. A board is a device that gets reimaged, corrupted by a power cut, or bricked by your own kernel module — and code that exists only there will eventually be lost. This one rule also keeps you honest: if the Pi has uncommitted state you cannot reproduce, you have a problem regardless of tooling.

The sync-and-build loop

# The workhorse. rsync sends only what changed, over the
# connection ~/.ssh/config already holds open (chapter 04).

$ rsync -az --delete \
    --exclude '.git' --exclude 'build/' --exclude '*.o' \
    ./ pi:~/proj/
$ ssh pi 'make -C ~/proj -j4 && ~/proj/app'

# Wrap it once and stop typing it:
cat > push.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
rsync -az --delete --exclude '.git' --exclude 'build/' \
      ./ pi:~/proj/
ssh pi "make -C ~/proj -j4 ${1:-} && ~/proj/app"
EOF
chmod +x push.sh

# MAKE IT AUTOMATIC. Re-run on every save:
$ sudo apt install entr            # or: brew install entr
$ find . -name '*.c' -o -name '*.h' -o -name Makefile | \
      entr -c ./push.sh

# Now saving a file in your editor rebuilds and runs on the
# Pi, with output in your terminal, in about a second. That
# loop is the whole point of this chapter - everything else
# here is a variation on it.

# For a one-off run without the sync:
$ ssh pi 'uname -a; vcgencmd measure_temp'

# rsync FROM the Pi, for logs and captured data:
$ rsync -az pi:~/proj/logs/ ./logs/

Mounting the Pi's filesystem

# sshfs makes the Pi's directory appear locally. Your editor
# sees ordinary files; no sync step exists at all.

$ sudo apt install sshfs
$ mkdir -p ~/mnt/pi
$ sshfs pi:/home/myuser ~/mnt/pi \
      -o reconnect,ServerAliveInterval=15,ServerAliveCountMax=3
$ fusermount -u ~/mnt/pi          # unmount

# HONEST ASSESSMENT: convenient for browsing and single-file
# edits, poor for anything that touches many files. Every
# stat() is a network round trip, so:
#   - grep across a tree is painfully slow
#   - git status in a mounted repo can take minutes
#   - a build reading hundreds of headers crawls
#   - a dropped link mid-write can truncate a file
#
# Use it to LOOK at the Pi, not to work on it. The reverse
# direction is better:

# NFS EXPORT FROM YOUR HOST, mounted on the Pi. Now the Pi
# builds from your laptop's disk, and your editor is purely
# local and fast:
#   host /etc/exports:
#     /home/me/proj  192.168.1.50(rw,sync,no_subtree_check)
$ sudo exportfs -ra
#   on the Pi:
$ sudo mount -t nfs 192.168.1.10:/home/me/proj /mnt/proj

# This is genuinely good: local editing speed, no sync step,
# and the build happens on the target. The cost is one NFS
# export to configure and a dependency on the network being
# up. For kernel module work (chapter 16) it is excellent.

Editor remote modes

# VS Code "Remote - SSH" installs a small server on the Pi
# and runs the UI locally. Full IntelliSense, debugging,
# terminal, extensions - against files on the board.

#   Ctrl-Shift-P -> Remote-SSH: Connect to Host -> pi
# It reads your ~/.ssh/config, so "pi" from chapter 04 just
# appears in the list.

# WHAT TO KNOW:
#   - the server is ~200 MB in ~/.vscode-server on the Pi.
#     On a small SD card this matters.
#   - it is a real background process using RAM and CPU. On
#     a 1 GB Pi 4 it competes with your build.
#   - the C/C++ extension's IntelliSense parses your
#     includes ON THE PI, which is slow the first time and
#     fine afterwards.
#   - it reconnects after a reboot, which is the single
#     nicest thing about it for embedded work.

# .vscode/c_cpp_properties.json so IntelliSense resolves
# kernel headers for chapter 16's module work:
{
  "configurations": [{
    "name": "Pi",
    "includePath": [
      "${workspaceFolder}/**",
      "/lib/modules/${env:KVER}/build/include",
      "/lib/modules/${env:KVER}/build/arch/arm64/include"
    ],
    "defines": ["__KERNEL__", "MODULE"],
    "compilerPath": "/usr/bin/gcc",
    "cStandard": "c11",
    "intelliSenseMode": "linux-gcc-arm64"
  }],
  "version": 4
}

# NEOVIM / EMACS users: both have equivalents (distant.nvim,
# TRAMP). TRAMP in particular has been doing this since
# before it was fashionable and works well over the
# multiplexed SSH connection from chapter 04.

Deploying like a product, not a demo

# Copying a binary into ~/ works until you have a service,
# a config file, a udev rule and a device tree overlay. At
# that point, build a package. Even a crude one.

# A minimal .deb, which apt can install, upgrade and remove
# cleanly - and which forces you to declare where every
# file belongs:
myapp/
  DEBIAN/
    control
    postinst
  usr/bin/myapp
  usr/lib/systemd/system/myapp.service
  etc/udev/rules.d/99-myapp.rules
  boot/firmware/overlays/myapp.dtbo

$ cat myapp/DEBIAN/control
Package: myapp
Version: 0.1.0
Architecture: arm64
Maintainer: you <you@example.com>
Depends: libgpiod2
Description: sensor daemon

$ dpkg-deb --build myapp
$ scp myapp.deb pi: && ssh pi 'sudo apt install -y ./myapp.deb'

# WHY BOTHER, on a development board:
#   - uninstall actually removes everything, so "it works on
#     my Pi" stops being a mystery of leftover files
#   - you find out now which files need root, which need a
#     udev rule, and what the dependencies really are
#   - reimaging becomes cheap: install one package and the
#     board is configured
#   - it is what you will have to do eventually anyway

# A systemd unit, so the thing starts on boot and restarts
# when it dies:
[Unit]
Description=sensor daemon
After=network.target

[Service]
ExecStart=/usr/bin/myapp
Restart=on-failure
RestartSec=2
User=sensord
SupplementaryGroups=gpio i2c
# Least privilege: this daemon does not need root, and
# saying so here is cheaper than discovering later that it
# assumed root everywhere.
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes

[Install]
WantedBy=multi-user.target
Two Pis are much better than one

The moment you start writing kernel modules or editing config.txt, you will have a board that does not boot. If that board is also the one holding your notes, your other project and your working environment, a five-minute experiment becomes an evening. A second Pi — even an older model — as the "break it" board changes how freely you experiment, which is the actual skill this track is trying to build. Failing that, the second SD card from chapter 01 serves the same purpose.
