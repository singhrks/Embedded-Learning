Virtualisation, containers and isolation

Three different answers to "run this workload without letting it interfere with that one" — with three very different isolation strengths and costs. This chapter closes the OS track by making the trade-off explicit.

The isolation spectrum

"Virtualisation" covers techniques from full machine emulation to little more than a directory change. Placing them on a spectrum of isolation versus overhead is what makes the choice between them rational.

weaker isolation, lower cost ──────────► stronger, higher cost

  (the kernel)    (the kernel)    (hypervisor)

The whole argument between containers and VMs is that middle row:
a container escape needs one kernel bug; a VM escape needs a
hypervisor bug, and there is far less hypervisor to get wrong.

Virtual machines

A virtual machine gives a guest operating system the illusion of owning hardware. What makes that both possible and efficient is hardware support that traps exactly the operations that would break the illusion.

TypeRuns onExamples
Type 1 (bare metal)Directly on hardwareXen, Hyper-V, ESXi, Jailhouse, Hafnium
Type 2 (hosted)On a host OSVirtualBox, VMware Workstation, QEMU/TCG
HybridA host kernel module becomes the hypervisorKVM — Linux is both host OS and Type 1 hypervisor
 
The three things a hypervisor must virtualise:

  CPU     the guest kernel expects to run privileged instructions.
          Modern hardware makes this cheap: the guest runs at EL1
          natively, and only "sensitive" operations TRAP to EL2.
          (ARM VHE, Intel VT-x, AMD-V)

  MEMORY  the guest believes it owns physical memory. A SECOND
          translation stage maps guest-physical (IPA) to real
          physical, owned by the hypervisor and unchangeable by
          the guest.
              guest VA ─[stage 1, guest]─► IPA ─[stage 2, HV]─► PA
          ARM chapter 16 covers the mechanics.

  I/O     the guest programs devices that do not exist.
          Either emulate them, paravirtualise them, or hand over
          a real one (below).

How a trap works

/* The guest kernel writes to what it believes is a UART register. */

        writel(1, uart_base + UART_CR);      /* guest, at EL1 */

/* 1. stage-1 translation: guest VA → IPA, using the guest's own
      page tables. Succeeds — the guest mapped it.
   2. stage-2 lookup of that IPA in VTTBR_EL2. The hypervisor
      deliberately left it UNMAPPED.
   3. stage-2 data abort → taken to EL2, not EL1.
   4. the hypervisor reads:
          HPFAR_EL2   the faulting IPA — which device register
          ESR_EL2.ISS ISV/SAS/SRT/WnR — size, direction, and which
                      guest register held the value
   5. it emulates the UART in software and updates its model.
   6. it advances the guest's ELR_EL2 past the faulting
      instruction and ERETs.

   The guest never knows. This is exactly how QEMU/KVM presents
   virtual hardware — and why emulated I/O is slow: every register
   access is a full world switch.                             */

Three ways to give a VM I/O

Giving a guest access to devices is the hardest part of virtualisation, and there are three approaches with very different performance and isolation characteristics.

ApproachMechanismCostGuest needs
Full emulationTrap every register access; emulate a real device (e1000, IDE)Very high — a trap per accessNothing; stock drivers work
Paravirtualisationvirtio: a shared-memory ring plus a doorbellLow — batched, few exitsA virtio driver
PassthroughAssign the real device to the guest via the IOMMUNear zeroThe real driver; the device is exclusive
SR-IOVThe device presents multiple virtual functions, one per guestNear zeroDevice support
 
virtio is the same design as io_uring and every high-performance
IPC (OS chapter 08):

   guest driver                        host / device backend
   ┌──────────────┐                   ┌──────────────────┐
   │ available    │──── shared ───────│  reads requests  │
   │   ring       │     memory        │                  │
   │ used ring    │◄──────────────────│  writes results  │
   └──────┬───────┘                   └────────▲─────────┘
          │ doorbell: ONE MMIO write            │ interrupt
          │ per BATCH, not per request          │ (or polling)
          └─────────────────────────────────────┘

  Bulk data by shared memory; exits only when the peer needs
  waking. Recognise this shape — it is the answer to nearly every
  "cross a boundary at high rate" problem in systems design.
Passthrough requires an IOMMU, without exception

A device assigned to a guest is programmed by the guest with guest-physical addresses. Without an IOMMU translating and constraining its DMA, the device would write those addresses as real physical addresses — scribbling over the host or another guest. The IOMMU's stage-2 translation is what makes passthrough safe, and it is the single most important reason the SMMU exists. Covered fully in the security track.

Containers

A container is not a thing

There is no container object in the Linux kernel. A "container" is an ordinary process started with a particular combination of namespaces (what it can see), cgroups (what it can use) and capabilities/seccomp/LSM (what it can do). Docker and Podman are tools that assemble that combination; the kernel only sees processes.

NamespaceIsolates
mntThe mount table — its own filesystem view
pidProcess IDs — the container's init is PID 1, and it cannot see host processes
netInterfaces, routes, firewall rules, ports
utsHostname and domain name
ipcSystem V IPC and POSIX message queues
userUID/GID mapping — root inside, unprivileged outside. The one that makes rootless containers possible.
cgroupThe cgroup hierarchy view
timeBoot and monotonic clock offsets
 
# build one by hand — this IS a container
sudo unshare --pid --net --mount --uts --ipc --fork --mount-proc \
     chroot /path/to/rootfs /bin/sh

# inspect any process's namespaces
ls -l /proc/self/ns/
readlink /proc/1/ns/net /proc/$$/ns/net    # same link = same namespace

nsenter -t PID -n -m -p /bin/sh            # join an existing one
# cgroups v2 — the resource half
mkdir /sys/fs/cgroup/myapp
echo $$              > /sys/fs/cgroup/myapp/cgroup.procs
echo "200000 1000000" > /sys/fs/cgroup/myapp/cpu.max     # 20% of one CPU
echo 512M            > /sys/fs/cgroup/myapp/memory.max
echo "259:0 rbps=10485760" > /sys/fs/cgroup/myapp/io.max

cat /sys/fs/cgroup/myapp/memory.current
cat /sys/fs/cgroup/myapp/memory.events     # oom_kill counter
cat /sys/fs/cgroup/myapp/cpu.stat          # throttling counters
The container is still using the host kernel

uname -r inside a container reports the host's kernel. Consequences that surprise people constantly:

  • A kernel exploit escapes the container. This is the entire isolation argument against containers for untrusted workloads.
  • Kernel modules, sysctl settings and the clock are shared or host-controlled.
  • /proc/cpuinfo and free show host values, not the cgroup limit — which is why JVMs and thread pools historically sized themselves for 64 cores inside a 2-core container. Modern runtimes read the cgroup files; older code and hand-rolled nproc logic do not.

Narrowing what a container can do

Isolation is only as good as the boundary, and a hypervisor's attack surface is larger than it first appears. These are the measures that actually reduce it.

/* Namespaces isolate what you SEE. These restrict what you can DO. */

/* 1. Capabilities — split root's power into ~40 pieces */
capsh --print
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE ...
/* CAP_SYS_ADMIN is so broad it is effectively root — never grant it */

/* 2. seccomp — filter system calls with a BPF program */
docker run --security-opt seccomp=profile.json ...
/* Docker's default profile blocks ~44 syscalls. A tight custom
   profile is one of the highest-value hardening steps available. */

/* 3. LSM — SELinux or AppArmor mandatory access control */

/* 4. no_new_privs — setuid binaries cannot regain privilege */
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);

/* 5. USER NAMESPACES — root in the container maps to an
      unprivileged host UID. Even a container escape lands as
      nobody. This is the strongest single control, and what
      rootless Podman is built on.                            */
podman run --userns=keep-id ...

The middle ground

Between full virtual machines and plain processes sit several designs offering most of the isolation for a fraction of the overhead — which is where much of the industry has settled.

Kata ContainersEach container runs in a lightweight VMContainer UX, VM isolation; ~100 ms extra startup
FirecrackerA minimal VMM — ~50 K lines, five emulated devices~125 ms boot, ~5 MB overhead. Powers AWS Lambda.
gVisorA user-space kernel intercepting syscallsSmall kernel attack surface; syscall overhead and imperfect compatibility
WebAssemblyA sandboxed bytecode VM with capability-based I/O (WASI)Microsecond startup, tiny images; a restricted programming model
UnikernelThe application linked with only the OS functions it needsMinimal surface, fast boot; hard to debug and operate

Virtualisation in embedded systems

Virtualisation in embedded systems serves a different purpose from the cloud: not packing many workloads onto one machine, but keeping a safety-critical function isolated from a rich but untrusted one.

Not a cloud technology — increasingly standard in vehicles and
industrial equipment, for CONSOLIDATION and MIXED CRITICALITY.

   one SoC, previously several ECUs:

   ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
   │ Instrument   │ │ Infotainment │ │  Safety      │
   │ cluster      │ │              │ │  functions   │
   │ (RTOS, ASIL) │ │ (Android)    │ │ (AUTOSAR)    │
   └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
   ┌──────▼────────────────▼────────────────▼───────┐
   │  Type-1 hypervisor  (Jailhouse, Xen, QNX HV,   │
   │                      Hafnium at S-EL2)          │
   └────────────────────────┬───────────────────────┘
                            ▼
                    one multi-core SoC

  Requirements that differ from cloud virtualisation:
    · STATIC partitioning — cores, memory and devices assigned at
      build time, not scheduled dynamically
    · bounded interference: cache partitioning, memory bandwidth
      regulation. Logical isolation is not enough when guests
      share a DRAM controller (OS chapter 19).
    · certification evidence for the hypervisor itself
    · fast boot: the instrument cluster must display within ~2 s

  Jailhouse is the clearest example: it does NOT schedule at all.
  It statically partitions the machine and then gets out of the
  way, which makes its worst-case behaviour analysable.
