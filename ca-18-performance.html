Measuring performance: CPI, Amdahl and roofline

Optimisation without measurement is superstition. This chapter gives you the three models that let you predict what an optimisation is worth before you spend a week on it, and the counters that tell you where the time actually went.

The performance equation

Everything starts here. Runtime decomposes into exactly three factors, and every optimisation you will ever make attacks one of them.

                instructions       cycles          seconds
   time  =    ───────────────  ×  ────────────  ×  ────────
                  program          instruction       cycle

                     ↑                 ↑                ↑
                  algorithm,          CPI            1 / clock
                  compiler,        (the micro-        frequency
                  ISA               architecture)

Who controls each factor:

  instruction count   you (algorithm, data structures), the compiler,
                      the ISA (CISC does more per instruction)
  CPI                 the microarchitecture, but YOU influence it
                      heavily through cache and branch behaviour
  clock period        the process node, the pipeline depth, power
                      and thermal limits (chapter 20)
The trap this equation exposes

These factors are not independent, so a "win" on one can be a loss overall. Deepening the pipeline raises the clock but worsens CPI on every mispredict. A CISC instruction lowers the instruction count but may take more cycles. Vectorising cuts instruction count but may increase memory traffic. Only end-to-end wall-clock time is real. This is why "we reduced instruction count by 30%" is not a result — it is a hypothesis.

Why MIPS and clock speed are useless as comparisons

MIPS = instruction count / (runtime × 10^6)

/* Fails because: */
- a compiler that emits MORE, simpler instructions scores HIGHER
  while running slower
- different ISAs do different amounts of work per instruction
- one core at 3 GHz with CPI 4 loses to one at 2 GHz with CPI 1

/* The same applies to FLOPS in isolation, and to clock speed.
   The only honest comparison is: the same real workload,
   measured end to end, on both machines. */

CPI, and where the cycles go

The useful form splits CPI into a base plus the stalls you can attack:

   CPI = CPI_ideal + Σ (stall events per instruction × penalty)

Worked example — a memory-bound loop

   CPI_ideal                             = 0.5   (2-wide superscalar)
   L1 D-miss:   4% × 12 cycles           = 0.48
   L2 miss:     1% × 40 cycles           = 0.40
   LLC miss:    0.5% × 200 cycles        = 1.00
   branch miss: 2% × 15 cycles           = 0.30
   ─────────────────────────────────────────────
   CPI                                   = 2.68

Read the table, not the total. The LLC misses alone cost more than
everything else combined, and they are 0.5% of accesses.

Halving the LLC miss rate:      CPI 2.68 -> 2.18   (19% faster)
Perfect branch prediction:      CPI 2.68 -> 2.38   (11% faster)
Doubling the issue width:       CPI 2.68 -> 2.43   ( 9% faster)

The expensive-and-rare event wins. This is why profiling by
COUNT is misleading and profiling by COST is correct.

The reciprocal, IPC (instructions per cycle), is what most tools report. IPC above ~2 on a wide core suggests you are compute-bound; IPC below ~0.5 almost always means you are waiting on memory.

Amdahl's law: the ceiling on any optimisation

This is the most important piece of arithmetic in performance work, and the one most often ignored. It sets a hard ceiling on what any optimisation can achieve, and that ceiling is usually far lower than intuition suggests.

   If a fraction p of runtime is improved by a factor s:

                        1
   speedup  =  ──────────────────
                (1 - p) + p / s

The part you did NOT improve sets a hard ceiling:

   max speedup = 1 / (1 - p)     even with s = ∞

Examples, and the intuition they should install:

   p = 0.95, s = ∞   ->  20x     ceiling
   p = 0.90, s = ∞   ->  10x
   p = 0.75, s = ∞   ->   4x
   p = 0.50, s = ∞   ->   2x     <- half the code, infinite speedup,
                                    and you barely double performance

   p = 0.90, s = 2   ->  1.82x
   p = 0.90, s = 10  ->  5.26x
   p = 0.90, s = 100 ->  9.17x   <- 10x more effort for 1.7x more gain
What Amdahl actually tells you to do

Profile first, always. A 10× improvement to code that is 5% of runtime yields 4.7% overall. A 30% improvement to code that is 80% of runtime yields 26%. Engineers routinely spend weeks on the former because it was the interesting problem. Measure, find the largest p, and attack that — then re-measure, because the profile changes as soon as you succeed.

Gustafson's counterpoint

Amdahl assumes a fixed problem size. In practice, more capable machines get used on bigger problems, and the parallel fraction often grows with problem size while the serial part stays constant. A weather model on a 1000-core cluster does not run the same simulation faster; it runs a finer grid. Both laws are correct — they answer different questions. Ask which one your situation is: fixed work, want it sooner (Amdahl) or fixed time, want more work (Gustafson).

The roofline model

The single most useful mental model for deciding whether to optimise compute or memory.

   Arithmetic intensity  I = FLOPs performed / bytes moved from DRAM

   Attainable GFLOP/s = min( peak_compute,  I × peak_bandwidth )

  GFLOP/s
    ▲
    │                    ┌──────────────── peak compute (the flat roof)
    │                   ╱
    │                  ╱
    │                 ╱  ← the slanted roof: I × peak bandwidth
    │                ╱
    │               ╱
    │              ╱
    └─────────────┴──────────────────────────────────► arithmetic intensity
                  ▲
             ridge point:  I = peak_compute / peak_bandwidth

   LEFT of the ridge  -> MEMORY BOUND.  Faster arithmetic buys nothing.
                         Improve locality, blocking, data layout,
                         compression, or fuse operations.

   RIGHT of the ridge -> COMPUTE BOUND. Bandwidth is not the issue.
                         Vectorise, use more cores, better algorithms.
/* Compute the intensity of your kernel and place it on the roofline. */

/* vector add: c[i] = a[i] + b[i]   over floats */
   FLOPs  = 1 per element
   bytes  = 12 per element  (read a, read b, write c)
   I      = 0.083 FLOP/byte        -> deeply MEMORY BOUND

/* dot product: s += a[i] * b[i] */
   FLOPs  = 2 per element
   bytes  = 8 per element
   I      = 0.25                   -> still memory bound

/* dense matrix multiply, N x N, properly blocked */
   FLOPs  = 2 N^3
   bytes  ≈ 3 N^2  (each matrix read/written once, if it fits in cache)
   I      ≈ 2N / 3                 -> grows with N: COMPUTE bound

/* This is exactly why blocked matrix multiply is the canonical
   optimisation, and why machine-learning kernels are written as
   matrix multiplies whenever possible - it moves them to the right
   of the ridge. See AI chapter 04.                               */
A typical ridge point today

A modern core might reach 100 GFLOP/s with 25 GB/s of bandwidth per core — a ridge at I = 4 FLOP/byte. Most real code sits at I between 0.1 and 1. The majority of programs are memory bound, which is why chapters 13 to 15 matter more for performance than instruction-level tricks, and why hardware keeps adding cache rather than ALUs.

Hardware performance counters

Every modern core has a PMU that counts microarchitectural events. This is ground truth, not inference.

# the standard first look
perf stat ./program

#   12,405,281,113  cycles                    #  2.98 GHz
#   18,204,113,782  instructions              #  1.47  insn per cycle
#    3,201,554,231  branches
#       62,119,882  branch-misses             #  1.94% of all branches
#    1,905,332,110  cache-references
#      210,553,901  cache-misses              # 11.05% of cache refs

# read it in this order:
#   IPC < 0.5      -> stalled; find out on what
#   IPC 0.5 - 1.5  -> mixed
#   IPC > 2        -> compute bound; algorithmic work is next
#   branch-misses > 2%      -> chapter 12
#   cache-miss rate high    -> chapters 13-14

# then localise it
perf record -g ./program && perf report      # which functions
perf record -e cache-misses ./program        # which lines miss
perf annotate                                # which instruction

# ARM-specific detail
perf stat -e l1d_cache_refill,l2d_cache_refill,dtlb_walk,\
stall_frontend,stall_backend ./program

# stall_frontend high  -> instruction supply: I-cache, branch mispredicts
# stall_backend  high  -> data supply or execution: D-cache, dependencies

Top-down analysis

Rather than guessing, classify every issue slot into one of four buckets. Intel formalised this as Top-Down; ARM's equivalent uses the stall counters above.

   every cycle's issue slots
            │
     ┌──────┴──────┐
   retiring     not retiring
   (useful)          │
            ┌────────┼────────┐
      bad speculation      stalled
      (mispredicts,          │
       machine clears)  ┌────┴────┐
                    frontend    backend
                    bound       bound
                    (I-cache,   (D-cache, DRAM,
                     decode,     execution ports,
                     branch)     dependencies)

Whichever bucket dominates tells you which chapter to reread:
  frontend bound  -> code layout, I-cache, chapter 12
  backend bound   -> data layout, chapters 13-15
  bad speculation -> chapter 12
  retiring high   -> you are done tuning; change the algorithm

Benchmarking honestly

Most performance measurements are wrong in one of a small number of predictable ways. These are the mistakes, and avoiding them is the difference between a number you can act on and a number that merely feels authoritative.

MistakeWhy it liesFix
Measuring onceNoise from scheduling, frequency, other loadMany runs; report median and spread, not the best
Reporting the meanOne outlier dominates itMedian plus p95/p99, which is what users feel
Cold vs warm confusionFirst run pays page faults and cache missesDecide which you are measuring, and say so
Dead code eliminationThe compiler deletes work whose result is unusedConsume the result; use a benchmark framework's DoNotOptimize
Unrealistic inputTiny inputs fit in cache; sorted inputs predict perfectlyUse production-shaped data
Frequency scalingTurbo and thermal throttling move the clock mid-runPin the governor, or measure cycles rather than seconds
Ignoring variance across coresbig.LITTLE cores differ several-foldPin with taskset
Optimising the benchmarkYou improved the measurement, not the productConfirm the win on the real workload
 
# make the machine quiet before you trust a number
sudo cpupower frequency-set -g performance     # fix the governor
taskset -c 2 ./program                          # pin to one core
sudo sh -c 'echo 3 > /proc/sys/vm/drop_caches'  # cold-start measurement

# measure cycles, not seconds, when the clock may move
perf stat -e cycles,instructions -r 20 ./program   # 20 runs, with stddev

Latency versus throughput

These are different goals and optimising one routinely harms the other. Be explicit about which you are being paid for.

LatencyThroughput
QuestionHow long does one operation take?How many per second?
Improved byShorter critical path, fewer dependent steps, avoiding queuesBatching, pipelining, parallelism, larger buffers
Harmed byBatching (you wait for the batch to fill)Small transfers, per-item overhead
Report asMedian, p95, p99, maxOperations or bytes per second
Matters most forInterrupt handlers, control loops, interactive UI, RTOSBulk data, network, storage, batch compute

Little's Law connects them: L = λW — items in flight equal arrival rate times time in system. Raising throughput by adding queueing necessarily raises latency. In hard real-time work (OS chapter 19) only the worst case counts, and average throughput is irrelevant.

A workflow that works

  1. Establish a reliable measurement of the thing you actually care about. If you cannot measure it repeatably, stop here — everything downstream is guesswork.
  2. Profile to find where time goes. Use cost, not call count.
  3. Apply Amdahl to the profile. Compute the best possible payoff for each candidate before you start.
  4. Classify the bottleneck with counters or roofline: memory, compute, branch, frontend, I/O.
  5. Fix the largest one, and only that one.
  6. Re-measure. Confirm the predicted gain appeared. If it did not, your model was wrong — that is valuable information.
  7. Re-profile. The bottleneck has moved. Repeat until the remaining gain is not worth the complexity.
  8. Keep the benchmark in CI so the win does not silently regress.
