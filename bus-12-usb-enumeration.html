USB: the bus, descriptors and enumeration

USB is by far the most complex bus in this track, and the one where a microcontroller almost never implements the hard parts itself. What you must understand is the model — endpoints, transfer types and descriptors — because that is the vocabulary every USB stack expects you to speak.

The model

   USB IS STRICTLY HOST-DRIVEN. A device NEVER initiates.
   The host polls; the device answers. Even an "interrupt"
   endpoint is polled - the name is historical.

   HOST                                  DEVICE
   +--------+                            +--------------+
   |        |  ---- token: IN, ep 1 ---> | endpoint 1 IN|
   |        |  <--- data packet -------- |              |
   |        |  ---- ACK -------------->  |              |
   +--------+                            +--------------+

   ENDPOINT: a buffer in the device with a number (0-15) and
   a direction. IN means device-to-host; OUT means
   host-to-device. Directions are ALWAYS named from the
   HOST's point of view, which is the first thing to get
   straight.

   ENDPOINT 0 is special: bidirectional, always present, and
   carries all control traffic including enumeration.

   INTERFACE: a group of endpoints implementing one function.
   CONFIGURATION: a set of interfaces. Devices almost always
   have exactly one configuration; the flexibility is
   rarely used.

   A composite device - say a USB headset - has several
   interfaces in one configuration: audio out, audio in,
   and HID for the volume buttons.

Four transfer types

TypeGuaranteesUsed for
ControlReliable, retried; 10% of bandwidth reservedEnumeration and configuration, on endpoint 0
BulkReliable, retried; no timing guarantee at allMass storage, serial ports, printers — anything where correctness beats latency
InterruptReliable, retried; guaranteed poll intervalKeyboards, mice, sensors — small data at a bounded latency
IsochronousGuaranteed bandwidth, no retries, no error recoveryAudio and video, where a late packet is worse than a lost one
 
   THE TRADE-OFF THAT DEFINES USB:

     BULK gets whatever bandwidth is left over, but it never
     loses data. A mass-storage transfer may stall for
     milliseconds if the bus is busy; it will not corrupt.

     ISOCHRONOUS reserves bandwidth in every frame and
     never retries. A dropped audio sample is a click; a
     late one would be a gap in playback, which is worse.
     So it simply does not retry.

   Choosing wrongly is a common design error: implementing
   an audio device over bulk gives you glitch-free data with
   unpredictable latency, which for audio is exactly the
   wrong trade.

   SPEEDS:
     Low   1.5 Mbit/s   HID only, 8-byte packets
     Full  12 Mbit/s    most MCU peripherals, 64-byte max
     High  480 Mbit/s   needs a ULPI PHY, 512-byte bulk
     Super 5 Gbit/s+    a different physical layer entirely,
                        essentially never on an MCU

Enumeration, step by step

   What happens in the second after you plug the cable in.

   1. ATTACH. The device pulls D+ (full speed) or D- (low
      speed) to 3.3 V through 1.5 kO. The host sees the
      line go high and knows something is there - and which
      speed it claims.

   2. RESET. The host drives both lines low for 10 ms. The
      device resets its USB state machine and adopts
      ADDRESS 0.

   3. GET_DESCRIPTOR (Device), 8 bytes. The host asks for
      the first 8 bytes only, because byte 7 is
      bMaxPacketSize0 and it does not yet know how large a
      packet the device can accept.

   4. RESET again.

   5. SET_ADDRESS. The host assigns 1-127. The device must
      complete the STATUS stage of this request at the OLD
      address, then switch. Getting that ordering wrong is
      a classic stack bug.

   6. GET_DESCRIPTOR (Device), all 18 bytes. Now the host
      has VID, PID and class.

   7. GET_DESCRIPTOR (Configuration), 9 bytes, then again
      for the full length reported. This returns the
      configuration, all interfaces, and all endpoints as
      ONE concatenated blob.

   8. GET_DESCRIPTOR (String) for manufacturer, product,
      serial - in UTF-16LE.

   9. The host matches VID/PID/class against its drivers
      and loads one.

   10. SET_CONFIGURATION(1). The device is now CONFIGURED
       and its non-zero endpoints become usable.

   IF ENUMERATION FAILS the host reports "device not
   recognised" and gives you nothing else. A protocol
   analyser or Wireshark's USB capture is the only
   practical way to see which step failed.

Descriptors are the device's declaration

/* Descriptors are packed structs the device returns. They
   ARE the device's interface contract - everything the host
   knows comes from them.                                  */

typedef struct __attribute__((packed)) {
    uint8_t  bLength;             /* 18                    */
    uint8_t  bDescriptorType;     /* 1 = DEVICE            */
    uint16_t bcdUSB;              /* 0x0200 = USB 2.0      */
    uint8_t  bDeviceClass;        /* 0 = see interface     */
    uint8_t  bDeviceSubClass;
    uint8_t  bDeviceProtocol;
    uint8_t  bMaxPacketSize0;     /* 8, 16, 32 or 64       */
    uint16_t idVendor;            /* assigned by USB-IF    */
    uint16_t idProduct;
    uint16_t bcdDevice;
    uint8_t  iManufacturer;       /* string INDEX, not text */
    uint8_t  iProduct;
    uint8_t  iSerialNumber;
    uint8_t  bNumConfigurations;  /* almost always 1        */
} usb_device_descriptor_t;

/* A CDC-ACM (virtual serial port) configuration, as the
   host receives it - one contiguous blob.                */
static const uint8_t config_desc[] = {
    /* Configuration: 9 bytes, total length 67, 2 interfaces */
    9, 0x02, 67, 0, 2, 1, 0, 0xC0, 50,

    /* Interface 0: communications class, 1 endpoint      */
    9, 0x04, 0, 0, 1, 0x02, 0x02, 0x01, 0,
    /*   CDC functional descriptors (5+4+5+5 bytes)       */
    5, 0x24, 0x00, 0x10, 0x01,
    4, 0x24, 0x02, 0x02,
    5, 0x24, 0x06, 0, 1,
    5, 0x24, 0x01, 0, 1,
    /*   Endpoint 0x82: interrupt IN, 8 bytes, 255 ms     */
    7, 0x05, 0x82, 0x03, 8, 0, 255,

    /* Interface 1: CDC data, 2 endpoints                 */
    9, 0x04, 1, 0, 2, 0x0A, 0, 0, 0,
    /*   Endpoint 0x01: bulk OUT, 64 bytes                */
    7, 0x05, 0x01, 0x02, 64, 0, 0,
    /*   Endpoint 0x81: bulk IN, 64 bytes                 */
    7, 0x05, 0x81, 0x02, 64, 0, 0,
};

/* ENDPOINT ADDRESS ENCODING: bit 7 is direction.
     0x01 = endpoint 1, OUT
     0x81 = endpoint 1, IN
   These are DIFFERENT endpoints that share a number.

   THE TOTAL LENGTH FIELD (67 here) MUST BE EXACT. The host
   requests that many bytes; if the descriptors actually sum
   to a different number, enumeration fails in a way that
   gives no useful error. Compute it with sizeof() rather
   than by hand:

     #define CONFIG_TOTAL_LEN (sizeof(config_desc))
     ... and place it with a _Static_assert to check.     */
Vendor IDs cost money, and there is a legitimate alternative

A USB Vendor ID from the USB-IF costs several thousand dollars, and using someone else's without permission means your device can collide with theirs and cannot legally carry the USB logo. For hobby and internal work, pid.codes allocates free PIDs under a shared VID for open-source projects. For a product, budget for a real VID — or use a USB-to-serial bridge chip whose vendor's VID/PID you are licensed to use by buying the chip.

What this means on a microcontroller

/* You will use a stack. TinyUSB, the vendor's middleware,
   or Zephyr's - not your own. USB is a case where writing
   it yourself is a month of work to reach parity.

   WHAT YOU ACTUALLY DO:                                   */

/* 1. Provide descriptors. */
uint8_t const *tud_descriptor_device_cb(void) {
    return (uint8_t const *) &device_desc;
}

/* 2. Implement class callbacks. */
void tud_cdc_rx_cb(uint8_t itf) {
    uint8_t buf[64];
    uint32_t n = tud_cdc_read(buf, sizeof(buf));
    handle_input(buf, n);
}

/* 3. Service the stack, from a task or the main loop. */
for (;;) {
    tud_task();
    application_step();
}

/* THE HARDWARE REQUIREMENTS people underestimate:

   - AN ACCURATE CLOCK. USB full speed needs 0.25%. The
     internal RC oscillator is not sufficient unless the
     part has crystal-less USB, where it trims the RC
     against the host's start-of-frame packets. Otherwise:
     a crystal, and one whose frequency divides to exactly
     48 MHz (mcu chapter 09).

   - CORRECT D+/D- ROUTING. 90 ohm differential impedance,
     matched lengths, no stubs. USB is fast enough that
     layout matters - this is not a bus you can wire with
     jumper leads and expect to work.

   - VBUS SENSING if bus-powered, so the device knows when
     it is actually attached.

   - THE 1.5k PULL-UP, ideally software-controlled so the
     device can force a re-enumeration by dropping off the
     bus and reattaching. Without it, changing descriptors
     requires physically unplugging.                       */

Check yourself

  • Explain why a USB device can never initiate a transfer.
  • Say whose point of view IN and OUT are named from.
  • Name the four transfer types and the guarantee each makes.
  • Explain why isochronous transfers do not retry.
  • Explain why the host asks for only 8 bytes of the device descriptor first.
  • Say what must happen at the old address during SET_ADDRESS.
  • Explain what wTotalLength covers and the failure when it is wrong.
  • Decode endpoint addresses 0x01 and 0x81.
  • State USB full speed's clock accuracy requirement and two ways to meet it.
  • Explain why a software-controlled pull-up is worth having.
