Power states, WFI/WFE and PSCI

Two instructions to stop a core, and a standard firmware interface to turn one off entirely. Between them they cover the whole range from an idle loop to booting a secondary CPU — and PSCI is why one kernel image works across every ARM SoC.

WFI and WFE

Both instructions stop the core executing until something wakes it, but they answer different questions and are used in genuinely different places in real code. WFI asks "has something happened that requires attention" and is the instruction behind every idle loop — a core with nothing to do executes it and draws a fraction of its running power until an interrupt arrives, and crucially it wakes even if that interrupt is currently masked by PSTATE.I, because the point is to resume execution so the software can decide what to do next, not to actually take the interrupt while asleep. WFE asks "has some other core signalled an event" and exists specifically to make spinlocks power-efficient: instead of a core burning cycles in a tight retry loop waiting for a lock, it can sleep on WFE and be woken the instant the lock holder executes SEV or releases an exclusive-access monitor.

The property that makes WFI usable

It wakes on an interrupt even if that interrupt is masked. So the idle loop can mask interrupts, check whether there is work, and WFI — without a race where an interrupt arrives between the check and the sleep. Unmask after waking and the interrupt is then taken normally.

Without that property, every idle loop would have a lost-wakeup window.

/* The correct idle loop */
static void cpu_idle(void)
{
        for (;;) {
                local_irq_disable();            /* mask */
                if (need_resched()) {
                        local_irq_enable();
                        schedule();
                        continue;
                }
                dsb(sy);                        /* outstanding
                                                   transactions must
                                                   complete first  */
                wfi();                          /* sleep           */
                local_irq_enable();             /* now take it     */
        }
}

   core enters a low-power state may never complete, hanging the
   interconnect. Chapter 21.                                */

/* WFE, in a spinlock (chapter 22) */
1:      ldaxr   w1, [x0]
        cbnz    w1, 2f                  /* held? wait              */
        stxr    w2, w3, [x0]
        cbnz    w2, 1b
        b       3f
2:      wfe                             /* sleep in low power      */
        b       1b
3:      /* acquired */

/* The unlock's STLR to the monitored address generates the event
   automatically — no explicit SEV is needed. And the timer's
   EVENT STREAM (chapter 32) guarantees a wake within ~100 µs
   even if the event is missed entirely.                    */

Both are hints

Neither instruction guarantees anything about power

WFI and WFE are architectural hints. A conforming implementation may treat them as NOP. What actually happens — clock gating, retention, or nothing at all — is entirely implementation defined.

What is architected is the wake-up condition. So the correctness of your idle loop does not depend on the power behaviour, which is the right split: software expresses intent, hardware decides the mechanism. Deeper states than the core can enter by itself require firmware, which is what PSCI is for.

The state hierarchy

Power management is a hierarchy rather than an on/off switch: a core, a cluster and the whole system each have states, and a deeper state can only be entered when everything inside it agrees.

   RUNNING
     │
     │ WFI — the core requests a low-power state
     ▼
   STANDBY / retention            wake: ~ns to µs
     · clocks gated, state PRESERVED in registers and caches
     · the core resumes exactly where it stopped
     · entered directly by WFI; no firmware needed
     │
     │ PSCI CPU_SUSPEND with a deeper state ID
     ▼
   POWER DOWN                     wake: ~10s-100s of µs
     · the core's power domain is turned OFF
     · ALL state is lost: registers, caches, MMU config, GIC
       CPU interface
     · software must SAVE everything before, and RESTORE after
     · the core restarts at a firmware entry point and works its
       way back
     │
     │ all cores in a cluster down
     ▼
   CLUSTER POWER DOWN
     · the shared L2 must be cleaned and invalidated first
     · the cluster's GIC redistributor state saved
     │
     ▼
   SYSTEM SUSPEND                 wake: ms
     · everything except an always-on domain
     · DRAM in self-refresh
     · wake sources configured in the always-on power controller

  Each level saves more power and costs more to leave. The
  BREAK-EVEN calculation from CA chapter 20 governs which one an
  OS governor picks.

PSCI

Power State Coordination Interface

A standard SMC-based API implemented by EL3 firmware. It abstracts every SoC-specific power controller behind one interface, so a single kernel image can boot secondary cores, idle, suspend and reboot on any platform. Before PSCI, every SoC needed its own smp_ops in the kernel — which is why old ARM32 Linux had dozens of platform-specific power drivers and ARM64 has none.

/* Starting a secondary CPU — this is how every ARM64 SMP kernel
   brings up its cores (OS chapter 18):                     */

#include <linux/arm-smccc.h>

static int cpu_on(u64 mpidr, u64 entry_point, u64 context_id)
{
        struct arm_smccc_res res;

        arm_smccc_smc(0xC4000003,       /* PSCI_CPU_ON, SMC64 */
                      mpidr,            /* which core         */
                      entry_point,      /* PHYSICAL address   */
                      context_id,       /* passed back in x0  */
                      0, 0, 0, 0, &res);

        return (int)res.a0;             /* 0 = success        */
}

/* The target core comes out of reset at entry_point with:
     · the MMU OFF
     · caches OFF
     · at the same EL the caller was at
     · x0 = context_id

   In other words, exactly the same contract as the primary CPU's
   boot entry (OS chapter 18) — which is why the secondary path
   in head.S shares most of its code with the primary path. */

CPU_SUSPEND and the power state ID

Requesting a low-power state means describing which state you want in an encoded parameter, and the encoding is the part most people get wrong first.

/* CPU_SUSPEND takes a platform-specific state ID describing HOW
   deep to go, and where to resume.                          */

        arm_smccc_smc(0xC4000001,       /* CPU_SUSPEND        */
                      power_state,      /* the state ID       */
                      resume_entry,     /* physical address   */
                      context_id,
                      0, 0, 0, 0, &res);

/* The power_state encoding (extended format, PSCI 1.0+):
     [3:0]   state ID — platform specific
     [16]    0 = standby (state preserved)
             1 = POWERDOWN (state LOST)
     [25:24] affinity level: 0 = core, 1 = cluster, 2 = system

   The state IDs come from the DEVICE TREE, so the kernel does
   not need platform knowledge:                             */

cpus {
        idle-states {
                entry-method = "psci";

                cpu_sleep_0: cpu-sleep-0 {
                        compatible = "arm,idle-state";
                        arm,psci-suspend-param = <0x0010000>;
                        entry-latency-us = <300>;
                        exit-latency-us = <1200>;
                        min-residency-us = <2000>;
                        local-timer-stop;    /* ← the timer STOPS  */
                };
        };
        cpu@0 {
                cpu-idle-states = <&cpu_sleep_0>;
        };
};

/* The kernel's cpuidle governor uses entry/exit latency and
   min-residency to decide whether the expected idle duration
   justifies this state — the break-even calculation from
   CA chapter 20, driven entirely by device tree data.     */
local-timer-stop matters

In deep states the per-core generic timer loses power and stops. If the kernel programmed it to wake the core, that wake-up never happens. The fix is a broadcast timer in the always-on domain: the kernel switches to it before entering such a state, and one core stays awake (or the always-on timer fires) to wake the others. Getting this wrong produces a core that goes idle and never returns — a hang that only appears when the system is quiet.

What must be saved before power-down

A powered-down core loses state, and exactly which state is lost determines what software must save first. Missing one register produces a system that resumes into nonsense.

A POWERDOWN state loses everything. The full sequence:

  1. save all system registers that are not restored by firmware:
        SCTLR_EL1, TCR_EL1, TTBR0/1_EL1, MAIR_EL1, VBAR_EL1,
        TPIDR_EL0/EL1, CPACR_EL1, and the debug registers

  2. save the GIC CPU interface and redistributor state
        ICC_PMR_EL1, ICC_CTLR_EL1, ICC_IGRPEN1_EL1,
        pending SGIs, the redistributor's enable and priority
        state (chapter 23)

  3. CLEAN AND INVALIDATE the caches to the Point of Coherency
        · this is the ONE legitimate use of the set/way
          operations (chapter 18)
        · for a cluster power-down, the shared L2 too
        · and it must be the LAST thing, because anything after
          it may dirty a line again

  4. DSB, then issue PSCI CPU_SUSPEND

  On resume, the core enters at resume_entry with the MMU off and
  must rebuild everything: page tables, MMU, caches, GIC, timers,
  then restore the saved state and return into the idle loop as
  though WFI had simply returned.

  Linux does this in cpu_suspend() / cpu_resume(), and the
  saved-register set is arch/arm64/mm/proc.S's cpu_do_suspend.

  A missing register in that list gives a system that resumes and
  then behaves subtly wrongly — the hardest class of power bug.

CPU hotplug

Bringing cores online and offline at runtime uses the same firmware interface, and it is how a kernel actually starts its secondary processors in the first place.

# Offlining a core uses PSCI CPU_OFF underneath
echo 0 > /sys/devices/system/cpu/cpu3/online
echo 1 > /sys/devices/system/cpu/cpu3/online

cat /sys/devices/system/cpu/online
cat /sys/devices/system/cpu/offline

/* What the kernel does on offline:
     1. migrate all tasks off that core
     2. migrate all interrupts (set_affinity) off it
     3. migrate timers and hrtimers
     4. run CPU_DYING notifiers in every subsystem
     5. call PSCI CPU_OFF — which does not return

   And on online:
     1. PSCI CPU_ON with the secondary entry point
     2. the core runs head.S's secondary path: MMU, caches, GIC
        redistributor, timer
     3. CPU_STARTING notifiers
     4. mark it online; the scheduler starts using it

   Used for: thermal management, power saving, taking a core out
   of service after a fault, and testing SMP code paths.   */

The spin-table alternative

Before the firmware interface existed, secondary cores were started by having them spin on a memory location. You will still meet it on older platforms, and it explains some otherwise odd device-tree properties.

/* Before PSCI, and still on some simple platforms, secondaries
   are released with a SPIN TABLE: each parked core polls a
   memory location until the primary writes an address.     */

cpu@1 {
        device_type = "cpu";
        compatible = "arm,cortex-a53";
        reg = <0x1>;
        enable-method = "spin-table";
        cpu-release-addr = <0x0 0x8000fff8>;
};

/* The parked core runs, from firmware:
        1:      ldr     x0, [release_addr]
                cbz     x0, 1b
                wfe                     ← so it does not burn power
                br      x0

   The primary writes the entry point and issues SEV.

   Why PSCI is better:
     · it also handles CPU_OFF, SUSPEND and SYSTEM_RESET, which
       a spin table cannot
     · the parked core consumes power and holds memory
     · the release address must be reserved from the kernel's
       memory map, which is error-prone
     · no way to power the core down at all

   Use PSCI unless the platform genuinely has no EL3 firmware. */
