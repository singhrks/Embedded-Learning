The I/O subsystem and device drivers

A driver is the adapter between one piece of hardware and one kernel subsystem. This chapter covers the concepts every driver model shares — device classes, the discovery and binding lifecycle, I/O models, and the layering that lets one read() reach a hundred different kinds of device.

What a driver actually does

Two interfaces, one translator

Upward, a driver implements a subsystem interface — the operations a network stack, a block layer or a VFS expects. Downward, it speaks the device's register protocol. Everything else in a driver is lifecycle and error handling.

This is why "write a driver" is not one skill: you must know the subsystem's contract as well as the hardware's. Reading an existing driver for the same subsystem is nearly always the fastest route.

Network devices are the odd one out: they are not files, because a packet interface does not fit read/write semantics well and because routing decisions happen above the device. Sockets are the file-like abstraction instead.

Discovery and binding

Before a driver can run, something must establish that a device exists. How that happens differs fundamentally between buses that can enumerate themselves and hardware that must be described externally.

Two worlds, and the difference drives everything:

  DISCOVERABLE BUSES — hardware can be interrogated
      PCI:  read configuration space → vendor ID, device ID, class,
            BAR sizes and types
      USB:  request descriptors from the device
      → the bus driver enumerates, and the core matches a driver
        by ID. Hotplug works naturally.

  NON-DISCOVERABLE — you cannot ask
      on-SoC peripherals, I2C and SPI slaves.
      There is no safe way to probe address 0x40001000; a wrong
      guess can hang the bus or trigger a side effect.
      → hardware must be DESCRIBED out of band:
            device tree (embedded, ARM)
            ACPI tables (servers, x86, Windows on ARM)

This is exactly why the device tree exists, and why an embedded
Linux driver looks structurally different from a PCIe driver.

Probe ordering is not guaranteed

Your driver may probe before the clock controller or regulator it depends on exists. Every modern driver model has an answer: Linux returns -EPROBE_DEFER and the core retries later; Windows' PnP manager starts devices as their dependencies become available. Never assume initialisation order, and never work around it with late_initcall — that is a race, not a fix.

The four resources every driver needs

Nearly every driver needs the same four things before it can talk to hardware, and each is assigned by the system rather than chosen by the driver. Acquiring them correctly is most of what a probe function does.

The three I/O models

There are three ways a driver can wait for a device, and they differ in how much processor time they waste. The choice is usually forced by how fast the device responds.

PollingInterruptDMA
CPU cost100% while waitingPer eventNear zero
LatencyLowest, most deterministicInterrupt entry overheadSetup cost, amortised
Best forVery short waits, early boot, hard real time, ultra-high-rate NICsMost peripheralsBulk transfer
HazardWastes power; must be boundedStorms if not cleared at the sourceCoherency and address translation
 
/* Polling, done correctly — ALWAYS with a timeout */
ret = readl_poll_timeout(base + STATUS, val, val & READY, 10, 1000);
if (ret)
        return -ETIMEDOUT;      /* say so, rather than hanging */

/* Hybrid models are common in practice:
     NAPI (network)   take one interrupt, then POLL until the
                      queue drains. Interrupt latency at low
                      rates, no interrupt storm at high rates.
     Adaptive coalescing  the device delays interrupts until N
                      packets or T microseconds.               */

DMA from the driver's point of view

Letting a device read and write memory directly removes the processor from the transfer entirely. The complication is that the device sees a different address space, and getting that translation wrong corrupts memory silently.

The three rules, which are the same on every OS:

  1. Program the device with the address the DEVICE must use —
     Linux calls it dma_addr_t, Windows calls it a logical address.
     It is NOT a virtual address and NOT necessarily a physical one:
     with an IOMMU it is an IOVA.

  2. Respect BUFFER OWNERSHIP. Between map and unmap the buffer
     belongs to the device. Touching it from the CPU without an
     explicit sync gives stale or corrupt data on non-coherent
     systems (CA chapter 15).

  3. Never DMA to stack memory or vmalloc memory. Stack buffers may
     share a cache line with unrelated data; vmalloc memory is not
     physically contiguous.

  And the reason an SMMU/IOMMU exists at all: a device issuing
  addresses bypasses the CPU's MMU entirely, so every isolation
  guarantee built with page tables has a hole in it unless
  something checks those transactions. Security track, ch. 02-07.

Drivers outside the kernel

Not every driver has to be in the kernel. Running one in user space trades some performance for a crash that takes down a process rather than the machine, which is frequently the right trade.

The trade-off (OS chapter 02, again):

  IN KERNEL       full speed, direct access, no context switches
                  a bug panics the machine
                  a vulnerability is total compromise

  IN USER SPACE   a crash kills one process
                  can use any language, any library, a debugger
                  can be restarted
                  syscall or mapping overhead per operation
                  needs an IOMMU to make DMA safe

  DPDK and SPDK take the user-space path AND remove the overhead,
  by mapping the device with VFIO and POLLING it from a dedicated
  core — no syscalls, no interrupts, no kernel in the data path.
  They trade a whole CPU core for latency and throughput.

Use an existing subsystem if one fits

A temperature sensor registered with hwmon is immediately visible to sensors, monitoring agents and fan control. The same sensor behind a custom ioctl needs bespoke tooling forever. Before inventing an interface, search for a subsystem that already models your device class — IIO for sensors, input for buttons and touch, v4l2 for video, ALSA for audio, hwmon for monitoring, rtc, watchdog, pwm, led. This is the difference between a driver that gets merged and one that does not.

Getting removal right

A driver is not simply loaded and run. It binds to a device, may be unbound, and must survive the device disappearing while in use — which is the path that receives the least testing and causes the most crashes.

/* Removal is where most driver bugs live, because it races with
   everything still in flight.                                */

static void my_remove(struct device *dev)
{
        struct my_dev *d = dev_get_drvdata(dev);

        /* 1. STOP the hardware generating events, FIRST */
        writel(0, d->regs + REG_IRQ_ENABLE);
        writel(0, d->regs + REG_CTRL);

        /* 2. unregister from the subsystem, so no NEW requests
              can arrive */
        unregister_device(&d->cdev);

        /* 3. wait for in-flight work to finish */
        cancel_work_sync(&d->work);
        del_timer_sync(&d->timer);

        /* 4. release resources in reverse order of acquisition */
        clk_disable_unprepare(d->clk);
        /* devm_ resources released automatically after this   */
}

/* Get the ORDER wrong and an interrupt fires after you freed the
   structure it references — a use-after-free that only appears
   under load.                                                */
# the single best driver test there is: bind/unbind in a loop
for i in $(seq 100); do
  echo 40010000.widget > /sys/bus/platform/drivers/mydrv/unbind
  echo 40010000.widget > /sys/bus/platform/drivers/mydrv/bind
done
dmesg | grep -iE 'kasan|use-after|warn|leak'
# Nearly every resource leak, missing-quiesce and lifetime bug
# surfaces here and almost nowhere else. Run it with KASAN on.

Observing the I/O subsystem

Which drivers are bound to which devices, and what resources each holds, is fully visible on a running system — which answers most "why is my device not working" questions immediately.

lspci -vv                    # PCI devices, BARs, capabilities, driver
lsusb -t                     # USB topology
ls /sys/bus/*/devices/       # everything the device model knows
ls /sys/bus/platform/drivers/mydrv/    # what bound to this driver
ls /sys/class/                # by device class

cat /proc/interrupts         # is the handler firing?
cat /proc/iomem              # who owns which physical range
cat /proc/devices            # major numbers
ls /sys/kernel/iommu_groups/*/devices/

udevadm info -a -n /dev/ttyUSB0     # every attribute, for writing rules
udevadm monitor                      # watch hotplug events live

dmesg -w                             # driver messages as they happen
