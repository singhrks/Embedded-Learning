References, value categories and overload resolution

References, the five value categories, and the rules by which C++ picks one function from several candidates. This is the machinery underneath move semantics and templates, and it is where C++'s apparent unpredictability usually comes from.

References

References look like pointers with nicer syntax and differ in ways that matter: they cannot be null, cannot be reseated, and one kind of them binds to temporaries — which is the foundation of move semantics.

        int x = 42;
        int&  r = x;            /* an lvalue reference - an
                                   ALIAS for x               */
        r = 10;                 /* x is now 10 */

/* PROPERTIES:
     · must be initialised - there is no null reference
     · cannot be reseated - `r = y` assigns to x, it does not
       make r refer to y
     · no separate object exists; the compiler implements it
       as a pointer, usually optimised away entirely

/* CONST REFERENCES bind to more things: */
        const int& cr = 42;     /* binds to a TEMPORARY, and
                                   EXTENDS ITS LIFETIME to
                                   that of cr                */
        int& bad = 42;          /* ERROR */

/* RVALUE REFERENCES (C++11) bind ONLY to rvalues: */
        int&& rr = 42;          /* OK */
        int&& bad2 = x;         /* ERROR - x is an lvalue */
        int&& ok = std::move(x); /* OK - move() casts to
                                    rvalue                   */

/* WHEN TO USE WHICH, in a function parameter:

     void f(T v)           by VALUE - for cheap types, or when
                           you need a copy anyway
     void f(const T& v)    by CONST REF - the default for
                           anything non-trivial you only read
     void f(T& v)          by REF - when you modify the
                           caller's object
     void f(T&& v)         by RVALUE REF - when you will STEAL
                           from it (chapter 05)
     void f(const T&& v)   almost never useful

/* THE THRESHOLD: pass by value for types up to about two
   registers (16 bytes on AArch64 - chapter 10's ABI), by
   const reference above that. int, float, pointers, small
   structs, string_view, span: by value. Everything else: by
   const reference.                                        */

/* THE DANGLING REFERENCE, and it is easy to write: */
        const std::string& f() {
                std::string s = "hello";
                return s;               /* DANGLING - s is
                                           destroyed         */
        }
        const int& bad = std::vector<int>{1,2,3}[0];
                                        /* the vector dies at
                                           the end of the
                                           statement         */
/* -Wreturn-local-addr and -Wdangling-gsl catch some of these;
   ASan catches the rest at run time.                     */

The five value categories

Every expression in C++ has a value category, and the terminology is notoriously opaque. The useful reduction is a single question: does this expression name something with an address that outlives the expression?

   C++11 split C's lvalue/rvalue into a lattice, because move
   semantics needed a third case.

                     expression
                    /          \
              glvalue          rvalue
             /       \        /      \
        lvalue        xvalue         prvalue

   THE TWO PROPERTIES that define them:

     has IDENTITY?   can you take its address, does it name a
                     specific object?
     is MOVABLE?     may its resources be stolen?

     lvalue    identity, NOT movable      a named variable
     xvalue    identity, MOVABLE          std::move(x), a
                                          function returning T&&
     prvalue   NO identity, movable       42, f() returning T,
                                          a temporary

     glvalue = lvalue + xvalue     "has identity"
     rvalue  = xvalue + prvalue    "movable"

   EXAMPLES:
        int x = 1;
        x                       lvalue
        42                      prvalue
        x + 1                   prvalue
        std::move(x)            xvalue
        f()   returning int     prvalue
        f()   returning int&    lvalue
        f()   returning int&&   xvalue
        arr[0]                  lvalue
        "hello"                 lvalue  (a string literal is
                                         an array object)

   THE PRACTICAL RULE, which covers almost every case:
     IF IT HAS A NAME, IT IS AN LVALUE.
   Even a parameter declared `T&& x` is an lvalue INSIDE the
   function, because it has a name. That is precisely why
   std::move is needed to pass it on (chapter 05).

Overload resolution

Overload resolution decides which function a call actually reaches, and its rules are elaborate enough that the answer is occasionally surprising. These are the parts that matter in practice.

/* Given several candidates, C++ picks one by a defined
   procedure. Knowing it removes most surprise.            */

   1. NAME LOOKUP: gather candidates. Ordinary scope lookup,
      plus ARGUMENT-DEPENDENT LOOKUP (below).

   2. Discard candidates that cannot be called with these
      arguments (wrong arity, or no conversion exists).

   3. RANK the conversions for each argument:

        EXACT MATCH               identity, lvalue-to-rvalue,
                                  array-to-pointer,
                                  qualification (T* -> const T*)
        PROMOTION                 char -> int, float -> double
        STANDARD CONVERSION       int -> double, D* -> B*,
                                  anything -> bool
        USER-DEFINED CONVERSION   a converting constructor or
                                  a conversion operator
                                  (AT MOST ONE per argument)
        ELLIPSIS                  ...

   4. The BEST candidate is the one that is no worse for every
      argument and better for at least one. If none is, the
      call is AMBIGUOUS - an error.

   5. Templates lose to equally-good non-templates.

/* WORKED: */
        void f(int);            /* 1 */
        void f(double);         /* 2 */
        void f(const char*);    /* 3 */

        f(42);                  /* 1: exact */
        f(42.0);                /* 2: exact */
        f('a');                 /* 1: PROMOTION beats
                                   conversion             */
        f(42.0f);               /* 2: promotion */
        f("s");                 /* 3: array-to-pointer is
                                   exact                  */
        f(nullptr);             /* 3 */
        f(0);                   /* 1 - and this is why
                                   nullptr exists         */

/* AMBIGUITY: */
        void g(long);
        void g(float);
        g(42);                  /* ERROR: int -> long and
                                   int -> float are both
                                   standard conversions,
                                   neither better           */

/* THE LVALUE/RVALUE OVERLOAD, which is what move semantics
   is built on: */
        void h(const T&);       /* binds lvalues AND rvalues */
        void h(T&&);            /* binds ONLY rvalues, and
                                   PREFERRED for them       */

        T a;
        h(a);                   /* const T& */
        h(T{});                 /* T&& - better match */
        h(std::move(a));        /* T&& */

Argument-dependent lookup

The compiler looks for functions in namespaces you did not name, based on the types of the arguments. This is deliberate and it is what makes some generic code work at all — and occasionally what makes it call something unexpected.

/* For an unqualified call, C++ ALSO searches the namespaces
   of the argument types. Without this, operator overloading
   would not work across namespaces.                       */

        namespace lib {
                struct Widget {};
                void process(const Widget&);
                std::ostream& operator<<(std::ostream&,
                                         const Widget&);
        }

        lib::Widget w;
        process(w);             /* FOUND via ADL, without
                                   `lib::`                  */
        std::cout << w;         /* likewise - and this is why
                                   operator<< can be defined
                                   in the type's own
                                   namespace                */

/* THE IMPORTANT IDIOM it enables - customisation points: */
        template<typename T>
        void algorithm(T& a, T& b)
        {
                using std::swap;        /* the fallback */
                swap(a, b);             /* UNQUALIFIED: ADL
                                           finds a
                                           type-specific swap
                                           if one exists,
                                           otherwise
                                           std::swap        */
        }
/* Writing `std::swap(a, b)` instead would ALWAYS use the
   generic one, missing an optimised overload. The
   `using` + unqualified call pattern is the standard
   solution, and you will see it throughout the STL.

/* THE HAZARD: ADL can find candidates you did not intend,
   particularly with templates and with types from large
   namespaces. If an overload is chosen that surprises you,
   ADL is usually why - and the fix is to qualify the call.  */
The tools for "which overload was chosen?" 
clang++ -Xclang -ast-dump -fsyntax-only file.cpp

The AST names the exact function selected and every implicit conversion applied (compilers chapter 04). On an ambiguity error, Clang lists every candidate with the reason it was rejected — read that list rather than guessing. These two habits resolve almost every overload question in under a minute.

const and its propagation

const on a member function is a promise about the object rather than about the function, and it participates in overload resolution — which means two functions can differ only in it.

        const int  ci = 1;
        int const  ci2 = 1;             /* the SAME thing */

        const int *p1;          /* pointer to const int -
                                   *p1 is const            */
        int const *p2;          /* identical to p1 */
        int * const p3 = &x;    /* CONST POINTER to int -
                                   p3 cannot be reseated   */
        const int * const p4 = &ci;     /* both */

/* READ RIGHT TO LEFT: `int * const` is "const pointer to
   int". Consistently declaring `int const *` rather than
   `const int *` makes the rule uniform - some codebases
   require it for that reason.

/* CONST MEMBER FUNCTIONS: */
        class Buffer {
                uint8_t *data_;
        public:
                uint8_t& at(size_t i)       { return data_[i]; }
                const uint8_t& at(size_t i) const
                                             { return data_[i]; }
        };
/* Two overloads differing only in constness - a const object
   gets the const one. Standard, and slightly tedious;
   C++23's "deducing this" collapses it into one.

/* CONSTNESS IS SHALLOW: a const member function may modify
   what a member pointer POINTS TO: */
        void Buffer::clear() const {
                data_[0] = 0;           /* LEGAL - data_ is
                                           const, *data_ is
                                           not               */
        }
/* Which is exactly the same rule as C, and a real source of
   false confidence. `std::experimental::propagate_const`
   exists for this, and is not widely used.

/* `mutable` - modifiable even in a const function: */
        class Cache {
                mutable bool valid_ = false;
                mutable int  cached_;
        public:
                int get() const {
                        if (!valid_) { cached_ = compute();
                                       valid_ = true; }
                        return cached_;
                }
        };
/* LEGITIMATE for caches, mutexes and lazily computed values -
   things that do not change the object's OBSERVABLE state.
   Anything else is a lie to the reader.                   */

/* AND THE EMBEDDED POINT: `const` on a namespace-scope object
   with a constant initialiser puts it in .rodata, which on a
   microcontroller means FLASH rather than RAM. On a part with
   32 KB of RAM that is not a stylistic matter.           */

Implicit conversions

C++ will convert types implicitly in more situations than C does, including through your own constructors. That is convenient until it silently picks a conversion you never intended.

/* C++ will convert types for you, and that is the source of
   several surprises. */

/* --- CONVERTING CONSTRUCTORS - block them --- */
        class Timeout {
                uint32_t ms_;
        public:
                Timeout(uint32_t ms) : ms_(ms) {}   /* implicit! */
        };
        void wait(Timeout t);
        wait(1000);             /* compiles - is 1000 ms, or
                                   seconds, or ticks?       */

        explicit Timeout(uint32_t ms);
        wait(1000);             /* now an ERROR */
        wait(Timeout{1000});    /* explicit at the call site */

/* --- CONVERSION OPERATORS - block those too --- */
        class Handle {
        public:
                operator int() const;   /* implicit - allows
                                           `handle + 1`, and
                                           every other
                                           nonsense           */
                explicit operator bool() const;  /* the useful
                                                    one       */
        };
        if (h) { }              /* explicit operator bool is
                                   still used HERE - a
                                   "contextual conversion" */

/* --- THE UNIFORM RULE that avoids all of it ---
     mark EVERY single-argument constructor and EVERY
     conversion operator `explicit`, except `operator bool`.
   Then conversions happen only where you wrote them.

/* --- ARITHMETIC CONVERSIONS still apply, exactly as in C
       (compilers chapter 04), including the signed/unsigned
       trap. Enable -Wconversion -Wsign-conversion.

/* --- AND enum class, which does NOT convert --- */
        enum        Old { A, B };       /* converts to int */
        enum class  New { A, B };       /* does NOT */

        int x = A;                      /* fine, and usually
                                           unwanted           */
        int y = New::A;                 /* ERROR */
        int z = static_cast<int>(New::A);   /* explicit */

        enum class Mode : uint8_t { Idle, Run, Fault };
/* An explicit underlying type is worth setting on embedded -
   it fixes the size and lets you use it in a packed
   structure.                                              */

A move did not happenThe argument had a name, so it was an lvalue — needs std::move

The wrong overload chosenPromotion beat conversion, or ADL found something unexpected
