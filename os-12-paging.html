Virtual memory, paging and page replacement

CA chapter 16 covered the hardware mechanism. This chapter is the software policy: which pages live in RAM, which are evicted, and how the OS makes a page fault into a feature rather than an error.

Demand paging

The idea

Do not load anything until it is touched. Mark pages invalid, and let the hardware tell you — via a page fault — exactly which page a program actually needs. Programs typically use a small fraction of what they map, so this converts a large up-front cost into a series of small on-demand ones.

Executing a 200 MB binary

  WITHOUT demand paging: read 200 MB from disk, then start.
                         Slow to start, and most of it is never used.

  WITH demand paging:    map the file, start immediately.
                         Fault in ~2 MB of actually-executed code.

  This is also why:
    · a huge malloc() returns instantly — nothing is allocated yet
    · a program's RSS is far smaller than its VSZ
    · the first run of a program is slower than the second
      (the second finds the pages in the page cache)

The page fault handler

A page fault is not an error; it is the normal mechanism by which memory becomes present. What matters is which of several very different situations just occurred, because only one is a bug.

How the kernel knows what should be there

The kernel does not track a process's memory page by page. It tracks regions with common properties, which is what makes a sparse multi-gigabyte address space cheap to describe.

/* The page tables say what IS mapped. A separate structure says
   what SHOULD be mappable — that is what the fault handler
   consults.                                                   */

struct vm_area_struct {          /* one per contiguous mapping */
        unsigned long vm_start, vm_end;
        unsigned long vm_flags;          /* READ|WRITE|EXEC|SHARED */
        struct file  *vm_file;           /* backing file, or NULL
                                            for anonymous          */
        unsigned long vm_pgoff;          /* offset within the file */
        const struct vm_operations_struct *vm_ops;   /* ->fault()  */
};
/* Kept in a maple tree (formerly a red-black tree) per mm_struct,
   so "which VMA contains this address?" is O(log n).          */

/* Windows: the same idea, called a Virtual Address Descriptor. */
cat /proc/self/maps
# 5584f2a00000-5584f2a02000 r-xp 00000000 fe:01 1234  /usr/bin/cat
# 5584f2c01000-5584f2c02000 rw-p 00001000 fe:01 1234  /usr/bin/cat
# 5584f4b1e000-5584f4b3f000 rw-p 00000000 00:00 0     [heap]
# 7ffd8a3c0000-7ffd8a3e1000 rw-p 00000000 00:00 0     [stack]
#      ^start        ^end   ^perms ^offset ^dev ^inode ^backing
#                    p = private (COW),  s = shared

cat /proc/self/smaps          # per-VMA: Rss, Pss, Shared/Private,
                              # Dirty/Clean, THP usage, swap

Page replacement policy

When memory is full, which page is evicted? The theoretically optimal choice — the page used furthest in the future — requires knowing the future, so every real policy approximates it.

PolicyRuleProblem
OPT / BeladyEvict the page used furthest in the futureUnimplementable; used only as a benchmark
FIFOEvict the oldestIgnores usage. Suffers Belady's anomaly: more frames can mean more faults.
LRUEvict the least recently usedGood, but exact LRU needs a timestamp on every access — far too expensive in hardware
Clock / second chanceCircular scan; if the access bit is set, clear it and move onCheap LRU approximation. The classic implementation.
Two-list (Linux)Active and inactive LRU lists; promotion on second referenceResists scan pollution
LFU / ARC / MGLRUTrack frequency as well as recencyMore state; better under mixed workloads
 
Linux's two-list approach, and the problem it solves

   ACTIVE list      pages referenced more than once — the working set
       ▲   │
       │   │ aging pushes down when the active list grows too large
       │   ▼
   INACTIVE list    candidates for eviction
           │
           ▼ evicted (clean: dropped; dirty: written back first)

  A page enters the INACTIVE list on first touch. It is promoted to
  ACTIVE only on a SECOND reference.

  Why: a large sequential scan — `cat bigfile`, a backup — touches
  millions of pages exactly once. With plain LRU those pages would
  evict your entire working set. With two lists they never reach
  the active list, and the working set survives. This is called
  scan resistance, and it is why `grep -r /` does not destroy your
  machine's performance for the next ten minutes.

  MGLRU (Multi-Gen LRU, Linux 6.1+) generalises this to several
  generations, with much lower overhead at scale.

Thrashing and the working set

When the working set exceeds physical memory, a system spends its time moving pages rather than computing. The transition is sharp rather than gradual, which is why it feels like a cliff.

   throughput
       ▲
       │        ╭──────────╮
       │      ╭─╯          ╰─╮
       │    ╭─╯               ╰──╮
       │  ╭─╯                     ╰────────  ← THRASHING
       │╭─╯                            ╰───────────
       └──────────────────────────────────────────► degree of
                                                     multiprogramming

  Beyond a point, adding processes means no process's working set
  fits. Every process faults, the disk saturates, and CPU
  utilisation COLLAPSES while the system appears maximally busy.

  The classic failure signature:
     · load average very high
     · CPU mostly in iowait
     · si/so columns in vmstat non-zero and large
     · everything, including your shell, responds in seconds

  WORKING SET: the set of pages a process has touched in the last
  T units of time. If the sum of all working sets exceeds RAM,
  thrashing is inevitable regardless of policy.

  Responses: reduce concurrency, add memory, use cgroup limits so
  one process cannot drag the system down, or enable PSI-based
  pressure handling.
# detect it
vmstat 1
#  r  b   swpd   free  buff  cache   si   so    bi    bo  cs us sy id wa
#              ^^^^                  ^^   ^^                          ^^
#   si/so = swap in/out per second. Sustained non-zero = thrashing.
#   wa    = iowait. High wa with low us/sy means waiting on disk.

# PSI — the modern, direct measure of pressure (Linux 4.20+)
cat /proc/pressure/memory
# some avg10=45.23 avg60=30.12 avg300=12.45
#      ^ % of time at least one task was stalled on memory
# This is far more actionable than free/available, and cgroup-aware.

Swap

Swap is widely misunderstood as "extra slow memory". Its actual role is subtler, and the common advice to disable it is usually counterproductive on a modern kernel.

QuestionAnswer
What is swapped?Only anonymous pages. File-backed pages are simply dropped and re-read from the file.
Is swap bad?No. Swapping out idle pages to make room for cache is good. Swapping in continuously is thrashing.
Should I disable it?Usually not — without swap the kernel cannot evict idle anonymous memory at all, so it evicts file pages instead, hurting more. Do disable it for hard real-time and for latency-critical databases with their own caching.
vm.swappiness0–200; the bias toward reclaiming anonymous versus file pages. Default 60. Lower means prefer dropping cache.
zram / zswapCompressed swap in RAM. Excellent on memory-constrained devices — CPU is cheaper than I/O.
 
swapon --show
cat /proc/PID/status | grep VmSwap        # how much THIS process has swapped
smem -s swap -r                            # per-process swap usage

# real-time and latency-critical work: pin everything resident
mlockall(MCL_CURRENT | MCL_FUTURE);
# ...and check RLIMIT_MEMLOCK allows it. Without this, a single
# major fault can blow a millisecond deadline.

Huge pages

Using larger pages reduces the number of translation entries needed, which matters because that resource is small and precious. The gains are real and so are the allocation difficulties.

/* TLB reach (CA chapter 16): 1024 entries x 4 KB = 4 MB.
   With 2 MB pages the same TLB covers 2 GB.                  */

/* Transparent Huge Pages — automatic, no code change */
cat /sys/kernel/mm/transparent_hugepage/enabled
#   [always] madvise never
madvise(p, len, MADV_HUGEPAGE);      /* opt in, per region */

/* Explicit huge pages — reserved, guaranteed, never swapped */
echo 1024 > /proc/sys/vm/nr_hugepages
mmap(NULL, len, PROT_READ|PROT_WRITE,
     MAP_PRIVATE|MAP_ANONYMOUS|MAP_HUGETLB, -1, 0);
THP is not free

Allocating a 2 MB huge page requires 2 MB of contiguous physical memory. Under fragmentation the kernel may enter synchronous compaction to find it, stalling the faulting process for milliseconds. Databases (MongoDB, Redis, Oracle) routinely recommend transparent_hugepage=madvise or never for exactly this reason — the latency variance is worse than the TLB benefit. Explicit hugetlbfs pages, reserved at boot, avoid the problem entirely.

Controlling paging from user space

Taking page faults at unpredictable moments is unacceptable for real-time work. Faulting everything in up front, and locking it, is how such programs avoid it.

madvise(p, len, MADV_WILLNEED);   /* prefetch: fault it in now */
madvise(p, len, MADV_DONTNEED);   /* discard: anonymous pages are
                                     freed and re-fault as ZERO   */
madvise(p, len, MADV_SEQUENTIAL); /* aggressive readahead         */
madvise(p, len, MADV_RANDOM);     /* disable readahead            */
madvise(p, len, MADV_FREE);       /* may be reclaimed lazily —
                                     faster than DONTNEED         */
madvise(p, len, MADV_HUGEPAGE);
madvise(p, len, MADV_COLD);       /* deprioritise, do not free    */

posix_fadvise(fd, off, len, POSIX_FADV_DONTNEED);   /* drop from cache */
posix_fadvise(fd, off, len, POSIX_FADV_WILLNEED);

mlock(p, len);                    /* pin: never evicted           */
mlockall(MCL_CURRENT | MCL_FUTURE);
mmap(..., MAP_POPULATE, ...);     /* prefault the whole mapping   */

Handling faults in user space

Page faults can be handled by a user-space program rather than the kernel, which is what makes live migration and certain garbage collectors possible.

/* userfaultfd lets a user process handle its own page faults.
   The mechanism behind live VM migration, distributed shared
   memory, and CRIU checkpoint/restore.                        */

int uffd = syscall(SYS_userfaultfd, O_CLOEXEC);
/* register a region; a helper thread reads fault events from uffd
   and supplies pages with UFFDIO_COPY. The faulting thread blocks
   until the page arrives — post-copy migration in a nutshell. */
