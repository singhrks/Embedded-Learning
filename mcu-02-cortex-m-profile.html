The Cortex-M profile: ARMv7-M and ARMv8-M

The ARM track on this site covers the A profile — AArch64, exception levels, page tables. The M profile is a different architecture with a different instruction set, a different exception model and a different memory map. This chapter is the map of what M means, and which M you are holding.

Three profiles, one company

ARM defines three architecture profiles, and they are not variants of each other. Code, tooling and mental models transfer only partly between them.

ProfileForDefining feature
A — ApplicationPhones, servers, anything running LinuxMMU, virtual memory, exception levels EL0–EL3
R — Real-timeStorage controllers, basebands, safety islandsMPU rather than MMU, but A-like performance and often lockstep cores
M — MicrocontrollerEverything in this trackThumb-only, hardware exception entry, deterministic latency, tiny gate count

The ARM architecture track teaches the A profile. Almost none of its exception-level material applies here: an M-profile core has no EL1, no SPSR_EL1, no vector base you set up with a table of branch instructions, and no MMU chapter to read. What transfers is the memory model vocabulary, the barrier instructions, and the general shape of a load/store architecture.

Reading a part number

"STM32F407" tells you the vendor (ST), the family (F4) and the peripheral set — but the core is only implied. The reference manual's first pages state it: Cortex-M4 with FPU, ARMv7E-M. That distinction decides whether you can use __disable_irq with a BASEPRI level, whether float costs one cycle or forty, and whether the vector table can be moved. Establish it before writing a line of code.

Thumb-2, and only Thumb-2

An M-profile core executes Thumb instructions exclusively. There is no A32/ARM state to switch into, and no AArch64 at all. Attempting to switch to ARM state is not a mode change — it is a fault.

/* Thumb-2 mixes 16-bit and 32-bit encodings freely. The
   assembler picks; you can force it with .w and .n suffixes. */

    movs  r0, #1          @ 16-bit encoding, 2 bytes
    mov.w r0, #0x12345678 @ 32-bit encoding, 4 bytes
    add   r1, r2, r3      @ assembler chooses

/* Every branch target must be Thumb, and the architecture
   encodes that in the LOW BIT of the address:              */

    ldr   r0, =my_function + 1   @ bit 0 SET = Thumb
    bx    r0                     @ branch and exchange

/* This is why every entry in the vector table is an odd
   number, and why a function pointer that looks "one byte
   off" is correct. Clear that bit and the core takes a
   UsageFault with INVSTATE set - it believes you asked it to
   execute ARM-state code, which it cannot do.

   You will meet this exactly once, when hand-writing a
   vector table or a context switch, and it will cost you an
   afternoon if nobody warned you.                          */

The core peripherals are part of the architecture

This is the single most useful structural fact about the M profile, and it has no equivalent on Cortex-A. The interrupt controller, the system timer, the fault registers and the MPU are defined by the architecture, at fixed addresses, identically on every vendor's chip.

   THE ARCHITECTURALLY FIXED MEMORY MAP

   0x00000000  +---------------------------+
               | Code      (flash, XIP)    |  512 MB region
   0x20000000  +---------------------------+
               | SRAM                      |  512 MB region
   0x40000000  +---------------------------+
               | Peripheral (vendor's)     |  512 MB region
   0x60000000  +---------------------------+
               | External RAM              |
   0xA0000000  +---------------------------+
               | External device           |
   0xE0000000  +---------------------------+
               | Private Peripheral Bus    |  <-- the core's
               |   0xE000E010  SysTick     |      own blocks
               |   0xE000E100  NVIC        |
               |   0xE000ED00  SCB         |
               |   0xE000ED90  MPU         |
               |   0xE0001000  DWT         |
   0xFFFFFFFF  +---------------------------+

   Regions also carry default memory ATTRIBUTES: the
   Peripheral and Device regions are non-cacheable and
   strongly ordered, so a store to 0x40020000 is not
   buffered the way a store to SRAM might be. You get
   sane peripheral behaviour without configuring anything.

So NVIC_EnableIRQ() is the same code on an ST, an NXP and a Nordic part, because the NVIC is at 0xE000E100 on all of them. Everything above 0xE0000000 is ARM's; the 0x40000000 region is the vendor's, and that is where the reference manual takes over from the architecture reference manual.

Two manuals, and knowing which one answers your question

The ARMv7-M Architecture Reference Manual defines the core: instructions, exceptions, NVIC, SysTick, MPU, fault registers. The vendor reference manual defines everything hanging off the bus matrix: clocks, GPIO, UART, timers, DMA. When a fault register puzzles you, reach for ARM's manual. When a peripheral does not respond, reach for the vendor's. Reaching for the wrong one is the most common way to waste an hour.

Hardware exception entry

On Cortex-A, taking an exception gives you a branch to a vector and the job of saving state yourself, in assembly. On Cortex-M the hardware does it: it pushes eight registers onto the active stack, loads the handler's address from the vector table, and enters it. Your handler is an ordinary C function.

/* This is a complete, correct interrupt handler. There is no
   assembly wrapper, no manual register save, no eret.       */

void TIM2_IRQHandler(void)
{
    TIM2->SR = ~TIM_SR_UIF;   /* clear the flag in hardware */
    ticks++;
}

/* The hardware stacked R0-R3, R12, LR, PC and xPSR on entry
   and will unstack them on return. Those are exactly the
   caller-saved registers of the ARM procedure call standard,
   which is why a plain C function is a valid handler: the
   compiler already preserves everything else.

   This is the "AAPCS-compatible exception model", and it is
   the reason M-profile interrupt latency is a fixed 12
   cycles rather than "however long your prologue takes".    */

Chapter 07 covers the vector table and NVIC in detail, and chapter 08 covers what happens when a second interrupt arrives during the first — where tail-chaining and late-arrival make the model faster than the naive description suggests.

Floating point, DSP and Helium

/* Three separate optional extensions. Knowing which you have
   changes how you write numerical code.                     */

/* 1. FPU (M4F, M7, M33). Single precision in one cycle.
      Double precision is software on almost everything.     */
float  a = x * y + z;   /* 1 instruction: VFMA.F32          */
double b = x * y + z;   /* ~100 cycles: a library call       */

/* 2. DSP extension (M4, M7, M33). SIMD within 32-bit
      registers, and a single-cycle multiply-accumulate.     */
sum = __SMLAD(pair1, pair2, sum);  /* two 16x16 MACs at once */

/* 3. Helium / MVE (M55, M85). True 128-bit vectors,
      the M-profile answer to NEON.                          */

/* If the part has no FPU, every float operation becomes a
   call into libgcc. Code written assuming hardware float can
   be 40x slower on an M0 without a single warning - it
   compiles and runs, it is simply slow. This is the classic
   "port the algorithm to the cheaper chip" trap.

   Fixed-point arithmetic is the answer, and it is why Q15
   and Q31 formats persist in embedded DSP code.             */
An FPU changes your context switch

The FPU adds 33 more registers. If more than one task uses floating point, the RTOS must save and restore them, which roughly triples context-switch cost. Cortex-M supports lazy stacking — reserving the space but only writing the registers when a second FP-using context actually appears — and it is enabled by default. If you hand-write a context switch (chapter 18) and forget the FP registers exist, you get corruption that only appears once two tasks both do float maths.
