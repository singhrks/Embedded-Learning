Operators, precedence and evaluation order

Precedence decides how an expression is parsed. Evaluation order decides when each part runs. C fixes the first completely and leaves much of the second deliberately unspecified — and confusing the two produces bugs that change with the optimisation level.

The precedence table

C's precedence table is larger than most languages' and contains several genuinely surprising entries. You do not need to memorise it; you need to know which few cases are traps, and to parenthesise those.

The four precedence mistakes that actually happen

Every one of these compiles without a word from the compiler unless you enable warnings.

/* 1. Bitwise operators bind LOOSER than comparison.
      This is C's oldest design mistake, inherited from B. */
if (x & MASK == 0)          /* parsed as  x & (MASK == 0)  ->  x & 0  ->  0 */
if ((x & MASK) == 0)        /* what you meant                                */

/* 2. Shift binds looser than arithmetic. */
x << 2 + 3                  /* parsed as  x << (2 + 3)  =  x << 5 */
(x << 2) + 3                /* what you probably meant             */

/* 3. Dereference binds looser than postfix ++. */
*p++                        /* parsed as  *(p++)   — increment the POINTER  */
(*p)++                      /* increment the VALUE                          */

/* 4. Assignment inside a condition, without parentheses. */
while (c = getchar() != EOF)      /* c = (getchar() != EOF)  ->  c is 0 or 1 */
while ((c = getchar()) != EOF)    /* correct                                 */

Build with -Wparentheses (in -Wall) and it will flag most of these. The habit that removes the whole class: parenthesise whenever mixing categories — bitwise with comparison, shift with arithmetic, assignment inside a condition. Clarity costs nothing.

Precedence is not evaluation order

The distinction

a() + b() * c() — precedence says the multiplication groups first, so the result is a() + (b() * c()). It says nothing about which function runs first. The compiler may call them in any order, and different optimisation levels genuinely produce different orders.

/* UNSPECIFIED: legal, but the order may vary. Do not depend on it. */
printf("%d %d\n", g(), h());        /* g and h in either order      */
int x = f() + g();                  /* likewise                     */
a[i()] = b[j()];                    /* likewise                     */

/* UNDEFINED: the standard imposes no requirements at all.
   Two modifications, or a modification and a read, of the same
   object with no sequencing between them.                          */
i = i++ + 1;
a[i] = i++;
i = ++i + i++;
f(i++, i++);

/* These are not "compiler-dependent" — they are BROKEN. The compiler
   may produce anything, and modern compilers exploit that to
   optimise. Enable -Wsequence-point (in -Wall).                     */

/* Short-circuit is a guarantee you can build on */
if (p != NULL && p->len > 0 && p->data[0] == 'x')   /* safe, in order */
if (i < n && a[i] == target)                          /* bounds check first */
if (denom == 0 || total / denom > limit)              /* no divide by zero  */

/* The comma operator, used properly — rare outside for-headers */
for (i = 0, j = n - 1; i < j; i++, j--)
        swap(&a[i], &a[j]);

/* Note: the comma in a function call is a SEPARATOR, not the comma
   operator, and imposes no ordering.                              */
f(a, b);           /* separator: no sequencing between a and b */
f((a, b));         /* comma OPERATOR: one argument, b, after evaluating a */

Shift is a minefield of undefined behaviour 
x << n     /* UB if n < 0, or n >= width of the PROMOTED type of x */
x >> n     /* same                                                  */

int x = 1;
x << 32;              /* UB: int is 32 bits, so n must be 0..31      */
x << 31;              /* UB in C: shifting into the sign bit of a
                         signed type overflows. Use unsigned.        */

1 << 31               /* UB — `1` is int                            */
1u << 31              /* fine — unsigned int                        */
1ull << 40            /* fine — need the wide literal for wide shifts */

uint64_t mask = 1 << bit;     /* BUG if bit >= 32: the shift happens
                                 in int, THEN widens                 */
uint64_t mask = 1ULL << bit;  /* correct                             */

/* Right shift of a NEGATIVE signed value is implementation-defined:
   arithmetic (sign-extending) on every real compiler, but not
   guaranteed. Use unsigned types for bit work — always.            */

The rule that avoids all of it: do bit manipulation in unsigned types, with suffixed literals (1u, 1ul, 1ull) wide enough for the shift.

/* the standard field extract/insert idioms */
#define FIELD_MASK(hi, lo)   (((1ull << ((hi) - (lo) + 1)) - 1) << (lo))
#define FIELD_GET(reg, hi, lo)  (((reg) & FIELD_MASK(hi, lo)) >> (lo))
#define FIELD_SET(reg, hi, lo, v) \
        (((reg) & ~FIELD_MASK(hi, lo)) | (((uint64_t)(v) << (lo)) & FIELD_MASK(hi, lo)))

/* Linux provides these properly, with compile-time checking: */
#include <linux/bitfield.h>
#define CTRL_SPEED  GENMASK(5, 2)
val = FIELD_GET(CTRL_SPEED, reg);
reg = (reg & ~CTRL_SPEED) | FIELD_PREP(CTRL_SPEED, 3);

Logical versus bitwise

Two pairs of operators that look nearly identical and behave completely differently. One pair short-circuits and produces 0 or 1; the other works bit by bit and does not — and mixing them up produces code that is right by accident.

/* && and & are NOT interchangeable, and the difference bites. */

if (p && p->valid)     /* safe: p->valid only evaluated if p is non-NULL */
if (p &  p->valid)      /* CRASH: both sides always evaluated;
                            and it computes a bitwise AND of a pointer   */

/* Type of the result differs too */
!x           /* int: 0 or 1                     */
~x           /* same type as promoted x         */
a && b       /* int: 0 or 1                     */
a &  b       /* the common type of a and b      */

/* A subtle one: !! forces a value to exactly 0 or 1 */
#define BOOL(x)  (!!(x))
flags |= BOOL(cond) << FLAG_SHIFT;    /* without !!, a value of 6 would
                                         shift into the wrong bits      */

Division, modulo and negative numbers

Integer division and the remainder operator have behaviour that is defined precisely but does not match mathematical intuition for negative numbers — and on some operands it is not defined at all.

/* Since C99, integer division truncates TOWARD ZERO, and
   the sign of % follows the DIVIDEND.                    */

 7 /  2  ==  3       7 %  2 ==  1
-7 /  2  == -3      -7 %  2 == -1     /* not +1 */
 7 / -2  == -3       7 % -2 ==  1
-7 / -2  ==  3      -7 % -2 == -1

/* Identity that always holds:  (a/b)*b + a%b == a  */

/* So the "is it even" test is fine, but a naive modulo bucket is not: */
if (x % 2 == 1)          /* FALSE for negative odd x, which gives -1 */
if (x % 2 != 0)          /* correct */

/* Mapping into 0..n-1 for possibly-negative x: */
int idx = ((x % n) + n) % n;

/* Division by zero is UNDEFINED, not a trap you can rely on.
   INT_MIN / -1 is also undefined — the result does not fit.  */
if (b == 0 || (a == INT_MIN && b == -1))
        return -EINVAL;

sizeof and friends

sizeof looks like a function call and is not: it is evaluated at compile time and its operand is usually not executed at all. That distinction causes real bugs when the operand has side effects.

sizeof(type)      /* parentheses required for a type    */
sizeof expr       /* parentheses optional for an expression */

/* sizeof does NOT evaluate its operand (except for VLAs) */
int i = 0;
size_t n = sizeof(i++);       /* i is still 0 — this is a compile-time
                                 operation, and a common interview trap */

/* Result type is size_t: unsigned. Chapter 02 explains why that matters. */
if (sizeof(a) - sizeof(b) > 0)   /* ALWAYS true — unsigned never negative */

/* The array-length macro, and why it is not safe on a pointer */
#define ARRAY_SIZE(a)  (sizeof(a) / sizeof((a)[0]))

int a[10];
ARRAY_SIZE(a);                /* 10, correct */

void f(int a[10]) {
        ARRAY_SIZE(a);        /* WRONG: `a` is a POINTER here (chapter 05).
                                 Gives sizeof(int*)/sizeof(int) = 2       */
}

/* Linux's version fails to COMPILE on a pointer, which is far better: */
#define ARRAY_SIZE(arr) \
        (sizeof(arr) / sizeof((arr)[0]) + __must_be_array(arr))

/* C11 alignment operators */
_Alignof(double)              /* alignment requirement, in bytes */
_Alignas(64) char buf[128];   /* force alignment — cache lines, DMA */

Compound assignment and increment

The compound assignment operators are not merely shorthand — they evaluate their left operand only once, which matters as soon as that operand is an expression with side effects.

/* Compound assignment evaluates the left operand ONCE. This matters
   when it has side effects or is expensive.                       */
a[f()] += 1;          /* f() called once            */
a[f()] = a[f()] + 1;  /* f() called twice, in unspecified order */

/* It also performs an implicit conversion back, which can hide narrowing */
uint8_t x = 200;
x += 100;             /* computed in int (300), truncated back to 44
                         — no warning without -Wconversion             */

/* Pre versus post increment */
int i = 5;
j = i++;      /* j = 5, i = 6 — yields the OLD value */
j = ++i;      /* j = 7, i = 7 — yields the NEW value */

/* In C, on scalars, there is no performance difference: the compiler
   discards the unused old value. The habit of preferring ++i comes
   from C++, where the operand may be a heavy iterator object.       */
