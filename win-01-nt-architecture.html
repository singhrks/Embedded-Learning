NT architecture

Windows solves the same problems as Linux with a different structure, different names, and a different philosophy about stability. This chapter is the map — and because you have just finished the Linux track, the comparisons will do most of the teaching.

The layers

Windows is built in layers, and almost every confusing thing about driver development comes from not knowing which one you are standing in. The names below recur constantly in documentation, headers and crash dumps, so it is worth fixing them in place before anything else.

   USER MODE
   +-------------------------------------------------------+
   | applications                                          |
   +-------------------------------------------------------+
   | subsystem DLLs:  kernel32.dll  user32.dll  advapi32   |
   +-------------------------------------------------------+
   | ntdll.dll        the syscall stubs. NtCreateFile etc.  |
   +--------------------------+----------------------------+
                              |  syscall (SVC on arm64)
   ==========================================================
   KERNEL MODE                |
   +--------------------------v----------------------------+
   |  ntoskrnl.exe  -  THE EXECUTIVE                        |
   |                                                        |
   |   Ob  object manager     Io  I/O manager               |
   |   Mm  memory manager     Ps  process/thread manager    |
   |   Cc  cache manager      Se  security reference monitor|
   |   Cm  configuration      Ex  executive support         |
   |       (registry)         Po  power manager             |
   |   Pnp plug and play      Rtl runtime library           |
   +--------------------------------------------------------+
   |  KERNEL (Ke)  -  scheduling, interrupts, spinlocks,    |
   |                  DPCs, IRQL. The lowest software layer.|
   +--------------------------------------------------------+
   |  HAL  -  hardware abstraction layer                    |
   |          interrupt controller, timers, bus access      |
   +--------------------------------------------------------+
   |  DRIVERS  -  loaded into the same address space,       |
   |              at the same privilege, as everything above|
   +--------------------------------------------------------+

  THE PREFIXES ARE THE MAP. Every kernel function begins with
  the two- or three-letter tag of the component that owns it:

     ObReferenceObjectByHandle    object manager
     IoCreateDevice               I/O manager
     MmGetSystemAddressForMdlSafe memory manager
     KeAcquireSpinLock            kernel
     ExAllocatePool2              executive
     PsGetCurrentProcessId        process manager
     RtlCopyMemory                runtime library
     ZwCreateFile                 the kernel-mode syscall entry

  Learn the prefixes and you can guess where to look for
  almost anything - which is the Windows equivalent of knowing
  the Linux source tree layout (Linux ch. 01).

The one difference that shapes everything else

Windows guarantees a stable kernel driver ABI. That single decision explains the closed driver ecosystem, the INF/driver-store installation model, mandatory signing, the WDF frameworks, and why Microsoft invests so heavily in verification tools: they cannot fix your driver during a refactor, because they never see it. Linux made the opposite trade — churn the API freely, and fix every in-tree driver when you do.

Neither is wrong. They are consistent answers to "who is responsible for keeping drivers working".

A syscall, end to end

The clearest way to see the layers cooperating is to follow one ordinary operation from an application all the way into the kernel. Every abstraction in this track sits somewhere along this path, and knowing the path is what lets you place a new concept the moment you meet it.

  application:  ReadFile(hFile, buf, len, &read, NULL);
        |
        v
  kernel32.dll: parameter marshalling, then
        |
        v
  ntdll.dll:    NtReadFile
                  mov  x8, #0x06        ; the syscall number
                  svc  #0               ; (arm64)
        |
        v  =============== kernel mode ===============
        |
  KiSystemService -> the SSDT -> NtReadFile in ntoskrnl
        |
        v
  I/O MANAGER (Io):
        · validate the handle    -> ObReferenceObjectByHandle
        · find the FILE_OBJECT and its DEVICE_OBJECT
        · BUILD AN IRP: IRP_MJ_READ, with the buffer, length
          and offset
        · IoCallDriver(deviceObject, irp)
        |
        v
  THE TOP DRIVER in the stack
        · may complete it, or pass it down
        |
        v
  ... each lower driver in turn ...
        |
        v
  THE FUNCTION DRIVER (yours)
        · does the work, or queues the IRP and returns
          STATUS_PENDING
        |
        v
  IoCompleteRequest(irp, IO_NO_INCREMENT)
        · completion routines run, bottom-up
        · the I/O manager copies results back
        · the waiting thread is woken
        |
        v
  ReadFile returns TRUE

  COMPARE Linux: read() -> vfs_read -> f_op->read on your
  file_operations. One indirection, one driver.

  Windows routes EVERYTHING through a self-contained REQUEST
  OBJECT (the IRP) that travels down a STACK of drivers, and
  may complete asynchronously at any level. That is more
  machinery, and it is what makes filter drivers, layered
  storage, and asynchronous I/O uniform rather than
  per-subsystem.

Everything is an object

Windows models almost everything nameable — files, devices, processes, events, registry keys — with one shared mechanism. That uniformity is deliberate: it means one set of rules for naming, security and lifetime serves the entire system, and learning it once pays off everywhere.

/* The object manager (Ob) is the closest Windows analogue to
   Linux's VFS-plus-everything, and it is more general.     */

   \                        the root
   \Device\                 device objects
   \Device\HarddiskVolume1
   \Driver\                 loaded drivers
   \DosDevices\  (\??\)     symbolic links: C: -> \Device\...
   \BaseNamedObjects\       named events, mutexes, sections
   \Windows\                windowing
   \REGISTRY\               the registry, as objects
   \KernelObjects\

/* EVERY object has:
     a header with a type, a NAME (optionally), a reference
     count, a handle count, and a security descriptor
     a body specific to its type

   TYPES: Process, Thread, File, Device, Driver, Event,
   Mutant, Semaphore, Timer, Section, Key, Token, Job, ...

   HANDLES are per-process indices into a handle table, with
   an access mask. A handle is NOT a pointer, and converting
   one is an explicit, checked operation:                   */

        status = ObReferenceObjectByHandle(handle,
                                           FILE_READ_DATA,
                                           *IoFileObjectType,
                                           UserMode,   /* CHECK
                                                          ACCESS */
                                           &fileObject,
                                           NULL);
        ...
        ObDereferenceObject(fileObject);

/* THE `UserMode` ARGUMENT IS A SECURITY CONTROL: it tells the
   object manager to enforce the access mask as if a user-mode
   caller asked. Passing KernelMode skips those checks - and
   passing it while handling a user request is a classic
   privilege-escalation bug (chapter 04).                  */

/* SEE IT: the WinObj tool from Sysinternals browses the whole
   namespace. Run it once; it makes the model concrete.   */

The registry, not the device tree

If you have come from Linux, this is the substitution that matters most. Windows has no device tree; hardware description, driver configuration and service settings all live in one hierarchical database that the kernel itself reads at boot.

; Where a driver's configuration lives:

HKLM\SYSTEM\CurrentControlSet\Services\MyDriver
    ImagePath     = \SystemRoot\System32\drivers\mydriver.sys
    Type          = 1          ; SERVICE_KERNEL_DRIVER
    Start         = 3          ; 0=boot 1=system 2=auto
                               ; 3=demand 4=disabled
    ErrorControl  = 1
    Group         = Extended Base

HKLM\SYSTEM\CurrentControlSet\Enum\PCI\VEN_1234&DEV_5678\...
    Service       = MyDriver   ; which driver claims it
    ClassGUID     = {...}
    HardwareID    = PCI\VEN_1234&DEV_5678
    Driver        = {class}\0001

; Per-device settings, the closest thing to DT properties:
HKLM\SYSTEM\CurrentControlSet\Enum\...\Device Parameters
    FifoDepth     = 32
    SampleRate    = 48000

/* READING them from a driver, via WDF: */
        WDFKEY key;
        ULONG  value;
        DECLARE_CONST_UNICODE_STRING(name, L"FifoDepth");

        status = WdfDeviceOpenRegistryKey(device,
                        PLUGPLAY_REGKEY_DEVICE,
                        KEY_READ, WDF_NO_OBJECT_ATTRIBUTES,
                        &key);
        if (NT_SUCCESS(status)) {
                status = WdfRegistryQueryULong(key, &name,
                                               &value);
                WdfRegistryClose(key);
        }
        if (!NT_SUCCESS(status))
                value = DEFAULT_FIFO_DEPTH;   /* always have a
                                                 default      */

/* WHERE THE VALUES COME FROM: the INF file writes them at
   install time (chapter 20). So the INF plays the role the
   device tree plays on Linux - describing this particular
   device - but it is applied once, into the registry, rather
   than parsed at every boot.

   ON ARM64 WINDOWS, hardware enumeration comes from ACPI
   rather than a device tree: the ACPI namespace describes the
   devices, and the PnP manager creates a device object for
   each.                                                    */

NTSTATUS

Kernel functions do not set errno and do not throw. They return a status code, and the single most common beginner mistake in Windows driver code is testing it the wrong way — the correct test is not a comparison against zero.

/* Windows kernel functions return NTSTATUS, not a negative
   errno.                                                    */

        NTSTATUS status;

        status = SomeFunction();
        if (!NT_SUCCESS(status))
                return status;

/* THE ENCODING - bits 31:30 are the severity: */
        0x0.......   SUCCESS
        0x4.......   INFORMATIONAL
        0x8.......   WARNING
        0xC.......   ERROR

        NT_SUCCESS(s)       s >= 0     (severity 0 or 1)
        NT_INFORMATION(s)
        NT_WARNING(s)
        NT_ERROR(s)

/* NOTE NT_SUCCESS IS TRUE FOR WARNINGS. A function returning
   STATUS_BUFFER_OVERFLOW (0x80000005) passes NT_SUCCESS().
   Checking `status == STATUS_SUCCESS` and checking
   `NT_SUCCESS(status)` are DIFFERENT tests, and choosing the
   wrong one is a real bug. Be deliberate.                 */

/* THE ONES YOU WILL SEE CONSTANTLY: */
        STATUS_SUCCESS
        STATUS_PENDING                 /* async, will complete
                                          later - not an error */
        STATUS_INVALID_PARAMETER
        STATUS_INSUFFICIENT_RESOURCES  /* = -ENOMEM */
        STATUS_BUFFER_TOO_SMALL
        STATUS_INVALID_DEVICE_REQUEST  /* = -ENOTTY */
        STATUS_DEVICE_NOT_READY
        STATUS_ACCESS_DENIED
        STATUS_NOT_SUPPORTED
        STATUS_CANCELLED
        STATUS_TIMEOUT
        STATUS_UNSUCCESSFUL            /* the last resort */

/* Win32 error codes are DIFFERENT again; user mode sees those
   via GetLastError(). The I/O manager translates. So one
   failure has two names, and the WinDbg command
   `!error <value>` decodes either.                        */

UNICODE_STRING

Kernel strings are not C strings. They are counted, UTF-16, and frequently not NUL-terminated, which means the string functions you know will read past the end of the buffer. This catches everyone exactly once, and the traps below are worth reading before you write any string code.

/* Kernel strings are counted UTF-16, not NUL-terminated
   char*. This catches every newcomer once.                */

typedef struct _UNICODE_STRING {
        USHORT Length;           /* in BYTES, not characters */
        USHORT MaximumLength;    /* in BYTES */
        PWSTR  Buffer;           /* NOT necessarily
                                    NUL-terminated!          */
} UNICODE_STRING, *PUNICODE_STRING;

/* CREATING one: */
        UNICODE_STRING name;
        RtlInitUnicodeString(&name, L"\\Device\\MyDevice");

        /* or, for a constant, with no runtime cost: */
        DECLARE_CONST_UNICODE_STRING(name,
                                     L"\\Device\\MyDevice");

/* WORKING with them: */
        RtlCopyUnicodeString(&dst, &src);        /* truncates */
        RtlAppendUnicodeStringToString(&dst, &src);
        RtlCompareUnicodeString(&a, &b, TRUE);   /* case-insens */
        RtlEqualUnicodeString(&a, &b, TRUE);
        RtlUnicodeStringToAnsiString(&ansi, &uni, TRUE);

/* PRINTING one - the %wZ specifier takes a POINTER: */
        DbgPrint("name: %wZ\n", &name);

/* THE TRAPS:
     · Length is in BYTES. A 5-character string has
       Length == 10. Off-by-two-times is common.
     · the buffer may not be NUL-terminated, so wcslen() and
       friends can run off the end. Use Length.
     · a UNICODE_STRING from user mode has an attacker-chosen
       Length AND Buffer. Validate both, and probe the buffer
       (chapter 08).                                        */

LIST_ENTRY and CONTAINING_RECORD

The other idiom you will meet on the first page of almost any driver, and the one that looks backwards until someone explains it. Kernel lists do not hold pointers to your data — the list node lives inside your structure, as an ordinary member, which is why adding something to a list can never fail and why one implementation serves every type in the system.

/* YOUR structure contains the node, not the other way round: */

typedef struct _MY_REQUEST {
        ULONG       Id;
        LIST_ENTRY  Link;        /* <-- the node IS a member */
        PVOID       Payload;
} MY_REQUEST, *PMY_REQUEST;

/* THE HEAD is just another LIST_ENTRY, pointing at itself
   when the list is empty: */
        LIST_ENTRY  Head;
        InitializeListHead(&Head);

        InsertTailList(&Head, &req->Link);    /* never fails */
        InsertHeadList(&Head, &req->Link);
        RemoveEntryList(&req->Link);
        if (IsListEmpty(&Head)) { ... }

/* WALKING IT - you get a pointer to the MEMBER, in the middle
   of someone's structure, and need to get back to the start.
   That is what CONTAINING_RECORD does, with the same pointer
   arithmetic Linux spells container_of():                   */

        PLIST_ENTRY entry = Head.Flink;

        while (entry != &Head) {
                PMY_REQUEST req =
                        CONTAINING_RECORD(entry, MY_REQUEST, Link);
                /*  = (PMY_REQUEST)((PCHAR)entry -
                       FIELD_OFFSET(MY_REQUEST, Link))        */

                DoSomething(req);
                entry = entry->Flink;
        }

/* REMOVING WHILE WALKING - capture the next pointer BEFORE
   you free, or you read freed memory to advance:           */
        entry = Head.Flink;
        while (entry != &Head) {
                PLIST_ENTRY next = entry->Flink;      /* first! */
                PMY_REQUEST req =
                        CONTAINING_RECORD(entry, MY_REQUEST, Link);
                RemoveEntryList(entry);
                ExFreePoolWithTag(req, MYDRV_TAG);
                entry = next;
        }

/* THE LIST DOES NO LOCKING. InsertTailList and
   RemoveEntryList are plain pointer writes. YOU hold the
   right lock for the IRQL involved (chapter 10) - or use
   ExInterlockedInsertTailList, which takes a spinlock for
   you.

   YOU HAVE ALREADY SEEN CONTAINING_RECORD without noticing:
   it is how a driver gets from a generic object the system
   handed it back to its own state, and WDF's typed context
   accessors (chapter 14) do exactly the same arithmetic
   behind a generated function.                             */

Getting set up

Before writing a line, you need a build environment and a way to run a driver without destroying your own machine. The standard arrangement is two machines — or two virtual machines — with a debugger attached from one to the other.

# WHAT YOU NEED:
#   Visual Studio 2022 (Community is fine)
#     + "Desktop development with C++"
#     + the Windows SDK
#   The Windows Driver Kit (WDK), matching the SDK version
#   The WDK's Visual Studio extension
#
# https://learn.microsoft.com/windows-hardware/drivers/download-the-wdk

# NEW PROJECT -> "Kernel Mode Driver, Empty (KMDF)"
# That template gives you a .sys, a .inf, and the signing and
# packaging steps already wired up.

# A TEST MACHINE IS NOT OPTIONAL. A driver bug bugchecks the
# machine, and you do not want that to be your development
# box. Use a VM:
#   Hyper-V, VMware or VirtualBox
#   with a serial or network kernel-debugging connection to
#   the host (chapter 23)

# ENABLE TEST SIGNING on the target, so unsigned-by-Microsoft
# builds will load (chapter 21):
    bcdedit /set testsigning on
    bcdedit /set nointegritychecks off
    shutdown /r /t 0
# A "Test Mode" watermark appears on the desktop. That is
# expected.

# AND SET UP KERNEL DEBUGGING on the target now, before you
# need it:
    bcdedit /debug on
    bcdedit /dbgsettings net hostip:192.168.1.10 port:50000 \
            key:1.2.3.4
