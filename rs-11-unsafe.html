Unsafe Rust and the unsafe boundary

Hardware access requires operations the compiler cannot verify. unsafe is where you take responsibility for them — and the discipline that makes Rust worthwhile is confining it behind safe abstractions rather than spreading it through the codebase.

What unsafe actually permits

unsafe is routinely misunderstood as switching the safety off. It permits exactly five additional operations, and knowing the list precisely is what makes the keyword usable rather than frightening.

   `unsafe` enables exactly FIVE things:

     1. dereference a RAW POINTER (*const T, *mut T)
     2. call an `unsafe fn` (including every extern "C"
        function)
     3. access or modify a `static mut`
     4. implement an `unsafe trait` (Send, Sync, and your own)
     5. access a union field

   IT DOES NOT:
     · turn off the borrow checker
     · turn off lifetimes
     · turn off type checking
     · make anything faster
     · permit undefined behaviour

   THAT LAST POINT IS THE ONE PEOPLE GET WRONG. `unsafe` does
   not grant permission to break the rules; it moves
   RESPONSIBILITY FOR UPHOLDING THEM from the compiler to you.
   Breaking them inside `unsafe` is still undefined behaviour,
   with all the consequences from compilers chapter 15 - and
   worse, because the rest of the program was optimised on
   the assumption that you did not.

   THE PROPERTIES YOU MUST UPHOLD:
     · no dangling or misaligned pointer dereferences
     · no aliasing violations: never two &mut, never &mut
       alongside &
     · no data races
     · every value must be VALID for its type - no bool that
       is 2, no char that is not a scalar value, no
       uninitialised reads
     · no breaking of any safe abstraction's invariants

Raw pointers

Raw pointers are what C pointers are, with no guarantees attached. The rules for using them correctly are stricter than C's, and violating them is undefined behaviour rather than a portability question.

    let x = 42;
    let p: *const i32 = &x;
    let mut y = 42;
    let q: *mut i32 = &mut y;

    // creating them is SAFE; dereferencing is not
    unsafe { println!("{}", *p); }
    unsafe { *q = 43; }

/* RAW POINTERS, unlike references:
     · may be null
     · may dangle
     · have no lifetime
     · may alias freely
     · are not automatically dereferenced

/* THE OPERATIONS worth knowing: */
    core::ptr::null::<u8>()
    core::ptr::null_mut::<u8>()
    p.is_null()
    p.offset(3)                 // in ELEMENTS, and it is UB
                                // to go out of bounds
    p.add(3)  p.sub(3)
    p.wrapping_add(3)           // no UB, but the result may
                                // not be dereferenceable

    unsafe { core::ptr::read(p) }
    unsafe { core::ptr::write(q, 5) }
    unsafe { core::ptr::read_volatile(p) }      // for MMIO
    unsafe { core::ptr::write_volatile(q, 5) }
    unsafe { core::ptr::copy(src, dst, n) }     // memmove
    unsafe { core::ptr::copy_nonoverlapping(src, dst, n) }
                                                // memcpy
    unsafe { core::ptr::swap(a, b) }

/* ALIGNMENT MATTERS AND IS CHECKED IN DEBUG BUILDS: */
    let buf: [u8; 8] = [0; 8];
    let p = buf.as_ptr() as *const u32;
    unsafe { *p }               // UB if buf is not 4-aligned
    // correct:
    unsafe { p.read_unaligned() }
    // or, better, no unsafe at all:
    u32::from_le_bytes(buf[0..4].try_into().unwrap())

/* AND `addr_of!` FOR UNALIGNED OR PACKED FIELDS - creating
   a reference to a misaligned field is UB even without
   dereferencing it: */
    use core::ptr::addr_of;
    let p = unsafe { addr_of!((*packed_ptr).field) };
    let v = unsafe { p.read_unaligned() };

The unsafe boundary

This is the most important idea in the chapter: unsafe code is not spread through a program, it is contained behind a safe interface that cannot be misused. Getting the boundary right is the whole discipline.

   THE CENTRAL DISCIPLINE:

     unsafe code should be SMALL, LOCAL, and WRAPPED IN A SAFE
     API whose invariants you can state and check.

   The goal is not to eliminate unsafe - hardware access
   requires it. The goal is that the REST of the program
   never needs it, so that a memory-safety bug can only be in
   the few hundred lines you audited.

   BAD:                          GOOD:
   ┌────────────────────┐        ┌────────────────────┐
   │ unsafe everywhere  │        │   safe application │
   │ every driver, every│        ├────────────────────┤
   │ access, no         │        │   safe driver API  │
   │ invariants written │        ├────────────────────┤
   │ down               │        │ unsafe: 20 lines,  │
   │                    │        │ documented, tested │
   └────────────────────┘        └────────────────────┘

   THE TEST: can you state, in one sentence, what the caller
   must guarantee? If yes, that sentence is the safety
   comment, and the wrapper can be safe. If no, the
   abstraction is wrong.
/* --- A SAFE MMIO WRAPPER, the canonical example --- */

pub struct Uart {
    base: *mut u32,
}

// SAFETY: the caller of `new` guarantees exclusive access to
// this peripheral, so sending it between contexts is sound.
unsafe impl Send for Uart {}

impl Uart {
    /// # Safety
    /// `base` must be the address of a UART peripheral of
    /// this type, correctly clocked, and no other Uart must
    /// exist for the same address.
    pub const unsafe fn new(base: usize) -> Self {
        Uart { base: base as *mut u32 }
    }

    // SAFE from here on - the constructor took the promise
    pub fn write_byte(&mut self, b: u8) {
        while self.flags() & FR_TXFF != 0 {}
        // SAFETY: base is valid by the constructor's
        // contract; DR is within the peripheral's register
        // block
        unsafe { self.base.add(REG_DR)
                          .write_volatile(b as u32) };
    }

    fn flags(&self) -> u32 {
        // SAFETY: as above
        unsafe { self.base.add(REG_FR).read_volatile() }
    }
}

/* TWO UNSAFE BLOCKS, each one line, each with a SAFETY
   comment. Everything above is safe, and a user of this
   driver writes no unsafe at all.

/* THE CONVENTIONS the ecosystem follows, and clippy enforces:
     · `# Safety` doc section on every `unsafe fn`, stating
       what the CALLER must guarantee
     · `// SAFETY:` comment on every `unsafe` BLOCK, stating
       why the requirements hold HERE
     · #![deny(unsafe_op_in_unsafe_fn)] - so an unsafe fn
       still needs explicit blocks inside, rather than being
       unsafe throughout
     · #![warn(clippy::undocumented_unsafe_blocks)]        */
The two comment kinds, and why both

# Safety on a function is a precondition: what the caller must ensure. // SAFETY: on a block is a proof: why the preconditions are met at this site. A codebase with both can be audited by reading only the unsafe blocks and checking each proof — which is exactly the property that makes the guarantee worth anything.

Hardware access patterns

Memory-mapped I/O is the reason most embedded Rust contains any unsafe at all, and there is a standard way to do it that confines the unsafe to a few lines.

/* --- 1. VOLATILE, always, for MMIO --- */
    unsafe { ptr.write_volatile(v) }
    unsafe { ptr.read_volatile() }
/* A plain `*p = v` may be elided, reordered or merged - the
   same rule as C's volatile (C++ chapter 02). Rust has no
   `volatile` type qualifier; it has volatile OPERATIONS,
   which is the more honest design.

/* --- 2. USE A PAC, and write no unsafe at all --- */
    let p = pac::Peripherals::take().unwrap();
    p.gpioa.moder.modify(|_, w| w.moder5().output());
    p.gpioa.odr.write(|w| w.odr5().set_bit());
/* The svd2rust-generated PAC (chapter 20) contains the
   unsafe; you get a typed, field-named, safe API. This is
   what "confine unsafe to a small audited layer" looks like
   when the layer is generated from the vendor's own SVD
   file.

/* --- 3. A CRITICAL SECTION for shared state --- */
    critical_section::with(|cs| {
        SHARED.borrow(cs).borrow_mut().update();
    });
/* The `cs` token proves interrupts are disabled
   (chapter 10). No unsafe needed at the use site.

/* --- 4. A STATIC BUFFER without `static mut` --- */
    use static_cell::StaticCell;
    static BUF: StaticCell<[u8; 1024]> = StaticCell::new();
    let buf: &'static mut [u8; 1024] = BUF.init([0; 1024]);
/* Safe, panics on double init, no heap.

/* --- 5. TRANSMUTE: almost always the wrong answer --- */
    let f: f32 = unsafe { core::mem::transmute(bits) };  // no
    let f = f32::from_bits(bits);                        // yes
    let bytes = unsafe { core::mem::transmute::<u32,
                                    [u8;4]>(x) };        // no
    let bytes = x.to_le_bytes();                         // yes
    let s = unsafe { core::str::from_utf8_unchecked(b) }; // no
    let s = core::str::from_utf8(b)?;                    // yes
/* transmute is the most dangerous function in Rust: it
   reinterprets bits with NO checking of size, validity or
   alignment. There is nearly always a safe alternative, and
   where there is not, `bytemuck` or `zerocopy` provide
   audited, trait-gated versions.

/* --- 6. slice::from_raw_parts, for a DMA buffer --- */
    // SAFETY: the DMA engine has finished (we checked the
    // completion flag), `ptr` points to `len` initialised
    // bytes within BUFFER, and no other reference to that
    // region exists.
    let data = unsafe {
        core::slice::from_raw_parts(ptr, len)
    };
/* One of the legitimate uses. Note the safety comment covers
   validity, initialisation, length AND aliasing - all four
   are required.                                          */

Unions and uninitialised memory

Two features that exist mainly for FFI and for performance-critical code, and that carry sharper edges than anything else in the chapter.

/* --- UNIONS, for FFI compatibility --- */
    #[repr(C)]
    union Register {
        word: u32,
        bytes: [u8; 4],
    }
    let r = Register { word: 0x1234_5678 };
    let b = unsafe { r.bytes };         // reading ANY field
                                        // is unsafe
/* Prefer an enum (chapter 05) unless you are matching a C
   layout. For bit reinterpretation, to_le_bytes is safe and
   clearer.

/* --- MaybeUninit, for genuinely uninitialised memory --- */
    use core::mem::MaybeUninit;

    let mut buf: [MaybeUninit<u8>; 1024] =
        unsafe { MaybeUninit::uninit().assume_init() };
        // ^ sound ONLY because MaybeUninit<u8> has no
        //   validity requirement

    let n = read_into(&mut buf);

    // SAFETY: read_into initialised the first `n` elements
    let data = unsafe {
        core::slice::from_raw_parts(buf.as_ptr() as *const u8,
                                    n)
    };

/* NEVER `mem::uninitialized()` - it is deprecated and always
   UB for types with validity requirements. And note that
   reading uninitialised memory is UB even for u8: the value
   is "poison" (compilers chapter 15), not a random number.

/* THE SAFE ALTERNATIVE, and usually the right one: */
    let mut buf = [0u8; 1024];          // zeroing 1 KB costs
                                        // ~100 cycles
/* Measure before deciding the initialisation is too
   expensive. It usually is not.                          */

Verifying unsafe code

Unsafe code cannot be checked by the compiler, which makes the tooling that can check it disproportionately valuable. These are the tools and what each one actually catches.

# --- MIRI: an interpreter that detects UB ---
    rustup +nightly component add miri
    cargo +nightly miri test

# It catches:
#   out-of-bounds accesses
#   use-after-free
#   invalid values (a bool that is 2)
#   misaligned accesses
#   ALIASING VIOLATIONS, under Stacked Borrows / Tree Borrows
#   data races
#   uninitialised reads
#   memory leaks
#
# MIRI IS THE MOST IMPORTANT TOOL IN THIS CHAPTER. It finds
# aliasing bugs that no amount of testing would, because the
# consequence of an aliasing violation is a wrong
# optimisation, not a crash.
#
# LIMITATION: it cannot run code that touches real hardware or
# calls into C. So structure the unsafe helpers so they can be
# tested against a mock on the host - the same argument as
# chapter 11's testing strategy.

# --- THE SANITIZERS ---
    RUSTFLAGS="-Zsanitizer=address" cargo +nightly test
    RUSTFLAGS="-Zsanitizer=thread"  cargo +nightly test

# --- CLIPPY LINTS worth denying ---
    #![deny(unsafe_op_in_unsafe_fn)]
    #![warn(clippy::undocumented_unsafe_blocks)]
    #![warn(clippy::multiple_unsafe_ops_per_block)]
    #![warn(clippy::missing_safety_doc)]
    #![warn(clippy::ptr_as_ptr, clippy::cast_ptr_alignment)]

# --- AND THE STRUCTURAL CHECK ---
    cargo geiger                # counts unsafe per dependency
    grep -rn 'unsafe' src/ | wc -l
# Track that number. In a well-structured embedded crate it
# should be in the tens and concentrated in a few files, not
# spread across every driver.

A review checklist

Unsafe code gets no help from the compiler, so the review has to supply what the compiler would. Working through a fixed list is what turns "this looks fine" into an actual check.

CheckWhy
Is there a # Safety section on every unsafe fn?The caller cannot uphold an unstated contract
Is there a // SAFETY: on every block?It is the proof that makes the audit possible
Is the block as small as it can be?Large blocks hide the operation that matters
Is every pointer non-null, aligned and in-bounds?All three are separate UB conditions
Could two &mut to the same data exist?The commonest and most damaging violation
Is the memory initialised before being read?Uninitialised reads are UB even for u8
Are all values valid for their type?A bool that is 2 is UB immediately
Does an interrupt or another core race here?Data races are UB regardless of the outcome
Is write_volatile used for MMIO?A plain write may be elided or reordered
Is there a safe alternative?Usually yes — from_bits, to_le_bytes, a PAC
Does Miri pass?It finds what testing cannot
Is the safe wrapper's invariant actually upheld?A safe API over unsound unsafe is worse than no wrapper
