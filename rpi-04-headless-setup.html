Headless bring-up: image, SSH and network

A development board with a monitor and keyboard attached is a desktop computer. A development board you reach over the network, reimage in ninety seconds and never physically touch is a tool. This chapter sets up the second kind.

Choosing an image

ImageUse when
Raspberry Pi OS Lite (64-bit)The right default for this track. No desktop, ~500 MB, boots in seconds, nothing running that you did not put there
Raspberry Pi OS (64-bit, desktop)Only if you need a GUI for the display or camera chapters
Ubuntu Server for PiCloser to a mainline kernel and a server distro; fewer Pi-specific conveniences and some overlays differ
Yocto / BuildrootWhat a product ships. Far more work; worth doing once, not for learning

Use 64-bit. The 32-bit image still exists for compatibility with older boards, but the ARM track on this site is AArch64 throughout, and a 32-bit userspace on an ARMv8 core teaches you the wrong instruction set.

Provisioning without ever attaching a monitor

   Raspberry Pi Imager can pre-seed everything before the
   card is ever inserted. This is the difference between a
   two-minute setup and a twenty-minute one with a keyboard.

   In Imager, choose the OS, choose the card, then open
   the SETTINGS / "Edit settings" panel and set:

     hostname          pidev              -> reachable as
                                             pidev.local
     username/password your account       -> there is no
                                             default login
                                             any more
     wifi SSID + PSK   if not using ethernet
     wifi country      REQUIRED, or the radio stays off
     locale/timezone   affects log timestamps
     ENABLE SSH        with PUBLIC KEY authentication,
                       pasting your ~/.ssh/id_ed25519.pub

   That last one matters: choosing "password authentication"
   here gives you a board reachable from your whole network
   with a password you will reuse. Public key only, from the
   start, costs nothing extra.

   THE OLD METHOD, still useful when Imager is unavailable:
   after writing the card, mount the FAT boot partition on
   your host and create files there directly.
# Manual headless enable, on the boot partition (chapter 03).
# Mount the card on your host; the FAT partition is the one
# you can read from any OS.

# 1. Enable SSH: an empty file named exactly "ssh"
$ touch /media/$USER/bootfs/ssh

# 2. Create the first user. Modern images have NO default
#    user, so without this the Pi boots and you cannot log
#    in. The password must be pre-hashed:
$ echo "myuser:$(echo 'mypassword' | openssl passwd -6 -stdin)" \
    > /media/$USER/bootfs/userconf.txt

# 3. Wi-Fi, if not using ethernet. On Bookworm and later,
#    NetworkManager is used and the old wpa_supplicant.conf
#    file is no longer the supported route - prefer Imager,
#    or configure it after first boot over ethernet.

# 4. Serial console (chapter 05) - do this now, not later:
$ echo "enable_uart=1" >> /media/$USER/bootfs/config.txt

# Then eject cleanly, boot, and find it.

Finding the board

# mDNS first - it works with no configuration and no router
# access, and it survives DHCP address changes.
$ ping pidev.local
$ ssh myuser@pidev.local

# If mDNS fails (some networks block it, some corporate
# networks are hostile to it), scan for it:
$ nmap -sn 192.168.1.0/24 | grep -i -B2 raspberry
$ arp -a | grep -iE "b8:27:eb|dc:a6:32|e4:5f:01|d8:3a:dd"
# Those OUI prefixes are Raspberry Pi Foundation ranges;
# there are others, and new ones appear.

# THE RELIABLE ANSWER: give it a fixed address. Two ways,
# and the first is better:

# (a) DHCP RESERVATION on your router, keyed to the MAC.
#     The Pi keeps using DHCP, so it works on any network,
#     but always lands on the same address at your desk.

# (b) A static address on the Pi itself. On Bookworm this
#     is NetworkManager:
$ sudo nmcli con mod "Wired connection 1" \
      ipv4.addresses 192.168.1.50/24 \
      ipv4.gateway 192.168.1.1 \
      ipv4.dns "1.1.1.1" \
      ipv4.method manual
$ sudo nmcli con up "Wired connection 1"

# Older releases used dhcpcd.conf. Check which your image
# has before following any tutorial:
$ systemctl is-active NetworkManager dhcpcd
A direct ethernet cable is the most reliable link there is

Plug the Pi straight into your laptop's ethernet port. Modern interfaces auto-negotiate the crossover, and with link-local addressing (169.254.x.x, which both ends do automatically) ssh myuser@pidev.local works with no router, no DHCP server and no Wi-Fi. It is immune to every network problem in your building, which makes it the right setup for a board you are actively breaking. Share your host's internet connection over that interface if the Pi needs to reach the outside.

SSH set up properly, once

# On your HOST, not the Pi. Do this once and stop typing
# passwords and hostnames forever.

$ ssh-keygen -t ed25519 -C "dev laptop"        # if needed
$ ssh-copy-id myuser@pidev.local               # if not pre-seeded

# ~/.ssh/config on the host:
Host pi
    HostName pidev.local
    User myuser
    IdentityFile ~/.ssh/id_ed25519
    # Keep one connection open and reuse it: subsequent
    # ssh/scp/rsync calls skip the handshake entirely.
    # This makes the deploy loop in chapter 07 feel instant.
    ControlMaster auto
    ControlPath ~/.ssh/cm-%r@%h:%p
    ControlPersist 10m
    # Survive Wi-Fi dropouts and a Pi that reboots:
    ServerAliveInterval 15
    ServerAliveCountMax 3
    # A board you reimage constantly changes host keys.
    # Do NOT disable checking globally; scope it here:
    StrictHostKeyChecking no
    UserKnownHostsFile ~/.ssh/known_hosts_pi

# Now:  ssh pi        scp file pi:      rsync -a src/ pi:dst/

# HARDEN THE PI ITSELF, even on a home network - it is a
# Linux box with a well-known default configuration:
$ sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' \
      /etc/ssh/sshd_config
$ sudo systemctl restart ssh
Set StrictHostKeyChecking no only for this host block

Reimaging generates a new host key, so a development board legitimately changes identity often — and the warning becomes noise you learn to click through. Scoping the exception to one Host entry with its own UserKnownHostsFile keeps that convenience local to the board while leaving real host-key verification intact everywhere else. Turning it off globally is how people end up ignoring a genuine man-in-the-middle warning years later.

First-boot checklist

# Confirm what you are actually running before you build
# anything on top of it.

$ cat /etc/os-release | head -2        # distro and version
$ uname -a                             # kernel, and aarch64
$ cat /proc/device-tree/model          # exact board revision
Raspberry Pi 5 Model B Rev 1.0

$ vcgencmd get_throttled               # 0x0 means healthy
throttled=0x0                          # anything else: see
                                       # chapter 18

$ df -h /                              # did the rootfs expand?
$ free -h
$ lsblk

# Expand the filesystem if the image did not (modern images
# do it automatically on first boot):
$ sudo raspi-config --expand-rootfs && sudo reboot

# Update once, at the start, then STOP. A board that
# auto-updates mid-project changes the kernel under your
# modules and invalidates yesterday's results:
$ sudo apt update && sudo apt full-upgrade -y
$ sudo apt install -y git build-essential vim tmux \
      i2c-tools gpiod libgpiod-dev python3-libgpiod \
      device-tree-compiler

# PIN THE KERNEL once you start building modules (chapter
# 16), or an apt upgrade will replace it and your out-of-
# tree module will refuse to load against the new one:
$ sudo apt-mark hold raspberrypi-kernel raspberrypi-bootloader

Make a golden image the moment it works

# The instant the board is configured the way you want,
# clone the card. This is your restore point, and it turns
# "I bricked it" from an afternoon into ninety seconds.

# On Linux/macOS host, with the card in a reader:
$ sudo dd if=/dev/sdX bs=4M status=progress | \
      gzip > pidev-golden-$(date +%F).img.gz

# Restore:
$ gunzip -c pidev-golden-2026-08-23.img.gz | \
      sudo dd of=/dev/sdX bs=4M status=progress conv=fsync

# CHECK THE DEVICE NAME TWICE. dd to the wrong device
# overwrites your own disk with no confirmation and no undo.
# Use lsblk immediately before, and prefer /dev/disk/by-id/
# paths which name the actual card reader.

# The image is the size of the CARD, not the data - a 64 GB
# card gives a 64 GB image. gzip handles the empty space
# well; pishrink is the usual tool if you want the file
# genuinely small.
