Rapid-fire fundamentals

Thirty-two questions that appear in embedded interviews constantly, with the answers that distinguish someone who has used the concept from someone who has read about it. Answer each aloud before opening it — recognition is not recall.

How to answer a rapid-fire question

   THE SHAPE OF A GOOD 60-SECOND ANSWER:

   1. The direct answer, in one sentence.
   2. The mechanism - why it is true.
   3. The boundary - what it does NOT do, or when it
      fails. This is the part that separates candidates.
   4. Optionally, where you have hit it.

   Example, for "what does volatile do?":

     1. It tells the compiler that a variable may change
        outside the program's control, so every access
        must actually happen.
     2. Without it the compiler may cache the value in a
        register, reorder accesses, or delete them - all
        legal, because C's abstract machine has no concept
        of a wire attached to memory.
     3. It does NOT make anything atomic, and it does NOT
        order accesses with respect to the HARDWARE. Two
        volatile writes to different peripherals can still
        land out of order past a bus bridge. You need a
        barrier for that.
     4. I hit this on a status-register poll that never
        exited at -O2.

   Step 3 is the whole game. Almost every candidate gets
   step 1. Very few volunteer the boundary unprompted, and
   interviewers are specifically listening for it.

C and memory

What does volatile do, and what does it not do?Junior

It tells the compiler the variable may change outside the program's control, so every read and write in the source must appear in the generated code, in order, and none may be cached in a register or elided.

What it does not do: it provides no atomicity — vol++ is still read-modify-write and still races. It provides no ordering with respect to hardware — the compiler will not reorder two volatile accesses relative to each other, but a write buffer or bus bridge still can, so you need a DMB/DSB for that. And it does not make a variable safe to share between threads; that needs an atomic or a lock.

Where it is required: memory-mapped registers, variables written by an ISR and read by main code, and variables written by DMA.

Listening forThe three things it does not do. Getting only the definition is a junior answer.
Weak answers"It stops the compiler optimising the variable" — vague, and it invites the follow-up you cannot answer. "It makes it thread-safe" — wrong, and a common belief.
  • Follow-up: "Where would you need both volatile and a barrier?" — a DMA completion flag: volatile so the poll re-reads it, a barrier so the buffer writes are visible before the flag is.
What are the three meanings of static in C?Junior

1. At file scope — internal linkage: the symbol is not visible outside this translation unit. This is the main tool for encapsulation in C and should be the default for anything not in a header.

2. On a local variable — static storage duration: it lives for the whole program, keeps its value between calls, and lives in .data or .bss rather than on the stack. On an MCU that also means it counts against your RAM budget permanently and is zero-initialised by startup code.

3. On a function — internal linkage again, which also lets the compiler inline more aggressively and lets the linker garbage-collect it if unused.

Embedded-specific angle: a static local makes a function non-reentrant, which matters if it can be called from both an ISR and main code.

Listening forAll three, plus the reentrancy consequence.
const, #define, or enum for a constant — which and why?Junior

const in almost all cases: it has a type, respects scope, is visible to the debugger, and on a Cortex-M it lands in flash rather than RAM. #define has no type and no scope, is invisible to the debugger, and can produce surprising substitutions — #define SIZE 10+2 then SIZE*4 is 18, not 48.

enum is right for a set of related integer constants, because it gives them a shared type that a compiler and a static analyser can check exhaustively in a switch.

Where #define is still correct: anything needed by the preprocessor itself — include guards, conditional compilation, array sizes in some older C standards, and stringification/token pasting.

Listening forThe flash-versus-RAM point, which is the embedded-specific reason.
Why does this struct occupy 12 bytes rather than 7, and how would you fix it?
struct s { char a; int b; char c; };
Junior

Alignment padding. int must be 4-byte aligned, so the compiler inserts 3 bytes after a; then c is followed by 3 more bytes of tail padding so that an array of these structs keeps every b aligned. Layout: a(1) pad(3) b(4) c(1) pad(3) = 12.

Fix by ordering members largest-first: { int b; char a; char c; } is 4+1+1+2 = 8 bytes. On a struct used in an array of thousands, that ordering is a real memory saving.

Do not reach for __attribute__((packed)) casually. It removes the padding but creates unaligned members, and on ARM an unaligned access to a member is either slower (M3 and above) or a fault (M0, and any access to Device memory). Packed is for matching an external wire or file format, not for saving RAM.

Listening forThe tail padding (many candidates only explain the middle padding) and the caution about packed.
How do you write a function that works regardless of endianness when parsing a network packet?Mid

Do not cast a pointer to a struct over the buffer. Read byte by byte and reassemble explicitly:

uint32_t be32(const uint8_t *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16)
         | ((uint32_t)p[2] <<  8) |  (uint32_t)p[3];
}

This is correct on any endianness, has no alignment requirement, and the compiler usually recognises the pattern and emits a single load plus a byte-reverse instruction — so it costs nothing. Casting a struct pointer over a buffer has three bugs at once: endianness, alignment, and padding.

The alternative is ntohl/htonl where available, or __builtin_bswap32, but those still leave you with the alignment problem if the buffer is not aligned.

Listening forNaming all three hazards of the struct-cast approach, not just endianness.
Where does a local array live, and what happens if it is too big?Junior

On the stack, allocated by adjusting the stack pointer at function entry. If it is too big it overflows the stack — and on a microcontroller with no MMU there is no guard page, so instead of a fault you silently overwrite whatever is adjacent: another task's stack, or your .bss. The symptom is a variable somewhere else changing for no reason, hours later.

Mitigations: put large buffers in static storage so the linker accounts for them; size stacks from measurement (watermarking) plus static analysis with -fstack-usage; and add an MPU guard region below each stack so an overflow becomes an immediate, attributable fault instead of corruption.

Listening for"No guard page, so it is silent corruption" — this is the answer that shows MCU experience rather than desktop experience.
Why is malloc discouraged in embedded systems, and what do you use instead?Mid

Four reasons: fragmentation — over a long run a heap can have enough free bytes but no contiguous block, so an allocation that succeeded for months suddenly fails; non-determinism — allocation time is not bounded, which breaks a real-time deadline; failure handling — every call needs an error path that is hard to test and usually wrong; and priority inversion — the allocator has a lock, so a high-priority task can block on it behind a low-priority one.

Instead: allocate everything statically at compile time, so the linker proves it fits; or use fixed-size pool allocators, where allocation is O(1), cannot fragment, and failure is a known, testable condition. If you must have a heap, allocate everything during initialisation and never free — which makes fragmentation impossible by construction.

Listening forFragmentation and determinism as distinct problems, plus a concrete alternative.
What is the difference between a pointer to const and a const pointer?Junior

const char *p — pointer to const: you cannot write *p, but you can point p elsewhere. char * const p — const pointer: you can write *p, but p itself cannot be reassigned. const char * const p — neither.

Read declarations right-to-left from the identifier: "p is a const pointer to char".

The embedded relevance: a pointer to a memory-mapped register is typically volatile uint32_t * const — the address never changes, the contents change outside your control. Getting that combination right is a small but reliable signal.

Listening forThe right-to-left reading rule, and ideally the MMIO example.

Hardware and peripherals

Walk me through what happens between power-on and the first line of main().Mid

On a Cortex-M: the brown-out circuit holds the core in reset until the supply is stable; the internal RC oscillator starts; boot pins or option bytes select what is mapped at address 0. The hardware then reads two words: the first becomes the main stack pointer, the second becomes the PC. That is the entire boot protocol.

Execution enters Reset_Handler, which copies .data from flash to RAM, zeroes .bss, calls SystemInit() to configure clocks and flash wait states, runs __libc_init_array() for C++ constructors, and calls main().

The detail worth volunteering: globals are not valid until the copy and zero loops have run, so anything executing before them — including some vendors' SystemInit() — is running in a language that merely resembles C. Writing SystemCoreClock there and having the .data copy overwrite it afterwards is a classic bug.

Listening forThe two-word handoff, and the ordering hazard around globals.
An interrupt is enabled but never fires. How do you debug it?Junior

Check the six gates in order, because exactly one of them is wrong: (1) is the peripheral clocked and configured to generate the event at all; (2) is the peripheral's own interrupt-enable bit set; (3) is its status flag actually being set — read it in a poll loop to confirm; (4) is the NVIC enable bit set for that IRQ; (5) is the priority such that it is not masked by BASEPRI or blocked by something already running; (6) is PRIMASK clear.

Reading the peripheral status register, NVIC_ISER, NVIC_ISPR (pending) and PRIMASK answers it every time. If pending is set but the handler never runs, it is masking or priority; if pending is never set, it is the peripheral.

The other classic cause: the handler name is misspelled, so the weak default handler is still linked and your function is never called. Nothing warns you.

Listening forA systematic gate-by-gate method rather than a list of guesses, and the misspelled-handler trap.
What are the rules for code inside an interrupt handler?Junior

Be short — tens of microseconds, because everything else waits. Never block: no mutex, no sleep, no waiting on a flag another task must set, because there is nothing to switch to. Never call a non-reentrant function or one that allocates. Clear the peripheral's status flag, or you will re-enter immediately and forever. Use only the ISR-safe variants of RTOS calls, and only if your priority is at or below the kernel's syscall threshold. Mark shared variables volatile.

The design principle underneath: an ISR should capture the event and hand it off. Put the byte in a ring buffer, signal a task, and return. All the parsing and decision-making happens outside.

Listening for"Defer the work" as the organising idea, not just a list of prohibitions.
When would you choose DMA over interrupts, with numbers?Mid

Compute the interrupt load. At 115200 baud you get 11,520 bytes/s; at roughly 30 cycles of overhead per interrupt that is 345,600 cycles/s, which on a 168 MHz core is 0.2% — interrupts are fine and simpler.

At 3 Mbaud you get 300,000 bytes/s, so 9,000,000 cycles/s ≈ 5.4% CPU and 300k interrupts per second, which starves everything else and collapses the moment something disables interrupts for 10 µs. Use DMA. The same arithmetic for a 1 Msample/s ADC gives 18% CPU doing nothing but copying — DMA, always.

The costs of DMA to acknowledge: buffer RAM, a controller to configure, cache maintenance on parts with a D-cache (Cortex-M7), buffers that must be in DMA-reachable memory and must not be on the stack, and a slightly harder debugging story.

Listening forThe arithmetic done out loud, and the costs named rather than DMA presented as free.
I2C or SPI for a new sensor — how do you decide?Junior

Usually the sensor decides: most support one. When you have a choice: SPI if you need speed (10–100 Mbit versus I2C's 0.1–1 Mbit) or if you want a bus that cannot hang. I2C if pins are scarce — ten devices on two wires versus three plus one chip-select each.

The point most candidates miss: count the interrupt lines. SPI and I2C slaves cannot initiate, so a sensor with new data needs a separate INT pin. Three interrupt-driven sensors on I2C is 2 + 3 = 5 pins against SPI's 3 + 3 = 6 — the advantage largely evaporates. And two identical sensors with a fixed I2C address need a multiplexer, which costs a part and two more wires.

Other decision factors: I2C has per-byte acknowledgement and can hang the bus (needing recovery logic); SPI has no error detection at all and cannot tell you whether the device is even present.

Listening forThe real pin arithmetic including interrupt lines, and the addressing constraint.
How do you debounce a mechanical switch, and where should that code live?Junior

A switch bounces for 1–20 ms, producing dozens of edges. The standard approach: on the first edge, disable that pin's interrupt and start a one-shot timer; when the timer expires, sample the pin once, act on the stable value, and re-enable the interrupt. That yields exactly one event per press, costs no polling, and keeps the ISR to a few instructions.

What not to do: a delay loop inside the ISR. It "works" and it blocks every other interrupt for 20 ms, which on a system with a control loop is catastrophic.

Alternative for a system that already has a periodic tick: sample the pin every 10 ms and require N consecutive equal readings. Simpler, no extra timer, slightly higher latency, and it composes well with a superloop.

On Linux the kernel does it for you — libgpiod exposes a debounce period as a line setting.

Listening forRejecting the delay-in-ISR approach explicitly.
Why does a peripheral register write sometimes do nothing?Junior

Most often the peripheral's clock is gated off. A peripheral with no clock does not fault — it silently discards writes and returns zero on reads. Enabling the clock in the RCC (or equivalent) register is the first step of every peripheral init.

Second most common: the write happened too soon after the clock enable. The enable is posted on the bus and the peripheral needs a couple of cycles; the idiomatic fix is a dummy read-back of the enable register, which forces the write to complete. Skipping it gives you code that works at -O0 and fails at -O2 because the optimiser tightened the instruction spacing.

Third: many peripherals latch configuration only while disabled and ignore writes to config fields while running. Configure first, enable last.

Listening forAll three, especially the read-back — it is a strong signal of hands-on register-level work.
What is the purpose of a pull-up resistor, and when do you need an external one?Junior

It defines the idle level of a line that would otherwise float. A floating CMOS input drifts near the switching threshold, so both transistors conduct — it reads randomly and wastes current, which matters enormously on a battery device.

Internal pull-ups (typically 20–50 kΩ) are fine for a button or a slow input. You need an external, stronger pull-up when the line must rise quickly against bus capacitance: I2C at 400 kHz needs a rise time under 300 ns, and with 100 pF of bus capacitance that requires roughly 2.2–4.7 kΩ. The internal resistors are far too weak and produce rounded edges and marginal timing that fails on long traces or hot days.

Also external: any open-drain bus shared between devices, and any line that must hold its state while the MCU is unpowered or in reset.

Listening forThe rise-time calculation, or at least the awareness that resistance and capacitance set the achievable speed.

RTOS and concurrency

Mutex or semaphore — what is the actual difference?Mid

A mutex has an owner; a semaphore does not. That single fact produces every practical difference.

Because a mutex knows who holds it, it can implement priority inheritance: while a low-priority task holds a mutex a high-priority task wants, the holder is temporarily raised to the waiter's priority, which bounds priority inversion. It can also support recursive acquisition, and it can enforce that only the owner releases it.

A semaphore is a counter with no owner, so anyone can give it. That makes it right for signalling — an ISR posting "data ready" to a task — and wrong for mutual exclusion, because using one as a lock silently gives up inheritance and reintroduces unbounded inversion.

The rule: mutual exclusion → mutex; signalling → semaphore. And never take a mutex in an ISR — there is no owner to record and no way to block, which is why no kernel offers xSemaphoreTakeFromISR.

Listening for"Ownership" as the root cause, not a list of surface differences.
Explain priority inversion and the two standard fixes.Mid

Three tasks: high, medium, low. Low takes a mutex; high becomes runnable, preempts low, and blocks on that mutex. Low is runnable again — but medium, which shares nothing with either, preempts it. Low never runs, so it never releases the mutex, so high never runs. High is effectively running at low's priority and is blocked by a task it outranks. The delay is unbounded, because any number of medium-priority tasks can keep arriving.

Priority inheritance: while low holds a mutex high wants, low runs at high's priority, so medium cannot preempt it. Priority ceiling: any task holding the mutex immediately runs at the highest priority of any task that can ever take it — which prevents the inversion and also prevents certain deadlocks, at the cost of raising priority even when there is no contention.

Bounded inversion — high waiting while low finishes its critical section — is unavoidable and fine; you bound it by keeping critical sections short. It is the unbounded case that must be designed out. This is the failure that put Mars Pathfinder into a reset loop, fixed by enabling priority inheritance on one mutex.

Listening forThe distinction between bounded and unbounded inversion, and the role of the third task.
How do you decide task priorities in an RTOS?Mid

For periodic tasks, rate-monotonic: shorter period gets higher priority. Not "more important" — more frequent. Liu and Layland proved this is optimal among fixed-priority schemes, meaning if any fixed-priority assignment can meet all deadlines, this one can.

Check schedulability with the utilisation bound: U = Σ(Cᵢ/Tᵢ) must be ≤ n(2^(1/n) − 1), which is 0.828 for two tasks, 0.757 for four, and tends to 0.693. That is why a fixed-priority real-time system is not planned above roughly 70% CPU.

Two things candidates forget: interrupt time must be included in the utilisation sum — a 20 µs ISR at 10 kHz is 20% before any task runs — and C must be the measured worst case, not the average, because the worst case is often 5–10× typical.

Listening forRate-monotonic by name, the ~69% figure, and the inclusion of interrupt load.
When is a superloop the right architecture, and when do you need an RTOS?Mid

A superloop with interrupts is behind more shipped firmware than every RTOS combined, and it is the right choice when the urgent work is short enough to live in ISRs and everything else can be written as non-blocking state machines. It has no data races between the loop functions by construction, no per-task stacks, no kernel RAM, and trivially analysable worst-case loop time. Below about 8 kB of RAM it is the only option.

You need a preemptive kernel when you have multiple independent deadlines that one loop cannot satisfy, or when sequential protocols with many wait states have made the state machines unreadable. That second reason is the honest one: an RTOS buys readability by letting you write blocking code that is correct, and it charges you data races in return.

What an RTOS does not do is make a slow system fast. If you miss a deadline because the computation takes too long, a scheduler adds overhead and changes nothing.

Listening forRecognition that the superloop is a legitimate architecture, and that an RTOS reallocates latency rather than creating CPU time.
Two contexts share a variable. Walk me through your options.Mid

First ask what the contexts are, because the answer differs. ISR↔task, task↔task and CPU↔DMA have different tools.

If it is a single aligned word and there is one writer: a plain volatile read/write is atomic on ARM and no lock is needed. This covers a surprising number of cases — a flag, a counter written only by an ISR.

Read-modify-write, or wider than a word: you need atomicity. Options in increasing cost: an atomic instruction (LDREX/STREX or LSE); briefly disabling interrupts (fine for a few instructions, and the only option inside an ISR); a mutex (tasks only, never in an ISR).

Producer/consumer streams: prefer a lock-free single-producer/single-consumer ring buffer, where one side writes the head and the other writes the tail, publishing the index after the data. Or just use the RTOS queue, which copies the data and handles blocking, waking and mutual exclusion in one object.

And note that a 64-bit counter is not atomic on a 32-bit core — it needs protection or a seqlock, or you will read a torn value roughly once a week in a busy system.

Listening forAsking which contexts first, and knowing that a single aligned word is already atomic.
What is a memory barrier and when do you need one on a microcontroller?Senior

An instruction that constrains the order in which memory accesses become visible. DMB orders memory accesses relative to each other; DSB waits until all preceding accesses have actually completed; ISB flushes the pipeline so subsequently fetched instructions see the new context.

On Cortex-M — largely in-order, no store buffer reordering to speak of in most implementations — you need them in four specific places rather than everywhere: after writing CONTROL or CPACR (ISB, because the very next fetch executes under new rules); after disabling an interrupt in the NVIC when you are about to free the buffer it uses (DSB+ISB, or an in-flight interrupt can still arrive); before entering a deep sleep mode (DSB, to drain posted writes); and around DMA buffer handoff, paired with cache maintenance on parts with a D-cache.

The framing that scores: volatile is for the compiler, a barrier is for the hardware. They solve different problems and you often need both.

Listening forThe compiler-versus-hardware distinction and at least one concrete place a barrier is mandatory.
How do you size a task's stack?Mid

Combine measurement with a bound. Watermarking: fill the stack with a known pattern at creation and later count how many words are still intact — FreeRTOS exposes this as uxTaskGetStackHighWaterMark. Run under peak load, deliberately exercising the error paths, then set the size to the observed maximum plus about 50%.

The limitation to volunteer: a watermark reports the worst case seen, not the worst case possible. If the error path that calls snprintf never ran during the test, its 200 bytes are not in the number. That is why you also use -fstack-usage plus the call graph to get a true static bound — and why recursion, alloca and VLAs are banned by embedded coding standards: they make the bound uncomputable.

Finally, add an MPU guard region below each stack so that being wrong produces an immediate, attributable fault rather than silent corruption. And remember each stack must also carry one exception frame (32 bytes, or 104 with FP context) unless interrupts run on a separate stack.

Listening forBoth measurement and static bounding, and the reason recursion is banned.
What does a watchdog actually protect against, and where should it be petted?Mid

It recovers a system that is powered but not making progress — a hung kernel, a deadlock, an infinite loop, a corrupted state machine. It is the only mechanism that recovers a device nobody can physically reach.

The rule that makes it useful: pet it only from the place that proves real progress. A watchdog fed by a timer interrupt or a dedicated thread will happily keep a completely stuck application alive forever — which is worse than no watchdog, because it hides the fault. Feed it from the main control loop after a successful cycle, or have each critical task check in and only feed the hardware when all of them have.

Also worth mentioning: record the reset cause at boot into non-volatile memory, or you will never know whether a field unit rebooted from a watchdog, a brown-out or a clean restart. A kernel-level watchdog does not catch a stuck application, which is why systemd offers WatchdogSec for the service in addition to the hardware timer.

Listening forThe petting rule, which is the part that distinguishes people who have used one from people who have configured one.

Systems and architecture

MMU or MPU — what is the difference and what does each buy you?Mid

An MMU translates addresses through page tables, giving each process its own virtual address space, demand paging, and hard isolation. An MPU does not translate at all — addresses stay physical — it only enforces permissions on a small number of regions, typically 8 or 16.

So an MPU cannot give you virtual memory, cannot give two processes the same address, and cannot isolate at page granularity. What it can do, cheaply, is turn silent corruption into an immediate fault: a no-access guard region below each stack makes an overflow fault at the instruction that overflowed and names the task; marking RAM and peripherals execute-never means a corrupted function pointer faults instead of executing data; marking .rodata read-only catches wild writes at the moment they happen.

Those three uses cost almost nothing and are worth doing on any MPU-equipped part. Full per-task isolation is real but constrained — with 8 regions and 3–4 spent on global policy, you get 4–5 per task, which runs out quickly.

Listening for"No translation" as the key distinction, and the practical high-value uses rather than a textbook definition.
Why does cache coherency matter for DMA, and what do you do about it?Senior

A DMA controller reads and writes main memory directly; the CPU reads and writes through its cache. On a part where the two are not hardware-coherent — Cortex-M7, for example — they can disagree.

Before a memory-to-peripheral transfer you must clean the cache, pushing your writes out to memory, or the DMA sends stale data. After a peripheral-to-memory transfer you must invalidate, or the CPU reads stale cache lines instead of the new data.

The subtlety worth volunteering: these operate on cache-line granularity, typically 32 bytes. If your DMA buffer shares a cache line with another variable, invalidating the buffer discards that variable's cached value too — so buffers must be aligned to the line size and padded to a multiple of it. Otherwise you get a corruption bug that depends on the linker's variable placement, which is about as unpleasant as debugging gets.

Alternatives: allocate DMA buffers from a region marked non-cacheable in the MPU, which trades throughput for never having to think about it.

Listening forBoth directions (clean and invalidate), and the cache-line granularity hazard.
How would you design a firmware update that cannot brick the device?Mid

A/B slots. Two application banks: run from A, write the new image into B, verify it (checksum and ideally a signature), set a flag telling the bootloader to try B, reboot. B must then confirm itself within a timeout; if it does not — because it crashes, or cannot reach the network — the watchdog resets and the bootloader falls back to A.

The property that matters: a power cut at any instant leaves a bootable system. During the download you are still running A; after the flag flip either B confirms or you revert. There is no window where neither bank is valid.

Costs to acknowledge: it roughly doubles your flash requirement, which candidates routinely forget when budgeting. Alternatives when flash is tight: a minimal recovery bootloader that can always re-download, which is smaller but leaves a window where the device needs network access to recover.

Use an existing implementation — RAUC, SWUpdate, Mender, MCUboot — rather than writing your own, because the failure cases are subtle.

Listening forThe confirmation step (not just A/B), and the flash doubling.
Where do you store a device's private key?Senior

Ideally in hardware that never reveals it: a secure element, a TPM, or an MCU with a key store where the key is generated on-device and only usable through a crypto engine. The design goal is that the key never exists in readable memory and never leaves the die — so extracting it requires physical attack rather than a firmware bug.

Next best: internal flash with readout protection enabled and the debug port disabled in production. Weaker, because readout protection on many parts has known bypasses, and because any firmware vulnerability can read it.

What to avoid: the same key on every device (one extraction compromises the fleet), keys in external flash (trivially readable with a clip), and keys baked into the firmware image (readable by anyone who obtains an update file).

Also cover provisioning: the key is generated per-device, ideally on-device so it is never transported, and the manufacturing line signs the corresponding public key into a certificate. That process needs designing too, and it is a place candidates rarely go unprompted.

Listening for"Generated on-device, never leaves" as the ideal, plus the provisioning question.
A product must run ten years on a battery. What dominates, and where do you look first?Mid

Do the arithmetic first: ten years is 87,600 hours, so a 2000 mAh cell allows about 23 µA average. That number is the design.

In a duty-cycled system the sleep current dominates the total even though it is the smallest number, because it is multiplied by the largest time. At a 0.1% duty cycle, 23 µA of budget means sleep must be a few microamps.

Where the microamps actually go, in order of how often it is the culprit: a floating input pin (each one can cost microamps to milliamps); a pull-up fighting a driven-low line (4.7 kΩ to 3.3 V held low is 700 µA continuously); a peripheral clock left enabled; an LED; an external sensor whose own sleep current exceeds your entire budget; and the regulator's quiescent current, which can cap your achievable sleep current before firmware runs at all.

And measure rather than model — sleep-current bugs are invisible to every software tool. You need an ammeter that resolves microamps and milliamps in the same trace, with the debugger detached, because SWD keeps clocks alive and makes measurements meaningless.

Listening forThe average-current arithmetic, and knowing that the debugger invalidates the measurement.
How do you diagnose a device that fails only in the field?Senior

Design the observability in before shipping, because you will not get the unit back in a reproducible state. Concretely: a crash log in a .noinit section that survives reset, recording the faulting PC, the fault status registers and the task name; the reset cause read from hardware at every boot; error counters per subsystem (I2C NACKs, CRC failures, watchdog resets, brown-outs) that are non-volatile and readable; and a way to extract all of it — a UART command, a BLE characteristic, an upload.

Then the analysis: addr2line on the recorded PC gives you the source line, provided you kept the exact binary and its symbols for every release — which means archiving build artefacts per version, a process requirement people forget.

The framing that scores: "a device that fails silently and a device that reports are different products", and the observability costs about forty lines of code if designed in, and is impossible to add afterwards.

Listening forNon-volatile crash logging and the archived-symbols requirement — both indicate having actually supported a fleet.
What is the difference between hard, firm and soft real-time? Give an example of each.Junior

Hard: a missed deadline is a system failure, possibly a safety event. An airbag deployment, motor commutation, a fuel injector. The value of a late result is not merely reduced — it is negative.

Firm: a missed deadline makes the result useless, but the system tolerates occasional misses. A video frame that arrives after its display slot is discarded; drop enough and quality degrades but nothing breaks.

Soft: a late result still has value, just less. A UI redraw, a temperature reading on a display, a log upload.

The design consequence: hard real-time drives you toward hardware enforcement or a small deterministic core with analysed worst-case timing, and away from Linux — which is precisely why so many products pair an application processor with a microcontroller. "Real-time" does not mean fast; it means predictable, and a slow system with a guaranteed bound is real-time while a fast one without is not.

Listening for"Predictable, not fast" — the single most common misunderstanding of the term.
You must cut $2 from a $15 BOM. How do you approach it?Senior

Start from the actual cost breakdown, biggest items first — usually the processor, the radio, the display, the enclosure and the PCB, in some order. Then ask of each: what requirement forces this, and is that requirement real?

The levers, roughly in order of yield: drop to a smaller MCU if the memory budget allows (which is why you did the budget); remove flash if the OTA scheme can be single-bank plus recovery; integrate discrete parts into the MCU (an on-chip ADC, an internal oscillator instead of a crystal — accepting the accuracy trade); reduce PCB layer count; relax component tolerances and temperature grades where the environment permits; consolidate two rails into one regulator.

What to protect: anything supporting safety, anything supporting field diagnosis or update, and test points. Saving twenty cents by deleting a debug header costs far more the first time a unit comes back.

And say the non-obvious thing: at volume, the cost of a part is not just its price — it is also qualification, second-sourcing and ten-year availability. A cheaper part with one supplier can be more expensive overall.

Listening forStarting from data rather than intuition, and knowing what must not be cut.

Check yourself

  • Give the four-part shape of a good rapid-fire answer, and say which part candidates omit.
  • State three things volatile does not do.
  • Explain why a stack overflow on an MCU is silent, and the two mitigations.
  • Give the interrupt-load arithmetic that decides between interrupts and DMA.
  • Explain the root difference between a mutex and a semaphore.
  • Describe unbounded priority inversion and both standard fixes.
  • State the rate-monotonic rule and the utilisation bound, including interrupt time.
  • Say when a plain volatile variable needs no lock, and when it does.
  • Give the two cache maintenance operations for DMA and the alignment hazard.
  • Explain why "real-time" means predictable rather than fast.
