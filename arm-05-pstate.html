PSTATE and the condition flags

ARMv7 had one CPSR register holding all processor state. AArch64 broke it into independently accessible fields called PSTATE. Understanding those fields — especially the interrupt masks — is what lets you read an exception handler, a critical section, or a crash dump.

What PSTATE is

Not a register

PSTATE is an abstraction: a collection of processor state bits, each accessed through its own system-register name. There is no instruction that reads all of PSTATE at once during normal execution. It is only gathered into a single value when an exception is taken, at which point the hardware writes it into SPSR_ELx — and ERET restores it from there.

The fields below fall into three groups worth telling apart. NZCV and DAIF are the ones you read and write constantly — flags from the last comparison, and the interrupt masks. EL and SPSel describe where you currently are and which stack you are using, and you query them rather than set them directly. Everything below nRW is a security or debug feature that most code never touches explicitly, but that shows up when you are chasing a specific class of bug — PAN when a kernel NULL-pointer dereference behaves unexpectedly, BTYPE when a jump is rejected under branch protection, TCO when Memory Tagging is involved. Knowing the field exists is often enough; you look up its exact semantics only when you need it.

The condition flags

Four bits summarise the result of the last flag-setting operation, and every conditional branch in the instruction set tests some combination of them. They are also the reason comparison and branch can be separate instructions.

   N  Negative   the result's sign bit was 1
   Z  Zero       the result was zero
   C  Carry      unsigned overflow (add) / NO borrow (subtract)
   V  oVerflow   SIGNED overflow

  Set only by instructions with the S suffix, or by CMP/CMN/TST/TEQ
  (which are themselves encoded as SUBS/ADDS/ANDS with XZR as the
  destination — see chapter 03).

  THE POINT of having both C and V: one comparison sets both, so
  the same CMP serves signed and unsigned tests. The condition code
  you branch on decides which interpretation applies.

/* Why the signed/unsigned distinction is not academic: */

        mov     w0, #-1              // 0xFFFFFFFF
        mov     w1, #1
        cmp     w0, w1

        b.lt    signed_less          // TAKEN:   -1 < 1        ✓
        b.lo    unsigned_less        // NOT taken: 0xFFFFFFFF > 1 ✓

/* Both are correct — for their respective interpretations. Using
   the wrong condition is the assembly equivalent of the signed/
   unsigned comparison bug in C chapter 02, and it is exactly as
   easy to get wrong.                                         */

/* Detecting signed overflow explicitly: */
        adds    w0, w1, w2
        b.vs    overflow_handler     // V set = signed overflow
/* This is what __builtin_add_overflow compiles to (C ch. 02). */
/* Flags survive across unrelated instructions, because most
   instructions do NOT set them. That enables useful scheduling: */

        cmp     x0, x1               // compute the condition EARLY
        ldr     x2, [x3]             // ...do a long-latency load...
        add     x4, x5, x6           // ...and other work...
        b.eq    equal                // ...then branch. The load has
                                     //    had time to complete.
/* On x86 nearly every instruction clobbers EFLAGS, so this
   separation is not possible. It is a small but real advantage
   of the explicit-S design.                                   */

The interrupt masks

Four more bits decide which kinds of interrupt the processor will currently accept. Masking them is how a critical section becomes uninterruptible — and forgetting to unmask them is how a system silently stops responding.

   D  Debug     mask debug exceptions
   A  SError    mask System Errors (imprecise external aborts)
   I  IRQ       mask normal interrupts
   F  FIQ       mask fast interrupts

   1 = MASKED (disabled).  0 = enabled.

   In DAIF, the bits sit at:   D=9  A=8  I=7  F=6

        msr     daifset, #2      // set I  → DISABLE IRQ
        msr     daifclr, #2      // clear I → ENABLE IRQ
        msr     daifset, #3      // set I and F
        msr     daifset, #0xF    // mask everything

   The immediate is a 4-bit mask over {D,A,I,F} = bits {3,2,1,0}
   of the immediate. So #2 = 0b0010 = the I bit.
/* Save-and-restore is the ONLY correct pattern for a critical
   section. Unconditionally re-enabling is a serious bug.     */

static inline unsigned long irq_save(void)
{
        unsigned long flags;
        asm volatile("mrs %0, daif\n\t"
                     "msr daifset, #2"
                     : "=r"(flags) :: "memory");
        return flags;
}

static inline void irq_restore(unsigned long flags)
{
        asm volatile("msr daif, %0" :: "r"(flags) : "memory");
}

/* Why unconditional enable is wrong:

        outer_lock();          // disables IRQs
            inner_lock();      // disables IRQs
            inner_unlock();    // ENABLES IRQs  ← WRONG
        ...                    // now running unprotected inside
                               //    the OUTER critical section
        outer_unlock();

   With save/restore, the inner unlock restores "already disabled"
   and nesting works. This is exactly why Linux has
   spin_lock_irqsave() and not just spin_lock_irq()
   (OS chapter 09).                                          */
Hardware masks D, A, I and F on every exception entry

This is not optional and not configurable. The reason is that ELR_ELx and SPSR_ELx are single registers, not a stack: a second exception arriving before your handler saved them would overwrite the return address, and you could never get back. Your handler saves them to the kernel stack first, and only then may unmask to allow nesting. Getting this order wrong destroys the interrupted context (chapter 28).

The practical consequence: on a TrustZone system, a Non-secure OS cannot mask secure interrupts by clearing I, because they arrive as FIQ and are configured to be taken to EL3. That separation is what lets the secure world preempt the normal world reliably (security track).

PAN, UAO and the kernel/user boundary

These features exist to stop a specific class of attack: kernel code being tricked into reading or executing user-supplied memory. They work by making such accesses fault by default, which is why kernels must deliberately turn them off to copy user data.

/* PAN (Privileged Access Never, ARMv8.1) — when set, EL1 and EL2
   accesses to memory marked user-accessible FAULT.

   Why: it turns "kernel accidentally dereferenced a user pointer"
   from a silent, exploitable bug into an immediate fault. It is
   the ARM equivalent of x86's SMAP.                          */

        msr     pan, #1              // enable PAN

/* Legitimate access to user memory then requires explicitly
   lifting it, which is exactly what copy_to_user does:      */
        msr     pan, #0
        // ... the actual copy, with an exception fixup installed
        msr     pan, #1

/* UAO (User Access Override, ARMv8.2) makes the unprivileged
   load/store instructions (LDTR/STTR) behave as privileged,
   which lets the kernel use ONE code path for both cases.  */

/* This is why you must never dereference a __user pointer
   directly (OS chapter 03) — on a PAN-enabled system it does not
   silently work, it faults.                                */

Reading PSTATE in a crash dump

PSTATE appears in every crash dump, usually as a single hexadecimal value. Decoding it takes a few seconds and frequently tells you the exception level, the interrupt state and the stack in use — before you read a single line of the trace.

/* A Linux arm64 oops prints the saved PSTATE: */

pstate: 60400009 (nZCv daif +PAN -UAO -TCO -DIT -SSBS BTYPE=--)
        ^^^^^^^^  ^^^^ ^^^^  ^^^^
        raw value │    │     features
                  │    └── masks: lowercase = CLEAR (enabled)
                  │                UPPERCASE = SET (masked)
                  └─────── flags:  lowercase = clear, upper = set

/* Reading it:
     nZCv   → N=0, Z=1, C=1, V=0   (the last comparison was equal)
     daif   → all lowercase = interrupts were ENABLED
     DAIF   → all uppercase = all masked (typical inside a handler)
     +PAN   → PAN was active, so this was NOT a user-memory access

   The low bits of the raw value encode the EL and SPSel:
     0x...09 = 0b1001 → EL2h    0x...05 = 0b0101 → EL1h
     0x...04 = 0b0100 → EL1t    0x...00 = 0b0000 → EL0t

   So `pstate: ...09` means the fault happened at EL2 using
   SP_EL2 — which immediately tells you it was hypervisor code,
   not the guest.                                            */
# in gdb
p/x $cpsr                    # PSTATE, on targets that expose it
p $pstate

# in Linux, at runtime
cat /proc/cpuinfo | grep Features       # pan, uao, ssbs, bti...

# check what the kernel enabled
dmesg | grep -iE 'PAN|SSBS|BTI|MTE'

SPSR: PSTATE, frozen

PSTATE has to be preserved across an exception, because the handler will change it. The saved copy is what makes returning to the interrupted code possible, and modifying it deliberately is how a kernel changes what it returns to.

On exception entry the hardware packs PSTATE into SPSR_ELx:

   31 30 29 28        21 20    12 11 10  9  8  7  6  5  4  3   0
  ┌──┬──┬──┬──┬────────┬──┬─────┬─────┬──┬──┬──┬──┬──┬──┬───────┐
  │ N│ Z│ C│ V│  ...   │IL│ ... │ ... │ D│ A│ I│ F│ 0│nRW│ M[3:0]│
  └──┴──┴──┴──┴────────┴──┴─────┴─────┴──┴──┴──┴──┴──┴──┴───────┘

   M[3:0] encodes the EL and stack selection to return to:
        0b0000  EL0t        0b0100  EL1t        0b1000  EL2t
                            0b0101  EL1h        0b1001  EL2h
        0b1100  EL3t        0b1101  EL3h

   ERET restores PSTATE from SPSR_ELx and PC from ELR_ELx, both
   ATOMICALLY. That atomicity is the whole point: there is no
   window in which the privilege has changed but the PC has not.

   Firmware uses this to DROP to a lower EL during boot: write the
   target state into SPSR_EL3, the entry point into ELR_EL3, then
   ERET (chapter 28).
