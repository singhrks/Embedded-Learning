Boolean algebra and logic gates

Everything a processor does is built from a handful of operations on single bits. This chapter is the bridge from "a transistor is a switch" to "a machine can add" — and it is also where the bit-manipulation idioms you will write every day come from.

The problem

You have bits. You need to compute with them. What is the smallest set of operations that lets you build any function of bits at all — arithmetic, comparison, memory addressing, instruction decoding?

The answer, from George Boole in 1847 and Claude Shannon in 1937, is remarkably small: AND, OR and NOT suffice. In fact a single gate type suffices, which is why chips are physically built from just one or two.

NAND is universal

Every one of the other gates can be built from NAND alone:

  NOT a       = a NAND a
  a AND b     = NOT(a NAND b)        = (a NAND b) NAND (a NAND b)
  a OR  b     = (NOT a) NAND (NOT b) = (a NAND a) NAND (b NAND b)

This matters physically: in CMOS, NAND and NOR are the natural gates — they need four transistors — while AND and OR are built as NAND followed by an inverter and therefore cost more. Synthesis tools rewrite your logic into NANDs and NORs for exactly this reason.

Why XOR earns its own gate

XOR is "these bits differ". That single property makes it the workhorse of arithmetic, error detection and cryptography:

a ^ 0 == a          /* identity: XOR with zero changes nothing            */
a ^ a == 0          /* self-inverse: the basis of parity and of one-time pads */
a ^ b ^ b == a      /* apply twice and you are back — reversible encryption  */

/* toggle exactly the bits set in a mask, leaving others alone */
reg ^= (1u << 3);   /* flip bit 3 */

/* the sum bit of a binary adder IS xor — see chapter 05 */
/* parity of a word: */
int parity(uint32_t v) { return __builtin_parity(v); }

The algebra

These identities are not academic — they are the rewrites the compiler and the synthesis tool perform, and knowing them lets you simplify register manipulation by hand.

De Morgan's laws

   ~(a & b)  ==  (~a) | (~b)
   ~(a | b)  ==  (~a) & (~b)

"Not both"    is    "either not"
"Neither"     is    "not either"

These are how a NAND-only fabric implements OR, and how a compiler rewrites your conditionals. They also catch a very common logic bug:

/* "if the flag is not READY and not ERROR" */
if (!(f & READY) && !(f & ERROR))     /* correct                          */
if (!(f & (READY | ERROR)))            /* also correct — De Morgan          */
if (!(f & READY & ERROR))              /* WRONG: true unless BOTH are set   */

In practice: the five bit idioms

Every driver you write uses these. They follow directly from the identity and null laws above.

GoalIdiomWhy it works

the field macros every embedded codebase reinvents
#define BIT(n)              (1u << (n))
#define GENMASK(h, l)       (((1u << ((h) - (l) + 1)) - 1) << (l))
#define FIELD_GET(mask, v)  (((v) & (mask)) / ((mask) & -(mask)))
#define FIELD_PREP(mask, v) (((v) * ((mask) & -(mask))) & (mask))

/* mask & -mask isolates the lowest set bit, which equals 1 << shift —
   so dividing by it is the same as shifting down, with no separate
   shift constant to keep in sync. This is the Linux kernel's trick. */

#define CTRL_MODE   GENMASK(5, 3)    /* bits 5:3 → 0x38 */
#define CTRL_ENABLE BIT(0)

uint32_t r = readl(base + CTRL);
uint32_t mode = FIELD_GET(CTRL_MODE, r);            /* read the field   */
r &= ~CTRL_MODE;                                     /* clear it         */
r |= FIELD_PREP(CTRL_MODE, 3) | CTRL_ENABLE;         /* set mode=3, on   */
writel(r, base + CTRL);
Read-modify-write is not always safe

reg |= BIT(3) is three operations: load, OR, store. If the hardware also modifies that register — a status bit setting itself, or another core writing it — you will read a stale value and write it back, silently undoing the hardware's change. Write-1-to-clear registers must be written directly (reg = BIT(3)), never read-modify-written, or you clear every other pending bit as a side effect. This theme returns in chapter 15.

Bitwise versus logical

C gives you two families of operators that look almost identical and behave completely differently. Confusing them is one of the most common bugs in beginner systems code, and the distinction is worth fixing firmly before going further.

/* BITWISE: operates on every bit position independently */
uint8_t a = 0x0C, b = 0x0A;
a & b   ==  0x08          /* 00001100 & 00001010 = 00001000 */
a | b   ==  0x0E
a ^ b   ==  0x06
~a      ==  0xF3

/* LOGICAL: treats each operand as a single true/false, and SHORT-CIRCUITS */
a && b  ==  1              /* both non-zero → true */
a || b  ==  1
!a      ==  0

/* the difference that bites */
if (flags & FLAG_A)        /* correct: tests the bit               */
if (flags && FLAG_A)       /* WRONG: true whenever flags is non-zero */

/* short-circuiting is a feature, not a detail */
if (p != NULL && p->field)  /* safe: p->field only evaluated if p is valid */
if (p != NULL &  p->field)  /* CRASH: bitwise & evaluates both operands    */

Shifts

Shifting moves every bit left or right by a given number of places. It is the cheapest operation a processor offers and the basis of most bit manipulation — with one asymmetry between left and right that catches people out.

Left shift:  a << n     multiply by 2ⁿ, zeros in from the right
   0000 1011 << 2  =  0010 1100        (11 → 44)

Logical right shift:  zeros in from the left — for UNSIGNED
   1011 0000 >> 2  =  0010 1100        (176 → 44)

Arithmetic right shift: the SIGN BIT replicates — for SIGNED
   1011 0000 >> 2  =  1110 1100        (-80 → -20)

C picks which one by the operand's type. ARM has separate
instructions: LSR (logical) and ASR (arithmetic).
Shift undefined behaviour

Three ways a shift is UB in C, all of which the optimiser is allowed to exploit:

  • Shifting by an amount ≥ the operand's width. x << 32 on a 32-bit int is not zero — on ARM the shift amount is masked to 5 bits, so it is a shift by 0.
  • Shifting a negative value left.
  • Shifting a value into or past the sign bit of a signed type: 1 << 31 is UB because 1 is int. Write 1u << 31, and 1ull << 40 for anything above 31.
