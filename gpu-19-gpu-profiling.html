Profiling and debugging a GPU

You cannot step through a shader with a breakpoint, and the thing you want to time runs asynchronously on another processor. GPU debugging is therefore a different discipline: capture a frame, inspect state, and measure with the right counter — in that order.

Find the bottleneck before optimising

   FOUR THINGS CAN LIMIT A FRAME. Optimising the wrong one
   changes nothing, and this is the most common wasted week in
   graphics work.

   1. CPU-BOUND
        GPU idle, waiting for commands.
        SIGN: GPU busy % well below 100. Frame time tracks CPU
              time.
        FIX: fewer draw calls, instancing, multi-threaded
             recording, fewer PSO switches.

   2. GEOMETRY / VERTEX BOUND
        SIGN: frame time scales with triangle count; the
              vertex shader dominates.
        FIX: LODs, better culling, fewer vertices. On mobile
             this hits far sooner (chapter 10).

   3. PIXEL / FILL BOUND
        SIGN: frame time scales with RESOLUTION. Halve the
              render resolution and it nearly halves.
        FIX: reduce overdraw, cheaper pixel shaders, smaller
             render targets, better early-Z.

   4. BANDWIDTH BOUND
        SIGN: frame time does NOT change when you simplify the
              shader, but DOES when you shrink texture formats
              or render-target sizes.
        FIX: compression, fewer/smaller targets, tighter
             formats, better locality.

   THE TWO-MINUTE TEST THAT IDENTIFIES ALL FOUR

     halve the resolution   -> much faster? PIXEL or BANDWIDTH
     replace the pixel
       shader with
       return float4(1,0,0,1)  -> much faster? PIXEL
                               -> no change?   BANDWIDTH or
                                               GEOMETRY
     draw half the objects  -> much faster? CPU or GEOMETRY
     do the same draws but
       with an empty
       command list         -> still slow? CPU-BOUND

   Do this before opening a profiler. It takes minutes and it
   stops you optimising the wrong thing.

RenderDoc for "why is it wrong", PIX for "why is it slow"

RenderDoc lets you click a draw, see every bound resource, step through a pixel shader for a chosen pixel, and view the history of every write to that pixel. That is the fastest way to answer a correctness question. PIX and the vendor tools have the hardware counters that answer performance questions. Using the wrong one wastes an afternoon.

Timing it yourself

/* GPU timestamps: the GPU writes a counter into a buffer at
   points you choose. You read them back a few frames later -
   never immediately, or you stall (chapter 16). */

D3D12_QUERY_HEAP_DESC qd = {};
qd.Type  = D3D12_QUERY_HEAP_TYPE_TIMESTAMP;
qd.Count = 64;                    /* 32 pairs */
device->CreateQueryHeap(&qd, IID_PPV_ARGS(&queryHeap));

/* Results land in a READBACK buffer. */
CreateBuffer(D3D12_HEAP_TYPE_READBACK, 64 * sizeof(UINT64),
             &readback);

/* The frequency is per-QUEUE and can change with clocks - ask
   each frame, do not cache it once. */
UINT64 freq = 0;
queue->GetTimestampFrequency(&freq);

/* --- recording --- */
cmd->EndQuery(queryHeap.Get(), D3D12_QUERY_TYPE_TIMESTAMP, 0);
    /* EndQuery, even for the "begin" - a timestamp is a point,
       not a range. Confusing, and it catches everyone once. */
    DrawShadowPass(cmd);
cmd->EndQuery(queryHeap.Get(), D3D12_QUERY_TYPE_TIMESTAMP, 1);

cmd->ResolveQueryData(queryHeap.Get(),
                      D3D12_QUERY_TYPE_TIMESTAMP,
                      0, 2, readback.Get(), 0);

/* --- reading, N frames later --- */
UINT64 *ts = nullptr;
D3D12_RANGE r = { 0, 2 * sizeof(UINT64) };
readback->Map(0, &r, (void **)&ts);
double ms = double(ts[1] - ts[0]) / double(freq) * 1000.0;
readback->Unmap(0, nullptr);

/* CAVEATS THAT MAKE NAIVE TIMINGS LIE

   1. The GPU pipelines aggressively. Two adjacent "passes"
      may overlap, so their measured times sum to more than
      the frame. Timestamps measure WHEN, not HOW LONG.

   2. Clocks vary. A GPU idling at 300 MHz and boosting to
      2.5 GHz gives you an 8x spread on the same work. Lock
      the clocks when benchmarking:
        nvidia-smi -lgc 1500,1500
        or use the tool's "stable power state" option.

   3. The first frame after a PSO change includes the
      compile. Discard the first several frames, always.

   4. Vsync makes everything look like 16.67 ms. Turn it off
      to measure.                                            */

Debugging a shader

/* You cannot printf from a shader. Four techniques, roughly
   in order of how often they are the right one. */

/* 1. OUTPUT THE VALUE AS COLOUR. Crude, immediate, and it
      answers most questions. */
        return float4(frac(worldPos.xyz * 0.1), 1);   /* is my
                                                         position
                                                         sane? */
        return float4(normal * 0.5 + 0.5, 1);         /* normals */
        return float4(uv, 0, 1);                      /* UVs     */
        return float4(depth.xxx / 100.0, 1);          /* depth   */
/* Values outside [0,1] clip to white or black, so scale
   deliberately - "everything is white" usually means your
   value is 47, not 0.47. */

/* 2. RENDERDOC PIXEL DEBUGGING. Capture, click the pixel,
      "Debug this pixel", and step through the shader with all
      intermediate values shown. This is the closest thing to
      a real debugger and it is remarkably good. */

/* 3. WRITE TO A UAV and read it back. The GPU's printf. */
        RWStructuredBuffer<float4> Debug : register(u7);
        if (all(id.xy == uint2(512, 384)))    /* one pixel only */
                Debug[0] = float4(computedValue, 0, 0, 1);
/* Guard it to ONE invocation, or thousands of threads race
   for slot 0 and you learn nothing. */

/* 4. WARP/WAVE INSPECTION in Nsight or PIX: pause a dispatch
      and inspect live registers per lane. Heavy, but the only
      way to see divergence directly. */

/* AND THE STRUCTURAL ONE: bisect the shader. Replace the
   second half with a constant, see if the artefact persists,
   and halve again. Four iterations localises almost any
   shader bug, and it needs no tools at all.               */
Timing captures need permission

PIX and the vendor profilers read hardware performance counters, which are disabled by default because they can leak information between processes. On Windows you need Developer Mode plus, for NVIDIA, the "allow access to GPU performance counters" setting in the control panel. The symptom is a capture that opens with every timing showing zero, which looks like a tool bug and is a permissions problem.

Make captures readable

/* An unmarked capture is 4,000 anonymous draws. Ten minutes
   of markers turns it into a readable frame. */

#include <pix3.h>

PIXBeginEvent(cmd, PIX_COLOR(255,0,0), "Shadow Pass");
    for (auto &light : lights) {
        PIXBeginEvent(cmd, PIX_COLOR(255,128,0),
                      "Light %d", light.id);
        DrawShadowMap(cmd, light);
        PIXEndEvent(cmd);
    }
PIXEndEvent(cmd);

/* An RAII wrapper so an early return cannot unbalance them: */
struct GpuScope {
    ID3D12GraphicsCommandList *c;
    GpuScope(ID3D12GraphicsCommandList *cl, const char *n,
             UINT col = PIX_COLOR_DEFAULT) : c(cl)
    { PIXBeginEvent(c, col, n); }
    ~GpuScope() { PIXEndEvent(c); }
};
#define GPU_SCOPE(cmd, name) GpuScope _s##__LINE__(cmd, name)

/* Plus SetName on every resource and PSO (chapter 12).
   Together these two habits are the difference between a
   capture you can read and one you cannot. */

/* Vulkan: vkCmdBeginDebugUtilsLabelEXT
   Metal:  pushDebugGroup / popDebugGroup
   All three tools understand all three.                    */

Reading the counters that matter

# NVIDIA, a compute kernel:
$ ncu --set full -o report ./app

  Speed Of Light
    Compute (SM) Throughput          18.2%
    Memory Throughput                91.4%     <-- the limiter
  Occupancy
    Achieved Occupancy               24.1%
    Theoretical Occupancy            50.0%     <-- and a gap
  Memory Workload Analysis
    L1 Hit Rate                      12.3%
    Global Load Efficiency           23.0%     <-- uncoalesced

# Read it top-down: memory-bound, poor coalescing, and only
# half the theoretical occupancy achieved. Fix the access
# pattern (chapter 4) before touching anything else.

# The gap between achieved and theoretical occupancy is
# usually load imbalance or the tail effect (chapter 5).

# AMD:
$ rgp ./app          # then open in Radeon GPU Profiler
# The wavefront timeline shows async compute overlap directly.

# Mobile:
$ Streamline / Adreno GPA - look for tile load/store cost
# above all else (chapter 10).
