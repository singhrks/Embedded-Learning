What QEMU is and its four modes

QEMU is two separable things that ship in one binary: a CPU emulator that can execute any supported architecture on any other, and a machine model — devices, buses, firmware, a device tree — that turns a CPU into a computer. Which of those you are using at a given moment decides everything about your speed and your debugging options.

The two halves

   +---------------------------------------------------------+
   |  MACHINE MODEL                                          |
   |    - devices: UART, GIC, RTC, virtio, PCIe host bridge  |
   |    - memory map: where each device lives                |
   |    - a generated device tree or ACPI tables             |
   |    - firmware loading, kernel loading                   |
   |    - the QMP/HMP monitor, migration, snapshots          |
   +---------------------------------------------------------+
                              |
                              | needs something to execute
                              | guest instructions
                              v
   +---------------------------------------------------------+
   |  ACCELERATOR - pick exactly one                         |
   |                                                         |
   |   tcg    software emulation. Any guest arch on any host |
   |          arch. ~10-100x slower than native.             |
   |                                                         |
   |   kvm    Linux hardware virtualisation. Guest arch MUST |
   |          equal host arch. Near-native.                  |
   |                                                         |
   |   hvf    macOS Hypervisor.framework. Same idea.         |
   |   whpx   Windows Hypervisor Platform. Same idea.        |
   |   nvmm   NetBSD.  xen  - Xen as the accelerator.        |
   +---------------------------------------------------------+

   The machine model does not care which accelerator is under
   it. That is why the same command line runs an emulated
   aarch64 board on your x86 laptop and a near-native one on an
   arm64 server, changing only -accel.

The four ways to run it

# System emulation: a whole aarch64 machine, on any host
$ qemu-system-aarch64 -M virt -cpu cortex-a57 -m 1G \
    -kernel Image -append "console=ttyAMA0" -nographic

# User-mode: run ONE aarch64 binary on an x86 host
$ qemu-aarch64 -L /usr/aarch64-linux-gnu ./my-arm-binary
# Or transparently, via binfmt_misc:
$ sudo apt install qemu-user-static binfmt-support
$ ./my-arm-binary          # the kernel invokes qemu-aarch64 for you
# This is how "docker run --platform linux/arm64" works on an
# x86 machine, and it is invaluable for running a cross-compiled
# test suite in CI.

# Tools:
$ qemu-img create -f qcow2 disk.qcow2 8G
$ qemu-img convert -O raw disk.qcow2 disk.raw
$ sudo qemu-nbd --connect=/dev/nbd0 disk.qcow2   # mount it
Why this track exists

Every project on this site — a Linux driver, a Windows driver, an OP-TEE trusted application, a bare-metal EL2 payload — can be built and debugged on QEMU without buying hardware. More than that: QEMU gives you things hardware cannot, including a stopped CPU with a GDB stub attached before the first instruction, and a complete trace of every memory access. Learn it properly once and every other track gets cheaper.

What to expect from each accelerator

   Same aarch64 guest, same workload, three ways:

   TCG on x86 host          ~10-50x slower than native arm64.
                            Kernel boot: 20-60 seconds.
                            Perfectly usable for driver work.
                            Timing is meaningless.

   TCG on arm64 host        Same. TCG does not shortcut when
                            the architectures match - use KVM.

   KVM on arm64 host        ~1.0-1.05x native for CPU work.
                            Kernel boot: under a second.
                            Timing is roughly meaningful.

   The corollary that catches people out:

     A race condition that reproduces on hardware may NEVER
     reproduce under TCG, because TCG executes one guest
     instruction stream at a time per vCPU and its memory
     ordering is far stronger than real ARM's.

     And a race that reproduces under TCG is real, because TCG
     is a valid (if unusual) execution.

   So: use TCG to find logic bugs and KVM to find timing bugs,
   and never conclude "the lock is fine" from a TCG run.

MTTCG and the ordering trap

/* Multi-Threaded TCG runs each guest vCPU in its own host
   thread. It is the default where the guest and host memory
   models are compatible.                                    */

$ qemu-system-aarch64 -M virt -smp 4 -accel tcg,thread=multi ...
$ qemu-system-aarch64 -M virt -smp 4 -accel tcg,thread=single ...

/* When emulating a WEAKLY ordered guest (arm64) on a STRONGLY
   ordered host (x86), MTTCG is safe: the host provides more
   ordering than the guest requires, so a guest that forgot a
   barrier still works.

   THAT IS THE PROBLEM. Your code appears correct.

   Emulating a strongly ordered guest on a weakly ordered host
   is the dangerous direction, and QEMU inserts explicit
   barriers to be safe.                                     */

/* Practical rules:

   1. Missing barriers in guest code are INVISIBLE under TCG on
      x86. Test on real arm64 hardware, or under KVM on arm64,
      before believing your lock-free code.

   2. -icount gives you deterministic, reproducible timing:
        -icount shift=5,align=off,sleep=off
      Each guest instruction takes 2^5 virtual ns. The run is
      REPRODUCIBLE - the same input gives the same interleaving
      every time. Invaluable for debugging a heisenbug, and it
      also makes record/replay possible:
        -icount shift=auto,rr=record,rrfile=replay.bin
        -icount shift=auto,rr=replay,rrfile=replay.bin

   3. -singlestep (now -accel tcg,one-insn-per-tb=on) forces
      one instruction per translation block. Very slow, and it
      makes tracing and breakpoints exact.                   */

Checking your setup

$ qemu-system-aarch64 --version
QEMU emulator version 8.2.2

# Which accelerators were compiled in and are usable here?
$ qemu-system-aarch64 -accel help
Accelerators supported in QEMU binary:
tcg
kvm

# Is KVM actually available?
$ ls -l /dev/kvm
crw-rw---- 1 root kvm 10, 232 /dev/kvm
$ groups | grep -q kvm && echo "you can use it" || \
    echo "run: sudo usermod -aG kvm $USER, then log out and in"

# Which machines does this binary know?
$ qemu-system-aarch64 -M help | head -20
virt                 QEMU 8.2 ARM Virtual Machine
raspi3b              Raspberry Pi 3B
sbsa-ref             QEMU SBSA Reference Platform
vexpress-a15         ARM Versatile Express for Cortex-A15
xlnx-zcu102          Xilinx ZynqMP ZCU102

# Which CPUs?
$ qemu-system-aarch64 -cpu help | head
cortex-a53  cortex-a57  cortex-a72  cortex-a76
neoverse-n1 neoverse-v1
max                  # every feature this QEMU implements
host                 # KVM only: pass the host CPU through

# The two you will use:
#   -cpu max   under TCG - gives you SVE, pointer auth, MTE,
#              every architectural feature, so you can develop
#              against hardware you do not own
#   -cpu host  under KVM - no translation, real features
-cpu max is a superpower

It implements architectural features that shipping silicon may not have: SVE2, MTE, pointer authentication, FEAT_NV2 for nested virtualisation, S-EL2. You can write and debug code for a CPU that does not exist yet. The catch is that max tracks the QEMU version, so pin your QEMU version in CI or your feature set moves under you.
