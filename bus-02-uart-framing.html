UART: framing, baud rate and error budget

The oldest interface still in daily use, and the one where an arithmetic error of two percent turns working communication into garbage. This chapter covers the frame, the sampling, and the calculation that tells you in advance whether a given clock can reach a given baud rate.

The frame

   Idle line is HIGH. One character, 8N1, value 0x41 ('A'):

        idle    start  b0 b1 b2 b3 b4 b5 b6 b7  stop  idle
   ----------+      +--+--+--+--+--+--+--+     +---------
             |      |  |  |  |  |  |  |  |     |
             +------+  +--+--+--+--+--+--+-----+
              START   1  0  0  0  0  0  1  0   STOP
                      <-- LSB FIRST -->

   0x41 = 0100 0001 binary, sent LSB first: 1,0,0,0,0,0,1,0

   THE START BIT IS THE WHOLE MECHANISM. It is the only
   guaranteed edge, and everything the receiver does is
   timed from it. An idle line and a start bit are
   distinguishable because idle is high and start is low -
   that is why the idle state is defined as high.

   FRAME NOTATION: 8N1 = 8 data bits, No parity, 1 stop bit.
   Others exist (7E1, 8N2, 9-bit for addressing) but 8N1 is
   the overwhelming default.

   OVERHEAD: 10 bits carry 8 bits of data. So
     bytes/second = baud / 10
   115200 baud = 11520 bytes/s. This division by ten is the
   most useful UART arithmetic you will do.

How the receiver stays aligned

   The receiver has NO clock from the transmitter. It
   oversamples - typically 16x the bit rate.

   1. Wait for the falling edge (start bit).
   2. Count 8 sample-clocks to reach the MIDDLE of the
      start bit. Verify it is still low; if not, it was
      noise - abandon and resume hunting.
   3. Thereafter sample every 16 clocks, taking three
      samples around the centre (7, 8, 9) and majority-voting
      them. Disagreement sets the NOISE flag.
   4. After the last data bit, check the stop bit is HIGH.
      If not: FRAMING ERROR.

        start bit
   ---+        +----
      |        |
      +--------+
      ^   ^^^  ^
      |   789  |
    edge  vote |
   detected    next bit boundary

   WHY ERROR ACCUMULATES: the receiver re-synchronises only
   on the START bit. Over the following 9 bit times, any
   difference between the two clocks accumulates. By the
   stop bit the sampling point has drifted by 9.5 bit times
   times the total error.

   TOLERANCE: the sample must still land inside the correct
   bit, so the accumulated drift must stay under half a bit:

     9.5 x total_error < 0.5
     total_error < 5.3%

   In practice, with the three-sample vote needing all of
   its window inside the bit, the usable budget is about
   +/-2%, SHARED between the two ends. So roughly 1% each -
   which is why the internal RC oscillator is marginal and
   a crystal is not a luxury (mcu chapter 09).

Computing the divisor, and its error

/* The divisor is an integer, so almost no baud rate is
   exactly achievable. The question is always: how far off?  */

/*   BRR = f_pclk / baud       (rounded to nearest)
     actual_baud = f_pclk / BRR
     error = (actual - wanted) / wanted                     */

static uint16_t brr_for(uint32_t pclk, uint32_t baud)
{
    return (uint16_t)((pclk + baud / 2u) / baud);   /* round */
}

/* WORKED: 16 MHz PCLK, 115200 baud.

     16000000 / 115200 = 138.89
     rounded            = 139
     actual = 16000000 / 139 = 115108 baud
     error  = (115108 - 115200) / 115200 = -0.08%

   Excellent. Now 8 MHz PCLK, 115200 baud:

     8000000 / 115200 = 69.44
     rounded          = 69
     actual = 8000000 / 69 = 115942
     error  = +0.64%

   Still fine alone, but add a 1% RC oscillator at each end
   and you are at 2.6% - outside budget, and it will fail
   intermittently and temperature-dependently.

   Now the classic disaster, 8 MHz and 921600:

     8000000 / 921600 = 8.68
     rounded          = 9
     actual = 8000000 / 9 = 888889
     error  = -3.55%

   Broken before you add any oscillator error at all. The
   divisor is small, so rounding it costs an enormous
   fraction. THIS IS WHY HIGH BAUD RATES NEED HIGH CLOCKS:
   not for throughput, but for divisor RESOLUTION.         */

/* ALWAYS CHECK AT COMPILE TIME. */
#define BAUD        115200u
#define PCLK        16000000u
#define BRR_VAL     ((PCLK + BAUD/2u) / BAUD)
#define ACTUAL      (PCLK / BRR_VAL)
#define ERR_PPT     (((int32_t)ACTUAL - (int32_t)BAUD) * 1000 / (int32_t)BAUD)
_Static_assert(ERR_PPT < 15 && ERR_PPT > -15,
               "UART baud error exceeds 1.5% - pick another "
               "clock or baud rate");

/* Twelve lines that turn an intermittent field failure into
   a build error. Put this in every UART driver you write. */
Why 115200, and why the odd numbers

The classic rates are divisions of 1.8432 MHz, the crystal fitted to the original 8250 UART, chosen precisely because it divides evenly to 110, 300, 1200, 9600, 19200, 38400, 57600 and 115200 with zero error. When you fit a 8 MHz or 16 MHz crystal instead you inherit rounding error at every rate. Parts intended for serial work often offer 7.3728 MHz or 11.0592 MHz crystals for this reason — they are 1.8432 MHz multiples, and they make the error exactly zero.

Fractional dividers and oversampling

/* Modern UARTs improve resolution two ways. */

/* 1. FRACTIONAL BRR. The divisor has a fractional part -
      on STM32, 4 bits of sixteenths.                       */
/*   BRR = mantissa << 4 | fraction
     16 MHz, 115200: 138.89 -> mantissa 138, fraction 14/16
                     = 138.875, actual = 115207 baud
                     error = +0.006%
   An order of magnitude better than integer rounding.     */

/* 2. OVERSAMPLING BY 8 INSTEAD OF 16. Halves the divisor,
      doubling the maximum baud rate for a given clock.     */
USART1->CR1 |= USART_CR1_OVER8;
/*   Costs noise immunity: with 8 samples per bit the vote
     window is narrower and the tolerance drops from about
     3.5% to 2%. Use it only when you need the rate and the
     link is short and clean.                               */

/* 3. AUTOBAUD. Some UARTs measure the rate from a known
      first character - typically 0x55 ('U'), which is
      alternating bits and gives the most edges to measure. */
USART1->CR2 |= USART_CR2_ABREN | USART_CR2_ABRMODE_0;
/*   Useful when the peer's rate is unknown or configurable.
     The peer must send the sync character first, so both
     ends need to agree on the protocol even if not the
     rate.                                                  */

Parity, and what it is worth

/* Parity adds one bit making the count of ones even or odd.
   It detects any ODD number of bit errors and misses every
   even number.                                             */

USART1->CR1 |= USART_CR1_PCE;      /* parity enable         */
USART1->CR1 &= ~USART_CR1_PS;      /* 0 = even, 1 = odd     */

/* THE TRAP: on most STM32 UARTs the parity bit is taken
   from the DATA LENGTH, not added to it. For 8 data bits
   plus parity you must set the word length to NINE:        */
USART1->CR1 |= USART_CR1_M0;       /* 9-bit word            */
/*   Forget this and you send 7 data bits plus parity, and
     every byte above 0x7F is corrupted while ASCII appears
     to work perfectly. A memorable afternoon.              */

/* IS IT WORTH IT? Rarely, on a modern link.
   - It costs 10% of your throughput (11 bits per byte).
   - It catches only single-bit errors, and real-world
     serial corruption is usually a burst that flips
     several bits.
   - Any protocol carrying data worth protecting should have
     a CRC over the whole message, which is strictly better.

   Use parity when a legacy peer demands it. For new
   designs, a CRC-16 over the frame gives far better
   detection for similar overhead on messages of any
   length.                                                  */
