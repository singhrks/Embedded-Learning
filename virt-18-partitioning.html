Static partitioning: Xen, Jailhouse and safety

Everything so far assumed the hypervisor should share resources cleverly. In safety-critical embedded systems that assumption is inverted: sharing is the hazard, and the hypervisor's job is to divide the machine once, at boot, and then get out of the way — ideally while executing no code at all during normal operation.

The inversion

Static partitioning inverts the usual goal: rather than sharing a machine efficiently, it divides one so that the parts cannot interfere. The design consequences follow from that single change.

   CONSOLIDATING hypervisor (KVM, Xen, VMware)

     goal: run N guests on M cores, N > M
     scheduler: yes, and it is the interesting part
     memory: overcommitted, ballooned, swapped
     devices: emulated or shared
     failure mode: a noisy guest degrades its neighbours
     metric: throughput per watt, density, utilisation


   PARTITIONING hypervisor (Jailhouse, Xen dom0-less,
                            Bao, PikeOS, QNX Hypervisor)

     goal: run N guests on N disjoint sets of cores
     scheduler: NONE. A core belongs to one guest, always.
     memory: statically carved, never shared, never reclaimed
     devices: statically assigned, one owner each
     failure mode: a guest can only harm itself
     metric: worst-case latency, certifiability, code size

   The partitioning hypervisor is not a worse consolidator.
   It is a different product, and asking it to time-share is
   asking it to stop being what it is.
Why "no scheduler" is the point

If the hypervisor never preempts a guest, then the guest's worst-case execution time is a property of the guest and the hardware alone. You can analyse it, bound it, and put it in a safety case. Add a scheduler and the worst case becomes a property of every other guest in the system — and that is not analysable in any useful sense. Certification does not reward cleverness; it rewards arguments you can finish.

Jailhouse: the minimal case

The minimal case is instructive because it does so little — and what it declines to do is the interesting part.

   Jailhouse does not boot the machine. Linux does.
   Then Linux hands pieces of itself away.

   Step 1: Linux boots normally on all 4 cores.
           You reserve memory with the kernel command line:
              memmap=0x4000000$0x3f000000

   Step 2: load the hypervisor
              jailhouse enable system-config.cell
           Jailhouse installs itself at EL2 UNDER the running
           Linux, which becomes the "root cell". Linux does not
           notice; it keeps running, now virtualised.

   Step 3: take resources away
              jailhouse cell create rtos.cell
              jailhouse cell load rtos 0 rtos.bin
              jailhouse cell start rtos
           Cores 2 and 3 are removed from Linux (offlined
           first), the reserved memory is unmapped from the
           root cell, and the RTOS starts on them.

   AFTER THIS POINT:

     +----------------------+   +---------------------+
     | root cell: Linux     |   | cell 1: RTOS        |
     | cores 0-1            |   | cores 2-3           |
     | RAM 0-1 GB           |   | RAM 1.0-1.06 GB     |
     | eth0, sd, usb        |   | CAN, one timer      |
     +----------------------+   +---------------------+
     +---------------------------------------------------+
     |  Jailhouse at EL2: ~10k lines, no scheduler,      |
     |  no dynamic memory, no drivers, no interrupts     |
     |  of its own. Configures stage 2, the SMMU and the |
     |  GIC, then ERETs and is essentially never         |
     |  entered again.                                    |
     +---------------------------------------------------+

   The hypervisor's steady-state CPU consumption is ZERO,
   because in steady state it does not run.
/* A Jailhouse cell configuration is a C struct compiled to a
   binary blob. This is the entire interface, and its
   explicitness is deliberate.                              */

struct { ... } config = {
        .cell = {
                .name = "rtos-cell",
                .flags = JAILHOUSE_CELL_PASSIVE_COMMREG,
                .cpu_set_size = sizeof(config.cpus),
                .num_memory_regions = ARRAY_SIZE(config.mem_regions),
                .num_irqchips = ARRAY_SIZE(config.irqchips),
                .vpci_irq_base = 100,
        },

        .cpus = { 0b1100 },          /* cores 2 and 3          */

        .mem_regions = {
                /* RAM: physical == virtual, exclusively ours  */
                {
                        .phys_start = 0x40000000,
                        .virt_start = 0x40000000,
                        .size       = 0x04000000,
                        .flags = JAILHOUSE_MEM_READ  |
                                 JAILHOUSE_MEM_WRITE |
                                 JAILHOUSE_MEM_EXECUTE |
                                 JAILHOUSE_MEM_LOADABLE,
                },
                /* The CAN controller - ONE owner, and Linux
                   must not have a driver bound to it.        */
                {
                        .phys_start = 0xff060000,
                        .virt_start = 0xff060000,
                        .size       = 0x1000,
                        .flags = JAILHOUSE_MEM_READ |
                                 JAILHOUSE_MEM_WRITE |
                                 JAILHOUSE_MEM_IO,
                },
        },

        .irqchips = {
                {
                        .address = 0xf9010000,   /* GICD       */
                        .pin_base = 32,
                        .pin_bitmap = { 1 << (142 - 32) },
                                        /* SPI 142 = the CAN   */
                },
        },
};

/* Notice what is NOT here: no memory size to grow into, no
   share of CPU time, no priority. Everything is a fixed
   assignment, decided before the system runs, auditable by
   reading one file.                                         */

Xen on ARM, and dom0-less

Xen's embedded configurations have moved a long way from the datacentre model, particularly in removing the privileged domain from the boot path.

   Classic Xen                    Xen dom0-less (embedded)

   +-------+ +-------+ +-----+    +-------+ +-------+ +-------+
   | dom0  | | domU  | |domU |    | dom0  | | domU1 | | domU2 |
   | Linux | | Linux | |RTOS |    | Linux | | Linux | | RTOS  |
   | DRIVERS AND CONTROL  |       |       | |       | |       |
   +-------+ +-------+ +-----+    +-------+ +-------+ +-------+
   +-------------------------+    +-------------------------+
   |          Xen            |    |          Xen            |
   +-------------------------+    +-------------------------+

   Classic: every domU's I/O goes through dom0's drivers via
            the split frontend/backend model. dom0 boots first,
            everything waits for it. Boot to a working domU:
            many seconds.

   Dom0-less: Xen starts ALL domains simultaneously from the
            device tree at boot, each with statically assigned
            memory and passed-through devices. A safety domain
            can be running its control loop before Linux has
            finished decompressing.

   Device tree fragment that does it:

     chosen {
         domU1 {
             compatible = "xen,domain";
             memory = <0 0x20000000>;
             cpus = <2>;
             vpl011;
             module@50000000 {
                 compatible = "multiboot,kernel", "multiboot,module";
                 reg = <0x50000000 0x2000000>;
                 bootargs = "console=hvc0 root=/dev/ram0";
             };
         };
     };

   This is the model behind Xilinx/AMD, NXP and Renesas
   automotive stacks, and behind most "Linux plus a safety
   island" designs shipping today.

The part everyone forgets: shared microarchitecture

The isolation these systems promise is defeated by hardware the partitioning does not divide, and this is the part that most often gets discovered during certification rather than design.

   You have partitioned cores, memory and devices. You have
   NOT partitioned:

     the last-level cache      a Linux guest streaming data
                               evicts the RTOS's working set

     the memory controller     bandwidth and queueing delay are
                               shared; a DMA-heavy guest adds
                               latency to every other access

     the interconnect          arbitration, and any shared
                               buffering

     shared TLB / prefetchers  on some designs

   Consequence: two guests that never share a byte of memory
   still interfere in TIME. For a throughput workload this is
   noise. For a 100 us control loop it is the difference
   between meeting and missing a deadline.

   MITIGATIONS, in increasing order of effort:

   1. CACHE COLOURING. Allocate each partition only physical
      pages that map to disjoint cache sets. Because the cache
      index comes from physical address bits, choosing pages
      chooses cache regions. Jailhouse and Bao support it;
      you pay in usable memory and in allocator complexity.

   2. MPAM (ARMv8.4 Memory System Resource Partitioning and
      Monitoring). Hardware support: tag each request with a
      PARTID, and configure cache-capacity and bandwidth limits
      per PARTID. This is the proper answer, and it is
      appearing in server and automotive silicon now.
        MPAM1_EL1 / MPAM2_EL2 hold the PARTID for each level.

   3. MEASURE AND OVER-PROVISION. Run the interference
      benchmark (a deliberately cache-hostile stressor) in the
      Linux partition while measuring the RTOS's worst-case
      latency. Whatever number you get IS your worst case.
      This is what safety cases actually contain.
Interference is a certification problem, not a bug

ISO 26262 and DO-178C both require you to argue freedom from interference. Partitioning the address space gets you spatial freedom. Temporal freedom needs measurement, and often needs MPAM or colouring. A design review that only shows the memory map has answered half the question.

Choosing

The three approaches differ mainly in what they refuse to do, so the choice follows from your requirements rather than from performance.

Trying it

These systems can be run on ordinary hardware or under emulation, which is worth doing because the configuration files make the design philosophy explicit.

# Jailhouse on QEMU's virt machine is the cheapest way to see
# a partitioning hypervisor work.

$ git clone https://github.com/siemens/jailhouse
$ cd jailhouse
$ make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
       KDIR=/path/to/linux
# Configs for qemu-arm64 ship in configs/arm64/

# Boot Linux under QEMU with reserved memory:
$ qemu-system-aarch64 -M virt,gic-version=3 -cpu cortex-a57 \
    -smp 4 -m 1G -nographic \
    -kernel Image -append "console=ttyAMA0 mem=768M" ...

# Inside the guest Linux:
$ insmod jailhouse.ko
$ jailhouse enable qemu-arm64.cell
Initializing Jailhouse hypervisor v0.12 on CPU 0
Code location: 0x0000ffffc0200000
Page pool usage after early setup: mem 39/993, remap 0/131072
...
The Jailhouse is opening.

$ jailhouse cell create qemu-arm64-inmate-demo.cell
$ jailhouse cell load 1 gic-demo.bin
$ jailhouse cell start 1
$ jailhouse cell list
ID      Name                    State             Assigned CPUs
0       qemu-arm64              running           0-2
1       inmate-demo             running           3

# Core 3 is now gone from Linux entirely:
$ nproc
3

# And the demo inmate is printing timer ticks on the second
# UART with a jitter of a few microseconds, regardless of what
# Linux is doing - which is the entire point.

How it shows up

SymptomCause
jailhouse enable fails with "CPU is not in EL2"Firmware dropped to EL1 — the same prerequisite as KVM (chapter 03)
Cell creation fails: memory region overlapsThe reserved region was not actually reserved from Linux, or two cells claim it
Linux crashes when a cell startsA device assigned to the cell is still bound to a Linux driver
Guest partition misses deadlines only when Linux is busyCache and memory-bandwidth interference; partitioning was spatial only
Interrupts for a cell's device arrive in the root cellThe GIC pin_bitmap does not include that SPI, or affinity routes it elsewhere
Cell runs once and cannot be restartedNo reset path for its assigned device; it resumed with stale state
Everything works until you enable the SMMUDevice StreamIDs not listed in the cell config, so its DMA now faults
Worst-case latency good in the lab, bad in the fieldThe lab never ran the interference workload; measure with a deliberate stressor
