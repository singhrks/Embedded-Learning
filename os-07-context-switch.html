Context switching, step by step

The mechanism that creates the illusion of concurrency. It is conceptually simple — save one thread's state, restore another's — and the details of what counts as "state", and what it costs beyond the registers, determine the performance of the entire system.

When a switch happens

Switching between tasks does not happen at arbitrary moments. There is a defined set of events that can trigger it, and knowing them tells you why a task did or did not get the processor.

Only ever from inside the kernel, and only for three reasons —
matching the three ways the kernel gains control (chapter 01):

  1. THE THREAD BLOCKS            voluntary
     read() with no data ready, lock contended, sleep(), wait()
     → mark it not-runnable, pick someone else

  2. A TIMER INTERRUPT FIRES      involuntary, preemption
     the quantum expired, or a higher-priority task woke
     → the scheduler is invoked on the way out of the interrupt

  3. A THREAD BECOMES RUNNABLE    involuntary, preemption
     an interrupt completes I/O and wakes a higher-priority thread
     → preempt immediately, if the policy allows

Linux marks the current task with TIF_NEED_RESCHED rather than
switching immediately. The actual switch happens at the next safe
point — on the way back to user space, or when a preemption-disabled
region ends. That is why PREEMPT_NONE vs PREEMPT changes latency
without changing the mechanism.

The register save is not the expensive part

Saving and restoring 31 registers is perhaps 100 cycles. The real cost is that the new thread arrives to find the caches full of the old thread's data, the branch predictor trained on the old thread's branches, and possibly a cold TLB. Refilling those costs thousands of cycles and does not appear anywhere in the switch routine. This is why the measured cost of a context switch ranges from ~1 µs to ~50 µs depending entirely on working-set size.

Thread switch versus process switch

Switching between two threads of one process is substantially cheaper than switching between processes, and the reason is a single thing that does not need to change.

SAME PROCESS (thread → thread)          DIFFERENT PROCESS
  save/restore registers                  save/restore registers
  swap kernel stack                       swap kernel stack
  swap TLS register                       swap TLS register
  — page tables UNCHANGED —               SWAP TTBR0_EL1
  — TLB stays valid —                     TLB entries now belong to
  — caches stay warm-ish —                  another ASID
                                          caches likely cold

  ~1-2 µs                                 ~2-5 µs, plus a much
                                          larger refill penalty

This is the concrete reason threads are "cheaper" than processes,
and why thread pools beat process pools for fine-grained work.

ASIDs make process switches survivable

/* Without address space identifiers, changing TTBR0 would require
   flushing the entire TLB — and the new process would then take
   hundreds of TLB misses warming it back up.

   With ASIDs (ARM) / PCIDs (x86), each TLB entry is tagged with
   its owning address space. A switch changes the current ASID;
   entries from BOTH processes coexist. No flush.              */

msr     ttbr0_el1, x0        /* x0[63:48] holds the ASID */
isb

/* Kernel mappings are marked GLOBAL (nG=0), so they match under any
   ASID and survive every switch — which is why a syscall does not
   disturb the TLB at all.                                       */

/* ASIDs are a limited resource (8 or 16 bits). When they are
   exhausted the kernel rolls over the generation and DOES flush
   everything. This is rare and shows up as a periodic latency
   blip on systems with very many processes.                    */
KPTI made this worse

Kernel Page Table Isolation, the Meltdown mitigation, gives the kernel a separate page table so that kernel addresses are not mapped while user code runs. Every system call and every interrupt therefore switches address space twice. On affected CPUs this added roughly 5–30% to syscall-heavy workloads. ARM cores were mostly not vulnerable and do not pay this; most x86 cores do, unless mitigated in hardware.

The switch itself

The actual switch is a short piece of architecture-specific assembly that saves one context and restores another. Reading it once removes most of the mystery from the concept.

/* Linux arm64, simplified from arch/arm64/kernel/entry.S.
   Only the CALLEE-SAVED registers need saving here — this runs as
   an ordinary C function call, so the caller already saved the
   volatile ones per the ABI (C chapter 11).                     */

SYM_FUNC_START(cpu_switch_to)
        /* x0 = prev task, x1 = next task */
        mov     x10, #THREAD_CPU_CONTEXT
        add     x8, x0, x10                  /* &prev->thread.cpu_context */
        mov     x9, sp

        stp     x19, x20, [x8], #16          /* save callee-saved */
        stp     x21, x22, [x8], #16
        stp     x23, x24, [x8], #16
        stp     x25, x26, [x8], #16
        stp     x27, x28, [x8], #16
        stp     x29, x9,  [x8], #16          /* FP and SP         */
        str     lr, [x8]                      /* return address    */

        add     x8, x1, x10                  /* &next->thread.cpu_context */
        ldp     x19, x20, [x8], #16          /* restore           */
        ldp     x21, x22, [x8], #16
        ldp     x23, x24, [x8], #16
        ldp     x25, x26, [x8], #16
        ldp     x27, x28, [x8], #16
        ldp     x29, x9,  [x8], #16
        ldr     lr, [x8]
        mov     sp, x9

        msr     sp_el0, x1                   /* `current` for the new task */
        ret                                   /* returns into NEXT's flow */
SYM_FUNC_END(cpu_switch_to)
The trick worth appreciating

cpu_switch_to is called by one thread and returns into a different one. The ret at the end jumps to the link register restored from the next task's saved context — which is wherever that thread last called this function. Every thread's stack is paused mid-call in the same place. A newly created thread has its saved context hand-crafted so that this ret lands on its entry function instead.

Lazy FPU switching

The vector and floating-point registers are large and most tasks do not use them. Saving them only when necessary is a worthwhile optimisation that has historically also been a source of security vulnerabilities.

/* FP/SIMD state is large — 32 x 128-bit V registers, or far more
   with SVE (up to 2048 bits each). Saving it on every switch would
   dominate the cost, and most threads never touch it.        */

/* The optimisation:
     1. on switch, DISABLE FP access for the incoming thread
        (CPACR_EL1.FPEN = 0)
     2. if it never uses FP, nothing was saved or restored — free
     3. if it executes an FP instruction, a trap fires; the kernel
        then saves the previous owner's state, restores this
        thread's, enables FP, and retries the instruction     */

/* Consequences you can observe:
     · the FIRST FP instruction after a switch is expensive
     · in the kernel, FP is FORBIDDEN by default precisely because
       its state is not saved on kernel entry (C chapter 16).
       Kernel code that needs it must bracket it explicitly:  */
kernel_neon_begin();
    /* SIMD-accelerated crypto or checksum here */
kernel_neon_end();

Measuring the cost

A context switch costs far more than the register copying suggests, because the real expense is the caches and TLB the new task arrives to find cold.

Direct cost — the switch routine itself
    save/restore registers            ~100 cycles
    scheduler decision (EEVDF)        ~200-500 cycles
    page table swap (process switch)  ~50 cycles + barriers

Indirect cost — the part nobody counts, and the part that matters
    cold L1/L2 for the new working set   100s-1000s of cycles
    TLB refill                            100s of cycles
    branch predictor retraining           100s of cycles

  Measured end to end:
    thread ↔ thread, tiny working set      ~1 µs
    process ↔ process, tiny working set    ~2 µs
    process ↔ process, 1 MB working set    ~10-50 µs

The variance IS the point: the switch has a fixed cost and a
working-set-dependent cost, and the second one dominates.
# count them
vmstat 1                        # cs column: switches per second
pidstat -w -p PID 1             # voluntary vs involuntary, per task
perf stat -e context-switches,cpu-migrations ./program
cat /proc/PID/status | grep ctxt

# see them
perf sched record ./workload && perf sched timehist
trace-cmd record -e sched:sched_switch -- ./workload

# measure the raw cost on your machine
perf bench sched pipe           # ping-pong through a pipe
perf bench sched messaging

# a rough rule: if `cs` is above ~50,000/s on a few cores, switching
# itself is a measurable fraction of your CPU budget.

Reducing switch cost

If switches are hurting a workload, there are several distinct ways to have fewer of them — and which applies depends on why they are happening in the first place.

TechniqueEffect
Fewer threads — a pool sized to core countRemoves switching that exists only because of oversubscription
Batch I/O — io_uring, readvFewer blocking points, so fewer voluntary switches
Async / coroutinesSwitching in user space costs ~20 ns, not ~1 µs — no kernel involved
CPU pinning (taskset)Prevents migration, preserves cache affinity
Longer quanta for batch workFewer preemptions; hurts latency
Spin briefly before blockingAdaptive mutexes: if the lock will be free within ~1 µs, spinning is cheaper than switching twice
Busy-poll for ultra-low latencyNever sleep at all — burns a core to remove the wake-up path entirely
Huge pagesFewer TLB entries to refill after a switch
 
/* Adaptive mutexes make the spin-versus-block decision automatically:
   spin while the lock HOLDER IS RUNNING on another CPU (it will
   likely release soon), block if the holder is descheduled (it
   will not).                                                    */

/* glibc: */
pthread_mutexattr_settype(&a, PTHREAD_MUTEX_ADAPTIVE_NP);

/* This is why uncontended and briefly-contended mutexes are
   nearly free, and heavily-contended ones are catastrophic —
   the cost cliff is exactly one context switch pair.         */

Context switching in an RTOS

A small real-time kernel switches contexts very differently from a general-purpose one, and comparing the two shows exactly which costs are essential and which are the price of generality.

/* On a Cortex-M with no MMU, a switch is far simpler and far
   faster — typically 50-200 cycles.                          */

void PendSV_Handler(void)      /* the standard RTOS switch hook */
{
        /* hardware already stacked R0-R3, R12, LR, PC, xPSR */
        __asm volatile (
        "   mrs   r0, psp            \n"   /* process stack pointer */
        "   stmdb r0!, {r4-r11}      \n"   /* save the rest         */
        "   ldr   r1, =current_tcb   \n"
        "   ldr   r2, [r1]           \n"
        "   str   r0, [r2]           \n"   /* save SP into the TCB  */
        "   bl    select_next_task   \n"
        "   ldr   r2, [r1]           \n"
        "   ldr   r0, [r2]           \n"   /* new SP                */
        "   ldmia r0!, {r4-r11}      \n"
        "   msr   psp, r0            \n"
        "   bx    lr                 \n"); /* hardware unstacks     */
}

/* Why it is so much cheaper:
     · no page tables, no TLB, no ASID
     · caches are small or absent, so little to lose
     · the hardware stacks half the registers for you
     · no scheduler tree — often a simple priority bitmap

   PendSV is used because it is the LOWEST-priority exception, so
   the switch happens only after all pending interrupts are handled.
   Switching from inside an ISR would otherwise nest badly.     */
