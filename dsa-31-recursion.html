Recursion and divide and conquer

Solve a problem by solving smaller copies of itself. Get comfortable here and backtracking, trees and dynamic programming all become variations rather than new topics.

The pattern

Every recursive function has the same three parts, and when one is wrong the failure is almost always in a predictable place. Naming them makes debugging recursion systematic rather than a matter of staring.

   EVERY RECURSIVE FUNCTION HAS EXACTLY THREE PARTS:

     1. BASE CASE      the smallest input, answered directly
     2. RECURSIVE CASE reduce toward the base case
     3. COMBINE        build the answer from the sub-answers

     function f(n) {
         if (n <= 1) return 1;        // 1. base
         return n * f(n - 1);         // 2 and 3
     }

   THE TWO FAILURES:
     NO BASE CASE           -> infinite recursion, stack
                               overflow
     RECURSION THAT DOES
     NOT SHRINK THE INPUT   -> same thing

   ALWAYS CHECK: does every recursive call move strictly
   closer to the base case?

   ---------------------------------------------------------
   THE LEAP OF FAITH

   Do NOT trace the whole call tree in your head. Instead:

     ASSUME the recursive call already returns the correct
     answer for a smaller input, and ask only "given that,
     how do I build MY answer?"

   For reversing a list: assume `reverse(head.next)` has
   correctly reversed everything after the head. Then you
   only have to attach the head to the end. That is one
   line, and you never think about the depth.

   THIS IS THE SINGLE MOST USEFUL MENTAL HABIT for
   recursion, and it is what makes tree problems (chapter 28)
   feel easy.

   ---------------------------------------------------------
   DIVIDE AND CONQUER — a shape of recursion

     1. DIVIDE the problem into independent parts
     2. CONQUER each part recursively
     3. COMBINE the results

     merge sort      split in half, sort each, merge
     quicksort       partition, sort each side
     binary search   discard half (only ONE side survives)
     maximum subarray left, right, or crossing the middle

   THE RECURRENCE TELLS YOU THE COST (chapter 02):
     T(n) = 2T(n/2) + O(n)   -> O(n log n)   merge sort
     T(n) = T(n/2)  + O(1)   -> O(log n)     binary search
     T(n) = 2T(n-1) + O(1)   -> O(2^n)       subsets

   ---------------------------------------------------------
   RECURSION VERSUS ITERATION

     Recursion costs O(depth) STACK SPACE, always. A
     recursive walk of a skewed tree or a long list is O(n)
     space and can overflow — typically around 10^4 frames in
     JavaScript, more in C++.

     TAIL RECURSION (the recursive call is the last thing
     that happens) can in principle be optimised into a loop.
     C++ compilers usually do this; JavaScript engines
     generally do NOT, despite the specification allowing it.
     Do not rely on it.

     CONVERT TO ITERATION with an explicit stack when depth
     is a risk (chapter 27).

When to reach for it

The problem is self-similar

Trees, nested structures, "the same thing but smaller".

Divide into independent halves

Sorting, searching, closest pair.

Enumerate all possibilities

Subsets, permutations — backtracking (ch. 36).

Overlapping subproblems

Add memoisation and it becomes DP (ch. 37).

Do NOT use it

When depth is O(n) and n is large, or a simple loop is clearer.
