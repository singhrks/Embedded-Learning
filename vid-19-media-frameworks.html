Media frameworks and acceleration APIs

Between your application and the hardware sits a stack of abstractions whose job is to hide the differences between vendors — and whose main failure mode is to hide the fact that it silently stopped using the hardware at all.

GStreamer, and the negotiation problem

# A pipeline is a graph of elements. The pieces negotiate
# CAPS - format, resolution, framerate, and crucially the
# memory type.

$ gst-launch-1.0 filesrc location=in.mp4 ! qtdemux ! h264parse \
    ! avdec_h264 ! videoconvert ! autovideosink
#   ^ software decode, and a videoconvert that will quietly
#     do an NV12 -> RGB pass on the CPU

# The hardware version, with everything staying in GPU memory:
$ gst-launch-1.0 filesrc location=in.mp4 ! qtdemux ! h264parse \
    ! vaapih264dec ! "video/x-raw(memory:VASurface)" \
    ! vaapipostproc ! vaapisink
#              ^^^^^^^^^^^^^^^^^^^ the caps filter that FORCES
#              the frames to stay in VA surfaces. Without it
#              GStreamer may insert a download to system
#              memory and you lose the whole benefit.

# V4L2 on embedded:
$ gst-launch-1.0 v4l2src device=/dev/video0 \
    ! "video/x-raw,format=NV12,width=1920,height=1080" \
    ! v4l2h264enc ! h264parse ! matroskamux ! filesink location=out.mkv

# THE DIAGNOSTIC THAT MATTERS - see what was actually
# negotiated, element by element:
$ GST_DEBUG=GST_CAPS:5 gst-launch-1.0 ... 2>&1 | grep -i 'caps:'

# Or dump the graph and look at it:
$ GST_DEBUG_DUMP_DOT_DIR=/tmp gst-launch-1.0 ...
$ dot -Tpng /tmp/*PLAYING*.dot -o pipeline.png
# Every element and the caps on every link. If you see
# videoconvert or a "system memory" caps where you expected
# a hardware memory type, you found your problem.

# "not-negotiated" is GStreamer's most common error and it
# always means: no common format between two adjacent
# elements. Read the caps on both sides and look for the
# missing overlap - usually a pixel format or a modifier
# (chapter 4).
Hardware memory types are the whole point

Every acceleration API has a notion of "a frame that lives in hardware memory" — memory:VASurface, memory:DMABuf, memory:GLMemory, AVHWFramesContext. Keeping frames in that domain from decoder to display is what zero-copy is (chapter 16). The moment a frame is downloaded to system memory the benefit is gone, and every framework will do that download automatically and silently to make an otherwise-impossible link work.

ffmpeg's hardware model

/* Two contexts, and understanding the split is most of it. */

  AVHWDeviceContext   the device: a VA display, a CUDA
                      context, a DRM fd
  AVHWFramesContext   a POOL of frames living on that device,
                      with a fixed format and size

/* Decoding into hardware frames: */

  AVBufferRef *hw_device = NULL;
  av_hwdevice_ctx_create(&hw_device, AV_HWDEVICE_TYPE_VAAPI,
                         "/dev/dri/renderD128", NULL, 0);

  codec_ctx->hw_device_ctx = av_buffer_ref(hw_device);
  codec_ctx->get_format    = get_hw_format;   /* see below */

/* THE CALLBACK IS MANDATORY. libavcodec asks which pixel
   format you want from a list; if you do not pick the
   hardware one, it silently gives you software frames and
   everything still works, slowly. */

static enum AVPixelFormat get_hw_format(AVCodecContext *ctx,
                                        const enum AVPixelFormat *fmts)
{
        for (const enum AVPixelFormat *p = fmts;
             *p != AV_PIX_FMT_NONE; p++)
                if (*p == AV_PIX_FMT_VAAPI)
                        return *p;
        fprintf(stderr, "no hardware format offered\n");
        return AV_PIX_FMT_NONE;      /* fail LOUDLY rather
                                        than fall back */
}

/* After decode, frame->format is AV_PIX_FMT_VAAPI and
   frame->data[3] is the VASurfaceID. The pixels are NOT in
   frame->data[0] - reading them requires an explicit
   transfer, which is exactly the copy you are trying to
   avoid: */

  av_hwframe_transfer_data(sw_frame, hw_frame, 0);   /* SLOW  */

/* Or export as DMABUF and hand it to DRM/KMS or the GPU
   (chapter 18): */
  av_hwframe_map(drm_frame, hw_frame, AV_HWFRAME_MAP_DIRECT);

/* THE CLI equivalents: */
$ ffmpeg -hwaccel vaapi -hwaccel_device /dev/dri/renderD128 \
    -hwaccel_output_format vaapi \
    -i in.mp4 -c:v h264_vaapi -b:v 5M out.mp4
#          ^^^^^^^^^^^^^^^^^^^^^^^^^ WITHOUT this the frames
#          are downloaded to system memory after decode and
#          uploaded again before encode - two full copies per
#          frame, and it still "works".

Android and the browser

// MediaCodec - Android's only sanctioned codec API.
// The same queue model as V4L2 underneath (chapter 17).

MediaCodec codec = MediaCodec.createDecoderByType("video/avc");
MediaFormat fmt = MediaFormat.createVideoFormat("video/avc", 1920, 1080);
fmt.setByteBuffer("csd-0", spsBuffer);      // SPS
fmt.setByteBuffer("csd-1", ppsBuffer);      // PPS

// THE ZERO-COPY DECISION IS THIS ONE LINE:
codec.configure(fmt, surface, null, 0);
//                   ^^^^^^^
//   a Surface  -> frames go straight to the compositor,
//                 never touch the CPU. Fast path.
//   null       -> frames come back as ByteBuffers you must
//                 read, convert and upload. Slow path.
// Passing null "to inspect the frames" is how a video app
// becomes a battery problem.

codec.start();
for (;;) {
    int in = codec.dequeueInputBuffer(10000);
    if (in >= 0) { /* fill and queueInputBuffer */ }

    MediaCodec.BufferInfo info = new MediaCodec.BufferInfo();
    int out = codec.dequeueOutputBuffer(info, 10000);
    if (out >= 0)
        codec.releaseOutputBuffer(out, true);  // true = render
                                               // it to the
                                               // Surface
}

// Check what the fast path is doing:
//   adb shell dumpsys SurfaceFlinger
//   look at the composition column: DEVICE = a hardware
//   plane, CLIENT = GPU composited (chapter 18)
// WebCodecs - raw codec access in the browser, hardware-backed
// where the platform allows.

const decoder = new VideoDecoder({
  output: (frame) => {
    // A VideoFrame. It may live in GPU memory - draw it
    // straight to a canvas or a WebGL texture and it never
    // touches JS memory.
    ctx.drawImage(frame, 0, 0);
    frame.close();          // MANDATORY. VideoFrames hold
                            // hardware buffers and the pool is
                            // small; forgetting close() stalls
                            // the decoder within a few frames.
  },
  error: (e) => console.error(e),
});

// Ask before you commit - support varies by browser and
// platform, and hardwareAcceleration is a HINT:
const support = await VideoDecoder.isConfigSupported({

  hardwareAcceleration: 'prefer-hardware',
});

Every framework will lie to you by succeeding

Ask for hardware decode into a texture. If the modifier does not match, or the format is unsupported, or the surface is the wrong type, the framework inserts a download, a colour conversion and an upload, and returns success. Frame rate on a desktop may be unaffected. The only reliable check is to measure the video engine's utilisation and the memory bandwidth — intel_gpu_top, nvidia-smi dmon, dumpsys SurfaceFlinger, or /sys/kernel/debug/dri/0/state — not whether the picture appears.
