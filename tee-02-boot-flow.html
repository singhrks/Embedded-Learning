The boot flow: TF-A, BL32 and the handover

OP-TEE does not boot itself. It is loaded, verified and started by ARM Trusted Firmware as one stage of a chain that begins in mask ROM and ends in Linux. Understanding which stage owns what — and which one you are debugging — is the difference between a productive afternoon and a wasted one.

The chain

The secure world must be running and verified before the normal world exists, which dictates the order of the entire boot sequence. Every stage loads and checks the next.

   POWER ON
      |
      v
   +--------------------------------------------------------+
   | BL1   boot ROM, or TF-A's BL1 stage.        EL3        |
   |       In mask ROM on real silicon - IMMUTABLE.         |
   |       Contains the root of trust: a hash of the public  |
   |       key that signs everything after it.               |
   |       Loads and VERIFIES BL2.                           |
   +--------------------------------------------------------+
      |
      v
   +--------------------------------------------------------+
   | BL2   trusted boot firmware.                 EL1 (S)   |
   |       Initialises DRAM. Parses the FIP. Loads and       |
   |       verifies BL31, BL32 and BL33 into their places.   |
   |       Builds the parameter structures each will need.   |
   |       Then hands control to BL31.                       |
   +--------------------------------------------------------+
      |
      v
   +--------------------------------------------------------+
   | BL31  EL3 RUNTIME FIRMWARE - the secure monitor.  EL3   |
   |       This one NEVER EXITS. It stays resident for the   |
   |       life of the system, and every world switch, every |
   |       PSCI call and every SMC goes through it.          |
   |                                                         |
   |       Its boot job: initialise the GIC, install the     |
   |       SMC vector table, then run each "runtime service" |
   |       initialiser - including the OP-TEE dispatcher     |
   |       (opteed), which starts BL32.                      |
   +--------------------------------------------------------+
      |
      +--> BL32 = OP-TEE OS                        S-EL1
      |         initialises: MMU, secure memory pools, the
      |         crypto library, the TA loader, its own
      |         console. Registers its entry vectors with
      |         BL31. Returns "I am ready".
      |
      v
   +--------------------------------------------------------+
   | BL33  NON-SECURE bootloader - U-Boot or UEFI.  EL2/EL1 |
   |       The normal world starts here. From this moment    |
   |       the secure world only runs when called.           |
   +--------------------------------------------------------+
      |
      v
   Linux -> optee driver probes -> /dev/tee0 appears
         -> tee-supplicant starts
         -> your client can open a session
BL31 is the one that stays

BL1 and BL2 run once and are gone. BL33 hands off to an OS. BL31 and BL32 remain resident for ever. Every SMC your client issues, for the rest of the machine's uptime, enters BL31 and is routed by it. When something goes wrong at the world boundary, BL31 is where it goes wrong.

The FIP: how the images travel together

All the images have to be packaged together in a way firmware can locate and verify. The container format is how that works, and knowing it makes build output comprehensible.

# A Firmware Image Package is a simple container: a header, a
# table of contents keyed by UUID, and the images.

$ fiptool info fip.bin
Trusted Boot Firmware BL2: offset=0xB0, size=0x54D8, cmdline="--tb-fw"
EL3 Runtime Firmware BL31: offset=0x5588, size=0xC1C8, cmdline="--soc-fw"
Secure Payload BL32 (Trusted OS): offset=0x11750, size=0x3E000, cmdline="--tos-fw"
Secure Payload BL32 Extra1: offset=0x4F750, size=0x5A000, cmdline="--tos-fw-extra1"
Secure Payload BL32 Extra2: offset=0xA9750, size=0x21000, cmdline="--tos-fw-extra2"
Non-Trusted Firmware BL33: offset=0xCA750, size=0x9B240, cmdline="--nt-fw"

# The three BL32 entries are OP-TEE's three parts:
#   tos-fw         tee-header_v2.bin   - the header
#   tos-fw-extra1  tee-pager_v2.bin    - the pageable part
#   tos-fw-extra2  tee-pageable_v2.bin - the rest
# (see chapter 5 for why OP-TEE is split this way)

# Building one:
$ fiptool create \
    --tb-fw         bl2.bin \
    --soc-fw        bl31.bin \
    --tos-fw        tee-header_v2.bin \
    --tos-fw-extra1 tee-pager_v2.bin \
    --tos-fw-extra2 tee-pageable_v2.bin \
    --nt-fw         u-boot.bin \
    fip.bin

# Unpack one you were given, to see what a vendor shipped:
$ fiptool unpack fip.bin --out ./extracted/

# TF-A's own build does this for you:
$ make -C arm-trusted-firmware PLAT=qemu \
       BL32=$OPTEE/out/arm-plat-vexpress/core/tee-header_v2.bin \
       BL32_EXTRA1=.../tee-pager_v2.bin \
       BL32_EXTRA2=.../tee-pageable_v2.bin \
       BL33=$UBOOT/u-boot.bin \
       SPD=opteed all fip

SPD: how BL31 learns about OP-TEE

Something has to dispatch calls from the normal world into the trusted OS. That component lives in EL3 firmware and knows the specific protocol the trusted OS expects.

/* SPD = Secure Payload Dispatcher. A TF-A runtime service that
   knows how to talk to a particular trusted OS. Build TF-A
   with SPD=opteed and you get the OP-TEE one.               */

  services/spd/opteed/
      opteed_main.c     initialisation and the SMC handler
      opteed_common.c   context save/restore
      teesmc_opteed.h   the private ABI between TF-A and OP-TEE

/* At boot: */

  1. BL31 runs its runtime service initialisers.
  2. opteed_setup() finds BL32's entry point from the
     parameters BL2 left behind.
  3. It builds a secure execution context and ERETs into
     OP-TEE's entry point, at S-EL1.
  4. OP-TEE initialises, then calls back:
         SMC(TEESMC_OPTEED_RETURN_ENTRY_DONE, vectors_addr)
     handing BL31 a table of entry points:
         fast_smc_entry     std_smc_entry
         cpu_on_entry       cpu_off_entry
         cpu_resume_entry   cpu_suspend_entry
         fiq_entry          system_off_entry  system_reset_entry
  5. opteed records them and returns to BL2's caller, which
     proceeds to BL33.

/* At RUNTIME, every OP-TEE SMC from the normal world: */

     normal world executes SMC
        -> EL3 vector table
        -> BL31 decodes the function ID
        -> it is in the Trusted OS range -> opteed
        -> opteed SAVES the non-secure context
        -> restores the secure context
        -> ERETs to std_smc_entry in OP-TEE
        ... OP-TEE does the work ...
        -> OP-TEE executes SMC(TEESMC_OPTEED_RETURN_CALL_DONE)
        -> opteed restores the non-secure context
        -> ERET back to the normal world

/* Two SMCs and two full context switches per invocation. That
   is the floor on TA call latency, and it is why TAs are for
   valuable operations rather than hot loops.                */

Verified boot: what "chain of trust" means concretely

Each handover is a signature check, and where the keys come from determines whether the chain means anything. This is what that looks like in practice.

   Each stage verifies the next BEFORE executing it.

   BL1  holds ROTPK_HASH in ROM or eFuses  (immutable)
     |    reads the Trusted Key certificate from the FIP
     |    checks: SHA256(public key in cert) == ROTPK_HASH
     |    checks: cert signature verifies with that key
     |    -> now the trusted world key is trusted
     v
   BL2  its hash is in a certificate signed by that key
     |    BL2 in turn verifies BL31, BL32 and BL33 the same way
     v
   BL31, BL32, BL33

   Turn it on:  make ... TRUSTED_BOARD_BOOT=1 GENERATE_COT=1 \
                         ARM_ROTPK_LOCATION=devel_rsa \
                         ROT_KEY=plat/arm/board/common/rotpk/arm_rotprivk_rsa.pem

   MEASURED boot is different and complementary:
     each stage HASHES the next and EXTENDS the hash into a
     PCR (a TPM register, or OP-TEE's own measurement store)
     before running it. Nothing is blocked; instead the record
     of what ran can later be attested.

     Verified boot  : refuses to run unexpected software
     Measured boot  : runs it, but records what it was

   Chapter 22's fTPM is where measured boot lands: the PCRs
   that record the boot chain live inside a trusted
   application.
Development keys are development keys

Every OP-TEE and TF-A tree ships a test signing key, and every tutorial uses it — including this one. It is public. A device shipped with the default key can have arbitrary trusted applications loaded onto it by anyone. Key management is covered in chapter 14; the short version is that the private key belongs in an HSM and never in a repository.

Watching the boot

Watching the boot happen, stage by stage, is the quickest way to confirm your mental model matches reality — and the fastest way to find which stage is failing.

$ qemu-system-aarch64 -M virt,secure=on,virtualization=on \
    -cpu max -smp 2 -m 1057 -nographic \
    -bios bl1.bin \
    -semihosting-config enable=on,target=native \
    -serial mon:stdio -serial file:secure.log
