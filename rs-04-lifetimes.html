Lifetimes

Lifetimes are how the compiler proves a reference never outlives what it points to. Most of the time they are inferred and invisible; when you must write them, they are describing a relationship you already understood implicitly.

What a lifetime is

Lifetimes are the most feared part of the language and the most over-feared. They are a name for something that already exists in the code, and the annotation describes a relationship rather than creating one.

   A lifetime is a REGION OF CODE for which a reference is
   valid. It is not a runtime value - it exists only during
   type checking, and generates no code whatsoever.

        {
            let r;                      // ---------+-- 'a
            {                           //          |
                let x = 5;              // -+-- 'b  |
                r = &x;                 //  |       |
            }                           // -+       |
            println!("{r}");            //          |
        }                               // ---------+

   `r` has lifetime 'a; `x` has lifetime 'b. The reference
   `&x` cannot outlive 'b, but it is used within 'a. Since
   'b is SHORTER than 'a, this is rejected:

        error[E0597]: `x` does not live long enough

   THE COMPILER IS ANSWERING ONE QUESTION: for every
   reference, is the thing it points to still alive at every
   point where the reference is used? That is the whole
   feature.

   AND THE SYNTAX, when you must write it:
        &'a T           a shared reference living at least 'a
        &'a mut T       an exclusive one
        'static         lives for the whole program

Elision — why you rarely write them

The reason you rarely write lifetime annotations is that three rules fill them in for you. Knowing the rules tells you exactly when you will have to write one.

/* Three rules let the compiler infer lifetimes in almost
   every function signature.                               */

   1. Each elided lifetime in a PARAMETER gets its own
      distinct lifetime.
   2. If there is EXACTLY ONE input lifetime, it is assigned
      to all elided output lifetimes.
   3. If one of the parameters is `&self` or `&mut self`, ITS
      lifetime is assigned to all elided output lifetimes.

/* SO THESE ARE ALL FINE without annotation: */

    fn first(s: &str) -> &str { &s[..1] }
    // rule 2: one input, so the output borrows from it

    fn len(s: &str) -> usize { s.len() }
    // no output reference - nothing to infer

    impl Buffer {
        fn as_slice(&self) -> &[u8] { &self.data }
        // rule 3: the output borrows from self
    }

/* AND THIS ONE IS NOT, which is the case you will meet: */

    fn longest(a: &str, b: &str) -> &str {      // ERROR
        if a.len() > b.len() { a } else { b }
    }
    // error[E0106]: missing lifetime specifier
    //   this function's return type contains a borrowed
    //   value, but the signature does not say whether it is
    //   borrowed from `a` or `b`

/* Rule 1 gives a and b DIFFERENT lifetimes, and rule 2 does
   not apply because there are two. So you must say: */

    fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
        if a.len() > b.len() { a } else { b }
    }

/* WHAT THAT SIGNATURE MEANS: the returned reference is valid
   for as long as BOTH inputs are - i.e. for the shorter of
   the two. It is not choosing a lifetime; it is stating a
   CONSTRAINT the caller must satisfy.

/* AND IF ONLY ONE INPUT IS ACTUALLY BORROWED FROM, say so -
   it is less restrictive for the caller: */
    fn prefix<'a>(s: &'a str, sep: &str) -> &'a str {
        s.split(sep).next().unwrap_or(s)
    }
    // `sep` can now be a shorter-lived temporary          */
A lifetime annotation does not change anything at run time

It does not extend a value's life, allocate anything, or emit code. It is a claim about a relationship that the compiler then verifies. Writing <'a> never fixes a problem by itself — it either states a relationship that is true, and the code compiles, or one that is false, and the error moves to the call site.

Lifetimes in structs

A struct holding a reference is where lifetimes become unavoidable, and it is also where beginners most often take a wrong turn that the borrow checker then fights for an hour.

/* A struct holding a reference must declare the lifetime,
   because the struct cannot outlive what it borrows.     */

    struct Parser<'a> {
        input: &'a str,
        pos: usize,
    }

    impl<'a> Parser<'a> {
        fn new(input: &'a str) -> Self {
            Parser { input, pos: 0 }
        }

        fn next_token(&mut self) -> Option<&'a str> {
            // returns a slice of the ORIGINAL input, not of
            // self - so it lives as long as 'a, and the
            // caller may hold it after calling next_token
            // again
            ...
        }
    }

    let text = String::from("a b c");
    let mut p = Parser::new(&text);
    let t = p.next_token();
    // drop(text);              // ERROR - p and t borrow it

/* NOTE THE DIFFERENCE between these two: */
    fn next_a(&mut self) -> Option<&'a str>    // borrows the
                                               // INPUT
    fn next_b(&mut self) -> Option<&str>       // elision
                                               // rule 3:
                                               // borrows SELF
/* The second one keeps `self` borrowed for as long as the
   result is held, so you cannot call it twice and keep both
   results. The first can. Choosing correctly is the main
   reason to write lifetimes explicitly on methods.

/* AND THE GENERAL ADVICE FOR EMBEDDED: a struct holding
   references is often better as a struct holding INDICES or
   owning its data. Borrowing structs are excellent for
   parsers and views over a buffer; they are awkward for
   long-lived state.                                      */

'static

'static is routinely misread as "lives forever", which is close enough to be useful and wrong in a way that matters on embedded targets.

/* 'static means "valid for the entire program". Two distinct
   things use it, and confusing them causes real trouble. */

/* --- 1. &'static T - a reference that lives forever --- */
    let s: &'static str = "hello";      // string literals are
                                        // in .rodata
    static TABLE: [u8; 256] = [0; 256];
    let t: &'static [u8] = &TABLE;

/* On embedded this is common and useful: */
    static mut BUFFER: [u8; 1024] = [0; 1024];
    // `static mut` requires unsafe to access - use a
    // StaticCell or a Mutex<RefCell<..>> instead
    // (chapter 19)

/* --- 2. T: 'static - a TYPE BOUND --- */
    fn spawn<F: FnOnce() + Send + 'static>(f: F);

/* This does NOT mean "lives forever". It means "contains no
   references with a lifetime shorter than 'static" - i.e. it
   either owns all its data, or only holds &'static
   references.

   String is 'static. i32 is 'static. Vec<String> is 'static.
   &'a str is NOT 'static unless 'a is.

   THAT IS WHY thread::spawn requires it: the thread may
   outlive the spawning scope, so its closure must not borrow
   anything local. Scoped threads (chapter 16) lift the
   requirement by guaranteeing the join happens first.

/* THE ANTI-PATTERN: adding `+ 'static` to silence an error.
   It usually pushes the problem to the caller, who then has
   to clone or leak. Work out what the real lifetime
   relationship is instead.                               */

Bounds and subtyping

Subtyping among lifetimes is mostly invisible and occasionally decisive. This is the minimum needed to read an error that mentions it.

/* --- LIFETIME BOUNDS --- */
    fn f<'a, 'b: 'a>(x: &'a str, y: &'b str) -> &'a str
/* `'b: 'a` reads "'b OUTLIVES 'a" - 'b is at least as long.
   So a &'b can be used where a &'a is expected.

    struct Wrapper<'a, T: 'a> { r: &'a T }
/* `T: 'a` means T contains no references shorter than 'a.
   Since Rust 2018 this is inferred in most positions and you
   rarely write it.

/* --- SUBTYPING: a longer lifetime coerces to a shorter --- */
    let long = String::from("x");
    {
        let r: &str = &long;    // &'long coerces to a shorter
                                // lifetime here
    }
/* This is why passing a &'static where &'a is wanted always
   works.

/* --- VARIANCE, which you will meet in error messages --- */
    &'a T           COVARIANT in 'a and in T
                    (a longer 'a works where a shorter is
                     wanted)
    &'a mut T       covariant in 'a, INVARIANT in T
    Cell<T>         invariant in T
    fn(T) -> U      CONTRAVARIANT in T, covariant in U

/* WHY &mut T IS INVARIANT IN T: if it were covariant you
   could write a shorter-lived reference through a
   &mut &'static T, creating a dangling &'static. The
   compiler forbids it, and the resulting error mentions
   "lifetime may not live long enough" in a way that only
   makes sense once you know variance exists.

/* YOU DO NOT NEED TO MEMORISE THIS. You need to recognise
   that an error about a &mut of a reference type is probably
   variance, and that the fix is usually to restructure
   rather than to add annotations.                        */

Practical patterns

A handful of shapes cover nearly all lifetime annotations you will write in real code.

/* --- 1. A ZERO-COPY PARSER, the best use of lifetimes --- */
    struct Packet<'a> {
        header: &'a [u8; 8],
        payload: &'a [u8],
    }

    fn parse(buf: &[u8]) -> Option<Packet<'_>> {
        if buf.len() < 8 { return None; }
        let (h, rest) = buf.split_at(8);
        Some(Packet {
            header: h.try_into().ok()?,
            payload: rest,
        })
    }
/* NO ALLOCATION, no copying - the packet is a VIEW into the
   receive buffer, and the compiler guarantees the buffer
   outlives it. That is a genuinely better answer than either
   copying (C++ safe version) or a raw pointer (C version).

   `'_` is the ANONYMOUS lifetime - "infer it, but I
   acknowledge one exists". Prefer it to omitting the
   parameter entirely; `-> Option<Packet>` is deprecated
   style for exactly this reason.

/* --- 2. A BUILDER THAT BORROWS --- */
    struct Config<'a> { name: &'a str, retries: u32 }

    impl<'a> Config<'a> {
        fn name(mut self, n: &'a str) -> Self {
            self.name = n; self
        }
        fn retries(mut self, r: u32) -> Self {
            self.retries = r; self
        }
    }
    let c = Config::default().name("dev").retries(3);
/* Taking `self` by value and returning it makes the chain
   work without any borrowing at all.

/* --- 3. AVOIDING LIFETIMES: own it, or index it --- */
    struct Owned { data: Vec<u8> }              // no
                                                // lifetimes
    struct Indexed { range: Range<usize> }      // no
                                                // lifetimes
/* When a struct with a lifetime becomes awkward - which
   happens when it needs to be stored, sent between threads,
   or held in a collection - one of these two is the answer.

/* --- 4. WHEN A REFERENCE MUST OUTLIVE ITS SCOPE --- */
    let leaked: &'static mut [u8] =
        Box::leak(vec![0u8; 1024].into_boxed_slice());
/* Deliberately leaks a heap allocation to obtain a 'static
   reference. Legitimate for one-time initialisation at
   startup - a DMA buffer, a global table - and a red flag
   anywhere else.

   ON no_std, StaticCell does the same thing without a heap
   (chapter 19).                                          */

Reading the errors

Lifetime errors are verbose and follow a fixed structure. Reading them in a fixed order turns them from intimidating into mechanical.

error[E0597]: `x` does not live long enough
  --> src/main.rs:6:13
   |
 5 |         let x = 5;
   |             - binding `x` declared here
 6 |         r = &x;
   |             ^^ borrowed value does not live long enough
 7 |     }
   |     - `x` dropped here while still borrowed
 8 |     println!("{r}");
   |               --- borrow later used here

/* THE THREE SPANS tell you everything: where it was
   borrowed, where it was dropped, and where the borrow was
   still needed. Read them in that order and the fix is
   usually obvious - either move the value out, extend its
   scope, or stop holding the reference.

/* THE OTHER COMMON ONES:

   E0106  missing lifetime specifier
          -> the compiler cannot tell which input the output
             borrows from. Add <'a> and say.

   E0621  explicit lifetime required
          -> a returned reference needs a longer lifetime
             than the signature promises.

   E0716  temporary value dropped while borrowed
          -> you borrowed from something that dies at the end
             of the statement:
                 let r = &String::from("x");    // ERROR
                 let s = String::from("x");
                 let r = &s;                    // fine

   E0759  argument requires that it is borrowed for 'static
          -> usually thread::spawn or a trait object; own the
             data or use a scoped thread.

/* AND THE PRACTICAL ADVICE: when stuck, try in this order:
     1. does the function really need to return a reference,
        or can it return an owned value?
     2. can the caller keep ownership and pass &T in?
     3. can the struct own its data instead of borrowing?
     4. can indices replace the references?
     5. only then, write the lifetime annotations.
   Four out of five times one of the first four is the right
   answer, and the annotation was a symptom.             */
