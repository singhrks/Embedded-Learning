The AArch64 virt machine

There is no such board. virt is a machine designed to be virtualised: a memory map chosen for convenience, only devices worth emulating, and a device tree generated at runtime to describe whatever you asked for. It is the target for every arm64 exercise on this site, and knowing its map by heart saves an enormous amount of time.

The device tree is generated, and you can read it

# QEMU builds a device tree describing exactly the machine you
# asked for - your CPU count, your memory size, your devices -
# and places it in memory for the kernel.

$ qemu-system-aarch64 -M virt,dumpdtb=virt.dtb \
    -cpu cortex-a57 -smp 4 -m 2G -nographic
# exits immediately, having written virt.dtb

$ dtc -I dtb -O dts virt.dtb -o virt.dts
$ less virt.dts

$ dtc -I fs -O dts /sys/firmware/devicetree/base | less
Why it is generated, not fixed

A real board has a device tree committed to a repository, describing hardware that cannot change. virt has no fixed hardware: the number of CPUs, the amount of RAM, the GIC version, whether there is an ITS, and which virtio devices exist are all decided by your command line. Generating the tree at startup is the only way to keep it truthful, and it means you never edit a DTS to change your VM's memory.

The machine options that matter

OptionValuesEffect
gic-version2, 3, 4, host, maxWhich interrupt controller. host matches the hardware under KVM; max is the newest QEMU supports
itson/offThe GICv3 ITS. Needed for PCIe MSI-X (virt chapter 12)
virtualizationon/offGive the guest EL2, so it can run its own hypervisor
secureon/offGive the machine EL3 and a secure world. Required for TF-A and OP-TEE
mteon/offMemory Tagging Extension
iommusmmuv3An SMMU, for passthrough and DMA isolation experiments
highmemon/offWhether to place devices above 4 GB. Turn off for a 32-bit-limited guest
acpion/offGenerate ACPI tables as well as a device tree — the server boot path
dumpdtb=filenameWrite the generated device tree and exit
memory-backend=object idBack RAM with hugetlbfs or shared memory — needed for vhost-user and virtiofs
 
# The configuration this site's ARM and security tracks use:
$ qemu-system-aarch64 \
    -M virt,secure=on,virtualization=on,gic-version=3 \
    -cpu max -smp 2 -m 1G -nographic

# Everything on, for exploring:
$ qemu-system-aarch64 \
    -M virt,gic-version=max,its=on,virtualization=on,secure=on,\
mte=on,iommu=smmuv3,acpi=on \
    -cpu max -smp 4 -m 4G -nographic

# Native speed on an arm64 host:
$ qemu-system-aarch64 -M virt,gic-version=host -cpu host \
    -accel kvm -smp 4 -m 4G -nographic
secure=on and -cpu max together

Turning on the secure world changes the boot: the CPU now starts at EL3, and QEMU expects firmware there. With -kernel QEMU synthesises a minimal EL3 stub that drops to EL1, which is fine for testing — but the moment you supply real firmware with -bios, the stub disappears and your image must handle EL3 itself. This trips up nearly everyone on their first OP-TEE build; see OP-TEE chapter 4.

    0000000000000000-0000000007ffffff (prio 0, romd): virt.flash0
    0000000008000000-000000000800ffff (prio 0, i/o): gicv3_dist
    0000000008080000-00000000080bffff (prio 0, i/o): gicv3_its

# This is the truth. If your guest faults at an address, find
# it here first: either there is no region (nothing modelled)
# or there is one and your driver is misusing it.

# Regions with "romd" are read-mostly flash; "i/o" are device
# models; "ram" is real backing memory.

# Overlaps are resolved by priority, which is how a boot ROM
# can shadow RAM at address 0 and then be removed.
