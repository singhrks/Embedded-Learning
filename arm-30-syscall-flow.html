A system call, end to end

Everything in this track converging on one path. Follow write(fd, buf, len) from a C call to the return value, naming every register, every check and every layer — and the whole architecture stops being a collection of separate topics.

The complete path

This chapter follows one system call through every mechanism the track has covered so far. If you can narrate this path from memory, you understand how user space and the kernel actually connect.

Step 1: the syscall ABI

The agreement about which register holds the call number and which hold the arguments is a contract between libc and the kernel. It is fixed per architecture, which is why binaries are not portable between them.

/* The syscall ABI differs from the C ABI in two ways that matter: */

   C ABI:       arguments in x0-x7, return in x0
   syscall ABI: arguments in x0-x5 ONLY, syscall number in x8,
                return in x0

/* Why x8 rather than x7? Because it keeps the argument registers
   contiguous and leaves x8 — the indirect result register, which
   a syscall never needs — free for the number.

   Why only six arguments? Because no Linux syscall needs more.
   Those that would (mmap, clone3) pass a POINTER TO A STRUCT
   instead, which is also how they stay extensible (OS ch. 03). */

/* A raw syscall in assembly: */
        mov     x0, #1                  /* fd = stdout */
        adr     x1, msg
        mov     x2, #3
        mov     x8, #64                 /* __NR_write  */
        svc     #0
        /* x0 now holds the result, or a negative errno */

/* From C, without libc: */
static inline long syscall3(long n, long a, long b, long c)
{
        register long x8 asm("x8") = n;
        register long x0 asm("x0") = a;
        register long x1 asm("x1") = b;
        register long x2 asm("x2") = c;
        asm volatile("svc #0"
                     : "+r"(x0)
                     : "r"(x8), "r"(x1), "r"(x2)
                     : "memory", "cc");
        return x0;
}
/* Note "memory": the kernel may modify anything the pointers
   reach, so the compiler must not cache values across it
   (C chapter 18).                                          */

Step 4: dispatch

Once inside, the kernel has to turn a number into a function. The mechanism is deliberately simple, and its simplicity is part of why the boundary is defensible.

/* The syscall table is an array of function pointers — exactly
   the dispatch table pattern from C chapter 12.            */

const syscall_fn_t sys_call_table[__NR_syscalls] = {
        [0 ... __NR_syscalls - 1] = __arm64_sys_ni_syscall,
#include <asm/unistd.h>
};

/* The bounds check is not optional, and on a speculating core it
   must survive speculation (CA chapter 12):                */

        if (scno < __NR_syscalls) {
                scno = array_index_nospec(scno, __NR_syscalls);
                /* → CMP + CSEL + CSDB: a MASK, not a branch, so
                     speculation cannot bypass it            */
                syscall_fn = sys_call_table[scno];
                ret = syscall_fn(regs);
        } else {
                ret = do_ni_syscall(regs, scno);
        }

/* Before dispatch, several hooks may intervene:
     ptrace       a debugger can inspect or change the arguments,
                  or skip the call entirely
     seccomp      a BPF filter can allow, deny, kill or trap
     audit        logging
   Each costs cycles, which is why a heavily-sandboxed process
   has measurably slower syscalls.                          */

Step 6: crossing the boundary

Every byte from user space is hostile

A system call argument is attacker-controlled input arriving at the highest privilege level. The kernel must assume the caller is malicious, not merely buggy — a local user exploiting a validation gap gets kernel code execution.

/* NEVER dereference a __user pointer directly. */

long sys_example(void __user *ubuf, size_t len)
{
        char kbuf[256];

        if (len > sizeof kbuf)
                return -EINVAL;                  /* bound FIRST */
        if (copy_from_user(kbuf, ubuf, len))
                return -EFAULT;                  /* bytes NOT copied */
        ...
}

/* copy_from_user does three things you cannot skip:

   1. RANGE CHECK — is the address really below the user/kernel
      boundary? On arm64 this is a single comparison against
      TASK_SIZE, made speculation-safe.

   2. EXCEPTION FIXUP — an entry in __ex_table maps the faulting
      instruction to a recovery address. If the user page is
      unmapped, the data abort handler finds the fixup and
      returns -EFAULT instead of oopsing. This is what makes
      passing a bad pointer an ERROR rather than a crash.

   3. PAN / LDTR — with PAN enabled (chapter 05), ordinary kernel
      loads from user pages FAULT. The copy routines either lift
      PAN briefly or use the unprivileged LDTR/STTR instructions
      (chapter 08), which behave as EL0 accesses. Either way, a
      pointer aimed at KERNEL memory fails the permission check
      rather than succeeding.                                */

/* The five validation rules (OS chapter 03):
     1. bound every length BEFORE using it
     2. COPY before validating — never validate in place (TOCTOU)
     3. check every index and enum against its range
     4. zero output structures fully — padding leaks stack data
     5. reject unknown flags rather than ignoring them        */

Steps 8–10: returning

Returning is more than reversing the entry: there are things the kernel must check before handing control back, which is where signal delivery and rescheduling actually happen.

/* ret_to_user is not just a restore. Two things must be checked
   at the boundary, because this is the only safe point to do
   them:                                                     */

   TIF_SIGPENDING     a signal is queued → build a signal frame
                      on the USER stack, and return into the
                      handler instead of the original code
   TIF_NEED_RESCHED   a higher-priority task became runnable →
                      call schedule() before returning

/* This is why signals are delivered "on return to userspace" and
   not at arbitrary points — the kernel needs a known-good state
   to rewrite the return context.                          */

/* The errno convention, at step 10: */
        if ((unsigned long)ret >= (unsigned long)-4095) {
                errno = -ret;
                return -1;
        }
        return ret;

/* The kernel returns a NEGATIVE ERRNO directly (-EINVAL = -22),
   never sets a global. libc translates. This is strictly better
   than errno (C chapter 16): the error travels in the return
   value, so it cannot be clobbered or forgotten.

   The -4095 boundary is why no syscall may return a legitimate
   value in the range -1 to -4095 — mmap returning a high
   address is why it is checked this way rather than just
   testing for negative.                                    */

Avoiding the syscall entirely

Some calls are frequent enough and simple enough that trapping for them is wasteful. The kernel maps a small piece of its own code into every process to answer them without crossing the boundary at all.

/* Some "syscalls" need no privilege at all. The vDSO is a small
   shared object the kernel maps into every process, containing
   implementations that run in USER MODE.                   */

clock_gettime(CLOCK_MONOTONIC, &ts);
/*  · reads a kernel-maintained page of timekeeping data
    · reads CNTVCT_EL0 — the counter, readable from EL0
      (chapter 32)
    · does the arithmetic
    · returns. NO exception, no privilege change.
    ~25 ns instead of ~300 ns.                              */

cat /proc/self/maps | grep vdso
LD_SHOW_AUXV=1 /bin/true | grep VDSO

/* Also served by the vDSO: gettimeofday, clock_getres, time,
   getcpu, and on some architectures rt_sigreturn.

/* The general principle: the fastest system call is the one you
   do not make. Hence io_uring (shared rings, often zero
   syscalls in steady state), mmap instead of read, and eBPF
   (run the logic kernel-side). OS chapter 03.             */

Where the time goes

Knowing where the cycles go explains which optimisations are worth making — and why mitigations for speculative-execution vulnerabilities made this path measurably more expensive.

   svc → first kernel instruction        ~15-30 cycles
   save 31 registers + 3 sysregs         ~20-40 cycles
   seccomp / audit / ptrace checks       0 to hundreds
   table lookup + indirect call          ~10 cycles
   ── the actual work ──
   signal / resched checks               ~10 cycles
   restore + eret                        ~30-50 cycles

   Plus, on affected systems:
     KPTI                                two address-space
                                         switches, +100-300 cycles
     Spectre-BHB mitigation              a flush sequence in the
                                         vector, +tens of cycles

   A "null" syscall (getppid) measures roughly:
      no mitigations       ~60-100 ns
      with KPTI + BHB      ~150-400 ns

   Measure your own:
      perf bench syscall basic
      strace -c ./program           ← count them first

HVC and SMC follow the same shape

Once you understand SVC as "a deliberate, synchronous request to the level above me", the other two instructions are the same idea reused at each successive privilege boundary: HVC is how a kernel deliberately asks its hypervisor for something, and SMC is how a kernel or hypervisor deliberately asks the secure monitor for something. All three land in the same exception class, differ only in which vector table receives them and which register the request landed in, and each has an explicit off switch that the level above can flip — a hypervisor without KVM enabled sets HCR_EL2.HCD to reject guests attempting hypercalls, and a system with no secure-world services set SCR_EL3.SMD the same way. Recognising this common shape means learning one mechanism rather than three.

/* The structure is identical: a deliberate synchronous exception
   to a higher level, arguments in registers, a number selecting
   the service, and ERET to return. Once you understand SVC, you
   understand all three.

   The differences are in what the handler does — and for SMC,
   the monitor must also save and restore the ENTIRE state of one
   world before switching (security track).               */

/* A PSCI call, for example — this is how a kernel starts a
   secondary CPU (chapter 33):                             */
        ldr     x0, =0xC4000003         /* PSCI_CPU_ON, SMC64 */
        mov     x1, target_mpidr
        ldr     x2, =secondary_entry
        mov     x3, #0
        smc     #0
        /* x0 = 0 on success, or a negative PSCI error */

Watching it happen

The whole path is traceable on a live system, which turns the preceding description from something you believe into something you can watch.

# count and time every syscall — ALWAYS do this first
strace -c ./program
#   % time     seconds  usecs/call     calls    errors syscall
#   ------ ----------- ----------- --------- --------- --------
#    89.12    0.451203           0   1204811           read
#     → 1.2 MILLION reads. That is the bug, whatever else is true.

strace -f -e trace=openat,read,write ./program
strace -p 1234                   # attach

# lower overhead, system-wide
perf trace ./program
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter {
        @[comm, args->id] = count(); }'

# the entry path itself
echo 1 > /sys/kernel/debug/tracing/events/raw_syscalls/enable
cat /sys/kernel/debug/tracing/trace_pipe

# the table
ausyscall --dump | head -20
cat /usr/include/asm-generic/unistd.h | grep __NR_write

# see the vDSO in action — no syscall for clock_gettime
strace -e trace=clock_gettime ./prog     # produces nothing
strace -c before anything else

When a program is slow with low CPU usage, this one command usually finds it: a million one-byte reads, thousands of failed stat() calls probing for a file, or a poll() loop with a zero timeout. All three are extremely common and all three are obvious in the summary. Reach for a profiler only after this comes back clean.
