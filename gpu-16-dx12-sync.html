DX12: fences, barriers and residency

The hardest part of the explicit APIs, and the one the old drivers were silently doing for you. Fences order the CPU against the GPU; barriers order the GPU against itself. Get either wrong and you get corruption, a hang, or a device removal — usually far from the cause.

Fences: CPU-to-GPU ordering

/* A fence is a monotonically increasing 64-bit counter that
   the GPU writes and either side can read or wait on. That
   is the entire abstraction. */

ComPtr<ID3D12Fence> fence;
device->CreateFence(0, D3D12_FENCE_FLAG_NONE, IID_PPV_ARGS(&fence));
HANDLE event = CreateEvent(nullptr, FALSE, FALSE, nullptr);

/* GPU side: "when you reach this point in the queue, set the
   counter to n". Signal is QUEUED - it happens when the GPU
   gets there, not when you call it. */
queue->Signal(fence.Get(), n);

/* CPU side: wait until the counter reaches n. */
if (fence->GetCompletedValue() < n) {
    fence->SetEventOnCompletion(n, event);
    WaitForSingleObject(event, INFINITE);
}

/* GPU side waiting on another queue - no CPU involvement: */
otherQueue->Wait(fence.Get(), n);

/* THE CANONICAL USE - frames in flight (chapter 13): */
UINT64 frameFence[kFrames] = {};
UINT64 next = 1;

/* end of frame: */
    frameFence[i] = next;
    queue->Signal(fence.Get(), next++);

/* start of the frame that reuses slot i, kFrames later: */
    WaitForFence(frameFence[i]);
    alloc[i]->Reset();            /* now provably safe         */

/* THE THREE THINGS FENCES PROTECT

   1. command allocators   - do not reset while executing
   2. upload buffers       - do not overwrite while being read
   3. resource destruction - do not free while referenced

   Every "it corrupts a few frames later" bug is one of these
   three. If you take one habit from this chapter, take this:
   NOTHING IS REUSED OR RELEASED UNTIL A FENCE PROVES THE GPU
   IS DONE WITH IT.                                          */
Do not wait on the fence you just signalled

queue->Signal(f, n); WaitForFence(n); is a full CPU/GPU stall — you have serialised the two processors and thrown away all the pipelining the API exists to provide. It is correct, and it is what "flush" means. Use it at shutdown, on resize, and nowhere in a frame loop. If your frame time equals CPU time plus GPU time rather than the maximum of the two, this is why.

Barriers: GPU-to-GPU ordering

   A resource is in exactly ONE STATE at a time, and the state
   tells the hardware how to lay it out and cache it.

     RENDER_TARGET            being drawn into
     PIXEL_SHADER_RESOURCE    being sampled
     DEPTH_WRITE / DEPTH_READ
     UNORDERED_ACCESS         compute reads and writes
     COPY_SOURCE / COPY_DEST
     PRESENT                  handed to the display
     COMMON                   the neutral state; required at
                              queue boundaries

   You cannot sample a texture you are still rendering into.
   The TRANSITION between states is a barrier, and it does
   three things:

     1. WAITS for prior work touching the resource to finish
     2. FLUSHES/INVALIDATES the relevant caches
     3. DECOMPRESSES or re-lays-out the memory if the two
        states use different layouts

   That third one is why barriers are not free: moving a
   render target to a shader resource may involve a full
   depth or colour decompression pass over the surface.
/* The three barrier types. */

/* 1. TRANSITION - the common one. */
D3D12_RESOURCE_BARRIER b = {};
b.Type  = D3D12_RESOURCE_BARRIER_TYPE_TRANSITION;
b.Flags = D3D12_RESOURCE_BARRIER_FLAG_NONE;
b.Transition.pResource   = tex.Get();
b.Transition.StateBefore = D3D12_RESOURCE_STATE_RENDER_TARGET;
b.Transition.StateAfter  = D3D12_RESOURCE_STATE_PIXEL_SHADER_RESOURCE;
b.Transition.Subresource = D3D12_RESOURCE_BARRIER_ALL_SUBRESOURCES;
cmd->ResourceBarrier(1, &b);

/* 2. UAV - no state change, but "finish all writes before any
      reads". Needed between two dispatches where the second
      reads what the first wrote. */
D3D12_RESOURCE_BARRIER u = {};
u.Type          = D3D12_RESOURCE_BARRIER_TYPE_UAV;
u.UAV.pResource = buffer.Get();
cmd->ResourceBarrier(1, &u);

/* 3. ALIASING - when two placed resources share heap memory
      and you switch which one is live. */

/* BATCH THEM. One call with five barriers is much cheaper
   than five calls, because the driver can merge the waits. */
D3D12_RESOURCE_BARRIER batch[3] = { b0, b1, b2 };
cmd->ResourceBarrier(3, batch);

/* SPLIT BARRIERS - start the transition early, finish it
   later, so the GPU can overlap the decompression with other
   work: */
b.Flags = D3D12_RESOURCE_BARRIER_FLAG_BEGIN_ONLY;
cmd->ResourceBarrier(1, &b);
    /* ... unrelated work happens here ... */
b.Flags = D3D12_RESOURCE_BARRIER_FLAG_END_ONLY;
cmd->ResourceBarrier(1, &b);
/* Between BEGIN and END the resource may not be used at all. */
/* THE TYPICAL FRAME, as a state machine. */

  backbuffer:  PRESENT
        |  transition
        v
      RENDER_TARGET      <- draw the scene
        |  transition
        v
      PRESENT            <- Present()

  shadowMap:   DEPTH_WRITE     <- render shadows
        |  transition
        v
      PIXEL_SHADER_RESOURCE    <- sample during lighting
        |  transition (next frame)
        v
      DEPTH_WRITE

  gbuffer:     RENDER_TARGET   <- geometry pass
        |
        v
      PIXEL_SHADER_RESOURCE    <- lighting pass

/* A helper, because writing the struct out every time is how
   mistakes happen: */
inline void Transition(ID3D12GraphicsCommandList *cmd,
                       ID3D12Resource *res,
                       D3D12_RESOURCE_STATES from,
                       D3D12_RESOURCE_STATES to)
{
    if (from == to) return;                 /* no-op, and the
                                               debug layer
                                               complains       */
    D3D12_RESOURCE_BARRIER b = {};
    b.Type = D3D12_RESOURCE_BARRIER_TYPE_TRANSITION;
    b.Transition.pResource   = res;
    b.Transition.StateBefore = from;
    b.Transition.StateAfter  = to;
    b.Transition.Subresource = D3D12_RESOURCE_BARRIER_ALL_SUBRESOURCES;
    cmd->ResourceBarrier(1, &b);
}

/* AND TRACK THE STATE YOURSELF. The runtime does not tell you
   what state a resource is in; you must know. A small
   wrapper that stores the current state per resource and
   asserts on mismatch pays for itself immediately - the debug
   layer catches errors, but only at execute time, and only
   the ones that actually execute. */
Enhanced barriers are the newer, better model

DX12's original barriers conflate three separate things: execution dependency, memory visibility, and layout transition. Enhanced barriers (Agility SDK 1.7+) split them, matching Vulkan's model and letting you express "wait for compute, but do not decompress" — which the old model could not say. New code should prefer them; the concepts in this chapter map across directly.

Too many barriers, and too few

/* TOO FEW: corruption, hangs, or the classic "works on
   NVIDIA, breaks on AMD" - because one driver happened to
   flush a cache the other did not.

   TOO MANY: every barrier is a potential pipeline drain. A
   barrier between every draw serialises the GPU completely
   and can cost more than the draws.                        */

/* BAD - a barrier per object. */
for (auto &o : objects) {
    Transition(cmd, o.tex, COPY_DEST, PIXEL_SHADER_RESOURCE);
    Draw(o);
}

/* GOOD - transition everything once, then draw. */
std::vector<D3D12_RESOURCE_BARRIER> barriers;
for (auto &o : objects)
    barriers.push_back(MakeTransition(o.tex, COPY_DEST,
                                      PIXEL_SHADER_RESOURCE));
cmd->ResourceBarrier((UINT)barriers.size(), barriers.data());
for (auto &o : objects) Draw(o);

/* THE GENERAL PATTERN: group your frame into PASSES, and put
   all the barriers at pass boundaries. Inside a pass, nothing
   changes state.

   A RENDER GRAPH is the industrial version of this idea: you
   declare which passes read and write which resources, and
   the graph derives the minimal barrier set, the state
   transitions and the aliasing opportunities automatically.
   Every large engine has one, for exactly this reason.    */

Residency

/* VRAM is not infinite and you are not the only application.
   Windows may EVICT your resources to system memory when
   another app needs the memory. */

DXGI_QUERY_VIDEO_MEMORY_INFO info = {};
adapter->QueryVideoMemoryInfo(0, DXGI_MEMORY_SEGMENT_GROUP_LOCAL,
                              &info);
/* info.Budget       - what the OS says you may use
   info.CurrentUsage - what you are using
   Exceeding the budget does not fail; it makes the OS start
   evicting, and your frame time falls off a cliff. */

/* Explicit control, for streaming systems: */
ID3D12Pageable *res[] = { texture.Get() };
device->Evict(1, res);                /* push to system memory */
device->MakeResident(1, res);         /* pull back - BLOCKING  */

/* The async form, so you can prefetch without stalling: */
device->EnqueueMakeResident(D3D12_RESIDENCY_FLAG_NONE, 1, res,
                            fence.Get(), fenceValue);

/* THE PRACTICAL ADVICE
     * poll the budget each frame and shed quality if you are
       over - drop mip levels, reduce the shadow atlas
     * do not fight the OS: if the budget shrinks because the
       user alt-tabbed to a browser, respect it
     * a frame time that suddenly doubles with no code change
       is very often eviction, not your rendering            */
