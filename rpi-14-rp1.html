RP1: what changed on the Pi 5

The Pi 5 moved every low-speed peripheral out of the SoC and onto a separate chip reached over PCIe. It is the most interesting architectural decision the platform has made, it broke a decade of example code, and it is a compact lesson in why kernel abstractions exist.

What RP1 is

   RP1 is a SOUTHBRIDGE: an I/O companion chip, designed by
   Raspberry Pi, on the Pi 5 board next to the BCM2712.

   +---------------------+                +--------------------+
   |  BCM2712            |                |  RP1               |
   |   4x Cortex-A76     |   PCIe 2.0 x4  |   GPIO (28 pins)   |
   |   LPDDR4X           |<==============>|   5x UART          |
   |   VideoCore VII     |   ~8 Gbit/s    |   6x SPI           |
   |   PCIe root complex |                |   4x I2C           |
   |   HDMI, video codec |                |   PWM, PIO         |
   +---------------------+                |   2x USB3, 2x USB2 |
                                          |   Gigabit Ethernet |
                                          |   2x CSI/DSI       |
                                          |   ADC, I2S         |
                                          +--------------------+

   WHY DO THIS:
     - the SoC process is optimised for CPU and GPU, which
       is expensive and unsuitable for analog and I/O pads
     - a separate, cheaper process suits I/O
     - dedicated bandwidth per interface rather than the
       Pi 4's shared USB2 bottleneck
     - Raspberry Pi controls the design, so it can add what
       it wants (PIO) instead of using the SoC vendor's
       fixed peripheral set
     - the same part can be reused on future boards

   THIS IS HOW REAL SoCs ARE BUILT. Splitting compute from
   I/O across a high-speed link is the normal arrangement in
   servers and phones. The Pi 5 is more representative of
   industry practice than the Pi 4, which is a point in its
   favour as a teaching board.

What it breaks

# EVERY LIBRARY THAT WRITES SoC REGISTERS DIRECTLY.

# On a Pi 4, this is the classic idiom:
int fd = open("/dev/mem", O_RDWR | O_SYNC);
volatile uint32_t *gpio = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE,
                               MAP_SHARED, fd, 0xFE200000);
gpio[7] = 1 << 17;              /* GPSET0: set GPIO17 */

# On a Pi 5 there is nothing at that address. GPIO is not
# in the SoC's memory map at all - it is behind a PCIe
# bridge, at addresses the kernel assigns at enumeration
# time, through a different register layout.

# CASUALTIES, and what to use instead:
#   RPi.GPIO       -> gpiozero (which uses libgpiod)
#   wiringPi       -> libgpiod (chapter 11)
#   bcm2835 lib    -> libgpiod
#   pigpio         -> check current Pi 5 status; the
#                     rewrite is non-trivial because its
#                     DMA waveform engine is SoC-specific
#   any tutorial saying "mmap 0xFE200000"

# WHAT SURVIVED UNCHANGED:
#   /dev/gpiochipN + libgpiod
#   /dev/i2c-N, /dev/spidevN.M, /dev/ttyAMAn
#   /sys/class/pwm
#   device tree overlays (different node names, same
#     mechanism - chapter 10)
#   any kernel driver written against the proper subsystem

# THE LESSON, and it is the point of this chapter: code
# written to the kernel's abstraction survived a change of
# hardware topology so complete that the peripherals moved
# to a different chip on a different bus. Code written to
# physical addresses did not survive at all.
#
# That is not an accident or good luck. It is the entire
# purpose of the driver model (Linux track, chapter 17),
# and this is the clearest demonstration of it you will
# ever get to run yourself.
The right way to write portable Pi code

Never name a chip number, a physical address, or a board model. Ask the kernel: resolve the GPIO chip by label, open /dev/i2c-1 by its stable device-tree alias, use gpiofind rather than a hardcoded offset. Code written that way ran unmodified across the RP1 transition, and will run on whatever comes next. It is also slightly more work today — which is exactly why so much example code took the shortcut and is now broken.

Seeing it on the board

# RP1 is a PCIe device, so it appears in lspci:
$ lspci
0000:00:00.0 PCI bridge: Broadcom Inc. Device 2712
0000:01:00.0 Multimedia controller: Raspberry Pi Ltd RP1 PCIe

$ lspci -vv -s 0000:01:00.0 | head -20
# BARs, capabilities, link speed and width. Genuinely worth
# reading once - it is a real PCIe endpoint and everything
# the virtualisation track says about BARs and MSI applies.

# The link, which is where the bandwidth budget comes from:
$ sudo lspci -vv | grep -i "LnkSta"
LnkSta: Speed 5GT/s, Width x4

# In the device tree it appears as a bus with children:
$ dtc -I fs -O dts /sys/firmware/devicetree/base 2>/dev/null \
      | grep -A3 "rp1"

# GPIO chip, by label (chapter 11):
$ gpiodetect
gpiochip0 [gpio-brcmstb@107d508500] (32 lines)   # SoC's own
gpiochip4 [rp1] (54 lines)                       # the header

# THE NUMBER 4 IS NOT STABLE. It has changed between kernel
# releases and will change again. Resolve by label:
$ gpiofind GPIO17
$ gpioinfo | grep -B20 GPIO17 | grep gpiochip

PIO: the interesting new capability

# RP1 includes a PIO block - the same programmable I/O idea
# as the RP2040 microcontroller. Small state machines that
# execute a tiny instruction set to drive pins with
# CYCLE-EXACT timing, independently of the CPU.

# THIS IS THE ANSWER to chapter 13's problem. A Pi 5 can now
# generate exact waveforms without a DMA trick and without
# an external microcontroller:
#   - WS2812 LED strips, natively
#   - protocols with no hardware peripheral
#   - extra UARTs, SPI-like buses, quadrature decoders
#   - precise pulse measurement

$ sudo apt install python3-rpi-lgpio   # naming varies
# Raspberry Pi ships a PIO library and examples; check the
# current documentation for the interface, as this is new
# enough that the API is still settling.

# THE CONCEPT, which is what matters here:
#   - up to 4 state machines, each with a small program
#   - instructions execute at a configurable clock divider
#   - FIFOs connect them to the CPU or to DMA
#   - a program is typically 5-20 instructions
#
# It occupies the same niche as a small FPGA or a
# co-processor: deterministic timing that the main CPU
# cannot provide, without the cost of a separate chip.
#
# If you have read the mcu track, the relationship is worth
# noting: PIO gives a Linux system a little of the
# determinism that made a Cortex-M attractive, for the
# specific job of driving pins.

Practical differences

AreaPi 4Pi 5 with RP1
GPIO from userspacelibgpiod or direct registerslibgpiod only
GPIO chipUsually gpiochip0The RP1 chip — resolve by label
Peripheral count1 SPI (usable), 1 I2C, 2 UARTConsiderably more of each
USB bandwidthUSB3 ports share one controllerIndependent, full bandwidth
EthernetSoC, via its own pathRP1, over PCIe
Exact waveformsDMA tricks (pigpio)PIO
Latency to a GPIO writeA store to a memory-mapped registerA PCIe write — slightly higher, and worth knowing if you measure
Analog inputNoneA basic ADC exists on RP1
Latency, not bandwidth, is the cost of the split

A single GPIO write on a Pi 5 crosses a PCIe link, so its latency is higher than a Pi 4's direct register store — tens of nanoseconds rather than a handful. Bandwidth is enormous and never the constraint; what changes is the cost of a round trip, which matters if you write then immediately read back. Batch your accesses, and prefer the multi-line atomic set that the GPIO character device offers (chapter 11) over several single-line calls.
