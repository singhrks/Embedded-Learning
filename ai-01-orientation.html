What this track assumes and where it goes

Twenty-eight chapters from "what is a vector" to a working transformer you write yourself. No prior machine learning, and no mathematics beyond school algebra — everything else is built here.

Why an embedded engineer should read this

This is a hardware-adjacent curriculum, so the case for spending weeks on linear algebra deserves to be made explicitly rather than assumed. The short version is that the interesting work is increasingly at the boundary, and the boundary is where the models meet the silicon.

   THREE HONEST REASONS:

   1. THE WORK IS ARRIVING IN YOUR DOMAIN.
      Keyword spotting on a Cortex-M4. Anomaly detection on
      a motor controller. Vision on a $5 SoC. NPUs in
      application processors you already ship. Someone has
      to write the driver for the accelerator, decide
      whether the model fits in SRAM, and explain why the
      quantised version is 3% less accurate.

   2. THE INTUITIONS TRANSFER BOTH WAYS.
      A transformer's forward pass is a fixed sequence of
      matrix multiplications over a known-size working set.
      That is a MEMORY BANDWIDTH problem and a CACHE
      BLOCKING problem - things you already reason about.
      Conversely, understanding numerical precision, fixed
      point and saturation is exactly what quantisation
      needs, and embedded engineers already have it.

   3. AND THE PLAIN ONE: these systems are now part of the
      tooling you use every day. Knowing what they are -
      really, mechanically - is the difference between using
      them well and guessing.

   WHAT THIS TRACK IS NOT:
     · not a research course. No proofs of convergence, no
       measure theory.
     · not a framework tutorial. You will see PyTorch, but
       the point is what it computes, not its API.
     · not a survey. One path, taken properly, ending at a
       working transformer.

Notation

Mathematical notation is a language with regional dialects, and most of the confusion in a first pass comes from that rather than from the ideas. These are the conventions this track uses throughout.

/* Introduced once, used throughout. Refer back here.     */

   SCALARS        lowercase italic:  x, y, alpha
   VECTORS        lowercase bold:    x, w      (column
                                                vectors by
                                                default)
   MATRICES       uppercase bold:    W, X, A
   TENSORS        the general case: an n-dimensional array.
                  A scalar is rank 0, a vector rank 1, a
                  matrix rank 2. "Tensor" in this field just
                  means "n-dimensional array" - the physics
                  meaning is not implied.

   x_i            the i-th element of vector x
   W_ij           row i, column j of W
   x^T            transpose
   ||x||          the norm (length) of x
   x · y          dot product
   A @ B          matrix multiplication (numpy/PyTorch
                  notation, used in code)
   A * B          ELEMENTWISE product (in code) - NOT matrix
                  multiplication. A frequent source of silent
                  bugs.

   SHAPES ARE WRITTEN LIKE THIS:  (batch, seq_len, d_model)
   and you should read every line of model code by tracking
   shapes. MOST BUGS IN THIS FIELD ARE SHAPE BUGS. The
   habit to build now: after every operation, ask "what
   shape is this, and why?"

   f(x)           a function
   df/dx          derivative
   ∇f             gradient - the vector of all partial
                  derivatives
   E[X]           expectation
   P(x)           probability

/* AND THE ONE CONVENTION THAT CONFUSES EVERYONE:

   In mathematics, a linear layer is usually written
        y = W x + b        with x a COLUMN vector
   In code, data comes in ROWS, so it is written
        Y = X @ W.T + b    or often just  X @ W + b
   with W stored already transposed.

   THESE ARE THE SAME OPERATION. When a paper and an
   implementation seem to disagree about which index is
   which, this is usually why.                           */
How to read this track

Do the arithmetic by hand at least once per chapter. A 2×2 matrix multiply, one step of gradient descent, one softmax over three numbers. The notation is compressed and it hides the fact that everything here is arithmetic you could do on paper — until you have done it on paper, the compression reads as magic. Every chapter ends with a "check yourself" list written to be answerable without looking.

An honest framing of the subject

A subject this hyped attracts both overclaim and reflexive dismissal, and neither helps you learn it. This is the position the track takes, stated once so it does not need restating in every chapter.

/* WHAT THESE SYSTEMS ARE:
     Function approximators with an enormous number of
     parameters, fitted to data by gradient descent. A large
     language model is a function from a sequence of tokens
     to a probability distribution over the next token,
     with a few hundred billion adjustable numbers, fitted
     to a large fraction of the written internet.

     THAT DESCRIPTION IS COMPLETE AND MECHANICAL. Everything
     in chapters 16-25 is an elaboration of it.

/* WHAT IS GENUINELY SURPRISING:
     That scaling this simple recipe - more parameters, more
     data, more compute - produces capabilities nobody
     explicitly designed: translation, arithmetic, code,
     in-context learning from examples in the prompt.
     Chapter 23 covers the scaling laws that describe this
     empirically. NOBODY HAS A COMPLETE THEORY OF WHY IT
     WORKS AS WELL AS IT DOES. That is the honest state of
     the field, and any source that tells you otherwise is
     selling something.

/* WHAT IS OFTEN OVERSTATED:
     · these are not databases; they do not retrieve facts
       reliably
     · they have no persistent memory between calls beyond
       what is in the context window (chapter 25)
     · confident output and correct output are not
       correlated as strongly as the fluency suggests
     · "reasoning" is a description of behaviour, not a
       claim about mechanism

/* WHAT THIS MEANS FOR AN ENGINEER:
     Treat model output as UNTRUSTED INPUT. Validate it,
     constrain it, and design the system so a wrong answer
     is recoverable. That is the same discipline you apply
     to a sensor reading or a network packet, and it is the
     right one here.                                      */
