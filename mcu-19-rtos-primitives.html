RTOS primitives: queues, semaphores and ISR-safe APIs

The concurrency track covers mutexes and condition variables in general. What is different on a microcontroller is that half your concurrency is with interrupts rather than tasks — and an interrupt cannot block, which changes every API it touches.

Why ISRs need their own API

   A TASK that cannot proceed BLOCKS: the kernel removes it
   from the ready list and switches to someone else. It
   resumes later, where it left off.

   AN ISR CANNOT DO THIS. There is nothing to switch to -
   an interrupt is not a schedulable entity, it has no TCB
   and no stack of its own to preserve. Blocking in an ISR
   would suspend whatever task happened to be interrupted,
   which is not the ISR and has done nothing wrong.

   So every kernel splits its API:

     xQueueSend(q, &item, portMAX_DELAY)
        may block. TASK ONLY.

     xQueueSendFromISR(q, &item, &woken)
        never blocks; returns pdFAIL if full. ISR ONLY.

   And the FromISR variants have an extra job: reporting
   whether they made a higher-priority task ready, so the
   ISR can request a context switch on the way out.

     void UART_IRQHandler(void)
     {
         BaseType_t woken = pdFALSE;
         xQueueSendFromISR(q, &byte, &woken);
         portYIELD_FROM_ISR(woken);   /* sets PendSV if so  */
     }

   Omit that last line and the woken task waits until the
   next tick - up to a full millisecond of latency, for no
   reason, and only under some timings. It is a classic
   intermittent-latency bug.
The priority ceiling for ISR calls

An ISR may only call kernel APIs if its priority is at or below configMAX_SYSCALL_INTERRUPT_PRIORITY (chapter 08). Above that line the kernel's BASEPRI critical sections do not block it, so it can interrupt the kernel mid-update and corrupt a list. The damage appears much later, in unrelated code. Keep configASSERT enabled in development — FreeRTOS checks this on every ISR API call and catches the mistake immediately rather than three weeks later.

The queue is the primitive you want

/* A queue copies data and handles the blocking, the
   waking, and the mutual exclusion in one object. Prefer
   it over a shared buffer plus a semaphore almost always. */

QueueHandle_t sensor_q;

void app_init(void)
{
    sensor_q = xQueueCreate(10, sizeof(sensor_reading_t));
}

/* PRODUCER - an ISR. */
void ADC_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;
    sensor_reading_t r = { .ts = g_ticks, .value = ADC1->DR };

    /* Never blocks. If the queue is full the reading is
       dropped, and that is a DESIGN DECISION you should
       make explicitly - count the drops.                  */
    if (xQueueSendFromISR(sensor_q, &r, &woken) != pdTRUE) {
        g_dropped++;
    }
    portYIELD_FROM_ISR(woken);
}

/* CONSUMER - a task. */
void sensor_task(void *arg)
{
    sensor_reading_t r;
    for (;;) {
        if (xQueueReceive(sensor_q, &r, pdMS_TO_TICKS(100))) {
            process(&r);
        } else {
            handle_sensor_timeout();     /* the timeout is  */
        }                                /* not optional    */
    }
}

/* WHY A QUEUE BEATS A SHARED BUFFER:
   - it COPIES, so there is no lifetime question about the
     producer's data;
   - the blocking receive means the consumer uses zero CPU
     while waiting, which is what lets the system sleep;
   - full and empty are handled once, correctly, rather
     than in every caller;
   - a timeout is available, so a stuck producer becomes a
     reported error rather than a hang.

   THE COST IS THE COPY. For large items, queue a POINTER
   to a buffer from a pool instead - but then you own the
   lifetime again, and the pool needs its own discipline. */

Semaphores, mutexes, and the difference that matters

/* BINARY SEMAPHORE - signalling. No owner.
   Use for: ISR says "something happened" to a task.        */
SemaphoreHandle_t data_ready;

void DMA1_IRQHandler(void) {
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(data_ready, &woken);
    portYIELD_FROM_ISR(woken);
}
void consumer(void *a) {
    for (;;) {
        xSemaphoreTake(data_ready, portMAX_DELAY);
        process_buffer();
    }
}

/* COUNTING SEMAPHORE - resource pools, or counting events
   that may arrive faster than they are consumed.          */
SemaphoreHandle_t slots = xSemaphoreCreateCounting(5, 5);

/* MUTEX - mutual exclusion. HAS AN OWNER, and that is the
   whole difference.                                       */
SemaphoreHandle_t spi_lock = xSemaphoreCreateMutex();

void use_spi(void) {
    xSemaphoreTake(spi_lock, portMAX_DELAY);
    spi_transfer(...);
    xSemaphoreGive(spi_lock);
}

/* BECAUSE A MUTEX HAS AN OWNER IT CAN DO TWO THINGS A
   SEMAPHORE CANNOT:

   1. PRIORITY INHERITANCE. While a low-priority task holds
      a mutex a high-priority task wants, the holder is
      temporarily raised to the waiter's priority. This
      bounds priority inversion - the failure that reset
      Mars Pathfinder (see the concurrency track, chapter
      15). A binary semaphore has no owner, so it cannot
      do this, and using one for mutual exclusion silently
      gives up the protection.

   2. RECURSION. xSemaphoreCreateRecursiveMutex lets the
      owner take it again without deadlocking.

   THE RULE:
     mutual exclusion -> MUTEX, always.
     signalling       -> BINARY SEMAPHORE.
   Using a semaphore as a lock is the single most common
   RTOS design error, and it works fine until the day a
   priority inversion costs you a deadline.

   NEVER take a mutex from an ISR. There is no owner to
   record, no priority to inherit, and no way to block.
   There is deliberately no xSemaphoreTakeFromISR.         */

Task notifications: the cheap path

/* A direct-to-task signal with no separate kernel object.
   Roughly 45x faster than a semaphore and it costs no RAM
   beyond a word already in the TCB.                       */

void DMA1_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;
    vTaskNotifyGiveFromISR(dma_task_handle, &woken);
    portYIELD_FROM_ISR(woken);
}

void dma_task(void *arg)
{
    for (;;) {
        /* pdTRUE = clear the count on exit, i.e. act as a
           binary semaphore.                                */
        if (ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(500))) {
            process_buffer();
        } else {
            dma_timeout_recovery();
        }
    }
}

/* THE LIMITATION that decides whether you can use it: a
   notification targets ONE SPECIFIC TASK. There is no
   broadcast and no queueing of senders. If two tasks might
   wait for the same event, or the sender does not know the
   receiver, use a semaphore or queue.

   For the extremely common ISR-to-one-task pattern -
   which is most of embedded signalling - notifications are
   strictly better and under-used.                         */
