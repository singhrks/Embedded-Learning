System registers, MRS and MSR

Every piece of processor configuration — the MMU, caches, exception vectors, timers, security state — lives in a system register. There are hundreds. This chapter covers the naming scheme, the access rules, and the one instruction sequence you must get right or your configuration will not take effect.

The naming scheme

NAME_ELx

The suffix names the lowest exception level that may access the register — not the level it applies to. SCTLR_EL1 is accessible from EL1, EL2 and EL3; it is not accessible from EL0. A register with no suffix, or _EL0, is accessible from user space.

   TTBR0_EL1        translation table base, accessible from EL1+
   TTBR0_EL2        the EL2 equivalent — a SEPARATE register
   VTTBR_EL2        stage-2 table base; only meaningful at EL2
   CNTPCT_EL0       physical counter — readable from USER SPACE
   SCTLR_EL3        secure monitor's system control

   Registers ending _EL1 often have _EL2 and _EL3 counterparts.
   They are DIFFERENT REGISTERS with independent contents, not
   different views of one register. Writing SCTLR_EL1 does not
   affect SCTLR_EL2.

   Special forms:
     _EL12, _EL02    accessed from EL2 with VHE enabled, these
                     alias the EL1/EL0 registers — how a host
                     kernel running at EL2 manipulates guest state
     ICC_*_EL1       GIC CPU interface (chapter 23)
     ID_*_EL1        read-only feature identification (chapter 01)

MRS and MSR

System registers cannot be used as operands in ordinary instructions. There are exactly two instructions for reaching them, and everything a kernel does to configure the processor goes through one of the two.

        mrs     Xt, <systemreg>      // System register → general
        msr     <systemreg>, Xt      // General → System register

/* Mnemonic: MRS = "Move Register from System"
             MSR = "Move System Register"                     */

/* A read-modify-write is three instructions, because system
   registers cannot be ALU operands (chapter 04):            */
        mrs     x0, sctlr_el1
        orr     x0, x0, #(1 << 0)      // set the M bit
        msr     sctlr_el1, x0
        isb                             // ← see below

/* There is also an immediate form for PSTATE fields only: */
        msr     daifset, #2
        msr     spsel, #1
        msr     pan, #1

The rule that catches everyone

A system register write needs an ISB to take effect

Instructions already in the pipeline were fetched, decoded and possibly executed under the old configuration. Writing SCTLR_EL1 to enable the MMU does not retroactively change how the next few instructions were translated.

ISB — Instruction Synchronization Barrier — flushes the pipeline so that everything after it is re-fetched and re-decoded under the new context. Without it, behaviour depends on pipeline depth and varies between cores, which is exactly the kind of bug that appears on one board and not another.

/* The canonical sequence, and why each part is there: */

        /* 1. make sure prior memory writes (e.g. the page tables
              you just built) are visible to the table walker  */
        dsb     ish

        /* 2. change the configuration */
        msr     ttbr0_el1, x0
        msr     tcr_el1, x1
        msr     sctlr_el1, x2

        /* 3. flush the pipeline so it takes effect NOW */
        isb

/* Which registers need it? Anything that changes how instructions
   are FETCHED, TRANSLATED or PERMITTED:
     SCTLR, TTBR, TCR, MAIR, VBAR, SCR, HCR, CPACR, CPTR, TPIDR

   Registers that only affect a later explicit read — CNTFRQ,
   most ID registers — do not.

   When in doubt, add the ISB. It costs a pipeline flush; the bug
   costs a week.                                              */

The registers you will actually use

There are hundreds of system registers, and no one reads the whole architecture manual before writing boot code — you look up the one you need, when you need it. This table is that lookup point: it groups the registers by what job they do rather than by their bit-encoding, and points at the chapter that explains the mechanism in depth. A useful way to read it the first time is to notice the pattern — SCTLR/TTBR/TCR/MAIR together configure address translation before you turn the MMU on, VBAR/ESR/FAR/ELR together describe an exception after it happens, and everything below MPIDR_EL1 answers questions that only come up once you are doing SMP bring-up, timers, or security work.

SCTLR_EL1, field by field

If one register deserves to be read field by field, this is it: it turns on the MMU, the caches, alignment checking and several security features. A surprising number of early bring-up problems are one wrong bit in this register.

The single most important register in early boot. The bits you
will actually touch:

   bit  0  M      MMU enable
   bit  1  A      Alignment check — fault on ANY unaligned access
   bit  2  C      Data cache enable
   bit  3  SA     Stack alignment check (SP must be 16-byte aligned)
   bit  4  SA0    Stack alignment check for EL0
   bit 12  I      Instruction cache enable
   bit 19  WXN    Writable implies eXecute-Never — a W^X hardening
   bit 25  EE     Exception endianness
   bit 39  TCF    Tag check fault behaviour (MTE)

  Reset value has M, C and I CLEAR: the MMU and caches are OFF
  when your boot code starts. Turning them on, in the right order
  and with the right barriers, is the job of early boot.

  A common bring-up bug: enabling C (data cache) before the MMU.
  With the MMU off, all memory is treated as Device-nGnRnE and
  the data cache does nothing — so it appears harmless. Then you
  enable the MMU and the previously-uncached writes are suddenly
  cacheable, and stale data appears. Enable M and C together,
  after the tables are built and a DSB has completed.

Access can be trapped

A higher exception level can arrange for a lower one's access to a system register to trap instead of executing. This is the mechanism behind virtualisation, and it explains why the same instruction can behave differently in a guest.

/* A higher exception level can configure a system register access
   at a LOWER level to trap instead of executing. This is the
   entire basis of virtualisation (chapter 31).              */

/* Example: HCR_EL2.TVM traps guest writes to virtual-memory
   control registers, so the hypervisor sees every TTBR change. */
        mrs     x0, hcr_el2
        orr     x0, x0, #(1 << 26)      // TVM
        msr     hcr_el2, x0
        isb

/* Now a guest at EL1 executing `msr ttbr0_el1, x0` takes a
   synchronous exception to EL2 with ESR_EL2.EC = 0x18
   (trapped MSR/MRS). The hypervisor decodes the syndrome to
   learn which register and which general register were involved,
   emulates the write, advances ELR_EL2 by 4, and ERETs.     */

/* Other common trap controls:
     CPACR_EL1.FPEN     trap FP/SIMD — used for lazy FPU switching
     CPTR_EL2/EL3       the EL2/EL3 equivalents
     HCR_EL2.TGE        route ALL EL0 exceptions to EL2
     MDCR_EL2/EL3       trap debug and performance monitor access
     SCR_EL3.SMD        disable SMC entirely                   */

Accessing them from C

C has no syntax for system registers, so reaching them from kernel code means inline assembly or a compiler intrinsic. There is a standard idiom, and it is worth copying rather than reinventing.

/* Inline assembly, with the constraints from C chapter 18: */

#define read_sysreg(r) ({                       \
        uint64_t __v;                           \
        asm volatile("mrs %0, " #r : "=r"(__v)); \
        __v;                                    \
})

#define write_sysreg(v, r) do {                 \
        uint64_t __v = (uint64_t)(v);           \
        asm volatile("msr " #r ", %0" :: "r"(__v)); \
} while (0)

uint64_t sctlr = read_sysreg(sctlr_el1);
write_sysreg(sctlr | 1, sctlr_el1);
asm volatile("isb");

/* Linux provides exactly this in arch/arm64/include/asm/sysreg.h,
   plus read_sysreg_s() for registers the assembler does not know
   by name (encoded as S<op0>_<op1>_<CRn>_<CRm>_<op2>).       */

/* Note: `volatile` is REQUIRED here. Without it the compiler may
   delete an MSR whose result is unused, or hoist an MRS out of a
   loop. A register write with a side effect needs it always.  */

The encoding, and unnamed registers

Every system register is really a set of coordinates, not a name. Knowing that is what lets you read a disassembly that refers to a register your tools do not have a name for — including registers added after your toolchain was built.

A system register is identified by five fields:

        S<op0>_<op1>_C<CRn>_C<CRm>_<op2>

Assemblers know the names for architected registers. For newer or
IMPLEMENTATION DEFINED ones, you encode them directly:

        mrs     x0, S3_1_C15_C2_0        // an IMP DEF register

Linux uses this for registers newer than the minimum supported
binutils version:

        #define SYS_ID_AA64ISAR2_EL1  sys_reg(3, 0, 0, 6, 2)
        read_sysreg_s(SYS_ID_AA64ISAR2_EL1);

If you see S3_x_Cy_Cz_w in a disassembly, look it up in the ARM ARM
register index — it is an architected register your disassembler
did not recognise, and it is often the interesting one.

System registers and context switching

Switching between processes or virtual machines means swapping a specific set of these registers. Knowing which ones must be saved, and which are banked automatically by hardware, is the difference between a correct context switch and a subtle one.

/* Which system registers must be saved on a context switch?
   Only those that are PER-CONTEXT:                          */

   TTBR0_EL1        per address space — this IS the switch
   TPIDR_EL0        thread pointer (TLS)
   TPIDRRO_EL0      read-only thread pointer
   FPCR / FPSR      FP control and status
   (PAC keys, if used)

/* NOT saved, because they are global to the kernel:         */
   SCTLR_EL1, MAIR_EL1, TCR_EL1, VBAR_EL1, TTBR1_EL1

/* This is why a thread switch within one process is cheaper than
   a process switch: TTBR0 does not change, so the TLB entries
   remain valid (OS chapter 07).

   A VM switch is far more expensive: the hypervisor must save and
   restore essentially the entire EL1 system register file, which
   is dozens of registers — one reason VM exits are costly.  */

Reading them at runtime

All of these are readable at runtime, which turns questions like "is the MMU actually on" and "which translation table is in use" from inference into observation.

# Linux exposes some via sysfs
cat /sys/devices/system/cpu/cpu0/regs/identification/midr_el1
cat /sys/devices/system/cpu/cpu0/regs/identification/revidr_el1

# gdb, on a bare-metal or kernel target
p/x $SCTLR_EL1
p/x $TTBR0_EL1
p/x $ESR_EL1
info all-registers | grep -i el1

# in a kernel oops, the relevant ones are printed for you
dmesg | grep -E 'ESR|FAR|pstate'

# a small kernel module or bare-metal routine to dump the
# configuration is worth having during bring-up:
pr_info("SCTLR=%016llx TCR=%016llx MAIR=%016llx TTBR0=%016llx\n",
        read_sysreg(sctlr_el1), read_sysreg(tcr_el1),
        read_sysreg(mair_el1),  read_sysreg(ttbr0_el1));
