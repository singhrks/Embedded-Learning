I/O, buses and interconnects

A CPU that cannot talk to the world is a heater. This chapter covers how software reaches a device, the three ways data moves, and what actually travels on the wires between blocks — which turns out to matter enormously for security.

How software reaches a device

Two historical approaches. Only one survives in modern designs.

Memory-mapped I/O

Peripheral registers are assigned addresses in the same physical address space as DRAM. Writing to a UART is the same instruction as writing to RAM; only the address differs. Everything follows from this: device access is protected by page tables, translated by the MMU, and subject to the same memory-attribute rules as any other access.

A physical memory map is a static, chip-designer decision

  0x0000_0000  +--------------------------+
               |  Boot ROM                |
  0x1000_0000  +--------------------------+
               |  On-chip SRAM            |
  0x4000_0000  +--------------------------+
               |  Peripheral region       |
               |    0x4000_0000  UART0    |   each block usually gets
               |    0x4000_1000  UART1    |   at least one 4 KB page,
               |    0x4000_2000  I2C0     |   so it can be mapped and
               |    0x4800_0000  GIC      |   protected independently
  0x8000_0000  +--------------------------+
               |  DRAM                    |
               +--------------------------+

The 4 KB granularity is not an accident: it is the page size, so that
one driver can be given exactly one peripheral and nothing else.

Why MMIO must not be cached

/* Device registers are not memory. They have SIDE EFFECTS. */

status = regs->FIFO;    /* reading POPS a byte from the FIFO      */
regs->CTRL = START;     /* writing STARTS a physical operation    */
n = regs->COUNT;        /* the value changes without any write    */

/* If this region were cached and speculatable:
     - a speculative read could drain a FIFO nobody asked to read
     - a cached read would return a stale count forever
     - a write could sit in a dirty line and never reach the device
     - two writes could be merged, or reordered

   Hence a distinct memory TYPE (ARM: Device-nGnRnE), not merely
   "uncached". See ARM chapter 11.                                */

/* And hence: never dereference an MMIO pointer directly. */
u32 v = readl(base + STATUS);       /* Linux                       */
writel(v | ENABLE, base + CTRL);    /* includes the right barriers */

The three ways data moves

Getting data between a processor and a device is not one mechanism but three, and they differ enormously in how much processor time they consume. Choosing correctly is one of the central decisions in driver design.

PollingInterruptsDMA
MechanismCPU spins reading a status bitDevice signals; CPU takes an exceptionDevice moves data to/from memory itself
CPU cost100% while waitingOnly on events, plus entry/exit overheadNear zero; one interrupt on completion
LatencyLowest and most deterministicInterrupt latency, typically µsSetup cost amortised over a large transfer
Best forVery short waits; early boot before interrupts exist; hard real-timeMost peripheralsBulk: network, storage, display, cameras
HazardWastes power; can hang forever — always bound the loopStorms if you fail to clear at the sourceCoherency and address translation
 
/* polling, done correctly - ALWAYS with a timeout */
ret = readl_poll_timeout(base + STATUS, val,
                         val & STATUS_READY,   /* condition            */
                         10,                   /* µs between polls     */
                         1000);                /* µs before giving up  */
if (ret)
        return -ETIMEDOUT;      /* the device is wedged; say so
                                   rather than hanging the kernel */

Why DMA changes everything

Without DMA                      With DMA

  device -> CPU register           device -> memory, directly
         -> memory                 CPU is not involved at all

  every byte costs instructions    one setup + one interrupt

But now a SECOND entity issues addresses onto the interconnect, and
it never passed through the CPU's MMU. Two consequences:

  1. COHERENCY. The device sees DRAM; the CPU sees its cache.
     (chapter 15)

  2. PROTECTION. Every isolation guarantee built with page tables
     has a hole in it, because the device's transactions were never
     checked. This is why the IOMMU/SMMU exists.
     (security track, chapters 02-07)

Bus topologies

How devices are physically connected determines who can talk to whom, how bandwidth is shared and what happens when one device misbehaves. The industry has moved decisively in one direction here, and knowing why explains most modern bus design.

Shared bus            one set of wires, arbitration decides who drives
                      + simple, cheap, easy to snoop
                      - one transaction at a time; does not scale
                      e.g. classic AHB, I2C, older PCI

Crossbar              every master connected to every slave
                      + full parallelism between disjoint pairs
                      - area grows as N x M
                      e.g. small AXI interconnects

Network on chip       routers and links, packets find their way
  (NoC / mesh)        + scales to dozens of masters
                      - variable latency, needs flow control
                      e.g. ARM CMN, CHI-based fabrics

Point to point        dedicated serial links, switched
  (serial)            + very high bandwidth per pin, hot-pluggable
                      - protocol complexity, serialisation latency
                      e.g. PCIe, USB, Ethernet

Parallel gave way to serial

Counter-intuitively, one differential pair beats 64 parallel wires. Parallel buses are limited by skew — bits on different wires arrive at slightly different times, and the clock period must exceed the worst skew. Serial links embed the clock in the data, eliminating skew entirely, and then use equalisation and error correction to push the rate far higher. This is why PCIe replaced PCI, SATA replaced PATA, and USB replaced the parallel port.

AMBA: the ARM family

Inside an ARM system-on-chip the connections between blocks follow one family of standards. You will meet these names constantly in datasheets and device trees, and knowing which is used where tells you what performance to expect.

AXI's five channels are independent, which is the whole point

  master                                          slave
    |--- AW: write address ------------------------->|
    |--- W:  write data ---------------------------->|
    |<-- B:  write response -------------------------|
    |--- AR: read address -------------------------->|
    |<-- R:  read data ------------------------------|

Because address and data are separate channels, a master can issue
many addresses before any data returns - OUTSTANDING TRANSACTIONS.
Because responses carry an ID, they may return OUT OF ORDER.

This is how a memory system hides 200-cycle DRAM latency: keep
dozens of requests in flight rather than waiting for each.

What travels besides address and data

This list is the foundation of the entire security track

An AXI transaction carries far more than an address:

  • AxADDR — the physical address.
  • AxID — the master's transaction ID, from which the SoC derives a master ID or StreamID: who is asking.
  • AxPROT[1] — the NS bit: Secure or Non-secure. One wire, and it is the entirety of TrustZone's bus-level enforcement.
  • AxPROT[0] — privileged or unprivileged. AxPROT[2] — instruction or data.
  • AxCACHE — cacheability and bufferability, derived from the page table's memory attributes.
  • AxLEN, AxSIZE, AxBURST — the shape of the burst.

So the NS and AttrIndx fields you set in a page table descriptor are not abstractions — they become physical signals, and hardware downstream (the SMMU, the TZASC, the XPU) makes allow/deny decisions from them. Setting a bit in a descriptor is setting a wire on the interconnect.

Discoverable versus described

DISCOVERABLE buses can be probed. Software asks, hardware answers.

  PCIe: read the configuration space at each bus/device/function
        -> vendor ID, device ID, class, BAR sizes
  USB:  the host requests descriptors from every device it detects

  -> the OS matches a driver against the reported IDs, automatically.

NON-DISCOVERABLE buses cannot. There is no way to ask address
0x40001000 whether a UART lives there - and a wrong guess may hang
the bus or trigger a side effect.

  On-SoC peripherals, I2C and SPI slaves are all in this category.

  -> the hardware must be DESCRIBED to software out of band:
       device tree (embedded Linux, ARM)
       ACPI tables  (servers, Windows on ARM, x86)
       board files  (legacy, deprecated)

This distinction is exactly why the device tree exists, and why an
embedded Linux driver looks so different from a PCIe driver.

Getting an interrupt from a device to a core

A device needs a way to say "I am ready" without the processor constantly asking. The path that signal takes — from a pin or a message, through a controller, to a specific core — is worth following once, because every interrupt problem lives somewhere along it.

Wired interrupt (traditional)

  device asserts a physical line -> interrupt controller -> core
  · limited by pin count, so lines get shared
  · shared lines mean every handler must check "is it mine?"
    and return "not mine" if not

Message-signalled interrupt (MSI / MSI-X, and ARM's LPIs)

  device performs a WRITE to a special address, carrying a payload
  · no dedicated wires at all - it is just a bus transaction
  · thousands of distinct interrupts per device
  · no sharing, so no "is it mine?" ambiguity
  · arrives IN ORDER with the DMA data it refers to, which removes
    a classic race: with a wired interrupt the signal can arrive
    before the data it announces has landed in memory

The interrupt controller itself — priority, masking, routing to a specific core, security grouping — is covered in ARM chapters 23 and 24.

Inspecting a real system

All of this topology is enumerable on a running machine. Walking it for a real system connects the abstractions above to hardware you can actually point at.

# who owns which physical address range
cat /proc/iomem
#   40000000-40000fff : serial@40000000
#   80000000-bfffffff : System RAM

# interrupt counts per CPU - is the handler actually firing?
cat /proc/interrupts

# enumerate discoverable buses
lspci -vv          # BARs, capabilities, link speed, MSI config
lsusb -t           # topology tree

# non-discoverable hardware, as described to the kernel
ls /proc/device-tree/
dtc -I fs -O dts /proc/device-tree | less

# DMA and IOMMU groupings
ls /sys/kernel/iommu_groups/*/devices/
