Device tree

A data structure describing hardware that cannot discover itself. It is how one kernel binary runs on a thousand different boards, and writing one correctly is half of embedded Linux bring-up.

Why it exists

On a PC, hardware announces itself: buses are enumerable and the kernel can ask what is plugged in. Most embedded hardware cannot do that — an I2C sensor soldered to a board has no way to say it exists. The device tree is how the kernel is told instead.

PCI and USB devices announce themselves: vendor ID, device ID,
BARs, interrupts - all readable from the bus.

An SoC's peripherals do not. There is no way to ask a chip
"is there a UART at 0x1c000000, and which interrupt does it
use?" The answer exists only in the datasheet.

  BEFORE DEVICE TREE: "board files" - C code in
  arch/arm/mach-*/ with static tables per board. By 2011 this
  was tens of thousands of lines of near-duplicate data, one
  kernel per board, and it was famously unsustainable.

  WITH DEVICE TREE: the hardware description is DATA, passed
  to the kernel at boot. One arm64 kernel binary boots
  hundreds of boards - the difference is which .dtb the
  bootloader hands it.

  WHAT BELONGS IN IT:
     what hardware exists, and where
     addresses, interrupts, clocks, resets, regulators
     how blocks connect to one another
     board-specific wiring: which GPIO is the reset line

  WHAT DOES NOT:
     policy or configuration ("enable debug mode")
     anything discoverable at runtime
     driver implementation details
     Linux-specific concepts

  The last point is a real rule with real teeth: device tree
  bindings are an ABI shared with U-Boot, BSD, and other
  kernels. "It is what my driver happens to need" is not a
  justification for a property.

Syntax

The format is small and you can learn it in one sitting. It is a plain text file describing a tree of nodes, each with properties, compiled into a compact binary the bootloader hands to the kernel.

/dts-v1/;

#include <dt-bindings/interrupt-controller/arm-gic.h>
#include <dt-bindings/gpio/gpio.h>

/ {                                    /* the ROOT node */
        model = "Vendor MyBoard v2";
        compatible = "vendor,myboard", "vendor,mysoc";
        #address-cells = <2>;          /* addresses use 2 cells */
        #size-cells = <2>;             /* sizes use 2 cells    */

        chosen {
                stdout-path = "serial0:115200n8";
                bootargs = "console=ttyAMA0 earlycon";
        };

        aliases {
                serial0 = &uart0;
        };

        memory@80000000 {
                device_type = "memory";
                reg = <0x0 0x80000000 0x0 0x40000000>;
        };

        soc {
                compatible = "simple-bus";
                #address-cells = <2>;
                #size-cells = <2>;
                ranges;                /* child addresses ==
                                          parent addresses    */

                uart0: serial@1c000000 {
                        compatible = "arm,pl011", "arm,primecell";
                        reg = <0x0 0x1c000000 0x0 0x1000>;
                        interrupts = <GIC_SPI 5 IRQ_TYPE_LEVEL_HIGH>;
                        clocks = <&uart_clk>, <&apb_clk>;
                        clock-names = "uartclk", "apb_pclk";
                        status = "okay";
                };
        };
};

/* THE PIECES:
     label:            uart0 - a handle for &references
     node@address      the @ part MUST match the first reg
                       entry, or dtc warns
     property = value;
     <>   cells: 32-bit big-endian integers
     ""   strings
     []   raw bytes
     &lbl a phandle - a reference to another node
     ;    every property ends with one                      */

#address-cells and #size-cells

These two properties trip up nearly everybody at first. They do not describe the node they appear in — they describe how to read the addresses of its children, which is why an error here produces a confusing failure one level down from where you look.

The single most common source of silent breakage.

  A PARENT declares how many 32-bit cells its CHILDREN use in
  their `reg` properties:

     #address-cells = <1>;  -> a 32-bit address
     #address-cells = <2>;  -> a 64-bit address (two cells)
     #size-cells    = <1>;  -> a 32-bit size
     #size-cells    = <2>;  -> a 64-bit size

  So with #address-cells=2, #size-cells=2:

     reg = <0x0 0x1c000000 0x0 0x1000>;
            \_____________/ \________/
             address, 64-bit  size, 64-bit
             = 0x1c000000     = 0x1000

  and with #address-cells=1, #size-cells=1:

     reg = <0x1c000000 0x1000>;

  GET IT WRONG and the values are parsed as completely
  different numbers. Symptoms: the kernel reports absurd
  memory sizes, ioremap maps the wrong place, or a device gets
  a zero-length resource. NOTHING WARNS at runtime - the data
  is syntactically valid, just meaningless.

  THE RULE: the cells properties on the PARENT govern the
  child's reg. An i2c controller declares
  #address-cells = <1>; #size-cells = <0>; because its
  children have a bus address and no size:

     eeprom@50 { reg = <0x50>; };

  ALWAYS run `make dtbs_check` - it catches most of these.

The standard properties

These properties recur across almost every device node regardless of bus, because they describe the same handful of things nearly all hardware needs to declare — what it is, where it lives, what interrupts it raises, and what resources (clocks, resets, power) it depends on — and a driver's binding document is really just this vocabulary specialised to one device.

PropertyMeaning
compatibleWhat this is, most specific first. The match key.
regAddress and size, per the parent's cells
interruptsPer the interrupt parent's #interrupt-cells
interrupt-parentWhich controller; inherited if absent
clocks / clock-namesClock inputs, by phandle and name
resets / reset-namesReset lines
*-supplyA regulator, e.g. vdd-supply = <&reg_1v8>
*-gpiosGPIOs, e.g. reset-gpios, with flags
dmas / dma-namesDMA channels
status"okay" or "disabled" — disabled nodes create no device
rangesAddress translation between a bus and its parent
iommusThe SMMU and StreamID (isolation ch. 03)
dma-coherentThis device's DMA is coherent with the CPU caches
dma-rangesWhat physical range the device can address
memory-regionA reserved-memory carve-out

   driver serve many parts: */

        compatible = "vendor,mysoc-uart", "arm,pl011",
                     "arm,primecell";

/* The kernel tries each in order. If nobody claims the
   SoC-specific string, the generic pl011 driver matches -
   which is exactly right when the block really is a pl011.

/* NAMING RULES for a new compatible:
        "manufacturer,model"
        lowercase, no underscores
        the manufacturer prefix must be in
        Documentation/devicetree/bindings/vendor-prefixes.yaml
        include a version or SoC name if variants differ:
             "vendor,mysoc-v2-uart"                          */

How real device trees are organised

Real device trees are not one file. They are split so that the parts describing a chip can be shared by every board using it, with each board adding only what is specific to it — the same separation of concerns that makes one kernel binary work everywhere.

# arch/arm64/boot/dts/vendor/

  mysoc.dtsi          the SoC: every peripheral, addresses,
                      interrupts, clocks. status = "disabled"
                      for anything optional.
  mysoc-pinctrl.dtsi  pin configurations
  myboard-common.dtsi shared across a board family
  myboard-v1.dts      one board: which peripherals are wired,
                      which regulators, which GPIOs
  myboard-v2.dts

# A board file INCLUDES the SoC and then OVERRIDES:

/dts-v1/;
#include "mysoc.dtsi"

/ {
        model = "Vendor MyBoard v2";
        compatible = "vendor,myboard-v2", "vendor,mysoc";
};

&uart0 {
        status = "okay";                /* enable it */
        pinctrl-0 = <&uart0_pins>;
        pinctrl-names = "default";
};

&i2c1 {
        status = "okay";
        clock-frequency = <400000>;

        /* a device that only exists on THIS board */
        sensor@48 {
                compatible = "vendor,my-sensor";
                reg = <0x48>;
                interrupt-parent = <&gpio2>;
                interrupts = <7 IRQ_TYPE_EDGE_FALLING>;
                vdd-supply = <&reg_3v3>;
                reset-gpios = <&gpio1 12 GPIO_ACTIVE_LOW>;
                vendor,sample-rate-hz = <100>;
        };
};

# THE PATTERN: the SoC .dtsi describes what the SILICON has,
# all disabled. Each board .dts enables what is actually wired
# and adds what is on the board. That separation is why one
# .dtsi supports dozens of products.

Reading properties in a driver

Everything above exists so your driver can read values out of it. In practice you rarely parse the tree yourself; the resource helpers do it for you, and you reach for these functions only for properties that are genuinely specific to your device.

/* Prefer the FIRMWARE-AGNOSTIC device_property_* API - it
   works for DT and ACPI alike: */

        u32 val;
        ret = device_property_read_u32(dev, "vendor,fifo-depth",
                                       &val);
        if (ret)
                val = 16;               /* default */

        u32 array[4];
        device_property_read_u32_array(dev, "vendor,thresholds",
                                       array, 4);

        const char *mode;
        device_property_read_string(dev, "vendor,mode", &mode);

        if (device_property_read_bool(dev, "vendor,invert"))
                d->invert = true;
        /* a BOOLEAN in DT is PRESENCE, not a value. Writing
           `vendor,invert = <0>;` still reads as TRUE.      */

        int n = device_property_count_u32(dev, "vendor,list");

/* THE OF-SPECIFIC API, when you need node relationships: */
        struct device_node *np = dev->of_node;
        struct device_node *child;

        for_each_available_child_of_node(np, child) {
                /* iterate sub-nodes - channels, ports, ... */
                of_property_read_u32(child, "reg", &idx);
                ...
                /* of_node_put(child) is handled by the macro
                   on normal exit, but you MUST call it if you
                   break out early:                          */
                if (error) {
                        of_node_put(child);
                        break;
                }
        }

        struct device_node *other;
        other = of_parse_phandle(np, "vendor,partner", 0);
        ...
        of_node_put(other);             /* REFCOUNTED - leaking
                                           these is a real bug */

/* CUSTOM PROPERTY NAMING: always prefix with your vendor
   string. "fifo-depth" may collide with a future standard
   property; "vendor,fifo-depth" cannot.                    */

Bindings: the contract

A binding is the written specification of what properties your device node accepts and what they mean. It is a real contract: once a binding ships, device trees in the field depend on it, and it can no longer be changed freely — which is why maintainers review bindings more carefully than driver code.

# Documentation/devicetree/bindings/.../vendor,my-device.yaml
# A new binding MUST come with the driver, in YAML, and it is
# machine-checked.

%YAML 1.2
---
$id: http://devicetree.org/schemas/misc/vendor,my-device.yaml#
$schema: http://devicetree.org/meta-schemas/core.yaml#

title: Vendor My Device

maintainers:
  - Your Name <you@example.com>

properties:
  compatible:
    enum:
      - vendor,my-device
      - vendor,my-device-v2

  reg:
    maxItems: 1

  interrupts:
    maxItems: 1

  clocks:
    maxItems: 1

  vendor,fifo-depth:
    $ref: /schemas/types.yaml#/definitions/uint32
    enum: [8, 16, 32, 64]
    default: 16
    description: Depth of the hardware FIFO in entries.

required:
  - compatible
  - reg
  - interrupts
  - clocks

additionalProperties: false

examples:
  - |
    device@1c000000 {
        compatible = "vendor,my-device";
        reg = <0x1c000000 0x1000>;
        interrupts = <0 42 4>;
        clocks = <&clk 3>;
        vendor,fifo-depth = <32>;
    };

# CHECK IT:
    make dt_binding_check DT_SCHEMA_FILES=vendor,my-device.yaml
    make dtbs_check                # every dtb against every
                                   # schema - run this
    pip install dtschema           # needed for the above
A binding is a permanent ABI

Once a device tree using your property ships in a product or a bootloader, you cannot change its meaning. Old device trees must keep working with new kernels — that is why dtbs_check exists and why maintainers review bindings more carefully than driver code. Design the properties before you write the driver, not after.

Inspecting and debugging

When a driver does not bind, the device tree is the first suspect, and you do not have to guess. The tree as the running kernel actually parsed it is visible at runtime, which settles most questions in seconds.

# The live tree, as the running kernel sees it:
    ls /proc/device-tree/
    cat /proc/device-tree/model
    hexdump -C /proc/device-tree/soc/serial@1c000000/reg
    # or, much better:
    dtc -I fs -O dts /proc/device-tree > live.dts

# Compile and decompile:
    dtc -I dts -O dtb -o my.dtb my.dts
    dtc -I dtb -O dts my.dtb > readable.dts   # what ACTUALLY
                                              # got built,
                                              # after includes
# ALWAYS decompile after building. The result of #include and
# override chains is frequently not what you intended, and
# reading the flattened output takes ten seconds.

# Preprocess only, to debug an include problem:
    cpp -nostdinc -I include -undef -x assembler-with-cpp \
        my.dts | less

# Which devices exist and what bound:
    ls /sys/firmware/devicetree/base/
    ls /sys/bus/platform/devices/
    cat /sys/kernel/debug/devices_deferred

# OVERLAYS - patch the tree at runtime, for add-on boards:
    /dts-v1/;
    /plugin/;
    &{/soc/i2c@1c001000} {
            sensor@48 { compatible = "vendor,my-sensor";
                        reg = <0x48>; };
    };
    dtc -@ -I dts -O dtb -o overlay.dtbo overlay.dts
    # applied by the bootloader, or via configfs where
    # CONFIG_OF_OVERLAY and a suitable interface exist
