The one-time pad and perfect secrecy

The only cipher that is provably unbreakable, why it is almost never usable, and what happens when the "one-time" part is violated. Understanding this fixes the intuition for every stream cipher that follows.

The construction

There is exactly one cipher with mathematically proven, unconditional security — it cannot be broken by any amount of computation. Understanding why establishes the standard everything else is measured against.

   KEY: a truly random sequence, AS LONG AS THE MESSAGE,
        used exactly ONCE, known only to both parties.

   ENCRYPT:  c = p XOR k
   DECRYPT:  p = c XOR k

   because  (p XOR k) XOR k = p

   plaintext   0 1 1 0  1 0 0 1
   key         1 1 0 1  0 1 1 0
   ciphertext  1 0 1 1  1 1 1 1

   THE CLAIM, proved by Shannon in 1949:

     For any ciphertext c and any candidate plaintext p' of
     the same length, there EXISTS a key k' = c XOR p' that
     produces it.

     Since every key is equally likely, every plaintext of
     that length is EQUALLY LIKELY given the ciphertext.

     The ciphertext therefore conveys ZERO information about
     the plaintext beyond its length.

   PERFECT SECRECY: P(plaintext | ciphertext)
                  = P(plaintext)

   This holds against an adversary with UNLIMITED
   computation - no future computer, no quantum algorithm,
   no mathematical advance changes it. It is the only cipher
   with that property.

   AND THE COST OF IT: Shannon also proved that perfect
   secrecy REQUIRES a key at least as long as the message.
   That is not an artefact of this construction; it is a
   lower bound. Which is why every practical cipher settles
   for COMPUTATIONAL security instead.

Why it is unusable

Given a provably unbreakable cipher exists, the obvious question is why nobody uses it. The answer is entirely practical, and the constraints that make it unusable are worth stating precisely.

/* THE FOUR REQUIREMENTS, and each one is a practical
   problem: */

   1. THE KEY MUST BE AS LONG AS THE MESSAGE.
      To send a gigabyte you need a gigabyte of key. But you
      must already have shared that key securely - and if you
      have a secure channel for a gigabyte of key, you could
      have sent the message on it.

   2. THE KEY MUST BE TRULY RANDOM.
      Not a PRNG (chapter 02). Real physical entropy, in the
      quantity above. Generating and storing that is itself a
      significant engineering problem.

   3. THE KEY MUST BE USED EXACTLY ONCE.
      See below - reuse is catastrophic, not merely
      weakening.

   4. THE KEY MUST BE DESTROYED AFTER USE.
      A stored key is a stored plaintext.

/* AND WHAT IT DOES NOT PROVIDE, which is the point people
   miss:

     NO INTEGRITY. XOR is linear (chapter 01), so flipping a
     ciphertext bit flips the plaintext bit. An attacker who
     knows the plaintext format can make arbitrary
     predictable changes without knowing the key at all.

     Perfect CONFIDENTIALITY, zero AUTHENTICITY. A one-time
     pad still needs a MAC.

/* WHERE IT IS ACTUALLY USED:
     · diplomatic and intelligence traffic, historically -
       the Moscow-Washington hotline used them
     · numbers stations broadcasting to agents with printed
       pads
     · quantum key distribution, where the physics provides
       the key material
   In every case the key distribution problem was solved by
   physical means - couriers, printed booklets, a fibre - and
   the volume was tiny.                                    */
The lesson that generalises

Every stream cipher — RC4, ChaCha20, AES-CTR — is a one-time pad in which the long random key is replaced by a keystream generated from a short key. That substitution is what makes it practical, and it means every one of them inherits the one-time pad's properties: keystream reuse is catastrophic, and there is no integrity. Both facts follow directly from this chapter, and both are responsible for real breaks (chapter 06).

The two-time pad

Using the same one-time pad twice destroys its security completely and recoverably — the failure is not gradual. This exact mistake reappears constantly in modern systems as nonce reuse, which is the same error wearing different clothes.

/* Use the same key twice and perfect secrecy collapses
   completely. */

        c1 = p1 XOR k
        c2 = p2 XOR k

        c1 XOR c2 = (p1 XOR k) XOR (p2 XOR k)
                  = p1 XOR p2          /* THE KEY CANCELS */

/* The attacker now has the XOR of two plaintexts, with no
   key involved. That is enough:

     · if either plaintext is known, the other falls out
       immediately
     · if both are English text, CRIB DRAGGING recovers them:
       guess a common word at some offset, XOR it in, and see
       whether the result at that offset in the other message
       is plausible text. Iterate.
     · with several messages under the same keystream, it is
       nearly trivial - the statistical structure of natural
       language does the work
     · with structured data - a protocol with fixed headers -
       it is immediate

/* THE HISTORICAL CASE: the VENONA project. Soviet one-time
   pads were duplicated during wartime production pressure.
   US cryptanalysts exploited the reuse to read thousands of
   messages over four decades. The cipher was perfect; the
   procedure was not.

/* AND THE MODERN CASES, all the same mathematics:
     · WEP reused IVs after 2^24 packets, and often much
       sooner
     · MS-PPTP reused the RC4 keystream in both directions
     · TLS implementations that reused a GCM nonce
     · a device with a fixed IV compiled into the firmware -
       common in IoT

/* SO THE RULE, which applies to every stream cipher and
   every counter mode:

     NEVER REUSE A KEY-AND-NONCE PAIR. The nonce need not be
     secret or random, but it must be UNIQUE for the lifetime
     of the key (chapter 02).                            */

Computational security

Since unconditional security is impractical, real cryptography settles for a weaker but sufficient guarantee: secure against any attacker with realistic computational resources. That shift is what the rest of the track is built on.

/* Since perfect secrecy demands an impractical key, every
   real cipher settles for something weaker but sufficient. */

   PERFECT SECRECY
     an adversary with UNLIMITED computation learns nothing.
     Requires |key| >= |message|.

   COMPUTATIONAL SECURITY
     an adversary with BOUNDED computation - say 2^128
     operations - learns nothing useful.
     Allows a short key and an arbitrarily long message.

/* THE TRADE IS OVERWHELMINGLY WORTH IT: 2^128 operations is
   not merely impractical but physically impossible
   (chapter 01), and a 256-bit key encrypts a terabyte.

/* WHAT COMPUTATIONAL SECURITY RESTS ON:
     · that certain problems are hard - factoring, discrete
       log, or that AES behaves like a random permutation
     · NONE of these are PROVEN hard. They are believed hard
       because they have resisted concerted attack for
       decades.
     · P versus NP is unresolved; if P = NP, most of
       cryptography fails.

/* SO THE HONEST STATEMENT: modern cryptography is secure
   because nobody has found a way to break it, not because
   nobody can. That is a weaker claim than the one-time pad's
   and it is the best available for anything practical.

/* THE SEMANTIC SECURITY DEFINITION, which is the modern
   formalisation:

     An adversary chooses two plaintexts of equal length. One
     is encrypted at random. The adversary cannot do better
     than guessing which.

   This is IND-CPA (chapter 01), and it has a direct
   consequence: encryption MUST BE RANDOMISED. A
   deterministic cipher fails immediately, because the
   adversary encrypts one candidate themselves and compares.
   That is why every mode needs an IV or nonce, and why ECB
   (chapter 05) is broken.                                */

Related "perfect" properties

If a long-term key is eventually compromised, does that expose traffic recorded years earlier? Whether the answer is no depends on a property that must be designed in, and it is the reason modern protocols negotiate ephemeral keys.

/* Two other properties use the word, and neither is perfect
   secrecy. */

/* --- FORWARD SECRECY (sometimes "perfect forward
       secrecy") --- */
/* Compromising a long-term key does NOT reveal past session
   traffic, because each session used an EPHEMERAL key that
   was discarded.

     RSA key transport      NO forward secrecy - recover the
                            server's private key and every
                            recorded session decrypts
     ECDHE                  YES - the ephemeral keys are
                            discarded after the handshake

   THIS IS WHY TLS 1.3 REMOVED static RSA key exchange
   entirely (chapter 17). "Harvest now, decrypt later" is a
   real adversary model, and forward secrecy is the defence.

/* --- POST-COMPROMISE SECURITY (self-healing) --- */
/* After a compromise ENDS, security is RESTORED - because
   the parties ratchet to new keys. The Signal protocol's
   double ratchet provides it; TLS does not.

/* NEITHER IS PERFECT SECRECY. Both are computational
   properties about WHICH keys are exposed by a compromise,
   not about an unbounded adversary.

/* AND THE RELATED CONSTRUCTION worth knowing - SECRET
   SHARING, which does achieve information-theoretic
   security: */
        split a secret s into n shares
        any k shares reconstruct s
        any k-1 shares reveal NOTHING - information-
        theoretically

/* Shamir's scheme: pick a random degree-(k-1) polynomial
   with s as the constant term; the shares are points on it.
   k points determine the polynomial; k-1 leave every
   constant term equally likely - the same argument as the
   one-time pad.

   USED FOR: splitting a root key across several HSMs or
   people, so no one person can use it. Genuinely practical,
   unlike the one-time pad, because the secret is small.  */

How it shows up

SymptomCause
Two ciphertexts XOR to readable textKeystream reuse — the two-time pad
Known plaintext reveals another messageThe same
A fixed IV in the firmwareEvery message uses the same keystream
Ciphertext modified undetectablyNo integrity — XOR is linear (ch. 01)
Same plaintext gives same ciphertextDeterministic encryption — fails IND-CPA
Recorded traffic decrypted after a key leakNo forward secrecy — static key exchange
"We use a one-time pad" in a productAlmost certainly a stream cipher with a reused key
Nonce counter resets after a reflashReuse across the reset — rotate the key instead
