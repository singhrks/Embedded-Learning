The TEE software stack and OP-TEE

Six pieces of software cooperate to run one trusted operation. This chapter names every one of them, follows a single request through all six, and gets OP-TEE running on QEMU so you can watch it happen.

The whole stack

A trusted execution environment is a full software stack rather than a single component, spanning both worlds. Knowing which piece lives where is what makes the call flow comprehensible.

   NORMAL WORLD                        SECURE WORLD
   ============                        ============

   your application                    Trusted Application
        |  libteec                         |  TA framework
        |  (GlobalPlatform Client API)     |  (GP Internal API)
        v                                  ^
   +----------------+                 +----+-------------+
   | tee-supplicant |                 |   OP-TEE OS      |  S-EL1
   | (daemon, EL0)  |                 |   (trusted OS)   |
   +--------+-------+                 +----+-------------+
            |  RPC                          ^
            v                                |
   +----------------------+                  |
   | optee driver         |  EL1             |
   | drivers/tee/optee    |                  |
   +----------+-----------+                  |
              |  SMC                         |
              v                              |
   +-----------------------------------------+------------+
   |  TF-A  BL31 - the secure monitor              EL3     |
   +-------------------------------------------------------+

   Six pieces, each with one job:

   1. your app        wants a secret operation performed
   2. libteec         turns API calls into ioctls on /dev/tee0
   3. optee driver    turns ioctls into SMCs, manages shared memory
   4. TF-A BL31       switches worlds
   5. OP-TEE OS       schedules and isolates trusted applications
   6. the TA          does the actual work

   plus tee-supplicant, off to the side, servicing RPC requests
   the secure world cannot perform for itself (chapter 11).

The GlobalPlatform APIs

Standard APIs exist for both the client and the trusted-application sides, which is what allows a trusted application to be portable between TEE implementations rather than tied to one vendor.

/* Two standard APIs, one on each side of the boundary. Learn
   these and your knowledge transfers between OP-TEE, Trusty,
   QSEE and Kinibi.                                          */

/* --- CLIENT API, normal world, libteec ------------------- */

   TEEC_InitializeContext()   connect to the TEE
   TEEC_OpenSession()         start talking to a TA (by UUID)
   TEEC_InvokeCommand()       ask it to do something
   TEEC_CloseSession()
   TEEC_FinalizeContext()
   TEEC_RegisterSharedMemory()  register your own buffer
   TEEC_AllocateSharedMemory()  or let the TEE allocate one

/* --- INTERNAL API, secure world, inside the TA ----------- */

   TA_CreateEntryPoint()          once, when the TA is loaded
   TA_OpenSessionEntryPoint()     per client session
   TA_InvokeCommandEntryPoint()   per command  <- the real work
   TA_CloseSessionEntryPoint()
   TA_DestroyEntryPoint()

   TEE_AllocateOperation()        crypto
   TEE_CipherInit/Update/DoFinal()
   TEE_DigestDoFinal()
   TEE_AsymmetricSignDigest()
   TEE_GenerateRandom()
   TEE_DeriveKey()

   TEE_CreatePersistentObject()   secure storage (chapter 13)
   TEE_OpenPersistentObject()
   TEE_ReadObjectData()

   TEE_Malloc/Free()              heap, inside the TA
   TEE_CheckMemoryAccessRights()  IS this pointer safe to touch?
   TEE_Panic()                    give up loudly

The parameter model

How arguments cross the boundary is the most security-sensitive part of the interface, because it is where untrusted data enters trusted code. The parameter model constrains that deliberately.

/* Every invocation carries FOUR parameter slots. Each slot is
   either a VALUE (two 32-bit numbers) or a MEMREF (a shared
   buffer), and each has a direction.                        */

   TEEC_NONE
   TEEC_VALUE_INPUT        a.b: two u32 in
   TEEC_VALUE_OUTPUT       two u32 out
   TEEC_VALUE_INOUT
   TEEC_MEMREF_TEMP_INPUT      a buffer, registered for this call
   TEEC_MEMREF_TEMP_OUTPUT
   TEEC_MEMREF_TEMP_INOUT
   TEEC_MEMREF_WHOLE           a pre-registered shared memory
   TEEC_MEMREF_PARTIAL_INPUT   part of a pre-registered one
   TEEC_MEMREF_PARTIAL_OUTPUT
   TEEC_MEMREF_PARTIAL_INOUT

/* Packed into one word: */
   op.paramTypes = TEEC_PARAM_TYPES(TEEC_VALUE_INPUT,
                                    TEEC_MEMREF_TEMP_OUTPUT,
                                    TEEC_NONE,
                                    TEEC_NONE);

/* And the TA MUST check that it got what it expected: */

TEE_Result TA_InvokeCommandEntryPoint(void *sess, uint32_t cmd,
                                      uint32_t ptypes,
                                      TEE_Param params[4])
{
        uint32_t exp = TEE_PARAM_TYPES(TEE_PARAM_TYPE_VALUE_INPUT,
                                       TEE_PARAM_TYPE_MEMREF_OUTPUT,
                                       TEE_PARAM_TYPE_NONE,
                                       TEE_PARAM_TYPE_NONE);

        if (ptypes != exp)
                return TEE_ERROR_BAD_PARAMETERS;   /* not optional */
        ...
}

/* Skipping that check means the client can pass a VALUE where
   you expect a MEMREF. You then read params[1].memref.buffer -
   which is now an arbitrary 64-bit number the attacker chose,
   dereferenced by the most privileged code in the system.

   This is the single most common OP-TEE TA vulnerability
   class.                                                   */
Every buffer from the client is hostile

A MEMREF points into non-secure shared memory. The client can change its contents at any moment, including between your bounds check and your read — and on another CPU it does not even need your call to return first.

  • Check params[i].memref.size before trusting it, and check it against what you will actually write.
  • Call TEE_CheckMemoryAccessRights() to confirm the buffer is where it claims to be.
  • Copy the input into TA-local memory, then validate the copy, then use only the copy.
  • Write outputs once, at the end. Never use the shared buffer as scratch space.
  • Never place a secret in an output buffer before deciding the caller is entitled to it.

One request, end to end

Following one client call from an application, through the kernel driver, across the world switch and into a trusted application ties every layer together — and it is the path you will trace when debugging.

app: TEEC_InvokeCommand(&sess, CMD_SIGN, &op, &origin)
  |
  v
libteec: build struct tee_ioctl_invoke_arg, translate the
         parameters, ioctl(fd, TEE_IOC_INVOKE, &arg)
  |
  v
optee driver (optee_invoke_func):
     get a free "call queue" entry
     translate each MEMREF: virtual -> the shared-memory cookie
       and physical address the secure world understands
     fill an optee_msg_arg in the shared memory pool
     arm_smccc_smc(OPTEE_SMC_CALL_WITH_ARG, msg_pa, ...)
  |
  v
TF-A BL31: save NS context, SCR_EL3.NS = 0, restore secure
           context, ERET to S-EL1
  |
  v
OP-TEE OS:
     entry from the monitor, pick the thread for this call
     find the session, find the TA
     is the TA loaded? -> if not, RPC to tee-supplicant to
                          fetch it, VERIFY ITS SIGNATURE, map it
     map the shared buffers into the TA's address space,
       NON-SECURE, non-executable
     drop to S-EL0 and call TA_InvokeCommandEntryPoint
  |
  v
TA: validate ptypes, copy input in, do the crypto with a key
    it derived from the HUK, write the result out, return
  |
  v
OP-TEE OS: unmap the buffers, set the return code, SMC back
  |
  v
TF-A BL31: save secure context, SCR_EL3.NS = 1, restore NS,
           ERET to Linux
  |
  v
optee driver: copy results back into the ioctl arg, return
  |
  v
libteec: fill in op.params, set return origin, return
  |
  v
app: TEEC_SUCCESS

  Two privilege boundaries crossed in each direction
  (S-EL0/S-EL1 and the world switch), plus a possible RPC
  excursion in the middle.

Where a TA runs

TypeRuns atLoaded fromUse for
User-mode TAS-EL0Signed .ta file, fetched by RPCAlmost everything — isolated, crashable, updatable
Early TAS-EL0Linked into the OP-TEE binaryNeeded before the filesystem exists
Pseudo TAS-EL1, inside the kernelCompiled inOnly when it truly needs kernel privilege
Secure partitionS-EL1 under S-EL2FF-A manifestMutually distrusting secure components
A pseudo TA has no memory protection at all

It runs in the trusted OS's own address space, at S-EL1, with full access to secure memory and every system register. A buffer overflow in a pseudo TA is not a crash — it is total compromise of the secure world. Write a user-mode TA unless you can state exactly which S-EL1-only operation forces your hand.

How OP-TEE isolates TAs

Trusted applications must be isolated from each other as well as from the normal world, because a compromise of one should not yield the keys of another.

/* Each user-mode TA gets:

     its own S-EL0 address space, with its own translation
       tables and its own ASID
     its own heap and stack, sized by its manifest
     no access to another TA's memory
     no access to OP-TEE OS memory
     no MMIO mappings unless explicitly granted
     no way to execute privileged instructions

   So the isolation model inside the secure world mirrors
   user/kernel in Linux (OS chapters 4 and 12) - and for the
   same reason. A trusted application is trusted RELATIVE TO
   THE NORMAL WORLD, not absolutely.                        */

/* A TA declares its needs in a header: */

#define TA_UUID  { 0x8aaaf200, 0x2450, 0x11e4, \
                 { 0xab, 0xe2, 0x00, 0x02, 0xa5, 0xd5, 0xc5, 0x1b } }

#define TA_FLAGS                (TA_FLAG_EXEC_DDR | \
                                 TA_FLAG_SINGLE_INSTANCE | \
                                 TA_FLAG_MULTI_SESSION)
#define TA_STACK_SIZE           (2 * 1024)
#define TA_DATA_SIZE            (32 * 1024)

/* SINGLE_INSTANCE  one copy shared by all clients
   MULTI_SESSION    several concurrent sessions allowed
   INSTANCE_KEEP_ALIVE   stays resident after the last session
   SECURE_DATA_PATH      may touch secure buffers (video, DRM)

   Ask for the SMALLEST stack and heap that work. The secure
   world's memory is a scarce, permanently carved-out resource
   (chapter 10), not Linux's elastic pool.                   */

The thread model

The secure world has a limited number of execution contexts, and exhausting them is a real failure mode with real denial-of-service consequences for the normal world.

/* OP-TEE has a FIXED number of threads - CFG_NUM_THREADS,
   typically 2 to 8, often one per CPU.

   Each concurrent secure call occupies one. When they are all
   busy the SMC returns OPTEE_SMC_RETURN_ETHREAD_LIMIT and the
   Linux driver puts the caller to sleep until one frees.

   CONSEQUENCES:
     - the secure world does not scale to hundreds of concurrent
       clients; it is not a server
     - a TA that blocks holds a thread the whole time
     - an RPC excursion also holds its thread - the normal world
       is servicing a request from a thread that is still
       "inside" the secure world
     - deadlock is possible: all threads waiting on an RPC that
       needs a thread to complete. This is why tee-supplicant
       must never itself call into the TEE.                  */

/* Each thread has a fixed stack, typically 8 KB. Deep recursion
   or a large local array in a pseudo TA overflows it, and the
   result is a secure-world crash with a stack dump on the
   console - which on production silicon you cannot see
   (chapter 10).                                            */

Hands-on: OP-TEE on QEMU

The whole stack runs under emulation, which makes it possible to experiment with a real TEE without any specialised hardware.

# The complete stack - TF-A, OP-TEE, Linux, buildroot, the test
# suite - built from one manifest. Budget an hour and ~20 GB.

mkdir -p ~/optee && cd ~/optee
repo init -u https://github.com/OP-TEE/manifest.git -m qemu_v8.xml
repo sync -j8
cd build
make toolchains -j4
make run -j$(nproc)

# Three windows open: QEMU's own console, a "Normal World" UART
# and a "Secure World" UART. In the QEMU console:
(qemu) c

# Log in as root in the normal world, then:
xtest                     # the full GlobalPlatform test suite
xtest -l 0                # quick pass
optee_example_hello_world # the smallest complete example

# WATCH THE SECURE CONSOLE while these run. Every TA load,
# every panic and every trace line appears there. That split -
# normal-world output in one window, secure-world in another -
# is exactly the boundary this track is about.
Read optee_example_hello_world before writing anything

It is about 120 lines across the two sides: host/main.c does InitializeContext / OpenSession / InvokeCommand, and ta/hello_world_ta.c implements the five entry points. Every TA you ever write has that skeleton. Copy the optee_examples directory structure rather than inventing a build.
