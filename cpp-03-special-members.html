Construction, destruction and the rule of zero/three/five

Six functions the compiler may generate for you, and the rules about when it does. Getting these wrong is how an RAII class silently double-frees a resource — and the correct answer is usually to write none of them.

The six special members

The compiler may generate six member functions for you, and whether it does depends on what else you declared. Most surprising C++ behaviour around copying and moving traces back to this table.

class Widget {
public:
        Widget();                               /* 1. default
                                                   constructor */
        ~Widget();                              /* 2. destructor */
        Widget(const Widget&);                  /* 3. copy ctor */
        Widget& operator=(const Widget&);       /* 4. copy
                                                   assignment  */
        Widget(Widget&&) noexcept;              /* 5. move ctor */
        Widget& operator=(Widget&&) noexcept;   /* 6. move
                                                   assignment  */
};

/* THE COMPILER GENERATES THESE IMPLICITLY, but the rules for
   WHEN are subtle and consequential:

   DEFAULT CONSTRUCTOR
        generated if you declare NO constructor at all.
        Declare any constructor and it disappears.

   DESTRUCTOR
        always generated unless you declare one.

   COPY CONSTRUCTOR and COPY ASSIGNMENT
        generated unless you declare a MOVE operation.
        DEPRECATED if you declare a destructor or the other
        copy operation - it still happens, with a warning.

   MOVE CONSTRUCTOR and MOVE ASSIGNMENT
        generated ONLY IF you declare NONE of: a destructor,
        either copy operation, or the other move operation.

   THE LAST RULE IS THE TRAP. Write a destructor - which every
   RAII class does - and you SILENTLY LOSE the move
   operations. Your class then falls back to COPYING, which
   for a resource-owning class is exactly wrong.         */
The default copy is a shallow copy 
class FileHandle {
        int fd_;
public:
        explicit FileHandle(const char *p) : fd_(open(p, O_RDONLY)) {}
        ~FileHandle() { close(fd_); }
        /* copy operations are IMPLICITLY GENERATED, and copy
           fd_ verbatim */
};

        FileHandle a("/dev/thing");
        FileHandle b = a;       /* both hold the SAME fd */
        /* both destructors run -> close(fd) TWICE.
           The second close may close a DIFFERENT file that
           reused the descriptor number. */

This is the single most common C++ resource bug, and it is silent: no warning, correct-looking code, corruption at a distance. The fix is one of the three rules below.

The three rules

Declaring one of the six suppresses others, in a pattern that is easy to get wrong by accident. The conventional rules exist to keep you on the safe side of it.

/* ---- RULE OF ZERO: the one to aim for ------------------ */
/* If your class has no raw resources, declare NONE of the six
   and let the compiler generate all of them correctly.    */

class Sensor {
        std::unique_ptr<Device> dev_;   /* handles its own
                                           lifetime */
        std::array<uint8_t, 64> buf_;   /* trivially copyable */
        std::string name_;              /* handles its own */
public:
        /* NOTHING. Move works, copy is correctly deleted
           (because unique_ptr is non-copyable), destruction
           is correct.                                      */
};

/* THIS IS THE GOAL. Push resource ownership into members
   that already do it right, and the enclosing class needs no
   special members at all.

/* ---- RULE OF FIVE: when you own a raw resource --------- */
class Buffer {
        uint8_t *data_ = nullptr;
        size_t   size_ = 0;

public:
        explicit Buffer(size_t n)
                : data_(new uint8_t[n]), size_(n) {}

        ~Buffer() { delete[] data_; }

        /* copy: DEEP */
        Buffer(const Buffer& o)
                : data_(new uint8_t[o.size_]), size_(o.size_)
        {
                std::copy_n(o.data_, size_, data_);
        }

        Buffer& operator=(const Buffer& o)
        {
                if (this == &o) return *this;   /* SELF-
                                                   ASSIGNMENT */
                uint8_t *p = new uint8_t[o.size_];  /* allocate
                                                       FIRST  */
                std::copy_n(o.data_, o.size_, p);
                delete[] data_;                 /* then release */
                data_ = p;
                size_ = o.size_;
                return *this;
        }

        /* move: STEAL */
        Buffer(Buffer&& o) noexcept
                : data_(o.data_), size_(o.size_)
        {
                o.data_ = nullptr;      /* leave it DESTRUCTIBLE */
                o.size_ = 0;
        }

        Buffer& operator=(Buffer&& o) noexcept
        {
                if (this == &o) return *this;
                delete[] data_;
                data_ = o.data_;
                size_ = o.size_;
                o.data_ = nullptr;
                o.size_ = 0;
                return *this;
        }
};

/* THE TWO NON-OBVIOUS REQUIREMENTS:
     1. SELF-ASSIGNMENT must work. `x = x` happens through
        references and aliases more often than you expect.
     2. THE MOVED-FROM OBJECT must be left in a valid,
        destructible state. Not "correct" - just safe to
        destroy and safe to assign to.

/* ---- RULE OF THREE: pre-C++11 ------------------------- */
/* Destructor, copy constructor, copy assignment. If you need
   one, you need all three. Still true; the rule of five just
   adds the move pair.                                     */

Saying what you mean

You can ask for the compiler's version explicitly or forbid it entirely, and both are better than leaving it implicit — because "implicit" depends on rules that change as the class grows.

/* `= default` and `= delete` make intent explicit and
   checkable.                                               */

/* --- MOVE-ONLY, the right shape for most resource types --- */
class FileHandle {
        int fd_ = -1;
public:
        explicit FileHandle(const char *p) : fd_(open(p, O_RDONLY)) {}
        ~FileHandle() { if (fd_ >= 0) close(fd_); }

        FileHandle(const FileHandle&)            = delete;
        FileHandle& operator=(const FileHandle&) = delete;

        FileHandle(FileHandle&& o) noexcept : fd_(o.fd_)
                { o.fd_ = -1; }
        FileHandle& operator=(FileHandle&& o) noexcept
        {
                if (this != &o) {
                        if (fd_ >= 0) close(fd_);
                        fd_ = o.fd_;
                        o.fd_ = -1;
                }
                return *this;
        }

        int get() const { return fd_; }
};
/* Now `FileHandle b = a;` is a COMPILE ERROR, not a
   double-close. That is the whole point.

/* --- NON-COPYABLE, NON-MOVABLE: a scope guard ----------- */
class InterruptLock {
public:
        InterruptLock();
        ~InterruptLock();
        InterruptLock(const InterruptLock&)            = delete;
        InterruptLock& operator=(const InterruptLock&) = delete;
        /* declaring the copy ops suppresses the move ops too */
};

/* --- BRINGING BACK A DEFAULT that was suppressed --------- */
class C {
public:
        C(int x);               /* suppresses the default ctor */
        C() = default;          /* bring it back */
        ~C() = default;
        C(C&&) = default;       /* and the moves, which the
        C& operator=(C&&) = default;   destructor suppressed */
};

/* --- AND FOR A BASE CLASS with virtual functions
       (chapter 11) --- */
        virtual ~Base() = default;
/* A polymorphic base needs a VIRTUAL destructor, or deleting
   through a Base* does not run the derived destructor. And
   declaring it suppresses the moves, so default them
   explicitly if you want them.                          */
noexcept on move operations is not decoration

std::vector reallocating chooses between moving and copying its elements based on whether the move constructor is noexcept — because if a move can throw partway through, the vector cannot restore its previous state. A move constructor that is not marked noexcept causes vector growth to copy every element instead. That is a large, silent performance loss, and the fix is one keyword.

Construction and destruction order

Construction and destruction happen in a strictly defined order — bases before members, and destruction exactly in reverse. Code that depends on a different order works by luck.

class Derived : public Base {
        Member1 m1_;
        Member2 m2_;
public:
        Derived() : Base(), m1_(), m2_() { /* body */ }
};

/* CONSTRUCTION ORDER:
     1. base classes, in declaration order
     2. members, in DECLARATION order
     3. the constructor body

   DESTRUCTION IS EXACTLY REVERSED:
     1. the destructor body
     2. members, in reverse declaration order
     3. base classes, in reverse

   WHICH MEANS: a member declared later may safely depend on
   one declared earlier, and not the other way round. Order
   the declarations to match the dependencies.

/* CALLING A VIRTUAL FUNCTION IN A CONSTRUCTOR: */
class Base {
public:
        Base() { init(); }              /* calls BASE::init */
        virtual void init() { }
};
class Derived : public Base {
        int *p_;
public:
        Derived() : p_(new int) { }
        void init() override { *p_ = 1; }   /* NEVER CALLED
                                               from Base's
                                               ctor - and p_
                                               is not yet
                                               initialised
                                               anyway       */
};
/* During Base's constructor the object IS a Base; the vtable
   pointer has not yet been updated. Same in destructors.
   NEVER call a virtual function from a constructor or
   destructor - use two-phase init if you need it.       */

/* DESTRUCTION OF LOCALS is reverse of construction, which is
   exactly what RAII needs: */
        void f() {
                ClockGate  clk(CLK_UART);   /* 1st */
                Uart       uart(0x9000000); /* 2nd */
                ChipSelect cs(pin);         /* 3rd */
                ...
        }   /* cs released, then uart, then the clock -
               correct: the clock must outlive the device
               that needs it.                            */

Copy elision

The compiler is permitted, and in some cases required, to skip copies and moves entirely. That changes how many times constructors run, which matters if yours have side effects.

/* The compiler may - and since C++17 for some cases MUST -
   construct an object directly in its destination rather than
   constructing and copying.                                */

        Buffer make() {
                return Buffer(1024);    /* GUARANTEED elision
                                           since C++17: the
                                           object is
                                           constructed
                                           directly in the
                                           caller's storage */
        }
        Buffer b = make();      /* NO copy, NO move, not even
                                   a call to them            */

/* NAMED RETURN VALUE OPTIMISATION - allowed, not guaranteed:
*/
        Buffer make2() {
                Buffer b(1024);
                b.fill(0);
                return b;       /* NRVO usually elides */
        }

/* AND THE PESSIMISATION TO AVOID: */
        return std::move(b);    /* WORSE - the explicit move
                                   DEFEATS NRVO, forcing an
                                   actual move construction */
/* -Wpessimizing-move warns. Just `return b;` - the compiler
   already treats a returned local as an rvalue.

/* THE MECHANISM (compilers chapter 10): the caller passes a
   hidden pointer in x8, and the callee constructs the result
   there. So a "return by value" of a large object is one
   construction, in place - not a construct-then-copy.

   WHICH MEANS: returning by value is the right default, even
   for large types. The out-parameter idiom C requires is
   unnecessary in C++.                                    */

Checking your class

What the compiler actually generated is inspectable. When copy or move behaviour surprises you, looking directly is far faster than reasoning about the rules.
