The stored-program computer

The idea that a program is just data in the same memory as everything else is what makes a computer general-purpose — and it is also the root of buffer overflows, JIT compilers, self-modifying boot code and the entire W^X security model.

The problem

Chapters 05 and 06 give you an ALU and registers. You could wire them into a machine that computes one fixed function — a calculator. To change what it does, you would rewire it. Early machines like ENIAC were literally reprogrammed by moving cables, which took days.

The stored-program insight, credited to the 1945 EDVAC report and usually named after von Neumann, is: put the instructions in memory alongside the data. Then changing the program is just changing memory contents, which the machine can do itself.

The von Neumann model

The idea that makes a computer general-purpose rather than a fixed machine is startlingly simple: put the instructions in the same memory as the data. Everything from compilers to malware follows from that one decision.

Why PC is incremented during fetch, not after execute

By the time a branch executes, the PC already points at the following instruction. A branch simply overwrites it. This is why a "relative branch" offset is measured from the instruction after the branch, and it is why BL (branch with link) can save the return address by copying the already-incremented PC into the link register — no separate addition needed. Every quirk of branch encoding traces back to this ordering.

Harvard and the modified Harvard architecture

Von Neumann's single memory port is a bottleneck: an instruction fetch and a data access compete for the same bus every cycle. The Harvard architecture gives instructions and data separate memories and separate buses, so both happen simultaneously.

The consequence you will actually hit

Write instruction bytes into memory — a JIT compiler, a bootloader relocating code, a kernel patching an alternative instruction sequence, a debugger inserting a breakpoint — and those bytes sit in the data cache. The instruction cache and the prefetcher know nothing about them. Execute that address and you run stale instructions.

    /* the mandatory sequence after writing code, on ARM */
    dc      cvau, x0        /* clean D-cache to the point of unification  */
    dsb     ish             /* wait for it to complete                    */
    ic      ivau, x0        /* invalidate I-cache for that address        */
    dsb     ish             /* wait                                       */
    isb                     /* flush already-prefetched stale instructions*/

Covered in full in ARM chapter 18. Every self-modifying mechanism on the platform depends on getting this exactly right.

W^X: taking the generality back

That last row is the problem. If an attacker can write bytes into a buffer and then redirect execution to it, the stored-program property is the vulnerability. The defence is to make memory writable XOR executable, never both, enforced by the MMU:

RegionPermissionsEnforced by
.text (code)Read + Execute, not WritePage table AP bits
.rodataRead onlyPage table AP bits
.data, .bss, heap, stackRead + Write, never ExecutePage table UXN/PXN bits

Related hardware mitigations, all of which exist because of this chapter's central idea:

  • PXN / UXN — privileged/unprivileged execute-never bits in ARM page descriptors.
  • PAN — Privileged Access Never: the kernel cannot accidentally dereference a user pointer without explicitly enabling access.
  • BTI — Branch Target Identification: an indirect branch may only land on a BTI instruction, which breaks jump-oriented programming.
  • Pointer authentication — signs return addresses so a corrupted stack cannot redirect a return.

A JIT compiler must therefore map a page writable, emit code, then remap it executable — never holding both permissions at once. Apple platforms enforce this so strictly that they provide a dedicated API for the transition.

The memory wall

Von Neumann's single path to memory has a second consequence, and it has grown into the dominant performance constraint in computing.

Relative improvement since ~1980

  CPU speed     ████████████████████████████████████  ~50,000×
  DRAM latency  ███                                   ~10×

The gap is the "von Neumann bottleneck" or "memory wall".
A DRAM access costs 100-300 CPU cycles. The processor is not
compute-limited; it is waiting.

Everything in chapters 13-15 — caches, prefetching, the whole memory
hierarchy — exists to hide this one number.
Why this matters for AI workloads

Large language model inference is almost entirely memory-bandwidth-bound, not compute-bound: generating each token requires streaming the entire weight matrix through the arithmetic units, and every weight is used exactly once. This is why quantisation (making the weights smaller) speeds up inference far more than a faster multiplier would, and why accelerators are designed around memory bandwidth. See AI chapter 26.
