RSA

The first practical public-key system, still everywhere in firmware signing and PKI, and the one whose textbook description is dangerously incomplete. The padding is not a detail — it is most of the security.

The core operation

The mathematical core of RSA is short enough to write in a few lines, and that simplicity is deceptive — everything difficult about RSA is in the padding and the implementation rather than the equation.

   KEY GENERATION
     1. pick two large random primes p, q  (1024 bits each
        for a 2048-bit key)
     2. n = p * q                    the MODULUS, public
     3. λ(n) = lcm(p-1, q-1)
     4. e = 65537                    the PUBLIC EXPONENT
     5. d = e^-1 mod λ(n)            the PRIVATE EXPONENT

     PUBLIC KEY  = (n, e)
     PRIVATE KEY = (n, d)  plus p, q and the CRT values
     AND p AND q MUST BE DESTROYED or protected exactly as
     hard as d - either one factors n instantly.

   THE OPERATIONS
     "encrypt" / verify:   c = m^e mod n
     "decrypt" / sign:     m = c^d mod n

     They are inverses because e*d ≡ 1 (mod λ(n)) - the
     derivation is in chapter 11.

   WHY e = 65537 = 2^16 + 1
     · only two set bits, so verification is 17 squarings and
       one multiply - very fast, which matters because
       verification happens on every boot
     · large enough to avoid the small-exponent attacks that
       killed e = 3
     · TINY e MAKES VERIFICATION FAST AND SIGNING SLOW, which
       is the right trade: a device verifies constantly and
       signs never.

   THE ASYMMETRY IN COST
     verify (e=65537)    ~0.1 ms      2048-bit
     sign   (d, w/ CRT)  ~2 ms
     A 4096-bit key is roughly 6-8x slower to sign with, and
     ~3x slower to verify.

Why textbook RSA is broken

RSA exactly as the mathematics describes it is insecure in several distinct ways. Seeing why is what motivates the padding schemes that follow, which are not optional extras.

/* "Just compute m^e mod n" fails in at least five distinct
   ways. Every one of these has broken a real system.     */

/* 1. IT IS DETERMINISTIC.
      Same message -> same ciphertext. An attacker who
      suspects the plaintext just encrypts the guess and
      compares. For a small message space - a command byte,
      a PIN, a yes/no - this breaks it completely.        */

/* 2. SMALL MESSAGES DO NOT WRAP.
      With e = 3 and a short m, m^3 < n, so no modular
      reduction happens. The attacker takes an ORDINARY CUBE
      ROOT over the integers and recovers m. No key needed. */

/* 3. IT IS MULTIPLICATIVELY HOMOMORPHIC.
          E(m1) * E(m2) = (m1*m2)^e = E(m1 * m2)  mod n

      So an attacker can BLIND a ciphertext: send c * r^e to
      a decryption oracle, get back m * r, divide by r,
      recover m. This is a total break of any system that
      decrypts attacker-supplied ciphertexts.

      The same property lets an attacker forge signatures:
      given signatures on m1 and m2, they have one on
      m1 * m2.                                             */

/* 4. NO STRUCTURE MEANS NO INTEGRITY.
      Any n-bit value is a "valid" ciphertext, decrypting to
      garbage the receiver cannot distinguish from a real
      message. Padding provides the redundancy that makes
      forgery detectable.                                  */

/* 5. RELATED MESSAGES LEAK.
      Håstad's attack: the same m encrypted to three
      recipients with e = 3 is recoverable by CRT plus a cube
      root. Franklin-Reiter: two messages with a known linear
      relation are both recoverable.                       */

/* THE RULE THAT FOLLOWS:

     NEVER CALL A RAW MODEXP ON A MESSAGE.
     ALWAYS USE A PADDING SCHEME - OAEP or PSS.

   And when you see mbedtls_rsa_public()/mbedtls_rsa_private()
   in code, that is the RAW primitive. The functions you want
   are mbedtls_rsa_rsaes_oaep_encrypt() and
   mbedtls_rsa_rsassa_pss_sign().                        */

OAEP: encryption padding

The correct padding for RSA encryption. Its predecessor was the subject of an attack that recurs to this day in implementations that handle errors carelessly.

/* PKCS#1 v2, RFC 8017. Optimal Asymmetric Encryption
   Padding.                                                */

    EM = 0x00 ‖ maskedSeed ‖ maskedDB

    DB         = lHash ‖ PS(zeros) ‖ 0x01 ‖ message
    seed       = random, hLen bytes
    dbMask     = MGF1(seed, k - hLen - 1)
    maskedDB   = DB XOR dbMask
    seedMask   = MGF1(maskedDB, hLen)
    maskedSeed = seed XOR seedMask

    then  c = EM^e mod n

/* WHAT EACH PART DOES:
     the RANDOM SEED makes encryption probabilistic, killing
       problem (1)
     the two-way MASKING is a Feistel structure: every
       ciphertext bit depends on every plaintext bit
     lHash and the 0x01 SEPARATOR give the redundancy that
       makes an invalid ciphertext detectable, killing (4)
     the FULL-WIDTH ENCODED MESSAGE means m is always close
       to n, killing (2)

/* CAPACITY: k - 2*hLen - 2 bytes.
     2048-bit key, SHA-256:  256 - 64 - 2 = 190 bytes.

   SO YOU CANNOT ENCRYPT A LARGE MESSAGE WITH RSA. Nobody
   does. The pattern is HYBRID ENCRYPTION:

       k_session = random 32 bytes
       c1 = RSA-OAEP(pubkey, k_session)
       c2 = AES-GCM(k_session, plaintext)     /* chapter 09 */
       send c1 ‖ c2

/* --- PKCS#1 v1.5 ENCRYPTION PADDING: DO NOT USE --- */
    EM = 0x00 ‖ 0x02 ‖ random_nonzero_padding ‖ 0x00 ‖ m

    BLEICHENBACHER'S ATTACK (1998): if the receiver reveals -
    by an error message, a timing difference, or a connection
    reset - whether the 0x00 0x02 prefix was correct, the
    attacker decrypts any ciphertext with about a million
    adaptive queries. It has been rediscovered repeatedly:
    ROBOT (2017) found it live in load balancers from several
    major vendors, nineteen years later.

    THE ONLY SAFE HANDLING is to make the failure path
    completely indistinguishable - which is so hard to get
    right that TLS 1.3 REMOVED RSA KEY TRANSPORT ENTIRELY.
    Use OAEP, or better, use ECDH (chapter 13).          */

PSS: signature padding

The correct padding for RSA signatures, and structurally different from the encryption case — signing is not simply encryption with the private key, despite how often it is described that way.

/* RSASSA-PSS, and this is the more important half for
   embedded work, because firmware verification is where RSA
   still lives.                                            */

    mHash  = H(message)
    salt   = random, sLen bytes
    M'     = 0x00 * 8 ‖ mHash ‖ salt
    H2     = H(M')
    DB     = PS(zeros) ‖ 0x01 ‖ salt
    EM     = maskedDB ‖ H2 ‖ 0xBC

    signature = EM^d mod n

/* THE RANDOM SALT makes signatures PROBABILISTIC: signing
   the same message twice gives different signatures. That
   is not a bug - it gives PSS a tight security proof that
   v1.5 does not have.

/* --- PKCS#1 v1.5 SIGNATURES: legacy but everywhere --- */
    EM = 0x00 ‖ 0x01 ‖ 0xFF...0xFF ‖ 0x00 ‖ DigestInfo ‖ H(m)

    Deterministic. NOT KNOWN TO BE BROKEN when implemented
    correctly, and mandated by so many existing formats and
    boot ROMs that it is not going away. USE IT WHEN A FORMAT
    REQUIRES IT; use PSS for anything new.

/* AND THE IMPLEMENTATION BUG THAT KEEPS RECURRING -
   BLEICHENBACHER'S SIGNATURE FORGERY, "BERserk":

   A LAZY VERIFIER parses the structure left to right,
   finds the hash, compares it, and IGNORES TRAILING BYTES.
   With e = 3, an attacker can construct a value whose cube
   root has the right prefix and arbitrary garbage after -
   and forge a signature WITH NO PRIVATE KEY.

   THE CORRECT VERIFICATION:
     · RECONSTRUCT the full expected EM from the hash
     · compare the ENTIRE block, byte for byte, in constant
       time
     · never parse-and-extract

   NSS, GnuTLS, Firefox, Chrome and several TLS libraries
   have all shipped this bug. If you are writing a boot ROM
   verifier, this is the bug to look for.               */
Verify a firmware signature like this 
1. hash the image with SHA-256
2. RSA-verify with PSS (or v1.5 if the format demands)
3. compare the FULL reconstructed encoding
4. check the key against a hash burned in OTP
5. check the version against an anti-rollback counter
6. only then jump to the image

Steps 4 and 5 are not part of RSA and are just as important — see the secure boot chapter.

Key sizes and the alternatives

RSA keys must be far larger than symmetric or elliptic-curve keys for equivalent security, and the gap widens as sizes grow. That scaling is the main practical argument against it.

3072-bit~128-bitP-256The current recommendation
4096-bit~140-bitP-313Common for long-lived roots
15360-bit~256-bitP-521Impractical — use ECC
 
/* THE SIZE CURVE IS BRUTAL: doubling RSA security multiplies
   the key size by roughly five, because the number field
   sieve is subexponential. ECC scales linearly - 256 bits
   for 128-bit security (chapter 14).

/* SO WHY IS RSA STILL EVERYWHERE IN EMBEDDED?

     · BOOT ROMS ARE MASK-PROGRAMMED and were fixed years
       ago. If the ROM verifies RSA-2048 PKCS#1 v1.5, that
       is what your firmware is signed with, permanently.
     · VERIFICATION IS FAST with e = 65537 - actually faster
       than ECDSA verification, which matters at boot.
     · UNIVERSAL TOOLING support.

   WHERE ECC WINS:
     · signature size: 64 bytes vs 256-512
     · key size: 32 bytes vs 256-512, which matters when the
       public key lives in OTP fuses
     · SIGNING speed
     · key GENERATION: microseconds vs seconds

   AND FOR NEW DESIGNS: use Ed25519 or ECDSA P-256, and plan
   for a post-quantum signature (chapter 20) if the device
   will live past 2035.                                  */

Implementation hazards

RSA implementations have leaked private keys through timing more than once. The countermeasures are well understood and are a strong argument for using a reviewed library rather than writing one.

/* --- 1. TIMING ATTACKS ON THE PRIVATE OPERATION --- */
    A naive square-and-multiply branches on each bit of d:

        for each bit of d:
            square
            if bit: multiply          /* <-- LEAKS d */

    Kocher (1996) recovered private keys this way. Brumley
    and Boneh (2003) did it REMOTELY over a network against
    OpenSSL.

    DEFENCES: a Montgomery ladder (constant operation
    sequence), and BLINDING:
        c' = c * r^e mod n
        m' = c'^d mod n
        m  = m' * r^-1 mod n
    The exponentiation now runs on a randomised value, so its
    timing carries no information about c. Every serious
    library blinds by default; check that yours has it
    enabled.

/* --- 2. THE CRT FAULT ATTACK --- */
    One corrupted half of a CRT signature reveals a prime via
    gcd(s^e - m, n) (chapter 11).

    DEFENCE: VERIFY EVERY SIGNATURE BEFORE RELEASING IT.
        sign(); if (verify() != OK) { wipe(); abort(); }
    Costs one cheap public operation. Non-negotiable on
    anything physically accessible.

/* --- 3. LEAKING THE PRIMES --- */
    p and q are as sensitive as d. Zero them, keep them out
    of swap and core dumps, and never log a key structure.

/* --- 4. SMALL PUBLIC EXPONENTS --- */
    e = 3 is legal and fast and has a long history of
    breaking things. Use 65537. If you must accept e = 3,
    padding must be flawless.

/* --- 5. NOT VALIDATING A RECEIVED PUBLIC KEY --- */
    Before using someone's RSA key:
        · n has the expected bit length
        · n is ODD (an even n is trivially factorable)
        · e is odd and 3 <= e < n
        · e is 65537 if your policy says so
    A hostile "public key" with a smooth n turns your
    encryption into a no-op.

/* --- 6. THE CODE PATTERN, mbedTLS --- */
    mbedtls_rsa_context rsa;
    mbedtls_rsa_init(&rsa);
    mbedtls_rsa_set_padding(&rsa, MBEDTLS_RSA_PKCS_V21,
                            MBEDTLS_MD_SHA256);  /* PSS/OAEP */

    ret = mbedtls_rsa_rsassa_pss_verify(
              &rsa, MBEDTLS_MD_SHA256, 32, hash, sig);
    if (ret != 0) {
            /* INVALID. No detail in the error path. */
            return -1;
    }
    mbedtls_rsa_free(&rsa);

/* NOTE THE ARGUMENT ORDER AND THE PADDING MODE. Calling
   pkcs1_v15_verify on a PSS signature returns an error;
   calling the RAW primitive returns success on garbage. */
