Pointers from first principles

A pointer is a value that designates an object. That is all. Every difficulty people have with pointers comes from confusing the pointer with the thing it points to, or from reading declarations in the wrong direction. Both are fixable in an afternoon.

The mental model

A pointer is not simply an address. In C's model it is an address plus a type plus, crucially, a notion of which object it points into — and that last part is what makes some pointer arithmetic undefined even when the arithmetic itself seems obvious.

Memory is a numbered array of bytes. An object occupies a run of them.
A pointer is a value that identifies where an object begins, together
with a TYPE that says how to interpret what is there.

   address:   0x1000   0x1004   0x1008   0x100C
             +--------+--------+--------+--------+
   memory:   |   42   |  ...   |  0x1000|  ...   |
             +--------+--------+--------+--------+
                 ^                 |
                 |                 |
                 x                 p        int *p = &x;

   x     the object.        value 42.
   &x    its address.        value 0x1000.
   p     a pointer object.   value 0x1000, stored at 0x1008.
   *p    the object at that address.   value 42.
   &p    the address of the pointer itself.  value 0x1008.

The TYPE matters as much as the address:
   int *p     -> "reading 4 bytes here gives an int"
   char *c    -> "reading 1 byte here gives a char"
   Two pointers can hold the same address and mean different things.
The two operators, said precisely

&x — "the address of x". Turns an object into a pointer value.
*p — "the object that p points to". Turns a pointer value back into an object.

They are inverses: *&x is x. Read * aloud as "the thing at", never as "pointer" — that single habit clears up most confusion.

Reading declarations

C declaration syntax mirrors use, not structure. The reliable technique is the spiral rule: start at the identifier, then move right when you can, left when you must.

   int *p;              p is a pointer to int
   int **p;             p is a pointer to a pointer to int
   int p[10];           p is an array of 10 ints
   int *p[10];          p is an ARRAY of 10 pointers to int
   int (*p)[10];        p is a POINTER to an array of 10 ints
   int *f(void);        f is a function returning pointer to int
   int (*f)(void);      f is a POINTER to a function returning int
   int (*f[5])(void);   f is an array of 5 pointers to functions
                          returning int
   int *(*f)(int *);    f is a pointer to a function taking int*
                          and returning int*

Why the parentheses: [] and () bind TIGHTER than *.
   int *p[10]    ==  int *(p[10])    array of pointers
   int (*p)[10]                      pointer to array

When it gets hard, stop and use a typedef. Professional code does.

   typedef int (*handler_fn)(struct device *, void *);
   handler_fn table[16];        /* obviously an array of handlers */

   cdecl(1) or `cdecl explain ...` will read any declaration aloud.

Where const goes

/* Read RIGHT TO LEFT from the identifier. const applies to what is
   immediately to its LEFT — unless it is leftmost, then to the right. */

const int *p;          /* p: pointer to const int   */
int const *p;          /* identical to the above    */
int *const p;          /* p: const pointer to int   */
const int *const p;    /* const pointer to const int */

const int *p;          *p = 5;   /* ERROR: object is const   */
                       p = &y;   /* fine: pointer is mutable */

int *const p = &x;     *p = 5;   /* fine: object is mutable  */
                       p = &y;   /* ERROR: pointer is const  */

/* The east-const style makes the rule uniform, which is why many
   codebases now prefer it:
        int const *p;        rather than  const int *p;
   Either is fine — be consistent.                            */

Pointer arithmetic

Arithmetic is in units of the pointed-to type, not bytes

p + 1 advances by sizeof(*p) bytes. This is what makes a[i] and *(a + i) equivalent, and it is why void * arithmetic is not standard C.

int a[5] = {10, 20, 30, 40, 50};
int *p = a;              /* points at a[0] */

p + 1                    /* a[1] — address advances by 4 bytes  */
*(p + 2)                 /* 30                                   */
p[2]                     /* identical: p[2] is *(p + 2) BY DEFINITION */
2[p]                     /* also 30 — legal, and a good argument for
                            why you should never write it        */

int *q = &a[4];
q - p                    /* 4 — a ptrdiff_t, in ELEMENTS not bytes */
(char *)q - (char *)p    /* 16 — in bytes                          */

/* void* arithmetic is a GNU extension (treats it as char*). It is
   used throughout the Linux kernel but is not portable ISO C.     */
void *v = p;
v + 1;                   /* GCC: +1 byte. MSVC/strict ISO: error   */

What arithmetic is legal

   int a[5];
   +----+----+----+----+----+----+
   |a[0]|a[1]|a[2]|a[3]|a[4]| ** |
   +----+----+----+----+----+----+
     ^                        ^
    &a[0]                  a + 5  = "one past the end"

  LEGAL:   any pointer from &a[0] to a+5 inclusive
           comparing any two of them
           dereferencing anything EXCEPT a+5

  UNDEFINED:  computing a - 1     (before the start)
              computing a + 6     (past one-past-the-end)
              dereferencing a + 5
              comparing pointers into DIFFERENT objects with < >

  The one-past-the-end rule is what makes the standard loop idiom
  legal, and it is why `end` pointers work at all:

      for (int *p = a; p != a + 5; p++)
              use(*p);
/* This looks fine and is undefined behaviour: */
for (int *p = &a[4]; p >= a; p--)     /* the final p-- computes a-1 */
        use(*p);

/* correct backwards iteration */
for (int *p = a + 5; p-- != a; )
        use(*p);
/* or just use an index */
for (size_t i = 5; i-- > 0; )
        use(a[i]);

Null pointers

The null pointer is a distinguished value meaning "points at nothing", and several things about it are commonly misunderstood — including whether it is necessarily all-zero bits.

int *p = NULL;        /* NULL is ((void*)0) or 0, implementation's choice */
int *p = 0;           /* the null pointer CONSTANT — same thing           */
int *p = nullptr;     /* C23, and clearer                                 */

if (p)                /* idiomatic: tests against null       */
if (p != NULL)        /* identical, more explicit            */

/* Dereferencing NULL is UNDEFINED, not "crashes with a segfault".
   On a system with memory at address 0 — many microcontrollers, and
   the x86 real-mode interrupt vector table — it silently reads
   garbage or corrupts something important.                        */

/* And the optimiser exploits it. This is a real Linux kernel CVE
   pattern (CVE-2009-1897):                                        */
struct s *p = get();
int x = p->field;          /* dereference implies p is non-NULL... */
if (p == NULL)             /* ...so the compiler DELETES this check */
        return -EINVAL;

/* Always check BEFORE dereferencing. The order is not stylistic. */

/* NULL is not necessarily all-zero bits. memset(&p, 0, sizeof p)
   is not guaranteed to produce a null pointer, though it does on
   every platform you will meet. Use explicit initialisation.      */

void pointers and generic code

void * is C's generic pointer: it can hold any object pointer and is what makes malloc and qsort possible. It also discards type information entirely, which is exactly why it is both useful and dangerous.

/* void* is "a pointer to something unspecified". It converts to and
   from any OBJECT pointer type without a cast.                     */

void *v = &x;            /* implicit, fine                */
int *p = v;              /* implicit in C (NOT in C++)     */
int *p = (int *)v;       /* explicit — required in C++, harmless in C */

*v;                      /* ERROR: cannot dereference, size unknown  */

/* This is the mechanism behind every generic C API: */
void *malloc(size_t);
void *memcpy(void *dst, const void *src, size_t n);
int qsort_cmp(const void *a, const void *b);

/* qsort's comparator: the standard idiom for recovering the type */
static int cmp_int(const void *a, const void *b)
{
        int x = *(const int *)a;
        int y = *(const int *)b;
        return (x > y) - (x < y);    /* avoids overflow of x - y */
}
qsort(arr, n, sizeof(int), cmp_int);

/* Do NOT cast the result of malloc in C.
      int *p = malloc(n * sizeof *p);        // correct, idiomatic
   The cast is required in C++, unnecessary in C, and historically
   it hid the missing-prototype bug. Note `sizeof *p` rather than
   `sizeof(int)` — it stays correct if the type of p changes.    */
void* does not mean "function pointer"

The standard guarantees conversion between void * and object pointers only. Converting a function pointer through void * is not guaranteed — on architectures where code and data addresses differ in width or format it genuinely breaks. POSIX requires it to work for dlsym(), which is why that API is a documented wart. Keep function pointers in function pointer types.

Pointers to pointers

Pointers to pointers are where most people's mental model breaks down. They are unavoidable in real code — anything that modifies a caller's pointer needs one — and the way to read them is mechanical rather than intuitive.

/* Reason 1: modifying a caller's pointer */
void alloc_buf(char **out, size_t n)
{
        *out = malloc(n);        /* write through to the caller's pointer */
}
char *buf;
alloc_buf(&buf, 100);

/* C is strictly pass-by-value. To let a function change your pointer,
   you must pass a pointer TO it. There is no other mechanism.      */

/* Reason 2: arrays of pointers — argv is the canonical example */
int main(int argc, char **argv)
/*                 char *argv[]  — identical in a parameter list */
{
        for (int i = 0; i < argc; i++)
                puts(argv[i]);
}

/* Reason 3: the linked-list deletion trick that removes all the
   special cases. Worth studying until it is obvious.             */
void remove_if(struct node **head, int target)
{
        struct node **pp = head;          /* pointer to the link itself */
        while (*pp) {
                struct node *entry = *pp;
                if (entry->value == target) {
                        *pp = entry->next;    /* unlink, whatever pp points to */
                        free(entry);
                } else {
                        pp = &entry->next;
                }
        }
}
/* No head-versus-middle special case, no `prev` pointer, no NULL
   checks for the previous node. Linus Torvalds has cited this as
   the difference between understanding pointers and not.          */

The four ways pointers go wrong

Pointer bugs are not one problem but four distinct ones, each with a different cause and a different fix. Naming them separately is what makes them findable.

FaultWhat it isDetection
DanglingPoints to storage whose lifetime endedASan, Valgrind, KASAN
WildUninitialised — contains garbageMSan, -Wuninitialized, always initialise
Out of boundsPast the end of the objectASan, -fsanitize=bounds
Type-punned illegallyAccessed through an incompatible type-Wstrict-aliasing, ch. 15
 
/* Dangling: returning a pointer to an automatic object */
char *bad(void)
{
        char buf[64];
        sprintf(buf, "hello");
        return buf;          /* buf's lifetime ends HERE */
}                            /* -Wreturn-local-addr catches this one */

/* Dangling: use after free */
free(p);
p->field = 1;                /* undefined; may silently work for a while */
free(p);                     /* double free: heap corruption            */

/* The discipline that prevents it: */
free(p);
p = NULL;                    /* now a later use crashes loudly and
                                a second free() is a no-op            */

/* Dangling: a pointer into a container that reallocated */
int *p = &vec->data[0];
vec_push(vec, x);            /* may realloc and move the buffer */
*p = 5;                      /* dangling — a very common real bug */

/* Wild: uninitialised */
int *p;                      /* contains whatever was on the stack */
*p = 5;                      /* undefined                          */
int *p = NULL;               /* at least it will fault predictably  */

restrict: promising no aliasing

This qualifier is a promise you make to the compiler: that the memory reached through this pointer is not reachable through any other. It enables real optimisation, and breaking the promise produces silent, data-dependent wrongness.

/* Without restrict, the compiler must assume dst and src may overlap,
   so it cannot keep values in registers across the loop.          */
void copy(int *dst, const int *src, size_t n)
{
        for (size_t i = 0; i < n; i++)
                dst[i] = src[i];      /* must reload src[i] each time */
}

/* restrict promises: within this scope, the object accessed through
   this pointer is not accessed through any other pointer.          */
void copy(int *restrict dst, const int *restrict src, size_t n)
{
        for (size_t i = 0; i < n; i++)
                dst[i] = src[i];      /* now vectorisable */
}

/* This is why memcpy() and memmove() are two functions:
       memcpy  — arguments are restrict; overlapping is UNDEFINED
       memmove — handles overlap correctly, and is slower for it

   Breaking a restrict promise is undefined behaviour with no
   diagnostic. Only use it where you genuinely control both
   pointers. See chapter 10.                                    */

Finding pointer bugs

Pointer errors rarely crash at the point of the mistake. These tools move the failure back to the offending line, which is the difference between a bug found in minutes and one hunted for days.

# AddressSanitizer — use-after-free, out-of-bounds, double free.
# Roughly 2x slowdown; run your whole test suite under it.
gcc -fsanitize=address -fno-omit-frame-pointer -g prog.c

# MemorySanitizer — reads of uninitialised memory (Clang only)
clang -fsanitize=memory -fno-omit-frame-pointer -g prog.c

# UndefinedBehaviorSanitizer — null deref, bad shifts, overflow
gcc -fsanitize=undefined -g prog.c

# Valgrind — no rebuild required, but ~20x slower
valgrind --leak-check=full --track-origins=yes ./prog

# Static analysis, free and fast
gcc -fanalyzer -Wall -Wextra prog.c
clang --analyze prog.c

# In the kernel: KASAN, KMSAN, and CONFIG_DEBUG_OBJECTS
