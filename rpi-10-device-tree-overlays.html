Device tree overlays on the Pi

The Linux track explains what a device tree is. The Pi is where you get to edit one — because a header with 40 pins and a thousand possible add-on boards is exactly the problem overlays were invented to solve.

Why overlays exist

   A device tree describes hardware the kernel cannot probe:
   which peripherals exist, at which addresses, with which
   interrupts and which pins.

   THE PI'S PROBLEM: the SoC is fixed, but what is attached
   to the 40-pin header is not. A sensor today, a display
   tomorrow, a HAT next week. Shipping one .dtb per
   combination is impossible.

   THE SOLUTION: a base .dtb for the board, plus small
   OVERLAY fragments that the firmware MERGES into it at
   boot, chosen by config.txt.

   base bcm2712-rpi-5-b.dtb
        |
        +--> overlay: i2c-sensor,bme280        (dtoverlay=)
        +--> overlay: spi0-1cs
        +--> parameter: i2c_arm=on             (dtparam=)
        |
        v
   final device tree --> handed to Linux at boot

   AN OVERLAY CAN:
     - enable a node that is disabled by default
       (status = "disabled" -> "okay")
     - add a child node: "there is a BME280 at address 0x76
       on this I2C bus"
     - change pin muxing
     - override any property

   IT CANNOT:
     - do anything at runtime after boot, except through
       the separate and Pi-specific dtoverlay(1) command
     - probe. You are ASSERTING what is connected; if you
       lie, the driver will try and fail.

Using the ones that ship

# Hundreds ship with the OS. Read before writing your own -
# the one you need often already exists.

$ ls /boot/firmware/overlays/ | head
$ ls /boot/firmware/overlays/ | wc -l
# typically 200+

# THE DOCUMENTATION IS ON THE BOARD, and it is the
# authoritative source for parameters:
$ zless /boot/firmware/overlays/README
# or search it:
$ grep -A20 "Name:   i2c-sensor" /boot/firmware/overlays/README
Name:   i2c-sensor
Info:   Adds support for a number of I2C sensors
Load:   dtoverlay=i2c-sensor,<param>=<val>
Params: addr    Set the address for the sensor
        bme280  Bosch BME280 pressure/temp/humidity sensor
        ...

# Enable it in config.txt (chapter 09):
dtoverlay=i2c-sensor,bme280,addr=0x76

# Reboot, then confirm the driver bound:
$ ls /sys/bus/i2c/devices/1-0076/
driver  hwmon  modalias  name  ...
$ cat /sys/bus/i2c/devices/1-0076/name
bme280
$ ls /sys/bus/iio/devices/
iio:device0

# THAT is the win: a standard overlay plus an in-tree driver
# gives you a proper IIO device with no code at all. Chapter
# 21 writes the driver from scratch anyway, because doing it
# once teaches you what this shortcut is hiding.

# TEST WITHOUT REBOOTING - a Pi-specific convenience:
$ sudo dtoverlay i2c-sensor bme280 addr=0x76
$ dtoverlay -l                       # what is loaded
$ sudo dtoverlay -r 0                # remove by index
# Not all overlays can be applied live, and a failed live
# apply can leave the tree inconsistent. Use it to iterate
# fast; put the final answer in config.txt.

Writing one

/* my-sensor-overlay.dts
   Declares a BME280 on I2C1 at 0x76, and a GPIO the sensor
   uses as an interrupt.                                    */

/dts-v1/;
/plugin/;                    /* THIS makes it an overlay    */

/ {
    compatible = "brcm,bcm2711", "brcm,bcm2712";

    /* Fragment 0: turn the I2C controller on. */
    fragment@0 {
        target = <&i2c1>;            /* a LABEL in the base */
        __overlay__ {
            status = "okay";
        };
    };

    /* Fragment 1: declare what is attached to it. */
    fragment@1 {
        target = <&i2c1>;
        __overlay__ {
            #address-cells = <1>;
            #size-cells = <0>;

            bme280@76 {
                compatible = "bosch,bme280";
                reg = <0x76>;
                status = "okay";
            };
        };
    };

    /* Fragment 2: an interrupt line on GPIO17. */
    fragment@2 {
        target = <&gpio>;
        __overlay__ {
            sensor_pins: sensor_pins {
                brcm,pins = <17>;
                brcm,function = <0>;      /* input          */
                brcm,pull = <2>;          /* pull-up        */
            };
        };
    };

    /* __overrides__ exposes parameters to the
       dtoverlay=name,param=value syntax. */
    __overrides__ {
        addr = <&bme280>,"reg:0";
    };
};

/* target = <&label> requires the base tree to EXPORT that
   label, which is why overlays are compiled with -@ (below):
   it emits a __symbols__ node recording every label so the
   firmware can resolve references at merge time. Forget -@
   and the overlay compiles cleanly and does nothing.       */

# Compile. The -@ is not optional (see above).
$ dtc -@ -I dts -O dtb -o my-sensor.dtbo my-sensor-overlay.dts

# Warnings about unit addresses and missing reg properties
# are normal for overlays and can usually be ignored; errors
# cannot.

$ sudo cp my-sensor.dtbo /boot/firmware/overlays/
# in config.txt:
dtoverlay=my-sensor

$ sudo reboot

# --- VERIFY, in this order ---

# 1. Did the firmware apply it? Serial console with
#    BOOT_UART=1 shows overlay load failures at boot; there
#    is no other report.

# 2. Is it in the live tree?
$ dtc -I fs -O dts /sys/firmware/devicetree/base 2>/dev/null \
      | grep -A6 "bme280"
            bme280@76 {
                    compatible = "bosch,bme280";
                    reg = <0x76>;
                    status = "okay";
            };
#    Present here = the overlay worked. Absent = it did not,
#    and nothing above this layer can work.

# 3. Did a driver bind?
$ ls /sys/bus/i2c/devices/1-0076/driver
#    Node present but no driver symlink means the tree is
#    right and no driver matched the compatible string -
#    which is exactly the state chapter 21's project starts
#    from.

# 4. Is the device actually there electrically?
$ i2cdetect -y 1
#    A "UU" at 0x76 means a driver has claimed it. A number
#    means present but unclaimed. Nothing means check wiring
#    (bus chapter 07).
The four-step verification is the whole skill

Overlay applied → node in the live tree → driver bound → device responds. Each step has a different fix, and knowing which one failed saves you from changing the wrong thing. Most time lost on device tree work comes from editing the .dts when the real problem was at step 3 (no driver for that compatible string) or step 4 (the sensor is on the wrong address). Run dtc -I fs before touching anything.

Pin conflicts

# The 40-pin header multiplexes. Two overlays wanting the
# same pin both "work" and one silently loses.

# What is claimed right now:
$ cat /sys/kernel/debug/pinctrl/*/pinmux-pins | head -20
pin 2 (GPIO2): 1000b0000.i2c (GPIO UNCLAIMED) function i2c1 group gpio2
pin 3 (GPIO3): 1000b0000.i2c (GPIO UNCLAIMED) function i2c1 group gpio3
pin 17 (GPIO17): (MUX UNCLAIMED) (GPIO UNCLAIMED)

# The Pi-specific summary, which is easier to read:
$ pinctrl get            # newer OS releases
$ raspi-gpio get         # older; same idea
GPIO 2: level=1 fsel=4 alt=0 func=SDA1
GPIO 17: level=0 fsel=0 func=INPUT

# COMMON COLLISIONS:
#   GPIO 2,3    I2C1     - and nothing else, ever
#   GPIO 7-11   SPI0     - a HAT wanting GPIO8 fights SPI
#   GPIO 14,15  UART     - and the serial console (ch 05)
#   GPIO 18,19,20,21  I2S - collides with PWM on 18/19
#
# The 1-wire overlay defaults to GPIO4; several HATs also
# want GPIO4. Both load, and the second one wins silently.

# Move a peripheral to different pins rather than fighting:
dtoverlay=i2c1,pins_44_45
dtoverlay=uart3,txd3_pin=4,rxd3_pin=5

# Check the overlays README for which pin sets each
# peripheral supports - they are fixed by the SoC's mux, not
# arbitrary.
