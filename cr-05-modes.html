Modes of operation

A block cipher encrypts 16 bytes. A mode turns it into something that encrypts a message — and the choice of mode determines almost every security property that matters. This is where most real encryption failures live.

ECB — never

The most obvious way to encrypt more than one block is also famously insecure, and the failure is visual: identical plaintext blocks produce identical ciphertext blocks, so structure survives encryption intact.

   ELECTRONIC CODEBOOK: encrypt each block independently.

        C_i = E_K(P_i)

   THE FAILURE IS IMMEDIATE: identical plaintext blocks give
   identical ciphertext blocks. The ciphertext preserves the
   structure of the plaintext.

   THE CANONICAL DEMONSTRATION is the "ECB penguin" - a
   bitmap encrypted with ECB in which the image is still
   plainly visible, because regions of uniform colour become
   regions of uniform ciphertext.

   WHAT THIS LEAKS IN PRACTICE:
     · repeated records in a database
     · structure in a protocol with fixed fields
     · whether two encrypted values are equal - which is
       enough to break a great many things
     · block boundaries and message structure

   AND IT FAILS IND-CPA (chapter 03): encryption is
   deterministic, so an adversary distinguishes two chosen
   plaintexts trivially.

   ECB IS ALSO MALLEABLE: an attacker can reorder, duplicate
   or delete whole blocks, and the result decrypts.

   THE ONLY LEGITIMATE USE: encrypting a single block of
   random data - a key being wrapped, for instance - and even
   there, use a proper key-wrap construction (RFC 3394)
   instead.

   IF YOU SEE ECB IN A CODEBASE, it is a finding.

CBC

Chaining each block into the next fixes the pattern leak, and introduces an initialisation vector with requirements that are easy to violate — plus a padding step that has been the basis of practical attacks.

/* CIPHER BLOCK CHAINING: XOR each plaintext block with the
   previous ciphertext block before encrypting.           */

        C_0 = E_K(P_0 XOR IV)
        C_i = E_K(P_i XOR C_{i-1})

        P_0 = D_K(C_0) XOR IV
        P_i = D_K(C_i) XOR C_{i-1}

/* PROPERTIES:
     + identical plaintext gives different ciphertext,
       provided the IV differs
     + a ciphertext error affects only two plaintext blocks
     - ENCRYPTION IS SEQUENTIAL - no parallelism
     + decryption IS parallelisable
     - requires PADDING to a block multiple
     - NO AUTHENTICATION

/* THE IV REQUIREMENT: it must be UNPREDICTABLE, not merely
   unique. A predictable IV enables a chosen-plaintext attack
   in which the adversary confirms a guessed plaintext block
   - which is exactly the BEAST attack on TLS 1.0, where the
   IV for each record was the previous record's last
   ciphertext block.

   SO: generate the IV with a CSPRNG (chapter 02), and
   transmit it in the clear alongside the ciphertext.

/* PADDING - PKCS#7, and it is where CBC goes wrong: */
        add N bytes each of value N, where 1 <= N <= 16
        a full block gets a WHOLE EXTRA BLOCK of padding

        "HELLO" -> 48 45 4C 4C 4F 0B 0B 0B 0B 0B 0B 0B 0B 0B 0B 0B

/* THE PADDING ORACLE (chapter 01): if the receiver
   distinguishes "bad padding" from "bad MAC" - through an
   error code, a response, or a TIMING DIFFERENCE - the
   attacker decrypts the whole message with about 128
   queries per byte. This broke TLS (Lucky 13), ASP.NET,
   Ruby on Rails, XML encryption and countless devices.

   THE FIX IS NOT constant-time padding checks - people
   tried, and Lucky 13 defeated them through timing anyway.
   THE FIX IS AEAD (chapter 09).

/* IF YOU MUST USE CBC: encrypt-then-MAC, with the MAC
   covering the IV and the ciphertext, and verify the MAC
   BEFORE attempting to decrypt or unpad. Then a forged
   message never reaches the padding check at all.       */
Encrypt-then-MAC, and only that order

Encrypt-then-MAC — MAC over the ciphertext and IV. Provably secure, and a forgery is rejected before any decryption happens. MAC-then-encrypt (what TLS 1.0–1.2 did) requires decrypting before you can check, which is exactly what enables padding oracles. Encrypt-and-MAC (SSH) can leak plaintext information through the MAC. Use an AEAD and the question does not arise.

CTR

Counter mode turns a block cipher into a stream cipher, which brings random access and parallelism. It also makes nonce reuse immediately catastrophic, in exactly the way one-time pad reuse is.

/* COUNTER MODE: turn the block cipher into a stream cipher
   by encrypting a counter and XORing the result.         */

        C_i = P_i XOR E_K(nonce ‖ counter_i)

/* PROPERTIES:
     + FULLY PARALLELISABLE, both directions
     + RANDOM ACCESS - decrypt block 1000 without the
       preceding blocks. Essential for disk and flash
       encryption.
     + NO PADDING - the keystream is truncated to the message
       length
     + only the ENCRYPT direction of the cipher is needed,
       which halves the code and table size on a
       microcontroller
     - NO AUTHENTICATION
     - CATASTROPHIC on nonce reuse

/* THE COUNTER BLOCK, typically:
        [ 96-bit nonce ][ 32-bit counter ]
   giving 2^32 blocks = 64 GB per nonce, which is the limit
   before the counter wraps into the next nonce's space.

/* THE NONCE REQUIREMENT: UNIQUE, not secret and not random.
   A counter is the correct choice, and better than random -
   because random nonces collide by the birthday bound
   (2^48 messages for a 96-bit nonce is uncomfortably close
   for a long-lived key), while a counter cannot collide
   until it wraps.

/* NONCE REUSE IS THE TWO-TIME PAD (chapter 03):
        C1 XOR C2 = P1 XOR P2
   and the key cancels. Everything in chapter 03 applies.

/* AND CTR IS MALLEABLE, exactly like any stream cipher: flip
   a ciphertext bit, flip the plaintext bit. Which is why CTR
   alone is never correct, and why GCM = CTR + a MAC
   (chapter 09).                                          */

/* --- XTS, and why disk encryption is different --- */
/* A disk sector must encrypt to exactly one sector - there
   is no room for an IV, a nonce or a tag. So XTS uses the
   SECTOR NUMBER as a tweak:                              */

        T = E_K2(sector) * α^j          /* in GF(2^128) */
        C_j = E_K1(P_j XOR T) XOR T

/* PROPERTIES: length-preserving, random access, and identical
   plaintext in DIFFERENT sectors encrypts differently.

   WHAT IT DOES NOT PROVIDE, and this is important:
     · NO AUTHENTICATION. An attacker with write access can
       modify sectors; the result decrypts to garbage, but
       predictable garbage in some cases.
     · NO FRESHNESS. An old sector can be replayed - the
       "watermarking" and rollback attacks on full-disk
       encryption.
     · identical plaintext in the SAME sector at different
       times gives identical ciphertext, so an observer sees
       when a sector did not change.

   XTS IS THE RIGHT ANSWER FOR DISKS anyway, because the
   alternatives require storing a tag per sector - which
   dm-integrity does, at a real cost. Know what you are not
   getting.

/* --- SIV and AES-GCM-SIV: nonce misuse resistance --- */
/* The tag is computed FIRST, over the plaintext, and used as
   the nonce for the encryption. So a repeated nonce with
   different plaintexts still produces different ciphertexts;
   the only leak is that identical (nonce, plaintext) pairs
   are visible as identical ciphertexts.

   USE IT when you cannot guarantee nonce uniqueness - a
   device that may be restored from backup, a stateless
   protocol, a system where the counter might reset
   (chapter 02). The cost is two passes over the plaintext,
   so it cannot stream.                                    */

Choosing

In practice this decision should almost never be made, because the modes above are all unauthenticated and you should be using an authenticated construction instead. This section explains when the choice legitimately arises.

   Do you need encryption?
        |
        +-- with authentication (you do)
        |     |
        |     +-- can you guarantee unique nonces?
        |     |     |
        |     |     +-- YES, and you have AES hardware
        |     |     |      -> AES-GCM
        |     |     +-- YES, no AES hardware
        |     |     |      -> ChaCha20-Poly1305
        |     |     +-- YES, very constrained device
        |     |     |      -> AES-CCM, or ASCON
        |     |     +-- NO / not sure
        |     |            -> AES-GCM-SIV
        |     |
        |     +-- and the API you should call is the AEAD
        |         one, not a mode plus a MAC you compose
        |         yourself (chapter 09)
        |
        +-- length-preserving, random access (a disk)
        |     -> AES-XTS, and understand what it omits
        |
        +-- wrapping a key
              -> AES-KW / KWP

   WHAT NEVER TO CHOOSE:
     ECB, for anything
     CBC or CTR without a MAC
     a mode you assembled from primitives yourself
     a mode because it was in the example code you copied

Getting it right

Encryption without authentication is broken in ways that are not obvious, and this is where that is demonstrated rather than asserted — the attacks work on correctly implemented, correctly keyed ciphers.
