RPC and tee-supplicant

The secure world has no filesystem, no network and no way to allocate normal-world memory. So when it needs those things it asks — by returning from the very SMC that invoked it, with "not finished, do this first". That inversion is elegant, it is why OP-TEE stays small, and it is the source of the deadlock in chapter 5.

Returning in order to ask

The secure world sometimes needs something only the normal world can do — read a file, allocate memory, get the time. That inversion of trust is deliberate, and carefully constrained, because it lets untrusted code influence trusted execution.

   The secure world cannot CALL the normal world. There is no
   such instruction: SMC goes up in privilege, never down.

   So OP-TEE uses the only channel it has - the return value of
   the call it is currently servicing.

     normal world:   SMC(CALL_WITH_ARG, msg)
                          |
                          v
     OP-TEE:         thread allocated, TA runs
                     TA calls TEE_OpenPersistentObject()
                          |
                          |  "I need a file. I cannot open
                          |   files."
                          v
                     SAVE the thread's full state
                     write an RPC request into shared memory
                     return to the normal world with
                        x0 = OPTEE_SMC_RETURN_RPC_CMD
                          |
                          v
     driver:         "this is not a result, it is a request"
                     hand it to tee-supplicant
                          |
                          v
     tee-supplicant: open("/data/tee/...")
                     read the data into shared memory
                     reply
                          |
                          v
     driver:         SMC(CALL_RETURN_FROM_RPC, thread_id, ...)
                          |
                          v
     OP-TEE:         find the saved thread, RESTORE it,
                     TEE_OpenPersistentObject() returns
                     TA continues as if nothing happened
                          |
                          ... eventually ...
                          v
                     return OPTEE_SMC_RETURN_OK

   The TA sees an ordinary blocking function call. Underneath,
   control left the secure world entirely and came back.

   THE THREAD IS HELD THROUGHOUT. That is the whole design
   constraint (chapter 5).

The RPC requests

The requests the secure world can make of the normal world are a fixed, small set. Knowing them is what tells you what a trusted application can and cannot depend on.

/* Two of these deserve a second look.

   LOAD_TA - the secure world asks the normal world to give it
   a trusted application. The normal world is untrusted. So
   OP-TEE VERIFIES THE SIGNATURE of whatever it receives
   (chapter 14). An attacker who substitutes a different .ta
   gets TEEC_ERROR_SECURITY, not code execution. This is the
   design pattern: accept data from an untrusted source, then
   verify it yourself.

   SOCKET - yes, a TA can open a TCP connection, tunnelled
   through tee-supplicant. Whether it SHOULD is another
   question: the normal world sees and can modify every byte
   unless you run TLS end-to-end inside the TA.            */
The security pattern that makes this safe

Every RPC hands work to an untrusted party. The rule that keeps it sound: the secure world never trusts the result. TA binaries are signature-checked. Secure storage is encrypted and authenticated, so a modified file fails its MAC. RPMB frames are MACed with a key the normal world does not have. Time is explicitly labelled untrusted. Where verification is impossible — as with wall-clock time — the API says so, and chapter 17 covers what to do instead.

tee-supplicant

A user-space daemon services those requests. If it is missing or unprivileged, secure-world operations fail in ways whose symptoms point nowhere near it.

/* A normal user-space daemon, ~2000 lines. Its whole life:  */

int main(void)
{
        int fd = open("/dev/teepriv0", O_RDWR);

        for (;;) {
                struct tee_ioctl_supp_recv_arg arg;

                /* Blocks until OP-TEE needs something. */
                ioctl(fd, TEE_IOC_SUPPL_RECV, &arg);

                switch (arg.func) {
                case OPTEE_RPC_CMD_LOAD_TA:
                        load_ta(&arg);      /* read
                                               /lib/optee_armtz/
                                               <uuid>.ta      */
                        break;
                case OPTEE_RPC_CMD_FS:
                        tee_supp_fs(&arg);  /* open/read/write/
                                               unlink under
                                               /data/tee/      */
                        break;
                case OPTEE_RPC_CMD_RPMB:
                        rpmb_process(&arg); /* ioctl to the
                                               eMMC             */
                        break;
                case OPTEE_RPC_CMD_GET_TIME:
                        get_time(&arg);
                        break;
                case OPTEE_RPC_CMD_I2C_TRANSFER:
                        i2c_transfer(&arg);
                        break;
                ...
                }

                ioctl(fd, TEE_IOC_SUPPL_SEND, &arg);
        }
}

/* Where it keeps things: */
    /lib/optee_armtz/<uuid>.ta    trusted applications
    /data/tee/                    secure storage files
                                  (encrypted; the normal world
                                   can delete them but not read
                                   or forge them)

/* Running it: */
$ tee-supplicant -d              # daemonise
$ tee-supplicant -f              # foreground, prints errors
$ tee-supplicant -f /dev/teepriv0
$ systemctl status tee-supplicant

/* WITHOUT IT:
     TEEC_OpenSession -> TEEC_ERROR_ITEM_NOT_FOUND, because
     nothing can load the TA binary.
   And a TA already loaded that tries to use secure storage
   will BLOCK, holding a thread, until the supplicant returns
   or the call is cancelled.                                */

Asynchronous notification

The secure world also needs to signal the normal world asynchronously, which is a different mechanism from answering a request and is how interrupt-driven trusted applications work.

/* A problem the RPC model does not solve: the secure world
   needs to tell the normal world something when it is NOT
   servicing a call. A secure interrupt arrived; a background
   task finished.

   With plain RPC there is no channel - OP-TEE only runs when
   called.

   CFG_CORE_ASYNC_NOTIF=y adds one:

     OP-TEE raises a dedicated non-secure interrupt.
       |
       v
     Linux's optee driver takes it, and issues
       SMC(OPTEE_SMC_GET_ASYNC_NOTIF_VALUE)
       to ask what happened.
       |
       v
     OP-TEE returns a notification value.
       |
       v
     The driver wakes whatever was waiting, or schedules
       OPTEE_MSG_CMD_DO_BOTTOM_HALF so OP-TEE can run
       deferred work.

   Confirm it:
     $ dmesg | grep optee
     optee: Asynchronous notifications enabled

   Without it, a TA that wants to wait for a secure interrupt
   must poll, holding a thread - which is exactly the pattern
   that exhausts the pool.                                  */

The deadlock, in full

Because the secure world can call out while the normal world is calling in, the two can wait on each other. The rules that prevent that are worth knowing before you design a protocol.

   CFG_NUM_THREADS = 4. Four application threads each invoke a
   TA that writes to secure storage.

     thread 1  in OP-TEE, blocked on RPC_CMD_FS
     thread 2  in OP-TEE, blocked on RPC_CMD_FS
     thread 3  in OP-TEE, blocked on RPC_CMD_FS
     thread 4  in OP-TEE, blocked on RPC_CMD_FS

   All four OP-TEE threads are held. Every one is waiting for
   tee-supplicant.

   tee-supplicant CAN service them - one at a time - and
   normally does, and everything is merely slow.

   It deadlocks when tee-supplicant itself cannot run:

     * tee-supplicant's own thread tries to invoke a TA
       (never do this)
     * the storage it must write to is on a filesystem that is
       itself waiting on something blocked in the TEE
     * an out-of-memory condition stops it being scheduled
     * a single-threaded supplicant is servicing a request that
       blocks on a device that is unresponsive

   Symptom: total silence. No error, no timeout, no log line.
   Every client hangs in ioctl(). The secure console shows
   nothing because OP-TEE is not running.

   DIAGNOSING IT:
     $ cat /proc/<client-pid>/stack        # blocked in optee
     $ cat /proc/<supplicant-pid>/stack    # what is IT waiting
                                             for?
     $ echo t > /proc/sysrq-trigger        # all task stacks

   AVOIDING IT:
     * never call into the TEE from a process that services the
       TEE
     * set CFG_NUM_THREADS comfortably above your peak
       concurrency
     * keep RPC-using operations (secure storage) off hot paths
     * give tee-supplicant a favourable scheduling class if it
       is on a loaded system
     * cancel long operations with TEEC_RequestCancellation
       from a watchdog thread
