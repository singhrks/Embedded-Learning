Undefined behaviour and the optimiser

Why a compiler deletes your bounds check, why a bug appears only at -O2, and why "it worked before" is not evidence. Undefined behaviour is not a bug in the compiler — it is a licence you granted it, and this chapter is about what it does with that licence.

The contract

   THE C STANDARD says: if a program executes undefined
   behaviour, the standard imposes NO REQUIREMENTS on what
   happens.

   THE OPTIMISER READS THAT CONTRAPOSITIVELY:

     "The programmer promised this program has no UB.
      Therefore I may ASSUME the conditions that would cause
      UB never occur, and optimise on that assumption."

   That is not aggressive interpretation - it is the only
   interpretation that makes optimisation possible at all.
   Every optimisation is "this transformation preserves
   behaviour for all DEFINED executions".

   THE CONSEQUENCES that surprise people:

     · UB is not "does something unpredictable at that line".
       It can affect code BEFORE it, because the compiler
       reasons backwards.

     · UB in a branch that is never taken can still change
       your program, because the compiler used it to conclude
       the branch is unreachable.

     · "It works" is not evidence of correctness. It is
       evidence that this compiler, at this optimisation
       level, this week, happened to choose an outcome you
       liked.

   FOUR CATEGORIES, and the difference matters:
     UNDEFINED         anything may happen
     UNSPECIFIED       one of several behaviours, no record
                       (argument evaluation order)
     IMPLEMENTATION-DEFINED   one of several, DOCUMENTED
                       (whether char is signed)
     LOCALE-SPECIFIC

The pattern behind all of them

The compiler is not looking for your UB and punishing it. It is doing ordinary reasoning — "this pointer was dereferenced, so it is non-null"; "this loop counter is int, so it does not wrap" — and propagating the conclusion. The transformation is correct for every program without UB. Yours has UB, so it is outside the set the compiler promised anything about.

Finding it

# --- UBSAN: the single most valuable tool here ---
    gcc -fsanitize=undefined -fno-sanitize-recover=all -g
    clang -fsanitize=undefined,integer,nullability -g

# It instruments the program and reports at RUN TIME:
    prog.c:10:12: runtime error: signed integer overflow:
    2147483647 + 1 cannot be represented in type 'int'

# WHAT IT CHECKS:
    signed integer overflow      shift out of range
    null dereference             misaligned access
    array bounds (with known sizes)
    division by zero             invalid enum/bool values
    float-to-int overflow        unreachable code reached
    object size violations       vptr misuse (C++)
    function pointer type mismatch

# COST: roughly 20% slower. Cheap enough to run all your tests
# under. THE MINIMAL PRODUCTION SUBSET:
    -fsanitize=undefined -fsanitize-minimal-runtime \
    -fno-sanitize-recover=all
# which traps rather than printing, and costs very little.

# --- ASAN: memory errors ---
    -fsanitize=address -fno-omit-frame-pointer
# use-after-free, buffer overflow, double free, leaks.
# ~2x slower, 3x memory. Reports with the allocation and free
# stacks.

# --- TSAN: data races ---
    -fsanitize=thread
# ~10x slower, but it finds races that no amount of testing
# will.

# --- MSAN: uninitialised reads (clang) ---
    -fsanitize=memory
# Requires ALL code including libraries to be instrumented,
# which is the practical obstacle.

# --- STATIC ANALYSIS ---
    gcc -fanalyzer             ; GCC 10+, genuinely good
    clang --analyze
    clang-tidy
    cppcheck
    scan-build make

# --- COMPILER WARNINGS THAT SPECIFICALLY CATCH UB ---
    -Wall -Wextra
    -Wstrict-aliasing=2
    -Warray-bounds=2
    -Wnull-dereference
    -Wshift-overflow=2
    -Wsequence-point
    -Wuninitialized -Wmaybe-uninitialized

# THE COMBINATION THAT FINDS THE MOST, in practice:
#   -Wall -Wextra -Werror in CI
#   + all tests under UBSan and ASan
#   + a nightly TSan run if threaded
# That catches the overwhelming majority of what this chapter
# describes.

Writing code that has none

/* --- CHECK BEFORE, NOT AFTER --- */
        if (p == NULL) return;
        int x = *p;                     /* right order */

/* --- CHECK OVERFLOW WITHOUT CAUSING IT --- */
        /* WRONG: */
        if (a + b < a) overflow();      /* the add is already
                                           UB               */
        /* RIGHT: */
        if (a > INT_MAX - b) overflow();
        /* OR, best: */
        int result;
        if (__builtin_add_overflow(a, b, &result))
                overflow();
        /* which compiles to one add plus a branch on the
           carry flag - no cost at all on ARM             */

/* --- USE UNSIGNED FOR BIT MANIPULATION --- */
        uint32_t mask = 1u << 31;       /* defined */
        int32_t  bad  = 1 << 31;        /* UB */

/* --- TYPE-PUN WITH memcpy --- */
        uint32_t u;
        memcpy(&u, &f, sizeof u);
        /* every compiler recognises this and emits ZERO
           instructions for it when the types are
           register-sized                                  */

/* --- PASS SIZES, ALWAYS --- */
        void f(int *a, size_t n);       /* not `int a[]` and
                                           a guess          */

/* --- USE THE SAFE STRING FUNCTIONS --- */
        strscpy(dst, src, sizeof dst);      /* kernel */
        snprintf(buf, sizeof buf, ...);
        /* never strcpy, strcat, sprintf, gets */

/* --- ENABLE THE FLAGS THAT NARROW UB --- */
        -fwrapv                 signed overflow wraps
        -fno-strict-aliasing    type punning permitted
        -fno-delete-null-pointer-checks
        -ftrivial-auto-var-init=zero     initialise locals
/* THE KERNEL USES ALL FOUR. They cost some optimisation and
   remove whole bug classes, which for a codebase of that size
   and lifetime is clearly the right trade. For your code,
   decide deliberately rather than by default.

/* --- AND THE STRUCTURAL ONES --- */
/*   · prefer array indices to pointer arithmetic
     · keep buffer sizes next to buffers, or use a struct
     · make invalid states unrepresentable where you can
     · initialise at declaration
     · one exit point for resources (C ch. 26 / cmp ch. 06) */

The language design answer

LanguageApproach to UB
C, C++Extensive UB, for optimisation freedom and to accommodate every historical machine
Java, C#Almost none: bounds checked, integers wrap, null throws. Pays runtime cost
GoAlmost none; bounds checked, but data races are still UB
RustNone in safe code — the compiler proves it away. UB is confined to unsafe blocks, which are auditable and rare (Rust ch. 02)
ZigUB is checked in debug builds, assumed in release — an explicit, per-build choice
Ada/SPARKChecked by default; provably absent with formal verification

This is the strongest single argument for Rust in systems programming, and it is worth stating precisely: Rust does not eliminate the hardware realities — it moves the burden of proving the absence of UB from the programmer's discipline to the compiler's type system, and confines the cases it cannot prove to blocks you must write unsafe on. The bugs in this chapter do not become easier to find; they become impossible to write outside a marked region.

Works at -O0, fails at -O2Almost certainly UB somewhere
