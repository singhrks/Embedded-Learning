Pi 4 and Pi 5: the differences that matter

The Pi 5 is not a faster Pi 4. It moved every low-speed peripheral onto a separate chip across a PCIe link, which changes register addresses, GPIO numbering, and every piece of code that talked to hardware directly. This chapter is the map of what actually differs.

Which to buy for this track

Either works, and nothing in this track is Pi-5-only. Buy a Pi 5 if you want the faster kernel builds (chapter 15 is roughly twice as fast), NVMe boot, and the more modern architecture. Buy a Pi 4 if you want peripherals in the SoC where the classic register-level documentation applies, or if you already own one. The Pi 4's simpler topology is arguably the better teacher for the ARM track; the Pi 5's RP1 split is the better teacher for how real SoCs are actually built.

The change that breaks code

   PI 4 — everything in one chip

   +--------------------------------------+
   |  BCM2711                             |
   |   A72 x4 --- bus --- GPIO            |
   |                  |-- I2C, SPI, UART  |
   |                  |-- PWM             |
   |                  +-- SD, DSI, CSI    |
   |                                      |
   |   PCIe --> VL805 (USB only)          |
   +--------------------------------------+

   A peripheral register is at a fixed physical address.
   mmap /dev/mem at 0xFE200000 and you are talking to GPIO.
   Every classic Pi tutorial does this.

   PI 5 — a southbridge

   +---------------------+        +---------------------+
   |  BCM2712            |  PCIe  |  RP1                |
   |   A76 x4            |<======>|   GPIO              |
   |   memory, video     |  x4    |   I2C, SPI, UART    |
   |   PCIe root         |  gen2  |   PWM, PIO          |
   +---------------------+        |   USB, Ethernet     |
                                  |   CSI/DSI           |
                                  +---------------------+

   Now a GPIO write is a PCIe transaction to another chip.

   WHAT THIS BREAKS:
     - fixed peripheral addresses: gone
     - /dev/mem poking: the addresses are different, and
       the mapping is not what tutorials assume
     - bcm2835 / wiringPi style libraries: dead on Pi 5
     - GPIO chip numbering: the header is on a DIFFERENT
       gpiochip, and which number varies by kernel version
     - anything that assumed one clock domain for GPIO

   WHAT THIS DOES NOT BREAK:
     - libgpiod (chapter 11)
     - /dev/i2c-*, /dev/spidev*, /dev/ttyAMA* (chapter 12)
     - kernel drivers written against the proper subsystems
     - device tree overlays (chapter 10)

   THE LESSON, and it generalises far beyond the Pi: code
   written against the KERNEL'S ABSTRACTION survived a
   complete change of hardware topology. Code written
   against physical addresses did not. That is the entire
   argument for the driver model.

The GPIO numbering trap

# The 40-pin header is not always gpiochip0. On a Pi 5 the
# RP1 gpiochip has been numbered differently across kernel
# releases, and hardcoding the number is a guaranteed
# future break.

# WRONG - works today on one machine, fails elsewhere
gpioset gpiochip0 17=1

# RIGHT - ask for it by LABEL and let the library resolve it
$ gpiodetect
gpiochip0 [gpio-brcmstb@107d508500] (32 lines)
gpiochip1 [gpio-brcmstb@107d508520] (4 lines)
gpiochip2 [gpio-brcmstb@107d517c30] (17 lines)
gpiochip3 [gpio-brcmstb@107d517c40] (6 lines)
gpiochip4 [rp1] (54 lines)          <-- the 40-pin header

# Find it by name rather than index:
$ gpiofind GPIO17
gpiochip4 17

# In libgpiod v2, resolve by chip label at runtime; in
# scripts, use gpiofind. The output above is from one
# particular Pi 5 kernel - CHECK YOURS rather than copying
# the number, because this is exactly the thing that moves.

# On a Pi 4 the header is normally gpiochip0, which is why
# so much example code hardcodes it and why so much example
# code is broken on a Pi 5.
Pin numbering has three competing schemes, and they all appear in documentation 
   BCM number   the SoC's GPIO number. What the kernel,
                device tree, libgpiod and this track use.
                "GPIO17"

   Physical     the position on the 40-pin header, 1-40.
                What a wiring diagram uses. "pin 11"

   WiringPi     a third scheme from a now-deprecated
                library. Still all over the internet.
                "wiringPi pin 0"

   GPIO17 = physical pin 11 = wiringPi 0. Same wire.

   ALWAYS STATE WHICH SCHEME YOU MEAN. Most Pi wiring
   mistakes are a BCM number read as a physical pin: BCM 3
   is physical pin 5, but physical pin 3 is BCM 2. Both are
   plausible, both are I2C-adjacent, and the error is
   invisible until nothing responds.

Architectural differences worth knowing

# The A76 is ARMv8.2-A; the A72 is ARMv8-A. That gains you
# features the ARM track discusses:

$ cat /proc/cpuinfo | grep Features
# Pi 4 (A72):
#   fp asimd evtstrm crc32 cpuid
# Pi 5 (A76):
#   fp asimd evtstrm aes pmull sha1 sha2 crc32 atomics
#   fphp asimdhp cpuid asimdrdm lrcpc dcpop asimddp

# The ones that matter:
#   aes, pmull, sha1, sha2  hardware crypto - see the
#                           cryptography track. AES on the
#                           Pi 5 is an order of magnitude
#                           faster than on a Pi 4.
#   atomics (LSE)           ARMv8.1 large-system extensions:
#                           real atomic instructions rather
#                           than load-exclusive loops. See
#                           the ARM track, chapter 22.
#   asimddp                 dot product, for ML workloads
#   lrcpc                   release-consistent loads

# Check exception level - both boot Linux at EL2 so KVM
# works (virtualisation track):
$ dmesg | grep -i "CPU: All CPU"
[    0.000000] CPU: All CPU(s) started at EL2

# EL2 is why you can run KVM on a Pi. If you ever see EL1
# here, the firmware dropped you and virtualisation is
# unavailable.
