Atomics, RCU and lockless techniques

RCU lets readers run with zero synchronisation overhead — no atomics, no cache-line bouncing, no waiting. The price is a discipline about how updates are published and when memory can be freed, and it rests entirely on the memory model from ARM chapters 20 and 21.

The idea

RCU solves a problem that sounds impossible at first: letting readers run with no locking whatsoever, no waiting and almost no cost, while writers change the data underneath them. The trick is that writers never modify anything in place — they publish a new version and leave the old one alone until every reader that might still be looking at it has finished.

A pointer to a data structure, read constantly, updated rarely.

  WITH A LOCK: every reader takes and releases the lock. On an
  8-core system that is one cache line ping-ponging between
  all eight caches, thousands of times a second, purely to
  read data that almost never changes.

  WITH RCU: readers do NOTHING. No atomic, no write, no wait.
  The update instead works like this:

     1. the writer makes a NEW copy with the change
     2. it publishes the new one with a single pointer store
     3. new readers see the new version; readers already
        running keep using the old one - which is fine,
        because it is still a consistent, valid version
     4. the writer WAITS until every reader that could still
        hold the old pointer has finished
     5. only then does it free the old copy

  Read - Copy - Update. Step 4 is the whole trick, and it is
  cheap because of a clever definition of "finished".

     time ->
     reader A: [--- reads old ---]
     reader B:      [------ reads old ------]
     writer:     publish new
                          |
                          +-- grace period --+
                                             |
                                          free old
                                       (A and B are done;
                                        anyone starting after
                                        "publish" sees new)

Grace periods, and why they are cheap

The obvious question is how the writer knows when it is safe to free the old version, given that readers announce nothing. The answer is the clever part, and it is why RCU reads cost nothing: instead of tracking readers, the kernel waits for a moment when every CPU has demonstrably finished any read it could have started.

/* THE KEY OBSERVATION: an RCU read-side critical section may
   not sleep or be preempted (in classic RCU). So if a CPU has
   passed through a CONTEXT SWITCH, it cannot possibly still be
   inside one.

   A "quiescent state" = context switch, idle, or userspace.
   A "grace period"    = every CPU has passed through at least
                         one quiescent state since the update.

   So RCU does not track individual readers at all. It waits
   for a system-wide condition that is already being reported
   for other reasons. That is why readers cost NOTHING - there
   is nothing to record.

   Typical grace period: a few milliseconds to tens of ms.
   RCU is therefore for data where UPDATES ARE RARE and the
   latency of reclaiming memory does not matter.           */

The API

The API is small, and most of it exists to tell the compiler and CPU what they may not reorder. The calls below do almost nothing at runtime — that is the point — but leaving one out breaks the guarantee in ways that only appear on some processors, under load.

#include <linux/rcupdate.h>

/* --- READER ---------------------------------------------- */
        rcu_read_lock();                /* NOT a lock. It just
                                           marks the section
                                           and disables
                                           preemption.       */
        p = rcu_dereference(gp);        /* the ONLY correct
                                           way to read the
                                           pointer           */
        if (p)
                use(p->field);          /* safe until
                                           rcu_read_unlock  */
        rcu_read_unlock();

/* RULES for the read side:
     · MAY NOT SLEEP inside (unless using SRCU)
     · the pointer is only valid INSIDE the section. Do not
       stash it in a global and use it later.
     · rcu_dereference() carries the dependency barrier that
       makes the ARM memory model safe here - a plain read is
       NOT equivalent (see below).

/* --- WRITER ---------------------------------------------- */
        struct foo *new, *old;

        new = kmalloc(sizeof(*new), GFP_KERNEL);
        *new = *old_contents;
        new->field = updated_value;      /* fully initialise
                                            BEFORE publishing */

        spin_lock(&update_lock);         /* writers still need
                                            mutual exclusion
                                            with EACH OTHER   */
        old = rcu_dereference_protected(gp,
                        lockdep_is_held(&update_lock));
        rcu_assign_pointer(gp, new);     /* PUBLISH */
        spin_unlock(&update_lock);

        synchronize_rcu();               /* wait for the grace
                                            period - SLEEPS  */
        kfree(old);

/* OR, without blocking: */
        call_rcu(&old->rcu_head, my_free_cb);
        /* the callback runs after the grace period */

static void my_free_cb(struct rcu_head *h)
{
        struct foo *p = container_of(h, struct foo, rcu_head);
        kfree(p);
}
/* For a plain kfree there is a shortcut: */
        kfree_rcu(old, rcu_head);
Why rcu_assign_pointer and rcu_dereference are not optional

They are the memory barriers that make this correct on a weakly-ordered machine like ARM (ARM chapters 20 and 21). rcu_assign_pointer is a release store: it guarantees the initialisation of the new object is visible before the pointer to it. rcu_dereference preserves the address dependency so the reader cannot observe the new pointer with stale contents. Write gp = new; and p = gp; instead and it will work on x86 and fail on ARM, rarely, under load — the worst possible failure mode.

RCU-protected lists

Since the commonest thing to protect this way is a list, the kernel provides RCU-aware list operations. They are ordinary list calls with the necessary publication ordering built in, and mixing them with the plain versions silently removes the protection.

/* The common real use: a list of devices, sessions, or rules,
   read on every operation, changed on hotplug.             */

        struct my_entry {
                struct list_head list;
                struct rcu_head  rcu;
                int              id;
                ...
        };

        LIST_HEAD(my_list);
        DEFINE_SPINLOCK(my_list_lock);   /* writers only */

/* --- READER: traverse without any lock ------------------- */
static struct my_entry *find_entry(int id)
{
        struct my_entry *e;

        list_for_each_entry_rcu(e, &my_list, list) {
                if (e->id == id)
                        return e;
        }
        return NULL;
}
        /* called as: */
        rcu_read_lock();
        e = find_entry(id);
        if (e)
                do_something(e->value);
        rcu_read_unlock();

/* --- WRITER: add --------------------------------------- */
        spin_lock(&my_list_lock);
        list_add_rcu(&new->list, &my_list);
        spin_unlock(&my_list_lock);
        /* no grace period needed to ADD - a reader either
           sees it or does not, and both are correct       */

/* --- WRITER: remove ------------------------------------- */
        spin_lock(&my_list_lock);
        list_del_rcu(&e->list);
        spin_unlock(&my_list_lock);

        synchronize_rcu();       /* now no reader holds e */
        kfree(e);
        /* or: kfree_rcu(e, rcu); */

/* NOTE list_del_rcu leaves the FORWARD pointer intact, so a
   reader already traversing the deleted node can still walk
   onward to the rest of the list. That is deliberate, and it
   is why you must use the _rcu variants rather than the
   ordinary list functions.                                */

The flavours

Plain RCU's rule that a reader may never sleep is a real restriction, not a formality, so the kernel offers several variants of the same read-side idea, each relaxing or specialising that rule for a different context — choosing between them is choosing which grace-period domain your reader actually needs to be counted in.

FlavourReaders may sleepUse
rcu_read_lock()NoThe default. Preemption disabled in the section.
rcu_read_lock_bh()NoData also touched from softirqs (networking).
rcu_read_lock_sched()NoPreempt-disable regions.
srcu_read_lock()YesSleepable RCU — readers may block. Per-domain, so one slow reader does not stall everyone.
RCU Tasks—For trampolines and tracing; waits for voluntary context switches.
 
/* SRCU, when a reader must sleep - e.g. it does I/O or copies
   to userspace: */

        struct srcu_struct my_srcu;
        init_srcu_struct(&my_srcu);

        int idx = srcu_read_lock(&my_srcu);
        p = srcu_dereference(gp, &my_srcu);
        ... may sleep here ...
        srcu_read_unlock(&my_srcu, idx);

        synchronize_srcu(&my_srcu);     /* the writer side */

/* SRCU grace periods can be MUCH longer, because a sleeping
   reader may sleep for a long time. Do not use it where you
   need memory back promptly.                              */

Barriers, briefly

Modern CPUs and compilers reorder memory accesses freely, and both will happily break code that depends on one write becoming visible before another. Barriers are how you forbid specific reorderings — a topic worth an entire track of its own, reduced here to what a driver author actually needs.

/* ARM is weakly ordered (ARM ch. 20-21). Without barriers,
   both the compiler and the CPU may reorder your accesses. */

        smp_mb()        full barrier
        smp_rmb()       reads before / reads after
        smp_wmb()       writes before / writes after
        smp_store_release(&p, v)    /* release store */
        v = smp_load_acquire(&p)    /* acquire load  */
        barrier()       compiler only, no CPU instruction

/* THE CANONICAL PAIR - publish a structure safely: */
        /* producer */
        obj->data = 42;
        smp_store_release(&shared_ptr, obj);

        /* consumer */
        p = smp_load_acquire(&shared_ptr);
        if (p)
                use(p->data);          /* guaranteed to be 42 */

/* WITHOUT the release/acquire pair, the consumer can observe
   shared_ptr as non-NULL while p->data is still stale. On
   arm64 this is not theoretical - it happens.

/* AND FOR DEVICE MEMORY, a DIFFERENT set (chapter 26):
        wmb()/rmb()/mb()       full barriers including devices
        dma_wmb()/dma_rmb()    ordering against a DMA engine
        writel()/readl()       already carry the ordering you
                               need for MMIO in most cases

   Do not use smp_* barriers for DMA ordering: the smp_
   variants compile to nothing on a UP kernel, and a DMA
   engine is a second agent regardless of how many CPUs you
   have. That substitution is a real and subtle bug.       */
The honest advice about lockless code

Use RCU where the pattern fits — a read-mostly pointer or list — because it is a well-tested framework with lockdep support and clear rules. Do not invent your own lockless algorithms. Hand-rolled lock-free code on a weakly-ordered architecture is beyond what code review reliably catches, and the bugs appear as one-in-a-billion corruption under load. If a mutex is fast enough, use the mutex.

Debugging RCU

RCU misuse rarely fails immediately; it produces rare corruption or a stall message long after the mistake. These options make the kernel check the rules on every access and complain the first time one is broken.

# Enable these while developing anything using RCU:
    CONFIG_PROVE_RCU=y              # lockdep for RCU
    CONFIG_DEBUG_OBJECTS_RCU_HEAD=y # double call_rcu, etc.
    CONFIG_RCU_EQS_DEBUG=y

# PROVE_RCU catches the big one - dereferencing outside a
# read-side section:

  WARNING: suspicious RCU usage
  drivers/mydrv/mydrv.c:142 suspicious rcu_dereference_check()
  usage!
  other info that might help us debug this:
  rcu_scheduler_active = 2, debug_locks = 1
  no locks held by mytask/431.

# "no locks held" = you called rcu_dereference() without
# rcu_read_lock(). A real bug, caught statically at runtime.

# If you legitimately hold a lock instead, say so:
    p = rcu_dereference_protected(gp, lockdep_is_held(&my_lock));

# RCU STALLS - a reader that never finishes:
  INFO: rcu_sched self-detected stall on CPU
# Means a CPU spent tens of seconds without a quiescent state.
# Causes: an infinite loop with preemption disabled, a very
# long rcu_read_lock section, or a spinlock deadlock.

# Watch grace periods and callbacks:
    cat /sys/kernel/debug/rcu/rcu_preempt/rcugp
    cat /proc/sched_debug | grep -i rcu

When RCU is the answer

RCU pays off specifically when reads vastly outnumber writes and readers cannot tolerate lock contention — the moment writes become frequent, or the reader needs anything stronger than "some recent, consistent snapshot," a lock or an atomic is the simpler and correct tool instead.

SituationRCU?
A list of registered devices, read on every I/OYes — the textbook case
A configuration structure, changed via sysfsYes
A routing or filter tableYes
A counterNo — use atomic_t or per-CPU
A queue with frequent adds and removesNo — grace periods will dominate
Data written as often as it is readNo — use a mutex
Memory that must be freed promptlyNo — grace periods delay reclamation
Readers that need a consistent view across two structuresNo — RCU gives per-pointer consistency only
