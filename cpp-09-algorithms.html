Iterators, algorithms and ranges

The standard algorithms are templates that compile to the same loop you would write by hand — but named, correct, and hard to get wrong. Almost all of them allocate nothing, which makes this the part of the standard library that transfers straight into embedded work.

Iterators

Iterators generalise pointers so that one algorithm can work with any container. They come in categories describing what they can do, and an algorithm's requirements are stated in terms of those categories.

An iterator generalises a pointer. The categories form a
hierarchy, and each algorithm requires a minimum category:

   input          read once, advance forward
      |           (an input stream)
   forward        read repeatedly, advance forward
      |           (forward_list, unordered_map)
   bidirectional  ...and backwards
      |           (list, map, set)
   random access  ...and jump: it += n, it2 - it1, it[n]
      |           (array, vector, deque, RAW POINTERS)
   contiguous     ...and the elements are adjacent in memory
                  (array, vector, span, pointers)  [C++20]

  A RAW POINTER IS A CONTIGUOUS ITERATOR. Every algorithm
  works on plain arrays:

        int a[10];
        std::sort(a, a + 10);
        std::sort(std::begin(a), std::end(a));

  WHY THE CATEGORY MATTERS: std::sort needs random access, so
  it cannot sort a std::list - which is why list has its own
  sort() member. std::advance is O(1) on random access and
  O(n) otherwise, which is why a loop calling it on a list is
  accidentally quadratic.

  THE RANGE CONVENTION is HALF-OPEN: [begin, end). end() is
  one past the last element and must not be dereferenced.
  This makes size = end - begin, an empty range is
  begin == end, and loops terminate naturally.

The algorithms worth knowing

The standard algorithms replace hand-written loops with named operations. The benefit is not brevity but correctness — the off-by-one errors are written once, in the library, rather than in every loop you write.

#include <algorithm>
#include <numeric>

/* --- SEARCHING --- */
        std::find(b, e, value);
        std::find_if(b, e, pred);
        std::count(b, e, value);
        std::count_if(b, e, pred);
        std::all_of(b, e, pred);  any_of  none_of
        std::binary_search(b, e, value);        /* SORTED */
        std::lower_bound(b, e, value);          /* SORTED */
        std::upper_bound(b, e, value);
        std::equal_range(b, e, value);
        std::search(b, e, sb, se);              /* subsequence */
        std::min_element(b, e);  max_element  minmax_element

/* --- MODIFYING --- */
        std::copy(b, e, out);
        std::copy_if(b, e, out, pred);
        std::copy_n(b, n, out);
        std::move(b, e, out);           /* moves elements */
        std::fill(b, e, value);
        std::iota(b, e, 0);             /* 0,1,2,3,... */
        std::generate(b, e, fn);
        std::transform(b, e, out, fn);
        std::transform(b1, e1, b2, out, binary_fn);
        std::replace(b, e, old, new);
        std::reverse(b, e);
        std::rotate(b, mid, e);
        std::swap_ranges(b1, e1, b2);

/* --- REMOVING: the erase-remove idiom --- */
        v.erase(std::remove(v.begin(), v.end(), value),
                v.end());
/* std::remove does NOT remove - it SHIFTS the kept elements
   forward and returns the new logical end. The container
   still holds the old size until erase() is called. This
   surprises everyone once.
   C++20 has the sane spelling:                            */
        std::erase(v, value);
        std::erase_if(v, pred);

/* --- SORTING --- */
        std::sort(b, e);                /* introsort, O(n log n),
                                           NOT stable      */
        std::stable_sort(b, e);         /* may ALLOCATE */
        std::partial_sort(b, mid, e);   /* top-k only */
        std::nth_element(b, nth, e);    /* O(n) selection */
        std::is_sorted(b, e);
        std::partition(b, e, pred);
        std::stable_partition(b, e, pred);   /* may allocate */

/* --- NUMERIC --- */
        std::accumulate(b, e, init);
        std::accumulate(b, e, init, binary_op);
        std::reduce(b, e);              /* C++17, may be
                                           parallel/reordered */
        std::inner_product(b1, e1, b2, init);
        std::partial_sum(b, e, out);
        std::adjacent_difference(b, e, out);
        std::clamp(v, lo, hi);          /* <algorithm> */
        std::gcd(a, b);  std::lcm(a, b);  /* <numeric> */

/* --- COMPARING --- */
        std::equal(b1, e1, b2);
        std::lexicographical_compare(b1, e1, b2, e2);
        std::mismatch(b1, e1, b2);

/* WHICH ONES ALLOCATE - the only three that matter for
   embedded:
        std::stable_sort
        std::stable_partition
        std::inplace_merge
   Every other algorithm in this list allocates nothing.  */
Why use them rather than a hand-written loop

They compile to the same instructions — std::find on a span<int> is byte-identical to the loop you would write, and often better because the implementation is specialised for contiguous ranges and vectorises. What you gain is a name at the call site, no off-by-one, no inverted comparison, and correct behaviour on empty ranges. That last one is where hand-written loops actually fail.

Lambdas

A lambda is an anonymous function object, and what matters for systems work is the capture list: it determines whether the lambda allocates, what it keeps alive, and whether it can outlive the scope that made it.

        auto is_even = [](int x) { return x % 2 == 0; };

        int threshold = 10;
        auto above = [threshold](int x) { return x > threshold; };
                                        /* capture BY VALUE */
        auto count_it = [&count](int x) { if (x) count++; };
                                        /* capture BY REFERENCE */

/* CAPTURE FORMS: */
        [ ]             nothing
        [x]             x by value
        [&x]            x by reference
        [=]             everything used, by value    (avoid)
        [&]             everything used, by reference (avoid)
        [this]          the enclosing object's members
        [*this]         a COPY of the enclosing object (C++17)
        [x = expr]      init capture: a new variable
        [p = std::move(ptr)]    move into the lambda

/* PREFER EXPLICIT CAPTURES. `[&]` in a lambda that outlives
   the scope is a dangling reference, and the capture list is
   the only place a reader can see what the lambda depends
   on.

/* WHAT A LAMBDA IS: a compiler-generated class with an
   operator(), and one member per capture. */
        auto f = [a, b](int x) { return a * x + b; };
/* becomes, in effect: */
        struct __lambda {
                int a, b;
                int operator()(int x) const { return a*x + b; }
        };
/* A CAPTURELESS lambda is an empty class, converts to a plain
   function pointer, and costs nothing at all:            */
        void (*fp)(int) = [](int x) { handle(x); };
/* which is how you pass one as a C callback (chapter 16).

/* GENERIC LAMBDAS (C++14): */
        auto print = [](const auto& x) { log(x); };
/* `auto` parameters make operator() a template.

/* THE COST QUESTION: a lambda passed to an algorithm as a
   template parameter is INLINED COMPLETELY - zero cost.
   Stored in a std::function it is type-erased: possibly a
   heap allocation and an indirect call. That difference is
   the whole story (chapter 01).                          */

        template<typename F> void each(F f);   /* free */
        void each(std::function<void(int)> f); /* not free */

Ranges

Ranges let algorithms take a container directly rather than a pair of iterators, and compose into pipelines. The convenience is real; the compile-time cost and error messages are too.

#include <ranges>       /* C++20 */
#include <algorithm>

/* 1. ALGORITHMS TAKE A RANGE, not two iterators: */
        std::ranges::sort(v);
        std::ranges::find(v, 42);
        std::ranges::copy(v, out);

/* Shorter, and it cannot mismatch begin and end from
   different containers - a real bug the iterator form
   permits.

/* 2. PROJECTIONS - apply a function before comparing: */
        struct Reading { uint32_t time; int16_t value; };
        std::vector<Reading> readings;

        std::ranges::sort(readings, {}, &Reading::time);
                                /* sort by .time, with the
                                   default comparator      */
        auto it = std::ranges::find(readings, 100,
                                    &Reading::value);
        auto m = std::ranges::max_element(readings, {},
                                          &Reading::value);

/* This replaces a lambda per call, and reads better.

/* 3. VIEWS - lazy, composable, non-owning: */
        namespace v = std::views;

        for (int x : v | v::filter([](int i){ return i > 0; })
                       | v::transform([](int i){ return i * 2; })
                       | v::take(10))
                use(x);

/* LAZY means no intermediate container is created - the
   pipeline is fused into one loop, and generates the same
   code as the hand-written version.

        v::iota(0, 10)          /* 0..9 without a container */
        v::reverse
        v::drop(n)  v::take(n)
        v::take_while(pred)  v::drop_while(pred)
        v::split(delim)
        v::join
        v::keys  v::values      /* for pairs */
        v::enumerate            /* C++23: index and value */
        v::chunk(n)  v::slide(n)    /* C++23 */
        v::zip                  /* C++23 */

/* AN EMBEDDED-RELEVANT EXAMPLE: */
        for (auto [i, sample] : v::enumerate(buffer
                                | v::filter(is_valid)
                                | v::take(MAX_SAMPLES)))
                process(i, sample);

/* THE CAVEATS FOR EMBEDDED:
     · ranges support in older toolchains is patchy; check
       before committing to it
     · compile times increase noticeably
     · error messages, without concepts support, are poor
     · debugging a pipeline is harder than debugging a loop
     · SOME views allocate (ranges::to, split on some
       implementations) - check what you use

   THE VERDICT: ranges are excellent, and worth adopting on
   embedded Linux with a modern toolchain. On a
   microcontroller with a vendor GCC 8, they are not
   available anyway.                                      */

Algorithms on embedded

Most standard algorithms are perfectly usable on a constrained target because they neither allocate nor throw. Knowing which ones do is what lets you use the library confidently rather than avoiding it wholesale.

/* Almost all of them are directly usable. Some examples that
   earn their place: */

/* --- on a fixed buffer --- */
        std::array<int16_t, 256> samples;

        auto peak = *std::max_element(samples.begin(),
                                      samples.end());
        auto sum  = std::accumulate(samples.begin(),
                                    samples.end(), 0);
        std::transform(samples.begin(), samples.end(),
                       output.begin(),
                       [](int16_t s) { return s * gain >> 8; });

/* --- on a span, so it works with any buffer --- */
        int16_t rms(std::span<const int16_t> s)
        {
                auto sq = std::inner_product(
                        s.begin(), s.end(), s.begin(), 0LL);
                return isqrt(sq / s.size());
        }

/* --- searching a constexpr table (chapter 08) --- */
        auto it = std::lower_bound(table.begin(), table.end(),
                                   key, by_key);

/* --- and the compile-time versions --- */
        static_assert(std::is_sorted(table.begin(),
                                     table.end(), by_key));
/* Most algorithms became constexpr in C++20, so you can run
   them on constexpr data and assert the result.

/* WHAT TO WATCH:

   1. THE THREE ALLOCATING ALGORITHMS - stable_sort,
      stable_partition, inplace_merge. Use sort and partition
      instead unless stability matters.

   2. std::sort IS INTROSORT: quicksort, falling back to
      heapsort, with insertion sort for small ranges. Its
      WORST CASE is O(n log n), so it is real-time-safe in
      complexity - but its constant factor and code size are
      substantial. For fewer than about 32 elements, an
      insertion sort you write yourself is smaller and
      faster.

   3. CODE SIZE: each instantiation of sort for a distinct
      type and comparator is a separate copy of a fairly large
      function. Check with nm --size-sort.

   4. std::reduce and the parallel algorithms (std::execution)
      have no place on a microcontroller - and on embedded
      Linux they need a threading runtime.               */

Writing your own

Writing your own algorithm in the same style makes it work with any container and compose with the standard ones. It is less work than it appears.

/* Follow the same conventions and your code composes with
   the standard library. */

template<typename It, typename T>
constexpr It find_last(It first, It last, const T& value)
{
        It result = last;
        for (; first != last; ++first)
                if (*first == value)
                        result = first;
        return result;
}

/* THE CONVENTIONS:
     · take [first, last), return an iterator
     · return `last` to mean "not found"
     · take the predicate or comparator as a template
       parameter, never std::function
     · mark it constexpr if it can be
     · require the WEAKEST iterator category that works

/* A RANGE-BASED VERSION, and a concept to constrain it: */
template<std::ranges::forward_range R, typename T>
constexpr auto find_last(R&& r, const T& value)
{
        return find_last(std::ranges::begin(r),
                         std::ranges::end(r), value);
}

/* AND A CUSTOM ITERATOR, when you need to present something
   as a range - a hardware FIFO, for example: */
class FifoIterator {
        Fifo *f_;
        bool  at_end_;
public:
        using iterator_category = std::input_iterator_tag;
        using value_type        = uint8_t;
        using difference_type   = std::ptrdiff_t;
        using pointer           = const uint8_t *;
        using reference         = uint8_t;

        uint8_t operator*() const  { return f_->peek(); }
        FifoIterator& operator++() { f_->pop();
                                     at_end_ = f_->empty();
                                     return *this; }
        bool operator==(const FifoIterator& o) const
                { return at_end_ == o.at_end_; }
};
/* Now std::copy, std::find and the rest work on your FIFO,
   with no allocation and no intermediate buffer.        */
