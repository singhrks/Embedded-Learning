Decoding a HardFault

A HardFault is not a mystery. The hardware records what happened, where, and in which instruction — you simply have to read four registers and know where the stack frame is. This chapter turns the most feared event on Cortex-M into a five-minute procedure.

The fault taxonomy

   CONFIGURABLE FAULTS - specific, informative, and DISABLED
   at reset:

     MemManage   MPU permission violation (chapter 14)
     BusFault    the bus said no: bad address, peripheral
                 with no clock, external memory not ready
     UsageFault  undefined instruction, illegal state,
                 unaligned access, divide by zero

   HARDFAULT - the catch-all. You land here when:

     a) the specific fault is not enabled (the default!), so
        it ESCALATES; or
     b) a fault occurs inside a fault handler; or
     c) a fault occurs at a priority that cannot be
        preempted - "priority escalation".

   FIRST ACTION IN ANY NEW PROJECT: enable the specific
   faults, so you get the informative one instead of the
   catch-all.

     SCB->SHCSR |= SCB_SHCSR_USGFAULTENA_Msk
                |  SCB_SHCSR_BUSFAULTENA_Msk
                |  SCB_SHCSR_MEMFAULTENA_Msk;

   This one line converts "HardFault, no information" into
   "UsageFault, UNALIGNED, at address X" and saves hours on
   every future bug.

The Configurable Fault Status Register

/* CFSR at 0xE000ED28 packs all three status bytes. */

/*  MMFSR   bits 0-7    MemManage
      0  IACCVIOL   instruction fetch from XN region
      1  DACCVIOL   data access violation
      3  MUNSTKERR  fault unstacking on exception return
      4  MSTKERR    fault stacking on entry = STACK OVERFLOW
      5  MLSPERR    fault during lazy FP stacking
      7  MMARVALID  MMFAR is valid

    BFSR    bits 8-15   BusFault
      8  IBUSERR       instruction bus error
      9  PRECISERR     data error, BFAR holds the address
     10  IMPRECISERR   data error, address UNKNOWN (see below)
     11  UNSTKERR      unstacking error
     12  STKERR        stacking error
     13  LSPERR        lazy FP stacking error
     15  BFARVALID     BFAR is valid

    UFSR    bits 16-31  UsageFault
     16  UNDEFINSTR    undefined instruction
     17  INVSTATE      invalid state - usually the Thumb bit
     18  INVPC         invalid PC on exception return
     19  NOCP          coprocessor absent - FPU not enabled
     24  UNALIGNED     unaligned access
     25  DIVBYZERO     divide by zero (if DIV_0_TRP set)  */

/* The three that account for most real faults:

   PRECISERR + BFARVALID
     A bad pointer, and BFAR names the address. Usually a
     null pointer (address near 0) or a peripheral whose
     clock is off (address in 0x4xxxxxxx).

   IMPRECISERR
     The write was buffered; the core moved on before the
     bus reported the error, so the address is LOST. Fix by
     putting a DSB after suspect writes to force precision
     while debugging, or set DISDEFWBUF in ACTLR to disable
     write buffering entirely - slow, but every fault
     becomes precise.

   MSTKERR
     Stack overflow, caught by an MPU guard region. The most
     valuable single bit on the chip.                      */

Reading the stacked frame

The hardware pushed eight registers before entering the handler. The stacked PC is the instruction that faulted, and that is what you actually want.

/* Step 1: a naked handler that finds the right stack and
   hands it to C. EXC_RETURN bit 2 says which one.         */

__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile (
        "tst   lr, #4            \n"  /* bit 2 of EXC_RETURN */
        "ite   eq                \n"
        "mrseq r0, msp           \n"  /* clear -> MSP        */
        "mrsne r0, psp           \n"  /* set   -> PSP        */
        "b     hardfault_report  \n"
    );
}

/* Step 2: the frame, in the order the hardware pushed it. */
typedef struct {
    uint32_t r0, r1, r2, r3;
    uint32_t r12;
    uint32_t lr;      /* return address of the faulting fn */
    uint32_t pc;      /* THE FAULTING INSTRUCTION          */
    uint32_t psr;
} frame_t;

void hardfault_report(frame_t *f)
{
    uint32_t cfsr = SCB->CFSR;
    uint32_t hfsr = SCB->HFSR;

    /* HFSR bit 30 = FORCED: a configurable fault escalated.
       If this is set, CFSR tells you the real cause.      */

    fault_log_t *log = &g_crash_log;      /* in .noinit    */
    log->magic = 0xDEADBEEF;
    log->pc    = f->pc;
    log->lr    = f->lr;
    log->cfsr  = cfsr;
    log->hfsr  = hfsr;
    log->bfar  = (cfsr & (1u << 15)) ? SCB->BFAR : 0;
    log->mmfar = (cfsr & (1u << 7))  ? SCB->MMFAR : 0;

    __asm volatile ("bkpt #0");   /* halt if debugger present */
    NVIC_SystemReset();           /* otherwise reboot          */
}

/* Step 3: turn the PC into a line of source.

     $ arm-none-eabi-addr2line -e firmware.elf -f -C 0x080012a4
     i2c_read
     /home/user/proj/src/i2c.c:142

   That is the whole procedure. Fault -> PC -> source line,
   in about a minute once the handler is in place.         */
Put the crash log in .noinit and report it after reboot

A fault handler that only halts is useful on your desk and useless in the field. Writing the log to a .noinit section (chapter 05) means it survives the reset; early in the next boot you check the magic number, transmit or store the record, and clear it. Now a unit that crashed in a customer's cabinet tells you the faulting PC when it comes back up. This costs about forty lines and is the difference between diagnosing a field failure and asking for the unit back.

The imprecise fault, and how to corner it

/* IMPRECISERR is the frustrating one: the address is gone
   and the stacked PC points several instructions past the
   real culprit. Three techniques, in order of cost:       */

/* 1. Disable the write buffer. Every fault becomes precise.
      Costs perhaps 10-20% performance - fine for a debug
      build.                                               */
SCnSCB->ACTLR |= SCnSCB_ACTLR_DISDEFWBUF_Msk;

/* 2. Bisect with barriers. Put __DSB() after groups of
      suspect writes; the fault becomes precise at whichever
      barrier follows the bad one.                          */

/* 3. Use the DWT watchpoint unit to trap writes to a
      specific address, which catches the corruptor rather
      than the victim - covered in chapter 16.              */

/* The single most common source: writing to a peripheral
   whose clock you have not enabled. The write is posted,
   the bus rejects it later, and the fault arrives with no
   address. If you see IMPRECISERR in code that just
   initialised a peripheral, check the RCC enable and the
   read-back (chapter 09) before anything else.            */
