Linked lists: reversal and surgery

No random access, no length, only next. Every linked-list problem is pointer manipulation, and every linked-list bug is a pointer you overwrote before you had finished with it.

The pattern

Linked-list questions test pointer discipline rather than insight. Three techniques cover nearly all of them, and each fails in the same way when a pointer is reassigned in the wrong order.

   THE THREE TECHNIQUES THAT SOLVE ALMOST EVERYTHING:

   1. REVERSAL — three pointers, one pass
        prev = null, cur = head
        while (cur) {
            next = cur.next     <-- SAVE FIRST. Always.
            cur.next = prev     <-- rewire
            prev = cur          <-- advance
            cur = next
        }
        return prev             <-- the new head

        null <- 1    2 -> 3 -> null
                ^    ^
              prev  cur

   2. DUMMY HEAD — removes every "what if it is the first
      node?" special case
        dummy = new ListNode(0, head)
        ... operate using `dummy` as a stable anchor ...
        return dummy.next

   3. TWO POINTERS — fast/slow for the middle, cycles and
      "nth from the end" (chapter 21)

   THE UNIVERSAL RULE:

     BEFORE YOU OVERWRITE A POINTER, SAVE WHAT YOU STILL
     NEED. Losing `cur.next` disconnects the rest of the
     list, and there is no way back — you cannot walk
     backwards.

   THE FOUR-LINE REVERSAL IS WORTH MEMORISING COLD. It
   appears inside palindrome checks, k-group reversal,
   reordering, and addition problems. If you can write it
   without thinking, a whole class of medium problems
   becomes routine.

   COSTS
     traverse / search      O(n)
     insert or delete at a KNOWN node   O(1)
     access the kth element O(n)     <-- no random access
     reverse                O(n) time, O(1) space

/* --- THE DUMMY-HEAD IDIOM, in full --- */
function removeElements(head, val) {
    const dummy = new ListNode(0, head);
    let prev = dummy;                  // ALWAYS a valid node
    while (prev.next) {
        if (prev.next.val === val) prev.next = prev.next.next;
        else                       prev = prev.next;
    }
    return dummy.next;   // correct even if the head was removed
}
/* WITHOUT the dummy you need a separate branch for
   "the node to delete is the head", and that branch is
   where the bug lives. USE A DUMMY WHENEVER THE HEAD MIGHT
   CHANGE.

   NOTE the else: only advance when you did NOT delete.
   Advancing after a deletion skips the next node — the
   most common bug in this shape, caught by [7,7,7,7]
   removing 7.                                            */
