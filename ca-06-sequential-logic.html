Sequential logic, flip-flops and state machines

Combinational logic computes. To remember — and therefore to have registers, caches, program counters or anything resembling a computer — you need feedback. This chapter is where storage comes from.

The problem

Every block in chapter 05 forgets its inputs the instant they change. A machine built only from those blocks cannot hold a value, cannot count, cannot have a program counter — it can only react.

The missing ingredient is feedback: route an output back to an input, and the circuit can hold itself in a state.

From feedback to a latch

Everything so far has been combinational — the output depends only on the inputs right now, and nothing is remembered. Memory appears the moment you feed an output back into an input, and that single change is the whole basis of storage.

SR latch — two cross-coupled NOR gates

        S ──►┌─────┐
             │ NOR │──┬──► Q
        ┌───►└─────┘  │
        │             │
        │  ┌──────────┘
        │  │
        └──┼──┐
           │  │
        ┌──▼──▼┐
   R ──►│ NOR  │─────► ~Q
        └──────┘

   S  R │ Q      behaviour
   ─────┼──────────────────────────
   0  0 │ hold   ← THE POINT: it remembers
   1  0 │  1     set
   0  1 │  0     reset
   1  1 │  ---   forbidden: both outputs 0, and the result on
                 release depends on gate timing (a race)

That "hold" row is the entire achievement. With S = R = 0, each gate's output feeds the other's input and the pair stays wherever it was. One bit is now stored — in nothing but the state of two gates driving each other.

Why latches are not enough

A plain latch is level-sensitive: while its enable is high, the output follows the input continuously. That transparency is dangerous — a signal can race through several latches in a single enable window, arriving somewhere it should not have reached until the next step.

Flip-flops: edge-triggered storage

A plain latch is transparent: while it is enabled, its output follows its input continuously, which makes it hard to reason about in a clocked system. A flip-flop fixes that by sampling only at one instant — the clock edge — which is what makes synchronous design possible.

D flip-flop — captures D only on the RISING EDGE of the clock

         ┌──────────┐
   D ───►│D        Q├───► Q
         │          │
  clk ──►│>         │
         └──────────┘

   clk:  ──┐   ┌───┐   ┌───┐   ┌──
           └───┘   └───┘   └───┘
              ▲       ▲       ▲
              │       │       │
           capture  capture  capture

Between edges, the output is frozen no matter what D does.
The circuit is now SYNCHRONOUS: state changes only at known instants.
Why edge-triggering makes design tractable

With edge-triggered storage, the whole machine advances in lockstep. Every combinational block gets one full clock period to settle, and the answer is sampled at a single, known instant. Reasoning reduces to a single question per path: does this settle in time? Without it, you would have to reason about overlapping propagation windows across the entire chip.

Registers

Put n flip-flops side by side, share the clock, and you have an n-bit register — the basic unit of storage in a processor.

Finite state machines

Combine a register (holding "which state am I in") with combinational logic (deciding "given this state and these inputs, what next"), and you have the general model of every controller in a computer.

        ┌────────────────────────────────────────┐
        │                                        │
  inputs├──►┌──────────────┐    ┌───────────┐    │
        │   │ next-state   │───►│  state    │────┴──► current state
        └──►│    logic     │    │ register  │
            └──────────────┘    └───────────┘
                                      │
                                      ▼
                              ┌──────────────┐
                              │ output logic │───► control signals
                              └──────────────┘

  Moore machine:  outputs depend only on the state
  Mealy machine:  outputs depend on state AND inputs (fewer states,
                  but outputs can glitch mid-cycle)

A worked example: a UART transmitter

   ┌──────┐  tx_start   ┌───────┐   bit sent   ┌──────┐
   │ IDLE ├────────────►│ START ├─────────────►│ DATA │
   └──────┘             └───────┘              └───┬──┘
       ▲                                           │ 8 bits sent
       │                                           ▼
       │              bit sent                 ┌──────┐
       └───────────────────────────────────────┤ STOP │
                                               └──────┘

  IDLE  : hold the line high, wait for tx_start
  START : drive the line low for one bit period
  DATA  : shift out 8 bits, LSB first, one per bit period
  STOP  : drive high for one bit period, then return to IDLE

That is the whole transmitter. Every serial protocol you will meet is
a state machine of this shape.
The same pattern in software

You will write this structure constantly in drivers, and for the same reason: a device's behaviour is naturally a state machine, and modelling it as one makes illegal transitions impossible to express rather than merely unlikely.

enum state { IDLE, START, DATA, STOP };

static void tick(struct uart *u)
{
        switch (u->state) {
        case IDLE:  if (u->pending) { line(0); u->state = START; } break;
        case START: line(u->byte & 1); u->bit = 1; u->state = DATA;  break;
        case DATA:  line((u->byte >> u->bit) & 1);
                    if (++u->bit == 8) u->state = STOP;              break;
        case STOP:  line(1); u->state = IDLE;                        break;
        }
}

Windows' PnP state machine, Linux's device probe/remove lifecycle and USB's enumeration are all the same idea at a larger scale.

Reset: the state you start in

On power-up, every flip-flop holds an arbitrary value — whichever way it happened to settle. A design without reset starts in a random state and behaves unpredictably.

KindBehaviourTrade-off
AsynchronousTakes effect immediately, no clock neededWorks before the clock is running — but releasing it near a clock edge can cause metastability
SynchronousApplied on a clock edge like any other inputClean and timing-analysable — but useless if the clock is not yet running
Async assert, sync releaseBothThe standard practice: assert immediately, release cleanly

This is why a datasheet lists a reset value for every register, why boot code must not assume a peripheral is in a known state unless it has reset it, and why "it works after a power cycle but not after a warm reset" is a recognisable class of bug — the two paths reset different things.
