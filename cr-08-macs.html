Message authentication codes

A keyed tag proving a message came from someone holding the key and has not been modified. This is the integrity half of chapter 01 — and the one place where a hand-rolled construction is almost guaranteed to be broken.

The model

Encryption hides content; it does not stop an attacker changing it. A message authentication code is what detects modification, and it answers a genuinely different question from confidentiality.

   MAC : key × message -> tag

   SENDER:    t = MAC(k, m);  send (m, t)
   RECEIVER:  t' = MAC(k, m); accept iff t' == t
                                        (in CONSTANT TIME)

   THE SECURITY GOAL: EXISTENTIAL UNFORGEABILITY under a
   CHOSEN-MESSAGE ATTACK (EUF-CMA).

     An adversary who can obtain tags for any messages they
     choose still cannot produce a valid (m, t) pair for any
     message they have not seen.

   WHAT A MAC PROVIDES:
     · INTEGRITY   - the message was not modified
     · AUTHENTICITY - it came from a holder of k

   WHAT IT DOES NOT:
     · CONFIDENTIALITY - the message is in the clear
     · NON-REPUDIATION - BOTH parties hold k, so either could
       have produced the tag. A third party learns nothing
       about which. That needs a signature (chapter 15).
     · FRESHNESS - a valid (m, t) pair replays forever. Add a
       counter, a timestamp or a nonce, and authenticate it.

   TAG LENGTH: 128 bits is standard. A truncated tag of t
   bits gives an attacker a 2^-t chance per forgery attempt -
   so 64 bits is acceptable only where the number of attempts
   is rate-limited, and 32 bits is a bad idea in almost every
   case.

HMAC

The standard way to build a MAC from a hash function, designed specifically to avoid the length-extension problem from the previous chapter. It is conservative, well-studied and almost always an acceptable answer.

/* THE CONSTRUCTION, RFC 2104: */

    HMAC(K, m) = H( (K' XOR opad) ‖ H( (K' XOR ipad) ‖ m ) )

        K'    the key, padded to the hash's BLOCK SIZE
              (64 bytes for SHA-256), or H(K) if longer
        ipad  0x36 repeated
        opad  0x5C repeated

/* WHY THE NESTING: it defeats length extension (chapter 07).
   The inner hash's output is fed into an outer hash keyed
   differently, so an attacker who knows the tag cannot
   continue the computation - the outer hash's state is
   unknown.

/* WHY TWO DIFFERENT PADS: ipad and opad differ in every bit
   position of every byte pair, which makes the two derived
   keys effectively independent.

/* THE SECURITY PROOF is remarkable: HMAC is secure if the
   compression function is a pseudorandom function - a much
   weaker assumption than collision resistance. Which is why
   HMAC-SHA1 REMAINS SECURE despite SHA-1's collision breaks
   (chapter 07). It should still be replaced, but it is not
   urgent in the way an SHA-1 signature is.

/* IMPLEMENTATION: */
    #include <mbedtls/md.h>

    uint8_t tag[32];
    const mbedtls_md_info_t *info =
        mbedtls_md_info_from_type(MBEDTLS_MD_SHA256);

    mbedtls_md_hmac(info, key, key_len, msg, msg_len, tag);

    /* streaming, for a large message */
    mbedtls_md_context_t ctx;
    mbedtls_md_setup(&ctx, info, 1);        /* 1 = HMAC */
    mbedtls_md_hmac_starts(&ctx, key, key_len);
    while ((n = read(buf, sizeof buf)) > 0)
        mbedtls_md_hmac_update(&ctx, buf, n);
    mbedtls_md_hmac_finish(&ctx, tag);
    mbedtls_md_free(&ctx);

/* VERIFICATION, and this is where implementations fail: */
    /* WRONG - early exit leaks how many bytes matched */
    if (memcmp(tag, received, 32) == 0) accept();

    /* RIGHT */
    if (mbedtls_ct_memcmp(tag, received, 32) == 0) accept();
    /* or sodium_memcmp, CRYPTO_memcmp, or the loop from
       chapter 07                                          */

/* THE TIMING ATTACK IS REAL AND PRACTICAL: an attacker
   submits candidate tags and measures the response. Each
   additional matching byte takes measurably longer, so they
   recover the tag one byte at a time - 256 x 16 attempts
   instead of 2^128. This has broken real APIs, including
   over a network where the difference was nanoseconds -
   statistical averaging over many requests extracts it
   (chapter 19).                                          */
Never build a MAC yourself

H(k ‖ m) falls to length extension. H(m ‖ k) reduces to finding a hash collision. H(k ‖ m ‖ k) has weaknesses too. Encrypting a hash, XORing a key in, truncating cleverly — every ad-hoc construction has been tried and broken. HMAC exists precisely so nobody has to reason about this again, and it is one function call.

Poly1305 and universal hashing

A one-time authenticator that is very fast and carries one absolutely rigid requirement: each key may be used for exactly one message. It is normally paired with a stream cipher that derives that key per message.

/* A different construction entirely: a ONE-TIME MAC based on
   polynomial evaluation in a prime field. Much faster than
   HMAC, and the authenticator inside ChaCha20-Poly1305 and
   (in a related form) AES-GCM.                            */

    Poly1305(r, s, m):
        split m into 16-byte chunks c1..cn, each with a
        high bit set
        evaluate  ((c1*r^n + c2*r^(n-1) + ... + cn*r) mod
                   (2^130 - 5))  +  s   mod 2^128

/* r and s are derived from the key and the nonce, and r has
   some bits CLAMPED to make the arithmetic efficient.

/* THE CRITICAL PROPERTY - AND THE CRITICAL WARNING:

     POLY1305 IS A ONE-TIME MAC. The (r, s) pair must NEVER
     be reused for two messages.

   With two tags under the same key, the attacker gets two
   polynomial equations in the unknown r, and can SOLVE FOR
   THE AUTHENTICATION KEY. They can then forge arbitrary
   messages.

   This is exactly why GCM nonce reuse is worse than CTR
   nonce reuse (chapter 05): CTR reuse leaks plaintexts;
   GCM reuse additionally hands over the ability to forge.

/* SO IT IS ALWAYS USED WITH A NONCE-DERIVED KEY: */
    ChaCha20-Poly1305:
        (r, s) = first 32 bytes of ChaCha20(key, nonce,
                                            counter=0)
        ciphertext = ChaCha20(key, nonce, counter=1) XOR
                     plaintext
        tag = Poly1305(r, s, aad ‖ ciphertext ‖ lengths)

/* THE LENGTH FIELDS AT THE END MATTER. Without them, an
   attacker could move bytes between the AAD and the
   ciphertext while keeping the concatenation identical -
   producing a valid tag for a different (aad, ciphertext)
   split. Any construction concatenating variable-length
   fields into an authenticator needs unambiguous encoding.

/* GHASH, used by GCM, is the same idea over GF(2^128)
   instead of a prime field - faster in hardware (the
   PMULL/CLMUL instructions), and with the same one-time
   requirement.                                            */

CMAC and the block-cipher MACs

A MAC built from a block cipher rather than a hash, which matters when the hardware you have accelerates AES and nothing else.

/* When you have an AES accelerator and no hash accelerator,
   a block-cipher MAC costs nothing extra.                 */

/* --- CBC-MAC: the naive version, and why it is broken --- */
        t = last block of CBC-encrypt(m) with IV = 0

/* SECURE ONLY for FIXED-LENGTH messages. With variable
   lengths:
        given  MAC(m1) = t1  and  MAC(m2) = t2
        then   MAC(m1 ‖ (m2[0] XOR t1) ‖ m2[1..]) = t2
   A forgery from two known tags, with no key.

/* --- CMAC (RFC 4493): CBC-MAC done correctly --- */
    Derive two subkeys K1, K2 from K.
    XOR the final block with K1 (if the message is a whole
    number of blocks) or pad and XOR with K2 (if not).
    That distinguishes padded from unpadded messages and
    closes the extension attack.

    /* mbedTLS */
    mbedtls_cipher_cmac(cipher_info, key, 128,
                        msg, msg_len, tag);

/* CMAC IS THE RIGHT CHOICE when:
     · you have AES hardware and no SHA hardware
     · you are already doing AES and want one primitive
     · a standard requires it (many do - it is NIST SP
       800-38B)

/* --- GMAC: GCM with no plaintext --- */
    AES-GCM with an empty plaintext and the data as AAD is a
    MAC. Very fast with PMULL/CLMUL. Inherits GCM's nonce
    requirement absolutely.

/* --- KMAC: the SHA-3 keyed mode --- */
    A sponge is naturally keyed - just absorb the key first.
    No HMAC-style nesting needed, because there is no length
    extension (chapter 07). Same for BLAKE2's keyed mode and
    BLAKE3's keyed_hash.                                   */

The choice between them is usually decided by what is already available and accelerated on your platform rather than by security differences, since all of the above are sound when used correctly.

/* THE DECISION, in practice:

   Encrypting anyway?           -> use an AEAD (chapter 09).
                                   The tag comes free and the
                                   composition is already
                                   correct.
   Authenticating only?         -> HMAC-SHA256
   AES hardware, no SHA?        -> CMAC
   Very constrained?            -> CMAC with the AES engine,
                                   or ASCON
   Already using BLAKE2/3?      -> its keyed mode

   AND ALMOST ALWAYS THE FIRST: if you find yourself choosing
   a MAC separately from a cipher, check whether you should
   be using an AEAD instead. Composing them by hand is where
   the mistakes are.                                       */

Using a MAC in a protocol

Having a MAC is not enough — how it is combined with encryption, and what exactly is covered, decide whether the result is secure. This is where most real failures occur.

/* --- 1. AUTHENTICATE EVERYTHING THAT MATTERS --- */
    /* WRONG - the header is unprotected */
    tag = HMAC(k, payload);
    send(header, payload, tag);
    /* an attacker changes the header freely: the message
       type, the destination, the length */

    /* RIGHT */
    tag = HMAC(k, header ‖ payload);

/* --- 2. INCLUDE A COUNTER, OR REPLAY IS TRIVIAL --- */
    struct Message {
        uint32_t seq;           /* monotonic, per direction */
        uint8_t  type;
        uint16_t len;
        uint8_t  payload[];
    };
    tag = HMAC(k, seq ‖ type ‖ len ‖ payload);

    /* the receiver: */
    if (msg.seq <= last_seen_seq) reject();     /* REPLAY */
    if (!ct_equal(tag, computed, 16)) reject();
    last_seen_seq = msg.seq;

/* AND CHECK THE TAG BEFORE THE SEQUENCE, or an attacker can
   probe your sequence-number state with forged messages.
   Actually check BOTH, and reject on either - but never act
   on unauthenticated data.

/* --- 3. USE SEPARATE KEYS FOR EACH DIRECTION AND
       PURPOSE --- */
    k_c2s_enc = HKDF(master, "client-to-server encryption");
    k_c2s_mac = HKDF(master, "client-to-server mac");
    k_s2c_enc = HKDF(master, "server-to-client encryption");
    k_s2c_mac = HKDF(master, "server-to-client mac");

/* ONE KEY FOR BOTH DIRECTIONS allows REFLECTION: the
   attacker replays a client message back to the client, and
   it authenticates. Real protocols have fallen to this.
   Key derivation is cheap (chapter 10); use distinct keys.

/* --- 4. UNAMBIGUOUS ENCODING --- */
    /* WRONG: */
    tag = HMAC(k, user ‖ action);
    /* ("alice", "delete") and ("alic", "edelete") produce the
       same input */
    /* RIGHT: */
    tag = HMAC(k, len(user) ‖ user ‖ len(action) ‖ action);

/* --- 5. AND THE VERIFICATION DISCIPLINE --- */
    · constant-time comparison, always
    · compare the FULL tag, never a prefix
    · on failure: reject the whole message, log nothing
      attacker-controlled, and return an INDISTINGUISHABLE
      error - "authentication failed", never "bad sequence
      number" or "unknown message type"
    · rate-limit failures, so an attacker cannot make 2^32
      attempts                                             */
