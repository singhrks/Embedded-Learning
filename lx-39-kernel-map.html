The Linux kernel map: layers, subsystems and where a driver sits

Thirty-eight chapters of this track each explain one subsystem in depth. This chapter is the single picture they all fit into — every major layer and module in one diagram, so that when a later chapter says "the block layer calls into the driver," you already know what is above it, what is below it, and which directory it lives in.

The whole kernel, in one diagram

Read the diagram as three questions, not fifty boxes

The map is only useful if you can compress it. Every box in it answers one of three questions: who asked for the work (user space, above the syscall line), who decides how it gets done (the kernel's own subsystems — scheduler, memory, VFS, block, network), and who actually touches the hardware (the driver core, the bus subsystems, the architecture layer). A driver you write lives entirely in the third group, is called by the second, and exists to serve the first.

What each layer is actually responsible for

The diagram shows what exists; this section says what each band is actually for. The distinction that matters most is between the layers that decide what should happen and the layers that make it happen on real hardware.

   USER SPACE
        Unprivileged. Cannot touch hardware, cannot read
        kernel memory, cannot crash the machine. Reaches the
        kernel ONLY through the syscall boundary - which is
        why udev, systemd and even a "user-space driver" like
        libusb are ordinary programs with no special powers
        beyond the file descriptors they are allowed to open.

   SYSTEM CALL INTERFACE
        The narrow waist of the whole design. Roughly 400
        calls, whose numbers and behaviour can never change
        once released (chapter 38). Everything user space is
        ever allowed to ask for is expressible here or not at
        all.

   KERNEL SUBSYSTEMS
        The parts that arbitrate: which task runs (scheduler),
        where memory comes from (MM), what a path resolves to
        (VFS), how bytes reach storage (block layer) or the
        network (net stack). These are POLICY. They decide
        what should happen and in what order - and then hand
        the actual work downward.

   DRIVER CORE + BUS SUBSYSTEMS
        The parts that translate a generic request into a
        specific device's language. "Read 4 KB from this
        block device" becomes SPI transactions, or NVMe
        submission-queue entries, or I2C register reads. This
        is MECHANISM, and it is where your code goes.

   ARCHITECTURE LAYER
        The small amount of code that genuinely cannot be
        written portably: the boot and exception entry paths,
        page-table format, cache and TLB maintenance, memory
        barriers and atomics, firmware interfaces. Everything
        above it is written once and compiles for every
        architecture BECAUSE this layer exists.

   HARDWARE
        The only layer that does not have a maintainer you
        can email.

One read() all the way down and back

The clearest way to see how the layers fit together is to follow one ordinary operation all the way down and back. Almost every performance or correctness question you will face is a question about one specific step in this sequence.

   A PROGRAM CALLS read(fd, buf, 4096) ON A FILE STORED ON
   AN SD CARD. FOLLOW IT THROUGH THE MAP ABOVE:

    1. libc          loads the syscall number, executes svc #0
    2. syscall entry saves registers, looks up sys_read
    3. VFS           fd -> struct file -> this filesystem's
                     read_iter (chapter 41)
    4. PAGE CACHE    already resident? copy out, RETURN NOW -
                     steps 5-10 never happen (chapter 42).
                     Otherwise, continue:
    5. FILESYSTEM    ext4 maps "file offset 8192" to "logical
                     block 4711" using its own metadata
    6. BLOCK LAYER   builds a bio, merges it with adjacent
                     pending I/O, hands it to blk-mq (ch. 43)
    7. MMC SUBSYSTEM turns the request into SD protocol
                     commands
    8. HOST DRIVER   programs the SD controller's registers
                     and starts a DMA transfer (chapter 30)
    9. HARDWARE      the card reads flash and DMAs into RAM
   10. INTERRUPT     the controller raises an IRQ; the handler
                     acknowledges it and completes the bio
                     (chapters 15 · 16)
   ... and the whole stack unwinds: bio completion wakes the
   blocked task, the page is now in the page cache, the VFS
   copies it to the user buffer (chapter 09), and read()
   returns 4096.

   NOTICE WHAT THIS MEANS FOR DEBUGGING: a slow read() could
   be a fragmented filesystem (step 5), a saturated queue
   (step 6), a misconfigured DMA (step 8) or a lost interrupt
   (step 10) - and each of those lives in a DIFFERENT layer
   with DIFFERENT tools. Knowing the map is what turns "the
   disk is slow" into a testable hypothesis.

How it shows up

SymptomCause
A "slow disk" turns out to be a lost interruptThe symptom appears at the top of the stack but the fault is near the bottom — trace layer by layer
A driver compiles but its probe() never runsThe driver core never matched it — the problem is in the device model layer, not your driver's logic (ch. 19)
Code works on arm64 and breaks on x86Something assumed a property the architecture layer abstracts — barriers, cache behaviour, or page size
A read() returns instantly with no device activityThe page cache served it; the lower layers were never reached at all
A user-space "driver" cannot touch a registerExpected — user space has no hardware access except through a device node the kernel exposes
Adding a syscall is proposed as the fix for a driver problemAlmost always wrong — the syscall layer is the one part deliberately kept narrow and permanent (ch. 38)
