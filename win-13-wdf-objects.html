The WDF object model

Handles, contexts, parenting and cleanup callbacks. Once you understand these four ideas, every WDF API follows the same shape — and most of your cleanup code disappears.

Objects and handles

You never hold a pointer to a WDF object. You hold an opaque handle, and the framework validates it — which means a stale or wrong handle produces a clear diagnostic rather than corrupting memory.

/* A WDF object is an opaque HANDLE, not a pointer: */

        WDFDEVICE     device;
        WDFQUEUE      queue;
        WDFREQUEST    request;
        WDFMEMORY     memory;
        WDFSPINLOCK   lock;
        WDFTIMER      timer;
        WDFINTERRUPT  interrupt;
        WDFDMAENABLER dmaEnabler;
        WDFCHILDLIST  childList;
        WDFFILEOBJECT fileObject;
        WDFCOLLECTION collection;
        WDFKEY        registryKey;
        WDFSTRING     string;
        WDFIOTARGET   ioTarget;

/* EVERY CREATION FUNCTION HAS THE SAME SHAPE: */

        NTSTATUS Wdf<Type>Create(
                <parent or config>,
                <type-specific config>,
                PWDF_OBJECT_ATTRIBUTES Attributes,
                <Type> *Handle);

/* AND EVERY OBJECT HAS: */
        a TYPE
        a PARENT              <-- the important one
        an optional CONTEXT   your data, attached to it
        a reference count
        optional EvtCleanupCallback and EvtDestroyCallback

/* YOU NEVER FREE AN OBJECT DIRECTLY in normal code. It is
   destroyed when its parent is. WdfObjectDelete exists but
   is needed only for objects you deliberately parented to
   something long-lived.                                    */

Parenting

This is the idea that makes WDF cleanup work, and the one worth understanding before any other: every object has a parent, and when the parent is destroyed its children are destroyed first, automatically, in order. Most driver cleanup code simply disappears.

   WDFDRIVER
      |
      +-- WDFDEVICE                (parent: the driver)
             |
             +-- WDFQUEUE          (parent: the device)
             |      |
             |      +-- WDFREQUEST (parent: the queue)
             |             |
             |             +-- WDFMEMORY
             |
             +-- WDFINTERRUPT
             +-- WDFDMAENABLER
             |      +-- WDFDMATRANSACTION
             +-- WDFTIMER
             +-- WDFWORKITEM
             +-- WDFSPINLOCK
             +-- WDFFILEOBJECT     (one per open handle)

   DESTROYING A PARENT DESTROYS ITS CHILDREN, depth-first,
   in reverse creation order.

   SO: parent everything to your WDFDEVICE and device removal
   cleans up the entire tree, in the correct order, on every
   path - including a failed EvtDeviceAdd.

   THE DEFAULT PARENT is usually sensible: WdfSpinLockCreate
   with WDF_NO_OBJECT_ATTRIBUTES parents to the DRIVER, which
   is almost never what you want. SET IT EXPLICITLY:

        WDF_OBJECT_ATTRIBUTES_INIT(&attr);
        attr.ParentObject = device;
        WdfSpinLockCreate(&attr, &lock);

   THIS IS EXACTLY Linux's devm_ (ch. 33) with a tree instead
   of a flat list - and the same payoff: correct unwinding
   that you did not have to write, on the error path you did
   not test.

Contexts

Your driver needs somewhere to keep its own state for each device, queue or request. Rather than maintaining a lookup table, WDF lets you attach a typed structure directly to any object and retrieve it with a generated accessor.

/* A context is YOUR structure attached to a WDF object. It
   replaces WDM's DeviceExtension, and unlike it, you can
   attach one to ANY object.                                */

/* 1. DECLARE the type and its accessor: */

typedef struct _MY_DEVICE_CONTEXT {
        WDFDEVICE     Device;
        WDFQUEUE      ReadQueue;
        WDFINTERRUPT  Interrupt;
        PUCHAR        RegBase;
        ULONG         RegLength;
        WDFSPINLOCK   StateLock;
        ULONG         SampleRate;
        LONG64        InterruptCount;
} MY_DEVICE_CONTEXT, *PMY_DEVICE_CONTEXT;

WDF_DECLARE_CONTEXT_TYPE_WITH_NAME(MY_DEVICE_CONTEXT,
                                   MyGetDeviceContext)
/* generates:
     PMY_DEVICE_CONTEXT MyGetDeviceContext(WDFOBJECT);
   plus the type information WDF needs to size the
   allocation.                                              */

/* 2. REQUEST it at creation: */
        WDF_OBJECT_ATTRIBUTES attributes;

        WDF_OBJECT_ATTRIBUTES_INIT_CONTEXT_TYPE(&attributes,
                                        MY_DEVICE_CONTEXT);
        status = WdfDeviceCreate(&DeviceInit, &attributes,
                                 &device);

/* 3. USE it: */
        PMY_DEVICE_CONTEXT ctx = MyGetDeviceContext(device);
        ctx->SampleRate = 48000;

/* SEVERAL CONTEXT TYPES ON ONE OBJECT is allowed, with
   different accessors - useful when a shared library and your
   driver both need private data on the same device.       */

/* PER-REQUEST CONTEXT, the common second use: */
typedef struct _MY_REQUEST_CONTEXT {
        WDFMEMORY  Memory;
        ULONG      Channel;
        LARGE_INTEGER StartTime;
} MY_REQUEST_CONTEXT, *PMY_REQUEST_CONTEXT;

WDF_DECLARE_CONTEXT_TYPE_WITH_NAME(MY_REQUEST_CONTEXT,
                                   MyGetRequestContext)

        /* attach it to requests arriving on a queue: */
        WDF_OBJECT_ATTRIBUTES_INIT_CONTEXT_TYPE(&attr,
                                        MY_REQUEST_CONTEXT);
        queueConfig.  /* ... */;
        WdfIoQueueCreate(device, &queueConfig, &attr, &queue);
        /* now every request on this queue has your context */

/* THE CONTEXT MEMORY IS NON-PAGED and ZEROED at creation, so
   you do not allocate or free it - it lives inside the
   object's own allocation.                                */
The most common WDF mistake

Calling MyGetDeviceContext() on an object created without WDF_OBJECT_ATTRIBUTES_INIT_CONTEXT_TYPE. The accessor returns garbage or NULL, and you get a crash with no obvious cause. If a context pointer looks wrong, check the creation call first — the attributes must name the same context type the accessor expects.

Cleanup and destroy callbacks

Two callbacks fire as an object goes away, at different moments and with different rules about what you may do. Choosing the wrong one is a common source of teardown bugs, and the distinction is genuinely subtle.

/* Two callbacks, at different points in an object's death. */

        WDF_OBJECT_ATTRIBUTES_INIT_CONTEXT_TYPE(&attr,
                                        MY_DEVICE_CONTEXT);
        attr.EvtCleanupCallback = MyEvtDeviceCleanup;
        attr.EvtDestroyCallback = MyEvtDeviceDestroy;
        attr.ParentObject       = parent;

VOID
MyEvtDeviceCleanup(_In_ WDFOBJECT Object)
{
        PMY_DEVICE_CONTEXT ctx = MyGetDeviceContext(Object);

        /* CLEANUP: the object is being deleted, but its
           children still exist and its context is still
           valid. This is where you release things you
           acquired yourself.

           IRQL: <= DISPATCH_LEVEL by default, or PASSIVE if
           you asked for WdfExecutionLevelPassive.        */

        if (ctx->MyOwnAllocation) {
                ExFreePoolWithTag(ctx->MyOwnAllocation, TAG);
                ctx->MyOwnAllocation = NULL;
        }
}

VOID
MyEvtDeviceDestroy(_In_ WDFOBJECT Object)
{
        /* DESTROY: the last reference is gone, all children
           are destroyed, and the memory is about to be
           freed. Very little belongs here.

           IRQL: <= DISPATCH_LEVEL. Do not touch children -
           they no longer exist.                          */
}

/* THE ORDER on deletion:
     1. EvtCleanupCallback on the object
     2. children are deleted (each with its own cleanup)
     3. EvtDestroyCallback on the object
     4. memory freed

/* WHICH TO USE: almost always Cleanup. Destroy is for the
   rare case where you must know the object is truly gone -
   for example, signalling that a device's memory can now be
   reused.

/* AND THE POINT: if everything you allocate is either a WDF
   object parented correctly, or a WDFMEMORY, you need
   NEITHER callback. Reach for them only for raw resources
   the framework does not know about.                     */

WDFMEMORY

A WDF memory object is an allocation with a lifetime attached to the object tree, so it is freed when its parent is. It also carries its own length, which removes the commonest cause of buffer overruns.

/* A WDF object wrapping a buffer, so allocation participates
   in parenting and lifetime management.                    */

        WDFMEMORY memory;
        PVOID buffer;
        WDF_OBJECT_ATTRIBUTES attr;

        WDF_OBJECT_ATTRIBUTES_INIT(&attr);
        attr.ParentObject = request;    /* dies with the
                                           request           */

        status = WdfMemoryCreate(&attr,
                                 NonPagedPoolNx,
                                 MY_POOL_TAG,
                                 size,
                                 &memory,
                                 &buffer);   /* optional out */
        if (!NT_SUCCESS(status))
                return status;

        /* no free needed - the request's completion destroys
           it                                                */

/* GETTING AT IT LATER: */
        size_t length;
        PVOID p = WdfMemoryGetBuffer(memory, &length);

/* WRAPPING A BUFFER YOU ALREADY HAVE, without copying: */
        status = WdfMemoryCreatePreallocated(&attr,
                        existingBuffer, size, &memory);
        /* WDF does NOT free the buffer in this case - you
           still own it. Use this to hand an existing buffer
           to an API that wants a WDFMEMORY.               */

/* COPYING, with bounds checking done for you: */
        WdfMemoryCopyFromBuffer(memory, offset, src, length);
        WdfMemoryCopyToBuffer(memory, offset, dst, length);
/* These return STATUS_BUFFER_TOO_SMALL rather than
   overrunning - which is the argument for using them instead
   of RtlCopyMemory on a raw pointer.                      */

Synchronisation scope

By default WDF may call your callbacks concurrently on several processors. Synchronisation scope lets you ask the framework to serialise them for you — a decision worth making deliberately, because the convenient answer costs concurrency.

/* WDF can AUTOMATICALLY serialise your callbacks, so you may
   not need locks at all.                                   */

        WDF_OBJECT_ATTRIBUTES attr;

        WDF_OBJECT_ATTRIBUTES_INIT(&attr);
        attr.SynchronizationScope = WdfSynchronizationScopeDevice;
        attr.ExecutionLevel       = WdfExecutionLevelPassive;

/* SYNCHRONIZATION SCOPE:

   WdfSynchronizationScopeDevice
        ALL callbacks for this device, and its queues, timers
        and DPCs, are serialised against one another with a
        single device lock. Simplest to reason about; limits
        parallelism.

   WdfSynchronizationScopeQueue
        callbacks for one queue are serialised with each
        other, but different queues run in parallel.

   WdfSynchronizationScopeNone
        no automatic serialisation. YOU do the locking.
        The default for a parallel queue, and the right choice
        for a high-throughput device.

   WdfSynchronizationScopeInheritFromParent
        the default for most objects.

/* EXECUTION LEVEL:

   WdfExecutionLevelPassive
        every callback runs at PASSIVE_LEVEL, so it may touch
        paged memory and sleep. The framework uses work items
        to arrange it.
        NOTE: cannot be combined with a queue that must run at
        DISPATCH_LEVEL, and it adds latency.

   WdfExecutionLevelDispatch
        callbacks may run at DISPATCH_LEVEL.

   WdfExecutionLevelInheritFromParent   the default.

/* THE TRADE, stated plainly:
     ScopeDevice + LevelPassive is the EASIEST model to write
     correctly - one lock, everything sleepable, no IRQL
     puzzles. It is also the slowest, because every callback
     serialises against every other.

     ScopeNone + parallel dispatch is the FASTEST and requires
     you to get the locking right yourself (chapter 10).

   START with the simple model. Move to the parallel one when
   you have measured a reason to.                          */

Collections and child lists

When a driver needs to track a set of objects — open handles, pending operations, child devices — WDF provides a container that participates in the same lifetime rules as everything else.

/* WDFCOLLECTION - an ordered set of WDF objects: */
        WDFCOLLECTION collection;

        WdfCollectionCreate(&attr, &collection);
        WdfCollectionAdd(collection, someObject);

        ULONG count = WdfCollectionGetCount(collection);
        for (ULONG i = 0; i < count; i++) {
                WDFOBJECT obj = WdfCollectionGetItem(collection, i);
                ...
        }
        WdfCollectionRemove(collection, someObject);

/* Holds a REFERENCE on each item, so an object in a
   collection outlives its parent's deletion attempt until
   removed. Convenient, and a source of "the device will not
   go away" bugs if you forget to empty it.               */

/* WDFCHILDLIST - for a BUS DRIVER that enumerates children: */
        WDF_CHILD_LIST_CONFIG config;

        WDF_CHILD_LIST_CONFIG_INIT(&config,
                        sizeof(MY_CHILD_ID),
                        MyEvtChildListCreateDevice);
        WdfFdoInitSetDefaultChildListConfig(DeviceInit,
                        &config, WDF_NO_OBJECT_ATTRIBUTES);

        /* when you discover a child: */
        WdfChildListBeginScan(list);
        WdfChildListAddOrUpdateChildDescriptionAsPresent(
                        list, &id.Header, NULL);
        WdfChildListEndScan(list);
        /* anything not re-reported during the scan is
           automatically reported as REMOVED - which handles
           hot-unplug without you tracking it            */

/* This is how a driver for a bus, a multi-function device, or
   a device with dynamically appearing endpoints reports its
   children to PnP (chapter 06).                          */

Debugging WDF objects

The framework's debugger extension can show you the whole object tree, the queues and every request in flight, which turns most WDF questions into a single command.

# The WDF debugger extension - load it first:
    .load wdfkd.dll
    !wdfkd.wdfhelp

# THE ESSENTIAL COMMANDS:
    !wdfdriverinfo mydriver         everything about the driver
    !wdfdevicequeues <WDFDEVICE>    every queue and its
                                    contents
    !wdfobjectdump                  every WDF object
    !wdfhandle <handle>             one object: type, parent,
                                    context, refcount
    !wdfobject <handle>
    !wdfqueue <WDFQUEUE>            requests in a queue
    !wdfrequest <WDFREQUEST>        one request's state
    !wdflogdump mydriver            THE FRAMEWORK'S OWN LOG

# !wdflogdump IS THE ONE TO REMEMBER. WDF keeps an internal
# trace of every state transition, every request, and every
# error it detected. On a crash, it usually tells you what the
# framework thought was happening - which is often the whole
# answer.

# ENABLE VERBOSE FRAMEWORK LOGGING during development:
#   in the registry, under the driver's Parameters\Wdf key:
    VerboseOn      = 1
    VerifierOn     = 1     ; WDF VERIFIER - see below
    DbgBreakOnError = 1

# Or via the WDF verifier settings in the WDK's
# "WDF Verifier Control Application" (wdfverifier.exe).

# WDF VERIFIER checks framework-specific rules: object
# lifetime, handle validity, IRQL for each API, correct
# request completion. It is separate from Driver Verifier
# (chapter 22) and catches a different, WDF-specific class of
# bug. Turn BOTH on.
