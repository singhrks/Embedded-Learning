Upstreaming and kernel culture

Getting your driver into mainline: why it is worth the effort, the mechanics of submitting a patch series, and what reviewers are actually looking for. The last chapter of the Linux track, and the one that decides whether your work outlives the product.

Why bother

Keeping a driver out of tree feels easier, and for a few weeks it is. This section is the case for the opposite, in practical rather than idealistic terms — the costs of staying out are real and they compound with every kernel upgrade.

THE OUT-OF-TREE COST, which compounds:

   the internal kernel API has no stability guarantee
   (chapter 02), so every kernel upgrade breaks your driver
      -> someone must fix it, forever
      -> that someone eventually leaves
      -> the product is stuck on a 2019 kernel with known CVEs

   THE VENDOR BSP PATTERN: a 4.19 kernel with 4,000 patches,
   which cannot take security fixes without a merge that
   nobody has budget for. This is the normal state of shipped
   embedded Linux, and it is a direct consequence of staying
   out of tree.

THE UPSTREAM BENEFIT:

   · other people fix your driver during API refactors, for
     free, forever
   · you get code review from people who have seen a thousand
     drivers
   · your users can run any kernel
   · security fixes flow automatically
   · new SoC variants are cheaper - the framework is already
     there
   · it is a portable, public record of your work

  THE HONEST COST: the first patch series takes weeks and
  several review rounds. The second takes days. It is a fixed
  learning cost, not a recurring one.

Before you send anything

Most rejected patches are rejected for reasons that have nothing to do with the code. Working through this list first removes almost all of them, and costs an afternoon rather than three review rounds.

# 1. IS IT ALREADY THERE? Search first.
    git log --oneline --all -- drivers/whatever/
    # and search lore.kernel.org for the device name, the
    # compatible string, and the vendor.
    # Finding an existing driver, or someone else's series
    # in flight, saves weeks.

# 2. USE THE RIGHT SUBSYSTEM (chapter 19). A temperature
#    sensor submitted as a custom char device will be asked
#    to become a hwmon driver. Find that out now, not after
#    three review rounds.

# 3. BASE ON THE RIGHT TREE.
    git remote add next \
      https://git.kernel.org/pub/scm/linux/kernel/git/next/linux-next.git
    # develop against linux-next or the relevant maintainer
    # tree, not against your vendor BSP.

# 4. CHECKPATCH, CLEAN.
    ./scripts/checkpatch.pl --strict -g HEAD~5..HEAD
    # --strict is what maintainers run. Fix everything it
    # reports, or be ready to explain why not.

# 5. SPARSE, COCCINELLE, THE BUILD BOTS' CHECKS.
    make C=1 M=drivers/mydrv/

# 6. TESTS. Increasingly expected, and increasingly the first
#    thing a maintainer asks for on new code.
    # KUnit - unit tests that run INSIDE the kernel, for the
    # parts of your driver that are pure logic: register
    # encoding, value scaling, buffer arithmetic.
    #   drivers/mydrv/mydrv_test.c  +  CONFIG_MYDRV_KUNIT_TEST
    ./tools/testing/kunit/kunit.py run --arch=arm64
    #
    # kselftest - userspace tests of the ABI you expose, which
    # is what actually protects the interface you can never
    # change (chapter 02):
    #   tools/testing/selftests/drivers/mydrv/
    make -C tools/testing/selftests TARGETS=drivers/mydrv run_tests
    #
    # A driver whose only test is "it worked on my board" is
    # much harder to accept, because no maintainer can verify
    # a regression in it later.
    make W=1 M=drivers/mydrv/
    make coccicheck M=drivers/mydrv/

# 6. BUILD FOR OTHER ARCHITECTURES. The 0-day bot will do
#    this and email you if it breaks. Beat it to it:
    make ARCH=x86_64 allmodconfig && make M=drivers/mydrv/
    make ARCH=arm allmodconfig    && make M=drivers/mydrv/
    # a 32-bit build catches the u64-division and pointer-size
    # bugs that arm64-only testing never will.

# 7. THE DT BINDING VALIDATES (chapter 20).
    make dt_binding_check DT_SCHEMA_FILES=vendor,my-device.yaml
    make dtbs_check

Splitting the series

A large change arrives as a series of small patches, not one enormous diff. This is not a formality: each patch must build and work on its own, so that a later bisection can land on any one of them.

# ONE LOGICAL CHANGE PER PATCH. A typical new-driver series:

  [PATCH 0/4] Add support for the Vendor MyDevice
  [PATCH 1/4] dt-bindings: misc: add vendor,my-device
  [PATCH 2/4] misc: mydev: add Vendor MyDevice driver
  [PATCH 3/4] arm64: dts: vendor: add mydev node to mysoc
  [PATCH 4/4] MAINTAINERS: add entry for Vendor MyDevice

# WHY THIS ORDER: the binding comes first because it defines
# the interface the driver implements, and because it goes to
# a different maintainer who reviews it independently.
# The DTS patch comes after the driver, and often goes through
# the SoC tree rather than the subsystem tree - which is why
# it must be a SEPARATE patch.

# EACH PATCH MUST:
#   · compile on its own
#   · not break anything on its own (bisectability)
#   · do one thing, described in its subject line

# THE SUBJECT LINE FORMAT matters and is checked:
    subsystem: driver: short imperative description
# Get the prefix right by looking at history:
    git log --oneline -10 -- drivers/misc/

Writing the commit message

The commit message is read far more often than the code, frequently years later by someone trying to work out why something is the way it is. It explains the why; the diff already shows the what.

misc: mydev: add Vendor MyDevice driver

The MyDevice block is a data acquisition controller found on
Vendor MySoC parts. It provides four sampling channels with a
configurable hardware FIFO, and raises an interrupt when the
FIFO reaches a programmable threshold.

Add a driver exposing the device through a character node,
with blocking reads, poll() support and per-channel
configuration via ioctl. The v2 variant has eight channels and
a deeper FIFO; both are supported through match data.

The device is documented in the MySoC TRM revision 1.4,
section 12.

Signed-off-by: Your Name <you@example.com>

/* WHAT MAKES THIS ONE ACCEPTABLE:

   · says WHAT the hardware is, for a reviewer who has never
     heard of it
   · says WHAT the patch adds, in the imperative mood
     ("Add a driver", not "Added" or "This adds")
   · mentions the variants and how they are handled
   · cites the documentation
   · wrapped at 72 columns
   · has a Signed-off-by

   WHAT TO AVOID:
     · "misc: mydev: fixes" - says nothing
     · a message that only restates the diff
     · internal ticket numbers with no public meaning
     · "as discussed offline"                              */

The trailer tags

These lines look like free-form metadata but each one is a specific, load-bearing claim the kernel community's process depends on — provenance, review, and testing all get tracked this way instead of through any tool external to the commit itself, which is exactly why a missing or fabricated tag is treated as a serious problem rather than a style nit.

TagMeaningWho adds it
Signed-off-byThe Developer's Certificate of Origin — a legal statement that you may contribute thisYou, and everyone in the chain
Reviewed-by"I read this carefully and it is correct"A reviewer
Acked-by"I am fine with this touching my area"A maintainer
Tested-by"I ran it"Anyone who did
Reported-byWho found the bugYou, crediting them
Closes:A URL to the bug reportYou
Fixes:<12-char sha> ("subject") — enables backportingYou, on any bug fix
Cc: stable@vger.kernel.orgBackport this to stable kernelsYou, for real fixes
Suggested-byWho proposed the approachYou
 
# Signed-off-by is NOT optional and is NOT a formality. It
# asserts the DCO (Documentation/process/submitting-patches.rst):
# that you wrote it or have the right to submit it. Patches
# without it are rejected automatically.

    git commit -s              # adds it for you
    git config format.signOff true

# Fixes: format, exactly:
    Fixes: a1b2c3d4e5f6 ("misc: mydev: add error handling")

    git config core.abbrev 12
    git config alias.fixes "show -s --format='Fixes: %h (\"%s\")'"
    git fixes a1b2c3d

Sending it

Kernel patches go by email, in a specific format, to a specific set of people. The tooling does all of it for you, and using the tooling rather than an email client is what keeps the patch applicable at the other end.

# 1. WHO TO SEND TO:
    ./scripts/get_maintainer.pl -f drivers/misc/mydev.c
    ./scripts/get_maintainer.pl 0001-*.patch
      Greg Kroah-Hartman <gregkh@...> (maintainer:CHAR AND MISC)
      linux-kernel@vger.kernel.org (open list)

# Maintainers in To:, lists in Cc:.

# 2. GENERATE:
    git format-patch -4 --cover-letter -o outgoing/ \
        --subject-prefix="PATCH v2" origin/master

# Then EDIT the cover letter. A cover letter that still says
# "*** SUBJECT HERE ***" is a guaranteed re-send.

# 3. CONFIGURE git send-email once:
    git config sendemail.smtpserver smtp.example.com
    git config sendemail.smtpuser you@example.com
    git config sendemail.smtpencryption tls
    git config sendemail.smtpserverport 587

# 4. TEST IT ON YOURSELF FIRST. Always.
    git send-email --to=you@example.com outgoing/*.patch
# Then check the received mail: no HTML, no wrapped lines, no
# base64, no signature separator eating the diff. Apply it:
    git am received.mbox
# If it does not apply cleanly to your own tree, it will not
# apply to anyone's.

# 5. SEND:
    git send-email \
      --to="Maintainer <maint@example.com>" \
      --cc="linux-kernel@vger.kernel.org" \
      --cc="linux-arm-kernel@lists.infradead.org" \
      outgoing/*.patch

# 6. OR use b4, which handles most of this:
    b4 prep --new my-driver
    b4 send --dry-run
    b4 send
Your mail client will mangle the patch

Gmail's web interface, Outlook, and any client that sends HTML or re-wraps lines will corrupt a patch beyond recovery, and the reply you get will be "your patch is whitespace-damaged, please resend". Use git send-email or b4. There is no third option that reliably works, and Documentation/process/email-clients.rst exists because so many people have learned this the hard way.

The cover letter

A series of patches gets one introductory message explaining the whole thing. It is where the reviewer decides whether to engage with your series at all, so it is worth more care than its length suggests.

Subject: [PATCH v3 0/4] Add support for the Vendor MyDevice

This series adds support for the MyDevice data acquisition
block found on Vendor MySoC parts.

The device provides four (v1) or eight (v2) sampling channels
feeding a hardware FIFO, with a threshold interrupt. Userspace
reads samples through a character device and configures
channels with ioctl.

Tested on the Vendor EVK board with both v1 and v2 silicon,
and under QEMU with a stub model.

Changes in v3:
 - use dev_err_probe() throughout, per Krzysztof's review
 - drop the custom "vendor,irq-threshold" property and derive
   it from the FIFO depth instead
 - fix the 32-bit build (u64 division), reported by the 0-day
   bot
 - add the MAINTAINERS entry that was missing in v2

Changes in v2:
 - convert the binding to YAML schema
 - use devm_clk_get_enabled() instead of manual enable/disable
 - drop the module parameter; the DT property covers it

Your Name (4):
  dt-bindings: misc: add vendor,my-device
  misc: mydev: add Vendor MyDevice driver
  arm64: dts: vendor: add mydev node to mysoc
  MAINTAINERS: add entry for Vendor MyDevice

Handling review

What reviewers are actually checking
  • The userspace ABI — the one thing that cannot be fixed later (ch. 23). Expect the most scrutiny here.
  • The DT binding — also permanent. Are the properties describing hardware, or your driver's preferences?
  • Is there already a subsystem for this? The most common substantive review outcome for a new driver.
  • Error paths — every one, including the unwinding order (ch. 33).
  • Locking — is it documented, is it consistent, is it necessary.
  • Modern APIs — devm_, dev_err_probe, of_device_get_match_data rather than the patterns of ten years ago.
  • Does it build everywhere — 32-bit, other architectures, allmodconfig.
  • Style — cheaply checked, so failing it signals you did not run checkpatch.
# HOW TO RESPOND:

# · Reply to every comment. Even "will fix" - silence reads as
#   disagreement or absence.
# · Reply inline, below the quoted text, trimming the rest.
#   Top-posting makes threads unreadable and will be noted.
# · Plain text only.
# · If you disagree, say why, technically. Reviewers change
#   their minds when given a reason.
# · Do not argue about style. Just change it.
# · WAIT a week before resending. Maintainers batch review;
#   a v2 sent four hours after v1 wastes everyone's time.
# · Send v2 as a NEW thread, with In-Reply-To pointing at the
#   v1 cover letter, and a changelog.

# THE TONE: reviews are blunt and about the code. "This is
# wrong because X" is a technical statement, not an insult.
# The kernel has a Code of Conduct
# (Documentation/process/code-of-conduct.rst) and it is
# enforced - but expect directness, and give directness back.

# HOW LONG IT TAKES:
#   first response:   days to two weeks
#   a merge:          two to six versions, over one to three
#                     months, is entirely normal for a new
#                     driver
#   NOTHING AT ALL:   ping politely after two weeks, in-thread.
#                     Patches do get lost.

Tracking your patch

Once sent, a patch has a public life you can follow — build bots test it, maintainers pick it up, it moves through trees. Knowing where to look saves you from either nagging too early or assuming silence means rejection.

# Is it applied?
    git log --oneline --all --grep="MyDevice"

# The public archive of your thread:
    https://lore.kernel.org/all/?q=MyDevice
    b4 mbox <message-id>        # fetch the whole thread

# Automated feedback arrives within a day or two:
#   the 0-day bot: build failures on architectures you did not
#                  try, sparse warnings, coccinelle findings
#   the DT bot:    binding schema errors
#   syzbot:        if it finds a crash later
# These emails are automated but the findings are real. Fix
# them before a human has to point them out.

# WHEN IT IS ACCEPTED, a maintainer replies "Applied, thanks"
# and it lands in their tree -> linux-next -> the next merge
# window -> a release. That is typically 2-10 weeks after
# acceptance.

# THEN: you are the maintainer. Add yourself to MAINTAINERS,
# and expect bug reports.

The recurring mistakes

None of these are subtle technical errors — they are process mistakes newcomers make repeatedly because the kernel's review culture optimises for maintainers reviewing thousands of patches a cycle, not for any single submission's convenience, so the same handful of avoidable missteps cost real time on every submission that makes them.

MistakeConsequence
A new custom char device where a subsystem existsAsked to rewrite against IIO/hwmon/input
DT properties describing driver policy, not hardwareBinding rejected
No YAML binding, or an unvalidated oneBounced by the DT maintainers immediately
Sent from an HTML mail client"Whitespace damaged, please resend"
One giant patchAsked to split; nobody reviews a 3,000-line diff
No changelog on v2Reviewers cannot tell what you changed
Resending within hoursReviewers stop reading the series
Ignoring the 0-day botA human eventually says the same thing, less patiently
Arguing about coding styleGoodwill spent on nothing
Silence on review commentsThe patch is dropped
Module parameters for hardware descriptionAsked to use DT
Missing Signed-off-byCannot be applied at all

What to read

The kernel documents its own submission process in detail, and every mistake in the table above is directly addressed by one of the documents below — reading them once, fully, before your first submission is faster than learning the same rules one rejected patch at a time.

The best preparation costs an afternoon

Find three recently-merged driver series in your target subsystem on lore, and read every message in each thread — the patches, the review comments, and the revisions. You will learn what that specific maintainer cares about, what the house patterns are, and what gets pushed back on, far faster than from any documentation. Then write yours to match.

Check yourself

  • Explain the compounding cost of staying out of tree.
  • Run the seven pre-submission checks on your own driver.
  • Split a new driver into a properly ordered patch series.
  • Write a commit message that a stranger could act on.
  • Explain what Signed-off-by asserts and why it is required.
  • Use get_maintainer.pl and send a patch to yourself successfully.
  • Write a cover letter with a real changelog.
  • Name eight things reviewers check, in order of how permanent they are.
  • Describe how to respond to review, including disagreement.
  • Read three merged series in your subsystem and list what that maintainer asks for.
