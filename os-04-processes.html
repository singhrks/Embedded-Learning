Processes and the process control block

A process is a program plus everything the OS must remember about it. This chapter covers what that state actually is, how processes are created and destroyed, and the lifecycle bugs — zombies, orphans, fork-in-a-threaded-program — that come from getting it wrong.

What a process is

Program versus process

A program is a file on disk: instructions and initial data. A process is a program in execution, together with all the state the OS maintains on its behalf. One program can back many processes; each has its own private state.

A process is the sum of:

  ADDRESS SPACE          its private virtual memory map
    text                 code, read-only, shared between instances
    data + bss           initialised and zeroed globals
    heap                 grows upward, via brk/mmap
    memory mappings      files, shared libraries, anonymous regions
    stack(s)             one per thread, grows downward

  EXECUTION STATE        registers, PC, stack pointer, flags
                         (per thread — see chapter 05)

  KERNEL RESOURCES       open file descriptors
                         current working directory, root directory
                         signal handlers and masks
                         timers
                         namespaces, cgroup membership

  IDENTITY               PID, PPID, UID/GID, capabilities,
                         security label (SELinux, AppArmor)

  ACCOUNTING             CPU time used, memory usage, priority,
                         start time, resource limits

The process control block

All of that lives in one kernel structure: task_struct in Linux, EPROCESS plus KPROCESS in Windows. It is the definitive answer to "what does the kernel know about this program?".

/* Linux: include/linux/sched.h — several hundred fields. The ones
   that matter for understanding the model:                     */

struct task_struct {
        /* ---- scheduling ---- */
        unsigned int          __state;        /* RUNNING, INTERRUPTIBLE... */
        int                   prio, static_prio, normal_prio;
        const struct sched_class *sched_class;
        struct sched_entity   se;             /* CFS/EEVDF bookkeeping */
        cpumask_t             cpus_mask;      /* affinity              */

        /* ---- memory ---- */
        struct mm_struct     *mm;             /* NULL for kernel threads */
        struct mm_struct     *active_mm;

        /* ---- identity and relationships ---- */
        pid_t                 pid, tgid;      /* thread id, THREAD GROUP id */
        struct task_struct __rcu *real_parent;
        struct list_head      children, sibling;
        const struct cred    *cred;           /* uid, gid, capabilities */

        /* ---- resources ---- */
        struct files_struct  *files;          /* fd table              */
        struct fs_struct     *fs;             /* cwd, root             */
        struct signal_struct *signal;
        struct sighand_struct *sighand;

        /* ---- kernel-side execution ---- */
        void                 *stack;          /* 8-16 KB kernel stack  */
        struct thread_struct  thread;         /* saved registers       */

        char                  comm[16];       /* the name in `ps`      */
};

/* `current` is a macro giving the running task. On arm64 it reads
   SP_EL0, which the kernel repurposes to hold the task pointer —
   so it is a single register read, not a lookup.               */
The key structural insight

In Linux there is no separate process structure. A process is a group of task_structs sharing a tgid, an mm_struct and a files_struct. Threads and processes are the same object with different sharing. This is why getpid() returns tgid while gettid() returns pid, and it is the single most important thing to understand about the Linux model (chapter 05).

Windows takes the opposite approach: EPROCESS owns the address space and handle table, and ETHREAD objects belong to it. Both designs work; the Linux one is simpler internally, the Windows one maps more directly onto the conceptual model.

Process states

A process is not simply running or not. It moves through a defined set of states, and the distinctions between the non-running ones are exactly what you need when diagnosing something that appears stuck.

                    ┌──────────┐
        created ───►│   NEW    │
                    └────┬─────┘
                         │ admitted
                    ┌────▼─────┐  scheduled  ┌──────────┐
                    │  READY   │────────────►│ RUNNING  │
                    │(runqueue)│◄────────────│          │
                    └────▲─────┘  preempted  └────┬─────┘
                         │                        │ blocks on I/O,
              event      │                        │ lock, or sleep
              occurs     │                        ▼
                    ┌────┴─────┐            ┌──────────┐
                    │ WAITING  │◄───────────│ BLOCKED  │
                    └──────────┘            └──────────┘
                                                 │ exit()
                                            ┌────▼─────┐
                                            │TERMINATED│ ← zombie until
                                            └──────────┘   the parent reaps

Linux state names, and what they mean in `ps`:

  R  TASK_RUNNING            running OR ready — the runqueue
  S  TASK_INTERRUPTIBLE      sleeping; a signal will wake it
  D  TASK_UNINTERRUPTIBLE    sleeping; signals will NOT wake it
                             usually blocked on disk or NFS.
                             A process stuck in D cannot be killed —
                             not even by SIGKILL. This is why
                             "unkillable process" happens.
  T  TASK_STOPPED            SIGSTOP / ptrace
  Z  EXIT_ZOMBIE             finished, awaiting reaping
  I  TASK_IDLE               idle kernel thread

Creating a process

Unix creates processes by duplicating an existing one and then replacing its contents — two steps rather than one. That split looks odd and turns out to be what makes shell redirection and pipes possible.

Unix: fork + exec

pid_t pid = fork();          /* duplicate the calling process */

if (pid < 0) {
        perror("fork");                     /* failed              */
} else if (pid == 0) {
        /* CHILD: fork returns 0 here */
        execl("/bin/ls", "ls", "-l", (char *)NULL);
        _exit(127);                          /* only if exec failed */
} else {
        /* PARENT: fork returns the child's pid */
        int status;
        waitpid(pid, &status, 0);
}
Why two calls instead of one "spawn"?

  Because the gap between fork and exec is where you configure the
  child, using ORDINARY code rather than a hundred spawn() flags:

      pid = fork();
      if (pid == 0) {
              close(0);  open("input.txt", O_RDONLY);   /* redirect */
              dup2(pipefd[1], 1);                        /* pipe out */
              setuid(nobody);                            /* drop privs */
              chdir("/srv");
              setrlimit(RLIMIT_CPU, &lim);
              execv(path, argv);
      }

  That is the entire design of the Unix shell — pipes, redirection
  and job control all live in that gap. Windows' CreateProcess takes
  a large parameter block instead, and cannot express arbitrary
  setup.

Cost, and why it is not as bad as it sounds:
  fork does NOT copy memory. It marks every page COPY-ON-WRITE and
  copies page TABLES only (chapter 13). Pages are duplicated lazily,
  on first write — and exec discards the address space immediately
  anyway, so most are never copied at all.

  posix_spawn() and vfork() exist for the case where even that is
  too much; posix_spawn is the portable choice.
fork() in a threaded program

Only the calling thread survives into the child. Every other thread vanishes mid-operation — including any that held a lock. If a thread was inside malloc when you forked, the child's heap lock is held by a thread that does not exist, and the next allocation deadlocks forever.

Between fork and exec in a multithreaded process you may call only async-signal-safe functions — a short list that excludes malloc, printf and most of libc. In practice: fork, immediately exec, and use posix_spawn() if you can, which handles this correctly.

Windows: CreateProcess

STARTUPINFO si = { .cb = sizeof si };
PROCESS_INFORMATION pi;

/* one call creates and starts a NEW program — no fork equivalent */
CreateProcess(
        L"C:\\Windows\\System32\\cmd.exe",   /* image        */
        cmdline,                              /* command line */
        NULL, NULL,                           /* security     */
        TRUE,                                 /* inherit handles */
        0, NULL, NULL,
        &si, &pi);

WaitForSingleObject(pi.hProcess, INFINITE);
CloseHandle(pi.hThread);
CloseHandle(pi.hProcess);      /* handles are refcounted — close both */

Termination, zombies and orphans

A process ending is more involved than it sounds: its exit status must be kept until someone collects it, and what happens if nobody does is the origin of zombie processes.

exit(0);       /* flushes stdio, runs atexit handlers, then _exit  */
_exit(0);      /* immediate; no cleanup — correct after a failed exec */

/* Kernel-side, exit() does:
     · close all file descriptors
     · release the address space
     · send SIGCHLD to the parent
     · re-parent any children to init (or the nearest subreaper)
     · become a ZOMBIE, keeping only the exit status  */
ZOMBIE — finished, but not yet reaped

  A dead process keeps a task_struct alive purely so the parent can
  read its exit status. It holds no memory, no fds, no CPU — but it
  does hold a PID.

  It is reaped when the parent calls wait()/waitpid(). If the parent
  never does, zombies accumulate until the PID space is exhausted
  and no process can be created system-wide.

  ps aux | grep 'Z'          <- state Z, "<defunct>"

  Fixes, in order of preference:
    · call waitpid() — ideally from a SIGCHLD handler, in a loop:
          while (waitpid(-1, &st, WNOHANG) > 0) ;
    · signal(SIGCHLD, SIG_IGN)  — the kernel reaps automatically
    · double-fork, so the grandchild is orphaned to init


ORPHAN — parent died first

  The child is re-parented to PID 1 (or the nearest process that
  called PR_SET_CHILD_SUBREAPER). init reaps continuously, so
  orphans are harmless. This is the normal way daemons detach.

The process tree

Processes form a tree, and that structure determines who gets told when one dies and what happens to the children of a process that exits first.

pstree -p                  # the whole hierarchy
ps -ef --forest
ps -o pid,ppid,pgid,sid,tty,stat,cmd

/* Four grouping levels, each with a purpose: */
PID      one process (in Linux, one thread group)
PGID     process group — a pipeline. Ctrl+C signals the whole group.
SID      session — a login. Has one controlling terminal.
         Detaching from it (setsid) is how a daemon is born.
Namespace  a private view of PIDs, mounts, network, users.
           This is the mechanism containers are built from.
/* Classic daemonisation, and what each step is for */
if (fork() > 0) _exit(0);      /* parent exits; child is orphaned  */
setsid();                       /* new session: no controlling tty  */
if (fork() > 0) _exit(0);      /* second fork: cannot ever reacquire
                                   a terminal                       */
chdir("/");                     /* do not pin a filesystem          */
umask(0);
close(0); close(1); close(2);   /* reopen on /dev/null              */

/* Modern systems: do NOT do this. Let systemd manage the lifecycle
   (Type=simple) and log to stdout. The double-fork dance exists to
   solve problems a service manager already solves.               */

Inspecting a process

Everything above is visible on a running system, and knowing where to look turns questions about a misbehaving process into observations rather than theories.

# everything the kernel knows, as files
ls /proc/self/
cat /proc/PID/status        # state, threads, uid, memory summary
cat /proc/PID/maps          # the virtual address space
cat /proc/PID/smaps         # per-mapping RSS, PSS, dirty pages
ls  /proc/PID/fd/           # open file descriptors, as symlinks
cat /proc/PID/cmdline       # NUL-separated argv
cat /proc/PID/environ
cat /proc/PID/limits        # rlimits
cat /proc/PID/stack         # kernel stack — WHY is it in D state?
ls  /proc/PID/task/         # one directory per thread

# resource usage
ps -o pid,ppid,stat,%cpu,%mem,rss,vsz,etime,cmd -p PID
top -H -p PID               # per-thread view
/usr/bin/time -v ./program  # peak RSS, faults, context switches

# limits
ulimit -a
prlimit --pid PID
cat /sys/fs/cgroup/.../memory.max
Diagnosing an unkillable process

A process in state D ignores SIGKILL because it is blocked in the kernel in a non-interruptible sleep. Read /proc/PID/stack and /proc/PID/wchan to see exactly which kernel function it is waiting in — almost always a storage or network filesystem call. The fix is to address the underlying I/O (a hung NFS mount, a failing disk), not the process.

Resource limits

The kernel caps what a single process may consume — memory, open files, processes of its own. These limits are the first thing to check when something fails at scale but works in testing.
