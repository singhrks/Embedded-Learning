The Linux device model

Buses, devices and drivers, and the matching process that brings them together. Once you can see this structure, every driver in the tree has the same shape — and the answer to "why does my probe never run" becomes a three-command investigation.

Three objects, one relationship

The device model is the machinery that connects a piece of hardware to the code that drives it. It rests on three objects and one relationship between them, and once that relationship is clear, most of what the kernel does at boot stops looking like magic.

   struct bus_type            "platform", "i2c", "spi", "pci"
        |     owns the MATCH function and the probe/remove
        |     protocol for everything on it
        |
        +-- struct device_driver     code that can drive
        |        · a name                 something
        |        · a match table (of_match_table, id_table)
        |        · .probe / .remove
        |
        +-- struct device            a thing that exists
                 · a parent (the topology)
                 · a bus
                 · resources: reg, irq, clocks, DMA config
                 · a driver, once bound

   THE CORE LOOP, in drivers/base/:

     a DEVICE is registered   -> try every driver on its bus
     a DRIVER is registered   -> try every unbound device on
                                 its bus

     for each candidate:  bus->match(dev, drv)
                                |
                          matched? -> drv->probe(dev)
                                          |
                                    0     -> BOUND
                                    -EPROBE_DEFER -> retry later
                                    other -> not bound

   That is the entire mechanism. Everything else is detail.

   YOU SUBCLASS the generic structures:

     struct platform_device  { struct device dev; ... }
     struct i2c_client       { struct device dev; ... }
     struct spi_device       { struct device dev; ... }

   and get back to yours with container_of(), or with the
   helpers each bus provides (to_platform_device(dev)).

Where devices come from

A struct device never appears from nothing — something in the kernel decided a piece of hardware exists and called device_register() on its behalf, and which mechanism did that decides how the device gets discovered, what identifies it to a driver, and whether it can appear after boot at all.

Matching

Matching is the moment the kernel decides that this driver is the one for that device. Each kind of bus answers that question differently — by name, by a string from the device tree, by a numeric vendor and product ID — but the outcome is always the same.

/* Each bus decides what "match" means. For platform devices
   (drivers/base/platform.c), it tries in order:              */

   1. OF: does dev->of_node's `compatible` appear in the
          driver's of_match_table?          <-- what you use
   2. ACPI match table
   3. the platform id_table
   4. plain strcmp of driver->name against device->name

/* THE OF WAY, which is what an embedded driver writes: */

static const struct of_device_id my_of_match[] = {
        { .compatible = "vendor,my-device-v2",
          .data = &v2_config },          /* per-variant data */
        { .compatible = "vendor,my-device",
          .data = &v1_config },
        { }                              /* SENTINEL - the
                                            empty entry is
                                            REQUIRED         */
};
MODULE_DEVICE_TABLE(of, my_of_match);   /* so modprobe can
                                           autoload this
                                           module for this
                                           compatible        */

static struct platform_driver my_driver = {
        .driver = {
                .name           = "my-driver",
                .of_match_table = my_of_match,
                .pm             = &my_pm_ops,
        },
        .probe  = my_probe,
        .remove = my_remove,
};
module_platform_driver(my_driver);       /* generates
                                            module_init and
                                            module_exit      */

/* USING THE MATCH DATA to support several variants with one
   driver - the standard pattern: */
static int my_probe(struct platform_device *pdev)
{
        const struct my_config *cfg;

        cfg = of_device_get_match_data(&pdev->dev);
        if (!cfg)
                return -EINVAL;

        d->nr_channels = cfg->nr_channels;
        d->has_dma     = cfg->has_dma;
        ...
}

/* THE SENTINEL MATTERS: the match loop runs until it finds an
   entry with an empty compatible string. Omit it and the
   kernel reads past the array - which manifests as a random
   crash during boot, or a driver that matches something
   absurd.                                                  */

A probe function, annotated

probe() is the function you will write most often and the one where most driver bugs live. It is called once per device the kernel decided you own, and its job is to acquire everything the device needs, prove the hardware is really there, and publish an interface.

static int my_probe(struct platform_device *pdev)
{
        struct device *dev = &pdev->dev;
        struct my_dev *d;
        int ret;

        /* 1. allocate the driver's per-device state, managed
              so it is freed automatically (chapter 33)      */
        d = devm_kzalloc(dev, sizeof(*d), GFP_KERNEL);
        if (!d)
                return -ENOMEM;
        d->dev = dev;

        /* 2. MMIO - maps AND reserves the region */
        d->base = devm_platform_ioremap_resource(pdev, 0);
        if (IS_ERR(d->base))
                return PTR_ERR(d->base);

        /* 3. clocks. May defer if the clock driver is late. */
        d->clk = devm_clk_get_enabled(dev, "core");
        if (IS_ERR(d->clk))
                return dev_err_probe(dev, PTR_ERR(d->clk),
                                     "no core clock\n");

        /* 4. regulators, resets, GPIOs, phys - same shape */
        d->vdd = devm_regulator_get(dev, "vdd");
        if (IS_ERR(d->vdd))
                return dev_err_probe(dev, PTR_ERR(d->vdd),
                                     "no vdd supply\n");
        ret = regulator_enable(d->vdd);
        if (ret)
                return ret;

        /* 5. DT properties specific to this device */
        ret = device_property_read_u32(dev, "vendor,fifo-depth",
                                       &d->fifo_depth);
        if (ret)
                d->fifo_depth = 16;      /* a sane default */

        /* 6. per-device locks and structures */
        mutex_init(&d->lock);
        init_waitqueue_head(&d->wq);
        INIT_WORK(&d->work, my_work_fn);

        /* 7. the interrupt - LAST among resources, because
              from here on the hardware can call into us     */
        d->irq = platform_get_irq(pdev, 0);
        if (d->irq < 0)
                return d->irq;

        ret = devm_request_threaded_irq(dev, d->irq, NULL,
                                        my_thread_fn,
                                        IRQF_ONESHOT,
                                        dev_name(dev), d);
        if (ret)
                return dev_err_probe(dev, ret, "irq %d\n",
                                     d->irq);

        /* 8. stash it so remove() and the fops can find it */
        platform_set_drvdata(pdev, d);

        /* 9. initialise the hardware */
        ret = my_hw_init(d);
        if (ret)
                return ret;

        /* 10. LAST: expose it to userspace. Nothing before
               this point could be used by anyone, so there is
               no window in which a half-set-up device is
               reachable.                                    */
        ret = misc_register(&d->misc);
        if (ret)
                return ret;

        dev_info(dev, "ready, %u channels\n", d->nr_channels);
        return 0;
}

/* THE TWO ORDERING RULES that matter:
     · acquire resources before enabling anything that can
       generate events
     · register the userspace interface LAST, and unregister
       it FIRST in remove()                                 */
dev_err_probe() in one line

It logs the error with the device name, records the deferral reason where /sys/kernel/debug/devices_deferred can show it, downgrades -EPROBE_DEFER to a debug message so your logs are not flooded during normal boot, and returns the error code so you can return it directly. Use it for every resource acquisition in probe; there is no reason not to.

Deferred probe, properly understood

Here is behaviour that looks like a bug the first time you see it: your probe() runs, fails because a clock is not available yet, and then runs again later and succeeds. That is deliberate, it is the standard solution to a genuinely hard ordering problem, and fighting it is a mistake.

/* The problem: drivers probe in an order nobody controls, and
   your device needs a clock from a driver that has not loaded.

   The mechanism:

     probe returns -EPROBE_DEFER
        -> the device goes on the DEFERRED LIST
        -> every time ANY driver probes successfully, the
           whole deferred list is retried
        -> eventually the provider appears and you succeed

   So ordering becomes self-organising. No initcall levels, no
   Makefile ordering, no retry loops.                       */

/* WHICH APIs RETURN IT: essentially every resource getter -
   clk_get, regulator_get, gpiod_get, reset_control_get,
   dma_request_chan, phy_get, of_find_i2c_device_by_node...

   JUST PROPAGATE IT. Never swallow it:                    */
        if (IS_ERR(clk))
                return PTR_ERR(clk);     /* right */

        if (IS_ERR(clk)) {
                dev_err(dev, "no clock\n");
                return -ENODEV;          /* WRONG - destroys
                                            the deferral, and
                                            the device never
                                            probes           */
        }

/* WHEN IT NEVER RESOLVES: */
        cat /sys/kernel/debug/devices_deferred
        1c000000.my-device      platform: wait for supplier
                                /soc/clock-controller@1b000000

/* That names both the waiting device and what it waits for.
   If the supplier never appears:
     · its driver is not enabled in the config
     · its DT node is missing or has a typo in `compatible`
     · its own probe is failing - look further up the log

   AND THE END-OF-BOOT REPORT:
        deferred_probe_timeout=10        # cmdline
   After the timeout, remaining deferrals are converted to
   real failures and logged - which turns a silent
   never-probes into a visible error.                      */

The device model in sysfs

Everything described above is visible as a directory tree. Being able to walk it is the fastest way to answer the question every stuck driver raises: did the device appear, did a driver claim it, and if not, which half is missing?

# Every device, by bus:
    ls /sys/bus/platform/devices/
    ls /sys/bus/i2c/devices/

# Every driver, and what it has bound:
    ls /sys/bus/platform/drivers/my-driver/
      bind  unbind  uevent  1c000000.my-device -> ...

# The physical topology:
    ls /sys/devices/platform/soc/1c000000.my-device/
      driver -> ../../../bus/platform/drivers/my-driver
      of_node -> ...
      power/
      uevent
      modalias

# MANUAL BIND AND UNBIND - the most useful debugging tool in
# this chapter:
    echo 1c000000.my-device > \
         /sys/bus/platform/drivers/my-driver/unbind
    echo 1c000000.my-device > \
         /sys/bus/platform/drivers/my-driver/bind

# This re-runs remove() and probe() without unloading the
# module or rebooting. It exercises exactly the paths that
# leak and race, and it is how you test error handling: make
# probe fail, unbind, fix, bind.

# What device tree node produced a device:
    cat /sys/devices/platform/.../of_node/compatible

# Which driver would autoload:
    cat /sys/devices/platform/.../modalias
      of:Nmy-deviceT(null)Cvendor,my-device
# udev matches this against MODULE_DEVICE_TABLE entries.

Classes and the userspace view

Devices are also grouped by what they are, independently of how they are wired. That grouping is what lets user space find every temperature sensor on a machine without knowing whether they sit on I2C, SPI or USB.

/* A device's place in /sys/devices is its PHYSICAL topology.
   A CLASS gives it a FUNCTIONAL identity:                  */

        /sys/class/net/eth0
        /sys/class/tty/ttyS0
        /sys/class/gpio/
        /sys/class/thermal/thermal_zone0
        /sys/class/misc/my-device

/* Registering with the right class is what makes generic
   userspace tools work with your device. A driver that
   registers as an IIO device gets libiio, a hwmon device gets
   `sensors`, an input device gets evdev - for free.

   THE ADVICE: before writing a character device with a custom
   ioctl interface (chapter 23), check whether a SUBSYSTEM
   already exists for your device class:

        IIO        sensors, ADCs, DACs
        hwmon      temperature, voltage, fan
        input      buttons, touch, keyboards
        rtc        real-time clocks
        watchdog   watchdogs
        pwm, led, gpio, regulator, clk, thermal
        v4l2       video capture
        ALSA       audio
        MTD        raw flash
        crypto     accelerators
        tee        trusted execution (isolation ch. 12)

   Using the right subsystem means: a stable, documented
   userspace ABI you did not have to design; existing tools;
   power management and buffering handled for you; and a much
   easier upstreaming path (chapter 45). Writing a bespoke
   char device for a temperature sensor is the most common
   avoidable mistake in embedded driver work.             */

Remove, the mirror image

Everything probe() did has to be undone, in reverse, when the device goes away or the module is unloaded. This path gets far less testing than probe and is where drivers that work perfectly in normal use fall over.

static void my_remove(struct platform_device *pdev)
{
        struct my_dev *d = platform_get_drvdata(pdev);

        /* EXACT REVERSE of probe: */

        /* 1. userspace interface first - no new users */
        misc_deregister(&d->misc);

        /* 2. stop the hardware generating events */
        writel(0, d->base + REG_INT_ENABLE);

        /* 3. wait for anything in flight (chapter 15) */
        cancel_work_sync(&d->work);

        /* 4. quiesce the device */
        my_hw_shutdown(d);

        /* 5. devm_ handles the irq, ioremap, clk and the
              allocation itself - in reverse order,
              automatically                                  */

        /* 6. what devm does NOT handle: anything you enabled
              or initialised by hand                         */
        regulator_disable(d->vdd);
}

/* NOTE remove() returns void in modern kernels (6.11+). It
   used to return int, and the return value was ignored
   anyway - because there is no meaningful way to refuse to
   remove a device that is going away.                     */
