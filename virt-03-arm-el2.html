EL2 and the ARM virtualisation extensions

EL2 is not simply "one more privilege level". It is a level with its own translation regime, its own vector table, its own timer, its own stack pointer and — crucially — a control register that decides which EL1 operations are allowed to complete without asking permission. This chapter is the anatomy.

Where EL2 sits

EL2 is not simply "one above EL1" — it sits differently from the other exception levels, and the asymmetries are what the rest of the track keeps running into.

                NON-SECURE                    SECURE

   EL0    application                    trusted application (S-EL0)
            |                                   |
   EL1    guest kernel                    trusted OS, e.g. OP-TEE (S-EL1)
            |                                   |
   EL2    HYPERVISOR                      S-EL2 partition manager
            |                             (ARMv8.4+, e.g. Hafnium)
            |                                   |
   EL3    +---------------------------------------------+
          |  secure monitor - TF-A BL31                 |
          |  the only code that switches WORLDS          |
          +---------------------------------------------+
                            |
                        hardware

   Two orthogonal axes, and confusing them is the commonest
   beginner error on this page:

     EXCEPTION LEVEL  = how much privilege   (EL0 < EL1 < EL2 < EL3)
     SECURITY STATE   = which world          (Non-secure | Secure | Realm)

   EL2 is a level. TrustZone is a state. A hypervisor at EL2 and
   a trusted OS at S-EL1 are not competing for the same seat;
   they are in different worlds, and EL3 arbitrates.
Realms, briefly

ARMv9 CCA adds a third security state (Realm) with its own R-EL2 running the Realm Management Monitor. The idea is a guest that even the hypervisor cannot read. It does not change anything in this chapter; it adds a column to the diagram. Chapter 20 covers the secure and realm sides together.

Register banking: the part that confuses everyone

System registers are banked per exception level. TTBR0_EL1 and TTBR0_EL2 are two different physical registers. The guest at EL1 writes TTBR0_EL1 and the hypervisor's own TTBR0_EL2 is untouched. This is why a guest can run with real EL1 registers without endangering EL2.

   What is banked (separate copy per level):

     SCTLR_EL1  SCTLR_EL2      system control
     TTBR0_EL1  TTBR0_EL2      translation base
     TCR_EL1    TCR_EL2        translation control
     VBAR_EL1   VBAR_EL2       vector base
     ESR_EL1    ESR_EL2        syndrome
     FAR_EL1    FAR_EL2        fault address
     ELR_EL1    ELR_EL2        return address
     SPSR_EL1   SPSR_EL2       saved state
     SP_EL1     SP_EL2         stack pointer
     MAIR_EL1   MAIR_EL2       memory attributes

   What is NOT banked and MUST be saved/restored by hand
   on every world switch:

     X0-X30, SP_EL0, PC (via ELR)
     the FP/SIMD register file  (lazily, if you are careful)
     PMU counters, debug/breakpoint registers
     TPIDR_EL0, TPIDRRO_EL0, TPIDR_EL1

   THIS asymmetry is exactly why the vCPU context switch
   (chapter 08) has the shape it does: the banked half is free,
   the unbanked half is a long list of MRS/MSR pairs.
Why banking is the performance story

Because EL1 state is banked away from EL2 state, entering the hypervisor does not destroy the guest's configuration. A trap that the hypervisor can service without touching guest registers — reading ESR_EL2, updating a shadow value, returning — costs a few hundred cycles. A full vCPU switch costs thousands, because the unbanked list above must move. Minimising exits matters; minimising full switches matters more.

Getting into EL2 in the first place

You do not enter EL2 by asking. On a cold boot the CPU comes up at the highest implemented level (EL3 if TrustZone is implemented), and firmware drops into EL2 deliberately. If your bootloader dropped you straight to EL1, no hypervisor can run on that system, and no amount of software will fix it.

/* TF-A BL31 preparing to hand off. Simplified. */

    /* Decide the level the next image runs at. */
    scr  = SCR_EL3_RW          /* next level is AArch64      */
         | SCR_EL3_NS          /* next level is Non-secure   */
         | SCR_EL3_HCE;        /* HVC is ENABLED - without
                                  this, HVC is UNDEFINED and
                                  no guest can call EL2      */
    write_scr_el3(scr);

    spsr = SPSR_MODE_EL2h      /* <-- land at EL2, using SP_EL2 */
         | DAIF_ALL_MASKED;
    write_spsr_el3(spsr);
    write_elr_el3(bl33_entry);
    eret;                      /* now executing at EL2         */


/* Linux's own head.S then decides whether to STAY at EL2. */

    mrs     x0, CurrentEL
    cmp     x0, #CurrentEL_EL2
    b.ne    1f                 /* booted at EL1: no KVM, ever  */

    /* We are at EL2. Two choices:
         - stay here  -> VHE, host kernel runs AT EL2 (ch. 09)
         - drop to EL1-> nVHE, only a small stub stays at EL2 */

The single most common bring-up failure

All CPU(s) started at EL1. Every secondary core must also arrive at EL2, not just the boot core — a firmware that starts CPU0 at EL2 and the rest at EL1 produces a kernel that initialises KVM and then fails on the first vCPU pinned elsewhere. Check CurrentEL on every core, not one.

Discovering what the silicon supports

Virtualisation features are optional and vary by implementation, so the first thing a hypervisor does is ask the silicon what it actually has. These are the registers that answer.

/* ID_AA64PFR0_EL1 - the feature register that matters here. */

  bits [11:8]  EL2 support
                 0b0000  EL2 not implemented -> no virtualisation
                 0b0001  EL2 implemented, AArch64 only
                 0b0010  EL2 implemented, AArch64 + AArch32

  bits [15:12] EL3 support (same encoding)

/* ID_AA64MMFR1_EL1 */

  bits [3:0]   VHE          0b0001 = ARMv8.1 VHE present (ch. 09)
  bits [7:4]   VMIDBits     0b0010 = 16-bit VMIDs, else 8-bit
  bits [15:12] HPDS, [19:16] HAFDBS ...

/* ID_AA64MMFR2_EL1 */
  bits [3:0]   CnP, [15:12] IESB, [55:52] E0PD ...

# On a phone this never matters. On a 128-core server running

HVC: the deliberate call

SVC goes EL0→EL1. HVC goes EL1→EL2. SMC goes to EL3. They are three doors at three levels, and the calling conventions rhyme.

/* A guest asking its hypervisor for something. This is how PSCI,
   KVM's PV features and Xen's hypercalls all work.            */

    mov     x0, #0x84000001        /* PSCI CPU_ON, SMC32 range   */
    mov     x1, target_cpu_mpidr
    mov     x2, entry_point
    mov     x3, context_id
    hvc     #0                     /* trap to EL2               */
    /* x0 now holds the return value, per SMCCC                 */

/* Which door a PSCI call goes through depends on the guest:
     bare-metal Linux at EL1, TF-A at EL3   -> SMC
     Linux guest under KVM                  -> HVC, and KVM
                                               either handles it
                                               or forwards to EL3

   KVM tells the guest which to use through the device tree:

     psci {
         compatible = "arm,psci-1.0";
         method = "hvc";        <-- or "smc" on bare metal
     };

   Getting this wrong gives you a guest that hangs on secondary
   CPU bring-up: it calls SMC, the call sails past EL2 to EL3,
   and firmware tries to power on a PHYSICAL core for a VIRTUAL
   request.                                                     */
