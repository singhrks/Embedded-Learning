Debugging bare metal: SWD, breakpoints and semihosting

There is no gdb attaching to a process here — there is a two-wire connection to the silicon itself, and a debug unit built into the core. This chapter covers what that unit can do, and the techniques that work when stopping the CPU is not an option.

SWD and what is behind it

   Two wires plus ground. SWCLK and SWDIO.

   HOST                    TARGET
   +--------+  SWCLK   +--------------------------------+
   | probe  |-------->--| SW-DP  (debug port)            |
   | ST-Link|  SWDIO   |    |                            |
   | J-Link |<------->--|    +-- AHB-AP (memory access)  |
   | CMSIS  |          |    |      |                     |
   | -DAP   |          |    |      +--> the whole bus:   |
   +--------+          |    |           RAM, flash,      |
                       |    |           peripherals      |
                       |    |                            |
                       |    +-- core debug registers:    |
                       |         halt, step, breakpoints |
                       |                                 |
                       |    FPB   6 hardware breakpoints |
                       |    DWT   4 watchpoints, cycle   |
                       |          counter, profiling     |
                       |    ITM   instrumentation trace  |
                       +--------------------------------+

   The key property: the AHB-AP is a BUS MASTER. The probe
   can read and write any address WITHOUT halting the core.
   That is what makes live variable watching possible, and
   it is the basis of the best debugging techniques here.

Breakpoints and watchpoints are finite

/* HARDWARE BREAKPOINTS: the FPB unit compares the fetch
   address against a small set of registers. Cortex-M3/M4
   give you SIX. Cortex-M0 gives you FOUR.

   They work in flash, which software breakpoints cannot -
   a software breakpoint replaces the instruction with BKPT,
   and you cannot rewrite flash cheaply. So on an MCU the
   limit is hard: your seventh breakpoint silently does not
   work, or your debugger refuses.

   WATCHPOINTS: the DWT unit, FOUR comparators, trigger on a
   data ADDRESS being read or written. These are the most
   under-used feature in embedded debugging.               */

/* THE CANONICAL USE: "this variable is being corrupted and
   I have no idea by what."                                */

(gdb) watch g_sensor_state
(gdb) continue
/* Hardware Watchpoint 2: g_sensor_state
   Old value = 3
   New value = 51966
   memcpy () at string.c:71                                */

/* Three seconds instead of three days. A watchpoint answers
   "who wrote here" directly, and it is the correct first
   move for any corruption bug rather than the last resort
   it usually is.

   You can also set one from code, which is useful when the
   corruption happens before the debugger connects:        */
DWT->COMP0     = (uint32_t) &g_sensor_state;
DWT->MASK0     = 0;
DWT->FUNCTION0 = (6u << 0);   /* watch for writes */
Halting changes the system

Stopping the core stops your code, but not the world. A motor keeps spinning, a PWM output freezes at whatever level it held, a UART peer times out, a watchdog fires, and any peripheral with a FIFO overflows. For anything with a control loop or a protocol partner, halting produces a state that could never occur at run time — and you then debug the artefact rather than the bug. This is why the non-stop techniques below matter more on an MCU than on a workstation.

Getting output, cheapest first

/* 1. A GPIO PIN AND A SCOPE.  Cost: ~2 cycles.
      The fastest instrumentation that exists. Toggle a pin
      at the top and bottom of an ISR and you can MEASURE
      its duration and jitter directly - something no
      software tool gives you.                             */
#define PROBE_HI()  (GPIOB->BSRR = (1u << 0))
#define PROBE_LO()  (GPIOB->BSRR = (1u << 16))

void TIM2_IRQHandler(void) {
    PROBE_HI();
    /* ... work ... */
    PROBE_LO();
}
/* The scope now shows execution time, frequency, and
   whether two ISRs ever overlap. For real-time work this
   beats every other technique.                             */

/* 2. ITM / SWO.  Cost: ~5 cycles per word.
      A dedicated trace pin. Non-blocking: writes go to a
      FIFO and are dropped if it is full, so your timing is
      barely perturbed.                                     */
static inline void itm_putc(char c) {
    if ((ITM->TCR & 1) && (ITM->TER & 1)) {
        while (ITM->PORT[0].u32 == 0) { }
        ITM->PORT[0].u8 = (uint8_t) c;
    }
}
/* SWO needs the trace clock configured to match the probe's
   expectation - the usual reason "SWO produces garbage".   */

/* 3. RTT (Segger's Real Time Transfer).  Cost: ~1 us.
      A ring buffer in RAM that the probe reads over SWD
      WITHOUT halting - using the AHB-AP's bus mastering.
      No extra pin, works on any part with SWD, and is
      roughly a thousand times faster than semihosting.
      For most projects this is the right answer.           */

/* 4. UART printf.  Cost: 87 us per character at 115200.
      Blocking, and slow enough to change timing profoundly.
      A printf in an ISR that runs at 10 kHz is an instant
      system failure. Use DMA if you must have it.          */

/* 5. SEMIHOSTING.  Cost: MILLISECONDS per call.
      The core executes BKPT 0xAB and the DEBUGGER performs
      the I/O. Convenient, needs no hardware, and:

        - HALTS THE CPU for every character
        - HANGS THE CHIP if no debugger is attached, because
          BKPT with no debugger escalates to HardFault

      That second point ships products that work on the
      bench and brick in the field. Use semihosting for
      early bring-up only, and make sure it cannot survive
      into a release build.                                 */

Measuring time exactly

/* The DWT cycle counter is a free, exact, 32-bit tally of
   core cycles. It is the correct tool for micro-benchmarks
   and for proving a deadline is met.                      */

static void cycle_counter_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->LAR   = 0xC5ACCE55;      /* unlock on some parts   */
    DWT->CYCCNT = 0;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;
}

uint32_t t0 = DWT->CYCCNT;
do_the_thing();
uint32_t elapsed = DWT->CYCCNT - t0;   /* wrap-safe subtraction */

/* At 168 MHz one cycle is 5.95 ns, and the counter wraps
   every 25.6 seconds. The subtraction above is correct
   across the wrap for any interval shorter than that.

   Use it to record a WORST CASE rather than an average -
   the maximum is what a deadline cares about:             */
static uint32_t worst;
if (elapsed > worst) { worst = elapsed; }

/* This turns "the ISR is fast enough" from an opinion into
   a number you can assert on. Combined with the priority
   analysis of chapter 08, it is most of what real-time
   verification amounts to on a small system.              */

When there is no debugger at all

   The situations that actually matter in production:

   FIELD FAILURE          -> .noinit crash log, reported on
                             the next boot (chapter 15)

   TIMING-DEPENDENT BUG   -> GPIO probe + scope; halting
                             would destroy the evidence

   HAPPENS ONCE A WEEK    -> RTT ring buffer left running,
                             read whenever it triggers

   DEBUG PORT DISABLED    -> a fault log over whatever
   (security)                interface the product already
                             has, gated behind
                             authentication

   BOOTS AND DIES BEFORE  -> toggle a pin at successive
   THE PROBE CONNECTS        points in startup; the last
                             one that toggles brackets it.
                             Crude, and it always works.

   The common thread: design the observability in before you
   need it. A product with a crash log, a probe pin and an
   RTT buffer is debuggable in the field. One without them
   requires the unit back on your desk - and it will then
   fail to reproduce.
