Race conditions and data races

Two different bugs share one word. A data race is undefined behaviour and a tool can find it. A race condition is a logic error that no tool can find, because the code is doing exactly what you wrote. Telling them apart tells you which of the two entirely different fixes you need.

The two bugs

Start with the smallest possible example. Two threads incrementing one counter is enough to lose updates, and seeing precisely where the interleaving goes wrong is what makes every mechanism later in the track obviously necessary.

   DATA RACE - a language-level violation

     two threads access the same memory location
     at least one writes
     they are not ordered by any synchronisation

     -> UNDEFINED BEHAVIOUR in C, C++ and Rust-with-unsafe.
        Not "you get one value or the other". The compiler
        was allowed to assume this never happens, so it may
        have optimised on that assumption.

     FOUND BY: ThreadSanitizer, Helgrind, the Go race
               detector, Rust's type system at compile time.
     FIXED BY: a lock, an atomic, or not sharing.


   RACE CONDITION - a logic error about ordering

     the program's correctness depends on which of several
     legal orderings actually happens.

     -> WELL-DEFINED BEHAVIOUR. Every individual operation is
        properly synchronised. The SEQUENCE is wrong.

     FOUND BY: thinking, review, stress tests, and production.
     FIXED BY: making the composite operation atomic, or
               removing the assumption about order.


   EVERY DATA RACE IS A RACE CONDITION.
   NOT EVERY RACE CONDITION IS A DATA RACE.

   And the second kind is the one that survives to production,
   precisely because your tools said the code was clean.
/* A DATA RACE. TSan finds this in seconds. */

int counter;                            /* plain int          */

void *worker(void *_) {
        for (int i = 0; i < 100000; i++)
                counter++;              /* unsynchronised RMW  */
        return NULL;
}
/* Fix: make it atomic, or hold a lock. */


/* A RACE CONDITION with NO data race. TSan says nothing. */

std::mutex m;
std::map<std::string, int> cache;

int get_or_create(const std::string &k)
{
        {   std::lock_guard<std::mutex> g(m);
            auto it = cache.find(k);
            if (it != cache.end())
                    return it->second;      /* properly locked  */
        }                                   /* LOCK RELEASED    */

        int v = expensive_compute(k);       /* slow, unlocked   */

        {   std::lock_guard<std::mutex> g(m);
            cache[k] = v;                   /* properly locked  */
            return v;
        }
}

/* Every access to `cache` is under the mutex. No data race.
   But two threads calling get_or_create("x") simultaneously
   both miss, both compute, and both insert. If
   expensive_compute has a side effect - allocating an id,
   opening a connection, charging a card - you have just done
   it twice.

   THE BUG IS THE GAP between the two locked regions. */
The test: could an adversary schedule this?

Imagine an adversary who chooses when every thread is preempted, at instruction granularity, with full knowledge of your code. Would the program still be correct? Not "is it likely" — the window in the example above is milliseconds wide, and under load it is hit constantly. Any reasoning of the form "the chance of that is tiny" is a bug you have decided not to fix.

The shapes races take

"Race condition" covers several distinct failure shapes with different causes and different fixes. Naming them separately is what turns an unreproducible bug into a specific thing to look for.

ShapeExampleFix
Check-then-actif (!exists(f)) create(f);One atomic operation: O_CREAT|O_EXCL, try_emplace, compare-and-swap
Read-modify-writex = x + 1An atomic RMW, or a lock
Lost updateTwo threads read a record, both edit, both saveOptimistic concurrency: a version number checked on write
Time-of-check to time-of-useaccess() then open()Never re-resolve; use the handle you already checked. A security bug, not just a correctness one
Publication raceSet a pointer, then initialise the objectInitialise fully, then publish with a release store (chapter 12)
Iterator invalidationOne thread iterates while another insertsHold the lock for the whole iteration, or copy, or use a concurrent container
Lifetime raceThread B uses an object thread A is destroyingShared ownership (shared_ptr, refcount) or a join before teardown
Lazy initDouble-checked locking, written by handstd::call_once, a function-local static, or an acquire/release pair done properly

Double-checked locking, the canonical wrong answer

Double-checked locking is the most famous broken optimisation in concurrent programming — it looks obviously correct, was widely published, and is wrong for reasons that only became expressible once languages gained memory models.

/* THE BROKEN VERSION. Published in books for a decade. */

Singleton *instance;                     /* plain pointer      */
std::mutex m;

Singleton *get(void)
{
        if (!instance) {                 /* 1. unsynchronised
                                               read            */
                std::lock_guard<std::mutex> g(m);
                if (!instance)
                        instance = new Singleton();   /* 2. */
        }
        return instance;
}

/* TWO independent defects:

   (a) Line 1 reads `instance` with no synchronisation while
       line 2 writes it. That is a DATA RACE: undefined
       behaviour, full stop.

   (b) Even if the read were somehow fine, `new Singleton()`
       is three steps:
              allocate
              construct
              assign to instance
       and nothing forces that order. A compiler or CPU may
       publish the pointer BEFORE the constructor has run.
       Another thread sees non-null, returns it, and uses a
       half-built object.

   Defect (b) is why this is famous: the code looks right, the
   bug is invisible in the source, and it appears only on
   weakly-ordered hardware like ARM - so it ships from an x86
   developer's laptop and fails on the phone.               */


/* CORRECT, and simplest: */
Singleton &get(void)
{
        static Singleton instance;   /* C++11 guarantees this
                                        is thread-safe and
                                        initialised exactly
                                        once                  */
        return instance;
}

/* CORRECT, when you need the pointer form: */
std::atomic<Singleton *> instance{nullptr};
std::mutex m;

Singleton *get(void)
{
        Singleton *p = instance.load(std::memory_order_acquire);
        if (!p) {
                std::lock_guard<std::mutex> g(m);
                p = instance.load(std::memory_order_relaxed);
                if (!p) {
                        p = new Singleton();
                        /* release: everything the constructor
                           wrote is visible to any thread that
                           acquires this pointer.             */
                        instance.store(p, std::memory_order_release);
                }
        }
        return p;
}

Finding them on purpose

Races rarely reproduce on demand, so finding them by testing is unreliable. These tools find them by checking the rules on every access rather than waiting for the unlucky interleaving to occur.

# ThreadSanitizer - finds DATA races, not race conditions.
# Roughly 5-15x slower, 5-10x more memory. Worth every cycle.
$ gcc -fsanitize=thread -g -O1 app.c -o app
$ ./app
WARNING: ThreadSanitizer: data race (pid=4211)
  Write of size 4 at 0x5586f4a0 by thread T2:
    #0 worker app.c:12
  Previous read of size 4 at 0x5586f4a0 by thread T1:
    #0 worker app.c:12
  Location is global 'counter' of size 4

# It only reports races it OBSERVES. Code paths not executed
# are not checked, so run it against your real workload.

$ valgrind --tool=helgrind ./app       # slower, no rebuild
$ go test -race ./...                  # built in
$ cargo +nightly build -Z sanitizer=thread

# For RACE CONDITIONS, no tool. What actually works:
#   * run with more threads than cores, so preemption is
#     constant rather than rare
#   * inject delays at suspicious points and see what breaks
#   * stress in a loop for hours; log the interleaving
#   * model-check the protocol (TLA+, Spin) if it is critical

# Widening the window deliberately - the cheapest technique
# in this whole chapter:
        auto it = cache.find(k);
        if (it != cache.end()) return it->second;
+       std::this_thread::sleep_for(std::chrono::milliseconds(50));
        int v = expensive_compute(k);
# If the bug is a gap between two locked regions, a sleep in
# the gap turns "once a week" into "every single time".
A clean TSan run is not a clean program

ThreadSanitizer proves the absence of data races on the paths it executed. It says nothing about race conditions, nothing about paths you did not run, and nothing about ordering bugs across processes or against hardware. Treat it as a lint that catches an important, mechanical class of bug — not as a proof.
