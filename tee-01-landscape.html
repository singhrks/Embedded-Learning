What OP-TEE is and what it is for

OP-TEE is a small operating system that runs in the ARM secure world and hosts isolated applications. Its purpose is narrow and worth stating precisely: to keep a handful of operations correct even when the main operating system running beside it has been completely compromised.

The threat model, stated properly

Before any code, be precise about what a TEE defends against — because it is a narrower set than most product requirements assume, and the gap between the two is where security theatre lives.

   WHAT OP-TEE DEFENDS AGAINST

     a compromised Linux kernel
     a compromised bootloader (after the point of measurement)
     a malicious or buggy application with root
     an attacker with a debugger on the normal world
     someone reading the eMMC out of a dead phone

   WHAT IT DOES NOT DEFEND AGAINST

     physical attacks on the SoC - decapping, laser fault
       injection, microprobing
     a compromised EL3 (TF-A). EL3 is above OP-TEE.
     a compromised boot ROM or fused-in keys
     side channels it has not been hardened against -
       cache timing, power analysis, Spectre-class leaks
     a bug in your own trusted application. A TA is
       PRIVILEGED code; a bug there is worse than a bug in
       Linux, not better.

   The last one is the important one. Moving code into the
   secure world does not make it secure. It makes it
   PRIVILEGED. If the code is wrong, you have moved the
   vulnerability somewhere harder to patch and more valuable
   to attack.
The rule for what belongs in a TA

Put in the secure world only what must be protected from the normal world, and as little of it as possible. A key that must never leave: yes. The policy that decides when to use it: yes, if the policy is security-relevant. The parsing of an untrusted network protocol: absolutely not — parse in Linux and pass a validated, fixed-size structure across.

Four things people get wrong

Four beliefs about trusted execution that are common, reasonable-sounding and wrong. Each leads to a design that is weaker than its authors believe.

BeliefReality
"Code in a TA is secure"Code in a TA is privileged. A buffer overflow there is exploitable at S-EL0 with access to key material
"The TEE protects against physical attack"Only as far as the SoC's own countermeasures go. TrustZone is not a secure element
"TAs are fast because they are close to the hardware"Every invocation is a world switch and an SMC. TAs are for infrequent, valuable operations
"OP-TEE can be added to a product later"It needs a secure memory carve-out, a TZASC configuration, a signing key infrastructure and a boot chain. It is a platform decision, not a feature

SymptomCause
