Storage duration, scope and linkage

Three independent properties that every identifier in C has, and that beginners routinely merge into one vague notion of "global". Separating them explains static's two unrelated meanings, why extern exists, and what actually ends up in each section of your binary.

Three orthogonal questions

Three separate questions get confused constantly because one keyword answers more than one of them. Separating them is what makes static — which does two entirely different things depending on where it appears — finally make sense.

PropertyQuestion it answersValues
Storage durationWhen does the object exist?static, automatic, thread, allocated
ScopeWhere is the name visible in the source?file, block, function, function-prototype
LinkageDo declarations in different translation units refer to the same object?external, internal, none
 
They are independent. All eight useful combinations occur:

  int g;                     file scope, external linkage, static duration
  static int s;              file scope, INTERNAL linkage, static duration
  void f(void) {
      int a;                 block scope, no linkage, AUTOMATIC duration
      static int c;          block scope, no linkage, STATIC duration
      extern int g;          block scope, external linkage
      _Thread_local int t;   thread duration
      int *p = malloc(4);    p is automatic; *p has ALLOCATED duration
  }

The word `static` means two completely different things depending on
where it appears. That is a genuine wart in the language, not
something you are failing to understand.

Storage duration

How long an object lives is a property of where and how it is declared, and it determines whether returning a pointer to it is fine or catastrophic.

Automatic

void f(void)
{
        int a;              /* INDETERMINATE — not zero */
        int b = 0;          /* explicitly initialised    */
        char buf[1024];     /* 1 KB of stack             */
}                           /* all cease to exist here    */

/* Reading an uninitialised automatic object is undefined behaviour,
   not "reads garbage". The compiler may assume it never happens.
   -Wuninitialized and -fsanitize=memory catch it.               */

/* Lifetime ends at the closing brace, INCLUDING inner blocks: */
int *p;
{
        int x = 5;
        p = &x;
}
*p;                         /* dangling: x's lifetime ended        */

/* Stack size is finite and often small:
     Linux userspace thread   8 MB default
     Linux KERNEL stack       8-16 KB    <- total, for the whole call chain
     Cortex-M firmware        1-8 KB
   Which is why kernel code never puts large buffers on the stack,
   and why VLAs are banned there (chapter 05).                    */

Static

int g_count;                /* zero-initialised, guaranteed */
static int s_flag = 1;
const char msg[] = "hi";

void f(void)
{
        static int calls = 0;    /* initialised ONCE, before main();
                                    retains its value between calls */
        calls++;
}

/* Static objects with no explicit initialiser are ZERO-initialised.
   This is a guarantee, unlike automatic storage.                  */

/* The initialiser must be a CONSTANT EXPRESSION — evaluated at
   translation time, not at run time:                             */
static int a = 5;              /* fine                    */
static int b = 5 * 3;          /* fine: constant folded   */
static int c = f();            /* ERROR in C (legal in C++) */
static int d = another_static; /* ERROR: not a constant     */
Static duration and reentrancy

A function-local static makes the function non-reentrant: two threads, or an interrupt handler and mainline code, share that one object. This is why strtok, asctime and gmtime all have _r variants, and why a "just cache it in a static" optimisation is a concurrency bug waiting for a second thread. Use a caller-supplied buffer, or _Thread_local.

Thread

#include <threads.h>
_Thread_local int errno_like;      /* C11; one instance per thread   */
thread_local int x;                 /* C23 spelling / <threads.h>     */
__thread int y;                     /* GCC extension, widely used     */

/* Cost: access needs a TLS lookup — cheap but not free, and in
   shared libraries it can require a function call the first time.
   In the Linux kernel the equivalent is per-CPU data:            */
DEFINE_PER_CPU(int, my_counter);
this_cpu_inc(my_counter);       /* no locking needed: it is ours */

Allocated

void *p = malloc(n);            /* lifetime: from malloc to free     */
/* Covered fully in chapter 14. The key point here is that the
   POINTER has automatic duration while the OBJECT has allocated
   duration — two different lifetimes, and confusing them is
   exactly what a memory leak or a dangling pointer is.          */

Linkage, and what the linker sees

Linkage decides whether a name in one translation unit refers to the same object as the same name in another. It is what the linker actually operates on, and mismatches here produce errors at link time rather than compile time.

LinkageMeaningHow to get it
ExternalOne object shared across all translation unitsFile-scope declaration without static
InternalOne object per translation unit; invisible to the linkerFile-scope static
NoneNot shared at allBlock-scope objects, function parameters, typedefs
 
/* util.c */
int  public_counter;              /* external: visible everywhere    */
static int private_state;         /* internal: only this file        */
static void helper(void) { }      /* internal: not in the symbol table */
void api_function(void) { }       /* external                        */

/* main.c */
extern int public_counter;        /* refers to util.c's object       */
/* extern int private_state; */   /* LINK ERROR: undefined symbol    */
Why static at file scope is good practice, not just hiding
  • Prevents name collisions across the whole program — a real problem in large C codebases with no namespaces.
  • Enables optimisation. The compiler can see every use of an internal-linkage function, so it can inline it aggressively, clone it, change its calling convention, or delete it entirely if unused.
  • Documents intent — this is an implementation detail, not API.
  • Shrinks the symbol table and the exported surface.

Rule: everything at file scope should be static unless it is declared in a header. Build with -Wmissing-prototypes to catch violations mechanically.

Declaration versus definition

C distinguishes declaring that something exists from defining it, and the rules about how many of each you may have are the direct cause of the most common linker errors.

/* A DECLARATION introduces a name and its type.
   A DEFINITION additionally allocates storage or supplies a body.
   You may declare a thing many times; you may define it once.    */

extern int x;                /* declaration                       */
int x;                       /* definition (tentative — see below) */
int x = 5;                   /* definition with initialiser        */

void f(void);                /* declaration (prototype)            */
void f(void) { }             /* definition                         */

/* The C-specific wrinkle: a TENTATIVE definition. */
int x;          /* at file scope, with no initialiser, this is a
                   "tentative definition". Several are allowed in
                   ONE translation unit and collapse into one.    */

/* Across translation units, C90 compilers accepted multiple
   tentative definitions and merged them — the "common symbol"
   model. GCC 10 changed the default to -fno-common, so this is
   now an error, as it always should have been:               */

/* a.c */  int counter;
/* b.c */  int counter;      /* error: multiple definition of `counter' */

/* THE CORRECT PATTERN, and the only one you should use: */

/* counter.h */
extern int counter;          /* declaration only, in the header */

/* counter.c */
#include "counter.h"         /* include your OWN header — this is
                                what makes the compiler check the
                                definition against the declaration */
int counter = 0;             /* the single definition             */

Header discipline

Headers are just textual inclusion, with no module system underneath. The conventions below exist to stop that simplicity producing duplicate definitions and inconsistent declarations.

/* my_module.h */
#ifndef MY_MODULE_H
#define MY_MODULE_H            /* include guard — always            */

#include <stddef.h>            /* headers must be self-contained:
                                  include what YOU need, so the
                                  user need not guess the order    */

struct my_thing;               /* forward declaration is enough if
                                  callers only handle pointers      */

extern int my_global;                       /* declaration       */
int  my_init(void);                          /* declaration       */
void my_process(struct my_thing *, size_t);

/* An inline function in a header needs care in C (unlike C++): */
static inline int my_helper(int x) { return x * 2; }
/* `static inline` gives every TU its own copy with internal
   linkage. It always works, and is what you want 99% of the time.
   Plain `inline` in C requires exactly one TU to also provide an
   `extern inline` definition, which is a rule almost nobody
   remembers correctly.                                          */

#endif /* MY_MODULE_H */
Put in the headerKeep in the .c file
Declarations of public functionsDefinitions
extern declarations of public variablesThe one definition
Types callers must know the size ofTypes callers only hold pointers to (opaque)
Macros and constants that are part of the APIInternal macros
static inline helpers, if small and hotEverything else
 
/* Opaque types: the single most useful encapsulation technique in C */

/* device.h — callers see only a pointer */
struct device;                            /* incomplete type      */
struct device *device_create(void);
int  device_read(struct device *, void *, size_t);
void device_destroy(struct device *);

/* device.c — the layout is private */
struct device {
        int fd;
        char name[64];
        struct buffer *buf;
};

/* Callers cannot allocate one on the stack, cannot access members,
   and cannot break when you change the layout. The whole struct is
   an implementation detail. This is how every good C library is
   structured — FILE*, pthread_t and struct device in the kernel
   are all this pattern.                                          */

Where objects actually land

Where a variable ends up in the final binary — initialised data, zero-filled data, read-only — follows from how you declared it, and on an embedded target that placement is something you actively care about.

   ELF sections, and what maps to each

   .text     code, read-only, executable
             functions, and const data on some targets

   .rodata   read-only data
             string literals, const arrays, jump tables
             -> writing here faults (chapter 05)

   .data     initialised read-write static-duration objects
             int g = 5;
             -> occupies space in the BINARY (the initial values
                must be stored somewhere)

   .bss      zero-initialised static-duration objects
             int g;  static char buf[1<<20];
             -> occupies NO space in the binary, only a size.
                The loader (or startup code) zeroes it.
                This is why a 1 MB zeroed array costs nothing on disk.

   stack     automatic-duration objects
   heap      allocated-duration objects
# see it for yourself
size ./program
#    text    data     bss     dec     hex filename
#   12345     456   10240   23041    5a01 ./program

nm -C --size-sort ./program | tail -20     # largest symbols
nm ./program | grep ' [bB] '               # bss symbols
readelf -S ./program                       # section headers
objdump -t ./program                        # full symbol table

# in embedded work, `size` is a build-gate metric: .text must fit
# in flash and .data + .bss must fit in RAM.

# placing objects in a specific section, for linker scripts
__attribute__((section(".fast_code"))) void isr(void) { }
__attribute__((section(".noinit")))    uint32_t boot_count;

Initialisation order

The order in which objects are initialised before main runs is only partly defined, and code that depends on the undefined part works until the link order changes.

/* Within one translation unit, static objects are initialised in
   declaration order — but in C they are all constant expressions,
   so there is no ordering hazard as there is in C++.

   What DOES have an ordering problem is constructor attributes: */

__attribute__((constructor))       void setup(void)   { }
__attribute__((constructor(101)))  void setup_early(void) { }
__attribute__((destructor))        void teardown(void) { }

/* Order ACROSS translation units is unspecified (priority values
   help, but only within one link unit). Do not build dependencies
   between constructors in different files.

   The robust pattern is explicit initialisation from main(), or
   lazy initialisation guarded by a flag:                        */

static bool ready;
static void ensure_init(void)
{
        if (!ready) { do_init(); ready = true; }
}
/* ...and note that this is NOT thread safe. For that you need
   call_once (C11) or pthread_once.                             */

#include <threads.h>
static once_flag once = ONCE_FLAG_INIT;
call_once(&once, do_init);
