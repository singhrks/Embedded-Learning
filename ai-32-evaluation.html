Evaluating LLM systems

Every other kind of software has a test suite. An LLM system has outputs that are neither right nor wrong, that change when nothing changed, and that no assertion can check. Building something you can actually measure is the least glamorous and most decisive work in the whole field.

Why the usual approach does not transfer

Coming from software where a test asserts equality, the instinct is to write assertions. It is worth understanding precisely why that fails before reaching for the alternatives.

   FOUR PROPERTIES THAT BREAK ORDINARY TESTING:

   1. MANY OUTPUTS ARE CORRECT.
        "Paris" / "It's Paris." / "The capital is Paris."
        assertEqual has nothing useful to say.

   2. THE SAME INPUT GIVES DIFFERENT OUTPUTS.
        Sampling is stochastic. Even at temperature 0,
        GPU batching and floating-point non-determinism
        mean bit-identical results are not guaranteed.

   3. QUALITY IS A GRADIENT, NOT A BOOLEAN.
        An answer can be correct and unhelpful, helpful and
        subtly wrong, or right for the wrong reason.

   4. THE SYSTEM CHANGES UNDER YOU.
        A provider updates a model and your behaviour moves
        without a line of your code changing. This alone is
        reason enough to have a suite you can re-run.

   ---------------------------------------------------------

   WHICH IS WHY THE ONLY QUESTION THAT MATTERS IS:

     "Is this version better than the last one?"

   NOT "is it good?" - unanswerable in the abstract.
   RELATIVE comparison on a FIXED set is answerable, and it
   is enough to make decisions with.

Four levels, cheapest first

These are not competing approaches; they are layers, and a serious system uses all four. The discipline is to push as much as possible down to the cheap deterministic levels, because those are the ones you can run on every commit.

LevelChecksCostRun it
1. AssertionsValid JSON, required fields, length bounds, no forbidden strings, citations resolveFree, deterministicEvery call, in production
2. Reference-basedExact match, contains, numeric tolerance — where a correct answer genuinely existsCheapEvery commit
3. Model-as-judgeGraded quality against a rubric, or A/B preference between two versionsAn API call per itemBefore each release
4. Human reviewEverything that actually matters and resists the aboveExpensive and slowWeekly sample, and to calibrate level 3

Level 1 is consistently undervalued. A surprising fraction of real failures are structural rather than semantic — malformed JSON, a missing field, a citation pointing at a document that was not retrieved, an answer ten times longer than the interface can display. Those are catchable with ordinary code, with no model in the loop, and they should be caught there.

The evaluation set is the asset

Almost everyone starts by looking for a benchmark. The thing that actually moves a system forward is a small, ugly, domain-specific set built from your own failures.

   HOW TO BUILD ONE THAT IS WORTH HAVING:

   START AT 20 CASES. Twenty is enough to detect a large
   regression and small enough that you will actually create
   it this afternoon. Perfect is the enemy here.

   GROW IT FROM REAL FAILURES. Every bug report becomes a
   case. This is the single most valuable habit in the
   chapter: your eval set becomes a precise record of every
   way your system has ever been wrong.

   COVER THE CATEGORIES DELIBERATELY:
     · typical cases              (the happy path)
     · EDGE cases                 (empty, enormous, unicode,
                                   ambiguous, contradictory)
     · cases that SHOULD BE REFUSED or answered "I don't
       know" - the most neglected category, and the one
       that catches overconfident systems
     · adversarial inputs         (chapter 32)

   SPLIT IT. Keep a HOLDOUT you do not look at while
   iterating. Tuning against your whole eval set is
   overfitting (chapter 12) performed by hand, and it
   produces a number that improves while the system does
   not.

   ---------------------------------------------------------

   AND ON PUBLIC BENCHMARKS: useful for comparing base
   models, nearly useless for telling you whether YOUR
   system works. They are also contaminated - benchmark
   items appear in training corpora, so a high score may
   measure memorisation rather than capability. Treat a
   leaderboard as a hint about which model to try first,
   never as evidence about your application.

Using a model as a judge, without fooling yourself

Having a model grade outputs is the only way to scale subjective quality assessment, and it comes with well-documented biases. It works if you treat the judge as an instrument that must itself be calibrated.

# A JUDGE PROMPT THAT WORKS

Score the ANSWER against the RUBRIC. Reply as JSON:
  {"reasoning": "...", "score": 1-5}

RUBRIC
  5  correct, complete, every claim supported by the sources
  4  correct, minor omission
  3  partially correct, or an unsupported claim
  2  mostly wrong
  1  wrong, or fabricated a source

QUESTION: {question}
SOURCES:  {sources}
ANSWER:   {answer}

# FOUR THINGS THAT MAKE IT USABLE:
#
#  · A CONCRETE RUBRIC. "Rate helpfulness 1-10" produces
#    noise; named, distinguishable levels produce signal.
#  · REASONING BEFORE THE SCORE. Same argument as chapter
#    29 - the score token needs the reasoning tokens to
#    have been computed first.
#  · A SMALL SCALE. Five levels are distinguishable; ten
#    are not, and the extra resolution is invented.
#  · PAIRWISE WHERE POSSIBLE. "Which of A and B is better"
#    is a much easier judgement than an absolute score, and
#    it is the question you usually want answered anyway.
The judge's biases are measurable, so measure them

Model judges reliably prefer longer answers, prefer the first option presented in a pairwise comparison, and rate text generated by a similar model more highly. The first two have direct mitigations: control for length in the rubric, and run every pairwise comparison in both orders — if A wins as first and also wins as second, that is a result; if it wins whichever position it occupies, you have measured position bias, not quality. The calibration step that makes the whole approach defensible is to grade fifty items yourself and compare with the judge. If it agrees with you most of the time you have a useful instrument. If it does not, you have an expensive random number generator, and every decision you made from its scores was noise.

Measuring the thing that is actually running

An offline suite tells you whether a change is an improvement. It cannot tell you what real users are doing, and the gap between those two is where most unpleasant surprises live.

   LOG ENOUGH TO RECONSTRUCT ANY SINGLE RESPONSE:

     the prompt template VERSION
     the model name AND version
     the sampling parameters
     the retrieved chunk ids            (ch. 29)
     the tool calls and their results   (ch. 30)
     latency and token counts
     the output

   IF YOU CANNOT REPLAY A BAD RESPONSE, you cannot debug it,
   and "it did something odd yesterday" is unactionable.

   ---------------------------------------------------------

   TRACK, CONTINUOUSLY:

     · ASSERTION FAILURE RATE     level 1, free, and the
                                  fastest alarm you have
     · REFUSAL RATE               a spike means retrieval
                                  broke; a collapse means
                                  the model stopped
                                  declining when it should
     · p50 AND p95 LATENCY        the tail is what users
                                  actually experience
     · COST PER REQUEST           the metric that ends
                                  projects
     · EXPLICIT USER FEEDBACK     sparse, biased toward
                                  complaints, and still the
                                  most honest signal here

   ---------------------------------------------------------

   AND THE HABIT WORTH MORE THAN ANY DASHBOARD:

     READ FIFTY REAL OUTPUTS, END TO END, EVERY WEEK.

   Aggregate metrics tell you that something changed. Reading
   the actual outputs tells you WHAT, and it reliably
   surfaces failure categories you would never have thought
   to write a metric for. Nobody wants to do this. It is the
   highest-value hour in the week.

How it shows up

SymptomCause
