Where Linux sits: exception levels and the two worlds

Every chapter of this track has quietly assumed one thing: that the kernel is the most privileged software on the machine. On ARM it is not. Linux runs at EL1 with at least one level above it and an entire parallel world beside it that it cannot see. Where chapter 03 mapped everything inside Linux, this chapter places that entire stack inside the ARM architecture around it, and says what that means concretely for a driver: which memory is invisible to you, which registers read back as zero, and why turning a CPU off is a function call into firmware.

The complete picture

Two independent axes, not one ladder

The mistake almost everyone makes first is reading this as a single ranking with EL3-secure at the top and EL0-non-secure at the bottom. It is two orthogonal things. Exception level is privilege: EL2 can trap what EL1 does, EL3 can trap what EL2 does. Security state is a separate bit entirely: it decides which copy of the world you are in — separate memory, separate peripherals, separate translation tables, in many cases separate banked system registers. Secure EL1 is not "more privileged than" non-secure EL1; it is the same privilege level in a different world that the non-secure side cannot address at all.

Where Linux actually runs

Given the diagram above, the natural question is which box Linux actually occupies — and the answer is not fixed. It depends on a decision the bootloader made before the kernel started, and the kernel tells you which case you got.

   THE HONEST ANSWER IS "IT DEPENDS", and the kernel tells
   you which case you are in at boot (chapter 04):

   ENTERED AT EL1
        The bootloader dropped to EL1 before jumping to the
        kernel. Everything in this track works. KVM does not,
        and cannot be enabled later - EL2 was left behind
        permanently.

   ENTERED AT EL2, WITHOUT VHE (older hardware)
        The kernel installs a small stub at EL2 and runs
        ITSELF at EL1. KVM works by bouncing through that
        stub on every world switch.

   ENTERED AT EL2, WITH VHE  (FEAT_VHE, ARMv8.1+, the normal
   case on anything modern)
        THE HOST KERNEL RUNS AT EL2 PERMANENTLY. The
        Virtualization Host Extensions make EL2's registers
        behave like EL1's, so the same kernel binary runs
        unmodified one level higher, and a guest's kernel
        gets the real EL1 underneath it.

        dmesg | grep "CPU(s) started at"
        CPU: All CPU(s) started at EL2

   WHAT DOES NOT CHANGE IN ANY OF THESE CASES: your driver.
   Driver code never names an exception level, never reads
   CurrentEL, and behaves identically whether the kernel
   around it is at EL1 or EL2 - which is exactly the point of
   the abstraction. The EL matters for what the KERNEL can
   do, not for what a DRIVER must write.

What a driver can and cannot reach

This is where the architecture stops being trivia and starts determining whether your code works. Crossing the boundary: what an SMC actually does

The dashed line in the diagram is not something software can simply step across. There is exactly one instruction that crosses it, and everything a driver ever asks of firmware or the secure world travels this way.

   A DRIVER CANNOT CALL THE SECURE WORLD. It can only ask
   EL3 to do it, using the one instruction that exists for
   this: SMC (Secure Monitor Call). Everything that crosses
   the dashed line in the diagram goes this way.

   Linux driver at NS-EL1
        |
        |  arm_smccc_smc(function_id, a1..a6, &res)
        |  which compiles to the SMC instruction
        v
   ================ SMC TRAPS TO EL3 ================
        |
   SECURE MONITOR (TF-A) at EL3
        · saves the non-secure CPU state
        · looks at the function ID to decide what this is
        · FLIPS THE NS BIT
        · restores the secure world's state
        |
        +---- if it is a PSCI call (CPU_ON, CPU_SUSPEND,
        |     SYSTEM_RESET) EL3 HANDLES IT ITSELF and returns
        |     directly - no secure OS involved at all
        |
        +---- if it is a TEE call, EL3 enters...
              |
              v
        OP-TEE OS at S-EL1  ->  Trusted Application at S-EL0
              |  does the work with secure keys and secure
              |  memory that NS-EL1 cannot address
              v
        returns through EL3, which flips the NS bit back,
        restores non-secure state, and returns to the
        instruction after your SMC.

   THE COST: this is a full context switch through the most
   privileged level on the chip, twice. It is measured in
   microseconds, not nanoseconds - which is why a driver
   batches TEE requests and never puts an SMC in a hot path
   or, worse, inside a spinlock.
/* Two ways a driver reaches across, in practice. */

/* 1. PSCI - and you almost never write this yourself. The
      cpuidle and CPU-hotplug cores issue it for you; the
      device tree simply declares that PSCI is present:      */

        psci {
                compatible = "arm,psci-1.0";
                method     = "smc";
        };

/* 2. The TEE subsystem - the supported path to OP-TEE
      (tee track chapter 10). A kernel driver that needs a
      key unwrapped or data signed opens a TEE context rather
      than issuing raw SMCs:                                 */

        #include <linux/tee_drv.h>

        ctx = tee_client_open_context(NULL, match_optee,
                                      NULL, NULL);
        tee_client_open_session(ctx, &arg, param);
        tee_client_invoke_func(ctx, &inv_arg, param);

/* RAW SMCs FROM A DRIVER ARE A RED FLAG. arm_smccc_smc()
   exists, and a handful of SoC drivers legitimately use it
   for vendor-specific firmware interfaces - but if there is
   a subsystem for what you want (PSCI, SCMI, TEE), using it
   instead is what makes your driver work on the next SoC as
   well as this one.                                         */

How all of this got started

All those levels had to be set up by something. The boot sequence is a walk down the exception levels, and it explains why the secure world is already protected by the time Linux runs.

   THE BOOT SEQUENCE IS ALSO A WALK DOWN THE EXCEPTION
   LEVELS - each stage runs at the highest privilege it will
   ever have, sets up the level below, and drops into it.
   Privilege is given away, never taken back.

     BL1   EL3   boot ROM, mask-programmed, immutable
      |          the root of trust (sec ch. 14)
      v
     BL2   EL3   loads and VERIFIES every image below
      |
      +--> BL31  EL3   TF-A's RUNTIME monitor. STAYS RESIDENT
      |                FOREVER - this is what answers every
      |                SMC for the rest of the boot
      |
      +--> BL32  S-EL1 OP-TEE. Initialises the secure world,
      |                then returns to BL31
      |
      +--> BL33  EL2   U-Boot / UEFI - the NON-SECURE
                       bootloader, the first code that runs
                       with the NS bit set
                        |
                        v
                 LINUX  at EL2 (or EL1) - chapter 04 picks up
                        exactly here, at head.S

   NOTE WHAT THIS ORDERING GUARANTEES: by the time Linux runs,
   the secure world is ALREADY initialised and the memory it
   owns is ALREADY fenced off by the TZASC. The kernel is not
   trusted to stay out of secure memory - it is made unable to
   reach it, before it ever executes an instruction.

Seeing it on a running system

None of this is theoretical — a running system will tell you which exception level it started at, whether firmware services are present, and whether a secure world exists at all.

# Which EL did the kernel get?
$ dmesg | grep "CPU(s) started at"
CPU: All CPU(s) started at EL2

# Is PSCI present, and which conduit does it use?
$ dmesg | grep -i psci
psci: probing for conduit method from DT.
psci: PSCIv1.1 detected in firmware.
psci: Using standard PSCI v0.2 function IDs
psci: SMC Conduit: yes

# Is there a secure world with a TEE at all?
$ ls /dev/tee*
/dev/tee0  /dev/teepriv0
$ dmesg | grep -i optee
optee: probing for conduit method.
optee: revision 4.1 (a1b2c3d4)
optee: initialized driver

# Is KVM usable - i.e. did we really keep EL2?
$ dmesg | grep -i kvm
kvm [1]: IPA Size Limit: 40 bits
kvm [1]: VHE mode initialized successfully

# What the non-secure world can see of physical memory.
# Secure carve-outs are simply ABSENT from this list - not
# listed as "reserved", but genuinely not there:
$ cat /proc/iomem | head
$ dmesg | grep -i "reserved memory"
ARMv9 adds a third world, on the same principle

The Confidential Compute Architecture introduces a Realm world alongside Secure and Non-secure, managed by a Realm Management Monitor, so that a guest's memory can be hidden from the hypervisor as well — closing the gap where a cloud tenant must currently trust the host. It changes the diagram above by adding a column, not by changing the idea: still orthogonal axes, still EL3 as the only level that arbitrates between worlds. Nothing in this track's driver code is affected today, but the shape is worth recognising when it appears in an SoC datasheet.

How it shows up
