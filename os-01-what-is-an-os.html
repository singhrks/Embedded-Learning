What an operating system is

An OS has exactly two jobs, and every feature it has is an instance of one of them. Getting this framing right makes the rest of the track — scheduling, memory, files, drivers — read as variations on a theme rather than a pile of unrelated machinery.

The two jobs

1. Abstraction

Turn awkward, varied hardware into a uniform interface. A program calls read() and does not care whether the bytes come from an NVMe SSD, a network socket, a USB stick or a pipe. Without this, every application would need a driver for every device.

2. Arbitration

Share finite resources among competing users, safely and fairly. CPU time, memory, devices, files — all must be divided so that one program cannot starve, corrupt or spy on another.

Every OS subsystem is one of those two, applied to one resource:

  resource          abstraction              arbitration
  ─────────────────────────────────────────────────────────────
  CPU               process / thread         scheduler
  memory            virtual address space    allocator + MMU
  storage           file, directory          permissions, quotas
  network           socket                   ports, firewall, qdisc
  devices           /dev node, handle        drivers, permissions
  time              timers, clocks           timer wheel

If you can place a feature in that table, you understand what it
is for. If you cannot, it is probably policy, not mechanism.

Mechanism versus policy

A design principle that runs through every good OS, and the reason Linux and Windows differ so much in places while doing identical things underneath.

Separating them is why Linux can ship several schedulers and several I/O elevators over the same core machinery, and why you can change one with a sysctl rather than a rebuild.

The privilege boundary

Arbitration requires enforcement, and enforcement requires that applications cannot bypass the OS. That needs hardware support — the exception levels of CA chapter 16 and ARM chapter 26.

   ┌──────────────────────────────────────────┐
   │  USER MODE      (ARM EL0, x86 ring 3)    │
   │  applications, libraries                 │
   │  · own virtual memory only               │
   │  · no privileged instructions            │
   │  · no direct device access               │
   │  · cannot disable interrupts             │
   └────────────────┬─────────────────────────┘
                    │  system call — the ONLY way up,
                    │  and the kernel chooses the entry point
   ┌────────────────▼─────────────────────────┐
   │  KERNEL MODE    (ARM EL1, x86 ring 0)    │
   │  scheduler, memory manager, drivers      │
   │  · all memory, all instructions          │
   │  · owns the page tables                  │
   └──────────────────────────────────────────┘

Three things make this enforceable, and all three are hardware:
  1. a mode bit the CPU tracks and user code cannot set
  2. an MMU that marks kernel pages inaccessible from user mode
  3. a fixed entry vector, so entering the kernel always lands on
     code the kernel chose (not an address the caller picked)
Why "the OS protects you" is imprecise

The OS configures protection; the hardware enforces it. A kernel bug can disable it, and a system without an MMU (a Cortex-M) has no enforcement at all — which is why a wild pointer on a microcontroller can silently corrupt anything, and why RTOS "protection" is advisory unless an MPU is configured.

Real-time does not mean fast

It means predictable. An RTOS that guarantees a 50 µs worst-case interrupt latency is "real-time"; Linux with a 5 µs average and an occasional 5 ms outlier is not. For a general-purpose OS the metric is throughput and the average case; for an RTOS it is the worst case, and average performance is almost irrelevant. Design decisions follow directly: no demand paging, no unbounded allocators, priority inheritance on every lock, bounded interrupt disable times.

How the OS gets control

An operating system does not start itself. Several programs run before it, each handing control to the next, and knowing that chain matters because a machine that fails to boot stopped at a specific link in it.

   power on
      │
   firmware / boot ROM        immutable, verifies the next stage
      │
   bootloader                 U-Boot, GRUB, UEFI
      │  loads the kernel image and a hardware description
      │  (device tree or ACPI tables)
      ▼
   kernel entry               still running on firmware's assumptions
      │  set up its own page tables, turn on the MMU,
      │  discover CPUs and memory, initialise subsystems
      ▼
   first user process         init / systemd / launchd
      │  everything after this point is scheduled normally
      ▼
   the system is "up"

Detail in os-18. The important structural point: the kernel is not
"always running". It is a library of handlers that runs when a
system call, an interrupt or a fault transfers control to it — and
otherwise the CPU is executing user code, or idle.

The kernel is event-driven

Once running, the kernel is not a program that executes continuously. It is code that runs only when something calls it or interrupts the processor — which is a genuinely different model from the one most people carry.

Three, and only three, ways the kernel gains control:

  1. SYSTEM CALL       user code deliberately asks           (ch. 03)
                       synchronous, on the caller's behalf

  2. INTERRUPT         a device signals asynchronously       (ch. 17)
                       unrelated to what was running

  3. EXCEPTION/FAULT   the current instruction failed        (CA ch. 16)
                       page fault, illegal instruction, alignment

  Everything the kernel does is triggered by one of these. There is
  no "kernel main loop" — except the idle task, whose entire job is
  to execute a low-power wait instruction until an interrupt arrives.

  This is why kernel code is written as short, non-blocking handlers,
  and why "what context am I in?" is the first question you ask about
  any kernel function (chapters 09 and 16).

What the abstraction costs

CostMagnitudeWhen it matters
System call~50–500 nsHigh-frequency I/O — hence io_uring, batching, vDSO
Context switch~1–5 µs, plus cache and TLB refillMany threads, or fine-grained switching
Page fault (minor)~1–5 µsFirst touch of each page
Page fault (major)MillisecondsAny real-time deadline
Scheduling jitterMicroseconds to millisecondsControl loops, audio, motion
Memory overheadKernel, page tables, per-task structuresSmall embedded systems

These costs explain the escape hatches that exist in every OS: mmap instead of read, io_uring instead of syscall-per-operation, huge pages, mlockall(), CPU isolation, kernel bypass (DPDK, SPDK), and ultimately choosing an RTOS or bare metal when the OS's guarantees are worth less than its overhead.
