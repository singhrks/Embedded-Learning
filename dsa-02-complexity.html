Complexity analysis and reading the constraints

Big-O is not academic decoration — the constraint line in the problem statement tells you which algorithm is expected, before you have had a single idea. Learn to read it and half the search is already done.

What the notation means

Big-O is simpler than its reputation, and the part that matters in an interview is knowing exactly what it throws away — because that is what you will be asked to defend.

   BIG-O IS AN UPPER BOUND ON GROWTH, ignoring constants
   and lower-order terms.

     3n^2 + 100n + 5000   ->   O(n^2)

   WHY THROW AWAY THE CONSTANTS: because for large n the
   fastest-growing term dominates everything else, and the
   constants depend on hardware you cannot predict.

     n = 1,000,000:
       3n^2   = 3,000,000,000,000
       100n   =       100,000,000    (0.003% of the total)
       5000   =             5,000    (negligible)

   THE THREE NOTATIONS, since interviewers occasionally ask:
     O(f)      grows NO FASTER than f   (upper bound)
     Omega(f)  grows NO SLOWER than f   (lower bound)
     Theta(f)  both — the tight bound

   In practice everyone says "O" and means Theta. Saying
   "O(n^2)" for something that is actually O(n) is
   technically true and will still be marked wrong.

   THE GROWTH LADDER, memorise the order:

     O(1)         constant      hash lookup, array index
     O(log n)     logarithmic   binary search, balanced tree
     O(n)         linear        one pass
     O(n log n)   linearithmic  good sorting, divide+conquer
     O(n^2)       quadratic     nested loops, all pairs
     O(n^3)       cubic         all triples, Floyd-Warshall
     O(2^n)       exponential   all subsets
     O(n!)        factorial     all permutations

   WHAT THOSE ACTUALLY COST at n = 1,000,000:

     O(1)          1 step
     O(log n)      20 steps
     O(n)          1,000,000
     O(n log n)    20,000,000
     O(n^2)        1,000,000,000,000       ~ hours
     O(2^n)        more steps than atoms in the observable
                   universe

   AND AT n = 20:  2^20 = 1,048,576 — perfectly fine.
   EXPONENTIAL IS NOT AUTOMATICALLY DISQUALIFYING. It
   depends entirely on n, which is why the constraints
   matter so much.

Reading the constraints backwards

This is the highest-value table in the whole track. The input limits are not decoration; they are the problem setter telling you which complexity is expected, and reading them first saves you from designing the wrong solution.

   THIS IS THE SINGLE MOST USEFUL TABLE IN INTERVIEW PREP.

   A judge runs roughly 10^8 simple operations per second.
   So from the largest n, you can read off the intended
   complexity:

     n up to          intended complexity     what that means
     ---------------------------------------------------------
     10^18            O(log n) or O(1)        maths, bit tricks
     10^8             O(n)                    one pass only
     10^6 - 10^7      O(n) or O(n log n)      sort is fine
     10^5             O(n log n)              sort, heap, BS
     10^4             O(n^2) is borderline    nested loop ok
     500 - 1000       O(n^2) or O(n^2 log n)  DP on pairs
     100 - 200        O(n^3)                  interval DP
     40 - 50          O(2^(n/2))              meet in middle
     20 - 25          O(2^n)                  subset DP,
                                              bitmask
     10 - 12          O(n!)                   permutations

   HOW TO USE IT, in the interview:

     "n is up to 10^5, so I need about O(n log n). That
      rules out checking every pair. Sorting is affordable,
      and so is a heap or a binary search. Let me look for
      one of those."

   YOU HAVE JUST NARROWED THE ENTIRE SEARCH SPACE OF
   ALGORITHMS, out loud, before having an idea. That is
   worth saying even if you then need a minute of silence.

   THE REVERSE READING IS EQUALLY USEFUL:
     · "n <= 20" almost always means BITMASK or
       BACKTRACKING (chapters 18, 36)
     · "n <= 100 and it asks for a minimum cost" -> DP
     · "answer is monotonic and the range is huge" ->
       BINARY SEARCH ON THE ANSWER (chapter 10)
     · "array values up to 10^9 but n only 10^5" -> the
       VALUES need hashing or coordinate compression, not
       an array indexed by value

Counting correctly

Almost all complexity mistakes come from combining loops wrongly rather than from misunderstanding the notation. Three rules cover every case you will meet.

/* --- SEQUENTIAL: ADD, then keep the largest --- */
    for (i = 0; i < n; i++) {}     // O(n)
    for (j = 0; j < n; j++) {}     // O(n)
    -> O(n) + O(n) = O(2n) = O(n)

/* --- NESTED: MULTIPLY --- */
    for (i = 0; i < n; i++)
        for (j = 0; j < m; j++) {}
    -> O(n*m)        NOT O(n^2) unless n == m. Say "n times
                     m" — interviewers notice.

/* --- THE TRIANGLE, which people get wrong --- */
    for (i = 0; i < n; i++)
        for (j = i; j < n; j++) {}
    -> n + (n-1) + ... + 1 = n(n+1)/2 = O(n^2)
    Half the work of the full square, but the SAME class.

/* --- HALVING IS LOGARITHMIC --- */
    while (n > 1) n = n / 2;       // O(log n)
    Each step throws away half the remaining input. The
    number of halvings of n before reaching 1 is log2(n).

/* --- THE ONE THAT LOOKS QUADRATIC AND IS NOT --- */
    let j = 0;
    for (let i = 0; i < n; i++) {
        while (j < n && cond(i, j)) j++;   // j NEVER RESETS
    }
    -> O(n), not O(n^2).

    THE ARGUMENT: `j` only ever increases and is bounded by
    n, so the inner loop body executes at most n times IN
    TOTAL across all iterations of the outer loop. This is
    AMORTISED ANALYSIS, and it is exactly why the sliding
    window (chapter 05) is linear. Be ready to say this out
    loud — it is a common follow-up question.

/* --- RECURSION: draw the tree --- */
    T(n) = 2*T(n/2) + O(n)      -> O(n log n)   merge sort
      log n levels, O(n) work per level

    T(n) = T(n/2) + O(1)        -> O(log n)     binary search
      one branch survives per level

    T(n) = 2*T(n-1) + O(1)      -> O(2^n)       subsets
      the tree DOUBLES each level

    T(n) = T(n-1) + O(n)        -> O(n^2)       naive quicksort
                                                worst case

/* --- SPACE COMPLEXITY: COUNT THE STACK --- */
    Recursion depth counts as space. A recursive DFS on a
    skewed tree of n nodes is O(n) SPACE even though it
    allocates nothing — which is precisely why "can you do
    it iteratively?" is asked (chapter 27).

    AND: the output does not usually count. If a problem
    asks for all n! permutations, you are not penalised for
    the O(n!) output. Say "O(n) auxiliary space, excluding
    the output" to show you know the distinction.        */
The complexity of the operations you use 
ARRAY        index O(1) · push/pop end O(1) amortised
             insert/delete middle O(n) · search O(n)
SORTED ARRAY binary search O(log n)
HASH MAP     insert/lookup/delete O(1) average, O(n)
             worst case (collisions)
BALANCED BST insert/lookup/delete O(log n), and it keeps
             the keys ORDERED — the reason to prefer it
             over a hash map
HEAP         push/pop O(log n) · peek O(1) · build O(n)
STACK/QUEUE  push/pop O(1)
LINKED LIST  insert/delete at a known node O(1)
             search O(n) · NO random access
TRIE         insert/search O(L), L = key length
UNION-FIND   near O(1) amortised with both optimisations
STRING       concatenation in a loop is O(n²) in most
             languages — build an array and join once

Knowing that Array.shift(), list.pop(0) and vector.erase(begin()) are all O(n) is the difference between an O(n) solution and an accidental O(n²) one. This is a genuinely common silent failure.

Amortised, average and worst case

Three different things get called "the complexity", and confusing them is how a correct answer gets marked down. Knowing which one you are quoting — and saying so — is the whole skill here.

/* --- WORST CASE is what you quote unless asked otherwise.
       It is the guarantee.

/* --- AVERAGE CASE assumes a distribution of inputs.
       Hash maps are O(1) average, O(n) worst (everything
       collides). Quicksort is O(n log n) average, O(n^2)
       worst (already-sorted input with a bad pivot).

/* --- AMORTISED is the average over a SEQUENCE of
       operations, and it is a WORST-CASE guarantee for the
       sequence — a much stronger statement than "average".

    THE CLASSIC: a dynamic array that doubles when full.
      Most pushes are O(1).
      A push that triggers a resize copies everything: O(n).
      But doubling means resizes happen at sizes
      1, 2, 4, 8, … n, and the total copying is
        1 + 2 + 4 + … + n < 2n
      so n pushes cost O(n) TOTAL, i.e. O(1) AMORTISED PER
      PUSH.

    THE KEY INSIGHT: doubling (not adding a constant) is
    what makes it amortised O(1). Growing by a fixed 10
    elements gives O(n) amortised per push and an O(n^2)
    total — a real performance bug people ship.

/* --- WHERE AMORTISED SHOWS UP IN INTERVIEWS ---
     · dynamic array / vector push
     · the sliding window's inner pointer (chapter 05)
     · the monotonic stack: each element is pushed once and
       popped at most once, so the whole scan is O(n) even
       though a single step can pop many items (chapter 23)
     · union-find with path compression (chapter 33)

   IN EACH CASE THE ARGUMENT IS THE SAME: bound the TOTAL
   work across the whole run, not the work of one step.
   "Each element is pushed once and popped at most once,
   so the total is O(n)" is a sentence worth memorising.  */

Practice: predict the complexity

These are not algorithm problems — each asks you to return the complexity of a snippet as a string. Getting them right quickly is a real interview skill.

Check yourself

  • Recite the growth ladder from O(1) to O(n!).
  • Give the intended complexity for n = 105, 103, and 20.
  • Explain why the triangle loop is O(n²) despite doing half the work.
  • Give the amortised argument for why a non-resetting inner pointer is O(n).
  • Explain why array doubling gives O(1) amortised push and fixed growth does not.
  • State the recurrence for merge sort and binary search, and solve each.
  • Say why recursion has a space cost even with no allocation.
  • Name three operations that look O(1) but are O(n).
