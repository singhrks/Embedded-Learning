Queues: BFS, deques and the monotonic deque

First in, first out — the structure behind every shortest-path-in-an-unweighted-graph problem. Add the ability to push and pop at both ends and you get the sliding-window maximum in linear time.

The pattern

A queue and a deque differ by one capability, and that capability is what makes the sliding-window maximum linear. Both come with a performance trap in JavaScript worth knowing before you benchmark anything.

   QUEUE — enqueue at the back, dequeue from the front.
   Its defining property: elements come out in the order
   they went in, so BFS explores strictly by DISTANCE.

     THE JAVASCRIPT TRAP: Array.shift() is O(n) because it
     reindexes the whole array. A "linear" BFS built on
     shift() is really O(n^2).

     THE FIX — a head index, never shrinking the array:
       const q = [start];
       let head = 0;
       while (head < q.length) {
           const node = q[head++];
           ...
           q.push(neighbour);
       }
     Memory is not reclaimed until the loop ends, which is
     fine for interview-sized inputs and is what a real
     implementation would do with a ring buffer.

   ---------------------------------------------------------
   DEQUE — push/pop at BOTH ends, all O(1).

     pushFront  popFront
     pushBack   popBack

     C++    std::deque
     Java   ArrayDeque
     Python collections.deque
     JS     an array, using push/pop/shift/unshift —
            with the same O(n) caveat at the front

   ---------------------------------------------------------
   THE MONOTONIC DEQUE — the pattern worth learning here.

   PROBLEM: the maximum of every window of size k.
   Recomputing the max per window is O(n·k). A heap gives
   O(n log k). A deque gives O(n).

   THE IDEA: keep indices in the deque so their VALUES are
   DECREASING. Then the front is always the window maximum.

     for i in 0..n-1:
        1. DROP FROM THE FRONT anything that has slid out of
           the window:      while (dq[0] <= i - k) popFront
        2. DROP FROM THE BACK anything smaller than a[i] —
           it can never be the maximum again, because a[i]
           is both LARGER and LATER:
                            while (a[dq.back] <= a[i]) popBack
        3. pushBack(i)
        4. once i >= k-1, a[dq[0]] is the window maximum

     [1, 3, -1, -3, 5, 3, 6, 7]   k = 3
      i=0  dq=[0]                 (1)
      i=1  3>1 pop 0, dq=[1]      (3)
      i=2  -1<3 push, dq=[1,2]    (3,-1)     window max 3
      i=3  -3<-1 push, dq=[1,2,3]            window max 3
      i=4  5 pops 3,2,1, dq=[4]              window max 5
      ...                          -> [3,3,5,5,6,7]

   WHY IT IS O(n): every index is pushed once and popped at
   most once. The same amortised argument as the monotonic
   stack (chapter 23).

   THE KEY INSIGHT, worth saying aloud: an element that is
   smaller than a later element is USELESS FOREVER — the
   later one outlives it in every future window and is
   bigger. So it can be discarded immediately.

When to reach for it

Shortest path, unweighted

BFS. The first time you reach a node is via a shortest path.

Level-by-level processing

Tree levels, rotting oranges, multi-source spread.

Sliding window max/min

Monotonic deque, O(n).

"Most recent k" / round robin

Plain queue or ring buffer.

Palindrome check on a stream

Deque, comparing both ends.

0-1 BFS

Deque: push weight-0 edges to the front, weight-1 to the back.

Problems

How it shows up

SymptomCause
BFS is unexpectedly slowshift() is O(n) — use a head index
Window maximum is staleExpired indices not dropped from the front
Deque grows without boundSmaller elements not popped from the back
Off by one on the first windowRecord only once i >= k − 1
Deque holds values, cannot expire themStore indices so you can test the window bound
Duplicates dropped incorrectly<= vs < when popping the back — either works for max, but be consistent
BFS revisits nodes foreverMark visited when enqueueing, not when dequeuing
