Scenario: an automotive ECU on CAN

A design round that is really about constraints: an electrically hostile environment, hard deadlines, a safety argument, and a twenty-year vehicle life. Work it yourself first.

The prompt

"Design the electronic control unit for an electric power steering assist system. It reads a torque sensor and a position sensor, drives an assist motor, and communicates on the vehicle's CAN bus. Walk me through it."

1 · Clarify

THE QUESTIONS, and the ones specific to this domain:

2 · Partition — the heart of this answer

   FIRST: WHAT IS NOT SOFTWARE.

     over-current on the motor phases -> comparator into
       the timer's BREAK input. Microseconds. A software
       path cannot respond in time and must not be trusted
       to.
     bridge dead-time -> generated by timer hardware, not
       by a software delay that could be preempted.
     a relay or MOSFET in series with the motor supply,
       de-energised by default, held on only by an active
       signal - so any failure that stops that signal
       removes assist.

   SECOND: THE PROCESSOR PARTITION.

   +--------------------------+   +---------------------+
   |  MAIN MCU                |   |  SAFETY MONITOR     |
   |  - current + assist loop |   |  - independent      |
   |  - motor commutation     |<->|    plausibility     |
   |  - CAN comms, UDS        |   |  - challenge/resp   |
   |  - diagnostics           |   |  - can disable the   |
   |                          |   |    motor supply     |
   +--------------------------+   +---------------------+
            |                              |
            +---- both must agree ---------+
                  to keep assist enabled

   WHY TWO: the monitor is small and simple, so proving it
   correct is tractable; it independently checks that the
   commanded torque is plausible given the sensor inputs;
   and it holds the enable line, so a hung or wrong main
   MCU loses assist rather than doing something dangerous.
   This also SHRINKS THE CERTIFICATION SCOPE dramatically -
   the high-integrity argument attaches to a small binary
   on a simple core rather than to the whole application.

   Some designs achieve the same with a lockstep dual-core
   part instead. Worth naming both and saying the choice
   depends on the integrity level and the supplier's
   toolchain.

   THIRD: SENSOR REDUNDANCY.
     The torque sensor is the input everything depends on,
     so it is dual-channel - ideally with DIVERSITY
     (different sensing principle or at minimum independent
     supplies and separate wiring), because two identical
     channels sharing a rail or a loom fail together
     (chapter 14).

3 · Real-time budget

  function            deadline  class  where
  ------------------- --------- ------ -------------------
  over-current trip      5 us   HARD   hardware comparator
  commutation           50 us   HARD   timer + ADC, ISR
  current loop           100us  HARD   high-priority task
  assist (torque) loop     1 ms HARD   task
  plausibility check       1 ms HARD   safety monitor
  CAN transmit            10 ms FIRM   task
  UDS diagnostics        100 ms SOFT   low-priority task
  fault logging            1 s  SOFT   idle

  UTILISATION on the main MCU:
    current loop   T=100us  C=25us  -> 0.250
    assist loop    T=1ms    C=120us -> 0.120
    CAN task       T=10ms   C=200us -> 0.020
    UDS            T=100ms  C=2ms   -> 0.020
    ADC ISR        P=100us  C=4us   -> 0.040
    CAN ISR        P=1ms    C=15us  -> 0.015
                                       -----
                                  U =  0.465

    Bound for 4 tasks = 0.757. Schedulable with margin,
    which matters because this design must tolerate
    worst-case paths and future features.

  THE CURRENT LOOP AT 10 kHz IS A QUARTER OF THE CPU. That
  is the number that decides the processor class, and it
  is worth stating: this is why a 180 MHz part with an FPU
  and a fast ADC, not a 48 MHz general-purpose MCU.

  JITTER MATTERS MORE THAN LATENCY here (chapter 10): the
  control maths assumes a fixed sample interval, so the
  ADC must be triggered by the TIMER, not by software, and
  the loop must run from that trigger rather than from a
  scheduler tick.

4 · The vehicle environment

   THE 12 V RAIL IS NOT 12 V.

     cranking      dips to 6 V or below, for tens of ms
     load dump     transients up to 80-100 V if the
                   alternator is disconnected under load
     reverse       a jump-start connected backwards
     cold start    -40 C, battery internal resistance high

   CONSEQUENCES: input protection (TVS, reverse-polarity
   protection), a regulator with a wide input range, and
   firmware that RIDES THROUGH a cranking dip rather than
   resetting - because losing steering assist while the
   engine cranks is not acceptable. That means enough bulk
   capacitance and a brown-out threshold chosen
   deliberately.

   CAN SPECIFICS (bus track, chapters 09-11):
     - the bus is shared with dozens of ECUs; our message
       IDs must be assigned by the vehicle integrator, and
       LOW ID = HIGH PRIORITY, so safety messages get low
       IDs and diagnostics get high ones
     - bit timing sample point at 75-87.5%, because the
       harness is long
     - error confinement means a faulty node removes
       itself; we must handle going bus-off and decide
       whether to auto-recover (and count it) or latch a
       fault
     - CAN has NO AUTHENTICATION - any node can send any
       ID. For safety-relevant messages, SecOC-style
       message authentication with a freshness counter, or
       accept that the bus is trusted and segment it

   EMC: this is one of the harshest environments there is.
   Slew rates conservative, every input validated, CRC on
   anything crossing a connector, and periodic refresh of
   external device configuration registers because ESD can
   silently corrupt them (chapter 16).

THE FAIL-SAFE RAMP IS WORTH CALLING OUT. Cutting assist
INSTANTLY changes steering effort abruptly, which is itself
a hazard at speed. So the fail-safe is a controlled ramp to
zero over a defined period where the fault allows it, and
an immediate cut only where continuing is more dangerous
than the transition. Knowing that "fail-safe" needs a
TRAJECTORY and not just a state is a strong signal.

Follow-up questions

Why a separate safety monitor rather than doing the checks in the main MCU?Senior

Independence, and certification scope. A check running on the same processor as the thing it is checking fails when that processor fails — a hang, a corrupted variable, a stack overflow or a bad firmware update takes the check with it. A separate monitor holding the motor enable line means a failure of the main MCU results in assist off, which is the safe state, without the main MCU's cooperation.

The second reason is practical: the verification burden scales with the size and complexity of what is in scope. A monitor that is a few thousand lines on a simple core can be argued to a high integrity level; the same argument for a full application with a CAN stack, diagnostics and a control algorithm is enormously more expensive. Partitioning to shrink the scope is one of the most valuable architectural moves available.

The alternative worth naming is a lockstep dual-core part, where the hardware compares two cores executing identically and flags divergence. That covers random hardware faults well but not systematic software faults — both cores run the same wrong code — so it complements rather than replaces plausibility checking.

Listening forCertification scope as a motivation, and knowing lockstep does not catch software faults.
What exactly is the fail-safe state here, and why is it not obvious?Senior

Assist off, with the motor de-energised so it neither drives nor significantly resists. The driver reverts to unassisted steering — heavier, but fully controllable. That has to be verified as acceptable: a vehicle whose unassisted steering effort is beyond a driver's capability has no safe fallback, which is a system-level design constraint on the mechanical side.

It is not obvious because two other plausible-sounding states are wrong. Holding the last commanded torque is dangerous — a stuck assist torque steers the vehicle. Free-wheeling with the motor shorted may add drag or cogging that makes manual steering worse.

And the transition matters as much as the state: removing assist instantly changes steering effort abruptly, which at speed is itself a hazard. So the fail-safe is a controlled ramp where the fault permits it, and an immediate cut only where continuing is more dangerous than the transition. Knowing that a fail-safe needs a trajectory rather than just a target is the part most candidates miss.

Listening forThe ramp, and checking that unassisted steering is actually viable.
Two torque sensor channels disagree. What do you do?Mid

With two channels you can detect disagreement but not resolve it — you do not know which is correct. So the response must be a defined fail-safe action rather than a guess: ramp assist down, disable, set a fault code and illuminate the warning. Choosing one channel by rule (the lower, the average) would mean acting on possibly false data in a safety-critical path.

If continued operation were required, that forces a third channel for two-out-of-three voting, or an independent model-based estimate to adjudicate — both of which cost money and would need justifying against the requirement.

The design questions underneath: what disagreement threshold counts as a fault, given both channels have tolerance, noise and temperature drift? For how long must they disagree before acting, so that a transient does not trip it? And are they genuinely independent — same part, same batch, same supply rail and same connector means a common cause defeats the redundancy entirely, which is why diversity matters more than duplication.

Listening for"Detect but not resolve", plus the threshold, persistence and independence questions.
How do you handle the 12 V rail during engine cranking?Mid

Ride through it rather than resetting, because losing steering assist during cranking is not acceptable behaviour. The rail can dip to 6 V or lower for tens of milliseconds, and at −40 °C the battery's internal resistance makes it worse.

The measures: a regulator specified for a wide input range including the cranking minimum; enough bulk capacitance to carry the load through the dip; and a brown-out threshold set deliberately — above the voltage where flash writes become unreliable, but below the cranking minimum so it does not trip.

Firmware behaviour: monitor the supply and degrade gracefully rather than being surprised — reduce assist current if the rail sags, since drawing peak motor current from a collapsing rail makes it worse; suspend any flash write in progress or defer it; and log the event so a pattern of marginal cranking is visible.

The related requirement is load dump at the other extreme — transients up to 80–100 V if the alternator is disconnected under load — which is a hardware protection problem (TVS and a regulator rated for it) but worth naming because it constrains part selection.

Listening forReducing load during a sag rather than only surviving it, and naming load dump as the opposite extreme.
What are the security implications of CAN here?Senior

CAN has no authentication whatsoever — any node can transmit any identifier, and receivers cannot tell whether a message is genuine. So a compromised or malicious node anywhere on the bus can impersonate any other, which for a safety-relevant actuator is a serious concern.

The defences, in layers. Segmentation: safety-critical buses are separate from infotainment and from the diagnostic port, with a gateway that filters — the well-known remote vehicle attacks pivoted from an infotainment system onto the control bus, and the gateway is what should have stopped it. Message authentication: AUTOSAR SecOC adds a truncated MAC and a freshness counter to critical messages, so a spoofed or replayed message is rejected. Plausibility: the ECU should not act on a single message that contradicts its own sensors, which is a defence against spoofing that costs nothing.

And the diagnostic path specifically: UDS includes a security-access mechanism, and it must be a real challenge-response with per-vehicle or per-tool keys rather than a fixed seed-key algorithm shared across a model line — because those get extracted and published.

Listening forSegmentation plus SecOC, and the diagnostic security-access weakness.
Can this ECU be updated in the field, and what constrains that?Senior

Yes, increasingly so, but with preconditions that the update process must enforce: the vehicle stationary and in an appropriate state, battery voltage sufficient to complete the operation, and — for a safety ECU — often a requirement that the function is unavailable during the update and the driver is informed.

Technically: A/B slots so an interrupted update cannot leave a non-functional steering ECU, signature verification anchored in a root of trust, and a self-confirmation step. The flash budget doubles, which needs to be in the part selection from the start.

The domain-specific constraints: the update is typically delivered over CAN via a gateway using UDS, which is slow, so a large image takes minutes and the preconditions must hold throughout. Multiple ECUs may need updating as a coordinated set with compatible versions, which is a vehicle-level orchestration problem — and our protocol needs a version field so a mismatch degrades rather than breaks.

And there is a regulatory and homologation dimension: changing the behaviour of a safety-critical system in the field may require re-approval, so what may be updated and how is not purely an engineering decision.

Listening forPreconditions, coordinated multi-ECU versioning, and the regulatory dimension.
The current loop is 25% of the CPU. Is that a problem?Mid

Not by itself — total utilisation is about 46% against a bound near 76%, so there is margin. But it is the single largest term and therefore the one to watch, and I would make three checks.

Is 25 µs the worst case or the typical? It must be measured with a cycle counter under the worst path — including any error handling, any branch that only runs occasionally, and with the caches and flash wait states in their worst state. If it is an average, the real number could be substantially higher.

Is the maths right for the part? A control loop doing floating-point on a part without an FPU is roughly 40× slower; on a part with one it is a cycle. If the 25 µs assumes hardware float, the part selection is locked in by that.

Can it move to hardware? Triggering the ADC from the timer, using DMA to place results, and letting the PWM comparators generate the outputs removes software from the timing path — which reduces both the CPU cost and, more importantly, the jitter.

If margin were tight, the levers would be reducing the loop rate (which the control design may not permit), optimising the maths (fixed-point, lookup tables), or a faster part.

Listening forQuestioning whether the number is a worst case, and the FPU dependency.
How would you test this?Senior

In layers, with the safety-relevant behaviour tested most aggressively.

Host unit tests for the control maths and the state machines, with hardware behind a substitutable interface. Hardware-in-the-loop with a motor and sensor emulator, so the ECU can be run through the full operating envelope, including conditions that are dangerous or impossible on a real vehicle — sensor failures, disagreements, out-of-range values.

Fault injection as the priority: disconnect each sensor, short each one, make the channels disagree by varying amounts, cut the supply mid-write, force CAN bus-off, hang the main MCU deliberately and confirm the safety monitor drops the enable. Every row of the failure table needs a test that proves the response, because those paths never run otherwise.

Environmental: the full temperature range, vibration, and EMC immunity testing — this environment is harsh enough that bench-only validation is meaningless.

Timing verification: measure worst-case execution and interrupt latency on real hardware under worst-case load, not just utilisation arithmetic.

And in-vehicle testing last, because by then the failure behaviour should already be proven.

Listening forFault injection prioritised, and testing every row of the failure table.
