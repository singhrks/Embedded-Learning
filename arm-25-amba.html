AMBA: APB, AHB, AXI, ACE and CHI

The interconnect is where a load instruction finally becomes electrical activity. Which protocol a block speaks tells you its performance class — and the sideband signals a transaction carries are the foundation of everything in the security track.

The protocol family

Reading the year column top to bottom is reading the history of what SoCs needed to scale next. APB is about as simple as a bus can be — one transfer at a time, no pipelining — which is exactly right for a UART that a CPU touches occasionally and never needs bandwidth from. AHB added pipelining and bursts once single transfers became the bottleneck for faster peripherals, but it is still one shared bus, so only one transaction is ever in flight. AXI's real innovation is splitting a transfer into five independent channels tagged with IDs, which lets many transactions from many masters be outstanding and completing out of order — necessary the moment a DMA controller, a GPU and several CPU cores all want the memory controller's attention at once. ACE and CHI then layer cache coherency on top of AXI's foundation, because once you have several CPU clusters each with their own cache, "who has the current copy of this line" becomes a protocol question in its own right — which is exactly the subject of the computer architecture track's coherence chapter.

ProtocolYearCharacterTypical use
APB1996Simple, no bursts, one transfer at a time, two clock cycles minimumSlow peripheral registers: UART, I2C, GPIO, timers
AHB1999Single shared bus, pipelined address/data, burstsCortex-M systems, simpler SoCs
AXI2003Five independent channels, out-of-order via IDs, multiple outstanding transactionsThe workhorse: memory controllers, DMA, GPU
ACE2011AXI plus coherency: snoop channelsCoherent CPU clusters
ACE-Lite2011Can snoop others, has no cache to be snoopedI/O-coherent DMA masters
CHI2013Packet-based, credit flow control, scalable meshLarge multi-core and server SoCs

AXI's five channels

AXI separates a transaction into independent channels so that addresses, data and responses can flow concurrently rather than in lockstep. That separation is the source of both its performance and its complexity.

   master                                              slave
     │                                                   │
     │──── AW: write address ──────────────────────────► │
     │──── W:  write data ─────────────────────────────► │
     │◄─── B:  write response ───────────────────────────│
     │──── AR: read address ───────────────────────────► │
     │◄─── R:  read data ────────────────────────────────│

  Each channel is INDEPENDENT, with its own VALID/READY handshake.
  Two consequences that matter enormously:

  1. OUTSTANDING TRANSACTIONS. Because address and data are
     separate channels, a master can issue many addresses before
     any data returns. This is how a memory system hides 200-cycle
     DRAM latency — keep dozens of requests in flight rather than
     waiting for each. Little's Law again (CA chapter 18).

  2. OUT-OF-ORDER COMPLETION. Each transaction carries an ID
     (AWID/ARID), and responses may return in any order. A slow
     DRAM read does not block a fast SRAM read behind it.

  The write response channel (B) is why a write can be ACKNOWLEDGED
  before it reaches the endpoint — the "early ack" in
  Device-nGnRE (chapter 11), and the reason a posted write needs
  a read-back to force completion.

Page table bits become wires

The NS and AttrIndx fields you set in a translation descriptor (chapter 14) are not abstractions. They are converted into AxPROT[1] and AxCACHE on the bus, and hardware downstream — the SMMU, the TZASC, an XPU — makes allow-or-deny decisions from them.

Setting a bit in a page table entry is setting a signal on the interconnect. Once you see that, the whole security track stops being a separate subject.

ACE and coherency

Once caches exist on multiple masters, the interconnect itself has to participate in keeping them consistent. These extensions are what make hardware coherency possible across a whole SoC.

ACE adds three SNOOP channels to AXI:

   AC   snoop address    the interconnect asks a master
                         "do you have this line?"
   CR   snoop response   "yes, modified" / "no" / "yes, clean"
   CD   snoop data       the master supplies the line

  This is how MESI is implemented in hardware (CA chapter 15).
  When core 0 wants a line that core 1 holds modified, the
  interconnect snoops core 1, gets the data, and forwards it —
  without going to DRAM at all.

  ACE          full coherency: can snoop AND be snooped.
               For CPU clusters with caches.
  ACE-Lite     can snoop others, but has no cache of its own.
               For DMA masters that need to see CPU-cached data.
               This is what `dma-coherent` in the device tree
               actually means (chapter 19).
  AXI          no coherency at all. Software must do cache
               maintenance (chapter 18).

  The DISTRIBUTED VIRTUAL MEMORY (DVM) messages ride on the same
  channels: TLB invalidations, instruction cache invalidations and
  synchronisation. That is what makes TLBI ...IS broadcast in
  hardware rather than needing an IPI (chapter 15).

CHI: scaling past a bus

At high core counts a shared bus stops working and the interconnect becomes a network. This is the protocol designed for that scale, and it is what large server and mobile SoCs actually use.

Broadcast snooping does not scale. With 64 cores, every coherent
access would snoop 63 caches.

CHI (Coherent Hub Interface) replaces the bus model entirely:

   · PACKET-BASED, not signal-based. Requests, responses, snoops
     and data are messages on a mesh network.
   · CREDIT-BASED flow control — no combinatorial ready/valid
     paths spanning the chip.
   · A HOME NODE per address range keeps a DIRECTORY of which
     caches hold which lines, so invalidations are sent
     point-to-point rather than broadcast.
   · Scales to hundreds of nodes on a 2-D mesh.

           ┌────┐ ┌────┐ ┌────┐ ┌────┐
           │ CPU│─│ CPU│─│ HN │─│ MC │      HN = home node
           └─┬──┘ └─┬──┘ └─┬──┘ └─┬──┘      MC = memory controller
           ┌─┴──┐ ┌─┴──┐ ┌─┴──┐ ┌─┴──┐      SN = slave node
           │ CPU│─│ CPU│─│ SN │─│ IO │
           └────┘ └────┘ └────┘ └────┘

  Implementations: Arm CMN-600/650/700, and every Neoverse-based
  server SoC.

  The practical consequence for software: latency now depends on
  DISTANCE across the mesh. Two cores adjacent to each other
  communicate faster than two on opposite corners, and memory
  attached to a near controller is faster than a far one. This is
  NUMA appearing inside a single chip, and it is why scheduler
  and allocator locality matters even on "one socket".

APB: still everywhere

Not everything needs bandwidth. A simple, low-cost protocol remains the right answer for configuration registers, and most peripherals in an SoC sit behind one.

/* The simplest protocol, and the one most peripheral registers
   actually sit behind.                                       */

   PSEL, PENABLE, PWRITE, PADDR, PWDATA, PRDATA, PREADY, PSLVERR

/* A transfer takes a minimum of TWO cycles (setup then access),
   with no pipelining and no bursts. That is why:

     · a register read behind an APB bridge can cost 20-100 CPU
       cycles even though the peripheral is "on chip"
     · reading a status register in a tight polling loop is
       genuinely expensive
     · the APB clock is often much slower than the CPU clock,
       multiplying the cost further

   Practical consequence: minimise register accesses in hot
   paths. Cache values in software where the hardware permits,
   batch writes, and prefer a single wide read over several
   narrow ones. A driver that reads six status registers per
   interrupt is doing something measurably expensive.       */

Interconnect topology

How masters and slaves are wired together determines who contends with whom for bandwidth. Two systems with identical components can perform very differently based on this alone.

   SHARED BUS        one set of wires, arbitration decides who
                     drives. Simple, cheap, does not scale.
                     → AHB, APB

   CROSSBAR          every master to every slave. Full parallelism
                     between disjoint pairs; area grows as N×M.
                     → small AXI interconnects (NIC-400)

   NETWORK ON CHIP   routers and links; packets find their way.
                     Scales to dozens of masters, at the cost of
                     variable latency.
                     → CMN, and most large SoC fabrics

   POINT TO POINT    dedicated links, switched.
                     → PCIe, and CHI links

A typical SoC has SEVERAL of these, layered:

   CPU cluster ──CHI──► coherent mesh ──► memory controllers
                              │
                         ──AXI──► GPU, DMA, video
                              │
                         ──AXI──► APB bridge ──► UART, I2C, GPIO
                                                  SPI, timers

  Reading a UART register therefore crosses a mesh, an AXI
  interconnect and an APB bridge. That is the real reason MMIO
  is slow — not the peripheral, the journey.

Quality of service and bandwidth

When several masters compete for memory bandwidth, something has to arbitrate — and a display controller missing its deadline is a visible failure in a way that a slow CPU is not.

/* AxQOS gives each transaction a 4-bit priority. Interconnect
   arbiters use it to decide who wins under contention.      */

/* Why it matters in real systems: a display controller MUST get
   its data before the scan-out deadline or the screen tears.
   A CPU running a batch job can wait. Without QoS, the CPU's
   bandwidth-hungry memcpy starves the display.

   Typical assignment on a phone SoC:
      display / camera   highest — hard real-time deadlines
      GPU                high
      CPU                medium
      background DMA     low

   Configured in the interconnect's registers, usually by
   firmware, and often exposed to Linux via the interconnect
   framework:                                                */

        &display {
                interconnects = <&mmss_noc MASTER_MDP &mc_virt SLAVE_EBI1>;
                interconnect-names = "mdp0-mem";
        };

/* And in the driver: */
        path = of_icc_get(dev, "mdp0-mem");
        icc_set_bw(path, avg_bw, peak_bw);

/* MPAM (ARMv8.4) extends this to cache and memory bandwidth
   PARTITIONING, which is what mixed-criticality systems need to
   bound interference between a real-time and a best-effort
   guest (OS chapter 19).                                    */

Bus errors

A transaction can fail on the bus, and what happens next depends on where the failure was detected. This is the origin of several fault types that are otherwise hard to explain.

/* A slave can respond with an error, and the response reaches
   the core as an ABORT.                                      */

   AXI RRESP / BRESP:
      OKAY        normal completion
      EXOKAY      exclusive access succeeded
      SLVERR      the slave signalled an error — unclocked
                  peripheral, illegal register, denied access
      DECERR      no slave at that address — a DECODE error

/* How software sees them:

   SYNCHRONOUS — for a read, or a non-posted write, the core is
   still waiting, so the abort is precise:
      ESR_EL1.EC   = 0x24/0x25 (data abort)
      ESR_EL1.DFSC = 0b010000  (synchronous external abort)
      FAR_EL1      = the address

   ASYNCHRONOUS — for a POSTED write, the core moved on long ago.
   The error arrives as an SError, and the reported PC has
   NOTHING to do with the cause. This is the hardest fault class
   to attribute, and it is exactly what an XPU denial of a posted
   write produces (security track, chapter 20).

   Mitigation: ESB (Error Synchronization Barrier) at known
   points confines an SError to a bounded region of code, making
   attribution possible. The RAS extension adds error records
   describing what failed.                                   */

Observing the interconnect

Interconnect behaviour is hard to observe from software, but not impossible — and on many SoCs there are counters specifically for it.

# the memory map — what lives where
cat /proc/iomem

# interconnect bandwidth requests (where the framework is used)
cat /sys/kernel/debug/interconnect/interconnect_summary

# PMU events for bus traffic
perf stat -e bus_access,bus_access_rd,bus_access_wr,\
bus_cycles,mem_access ./prog

# many SoCs expose interconnect PMUs — CMN, DSU, memory controller
perf list | grep -iE 'cmn|arm_dsu|imc'
perf stat -e arm_cmn/hnf_cache_miss/ ./prog

# bandwidth saturation is the usual finding: if bus_access is
# high and IPC is low with few cache misses, you are waiting on
# the interconnect, not on DRAM latency.

# in a JTAG debugger, most vendors provide interconnect trace —
# Arm CoreSight can capture bus transactions directly, which is
# the definitive way to see what actually reached a peripheral.
