CPU scheduling algorithms

The scheduler decides which thread runs next, and it must satisfy goals that directly contradict each other. Understanding which goal a scheduler is optimising explains every design decision it makes — and tells you which one your workload actually needs.

Goals that conflict

GoalDefinitionConflicts with
ThroughputWork completed per secondFairness, latency — switching costs time
Latency / responseTime from ready to runningThroughput — frequent preemption thrashes caches
FairnessProportional share of CPUPriority, throughput
PriorityImportant work firstFairness — and risks starvation
DeterminismBounded worst caseNearly everything else
EfficiencyLow scheduler overhead itselfSophistication of the policy
The one question to ask

"Is this system optimising the average case or the worst case?" A general-purpose OS optimises the average — it will happily add 10 ms of jitter to gain 5% throughput. An RTOS optimises the worst case and gives up throughput without hesitation. Almost every argument about scheduler behaviour is really a disagreement about which of these the system should do.

Preemptive versus cooperative

Whether the kernel can take the processor away from running code, and when, is the single decision that shapes a system's responsiveness. It also determines what kernel code must protect itself against.

COOPERATIVE           a thread runs until it yields or blocks
                      + no preemption points, so no locks needed
                        between yields — much simpler reasoning
                      + very low overhead
                      - one runaway thread hangs the system
                      - a buggy thread can never be recovered
                      used by: async runtimes, some RTOSes,
                               classic Mac OS and Windows 3.x

PREEMPTIVE            a timer interrupt can switch at any moment
                      + one thread cannot monopolise the CPU
                      + latency is bounded by the tick or better
                      - every shared structure needs synchronisation
                      - context switch cost on every switch
                      used by: every general-purpose OS

Linux preemption levels, chosen at build time:
  PREEMPT_NONE        kernel code never preempted — best throughput
  PREEMPT_VOLUNTARY   explicit reschedule points in long loops
  PREEMPT             kernel is preemptible except in critical
                      sections — the desktop default
  PREEMPT_RT          almost fully preemptible: most spinlocks
                      become sleeping mutexes and IRQ handlers
                      become threads. Latency in tens of µs,
                      at a throughput cost.

The classic algorithms

The textbook algorithms are worth knowing not because any system uses them unmodified, but because every real scheduler is a compromise between the properties they demonstrate in isolation.

AlgorithmRuleStrengthWeakness
FCFS / FIFOFirst to arrive runs to completionTrivially simple, no starvationConvoy effect: one long job blocks everything behind it
SJFShortest job firstProvably optimal average wait timeRequires knowing job length; starves long jobs
SRTFPreemptive SJFEven better averageSame problems, plus more switching
Round robinEach gets one time slice, cyclicallyFair, responsive, no starvationQuantum choice is a hard trade-off
PriorityHighest priority runsExpresses importanceStarvation; priority inversion
MLFQSeveral queues; demote CPU hogs, promote I/O-bound tasksApproximates SJF without knowing job lengthsTunable in many ways; gameable
Fair-share / CFSTrack CPU consumed; run whoever is furthest behindFair by construction; no heuristics to tuneNot real-time
Lottery / strideTickets proportional to shareSimple proportional sharingRandomness gives poor short-term fairness
 
The quantum trade-off, made concrete

  Context switch cost ≈ 1-5 µs (plus cache and TLB refill)

    quantum 1 ms  →  overhead 0.1-0.5%   latency up to 1 ms
    quantum 10 ms →  overhead 0.01-0.05% latency up to 10 ms
    quantum 100 µs → overhead 1-5%       latency up to 100 µs

  Interactive work wants short quanta; batch work wants long ones.
  This is precisely why MLFQ exists: give short quanta at high
  priority to tasks that block quickly, and long quanta at low
  priority to tasks that burn their whole slice.

Multi-level feedback queue

Rather than picking one algorithm, most practical schedulers infer what a task needs from how it has behaved — moving interactive work up and CPU-bound work down automatically.

   priority
     high  ┌──────────────┐  quantum 10 ms
       Q3  │ A            │  ← new arrivals start here
           └──────┬───────┘
                  │ used the whole quantum → demote
       Q2  ┌──────▼───────┐  quantum 20 ms
           │ B  C         │
           └──────┬───────┘
                  │
       Q1  ┌──────▼───────┐  quantum 40 ms
           │ D            │
           └──────┬───────┘
                  │
     low   Q0  ┌──▼───────┐  quantum 80 ms
           │ E            │
           └──────────────┘

  Rules:
   1. run the highest non-empty queue, round robin within it
   2. a job that uses its full quantum is DEMOTED (it is CPU-bound)
   3. a job that blocks early stays or is PROMOTED (it is I/O-bound,
      and is probably interactive)
   4. periodically boost everything back to the top — this prevents
      starvation, and defeats gaming rule 3 by yielding just before
      the quantum expires

  This infers job length from OBSERVED behaviour, which is why it
  approximates SJF without an oracle. Windows and older Linux both
  used variants of this.

Fair scheduling: CFS and EEVDF

Linux's approach abandons time slices and priorities as the primary mechanism, tracking instead how much CPU each task has already received and running whoever is furthest behind.

/* CFS (Completely Fair Scheduler), Linux 2.6.23-6.5, replaced the
   heuristic MLFQ with a single idea:                            */

   VIRTUAL RUNTIME (vruntime) = actual runtime, weighted by nice

       vruntime += delta_exec * (NICE_0_WEIGHT / task_weight)

   · a low-nice (high-priority) task has a large weight, so its
     vruntime advances SLOWLY, so it is picked more often
   · always run the task with the SMALLEST vruntime
   · tasks are kept in a red-black tree keyed by vruntime, so
     "smallest" is O(1) to find and O(log n) to reinsert

   No heuristics, no priority boosting, no interactivity guessing —
   just: whoever has had the least CPU (weighted) runs next.

   nice values map to weights on a ~1.25x-per-step curve:
       nice  0 → weight 1024
       nice -5 → weight 3121   (~3x more CPU)
       nice  5 → weight  335   (~3x less)
       nice ±1 is roughly a 10% change in share
/* EEVDF (Earliest Eligible Virtual Deadline First) replaced CFS in
   Linux 6.6. Same fairness core, plus an explicit LATENCY term:

     · each task gets a virtual deadline based on its requested
       latency (settable per task via sched_setattr)
     · among ELIGIBLE tasks (those not ahead of their fair share),
       run the earliest deadline
     · so a task can ask for low latency WITHOUT asking for more
       CPU — which CFS could not express

   This matters for audio, games and interactive work, which want
   to be scheduled QUICKLY but not necessarily OFTEN.          */

chrt --help                      # see and set policies
nice -n 10 ./batch_job
renice -n -5 -p 1234
schedtool -n -5 -e ./program

Real-time scheduling

When a task must run within a bounded time, fairness is the wrong goal entirely. These classes drop it, and with it the guarantee that anything else will ever run.

PolicyRuleUse for
SCHED_FIFOPriority 1–99. Runs until it blocks or yields. No time slicing.Short, bounded, critical work
SCHED_RRSame, plus round-robin among equal prioritiesSeveral equal-priority RT tasks
SCHED_DEADLINESpecify runtime, deadline and period explicitly. EDF + constant bandwidth server.Periodic tasks with real deadlines
SCHED_OTHERThe fair schedulerEverything else
SCHED_IDLEOnly when nothing else wants the CPUBackground scavenging
 
#include <sched.h>
struct sched_param p = { .sched_priority = 50 };
sched_setscheduler(0, SCHED_FIFO, &p);

/* SCHED_DEADLINE — say what you actually need */
struct sched_attr attr = {
        .size          = sizeof attr,
        .sched_policy  = SCHED_DEADLINE,
        .sched_runtime =  2 * 1000 * 1000,   /*  2 ms of CPU     */
        .sched_deadline = 8 * 1000 * 1000,   /*  within 8 ms     */
        .sched_period  = 10 * 1000 * 1000,   /*  every 10 ms     */
};
syscall(SYS_sched_setattr, 0, &attr, 0);
/* The kernel performs an ADMISSION TEST: if total utilisation
   would exceed capacity, the call fails rather than silently
   missing deadlines. That is what makes it genuinely real-time. */
A SCHED_FIFO infinite loop hangs the machine

It never yields, and nothing at lower priority — including your shell — will ever run again. Protections: sched_rt_runtime_us reserves a slice for non-RT tasks (95% RT by default), and you should always test RT code on an isolated CPU. Reserve SCHED_FIFO for short, provably bounded work, and always pair it with mlockall() so a page fault cannot introduce unbounded delay.

Priority inversion

A high-priority task can be blocked indefinitely by a low-priority one holding a lock it needs. This is not a hypothetical — it is the failure that nearly ended a Mars mission, and the fixes are well understood.

   HIGH  ────────────┐                      ┌─────────
                     │ blocked on the lock  │
   MED        ┌──────┴──────────────────────┘
              │ runs — it preempts LOW, which still holds the lock
   LOW  ──────┴───┐
        holds lock│

  HIGH waits on LOW; MED preempts LOW; therefore MED delays HIGH
  indefinitely. Priority is effectively inverted.

  This is not theoretical: it nearly ended the Mars Pathfinder
  mission in 1997. The fix was uploaded from Earth.

  SOLUTIONS
   Priority inheritance  the lock holder temporarily inherits the
                         highest priority among its waiters.
                         → PTHREAD_PRIO_INHERIT, and RT-mutexes
                           throughout PREEMPT_RT
   Priority ceiling      the lock carries a priority; anyone taking
                         it is raised to that level immediately
   Avoid sharing         lock-free structures, or per-CPU data
pthread_mutexattr_t a;
pthread_mutexattr_init(&a);
pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&m, &a);
/* Costs a little on every lock and unlock. Mandatory when RT and
   non-RT threads share a mutex.                                */

Multiprocessor scheduling

With several processors, scheduling gains a second question: not only which task runs next, but where. Moving a task between cores costs cache warmth, and the balance between that and idle cores is delicate.

ConcernMechanism
Per-CPU runqueuesAvoids one global lock. Linux has one runqueue per CPU.
Load balancingPeriodically migrate tasks between runqueues; also on wake-up and fork
Cache affinityPrefer the CPU a task last ran on — its cache is still warm. Migration costs a full cache refill.
Scheduling domainsA hierarchy — SMT sibling → core → cluster → NUMA node — with balancing cheapest at the closest level
NUMAKeep a task near its memory; migrating across nodes can double memory latency
Heterogeneous coresbig.LITTLE: energy-aware placement. Small tasks to LITTLE, bursty ones to big.
 
# pin to specific CPUs — essential for benchmarking and RT
taskset -c 2,3 ./program
taskset -pc 2 1234

# isolate CPUs from the general scheduler entirely (kernel cmdline)
isolcpus=2,3 nohz_full=2,3 rcu_nocbs=2,3
# then place your RT threads there with taskset. This is the
# standard recipe for low-latency work on Linux.

# NUMA placement
numactl --cpunodebind=0 --membind=0 ./program
numastat -p 1234

Observing the scheduler

Scheduler behaviour is fully observable, which turns latency complaints into measurements — showing exactly which task ran when and why yours did not.

# where is the time going?
vmstat 1                    # r = runnable, cs = context switches/s
pidstat -w -p PID 1         # voluntary vs involuntary switches
                            #   voluntary   = blocked on I/O or a lock
                            #   involuntary = preempted (CPU contention)

# per-task scheduler statistics
cat /proc/PID/sched         # vruntime, wait time, migrations
cat /proc/PID/status | grep -i ctxt
cat /proc/schedstat

# tracing
perf sched record ./workload && perf sched latency
perf sched timehist
trace-cmd record -e sched:'*' -- ./workload

# latency measurement for RT tuning
cyclictest -t4 -p 90 -i 200 -m -D 60
#   reports min/avg/MAX latency. The MAX is the number that matters.
Reading the two switch counts

High voluntary context switches means the task blocks a lot — it is I/O-bound, and the fix is usually fewer, larger operations. High involuntary switches means it is being preempted — the machine is oversubscribed, or something with higher priority keeps arriving. They call for completely different responses, and pidstat -w distinguishes them in one line.
