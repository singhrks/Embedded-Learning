SMMU: faults and debugging

SMMU faults are asynchronous, reported through a queue rather than as an exception, and easy to misread. This chapter is the practical one: decode an event record, work out which of six things went wrong, and fix it.

How a fault is reported

When the SMMU blocks a transaction it records what happened in an event queue rather than raising an immediate exception on some processor. Knowing where that record lands is the first step of every SMMU investigation.

Unlike a CPU fault, which is a synchronous exception with ESR
and FAR (ARM chapter 29), an SMMU fault is:

   1. detected while translating a DEVICE transaction
   2. written as a 32-byte EVENT RECORD into the event queue
   3. signalled by an interrupt (or MSI)
   4. read and logged by software, LATER

  So the fault is decoupled from anything the CPU was doing.
  There is no register to read at the moment it happens — the
  event record IS the evidence.

  The transaction itself is either TERMINATED (an abort returned
  to the device) or STALLED, depending on STE.S1STALLD and
  whether the device supports stalling.

  CONSEQUENCE: a device that faults typically reports a bus
  error, a timeout, or simply produces wrong data — and the
  SMMU's event record in dmesg is the only thing that says why.

Reading an event record

An event record names the device, the address, the access type and the reason. Reading one field by field turns "DMA is not working" into a specific statement about which check failed.

arm-smmu-v3 2b400000.iommu: event 0x10 received:
arm-smmu-v3 2b400000.iommu: 0x0000004200000010
arm-smmu-v3 2b400000.iommu: 0x0000000000000000
arm-smmu-v3 2b400000.iommu: 0x00000000fffff000
arm-smmu-v3 2b400000.iommu: 0x0000000000000000

/* Four 64-bit words. The layout, generally: */

   word 0  [7:0]    event type
           [63:32]  StreamID
   word 1  [31:0]   SubstreamID (if SSV set)
           [32]     SSV — SubstreamID valid
           [33]     PnU — privileged or unprivileged
           [34]     InD — instruction or data
           [35]     RnW — read or write
           [36]     S2  — the fault was at stage 2
           [37]     Class
   word 2  [63:12]  the faulting INPUT ADDRESS (IOVA or IPA)
   word 3           the faulting IPA, for stage-2 faults

/* Decoding the example above:
      type      = 0x10  = C_BAD_STREAMID
      StreamID  = 0x42
      address   = 0xfffff000

   Meaning: a device emitting StreamID 0x42 issued a transaction,
   and there is no valid Stream Table Entry for 0x42.

   The address is almost irrelevant here — the problem is the
   StreamID, not what it tried to touch.                    */

The three-way split

Group the event types by what they tell you:

  • Configuration faults (C_BAD_*, F_*_FETCH) — the SMMU could not find or parse its own tables. A software or integration bug; the device did nothing wrong.
  • Translation faults (F_TRANSLATION, F_ACCESS, F_PERMISSION) — the tables were fine; the address or the access type was wrong. Almost always a driver bug.
  • Stream faults (C_BAD_STREAMID, F_STREAM_DISABLED) — identity. Device tree, IORT, or an unconfigured device.

Triage

SMMU faults come from a small number of causes, and the record usually distinguishes them directly. This is the order to check them in, cheapest question first.

Reading the faulting address

With two stages of translation and several address spaces in play, the single hardest question during a fault is which kind of address you are looking at. Getting that wrong sends investigations in the wrong direction entirely.

/* The address in word 2 is the single most informative field
   after the event type. Learn to recognise the shapes:    */

   0x0000_0000_8xxx_xxxx    looks like a PHYSICAL address on a
                            typical SoC (DRAM at 0x80000000)
                            -> the driver passed phys_to_dma
                               incorrectly, or used virt_to_phys

   0xffff_8xxx_xxxx_xxxx    a KERNEL VIRTUAL address
                            -> the driver passed a kmalloc pointer
                               straight to the device

   0x0000_0000_0000_0000    NULL
                            -> uninitialised descriptor, or a
                               failed allocation not checked

   0x0000_00ff_xxxx_xxxx    a plausible IOVA in the allocated
                            range
                            -> the mapping existed and was torn
                               down. Look for: dma_unmap before
                               the device finished, remove()
                               without quiescing the device, or
                               a driver freeing a buffer early.

   0x0000_0000_08xx_xxxx    the ITS doorbell region
                            -> an MSI write that was not mapped
                               (chapter 03)

/* Cross-check against what was actually mapped: */
echo 1 > /sys/kernel/debug/tracing/events/iommu/enable
cat /sys/kernel/debug/tracing/trace_pipe | grep -i map
#   map: IOVA=0x00000000ff000000 paddr=0x0000000082340000 size=4096

The bisection that works

One experiment halves the search space

Boot once with iommu.passthrough=1.

  • The problem disappears → it is a mapping or StreamID issue. The device programming is fine; the SMMU configuration is not.
  • The problem persists → the bug is in how the device is programmed. The SMMU was just the messenger reporting it.

Never ship with passthrough enabled — but during bring-up this single reboot saves hours of speculation.

# the sequence that resolves most SMMU bring-up problems

# 1. is the SMMU even active?
dmesg | grep -iE 'smmu|iommu'
#   arm-smmu-v3 ...: ias 48-bit, oas 48-bit (features 0x...)
#   iommu: Default domain type: Translated     <- good
#   iommu: Default domain type: Passthrough    <- NOT translated

# 2. is this device behind it?
ls -l /sys/bus/platform/devices/2c000000.dma/iommu_group
cat /sys/kernel/iommu_groups/*/devices/*

# 3. trigger a transfer and read the fault
dmesg -w & ./trigger_dma

# 4. compare the StreamID in the record with the device tree
hexdump -C /proc/device-tree/soc/dma@2c000000/iommus

# 5. watch the mappings being created
echo 1 > /sys/kernel/debug/tracing/events/iommu/enable
cat /sys/kernel/debug/tracing/trace_pipe

# 6. bisect with passthrough
# add iommu.passthrough=1 to the command line, reboot, retest

The driver bugs behind most faults

Most SMMU faults are not attacks or hardware problems — they are ordinary driver mistakes that were previously invisible because nothing was checking. The SMMU simply made them fatal and visible.

Passed a physical addressF_TRANSLATION, PA-shaped addressSame
Unmapped while the transfer was in flightF_TRANSLATION, valid IOVAWait for completion before unmapping
Did not quiesce the device in remove()F_TRANSLATION after unbindStop the hardware first (OS 16)
Wrong DMA directionF_PERMISSIONMatch DMA_TO_DEVICE/FROM_DEVICE to reality
DMA to a stack bufferVariesNever — the stack is not DMA-able
DMA to vmalloc memoryF_TRANSLATIONNot physically contiguous; use kmalloc or scatter-gather

Stall mode and hangs

A faulting transaction can be aborted or held pending while software decides what to do. The second option enables demand paging for devices and requires the device itself to tolerate the wait.

/* If STE.S1STALLD = 0 and the device supports stalling, a
   faulting transaction is HELD rather than terminated. The
   device's pipeline stops until software responds.

   Consequences:
     · the device appears HUNG rather than reporting an error
     · a storm of stalled transactions can exhaust the device's
       internal queues and deadlock it
     · software MUST respond with CMD_RESUME, or the device
       never recovers

   Which is why Linux sets S1STALLD = 1 (terminate) unless PRI
   is in use — an unhandled stall is worse than a clean abort. */

/* If a device hangs with no fault reported at all, check: */
        dmesg | grep -i 'stall\|resume'
        cat /sys/kernel/debug/tracing/events/iommu/dev_fault/enable

/* And check the GLOBAL ERROR register — a malformed command or
   a queue overflow is reported there, not in the event queue: */
        SMMU_GERROR vs SMMU_GERRORN
//   arm-smmu-v3: GERROR MSI write aborted
//   arm-smmu-v3: CMD_SYNC timeout at 0x...
//   arm-smmu-v3: unexpected global error reported

Faults under virtualisation

Under virtualisation a fault may belong to the guest, to the host, or to the boundary between them — and routing it to the right one is part of what the hypervisor must configure.

/* With stage 2 in use, a fault may be at either stage — word 1
   bit 36 (S2) says which, and word 3 holds the IPA.        */

   S2 = 0   a stage-1 fault. The guest's own IOMMU tables are
            wrong, or the guest programmed the device with a bad
            IOVA. The guest's problem.

   S2 = 1   a stage-2 fault. The hypervisor has not mapped that
            IPA for the device. The HOST's problem — usually
            memory the guest owns but the host has not pinned
            and mapped for DMA.

/* A very common case: a guest passed a device a buffer in memory
   the hypervisor had not mapped into the device's stage-2
   tables. VFIO pins and maps all guest memory for exactly this
   reason, which is why passthrough VMs cannot use ballooning
   or overcommit without extra machinery.                   */

# on the host
dmesg | grep -A4 'event.*received'
cat /sys/kernel/debug/tracing/events/iommu/enable

The full toolkit

Everything above is inspectable from a running kernel, which means most SMMU problems can be diagnosed without a debugger or a logic analyser.

# fault records
dmesg -w | grep -i smmu

# mappings, live
echo 1 > /sys/kernel/debug/tracing/events/iommu/enable
cat /sys/kernel/debug/tracing/trace_pipe

# per-event tracepoints
ls /sys/kernel/debug/tracing/events/iommu/
#   add_device_to_group  attach_device_to_domain  map  unmap
#   io_page_fault  dev_fault  dev_page_response

# groups, domains and reserved regions
ls -l /sys/kernel/iommu_groups/*/devices/
cat /sys/kernel/iommu_groups/*/type
cat /sys/kernel/iommu_groups/*/reserved_regions

# SMMU performance counters, where present
perf list | grep -i smmu
perf stat -e arm_smmu_v3_pmcg_*/transaction/ -a sleep 5

# from a JTAG debugger: read SMMU_STRTAB_BASE, index by the
# StreamID from the fault record, and dump the STE. If it is
# zero or invalid, the configuration never reached the hardware.

# bpftrace on the fault path
sudo bpftrace -e 'tracepoint:iommu:io_page_fault {
        printf("%s dev=%s addr=%llx\n", comm, str(args->device),
               args->iova); }'
