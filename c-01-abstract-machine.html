The C abstract machine and translation phases

C does not describe what your processor does. It describes a hypothetical machine, and the compiler must only produce a program that behaves as if that machine ran it. Everything confusing about C — optimisation surprises, undefined behaviour, volatile — follows from this one idea.

What C actually is

Beginners learn C as "portable assembly": each statement becomes a few instructions. That model is wrong, and it will mislead you for years.

The as-if rule

The C standard defines an abstract machine with its own rules for evaluation, storage and side effects. A conforming implementation must reproduce the abstract machine's observable behaviour — and nothing else is guaranteed. Observable behaviour is:

  • accesses to volatile objects, exactly as written;
  • data written to files at program termination;
  • interactive input and output prompts, appearing before the reads they prompt.

Everything else — how many instructions, which registers, whether a variable exists at all, in what order independent computations happen — is the compiler's business.

/* You wrote this: */
int f(void) {
        int a = 10;
        int b = 20;
        int c = a * b;
        int d[100];
        for (int i = 0; i < 100; i++) d[i] = i;
        return c;
}

/* GCC -O2 emits this: */
f:
        mov     w0, #200
        ret

/* The array, the loop, and the variables never existed. Nothing about
   them was observable, so the abstract machine permits their removal.
   The compiler is not "cheating" — it is doing exactly what C says. */

The mental shift

Stop asking "what instructions will this produce?" and start asking "what am I permitted to assume?" The compiler is not your adversary, but it is a strict contract lawyer: it will use every freedom the standard grants. Code that relies on unguaranteed behaviour works until the day you raise the optimisation level, change compilers, or upgrade GCC — and then fails in production.

The eight translation phases

The standard defines translation as a sequence of phases. Knowing them explains a whole class of otherwise baffling errors.

  1  Map physical source characters to the source character set.
     Trigraphs (??= for #) replaced. Removed in C23; good riddance.

  2  Splice lines ending in backslash-newline.
     -> why a stray space AFTER the backslash in a multi-line macro
        breaks it: the backslash is no longer at end of line.

  3  Decompose into preprocessing tokens and whitespace.
     Comments become a single space HERE — so a comment cannot be
     produced by a macro, and /* */ inside a string literal is text.

  4  Execute preprocessing directives, expand macros, and recursively
     process #include files. Phases 1-4 run again on each header.
     -> #include is literal text substitution. Nothing more.

  5  Convert escape sequences and characters in literals to the
     execution character set.

  6  Concatenate adjacent string literals.
     -> "abc" "def" becomes "abcdef". This is why the PRIu32 macros
        work:  printf("%" PRIu32 "\n", x)

  7  COMPILE. Tokens are analysed syntactically and semantically,
     and translation units become object code.

  8  LINK. Resolve external references; combine translation units
     and library components into the final image.
/* Phase 2 in action — the classic multi-line macro bug */
#define SWAP(a, b) do {  \
        int t = (a);     \
        (a) = (b);       \ <-- one trailing space here
        (b) = t;         \
} while (0)
/* error: unterminated argument list / stray '\'
   because the line no longer ends in backslash-newline.       */

/* Phase 6 in action — adjacent literal concatenation */
#include <inttypes.h>
printf("count = %" PRIu32 " items\n", n);
/* PRIu32 expands to "u" (or "lu"), and phase 6 glues the three
   literals into one format string. This is how the standard makes
   printf portable across platforms with different int widths.  */

The translation unit

C's unit of compilation is one source file after preprocessing — the file plus every header it included, textually pasted in.

   main.c  ─┐
   stdio.h ─┼──[ preprocess ]──> one translation unit ──[ compile ]──> main.o
   mydefs.h ┘                                                            │
                                                                         │
   util.c  ─┐                                                            │
   mydefs.h ┴──[ preprocess ]──> another TU ────────[ compile ]──> util.o│
                                                                    │    │
                                                          [ link ]<──┴────┘
                                                              │
                                                            program

KEY CONSEQUENCE: the compiler sees ONE translation unit at a time.
It knows nothing about util.c while compiling main.c. That is why:

  · you need declarations in headers (the compiler must be told
    what exists elsewhere)
  · a mismatch between declaration and definition is a LINK error,
    or worse, silent corruption
  · `static` at file scope means "not visible to the linker"
  · cross-file inlining requires link-time optimisation (-flto)
/* the classic silent disaster this enables */

/* a.c */                          /* b.c */
int counter;                       extern short counter;   /* WRONG type */
void inc(void) { counter++; }      void reset(void) { counter = 0; }

/* Each TU compiles cleanly. The linker matches them by NAME only.
   b.c writes 2 bytes where a.c expects 4. Result: corruption that
   depends on endianness and layout.

   The fix is structural, not a matter of care: declare it ONCE, in a
   header, and include that header in BOTH files — including the one
   that defines it, so the compiler checks the definition against
   the declaration.                                                */

/* counter.h */
extern int counter;
void inc(void);
void reset(void);

Sequencing and the abstract machine's clock

The abstract machine does not execute one statement at a time in a simple order. It has sequence points (C99) or, more precisely, a sequenced-before relation (C11).

Guaranteed sequencedNOT sequenced
End of a full expression (the ;)Between function arguments
Between && and || operandsBetween the two operands of +, *, =
Between , operator operandsBetween subexpressions generally
Before a function call's body runsTwo calls in one expression: order unspecified
Between ?: condition and the chosen branch
 
/* Undefined behaviour: i modified twice with no sequencing between */
i = i++ + 1;
a[i] = i++;
f(i++, i++);          /* also: argument evaluation order is unspecified */

/* Well defined, because && sequences its operands */
if (p != NULL && p->field > 0)      /* p->field is not evaluated if p is NULL */

/* Unspecified but NOT undefined: the order of the two calls */
printf("%d %d\n", g(), h());        /* g may run before or after h */

/* This is why the "clever" one-liner is a genuine bug, not a style
   issue. There is no "what it does on my compiler" — the standard
   permits anything, including formatting your disk, and in practice
   different optimisation levels give different answers.          */

Objects, values and lvalues

C is defined in terms of an imaginary machine, not your processor. Almost every surprising thing the language does — and every optimisation that appears to break your code — follows from the compiler being allowed to do anything it likes as long as this abstract machine's observable behaviour is preserved.

TermMeaning
ObjectA region of storage whose contents can represent values. Not "an instance of a class" — C has no classes.
ValueThe meaning of an object's contents, as interpreted by its type
LvalueAn expression that designates an object. "Locator value" — it has an address.
RvalueInformally, the value of an expression. The standard says "value of an expression".
Effective typeThe type through which an object may be accessed. Violating it breaks strict aliasing (ch. 15).
LifetimeThe span during which storage is guaranteed reserved. Using an object outside its lifetime is undefined.
 
int x = 5;
int *p = &x;

x        /* lvalue: designates the object x        */
*p       /* lvalue: designates the object x        */
x + 1    /* not an lvalue: designates no object    */
&x       /* not an lvalue: the address is a value  */

x = 10;      /* fine: lvalue on the left  */
x + 1 = 10;  /* error: not an lvalue      */

/* Arrays are lvalues that are NOT assignable — a distinct category
   the standard calls "non-modifiable lvalue". Hence: */
int a[10], b[10];
a = b;       /* error, even though both are lvalues */

The abstract machine's memory model

C's memory model is deliberately vague about where things live, because the standard must cover machines that look nothing like each other. What it does define precisely is the lifetime of each object, and that is what actually governs your code.

C guarantees FOUR storage durations, not "the stack and the heap".
Where they physically live is the implementation's choice.

  static        exists for the whole program run
                globals, file-scope and function-scope `static`
                zero-initialised if not explicitly initialised
                -> typically .data and .bss

  thread        one instance per thread (_Thread_local, C11)
                -> typically thread-local storage blocks

  automatic     exists from block entry to block exit
                ordinary local variables
                INDETERMINATE unless you initialise them
                -> typically registers or the stack; often neither,
                   if the optimiser can prove no storage is needed

  allocated     from malloc/calloc/realloc until free
                -> typically the heap

The words "stack" and "heap" appear NOWHERE in the C standard. A
freestanding implementation (chapter 20) may have no heap at all.

Hosted versus freestanding

The standard defines two conformance levels, and the distinction is exactly the one that matters for kernel and bare-metal work.

HostedFreestanding
Entry pointmain() with the standard signatureImplementation-defined — _start, Reset_Handler, DriverEntry
LibraryThe complete standard libraryOnly headers with no runtime: <stddef.h>, <stdint.h>, <stdbool.h>, <limits.h>, <stdarg.h>, <float.h>, <iso646.h>, <stdalign.h>, <stdnoreturn.h>
ExamplesApplication on Linux or WindowsLinux kernel, bootloaders, Cortex-M firmware, UEFI
 
# building freestanding — what these flags actually mean
aarch64-none-elf-gcc \
    -ffreestanding \      # do not assume the standard library exists
    -nostdlib \           # do not link libc or the startup files
    -fno-builtin \        # do not replace calls with builtin versions
    -fno-stack-protector \
    -c main.c

# -fno-builtin matters more than it looks. Without it, GCC may turn
# a hand-written loop into a call to memcpy() — which does not exist
# in your freestanding image. Linker error, in a function you never
# called. The Linux kernel builds with -ffreestanding for this reason.

Standard versions

"C" is not one language. Each standard added features and, more importantly, changed rules — so the same source can be valid, invalid or subtly different depending on which version you compile against.

StandardWorth knowing for
C89 / C90Declarations at the top of a block only; no // comments. Still mandated in some safety-critical and legacy codebases.
C99// comments, declarations anywhere, <stdint.h>, <stdbool.h>, inline, VLAs, designated initialisers, compound literals, restrict
C11_Atomic, _Thread_local, _Static_assert, _Alignas/_Alignof, anonymous structs and unions, a real memory model
