Debugging in practice: four bugs, hunted end to end

Chapter 34 gave you the tools. This chapter uses them. Four real bugs — a crash, a silence, a delayed crash and an intermittent one — each followed from the symptom you are actually handed to the line that caused it, including the wrong turns worth not taking. Read it as four worked examples rather than as reference material.

The one principle underneath all four

Ask the cheapest question that eliminates the most possibilities. Every hunt below is an application of that: not "what is wrong with my code" — which is unanswerable — but "is the device even there", "was it allocated or freed", "which context was I in". Each answer removes half the search space, and each one costs seconds. Reading code in the hope of spotting the bug is the most expensive question available, and it goes last, not first.

Bug 1 — the crash: an oops during probe

This is the most approachable kind of failure, because the kernel has already done most of the work for you: it tells you where it died and what it was touching. The skill is knowing which five lines of the dump matter and ignoring the other forty.

# WHAT YOU ARE HANDED:

$ sudo insmod mydrv.ko
Killed
$ dmesg | tail -40
Unable to handle kernel NULL pointer dereference at virtual
        address 0000000000000018
Mem abort info:
  ESR = 0x0000000096000005
  EC = 0x25: DABT (current EL), IL = 32 bits
  FSC = 0x05: level 1 translation fault
Data abort info:
  ISV = 0, ISS = 0x00000005
  CM = 0, WnR = 0
Internal error: Oops: 96000005 [#1] PREEMPT SMP
Modules linked in: mydrv(O+)
CPU: 1 PID: 412 Comm: insmod Tainted: G           O  6.12.0 #1
pc : mydrv_probe+0x8c/0x1f0 [mydrv]
lr : platform_probe+0x70/0xd0
Call trace:
 mydrv_probe+0x8c/0x1f0 [mydrv]
 platform_probe+0x70/0xd0
 really_probe+0xbc/0x2a8
 driver_probe_device+0x3c/0x118
 ...

Four facts in that dump answer almost the whole question, and the rest is noise on a first pass. Reading them in this order turns a wall of hex into a specific line of your code.

   1. "NULL pointer dereference at ... 0000000000000018"

        NOT simply "a NULL pointer". The address is 0x18 = 24
        DECIMAL. Something did ptr->member where ptr was NULL
        and `member` sits 24 BYTES INTO THE STRUCTURE. That
        offset is the single most useful number in the dump.

   2. "WnR = 0"

        Write-not-Read. 0 means it was a READ. So the code was
        reading a field, not assigning to one - which usually
        halves the candidate lines immediately.

   3. "pc : mydrv_probe+0x8c/0x1f0 [mydrv]"

        The faulting instruction is 0x8c bytes into
        mydrv_probe, which is 0x1f0 bytes long. This is an
        exact location, not an approximation.

   4. The call trace, read TOP-DOWN

        mydrv_probe was called by platform_probe, called by
        really_probe. So this is the driver core binding your
        device - you are in probe, not in some later path.
        Nothing above your function is suspicious; the bug is
        yours.

Now turn those two numbers — the function offset and the structure offset — into a line of source and a field name. Two tools do this, and neither requires reproducing the bug again.

# THE OFFSET INTO THE FUNCTION -> A SOURCE LINE:
$ ./scripts/faddr2line mydrv.ko mydrv_probe+0x8c
mydrv_probe+0x8c/0x1f0:
mydrv_probe at /home/you/mydrv/mydrv.c:118

$ sed -n '118p' mydrv.c
        dev_info(dev, "fifo depth %u\n", d->cfg->fifo_depth);

# THE OFFSET INTO THE STRUCT -> A FIELD NAME:
$ pahole -C mydev_config mydrv.ko
struct mydev_config {
        unsigned int  nr_channels;   /*   0   4 */
        unsigned int  reserved;      /*   4   4 */
        ...
        unsigned int  fifo_depth;    /*  24   4 */   <-- 0x18
        ...
};

# So: d->cfg was NULL, and the code read cfg->fifo_depth at
# offset 24. Both numbers agree. That is the bug, located
# without ever re-running it.
/* THE CAUSE, back in the source: */

        d->cfg = of_device_get_match_data(dev);
        dev_info(dev, "fifo depth %u\n", d->cfg->fifo_depth);
        /*                                ^^^^^^ unchecked   */

/* of_device_get_match_data() returns NULL when the matched
   of_device_id entry has no .data - which is exactly what
   happens when someone adds a new compatible string to the
   table and forgets the .data field:                       */

static const struct of_device_id my_of_match[] = {
        { .compatible = "vendor,mydev-v2", .data = &v2_config },
        { .compatible = "vendor,mydev-v3" },   /* <-- no .data */
        { }
};

/* THE FIX - check it, as chapter 33 says to check every
   return:                                                  */
        d->cfg = of_device_get_match_data(dev);
        if (!d->cfg)
                return -EINVAL;
What this generalises to

A NULL dereference plus a non-zero offset is always the same three-step hunt: the faulting address gives you the field offset, faddr2line gives you the source line, and pahole names the member. Getting fluent with those two commands turns most oopses into a two-minute job — and it is worth building the module with CONFIG_DEBUG_INFO=y before you need them, because both require it.

Bug 2 — the silence: probe never runs at all

This one is harder than a crash, because there is no error message anywhere. The module loads, nothing happens, and dmesg is empty. Debugging an absence needs a different approach: rather than following a failure backwards, you walk the chain of things that must each have happened and find the first one that did not.

   THE CHAIN, and every link is separately checkable:

     1. the device tree node exists in the running kernel
              |
     2. its status is "okay" (not "disabled")
              |
     3. a struct device was created from it
              |
     4. the driver is loaded
              |
     5. the driver's compatible string MATCHES the node's
              |
     6. probe() is called
              |
     7. probe() returns 0

   ASK THEM IN ORDER. Whichever is the first "no" is your
   bug, and checking all seven takes under a minute.
# 1 and 2 - is the node there, and is it enabled?
$ ls /proc/device-tree/soc/ | grep mydev
mydev@1c000000
$ cat /proc/device-tree/soc/mydev@1c000000/status; echo
disabled                     # <-- FOUND IT, in most cases

# (If status is "okay", or the property is absent - which
#  also means enabled - carry on.)

# 3 - did a device get created?
$ ls /sys/bus/platform/devices/ | grep mydev
1c000000.mydev               # yes, the device exists

# 4 - is the driver actually loaded?
$ lsmod | grep mydrv
mydrv                  16384  0

# 5 - is anything bound to the device?
$ ls -l /sys/bus/platform/devices/1c000000.mydev/driver
ls: cannot access '.../driver': No such file or directory
#    ^ nothing claimed it. So the MATCH failed.

# WHICH compatible does the DEVICE advertise?
$ cat /sys/bus/platform/devices/1c000000.mydev/uevent
DRIVER=
OF_NAME=mydev
OF_COMPATIBLE_0=vendor,mydev-v3
OF_COMPATIBLE_N=1

# WHICH does the DRIVER accept?
$ modinfo mydrv.ko | grep alias
alias:          of:N*T*Cvendor,mydev-v2C*
alias:          of:N*T*Cvendor,mydev-v2

#   device says:  vendor,mydev-v3
#   driver says:  vendor,mydev-v2
#   They do not match. That is the entire bug.

The five most common causes all show up at a specific step of that walk, which is why doing it in order is worth more than any single command.

Fails at stepUsual causeFix
1 — no nodeThe .dtb being booted is not the one you editedCheck what the bootloader actually loaded; rebuild and reinstall the DTB
2 — disabledThe SoC .dtsi disables it by default and the board file never enabled itstatus = "okay"; in the board's node
3 — no deviceThe node is outside a bus that gets populated, or its parent is disabled Check the parent node too — a disabled parent silently disables every child
4 — not loadedMissing MODULE_DEVICE_TABLE, so autoloading never happens Add it, then depmod -a
5 — no matchA typo, or a compatible string added to the DT but not the driverCompare uevent with modinfo, exactly as above
6 — probe deferred foreverA resource provider never appearscat /sys/kernel/debug/devices_deferred
The deferred-probe list is the one people never find

If probe runs but keeps returning -EPROBE_DEFER (chapter 19), the device sits in a queue and nothing is ever printed at the default log level — so it looks exactly like a match failure. /sys/kernel/debug/devices_deferred lists every device still waiting and, usefully, which resource each is waiting for. Check it before concluding that matching is broken.

Bug 3 — the delayed crash: use-after-free

Here the machine crashes minutes after the mistake, in code that has nothing to do with the bug — the hardest kind to reason about, and the kind KASAN was built to eliminate. With it enabled, a bug that would have taken days becomes a report that names both the guilty line and the moment the memory was freed.

# THE SYMPTOM WITHOUT KASAN: random crashes, minutes after
# unbinding the device, in unrelated subsystems. Different
# backtrace every time. Unreproducible on demand.

# REBUILD WITH KASAN (chapter 18) AND IT BECOMES THIS:

BUG: KASAN: slab-use-after-free in mydrv_work+0x2c/0xf0 [mydrv]
Read of size 4 at addr ffff0000c8a41218 by task kworker/1:2/89

Call trace:
 mydrv_work+0x2c/0xf0 [mydrv]          <-- WHO TOUCHED IT
 process_one_work+0x1f4/0x448
 worker_thread+0x6c/0x458

Allocated by task 412:                  <-- WHERE IT CAME FROM
 mydrv_probe+0x40/0x1f0 [mydrv]
 platform_probe+0x70/0xd0

Freed by task 455:                      <-- AND WHO KILLED IT
 mydrv_remove+0x38/0x60 [mydrv]
 platform_remove+0x28/0x60
 device_release_driver_internal+0x1cc/0x228

Those three backtraces are the complete story, and they should be read as a single sentence rather than as three separate stack traces.

   "A WORK ITEM read memory that mydrv_remove had already
    freed."

   Which immediately tells you the shape of the bug WITHOUT
   reading any code: remove() ran while a work item was still
   queued or running. The work item then dereferenced the
   driver state that remove() had just released.

   THE RACE:

     remove()                    kworker
     --------                    -------
                                 (work queued earlier by the
                                  interrupt handler)
     devm frees d
     module unloads
                                 mydrv_work(d) runs
                                 reads d->something   <-- BOOM

   THIS IS EXACTLY chapter 13's question - "who frees this,
   and when?" - answered wrongly. remove() is not the moment
   the object stops being reachable; it is only the moment
   the DEVICE goes away.
/* THE FIX, and there are two levels of it. */

/* LEVEL 1 - stop the work before releasing anything: */
static void mydrv_remove(struct platform_device *pdev)
{
        struct mydev *d = platform_get_drvdata(pdev);

        cancel_work_sync(&d->work);      /* BLOCKS until any
                                            running instance
                                            finishes, and
                                            cancels a queued
                                            one                */
        /* only now is it safe for d to go away */
}

/* NOTE the ordering trap with devm_ (chapter 33): managed
   resources are freed AFTER remove() returns, so putting
   cancel_work_sync() in remove() is correct. Registering it
   with devm_add_action_or_reset() at probe time works too,
   and is tidier - but doing NEITHER, and relying on the work
   "probably not being queued", is the bug above.           */

/* LEVEL 2 - if the object can outlive the device for OTHER
   reasons too (an open file descriptor, say), cancelling is
   not enough and it needs a real reference count:          */
        kref_put(&d->refcount, mydev_release);
/* chapter 13 covers this properly. The rule of thumb: if the
   only other user is your own deferred work, cancel_work_sync
   is sufficient and simpler. If USER SPACE can still hold the
   object, you need refcounting.                             */
Turn KASAN on before you need it, not after

The bug above is essentially unfindable without KASAN and essentially trivial with it — the difference is not skill, it is whether the option was enabled when the crash happened. It costs roughly 2–3× slower execution and about an eighth more memory, which is irrelevant on a development board and buys you the two extra backtraces that make the report self-explanatory. Enable it in every development build, along with lockdep and CONFIG_DEBUG_ATOMIC_SLEEP, and leave them on.

Bug 4 — the intermittent: fine on the bench, fails under load

The last kind is the one that damages schedules: everything works during testing and fails at a customer site, or once a day, or only when the system is busy. These almost always turn out to be context or timing bugs that were present from the first day and simply had no opportunity to fire — and the fix is usually to make them deterministic rather than to catch them in the act.

# THE REPORT: "the board locks up after a few hours, but only
# when the network is busy." Nothing in dmesg on the customer's
# build.

# STEP 1 - do NOT try to reproduce it as-is. Rebuild with the
# checkers turned on and run the same workload. Now:

BUG: sleeping function called from invalid context
        at kernel/locking/mutex.c:283
in_atomic(): 1, irqs_disabled(): 0, non_block: 0,
        pid: 0, name: swapper/0
preempt_count: 101, expected: 0
CPU: 0 PID: 0 Comm: swapper/0 Tainted: G  O  6.12.0 #1
Call trace:
 __might_sleep+0x4c/0x60
 mutex_lock+0x28/0x90
 mydrv_timer_fn+0x2c/0xa0 [mydrv]      <-- yours
 call_timer_fn+0x38/0x1c0
 __run_timers+0x230/0x298
 run_timer_softirq+0x40/0x80           <-- SOFTIRQ context

The dump names the mistake outright, but the interesting question is why it stayed hidden for hours of testing — and the answer is a genuinely useful piece of kernel knowledge rather than bad luck.

   THE MISTAKE: a timer callback takes a mutex.

     Timer callbacks run in SOFTIRQ context (chapter 15).
     Softirq context MAY NOT SLEEP (chapter 02).
     mutex_lock() MAY sleep.
     Therefore this is always, unconditionally wrong.

   SO WHY DID IT WORK FOR HOURS?

     BECAUSE mutex_lock() ONLY SLEEPS IF THE MUTEX IS
     CONTENDED. An uncontended mutex_lock() takes the fast
     path - a single atomic operation - and returns
     immediately without ever calling schedule().

     On an idle bench system, nothing else held that mutex,
     so the call never slept and nothing went wrong.

     Under load, another thread held it, the timer callback
     tried to sleep in softirq context, and the kernel died.

   THIS IS THE GENERAL SHAPE OF "WORKS ON MY MACHINE":
   the bug was 100% present from day one. What varied was
   whether the conditions existed to EXPRESS it. Which is
   why the fix is never "add a retry" and always "find the
   rule that was broken".
/* THE FIX - move the work somewhere it is allowed to sleep,
   which is exactly what chapter 15's workqueue is for:     */

static void mydrv_timer_fn(struct timer_list *t)
{
        struct mydev *d = from_timer(d, t, timer);

        schedule_work(&d->work);        /* softirq-safe */
}

static void mydrv_work(struct work_struct *w)
{
        struct mydev *d = container_of(w, struct mydev, work);

        mutex_lock(&d->lock);           /* process context -
                                           sleeping is legal */
        ...
        mutex_unlock(&d->lock);
}

/* OR, if the critical section is genuinely short and must
   stay in the timer, use a spinlock instead - but then
   NOTHING inside it may sleep either (chapter 12).         */
The rule for every intermittent bug

Do not chase the symptom; make the bug deterministic. Rebuild with CONFIG_DEBUG_ATOMIC_SLEEP, CONFIG_PROVE_LOCKING and KASAN, then run the workload again. These checkers do not wait for the bad thing to happen — they verify the rules on every single call, so a violation is reported the first time the code path executes, whether or not the timing that would actually corrupt something ever occurs. An intermittent bug that survives all three checkers is rare; an intermittent bug found by them in ten minutes is the normal outcome.
