The NT layers: HAL, kernel and executive

Everything from here to the end of the track steps back from writing a driver to understanding the operating system the driver runs inside. Chapter 01 sketched the picture; this chapter and the ones after it look at each piece closely enough to explain why Windows behaves the way it does — not just what API to call.

Four layers, one job each

Windows is often described as a monolithic kernel, which is true but not useful. What actually matters is that the code inside it is divided into four layers with genuinely different responsibilities and genuinely different rules — and your driver sits at a specific one of them.

The names are easy to memorise and easy to misunderstand, so it is worth being precise about what each layer actually does and why the boundary sits where it does.

The HAL: one abstraction, one reason it exists

The Hardware Abstraction Layer exists to answer exactly one question for the rest of the kernel: how do I talk to the interrupt controller, the timers, and the buses on whatever chipset this particular machine has? Two x86 machines from different vendors can wire their interrupt controllers, ACPI tables and DMA controllers up differently at the chipset level even though they run the identical ntoskrnl.exe. Rather than fill the kernel with chipset-specific branches, Microsoft isolated all of that into a single replaceable module — hal.dll — with a fixed function table that the kernel calls through. Change the chipset, ship a different HAL; the kernel itself does not change a line.

Why this matters to a driver author

You almost never call the HAL directly. You call WdfInterruptCreate, or read a system time, and the executive or kernel routes the request through the HAL on your behalf. The reason to know it exists is diagnostic: if a bugcheck or a hang traces into hal.dll, you are looking at a genuinely low-level, often chipset-specific problem — an ACPI table the HAL misparsed, an interrupt routing issue, a timer programmed wrong — rather than an ordinary driver logic bug. It is also why WinDbg's lmvm hal is one of the first things worth checking on a boot hang.

The kernel: the "Ke" layer

Inside the same ntoskrnl.exe binary, one layer above the HAL, sits what Microsoft's own source calls the kernel proper — functions prefixed Ke. This is the smallest, most privileged, most carefully guarded code in the whole system, and it does exactly four things: it decides which thread runs next on each processor (the scheduler); it dispatches hardware interrupts and CPU exceptions to the right handler; it implements the primitive synchronisation objects — KEVENT, KMUTEX, KSPIN_LOCK — that everything else in Windows is built out of; and it performs the actual context switch, saving one thread's registers and loading another's.

Everything in this layer runs at DISPATCH_LEVEL or above (chapter 03), by necessity — you cannot schedule threads using a mechanism that itself needs to be scheduled. This is also why the kernel layer is deliberately tiny: less code at the highest privilege and the least interruptible state means fewer places for a catastrophic bug to hide.

The executive: where drivers actually live

The executive is the layer a driver author spends the most time in, even though it is easy to overlook as a distinct thing because it shares a binary with the kernel. It is where the higher-level services get built on top of the kernel's raw primitives: the Object Manager turns kernel objects into something that can be named, referenced by handle and protected by an access control list (chapter 31); the Memory Manager turns physical pages and the kernel's low-level page-table primitives into virtual address spaces, working sets and the paging file (chapter 30); the I/O Manager turns raw interrupts into IRPs flowing down a device stack (chapter 05); the Process and Thread Manager turns a scheduled kernel thread into the full Win32 notion of a process with a handle table, an address space and a security token (chapter 28).

   a hang inside KeWaitForSingleObject is the scheduler
   putting a thread to sleep; ObReferenceObjectByHandle is
   the object manager resolving a handle. Learning this
   table once removes a surprising amount of mystery from
   every crash dump you will ever read.

Environment subsystems: why cmd.exe and a Linux binary can both "just run"

Above the executive, in user mode, sit the environment subsystems — historically OS/2, POSIX, and the survivor, Win32 (csrss.exe plus kernel32.dll and friends). The native NT API exposed by ntdll.dll is deliberately generic and not Win32-specific; Win32 is one particular personality built on top of it. This is precisely how the Windows Subsystem for Linux 1 worked: WSL1 implemented a different personality — translating Linux syscalls into NT executive calls — rather than emulating an entire Linux kernel. WSL2 abandoned that approach in favour of a real Linux kernel in a lightweight VM, which tells you something honest about how hard it is to get a translation layer's semantics exactly right at that level, but the NT design that made WSL1 possible at all is the point: the kernel and executive know nothing about Win32 specifically. A driver, correspondingly, talks to the executive and kernel through the native NT API, never through Win32.

Reading a stack trace as a map through these layers

Here is the practical payoff. A stack trace is a walk through exactly these layers, and reading one from the bottom up tells you how a request arrived at the line that crashed — which is usually most of the diagnosis.

How it shows up

SymptomCause

Crash inside a function starting MmThe memory manager — almost always a page fault or an address-space bug (chapter 30)
Crash inside a function starting ObThe object manager — a handle or reference counting bug (chapter 31)
