Types, ranks and integer promotion

C silently converts operand types before almost every operation. The rules are precise, mostly invisible, and responsible for a remarkable share of real security vulnerabilities. This chapter makes them explicit.

The types, and what is actually guaranteed

C does not fix the size of its integer types. It fixes minimum ranges, and leaves the rest to the implementation.

TypeGuaranteed minimumTypical LP64 (Linux/ARM64)Typical LLP64 (Windows x64)
char8 bits88
short16 bits1616
int16 bits3232
long32 bits6432
long long64 bits6464
void *—6464
The single most expensive assumption in C

long is 64-bit on Linux and macOS, and 32-bit on Windows. Code that stores a pointer or a file offset in a long compiles cleanly on both and silently truncates on one. Every large port between these platforms has hit this. The rule: never use long when you mean "64 bits" — use int64_t, and use size_t/uintptr_t for sizes and pointer-sized integers.

The types you should actually use

#include <stdint.h>
#include <stddef.h>
#include <inttypes.h>

/* exact width — use these for anything that touches hardware,
   a file format, or the wire. They are optional in the standard
   but present on every platform you will meet.                  */
int8_t  int16_t  int32_t  int64_t
uint8_t uint16_t uint32_t uint64_t

/* at-least width, possibly faster than the exact type */
int_least32_t   int_fast32_t

/* pointer-sized integers */
intptr_t  uintptr_t          /* a pointer fits in these           */
ptrdiff_t                    /* result of subtracting pointers    */

/* sizes and counts */
size_t                       /* result of sizeof; unsigned        */
ssize_t                      /* POSIX: a size or -1 for error     */

/* printing them portably — this is what <inttypes.h> is for */
printf("%" PRIu32 " %" PRIx64 "\n", a, b);
printf("%zu %td %p\n", sz, diff, (void *)ptr);
/* %zu for size_t, %td for ptrdiff_t, and cast to void* for %p —
   all three are required, and all three are commonly got wrong.  */

Integer promotion

The rule

In almost any arithmetic context, any operand of a type whose rank is lower than int — char, short, _Bool, bitfields — is first converted to int, if int can represent all its values. Otherwise to unsigned int.

This happens before the operator is applied, and it happens whether you want it or not.

uint8_t a = 200, b = 100;

uint8_t c = a + b;
/* What happens:
     a is promoted to int -> 200
     b is promoted to int -> 100
     the addition is done in int -> 300      (NO wraparound here)
     the result is converted back to uint8_t -> 300 % 256 = 44
   So c == 44, but the intermediate value really was 300.        */

/* This matters when you check for overflow: */
if (a + b > 255)     /* TRUE — the comparison is done in int */
        handle_overflow();
/* ...which is what you wanted. But: */
if ((uint8_t)(a + b) < a)
        handle_overflow();   /* also works, and is the usual idiom */
/* The classic promotion surprise */
uint16_t x = 0xFFFF;
uint16_t y = ~x;                 /* what is y? */

/* Step by step:
     x promotes to int:        0x0000FFFF
     ~ applied in int:         0xFFFF0000   (int is 32-bit)
     converted back to uint16: 0x0000
   y == 0. Which is what you wanted, by luck.

   But this one is not luck: */
if (~x == 0xFFFF0000) ...        /* comparing uint16_t against int */

/* And this is a real bug: */
uint32_t z = ~x;                 /* z == 0xFFFF0000, NOT 0x0000FFFF */
/* Because ~x was computed in int, not in uint16_t. */

The usual arithmetic conversions

Once both operands are at least int, they are brought to a common type:

  1. If either is a floating type, convert to the larger floating type
     (long double > double > float).

  2. Otherwise, integer promotion is applied to both.

  3. If both have the same type, done.

  4. If both are signed, or both unsigned: convert to the HIGHER RANK.
     rank: long long > long > int > short > char

  5. MIXED SIGNEDNESS — where the bugs live:

     a) If the UNSIGNED type has rank >= the signed type's rank,
        the signed operand is converted to UNSIGNED.
                     <-- this is the dangerous case

     b) Otherwise, if the signed type can represent all values of
        the unsigned type, the unsigned operand is converted to
        SIGNED.

     c) Otherwise, both are converted to the unsigned version of
        the signed type.
Rule 5a, and the vulnerability it creates 
int len = -1;
if (len < sizeof(buffer))         /* sizeof yields size_t: UNSIGNED */
        memcpy(buffer, src, len);

/* len is converted to size_t.
   -1 as an unsigned 64-bit value is 18446744073709551615.
   The comparison is FALSE... no wait — it is 18446744073709551615 <
   sizeof(buffer)? No. So the branch is not taken. Lucky.

   Now flip the comparison, which is just as natural to write: */

if (len > sizeof(buffer))
        return -EINVAL;           /* NOT taken: -1 became huge?  no —
                                     huge > sizeof, so it IS taken.  */

/* The point is that you cannot reason about it at a glance, and the
   answer changes with the direction of the comparison and the types
   involved. Compare a signed length against a signed limit, or
   validate that the length is non-negative FIRST:                  */

if (len < 0 || (size_t)len > sizeof(buffer))
        return -EINVAL;

CVE databases are full of this pattern. Compile with -Wsign-compare (included in -Wextra) and treat every warning as a bug, not noise.

/* another everyday instance of the same rule */
for (int i = 0; i < strlen(s) - 1; i++)   /* strlen returns size_t */
        ...
/* If s is empty: strlen(s) is 0, and 0 - 1 in size_t is SIZE_MAX.
   The loop runs about 18 quintillion times. */

/* fix: compute the bound once, in a signed type, or restructure */
size_t n = strlen(s);
for (size_t i = 0; i + 1 < n; i++)        /* no subtraction below zero */
        ...

Signed versus unsigned: choosing deliberately

Choosing between signed and unsigned looks like a matter of whether negative values are possible. It is not: the two behave differently on overflow, in comparisons and in conversions, and picking by habit rather than deliberately is the source of a long list of real security bugs.

SignedUnsigned
OverflowUndefined behaviour — the compiler assumes it cannot happenDefined: wraps modulo 2N
OptimisationBetter: the compiler can assume i + 1 > iWorse: must handle wraparound
Comparison against the otherDangerous — see above
Right shiftImplementation-defined for negatives (arithmetic in practice)Defined: logical, fills with zero
Use forQuantities that can meaningfully be negative; loop indices that count downBit manipulation, hardware registers, sizes, hashes, modular arithmetic
 
/* Signed overflow is UB, and the optimiser acts on it: */
int check(int x) {
        return x + 1 > x;        /* compiles to `return 1;` */
}
/* Because signed overflow "cannot happen", x + 1 > x is always true.
   Your overflow check is deleted. See chapter 15.                  */

/* Unsigned wraps predictably, which is why hardware code uses it: */
uint32_t elapsed = now - start;   /* correct even when `now` wrapped */

/* Countdown loops with unsigned indices are a perennial bug: */
for (size_t i = n - 1; i >= 0; i--)   /* i >= 0 is ALWAYS true */
        ...                            /* infinite loop         */

for (size_t i = n; i-- > 0; )          /* correct idiom          */
        use(a[i]);

The three character types

char is the one type in C whose signedness is not specified by the language. It varies between platforms, which means code that works on x86 can fail on ARM for a reason that is invisible in the source.

/* char, signed char and unsigned char are THREE DISTINCT TYPES.
   Whether plain `char` is signed is implementation-defined:
       x86, ARM on Windows/macOS  -> signed
       ARM on Linux, PowerPC      -> UNSIGNED
   This has broken more ports than almost anything else.        */

char c = 200;            /* signed char: this is -56. unsigned: 200 */
if (c == 200) ...        /* false on ARM Linux, true on x86         */

/* The classic getchar() bug: */
char c;
while ((c = getchar()) != EOF)   /* WRONG */
        process(c);
/* getchar returns int so it can return 256 distinct byte values PLUS
   EOF (-1). Storing it in char loses that distinction: on a signed-
   char platform, byte 0xFF becomes -1 and terminates the loop early;
   on an unsigned-char platform the loop NEVER terminates because c
   can never equal -1.                                              */

int c;                            /* correct */
while ((c = getchar()) != EOF)
        process((unsigned char)c);

/* Rules that keep you out of trouble:
     - use `unsigned char` for raw bytes and buffers
     - use `char` only for actual text
     - cast to unsigned char before passing to <ctype.h> functions:
           isalpha((unsigned char)c);
       passing a negative char there is undefined behaviour        */

/* -funsigned-char / -fsigned-char force it, but relying on a flag
   makes your code non-portable in a different way. Be explicit. */

Conversion rules

C converts between types silently and constantly, following rules that are precise but unintuitive. These are the rules — and the reason an expression involving small types can produce a result you did not expect.

ConversionBehaviour
Narrowing to unsignedWell defined: modulo 2N. (uint8_t)300 is 44.
Narrowing to signedValue fits: preserved. Does not fit: implementation-defined (in practice, truncation with the top bit becoming the sign)
Signed → unsignedWell defined: add 2N until in range. (unsigned)-1 is UINT_MAX.
Unsigned → signedFits: preserved. Does not fit: implementation-defined
Integer → floatRounded if not exactly representable (CA ch. 03)
Float → integerTruncates toward zero. Out of range or NaN is undefined.
Anything → _Bool0 becomes false, anything else true. Not truncation.
 
(int)3.99      ->  3      /* truncation, not rounding      */
(int)-3.99     -> -3      /* toward zero, not toward -inf  */
(int)1e30      ->  UNDEFINED — does not fit in int
(_Bool)256     ->  1      /* not 0! _Bool is not a narrow int */

/* rounding, when you actually want it */
#include <math.h>
lround(3.5)    ->  4
(int)(x + 0.5) ->  wrong for negatives, and for x near the .5 boundary

Writing overflow checks that survive the optimiser

Since conversions happen silently, the only practical defence is making the compiler tell you when one is dangerous. These are the ways to do that before the behaviour reaches a running system.

/* WRONG: relies on signed overflow, which is UB, so it is deleted */
if (a + b < a) overflow();

/* RIGHT 1: compiler builtins. Portable across GCC and Clang,
   and they map to the CPU's flags — one instruction. */
int result;
if (__builtin_add_overflow(a, b, &result))
        return -EOVERFLOW;

/* RIGHT 2: check before the operation, using the type's limits */
#include <limits.h>
if (b > 0 && a > INT_MAX - b) return -EOVERFLOW;
if (b < 0 && a < INT_MIN - b) return -EOVERFLOW;

/* RIGHT 3: for sizes, use unsigned and check the wrap — defined behaviour */
size_t total = n * size;
if (n != 0 && total / n != size)
        return -EOVERFLOW;              /* the classic malloc guard */

/* Linux kernel helpers that do exactly this */
check_add_overflow(a, b, &res);
array_size(n, size);          /* saturates to SIZE_MAX on overflow */
struct_size(p, member, n);

Compiler flags that catch these

Much of what follows is only visible if the compiler is asked to look. This is the set of flags worth turning on permanently, and what each one actually catches.

gcc -Wall -Wextra \
    -Wsign-compare \        # signed/unsigned comparison — enable and OBEY
    -Wconversion \          # implicit narrowing conversions (noisy but valuable)
    -Wsign-conversion \
    -Wshadow \
    -Wcast-align \
    -Wpointer-arith \
    -Wstrict-overflow=5 \   # warn where the optimiser assumes no overflow
    -fno-strict-overflow    # ...or make signed overflow defined (wraps)

# find them at runtime instead
gcc -fsanitize=undefined -fsanitize=signed-integer-overflow
# UBSan reports the exact file, line and values at the moment it happens.
# Run your test suite under it — it costs a few percent and finds real bugs.
