Putting it together: one load instruction

Everything in this track converging on a single instruction. Follow ldr x1, [x0] from fetch to retirement, naming every structure it touches and every way it can fail — and the whole architecture becomes one connected picture.

The complete journey

This final chapter follows one memory access through every mechanism in the track at once. It is the synthesis: nothing here is new, but seeing it assembled is what turns a set of chapters into a working model.

        ldr  x1, [x0]        with x0 = 0xFFFF_0000_C0DE_1234

 ① FETCH                                            chapters 10, 12
      PC → I-TLB → L1 I-cache → the instruction word
      the branch predictor has already guessed the next PC
      FAILS: instruction abort — unmapped, or execute-never

 ② DECODE                                              chapters 03, 07
      fixed 32-bit encoding, decoded in parallel with neighbours
      recognised: 64-bit load, base x0, offset 0
      FAILS: undefined instruction, or trapped by a higher EL

 ③ RENAME / ISSUE                                        chapter 10
      x1 mapped to a fresh physical register
      the instruction waits until x0 is ready

 ④ ADDRESS GENERATION                                    chapter 08
      effective address = x0 + 0
      FAILS: nothing yet

 ⑤ ALIGNMENT CHECK                                       chapter 11
      Device memory → ANY unaligned access faults
      Normal memory → allowed unless SCTLR.A
      FAILS: alignment fault, ESR.DFSC = 0b100001

 ⑥ TRANSLATION                                    chapters 12, 13, 15
      VA[55] == 1 → TTBR1_EL1
      D-TLB lookup, tagged by ASID
        HIT  → PA and attributes in ~1 cycle
        MISS → hardware walks L0 → L1 → L2 → L3
               up to 4 memory accesses, each cacheable
      FAILS: translation fault, DFSC = 0b0001LL
             the LEVEL tells you which table was wrong

 ⑦ PERMISSION CHECK                                      chapter 14
      AP[2:1] vs the current EL and the access type
      UXN / PXN for instruction fetches
      PAN: may EL1 touch this EL0-accessible page right now?
      FAILS: permission fault, DFSC = 0b0011LL

 ⑧ STAGE 2                                               chapter 16
      only if a hypervisor is active
      IPA → PA via VTTBR_EL2, second permission check
      FAILS: exception to EL2, not EL1. HPFAR_EL2 holds the IPA.

 ⑨ MEMORY TYPE                                           chapter 11
      AttrIndx → MAIR_EL1 slot → Normal-WB / Device-nGnRE / …
      shareability from SH[1:0]
      determines: cacheable? speculatable? reorderable?

 ⑩ CACHE                                            chapters 17, 19
      L1 D-cache probe (VIPT — indexed with the VA while the TLB
      produced the tag)
        miss → L2 → cluster L3 → system cache
      coherency maintained across the shareability domain

 ⑪ INTERCONNECT                                          chapter 25
      an AXI/CHI read carrying:
        ADDR = PA
        ID   = the master ID
        PROT[1] = the NS bit          ← TrustZone
        CACHE   = the attributes
      → an SMMU may translate it (non-CPU masters)
      → an XPU may REFUSE it
      FAILS: external abort, DFSC = 0b010000
             — translation SUCCEEDED; the bus said no

 ⑫ MEMORY CONTROLLER → DRAM

 ⑬ RETURN
      a 64-byte line fills L2 and L1
      x1 receives the requested 8 bytes

 ⑭ RETIRE                                                chapter 10
      x1 architecturally updated, IN PROGRAM ORDER
      only NOW is the instruction irrevocable

The distinction that saves the most time

Translation fault versus external abort. A translation fault means the page tables are wrong — a software problem you can fix by reading descriptors. An external abort means translation succeeded, a real bus transaction went out, and something out there refused it — a platform problem: an unclocked peripheral, a powered-down domain, or a firewall.

They send you to completely different parts of the system, and one field in ESR tells you which.

What each step costs

Each step has a price, and they differ by orders of magnitude. Knowing the relative costs is what lets you predict where time goes before measuring.

   TLB hit + L1 hit                      ~4 cycles
   TLB hit + L2 hit                      ~15 cycles
   TLB hit + LLC hit                     ~40 cycles
   TLB hit + DRAM                        ~200 cycles
   TLB MISS + walk cache hit             +10-20 cycles
   TLB MISS + full 4-level walk          +4 memory accesses
   TLB miss + TWO-STAGE walk             up to 24 accesses  (ch. 16)
   plus a page fault to the OS           ~1-5 µs           (minor)
   plus a page fault to DISK             ~100 µs - 10 ms   (major)

  Which is why the whole architecture exists as it does:
     · TLBs, because walks are expensive
     · walk caches, because even a partial walk is expensive
     · huge pages, because TLB reach is the limit
     · the two-register split, because context switches must not
       flush the TLB
     · ASIDs, for the same reason
     · caches at three levels, because DRAM is 50x a register

The parallel picture

Everything above described one access on one core. Running the same picture on several cores at once is where coherence, barriers and contention all enter simultaneously.

One load, and a second core doing the same thing:

   Core 0                          Core 1
   ldr x1, [x0]                    str x2, [x0]
      │                               │
      │ both translate the same VA    │
      │ (same ASID, or a Global page) │
      ▼                               ▼
   L1 D-cache                      L1 D-cache
      │                               │
      └──────── COHERENCY ────────────┘        chapters 17, 19
                MESI over ACE/CHI
                automatic WITHIN the shareability domain
                     │
                     ▼
              same physical line

  Coherency is free. ORDERING is not:                chapters 20, 21
     · these two accesses to the SAME address are coherent and
       ordered — that is guaranteed
     · accesses to DIFFERENT addresses may be observed in any
       order unless you use a barrier or an ordered access

  And ATOMICITY is a third thing again:                 chapter 22
     · read-modify-write needs exclusives or LSE
     · which need SHAREABLE, cacheable memory to work at all

  Three separate guarantees, three separate mechanisms, three
  distinct failure modes. Diagnose which one you have before
  reaching for a fix.

The isolation stack

The same access is also checked by several independent protection mechanisms, each answering a different question. Seeing them stacked explains why a single access can fail in so many distinct ways.

The same load, seen as a security question — "who is allowed to
touch this?"

   ┌──────────────────────────────────────────────────────┐
   │ EL0 application                                       │
   │   constrained by: stage-1 AP bits, UXN                │
   ├──────────────────────────────────────────────────────┤
   │ EL1 kernel                          chapters 14, 26   │
   │   constrained by: PXN, PAN, WXN, and its own tables   │
   ├──────────────────────────────────────────────────────┤
   │ EL2 hypervisor                      chapters 16, 31   │
   │   constrains EL1 via stage 2 and traps                │
   ├──────────────────────────────────────────────────────┤
   │ EL3 secure monitor                                    │
   │   owns SCR_EL3.NS — the security state itself         │
   ├──────────────────────────────────────────────────────┤
   │ MMU / SMMU               translation + permissions    │
   ├──────────────────────────────────────────────────────┤
   │ INTERCONNECT FIREWALL                    chapter 25   │
   │   the last checkpoint: master ID + address + NS bit   │
   ├──────────────────────────────────────────────────────┤
   │ DRAM · peripherals · fuses                            │
   └──────────────────────────────────────────────────────┘

  Every access is checked at least twice: once by the page tables
  (is this VA mapped, and readable?) and once by the interconnect
  (is this MASTER allowed here, in this security state?).

  Fail either and you get a fault — but a DIFFERENT fault, which
  is exactly the distinction above.

  The security track takes this stack apart in detail.

The diagnostic procedure

With the whole path in view, diagnosis becomes a matter of walking it in order rather than guessing. This is that walk, as a procedure.

Given any memory-related failure on ARM:

  1. READ ESR FIRST.
       EC tells you the kind. DFSC tells you the cause.
       0x24 vs 0x25 tells you user vs kernel.        chapter 29

  2. Was there a FAULT at all?
       yes → continue at 3
       no  → this is a coherency, ordering or atomicity problem.
             Which one?                          chapters 19-22
               cores durably disagree  → shareability
               wrong order observed    → barriers
               update lost             → atomics

  3. TRANSLATION fault?
       → the address is not mapped. Check the page tables,
         and check the TLB was invalidated.       chapters 13, 15
       → use AT + PAR_EL1 to ask the hardware.        chapter 12

  4. PERMISSION fault?
       → it IS mapped. Check AP, XN, and PAN.         chapter 14

  5. EXTERNAL abort?
       → translation succeeded. This is a PLATFORM problem:
           · is the peripheral clocked and powered?
           · is the address right?
           · is a firewall denying this master?
         Check clocks FIRST — it is the most common cause and
         the cheapest to rule out.                    chapter 25

  6. SError?
       → imprecise. ELR is meaningless. Use ESB to bisect, and
         read the interconnect's latched error registers.

  7. No fault, wrong DATA?
       → memory type (cached MMIO?), or cache maintenance
         (DMA?).                                 chapters 11, 18

How the chapters connect

This track was written to be read once in order and then never read in order again — after the first pass, the way you will actually use it is by symptom, jumping straight to whichever two or three chapters explain the mechanism behind whatever is in front of you. The reason most rows list several chapters rather than one is that real ARM bugs almost never live in a single mechanism: an MMIO device behaving strangely is usually some combination of the wrong memory type, a missing barrier and a misunderstanding of the interconnect, so the row sends you to all three rather than pretending one chapter is the whole answer.
