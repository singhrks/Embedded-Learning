IRQL

Interrupt Request Level is the single most important concept in Windows kernel programming. It is a per-CPU number that determines what your code is allowed to do, and violating its rules is the cause of most driver bugchecks.

The levels

IRQL is the single most important concept in Windows driver development and has no direct Linux equivalent. It is a per-processor priority level that determines what the processor is currently allowed to be interrupted by — and, as a direct consequence, what your code is allowed to do.

   HIGH_LEVEL        (15)  bugcheck, everything masked
   ...
   CLOCK_LEVEL       (13)  the clock interrupt
   IPI_LEVEL         (14)  inter-processor interrupts
   ...
   DIRQL             (3-12) DEVICE interrupt levels - your ISR
                            runs here
   DISPATCH_LEVEL     (2)  the scheduler and DPCs
   APC_LEVEL          (1)  asynchronous procedure calls
   PASSIVE_LEVEL      (0)  normal thread execution
                                     ^ lowest

  THE RULE THAT DEFINES EVERYTHING:

     Code running at IRQL N can only be interrupted by code at
     IRQL > N, on the same CPU. Code at IRQL N cannot be
     preempted by anything at or below N.

  So raising IRQL MASKS everything at or below it. At
  DISPATCH_LEVEL the scheduler itself cannot run - which is
  why you cannot block, wait, or page fault there.

  THE CRITICAL BOUNDARY IS BETWEEN 1 AND 2:

     <= APC_LEVEL       the scheduler still works.
                        You may block, wait, and touch
                        paged memory.

     >= DISPATCH_LEVEL  the scheduler is masked.
                        NO blocking. NO waiting. NO paged
                        memory. NO page faults.

  Everything else in this chapter follows from that line.
The Linux comparison

IRQL does the job that "context" does in Linux (chapter 02), but as an explicit, readable, settable number rather than an implicit property of how you were called. Roughly: PASSIVE_LEVEL is process context; DISPATCH_LEVEL is softirq context or holding a spinlock; DIRQL is hardirq context. The difference is that Windows lets you query it (KeGetCurrentIrql()) and raise it deliberately, and every API's documentation states the IRQL it requires.

What you may do at each level

Every "No" in this table traces back to the same root cause: at DISPATCH_LEVEL and above, the scheduler is masked, and every one of these operations secretly depends on the scheduler being able to run. Blocking or waiting means suspending the current thread and running a different one — impossible with no scheduler. Touching paged memory means accepting the possibility of a page fault, and servicing a page fault means reading from disk, which means blocking, which loops back to the same problem. A fast mutex and an ERESOURCE are built on the same waiting primitive as an ordinary wait, so they inherit the restriction too. The one row that is "Yes" everywhere — non-paged pool and queuing a DPC — is the tell: those are the only operations the kernel guarantees never need the scheduler, which is exactly why they are the tools you are left with once you are running at an elevated IRQL.

/* THE PAGED MEMORY RULE IS THE SUBTLE ONE.

   Touching paged-out memory takes a page fault. Servicing a
   page fault requires disk I/O, which requires the scheduler
   to block the thread. At DISPATCH_LEVEL the scheduler cannot
   run.

   RESULT: bugcheck 0xA, IRQL_NOT_LESS_OR_EQUAL.

   And it is a LATENT bug: the memory is usually resident, so
   the code works for weeks. Then the machine is under memory
   pressure, the page is evicted, and the driver crashes -
   apparently at random.

   THIS IS WHY Driver Verifier has a "force IRQL checking"
   option that makes every pageable page non-resident, turning
   the latent bug into a reliable one (chapter 22). Use it.  */

Querying and changing IRQL

Most of the time you know your IRQL from context, because the documentation states it for every callback. When you genuinely cannot tell, the system will tell you, and raising or lowering it yourself is occasionally necessary — with one rule that must never be broken.

        KIRQL irql = KeGetCurrentIrql();

        if (irql > DISPATCH_LEVEL)
                return STATUS_INVALID_DEVICE_STATE;

/* RAISING and LOWERING - always paired, always LIFO: */
        KIRQL oldIrql;

        KeRaiseIrql(DISPATCH_LEVEL, &oldIrql);
        /* ... the scheduler cannot run here ... */
        KeLowerIrql(oldIrql);

/* You rarely do this explicitly. Acquiring a spinlock does it
   for you: */
        KIRQL oldIrql;

        KeAcquireSpinLock(&lock, &oldIrql);   /* raises to
                                                 DISPATCH     */
        /* ... critical section ... */
        KeReleaseSpinLock(&lock, oldIrql);    /* restores */

/* Or, when you KNOW you are already at DISPATCH_LEVEL: */
        KeAcquireSpinLockAtDpcLevel(&lock);
        ...
        KeReleaseSpinLockFromDpcLevel(&lock);
/* Cheaper - no IRQL change. Calling it below DISPATCH_LEVEL
   is a bug that Driver Verifier catches.                   */

/* ASSERT IT, in every function whose IRQL matters: */
        NT_ASSERT(KeGetCurrentIrql() == PASSIVE_LEVEL);
        NT_ASSERT(KeGetCurrentIrql() <= DISPATCH_LEVEL);

/* And DOCUMENT it in the function header, the way Microsoft's
   own headers do:

     IRQL_requires_max_(DISPATCH_LEVEL)
     NTSTATUS MyFunction(...);

   Those SAL annotations are checked by static analysis
   (chapter 22) - so an annotated codebase catches IRQL
   violations at BUILD time rather than at run time. That is
   the highest-value habit in this chapter.               */

SAL annotations

The compiler can check much of this for you, if you tell it what your functions expect. These annotations look like noise at first and are in fact the cheapest bug-prevention available in Windows driver work — static analysis uses them to find IRQL violations before the code ever runs.

/* Windows drivers are annotated with SAL - Microsoft's source
   annotation language. Code Analysis reads them and finds
   real bugs statically.                                    */

_IRQL_requires_max_(DISPATCH_LEVEL)
_IRQL_requires_min_(PASSIVE_LEVEL)
_IRQL_requires_(PASSIVE_LEVEL)
_IRQL_raises_(DISPATCH_LEVEL)
_IRQL_saves_                    /* on an out KIRQL parameter */
_IRQL_restores_

_Must_inspect_result_
_Check_return_

_In_            /* input, must be valid */
_Out_           /* output, written by the callee */
_Inout_
_In_opt_        /* may be NULL */
_In_reads_bytes_(n)
_Out_writes_bytes_(n)

_Requires_lock_held_(lock)
_Acquires_lock_(lock)
_Releases_lock_(lock)

/* A realistic annotated declaration: */
_IRQL_requires_max_(DISPATCH_LEVEL)
_Must_inspect_result_
NTSTATUS
MyQueueRequest(
        _In_ PMY_DEVICE Device,
        _In_reads_bytes_(Length) PVOID Buffer,
        _In_ SIZE_T Length
        );

/* WHY BOTHER: Code Analysis will then tell you, at compile
   time, that you called this from a DIRQL ISR, or ignored its
   return value, or passed a buffer shorter than Length. Those
   are exactly the bugs that otherwise become bugchecks on a
   customer machine.

   ANNOTATE AS YOU WRITE. Retrofitting SAL to an existing
   driver is tedious; adding it to a new function costs
   seconds.                                                */

The bugchecks IRQL causes

Getting IRQL wrong does not produce a subtle misbehaviour; it produces one of a small set of very recognisable blue screens. Learning to read these three by name means you often know the cause before opening the dump.

/* --- 0x0A  IRQL_NOT_LESS_OR_EQUAL --------------------------
   The most common driver bugcheck by a wide margin.

   MEANS: memory was touched at too high an IRQL. Either the
   memory is paged out, or the address is garbage.

   Parameters:
     1  the address referenced
     2  the IRQL at the time
     3  0 = read, 1 = write, 8 = execute
     4  the instruction address

   PARAMETER 2 IS THE DIAGNOSIS. If it is 2 or higher and the
   address looks plausible, you touched paged memory at
   DISPATCH_LEVEL. If the address is near zero, it is a NULL
   dereference that happens to have occurred at high IRQL. */

/* --- 0xD1  DRIVER_IRQL_NOT_LESS_OR_EQUAL ------------------
   The same thing, but the faulting code was identified as a
   driver. Same parameters. Parameter 4 names YOUR function.

/* --- 0xC4  DRIVER_VERIFIER_DETECTED_VIOLATION -------------
   Verifier caught an IRQL rule violation before it became a
   crash. The subcode says which rule (chapter 22).

/* --- 0x1E  KMODE_EXCEPTION_NOT_HANDLED --------------------
   An unhandled exception - often an access violation at high
   IRQL.

/* --- 0x7E  SYSTEM_THREAD_EXCEPTION_NOT_HANDLED ------------
   Same, in a system thread.

/* --- 0x133 DPC_WATCHDOG_VIOLATION -------------------------
   A DPC ran for more than ~20 microseconds too long, or the
   system stayed at DISPATCH_LEVEL for more than ~10 seconds.
   MEANS: your DPC is doing far too much work
   (chapter 11).                                          */

/* READING ONE in WinDbg (chapter 23): */
        !analyze -v
        .bugcheck
        kb                    /* the stack */
        !irql                 /* the IRQL at crash time */

Patterns that keep you correct

Rather than reasoning about IRQL afresh on every function, experienced driver authors follow a handful of habits that make violations structurally difficult. These are those habits.

/* 1. KNOW WHICH IRQL YOUR CALLBACK RUNS AT. Every framework
      callback documents it. Memorise the common ones:      */

        DriverEntry                      PASSIVE_LEVEL
        EvtDriverDeviceAdd               PASSIVE_LEVEL
        EvtDevicePrepareHardware         PASSIVE_LEVEL
        EvtDeviceD0Entry                 PASSIVE_LEVEL
        EvtIoRead / EvtIoWrite           <= DISPATCH_LEVEL
        EvtIoDeviceControl               <= DISPATCH_LEVEL
        EvtInterruptIsr                  DIRQL
        EvtInterruptDpc                  DISPATCH_LEVEL
        EvtWorkItem                      PASSIVE_LEVEL
        EvtTimerFunc                     DISPATCH_LEVEL
        EvtCleanupCallback               <= DISPATCH_LEVEL

/* 2. IF YOU NEED PASSIVE_LEVEL FROM A HIGHER ONE, queue a
      WORK ITEM (chapter 11). You cannot simply lower IRQL to
      escape - lowering below where you were called is a
      serious bug.

/* 3. MARK CODE PAGEABLE ONLY IF IT RUNS AT PASSIVE_LEVEL: */

        #pragma alloc_text(INIT,  DriverEntry)
        #pragma alloc_text(PAGE,  MyDeviceAdd)
        #pragma alloc_text(PAGE,  MyPrepareHardware)

        NTSTATUS MyDeviceAdd(...)
        {
                PAGED_CODE();     /* ASSERTS PASSIVE_LEVEL -
                                     put this at the top of
                                     every PAGE function     */
                ...
        }

   INIT   discarded after boot (like Linux's __init)
   PAGE   pageable
   .text  always resident - the default

/* PAGED_CODE() costs nothing in a release build and catches
   the mistake immediately in a checked one. Use it in every
   pageable function without exception.

/* 4. NON-PAGED DATA for anything touched above PASSIVE: */
        ExAllocatePool2(POOL_FLAG_NON_PAGED, size, 'GATd');
   and never a global marked with #pragma data_seg("PAGE").

/* 5. THE ONE-LINE HABIT that prevents most of this: before
      writing any line that touches memory or calls an API,
      ask "what IRQL am I at?" If you cannot answer instantly,
      look at the callback that got you here.             */

IRQL and spinlocks

Spinlocks and IRQL are two aspects of one mechanism, which is why they are easy to confuse. Acquiring a spinlock raises your IRQL, so a lock is not only mutual exclusion — it silently changes what the code inside it may do.

/* A spinlock protects data; raising IRQL protects against
   PREEMPTION. Windows combines them because you almost always
   need both.                                               */

/* Data shared between PASSIVE code and a DPC: */
        KeAcquireSpinLock(&d->Lock, &oldIrql);
        /* now at DISPATCH_LEVEL: the DPC cannot run on this
           CPU, and the spinlock excludes other CPUs        */
        ...
        KeReleaseSpinLock(&d->Lock, oldIrql);

/* Data shared with an ISR - the spinlock must be acquired at
   the DEVICE's IRQL, or the ISR can interrupt you while you
   hold it and deadlock (exactly the Linux spinlock
   self-deadlock, chapter 12):                             */
        KeAcquireInterruptSpinLock(interrupt, &oldIrql);
        ...
        KeReleaseInterruptSpinLock(interrupt, oldIrql);

/* In WDF this is: */
        WdfInterruptAcquireLock(interrupt);
        ...
        WdfInterruptReleaseLock(interrupt);

/* THE RULES:
     · a spinlock section runs at DISPATCH_LEVEL or higher, so
       everything forbidden at DISPATCH_LEVEL is forbidden
       inside it - no paged memory, no blocking, no
       paged-pool allocation
     · keep it SHORT. Other CPUs spin.
     · never acquire a lower-IRQL lock while holding a
       higher-IRQL one
     · the `oldIrql` variable must be LOCAL. Sharing one
       between CPUs corrupts the IRQL restore.            */
