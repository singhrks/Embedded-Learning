Thread pools, work queues and work stealing

Creating a thread costs about as much as ten thousand mutex operations, so you create them once and feed them work. That single decision brings its own set of problems: how many threads, what happens when the queue fills, and the deadlock that every pool eventually hits.

The shape

Creating a thread per unit of work does not scale, for reasons the cost discussion in chapter 1 already established. A pool separates the expensive thing — having threads — from the cheap thing — having work.

   submit(task) ---> +---------------------------+
                     |      TASK QUEUE           |
                     +---------------------------+
                        |        |        |
                     +--v--+  +--v--+  +--v--+
                     | W 0 |  | W 1 |  | W 2 |    N workers,
                     +-----+  +-----+  +-----+    created once

   Each worker:
        for (;;) {
                task = queue.pop();     /* blocks when empty  */
                if (!task) break;       /* shutdown sentinel  */
                task();
        }

   WHAT THE POOL BUYS
     * thread creation cost paid once, not per task
     * a bound on concurrency - N threads, not N-thousand
     * a natural place to apply backpressure
     * warm caches: a worker keeps running the same code

   WHAT IT COSTS
     * the queue is a contention point
     * a blocking task occupies a worker doing nothing
     * thread-local state now belongs to the WORKER, not the
       task (chapter 2)
     * and the deadlock in the "recursion" section below

How many threads

How many threads a pool should hold has a real answer, and it differs sharply depending on whether the work is CPU-bound or blocks on I/O. Using the wrong formula wastes either cores or memory.

/* THE ONLY TWO RULES YOU NEED */

/* CPU-BOUND work: N = number of cores.
   More threads do not create more CPU; they add context
   switches and cache pressure. */
        unsigned n = std::thread::hardware_concurrency();
        /* subtract one if the main thread also works */

/* I/O-BOUND work: N = cores / (1 - blocked_fraction)
   A thread blocked 90% of the time uses 10% of a core, so
   you need ~10x more threads to keep the cores busy. */

        /* measured: each task spends 45 ms waiting, 5 ms
           computing -> blocked_fraction = 0.9
           8 cores / (1 - 0.9) = 80 threads               */

/* AND THE REAL ADVICE: if the answer is "80 threads", you
   probably want async I/O and a small pool instead
   (chapter 18). Eighty stacks is 640 MB of reserved address
   space and eighty things for the scheduler to consider. */

/* MIXED WORKLOADS: use SEPARATE POOLS, sized differently.
   One CPU pool of `cores` threads, one I/O pool of many.
   A single pool sized for I/O will thrash on CPU work; sized
   for CPU it will stall on I/O.                          */

/* MEASURE, do not calculate:
     * are all workers busy?         -> add threads
     * are cores idle with work queued?  -> workers are
                                            blocking
     * is throughput flat but latency rising? -> the queue is
                                            growing; you are
                                            past capacity     */

A pool, complete

A pool is a queue plus some workers, and nearly all of the difficulty is in the queue — specifically in how workers wait when it is empty and how the pool shuts down without losing work.

#include <thread>
#include <mutex>
#include <condition_variable>
#include <deque>
#include <functional>
#include <future>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(unsigned n, size_t max_queue = 4096)
        : max_(max_queue)
    {
        for (unsigned i = 0; i < n; i++)
            workers_.emplace_back([this] { run(); });
    }

    ~ThreadPool() { shutdown(); }

    /* Returns a future, so the caller can wait for a result -
       and, crucially, so an exception in the task surfaces at
       get() instead of calling std::terminate. */
    template <class F>
    auto submit(F f) -> std::future<decltype(f())>
    {
        using R = decltype(f());
        auto task = std::make_shared<std::packaged_task<R()>>(
                        std::move(f));
        auto fut = task->get_future();
        {
            std::unique_lock<std::mutex> lk(m_);

            /* BACKPRESSURE. An unbounded queue is not a
               feature - it converts "too slow" into "out of
               memory", much later, somewhere else. */
            not_full_.wait(lk, [this] {
                    return q_.size() < max_ || stop_; });
            if (stop_) throw std::runtime_error("pool stopped");

            q_.emplace_back([task] { (*task)(); });
        }
        not_empty_.notify_one();
        return fut;
    }

    void shutdown()
    {
        { std::lock_guard<std::mutex> g(m_);
          if (stop_) return;
          stop_ = true; }
        not_empty_.notify_all();      /* release every waiter  */
        not_full_.notify_all();
        for (auto &t : workers_)      /* THEN join. Signal all,
            if (t.joinable()) t.join();  then join all
                                         (chapter 3).          */
        workers_.clear();
    }

private:
    void run()
    {
        for (;;) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lk(m_);
                not_empty_.wait(lk, [this] {
                        return !q_.empty() || stop_; });
                if (q_.empty()) return;     /* stopping, drained */
                task = std::move(q_.front());
                q_.pop_front();
            }
            not_full_.notify_one();

            /* A task that throws must not kill the worker, or
               the pool silently shrinks to zero and everything
               hangs. packaged_task captures the exception into
               the future; this catch is the belt to that
               braces. */
            try { task(); }
            catch (...) { /* log it */ }
        }
    }

    std::mutex                        m_;
    std::condition_variable           not_empty_, not_full_;
    std::deque<std::function<void()>> q_;
    std::vector<std::thread>          workers_;
    size_t                            max_;
    bool                              stop_ = false;
};
The deadlock every pool eventually hits

A task submits another task to the same pool and waits for it. With N workers, N such tasks occupy every worker, and the sub-tasks they are waiting for can never be scheduled. The pool is full of threads waiting for work that cannot start. It works fine in testing with one request and deadlocks under load.

/* THE DEADLOCK */
pool.submit([&] {
        auto f = pool.submit([] { return part_two(); });
        return part_one() + f.get();     /* <-- waits, holding
                                            a worker            */
});

/* FIXES, in order of preference:

   1. DO NOT BLOCK IN A TASK. Restructure so the continuation
      is itself a task, triggered by completion. This is what
      async/await and future.then() are for (chapter 18).

   2. SEPARATE POOLS. Parent tasks in pool A, children in
      pool B. The cycle is broken because they are different
      resources - the same reasoning as lock ordering.

   3. HELP WHILE WAITING. The waiting thread runs queued tasks
      instead of blocking. This is what work-stealing runtimes
      (TBB, Rayon, Go, .NET) do, and it is why they tolerate
      nested parallelism. Note it changes the semantics: your
      task can now be re-entered on the same thread.

   4. AN UNBOUNDED POOL that grows when all workers block.
      .NET's injection heuristic. Effective, and it makes
      thread counts unpredictable.                          */

Work stealing

A single shared queue becomes a bottleneck as workers multiply. Giving each worker its own queue and letting idle workers take from busy ones removes that, and is how most modern task systems are built.

   ONE SHARED QUEUE
     every pop contends on one lock and one cache line. With
     many short tasks the queue IS the bottleneck.

   PER-WORKER DEQUES + STEALING
     Each worker owns a double-ended queue.

       own work:  push and pop at the BOTTOM  (LIFO)
       stealing:  other workers take from the TOP (FIFO)

     +--------+   +--------+   +--------+
     | W0 [==]|   | W1 [  ]|   | W2 [==]|
     +---^----+   +---^----+   +--------+
         |            |
      pop bottom   empty -> steal from the top of a random
      (hot, LIFO)  victim's deque

   WHY LIFO FOR YOUR OWN WORK
     the most recently pushed task is the most recently
     touched data - it is still in L1. Depth-first execution
     also bounds memory: you finish subtrees before starting
     new ones.

   WHY FIFO FOR STEALING
     the oldest task is the largest remaining subtree, so one
     steal transfers a lot of work. And the top is far from
     the bottom, so the owner and the thief rarely touch the
     same cache line.

   WHY IT SCALES
     in the common case a worker never synchronises with
     anyone. Stealing happens only when a worker runs dry,
     which under good load balance is rare.

   Used by: Cilk, Intel TBB, Java ForkJoinPool, Rust's Rayon,
   Go's scheduler, .NET's ThreadPool.
Thread-local state belongs to the worker, not the task

A thread_local holding "the current request id" is set by task 1 and still there when unrelated task 2 runs on the same worker. With work stealing it is worse: a task can migrate mid-tree, so even "the same task" may see different thread-local state. Either clear it at every task boundary, or pass context explicitly. This is a common source of logs attributing work to the wrong request.
