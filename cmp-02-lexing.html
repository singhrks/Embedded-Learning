Lexical analysis

Turning a stream of characters into a stream of tokens. The simplest phase of a compiler, and the one whose rules produce the most surprising error messages when you break them.

What a token is

   SOURCE:      int count = x + 42;   /* a comment */

   TOKENS:
      KEYWORD      "int"
      IDENTIFIER   "count"
      PUNCTUATOR   "="
      IDENTIFIER   "x"
      PUNCTUATOR   "+"
      NUMBER       "42"        value 42, type int
      PUNCTUATOR   ";"
      (the comment is discarded, replaced by one space)

   EACH TOKEN CARRIES:
      a KIND
      the TEXT (its "spelling")
      a SOURCE LOCATION - file, line, column
      for literals, a computed VALUE and TYPE

   THE SOURCE LOCATION is why error messages can point at the
   right character, and why it must be preserved all the way
   through the front end. A compiler that loses it produces
   the "error somewhere in this file" diagnostics that older
   toolchains were notorious for.

   C's TOKEN CATEGORIES (C11 6.4):
      keywords          int, if, while, _Atomic, ...
      identifiers       count, printf, _my_var
      constants         42, 0x2A, 3.14, 'c', 1e-9
      string literals   "hello"
      punctuators       + - * / = == { } [ ] ; ...
      header names      <stdio.h>  (only after #include)

The maximal munch rule

/* THE RULE: at each point, take the LONGEST sequence of
   characters that forms a valid token. Greedily, without
   looking at whether the result makes sense.              */

        x+++y

/* Munched maximally: */
        x  ++  +  y        -> (x++) + y
/* NOT: */
        x  +  ++y

/* AND THE FAMOUS ONE: */
        a = b //*divide*/c;
             ^^
/* `//` starts a line comment in C99 and later, so this is: */
        a = b;
/* In C89, where // was not a comment, it was: */
        a = b / c;
/* The same source, two meanings, decided by the standard
   version. Real code was broken by this transition.      */

/* THE DIVISION TRAP: */
        int x = a /*p;      /* `/*` opens a comment! */
/* intended: a divided by *p. Write it as: */
        int x = a / *p;
        int x = a / (*p);

/* AND IN C++ BEFORE C++11: */
        vector<vector<int>> v;
                        ^^
/* `>>` munched as the right-shift operator, not two closing
   angle brackets. You had to write `> >`. C++11 special-cased
   it - which tells you the rule is a genuine design tension,
   not a curiosity.                                        */

/* THE PRACTICAL LESSON: whitespace is not decoration. When an
   expression parses strangely, add spaces between operators
   and look again.                                          */

The translation phases

C defines EIGHT translation phases, in order (C11 5.1.1.2).
Knowing them explains several otherwise baffling behaviours:

  1. Map physical characters to the source character set.
     Replace trigraphs (??= for #). Removed in C23.

  2. DELETE backslash-newline pairs - LINE SPLICING.
     Happens BEFORE tokenising, which is why:

         int x = 1; \
         int y = 2;

     is one line, and why a stray space AFTER the backslash
     breaks a macro continuation with a confusing error.

  3. Decompose into PREPROCESSING TOKENS and whitespace.
     Each comment becomes one space.

  4. Execute PREPROCESSING DIRECTIVES and expand macros.
     #include files are processed recursively through phases
     1-4.

  5. Convert escape sequences in character and string
     literals.

  6. CONCATENATE ADJACENT STRING LITERALS:
         "hello" " " "world"   ->   "hello world"
     which is why this works:
         #define PREFIX "app: "
         puts(PREFIX "started");

  7. Convert preprocessing tokens to TOKENS. Syntax and
     semantic analysis. -> a translation unit

  8. Resolve external references. LINK. -> a program

  PHASES 1-6 ARE THE PREPROCESSOR. Phase 7 is the compiler
  proper. Phase 8 is the linker (chapter 12).

  THE CONSEQUENCE PEOPLE MEET: the preprocessor operates on
  PREPROCESSING TOKENS, which are not quite tokens. A number
  like 0x1p+3 is one pp-number even though it would not be a
  valid integer, which is why some macro tricks work and
  others produce "invalid suffix" errors.

The hard cases

/* --- 1. IS IT A TYPE OR A VARIABLE? --------------------- */
        foo * bar;
/* This is EITHER:
     a declaration: `bar` is a pointer to `foo`
     an expression: `foo` multiplied by `bar`
   depending on whether `foo` is a typedef name.

   THE LEXER CANNOT KNOW. It must ask the symbol table, which
   is built by the parser. This is "the lexer hack": C
   compilers feed type information BACKWARDS from the parser
   to the lexer, so it can emit TYPEDEF_NAME or IDENTIFIER.

   This is why C's grammar is not context-free, and why
   `typedef` makes C genuinely harder to parse than languages
   that spell declarations differently.                    */

/* --- 2. NUMERIC LITERALS -------------------------------- */
        42          int
        42u         unsigned
        42l  42L    long
        42ull       unsigned long long
        0x2A        hex
        052         OCTAL - leading zero! A classic bug:
                    permissions written as 0644 are octal
                    (correct), but a zero-padded decimal like
                    0100 is 64, not 100.
        0b101010    binary - a GNU extension, standard in C23
        1'000'000   digit separators (C++14, C23)
        3.14        double
        3.14f       float
        1e-9        double
        0x1.8p3     hex float: 1.5 * 2^3 = 12.0

/* --- 3. CHARACTER AND STRING ESCAPES -------------------- */
        '\n' '\t' '\\' '\'' '\0'
        '\x41'      hex - CONSUMES AS MANY HEX DIGITS AS IT
                    CAN, so "\x41BC" is ONE character with
                    value 0x41BC (implementation-defined
                    overflow), not 'A' followed by "BC".
                    Write "\x41" "BC" instead.
        '\101'      octal - exactly up to three digits
        u8"..."     UTF-8
        L"..."      wide
        R"(raw)"    raw string (C++)

/* --- 4. THE `>>` AND `<:` DIGRAPHS ---------------------- */
        <: :> <% %> %: %:%:
/* alternative spellings of [ ] { } # ## for keyboards
   lacking those characters. Still in the standard. They very
   occasionally surprise someone using `<:` in a template
   argument.                                               */
The octal trap is a real embedded bug

#define TIMEOUT_MS 0100 is 64, not 100. It appears in configuration constants, in zero-padded register values copied from a datasheet table, and in permission masks where octal was intended but the reader does not realise. Never zero-pad a decimal constant, and when you do mean octal, use 0o (C23) or a comment.

Writing one

/* Lexers are simple enough to write by hand, and most
   production compilers do - it is faster and gives better
   error messages than a generated one.                    */

typedef enum {
        TOK_EOF, TOK_IDENT, TOK_NUMBER, TOK_STRING,
        TOK_PLUS, TOK_MINUS, TOK_STAR, TOK_SLASH,
        TOK_LPAREN, TOK_RPAREN, TOK_SEMI, TOK_EQ, TOK_EQEQ,
        TOK_KEYWORD_IF, TOK_KEYWORD_WHILE, /* ... */
} TokenKind;

typedef struct {
        TokenKind kind;
        const char *start;      /* into the source buffer */
        size_t      length;
        int         line, column;
        union { long ival; double dval; };
} Token;

static Token next_token(Lexer *lx)
{
        skip_whitespace_and_comments(lx);

        if (at_end(lx))
                return make(lx, TOK_EOF);

        char c = advance(lx);

        /* identifiers and keywords */
        if (isalpha(c) || c == '_') {
                while (isalnum(peek(lx)) || peek(lx) == '_')
                        advance(lx);
                /* look it up in a keyword table - a perfect
                   hash, or just a sorted bsearch           */
                return make_ident_or_keyword(lx);
        }

        /* numbers */
        if (isdigit(c))
                return scan_number(lx);

        /* strings */
        if (c == '"')
                return scan_string(lx);

        /* MAXIMAL MUNCH on operators: check the longest
           first                                            */
        switch (c) {
        case '=':
                if (match(lx, '=')) return make(lx, TOK_EQEQ);
                return make(lx, TOK_EQ);
        case '+': return make(lx, TOK_PLUS);
        case '(': return make(lx, TOK_LPAREN);
        ...
        }

        return error_token(lx, "unexpected character");
}

/* NOTE `start` and `length` POINT INTO THE SOURCE rather than
   copying the text. That is how real compilers avoid
   allocating a string per token, and it is why the source
   buffer must outlive the tokens.

   THE OTHER PRODUCTION DETAIL: a keyword is just an
   identifier whose spelling is in a table. Do not write a
   separate scanner for each.                             */

Generated lexers

/* flex / lex - a regular expression per token kind: */

%%
[ \t\n]+                { /* skip */ }
"/*"([^*]|\*[^/])*"*/"  { /* comment */ }
"if"                    { return TOK_IF; }
"while"                 { return TOK_WHILE; }
[a-zA-Z_][a-zA-Z0-9_]*  { return TOK_IDENT; }
[0-9]+                  { yylval.ival = atol(yytext);
                          return TOK_NUMBER; }
"=="                    { return TOK_EQEQ; }
"="                     { return TOK_EQ; }
"+"                     { return TOK_PLUS; }
.                       { return TOK_ERROR; }
%%

/* flex compiles these into a DFA - a state machine that
   consumes one character per step, in constant time. That is
   why lexing is linear and fast.

   THE RULE ORDER MATTERS: flex prefers the longest match, and
   among equal-length matches, the rule listed FIRST. So
   keywords must come before the identifier rule, or every
   keyword lexes as an identifier.

/* WHEN TO USE A GENERATOR: prototypes, small languages,
   configuration file parsers. For a production compiler,
   hand-written wins on error messages, on incremental
   re-lexing for an IDE, and on the context sensitivity C
   needs anyway.                                            */
