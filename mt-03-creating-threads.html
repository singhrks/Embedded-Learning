Creating, joining and cancelling threads

Starting a thread is three lines in any language. Ending one correctly is where the bodies are buried: lifetimes that outlive the data they point at, detached threads still running during static destruction, and cancellation, which is almost always the wrong tool.

The same idea, four spellings

Three interfaces, one underlying mechanism. Which you use is mostly a matter of language and portability, and the differences that matter are in error handling and in what happens if you forget to clean up.

/* POSIX */
#include <pthread.h>

static void *worker(void *arg)
{
        int id = *(int *)arg;
        printf("worker %d\n", id);
        return (void *)(intptr_t)(id * 2);      /* the result  */
}

int main(void)
{
        pthread_t t;
        int id = 7;

        /* &id is a pointer to a LOCAL. Safe only because we
           join before main's frame goes away. See below.     */
        if (pthread_create(&t, NULL, worker, &id) != 0)
                return 1;      /* returns errno, does NOT set it */

        void *ret;
        pthread_join(t, &ret);
        printf("result %d\n", (int)(intptr_t)ret);
        return 0;
}
// C++11 and later - the same thing, with types and RAII
#include <thread>
#include <future>

int worker(int id) { return id * 2; }

int main()
{
    std::thread t(worker, 7);   // arguments are COPIED by value
    t.join();                   // or t.detach() - one or the
                                // other, or std::terminate

    // When you want a result, do not hand-roll it:
    std::future<int> f = std::async(std::launch::async, worker, 7);
    int result = f.get();       // blocks, and rethrows any
                                // exception the worker threw
}

// std::jthread (C++20) joins in its destructor and carries a
// stop_token. It is what std::thread should have been.
#include <stop_token>
std::jthread jt([](std::stop_token st) {
    while (!st.stop_requested()) { /* work */ }
});
// no join needed: the destructor requests stop, then joins.
// Rust - the lifetime problem solved by the type system
use std::thread;

let data = vec![1, 2, 3];
let h = thread::spawn(move || {          // `move` transfers
    data.iter().sum::<i32>()             // ownership in
});                                      // -- no dangling
let total: i32 = h.join().unwrap();      // possible

// Borrowing across threads needs a SCOPE, which guarantees
// the threads end before the borrow does (Rust 1.63+):
let v = vec![1, 2, 3];
thread::scope(|s| {
    s.spawn(|| println!("{:?}", &v));    // borrow is fine:
    s.spawn(|| println!("{}", v.len())); // scope joins all
});                                      // before returning
/* Windows */
#include <windows.h>
#include <process.h>

static unsigned __stdcall worker(void *arg)
{
        return (unsigned)(uintptr_t)arg * 2;
}

int main(void)
{
        /* _beginthreadex, NOT CreateThread, for anything that
           touches the CRT: it allocates the per-thread CRT
           state that errno, strtok and friends need.         */
        uintptr_t h = _beginthreadex(NULL, 0, worker,
                                     (void *)(uintptr_t)7, 0, NULL);
        WaitForSingleObject((HANDLE)h, INFINITE);

        DWORD code = 0;
        GetExitCodeThread((HANDLE)h, &code);
        CloseHandle((HANDLE)h);        /* a HANDLE is a resource;
                                          leaking it leaks the
                                          thread object          */
        return 0;
}
Join or detach — there is no third option

Every thread you create holds resources until someone collects it. join waits and collects; detach says "collect yourself when you finish". Do neither and you leak a thread control block per thread, which on a long-running server is a slow death. C++ chose to make this loud: ~std::thread on a joinable thread calls std::terminate, deliberately, so the bug is a crash rather than a leak.

The lifetime bug

A thread outliving the data it refers to is the most common source of crashes in threaded programs, and it happens because the creating function returned while the thread was still running.

   THE MISTAKE

     void start(void)
     {
             int id = 7;                     // on start's stack
             pthread_t t;
             pthread_create(&t, NULL, worker, &id);
             pthread_detach(t);
     }                                       // frame destroyed
                                             // HERE
     worker() now reads &id -> whatever the next call put there

   The window is tiny and the value is often still correct,
   which is what makes it survive testing.

   THREE FIXES

   1. JOIN before the frame ends.
        pthread_join(t, NULL);   // id is alive until here

   2. HEAP-ALLOCATE the argument, worker frees it.
        struct arg *a = malloc(sizeof *a);
        a->id = 7;
        pthread_create(&t, NULL, worker, a);
        // worker: ... free(a);
        // and if pthread_create FAILS, free it yourself

   3. PASS BY VALUE where the API allows.
        pthread_create takes void*, so you can smuggle an int:
        pthread_create(&t, NULL, worker, (void *)(intptr_t)7);
        Legal, ugly, and it does not scale past one small value.

   C++ picks fix 3 by default - std::thread COPIES its
   arguments - which is why passing a reference needs the
   explicit std::ref(), and why doing so reintroduces the bug.

   Rust picks fix 1 and 2 and makes the compiler check, which
   is the entire point of `move` and thread::scope.

Cancellation, and why you should not

Stopping a thread from outside is far harder than starting one, because it may be holding a lock or halfway through modifying shared state. The mechanisms reflect that, and the safest approach avoids them entirely.

/* POSIX cancellation exists. Almost every use of it is wrong. */

    pthread_cancel(t);          /* politely ask                */

/* What actually happens depends on two per-thread settings:

     PTHREAD_CANCEL_DEFERRED   (default)
       the thread dies at the next CANCELLATION POINT - a list
       of ~100 functions including read, write, sleep, wait,
       printf, malloc-sometimes. Between them it is immune.

     PTHREAD_CANCEL_ASYNCHRONOUS
       the thread dies at literally any instruction. Which
       means it can die holding a mutex, halfway through a
       malloc, with a file half-written. Almost nothing is
       async-cancel-safe. Do not use this.

   Even deferred cancellation leaves you needing cleanup
   handlers for every resource:                              */

static void *worker(void *arg)
{
        char *buf = malloc(1024);
        pthread_cleanup_push(free, buf);       /* runs on cancel */

        pthread_mutex_lock(&m);
        pthread_cleanup_push(unlock_helper, &m);

        read(fd, buf, 1024);                   /* cancellation
                                                  point         */
        pthread_cleanup_pop(1);                /* unlock         */
        pthread_cleanup_pop(1);                /* free           */
        return NULL;
}

/* And in C++ this is worse than it looks: on glibc, cancellation
   is implemented by throwing a special exception through your
   frames. A `catch (...)` that does not rethrow swallows it and
   the thread refuses to die.                                 */
Use a stop flag instead. Always.

Cooperative cancellation is simpler, portable, testable and correct: an atomic flag the worker checks at points it chooses, so it is never interrupted mid-invariant. Every modern design does this — std::stop_token, Rust channels, Go's context, .NET's CancellationToken. The only thing pthread_cancel gives you is the ability to interrupt a blocking syscall, and the right answer there is a self-pipe, an eventfd, or a timeout.

/* The pattern to use, in full. */

struct worker {
        atomic_bool     stop;
        int             wake_fd[2];   /* self-pipe            */
        pthread_t       tid;
};

static void *run(void *arg)
{
        struct worker *w = arg;
        struct pollfd fds[2] = {
                { .fd = w->sock,        .events = POLLIN },
                { .fd = w->wake_fd[0],  .events = POLLIN },
        };

        while (!atomic_load_explicit(&w->stop, memory_order_relaxed)) {
                if (poll(fds, 2, -1) < 0) {
                        if (errno == EINTR) continue;
                        break;
                }
                if (fds[1].revents)      /* woken to stop      */
                        break;
                handle(w->sock);         /* never interrupted
                                            mid-operation       */
        }
        cleanup(w);                      /* ordinary code, no
                                            cleanup handlers    */
        return NULL;
}

void worker_stop(struct worker *w)
{
        atomic_store_explicit(&w->stop, true, memory_order_relaxed);
        write(w->wake_fd[1], "x", 1);    /* break the poll     */
        pthread_join(w->tid, NULL);      /* and WAIT for it    */
}

/* The join at the end is not optional. "I set the flag" is not
   "it has stopped", and shutting down while a worker still
   touches your data is the commonest shutdown crash there is. */

Shutdown order

Getting threads to stop cleanly at program exit is rarely designed and usually discovered as a crash during teardown. A deliberate shutdown protocol is much simpler than debugging the alternative.

   The rule: a thread must not outlive anything it points at.

   BAD, and extremely common:

     main() returns
       -> static destructors run
       -> a detached worker wakes up
       -> touches a logger that no longer exists
       -> crash during exit, in a stack trace that makes no
          sense because the frames are gone

   THE ORDER THAT WORKS

     1. tell every worker to stop        (set flags, wake them)
     2. JOIN every worker                (now none are running)
     3. tear down what they used         (queues, loggers, pools)
     4. return from main

   Steps 1 and 2 are separate for a reason: signalling all of
   them before joining any of them means shutdown takes as long
   as the slowest worker, not the sum of all of them.

   AND NOTE: detached threads cannot be joined, so a design
   with detached threads has NO correct shutdown. That is the
   real argument against detach - not the leak.
