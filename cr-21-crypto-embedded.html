Cryptography in embedded systems

Everything in this track, applied to a device with 256 KB of RAM, no clock, a physically accessible attacker and a fifteen-year service life. The closing chapter: what to choose, what it costs, and what actually goes wrong in shipped products.

What makes embedded different

Everything in this track assumed adequate memory, a good random source and time to spare. Embedded devices frequently have none of those, and the choices change accordingly.

   THE CONSTRAINTS

   MEMORY        20-40 KB of RAM for one TLS session; a
                 whole MCU may have 64 KB. RAM, not CPU, is
                 usually what stops you.
   FLASH         a TLS stack is 60-100 KB. On a 256 KB part
                 that is a third of your budget.
   POWER         a battery device may have a lifetime energy
                 budget. Every handshake costs measurable
                 charge.
   NO CLOCK      no RTC, or one that resets. Certificate
                 dates cannot be checked (chapter 16).
   NO ENTROPY    at first boot, before any peripheral has
                 produced noise (chapter 02).
   NO UPDATES    or updates that many units never take.
   BANDWIDTH     a 127-byte 802.15.4 frame; a LoRa payload
                 measured in tens of bytes.
   LIFETIME      15-20 years. Longer than the algorithms.

   THE THREAT MODEL

   THE ATTACKER OWNS THE HARDWARE. They can:
     · read the external flash with a $20 clip
     · probe the buses
     · glitch the power and clock (chapter 19)
     · decapsulate the die
     · buy a hundred units and destroy ninety-nine
     · and take as long as they like

   AND THE ECONOMICS: BREAK ONE, BREAK ALL. If the key is the
   same in every unit, one extraction is a product-wide
   compromise, permanently, with no way to recall. This is
   the single fact that should drive every design decision
   in this chapter.

   SO: PER-DEVICE KEYS, GENERATED ON-DEVICE, HELD IN
   HARDWARE (chapter 18). Everything else is secondary.

Picking the algorithms

Given tight constraints, algorithm choice is driven by what the hardware accelerates and what fits in the available memory — while staying inside the set that is actually secure.

/* AND THE FIRST QUESTION, BEFORE ANY OF THAT:

     WHAT DOES THE SILICON ALREADY HAVE?

   Read the TRM's security chapter before choosing anything.
   Most modern MCUs have more than developers use:

     AES engine (often with GCM/CCM modes)
     SHA accelerator
     a true RNG
     a PKA / ECC accelerator
     a hardware-only key slot wired into the AES engine
     a unique device ID
     OTP fuses
     a tamper or glitch detector
     a monotonic counter

   USING THE ACCELERATOR IS 10-50x FASTER AND USUALLY MORE
   SIDE-CHANNEL RESISTANT than your software implementation.
   And the hardware key slot means the key never enters
   CPU-addressable memory at all - which is worth more than
   any amount of careful C.

   THE INTEGRATION POINT: mbedTLS ALT implementations
   (MBEDTLS_AES_ALT and friends), or the PSA Crypto API,
   which is the modern way - you ask for "an AES-GCM
   operation with key handle 3" and the implementation routes
   it to hardware or software as available. WRITE AGAINST
   PSA CRYPTO if your stack supports it; it makes the
   hardware/software choice a build-time concern instead of
   a code change.                                         */

What it costs

Cryptography costs time and energy, both of which are measurable and both of which matter on a battery-powered device. These are the figures to design against.

/* CORTEX-M4 AT 100 MHz, SOFTWARE, ROUGH ORDERS OF MAGNITUDE

   OPERATION                    TIME        FLASH
   AES-128-GCM, 1 KB            ~250 us     ~6 KB
     with hardware AES          ~10 us      ~1 KB
   ChaCha20-Poly1305, 1 KB      ~150 us     ~4 KB
   SHA-256, 1 KB                ~100 us     ~3 KB
     with hardware              ~5 us
   HMAC-SHA-256                 ~200 us     +1 KB
   X25519 scalar multiply       ~40 ms      ~8 KB
   Ed25519 sign                 ~50 ms      ~12 KB
   Ed25519 verify               ~140 ms
   ECDSA P-256 sign             ~80 ms      ~15 KB
   RSA-2048 verify (e=65537)    ~30 ms      ~10 KB
   RSA-2048 sign (CRT)          ~900 ms
   Argon2id, 16 MB              ~2 s        ~5 KB + 16 MB RAM
   ML-KEM-768 encapsulate       ~15 ms      ~15 KB

   A FULL TLS 1.3 HANDSHAKE, ECDHE + ECDSA, in software:
     ~400-800 ms and ~25 KB of RAM.
   With a PKA accelerator: ~50-100 ms.

/* THE ENERGY VIEW, which matters more on a battery:
     one handshake  ~ 50-200 mJ in software
     one AEAD record ~ negligible

   SO THE DESIGN RULE FOR BATTERY DEVICES:
     HANDSHAKE RARELY, ENCRYPT FREELY.
       · session resumption / PSK tickets, so one handshake
         per boot rather than per message
       · long-lived sessions rather than reconnecting
       · batch messages
       · and if the device wakes to send 20 bytes once an
         hour, a full TLS handshake each time may cost more
         energy than the radio. Consider a
         provisioned-symmetric design (chapter 17's PSK
         mode) with per-device keys, or OSCORE/EDHOC for
         CoAP - which were designed for exactly this
         profile.

/* AND THE SIZING SHORTCUT: if the part has hardware AES and
   SHA, symmetric crypto is essentially free and you should
   use it liberally. It is the PUBLIC-KEY operations that
   cost, so the design question is always "how often do we do
   asymmetric work?"                                      */

Four patterns worth copying

A handful of patterns cover most embedded cryptographic needs — secure boot, firmware update, device identity, session protection. Each has an established shape worth following rather than inventing.

/* --- 1. SECURE BOOT --- */
    ROM (immutable)
      verify bootloader signature against a key hash in OTP
      check the anti-rollback counter
    BOOTLOADER
      verify the application signature
      check version, device class, image length
      measure into a TPM/PCR if present
    APPLICATION
      verify any signed data it loads

    EACH STAGE VERIFIES THE NEXT BEFORE TRANSFERRING
    CONTROL. The chain is only as strong as the ROM, which
    cannot be changed - so ROM bugs are permanent, and this
    is why boot ROM code is short and heavily reviewed.
    (Full treatment in the isolation track.)

/* --- 2. FIRMWARE UPDATE --- */
    a signed MANIFEST containing:
      format version, firmware version, device class,
      image hash, image length, timestamp
    encrypted image, if confidentiality matters
    verification BEFORE installation
    an anti-rollback counter in fuses
    A/B SLOTS AND A ROLLBACK-ON-FAILURE PATH

    THE ORDERING RULE: EVERY CHECK THAT CAN REJECT HAPPENS
    BEFORE ANYTHING IRREVERSIBLE. And hash the image in its
    final location, so DMA cannot swap it after the check
    (chapter 15).

/* --- 3. DEVICE IDENTITY --- */
    key pair generated INSIDE the secure element at
      manufacture; the private half never exists elsewhere
    a certificate signed by the vendor CA, containing the
      device serial and product class
    mutual TLS to the cloud, validated against a PINNED
      vendor root
    the cloud checks the serial against inventory:
      registered? activated? reported stolen? firmware
      version acceptable?
    (chapters 16 and 17)

/* --- 4. SECURE STORAGE --- */
    key = KDF(hardware_unique_key, "storage v1")
    each record: version ‖ nonce ‖ ciphertext ‖ tag
    version authenticated as AAD -> no rollback
    nonce from a counter IN FLASH, not RAM
    crypto-erase to destroy, never overwrite
    (chapter 18)                                          */
The five rules, if you remember nothing else 
1. PER-DEVICE KEYS, generated on-device, in hardware.
2. USE AN AEAD. Never compose a cipher and a MAC yourself.
3. NEVER REUSE A (key, nonce) PAIR.
4. USE A MAINTAINED LIBRARY, AND KEEP IT UPDATED.
   Your update mechanism is a security control.
5. VERIFY BEFORE YOU ACT. Signature, then version, then
   identity, then use — and only then anything
   irreversible.

The mistakes that ship

The same errors recur across embedded products, and they are rarely exotic. Each one below has shipped in volume, in devices whose designers knew better in principle.

/* Ranked by how often they appear in real teardowns.     */

   1.  THE SAME KEY IN EVERY UNIT. Found by `strings`.
       One extraction, whole product line.

   2.  NO SECURE BOOT. Or secure boot present but disabled
       in production, because the fuse was never blown on
       the line. CHECK YOUR PRODUCTION UNITS, not your dev
       boards.

   3.  DEBUG PORTS OPEN. JTAG/SWD enabled in shipped
       hardware, or re-enabled by a lifecycle state that
       was never advanced.

   4.  CERTIFICATE VALIDATION DISABLED. The development
       bypass that shipped (chapter 16).

   5.  HOSTNAME VERIFICATION NOT ENABLED. A one-line
       omission that silently accepts any valid certificate
       (chapter 17).

   6.  WEAK ENTROPY AT FIRST BOOT. Keys generated before the
       RNG was seeded (chapter 02), producing duplicate or
       factorable keys across a fleet.

   7.  ROLLING YOUR OWN. A custom "encryption" scheme, an
       XOR obfuscation, a hand-built MAC. It is always
       broken, and it is always broken quickly.

   8.  ECB MODE. Because it was the default parameter
       (chapter 05).

   9.  NO ANTI-ROLLBACK. Old vulnerable firmware reinstalls
       with a perfectly valid signature.

   10. NO UPDATE MECHANISM AT ALL. Which converts every
       future vulnerability into a permanent one.

   11. NONCE COUNTERS IN RAM, resetting on every power
       cycle.

   12. UNAUTHENTICATED BUSES to a secure element - the SE
       is correct, and the attacker replays "OK" on the I2C
       lines.

   13. SECRETS IN LOGS on an accessible UART.

   14. NO PLAN FOR COMPROMISE. No key IDs, no rotation
       path, no revocation, no incident procedure.

/* NOTICE HOW FEW OF THESE ARE CRYPTOGRAPHIC. Almost every
   one is a PROVISIONING, CONFIGURATION, LIFECYCLE or
   PROCESS failure. That is the real lesson of this track:
   the algorithms are the easy part, and they are not where
   your product will fail.                               */

A pre-ship checklist

Rather than reasoning from scratch on each project, this reduces the track to a review procedure you can apply to a design before it ships.

   KEYS
   [ ] every key is per-device
   [ ] device keys generated on-device, never exported
   [ ] no key material in the firmware image (verify with
       `strings` and an entropy scan on the RELEASE binary)
   [ ] all working keys derived from a root, with context
       strings
   [ ] key IDs in every stored and transmitted format
   [ ] a written rotation and compromise plan

   BOOT AND UPDATE
   [ ] secure boot enabled AND VERIFIED ON A PRODUCTION UNIT
   [ ] root key hash in OTP, with spare slots
   [ ] anti-rollback counter, and it is actually incremented
   [ ] update images signed; manifest includes version and
       device class
   [ ] verify-before-install, with A/B and recovery
   [ ] the update path itself has been tested from a
       corrupted state

   PROTOCOL
   [ ] AEAD everywhere; no hand-composed cipher+MAC
   [ ] nonce uniqueness guaranteed by a mechanism, not a hope
   [ ] certificate validation on, hostname verification on,
       root pinned
   [ ] minimum TLS version floored
   [ ] replay protection (sequence numbers) present
   [ ] tested against expired, wrong-name, self-signed and
       malformed certificates

   IMPLEMENTATION
   [ ] a maintained library, pinned version, CVE monitoring
       subscribed
   [ ] hardware accelerators used where present
   [ ] constant-time comparisons for all secrets
   [ ] secrets zeroised with a non-removable primitive
   [ ] dudect or ctgrind in CI if you wrote any primitive
       yourself

   LIFECYCLE
   [ ] debug ports disabled in the SECURED state
   [ ] the RMA path erases secrets before re-enabling debug
   [ ] no secrets on any log output
   [ ] production units audited, not just development
       boards

/* AND THE LAST ONE, WHICH IS NOT A CHECKBOX:

     HAVE SOMEONE ELSE TRY TO BREAK IT.

   An external review, or at minimum a colleague who did not
   write it, with a logic analyser, a flash clip and a
   ChipWhisperer. Every item above is something a reviewer
   finds in an afternoon and a designer misses for a year.
                                                          */
