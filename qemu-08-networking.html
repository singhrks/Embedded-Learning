Networking

Four backends, each with a different answer to "who can talk to whom". Picking the wrong one is why guests cannot reach the internet, why you cannot SSH in, and why two guests that should see each other do not. This chapter is the decision table plus the exact commands.

The four backends

user (SLIRP)Yes, NATOnly via hostfwdNoNo

   Decide in this order:

   Do I just need the guest to reach the internet and to
   SSH in?                         -> USER + hostfwd. Done.
                                      No root, no setup, works
                                      on every host including
                                      macOS and Windows.

   Do I need the guest to be a real host on my LAN, with its
   own IP, reachable by other machines?
                                   -> BRIDGE.

   Do I need several guests on a private network, with the host
   as a router or observer?
                                   -> TAP + a host bridge.

   Do I need two guests to talk to each other and nothing else,
   without root?
                                   -> SOCKET.

   Am I testing a driver and do not care about connectivity?
                                   -> USER, or none at all.

user: the default that is almost always right

# SLIRP implements a TCP/IP stack in QEMU's own process. The
# guest gets 10.0.2.15, a gateway at 10.0.2.2 and DNS at
# 10.0.2.3. No configuration on the host at all.

$ qemu-system-aarch64 -M virt ... \
    -netdev user,id=n0 \
    -device virtio-net-device,netdev=n0

# Guest:
$ udhcpc -i eth0          # or: dhclient eth0
$ ip addr show eth0
    inet 10.0.2.15/24
$ ping -c1 10.0.2.2       # the gateway = QEMU itself
$ curl https://example.com   # works, NATted through the host

# SSH IN - this is the option you will use every day:
$ qemu-system-aarch64 ... \
    -netdev user,id=n0,hostfwd=tcp::2222-:22 \
    -device virtio-net-device,netdev=n0
$ ssh -p 2222 root@localhost

# Several forwards at once:
-netdev user,id=n0,hostfwd=tcp::2222-:22,hostfwd=tcp::8080-:80,\
hostfwd=udp::5353-:53

# Bind a forward to one host interface only:
-netdev user,id=n0,hostfwd=tcp:127.0.0.1:2222-:22

# Serve a directory over TFTP, for netbooting the guest:
-netdev user,id=n0,tftp=/srv/tftp,bootfile=/Image

# Give the guest a share over SMB (needs samba on the host):
-netdev user,id=n0,smb=/home/me/share
# guest: mount -t cifs //10.0.2.4/qemu /mnt

# Change the network:
-netdev user,id=n0,net=192.168.76.0/24,host=192.168.76.9,\
dhcpstart=192.168.76.20

# Restrict the guest to only what you forward:
-netdev user,id=n0,restrict=on,hostfwd=tcp::2222-:22
# No internet, no host access except the forward. Good for
# running something you do not trust.
What user networking cannot do

ICMP from the guest often does not work (SLIRP needs raw sockets or ping_group_range), so ping failing does not mean the network is broken — test with curl instead. Guests cannot see each other. The host cannot initiate a connection except through hostfwd. And throughput is limited by SLIRP's userspace stack: expect hundreds of Mbit/s, not tens of Gbit/s.

tap: a real interface on the host

# A tap device is a virtual Ethernet interface the kernel
# exposes as a file descriptor. QEMU writes frames into it; the
# host's network stack sees them arriving on an interface.

# 1. Create a persistent tap owned by you (do this once):
$ sudo ip tuntap add dev tap0 mode tap user $USER
$ sudo ip link set tap0 up
$ sudo ip addr add 192.168.100.1/24 dev tap0

# 2. Use it - no root needed now, because you own tap0:
$ qemu-system-aarch64 -M virt ... \
    -netdev tap,id=n0,ifname=tap0,script=no,downscript=no \
    -device virtio-net-device,netdev=n0,mac=52:54:00:12:34:56

# 3. Guest:
$ ip addr add 192.168.100.2/24 dev eth0
$ ip link set eth0 up
$ ip route add default via 192.168.100.1
$ ping 192.168.100.1              # the host. Works.

# 4. Give the guest internet, by NATting on the host:
$ sudo sysctl -w net.ipv4.ip_forward=1
$ sudo iptables -t nat -A POSTROUTING -s 192.168.100.0/24 \
       -o eth0 -j MASQUERADE
$ sudo iptables -A FORWARD -i tap0 -j ACCEPT
$ sudo iptables -A FORWARD -o tap0 -m state \
       --state RELATED,ESTABLISHED -j ACCEPT

# 5. vhost, for near-native throughput (virt chapter 15):
-netdev tap,id=n0,ifname=tap0,script=no,downscript=no,vhost=on

# ALWAYS set an explicit MAC. QEMU's default is the same for
# every guest, so two guests on one bridge collide, and the
# symptom is intermittent packet loss that looks like a driver
# bug.

bridge: the guest as a peer on your LAN

# The guest gets an address from your real DHCP server and is
# reachable from any machine on the network.

# 1. Build a bridge and move your physical NIC onto it.
#    WARNING: this drops your connection momentarily. Do not do
#    it over SSH without a console.
$ sudo ip link add br0 type bridge
$ sudo ip link set eth0 master br0
$ sudo ip addr flush dev eth0
$ sudo ip link set br0 up
$ sudo dhclient br0

# NetworkManager equivalent, which survives reboots:
$ nmcli con add type bridge ifname br0 con-name br0
$ nmcli con add type ethernet ifname eth0 master br0
$ nmcli con up br0

# 2. Allow QEMU's helper to use it:
$ echo "allow br0" | sudo tee /etc/qemu/bridge.conf
$ sudo chmod u+s /usr/lib/qemu/qemu-bridge-helper

# 3. Run:
$ qemu-system-aarch64 -M virt ... \
    -netdev bridge,id=n0,br=br0 \
    -device virtio-net-device,netdev=n0,mac=52:54:00:aa:bb:cc

# Guest gets a LAN address by DHCP. Colleagues can reach it.
# So can anything else on that network - treat it accordingly.

socket: guests talking to each other, no root

# A pure userspace virtual switch. Ideal for testing a network
# protocol between two guests on a laptop.

# Guest A listens:
$ qemu-system-aarch64 ... \
    -netdev socket,id=n0,listen=:1234 \
    -device virtio-net-device,netdev=n0,mac=52:54:00:00:00:01

# Guest B connects:
$ qemu-system-aarch64 ... \
    -netdev socket,id=n0,connect=127.0.0.1:1234 \
    -device virtio-net-device,netdev=n0,mac=52:54:00:00:00:02

# More than two, using multicast as a shared bus:
$ qemu-system-aarch64 ... \
    -netdev socket,id=n0,mcast=230.0.0.1:1234 \
    -device virtio-net-device,netdev=n0,mac=52:54:00:00:00:0N

# Then inside each guest, configure static addresses on the
# same subnet. Nothing leaves the host.

# Two NICs in one guest - one for management, one for the test
# network. This is the standard shape for a router or firewall
# under test:
$ qemu-system-aarch64 ... \
    -netdev user,id=mgmt,hostfwd=tcp::2222-:22 \
    -device virtio-net-device,netdev=mgmt,mac=52:54:00:00:00:10 \
    -netdev socket,id=lab,mcast=230.0.0.1:1234 \
    -device virtio-net-device,netdev=lab,mac=52:54:00:00:00:11

Capturing traffic

# QEMU can write a pcap of everything on a netdev. No tcpdump
# in the guest, no host interface to find - and it captures
# frames the guest never successfully received, which is
# exactly what you want when debugging a NIC driver.

$ qemu-system-aarch64 ... \
    -netdev user,id=n0 \
    -object filter-dump,id=f0,netdev=n0,file=capture.pcap

$ wireshark capture.pcap
$ tcpdump -r capture.pcap -nn

# Attach a dump filter at runtime, from the monitor:
(qemu) object_add filter-dump,id=f1,netdev=n0,file=/tmp/live.pcap
(qemu) object_del f1

# Other filters worth knowing:
-object filter-buffer,id=f1,netdev=n0,interval=1000
      # delay all traffic by 1 ms - test timeout handling
-object filter-mirror,id=f2,netdev=n0,outdev=chr0
      # mirror to a chardev, for a live analyser
-object filter-redirector,...
      # send traffic somewhere else entirely

# On a tap, the host interface is real, so ordinary tools work:
$ sudo tcpdump -i tap0 -nn
$ sudo tcpdump -i br0 -nn 'ether host 52:54:00:12:34:56'

Throughput, and what limits it

# Measure honestly: run iperf3 in the guest against the host.
$ iperf3 -s                       # host
$ iperf3 -c 10.0.2.2 -t 20        # guest

# Rough expectations on a modern machine:
#   user (SLIRP), TCG guest        50-200 Mbit/s
#   user (SLIRP), KVM guest        0.5-2 Gbit/s   (SLIRP is the
#                                                  bottleneck)
#   tap, no vhost, KVM             2-5 Gbit/s
#   tap + vhost=on, KVM            10-40 Gbit/s
#   tap + vhost + multiqueue       scales with vCPUs
#   passthrough VF (SR-IOV)        line rate

# The three changes that matter, in order:
#  1. -accel kvm            (if the architectures match)
#  2. vhost=on              (tap only; SLIRP cannot use it)
#  3. multiqueue:
-netdev tap,id=n0,ifname=tap0,script=no,downscript=no,\
vhost=on,queues=4 \
-device virtio-net-pci,netdev=n0,mq=on,vectors=10
# vectors = 2*queues + 2. Too few silently reduces the queue
# count.

# Guest side, confirm what you got:
$ ethtool -l eth0
$ ethtool -k eth0 | grep -E 'tso|gso|gro|checksum'

How it shows up

SymptomCause
Guest has no interface at allNo -device for the netdev, or the guest kernel lacks CONFIG_VIRTIO_NET
Interface exists, no addressNo DHCP client ran; with user networking run udhcpc/dhclient
ping fails but curl worksSLIRP and ICMP. Not a problem
Cannot SSH inNo hostfwd, or sshd not running, or the guest firewall
Two guests cannot see each otherBoth on user, which is isolated by design. Use socket, tap or bridge
Intermittent loss with two guests on a bridgeBoth using QEMU's default MAC — set them explicitly
could not open /dev/net/tunTap not created, not owned by you, or no CAP_NET_ADMIN
bridge helper failedBridge not listed in /etc/qemu/bridge.conf, or the helper is not setuid
Host loses network when creating a bridgeExpected while the NIC moves; reconfigure br0
Throughput far below expectationSLIRP, or vhost=on missing, or TCG
Multiqueue configured, one queue usedvectors too small
