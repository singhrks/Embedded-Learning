Choosing between UART, SPI and I2C

Three buses, overlapping capabilities, and a choice usually made by whichever the sensor happens to support. When you do have a choice — and in your own designs you always do — these are the axes that matter.

The decision, in order

   1. IS THE PEER OFF-BOARD OR MORE THAN ~30 CM AWAY?
        -> NOT SPI, NOT I2C. Both are chip-to-chip buses on
           one board. Use UART, or RS-485/CAN for real
           distance (chapters 14, 09).

   2. DO YOU NEED MORE THAN ~1 MBIT/S?
        -> SPI. Nothing else here comes close. Displays,
           external flash, high-rate ADCs, radio modules.

   3. ARE PINS THE BINDING CONSTRAINT?
        -> I2C. Ten sensors on two wires versus thirteen
           pins for SPI. On a 20-pin part this decides it.

   4. IS THIS A CONSOLE, A LOG, OR A MODEM-STYLE DEVICE?
        -> UART. GPS, GSM, Bluetooth modules and debug
           consoles are all UART by convention, and fighting
           the convention costs more than it saves.

   5. DOES THE DEVICE NEED TO INITIATE?
        -> UART, or add an interrupt line. SPI and I2C
           slaves cannot speak unprompted; the near-universal
           solution is a separate INT pin that tells the
           master to come and read - which quietly costs you
           the pin you saved by choosing I2C.

   6. OTHERWISE
        -> I2C for slow sensors, SPI for anything else.

   AND THE HONEST ANSWER MOST OF THE TIME: the sensor you
   want supports one bus, and that decides it. The choice
   above matters when you are designing the protocol between
   two chips you control - an MCU talking to an application
   processor, or two MCUs in one product.

The interrupt line nobody counts

/* SPI and I2C are strictly master-driven. A sensor with new
   data has no way to say so, which leaves three options.  */

/* 1. POLLING - simple, wasteful, and adds latency. */
for (;;) {
    if (i2c_read_reg(ADDR, STATUS) & DATA_READY) {
        read_and_process();
    }
    delay_ms(10);          /* 100 transactions/s doing
                              nothing, and up to 10 ms of
                              latency                     */
}

/* 2. AN INTERRUPT PIN - one extra wire, and the right
      answer nearly always.                                */
void EXTI9_5_IRQHandler(void)
{
    EXTI->PR = (1u << 7);
    /* Do NOT do I2C in the ISR - it blocks for hundreds of
       microseconds. Signal a task (mcu chapter 19).       */
    vTaskNotifyGiveFromISR(sensor_task, &woken);
    portYIELD_FROM_ISR(woken);
}

/* Now: zero bus traffic when idle, microseconds of latency,
   and the CPU can sleep. The pin you spent buys back more
   than it cost.

   SHARED INTERRUPT LINES: several open-drain INT outputs
   can share one MCU pin with a pull-up - any device pulling
   low signals, and the handler polls each device's status
   to find out who. This is exactly the wired-OR idea from
   chapter 06, and it keeps the pin count at one regardless
   of device count.                                        */

/* 3. A FIFO IN THE SENSOR - increasingly common and the
      best of both. The device buffers 32-512 samples and
      interrupts only when the FIFO passes a watermark. The
      master then reads a burst.

      This is how a modern IMU is used: instead of 1000
      interrupts per second for 1000 samples, you get 10
      interrupts and read 100 samples each time. The CPU
      sleeps 99% of the time and the bus carries the same
      data in a tenth of the transactions.

      If a sensor offers a FIFO, use it. It is usually the
      difference between a design that meets its power
      budget and one that does not.                       */
Count the real pin cost

I2C's two-wire claim assumes no interrupt lines and no address conflicts. Three sensors that each need an interrupt pin cost 2 + 3 = 5 pins, against SPI's 3 + 3 = 6 — and if two of them share a fixed address you also need a multiplexer, which costs a part, board area and another two wires. Do this arithmetic with the actual devices before committing the schematic, not after.

Mixing them, and level shifting

   A real board runs all three at once, and the interesting
   problem becomes voltage domains.

   MCU at 3.3 V, sensor at 1.8 V:

   PUSH-PULL BUSES (SPI, UART) need a proper level shifter -
   a dedicated translator IC, or a resistor divider for
   3.3 -> 1.8 in the slow direction only. A divider cannot
   shift UP, and it slows the edge, so it is unsuitable for
   fast SPI.

   OPEN-DRAIN BUSES (I2C) shift with ONE MOSFET PER LINE:

        3.3V                    1.8V
         |                       |
       [4.7k]                  [4.7k]
         |                       |
   SDA_3V3 ----+           +---- SDA_1V8
               |           |
             +-+-----------+-+
             | G   MOSFET    |    gate tied to 1.8 V
             | S           D |
             +---------------+

   Either side pulling low pulls the other low, through the
   body diode and then the channel. Elegant, cheap, and the
   standard solution - the BSS138 in this configuration
   appears on an enormous number of boards.

   THIS IS ANOTHER CONSEQUENCE OF OPEN-DRAIN, and a real
   advantage of I2C in mixed-voltage designs.

   ALWAYS CHECK: is the sensor 5 V tolerant? Many 3.3 V
   parts are not, and an I2C bus pulled up to 5 V will
   damage them - slowly, so the board works for a week.
