Elliptic curve cryptography

The same discrete-logarithm idea in a group where the best known attacks are much worse, so the keys are eight to twelve times smaller. That size difference is what makes public-key cryptography practical on a microcontroller.

The group

An elliptic curve is a set of points satisfying an equation, with a rule for "adding" two points that turns out to form exactly the algebraic structure cryptography needs. No geometry intuition is required to use it.

   A SHORT WEIERSTRASS CURVE over the field F_p:

        y^2 = x^3 + a*x + b   (mod p)

   The GROUP ELEMENTS are the (x, y) pairs satisfying it,
   plus a POINT AT INFINITY O that acts as the identity.

   POINT ADDITION, geometrically:
     · draw the line through P and Q
     · it meets the curve at a third point
     · REFLECT it in the x-axis -> that is P + Q

              |        .-'
              |  P  .-'      the chord through P and Q
              |  x-'         hits the curve at -(P+Q);
              | / \  Q       reflecting gives P+Q
        ------+------x-------------
              |       \
              |        x  P+Q

   POINT DOUBLING (P + P) uses the TANGENT at P instead.

   SCALAR MULTIPLICATION is repeated addition:
        k * P = P + P + ... + P     (k times)
   done by DOUBLE-AND-ADD in O(log k) operations.

   THE ELLIPTIC CURVE DISCRETE LOGARITHM PROBLEM (ECDLP):
        given P and Q = k*P, find k.

   THE BEST KNOWN ATTACK is Pollard's rho, at O(sqrt(n))
   where n is the group order. INDEX CALCULUS - the
   subexponential algorithm that forces finite-field DH and
   RSA to use thousands of bits - DOES NOT APPLY to elliptic
   curve groups.

   HENCE:
        256-bit curve  ->  ~128-bit security
        3072-bit RSA   ->  ~128-bit security
        Same strength. Twelve times the key.

The arithmetic, in practice

Everything in elliptic-curve cryptography reduces to multiplying a point by a scalar. How that is implemented determines both the speed and whether the private key leaks through timing.

/* THE AFFINE FORMULAS, for reference: */

    P + Q, with P != Q:
        s  = (y2 - y1) / (x2 - x1)   mod p
        x3 = s^2 - x1 - x2           mod p
        y3 = s*(x1 - x3) - y1        mod p

    P + P (doubling):
        s  = (3*x1^2 + a) / (2*y1)   mod p
        x3 = s^2 - 2*x1              mod p
        y3 = s*(x1 - x3) - y1        mod p

/* THE DIVISIONS ARE MODULAR INVERSES (chapter 11), and they
   are EXPENSIVE - roughly 100x a multiplication.

/* SO REAL IMPLEMENTATIONS USE PROJECTIVE COORDINATES:
   represent a point as (X, Y, Z) with x = X/Z, y = Y/Z (or
   Jacobian: x = X/Z^2, y = Y/Z^3). Addition and doubling
   then need NO INVERSIONS - one inversion at the very end
   converts back to affine. This is not an optimisation
   detail you can skip; it is the difference between a
   scalar multiply taking 1 ms and 100 ms.

/* --- THE SCALAR MULTIPLY, AND ITS SIDE CHANNEL --- */

    /* NAIVE - LEAKS EVERY BIT OF THE SCALAR */
    R = O;
    for (i = top_bit; i >= 0; i--) {
            R = double(R);
            if (bit_i_of_k)                 /* <-- BRANCH */
                    R = add(R, P);          /* <-- TIMING */
    }
    /* An attacker measuring power or time sees the pattern
       of doublings and additions, and reads k directly. This
       is textbook SPA - simple power analysis - and it works
       on an oscilloscope in an afternoon (chapter 19). */

    /* THE MONTGOMERY LADDER - constant operation sequence */
    R0 = O; R1 = P;
    for (i = top_bit; i >= 0; i--) {
            b  = bit_i_of_k;
            /* CONSTANT-TIME CONDITIONAL SWAP - no branch */
            cswap(b, &R0, &R1);
            R1 = add(R0, R1);
            R0 = double(R0);
            cswap(b, &R0, &R1);
    }
    return R0;
    /* EVERY ITERATION DOES EXACTLY ONE ADD AND ONE DOUBLE,
       whatever the bit. The cswap is a masked exchange:
           mask = -(uint64_t)b;
           t = mask & (R0[j] ^ R1[j]);
           R0[j] ^= t;  R1[j] ^= t;
       No branch, no memory-access difference.            */

/* AND EVEN THAT IS NOT ENOUGH AGAINST DIFFERENTIAL POWER
   ANALYSIS. Add SCALAR BLINDING (use k + r*n for random r;
   it computes the same point since n*P = O) and PROJECTIVE
   COORDINATE RANDOMISATION.                             */

The curves that matter

A handful of curves are used in practice, and they differ in origin, in how their parameters were chosen, and in how easy they are to implement without introducing side channels.

/* WHY THE CURVE FORM MATTERS:

   MONTGOMERY (Curve25519): By^2 = x^3 + Ax^2 + x
     · x-coordinate-only ladder, very fast and naturally
       constant time
     · no point validation needed for X25519
     · perfect for KEY EXCHANGE, awkward for signatures

   TWISTED EDWARDS (Ed25519): -x^2 + y^2 = 1 + d*x^2*y^2
     · a COMPLETE addition formula - ONE formula works for
       every pair of points, including P+P and P+O
     · no special cases means no exceptional-case branches,
       and no exceptional-case bugs
     · perfect for SIGNATURES

   SHORT WEIERSTRASS (P-256): the classical form
     · addition and doubling are DIFFERENT formulas, and
       P + (-P) = O is a special case
     · so implementations have branches, and those branches
       are where the bugs and leaks live
     · but it is what FIPS specifies and what most hardware
       accelerators implement

/* THE NIST-CURVE CONTROVERSY, briefly: the P-curve
   parameters were generated by hashing unexplained seed
   values. Nobody has demonstrated a weakness, but nobody can
   explain the seeds either. Curve25519 and Brainpool were
   both designed with FULLY EXPLAINED, "NOTHING UP MY SLEEVE"
   parameter derivation as an explicit goal.

   THE PRACTICAL POSITION: P-256 is fine and you will use it
   whenever a certificate or an accelerator demands it.
   Choose 25519 when you are free to.                    */
What to pick 
key exchange, free choice      -> X25519
signatures, free choice        -> Ed25519

  FIPS, or an existing PKI     -> P-256 (ECDSA/ECDH)
higher margin                  -> Ed448 or P-384
blockchain interop             -> secp256k1

Point encoding and validation

How a point is represented on the wire is a surprisingly common source of interoperability failure and of security bugs — particularly when a decoder accepts points that are not on the curve at all.

/* --- ENCODING, for Weierstrass curves (SEC1) --- */
    0x04 ‖ X ‖ Y        UNCOMPRESSED, 65 bytes for P-256
    0x02 ‖ X            COMPRESSED, y even     33 bytes
    0x03 ‖ X            COMPRESSED, y odd

    Compression works because y^2 = x^3 + ax + b has exactly
    two solutions for y; one bit says which. Recovering y
    costs a modular square root - a single exponentiation,
    typically ~1/50 of a scalar multiply. WORTH IT when the
    key lives in OTP fuses or travels over a constrained
    radio link.

/* --- X25519 AND Ed25519 --- */
    Always 32 bytes. X25519 sends the x-coordinate only.
    Ed25519 sends y with the sign of x in the top bit.
    No format byte, no options, no negotiation.

/* --- VALIDATION: MANDATORY FOR WEIERSTRASS CURVES --- */

    int validate_point(const ec_point *Q, const ec_group *g)
    {
        /* 1. NOT the point at infinity */
        if (is_infinity(Q)) return -1;

        /* 2. coordinates are in range [0, p-1] */
        if (cmp(Q->x, g->p) >= 0) return -1;
        if (cmp(Q->y, g->p) >= 0) return -1;

        /* 3. THE POINT IS ACTUALLY ON THE CURVE */
        if (!on_curve(Q, g)) return -1;

        /* 4. it is in the correct SUBGROUP:  n*Q == O
              (skippable when the cofactor is 1, as for the
              NIST prime curves) */
        if (!is_infinity(scalar_mul(g->n, Q))) return -1;

        return 0;
    }

/* SKIPPING STEP 3 IS THE INVALID CURVE ATTACK. The attacker
   sends a point that satisfies a DIFFERENT curve equation -
   one whose group has small order. Your scalar multiply
   ignores `b` entirely (look at the formulas above: b never
   appears), so it happily computes on the attacker's curve
   and the result reveals your private scalar modulo a small
   number. Repeat with several curves, apply CRT, and the
   full key falls in a few thousand queries.

   THIS HAS BROKEN: several TLS libraries, a Bluetooth
   pairing implementation (CVE-2018-5383, affecting
   essentially every major OS), and multiple hardware
   wallets.

/* AND THE TWIST ATTACK is the same idea against
   x-coordinate-only implementations. Curve25519 was designed
   to be TWIST-SECURE - the twist's order also has a large
   prime factor - so X25519 needs no validation at all. That
   is a deliberate design decision to remove a class of
   implementation bug, and it is why X25519 is the
   recommendation.                                        */

Using it

You should not implement any of this. This is what to call instead, and the small number of decisions that remain yours.

/* --- ECDH WITH P-256, mbedTLS --- */
    mbedtls_ecdh_context ctx;
    mbedtls_ecdh_init(&ctx);
    mbedtls_ecdh_setup(&ctx, MBEDTLS_ECP_DP_SECP256R1);

    /* our ephemeral key, and the public part to send */
    mbedtls_ecdh_make_public(&ctx, &olen, buf, sizeof buf,
                             mbedtls_ctr_drbg_random, &drbg);

    /* the peer's - THIS VALIDATES THE POINT internally,
       and returning non-zero here is a security event, not
       a parse error */
    if (mbedtls_ecdh_read_public(&ctx, peer, peer_len) != 0)
            return INVALID_PEER_KEY;

    uint8_t secret[32];
    mbedtls_ecdh_calc_secret(&ctx, &olen, secret,
                             sizeof secret,
                             mbedtls_ctr_drbg_random, &drbg);
    /* PASSING THE RNG HERE ENABLES BLINDING. Do not pass
       NULL to "save time" - that disables the countermeasure
       (chapter 19). */

    /* AND THEN, ALWAYS, A KDF (chapter 10): */
    mbedtls_hkdf(sha256, salt, salt_len, secret, olen,
                 (const uint8_t *)"myproto v1 session", 18,
                 session_key, 32);

    mbedtls_platform_zeroize(secret, sizeof secret);
    mbedtls_ecdh_free(&ctx);

/* --- X25519, libsodium: the whole thing --- */
    unsigned char my_sk[32], my_pk[32], shared[32];
    randombytes_buf(my_sk, 32);
    crypto_scalarmult_base(my_pk, my_sk);
    /* send my_pk ... receive their_pk ... */
    if (crypto_scalarmult(shared, my_sk, their_pk) != 0)
            return BAD_KEY;
    /* then hash, as in chapter 13 */

/* --- PERFORMANCE, Cortex-M4 at 100 MHz, rough --- */
    X25519 scalar multiply       ~ 4 M cycles   ( 40 ms)
    P-256 with a good library    ~ 8 M cycles   ( 80 ms)
    Ed25519 sign                 ~ 5 M cycles   ( 50 ms)
    Ed25519 verify               ~14 M cycles   (140 ms)
    RSA-2048 verify (e=65537)    ~ 3 M cycles   ( 30 ms)
    RSA-2048 sign with CRT       ~90 M cycles   (900 ms)

   THE SHAPE TO REMEMBER: RSA VERIFICATION IS THE FASTEST
   THING HERE, which is why boot ROMs use it. Everything
   else favours ECC by a wide margin, and key generation
   favours it by orders of magnitude.

   AND IF THE PART HAS A PKA/CRYPTOCELL ACCELERATOR, these
   numbers drop by 10-50x - check before you optimise
   software.                                             */
