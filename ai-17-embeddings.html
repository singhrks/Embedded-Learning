Embeddings and vector semantics

Token IDs are arbitrary integers with no meaning. An embedding table turns each one into a learned vector whose position carries meaning — and that is the input to every model in the rest of this track.

Why a lookup table

Token IDs are arbitrary integers with no meaningful relationships between them. The embedding table is where arbitrary identifiers become geometry, and geometry is something a network can work with.

   TOKEN ID 4821 IS NOT A NUMBER YOU CAN COMPUTE WITH.
   ID 4821 is not "more" than ID 4820, and their difference
   means nothing.

   ONE-HOT ENCODING makes them comparable but is useless:
       "cat"  -> [0,0,...,1,...,0]     50,000 entries
       "dog"  -> [0,0,...,0,...,1]
     · 50,000 dimensions per token
     · EVERY PAIR IS EQUALLY DISSIMILAR - "cat" and "dog"
       are exactly as unrelated as "cat" and "hydraulic"
     · almost all zeros

   AN EMBEDDING is a LEARNED DENSE VECTOR:

       "cat"  -> [0.2, -0.5, 0.8, ..., 0.1]   768 numbers
       "dog"  -> [0.3, -0.4, 0.7, ..., 0.2]   NEARBY
       "hydraulic" -> [-0.9, 0.1, -0.3, ...]  FAR AWAY

   THE EMBEDDING TABLE is simply a (vocab_size, d_model)
   matrix, and "embedding a token" is a ROW LOOKUP:

       E = matrix of shape (50000, 768)
       embed(4821) = E[4821]

   AND NOTICE: THIS IS EXACTLY EQUIVALENT to multiplying the
   one-hot vector by E. The lookup is just the efficient
   implementation of that matrix product - which is why the
   gradient of an embedding lookup is "add the incoming
   gradient to that row" and nothing else.

   THE PARAMETERS ARE LEARNED. Nobody assigns coordinates.
   Backpropagation moves each row so that the model predicts
   better, and semantic structure EMERGES from that pressure.

   SIZE MATTERS: a 128k vocabulary at d_model = 4096 is
   524 million parameters IN THE EMBEDDING TABLE ALONE -
   often 10-20% of a mid-sized model, and the largest single
   tensor in a small one.

What the space looks like

The claim that meaning becomes direction in a vector space sounds mystical and is empirically testable. It is also more limited than the famous examples suggest.

/* THE DISTRIBUTIONAL HYPOTHESIS (Firth, 1957):
   "You shall know a word by the company it keeps."

   Words appearing in similar contexts get similar vectors,
   because the training objective pushes them there. That is
   the entire mechanism - no semantics were programmed in. */

import numpy as np

def cosine(a, b):                              # chapter 02
    return (a @ b) / (np.linalg.norm(a) * np.linalg.norm(b))

cosine(E["cat"], E["dog"])        # ~0.7   related
cosine(E["cat"], E["kitten"])     # ~0.8   closely related
cosine(E["cat"], E["hydraulic"])  # ~0.05  unrelated

/* --- THE ANALOGY RESULT --- */
    vec("king") - vec("man") + vec("woman")  ~=  vec("queen")
    vec("Paris") - vec("France") + vec("Italy")
                                             ~=  vec("Rome")

    DIRECTIONS IN THE SPACE CORRESPOND TO RELATIONSHIPS.
    Gender is a direction. Capital-of is a direction. Plural
    is a direction.

    THE HONEST CAVEAT, because this result is over-sold: the
    analogy typically only works when you EXCLUDE the three
    input words from the nearest-neighbour search, and it is
    sensitive to normalisation. The underlying claim -
    that linear structure exists - is solid; the party trick
    is fragile.

/* --- WHAT ELSE IS ENCODED --- */
    · syntax: nouns cluster, verbs cluster, tenses align
    · sentiment: a direction separating positive from
      negative
    · morphology: "run"/"running" offset resembles
      "walk"/"walking"
    · AND SOCIAL BIAS. Embeddings trained on human text
      encode human associations, including harmful ones:
      occupations align with gender directions,
      names align with sentiment by ethnicity. This is not a
      training bug - it is an accurate reflection of the
      corpus, and it propagates into any downstream system
      that uses the embeddings. MEASURE IT (WEAT and similar
      tests) IF YOUR SYSTEM MAKES DECISIONS ABOUT PEOPLE.

/* --- SUPERPOSITION: how so much fits in so few
       dimensions --- */
    A model with 768 dimensions appears to represent far
    more than 768 distinct features. It can, because in high
    dimensions there are exponentially many ALMOST-orthogonal
    directions (chapter 02). Features are stored in
    superposition, with small interference.

    THIS IS THE LEADING EXPLANATION for why bigger models
    are disproportionately better - more dimensions means
    exponentially more room - and it is the basis of the
    sparse-autoencoder work in mechanistic interpretability,
    which tries to decompose those superposed directions back
    into individual interpretable features.               */

Static versus contextual

This distinction is the dividing line between the previous generation of language models and the current one, and it explains what the transformer is actually for.

   STATIC EMBEDDINGS - word2vec (2013), GloVe, fastText
     ONE VECTOR PER WORD, FIXED.

     "I went to the BANK to deposit money"
     "I sat on the river BANK"
        -> the SAME vector. The model cannot distinguish
           them.

     word2vec's two training objectives:
       SKIP-GRAM   predict context words from the centre
                   word
       CBOW        predict the centre word from its context
     plus NEGATIVE SAMPLING, which turns an expensive softmax
     over the whole vocabulary into a handful of binary
     classifications.

     STILL USEFUL: they are tiny, fast, need no GPU, and for
     a keyword or intent classifier on a microcontroller they
     may be the only option that fits (chapter 27).

   CONTEXTUAL EMBEDDINGS - ELMo, BERT, GPT, everything since
     THE VECTOR DEPENDS ON THE SURROUNDING TEXT.

     The embedding TABLE still gives a static starting
     vector, but each transformer layer MIXES INFORMATION
     FROM OTHER POSITIONS via attention (chapter 19). By the
     final layer, "bank" in the two sentences has two very
     different representations.

     THE INPUT EMBEDDING IS THE STARTING POINT, NOT THE
     ANSWER. This distinction is the single most important
     thing in this chapter: everything a transformer does is
     progressively refining these vectors using context.

   SENTENCE / DOCUMENT EMBEDDINGS
     One vector for a whole passage, for retrieval and
     similarity.
     · mean-pool the token embeddings (simple, decent)
     · use the [CLS] position (BERT-style)
     · OR TRAIN FOR IT: sentence-transformers, E5, BGE, and
       similar models are fine-tuned with a CONTRASTIVE
       objective so that cosine similarity actually
       corresponds to semantic similarity.

     AND THIS MATTERS: raw mean-pooled BERT embeddings are
     notoriously poor at similarity. Use a model TRAINED for
     embedding, not a language model's hidden states.

Implementation

Embeddings are simpler in code than the discussion suggests — a lookup followed by a gradient that touches only the rows you used.

import torch
import torch.nn as nn

# --- THE LAYER ---
emb = nn.Embedding(num_embeddings=50000, embedding_dim=768)

ids = torch.tensor([[15496, 11, 995]])   # (batch=1, seq=3)
vecs = emb(ids)                           # (1, 3, 768)

# THAT IS THE ENTIRE INPUT PIPELINE OF A TRANSFORMER:
# integers in, vectors out.

# --- WEIGHT TYING: a free improvement ---
model.lm_head.weight = model.embed_tokens.weight
# Share the input embedding table with the output projection
# to the vocabulary. THE INTUITION: both matrices map
# between token space and vector space, in opposite
# directions.
#
#   · SAVES vocab*d_model PARAMETERS - 524M for the example
#     above, which is enormous
#   · usually IMPROVES quality for small and mid-sized
#     models
#   · standard in GPT-2 and many others
#
# Very large models sometimes untie them, having enough
# capacity that the constraint costs more than it saves.

# --- PADDING ---
emb = nn.Embedding(50000, 768, padding_idx=0)
# Row 0 is fixed at zero and receives NO GRADIENT. Without
# this, the pad token accumulates updates and drifts into a
# meaningless but non-zero position.

# --- FROZEN PRETRAINED EMBEDDINGS ---
emb = nn.Embedding.from_pretrained(vectors, freeze=True)
# Useful with small datasets: you inherit semantics learned
# from a large corpus without the data to relearn them.

# --- A RETRIEVAL SYSTEM, end to end ---
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('all-MiniLM-L6-v2')

docs = ["The cat sat on the mat", "Dogs are loyal",
        "Python is a programming language"]
doc_vecs = model.encode(docs, normalize_embeddings=True)

q = model.encode("feline on a rug", normalize_embeddings=True)
scores = doc_vecs @ q          # NORMALISED -> the dot
                               # product IS cosine similarity
best = scores.argmax()         # -> document 0

# THIS IS THE WHOLE OF SEMANTIC SEARCH, and the retrieval
# half of RAG (retrieval-augmented generation). At scale,
# the linear scan is replaced by an APPROXIMATE NEAREST
# NEIGHBOUR index - HNSW or IVF-PQ, in FAISS or a vector
# database - which trades a little recall for logarithmic
# search time.

# --- AND THE THING TO GET RIGHT ---
# NORMALISE ONCE AT INSERT TIME (chapter 02). Then querying
# is pure matrix-vector multiplication, which is exactly the
# memory-bound operation from chapter 04 - so a vector
# search over a million documents is a BANDWIDTH problem,
# and quantising the stored vectors to int8 makes it 4x
# faster. The same reasoning as LLM inference, applied to a
# database.
Embeddings are the interface

Every modality reaches a transformer the same way: as a sequence of vectors. Text goes through a token embedding table. Images are split into patches and each patch is linearly projected. Audio becomes spectrogram frames. Once anything is a sequence of d_model-dimensional vectors, the architecture in the next chapters does not care where it came from — which is precisely why multimodal models were an incremental change rather than a redesign.
