Hypervisor attack surface and VM escape

A hypervisor's entire value is a boundary, and a boundary is only as good as the code that sits on it. Almost every published escape has come from the same small number of places — and knowing which places they are turns "is this design secure?" into a question you can actually answer.

Where the attack surface actually is

The instinct is that a hypervisor is small and therefore safe. The hypervisor often is small; the surface a guest can reach is usually much larger, and it is almost never where people first look.

   EVERYTHING A MALICIOUS GUEST CAN REACH:

   1. THE EXIT HANDLERS                        (chapters 04, 06)
        Every trap reason is an entry point taking
        attacker-controlled input. The guest chooses which
        one to invoke and with what register state.

   2. EMULATED DEVICE MODELS                   (chapter 14)
        BY FAR THE LARGEST SURFACE. Thousands of lines of C
        parsing attacker-controlled register writes, in the
        VMM, usually at host privilege. Historically the
        source of most escapes.

   3. THE VIRTIO RINGS                         (chapter 15)
        Shared memory the guest writes and the host reads.
        Every index, length and descriptor is attacker
        controlled and can CHANGE between your check and
        your use.

   4. HYPERCALLS                               (chapter 04)
        A deliberate syscall-like interface, with the same
        obligations as any syscall boundary.

   5. STAGE-2 MANAGEMENT                       (chapter 05)
        Where you decide which physical pages a guest may
        reach. A bug here is an immediate escape.

   6. SHARED MICROARCHITECTURE                 (chapter 19)
        Caches, branch predictors, memory bandwidth. Not
        reachable by writing to a register - reachable by
        measuring.

   ---------------------------------------------------------

   NOTE THE SHAPE: items 1, 4 and 5 live in a small, audited
   hypervisor. Item 2 lives in a large user-space program
   nobody thinks of as security-critical. THAT ASYMMETRY IS
   THE WHOLE POINT OF THIS CHAPTER.

The classes of escape, with the mistake that causes each

Published escapes cluster into a handful of patterns. They are all familiar from ordinary systems programming, which is reassuring — the boundary is exotic, the bugs are not.

The double-fetch is the one worth internalising

Shared memory is not a snapshot. When a guest hands you a descriptor containing a length, and you validate that length and then read it a second time to use it, a second vCPU can rewrite it in between — and your validated value and your used value are different. This is not a race you can win by being fast, and it is exactly the same bug as re-reading a user pointer in a syscall, or re-reading a shared buffer in a TEE (OP-TEE chapter 20). The rule is identical in all three places: copy out of shared memory once, into memory only you can write, then validate the copy, then use only the copy. Any code that reads the same shared field twice is a bug regardless of what it does in between.

/* THE BUG, in the shape it actually appears */
struct vring_desc *d = &vq->desc[idx];    /* GUEST memory */

if (d->len > MAX_LEN)                     /* fetch 1: check */
        return -EINVAL;

buf = map_guest(d->addr, d->len);         /* fetch 2: USE  */
/*                       ^^^^^^ a second vCPU changed it
                                between the two reads.    */

/* THE FIX: one fetch, into local storage. */
struct vring_desc d = vq->desc[idx];      /* COPY, once    */

if (d.len > MAX_LEN)                      /* check the copy */
        return -EINVAL;
if (!guest_owns(d.addr, d.len))           /* and the address */
        return -EINVAL;

buf = map_guest(d.addr, d.len);           /* use the copy   */

/* AND NOTE THE SECOND CHECK. A length that is in range says
   nothing about whether the ADDRESS belongs to this guest.
   Both must be validated, on the copy, before either is
   used.                                                  */

Reducing the surface, in order of effect

These are architectural rather than defensive-coding measures, and they are ordered by how much they actually remove rather than by how much they are discussed.

MeasureWhat it removesCost
Delete device models you do not needThe largest surface, entirely. A VMM with four devices instead of fortyNone — this is the cheapest real win available
Sandbox the VMMTurns a device-model escape into access to a confined process rather than to the host — seccomp, namespaces, a dedicated userSome engineering; standard practice
Move devices out of the monolithOne compromised device model cannot reach the others (vhost-user, per-device processes)Complexity, and more IPC
Write device models in a memory-safe languageThe entire memory-safety class (Rust chapter 01)Rewriting; increasingly common in new VMMs
Use an IOMMU for every DMA-capable deviceDevice-initiated escapes Setup, and pinned memory
Shrink the trusted hypervisorSurface in the most privileged code — the pKVM and Jailhouse argumentFunctionality; a design decision, not a patch
Static partitioningNearly all runtime surface, by not sharing (chapter 19)Efficiency — you gave up sharing
Disable SMT for sensitive workloadsA large family of side channelsUp to half your throughput
Fuzz the guest-facing interfacesBugs, before someone else finds themCheap; badly under-used

The first row deserves emphasis because it is so often skipped. A general-purpose VMM emulates a large collection of legacy devices that a purpose-built guest will never touch, and every one of them is reachable code. Removing them costs nothing and is frequently the single biggest reduction available — which is the argument behind the minimal VMMs in chapter 18.

Reviewing a guest-facing handler

Whether the code is an exit handler, a hypercall or a device model, the questions are the same. This is the checklist worth applying to every one of them.

   □ IS EVERY INPUT TREATED AS HOSTILE?
     Register values, lengths, indices, addresses,
     descriptors. The guest chose all of them.

   □ IS SHARED MEMORY READ EXACTLY ONCE?
     Copy first, then validate the copy, then use the copy.
     Any second read of the same field is a bug.

   □ IS EVERY GUEST ADDRESS CHECKED FOR OWNERSHIP?
     In range is not the same as belongs to this guest.

   □ ARE LENGTHS CHECKED AGAINST THE DESTINATION, not just
     against a constant?

   □ CAN AN ARITHMETIC OPERATION ON GUEST INPUT OVERFLOW,
     and would the result then pass the bounds check?

   □ IS THE LOOP BOUNDED?
     A guest-supplied count that drives iteration is a
     denial of service at best.

   □ WHAT HAPPENS ON THE ERROR PATH?
     Partially applied state, a freed pointer still
     installed, a lock not dropped.

   □ DOES THIS RUN AT HOST PRIVILEGE, and does it need to?

   □ IS THE OPERATION AUTHORISED for THIS guest, or only
     valid in general?

   ---------------------------------------------------------

   IF YOU HAVE READ THE DRIVER TRACKS, THIS LIST IS FAMILIAR.
   It is the IOCTL review checklist (Windows chapter 16),
   the syscall checklist (Linux chapter 33), and the TA
   parameter checklist (OP-TEE chapter 20), with the nouns
   changed. THE BOUNDARY IS NEW; THE DISCIPLINE IS NOT.

What a hypervisor boundary is worth

It is worth being honest about the strength of this boundary relative to the others on this site, because it is frequently oversold in both directions.

   STRONGER THAN a process boundary: far less shared state,
   a much narrower interface, and hardware enforcement of
   the memory separation.

   WEAKER THAN it is usually presented: the VMM is a large
   user-space program at host privilege, and it is part of
   the boundary whether or not your threat model says so.

   AND THE HONEST SUMMARY:

     A VM IS A GOOD BOUNDARY AGAINST A COMPROMISED WORKLOAD.
     IT IS A WEAKER BOUNDARY AGAINST A DETERMINED ATTACKER
     WHO ALREADY HAS CODE EXECUTION IN THE GUEST AND TIME TO
     SPEND ON YOUR DEVICE MODELS.

   IF THE SECOND IS YOUR THREAT MODEL, the answer is not a
   better device model. It is to remove the hypervisor from
   the trusted set entirely - which is what confidential
   computing (chapter 21) does - or to stop sharing the
   machine at all (chapter 19).

   CHOOSING BETWEEN THOSE IS AN ARCHITECTURE DECISION, and
   it should be made before the code is written rather than
   after the first advisory.
