Building and booting a custom kernel

Configure, cross-compile, boot it under QEMU, and get to a shell — with a development loop fast enough that you will actually use it. This is the workbench everything else in the track runs on.

The toolchain

Building a kernel for a different architecture than the one you are sitting at needs a cross-compiler and two environment variables. Getting this setup right once saves a great deal of confusion later, because most build failures at this stage are the toolchain, not the code.

# Debian/Ubuntu:
sudo apt install gcc-aarch64-linux-gnu build-essential \
     bc bison flex libssl-dev libelf-dev libncurses-dev \
     qemu-system-arm qemu-user-static debootstrap \
     device-tree-compiler cpio

# Verify:
aarch64-linux-gnu-gcc --version
qemu-system-aarch64 --version

# EVERY kernel command needs these two, so export them once:
export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-

# (Or pass them on each make line. Forgetting them and
# building a host x86 kernel by accident is the single most
# common wasted 20 minutes in embedded work.)

Configuring

A kernel has tens of thousands of configuration options, and you will never set them by hand. In practice you start from a configuration that already works for your board and change the handful you care about.

# Start from a sensible base:
make defconfig              # arm64 generic - boots on QEMU
                            # virt and most server-class parts
make ARCH=arm64 vendor_defconfig      # a board's own config
                                      # in arch/arm64/configs/

# Then adjust:
make menuconfig             # ncurses. '/' SEARCHES - use it.
make nconfig                # nicer ncurses
make xconfig                # Qt
make savedefconfig          # writes a MINIMAL defconfig
                            # containing only non-default
                            # options - what you commit

# Scripted, which is what CI should do:
./scripts/config --enable  CONFIG_DEBUG_INFO_DWARF5
./scripts/config --enable  CONFIG_KASAN
./scripts/config --enable  CONFIG_PROVE_LOCKING
./scripts/config --module  CONFIG_MY_DRIVER
./scripts/config --disable CONFIG_MODULE_SIG_FORCE
./scripts/config --set-val CONFIG_LOG_BUF_SHIFT 18
make olddefconfig           # resolve the consequences
                            # WITHOUT prompting

# Other useful targets:
make oldconfig              # prompts for NEW options only -
                            # use after updating the tree
make listnewconfig          # what changed, without asking
make localmodconfig         # keep only modules currently
                            # loaded. Shrinks a distro config
                            # enormously; be careful, it
                            # drops anything not plugged in
                            # right now.
The development config

Turn these on while writing drivers. They cost performance and find bugs your testing never will:

CONFIG_DEBUG_KERNEL=y
CONFIG_DEBUG_INFO_DWARF5=y     # for gdb and pahole
CONFIG_KASAN=y                 # memory errors
CONFIG_KASAN_INLINE=y
CONFIG_PROVE_LOCKING=y         # lockdep
CONFIG_DEBUG_ATOMIC_SLEEP=y    # sleeping in atomic context
CONFIG_DEBUG_SPINLOCK=y

CONFIG_DEBUG_KMEMLEAK=y

CONFIG_FTRACE=y

Building

The build produces several outputs and it matters which one your board actually needs. This is also where the development loop is won or lost — a full rebuild takes minutes, and almost all of that is avoidable.

# The whole thing:
make -j$(nproc) Image dtbs modules

# Targets that matter:
#   Image        the raw kernel (arm64 does not use zImage)
#   Image.gz     compressed - most bootloaders accept it
#   dtbs         all device trees for this arch
#   modules      the .ko files
#   vmlinux      the ELF with symbols - NOT bootable, but this
#                is what gdb and addr2line need. Keep it.

# Just one file, while iterating on a driver:
make drivers/mydrv/mydrv.ko

# Just one device tree:
make arch/arm64/boot/dts/vendor/myboard.dtb

# Install modules to a staging root:
make INSTALL_MOD_PATH=/path/to/rootfs modules_install

# SPEED, which matters more than anything else here:
    ccache      export CROSS_COMPILE="ccache aarch64-linux-gnu-"
                a rebuild after a config change goes from
                20 minutes to 2
    make -j$(nproc)
    -j with distcc or icecc if you have a build farm

# Verify what you produced:
    file arch/arm64/boot/Image
      Linux kernel ARM64 boot executable Image, little-endian
    ls -lh arch/arm64/boot/Image

Booting it under QEMU

You do not need hardware to run a kernel you built. QEMU boots your image on an emulated board in a couple of seconds, gives you a console immediately, and lets you attach a debugger — which makes it the fastest place to develop almost anything that is not tied to a specific chip.

# The fastest development loop available, and it needs no
# hardware. Start with an initramfs so there is no filesystem
# to manage.

# 1. Build a tiny userspace with busybox:
    wget https://busybox.net/downloads/busybox-1.36.1.tar.bz2
    tar xf busybox-1.36.1.tar.bz2 && cd busybox-1.36.1
    make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
         defconfig
    ./scripts/config --enable CONFIG_STATIC   # no libc needed
    make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
         -j$(nproc) install          # -> ./_install

# 2. Build the initramfs:
    cd _install
    mkdir -p proc sys dev
    cat > init <<'EOF'
#!/bin/sh
mount -t proc  none /proc
mount -t sysfs none /sys
mount -t devtmpfs none /dev
echo "=== userspace is up ==="
exec /bin/sh
EOF
    chmod +x init
    find . | cpio -o -H newc | gzip > ../initramfs.cpio.gz

# 3. Boot:
    qemu-system-aarch64 \
      -M virt -cpu cortex-a57 -smp 4 -m 1024 \
      -kernel arch/arm64/boot/Image \
      -initrd initramfs.cpio.gz \
      -append "console=ttyAMA0 earlycon rdinit=/init" \
      -nographic

# Ctrl-A then X quits. Ctrl-A then C is the QEMU monitor.

# THE ITERATION LOOP is now:
#   edit -> make -j -> qemu -> test        ~30 seconds
# versus flashing hardware, which is minutes. Do as much as
# possible here and move to real hardware only for what
# genuinely needs it.

Useful QEMU options

A few QEMU options turn it from "it boots" into a genuine development environment — sharing files with the host, attaching a debugger, and emulating devices to drive your driver.

# Attach a virtual disk:
    -drive file=rootfs.ext4,format=raw,if=none,id=hd0 \
    -device virtio-blk-device,drive=hd0 \
    -append "root=/dev/vda rw console=ttyAMA0"

# Networking with a port forward to ssh:
    -netdev user,id=net0,hostfwd=tcp::5555-:22 \
    -device virtio-net-device,netdev=net0

# SHARE A HOST DIRECTORY - the best way to get a freshly
# built module into the guest without rebuilding anything:
    -virtfs local,path=/host/dir,mount_tag=host,\
security_model=none,id=host
    # in the guest:
    mount -t 9p -o trans=virtio host /mnt

# Dump the device tree QEMU generated, to read or modify:
    -machine dumpdtb=virt.dtb
    dtc -I dtb -O dts virt.dtb > virt.dts

# Emulate TrustZone with secure firmware (isolation ch. 11):
    -machine virt,secure=on -bios bl1.bin

# GDB - halt at the first instruction and wait:
    -s -S
    # then, in another terminal:
    aarch64-linux-gnu-gdb vmlinux
    (gdb) target remote :1234
    (gdb) hbreak start_kernel
    (gdb) continue
QEMU's virt machine is a real, well-documented platform

It has a GIC, a PL011 UART, virtio devices, an SMMU (-machine virt,iommu=smmuv3), PSCI, and optional EL3 and EL2. Nearly everything in this track can be exercised on it, including SMMU faults, secure-world calls and CPU hotplug. Use hardware for timing, real peripherals, and power — and QEMU for everything else.

A real root filesystem

A kernel alone boots and then panics, because it has nothing to run. You need a root filesystem containing at least one program, and there are two practical ways to provide one depending on how much of a real system you want.

# Option 1: Debian, via debootstrap. Big, but complete -
# apt, gdb, perf, python all available.
    sudo debootstrap --arch=arm64 --foreign bookworm \
         ./rootfs http://deb.debian.org/debian
    sudo cp /usr/bin/qemu-aarch64-static ./rootfs/usr/bin/
    sudo chroot ./rootfs /debootstrap/debootstrap --second-stage
    sudo chroot ./rootfs passwd root

    dd if=/dev/zero of=rootfs.ext4 bs=1M count=2048
    mkfs.ext4 rootfs.ext4
    sudo mount -o loop rootfs.ext4 /mnt
    sudo cp -a rootfs/* /mnt/
    sudo umount /mnt

# Option 2: Buildroot. Small, fast, reproducible - what most
# embedded products actually use.
    git clone https://git.buildroot.net/buildroot
    cd buildroot
    make qemu_aarch64_virt_defconfig
    make menuconfig      # add packages, set the kernel
    make -j$(nproc)
    # produces output/images/{Image,rootfs.ext4,start-qemu.sh}

# Option 3: Yocto. Heaviest, most configurable, and the one
# you will meet at a vendor. Layers, recipes, bitbake.
# Worth learning if you ship products; overkill for study.

# INSTALL YOUR MODULES into whichever you chose:
    make INSTALL_MOD_PATH=./rootfs modules_install
    # then depmod against the TARGET's module tree:
    depmod -b ./rootfs $(make kernelrelease)

Onto real hardware

Eventually the code has to run on the actual board. This is where the loop gets slow, so the goal of everything below is to avoid physically touching the hardware — no card swapping, no reflashing — on every iteration.

# The parts you now need that QEMU did not:

# 1. A SERIAL CONSOLE. Non-negotiable. A USB-TTL adapter and
#    three wires. Without it you are debugging blind.
    picocom -b 115200 /dev/ttyUSB0
    # or: screen /dev/ttyUSB0 115200

# 2. A device tree for YOUR board, not the generic one.
    make arch/arm64/boot/dts/vendor/myboard.dtb

# 3. A way to load a kernel without reflashing every time.
#    U-Boot over TFTP is the standard answer:
    # on the host:
    sudo apt install tftpd-hpa
    sudo cp Image myboard.dtb /srv/tftp/

    # in U-Boot:
    setenv serverip 192.168.1.10
    setenv ipaddr 192.168.1.20
    tftpboot ${kernel_addr_r} Image
    tftpboot ${fdt_addr_r} myboard.dtb
    setenv bootargs "console=ttyS0,115200 earlycon \
                     root=/dev/nfs nfsroot=192.168.1.10:/srv/nfs \
                     ip=dhcp rw"
    booti ${kernel_addr_r} - ${fdt_addr_r}

# 4. NFS ROOT, so userspace changes need no reflash either.
#    Kernel over TFTP + rootfs over NFS = a development loop
#    on real hardware that is nearly as fast as QEMU. Set this
#    up on day one of any board bring-up; it pays for itself
#    within a day.

# 5. A recovery path. Know how to get back to a working image
#    before you break the one that boots - a second boot slot,
#    an SD card, or a USB recovery mode.

Keeping the loop fast

Every technique here attacks the same cost: the round trip from "change one line" to "see the result," which for a naive full-kernel rebuild-and-reboot cycle can run to minutes and quickly becomes the dominant cost of a whole day's driver development. None of these require exotic tooling — they are ordinary build and deployment choices that happen to compound.

TechniqueSaves
ccacheMost of a rebuild after a config change
Build the driver as =mThe whole kernel rebuild, and the reboot
QEMU instead of hardwareMinutes per iteration
TFTP + NFS rootReflashing, on real hardware
9p share into QEMURebuilding the initramfs to test one module
make M=drivers/mydrvScanning the whole tree
Unbind/bind instead of rebootRe-running probe without unloading
A scripted configRe-deriving your options after every tree update
