Hardware encoders and decoders

A dedicated block that decodes 4K60 at a fraction of a watt, where software would need several CPU cores. It is not a fast CPU — it is a fixed-function pipeline with fixed capabilities, and knowing what it can and cannot do decides whether your product works on battery.

Why the silicon exists

   DECODING 4K60 HEVC

     software, 8 CPU cores      ~25 W, and the phone is now
                                unusable for anything else
     hardware VPU               ~0.5 W

   A 50x power difference. That is the entire argument, and it
   is why every SoC has one (see the SoC section on the home
   page). Battery life on video playback is almost entirely a
   question of whether the hardware path was used.

   WHAT THE BLOCK ACTUALLY CONTAINS

     +---------------------------------------------------+
     |  entropy decoder (CABAC)  - the serial bottleneck  |
     |    -> its throughput sets the max bitrate the      |
     |       chip supports (chapter 8)                    |
     |  inverse transform + dequantise                    |
     |  motion compensation - the interpolation filters   |
     |  intra prediction                                  |
     |  in-loop filters: deblock, SAO, CDEF               |
     |  reference frame DMA + a reference cache           |
     +---------------------------------------------------+
                    |
              DRAM: the DPB (chapter 10)

   IT IS A PIPELINE, not a processor. Every stage is
   hard-wired for specific codecs, specific profiles and
   specific block sizes. There is no microcode to change - a
   chip that decodes H.264 and HEVC will never decode AV1,
   ever, at any clock speed.

   WHICH IS WHY the codec landscape (chapter 14) moves so
   slowly: adopting a new codec means waiting for a hardware
   generation, then for the installed base to turn over.
   Roughly five to eight years.
Hardware encode is worse per bit than software, always

A fixed-function encoder has a fixed, shallow search: limited motion search range, few partition candidates, no multi-pass lookahead, simplified rate-distortion decisions. Expect 20–50% more bitrate than x264 --preset slow at the same quality. That is the price of 50× the speed and 1/50th the power. Use hardware for live and for anything power-constrained; use software for VOD you encode once and stream a million times.

The constraints that bite

/* A hardware codec has HARD limits, and it fails ungracefully
   when you exceed them - usually a silent fall back to
   software (slow), or an error code with no explanation. */

  CODEC AND PROFILE
      "H.264 decode" means specific profiles. High 4:4:4 or
      High10 is often absent even where High is present
      (chapter 14).

  LEVEL
      Max resolution, frame rate, bitrate, DPB size and BIN
      RATE. A stream can be within the bitrate and still
      exceed the bin rate.

  PIXEL FORMAT
      Almost always NV12 in, NV12 out (chapter 4). Feeding it
      RGB means a conversion pass you did not budget for.

  ALIGNMENT
      Width and height usually to 16 or 32; stride to 128 or
      256; the buffer base to 4 KB. A 1920x1080 surface is
      often physically 1920x1088 - the extra 8 rows are real
      and must not be displayed.

  MEMORY
      Physically contiguous, or IOMMU-mapped. Often a specific
      heap - CMA, or a carve-out. malloc'd memory will not do.

  TILING
      The output may be in a vendor tiled or compressed layout
      (chapter 4). Reading it with the CPU without detiling
      gives you scrambled rectangles.

  CONCURRENCY
      Usually ONE session, or a small fixed number. Two apps
      both wanting hardware decode is a real failure mode on
      phones.

  LATENCY
      The pipeline is deep. Frames go in and come out several
      later - you must feed it continuously and collect
      asynchronously, never call "decode this frame" and wait.

/* THE 1088 PROBLEM, concretely: H.264 codes in 16x16
   macroblocks, so 1080 rounds up to 1088. The bitstream
   carries CROPPING information saying "display 1080 of these
   1088 rows". Ignore it and you get 8 rows of garbage at the
   bottom - one of the most common hardware-decode bugs, and
   it looks like a driver fault.                            */

Zero-copy, and why it is the whole game

   THE NAIVE PIPELINE - four copies of every frame:

     decoder -> DRAM -> CPU reads -> converts NV12 to RGB
             -> DRAM -> GPU uploads as a texture
             -> DRAM -> composites -> display

     At 4K60 NV12 that is 12 MB per frame, 750 MB/s per copy.
     Four copies plus a colour conversion is several GB/s of
     memory traffic, and on a phone that is the entire
     bandwidth budget (mobile GPU chapter 10).

   THE ZERO-COPY PIPELINE - one buffer, passed by handle:

     decoder writes NV12 into a DMABUF
        |  export as an fd
        v
     GPU imports the SAME memory as an EGLImage / VkImage
        |
        v
     display controller scans out the SAME memory directly,
     converting NV12 to RGB in its own hardware plane
     (chapter 18)

     ZERO copies. The pixels are written once, by the decoder,
     and read once, by the display.

   WHAT MAKES IT WORK, and all four must hold:
     1. DMABUF - a kernel object representing a buffer,
        passed between drivers as a file descriptor
     2. an agreed PIXEL FORMAT (NV12) and MODIFIER (the exact
        tiling - chapter 4)
     3. an IOMMU or contiguous memory so every device can
        address it
     4. explicit or implicit FENCING so the GPU does not read
        a frame the decoder is still writing

   WHEN ONE OF THOSE FAILS the stack silently inserts a copy,
   or a format conversion, or both. Your pipeline still works
   and uses three times the power. This is the single most
   common performance problem in embedded video, and it is
   invisible unless you measure memory bandwidth.
"It works" and "it is on the fast path" are different questions

Every media framework falls back gracefully. Ask for hardware decode into a GPU texture and, if any link in the chain cannot be negotiated, you will get a working pipeline with a hidden memcpy and a software colour conversion. Frame rate may even be fine on a desktop. The way to know is to measure: GPU video engine utilisation, memory bandwidth, and power — not whether the picture appears.
