Kernel data structures and object lifetime

You cannot read kernel source without these. Almost every structure in the kernel is on a linked list, and almost every shared object is reference-counted — and both are done in a way that looks backwards the first time you see it. This chapter is the toolkit: the lists, trees and ID maps the kernel gives you, and the answer to the question that causes more crashes than any other, who frees this, and when?

Lists are inside-out compared with what you know

The kernel's linked lists work in the opposite direction from the ones you have probably written before, and the difference is not stylistic. Once you see why they are built this way, a great deal of kernel code stops looking strange.

   IN USER-SPACE C, A LINKED LIST USUALLY HOLDS POINTERS TO
   YOUR DATA. Each node is a separate little allocation:

     +--------+      +--------+      +--------+
     | node   |---->| node   |---->| node   |
     | data*  |      | data*  |      | data*  |
     +---|----+      +---|----+      +---|----+
         v               v               v
     your struct     your struct     your struct

   THE KERNEL DOES THE OPPOSITE. The list node lives INSIDE
   your structure, as an ordinary member:

     struct my_device {
             int              id;
             char             name[16];
             struct list_head list;      <-- the node IS a
     };                                       member

     +---------------------+     +---------------------+
     | my_device           |     | my_device           |
     |   id, name          |     |   id, name          |
     |   list.next --------|---->|   list.next --------|-->
     |   list.prev <-------|-----|-- list.prev         |
     +---------------------+     +---------------------+

   THIS IS CALLED AN INTRUSIVE LIST, and the kernel uses it
   everywhere for three reasons:

     · NO EXTRA ALLOCATION. Adding an object to a list cannot
       fail, because there is nothing to allocate - which
       matters enormously in code that may be holding a
       spinlock or running out of memory (chapter 07).
     · ONE IMPLEMENTATION FOR EVERY TYPE. C has no generics,
       so a pointer-based list would need casting or macros
       per type. Here list.c is written once and works for
       every structure in the kernel.
     · AN OBJECT CAN BE ON SEVERAL LISTS AT ONCE simply by
       having several list_head members - a device can be on
       its bus's list and on a global list simultaneously.

   THE PRICE: given a `struct list_head *`, you are pointing
   at the MIDDLE of someone's structure and you need a way to
   get back to the start. That is what container_of does.

container_of: the trick that makes it work

The inside-out design leaves one problem to solve: if you are holding a pointer to a member in the middle of a structure, how do you get back to the structure itself? The answer is a small piece of pointer arithmetic you will see everywhere.

/* You have a pointer to the member. You want a pointer to
   the structure containing it. The compiler knows the
   member's OFFSET inside the type, so the answer is simple
   arithmetic:                                              */

        container_of(ptr, type, member)

/* which expands to roughly:

        (type *)( (char *)ptr - offsetof(type, member) )

   "take the address of the member, step BACKWARDS by however
   many bytes into the struct that member sits, and call the
   result a pointer to the whole struct."                   */

struct my_device {
        int              id;         /* offset 0            */
        char             name[16];   /* offset 4            */
        struct list_head list;       /* offset 24, say      */
};

        struct list_head *p = ...;              /* points at
                                                   offset 24 */
        struct my_device *d =
                container_of(p, struct my_device, list);
        /* p minus 24 = the start of my_device. Done.       */

/* YOU HAVE ALREADY SEEN THIS WITHOUT NOTICING. It is how a
   driver gets from the generic object the kernel handed it
   back to its OWN state:

     to_platform_device(dev)   is container_of on struct device
     gpiochip_get_data(gc)     does the equivalent (chapter 29)
     from_timer(d, t, timer)   the same, for timers (ch. 15)

   Every subsystem that hands you a generic pointer expects
   you to walk back to your own structure this way. It is not
   a trick used occasionally - it is the fundamental idiom of
   kernel C.                                                */

The list API you will actually use

The API is small and you will use perhaps six of its calls constantly. The one thing to read carefully is the difference between the two iteration macros, because choosing wrongly produces a bug that does not crash immediately.

#include <linux/list.h>

struct my_driver_state {
        struct list_head devices;   /* the list HEAD        */
        struct mutex     lock;      /* protects the list    */
};

struct my_device {
        int              id;
        struct list_head node;      /* the list MEMBER      */
};

/* CREATE - two ways, depending on where it lives */
        LIST_HEAD(global_list);                  /* static  */
        INIT_LIST_HEAD(&state->devices);         /* dynamic */

/* ADD - and note this can never fail */
        list_add(&dev->node, &state->devices);       /* front */
        list_add_tail(&dev->node, &state->devices);  /* back  */

/* ITERATE - this is the one you will type most.
   Note it gives you `dev` directly, already container_of'd. */
        struct my_device *dev;

        list_for_each_entry(dev, &state->devices, node) {
                pr_info("device %d\n", dev->id);
        }

/* ITERATE WHILE DELETING - you MUST use the _safe form.
   The plain version reads dev->node.next to advance, and if
   you freed dev, that read is a use-after-free. The _safe
   form stashes the next pointer BEFORE running the body,
   which is exactly what makes deletion legal.              */
        struct my_device *dev, *tmp;

        list_for_each_entry_safe(dev, tmp, &state->devices, node) {
                list_del(&dev->node);
                kfree(dev);
        }

/* REMOVE */
        list_del(&dev->node);        /* poisons the pointers -
                                        touching them after this
                                        oopses LOUDLY, on
                                        purpose                */
        list_del_init(&dev->node);   /* leaves it valid+empty,
                                        so list_empty() works  */

/* TEST */
        if (list_empty(&state->devices))
                ...

/* THE LIST IS NOT THREAD-SAFE. list_add and list_del are
   plain pointer writes with no locking whatsoever. YOU hold
   the lock (chapter 12), or you use the RCU variants
   (list_add_rcu / list_for_each_entry_rcu, chapter 14) for
   read-mostly lists.                                       */
The most common list bug, and why _safe exists

Deleting entries inside a plain list_for_each_entry() loop is the classic beginner mistake and it produces a use-after-free that may not crash until much later, somewhere unrelated. The loop advances by reading dev->node.next after your loop body has run — so if the body freed dev, that read touches freed memory. Use list_for_each_entry_safe() whenever the body might delete or free, and turn on CONFIG_DEBUG_LIST and KASAN in development (chapter 18), which catch exactly this.

The rest of the toolkit, and when to reach for each

Lists are the default and cover most needs, but the kernel provides several other structures for cases where a linear scan is the wrong shape. Each of these exists because a real subsystem needed it, and knowing they exist stops you from hand-rolling a worse version.

/* kfifo is worth showing, because chapters 07 and 12 both
   USE it and neither stops to explain it. It is a ring
   buffer with the index arithmetic already correct:       */

#include <linux/kfifo.h>

struct my_dev {
        DECLARE_KFIFO(fifo, struct my_event, 128);  /* MUST be
                                                       a power
                                                       of two  */
};
        INIT_KFIFO(d->fifo);

        /* producer - returns 0 if full, never blocks */
        if (!kfifo_put(&d->fifo, event))
                dev_warn(dev, "fifo full, event dropped\n");

        /* consumer - returns 0 if empty */
        while (kfifo_get(&d->fifo, &event))
                handle(event);

/* WITH EXACTLY ONE PRODUCER AND ONE CONSUMER, kfifo needs no
   lock at all - the two sides touch different indices and
   the barriers are inside. With more than one of either, you
   lock it yourself. This is why it is so common between an
   interrupt handler (producer) and a workqueue or read()
   (consumer) - chapters 15 and 36.                         */

Object lifetime: who frees this, and when?

Now the second half of the chapter, and a question that causes more crashes than any other in driver work: when several parts of the kernel hold a pointer to the same object, which of them is responsible for freeing it?

   THE PROBLEM, IN ITS SIMPLEST FORM:

     Your driver allocates a struct my_device.
     It is on a list. An interrupt handler has a pointer to
     it. A workqueue item has a pointer to it. A user process
     has it open through a file descriptor.

     NOW THE DEVICE IS UNPLUGGED. Who calls kfree?

   IF THE ANSWER IS "remove() does", YOU HAVE A BUG. remove()
   runs when the device goes away, but the workqueue item may
   still be queued and the user's file descriptor is still
   open. Freeing now means every one of those becomes a
   use-after-free.

   THE ANSWER IS REFERENCE COUNTING: the object is freed by
   WHOEVER PUTS THE LAST REFERENCE, which may be any of them,
   and nobody needs to know which one they are.

     get  ->  "I am keeping a pointer; do not free this"
     put  ->  "I am done with my pointer"
     when the count reaches zero, the object frees itself.
/* refcount_t - a plain counter, when YOU still control the
   freeing. It is an atomic_t that SATURATES instead of
   wrapping: overflow and use-after-free-by-underflow are
   detected and warn, rather than silently corrupting.     */

        refcount_t users;
        refcount_set(&d->users, 1);
        refcount_inc(&d->users);
        if (refcount_dec_and_test(&d->users))
                kfree(d);              /* the last one frees */

/* NEVER use a plain int for this, and prefer refcount_t over
   atomic_t for counts that control lifetime - the saturation
   behaviour is a real security property, not a nicety.    */


/* kref - the same idea, packaged with the release callback,
   so the freeing rule lives in ONE place instead of at every
   put site.                                               */

#include <linux/kref.h>

struct my_device {
        struct kref      refcount;
        struct list_head node;
        void            *buffer;
};

static void my_device_release(struct kref *kref)
{
        struct my_device *d =
                container_of(kref, struct my_device, refcount);
        /* container_of again - the kref does not know what
           contains it, so we walk back.                    */

        kfree(d->buffer);
        kfree(d);
}

        /* creation: the count starts at 1, held by whoever
           created it                                       */
        kref_init(&d->refcount);

        /* anyone taking a lasting pointer */
        kref_get(&d->refcount);

        /* everyone, when finished. Only the LAST one causes
           my_device_release to run.                        */
        kref_put(&d->refcount, my_device_release);

/* THE RULE THAT MAKES IT CORRECT: take the reference BEFORE
   publishing the pointer anywhere another thread could find
   it, and drop it only after you can no longer reach it.
   A get() that happens after the object is already
   discoverable is a race, not a reference.                */
Where you have already been using this without knowing

struct device contains a kobject, which contains a reference count — which is why get_device() and put_device() exist and why a device's release callback, not remove(), is what finally frees it. The same applies to struct file (chapter 41: the inode outlives the last name because open descriptors hold references) and to modules (.owner = THIS_MODULE in chapter 24 takes a reference on your module while a file is open). Reference counting is not an advanced technique you graduate to — it is already underneath everything you have written so far.

Why devm_ does not remove the need for this

Chapter 33's managed allocations free themselves when the device unbinds, which covers the common case completely and is why most driver code needs no explicit refcounting at all. What devm_ cannot do is keep an object alive past unbind — and that is exactly the situation reference counting exists for. If a user process can still hold your object open after the device is gone, or a work item can still be queued against it, then unbind is not the right moment to free it, and devm_ is the wrong tool for that particular allocation.
