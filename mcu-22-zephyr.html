Zephyr in practice

Zephyr is not FreeRTOS with more features — it is a different proposition. FreeRTOS gives you a scheduler and leaves the system to you; Zephyr gives you a whole operating system with device drivers, a device tree, a build system and a networking stack, and asks you to work its way.

The essential difference

FreeRTOSZephyr
What it isA scheduler and IPC primitivesA complete RTOS with drivers, subsystems and a build system
Hardware descriptionYour code, vendor HALDevice tree, as in Linux
ConfigurationOne headerKconfig, as in Linux
BuildYour Makefile or IDEwest plus CMake
DriversVendor HAL, per-chipPortable driver API across all supported chips
Footprint~6 kB flash minimum~20 kB minimum, realistically much more
Learning curveAn afternoonGenuinely a week or two
Board supportYou write it750+ boards supported upstream

The trade is legibility against leverage. FreeRTOS is small enough to read in a day; you will never wonder what it is doing. Zephyr abstracts the hardware so completely that the same application source builds for an nRF52, an STM32 and a RISC-V part — but understanding why something does not work means learning device tree, Kconfig and the driver model first.

Device tree: hardware as data

/* Zephyr borrows the device tree wholesale from Linux (see
   the Linux track, chapter 18). Hardware is DESCRIBED, not
   coded.                                                   */

/* boards/arm/my_board/my_board.dts */
/ {
    aliases {
        status-led = &led0;
        sensor-bus = &i2c1;
    };

    leds {
        compatible = "gpio-leds";
        led0: led_0 {
            gpios = <&gpioa 5 GPIO_ACTIVE_HIGH>;
            label = "Status LED";
        };
    };
};

&i2c1 {
    status = "okay";
    clock-frequency = <I2C_BITRATE_FAST>;

    bme280@76 {
        compatible = "bosch,bme280";
        reg = <0x76>;
    };
};

/* The application never names a pin, a port or a register: */

#include <zephyr/drivers/gpio.h>

static const struct gpio_dt_spec led =
    GPIO_DT_SPEC_GET(DT_ALIAS(status_led), gpios);

int main(void)
{
    if (!gpio_is_ready_dt(&led)) {
        return -ENODEV;
    }
    gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE);

    for (;;) {
        gpio_pin_toggle_dt(&led);
        k_msleep(500);
    }
}

/* This source is portable across every supported board. Move
   to different silicon and you change the .dts, not the
   application. That is the leverage Zephyr is selling, and
   on a product line with several hardware variants it is a
   very large saving.

   The macros are resolved at COMPILE time - devicetree.h is
   generated from the .dts during the build - so there is no
   runtime parsing cost, unlike Linux.                       */
Device tree errors are compile-time and cryptic

A missing node or a typo'd alias produces an error inside a generated header, pointing at a macro expansion rather than your .dts. The habit that saves hours: after any device tree change, read build/zephyr/zephyr.dts — the fully merged and resolved tree — rather than your fragment. It shows what the build actually concluded, including everything the SoC's own .dtsi files contributed.

The kernel API

/* Same concepts as chapter 19, different spelling, and
   static definition is idiomatic rather than exceptional.  */

#include <zephyr/kernel.h>

/* Threads. Note K_THREAD_DEFINE creates it at BOOT with no
   runtime allocation - the Zephyr default style.           */
K_THREAD_DEFINE(sensor_tid, 1024, sensor_thread,
                NULL, NULL, NULL,
                5,        /* priority: LOWER = more urgent,
                             the OPPOSITE of FreeRTOS and the
                             same as the NVIC. Cooperative
                             priorities are negative.        */
                0, 0);

/* Message queue - the queue of chapter 19. */
K_MSGQ_DEFINE(sensor_q, sizeof(struct reading), 10, 4);

void sensor_thread(void *a, void *b, void *c)
{
    struct reading r;
    while (1) {
        if (k_msgq_get(&sensor_q, &r, K_MSEC(100)) == 0) {
            process(&r);
        }
    }
}

/* From an ISR - note there is no separate FromISR API.
   Zephyr's calls detect ISR context themselves and require
   only that you pass K_NO_WAIT.                            */
void my_isr(const void *arg)
{
    struct reading r = read_hw();
    k_msgq_put(&sensor_q, &r, K_NO_WAIT);   /* must not block */
}

/* Other primitives, mapping onto chapter 19:
     k_mutex      mutex, with priority inheritance
     k_sem        counting semaphore
     k_event      event flags
     k_fifo/lifo  linked-list queues, no copy
     k_work       deferred work to a system workqueue -
                  the standard "get it out of the ISR"
                  mechanism, equivalent to a Linux workqueue

   K_FOREVER, K_NO_WAIT and K_MSEC(n) replace FreeRTOS's
   portMAX_DELAY and tick arithmetic, and are type-safe.    */

Kconfig and west

# prj.conf - application configuration, Kconfig syntax
CONFIG_GPIO=y
CONFIG_I2C=y
CONFIG_SENSOR=y
CONFIG_BME280=y
CONFIG_LOG=y
CONFIG_LOG_DEFAULT_LEVEL=3
CONFIG_MAIN_STACK_SIZE=2048
CONFIG_THREAD_ANALYZER=y          # stack watermarks, ch 20
CONFIG_THREAD_ANALYZER_AUTO=y

# Build and flash
$ west build -b nucleo_f429zi app/
$ west flash
$ west debug

# Inspect what Kconfig actually resolved to - symbols have
# dependencies, and one you set may be silently disabled
# because its prerequisite is off. This file is the truth:
$ less build/zephyr/.config

# Change configuration interactively, which also SHOWS the
# dependency that is blocking a symbol:
$ west build -t menuconfig

/* The most common Zephyr frustration by far: "I set
   CONFIG_FOO=y and it had no effect." Almost always FOO
   depends on BAR which is not enabled, and Kconfig silently
   dropped it. menuconfig's search (press /) tells you the
   dependency chain immediately.                            */

Choosing between them

SituationChoice
32 kB flash, one board, fixed scopeFreeRTOS, or no RTOS at all
You need BLE, Wi-Fi, USB or TCP/IPZephyr — the stacks are integrated and maintained
Several hardware variants of one productZephyr — the device tree pays for itself quickly
Vendor supplies a FreeRTOS BSP and examplesFreeRTOS — swimming with the current
You must read and justify every line for certificationFreeRTOS, or a certified kernel like SAFERTOS
Long-lived product needing upstream security fixesZephyr — an active foundation and a real release cadence
Team already knows Linux device tree and KconfigZephyr — the concepts transfer directly
You need it working this weekFreeRTOS

How it shows up

SymptomCause
CONFIG_FOO=y has no effectAn unmet Kconfig dependency; check build/zephyr/.config
Cryptic error inside a generated headerDevice tree node or alias missing — read the merged zephyr.dts
gpio_is_ready_dt returns falseThe controller's node has status = "disabled"
Device not found at runtimeDriver not enabled in Kconfig even though the node exists
Priorities behave backwards versus FreeRTOSZephyr uses lower = more urgent, and negative for cooperative
Kernel call hangs the system from an ISRA timeout other than K_NO_WAIT passed in interrupt context
Build succeeds, board does nothingWrong board target — the binary is for different silicon
Binary far larger than expectedLogging, shell or asserts left enabled in a release build
Stack overflow in the system workqueueLong work items — raise CONFIG_SYSTEM_WORKQUEUE_STACK_SIZE
Cannot find where a pin is configuredIt is in the pinctrl node of the board's .dts, not in code
