TrustZone: the NS bit

Everything about TrustZone follows from one design decision: add a single extra bit to every bus transaction saying which world it came from, then teach every block in the SoC to respect it. One wire, system-wide.

The whole idea

The rule

A Non-secure master cannot access Secure resources. A Secure master can access both.

This is enforced in hardware — at the memory controller, at each peripheral, at the interrupt controller, at the SMMU and on the interconnect itself. Not by software checks that a compromised kernel could skip.

The bit is AxPROT[1] on AXI (ARM chapter 25), universally called
the NS bit:

   NS = 0   this access is SECURE
   NS = 1   this access is NON-SECURE

   CPU core                       peripheral / memory
      |                                  ^
      |  ADDR                            |
      |  DATA                            |
      |  AxPROT[1] = NS  ----------------+  checked HERE
      |  AxID = master id
      |  AxCACHE = attributes

  Where NS comes from, for a CPU access:
     · at EL3, from SCR_EL3.NS
     · at EL0/EL1/EL2, from the current SECURITY STATE, which
       EL3 set via SCR_EL3.NS before dropping down
     · plus the page descriptor's NS bit, for Secure software
       creating a mapping that issues Non-secure accesses
       (ARM chapter 14)

  Where it comes from for a DEVICE access:
     · hard-wired per master, or
     · from the SMMU's STE/CD NSCFG fields (chapter 04), or
     · assigned dynamically by a TZPC (chapter 10)

Why this differs from a hypervisor

TrustZone is often described as a second processor or a special mode. It is neither: it is one extra bit carried with every transaction, and nearly everything else follows mechanically from that.

   HYPERVISOR ISOLATION            TRUSTZONE ISOLATION
   --------------------            -------------------
   software isolating software     SILICON isolating silicon
   the hypervisor is code that     the NS bit is a WIRE; the
     can have bugs                   memory controller physically
   a guest escape gives you the      refuses the transaction
     hypervisor's privilege        a compromised EL1 with
   stage-2 tables are configured     arbitrary code execution
     by that software                still cannot read Secure DRAM
                                     — the data never comes back

  Both are useful, and they compose: a system can run a
  hypervisor in the Normal world AND have a Secure world beneath
  both. They defend against different things.

  The practical distinction: a hypervisor protects guests from
  each other, assuming the hypervisor is correct. TrustZone
  protects secrets from the ENTIRE normal-world software stack,
  assuming only that EL3 firmware and the hardware are correct.

Security state versus exception level

The security state is a property of execution, not of a core, and it changes at defined moments. Knowing exactly when it changes is what makes the world switch comprehensible.

/* These are ORTHOGONAL. A context is identified by BOTH. */

                   Non-secure          Secure
   EL0             applications        trusted applications
   EL1             Linux, Windows      trusted OS (OP-TEE)
   EL2             hypervisor          secure partition mgr (v8.4+)
   EL3             ------- the monitor, in BOTH -------

/* Which security state am I in? There is no register that says
   so directly at EL1 — by design. Secure software knows because
   it was loaded into the secure world; Non-secure software
   cannot tell and should not need to.

   At EL3: */
        mrs     x0, scr_el3
        tst     x0, #1                  /* SCR_EL3.NS */
        /* NS=0: the world below is Secure
           NS=1: the world below is Non-secure */

/* SCR_EL3.NS is the ONE bit that selects which world exists
   below EL3. Changing it and executing ERET is the world
   switch (chapter 11).                                    */

Banked state

Many system registers exist twice — once per security state — so that the two worlds cannot observe or disturb each other's configuration. Which registers are banked is worth knowing before you debug across the boundary.

Because the two worlds must not see each other's configuration,
much of the EL1 system register file is BANKED by security
state:

   SCTLR_EL1        one for Secure, one for Non-secure
   TTBR0_EL1        ditto — the two worlds have entirely
   TTBR1_EL1        separate page tables
   TCR_EL1
   MAIR_EL1
   VBAR_EL1         separate vector tables
   ESR_EL1, FAR_EL1, ELR_EL1, SPSR_EL1
   TPIDR_EL0/EL1
   ...

  SCR_EL3.NS selects which bank EL3 sees. So when the monitor
  switches worlds it does NOT have to save and restore these —
  the hardware provides two copies.

  What it DOES have to save and restore: the general-purpose
  registers X0-X30, the FP/SIMD state, and any registers that
  are NOT banked. That is the bulk of the world-switch cost
  (chapter 11).

  NOT banked: the caches and TLBs, which instead TAG their
  entries with the security state so entries from the two
  worlds coexist without leaking (chapter 10).

The NS bit in page tables

The NS bit appears in page-table descriptors too, which is how the secure world decides whether a mapping it creates reaches secure or non-secure memory. This is the page-table half of the mechanism.

/* Secure software can create a mapping that issues NON-SECURE
   accesses. That is how a trusted OS reads a buffer shared with
   the normal world.                                          */

   descriptor bit 5   NS
        0   accesses through this mapping are SECURE
        1   accesses through this mapping are NON-SECURE

/* Only meaningful in the SECURE translation regime. Non-secure
   software's accesses are always NS=1 regardless of what its
   descriptors say — enforced by hardware, not by the tables. */

/* And in TABLE descriptors there is a separate NSTable bit
   (bit 63): it forces every entry BELOW it to be Non-secure,
   whatever those entries claim. A way to delegate an entire
   subtree safely — useful when secure software builds a
   mapping region for shared buffers.                       */

/* The practical rule for secure software:
     · map your own memory NS=0
     · map shared buffers NS=1
     · NEVER map normal-world memory NS=0, or a normal-world
       pointer becomes a secure access                       */

Partitioning memory

Physical memory is partitioned by the same bit, enforced by hardware outside the processor. That is why secure memory is not merely protected from the normal world but genuinely invisible to it.

Physical memory as a TZASC (chapter 10) is typically configured
at boot:

  0x8000_0000  +--------------------------------+
               | Non-secure DRAM                |  NS=1 permitted
               |   Linux kernel + userspace     |  NS=0 also permitted
               |   ~1.9 GB                      |  (Secure can read it)
  0xFC00_0000  +--------------------------------+
               | SHARED buffer region           |  both worlds
               |   TEE message passing          |
  0xFE00_0000  +--------------------------------+
               | Secure DRAM                    |  NS=1 -> REFUSED
               |   OP-TEE OS + TA heap          |  invisible to Linux
  0xFF00_0000  +--------------------------------+
               | EL3 firmware (BL31)            |  Secure only, and
               |                                |  often LOCKED so even
  0xFF10_0000  +--------------------------------+  S-EL1 cannot write it

  What "refused" means concretely: the memory controller returns
  an error response, which becomes an external abort at the CPU
  (ARM chapter 29, DFSC 0b010000) — or, on some configurations,
  returns zeros silently. The latter is far harder to debug and
  is why chapter 20 exists.

  Note the LOCKED EL3 region: even the secure world's own OS
  cannot modify the monitor. Privilege inside a world is still
  layered.

The consequence worth internalising

A single bit is cheap to add to a bus, so it could be added everywhere. That is why TrustZone is a system-wide property rather than a CPU feature, and why an SoC that implements it partially — a peripheral that ignores the NS bit, a bus segment that drops it — has a complete bypass. Verifying that every block honours it is a real part of SoC security review.

The symptom this produces

"The peripheral reads back all zeros"

If a peripheral is marked Secure in the TZPC, a Linux driver that ioremap()s its registers gets an error or zeros — because the access carries NS=1 and the peripheral refuses it. The address is right, the clock is on, the driver is correct, and nothing works.

This is the single most confusing TrustZone symptom for driver authors, because nothing in the normal-world software stack knows the secure world exists. When a peripheral behaves as though it is not there on production hardware but works on a development board, suspect the security configuration before suspecting your driver.

/* What you see from Linux: */
        val = readl(base + REG_ID);
        /* val == 0, or 0xFFFFFFFF, or an external abort */

/* dmesg, if it aborts: */
//   Unhandled fault: synchronous external abort (0x96000010)
//                                                      ^^ DFSC
//                                                      external abort

/* How to confirm it is a security issue rather than a clock or
   address problem:
     1. check the clock and power domain first — same symptom
     2. read the SoC TRM for the peripheral's default TZPC
        assignment
     3. if firmware exposes it, query via an SMC
     4. compare against a development board, where the fuses
        and firmware configuration usually differ            */

What one bit does not give you

One bit provides a strong boundary and a surprisingly narrow one. These are the things it does not give you, each of which has been mistaken for a guarantee it never made.

Confirming the hardware honours it

Whether a given platform actually implements the enforcement blocks behind TrustZone varies, and a system with the architectural feature but without the enforcement hardware offers much weaker guarantees than it appears to.

/* During SoC bring-up or security review, test the NEGATIVE
   cases explicitly. A policy never exercised is a policy you do
   not know works.                                           */

/* From the Normal world, attempt to read Secure DRAM: */
        void __iomem *p = ioremap(SECURE_DRAM_BASE, 4);
        u32 v = readl(p);
        /* EXPECTED: an external abort, or a latched fault in the
           TZASC. If it returns real data, the region is not
           actually protected.                                */

/* From the Normal world, attempt to program a Secure device: */
        writel(1, secure_dev_base + CTRL);
        /* EXPECTED: refused. Verify by reading back, and by
           checking the peripheral did not act.               */

/* And from the Secure world, verify you CAN reach both: */
        secure read of Non-secure DRAM   -> should succeed
        secure read of Secure DRAM       -> should succeed

/* Write these as a boot-time self-test on development
   firmware. Chapter 19 covers building the full matrix.  */
