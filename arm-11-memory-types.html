Memory types: Normal versus Device

ARM tags every region of memory with a type that changes what the hardware is permitted to do with accesses to it — reorder them, merge them, speculate them, cache them. Choosing the wrong type is one of the most common and most confusing driver bugs, because the symptom rarely points at the cause.

Why a type is needed at all

RAM and registers are not the same thing

Reading RAM twice gives the same answer and costs nothing. Reading a FIFO register twice consumes two bytes. Writing RAM has no effect until someone reads it; writing a control register starts a motor.

The optimisations that make RAM fast — caching, speculation, write merging, reordering — are all incorrect for a peripheral. So the architecture provides a type that switches them off, and the page table says which is which.

The two types

Every one of these differences traces back to one fact: a peripheral register is not memory, even though you access it with a load or store instruction. RAM does not care how many times you read it, does not mind if the CPU speculatively reads an address "just in case", and does not care whether two adjacent bytes are combined into one wider access. A UART's status register cares about all three — reading it twice can consume a byte you never asked for, a speculative read can trigger a side effect that should never have happened, and merging two 8-bit register accesses into one 16-bit bus transaction can hit two registers that were never meant to be touched together. Device memory exists to switch all of that hardware behaviour off.

Device sub-types

Device memory is not one thing. The sub-types differ in what the processor may reorder, combine or repeat — and picking a more permissive one than your hardware tolerates produces failures that appear only under load.

Written Device-<G|nG><R|nR><E|nE>, each letter a permission:

   G / nG   GATHERING — may two accesses be merged into one
                        larger access, or one access split?
   R / nR   REORDERING — may accesses to DIFFERENT addresses in
                        this region be reordered with each other?
   E / nE   EARLY WRITE ACKNOWLEDGEMENT — may a write be
                        acknowledged before it reaches the
                        endpoint (i.e. buffered en route)?

   Device-nGnRnE   nothing allowed. The strictest.
                   Use for: control registers where every write
                   must land, in order, before the next.
                   MAIR encoding 0x00

   Device-nGnRE    early ack permitted, still no gathering or
                   reordering. The common default for most
                   peripherals — noticeably faster than nGnRnE
                   because writes need not stall.
                   MAIR encoding 0x04

   Device-nGRE     reordering permitted
                   MAIR encoding 0x08

   Device-GRE      everything permitted. Use for framebuffers and
                   large streaming windows, where throughput
                   matters and individual accesses have no
                   side effects.
                   MAIR encoding 0x0C

  Ordering of strictness: nGnRnE > nGnRE > nGRE > GRE

  Note that even the most relaxed Device type is NOT cacheable and
  NOT speculatable. Those two properties define "Device".

Normal memory cacheability

Ordinary memory can be cached in several different ways, and the choice is made per region rather than globally. The options matter most when memory is shared with something that is not a CPU.

/* Normal memory has independent INNER and OUTER cacheability
   attributes, each one of:                                   */

   Non-cacheable
   Write-Through,  Read-Allocate / Write-Allocate
   Write-Back,     Read-Allocate / Write-Allocate    ← the usual

/* "Inner" and "Outer" are implementation-defined boundaries.
   Typically Inner = the CPU cluster's caches (L1, L2), Outer =
   a system-level cache beyond it. Most software sets them the
   same.                                                       */

/* And a SHAREABILITY attribute, which is separate:            */
   Non-shareable       no coherency maintained
   Inner Shareable     coherent within the inner domain — this is
                       what SMP kernel memory uses
   Outer Shareable     coherent across a wider domain, including
                       some DMA masters

/* Shareability determines how far a barrier or a TLBI
   propagates (chapters 19 and 21). Getting it wrong gives you
   coherency bugs that only appear on multi-core.             */

MAIR: how a descriptor names a type

A page descriptor does not carry a memory type directly; it carries an index into a register that defines eight possible types. That indirection is why changing one register can alter the behaviour of every mapping at once.

A page table descriptor has only 3 bits for attributes (AttrIndx).
Three bits cannot encode all the combinations above, so ARM uses
INDIRECTION:

   MAIR_EL1 holds EIGHT 8-bit attribute values, one per slot.
   The descriptor's AttrIndx selects a slot.

   MAIR_EL1 = 0x00000000_0044FF04
                             ││ ││
                             ││ │└─ slot 0 = 0x04 Device-nGnRE
                             ││ └── slot 1 = 0xFF Normal WB RW-alloc
                             │└──── slot 2 = 0x44 Normal Non-cacheable
                             └───── slot 3 = 0x00 Device-nGnRnE

   Encoding of each byte:
      0x00        Device-nGnRnE
      0x04        Device-nGnRE
      0x08        Device-nGRE
      0x0C        Device-GRE
      0xFF        Normal, Inner+Outer WB, RW-allocate
      0x44        Normal, Inner+Outer Non-cacheable
      high nibble = Outer, low nibble = Inner (for Normal)

   Change MAIR and EVERY page using that slot changes type at
   once — which is convenient, and also a way to break the whole
   system with one register write.
/* Setting it up, in boot code */
#define MAIR_DEVICE_nGnRnE  0x00
#define MAIR_DEVICE_nGnRE   0x04
#define MAIR_NORMAL_NC      0x44
#define MAIR_NORMAL_WB      0xFF

#define IDX_DEVICE_nGnRnE   0
#define IDX_DEVICE_nGnRE    1
#define IDX_NORMAL_NC       2
#define IDX_NORMAL_WB       3

        uint64_t mair =
                ((uint64_t)MAIR_DEVICE_nGnRnE << (8 * IDX_DEVICE_nGnRnE)) |
                ((uint64_t)MAIR_DEVICE_nGnRE  << (8 * IDX_DEVICE_nGnRE))  |
                ((uint64_t)MAIR_NORMAL_NC     << (8 * IDX_NORMAL_NC))     |
                ((uint64_t)MAIR_NORMAL_WB     << (8 * IDX_NORMAL_WB));

        asm volatile("msr mair_el1, %0" :: "r"(mair));
        asm volatile("isb");            /* chapter 06 */

/* then a descriptor references a slot: */
        pte = pa | PTE_VALID | PTE_AF
                 | PTE_ATTR(IDX_DEVICE_nGnRE)   /* bits [4:2] */
                 | PTE_UXN | PTE_PXN;           /* never execute MMIO */

The bugs, and why they are confusing

MMIO mapped as Normal cacheable

This is the classic, and it produces four distinct failure modes that look unrelated:

  1. Writes never reach the device. They sit in a dirty cache line until eviction — which may be never, or may happen minutes later at an unrelated moment.
  2. Reads return stale values forever. The first read caches the line; every subsequent read hits the cache. A status register appears frozen.
  3. A FIFO drains spontaneously. Speculative execution reads addresses the program never touched. Reading a FIFO register pops it, so data vanishes with no code responsible.
  4. Writes are merged or reordered. A sequence that must be written in order arrives coalesced, and the device sees an illegal state transition.

The tell: it often works under a debugger (single-stepping defeats the caching and speculation) and fails at speed. If a peripheral "works in debug, fails in release", check the mapping attributes before anything else.

Normal memory mapped as Device

The reverse mistake is less dramatic but very costly: correctness is fine, performance collapses. No caching, no speculation, no merging — every access goes to DRAM individually. A memcpy through a Device-mapped buffer can be 50–100× slower than through Normal memory. This is a common cause of "why is my DMA buffer so slow to fill?".

/* Two more subtle ones: */

/* 1. Exclusives on Device memory are UNDEFINED. */
        /* A spinlock in a Device-mapped shared region will not
           work — LDXR/STXR need a coherent monitor that Device
           memory does not provide. Shared memory between a CPU
           and a device must be Normal Non-cacheable, not Device,
           if you intend to use atomics on it.                */

/* 2. Unaligned access to Device memory ALWAYS faults, even
      though the same code works on Normal memory.           */
        uint8_t *regs = ioremap(...);
        uint32_t v = *(uint32_t *)(regs + 1);   /* alignment fault */
        /* Which is why casting a byte pointer into a register
           block is a bug, and why register structs must have
           explicit padding (C chapter 07).                   */

How the OS picks the type for you

In practice you rarely set these yourself — the operating system chooses based on which API you called. Knowing the mapping from API to memory type is what lets you predict the behaviour you will get.

/* Linux — the mapping function encodes the choice: */

ioremap(phys, size)          /* Device-nGnRE — the default for MMIO */
ioremap_np(phys, size)       /* Device-nGnRnE — "non-posted", for
                                registers needing strict ordering  */
ioremap_wc(phys, size)       /* Normal Non-cacheable, write-combining
                                — framebuffers, large windows      */
ioremap_cache(phys, size)    /* Normal cacheable — ROM, or memory
                                the device does not modify         */
memremap(phys, size, MEMREMAP_WB)   /* explicitly Normal WB        */

/* And the accessors that go with them: */
readl(addr) / writel(v, addr)               /* with barriers        */
readl_relaxed() / writel_relaxed()          /* without              */

/* Windows */
MmMapIoSpaceEx(pa, len, PAGE_READWRITE | PAGE_NOCACHE);
MmMapIoSpaceEx(pa, len, PAGE_READWRITE | PAGE_WRITECOMBINE);
READ_REGISTER_ULONG / WRITE_REGISTER_ULONG

/* In device tree, a region's cacheability for DMA is expressed
   separately, by whether the device is coherent:              */
        dma-coherent;         /* device participates in coherency  */
        no-map;               /* kernel must not map this at all   */

DMA buffers: the third case

Memory shared with a device is the case where all of this becomes unavoidable, because two different agents with different caching behaviour are looking at the same bytes.

A DMA buffer is Normal memory, but WHICH Normal memory depends on
whether the device is coherent:

  COHERENT DEVICE (ACE-Lite, CHI, `dma-coherent` in DT)
     map Normal Write-Back Inner-Shareable
     the interconnect keeps the device's view coherent with the
     CPU's caches — no maintenance needed
     dma_alloc_coherent() gives you cacheable memory

  NON-COHERENT DEVICE
     option A: Normal Non-cacheable
               simple and correct, but CPU access is slow
               dma_alloc_coherent() gives you this on such systems
     option B: Normal Write-Back plus explicit cache maintenance
               fast CPU access, but you must clean before the
               device reads and invalidate before you read what
               it wrote (chapter 18, CA chapter 15)
               dma_map_single() / dma_sync_* do this for you

  NEVER map a DMA buffer as Device. It is memory, not registers:
  you want the CPU side to be fast, and the device does not care.

  This is precisely why you must use the DMA API rather than
  choosing yourself — it knows which case applies.

Checking what you got

When a device sees stale data or a write appears to vanish, the memory type is the first suspect. These are the ways to find out what attributes a mapping actually has, rather than what you intended.

# Linux: what is mapped where, and how
cat /proc/vmallocinfo | grep ioremap
#   0xffff800010000000-0xffff800010002000  8192 ioremap ...

cat /proc/iomem                    # physical resource map
cat /proc/self/pagemap             # per-page details (needs root)

# read MAIR and a descriptor from a debug module
pr_info("MAIR_EL1 = %016llx\n", read_sysreg(mair_el1));

# in gdb on a bare-metal target
p/x $MAIR_EL1
p/x $TCR_EL1
# then walk the tables by hand for the address in question
# (chapter 13) and read AttrIndx from bits [4:2]

# the AT instruction asks the hardware to translate for you
        at      s1e1r, x0          // stage-1, EL1, read
        mrs     x1, par_el1        // result: PA plus attributes
/* PAR_EL1 reports the memory attributes actually applied —
   the definitive answer to "how is this address mapped?"   */
AT plus PAR_EL1 is the debugging tool to remember

Rather than walking page tables by hand, ask the MMU. AT S1E1R, Xn performs a translation and writes the resulting physical address and its memory attributes into PAR_EL1. If the translation fails, PAR_EL1.F is set and the fault status tells you why. This answers "is this address mapped, and as what?" in two instructions, from a live system.
