start_kernel and initcalls

One function, about a hundred calls, and by the end the kernel is fully alive. Understanding its order is what lets you answer the two questions that dominate bring-up: why is my driver probing too early, and where exactly did it hang.

The order, and why it is that order

start_kernel() is a long, flat list of initialisation calls, and the order is not a matter of taste — each entry depends on the ones above it having already run. Reading it from top to bottom is genuinely the fastest way to understand what a kernel is actually made of.

Three lines to remember
  • mm_core_init() — before this, no kmalloc. Early code uses memblock instead.
  • local_irq_enable() — before this, nothing is asynchronous. No timers, no interrupts, no preemption.
  • console_init() — before this, printk output goes into a ring buffer and is only flushed once a console exists. A crash before it, without earlycon, is silent.

Initcalls: how everything else runs

A kernel contains thousands of subsystems and drivers, all of which need initialising. Keeping one central list of them would be unmaintainable and would mean every new driver had to edit a shared file, so the kernel uses a neat trick instead: each piece of code registers itself, and the kernel simply walks the registrations.

/* The kernel has thousands of subsystems and drivers to
   initialise. Rather than a giant list of calls, each one
   REGISTERS itself into a section of the binary, and the
   kernel walks those sections in order.                     */

static int __init my_init(void)
{
        pr_info("hello\n");
        return 0;                /* 0 = success. Non-zero is
                                    logged but boot continues. */
}
subsys_initcall(my_init);

/* The macro puts a POINTER to my_init into a section named
   .initcall4.init. The linker script gathers all such
   sections in order, and do_initcalls() walks them.        */

/* THE LEVELS, in execution order: */

  early_initcall          before most things; very restricted
  pure_initcall           0    no dependencies at all
  core_initcall           1    core subsystems
  postcore_initcall       2
  arch_initcall           3    architecture-specific
  subsys_initcall         4    BUSES register here
                               (platform, i2c, spi, pci)
  fs_initcall             5    filesystems
  rootfs_initcall         rootfs
  device_initcall         6    <-- MOST DRIVERS. module_init()
                                   becomes this when built in.
  late_initcall           7    things needing everything else

  and each has a _sync variant that waits for outstanding
  asynchronous work before the next level begins.

/* WHY THE LEVELS EXIST: a driver at device_initcall can rely
   on its bus existing, because buses registered at
   subsys_initcall. Ordering WITHIN a level is link order -
   i.e. Makefile order - which you must never depend on.

/* module_init() is level 6 when built in, and simply "when
   insmod runs" when built as a module. That difference is why
   a driver can work as a module and fail built-in, or the
   reverse.                                                 */

/* DO NOT solve ordering problems by changing your initcall
   level. That is the classic wrong fix - it works on your
   board and breaks on the next one. Use -EPROBE_DEFER
   instead (chapter 19).                                    */

Watching it happen

All of that initialisation is observable. With one command-line option the kernel prints every initcall as it runs, in order, with the time each one took — which turns boot from something you guess about into something you can measure.

# initcall_debug on the command line:

    calling  gic_of_init+0x0/0x1a4 @ 1
    initcall gic_of_init+0x0/0x1a4 returned 0 after 1953 usecs
    calling  my_driver_init+0x0/0x28 @ 1
    initcall my_driver_init+0x0/0x28 returned -517 after 12 usecs
                                              ^^^^
                                              -EPROBE_DEFER

# READS AS:
#   "calling" with no matching "initcall ... returned"  -> IT
#     HUNG HERE. You just found your boot hang, by name.
#   returned -517  -> EPROBE_DEFER: a dependency was missing;
#     it will be retried later. Normal, not an error.
#   returned -19   -> ENODEV: no such device. Usually fine.
#   a huge "after N usecs" -> your boot-time regression.

# Sort the slow ones:
    dmesg | grep initcall | \
      sed 's/.*after \([0-9]*\) usecs/\1 &/' | sort -rn | head -20

# And the graphical version:
    systemd-analyze plot > boot.svg          # userspace
    cat /sys/kernel/debug/bootgraph          # with
                                             # CONFIG_BOOT_PRINTK

# printk timestamps, essential for any of this:
    printk.time=1        # or CONFIG_PRINTK_TIME=y

Handing over to user space

At some point the kernel has finished setting itself up and must start the first user-space program. That transition is more gradual than it sounds: the first process begins life as kernel code and only becomes a normal user program at the very last moment.

/* kernel_init() runs as PID 1, still in kernel mode: */

static int __ref kernel_init(void *unused)
{
        kernel_init_freeable();
             /* wait for async work
                do_basic_setup():
                   driver_init()          the device model
                   init_irq_proc()
                   do_ctors()
                   do_initcalls()      <-- ALL levels run here
                prepare_namespace()       mount the root fs */

        free_initmem();      /* __init code and data FREED.
                                "Freeing unused kernel memory:
                                 4096K" in dmesg. This is why
                                calling an __init function
                                later crashes.               */
        mark_readonly();

        /* Then try, in order: */
        if (execute_command) {          /* init= on cmdline */
                ret = run_init_process(execute_command);
                if (!ret) return 0;
                panic("Requested init %s failed (error %d).",
                      execute_command, ret);
        }

        if (!try_to_run_init_process("/sbin/init")  ||
            !try_to_run_init_process("/etc/init")   ||
            !try_to_run_init_process("/bin/init")   ||
            !try_to_run_init_process("/bin/sh"))
                return 0;

        panic("No working init found.  Try passing init= ...");
}

/* THE TWO FAMOUS PANICS:

   "Kernel panic - not syncing: VFS: Unable to mount root fs
    on unknown-block(0,0)"
        the ROOT FILESYSTEM was not found. Causes: wrong
        root=, the storage driver not built in (a module in an
        initramfs you did not supply), the filesystem type not
        compiled in, or the partition table not read.
        Look at the "Available partitions:" list the kernel
        prints just above - if it is empty, the storage driver
        never probed.

   "No working init found."
        the root filesystem MOUNTED but has no init. Wrong
        rootfs image, missing /sbin/init, a dynamically linked
        init with no libraries, or the wrong architecture
        binaries.
        Try init=/bin/sh to get a shell and look around.    */
init=/bin/sh is the debugging trapdoor

It skips the entire init system and drops you at a shell with the root filesystem mounted. From there you can check what is present, load modules by hand, and read /proc. If that works, the problem is in userspace, not the kernel — which halves the search space in one boot.

Kernel parameters

Kernel parameters are the strings on the boot command line — console=ttyS0, root=/dev/mmcblk0p2 and so on. There are two separate mechanisms for handling them, they run at very different times, and picking the wrong one gives you a value that is not there yet when you read it.

/* Two mechanisms, easily confused. */

/* 1. early_param - parsed in setup_arch(), very early, for
      things that must be known before memory is set up:   */

static int __init parse_my_option(char *p)
{
        my_value = memparse(p, &p);
        return 0;
}
early_param("my_option", parse_my_option);
        /* command line:  my_option=64M */

/* 2. module_param - a variable exposed as a parameter,
      settable at insmod time or via the command line:     */

static int buffer_size = 4096;
module_param(buffer_size, int, 0644);
MODULE_PARM_DESC(buffer_size, "Ring buffer size in bytes");

        /* as a module:   insmod mydrv.ko buffer_size=8192
           built in:      mydrv.buffer_size=8192
           at runtime:    /sys/module/mydrv/parameters/buffer_size
                          (because the mode is 0644)        */

/* The permission argument is the sysfs mode. Use 0444 for
   read-only visibility, 0644 to allow runtime changes - and
   only if changing it at runtime is actually safe, which for
   a buffer size it usually is not.                        */

/* SEEING what was passed: */
        cat /proc/cmdline
        cat /sys/module/mydrv/parameters/*
        dmesg | grep "Kernel command line"

The ordering problem, properly solved

Here is a problem every driver author eventually hits: your driver needs a clock, a regulator or a GPIO that another driver provides, and that other driver has not started yet. It is tempting to solve this by making your driver start later, and that instinct is wrong in a way worth understanding properly.

/* THE SITUATION: your driver needs a clock, a regulator, a
   GPIO or a DMA channel that another driver provides - and
   that driver has not probed yet.

   THE WRONG FIXES:
     · changing your initcall level          (board-specific)
     · reordering the Makefile               (fragile, silent)
     · a retry loop with msleep()            (blocks boot)
     · initialising in module_init instead of probe (breaks
       hotplug and unbind)

   THE RIGHT FIX - return -EPROBE_DEFER: */

static int my_probe(struct platform_device *pdev)
{
        struct clk *clk;

        clk = devm_clk_get(&pdev->dev, "core");
        if (IS_ERR(clk))
                return dev_err_probe(&pdev->dev, PTR_ERR(clk),
                                     "failed to get core clock\n");
        ...
}

/* dev_err_probe() is the modern idiom: it logs at error level
   for real errors, at DEBUG level for -EPROBE_DEFER (so you
   are not spammed by the normal case), and returns the error.
   Use it for every resource acquisition in probe.

   The driver core keeps a DEFERRED PROBE LIST and retries
   everything on it whenever any new driver successfully
   probes. Eventually the dependency appears and you succeed -
   in any link order, on any board.                         */

/* WHEN IT NEVER RESOLVES: */
        cat /sys/kernel/debug/devices_deferred
   lists every device still waiting, and why. If your device is
   there at the end of boot, the provider driver is missing,
   not merely late - a missing CONFIG, or a DT node that does
   not match anything.                                      */
