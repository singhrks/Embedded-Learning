TCG: how emulation actually works

QEMU does not interpret instructions one at a time — that would be a hundred times slower still. It translates blocks of guest code into host code, caches them, and chains them together so that straight-line guest execution never returns to the translator. Understanding that machinery explains every performance surprise and every debugging limitation you will meet.

Translate, cache, chain

   guest PC = 0x40080000, nothing cached
        |
        v
   +--------------------------------------------------+
   | 1. FIND: is there a translation block for this   |
   |    (PC, CPU flags, MMU mode)?  No.               |
   +--------------------------------------------------+
        |
        v
   +--------------------------------------------------+
   | 2. TRANSLATE. Decode guest instructions from the |
   |    PC until a branch, a system instruction, or a |
   |    page boundary. Emit TCG IR - a small, target- |
   |    independent RISC-like intermediate language.  |
   +--------------------------------------------------+
        |
        v
   +--------------------------------------------------+
   | 3. OPTIMISE the IR: dead code, constant folding, |
   |    liveness. Cheap passes only - translation time|
   |    is on the critical path.                      |
   +--------------------------------------------------+
        |
        v
   +--------------------------------------------------+
   | 4. EMIT host machine code into the code cache.   |
   +--------------------------------------------------+
        |
        v
   +--------------------------------------------------+
   | 5. EXECUTE it. Guest registers live in a struct  |
   |    (CPUARMState); the emitted code loads and     |
   |    stores them.                                  |
   +--------------------------------------------------+
        |
        v
   +--------------------------------------------------+
   | 6. CHAIN. If the block ends in a direct branch   |
   |    to a block already translated, PATCH the jump |
   |    so it goes straight there next time, without  |
   |    returning to the dispatcher at all.           |
   +--------------------------------------------------+

   A hot loop therefore becomes host code jumping directly to
   host code. The translator runs once. That is why TCG is
   10-50x slower than native and not 1000x.

Helpers: the escape hatch

/* Some guest instructions are too complex to express in 150 IR
   operations. For those, TCG emits a CALL to a C function
   called a HELPER.                                          */

/* target/arm/helper.c - a real one, simplified: */

void HELPER(msr_i_daifset)(CPUARMState *env, uint32_t imm)
{
        env->daif |= (imm << 6) & PSTATE_DAIF;
        arm_rebuild_hflags(env);
}

/* And in the translator, target/arm/translate-a64.c: */

    gen_helper_msr_i_daifset(cpu_env, tcg_constant_i32(imm));

/* What becomes a helper:
     - system register access
     - MMU translation (the slow path; the fast path is the
       software TLB, below)
     - floating point and SIMD, mostly
     - cryptographic instructions
     - anything touching CPU mode or exception state

   What stays in IR:
     - arithmetic, logic, shifts
     - loads and stores (fast path)
     - branches

   A helper call costs a real host function call, so an
   instruction that becomes a helper is far slower than one
   that does not. This is why FP-heavy code is
   disproportionately slow under TCG, and why crypto benchmarks
   inside QEMU are meaningless.                              */

The software TLB

   Every guest load and store needs a guest-virtual to
   host-virtual translation. Doing a full page-table walk in
   software per access would be catastrophic, so TCG keeps a
   direct-mapped software TLB and inlines the lookup.

   Emitted code for a guest LDR, conceptually:

     index = (guest_addr >> 12) & (CPU_TLB_SIZE - 1)
     entry = env->tlb_table[mmu_idx][index]

     if (entry.addr_read == (guest_addr & TARGET_PAGE_MASK)) {
             /* FAST PATH: a few host instructions            */
             host_addr = guest_addr + entry.addend;
             value = *(uint64_t *)host_addr;
     } else {
             /* SLOW PATH: call a helper that walks the guest
                page tables, fills the TLB entry, and may
                raise a guest fault - or dispatches to a
                DEVICE MODEL if the address is MMIO.          */
             value = helper_ldq_mmu(env, guest_addr, oi, ra);
     }

   Consequences you can feel:

   * A guest that thrashes its own TLB thrashes QEMU's too, and
     the slow path is a C function call plus a walk.
   * MMIO is ALWAYS the slow path, by construction - that is
     how device models get called.
   * mmu_idx encodes the exception level and translation
     regime, so a guest that switches EL frequently invalidates
     less than you would fear but still pays.
   * Flushing: any guest TLBI causes QEMU to flush its software
     TLB. A guest doing aggressive TLB maintenance is slow
     under TCG for a reason that does not exist on hardware.

Self-modifying code and page protection

/* The cached translation is only valid while the guest code it
   came from is unchanged. If the guest rewrites its own
   instructions - JIT compilers, bootloaders relocating
   themselves, module loaders - QEMU must notice.

   Mechanism: any guest page that has been translated is
   marked, and writes to it are detected. The affected
   translation blocks are invalidated and retranslated.     */

  Symptoms of a guest that fights this:

    * A JIT (a JVM, V8, or the kernel's BPF JIT) inside a TCG
      guest is dramatically slower than the rest of the guest,
      because it repeatedly invalidates translations.

    * A guest that writes data into the same PAGE as code -
      even not overlapping the code - triggers invalidation.
      Literal pools next to code, or a bootloader keeping
      variables in its text section, do this.

  Tuning the code cache, which matters for large guests:

$ qemu-system-aarch64 -accel tcg,tb-size=512 ...
      # 512 MB of translation cache. Default is smaller and is
      # sized from RAM. A large kernel plus a large userspace
      # can thrash a small cache, and the symptom is a guest
      # that gets SLOWER the longer it runs.

$ qemu-system-aarch64 -accel tcg,one-insn-per-tb=on ...
      # one guest instruction per block. Very slow, but exact:
      # every instruction boundary is a block boundary, so
      # breakpoints, tracing and -d exec become precise.
What TCG does not model

Caches, pipelines, branch prediction, memory latency, DVFS, and real interrupt timing. A cycle count from TCG is not merely inaccurate — it is meaningless. Use TCG to prove that logic is correct and to observe what the guest did; use hardware or KVM to find out how long it takes.

TCG plugins

# Since QEMU 4.2 you can load a shared library that gets called
# on translation and execution events. This is the closest
# thing to a hardware trace probe that costs nothing.

$ ls /usr/lib/qemu/         # or build them from tests/plugin/
libinsn.so  libmem.so  libhotblocks.so  libhotpages.so
libcache.so libhowvec.so

# Count every instruction executed:
$ qemu-aarch64 -plugin /usr/lib/qemu/libinsn.so -d plugin ./workload
insns: 48120311

# Find the hottest basic blocks:
$ qemu-system-aarch64 -M virt -kernel Image \
    -plugin /usr/lib/qemu/libhotblocks.so -d plugin ...
collected 25011 entries
pc, hits, insns
0x40081234, 1204551, 12
0x40095678,  883012,  8

# Model a cache and count misses - a real one, not a guess:
$ qemu-system-aarch64 ... \
    -plugin /usr/lib/qemu/libcache.so,dcachesize=32768,\
dassoc=4,dblksize=64

# Trace every memory access:
$ qemu-aarch64 -plugin /usr/lib/qemu/libmem.so,inline=on ./prog

# Writing your own is ~100 lines: register callbacks in

# This is how you answer "how many times does my driver touch
