Number theory for public-key cryptography

The minimum mathematics needed to understand what RSA, Diffie–Hellman and elliptic curves actually do — and, more importantly, what makes them hard to break and easy to implement wrongly.

Modular arithmetic

Public-key cryptography rests on arithmetic in a finite set rather than on the integers. The rules are close enough to ordinary arithmetic to be learnable quickly and different enough to matter.

   a mod n  is the remainder of a divided by n, always in
   the range [0, n-1].

   ARITHMETIC MODULO n WRAPS:
        (a + b) mod n
        (a * b) mod n
        (a ^ e) mod n

   All of public-key cryptography lives inside one of these
   wrapped worlds, because they are FINITE and because some
   operations in them are EASY FORWARDS AND HARD BACKWARDS.

   CONGRUENCE:  a ≡ b (mod n)  means n divides (a - b).

   THE KEY STRUCTURES:

     Z_n        the integers 0..n-1 with + and *
     Z_n*       the elements of Z_n that have a MULTIPLICATIVE
                INVERSE - exactly those coprime to n

   WHEN n IS PRIME p:
     every non-zero element is invertible, so Z_p is a FIELD.
     You can add, subtract, multiply AND DIVIDE. This is what
     makes prime moduli so useful.

   WHEN n = p*q (RSA):
     the elements sharing a factor with n have no inverse -
     and finding one of them means factoring n, which is the
     hard problem RSA rests on.

   THE PRACTICAL POINT FOR IMPLEMENTERS: these numbers are
   2048 to 4096 bits wide. There is no CPU instruction for
   them. Every operation is a loop over machine words, and
   the TIMING of that loop is where the secrets leak
   (chapter 19).

Euclid, inverses and the extended algorithm

An algorithm from antiquity that turns out to be exactly what is needed to compute modular inverses — which is a step in both key generation and signature verification.

/* --- GCD: the oldest algorithm still in daily use --- */
    gcd(a, b):
        while b != 0:
            a, b = b, a mod b
        return a

    gcd(252, 198) = gcd(198, 54) = gcd(54, 36)
                  = gcd(36, 18) = gcd(18, 0) = 18

/* --- EXTENDED EUCLID: also finds x, y with
       a*x + b*y = gcd(a, b)  --- */

    ext_gcd(a, b):
        if b == 0: return (a, 1, 0)
        (g, x, y) = ext_gcd(b, a mod b)
        return (g, y, x - (a / b) * y)

/* WHY THIS MATTERS: THE MODULAR INVERSE.

       a * a^-1 ≡ 1  (mod n)

   Set b = n. If gcd(a, n) = 1, then a*x + n*y = 1, so
   a*x ≡ 1 (mod n), and x is the inverse.

     inverse(a, n):
         (g, x, _) = ext_gcd(a, n)
         if g != 1: FAIL - no inverse exists
         return x mod n

/* USED FOR:
     · computing the RSA private exponent d from e
       (chapter 12)
     · converting projective to affine coordinates on an
       elliptic curve (chapter 14)
     · the s value in ECDSA signing (chapter 15)
     · Montgomery arithmetic setup

/* THE SIDE-CHANNEL WARNING: the loop above runs a
   DATA-DEPENDENT NUMBER OF ITERATIONS. Used on a secret, it
   leaks. Real libraries use a constant-time binary GCD, or
   Fermat's little theorem (a^(p-2) mod p) when the modulus
   is prime. Never write your own for secret inputs.      */

Fermat, Euler, and why exponents wrap

Two classical results that between them explain why the exponents in RSA work at all, and which underpin the primality testing used to generate keys.

/* --- FERMAT'S LITTLE THEOREM --- */
    For prime p and a not divisible by p:

        a^(p-1) ≡ 1  (mod p)

    Consequences:
        a^p     ≡ a       (mod p)
        a^(p-2) ≡ a^-1    (mod p)   /* a constant-time
                                       inverse! */

/* --- EULER'S TOTIENT φ(n) --- */
    φ(n) = how many integers in [1, n] are coprime to n

        φ(p)     = p - 1              /* p prime */
        φ(p*q)   = (p-1)(q-1)         /* p, q distinct
                                         primes */
        φ(p^k)   = p^k - p^(k-1)

/* --- EULER'S THEOREM: the generalisation --- */
        a^φ(n) ≡ 1  (mod n)   when gcd(a, n) = 1

/* THIS IS EXACTLY WHY RSA WORKS.

   Choose e and d with  e*d ≡ 1 (mod φ(n)),
   so  e*d = 1 + k*φ(n)  for some k.

   Then:
        (m^e)^d = m^(e*d) = m^(1 + k*φ(n))
                = m * (m^φ(n))^k
                ≡ m * 1^k
                ≡ m   (mod n)

   Encryption and decryption are inverse operations because
   the exponents wrap modulo φ(n). That is the whole of RSA's
   correctness argument.

/* --- CARMICHAEL'S λ(n) --- */
    The SMALLEST exponent that works:
        λ(p*q) = lcm(p-1, q-1)
    It divides φ(n), so d computed mod λ(n) is smaller and
    decryption is faster. Modern RSA key generation uses λ.

/* --- THE CHINESE REMAINDER THEOREM --- */
    Knowing x mod p and x mod q, with p, q coprime, uniquely
    determines x mod (p*q).

    RSA-CRT makes private-key operations ~4x FASTER:
        m_p = c^(d mod p-1) mod p
        m_q = c^(d mod q-1) mod q
        m   = recombine(m_p, m_q)

    Two exponentiations on half-size numbers beat one on the
    full size, because modular exponentiation is roughly
    cubic in the bit length.

    AND THE FAMOUS DANGER: if a FAULT corrupts exactly one of
    m_p or m_q, the attacker computes
        gcd(m^e - c, n)
    and RECOVERS A PRIME FACTOR from a single faulty
    signature. This is the Bellcore attack. Real
    implementations VERIFY the signature before releasing it,
    which is why you sometimes see a public-key operation
    inside a signing routine.                             */
Two hard problems hold up everything 
FACTORING:  given n = p*q, find p and q.
            -> RSA (chapter 12)

DISCRETE LOG: given g and g^x mod p, find x.
            -> Diffie-Hellman (13), DSA, ElGamal
            and the same problem on an elliptic
            curve group -> ECC (14), ECDSA, Ed25519

Neither is PROVEN hard. Both have resisted centuries and
decades respectively of effort. Both FALL COMPLETELY to a
sufficiently large quantum computer (chapter 20).

Groups, generators and orders

The structures underneath both RSA and elliptic curves are the same kind of mathematical object, and seeing that is what makes the two systems feel related rather than arbitrary.

/* A GROUP is a set with an operation that is:
     closed, associative, has an identity, and has inverses.

   For cryptography, always FINITE and usually ABELIAN
   (commutative).

/* --- THE MULTIPLICATIVE GROUP MOD p --- */
    Z_p* = {1, 2, ..., p-1} under multiplication mod p
    ORDER (size) = p - 1

    A GENERATOR g produces every element by repeated
    multiplication:
        g^1, g^2, ..., g^(p-1) = all of Z_p*
    Such a g is also called a PRIMITIVE ROOT.

    Example, p = 7:  3^1=3, 3^2=2, 3^3=6, 3^4=4, 3^5=5,
                     3^6=1
    3 generates all six non-zero elements, so 3 is a
    generator mod 7.

/* --- THE ORDER OF AN ELEMENT --- */
    The smallest k with g^k = 1. LAGRANGE'S THEOREM says it
    always divides the group order.

/* WHY THIS MATTERS IN PRACTICE:

   1. SAFE PRIMES. For Diffie-Hellman, choose p = 2q + 1
      with q also prime. Then the only subgroup orders are
      1, 2, q and 2q. An attacker cannot trap you in a small
      subgroup.

   2. SMALL-SUBGROUP CONFINEMENT ATTACKS. If p-1 has many
      small factors and you accept an arbitrary peer key, the
      attacker sends an element of small order. Your shared
      secret then lies in a tiny set, and they learn your
      private exponent modulo that small order. Repeat with
      several small factors, apply CRT, and they recover the
      key.

      THE DEFENCE: use a safe prime, VALIDATE the peer's
      public key (1 < y < p-1 and y^q ≡ 1), or use a curve
      designed so the check is unnecessary - X25519 clamps
      and has a cofactor of 8 (chapter 14).

   3. THE DISCRETE LOG PROBLEM. Given g, p and g^x mod p,
      find x. Best classical algorithms:
        · baby-step giant-step / Pollard rho: O(sqrt(order))
          -> so the SUBGROUP ORDER must be at least 2^256 for
             128-bit security
        · index calculus / number field sieve: SUBEXPONENTIAL
          in p, and this is why finite-field DH needs a
          3072-bit p for 128-bit security while an elliptic
          curve needs only 256 bits - index calculus does not
          apply to elliptic curve groups.               */

Generating primes

Key generation needs large primes, and finding them means testing candidates probabilistically rather than proving primality. What that probability actually means in practice is worth being precise about.

/* RSA and finite-field DH need large random primes.
   Deterministic primality proving is slow; probabilistic
   testing is what everyone uses.                         */

/* --- MILLER-RABIN --- */
    Write n - 1 = 2^s * d with d odd.
    Pick a random base a.
        compute a^d mod n
        if it is 1 or n-1: n MIGHT be prime
        else square up to s-1 times looking for n-1
        if never found: n is DEFINITELY COMPOSITE

    Each round has at most a 1/4 chance of being fooled, so
    k rounds give an error probability below 4^-k. For random
    candidates the true error rate is far lower; 40-64 rounds
    is standard, and FIPS 186-5 tabulates the requirement by
    key size.

/* --- THE GENERATION LOOP --- */
    do {
        p = random_odd_number(bits);
        p |= (1 << (bits-1));      /* force the top bit, so
                                      the modulus has the
                                      full length */
        p |= 1;                     /* force odd */
    } while (divisible_by_small_prime(p) ||
             !miller_rabin(p, rounds));

    /* the small-prime sieve first: trial division by the
       primes below ~2000 rejects ~90% of candidates for
       almost no cost, and Miller-Rabin is expensive */

/* --- WHAT GOES WRONG, and it has gone wrong at scale --- */

   1. A WEAK RNG. In 2012 researchers found that a
      meaningful fraction of TLS and SSH keys on the public
      internet shared a prime factor with another key -
      because embedded devices generated keys at first boot
      with almost no entropy (chapter 02). Computing
      gcd(n1, n2) over the whole set factored them all.
      THE FIX: never generate a key before the entropy pool
      is ready.

   2. THE PRIMES TOO CLOSE TOGETHER. If |p - q| is small,
      FERMAT FACTORISATION finds them immediately. Enforce a
      minimum difference.

   3. p-1 OR p+1 SMOOTH (having only small factors). Pollard
      p-1 and Williams p+1 then factor n cheaply. "Strong
      primes" avoid this; with random 1024-bit primes the
      probability is negligible, so modern standards no
      longer require the check.

   4. REUSED PRIMES ACROSS KEYS - same failure as (1), and
      the same gcd attack.

/* AND THE ADVICE: DO NOT IMPLEMENT KEY GENERATION. Use the
   library's, seeded from a real entropy source, and check
   that it is seeded before you call it.                 */
