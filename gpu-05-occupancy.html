Occupancy and latency hiding

Occupancy is how many warps are resident on an SM as a fraction of the maximum. It is the knob everyone tunes first and the one most often misunderstood: more is not always better, and 100% occupancy is frequently the wrong target.

Three budgets, and the smallest wins

   An SM has fixed resources. A block consumes some of each.
   The number of resident blocks is the MINIMUM across all
   limits.

   Typical modern SM:
     max warps resident ....... 64      (2048 threads)
     max blocks resident ...... 16-32
     register file ............ 65,536 x 32-bit
     shared memory ............ up to 164 KB

   WORKED EXAMPLE
     block = 256 threads = 8 warps
     registers per thread = 40
     shared memory per block = 8 KB

     by warps:      64 / 8            = 8 blocks
     by registers:  65536 / (256*40)  = 6.4  -> 6 blocks
     by shared mem: 164 KB / 8 KB     = 20 blocks
     by block limit:                    16 blocks

     LIMIT = 6 blocks = 48 warps = 48/64 = 75% occupancy
     and REGISTERS are the binding constraint.

   NOW ADD ONE VARIABLE that pushes registers to 48:
     by registers: 65536 / (256*48)   = 5.3  -> 5 blocks
     = 40 warps = 62% occupancy

   One local variable cost you 13% of your occupancy. This is
   why GPU performance is famously sensitive to trivial code
   changes, and why "register pressure" is a phrase you will
   hear constantly.

How much is enough

   Occupancy exists to hide latency. Once latency is hidden,
   more occupancy buys NOTHING.

   THE LITTLE'S LAW VIEW
     needed parallelism = latency x throughput

     to hide a 500-cycle memory latency on an SM that issues
     4 instructions/cycle, you need ~2000 instructions in
     flight. If each warp has 10 independent instructions
     between dependent loads, that is 200 warp-instructions -
     roughly 25 warps.

   TYPICAL SHAPE OF THE CURVE

     performance
        |            ....------------------  flat
        |         ..
        |       .
        |     .
        |   .
        | .
        +------------------------------------- occupancy
        0%   25%   50%   75%   100%

     The knee is usually between 25% and 50%. Past it you are
     tuning a number that does not affect the outcome.

   AND THE CURVE CAN GO DOWN:
     * more warps share the same L1 and L2, so each gets less
       cache. A tiled kernel with a working set that fits at
       50% occupancy may thrash at 100%.
     * fewer registers per thread means less data kept close,
       so more memory traffic.

   INSTRUCTION-LEVEL PARALLELISM SUBSTITUTES FOR OCCUPANCY.
   Volkov's well-known result: a kernel where each thread
   processes 4 independent elements can hit peak at 25%
   occupancy, because the 4 loads are in flight simultaneously
   from one warp. Fewer, fatter threads often beat more,
   thinner ones.
The right question

Not "how do I get to 100% occupancy" but "am I latency-bound, bandwidth-bound or compute-bound?" Occupancy only helps the first. If you are already at 80% of peak memory bandwidth, no amount of extra occupancy matters — you need to move fewer bytes (chapter 4). Nsight's Speed-of-Light section answers this in one screen and should be the first thing you look at.

Trading occupancy for work per thread

/* ONE ELEMENT PER THREAD - maximum occupancy, minimum ILP.
   Each thread issues one load and then waits.              */
__global__ void v1(float *out, const float *a, const float *b, int n)
{
        int i = blockIdx.x * blockDim.x + threadIdx.x;
        if (i < n) out[i] = a[i] * b[i];
}

/* FOUR ELEMENTS PER THREAD - fewer warps, but four
   INDEPENDENT loads in flight per thread. The scheduler can
   overlap them without needing another warp.               */
__global__ void v4(float4 *out, const float4 *a, const float4 *b, int n4)
{
        int i = blockIdx.x * blockDim.x + threadIdx.x;
        if (i < n4) {
                float4 x = a[i];        /* ONE 16-byte load -
                                           wider transactions,
                                           fewer of them      */
                float4 y = b[i];
                out[i] = make_float4(x.x*y.x, x.y*y.y,
                                     x.z*y.z, x.w*y.w);
        }
}
/* Two wins at once:
     - vectorised loads (float4 = 16 bytes) use the memory
       system better than four separate 4-byte loads
     - more independent work per thread, so lower occupancy
       still hides the latency

   Requires 16-byte alignment. cudaMalloc guarantees 256-byte
   alignment, so the base is fine; an offset into the middle
   of an array may not be.

   THE GENERAL TECHNIQUE is called THREAD COARSENING, and it
   is usually worth trying 2 or 4 elements per thread before
   any other optimisation.                                   */

Choosing a block size

SizeWarpsNotes
321Too small — the block limit (16–32 blocks) caps you at 32 warps before any other resource does
1284Good default. Divides evenly into most SM limits, flexible for the scheduler
2568The most common choice. Good balance of granularity and overhead
51216Fine if register use is low; coarse granularity wastes an SM on the tail
102432Maximum. Only one or two blocks fit, so a single barrier stalls half the SM. Rarely best
Not a multiple of 32—Always wrong. The final warp runs with idle lanes
 
/* Do not guess - ask the runtime. */
int block, grid;
cudaOccupancyMaxPotentialBlockSize(&grid, &block, my_kernel, 0, 0);
my_kernel<<<grid, block>>>(...);

/* Or query for a specific choice: */
int blocks_per_sm;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(
        &blocks_per_sm, my_kernel, 256, 0);

/* AND SIZE THE GRID FOR THE MACHINE, not for the data, when
   using a grid-stride loop (chapter 4): */
int nsm;
cudaDeviceGetAttribute(&nsm, cudaDevAttrMultiProcessorCount, 0);
int grid = nsm * blocks_per_sm;     /* fill the GPU exactly    */

/* THE TAIL EFFECT, worth knowing:
     108 SMs, 110 blocks -> the last 2 blocks run alone while
     106 SMs idle. The kernel takes twice as long as the work
     requires. Either round the grid to a multiple of the SM
     count with a grid-stride loop, or use many small blocks
     so the imbalance is proportionally tiny.                */
Register spilling beats occupancy every time

Forcing -maxrregcount=32 to reach 100% occupancy, and thereby spilling ten registers to local memory, is a large net loss: each spill is a global-memory round trip in the inner loop. Always check the ptxas spill counters after changing register limits. Zero spills at 50% occupancy is almost always better than heavy spilling at 100%.
