Polling, interrupts and DMA: three ways to move data

Every peripheral transfer is one of three mechanisms, and choosing wrongly is the most common cause of a design that works on the bench and falls over in the field. This chapter is the decision, with the arithmetic that makes it.

The three mechanisms

   POLLING
     CPU: while (!(flag)) { }  then read
     Cost: 100% of a core, doing nothing useful
     Latency: as good as it gets - you are already looking
     Use when: the wait is shorter than an interrupt entry
               (~12 cycles + your prologue), or during init,
               or in a hard real-time loop that has nothing
               else to do.

   INTERRUPT
     CPU: handler runs per BYTE or per EVENT
     Cost: ~20-40 cycles of overhead per event
     Latency: 12 cycles + whatever is blocking you
     Use when: events are infrequent relative to the
               overhead, or their timing is unpredictable.

   DMA
     CPU: configure once, then nothing until the block ends
     Cost: bus bandwidth, contention with the CPU
     Latency: irrelevant per byte; one interrupt per BLOCK
     Use when: the data is a block, or the rate is high
               enough that per-event interrupts would
               saturate the CPU.

   THE ARITHMETIC THAT DECIDES:

     UART at 115200 baud = 11520 bytes/s
       per-byte interrupt at 30 cycles = 345,600 cycles/s
       on a 168 MHz core = 0.2% CPU. Interrupts are fine.

     UART at 3 Mbaud = 300,000 bytes/s
       per-byte interrupt at 30 cycles = 9,000,000 cycles/s
       = 5.4% CPU, and 300k interrupts/s starves everything
       else. Use DMA.

     ADC at 1 Msample/s
       per-sample interrupt = 30,000,000 cycles/s = 18% CPU
       doing nothing but copying. Use DMA. Always.

   Do this calculation. It takes thirty seconds and it is
   the difference between a design that scales and one that
   is rewritten under deadline.

Polling, done correctly

/* Polling gets a bad name because it is usually written
   without a timeout. This version cannot hang.            */

int uart_send_blocking(const uint8_t *p, size_t n, uint32_t ms)
{
    uint32_t deadline = g_ms + ms;

    for (size_t i = 0; i < n; i++) {
        while (!(USART1->ISR & USART_ISR_TXE)) {
            if ((int32_t)(g_ms - deadline) >= 0) {
                return -ETIMEDOUT;      /* the crucial part */
            }
        }
        USART1->TDR = p[i];
    }
    return 0;
}

/* Three rules for any polling loop that ships:

   1. A TIMEOUT, always. A peripheral that never sets its
      flag - because a clock is off, a cable is unplugged,
      or the far end died - turns a poll into a hang. This
      is the single most common cause of a field unit that
      "just stops".

   2. The flag variable must be volatile, or read through a
      volatile pointer. Otherwise the compiler may hoist the
      load out of the loop and spin forever on a stale value
      (see the C track, chapter 10).

   3. Consider what else is starved. A 10 ms poll with
      interrupts enabled is fine; the same poll inside a
      critical section delays every interrupt by 10 ms.     */

DMA: the controller does the copying

/* DMA is a second bus master. It reads and writes memory
   without the CPU, arbitrating for the bus alongside it.  */

/* UART receive into a circular buffer - the configuration
   worth memorising, because it never overruns.            */

DMA2_Stream5->PAR  = (uint32_t) &USART1->RDR;   /* source */
DMA2_Stream5->M0AR = (uint32_t) rx_buffer;      /* dest   */
DMA2_Stream5->NDTR = sizeof(rx_buffer);
DMA2_Stream5->CR   = (4u << 25)          /* channel 4      */
                   | DMA_SxCR_MINC       /* increment mem  */
                   | DMA_SxCR_CIRC       /* CIRCULAR       */
                   | DMA_SxCR_TCIE       /* half/full IRQ  */
                   | DMA_SxCR_HTIE;
USART1->CR3 |= USART_CR3_DMAR;
DMA2_Stream5->CR |= DMA_SxCR_EN;

/* CIRCULAR mode means NDTR reloads automatically at the end
   and the controller wraps to the buffer start. Combined
   with the half-transfer interrupt you get a classic
   double-buffer: process the first half while the second
   fills, and vice versa. The UART can now receive
   continuously, forever, with two interrupts per buffer
   instead of one per byte.

   Add the UART's IDLE-line interrupt and you also learn
   when a variable-length message ENDED, which is what makes
   this pattern work for protocols rather than just streams:

     bytes_received = sizeof(rx_buffer) - DMA2_Stream5->NDTR;

   That expression, read in the IDLE handler, tells you
   exactly how much arrived. This combination - circular DMA
   plus IDLE detection - is the standard high-performance
   UART receive design, and it is worth knowing by heart.  */
Four DMA rules that are not optional 
   1. THE BUFFER MUST BE REACHABLE.
      Many parts have RAM banks the DMA engine cannot see -
      CCM RAM on STM32F4 is the classic. A buffer there
      produces a transfer error or silent zeros. Place DMA
      buffers explicitly (chapter 05).

   2. THE BUFFER MUST NOT BE ON THE STACK.
      A local array goes out of scope when the function
      returns; the DMA controller keeps writing to it. This
      corrupts whatever occupies that stack space next, at
      a delay, and is genuinely one of the hardest embedded
      bugs to find. Use static or heap.

   3. CACHE MAINTENANCE ON M7.
      Cortex-M7 has data caches. Before a memory-to-
      peripheral transfer, CLEAN the cache so the DMA sees
      your writes. After a peripheral-to-memory transfer,
      INVALIDATE so the CPU does not read stale lines.
      Miss this and it works at -O0 and fails at -O2, or
      works until the buffer happens to stay in cache.

        SCB_CleanDCache_by_Addr((uint32_t*)buf, len);
        ... start TX DMA ...

        ... RX DMA completes ...
        SCB_InvalidateDCache_by_Addr((uint32_t*)buf, len);

      M0/M3/M4 have no data cache, so this is one of the
      few places where code does not port upward cleanly.

   4. ALIGNMENT AND WIDTH MUST AGREE.
      A 32-bit peripheral width with a byte-aligned buffer
      is a transfer error, not a slow transfer.

The compiler does not know about DMA

/* DMA writes memory behind the compiler's back. Every
   variable the DMA controller touches must be volatile, and
   volatile alone is still not quite enough.               */

static volatile uint8_t rx_buffer[256];   /* volatile: yes */
static volatile int     rx_done;

void DMA2_Stream5_IRQHandler(void)
{
    DMA2->HIFCR = DMA_HIFCR_CTCIF5;
    rx_done = 1;
}

void consumer(void)
{
    while (!rx_done) { }        /* volatile: the load repeats */

    __asm volatile ("dmb");     /* ordering: see below        */
    process(rx_buffer);
}

/* The DMB matters. volatile guarantees the COMPILER does
   not reorder or elide the accesses. It says nothing about
   the memory system. On Cortex-M the core is largely
   in-order and this is usually benign, but write buffers
   and the bus matrix can still reorder the DMA's buffer
   writes relative to its completion signal.

   The rule: volatile for the compiler, a barrier for the
   hardware. They solve different problems and you often
   need both. This is exactly the distinction the ARM track
   makes in its barriers chapter, and it applies here in
   miniature.                                               */
