Project: the Windows four-layer stack — VBS, VTL1 and the seams

The same design as the OP-TEE project, built with Windows' own isolation instead of TrustZone: an application asks for a signature, a KMDF driver decides whether it may, a VBS enclave in VTL1 performs it with a key that never leaves, and the secure kernel seals that key to the platform. The shape is identical. One of the seams is not, and that difference is the most useful thing in this project.

VTL0, VTL1, and what actually enforces the boundary

TrustZone splits the machine with a bit in the bus fabric. Windows splits it with the hypervisor, which is a completely different mechanism reaching the same result — and the difference shows up the moment you try to cross it.

   VIRTUAL TRUST LEVELS. Both levels have a full ring 0 and
   ring 3. The hypervisor decides which physical pages each
   level may see, using second-level address translation.

   ┌──────────────── VTL 0 ────────┐ ┌───── VTL 1 ────────┐
   │  ring 3                       │ │  ring 3            │
   │    your applications          │ │    TRUSTLETS and   │
   │    services, everything       │ │    VBS ENCLAVES    │
   │                               │ │    (LSAIso, and    │
   │                               │ │     our enclave)   │
   ├───────────────────────────────┤ ├────────────────────┤
   │  ring 0                       │ │  ring 0            │
   │    ntoskrnl.exe               │ │    securekernel.exe│
   │    EVERY third-party driver   │ │    (Microsoft only)│
   └───────────────────────────────┘ └────────────────────┘
         ▲                                    ▲
         └────────── HYPERVISOR ──────────────┘
            enforces the split; neither kernel
            can override it

   THE PROPERTY: VTL1 can read VTL0's memory. VTL0 CANNOT
   read VTL1's. That asymmetry is the whole design, and it
   is the same asymmetry the secure world has in TrustZone.

   THE CONSEQUENCE YOU CARE ABOUT: ntoskrnl.exe is in VTL0.
   A kernel driver - yours, and a rootkit's - is on the
   UNTRUSTED side of this line. That is a strange thought
   the first time, and it is the point.
Windows' secure world is not open the way OP-TEE's is

In OP-TEE you can write code for every layer, including the trusted OS itself. In Windows, VTL1 ring 0 — securekernel.exe — is Microsoft's, and so are the classic trustlets (LSAIso.exe, which is Credential Guard). What is open to you is VTL1 ring 3, as a VBS enclave: a DLL loaded into an isolated region of your own process that the rest of the system, kernel included, cannot read. That is the layer this project builds, and it is genuinely the Windows equivalent of a trusted application.

The four layers

Read it as the same sequence of trust reductions as the OP-TEE stack, because it is — right up until the third arrow, which works differently for a reason worth understanding.

   LAYER 1   winsign.exe                          VTL0
             an ordinary application             ring 3
                  │  DeviceIoControl(IOCTL_WINSIGN_SIGN)
                  │  ── SEAM A: the IOCTL contract ──
                  ▼
   LAYER 2   winsign.sys                          VTL0
             a KMDF driver                       ring 0
             · decides WHO may sign, from the
               caller's token
             · bounds and copies the request
                  │
                  │  ?? it cannot call the enclave ??
                  │  ── SEAM B: the inverted call ──
                  ▼
             winsignhost.exe                      VTL0
             a service that HOSTS the enclave     ring 3
             · no security role whatsoever
                  │  CallEnclave(...)
                  │  ── SEAM C: the VTL transition ──
                  ▼
   LAYER 3   winsign_enclave.dll                  VTL1
             a VBS enclave                       ring 3
             · holds the private key
             · re-validates everything
                  │  EnclaveSealData / EnclaveUnsealData
                  │  ── SEAM D: the secure-kernel call ──
                  ▼
   LAYER 4   securekernel.exe + TPM               VTL1
             seals the key to this platform      ring 0

   THREE TRUST BOUNDARIES (A, C, D) AND ONE HOP THAT IS NOT
   ONE (B). Keeping those apart in your head is the single
   most important thing on this page.

Why the kernel driver cannot call the enclave

This is the structural difference from OP-TEE, and it is not something you can engineer around — so it is better to understand it than to fight it.

   IN OP-TEE:
     SMC is a CPU instruction available at EL1. A Linux
     driver issues it directly. Kernel to secure world is
     ONE HOP.

   IN WINDOWS:
     A VBS enclave is entered by CallEnclave, which is a
     VTL0 USER-MODE operation against an enclave that a
     USER-MODE process created in its own address space.
     There is no kernel-mode equivalent exposed to drivers.

     So: kernel to enclave needs a user-mode process in
     between. Always.

   WHICH MEANS THE DRIVER MUST GET WORK *OUT* TO USER MODE.
   The standard Windows pattern for that is the INVERTED
   CALL MODEL:

     the host service issues an IOCTL and the driver does
     not complete it - it holds the IRP pending in a queue.
     When work arrives, the driver completes that pending
     IRP with the work as its output. The service does the
     work, posts the result back with a second IOCTL, and
     immediately issues another pending IOCTL to wait again.

     A "call" from kernel to user mode, built entirely out
     of the user-mode side asking first.

   YOU HAVE SEEN THIS SHAPE BEFORE. It is the same trick as
   a blocking read() that a driver completes later, which is
   why it is worth recognising rather than memorising.
The host service is plumbing, not security — and mistaking it for security is the classic error

It is tempting to put a check in winsignhost.exe, because it is convenient and it is where the data is. But the host is an ordinary VTL0 user-mode process: an attacker with SYSTEM can debug it, patch it, or replace it entirely. Everything it does can be forged. The only two places a decision means anything are layer 2, which has the original caller's token and runs where an attacker needs kernel access to interfere, and layer 3, which the attacker cannot reach at all. Anything you enforce in between is decoration.

The seams, and the contract at each

Same exercise as the OP-TEE project, and for the same reason: writing down what each boundary guarantees is what makes the validation code in the next three chapters look necessary rather than paranoid.

SeamMechanismTrust boundary?What the lower side must assume
A app → driverDeviceIoControl, buffered I/OYes Lengths are attacker-chosen; with METHOD_NEITHER the pointers would be too
B driver ↔ hostInverted call, pended IRPNo Nothing. The host is as untrusted as the app — it just happens to be convenient
C host → enclaveCallEnclave, VTL0 → VTL1Yes — the important oneThe parameter points into VTL0 memory that VTL0 can change while you read it
D enclave → secure kernelEnclaveSealData and friendsYesBoth sides are VTL1; the policy argument decides what can later unseal the blob
Seam C has the same hazard as OP-TEE's shared memory, with a sharper edge

An enclave can read all of VTL0's address space, which sounds like a convenience and is actually the trap: the parameter you were handed lives in memory the untrusted side can rewrite after you have validated it. Reading a length, checking it, and then reading the buffer gives the attacker a window between the two. The rule is identical to the one in OP-TEE chapter 20 — copy into enclave memory first, then validate the copy, then use only the copy — and chapter 42 does exactly that, in the one place it matters.

What this design defends against

Stating this before any code exists keeps the rest of the project honest, and it is the section a reviewer will ask for first.

The order to build it in

Four moving parts on a machine where a mistake in one of them bugchecks the box. This order keeps a working system in front of you at every step, and leaves the driver — the only piece that can take the machine down — until after the hard part is proved.

   0. CHECK VBS IS ACTUALLY ON. msinfo32, or the one-liner
      in chapter 42. Everything below fails confusingly if
      it is not, and the failure does not say so.

   1. THE ENCLAVE, called directly by a throwaway host of
      twenty lines. No driver, no service, no IOCTL. This
      is the part most likely to fight you - signing, the
      supported-DLL set, the entry point - so do it while
      nothing else can be blamed.              (chapter 42)

   2. SEALING, so the key survives a restart. Still no
      driver.                                  (chapter 43)

   3. THE DRIVER, with a test IOCTL that returns a constant.
      Proves seam A, the INF, the interface ACL and your
      test-signing setup - separately from any of the
      logic.                                   (chapter 41)

   4. THE INVERTED CALL, joining 1-3 together. Proves
      seam B.                                  (chapter 41)

   5. THE ATTACK TESTS. Only now is there anything to
      attack.                                  (chapter 43)

   NOTE THIS IS THE OPPOSITE ORDER TO THE OP-TEE PROJECT,
   where the secure side was easy and the transport was not.
   Here the transport is routine Windows driver work and the
   enclave is where the surprises live.
You need a machine you can afford to break

Test-signed drivers, a VBS-capable machine and an enclave that must be loaded into a live process is not a combination to develop on your daily driver. A VM with nested virtualisation enabled and a checkpoint taken before each install is the right setup — see chapter 23 for attaching a kernel debugger to it, which you will want by step 3.
