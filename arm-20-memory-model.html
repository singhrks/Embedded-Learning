The weak memory model

ARM permits your memory accesses to become visible to other cores in almost any order. This is not a bug or an implementation detail — it is the specification, and it is why lock-free code that has worked on x86 for a decade can fail the first time it runs on ARM.

What "weak" means

The guarantee

ARM guarantees that a single thread observes its own accesses in program order. It guarantees nothing about the order in which other observers see them, unless you use a barrier or an ordered access.

Accesses to the same location are always coherent and ordered — that is a separate guarantee (CA ch. 15). The weakness is entirely about accesses to different locations.

This table is the concrete meaning of "weak" versus x86's "strong" (TSO) model, expressed as which reorderings a real program can actually observe. Three of the four rows are allowed on ARM and forbidden on x86: a core is free to complete a later load before an earlier one, to complete a load before an earlier store has become globally visible, or to complete a later store before an earlier one — all in the name of letting the hardware overlap independent work rather than draining everything in strict program order. The one row that is allowed on both — a store followed by a later, independent load reordered ahead of it — exists on x86 too, which is the detail that catches people who assume TSO means "no reordering at all": it means almost none, not none.

Reorderingx86-64 (TSO)ARM (weak)
Load → LoadNot allowedAllowed
Load → StoreNot allowedAllowed
Store → StoreNot allowedAllowed
Store → LoadAllowedAllowed
 
Why ARM chose this:

  Enforcing order costs hardware. A store buffer that must drain
  in order, load queues that must not reorder, and snoop
  responses that must be sequenced all consume area, power and
  latency. Relaxing them lets the core:

     · retire stores into a buffer and continue
     · issue loads as soon as their address is known
     · let the interconnect route messages by any path
     · merge and reorder writes for bandwidth

  The cost is moved to SOFTWARE, which must ask for ordering
  where it genuinely needs it — which is a small fraction of the
  time. Given that, the trade is clearly correct for a
  power-sensitive architecture.

  x86 made the opposite choice for compatibility reasons, and
  pays for it in hardware complexity.

The canonical failure

Start with the example that shows the problem exists. This sequence looks obviously correct, runs correctly on x86, and can fail on ARM — and understanding why is the entire point of the chapter.

/* Both variables start at 0. */

/* Core 0 — producer */          /* Core 1 — consumer */
data = 42;                       while (flag == 0)
flag = 1;                                ;
                                 use(data);        /* may read 0! */
Three independent things can produce the failure:

  1. COMPILER reordering — nothing in the source forbids swapping
     the two stores, since they are independent single-threaded.

  2. STORE BUFFER — the store to `data` retires into a buffer and
     has not yet reached the coherency point when `flag`'s store
     does. Other cores see flag=1 first.

  3. LOAD reordering on the consumer — the load of `data` can
     issue BEFORE the load of `flag`, because its address is known
     and there is no dependency between them.

  Point 3 is the one that surprises people most: even if the
  producer's stores are ordered, the CONSUMER can still break it.
  Both sides need ordering.

Dependencies that do order

Not everything can be reordered. Certain relationships between instructions are respected by the hardware for free, and knowing which ones lets you avoid barriers you do not actually need.

/* Not everything requires an explicit barrier. Some orderings
   come free from the dependency structure.                    */

/* ADDRESS DEPENDENCY — guaranteed ordered */
        ptr = atomic_load(&head);
        val = ptr->field;          /* the second load CANNOT be
                                      reordered before the first —
                                      its address depends on it   */
/* This is what makes RCU readers free on ARM (OS chapter 09):
   rcu_dereference() relies on exactly this.                   */

/* DATA DEPENDENCY on a STORE — guaranteed ordered */
        x = load(&a);
        store(&b, x);              /* ordered: b's value needs a  */

/* CONTROL DEPENDENCY on a STORE — ordered, but fragile */
        if (load(&a))
                store(&b, 1);      /* the store cannot be
                                      speculated before the load */

/* CONTROL DEPENDENCY on a LOAD — NOT ordered */
        if (load(&a))
                y = load(&b);      /* the second load CAN be
                                      speculated. No ordering.   */
Do not rely on control dependencies

They order stores but not loads, they are not expressible in the C or C++ memory model, and the compiler is entitled to remove them — by turning a branch into a conditional select (CSEL), or by hoisting a store that occurs on both paths. The Linux kernel documents this at length in Documentation/memory-barriers.txt and the advice is: use smp_load_acquire() or an explicit barrier instead. Address dependencies are safe; control dependencies are a trap.

Fixing it

With the failure understood, the repair is straightforward — the difficulty is choosing the weakest construct that is still sufficient, because the strongest one is always correct and often needlessly expensive.

/* Option 1: explicit barriers */
/* Core 0 */                      /* Core 1 */
data = 42;                        while (flag == 0)
DMB ISHST;                                ;
flag = 1;                         DMB ISHLD;
                                  use(data);

/* Option 2: acquire/release — cheaper, and the modern idiom */
/* Core 0 */                      /* Core 1 */
data = 42;                        while (LDAR(flag) == 0)
STLR(flag, 1);                            ;
                                  use(data);

/*  STLR — store-release:  no EARLIER access may be reordered
                           after it
    LDAR — load-acquire:   no LATER access may be reordered
                           before it

   Together they form a RELEASE-ACQUIRE PAIR: everything core 0
   did before the release is visible to core 1 after the acquire.

   Cheaper than a standalone barrier because the ordering is
   attached to an access the core was performing anyway — the
   core can keep other work in flight.                        */

The C and C++ view

You will usually express ordering in C rather than assembly. The language's model maps onto the architecture's, and knowing the correspondence is what lets you reason about the generated code.

#include <stdatomic.h>

_Atomic int flag = 0;
int data = 0;                     /* a plain int is fine now */

/* producer */
data = 42;
atomic_store_explicit(&flag, 1, memory_order_release);

/* consumer */
while (atomic_load_explicit(&flag, memory_order_acquire) == 0)
        ;
use(data);                        /* guaranteed to see 42 */

C11's memory_order values exist to let one piece of portable source code compile to the cheapest correct instruction on whatever architecture it targets, and on ARM each level maps onto a distinct instruction rather than onto extra fence instructions bolted on afterwards. That mapping is worth internalising because it explains a real performance property of the architecture: acquire and release are essentially free here — LDAR/STLR are ordinary loads and stores with an ordering bit set, not a load plus a separate barrier — where on a weaker-in-different-ways architecture the same C code might need extra fence instructions. seq_cst is the one exception: because it additionally demands a single global total order across every thread's accesses, ARM sometimes needs a real DMB alongside the ordered load or store to deliver it.

/* Linux kernel spellings of the same concepts: */
smp_store_release(&flag, 1);
val = smp_load_acquire(&flag);
smp_mb();   smp_rmb();   smp_wmb();      /* full / read / write */
READ_ONCE(x);   WRITE_ONCE(x, v);        /* stop the COMPILER only */
rcu_dereference(p);                       /* address dependency     */

/* READ_ONCE/WRITE_ONCE are worth understanding: they prevent the
   COMPILER from tearing, fusing or inventing accesses, but emit
   NO hardware barrier. They are the minimum for any shared
   variable, even one you think is "just a flag".            */

Litmus tests

These small tests are the standard vocabulary for discussing memory models precisely. Each isolates one reordering, and recognising them by name makes the literature on this subject readable.

The standard vocabulary for reasoning about memory models. Worth
knowing by name, because papers, kernel documentation and tooling
all use them.

MESSAGE PASSING (MP) — the flag/data case above
   P0: x = 1; y = 1        P1: r1 = y; r2 = x
   Can r1 == 1 && r2 == 0?     ARM: YES.  x86: no.

STORE BUFFERING (SB)
   P0: x = 1; r1 = y       P1: y = 1; r2 = x
   Can r1 == 0 && r2 == 0?     ARM: YES.  x86: YES.
   → the one reordering even TSO allows. Requires a full barrier
     on BOTH sides to prevent; acquire/release is not enough.

LOAD BUFFERING (LB)
   P0: r1 = x; y = 1       P1: r2 = y; x = 1
   Can r1 == 1 && r2 == 1?     ARM: YES.  x86: no.

INDEPENDENT READS OF INDEPENDENT WRITES (IRIW)
   P0: x = 1    P1: y = 1
   P2: r1 = x; r2 = y      P3: r3 = y; r4 = x
   Can P2 and P3 disagree about the ORDER of the two writes?
   ARM: NO — ARMv8 is MULTI-COPY ATOMIC. A write becomes visible
   to all observers at the same time. (ARMv7 was not, which made
   reasoning far harder.)

  Multi-copy atomicity is the single most important simplification
  ARMv8 made over ARMv7, and it is why the ARMv8 model is
  formally tractable.

Device memory is different

Everything above concerns ordinary memory. Device memory has stricter rules by default, which is why driver code sometimes needs fewer barriers than you would expect — and sometimes more.

/* Device memory (chapter 11) has its OWN ordering rules, and they
   are much stronger:

     Device-nGnRnE   no gathering, no reordering, no early ack —
                     accesses arrive in program order
     Device-nGnRE    reordering still forbidden between Device
                     accesses to the same peripheral

   But note what is NOT guaranteed: ordering between a Device
   access and a NORMAL memory access. That combination needs an
   explicit barrier, and it is exactly the DMA handoff case:  */

        /* fill the DMA buffer — Normal memory */
        memcpy(buf, data, len);

        /* the buffer writes must be VISIBLE before the device
           is told to start                                     */
        dsb     sy                    /* or dma_wmb() in Linux */

        /* start the transfer — Device memory */
        writel(START, regs + CTRL);

/* Linux's writel() includes a barrier for exactly this reason;
   writel_relaxed() does not, and is for when you have already
   ordered things yourself or genuinely do not care.        */

Porting from x86

The code was always wrong; x86 hid it

x86's TSO forbids three of the four reorderings, which happens to be enough for most naive lock-free code to work by accident. On ARM those reorderings are permitted and do occur.

Worse, the failure is rare and load-dependent: it needs the store buffer to be occupied, or two cores to interleave in a particular way. It typically passes every test and appears in production, once, on a customer's machine.

Practical steps when porting:

  • Search for every shared variable accessed without a lock. Each one is a candidate.
  • Replace hand-rolled flags with _Atomic and explicit memory orders — the compiler then emits correct code for both architectures.
  • Run under ThreadSanitizer, which models the C++ memory model rather than any one CPU.
  • Do not "fix" it by adding volatile. It constrains the compiler and does nothing to the hardware (C ch. 10).

Practical rules

Everything above this point is the theory; this table is the cheat sheet you actually reach for while writing code. The organising idea is to match the strength of the ordering to the shape of the pattern rather than defaulting to the strongest tool everywhere — a publish-then-flag pattern needs only a release on the write side and an acquire on the read side, because that pairing alone is sufficient to make the published data visible; the store-buffering pattern is the one well-known case where acquire/release genuinely is not enough and a full barrier is required on both sides, because that pattern depends on a total order that acquire/release does not provide. When none of the specific rows obviously apply, the last row is the safe fallback: reach for seq_cst, get it working, and only relax it once you have measured that the ordering cost actually matters.
