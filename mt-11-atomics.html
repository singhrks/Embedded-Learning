Atomic operations and the CAS loop

An atomic operation is one that no other thread can observe half-finished. That is a smaller guarantee than people assume — it says nothing about ordering, and it does not compose. Both of those gaps are where the bugs live.

What atomic buys, and what it does not

An atomic operation is one that cannot be observed half-finished. That is a weaker guarantee than it sounds — it says nothing about ordering relative to other operations, which is the subject of the next chapter.

   ATOMIC GIVES YOU

     indivisibility   no thread sees a half-written value.
                      No torn reads, no lost read-modify-write.

     a defined value  the result is one of the values some
                      thread actually wrote - never a mixture.

   ATOMIC DOES NOT GIVE YOU

     ordering         unless you ask. atomic_fetch_add with
                      memory_order_relaxed orders NOTHING
                      around it (chapter 12).

     composition      two atomic operations are not one atomic
                      operation:

                          if (atomic_load(&a) == 0)     // 1
                                  atomic_store(&b, 1);  // 2

                      anything can happen between 1 and 2.
                      This is the check-then-act race with
                      extra syntax.

     atomicity of the SURROUNDING LOGIC. An atomic counter
     that is correct tells you nothing about the invariant it
     was counting.

   THE ONE OPERATION THAT COMPOSES is compare-and-swap, because
   it folds the check and the act into a single indivisible
   step. Everything lock-free is built out of it.

The operation set

The available operations are a small set, and knowing which are provided natively by the hardware matters: anything not provided is emulated with a retry loop, which performs very differently under contention.

#include <stdatomic.h>                 /* C11                   */

atomic_int   counter = 0;
atomic_bool  flag    = false;
_Atomic(struct point) pt;              /* may be lock-free or
                                          not - see below      */

/* LOAD / STORE - indivisible, but nothing more by default. */
        int v = atomic_load(&counter);
        atomic_store(&counter, 42);

/* READ-MODIFY-WRITE - the useful ones. Each returns the OLD
   value, which is what makes them composable into algorithms. */
        old = atomic_fetch_add(&counter,  1);
        old = atomic_fetch_sub(&counter,  1);
        old = atomic_fetch_or (&flags, MASK);
        old = atomic_fetch_and(&flags, ~MASK);
        old = atomic_fetch_xor(&flags, MASK);
        old = atomic_exchange (&ptr, newptr);

/* COMPARE-AND-SWAP - the universal primitive. */
        bool ok = atomic_compare_exchange_strong(&p, &expected, desired);
        /* if (*p == expected) { *p = desired; return true; }
           else                { expected = *p; return false; }

           NOTE: `expected` is updated on failure. That is not
           a wart - it saves you a reload in the retry loop.  */

/* C++ is the same set, spelled as methods: */
        std::atomic<int> c{0};
        c.fetch_add(1, std::memory_order_relaxed);
        c.compare_exchange_weak(exp, des);

/* Rust: */
        use std::sync::atomic::{AtomicUsize, Ordering};
        let c = AtomicUsize::new(0);
        c.fetch_add(1, Ordering::Relaxed);
        c.compare_exchange_weak(exp, des, Ordering::AcqRel,
                                Ordering::Relaxed)
strong versus weak

compare_exchange_weak may fail spuriously — return false even when the value matched. That sounds useless until you remember ARM's LL/SC (chapter 6): the store-exclusive fails if anything touched the cache line, including an unrelated access. The weak form maps to one LL/SC attempt; the strong form has to add a retry loop inside. Use weak inside a loop you were writing anyway; use strong when a single attempt must be conclusive. On x86 they compile identically.

The CAS loop

Compare-and-swap is the universal primitive — every other atomic operation can be built from it, and every lock-free algorithm uses it. It also brings one notorious failure mode that its interface cannot detect.

/* The shape of every lock-free update. Learn it once. */

        T old = atomic_load_explicit(&obj, memory_order_relaxed);
        T new;
        do {
                new = compute_new_from(old);     /* pure! */
        } while (!atomic_compare_exchange_weak_explicit(
                        &obj, &old, new,
                        memory_order_acq_rel,    /* on success */
                        memory_order_relaxed));  /* on failure */

/* WHY IT IS CORRECT: the CAS only succeeds if `obj` is still
   `old` - i.e. nobody changed it while you were computing.
   If someone did, `old` is refreshed with the current value
   and you recompute. Progress is guaranteed for the system
   (someone always wins) but not for any given thread.

   THREE RULES FOR THE BODY:

   1. compute_new_from() MUST be pure and cheap. It runs again
      on every failure. Anything with a side effect - logging,
      allocating, incrementing another counter - happens
      multiple times.

   2. It must not be able to loop for ever. Under heavy
      contention a thread can lose repeatedly; if that matters,
      add back-off, or use a lock.

   3. Do NOT reload `old` yourself at the top of the loop.
      compare_exchange already wrote the current value into it.
      Reloading opens a window and is a common source of
      subtle livelock.                                        */

/* A worked example: atomically clamp-and-add. */
int add_clamped(atomic_int *c, int delta, int max)
{
        int old = atomic_load_explicit(c, memory_order_relaxed);
        int new;
        do {
                if (old >= max)
                        return -1;               /* full        */
                new = old + delta;
                if (new > max) new = max;
        } while (!atomic_compare_exchange_weak_explicit(
                        c, &old, new,
                        memory_order_acq_rel, memory_order_relaxed));
        return new;
}
/* You cannot write that with fetch_add. This is exactly the
   class of problem CAS exists for: a read-modify-write whose
   "modify" involves a decision.                              */

Is it actually lock-free?

Whether a type is genuinely lock-free is a property of the platform, not of the language. Assuming rather than checking produces code that silently takes a lock on the one target where that matters most.

/* An "atomic" type is not necessarily implemented in hardware.
   If the type is too big, the compiler emits a hidden LOCK. */

        _Atomic(struct { long a, b, c; }) big;   /* 24 bytes    */

        printf("%d\n", atomic_is_lock_free(&big));   /* 0       */

/* C++ has the compile-time version, which is what you want in
   a static_assert: */
        static_assert(std::atomic<MyType>::is_always_lock_free,
                      "this type needs a hidden mutex");

/* WHAT IS LOCK-FREE, TYPICALLY

     1, 2, 4, 8 bytes         yes, everywhere
     16 bytes                 x86-64: yes, via CMPXCHG16B
                              ARM64:  yes, via LDXP/STXP or
                                      CASP (LSE)
                              but often only if you compile
                              with -mcx16 / -march=armv8.1-a
     anything larger          NO - a lock table, keyed by
                              address, inside libatomic

   WHY IT MATTERS

     * a hidden lock is not async-signal-safe, so your
       "atomic" is illegal in a signal handler
     * it is not usable across processes in shared memory:
       the lock table is per-process, so two processes
       "atomically" updating the same shared struct do not
       exclude each other AT ALL
     * performance falls off a cliff you cannot see in the
       source

   Check it. Once, in a static_assert, and never worry again. */
volatile is still not atomic

Worth repeating from chapter 2 because it is the most durable misconception in this field. volatile stops the compiler caching a value in a register. It does not make the access indivisible, does not stop the CPU reordering, and does not give any ordering guarantee. On MSVC with /volatile:ms it happens to add acquire/release semantics — which is why code written for Windows breaks when ported, and why /volatile:iso exists.

What atomics are actually for

Atomics are reached for far more often than they are needed, and used for far fewer things than they could be. These are the cases where they are genuinely the right tool rather than a premature optimisation.

/* The reference-count idiom, written correctly. It is the
   most common real use of non-trivial ordering.            */

void ref_get(struct obj *o)
{
        /* relaxed: we already hold a reference, so the object
           cannot die under us, and no data is being published */
        atomic_fetch_add_explicit(&o->refs, 1, memory_order_relaxed);
}

void ref_put(struct obj *o)
{
        if (atomic_fetch_sub_explicit(&o->refs, 1,
                                      memory_order_release) == 1) {
                /* We dropped the last reference. The release
                   above published OUR writes. Now we must
                   ACQUIRE everyone else's before we destroy,
                   or we may free memory whose last write we
                   never saw.                                 */
                atomic_thread_fence(memory_order_acquire);
                destroy(o);
        }
}
/* This exact pattern is in the C++ standard's shared_ptr
   discussion, in Boost, and in the Linux kernel's kref. If you
   find yourself writing a refcount by hand, copy it exactly. */
