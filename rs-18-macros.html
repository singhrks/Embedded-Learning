Macros: declarative and procedural

Rust macros operate on the syntax tree, not on text. That single difference removes every hazard that makes C macros dangerous, and it is why #[derive], println! and the entire embedded register-generation ecosystem can exist without anyone being afraid of them.

Why these are not C macros

If your instinct is that macros are a last resort, that instinct was trained on the C preprocessor and does not transfer. The differences are not stylistic — they are the removal of specific failure modes.

   THE C PREPROCESSOR IS A TEXT SUBSTITUTION PASS that runs
   before the compiler knows anything about the language.

     #define SQUARE(x) x * x
     SQUARE(1 + 2)        ->  1 + 2 * 1 + 2   ==  5

   Every C programmer learns to write ((x) * (x)). That is
   a WORKAROUND for a design flaw.

     #define MAX(a,b) ((a) > (b) ? (a) : (b))
     MAX(i++, j)          ->  i++ evaluated TWICE

   ---------------------------------------------------------

   RUST MACROS OPERATE ON TOKEN TREES, after parsing. So:

     · AN ARGUMENT IS A PARSED EXPRESSION. square!(1 + 2)
       receives the expression (1+2), not the characters.
       No parenthesisation ritual, ever.
     · HYGIENE. A variable the macro introduces cannot
       collide with one at the call site. The C "declare a
       temp and hope the caller did not use that name"
       problem does not exist.
     · THEY ARE TYPE CHECKED after expansion, with errors
       reported against your source.
     · THEY ARE SCOPED AND IMPORTABLE like other items,
       rather than being globally visible from the point of
       #define onwards.

   ---------------------------------------------------------

   WHICH IS WHY MACROS ARE ORDINARY IN RUST. println!,
   vec!, assert_eq!, #[derive(Debug)], #[tokio::main] and
   every register definition in a PAC (chapter 20) are
   macros. You have been using them since chapter 01.

   YOU CAN SEE WHAT ANY OF THEM EXPANDS TO:
     cargo expand
   which is the single most useful thing to know in this
   chapter, and the fastest way to stop finding a macro
   mysterious.

When a macro is the right answer

Macros are still the heavier tool, and functions or generics handle most cases. The test is whether what you need is expressible in the type system at all.

You needReach for
The same logic for several typesGenerics — type-checked once, no expansion to debug
Shared behaviour across typesTraits
A variable number of argumentsA macro — Rust has no variadic functions
To implement a trait for many types mechanicallyA declarative macro, or a derive
To generate code from a type's fieldsA derive macro — this is what #[derive(Debug)] is
To capture the source text of an argumentA macro — assert! printing the failing expression needs this
Compile-time file, line or moduleA macro
A domain-specific syntaxA function-like proc macro — and think hard first

The honest summary is that you will write declarative macros occasionally and proc macros rarely, and you will read both constantly. Reading is the skill worth having.

Declarative macros: macro_rules!

A declarative macro is pattern matching over syntax. You write the shapes the call may take, and the code each shape expands to — which makes it much closer to a match expression than to a #define.

// The whole idea in one example.
macro_rules! square {
    ($x:expr) => { $x * $x };
    //  ^   ^-- FRAGMENT SPECIFIER: parse this as an
    //  |       expression
    //  +------ a metavariable, named by you
}

// square!(1 + 2) expands to (1 + 2) * (1 + 2) == 9.
// The expression is captured as ONE node, so precedence
// cannot be broken. No parentheses required.

// -------------------------------------------------------
// REPETITION is what makes them worth writing.

macro_rules! my_vec {
    () => { Vec::new() };

    // $(...),*  means "the pattern, comma separated, zero
    // or more times". The trailing $(,)? permits a trailing
    // comma - a courtesy every real macro should include.
    ($($item:expr),* $(,)?) => {{
        let mut v = Vec::new();
        $( v.push($item); )*      // expand once PER item
        v
    }};
}

let v = my_vec![1, 2, 3];

// NOTE THE DOUBLE BRACES {{ }}: the outer pair is the macro
// body, the inner pair is a BLOCK EXPRESSION so that the
// whole thing has a value. Forgetting this is the most
// common beginner mistake.

// -------------------------------------------------------
// THE PATTERN YOU WILL ACTUALLY USE: implementing a trait
// for a list of types without writing it out n times.

macro_rules! impl_register {
    ($($t:ty => $width:expr),* $(,)?) => {
        $(
            impl Register for $t {
                const WIDTH: u8 = $width;
                fn raw(&self) -> u32 { self.0 as u32 }
            }
        )*
    };
}

impl_register! {
    Ctrl   => 32,
    Status => 16,
    Fifo   => 8,
}

/* THE FRAGMENT SPECIFIERS WORTH KNOWING:

     expr    an expression          ty     a type
     ident   an identifier          path   a::b::C
     literal a literal              block  { ... }
     stmt    a statement            item   fn/struct/impl
     tt      ONE token tree - matches anything, and is the
             escape hatch when nothing else fits

   PICK THE NARROWEST ONE THAT WORKS. expr and ty are parsed
   and give good errors; tt accepts anything and gives you
   nothing, so errors surface deep inside the expansion.  */
The two rules that keep declarative macros usable

A metavariable is captured, not substituted. $x:expr becomes a single parsed node, so precedence is already correct — but it also means the expression is expanded wherever $x appears, so using $x twice evaluates it twice. square!(next()) calls next() twice, exactly as the C version would. Bind it to a local first if that matters, and hygiene means your local cannot collide with the caller's. Hygiene applies to variables, not to types. A local introduced inside the macro is invisible to the caller, which is the property C lacks. Type and function paths are not hygienic in the same way, so a macro that mentions Vec breaks at a call site that shadowed it — write ::std::vec::Vec with a leading :: in a macro you intend to export.

Procedural macros

When pattern matching is not enough — when you need to look at a type's fields and generate code from them — you write a Rust program that transforms the syntax tree. That is all a proc macro is, and its main cost is structural rather than conceptual.

   THREE KINDS, distinguished by how they are invoked:

     DERIVE          #[derive(Debug, Serialize)]
                     reads a struct or enum, ADDS new code
                     alongside it. The common case by far.

     ATTRIBUTE       #[tokio::main]  #[entry]  #[interrupt]
                     reads an item and REPLACES it. This is
                     how embedded entry points and interrupt
                     handlers work (chapter 20).

     FUNCTION-LIKE   sql!(SELECT * FROM t)
                     arbitrary tokens in, code out.

   ---------------------------------------------------------

   THEY MUST LIVE IN THEIR OWN CRATE, marked
   proc-macro = true in Cargo.toml. That is not arbitrary:
   the macro RUNS AT COMPILE TIME, so it is compiled first,
   for the HOST - which is also why a proc macro works fine
   in a no_std crate compiled for a microcontroller. The
   macro runs on your laptop; only its output is cross
   compiled.

   THE STANDARD THREE DEPENDENCIES:
     syn     parse TokenStream into a typed syntax tree
     quote   build a TokenStream from a template
     proc-macro2  the types that let the other two work
                  outside the compiler, so they can be
                  unit tested

   ---------------------------------------------------------

   THE COST: compile time. A proc macro crate and its
   dependencies must be built before your crate starts, and
   syn is not small. This is a real and frequently
   underestimated part of why some Rust builds are slow.
// A complete derive macro: #[derive(FieldNames)] generates
// a method listing a struct's field names.

use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, Data, DeriveInput, Fields};

#[proc_macro_derive(FieldNames)]
pub fn derive_field_names(input: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;

    // Pull the field names out, or fail with a message
    // pointing at the user's type rather than at us.
    let fields = match &ast.data {
        Data::Struct(s) => match &s.fields {
            Fields::Named(f) => &f.named,
            _ => return syn::Error::new_spanned(
                     &ast.ident,
                     "FieldNames requires named fields")
                 .to_compile_error().into(),
        },
        _ => return syn::Error::new_spanned(
                 &ast.ident, "FieldNames is for structs only")
             .to_compile_error().into(),
    };

    let names = fields.iter()
        .map(|f| f.ident.as_ref().unwrap().to_string());

    // quote! is a template. #name interpolates; #(...),*
    // repeats over an iterator.
    let expanded = quote! {
        impl #name {
            pub const FIELD_NAMES: &'static [&'static str] =
                &[ #(#names),* ];
        }
    };
    expanded.into()
}

/* THE ERROR HANDLING IS THE PART TO COPY. A proc macro that
   panics produces "proc-macro derive panicked", which tells
   the user nothing. Returning a compile_error! built with
   new_spanned points the compiler at the offending line in
   THEIR code, with your message. The difference between a
   pleasant macro and a hated one is almost entirely this. */

Debugging a macro

Macro errors are reported against expanded code you never wrote, which is disorienting the first time. Three tools make it tractable, and the first is the one to reach for every time.

   1. cargo expand
        Shows the code your macro actually produced. Nine
        problems in ten become obvious immediately. Install
        it before you write your first macro, not after.

          cargo expand                 whole crate
          cargo expand path::to::item  one item

   2. trace_macros!(true)          (nightly)
        Prints each macro_rules! expansion step as the
        compiler performs it - useful when a recursive macro
        is not terminating.

   3. UNIT TEST THE PROC MACRO ITSELF.
        Because syn and quote work on proc-macro2 types, the
        transformation is an ordinary function you can call
        from a test. Assert on the generated token string.
        Most people never do this, and it is why proc macros
        have a reputation for being hard to work on.

   ---------------------------------------------------------

   AND THE THING THAT SAVES THE MOST TIME: WRITE THE OUTPUT
   BY HAND FIRST. Write the impl you want, for one concrete
   type, and get it compiling. THEN turn the parts that vary
   into metavariables. Trying to design a macro and the code
   it generates simultaneously is how afternoons disappear.
