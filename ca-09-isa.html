Instruction set architecture: RISC vs CISC

The ISA is the contract between hardware and software — the only part of a processor that software can see, and the only part the manufacturer cannot change. This chapter explains what belongs in that contract, why the RISC/CISC argument happened, and why the answer today is stranger than either side predicted.

The problem: what must a processor promise?

A chip designer wants freedom. Caches, pipeline depth, how many instructions issue per cycle, whether execution is in order — all of that should be changeable between generations without breaking existing software.

A software author wants stability. A binary compiled in 2015 should still run in 2030.

The instruction set architecture is the negotiated boundary. It specifies exactly what software may rely on, and by omission grants the designer freedom over everything else.

Architecture versus microarchitecture

Architecture is the specification: instructions, their encodings and effects, the register set, the memory model, the exception model. It is a document — for ARM, the Architecture Reference Manual.

Microarchitecture is one implementation of that specification: Cortex-A78, Neoverse N2, Apple's M-series cores. Pipeline depth, cache sizes, branch predictor design, reorder buffer size.

The distinction is the most practically useful one in this chapter. Architectural behaviour is portable across every implementation — if your code is architecturally correct it works everywhere. Microarchitectural behaviour is timing, and is chip-specific. When debugging, always ask which one you are fighting: architectural bugs reproduce anywhere, microarchitectural surprises (timing, cache effects, errata) do not.

Everything not on that list — how many cycles an instruction takes, whether there is an L3 cache, how branches are predicted — is deliberately unspecified, and that omission is what lets a Cortex-A55 and a Cortex-X4 run identical binaries at wildly different speeds.

The CISC era and its logic

In the 1970s, memory was scarce and expensive, compilers were poor, and much code was written by hand in assembly. Those three facts pointed in one direction: make each instruction do as much as possible.

The CISC bet, stated plainly:

  - Programs are stored in expensive memory  →  make instructions DENSE
  - Humans write assembly                    →  make instructions EXPRESSIVE
  - Compilers are weak                       →  close the "semantic gap" in HARDWARE

Result: instructions that are almost statements in a high-level language.

  VAX-11 (the extreme case):
      MOVC3  len, src, dst      ; copy a string, one instruction
      POLYD  x, degree, table   ; evaluate a polynomial, one instruction
      INDEX  ...                ; bounds-checked array index with trap

  x86:
      REP MOVSB                 ; copy ECX bytes from ESI to EDI
      ADD  [ebx+ecx*4+8], eax   ; load, add, store — one instruction
                                ; and it can also set flags and fault mid-way

What went wrong with it

  • Variable-length encoding. An x86 instruction is 1 to 15 bytes. You cannot know where instruction n+1 begins until you have decoded instruction n. That makes decoding inherently serial — a severe problem once you want to decode four or eight instructions per cycle.
  • Microcode. Complex instructions are not executed directly; they are interpreted by a small internal program. Microcode is slow, hard to pipeline, and a source of errata.
  • The 90/10 measurement. Studies in the late 1970s found compilers used a small fraction of the available instructions. The exotic ones cost design effort, area and verification, and almost nobody emitted them.
  • Complex instructions can be slower than the equivalent sequence. A famous finding: on some VAX models, INDEX was slower than the several simple instructions that did the same job — the hardware could not be optimised for every case.
  • Faults in the middle. If ADD [mem], eax page-faults after the load but before the store, the machine must be able to restart or complete it precisely. This complicates the exception model enormously.

The RISC counter-argument

Berkeley RISC and Stanford MIPS, around 1980, inverted every assumption:

PrincipleReasoning
Fixed-length instructionsDecode becomes trivial and parallel; you can fetch and decode N instructions per cycle without knowing their contents
Load/store architectureOnly explicit loads and stores touch memory. Every other instruction is register-to-register, so only one class of instruction can fault on a data access.
Many registersKeep values in registers rather than spilling to memory. RISC designs went from 8 to 32.
Simple addressing modesOne memory address computation per instruction, at most
No microcodeInstructions execute directly in hardware, one per cycle in the ideal case
Let the compiler do the workCompilers had improved. Scheduling, register allocation and strength reduction move to software, where they can be improved without new silicon.
 
The same operation, both philosophies

CISC (x86-64):
    add    QWORD PTR [rbx+rcx*8+16], rax     ; one instruction
                                              ; internally: load, add, store

RISC (AArch64):
    add    x3, x1, x2, lsl #3    ; compute the address
    ldr    x4, [x3, #16]         ; LOAD
    add    x4, x4, x0            ; ADD  (registers only)
    str    x4, [x3, #16]         ; STORE

More instructions, more bytes. But each one is simple, fixed-width,
independently schedulable, and can fault in exactly one obvious place.

The cost RISC accepted

Code density. A fixed 32-bit encoding wastes bits on simple operations — MOV X0, X1 uses the same four bytes as a complex shifted-add. Larger binaries mean more instruction-cache pressure, which is a real performance cost, not a cosmetic one.

ARM's answer to this was Thumb (1994) and later Thumb-2: a 16-bit encoding of the most common instructions, mixed freely with 32-bit ones, typically saving 30% of code size. Thumb is why ARM won the mobile market, where flash memory cost real money. Notably, AArch64 removed Thumb — by 2011 memory was cheap and decode simplicity mattered more.

Why the debate ended in a draw nobody predicted

Modern high-performance x86 processors decode their CISC instructions into internal RISC-like micro-operations and execute those on an out-of-order engine that would be entirely familiar to a RISC designer.

A modern x86 core, internally

   x86 instruction bytes (1-15 bytes each)
              │
              ▼
   ┌──────────────────────┐
   │  length pre-decode    │   ← expensive, serial, uniquely x86
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │      decoders         │   ← simple ops → 1 µop
   │                       │     complex ops → microcode sequencer
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │     µop cache         │   ← caches already-decoded µops so the
   └──────────┬───────────┘     expensive decode is skipped in loops
              ▼
   ┌──────────────────────────────────────────┐
   │  rename → schedule → execute → retire     │  ← this part is
   │  fixed-width internal ops, many registers │    essentially RISC
   └──────────────────────────────────────────┘

So RISC won architecturally inside the chip, while CISC survived as an external interface because of binary compatibility. Meanwhile ARM, nominally RISC, has accumulated crypto instructions, complex SIMD, atomic memory operations that execute near the memory controller, and load/store-pair instructions — none of which a 1980 RISC purist would have accepted.

Where the difference still genuinely matters

The lasting advantage is not instruction complexity, it is decode. Fixed 32-bit encoding means an ARM core can decode 8 instructions per cycle with 8 simple parallel decoders. An x86 core needs length pre-decode first, which is serial and power-hungry, and mitigates it with a µop cache — extra area and power that ARM simply does not spend. This is a large part of why ARM designs reach better performance per watt, and why Apple's cores could go so wide so cheaply.

Reading an instruction encoding

Fixed-width encoding is not just a design principle; it is something you will read directly when debugging without symbols. Here is an AArch64 instruction taken apart.

    ADD X0, X1, X2          encodes as 0x8B020020

 31 30 29 28    24 23 22 21 20   16 15    10 9    5 4    0
┌──┬──┬──┬────────┬─────┬──┬───────┬────────┬──────┬──────┐
│sf│op│ S│ 0 1 0 1│shift│ 0│   Rm  │ imm6   │  Rn  │  Rd  │
└──┴──┴──┴────────┴─────┴──┴───────┴────────┴──────┴──────┘
  1  0  0   01011    00   0  00010   000000  00001  00000

  sf    = 1   → 64-bit operands (0 would mean 32-bit, Wn registers)
  op    = 0   → ADD (1 would be SUB)
  S     = 0   → do not set flags (1 gives ADDS)
  shift = 00  → LSL
  Rm    = 2   → X2
  imm6  = 0   → shift amount 0
  Rn    = 1   → X1
  Rd    = 0   → X0

Change sf to 0 and you have ADD W0, W1, W2 — same instruction, 32-bit.
Change S to 1 and it sets NZCV. Change op to 1 and it subtracts.

Every field is in a FIXED position. That is what makes the decoder
(chapter 05's decoder block) small and fast.

Notice that the last two classes are where a general-purpose ISA stops being general. System instructions are the entire subject of the ARM track's second half, and SIMD is the reason machine learning runs at all on a CPU.

Orthogonality and why compilers care

An ISA is orthogonal when any operation works with any register and any addressing mode, with no exceptions. Orthogonality makes a compiler's register allocator simple, because no register is special.

Non-orthogonal (8086, and it shaped a generation of compilers):
    - MUL always uses AX and DX implicitly
    - String instructions require SI, DI, CX
    - Only BX, SI, DI, BP may be used as base registers
    → the allocator must reason about which value must live where

Orthogonal (AArch64, nearly):
    - Any Xn can be any operand of almost any instruction
    - Exceptions are few and documented:
        · X30 is written by BL
        · X16/X17 may be clobbered by linker veneers
        · X18 is reserved on some platforms
        · SP must be 16-byte aligned at public interfaces
        · XZR reads as zero and discards writes

This is why the same compiler back end typically produces better code for ARM than for 32-bit x86: fewer constraints to satisfy, more registers to allocate into, less spilling to the stack.

How an ISA grows without breaking

An ISA must evolve — new workloads need new instructions — without invalidating existing binaries. The mechanisms are worth knowing because you will write the code that uses them.

  1. Reserve encoding space. Undefined encodings are kept available and made to fault, so they can later be given meaning.
  2. Add optional extensions. ARMv8.1 added LSE atomics; v8.3 added pointer authentication; v9 added SVE2. Each is optional at a given architecture level.
  3. Advertise features in ID registers. ID_AA64ISAR0_EL1 and friends report what this specific chip implements.
  4. Have software detect and adapt. The OS reads the ID registers at boot and patches code paths accordingly.
/* Linux exposes CPU features to user space through HWCAP */
#include <sys/auxv.h>
#include <asm/hwcap.h>

unsigned long hw  = getauxval(AT_HWCAP);
unsigned long hw2 = getauxval(AT_HWCAP2);

if (hw & HWCAP_ATOMICS)   use_lse_atomics();    /* single-instruction atomics */
else                      use_ldxr_stxr();      /* the exclusive-monitor loop */

if (hw & HWCAP_ASIMD)     use_neon_kernel();
if (hw & HWCAP_SVE)       use_sve_kernel();
if (hw2 & HWCAP2_SVE2)    use_sve2_kernel();

/* the kernel does the same thing internally, but patches the code in
   place at boot with "alternatives" so there is no runtime branch:
   ALTERNATIVE("ldxr ...", "ldadd ...", ARM64_HAS_LSE_ATOMICS)          */
The trap this creates

Code compiled with -march=armv8.2-a+crypto will execute an illegal-instruction fault on a chip lacking those extensions — usually as SIGILL, often long after startup, in a library you did not write. Distribution binaries therefore target a baseline and dispatch at runtime. When you see "Illegal instruction" on one machine and not another, this is almost always the reason.
