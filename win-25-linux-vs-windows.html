Linux and Windows drivers compared

Two operating systems solving identical problems with opposite philosophies. Having built a driver in each, the comparison is now concrete — and it is the fastest way to see what each design actually costs and buys.

The root difference

Almost every difference between the two systems traces back to one decision about who is responsible for keeping drivers working. Holding that single idea makes the rest of the comparison predictable rather than a list to memorise.

   ONE DECISION EXPLAINS ALMOST EVERYTHING ELSE:

   LINUX: NO STABLE INTERNAL ABI.
      The kernel may refactor any interface at any time,
      because it can fix every in-tree driver in the same
      commit.

      -> drivers must be UPSTREAM to survive
      -> therefore the source is public
      -> therefore review is by humans reading code
      -> therefore no signing requirement, no certification
      -> therefore no framework is needed: the core can be
         changed to suit the drivers
      -> and an out-of-tree driver is a permanent maintenance
         liability (Linux ch. 45)

   WINDOWS: A STABLE DRIVER ABI, FOR DECADES.
      A driver from 2015 often still loads.

      -> drivers ship as closed binaries
      -> therefore Microsoft never sees the source
      -> therefore review must be MECHANICAL: static
         analysis, Driver Verifier, HLK
      -> therefore signing is mandatory - identity is the only
         accountability available
      -> therefore a FRAMEWORK (WDF) is needed, because the
         protocol cannot be simplified by changing the core
      -> and installation needs a declarative package (the
         INF) rather than "copy the file"

   NEITHER IS WRONG. They are consistent answers to: who is
   responsible for keeping drivers working?
     Linux says: the kernel community, for code it can see.
     Windows says: the vendor, for code it cannot.

Concept map

The two kernels solve the same set of problems — because the underlying hardware and the underlying requirements are the same — and diverge mainly in whether a concept is implicit or explicit. The clearest example is the very first row: Linux infers "can I sleep here?" from which kind of context you happen to be running in, which you learn to recognise by convention, while Windows makes it an actual number you can read with a function call and that every API documents a requirement against. Neither approach is more capable than the other — a Linux hardirq and a Windows DIRQL handler have identical restrictions — but if you already know one kernel, the fastest way to learn the other is to find the row here for whatever you are trying to do and treat the difference as a change of spelling for a mechanism you already understand, rather than a new mechanism to learn from scratch.

The honest summary

Linux is easier to start with and easier to learn from, because everything is readable and the loop is fast. Windows is better at keeping you correct, because the framework owns the hard protocols and the verification tooling finds the bugs mechanically. A developer who has done both tends to want Linux's iteration speed and Windows' verifiers — and, in practice, to bring habits from each into the other: annotating invariants like SAL, and running the negative-test discipline that the HLK enforces.

What is the same everywhere

Beneath the different names and APIs, the hard problems are identical — and recognising that is what makes experience on one platform transfer to the other rather than starting over.

Strip away the APIs and the same problems remain, because
they come from the HARDWARE, not the OS:

  · an interrupt handler must be short, because it blocks
    everything else
  · deferred work needs a tier that can sleep and one that
    cannot
  · shared data needs a lock chosen by the highest-priority
    context that touches it
  · a lock held too long is a latency bug for the whole system
  · DMA needs the device's address, not the CPU's, and the
    pages must be pinned
  · caches must be maintained, or coherent hardware must do it
  · the power-up sequence in the datasheet is a specification
  · resources must be acquired in order and released in
    reverse
  · teardown must stop the source before waiting for what is
    in flight
  · every input crossing a trust boundary must be validated,
    copied in, and bounded
  · hardware that stops responding must produce a timeout,
    never an infinite wait
  · error paths are the least-tested code and need mechanical
    exercise

  THAT LIST is what this whole track has actually been about.
  The two dialects are how you say it; the list is what you
  say.

Porting between them

Moving a driver between the two is mostly a matter of separating the hardware logic from the platform glue. This is what that separation looks like in practice, and what genuinely cannot be shared.

/* If you must support both - which is common for a chip
   vendor - structure the driver so the shared part is real. */

   +-----------------------------------------------+
   |  HARDWARE LOGIC - shared, portable C           |
   |    register definitions                        |
   |    the state machine                           |
   |    protocol encoding and decoding              |
   |    NO OS calls at all                          |
   +-----------------------------------------------+
              |                        |
   +----------v---------+   +----------v-----------+
   |  LINUX SHIM        |   |  WINDOWS SHIM        |
   |   readl/writel     |   |   READ_REGISTER_*    |
   |   spin_lock        |   |   WdfSpinLockAcquire |
   |   kmalloc          |   |   ExAllocatePool2    |
   |   dev_err          |   |   TraceEvents        |
   |   probe/remove     |   |   EvtDeviceAdd/...   |
   +--------------------+   +----------------------+

/* DEFINE A THIN OS ABSTRACTION and implement it twice: */

        osal_reg_read32(dev, offset)
        osal_reg_write32(dev, offset, value)
        osal_lock_acquire(lock)
        osal_alloc(size)
        osal_delay_us(n)
        osal_log(level, fmt, ...)

/* WHAT PORTS WELL:  register access, hardware sequences,
   protocol logic, data formats, error decoding.

   WHAT DOES NOT:    everything about the OS - PnP, power,
   queueing, buffering, cancellation, installation, security.
   Do NOT try to abstract those; the models are too different
   and the abstraction becomes worse than either.

/* THE REALISTIC SPLIT on a typical device driver: 30-40% of
   the code is hardware logic and shareable; the rest is OS
   integration, written twice. That is still a large saving,
   and more importantly it means the hardware behaviour is
   defined in ONE place, so a silicon erratum workaround is
   applied once rather than diverging.                     */

Which to learn

A practical question worth answering honestly rather than tribally: the two ecosystems hire for different things, and which to invest in depends on what you want to build.

   EMBEDDED LINUX dominates:
     · phones, tablets, TVs, set-top boxes
     · automotive infotainment and increasingly ADAS
     · networking equipment, from home routers to core
     · industrial control, robotics, drones
     · almost everything running on an ARM SoC that is not a
       microcontroller
     -> if "embedded" is your field, Linux is the default and
        this is where the jobs are

   WINDOWS DRIVERS dominate:
     · PC peripherals of every kind
     · enterprise storage and networking hardware
     · specialised industrial and medical equipment on
       Windows
     · anything sold into a Windows-first ecosystem
     -> a smaller field, with fewer people who know it well,
        and correspondingly good demand

   LEARNING BOTH is worth more than the sum: each makes the
   other's design decisions visible. You cannot really see
   why Linux has no stable ABI until you have felt what a
   stable one costs, and you cannot appreciate what WDF does
   until you have hand-written a cancellation path.

   AND THE HARDWARE KNOWLEDGE - the ARM architecture,
   isolation, memory ordering, DMA, caches, interrupts, power -
   TRANSFERS COMPLETELY. That is the durable part, and it is
   why the tracks before these two are the foundation rather
   than the preamble.
