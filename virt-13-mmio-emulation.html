Trapping MMIO and emulating a device

A device model is a state machine driven by faults. The guest stores to an address that has no memory behind it, the hypervisor decodes what that store meant, updates some software state, and possibly raises an interrupt. This chapter builds one from nothing, and shows why doing it in the fewest possible traps is the entire design problem.

A device is a hole in the address space

A virtual device is, mechanically, a region of guest address space that is deliberately left unmapped so that every access faults. That is the whole trick.

   Guest's view of its own physical memory:

     0x0000_0000  +--------------------+
                  |  (nothing)         |
     0x0800_0000  +--------------------+
                  |  GIC distributor   |  <- emulated
     0x0801_0000  +--------------------+
                  |  GIC redistributor |  <- emulated
     0x0900_0000  +--------------------+
                  |  PL011 UART        |  <- emulated
     0x0900_1000  +--------------------+
                  |  RTC               |  <- emulated
     0x0a00_0000  +--------------------+
                  |  virtio-mmio x32   |  <- emulated
     0x1000_0000  +--------------------+
                  |  PCIe ECAM         |  <- emulated
     0x4000_0000  +--------------------+
                  |                    |
                  |  RAM               |  <- REAL memory,
                  |                    |     mapped at stage 2
                  +--------------------+

   Stage 2 maps the RAM region and leaves EVERYTHING ELSE
   unmapped. Every access to a device region therefore takes a
   stage-2 translation fault, which is exactly the notification
   the hypervisor wants.

   In KVM this is expressed as MEMSLOTS: user space registers
   "guest physical range X is backed by this host virtual
   address". Anything outside a memslot is, by definition, MMIO.

The path of one register write

Following one register write from the guest instruction to the device model and back shows exactly where the cost is.

/* Guest driver:                                             */
        writel(0x41, uart_base + UARTDR);   /* print 'A'      */

/* 1. STR w0, [x1] where x1 -> IPA 0x0900_0000               */

/* 2. Stage-2 translation fault. ESR_EL2:
        EC   = 0x24  data abort from lower EL
        ISV  = 1     syndrome valid
        SAS  = 0b10  word access
        SRT  = 0      register x0
        WnR  = 1      it was a write
        DFSC = 0b000111  translation fault, level 3

      HPFAR_EL2 gives IPA 0x0900_0000.                       */

/* 3. KVM: is 0x0900_0000 inside a memslot?  No.
      -> it is MMIO. Is there an in-kernel device claiming it?
         (vGIC, arch timer, PV interfaces)  No.
      -> hand it to user space.                              */

/* 4. KVM_RUN returns. kvm_run->exit_reason = KVM_EXIT_MMIO:  */

        struct {
                __u64 phys_addr;   /* 0x09000000              */
                __u8  data[8];     /* 0x41                    */
                __u32 len;         /* 4                       */
                __u8  is_write;    /* 1                       */
        } mmio;

/* 5. QEMU dispatches to the PL011 model, which appends 'A' to
      the character device. If this were a READ, QEMU would
      instead fill kvm_run->mmio.data before re-entering.    */

/* 6. ioctl(KVM_RUN) again. KVM writes the read data into the
      guest's register x0 if needed, ADVANCES THE GUEST PC past
      the faulting instruction, and ERETs.

      Note: skip, not retry. The access was emulated, not
      fixed - the opposite of a memory fault (chapter 06).    */
Two tiers of device model

Devices that are hot and simple live in the kernel: the vGIC, the architected timer, the PV interfaces. Their exits never leave KVM_RUN, costing single-digit microseconds. Everything else lives in user space, costing ten times that but gaining the ability to be written in ordinary code with files, threads and sockets. Deciding which tier a device belongs in is the main performance lever you have.

Writing a device model

Device models are less mysterious than they sound, and a small complete one makes the pattern obvious.

/* A minimal PL011 UART model. This is the shape of every
   device model you will ever write: a struct of state, a read
   function, a write function, and an interrupt line.        */

struct pl011 {
        uint32_t dr;          /* data                        */
        uint32_t fr;          /* flags                       */
        uint32_t imsc;        /* interrupt mask              */
        uint32_t ris;         /* raw interrupt status        */
        uint32_t cr;          /* control                     */
        uint8_t  rxfifo[16];
        unsigned rxhead, rxtail;
        int      irq;         /* which vINTID we raise       */
        int      chr_fd;      /* where output goes           */
};

#define UARTDR    0x000
#define UARTFR    0x018
#define UARTIMSC  0x038
#define UARTRIS   0x03c
#define UARTMIS   0x040
#define UARTCR    0x030
#define UARTICR   0x044

#define FR_RXFE   (1u << 4)   /* receive FIFO empty          */
#define FR_TXFF   (1u << 5)   /* transmit FIFO full          */
#define INT_RX    (1u << 4)
#define INT_TX    (1u << 5)

static uint32_t pl011_read(struct pl011 *u, uint64_t off)
{
        switch (off) {
        case UARTDR: {
                uint32_t c = 0;
                if (u->rxhead != u->rxtail) {
                        c = u->rxfifo[u->rxtail++ % 16];
                        if (u->rxhead == u->rxtail)
                                u->fr |= FR_RXFE;
                }
                /* READING CLEARS STATE. This is why speculative
                   reads of device memory are forbidden - see
                   chapter 07.                                */
                pl011_update_irq(u);
                return c;
        }
        case UARTFR:   return u->fr;
        case UARTRIS:  return u->ris;
        case UARTMIS:  return u->ris & u->imsc;
        case UARTIMSC: return u->imsc;
        default:       return 0;      /* never fault the guest
                                         for an unknown offset -
                                         real hardware does not */
        }
}

static void pl011_write(struct pl011 *u, uint64_t off, uint32_t v)
{
        switch (off) {
        case UARTDR: {
                uint8_t c = v & 0xff;
                write(u->chr_fd, &c, 1);
                u->ris |= INT_TX;       /* transmit completed   */
                pl011_update_irq(u);
                break;
        }
        case UARTIMSC: u->imsc = v; pl011_update_irq(u); break;
        case UARTICR:  u->ris &= ~v;  pl011_update_irq(u); break;
        case UARTCR:   u->cr   = v; break;
        }
}

static void pl011_update_irq(struct pl011 *u)
{
        int level = (u->ris & u->imsc) != 0;
        set_irq_line(u->irq, level);     /* KVM_IRQ_LINE ioctl  */
}

/* Rules this small function already demonstrates:

   1. NEVER fault on an unrecognised offset. Return 0 and log.
      Guests probe. Hardware tolerates probing.
   2. Model side effects of READS explicitly (clear-on-read,
      FIFO pop). Getting these wrong causes lost data that
      looks like a driver bug.
   3. Recompute the interrupt line after any state change, and
      drive it as a LEVEL, not an edge. Level semantics are
      self-correcting; edges get lost.
   4. Handle partial-width accesses. A guest may read a byte of
      a 32-bit register.                                      */

The cost, and how to escape it

The cost per access is high enough that it shapes designs, which is the reason virtio exists at all.

/* ioeventfd: the single most valuable optimisation for a
   device model, and the reason virtio is fast.             */

  Ordinary path for "kick the queue":
     guest writes QueueNotify
       -> stage-2 fault
       -> exit to EL2
       -> exit to host kernel
       -> exit to QEMU
       -> QEMU decodes, finds the queue, processes
       -> re-enter (4 transitions)

  With ioeventfd:
     QEMU tells KVM in advance:
        "a write to 0x0a000050 of any value means: signal
         eventfd 7. Do not tell me the value. Do not return
         from KVM_RUN."

     guest writes QueueNotify
       -> stage-2 fault
       -> KVM writes eventfd 7 and IMMEDIATELY RE-ENTERS
       -> a separate QEMU thread (or vhost kernel thread)
          wakes on eventfd 7 and does the work CONCURRENTLY
          with the guest continuing to run.

  The guest never waits. The exit is a light one. This is the
  difference between "virtio is fine" and "virtio is fast".  */

/* The registration, in QEMU terms: */
   struct kvm_ioeventfd ke = {
           .addr     = 0x0a000050,
           .len      = 4,
           .fd       = evfd,
           .flags    = 0,     /* KVM_IOEVENTFD_FLAG_DATAMATCH
                                 if you need to distinguish
                                 which queue was kicked      */
   };
   ioctl(vmfd, KVM_IOEVENTFD, &ke);

Telling the guest the device exists

A guest will not use a device it does not know about, and how it is told differs between platform and discoverable buses.

/* A device model is useless unless the guest is told where it
   is. Two mechanisms; on embedded arm64 it is the device tree. */

/ {
        soc {
                #address-cells = <2>;
                #size-cells    = <2>;

                pl011@9000000 {
                        compatible = "arm,pl011", "arm,primecell";
                        reg = <0x0 0x09000000 0x0 0x1000>;
                        interrupts = <0 1 4>;  /* SPI 1, level  */
                        clocks = <&uartclk>;
                        clock-names = "uartclk";
                };

                virtio_mmio@a000000 {
                        compatible = "virtio,mmio";
                        reg = <0x0 0x0a000000 0x0 0x200>;
                        interrupts = <0 16 1>;
                };
        };
};

/* QEMU GENERATES this device tree at runtime from the machine
   model, which is why -M virt "just works" for any memory size
   and CPU count. To see what your guest was actually given: */

$ qemu-system-aarch64 -M virt,dumpdtb=virt.dtb -nographic ...
$ dtc -I dtb -O dts virt.dtb | less

/* And from inside a running guest: */
$ ls /sys/firmware/devicetree/base/
$ dtc -I fs -O dts /sys/firmware/devicetree/base | less

/* A mismatch between the model's address and the device tree's
   reg property produces a device that is never probed, or a
   guest that faults on a region nothing models. The dumpdtb
   trick resolves this in seconds and is the first thing to
   reach for when "my device does not appear".              */
Never fault the guest for an unknown register

It is tempting to signal an abort when a guest touches an offset you did not implement. Do not. Guests probe hardware, read reserved fields, and read whole register blocks in a loop to dump state. Real silicon returns zero or garbage and carries on. A model that aborts turns a harmless probe into a guest kernel panic, and the panic points at the guest driver rather than at your model.
