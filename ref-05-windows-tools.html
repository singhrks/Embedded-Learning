The Windows debugging toolkit

WinDbg is the most capable debugger in common use and the one with the steepest learning curve. This is the subset that does the work, plus the driver-specific tools that have no Linux equivalent.

Setting up

REM ---- INSTALL ----
REM Windows SDK "Debugging Tools for Windows", or:
winget install Microsoft.WinDbg

REM ---- SYMBOLS: DO THIS FIRST OR NOTHING WORKS ----
setx _NT_SYMBOL_PATH srv*C:\symbols*https://msdl.microsoft.com/download/symbols

REM add your own build output IN FRONT:
setx _NT_SYMBOL_PATH "C:\myproject\out;srv*C:\symbols*https://msdl.microsoft.com/download/symbols"

REM and source, so you get source-level stepping:
.srcpath C:\myproject\src

REM ---- WITHOUT SYMBOLS, EVERY STACK IS HEXADECIMAL AND
REM      USELESS. If a stack looks like nonsense, run
REM      !sym noisy and .reload /f and read what it says
REM      it could not find.

REM ---- KERNEL DEBUGGING: two machines, or a VM ----
REM On the TARGET (an admin prompt), for a network
REM connection:
bcdedit /debug on
bcdedit /dbgsettings net hostip:192.168.1.10 port:50000 key:1.2.3.4
REM ^ it prints a KEY. Save it - the host needs it.

REM Then on the HOST:
windbg -k net:port=50000,key=1.2.3.4

REM Other transports:
bcdedit /dbgsettings serial debugport:1 baudrate:115200
bcdedit /dbgsettings usb targetname:mytarget

REM ---- TEST SIGNING, for driver development ----
bcdedit /set testsigning on
REM reboot. Without this an unsigned driver will not load,
REM and the failure message is not always obvious.

REM ---- CRASH DUMP CONFIGURATION ----
REM System Properties -> Advanced -> Startup and Recovery
REM   Kernel memory dump   the usual choice
REM   Complete memory dump needs a page file at least RAM
REM                        size; use it when you need user
REM                        memory too
REM Dumps land in C:\Windows\MEMORY.DMP

REM ---- FORCE A CRASH, to test the dump path ----
REM Enable the keyboard crash: HKLM\SYSTEM\CurrentControlSet\
REM   Services\kbdhid\Parameters\CrashOnCtrlScroll = 1
REM then Ctrl + ScrollLock + ScrollLock.
REM TEST THIS BEFORE YOU NEED IT.

The commands that matter

* ---- THE THREE-COMMAND CRASH ANALYSIS ----
!analyze -v          * START HERE, ALWAYS. Identifies the
                     * bugcheck, the faulting module, the
                     * probable cause and the stack.
                     * It is right most of the time.
k                    * the stack
lm                   * loaded modules; lm v m mydrv for
                     * detail

* ---- STACKS ----
k                    * current thread
kb                   * with the first three arguments
kv                   * verbose: frame pointers, calling
                     * convention
kP                   * full parameters with types - the
                     * most readable
!thread              * the current thread's full state
!process 0 7         * ALL processes with ALL thread
                     * stacks. Huge, and the right tool for
                     * a hang.
~*k                  * all threads in the current process
                     * (user mode)

* ---- MEMORY ----
dd addr              * dwords
dq addr              * qwords
db addr              * bytes + ASCII
dc addr              * dwords + ASCII
du addr              * UNICODE string
da addr              * ASCII string
dt nt!_EPROCESS addr * DUMP A TYPED STRUCTURE - the single
                     * most useful WinDbg command
dt mydrv!_DEVICE_CONTEXT addr
dt -r nt!_IRP addr   * recursive, expanding substructures
!pool addr           * which pool allocation an address is
                     * in
!address addr        * what kind of memory this is
ed / eb / eq         * EDIT memory
s -b 0 L?ffffffff 41 42 43   * SEARCH memory

* ---- DRIVER-SPECIFIC, and these have no Linux
*      equivalent ----
!irp addr            * decode an IRP: which stack location,
                     * which driver, what major function
!devobj addr         * a device object
!drvobj mydrv 7      * a driver object with all its
                     * dispatch routines - shows instantly
                     * whether you registered the handler
                     * you think you did
!devstack addr       * the whole device stack - who is
                     * above and below you
!devnode 0 1         * the PnP device tree
!wdfkd.wdfdriverinfo mydrv   * KMDF state
!wdfkd.wdfqueue addr
!wdfkd.wdfdevice addr
!wdflogdump mydrv    * THE KMDF INTERNAL LOG. Read this
                     * before anything else when a KMDF
                     * driver misbehaves.

* ---- POOL AND MEMORY LEAKS ----
!poolused 2          * per-tag, sorted by usage. USE A
                     * UNIQUE POOL TAG PER ALLOCATION SITE
                     * IN YOUR DRIVER and this finds your
                     * leak in one command.
!poolfind MyTg
!vm                  * system memory summary
!heap -s             * user-mode heaps

* ---- BREAKPOINTS ----
bp mydrv!MyDispatch          * software breakpoint
bu mydrv!MyDispatch          * UNRESOLVED - set it before
                             * the driver loads, and it
                             * arms when it does. THIS IS
                             * THE ONE YOU WANT for
                             * DriverEntry.
ba w4 addr                   * hardware WRITE breakpoint on
                             * 4 bytes - the watchpoint
                             * equivalent
bp mydrv!Fn ".printf \"len=%d\\n\", @rcx; gc"
                             * print and continue, without
                             * stopping
bl                           * list
bc *                         * clear all

* ---- EXECUTION ----
g        * go
p        * step over
t        * step into
gu       * go up (finish)
.restart

* ---- SESSION ----
.reload /f           * force symbol reload
.sympath+ C:\mysyms
.logopen C:\log.txt  * LOG THE WHOLE SESSION. Do this.
.dump /ma C:\my.dmp  * write a full dump
!sym noisy           * diagnose symbol loading
.hh command          * open help for a command

Reading a bugcheck

* !analyze -v output, and what to actually read:

  DRIVER_IRQL_NOT_LESS_OR_EQUAL (d1)
  Arguments:
    Arg1: ffffb00000000000   memory referenced
    Arg2: 0000000000000002   IRQL at the time
    Arg3: 0000000000000001   0 = read, 1 = WRITE
    Arg4: fffff80512345678   address that referenced it

  READ THE FOUR ARGUMENTS. They usually contain the whole
  answer: what was touched, at what IRQL, read or write,
  and from where.

* ---- THE BUGCHECKS YOU WILL ACTUALLY MEET ----

  0x0A  IRQL_NOT_LESS_OR_EQUAL
        Touched pageable memory, or a bad pointer, at
        DISPATCH_LEVEL or above.
  0xD1  DRIVER_IRQL_NOT_LESS_OR_EQUAL
        The same thing, and it was a driver. THE MOST
        COMMON DRIVER BUGCHECK BY A LARGE MARGIN.
        Cause: paged memory accessed at raised IRQL, or a
        freed pointer.
  0x1E  KMODE_EXCEPTION_NOT_HANDLED
  0x50  PAGE_FAULT_IN_NONPAGED_AREA
        Freed memory, or a wild pointer.
  0x7E  SYSTEM_THREAD_EXCEPTION_NOT_HANDLED
  0x9F  DRIVER_POWER_STATE_FAILURE
        A driver did not complete a power IRP. Arg1 = 3
        means a device object blocked the transition.
  0xC4  DRIVER_VERIFIER_DETECTED_VIOLATION
        Driver Verifier caught you. The subcode says
        exactly what.
  0xC9  DRIVER_VERIFIER_IOMANAGER_VIOLATION
  0xC5  DRIVER_CORRUPTED_EXPOOL
        Pool corruption - you wrote past an allocation.
  0x139 KERNEL_SECURITY_CHECK_FAILURE
        A stack cookie or list-entry corruption check.
  0x133 DPC_WATCHDOG_VIOLATION
        A DPC ran too long, or IRQL stayed high. Usually a
        loop that should have been in a work item.

* ---- THE IRQL RULE THAT CAUSES MOST OF THESE ----
    PASSIVE_LEVEL (0)   may touch paged memory, may block
    APC_LEVEL (1)
    DISPATCH_LEVEL (2)  NO PAGED MEMORY. NO BLOCKING. NO
                        WAITING.
    DIRQL (3+)          device interrupt level

    At DISPATCH_LEVEL or above, touching pageable memory
    faults, and a page fault cannot be serviced because
    the page-fault handler needs to wait. THAT IS BUGCHECK
    0xD1, and it is why the rule exists.

    !irql               * check where you are
    KeGetCurrentIrql()  * from code

* ---- A HANG RATHER THAN A CRASH ----
    !analyze -v -hang
    !process 0 7        * every thread stack
    !locks              * held resources and waiters
    !stacks 2           * all kernel stacks, filtered
    Look for a cycle: A waits on a lock held by B, which
    waits on a lock held by A.
Driver Verifier is not optional 
verifier /standard /driver mydrv.sys
shutdown /r /t 0

It injects allocation failures, checks IRQL rules,
detects pool corruption immediately rather than
later, catches leaked resources at unload, and forces
DMA and IRP misuse to fail loudly at the point of the
mistake.

verifier /flags 0x209BB /driver mydrv.sys   (more)
verifier /volatile /flags 0x8 /adddriver mydrv.sys
verifier /querysettings
verifier /reset                             (turn off)

It will crash your driver on bugs that would otherwise corrupt memory silently and fail a week later in someone else's code. Run every driver under Verifier before shipping it — and expect the first run to find something.

The rest of the toolkit

REM ---- SYSINTERNALS: download the whole suite ----
Process Explorer   handles, DLLs, threads, stacks. The
                   better Task Manager.
Process Monitor    EVERY file, registry, network and
                   process event, with a stack for each.
                   THE FIRST TOOL for "why can't it find
                   this file" and "why is this failing with
                   access denied".
                   FILTER HARD or you will drown - by
                   process name first.
WinObj             the kernel object namespace: device
                   objects, symbolic links, sections
DebugView          captures DbgPrint output from user AND
                   kernel mode, without a debugger
                   attached. Enable kernel capture in the
                   menu.
Autoruns           what starts, and from where
RAMMap / VMMap     physical and virtual memory breakdown
Handle             which process has that file open
LiveKD             kernel debugging on a LIVE system with
                   no second machine - read-only, but
                   frequently enough

REM ---- ETW: the platform's tracing infrastructure ----
wpr -start GeneralProfile -filemode
REM ... reproduce ...
wpr -stop trace.etl
wpa trace.etl                REM Windows Performance
                             REM Analyzer

logman query providers       REM everything that can be
                             REM traced
tracelog -start mytrace -guid #GUID -f out.etl -flag 0xff
tracefmt out.etl -o out.txt  REM decode WPP (chapter 02)

REM ETW IS THE SAME IDEA AS ftrace/eBPF: always compiled
REM in, negligible when off, enabled at runtime. It covers
REM the kernel, drivers, .NET and applications in ONE
REM correlated timeline, which is genuinely better than
REM anything on Linux for whole-system analysis.

REM ---- DEVICE AND DRIVER STATE ----
pnputil /enum-devices /connected
pnputil /enum-drivers
devcon status *              REM from the WDK
devmgmt.msc                  REM and turn on
                             REM View -> Devices by
                             REM connection

REM ---- INSTALLATION FAILURES ----
REM C:\Windows\INF\setupapi.dev.log
REM IT LOGS EXACTLY WHY AN INSTALL FAILED - signature,
REM ranking, a missing file, a hardware ID mismatch. Search
REM it before guessing.

REM ---- DRIVER TESTING ----
REM HLK (Hardware Lab Kit) - required for WHQL
REM certification
REM Static Driver Verifier, at build time:
msbuild /p:RunCodeAnalysis=true
REM SDV does formal verification of DDI usage rules and
REM finds real bugs on paths your tests never reach.
REM Code Analysis with driver-specific rules:
REM   /analyze plus the WDK ruleset

REM ---- USER-MODE CRASHES ----
REM Configure Windows Error Reporting local dumps:
REM HKLM\SOFTWARE\Microsoft\Windows\
REM   Windows Error Reporting\LocalDumps
REM     DumpFolder  = C:\dumps
REM     DumpType    = 2   (full)
windbg -z C:\dumps\myapp.exe.1234.dmp
!analyze -v

How it shows up

SymptomCause
Stacks are all hex addressesSymbols not configured — set _NT_SYMBOL_PATH, run !sym noisy
Bugcheck 0xD1Paged memory or a bad pointer at raised IRQL
Bugcheck 0x133A DPC ran too long — move the work to a work item
Bugcheck 0xC4Driver Verifier caught a rule violation — read the subcode
Bugcheck 0x9FA power IRP was never completed
Pool corruption reported far from the causeRun under Verifier — it catches it at the point of the write
Driver will not load, no errorsetupapi.dev.log has the reason; check test signing
Breakpoint on DriverEntry never hitsUse bu, not bp — the module is not loaded yet
Cannot find why a file open failsProcess Monitor, filtered by process name
System hangs, no crash!process 0 7 and !locks — look for a wait cycle
KMDF request handled by the wrong queue!wdflogdump and !wdfqueue
Leak with no obvious owner!poolused 2 — needs unique pool tags

Check yourself

  • Configure a symbol path and explain why it must come first.
  • Set up kernel debugging over the network, including the key.
  • Name the three commands you run first on any crash dump.
  • Use dt to dump a typed structure, recursively.
  • Explain what !drvobj, !devstack and !irp each tell you.
  • Say why !wdflogdump comes first for a KMDF driver.
  • Read the four arguments of a 0xD1 bugcheck.
  • State the IRQL rule and explain why violating it causes 0xD1.
  • Explain the difference between bp and bu.
  • Say what Driver Verifier injects and checks, and why you run it before shipping.
  • Describe what ETW has in common with ftrace and WPP.
  • Say where to look when a driver installation fails.
