Interprocess communication

Isolation is the point of a process, so any communication must be arranged deliberately through the kernel. The mechanisms differ in throughput, latency, direction, naming and what they can carry — and choosing wrongly is the difference between microseconds and milliseconds.

The choices that matter

There are a dozen ways for two processes to talk, and choosing between them is easier once you see that they differ along only a few axes. Fix those and the right mechanism usually names itself.

QuestionOptionsConsequence
Data or control?Bulk bytes vs a signal or eventShared memory vs eventfd
How much data?Bytes vs megabytesCopy cost decides everything
Same machine?Local vs networkUnix sockets vs TCP
Related processes?Parent/child vs unrelatedAnonymous pipe vs a named object
Message or stream?Preserved boundaries vs a byte streamDatagram vs stream socket
One-to-one or many?Point-to-point vs multicastPipe vs pub/sub
Synchronisation included?Blocking built in, or your problemPipes block; shared memory does not
 
Rough cost, same machine, small messages:

  shared memory + atomics    ~20-100 ns     no syscall in steady state
  futex wake                 ~1-5 µs        only when actually blocking
  pipe / socketpair          ~5-15 µs       two copies + two switches
  Unix domain socket         ~5-20 µs
  POSIX message queue        ~5-20 µs
  D-Bus / Binder             ~50-200 µs     plus marshalling
  loopback TCP               ~20-50 µs      full protocol stack

The pattern: anything that copies through the kernel costs
microseconds. Shared memory costs nanoseconds but hands you the
entire synchronisation problem in exchange.

Pipes

The simplest IPC in Unix, and the one the shell uses for every pipeline. Its behaviour at the edges — a full buffer, a closed reader — is what determines how programs using it actually terminate.

int fd[2];
pipe(fd);                       /* fd[0] read end, fd[1] write end */

if (fork() == 0) {
        close(fd[0]);                    /* child writes           */
        dup2(fd[1], STDOUT_FILENO);      /* stdout → pipe          */
        close(fd[1]);
        execlp("ls", "ls", NULL);
}
close(fd[1]);                            /* parent MUST close its
                                            write end, or it never
                                            sees EOF                */
char buf[4096];
ssize_t n;
while ((n = read(fd[0], buf, sizeof buf)) > 0)
        process(buf, n);
/* read returns 0 (EOF) only when ALL write ends are closed */
PropertyBehaviour
DirectionUnidirectional. Two pipes for bidirectional, or use socketpair().
NamingAnonymous — inherited across fork. mkfifo() gives a named pipe for unrelated processes.
BoundariesA byte stream. Two writes may be read as one. Frame it yourself.
Capacity64 KB by default (F_SETPIPE_SZ to change). Writer blocks when full; reader blocks when empty.
AtomicityWrites up to PIPE_BUF (4096) are atomic — they will not interleave with other writers.
Closed readerWriting gives SIGPIPE, which kills the process by default. Almost always you want signal(SIGPIPE, SIG_IGN) and to handle EPIPE.
The two pipe bugs everyone writes

Forgetting to close unused ends. If the parent keeps its copy of the write end open, the reader never sees EOF and hangs forever. Every process must close every descriptor it does not use.

Assuming message boundaries. A pipe is a byte stream. If you write() two 100-byte messages, the reader may get 200 bytes in one read(), or 37 then 163. Prefix each message with a length, or use a datagram mechanism.

Sockets

Sockets work between machines and, in their local form, between processes on one machine. That uniformity is why a program written for one frequently works for the other unchanged.

/* Unix domain sockets: the default choice for local IPC.
   Same API as network sockets, but no protocol stack overhead. */

int sv[2];
socketpair(AF_UNIX, SOCK_STREAM, 0, sv);   /* bidirectional pipe */

/* Named, for unrelated processes */
int s = socket(AF_UNIX, SOCK_STREAM, 0);
struct sockaddr_un a = { .sun_family = AF_UNIX };
strcpy(a.sun_path, "/run/myservice.sock");
bind(s, (struct sockaddr *)&a, sizeof a);
listen(s, 16);
int c = accept(s, NULL, NULL);

/* SOCK_DGRAM preserves message boundaries;
   SOCK_SEQPACKET gives boundaries AND reliable ordering.     */
/* The killer feature: passing FILE DESCRIPTORS between processes.
   No other local IPC mechanism can do this.                    */

struct msghdr msg = {0};
char cmsgbuf[CMSG_SPACE(sizeof(int))];
msg.msg_control = cmsgbuf;
msg.msg_controllen = sizeof cmsgbuf;

struct cmsghdr *cm = CMSG_FIRSTHDR(&msg);
cm->cmsg_level = SOL_SOCKET;
cm->cmsg_type  = SCM_RIGHTS;              /* "here is an fd"      */
cm->cmsg_len   = CMSG_LEN(sizeof(int));
memcpy(CMSG_DATA(cm), &fd_to_send, sizeof(int));

sendmsg(sock, &msg, 0);

/* The receiver gets a NEW descriptor in its own table, referring
   to the same open file. This is how systemd socket activation,
   privilege separation, Wayland buffer passing and container
   runtimes all work — a privileged process opens the resource
   and hands the descriptor to an unprivileged one.
   SCM_CREDENTIALS similarly passes verified pid/uid/gid.      */

Shared memory

The fastest IPC is no copying at all: two processes mapping the same physical memory. It is also the only mechanism with no built-in synchronisation, which you must therefore supply yourself.

/* POSIX shared memory — the fastest mechanism, and the one with
   no synchronisation included.                                */

int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0600);
ftruncate(fd, SIZE);
void *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
close(fd);                     /* the mapping keeps it alive     */
/* ... both processes now see the same physical pages ...        */
munmap(p, SIZE);
shm_unlink("/myshm");          /* remove the name                */

/* Anonymous shared memory, for related processes: */
void *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE,
               MAP_SHARED | MAP_ANONYMOUS, -1, 0);
fork();                        /* both see the same pages        */

/* memfd_create: an anonymous, sealable region you can pass by fd */
int fd = memfd_create("buf", MFD_ALLOW_SEALING);
fcntl(fd, F_ADD_SEALS, F_SEAL_SHRINK | F_SEAL_GROW);
/* Sealing lets the receiver TRUST that the sender cannot shrink
   the region underneath it — otherwise a malicious sender causes
   SIGBUS in the receiver. This is what Android and Wayland use. */
Shared memory gives you no synchronisation whatsoever

You get raw memory shared between address spaces. Everything from CA chapter 15 applies in full: you need atomics with correct memory ordering, or a lock placed in the shared region itself. And because the peer may be malicious, you must additionally validate everything you read — a shared-memory protocol is a trust boundary.

/* A lock that lives in the shared region */
pthread_mutexattr_t a;
pthread_mutexattr_init(&a);
pthread_mutexattr_setpshared(&a, PTHREAD_PROCESS_SHARED);   /* essential */
pthread_mutexattr_setrobust(&a, PTHREAD_MUTEX_ROBUST);      /* see below */
pthread_mutex_init(&shared->lock, &a);

/* ROBUST matters: if the peer dies holding the lock, a normal
   mutex is stuck forever. A robust mutex returns EOWNERDEAD to
   the next acquirer, which can repair the state and call
   pthread_mutex_consistent().                                */

Signalling without data

Sometimes you need to signal that something happened without transferring data. Several mechanisms do this, and they differ mostly in whether they compose with a polling loop.

MechanismUseNote
eventfdA counter you can poll()The standard way to wake an event loop from another thread or process
signalfdSignals as a readable fdRemoves async-signal-safety from the problem entirely
timerfdTimers as a readable fdIntegrates cleanly with epoll
futexFast userspace mutexThe primitive under every Linux lock — see below
POSIX semaphoressem_open, sem_waitNamed or in shared memory
Signalskill(pid, SIGUSR1)No payload, can be coalesced, async-safety restrictions
 
The futex, which is worth understanding once

  A mutex that never contends should cost ZERO syscalls. A mutex
  that does contend must eventually sleep, which requires the kernel.
  futex gives you both:

    lock:   atomic compare-and-swap in USER SPACE
            uncontended → done, ~20 ns, no syscall
            contended   → futex(FUTEX_WAIT) → kernel puts you to sleep

    unlock: atomic store in user space
            if waiters were recorded → futex(FUTEX_WAKE)

  The kernel is involved ONLY on contention. This is why an
  uncontended pthread_mutex_lock is nearly free and a contended
  one costs microseconds — the cliff is exactly one syscall pair.

  Every Linux mutex, condition variable, semaphore and barrier is
  built on this.

System V IPC

The older System V facilities predate most of the above, persist beyond process lifetime, and are generally worth avoiding — but you will meet them in existing code and need to recognise them.

/* The 1983 API: message queues, semaphores and shared memory,
   named by integer keys.                                     */
key_t key = ftok("/some/path", 'A');
int shmid = shmget(key, SIZE, IPC_CREAT | 0600);
void *p = shmat(shmid, NULL, 0);

/* Avoid in new code:
     · a global integer namespace with collisions and no cleanup
     · objects PERSIST after all processes exit (ipcs / ipcrm)
     · not pollable — cannot be used with epoll
     · clumsier API

   POSIX equivalents (shm_open, mq_open, sem_open) are namespaced
   under a filesystem path, follow fd semantics, and are pollable.
   Use those.                                                  */

ipcs -a          # list leftover System V objects
ipcrm -m ID      # clean them up manually

The recurring design

Notice that io_uring, virtio, Binder and every high-performance IPC converge on the same structure: a shared-memory ring buffer with atomic head and tail indices, plus a doorbell (an eventfd, an MMIO write, a futex) used only when the peer needs waking. Bulk data by shared memory; wake-ups by syscall, as rarely as possible. Once you recognise this shape you will see it everywhere in systems design.

Choosing

With the mechanisms covered, this is the decision reduced to a short procedure — because the common cases have a clear best answer rather than a trade-off.

  Need to wake an event loop?              eventfd
  Parent/child, one direction, a stream?   pipe
  Bidirectional, local, need fd passing?   Unix socket (socketpair)
  Message boundaries matter?               SOCK_SEQPACKET or datagram
  Megabytes of data?                       shared memory + a ring
  Across machines?                         TCP, or a real RPC framework
  Unrelated processes, need naming?        named socket or shm_open
  Structured API with versioning?          D-Bus, gRPC
  Absolute lowest latency?                 shared memory + busy poll

Default answer for local IPC on Linux: a Unix domain socket. It is
bidirectional, ordered, has a sane API, passes credentials and file
descriptors, works with epoll, and cleans up when the process dies.
Reach for shared memory only when you have measured that it matters.

Debugging IPC

When IPC stops working the question is usually which side is blocked and why. These tools answer that directly rather than by inference.

# what is open, and connected to what
lsof -p PID
ls -l /proc/PID/fd/
ss -xp                          # Unix sockets and their peers
lsof -U

# System V leftovers
ipcs -a

# shared mappings
cat /proc/PID/maps | grep -E 'shm|SYSV|memfd'
cat /proc/PID/smaps             # Shared_Clean / Shared_Dirty per mapping

# trace the traffic
strace -e trace=read,write,sendmsg,recvmsg -p PID
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_futex { @[comm] = count(); }'

# a hang: where is each side blocked?
cat /proc/PID/stack
cat /proc/PID/wchan
gdb -p PID -batch -ex 'thread apply all bt'
