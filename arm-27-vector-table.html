Exception types and the vector table

Sixteen entries of 128 bytes each, indexed by where the exception came from and what kind it was. The layout looks arbitrary until you see what it is optimising for — and then it explains why kernel entry code is structured the way it is.

What counts as an exception

"Exception" in ARM terminology covers far more than errors: system calls, interrupts, faults and debug events are all exceptions, and they are all delivered by the same mechanism.

ARM uses "exception" as the umbrella term for anything that
diverts execution to a handler. Two families:

  SYNCHRONOUS — caused by the current instruction, reported
                PRECISELY. You know exactly which instruction.

     SVC / HVC / SMC        deliberate calls to EL1 / EL2 / EL3
     Data abort             a load or store failed translation
                            or permission checks
     Instruction abort      the FETCH itself failed
     Undefined instruction  bad encoding, or disabled at this EL
     Alignment fault        unaligned Device access, or SCTLR.A
     Trapped register access a higher EL configured a trap
     PC alignment fault     the PC was not 4-byte aligned
     SP alignment fault     SP was not 16-byte aligned
     Breakpoint / watchpoint / software step

  ASYNCHRONOUS — caused by something outside the instruction
                 stream, taken BETWEEN instructions.

     IRQ      normal interrupt.  Masked by PSTATE.I
     FIQ      fast interrupt.    Masked by PSTATE.F
     SError   System Error — typically an IMPRECISE external
              abort: an ECC failure, or a bus error from a write
              posted long ago. Masked by PSTATE.A.

  SError is the awkward one: the reported PC has NOTHING to do
  with the cause, because the failing transaction retired long
  before the error came back (chapter 25).

The vector table

The table is not a simple list. It is organised by where the exception came from and what state that code was in, which is why it has sixteen entries rather than four.

VBAR_ELx holds the base address. 16 entries, 128 bytes each,
2 KB total.

VBAR + offset    source of the exception              type

  0x000   Synchronous  ┐
  0x080   IRQ / vIRQ   │  CURRENT EL, using SP_EL0
  0x100   FIQ / vFIQ   │  (SPSel = 0, "EL1t")
  0x180   SError       ┘

  0x200   Synchronous  ┐
  0x280   IRQ / vIRQ   │  CURRENT EL, using SP_ELx
  0x300   FIQ / vFIQ   │  (SPSel = 1, "EL1h")   ← the normal
  0x380   SError       ┘                          kernel case

  0x400   Synchronous  ┐
  0x480   IRQ / vIRQ   │  LOWER EL, AArch64
  0x500   FIQ / vFIQ   │  ← syscalls and user faults land here
  0x580   SError       ┘

  0x600   Synchronous  ┐
  0x680   IRQ / vIRQ   │  LOWER EL, AArch32
  0x700   FIQ / vFIQ   │  (32-bit compatibility)
  0x780   SError       ┘
Why split by source

The handler needs to know immediately whether it must switch stacks and save user state, or whether this is a nested exception already on the kernel stack. Encoding that in the vector address means the answer costs zero instructions — no test, no branch, no register read. On a path taken millions of times a second, that matters.

The AArch32 split exists for the same reason: a 32-bit process's register layout differs, so it needs a different save path.

Each entry is code, not an address

This is the detail that surprises people coming from other architectures: an entry is not a pointer to a handler, it is the handler's first instructions, sitting directly in the table.

/* Unlike Cortex-M, where the vector table holds ADDRESSES, on
   A-profile each entry is 128 bytes of actual CODE — 32
   instructions. You either handle it there or branch out.  */

.macro VECTOR_ENTRY label
        .align 7                        /* 128 bytes = 2^7 */
        b       \label
.endm

        .align 11                       /* the table must be 2 KB
                                           aligned */
        .global vector_table
vector_table:
        /* current EL, SP_EL0 — should never happen in a normal
           kernel, so these are error handlers */
        VECTOR_ENTRY  invalid_sync_el1t
        VECTOR_ENTRY  invalid_irq_el1t
        VECTOR_ENTRY  invalid_fiq_el1t
        VECTOR_ENTRY  invalid_err_el1t

        /* current EL, SP_ELx — kernel-mode exceptions */
        VECTOR_ENTRY  el1_sync
        VECTOR_ENTRY  el1_irq
        VECTOR_ENTRY  el1_fiq
        VECTOR_ENTRY  el1_error

        /* lower EL, AArch64 — user-mode exceptions and syscalls */
        VECTOR_ENTRY  el0_sync
        VECTOR_ENTRY  el0_irq
        VECTOR_ENTRY  el0_fiq
        VECTOR_ENTRY  el0_error

        /* lower EL, AArch32 */
        VECTOR_ENTRY  el0_sync_compat
        VECTOR_ENTRY  el0_irq_compat
        VECTOR_ENTRY  el0_fiq_compat
        VECTOR_ENTRY  el0_error_compat

/* Installing it: */
        adr     x0, vector_table
        msr     vbar_el1, x0
        isb                             /* REQUIRED — chapter 06 */
Alignment is not advisory

VBAR_ELx requires 2 KB alignment — the low 11 bits are RES0 and writing a misaligned address silently ignores them. Each entry must be exactly 128 bytes apart. Get either wrong and exceptions dispatch to the wrong handler, or into the middle of an instruction.

The symptom is spectacular and unhelpful: the machine takes an exception and immediately takes another, usually ending in an unrecoverable loop before anything can be printed. Use .align 11 for the table and .align 7 per entry, and verify with readelf -s | grep vector.

Why 128 bytes matters

Each entry gets exactly 128 bytes, which is enough for a handful of instructions and no more. That constraint shapes how every real entry stub is written.

/* 32 instructions is enough to do real work before branching,
   which several important techniques exploit:               */

/* 1. Linux's KPTI trampoline. When kernel page-table isolation
      is active, the entry code must switch TTBR1 before it can
      touch kernel memory — and that switch has to happen in the
      vector itself, using only registers.                   */

/* 2. Spectre-BHB mitigations. Some cores need a loop of branches
      or a specific instruction sequence at the very start of the
      vector to flush the branch history buffer before any
      speculation on kernel addresses can occur. Linux patches
      the vectors at boot to insert exactly the sequence that
      core requires.                                          */

/* 3. Fast paths. A hypervisor can handle a trivial trap
      entirely within the vector entry and ERET without ever
      building a full context save.                          */

/* Which is why Linux's vectors are generated by a macro with
   several variants, and why `objdump -d` of the vector region
   shows more than a single branch on modern kernels.       */

Virtual interrupts

A hypervisor needs to deliver interrupts to a guest without the real interrupt controller being involved. Virtual interrupts are that mechanism, and they appear to the guest exactly like real ones.

/* When HCR_EL2.{IMO,FMO,AMO} are set, physical IRQ/FIQ/SError go
   to EL2, and the entries at EL1 receive VIRTUAL interrupts
   instead — injected by the hypervisor through the GIC list
   registers (chapter 23).                                   */

   HCR_EL2.IMO = 1   physical IRQ    → EL2
                     virtual vIRQ    → EL1
   HCR_EL2.VI  = 1   assert a virtual IRQ to the guest

/* From the guest's point of view nothing is different: it takes
   an exception at VBAR_EL1 + 0x480 exactly as it would on bare
   metal. It cannot tell the interrupt was injected.

   This is what makes guest interrupt handling fast: no
   hypervisor trap is needed for the guest to acknowledge and
   EOI, because the GIC's virtual CPU interface handles it.  */

What hardware does on entry

Taking an exception changes processor state automatically, before any of your code runs. Knowing exactly what the hardware did is essential, because your stub must not repeat it and must eventually undo it.

Before your first instruction runs, the hardware has ALREADY:

   1. ELR_ELx   ← the address to return to
   2. SPSR_ELx  ← the entire PSTATE at the moment of the exception
   3. ESR_ELx   ← the syndrome: exception class and details
   4. FAR_ELx   ← the faulting address (aborts and watchpoints)
   5. PSTATE    → EL raised, SPSel = 1, and D, A, I, F ALL MASKED
   6. PC        ← VBAR_ELx + the vector offset

  Step 5's masking is not optional and not configurable. The
  reason: ELR_ELx and SPSR_ELx are single registers, not a stack.
  A second exception before your handler saved them would
  overwrite the return address, and you could never get back.

  Your handler saves them to the kernel stack FIRST, and only
  then may unmask to allow nesting. Chapter 28 covers the full
  sequence.

  Note what is NOT saved: X0-X30. Nothing is banked in AArch64
  (chapter 04). Software saves everything.

The "impossible" entries

Several table entries correspond to situations that should never occur in a correctly configured system. Filling them with something that reports loudly rather than falling through is what turns a mysterious hang into a diagnosable fault.

/* The four "current EL with SP_EL0" entries should never be taken
   in a correctly configured kernel, which runs with SPSel = 1.
   Reaching one means something is badly wrong — and that is
   exactly why they are worth implementing properly.        */

invalid_sync_el1t:
        /* We cannot trust SP. Switch to a known-good emergency
           stack before doing anything.                       */
        adr_this_cpu x0, emergency_stack, x1
        mov     sp, x0
        bl      panic_bad_mode

/* Common causes of landing here:
     · SPSel accidentally cleared
     · a corrupted SP that faulted during the save sequence
     · a fault in early boot before SP_EL1 was established
     · stack overflow — the guard page faulted, and the fault
       handler could not push a frame

   Linux handles the stack-overflow case specially with an
   OVERFLOW STACK per CPU, so a kernel stack overflow produces a
   readable oops instead of an infinite fault loop. That is worth
   copying in any serious bare-metal system.               */

The M-profile design costs a fixed ~12 cycles of hardware stacking on every interrupt but removes the software prologue entirely, which is why M-profile interrupt latency is both lower and far more deterministic. A-profile trades that for flexibility and for not paying the cost on exceptions that do not need it.

Inspecting the vectors

The vector base address is a register, so you can always find the active table and check that it is the one you think it is — a useful sanity check during bring-up.

# where is the table?
sudo cat /proc/kallsyms | grep vectors
#   ffff800008011000 T vectors

# in gdb on a kernel or bare-metal target
p/x $VBAR_EL1
x/16i $VBAR_EL1              # the first entry
x/4i  $VBAR_EL1 + 0x400      # lower EL, synchronous — the syscall path

# check alignment
readelf -s vmlinux | grep -w vectors
#   the address must end in 0x?800 or 0x?000 — 2 KB aligned

# see what Linux patched in
sudo objdump -d --start-address=0x... vmlinux | head -60
#   on a mitigated kernel you will see BHB-flush sequences
#   before the branch
Debugging a machine that resets immediately

A misaligned or uninstalled vector table produces a system that appears to die instantly with no output. The diagnostic sequence: halt with JTAG at reset, single-step to the point where VBAR is written, read it back, and confirm the low 11 bits are zero. Then set a hardware breakpoint on VBAR + 0x200 and VBAR + 0x400 — whichever is hit first tells you whether the fault came from kernel or user context, which usually identifies the bug immediately.
