Physical memory management and allocators

Before virtual memory can hand out address spaces, something must track which physical pages are free. This chapter covers that layer — the page allocator, the object allocators built on it, and fragmentation, which is the problem all of them exist to fight.

The allocator stack

Memory management is several allocators stacked on one another, each solving a problem the layer beneath cannot. Seeing them as a stack is what makes the individual pieces make sense.

   kmalloc(64)                    application malloc(64)
        │                                  │
        ▼                                  ▼
   ┌─────────────────┐             ┌──────────────────┐
   │  SLAB / SLUB    │             │  libc allocator   │
   │  object caches  │             │  (ptmalloc, etc.) │
   │  bytes → objects│             │  bins, arenas     │
   └────────┬────────┘             └─────────┬────────┘
            │                                 │ brk / mmap
            ▼                                 ▼
   ┌──────────────────────────────────────────────────┐
   │  BUDDY ALLOCATOR — the page allocator             │
   │  hands out 2^order contiguous pages               │
   └────────────────────┬─────────────────────────────┘
                        ▼
   ┌──────────────────────────────────────────────────┐
   │  memblock / early allocator (boot only)           │
   │  physical memory map from firmware / device tree  │
   └──────────────────────────────────────────────────┘

Each layer solves the layer above's granularity problem: the buddy
allocator deals in pages, but most allocations are tens of bytes.

The buddy allocator

The foundation allocator hands out power-of-two runs of pages, splitting and merging as needed. Its behaviour — especially how it fragments — leaks upward into everything built on it.

Free lists, one per ORDER, where order n means 2^n contiguous pages.

  order 0:  4 KB      order 3:  32 KB     order 6:  256 KB
  order 1:  8 KB      order 4:  64 KB     order 7:  512 KB
  order 2: 16 KB      order 5: 128 KB     ... up to order 10 (4 MB)

ALLOCATION of order 2, when only an order-4 block is free:

   order 4:  [================ 64 KB ================]
                       split
   order 3:  [====== 32 KB ======][====== 32 KB ======]
                  split                  ↑ freed to order-3 list
   order 2:  [= 16 =][= 16 =]
              return   ↑ freed to order-2 list

FREEING: when a block is released, check whether its BUDDY — the
adjacent block of the same size, found by flipping one address bit —
is also free. If so, merge them and repeat upward.

   buddy_address = block_address XOR (block_size)

That single XOR is why the scheme is fast: finding the buddy is one
arithmetic operation, not a search.

  + coalescing is automatic and cheap
  + finding a block is O(1) amortised
  - INTERNAL fragmentation: a 5-page request takes an order-3
    block (8 pages), wasting 3
  - EXTERNAL fragmentation: many scattered order-0 blocks cannot
    satisfy an order-5 request even with plenty free
# see it live
cat /proc/buddyinfo
# Node 0, zone   Normal   1024   512   256   64   16   4   1   0   0   0   0
#                         ^order0 ^1    ^2   ...                    ^order10
# Lots of low-order blocks and zeros at high orders means the memory
# is FRAGMENTED: plenty free, but no large contiguous runs.

cat /proc/pagetypeinfo     # per migrate-type breakdown
cat /proc/zoneinfo         # free pages, watermarks, per zone

Zones and NUMA nodes

Not all physical memory is equivalent. Some can be reached by every device, some cannot, and on larger machines some is closer to one processor than another — so the allocator must know which is which.

ZONE_NORMALThe restGeneral use

   a device needing DMA32 memory cannot use pages above 4 GB.
   This is exactly what dma_set_mask() communicates.          */

/* NUMA: on multi-socket systems, memory attached to another
   socket costs 1.5-2x the latency. The allocator prefers the
   local node.                                                */

Slab allocators

Most kernel allocations are small and short-lived, which the page allocator handles badly. A layer above it keeps caches of same-sized objects, which is both faster and far less wasteful.

The problem: kmalloc(64) from a 4 KB page allocator wastes 98%.
Plus, initialising a complex object is expensive if repeated.

The slab idea (Bonwick, 1994):
  · allocate a PAGE (or several), carve it into equal-size objects
  · keep a free list threaded through the unused objects
  · allocation = pop the list; free = push it. O(1), no search.
  · objects of one TYPE share a cache, so they stay hot in CPU cache

   ┌──────────── one slab (4 KB page) ────────────┐
   │ obj0 │ obj1 │ obj2 │ obj3 │ ... │ objN │ meta │
   └──┬────────────┬───────────────────────────────┘
      └── free ────┘  a singly-linked list through free objects

Linux has had three implementations:
  SLAB   original; per-CPU and per-node queues, complex
  SLUB   the current default; simpler, better multicore scaling,
         less metadata, better debugging
  SLOB   tiny, for very small systems (removed in 6.4)
/* generic sizes — kmalloc uses power-of-two caches */
void *p = kmalloc(100, GFP_KERNEL);      /* comes from kmalloc-128,
                                            so 28 bytes are wasted */

/* a dedicated cache, when you allocate one type constantly */
static struct kmem_cache *my_cache;

my_cache = kmem_cache_create("my_objects",
                             sizeof(struct my_object),
                             0,                     /* alignment  */
                             SLAB_HWCACHE_ALIGN,    /* flags      */
                             NULL);                 /* constructor */

struct my_object *o = kmem_cache_alloc(my_cache, GFP_KERNEL);
kmem_cache_free(my_cache, o);
kmem_cache_destroy(my_cache);

/* Benefits over kmalloc: exact sizing (no power-of-two waste),
   a named entry in /proc/slabinfo for leak hunting, per-type
   locality, and optional constructors.                       */
# which caches are consuming memory?
sudo slabtop -s c              # sorted by cache size
cat /proc/slabinfo

# a steadily growing cache with no corresponding workload growth
# is a kernel memory leak, and slabtop names the object type —
# which usually identifies the subsystem immediately.

Fragmentation

Memory can be plentiful and still unusable, if what is free is scattered. There are two distinct kinds of this problem with two distinct remedies, and conflating them leads to the wrong fix.

KindMeaningMitigation
InternalAllocated more than requested; the remainder is unusableSize-class tuning, dedicated slab caches
ExternalEnough total free memory, but not contiguousCompaction, migration, avoiding large allocations
 
External fragmentation, made concrete

   memory:  [used][free][used][free][used][free][used][free]
              4KB   4KB   4KB   4KB   4KB   4KB   4KB   4KB

   16 KB free in total. An order-2 (16 KB contiguous) request FAILS.

Linux's defences:

  MIGRATE TYPES     group pages by movability, so unmovable kernel
                    allocations do not scatter through regions that
                    would otherwise be compactable
                      MIGRATE_UNMOVABLE   kernel data, page tables
                      MIGRATE_MOVABLE     user pages, page cache
                      MIGRATE_RECLAIMABLE caches that can be dropped

  COMPACTION        physically MOVE movable pages to create
                    contiguous free runs, updating page tables and
                    reverse mappings as it goes
                      echo 1 > /proc/sys/vm/compact_memory

  CMA               reserve a region at boot that is normally used
                    for movable pages but can be reclaimed on demand
                    for large contiguous DMA buffers — cameras,
                    video codecs, GPUs

  This is why kmalloc of large sizes can fail on a long-running
  system, and why kvmalloc() exists: try kmalloc (contiguous),
  fall back to vmalloc (virtually contiguous only).           */

vmalloc versus kmalloc

When a large allocation does not need to be physically contiguous, the kernel can stitch scattered pages into one contiguous virtual range — with consequences for anything that then wants a physical address.

kmallocvmalloc
Physically contiguousYesNo
Virtually contiguousYesYes
Usable for DMAYesNo
Max practical sizeA few MB, and fails under fragmentationLarge — limited by the vmalloc area
CostFastSlower: page table setup, TLB pressure
Can sleepDepends on GFP flagAlways — never in atomic context
 
void *p = kvmalloc(size, GFP_KERNEL);   /* try kmalloc, fall back
                                           to vmalloc              */
kvfree(p);
/* Use this whenever the buffer is large and does NOT need to be
   physically contiguous. It is the right default for most
   variable-size kernel allocations.                          */

Reclaim and the OOM killer

When memory runs short the kernel does not simply fail. It works progressively harder to free some, and knowing that sequence explains both the latency spikes and the eventual killing of a process.

Watermarks per zone drive reclaim:

   free pages
      │
   HIGH  ──────  above this: no reclaim needed
      │
   LOW   ──────  kswapd wakes and reclaims in the BACKGROUND
      │
   MIN   ──────  allocators reclaim SYNCHRONOUSLY (direct reclaim)
      │          — the allocating task now pays the cost, and
      │            latency spikes
      0          allocation fails → OOM killer

What gets reclaimed, cheapest first:
  1. clean page cache          just drop it, it is on disk
  2. clean anonymous pages     only if swap exists
  3. dirty page cache          must write back first
  4. dirty anonymous pages     swap out
  5. slab caches               shrinkers: dentry, inode, fs caches

  echo 3 > /proc/sys/vm/drop_caches     # drop clean caches (testing)
  vm.swappiness                          # anon vs file cache bias
  vm.min_free_kbytes                     # raise for network/RT work
                                         # to avoid direct reclaim
# when reclaim fails: the OOM killer picks a victim by oom_score
cat /proc/PID/oom_score
echo -1000 > /proc/PID/oom_score_adj    # never kill this process
dmesg | grep -A20 'Out of memory'

# In containers, the cgroup limit triggers a per-cgroup OOM long
# before the machine is out of memory:
cat /sys/fs/cgroup/.../memory.max
cat /sys/fs/cgroup/.../memory.events    # oom_kill counter
Reading "free" correctly 
free -h
#               total   used   free   shared  buff/cache  available
# Mem:            16G    4G     1G      200M        11G         11G
#                              ^^^      low, and PERFECTLY NORMAL
#                                                              ^^^
#                                              THIS is what matters

/* "free" memory is wasted memory — Linux uses everything spare for
   page cache, which it can drop instantly. Look at AVAILABLE, which
   accounts for reclaimable cache. Alarm on `free` being low is the
   single most common Linux memory misdiagnosis.                */

The user-space side

An application's allocator sits above all of this, and the gap between what it requests and what the kernel provides explains why freeing memory often does not return it to the system.

/* malloc does not call the kernel for every allocation. */

brk / sbrk        grow the heap contiguously. Simple, but memory is
                  only returned to the OS from the TOP — one live
                  allocation at the end pins everything below it.

mmap              anonymous mappings. glibc uses this for requests
                  above MMAP_THRESHOLD (128 KB by default), and
                  returns them to the OS immediately on free.

/* Which explains a common observation: freeing a lot of memory
   sometimes reduces RSS and sometimes does not. Small allocations
   from the brk heap are recycled internally; large mmap'd ones
   go straight back.                                            */

mallopt(M_MMAP_THRESHOLD, 64*1024);
malloc_trim(0);                  /* ask glibc to return free pages */
MALLOC_ARENA_MAX=2 ./program     /* limit per-thread arenas —
                                    often cuts RSS substantially in
                                    highly threaded programs      */

Embedded systems

On a small system without swap, most of the mechanisms above either do not exist or behave very differently — which changes what running out of memory actually looks like.

/* No MMU means no virtual memory, so physical fragmentation is
   permanent and unrecoverable. This is why (C chapter 14):     */

/* Static allocation — the linker proves it fits at BUILD time */
static struct session sessions[MAX_SESSIONS];

/* Fixed-size pools — O(1), no fragmentation, bounded */
static struct msg pool[64];
static uint64_t  used;

/* TLSF (Two-Level Segregated Fit) — a real-time heap with
   BOUNDED worst-case allocation time, unlike a general malloc */

/* FreeRTOS ships five heap implementations, and choosing between
   them is a real design decision:
     heap_1  allocate only, never free — safest
     heap_2  free supported, no coalescing — fragments
     heap_4  coalescing — the usual choice
     heap_5  heap_4 across multiple memory regions            */
