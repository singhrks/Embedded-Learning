Traits and generics

Rust's abstraction mechanism: interfaces that types opt into, and generics constrained by them. Unlike C++ templates, the constraints are checked when the generic is defined, so the errors appear where the mistake is.

Traits

Traits are Rust's answer to interfaces, and the differences from virtual inheritance matter both for what you can express and for what it costs.

    trait Sensor {
        fn read(&mut self) -> u16;              // required

        fn read_averaged(&mut self, n: u8) -> u16 {
            let mut sum = 0u32;                 // a DEFAULT
            for _ in 0..n {                     // method
                sum += self.read() as u32;
            }
            (sum / n as u32) as u16
        }

        const MAX_VALUE: u16 = 4095;            // associated
                                                // constant
        type Unit;                              // associated
                                                // TYPE
    }

    struct Thermistor { channel: u8 }

    impl Sensor for Thermistor {
        type Unit = Celsius;
        fn read(&mut self) -> u16 { adc_read(self.channel) }
        // read_averaged comes free from the default
    }

/* THE COHERENCE (ORPHAN) RULE: you may implement a trait for
   a type only if you own the TRAIT or you own the TYPE. So
   nobody can implement a foreign trait for a foreign type,
   which guarantees exactly one implementation exists
   anywhere in the program.

   THE WORKAROUND when you need to: a newtype (chapter 05).
        struct MyVec(Vec<u8>);
        impl SomeForeignTrait for MyVec { ... }

/* A TRAIT MUST BE IN SCOPE to call its methods: */
    use my_crate::Sensor;       // without this, `.read()` is
                                // "method not found"
/* Which is why the standard library has PRELUDES, and why
   embedded HAL crates tell you to `use embedded_hal::prelude
   ::*`.                                                   */

Generics

Generics are monomorphised, which makes them closer to C++ templates than to Java generics — with the important difference that the constraints are checked when the generic is written rather than when it is used.

    fn largest<T: PartialOrd>(list: &[T]) -> &T {
        let mut max = &list[0];
        for x in list {
            if x > max { max = x; }
        }
        max
    }

/* THE BOUND `T: PartialOrd` IS CHECKED AT DEFINITION. If the
   body used `+` you would get an error HERE, not at some
   distant instantiation - which is the central difference
   from C++ templates (C++ chapter 06), and the reason Rust's
   generic errors are readable.

/* THREE SYNTAXES for the same thing: */
    fn f<T: Display + Clone>(x: T) { }
    fn f<T>(x: T) where T: Display + Clone { }
    fn f(x: impl Display + Clone) { }           // "impl
                                                // Trait" -
                                                // shortest,
                                                // but the
                                                // caller
                                                // cannot
                                                // turbofish it

/* GENERIC STRUCTS AND IMPLS: */
    struct RingBuffer<T, const N: usize> {
        data: [T; N],
        head: usize,
        tail: usize,
    }

    impl<T: Copy + Default, const N: usize> RingBuffer<T, N> {
        pub const fn capacity(&self) -> usize { N }

        pub fn push(&mut self, v: T) -> Result<(), T> {
            let next = (self.head + 1) % N;
            if next == self.tail { return Err(v); }
            self.data[self.head] = v;
            self.head = next;
            Ok(())
        }
    }

    let mut rb: RingBuffer<u8, 64> = RingBuffer::new();

/* CONST GENERICS (`const N: usize`) are the embedded feature:
   a fixed-capacity container with the size in the type, no
   heap, and `% N` folded to an AND when N is a power of two.
   Exactly the C++ template-parameter pattern (C++ ch. 06).

/* MONOMORPHISATION: the compiler generates a separate copy
   for each concrete type used - same as C++ templates, same
   code-size consideration, same zero runtime cost.       */
Constrained generics versus duck-typed templates

A C++ template is checked when instantiated, so an error inside std::sort reports a hundred lines deep. A Rust generic is checked when defined: if the body calls a method the bound does not promise, the error is on that line, in your function. That is why C++20 added concepts (C++ chapter 06) — it is retrofitting the same property.

Static versus dynamic dispatch

The choice between static and dynamic dispatch is the main performance decision in ordinary Rust code, and on embedded targets it is also a code-size decision.

/* --- STATIC: one copy per type, fully inlinable --- */
    fn sample<S: Sensor>(s: &mut S) -> u16 { s.read() }

    sample(&mut thermistor);    // generates sample::<Thermistor>
    sample(&mut photodiode);    // and sample::<Photodiode>

/* -> a direct call, usually inlined to nothing. Zero cost,
   more code.

/* --- DYNAMIC: one copy, a vtable --- */
    fn sample_dyn(s: &mut dyn Sensor) -> u16 { s.read() }

    let sensors: [&mut dyn Sensor; 3] = [&mut a, &mut b,
                                          &mut c];
    for s in sensors { sample_dyn(s); }

/* A `&dyn Trait` is a FAT POINTER - two words: the data
   pointer and a vtable pointer. Note the difference from
   C++ (C++ chapter 11), where the vptr is INSIDE the object:
     · a Rust object has no vtable pointer unless you make a
       trait object of it, so non-polymorphic use costs
       nothing
     · but &dyn T is 16 bytes rather than 8

    assert_eq!(size_of::<&u8>(), 8);
    assert_eq!(size_of::<&dyn Sensor>(), 16);

/* OBJECT SAFETY - a trait can only be a `dyn` object if:
     · no generic methods
     · no methods taking or returning `Self` by value
     · no associated constants (before Rust 1.79)
     · every method is dispatchable
   `Clone` is not object safe, for instance, because clone()
   returns Self.

/* CHOOSING - the same decision as C++ chapter 11:
     the type set is known at compile time  -> GENERICS
     a heterogeneous collection, or a plugin -> dyn
     code size matters more than speed       -> dyn
     it is in a hot path                     -> generics

   ON EMBEDDED, generics dominate: the peripheral set is
   known, and monomorphisation lets the optimiser fold the
   whole driver stack into a few instructions.

/* AND `impl Trait` IN RETURN POSITION, which is static
   dispatch with the type hidden: */
    fn make_sensor() -> impl Sensor { Thermistor::new(0) }
/* One concrete type, chosen by the function, opaque to the
   caller. No allocation, no vtable. For a heterogeneous
   return you need Box<dyn Sensor> instead.             */

/* OPERATOR OVERLOADING is just implementing a trait: */
    use core::ops::{Add, BitOr};

    #[derive(Clone, Copy)]
    struct Flags(u32);

    impl BitOr for Flags {
        type Output = Flags;
        fn bitor(self, rhs: Flags) -> Flags {
                Flags(self.0 | rhs.0) }
    }
    let f = Flags(1) | Flags(2);

/* Deref, and its one legitimate use - smart pointers: */
    impl Deref for MyBox<T> {
        type Target = T;
        fn deref(&self) -> &T { &self.0 }
    }
/* DO NOT use Deref to fake inheritance. It is for types that
   ARE a pointer to something, and abusing it produces
   confusing method resolution.                           */

The embedded-hal traits

The embedded ecosystem is built on a shared set of traits, and understanding them is what makes a driver written for one microcontroller work on another.

/* The embedded ecosystem is built on one set of traits, so a
   driver written once works on every chip (chapter 20).  */

    use embedded_hal::digital::{OutputPin, InputPin};
    use embedded_hal::spi::SpiDevice;
    use embedded_hal::delay::DelayNs;

    pub struct Display<SPI, DC, RST> {
        spi: SPI,
        dc:  DC,
        rst: RST,
    }

    impl<SPI, DC, RST, E> Display<SPI, DC, RST>
    where
        SPI: SpiDevice<Error = E>,
        DC:  OutputPin,
        RST: OutputPin,
    {
        pub fn init(&mut self, delay: &mut impl DelayNs)
                -> Result<(), E>
        {
            self.rst.set_low().ok();
            delay.delay_ms(10);
            self.rst.set_high().ok();
            delay.delay_ms(120);

            self.dc.set_low().ok();             // command mode
            self.spi.write(&[0x11])?;           // sleep out
            Ok(())
        }
    }

/* THIS DRIVER COMPILES FOR EVERY CHIP whose HAL implements
   the traits - STM32, nRF, ESP32, RP2040 - with no
   conditional compilation and no porting layer. That is the
   ecosystem's central achievement, and it has no equivalent
   in the C world, where every vendor HAL has its own
   incompatible API.

   AND IT IS ZERO COST: SPI, DC and RST are concrete types at
   the call site, so every trait call is direct and inlined.
   The generated code is identical to a chip-specific
   driver.                                                */

Patterns worth knowing

A few trait patterns appear often enough in real libraries that not recognising them makes the source unreadable.

/* --- BLANKET IMPLEMENTATIONS --- */
    trait Loggable { fn log(&self); }

    impl<T: Display> Loggable for T {
        fn log(&self) { println!("{self}"); }
    }
/* EVERY type implementing Display now implements Loggable.
   The standard library uses this heavily - `impl<T> Into<U>
   for T where U: From<T>` is why implementing From gives you
   Into.

/* --- MARKER TRAITS: no methods, only a promise --- */
    unsafe trait Zeroable {}            // "all-zero bits is a
                                        // valid value"
    unsafe impl Zeroable for u32 {}
    fn zeroed<T: Zeroable>() -> T { unsafe { core::mem::zeroed() } }
/* `unsafe trait` means implementing it is a promise the
   compiler cannot check - which is how Send and Sync work
   (chapter 16).

/* --- EXTENSION TRAITS: add methods to a foreign type --- */
    trait BitExt { fn bit(self, n: u8) -> bool; }
    impl BitExt for u32 {
        fn bit(self, n: u8) -> bool { (self >> n) & 1 != 0 }
    }
    if reg.bit(5) { }
/* Legal because you own the trait. Extremely useful for
   register manipulation.

/* --- SEALED TRAITS: public to use, private to implement --- */
    mod private { pub trait Sealed {} }
    pub trait Register: private::Sealed { ... }
    impl private::Sealed for CTRL {}
    impl Register for CTRL { ... }
/* Nobody outside your crate can implement Register, because
   they cannot name Sealed. Used throughout the PAC crates
   (chapter 20) so the register set is closed.

/* --- ASSOCIATED TYPES versus GENERIC PARAMETERS --- */
    trait Container { type Item; fn get(&self)
                                        -> Option<&Self::Item>; }
    trait Convert<T> { fn convert(&self) -> T; }
/* USE AN ASSOCIATED TYPE when there is exactly one sensible
   choice per implementing type (Iterator::Item). Use a
   GENERIC PARAMETER when a type may implement it several
   ways (From<u8> and From<u16> for the same type). Getting
   this wrong makes an API either too rigid or ambiguous. */
