Kernel architectures: monolithic, micro, hybrid

Where you draw the line between "in the kernel" and "outside it" determines the system's performance, its reliability and its attack surface. This is the oldest live argument in operating systems, and the answer genuinely depends on what you are building.

The question

An OS provides file systems, drivers, networking, memory management and scheduling. Which of those run in kernel mode, with full privilege and no isolation from each other — and which run as ordinary isolated processes?

The trade-off, stated once:

  IN THE KERNEL              function call: ~1 ns
                             full access to everything
                             a bug is a system crash
                             a vulnerability is total compromise

  OUT OF THE KERNEL          IPC round trip: ~1-10 µs
                             isolated address space
                             a bug kills one service
                             a vulnerability is contained

  Everything below is a different answer to: how much performance
  is that isolation worth?

Monolithic

The dominant design, and the one Linux and Windows both use: everything in one address space at one privilege level. Its advantages and its single significant weakness both follow directly from that choice.

   ┌─────────────────────────────────────────┐
   │  user processes                          │
   └──────────────────┬──────────────────────┘
                      │ system calls
   ┌──────────────────▼──────────────────────┐
   │  KERNEL — one address space              │
   │  ┌────────┐ ┌────────┐ ┌──────────────┐ │
   │  │scheduler│ │  VFS   │ │ TCP/IP stack │ │
   │  └────────┘ └────────┘ └──────────────┘ │
   │  ┌────────┐ ┌────────┐ ┌──────────────┐ │
   │  │  MM    │ │ ext4   │ │ NIC driver   │ │
   │  └────────┘ └────────┘ └──────────────┘ │
   │   everything can call everything          │
   └─────────────────────────────────────────┘

   Linux, BSD, older UNIX. Loadable modules do NOT change this:
   a .ko is linked into the same address space at runtime.
AdvantageDisadvantage
Subsystem calls are direct function calls — no marshalling, no context switchAny driver bug can corrupt any kernel data

Why Linux is monolithic and stays that way

Roughly 70% of the Linux tree is drivers, all running at EL1 with no isolation from each other. That is a deliberate trade: driver authors get direct access and full speed, and the project accepts that a bad driver can panic the system. Mitigations added over time — lockdep, KASAN, the driver model, and increasingly Rust for new drivers — attack the bug rate rather than the architecture.

Microkernel

The alternative puts as little as possible in the kernel and runs drivers and filesystems as ordinary processes. It is more robust in principle and has a cost that kept it from dominating in practice.

   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
   │   app    │ │   file   │ │  network │ │  device  │
   │          │ │  system  │ │   stack  │ │  driver  │  ← all
   └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘    user
        │            │            │            │           mode,
        └────────────┴─────┬──────┴────────────┘           isolated
                           │ IPC messages
   ┌───────────────────────▼─────────────────────────────┐
   │  MICROKERNEL — only what MUST be privileged:         │
   │    address spaces, threads, scheduling, IPC          │
   │    typically 10,000 - 15,000 lines                   │
   └─────────────────────────────────────────────────────┘

   seL4, QNX, MINIX 3, L4 family, Zircon (Fuchsia)
AdvantageDisadvantage
A driver crash kills one process; a supervisor can restart itEvery cross-component call is IPC: two context switches minimum
Trusted computing base is small enough to formally verify (seL4 is proved correct)Data must be copied or shared explicitly
Components can be replaced or upgraded independentlyMore complex to design: everything is a protocol
Strong fault isolation and least privilege throughoutHistorically 10–50% slower on I/O-heavy workloads
Natural fit for certification (DO-178C, IEC 61508)Small ecosystem; fewer drivers exist
 
Why the performance gap narrowed but did not close

  1980s L3/L4 work showed IPC could be made ~20x faster than
  Mach's, by making it synchronous, register-based and avoiding
  the scheduler. Modern microkernels do a round trip in a few
  hundred nanoseconds, not microseconds.

  What still costs:
    · two address-space switches -> TLB pressure, even with ASIDs
    · cache footprint of crossing between components
    · data copies, unless shared memory is set up (which erodes
      the isolation you paid for)
    · the scheduler is now on the critical path of every I/O

  Where it wins outright: when a fault MUST be contained.
  seL4 in avionics and automotive; QNX in vehicles and medical
  devices. Isolation is the product, and the cycles are the price.

Hybrid

Most real systems are not purely one design or the other. Knowing where a given kernel actually sits on the spectrum is more useful than the label its documentation uses.

   ┌───────────────────────────────────────────────┐
   │  user mode: apps, some subsystems, UMDF drivers│
   └────────────────────┬──────────────────────────┘
   ┌────────────────────▼──────────────────────────┐
   │  KERNEL MODE — microkernel-STYLE structure,    │
   │  but a single address space                    │
   │  ┌──────────┐ ┌───────────┐ ┌───────────────┐ │
   │  │ Executive│ │  I/O mgr  │ │ KMDF drivers  │ │
   │  └──────────┘ └───────────┘ └───────────────┘ │
   │  ┌────────────────────────────────────────┐   │
   │  │  Kernel (KE): scheduling, IRQL, sync    │   │
   │  └────────────────────────────────────────┘   │
   │  ┌────────────────────────────────────────┐   │
   │  │  HAL                                    │   │
   │  └────────────────────────────────────────┘   │
   └───────────────────────────────────────────────┘

   Windows NT, macOS/XNU (a Mach microkernel with BSD and
   drivers linked into the same address space).

"Hybrid" mostly means: organised like a microkernel — layered, with defined interfaces and object abstractions — but running like a monolith, in one address space, for speed. Windows adds a genuine escape hatch with UMDF: user-mode drivers for classes of device (USB, HID, sensors) where a crash must not be fatal. That is the microkernel argument applied selectively, where the performance cost is acceptable.

Other shapes

Beyond the familiar three, several other shapes exist and are worth recognising because they appear in specific niches — unikernels in the cloud, exokernels in research, hypervisor-first designs in safety-critical work.

ArchitectureIdeaUsed for
ExokernelThe kernel only multiplexes hardware securely; applications implement their own abstractions in librariesResearch; influenced kernel-bypass networking (DPDK) and unikernels
UnikernelOne application linked with just the OS functions it needs, in a single address space, no user/kernel splitCloud appliances, MirageOS, Unikraft — tiny images, fast boot, minimal attack surface
Library OSOS services as a library the application links; isolation is provided from outsideGraphene, Windows Drawbridge, WASM runtimes
Nanokernel / separation kernelOnly spatial and temporal partitioning; everything else is a partitionAvionics (ARINC 653), mixed-criticality automotive
No kernelA superloop plus interruptsCortex-M firmware (C ch. 20)

Loadable modules

Loadable modules let a monolithic kernel gain and lose functionality at run time, which recovers some of the flexibility of a microkernel without the performance cost — and introduces its own problems.

# Linux — the module runs in the SAME address space at full privilege.
# This is convenience, not isolation.
sudo insmod driver.ko          # link into the running kernel
lsmod                          # what is loaded, and who depends on it
sudo rmmod driver              # unlink
modinfo driver.ko              # metadata, parameters, dependencies

# Windows
sc create mydrv type= kernel binPath= C:\drv.sys
sc start mydrv
pnputil /add-driver mydrv.inf /install
BenefitCost
Smaller base image; load only what the hardware needsSymbol resolution and relocation at load time
Third-party drivers without rebuilding the kernelA module can do anything — signing becomes essential
Development without rebootingNo stable in-kernel ABI in Linux: rebuild per version
Unload to reclaim memoryUnload races are a classic source of use-after-free

Windows does maintain a stable driver ABI across releases, which is why a driver from years ago often still loads. Linux deliberately does not, to force drivers upstream where they are maintained with the API. Both positions are defensible and both have real costs — this is one of the clearest philosophical differences between the two systems.

eBPF is the most interesting of these: it lets you run user-supplied code in the kernel while retaining safety, by proving properties statically instead of isolating at runtime. It is effectively a fourth answer to the original question.

The pattern worth carrying away

Every architecture here is answering "where do I put the isolation boundary?" — and the same question recurs at every level of this site. TrustZone puts it between two worlds; the SMMU puts it in front of DMA; the MMU puts it between processes; a hypervisor puts it between kernels. The mechanism differs; the reasoning about cost versus containment is identical every time.

How it shows up

SymptomArchitectural cause
