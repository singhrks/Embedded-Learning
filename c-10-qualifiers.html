const, volatile and restrict

Three qualifiers, three completely different jobs. const is a promise you make to the compiler; volatile is a promise the compiler makes to you; restrict is a promise you make that the compiler cannot verify. Each is routinely misunderstood, and volatile especially so.

const

What it means

const says "I will not modify this object through this expression." It is a type-system constraint, checked at compile time. It does not mean the object is immutable, and it does not mean the value is a compile-time constant.

/* Placement — read right to left from the identifier */
const int *p;          /* pointer to const int: *p is read-only     */
int const *p;          /* identical                                  */
int *const p;          /* const pointer: p itself cannot be reseated */
const int *const p;    /* both                                       */

const int *p = &x;
*p = 5;                /* error: object is const through p           */
p = &y;                /* fine                                       */
x = 5;                 /* FINE — x itself is not const               */

/* That last line is the point: const on a pointer restricts what
   YOU may do through that pointer, not what the object is.       */

Where const earns its place

/* 1. API documentation the compiler enforces */
size_t strlen(const char *s);          /* will not modify s          */
void *memcpy(void *dst, const void *src, size_t n);   /* src is read */

/* 2. Genuinely read-only data goes in .rodata, saving RAM —
      which on a microcontroller is the scarce resource         */
static const uint8_t font_table[4096] = { ... };   /* flash, not RAM */

/* 3. Catching mistakes at compile time */
void process(const struct config *cfg)
{
        cfg->retries = 3;      /* error — caught immediately         */
}
Three things const is not
  1. Not a compile-time constant. const int n = 10; int a[n]; is a VLA in C, not a fixed array. Use #define, an enum, or C23's constexpr for array bounds and case labels.
  2. Not immutability. Casting it away and writing is undefined only if the object was originally defined const. Writing through a cast to a non-const object is legal — which is why const cannot be relied on for security.
  3. Not deep. const struct s *p makes p->field const, but if field is a pointer, *p->field is still writable. C has no transitive const.
/* The const-correctness annoyance you will hit: C, unlike C++, does
   not implicitly convert `T**` to `const T**`. This is by design —
   allowing it would let you smuggle a const pointer into a
   non-const one — but it means some correct code needs a cast.   */
void f(const char **p);
char *argv[10];
f(argv);                    /* warning: incompatible pointer type */
f((const char **)argv);     /* explicit, and safe here            */

volatile

What it means

volatile tells the compiler: this object may change by means outside this program's control, so perform every access exactly as written — do not cache it in a register, do not eliminate it, do not duplicate it, and do not reorder it relative to other volatile accesses.

It constrains the compiler. It says nothing to the CPU or the memory system.

/* Without volatile, this is an infinite loop at -O2 */
uint32_t *status = (uint32_t *)0x40000018;
while (!(*status & READY))     /* nothing in the loop changes *status,
        ;                         so the compiler loads it ONCE, or
                                  deletes the loop entirely          */

/* With volatile, the load happens every iteration */
volatile uint32_t *status = (volatile uint32_t *)0x40000018;
while (!(*status & READY))
        ;

The three legitimate uses

UseWhy
Memory-mapped I/OHardware changes the value; reads and writes have side effects
Variables modified by a signal handlerMust be volatile sig_atomic_t; the handler runs outside normal flow
Variables modified across setjmp/longjmpNon-volatile locals have indeterminate values after a longjmp
volatile is NOT for threads

This is the most persistent misconception in C. volatile gives you none of what concurrent code needs:

  • No atomicity. volatile int x; x++; is still a load, an add and a store. Two threads can still lose an update.
  • No memory ordering. Volatile accesses are ordered relative to each other, but not relative to ordinary accesses, and the hardware is free to reorder everything anyway on a weakly ordered machine like ARM (CA ch. 15).
  • No visibility guarantee. Nothing forces the store out of the store buffer or invalidates another core's cache line.

For threads, use _Atomic / <stdatomic.h>, or your platform's primitives. Linus Torvalds' well-known essay on this is Documentation/process/volatile-considered-harmful.rst in the kernel tree — it is worth reading.

/* WRONG — a classic that appears to work until it does not */
volatile bool done = false;
volatile int  result;

void producer(void) { result = compute(); done = true; }
void consumer(void) { while (!done) ; use(result); }
/* On ARM the two stores may become visible in either order, so the
   consumer can see done==true and a stale result. volatile did
   nothing to prevent it.                                        */

/* RIGHT — C11 atomics */
#include <stdatomic.h>
atomic_bool done = false;
int result;                              /* plain int is fine now */

void producer(void)
{
        result = compute();
        atomic_store_explicit(&done, true, memory_order_release);
}
void consumer(void)
{
        while (!atomic_load_explicit(&done, memory_order_acquire))
                ;
        use(result);                     /* guaranteed to see it   */
}

volatile in MMIO, done properly

/* volatile alone is not sufficient for device registers either —
   it stops the COMPILER reordering, not the CPU or the bus.     */

/* Bare metal: pair it with barriers where ordering matters */
static inline void mmio_write32(uintptr_t a, uint32_t v)
{
        *(volatile uint32_t *)a = v;
        __asm__ volatile("dsb sy" ::: "memory");   /* if it must land */
}

/* In an OS, use the accessors — they get this right for you: */
writel(val, base + CTRL);        /* Linux: volatile + barriers      */
readl(base + STATUS);
writel_relaxed(val, base + CTRL);  /* no barrier, when order is
                                      genuinely irrelevant           */
WRITE_REGISTER_ULONG(reg, val);  /* Windows                          */

/* Never hand-roll MMIO access in kernel code. The accessors also
   encode endianness and, on some architectures, special
   instructions that a plain volatile store would not use.       */

The volatile-qualified struct pattern

/* Correct: every member volatile */
struct uart_regs {
        volatile uint32_t DR;
        volatile uint32_t FR;
};

/* Also correct, and shorter: qualify the pointer */
struct uart_regs { uint32_t DR; uint32_t FR; };
volatile struct uart_regs *u = (volatile struct uart_regs *)BASE;

/* WRONG: qualifying the pointer variable rather than the target */
struct uart_regs *volatile u;      /* the POINTER is volatile;
                                      the registers are not!      */

restrict

What it means

restrict on a pointer promises: within the lifetime of this pointer, the object it points to will not be accessed through any other pointer. It is a promise you make. The compiler cannot check it, and breaking it is undefined behaviour with no diagnostic.

It applies only to pointers, and it exists purely to enable optimisation.

/* Without restrict, the compiler must assume a and b may overlap */
void add(int *a, const int *b, size_t n)
{
        for (size_t i = 0; i < n; i++)
                a[i] += b[i];
}
/* Every iteration must RELOAD b[i], because the previous store to
   a[i] might have modified it. No vectorisation possible.       */

/* With restrict, the promise unlocks it */
void add(int *restrict a, const int *restrict b, size_t n)
{
        for (size_t i = 0; i < n; i++)
                a[i] += b[i];
}
/* Now the compiler can load a block of b, load a block of a, add
   them with SIMD, and store. Typically 4-8x faster.             */
/* The canonical illustration: two functions, one difference. */
void *memcpy (void *restrict dst, const void *restrict src, size_t n);
void *memmove(void       *dst, const void       *src, size_t n);

/* memcpy's arguments are restrict: overlapping is UNDEFINED, and
   glibc's memcpy really does misbehave on overlap — it copies in
   whatever order is fastest, including backwards.

   memmove handles overlap correctly and pays for it.

   If you are not certain the buffers are disjoint, use memmove. The
   "memcpy is faster" reasoning is not worth a corruption bug.   */
How to break a restrict promise without noticing 
void f(int *restrict a, int *restrict b);
int arr[10];
f(arr, arr);              /* UB — same object through both        */
f(arr, arr + 5);          /* UB if the accessed ranges overlap    */

/* Aliasing through a struct member is easy to miss: */
void g(struct s *restrict p, int *restrict q);
g(&obj, &obj.field);      /* UB — q points inside *p              */

/* Rule of thumb: only use restrict on parameters of leaf functions
   whose callers you control, or where the API contract explicitly
   forbids overlap (and is documented as doing so).             */

Combining qualifiers

The qualifiers can be combined, and the combinations mean precise things — particularly where the qualifier sits relative to a pointer's asterisk, which changes whether it applies to the pointer or to what it points at.

/* const volatile — real and useful: a hardware register that the
   device updates but software must never write.                */
const volatile uint32_t *status = (const volatile uint32_t *)0x40000018;
uint32_t s = *status;      /* fine: reads happen every time      */
*status = 0;               /* compile error: correctly rejected  */

/* Typical for: status registers, free-running counters, ID registers */

/* volatile const is the same thing; order does not matter.       */

/* restrict + const is common in read-only source parameters */
void transform(float *restrict out, const float *restrict in, size_t n);

_Atomic, for completeness

C11 added a qualifier for objects accessed concurrently, giving the language its own memory model rather than leaving it to the platform. Kernel code generally does not use it, and knowing why is worth more than the syntax.

#include <stdatomic.h>

_Atomic int counter;                /* C11 type qualifier         */
atomic_int counter;                 /* the convenience typedef     */

atomic_fetch_add(&counter, 1);      /* atomic read-modify-write   */
atomic_load(&counter);
atomic_store(&counter, 0);
atomic_compare_exchange_strong(&p, &expected, desired);

/* _Atomic gives you what volatile does not:
     - indivisibility of read-modify-write
     - a memory ordering model you can reason about
     - the compiler emits LDAXR/STLXR or LSE atomics on ARM

   Note: atomic operations on large types may be implemented with a
   lock. Check with:                                             */
atomic_is_lock_free(&obj);
ATOMIC_INT_LOCK_FREE                /* compile-time: 0, 1 or 2    */
