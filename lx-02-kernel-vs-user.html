Kernel versus user-space programming

You already know C. Kernel C is the same language with a different standard library, no safety net, and a set of rules that are not written in the compiler. This chapter is the list of everything that changes, so the first week costs you hours instead of days.

Everything that is different

None of these differences is arbitrary — each one follows from the same fact: kernel code runs with no process boundary underneath it, so nothing catches its mistakes and nothing frees its resources when it misbehaves. Read this table once as a reference, then again after the rest of the chapter, when each row has a reason attached to it rather than just a contrast.

The stack is 16 KB

This is the constraint that surprises people most. In user space the stack grows to megabytes on demand; in the kernel you get a small, fixed allocation that never grows, shared with anything that interrupts you — and overflowing it corrupts whatever happens to sit next to it in memory.

/* THE most common beginner crash. On arm64, THREAD_SIZE is
   16 KB by default - and that is the whole kernel stack for
   the task, shared by every function on the call chain.     */

/* WRONG - 8 KB of stack in one line: */
static int my_ioctl(struct file *f, unsigned int cmd,
                    unsigned long arg)
{
        char buf[8192];                 /* half the stack */
        struct big_thing thing;         /* another 2 KB    */
        ...
}

/* RIGHT - allocate it: */
static int my_ioctl(struct file *f, unsigned int cmd,
                    unsigned long arg)
{
        char *buf;
        int ret;

        buf = kmalloc(8192, GFP_KERNEL);
        if (!buf)
                return -ENOMEM;
        ...
        kfree(buf);
        return ret;
}

/* THE RULE OF THUMB: keep any single frame under ~256 bytes,
   and never put an array larger than about 128 bytes on the
   stack. The compiler will warn above 1024 with
   -Wframe-larger-than, and the kernel sets that. DO NOT
   silence it.

   ALSO ON THE STACK, uninvited:
     · interrupt handlers, unless IRQ_STACKS is on
     · deep call chains through the block or network stack
     · recursion - which is why the kernel has almost none

   OVERFLOW SYMPTOM: not a clean error. You corrupt
   thread_info or the adjacent page and crash later,
   somewhere else, with a nonsensical backtrace. Enable
   CONFIG_VMAP_STACK (default on arm64) and overflow becomes a
   clean fault with a real trace instead.                   */

Context: the rule everything else follows

If you take one idea from this chapter, take this one. "Context" means the circumstances your code is running under, and it determines what you are permitted to do — most importantly whether you may sleep. Nearly every rule in the rest of this track is a consequence of it.

Kernel code runs in one of three contexts, and what you may do
depends entirely on which:

  PROCESS CONTEXT (also "task context")
     Entered via a syscall, or in a kernel thread.
     You have a `current` task. You may SLEEP.
     -> syscalls, ioctl, read/write, probe(), workqueues

  SOFTIRQ / TASKLET / BOTTOM-HALF CONTEXT
     Deferred interrupt work. No `current` you can rely on.
     MAY NOT SLEEP.
     -> network receive, some timers

  HARDIRQ CONTEXT (interrupt handler)
     Interrupts possibly disabled, must be FAST.
     MAY NOT SLEEP. May not call anything that might.
     -> your request_irq() top half

  AND A FOURTH STATE, orthogonal: ATOMIC.
     Holding a spinlock, or with preemption or interrupts
     disabled. MAY NOT SLEEP - even in process context.

  "MAY NOT SLEEP" MEANS you may not call:
       kmalloc(GFP_KERNEL)      -- may wait for reclaim
       mutex_lock()             -- may block
       copy_to_user()           -- may take a page fault
       msleep(), schedule()
       anything that says "might sleep" in its docs
       vmalloc(), most of the filesystem API

  and you MAY call:
       kmalloc(GFP_ATOMIC)      -- fails rather than waits
       spin_lock()
       readl()/writel()
       pr_info() (with care - it can be slow)

  HOW TO KNOW WHICH CONTEXT YOU ARE IN:
     read the caller. There is no runtime flag that answers it
     reliably - which is why the kernel gives you a checker:

       CONFIG_DEBUG_ATOMIC_SLEEP=y

     turns every illegal sleep into a loud
       "BUG: sleeping function called from invalid context"
     with a backtrace. TURN IT ON. It is the single most
     valuable debug option for a new kernel developer.
The question to ask before every call

"What context am I in, and can this function sleep?" Nearly every kernel bug a newcomer writes is an answer to that question they never asked. The kernel-doc for a function says Context: explicitly for many APIs; where it does not, the convention is that GFP_KERNEL, mutex and _interruptible in a name all imply sleeping.

The library you get instead

There is no libc in the kernel, so the familiar functions are simply absent. What you get instead is a smaller set with similar names and deliberately different behaviour — and the differences exist because the kernel versions were designed after decades of watching the originals cause security bugs.

/* PRINTING */
        printf("x=%d\n", x);            /* NO */
        pr_info("x=%d\n", x);           /* yes */
        pr_err(), pr_warn(), pr_debug()
        dev_info(dev, "..."), dev_err(dev, "...")   /* BEST -
                       prefixes the device name automatically */

/* format specifiers differ - use the kernel's: */
        %pK    a pointer, hashed unless privileged
        %pa    a phys_addr_t / dma_addr_t
        %pOF   a device_node's full path
        %pe    an ERR_PTR, printed as "-ENOMEM"
        %*ph   a hex dump of n bytes
        size_t is %zu, not %lu

/* MEMORY */
        malloc(n)   ->  kmalloc(n, GFP_KERNEL)
        calloc      ->  kcalloc(n, size, GFP_KERNEL)
        realloc     ->  krealloc()
        free        ->  kfree()
        large       ->  vmalloc()  (virtually contiguous only)
        page-sized  ->  alloc_pages() / __get_free_pages()
        best        ->  devm_kzalloc(dev, n, GFP_KERNEL)
                        - freed automatically (chapter 33)

/* STRINGS - and the safe variants matter */
        strcpy      ->  strscpy(dst, src, sizeof(dst))
                        NOT strncpy, NOT strlcpy - strscpy
                        always NUL-terminates and returns
                        -E2BIG on truncation
        sprintf     ->  scnprintf(buf, size, ...)
                        returns what was ACTUALLY written,
                        unlike snprintf
        memcpy, memset, memcmp   -- these exist, use freely

/* ERRORS - negative errno, always */
        return -ENOMEM;
        return -EINVAL;
        return -EIO;
        return -EPROBE_DEFER;   /* kernel-specific: "try me
                                   again later" (chapter 19) */

/* POINTERS THAT ARE ERRORS */
        p = some_func();                /* returns ERR_PTR */
        if (IS_ERR(p))
                return PTR_ERR(p);
        /* NOT: if (!p) - a valid error pointer is non-NULL */

/* NO FLOATING POINT. None. The kernel does not save FP state
   on entry, so touching it corrupts user space's registers.
   Use fixed-point arithmetic:                              */
        /* instead of: temp_c = raw * 0.0625;               */
        temp_milli_c = (raw * 625) / 10;

/* DIVISION of 64-bit values on 32-bit builds needs helpers: */
        do_div(n64, d32);               /* modifies n64 */
        div_u64(n64, d32);
        div64_u64(n64, d64);
/* A plain `a / b` on two u64s can fail to link on 32-bit. */

Everything runs at once

In user space you reason about the threads you created. In the kernel your code can be entered simultaneously on every CPU, by an interrupt, by a timer, and by several processes, without you having started any of them — so code that is obviously single-threaded is usually not.

/* In user space you know which threads you created. In the
   kernel, your code can be entered:

     · by every CPU simultaneously
     · re-entered by an interrupt on the same CPU
     · by a timer, a workqueue, or an RCU callback
     · by a different process through the same file descriptor
     · while your module is being unloaded

   ALL AT ONCE, from the first line you write.              */

/* WRONG - a shared counter with no protection: */
static int count;
static ssize_t my_write(...)
{
        count++;                /* read-modify-write RACE */
        ...
}

/* RIGHT - pick a mechanism (chapter 12): */
static atomic_t count = ATOMIC_INIT(0);
        atomic_inc(&count);

/* or, for anything more than a counter: */
static DEFINE_MUTEX(my_lock);           /* process context   */
static DEFINE_SPINLOCK(my_slock);       /* any context       */

/* AND THE SUBTLER ONE - your module can be unloaded while a
   callback is still queued: */
static void my_exit(void)
{
        cancel_delayed_work_sync(&work);  /* SYNC: wait for it */
        del_timer_sync(&timer);           /* SYNC */
        free_irq(irq, dev);
        /* only now is it safe for your code to disappear */
}
/* Get this wrong and you get "BUG: unable to handle page
   fault" inside freed module text - a crash with a
   backtrace pointing at addresses that no longer exist.  */

The compiler is not the one you know

The kernel is compiled with a different set of assumptions from any user-space program: no standard library, no floating point, different optimisation rules, and warnings treated far more seriously. Some things that are legal C simply do not work here.

# The kernel builds with, roughly:
    -ffreestanding          no assumptions about libc
    -fno-common
    -fno-strict-aliasing    the kernel type-puns deliberately
    -fno-delete-null-pointer-checks
    -fno-stack-protector    (or a kernel-specific one)
    -Wall -Wundef -Werror=implicit-function-declaration
    -Wframe-larger-than=1024 (or 2048)
    -std=gnu11
    no -O0 - the kernel REQUIRES optimisation to build
             correctly (inline assembly and __builtin
             constant folding depend on it)

# CONSEQUENCES:
#   · no libc headers. <stdio.h> does not exist. Use
#     <linux/kernel.h>, <linux/string.h>, <linux/types.h>.
#   · u8/u16/u32/u64 and s8..s64 instead of stdint types
#     (though stdint-style names exist via <linux/types.h>)
#   · __le32 / __be32 for explicit endianness, with
#     le32_to_cpu() etc. - and `sparse` checks you converted
#   · GNU extensions are used freely: statement expressions,
#     typeof, __attribute__, designated initialisers,
#     case ranges

# RUN SPARSE. It catches __user/__iomem/endian mistakes that
# the compiler cannot:
    make C=1 M=drivers/mydrv/          # check changed files
    make C=2 M=drivers/mydrv/          # check all files

Two kinds of ABI, opposite rules

The kernel enforces two contradictory stability promises simultaneously, and confusing which one applies to the code you are touching is a common and avoidable mistake: internal APIs are free to change because only kernel code itself depends on them, while anything a user-space program can observe must never change, because an unknown number of programs already depend on it and cannot all be recompiled together.

Internal kernel APIUser-space ABI
StabilityNone. Functions and structs change every releaseAbsolute. "We do not break user space"
Includesinclude/linux/include/uapi/, syscalls, ioctl numbers, sysfs paths, netlink messages, /proc formats
ConsequenceOut-of-tree modules break on every upgrade — a reason to upstreamDesign your ioctl interface once, carefully (ch. 23)
The asymmetry is deliberate

Internal churn is allowed precisely so that the kernel can be refactored to keep the external promise. That is why maintainers care so much about what your driver exposes to userspace and comparatively little about how it is structured internally: the first is forever, the second they can fix themselves.

Style, and why it is enforced

Kernel style is unusually strict and unusually well enforced, which strikes newcomers as bureaucratic. There is a practical reason: with thousands of contributors reading each other's code, consistency is what makes a patch reviewable at all — and there is a tool that checks it for you.

# Documentation/process/coding-style.rst. Non-negotiable in
# review, and mechanically checkable:

    ./scripts/checkpatch.pl --strict -f drivers/mydrv/mydrv.c

# The rules that trip people up:
#   tabs, 8 wide. Not spaces.
#   ~80 columns (100 tolerated, but aim for 80)
#   opening brace on the same line, EXCEPT for functions
#   no braces on single-statement bodies
#   typedef is discouraged - write `struct foo`
#   one declaration per line, no assignments in conditions
#   goto for error unwinding is CORRECT and idiomatic (ch. 33)
#   comments: /* ... */, not //, for multi-line

/* The idiomatic error path - learn to read and write this: */
static int my_probe(struct platform_device *pdev)
{
        struct my_dev *d;
        int ret;

        d = devm_kzalloc(&pdev->dev, sizeof(*d), GFP_KERNEL);
        if (!d)
                return -ENOMEM;

        d->base = devm_platform_ioremap_resource(pdev, 0);
        if (IS_ERR(d->base))
                return PTR_ERR(d->base);

        ret = my_setup(d);
        if (ret)
                return ret;            /* devm cleans up */

        platform_set_drvdata(pdev, d);
        return 0;
}
/* Note: `sizeof(*d)` not `sizeof(struct my_dev)` - so it stays
   correct if the type changes. This is house style and
   reviewers will ask for it.                               */
