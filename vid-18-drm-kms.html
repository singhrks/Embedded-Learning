DRM/KMS, planes and zero-copy display

The last stage of the pipeline, and the one that decides whether video playback costs half a watt or five. The display controller can scan out NV12 directly, scale it, convert its colour and composite it — if you ask correctly. If you do not, the GPU does all of that instead, at ten times the power.

The KMS object model

   Kernel Mode Setting exposes the display hardware as five
   object types. Every display configuration is a set of
   properties on these.

   FRAMEBUFFER    a buffer plus its format and modifier
        |         (chapter 4). Wraps a DMABUF or GEM object.
        v
   PLANE          a hardware scanout engine. Reads a
        |         framebuffer, optionally scales it, converts
        |         its colour, and positions it.
        |           PRIMARY  the main one, one per CRTC
        |           OVERLAY  extra planes for compositing
        |           CURSOR   small, always on top
        v
   CRTC           the scanout engine proper. Owns the mode
        |         (resolution, refresh, timings), blends the
        |         planes, and generates the pixel clock.
        v
   ENCODER        converts the pixel stream to a signal -
        |         HDMI, DisplayPort, MIPI DSI, LVDS.
        v
   CONNECTOR      the physical port and the attached display.
                  Carries EDID: what the monitor supports.

   THE CHAIN: framebuffer -> plane -> CRTC -> encoder ->
   connector -> the screen.

   PLANES ARE THE POINT OF THIS CHAPTER. A hardware plane can
   do, for free and in the display controller:
     * YUV to RGB conversion
     * scaling
     * positioning and cropping
     * alpha blending with the other planes
     * (sometimes) rotation and colour management

   That is exactly the work a GPU composite would otherwise
   do, and the display controller does it while reading the
   pixels it has to read anyway - so it costs no extra memory
   bandwidth at all.
The video plane is why phones can play 4K for hours

Put decoded NV12 on an overlay plane and the pipeline is: decoder writes the frame once, display controller reads it once. The GPU is never involved and can stay powered down. Composite the same frame with the GPU instead and you add a texture read, a colour conversion, a render pass and a write — several hundred megabytes per second at 4K60, and the GPU cannot idle. On mobile that is the difference between a warm phone and a hot one.

Atomic modesetting

/* The old API set one thing at a time - mode, then plane,
   then cursor - and each could fail halfway, leaving the
   display in a broken intermediate state. The ATOMIC API
   submits every change as ONE transaction that either applies
   completely or not at all.                                */

#include <xf86drm.h>
#include <xf86drmMode.h>

int fd = open("/dev/dri/card0", O_RDWR | O_CLOEXEC);

/* You must ask for the modern capabilities explicitly. */
drmSetClientCap(fd, DRM_CLIENT_CAP_UNIVERSAL_PLANES, 1);
drmSetClientCap(fd, DRM_CLIENT_CAP_ATOMIC, 1);

/* Build a request from property changes. */
drmModeAtomicReq *req = drmModeAtomicAlloc();

drmModeAtomicAddProperty(req, plane_id, prop_fb_id,   fb_id);
drmModeAtomicAddProperty(req, plane_id, prop_crtc_id, crtc_id);
/* SRC coordinates are 16.16 FIXED POINT - the source
   rectangle within the framebuffer. */
drmModeAtomicAddProperty(req, plane_id, prop_src_x, 0);
drmModeAtomicAddProperty(req, plane_id, prop_src_y, 0);
drmModeAtomicAddProperty(req, plane_id, prop_src_w, 1920 << 16);
drmModeAtomicAddProperty(req, plane_id, prop_src_h, 1080 << 16);
/* CRTC coordinates are plain integers - where it lands on
   screen. Different units for source and destination, in the
   same call, is a reliable source of bugs. */
drmModeAtomicAddProperty(req, plane_id, prop_crtc_x, 0);
drmModeAtomicAddProperty(req, plane_id, prop_crtc_y, 0);
drmModeAtomicAddProperty(req, plane_id, prop_crtc_w, 3840);
drmModeAtomicAddProperty(req, plane_id, prop_crtc_h, 2160);
/* src != crtc size means the plane SCALES - for free. */

/* TEST_ONLY asks "would this work?" without changing
   anything. This is the single most useful feature of the
   atomic API: probe your configuration, fall back if the
   hardware cannot do it, and never leave the display broken. */
int ret = drmModeAtomicCommit(fd, req,
                              DRM_MODE_ATOMIC_TEST_ONLY, NULL);
if (ret == 0)
        drmModeAtomicCommit(fd, req,
                            DRM_MODE_ATOMIC_NONBLOCK |
                            DRM_MODE_PAGE_FLIP_EVENT, user_data);
else
        fallback_to_gpu_composite();

drmModeAtomicFree(req);

/* PAGE_FLIP_EVENT means the commit happens at the next
   VBLANK and you get an event on the fd when it has. That is
   how you avoid tearing and how you pace your rendering -
   read the event, then draw the next frame. */

Getting video onto a plane

   THE FULL ZERO-COPY PATH (chapter 16):

     V4L2 decoder
       VIDIOC_EXPBUF  ->  dmabuf fd
            |
            v
     drmPrimeFDToHandle(fd, dmabuf_fd, &gem_handle)
            |
            v
     drmModeAddFB2WithModifiers(
            fd, w, h, DRM_FORMAT_NV12,
            handles,      /* the same handle for both planes */
            pitches,      /* per-plane stride                */
            offsets,      /* per-plane offset into the buffer*/
            modifiers,    /* THE TILING - must match!        */
            &fb_id, DRM_MODE_FB_MODIFIERS)
            |
            v
     atomic commit: put fb_id on an overlay plane
            |
            v
     the display controller scans it out, converting NV12 to
     RGB in hardware.

   THE FOUR THINGS THAT MUST LINE UP, and any one of them
   failing sends you back to a GPU composite:

     1. FORMAT   the plane must advertise NV12 (or P010 for
                 10-bit). Query IN_FORMATS on the plane.
     2. MODIFIER the exact tiling the decoder produced must be
                 one the plane accepts (chapter 4).
     3. SCALING  the plane's min/max scale factors. Many
                 overlay planes cannot scale at all, and some
                 cannot scale down below 1:2.
     4. BANDWIDTH the display controller has a fixed budget.
                 Two 4K planes may simply exceed it, and the
                 commit fails at TEST_ONLY.

   AND COLOUR: a YUV plane needs its properties set, or you
   get the washed-out or crushed picture of chapter 2:
     COLOR_ENCODING  ITU-R BT.601 / BT.709 / BT.2020
     COLOR_RANGE     YCbCr limited range / YCbCr full range
   Defaults are usually BT.601 limited, which is wrong for
   almost all modern content.

Plane assignment is a negotiation you can lose silently

A compositor tries to put your video on a hardware plane and falls back to GPU composition when it cannot — because another window overlaps it, because the scaling factor is out of range, because a rounded corner needs alpha, or because bandwidth is exhausted. Nothing tells you. The picture is identical; the power draw triples. On Linux the way to know is /sys/kernel/debug/dri/0/state; on Android it is dumpsys SurfaceFlinger and the DEVICE versus CLIENT composition column.

Tearing, vblank and presentation

/* TEARING: the scanout reads the framebuffer while you are
   writing it, so the top of the screen shows the old frame
   and the bottom the new one.

   THE FIX: DOUBLE BUFFERING plus a flip at VBLANK - the
   interval between the last line of one frame and the first
   of the next, when nothing is being read.                 */

  drmModePageFlip(fd, crtc, new_fb, DRM_MODE_PAGE_FLIP_EVENT,
                  user_data);
  /* returns immediately; the flip happens at the next vblank */

  struct pollfd p = { .fd = drm_fd, .events = POLLIN };
  poll(&p, 1, -1);
  drmHandleEvent(drm_fd, &evctx);    /* your page_flip_handler
                                        runs; now the old
                                        buffer is free to
                                        reuse               */

/* THE RULE: do not touch a buffer until you have been told
   the flip completed. It is exactly the fence discipline of
   GPU chapter 16, in a different API.

/* VARIABLE REFRESH RATE - the display waits for you instead
   of the other way round. FreeSync/G-Sync/HDMI VRR, exposed
   as the CRTC's VRR_ENABLED property. Removes judder when
   the content rate does not divide the refresh rate.

/* AND THE CADENCE PROBLEM, which VRR was invented for:
     24 fps film on a 60 Hz display needs 3:2 PULLDOWN -
     frame A for 3 refreshes, frame B for 2, alternating.
     The uneven timing is visible as JUDDER on slow pans.
     A 120 Hz display divides evenly by both 24 and 30, which
     is why 120 Hz panels matter more for film than for games.

/* MULTIPLE PLANES, ONE COMMIT: the atomic API lets you flip
   the UI plane and the video plane in the same transaction,
   so they change together. Flipping them separately means one
   frame where the subtitle belongs to the previous video
   frame - a subtle artefact that is very hard to attribute.*/
