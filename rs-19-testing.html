Testing: unit, integration, doc and property

Testing is built into Cargo rather than bolted on, which changes how much of it gets written. The interesting parts for a systems programmer are the kinds of test the compiler cannot replace — and how you test code that cannot run on the machine you are compiling it on.

Four kinds, and what each is for

Rust's test kinds are not arbitrary categories; each sees a different slice of your crate, and that visibility difference is what decides where a test belongs.

KindLives inCan seeUse it for
UnitA #[cfg(test)] mod tests in the same filePrivate itemsInternal logic, edge cases, the awkward branch
Integrationtests/*.rs, one binary per fileOnly the public APIWhether the crate is usable from outside
Doc/// commentsPublic APIExamples that are compiled and run, so they cannot rot
PropertyEither, with a crateEitherInvariants over generated inputs, rather than examples you thought of

The visibility rule is the one that matters in practice. An integration test that will not compile because something is private is telling you something real about your API, and the fix is usually to reconsider the API rather than to make the item public.

// UNIT TESTS - same file, private access, compiled away
// entirely in a normal build thanks to cfg(test).

pub fn checksum(data: &[u8]) -> u16 {
    data.iter().fold(0u16, |a, &b| a.wrapping_add(b as u16))
}

fn is_frame_start(b: u8) -> bool { b == 0x7E }   // private

#[cfg(test)]
mod tests {
    use super::*;              // bring the parent into scope

    #[test]
    fn checksum_of_empty_is_zero() {
        assert_eq!(checksum(&[]), 0);
    }

    #[test]
    fn checksum_wraps_rather_than_panicking() {
        // The case that would panic in a debug build if the
        // implementation used + instead of wrapping_add.
        assert_eq!(checksum(&[0xFF; 300]), 0xFF * 300 % 65536);
    }

    #[test]
    fn private_items_are_visible_here() {
        assert!(is_frame_start(0x7E));   // an integration
    }                                    // test could not

    #[test]
    #[should_panic(expected = "out of range")]
    fn rejects_bad_input() {
        parse_channel(99);
    }

    #[test]
    fn result_tests_can_use_question_mark() -> Result<(), Error> {
        let cfg = Config::parse("mode=fast")?;
        assert_eq!(cfg.mode, Mode::Fast);
        Ok(())
    }

    #[test]
    #[ignore = "needs hardware attached"]
    fn talks_to_the_device() { /* cargo test -- --ignored */ }
}

Doc tests, which are the underrated one

An example in a comment that is compiled and executed on every test run cannot drift out of date, and that makes documentation a category of test rather than a category of prose. No other mainstream systems language gives you this by default.

/// Decodes one frame from `buf`.
///
/// Returns the frame and the number of bytes consumed, or
/// `None` if `buf` does not yet hold a complete frame.
///
/// # Examples
///
/// ```
/// use myproto::decode;
/// let (frame, used) = decode(&[0x7E, 0x01, 0x41]).unwrap();
/// assert_eq!(frame.payload, b"A");
/// assert_eq!(used, 3);
/// ```
///
/// A partial buffer yields `None`:
///
/// ```
/// assert!(myproto::decode(&[0x7E]).is_none());
/// ```
///
/// # Panics
///
/// Panics if `buf` is longer than `MAX_FRAME`.
pub fn decode(buf: &[u8]) -> Option<(Frame, usize)> { todo!() }

     ```no_run      compiled, not executed - for examples
                    that need hardware or a network
     ```ignore      not even compiled - use sparingly, it is

     ```text        not Rust at all

Property testing

Example-based tests check the cases you thought of, which are by definition not the ones that will break you. Property testing inverts that: you state an invariant, and the framework hunts for a counterexample.

   THE SHAPE:

     for ANY input the generator produces,
        THIS PROPERTY must hold.

   THE PROPERTIES THAT ARE ALMOST ALWAYS AVAILABLE:

     ROUND TRIP      decode(encode(x)) == x
                     the highest-value property in systems
                     code, and usually free to state
     INVARIANT       the output is always sorted / in range
                     / shorter than the input
     ORACLE          the fast version agrees with the obvious
                     slow one
     NEVER PANICS    parse(arbitrary bytes) returns Err
                     rather than panicking

   ---------------------------------------------------------

   THE FEATURE THAT MAKES IT WORTH THE DEPENDENCY IS
   SHRINKING. On failure the framework does not hand you the
   4KB random buffer that broke it - it repeatedly simplifies
   the input while keeping it failing, and reports the
   MINIMAL case. You get "fails on [0x7E, 0x00]" rather than
   a haystack.

   ---------------------------------------------------------

   AND ITS BIGGER SIBLING: FUZZING. cargo-fuzz runs a
   coverage-guided fuzzer over a parser for hours and finds
   the inputs no generator would invent. For anything that
   parses UNTRUSTED input - a protocol frame, a file format,
   anything off a wire - this is the single highest-value
   test you can write, and it is about ten lines.
// A property test, with proptest:
proptest! {
    #[test]
    fn decode_reverses_encode(payload: Vec<u8>) {
        let bytes = encode(&payload);
        let (frame, used) = decode(&bytes).unwrap();
        prop_assert_eq!(frame.payload, payload);
        prop_assert_eq!(used, bytes.len());
    }

    #[test]
    fn decode_never_panics(bytes: Vec<u8>) {
        let _ = decode(&bytes);      // Err is fine. Panic is not.
    }
}

// A fuzz target, with cargo-fuzz:
#![no_main]
libfuzzer_sys::fuzz_target!(|data: &[u8]| {
    let _ = myproto::decode(data);
});
// $ cargo fuzz run decode
// Runs until it finds a panic, then writes the input to a
// file you can replay. Leave it running over lunch.

Testing what the type system cannot check

For ordinary safe Rust the compiler has already eliminated the bug classes most tests are written to catch. The tests that earn their keep are the ones aimed at what the compiler cannot see — which means unsafe code above all.

ToolFindsNote
cargo testLogic errorsDebug builds catch integer overflow; release builds wrap — test both
cargo clippySuspicious patterns and idiom problemsRun with -D warnings in CI
cargo miri testUndefined behaviour in unsafe code — invalid aliasing, out-of-bounds, uninitialised readsInterprets rather than executes; slow, and the only practical UB detector. Essential for chapter 14
SanitizersData races, leaks, memory errorsNightly; useful where Miri cannot go (FFI)
cargo-fuzzCrashes on untrusted inputTen lines, enormous value for any parser
cargo docBroken intra-doc linksFree correctness on the documentation itself
Miri is the one to actually install

Safe Rust does not need a memory checker; the compiler already did that job. Unsafe Rust needs one badly, because the whole point of unsafe is that you have taken on obligations nothing checks. Miri runs your test suite under an interpreter that tracks provenance and aliasing, and it catches the exact mistakes that otherwise appear as corruption six months later on a different machine — the dangling temporary from chapter 09 among them. If your crate contains a single unsafe block, running cargo miri test in CI is the highest-value ten minutes available. It cannot follow calls into C, which is exactly where sanitizers take over.

Testing firmware

Everything above assumes tests run where you compile. On a microcontroller that is false, and the standard answer is to split the problem so that most of it becomes testable on the host anyway.

   SPLIT THE CRATE IN TWO, and this is good design
   independently of testing:

     PURE LOGIC          protocol parsing, state machines,
                         filters, checksums, scheduling
                         decisions
                         -> no hardware. Compiles for the
                            host. Test it with cargo test
                            like anything else.

     HARDWARE ACCESS     register writes, DMA, interrupts
                         -> must run on the device.

   MOST FIRMWARE BUGS LIVE IN THE FIRST HALF, and the first
   half needs no hardware to test. Getting the split right is
   worth more than any testing tool.

   ---------------------------------------------------------

   FOR THE SECOND HALF, TWO OPTIONS:

     MOCK THE TRAIT. Because drivers are written against
     embedded-hal traits (chapter 20), you can implement
     those traits over a Vec of expected transactions and
     test the driver on the host. embedded-hal-mock does
     exactly this, and it verifies the SEQUENCE of bus
     operations - which is usually what you actually wanted
     to assert.

     RUN ON THE TARGET. defmt-test and probe-rs run a real
     test harness on the chip and report results back over
     the debug probe. `cargo test` for firmware, with the
     device attached.

   ---------------------------------------------------------

   AND THE no_std SNAG WORTH KNOWING BEFORE IT BITES: the
   standard test harness needs std. A no_std crate is
   usually arranged so that the library builds for both -
   `#![cfg_attr(not(test), no_std)]` - so the host test run
   gets std and the firmware build does not.

SymptomCause
