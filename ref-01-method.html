The debugging method

Debugging is not a talent. It is a procedure, and the engineers who look fast at it are following it deliberately while everyone else is guessing.

The loop

   1. OBSERVE          what ACTUALLY happens, precisely
   2. HYPOTHESISE      one falsifiable explanation
   3. PREDICT          "if this is true, then X will be
                        true"
   4. TEST             the cheapest experiment that
                        distinguishes
   5. CONCLUDE         confirmed, or eliminated
   6. REPEAT

   THE SCIENTIFIC METHOD, applied to a machine that cannot
   lie to you.

   THE FAILURE MODE THAT WASTES DAYS - "SHOTGUN DEBUGGING":
     change something, rebuild, see if it helps, change
     something else.

   Why it fails:
     · you learn NOTHING when it does not help
     · when it DOES help you do not know why, so you cannot
       be sure it is fixed
     · you accumulate unexplained changes, each a future bug
     · and you cannot tell whether you fixed the problem or
       merely moved it

   THE DISCIPLINE THAT REPLACES IT:

     CHANGE ONE THING. PREDICT THE RESULT FIRST. WRITE THE
     PREDICTION DOWN.

   Predicting first is what converts an experiment into
   information. If the result matches, you have confirmed a
   model. IF IT DOES NOT, YOU HAVE LEARNED SOMETHING FAR
   MORE VALUABLE: your mental model of the system is wrong,
   and you now know approximately where.

   THE FOUR QUESTIONS THAT START EVERY INVESTIGATION:

     WHAT did you expect to happen?
     WHAT actually happened?
     WHAT is the smallest difference between the working
       case and the broken one?
     WHEN did it last work?

   That fourth one is often the whole answer. Something
   changed.

Reproduce it first

/* A BUG YOU CANNOT REPRODUCE IS A BUG YOU CANNOT FIX AND -
   more importantly - CANNOT PROVE YOU FIXED.

   THE PROGRESSION:

   1. REPRODUCE IT AT ALL.
      Even at 1 in 1000. Automate the attempt and let it run
      overnight.

   2. REPRODUCE IT RELIABLY.
      Find the conditions. Then make a script.

   3. MINIMISE THE REPRODUCTION.
      Cut everything that is not required. Halve the input.
      Remove modules. Delete configuration.
      Each cut either preserves the bug (keep cutting) or
      kills it (you just found something relevant).

   4. AUTOMATE IT.
      A one-command reproduction is worth an hour of setup,
      because you will run it fifty times.

/* --- WHEN IT IS INTERMITTENT --- */
    INCREASE THE RATE, don't chase it:
      · run it in a loop, thousands of times
      · add STRESS: other load, memory pressure, thermal
      · vary TIMING: add random delays, change thread
        priorities, run on fewer cores
      · run on the SLOWEST and the FASTEST hardware you
        have - races often appear only at one extreme
      · disable optimisations, or ENABLE them - both change
        timing and both find different bugs
      · use the sanitisers and analysis tools that turn
        latent problems into deterministic failures
        (chapter 04 for Linux, 05 for Windows)

    AND CAPTURE STATE WHEN IT HAPPENS. If it takes six
    hours to reproduce, you cannot afford to catch it and
    learn nothing. Set up the logging, the core dump, the
    trace buffer BEFORE the long run.

/* --- WHEN IT ONLY HAPPENS IN THE FIELD --- */
    · what is different? hardware revision, temperature,
      supply, EMI, network, uptime, data volume, locale
    · get the LOGS and the CONFIGURATION
    · ask what the user was actually doing, not what they
      think they were doing
    · and consider whether your development environment is
      hiding it: a debugger attached changes timing, a
      development build has different optimisation, a bench
      supply is cleaner than a battery.               */

Bisection

/* THE MOST POWERFUL DEBUGGING TECHNIQUE, IN ANY DIMENSION.
   Halve the search space repeatedly: 1000 candidates becomes
   10 tests.                                               */

/* --- BISECT IN TIME: git bisect --- */
    git bisect start
    git bisect bad                # current commit fails
    git bisect good v1.2.0        # this one worked
    # git checks out the midpoint; test and mark it
    git bisect good     # or: git bisect bad
    # ... repeat ~log2(n) times
    git bisect reset

    AUTOMATED, which is how you should do it:
      git bisect run ./test.sh
      # exit 0 = good, 1 = bad, 125 = skip (cannot build)

    10,000 commits -> 14 tests. If your test takes a minute,
    that is a quarter of an hour to find the exact commit
    that introduced a bug, unattended.

/* --- BISECT IN SPACE: the code --- */
    Comment out half the initialisation. Still broken?
    The cause is in the other half.
    Crude, and extremely effective.

/* --- BISECT IN CONFIGURATION --- */
    A working config and a broken one that differ in forty
    settings: change twenty, test, then ten. Six tests.

/* --- BISECT IN DATA --- */
    A parser crashes on a 10 MB file. Halve it. Still
    crashes? Halve again. You will have a 40-byte
    reproduction in twenty steps.
    (And this is exactly what a fuzzer's test-case minimiser
    does automatically.)

/* --- BISECT IN HARDWARE --- */
    Two boards, one works. Swap the module. Swap the cable.
    Swap the power supply. Swap the SD card. Each swap
    halves the space.

/* --- BISECT ACROSS THE STACK --- */
    Is the problem above or below this layer? Instrument the
    boundary. Application, library, syscall, driver,
    hardware register, bus, device.

    THE SINGLE MOST USEFUL QUESTION IN EMBEDDED DEBUGGING:

      DID THE BYTES ACTUALLY GO OUT ON THE WIRE?

    Put a logic analyser or a scope on it and find out.
    Half of all "the driver is broken" investigations end
    at "the pin was never configured as an output" or "the
    device NAKed and nobody checked".                     */
Read the error message

Actually read it. All of it. Then read the line before it, and the line after. An enormous fraction of debugging time is spent on problems whose exact cause, file and line number were printed on screen and skimmed past. The same applies to the compiler's first error — the ones after it are usually consequences, and fixing the first often fixes forty.

Question the assumptions

/* WHEN YOU ARE GENUINELY STUCK, THE BUG IS IN SOMETHING YOU
   ARE CERTAIN ABOUT. That is definitionally where it must
   be - you have already checked everything you doubt.

   SO GO AND VERIFY THE CERTAINTIES:

   "The code I'm editing is the code that's running."
     -> Is it? Check the timestamp. Check the build actually
        succeeded. Check you flashed the right image to the
        right board. Add a deliberate crash and confirm it
        crashes. THIS IS NOT A JOKE - it is one of the most
        common causes of an impossible bug.

   "The compiler generated what I wrote."
     -> Read the disassembly (chapter 03, and the compilers
        track). Undefined behaviour licenses the optimiser
        to do surprising things, and a `volatile` you forgot
        means your register read was hoisted out of the loop.

   "This function returns what I think."
     -> Check the return value. Every time. The number of
        bugs that are an unchecked error code is
        extraordinary.

   "The hardware works."
     -> Usually true, and not always. Check the supply rail
        under load. Check the crystal is oscillating. Check
        the reset line. Check the part number matches the
        datasheet you are reading. Check the errata sheet -
        vendors publish them because the silicon has bugs.

   "The data is what I expect."
     -> Print it. In hex. With its length. Endianness,
        alignment, sign extension, off-by-one, and a
        stray 0x0D from a Windows line ending have all
        cost people days.

   "The clock is configured."
     -> A peripheral with no clock reads back zeros or
        retains defaults, and writes silently do nothing.
        A gated clock is the single most common cause of
        "the peripheral doesn't respond".

   "The other side is doing its part."
     -> Instrument the boundary and confirm.

/* AND THE META-ASSUMPTION:

     "This cannot possibly be related."

   Note it anyway. Coincidences in a deterministic machine
   are usually causation you have not traced yet.       */

Tactics that work

/* --- RUBBER DUCK DEBUGGING --- */
    Explain the problem, out loud, in complete sentences, to
    something that cannot help you. The bug frequently
    surfaces mid-sentence, because articulating forces you
    to state assumptions you had been skipping over.
    THIS SOUNDS SILLY AND IT WORKS.

/* --- WRITE IT DOWN --- */
    A running log of what you tried, what you predicted, and
    what happened. Three benefits: you stop repeating
    experiments, you can hand it to someone else, and the
    act of writing forces precision.

/* --- CHANGE ONE THING --- */
    Two changes at once and a fixed bug tells you nothing.

/* --- REVERT TO A KNOWN-GOOD STATE --- */
    When you have made twenty changes and it is worse than
    when you started: revert everything, reproduce, and
    start again with what you have learned. Sunk cost is
    not a debugging strategy.

/* --- TAKE A BREAK --- */
    Genuinely effective, for a real reason: you get stuck in
    a search path and stop generating new hypotheses. A
    walk, or sleep, resets it. Many hard bugs are solved in
    the first ten minutes of the next morning.

/* --- ASK SOMEONE --- */
    Not because they know more, but because explaining it
    (see rubber duck) plus one outside assumption is often
    all it takes. Set a time limit on solo effort - two
    hours, say - and then ask.

/* --- FIND THE SIMPLEST THING THAT FAILS --- */
    Strip until it works, then add back until it breaks.
    The last thing you added is where to look.

/* --- AND WHEN YOU FIX IT --- */
    1. UNDERSTAND WHY THE FIX WORKS. A change that makes the
       symptom disappear for a reason you cannot state is
       not a fix - it is a timing change that will come
       back.
    2. WRITE A TEST that fails without it.
    3. LOOK FOR THE SAME BUG ELSEWHERE. Bugs come in
       families; the same mistake is usually in three other
       places, made by the same person on the same
       afternoon.
    4. ASK WHY IT WAS POSSIBLE. Could a type, an assertion,
       a lint rule, or an API change make this class of bug
       unrepresentable? That question is worth more than the
       fix.
    5. WRITE IT DOWN somewhere the next person will find
       it.                                               */

How it shows up

SymptomWhat it usually means
"It works on my machine"An environment difference — enumerate them
"It's random"It is not. Uninitialised memory, a race, or an input you have not identified
Adding a printf makes it go awayA race, or a timing-dependent bug — a heisenbug
Works in debug, fails in releaseUndefined behaviour, uninitialised memory, or a missing volatile
Fails only under the debuggerTiming, or a breakpoint changing interrupt latency
Fixed itself after a rebuildIt did not. A stale object file, or the bug moved
Impossible state observedMemory corruption, a stack overflow, or the wrong binary is running
Only fails after hoursA leak, a counter wrap, or fragmentation
Only fails on one unitHardware, or a per-unit configuration or calibration value
Only fails when cold or hotTiming margin, crystal drift, or a marginal supply
Peripheral reads back all zerosClock not enabled
