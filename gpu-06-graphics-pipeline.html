The graphics pipeline, stage by stage

Triangles in, pixels out. Every graphics API is a way of configuring the same fixed sequence of stages, some programmable and some not — and knowing which is which tells you exactly what you can and cannot change.

The pipeline

   [P] = programmable    [F] = fixed function, configurable

   INPUT ASSEMBLER                                        [F]
     reads vertex + index buffers, assembles primitives.
     Decides what a "triangle" is: list, strip, or fan.
        |  vertices
        v
   VERTEX SHADER                                          [P]
     runs ONCE PER VERTEX. Transforms object space -> clip
     space. Must output SV_Position. Whatever else you emit is
     interpolated for the pixel shader.
        |
        v
   [ HULL / TESSELLATOR / DOMAIN ]              [P][F][P]
     optional. Subdivide patches into more triangles on the
     GPU. Used for terrain and smooth surfaces; less popular
     now that mesh shaders exist.
        |
   [ GEOMETRY SHADER ]                                    [P]
     optional, runs per PRIMITIVE, can emit 0..N primitives.
     Famously slow on most hardware - it serialises. Avoid.
        |
        v
   CLIPPING + PERSPECTIVE DIVIDE + VIEWPORT                [F]
     clip to the frustum, divide xyz by w, map to pixels.
        |
        v
   RASTERISER                                             [F]
     triangles -> fragments. Also does back-face culling and
     the early-Z test. Generates 2x2 QUADS, always
     (chapter 8).
        |  fragments
        v
   PIXEL / FRAGMENT SHADER                                [P]
     runs ONCE PER FRAGMENT. Computes a colour. This is where
     nearly all your shading cost lives.
        |
        v
   OUTPUT MERGER                                          [F]
     depth test, stencil test, blending, write to the render
     target. Blending is fixed-function because it must be
     ORDER-DEPENDENT and atomic per pixel.
        |
        v
   RENDER TARGET

   NOTE WHAT IS FIXED: rasterisation, clipping, depth test and
   blending. These are fixed because they are done billions of
   times per frame and because they need guarantees
   (ordering, atomicity) that general code cannot give
   cheaply. You configure them; you do not write them.
The two counts that decide your frame time

Vertex shaders run per vertex — perhaps a million per frame. Pixel shaders run per fragment — at 4K with any overdraw, tens of millions. A pixel shader is typically 10–100× more invocations than the vertex shader, which is why "move work to the vertex shader" is the oldest optimisation in real-time graphics, and why overdraw matters so much.

The coordinate spaces

/* A vertex is transformed through five spaces. Every graphics
   bug that renders "nothing at all" is a matrix in the wrong
   place in this chain.                                     */

  OBJECT / MODEL SPACE    the mesh as the artist made it,
                          origin at its own centre
        | x World matrix          (position, rotate, scale)
        v
  WORLD SPACE             everything in one shared frame
        | x View matrix           (the inverse of the camera's
        v                          transform)
  VIEW / CAMERA SPACE     camera at the origin, looking down
                          -Z (GL) or +Z (D3D)
        | x Projection matrix     (frustum -> a cube)
        v
  CLIP SPACE              homogeneous. -w <= x,y <= w and
                          0 <= z <= w (D3D) or -w <= z <= w (GL)
        | divide by w             (the PERSPECTIVE DIVIDE)
        v
  NDC                     the canonical cube
        | viewport transform
        v
  SCREEN SPACE            pixels, plus a depth in [0,1]

/* The vertex shader's job is object -> clip. Everything after
   is fixed function.                                        */

float4 VSMain(float3 pos : POSITION) : SV_Position
{
        float4 world = mul(float4(pos, 1.0), World);
        float4 view  = mul(world, View);
        return mul(view, Projection);          /* CLIP space   */
        /* Do NOT divide by w yourself - the hardware does it,
           and it also uses w for perspective-correct
           interpolation.                                     */
}

/* D3D vs GL DIFFERENCES that cause upside-down or clipped
   output when porting:
     clip-space Z range   D3D [0,1]      GL [-1,1]
     texture origin       D3D top-left   GL bottom-left
     matrix convention    D3D row-major, row-vector by default
                          GL  column-major, column-vector
   Vulkan follows D3D on Z and GL on Y, which catches
   everyone exactly once.                                    */

Perspective-correct interpolation

   The rasteriser interpolates your vertex outputs across the
   triangle. Doing that LINEARLY IN SCREEN SPACE is wrong for
   anything in perspective.

   A wall receding into the distance, with a checker texture:

     LINEAR interpolation of u:
       the checks stay evenly spaced -> the wall looks like
       it is BENDING. This is the classic PlayStation 1 look;
       that hardware had no perspective correction.

     PERSPECTIVE-CORRECT:
       interpolate u/w and 1/w linearly, then divide:
             u = (u/w interpolated) / (1/w interpolated)
       checks compress with distance. Correct.

   The hardware does this for you, per attribute, which is
   why the vertex shader must output w and must NOT divide.

   YOU CAN TURN IT OFF, and occasionally should:

     noperspective float2 screenUV : TEXCOORD0;
       for screen-space effects, where you want the value to
       vary linearly in pixels.

     nointerpolation uint materialID : TEXCOORD1;
       "flat" - takes the value from the provoking vertex.
       MANDATORY for integers: interpolating an ID gives you
       fractional nonsense.

Hidden surface removal

/* Drawing a pixel you cannot see costs the same as one you
   can. Four mechanisms remove that work, at different
   stages.                                                  */

/* 1. BACK-FACE CULLING - rasteriser, free.
      Discards triangles facing away, based on winding order.
      Removes ~50% of a closed mesh for nothing.           */
        rasterizerDesc.CullMode = D3D12_CULL_MODE_BACK;
        rasterizerDesc.FrontCounterClockwise = FALSE;
/* If your model renders inside-out, this is the setting. */

/* 2. FRUSTUM CULLING - your code, on the CPU or in a compute
      shader. Do not submit what is off-screen.            */

/* 3. EARLY-Z - rasteriser, before the pixel shader.
      Tests depth BEFORE shading. The single biggest saving
      in a typical scene.

      IT IS DISABLED, silently, if the pixel shader:
        * writes SV_Depth
        * uses `discard` / `clip()`
        * writes to a UAV
      because in each case the hardware cannot know the final
      depth or whether the pixel survives before running the
      shader.

      So a single alpha-test material can cost far more than
      its pixel count suggests: it forces late-Z for those
      draws. If you must discard, mark it:                 */
        [earlydepthstencil]           /* HLSL: "test anyway,
        void PSMain(...) { ... }         I promise it is safe" */

/* 4. HIERARCHICAL-Z - a low-resolution depth pyramid, so
      whole tiles can be rejected at once. Automatic, but it
      is INVALIDATED by depth writes from the pixel shader
      and by changing the depth comparison direction
      mid-frame. Pick one direction and keep it.           */

/* THE STANDARD CONSEQUENCE: sort opaque geometry FRONT TO
   BACK. Near objects fill the depth buffer first, so far
   ones fail early-Z and never shade. Then draw transparent
   geometry BACK TO FRONT, because blending is order
   dependent - and that is why transparency is expensive and
   why it cannot use early-Z at all.                       */
Overdraw is measured in shaded fragments, not pixels

A 4K frame is 8.3 million pixels. With an average overdraw of 3 — perfectly normal for a scene with foliage, particles and UI — the pixel shader runs 25 million times. Halving the shader cost saves less than eliminating one layer of overdraw. Every profiler has an overdraw visualisation; it is usually the first place to look when a frame is slow and the geometry count is modest.

Mesh shaders: the pipeline being replaced

   The front of the pipeline is a 1998 design: fixed input
   assembly, one vertex in and one vertex out, optional
   tessellation stages nobody enjoys.

   MESH SHADERS (DX12 Ultimate, Vulkan, Metal) replace
   IA + VS + hull/domain/GS with two compute-like stages:

     AMPLIFICATION / TASK SHADER
       runs first, decides HOW MANY mesh shader groups to
       launch. This is where you do GPU-side culling.
        |
     MESH SHADER
       a workgroup cooperatively produces a MESHLET - a small
       batch of vertices and primitives (typically up to 64
       vertices, 126 triangles) - and writes them straight
       into the rasteriser.

   WHY IT IS BETTER
     * you control the data layout; no fixed input assembler
     * culling per meshlet, on the GPU, before any vertex work
     * no serialisation bottleneck like the geometry shader
     * one workgroup can share vertex work across triangles

   WHY IT IS NOT UNIVERSAL YET
     * needs newer hardware (Turing+, RDNA2+)
     * the asset pipeline must build meshlets offline
     * the classic path still works fine for most content

   Worth knowing exists; the rest of this track uses the
   classic pipeline because that is what you will meet.

How it shows up

SymptomCause
Nothing renders at allMatrix order wrong, or the object is behind the camera or outside the frustum
Model appears inside-outWinding order versus cull mode
Textures swim or bend on receding surfacesInterpolation not perspective-correct — usually because w was divided too early
Image is upside down after a portD3D/GL texture origin or clip-space Y

Transparent objects render in the wrong orderBlending is order-dependent; sort back to front
Geometry shader is unexpectedly slowIt serialises on most hardware — use instancing or mesh shaders
