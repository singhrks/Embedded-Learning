What machine learning is

Fitting a function to data instead of writing it. That is the whole idea — and knowing when not to do it is as valuable as knowing how.

The shift

Coming from systems programming, the hardest thing about machine learning is not the mathematics; it is that the contract between you and the program is different. Naming that difference explicitly is worth doing once.

   TRADITIONAL PROGRAMMING
        rules + data  ->  [program]  ->  answers

   MACHINE LEARNING
        data + answers -> [training] ->  RULES
        then:  new data + rules      ->  answers

   YOU SPECIFY WHAT, NOT HOW.

   THE FORMAL SETUP:
     · a HYPOTHESIS SPACE - the set of functions the model
       can represent, determined by its architecture and
       parameters
     · a LOSS FUNCTION - how wrong a given function is on
       the data (chapters 09, 10)
     · an OPTIMISER - a search procedure over the hypothesis
       space (chapter 11)

   TRAINING = SEARCHING FOR THE FUNCTION IN THAT SPACE THAT
   MINIMISES THE LOSS.

   THE THREE CLASSICAL SETTINGS:

   SUPERVISED       inputs WITH labels.
                    classification (discrete labels),
                    regression (continuous).
                    The overwhelming majority of deployed
                    systems.

   UNSUPERVISED     inputs, no labels. Clustering,
                    dimensionality reduction (chapter 05),
                    density estimation.

   REINFORCEMENT    an agent acting in an environment,
                    receiving rewards. Games, robotics, and
                    RLHF (chapter 24).

   AND THE ONE THAT MATTERS MOST NOW:

   SELF-SUPERVISED  labels DERIVED FROM THE DATA ITSELF.
                    "Predict the next token" needs no
                    annotation - the next token IS the
                    label, and every document is millions of
                    training examples.

                    THIS IS WHY LARGE LANGUAGE MODELS WERE
                    POSSIBLE. Labelled data is scarce and
                    expensive; raw text is essentially free
                    and effectively unlimited. The entire
                    scaling story (chapter 23) rests on
                    removing the labelling bottleneck.

Generalisation: the actual problem

Fitting the data you have is easy and almost worthless. The entire discipline is about the gap between that and performing on data you have never seen.

/* MEMORISING THE TRAINING DATA IS TRIVIAL. A lookup table
   achieves zero training error. IT IS ALSO USELESS.

   THE GOAL IS PERFORMANCE ON DATA YOU HAVE NEVER SEEN.

/* --- THE SPLIT, and it is non-negotiable --- */
    TRAIN        60-80%   the model fits this
    VALIDATION   10-20%   you choose hyperparameters using
                          this
    TEST         10-20%   YOU LOOK AT THIS ONCE, AT THE END

    IF YOU TUNE ON THE TEST SET, YOU HAVE NO TEST SET. Each
    decision you make based on test performance leaks a
    little information, and after fifty experiments your
    test score is an optimistic fiction. This is the most
    common methodological failure in applied work, and it is
    invisible until deployment.

/* --- UNDERFITTING AND OVERFITTING --- */

    UNDERFIT       high train error, high test error.
                   The model is too simple, or undertrained.
    GOOD FIT       low train error, low test error.
    OVERFIT        LOW train error, HIGH test error.
                   The model memorised noise.

      error
        |  \                    /   test
        |   \                  /
        |    \        ________/
        |     \______/
        |      \_______________ train
        +---------------------------> model capacity
                    ^
                  the sweet spot

/* --- BIAS AND VARIANCE --- */
    BIAS       error from wrong assumptions. A linear model
               fitting a curve. -> UNDERFITTING.
    VARIANCE   sensitivity to the particular training sample.
               -> OVERFITTING.

    Classically these trade off. IN DEEP LEARNING THEY
    LARGELY DO NOT, and this is worth knowing because it
    contradicts the textbooks:

/* --- DOUBLE DESCENT --- */
      test
      error |    /\
            |   /  \        <- classical U-curve
            |  /    \
            | /      \    /-------____
            |/        \__/            ---____
            +-------------------------------------->
                       ^         model capacity
                  INTERPOLATION THRESHOLD
                  (enough capacity to fit the training data
                   exactly)

    Past the point where a model can fit the training data
    perfectly, test error DROPS AGAIN - often below the
    classical minimum. Bigger models generalise BETTER, not
    worse, which is the opposite of what classical
    statistical learning theory predicts.

    NOBODY HAS A COMPLETE EXPLANATION. The leading intuition
    involves implicit regularisation from SGD and the
    flat-minima argument (chapter 11). This is one of
    several places where the practice ran ahead of the
    theory and the theory has not caught up.

/* --- WHAT ACTUALLY CONTROLS OVERFITTING (chapter 15) --- */
      MORE DATA           the most effective by a wide
                          margin
      data AUGMENTATION   more data, cheaply
      REGULARISATION      weight decay, dropout
      EARLY STOPPING      stop when validation loss rises
      a SMALLER model     the classical answer, and often
                          the wrong one now                */

Measuring it properly

Accuracy is the metric everyone reaches for and it is misleading in exactly the situations that matter most. These are the alternatives and when each one is the honest choice.

/* ACCURACY IS USUALLY THE WRONG METRIC, for the reason in
   chapter 09: with a 0.1% positive rate, a model that always
   says "no" is 99.9% accurate and worthless.             */

    THE CONFUSION MATRIX:
                      PREDICTED
                    pos       neg
        ACTUAL pos   TP        FN     (missed)
               neg   FP        TN
                    (false alarm)

    PRECISION = TP / (TP + FP)
        "Of the ones I flagged, how many were real?"
        Matters when a FALSE ALARM IS EXPENSIVE - shutting
        down a production line, blocking a legitimate
        transaction.

    RECALL    = TP / (TP + FN)
        "Of the real ones, how many did I catch?"
        Matters when a MISS IS EXPENSIVE - a missed fault, a
        missed diagnosis.

    F1 = 2 * P * R / (P + R)      the harmonic mean

    ROC-AUC       ranking quality across all thresholds
    PR-AUC        BETTER FOR IMBALANCED DATA than ROC-AUC,
                  which looks deceptively good when
                  negatives dominate

/* THE PRECISION-RECALL TRADE-OFF IS A THRESHOLD CHOICE, not
   a model property. One model gives a whole curve; where you
   sit on it is a PRODUCT decision, and it should be made
   with whoever owns the consequences.

/* --- REGRESSION METRICS --- */
    MSE / RMSE    penalises large errors quadratically;
                  sensitive to outliers (chapter 09)
    MAE           linear penalty, robust
    R^2           fraction of variance explained
    MAPE          percentage error - and it EXPLODES when
                  true values are near zero

/* --- CROSS-VALIDATION, when data is scarce --- */
    Split into k folds; train k times, each time holding out
    one fold. Average the results.
    k = 5 or 10 is standard.

    AND THE TRAPS:
      · TIME SERIES: never shuffle. Use forward-chaining
        splits, or you train on the future and predict the
        past.
      · GROUPED DATA: if the same patient, device or user
        appears in both train and test, you are measuring
        memorisation. Split by GROUP.
      · IMBALANCED CLASSES: stratify, so each fold has the
        same class ratio.

/* --- DATA LEAKAGE: the failure that ruins projects --- */
    Information in the training data that will not exist at
    prediction time. The model learns it, scores brilliantly
    in evaluation, and fails completely in production.

    REAL EXAMPLES:
      · a feature computed AFTER the outcome (an "account
        closed" flag when predicting churn)
      · normalising using statistics from the FULL dataset
        before splitting - the test set's mean has leaked
        into training
      · duplicate records across the train/test boundary
      · an ID that correlates with the label because of how
        the data was collected
      · IN LLM EVALUATION: the benchmark's test set is in
        the pretraining corpus. This is now a serious and
        widespread measurement problem, and it is why
        contamination checks and held-out private evals
        matter.

    THE SMELL TEST: IF YOUR RESULTS LOOK TOO GOOD, THEY ARE.
    Go looking for the leak; you will usually find it.    */
When not to use machine learning 
· THE RULES ARE KNOWN. Write them. A deterministic
  algorithm is faster, testable, explainable, and does
  not degrade silently.
· YOU LACK DATA. A few hundred examples rarely
  supports a learned model.
· ERRORS ARE UNACCEPTABLE. ML systems are wrong
  sometimes, by construction.
· YOU NEED AN EXPLANATION. Regulated decisions often
  require a reason, not a probability.
· THE DISTRIBUTION SHIFTS CONSTANTLY. A model trained
  on last month's data may be worse than a simple
  heuristic on this month's.
· A SIMPLE BASELINE ALREADY WORKS. Threshold, moving
  average, lookup table, linear model.

Always build the trivial baseline first — majority class, last value, a hand-tuned threshold. If your model does not clearly beat it, it does not justify its complexity, its latency, or its maintenance cost. This is the single most useful habit in applied machine learning.

The real workflow

Very little of a real machine-learning project is modelling, which is a genuine surprise the first time. This is where the time actually goes.

/* THE PROPORTIONS SURPRISE PEOPLE:

     define the problem and the metric      5%
     get and clean the data                40%     <<<
     feature engineering / preprocessing   20%
     model selection and training          10%
     evaluation and error analysis         15%
     deployment and monitoring             10%

   THE MODEL IS THE SMALL PART. Anyone telling you
   otherwise has not shipped one.

/* --- 1. DEFINE THE PROBLEM AND THE METRIC FIRST --- */
    What decision does this output feed?
    What does a false positive cost? A false negative?
    What performance would make this worth deploying?
    AGREE THE METRIC BEFORE YOU START, or you will pick the
    metric that flatters the result you got.

/* --- 2. DATA --- */
    Is it representative of production?
    How is it labelled, and how good are the labels? (Label
      noise sets a ceiling on achievable accuracy.)
    Is it balanced? Biased? Does it encode a historical
      decision you should not replicate?
    HOW MUCH IS THERE? This determines what is possible more
      than any architectural choice.

/* --- 3. BASELINE --- */
    The trivial one. Then a simple model - logistic
    regression, gradient-boosted trees. FOR TABULAR DATA,
    GRADIENT BOOSTING (XGBoost, LightGBM) STILL BEATS NEURAL
    NETWORKS MOST OF THE TIME. Deep learning wins on
    perceptual and sequential data - images, audio, text -
    not on spreadsheets.

/* --- 4. ITERATE ON ERRORS, NOT ON ARCHITECTURE --- */
    LOOK AT THE MISTAKES. Sort by loss, read the worst
    hundred examples by hand. You will find mislabelled
    data, a preprocessing bug, or a systematic gap - and any
    of those is worth more than a hyperparameter sweep.

    This is the highest-value hour in any ML project and it
    is the one most often skipped.

/* --- 5. DEPLOY AND MONITOR --- */
    LATENCY, memory, throughput - the embedded constraints
      (chapter 27)
    INPUT DISTRIBUTION MONITORING: is production data
      drifting from training data?
    OUTPUT MONITORING: is the prediction distribution
      changing?
    A FALLBACK PATH for when the model is unavailable or
      obviously wrong
    AND A RETRAINING PLAN, because the world moves.

    MODELS DEGRADE SILENTLY. Unlike a crashed service,
    a model that has become wrong keeps returning confident
    answers. YOU WILL NOT NOTICE WITHOUT MONITORING.      */

How it shows up

SymptomCause
99% accuracy, useless in productionImbalanced classes — use precision and recall
Excellent evaluation, poor deploymentData leakage, or a train/production distribution gap
Test score drifts up over a projectTuning on the test set — it is no longer held out
Perfect training loss, poor validationOverfitting — more data or more regularisation
Both losses highUnderfitting — more capacity or longer training
Time-series model looks perfectShuffled split — the model saw the future
Great cross-validation, bad on new usersSame group in train and test — split by group
Benchmark scores far above real-world qualityTest-set contamination in the training corpus
Bigger model generalises better than theory predictsDouble descent — expected past the interpolation threshold
Model quality decays over monthsDistribution drift with no monitoring
Neural network loses to gradient boostingTabular data — that is the normal result
