Shared memory across the boundary

Every byte that crosses between worlds crosses through non-secure shared memory, because the normal world cannot be given a pointer into secure memory and the secure world will not trust a pointer the normal world chose. How that buffer is allocated, registered and validated is the security-critical seam of the whole design.

Why it must be non-secure

The two worlds must exchange data, and they cannot do so through secure memory. The shared region is therefore the one place untrusted input legitimately reaches trusted code — which makes it the most security-sensitive memory on the device.

   Consider the two alternatives and why both fail.

   1. The TA writes directly into normal-world memory at an
      address the client supplied.

      -> The client controls the address. It can name kernel
         memory, another process's memory, a device register,
         or OP-TEE's own memory. The TA, running with secure
         privilege, would perform the write.
      -> This is the single most dangerous class of TEE bug,
         and it is why every address must be VALIDATED, not
         merely used.

   2. The client reads from secure memory the TA allocated.

      -> Impossible. The TZASC refuses (chapter 6).

   So: a third region, non-secure, agreed by both sides.

     +-------------------+
     |  SHM              |  NS=1, so:
     |  non-secure       |    normal world: read/write
     |  shared memory    |    secure world: read/write
     +-------------------+

   The secure world can read and write non-secure memory - it
   is more privileged, not less. The restriction is one-way.

   And therefore: ANYTHING IN SHM IS ATTACKER-CONTROLLED. The
   client can change it at any moment, including between the
   TA's validation of a value and the TA's use of it.
The double-fetch rule

Shared memory can change under you. A TA that reads a length field, checks it, and then reads it again to use it has a time-of-check-to-time-of-use bug: the client can change the value in between, from another thread, and defeat the check. Copy everything you will act on into secure memory first, then validate the copy, then use only the copy. This is elaborated in chapter 20 and it is the rule that matters most in this entire track.

Two kinds of shared memory

Two mechanisms for sharing, differing in who allocates and how long the sharing lasts. The choice affects both performance and what the trusted application must validate.

Three ways a client provides a buffer

From the application side, sharing memory is a few API calls — and the details of who owns the buffer and when it may be touched matter more than the call signatures.

/* 1. ALLOCATE - let the TEE choose the memory. Simplest,
      always works, always contiguous.                      */

    TEEC_SharedMemory shm = {
            .size  = 4096,
            .flags = TEEC_MEM_INPUT | TEEC_MEM_OUTPUT,
    };
    res = TEEC_AllocateSharedMemory(&ctx, &shm);
    memcpy(shm.buffer, data, len);

    op.paramTypes = TEEC_PARAM_TYPES(TEEC_MEMREF_WHOLE,
                                     TEEC_NONE, TEEC_NONE,
                                     TEEC_NONE);
    op.params[0].memref.parent = &shm;
    /* ... invoke ... */
    TEEC_ReleaseSharedMemory(&shm);


/* 2. REGISTER - hand the TEE memory you already have. Avoids
      a copy; needs dynamic SHM.                            */

    void *mybuf = malloc(65536);          /* or mmap, or a
                                             dmabuf           */
    TEEC_SharedMemory shm = {
            .buffer = mybuf,
            .size   = 65536,
            .flags  = TEEC_MEM_INPUT,
    };
    res = TEEC_RegisterSharedMemory(&ctx, &shm);
    /* the kernel pins the pages and sends OP-TEE a page list */


/* 3. TEMPORARY - a pointer passed inline; libteec allocates,
      copies in, invokes, copies out, frees. Convenient and it
      COPIES TWICE.                                         */

    op.paramTypes = TEEC_PARAM_TYPES(TEEC_MEMREF_TEMP_INPUT,
                                     TEEC_MEMREF_TEMP_OUTPUT,
                                     TEEC_NONE, TEEC_NONE);
    op.params[0].tmpref.buffer = input;
    op.params[0].tmpref.size   = inlen;
    op.params[1].tmpref.buffer = output;
    op.params[1].tmpref.size   = sizeof output;

/* Use TEMP for small parameters and control messages. Use
   REGISTER for anything large or repeated - a 1 MB buffer
   copied twice per call, at 60 calls a second, is 120 MB/s of
   pure waste.                                              */

The parameter model

The parameter types the interface supports encode the direction and ownership of each buffer, which is what lets the framework check some of the rules for you.

/* Four slots per invocation. Each is a VALUE (two 32-bit
   numbers) or a MEMREF (a buffer), each with a direction.  */

    TEEC_NONE
    TEEC_VALUE_INPUT           a, b: two uint32_t in
    TEEC_VALUE_OUTPUT          two uint32_t out
    TEEC_VALUE_INOUT
    TEEC_MEMREF_TEMP_INPUT     an inline buffer
    TEEC_MEMREF_TEMP_OUTPUT
    TEEC_MEMREF_TEMP_INOUT
    TEEC_MEMREF_WHOLE          all of a registered shm
    TEEC_MEMREF_PARTIAL_INPUT  part of a registered shm
    TEEC_MEMREF_PARTIAL_OUTPUT
    TEEC_MEMREF_PARTIAL_INOUT

    op.paramTypes = TEEC_PARAM_TYPES(TEEC_VALUE_INPUT,
                                     TEEC_MEMREF_TEMP_OUTPUT,
                                     TEEC_NONE,
                                     TEEC_NONE);

/* On the TA side the same four slots arrive, and the TA MUST
   check that it got what it expected: */

TEE_Result TA_InvokeCommandEntryPoint(void *sess, uint32_t cmd,
                                      uint32_t ptypes,
                                      TEE_Param params[4])
{
        uint32_t exp = TEE_PARAM_TYPES(TEE_PARAM_TYPE_VALUE_INPUT,
                                       TEE_PARAM_TYPE_MEMREF_OUTPUT,
                                       TEE_PARAM_TYPE_NONE,
                                       TEE_PARAM_TYPE_NONE);
        if (ptypes != exp)
                return TEE_ERROR_BAD_PARAMETERS;   /* MANDATORY */
        ...
}

/* Skip that check and a client can pass a VALUE where you
   expect a MEMREF. You then read params[1].memref.buffer -
   which is now an arbitrary 64-bit integer the attacker chose,
   dereferenced by code running with secure privilege.

   This is the most common OP-TEE TA vulnerability class, and
   it is prevented by four lines.                            */

What the TA must do with a buffer

On the trusted side, every shared buffer is attacker-controlled: its contents, its size, and whether it changes while you are reading it. The validation rules follow from that.

/* The four rules, in order of importance.                   */

/* RULE 1: check the parameter types. Above. */

/* RULE 2: check that the memory is really where it claims. */

    res = TEE_CheckMemoryAccessRights(
                TEE_MEMORY_ACCESS_READ |
                TEE_MEMORY_ACCESS_ANY_OWNER,
                params[1].memref.buffer,
                params[1].memref.size);
    if (res != TEE_SUCCESS)
            return res;

/* This asks OP-TEE: is this pointer, for this length, actually
   a buffer this session was given? It catches a client that
   passed a length larger than the buffer it registered.    */

/* RULE 3: copy before you use. */

    if (params[0].memref.size > MAX_INPUT)
            return TEE_ERROR_SHORT_BUFFER;

    uint8_t local[MAX_INPUT];
    /* ONE read of the shared memory. */
    memcpy(local, params[0].memref.buffer, params[0].memref.size);

    /* validate the COPY, act on the COPY */
    if (!looks_sane(local, params[0].memref.size))
            return TEE_ERROR_BAD_PARAMETERS;
    do_work(local, params[0].memref.size);

/* RULE 4: write output once, at the end, and only on success. */

    if (params[1].memref.size < needed) {
            params[1].memref.size = needed;   /* tell them how
                                                 much          */
            return TEE_ERROR_SHORT_BUFFER;
    }
    memcpy(params[1].memref.buffer, result, needed);
    params[1].memref.size = needed;
    return TEE_SUCCESS;

/* Writing partial results into the output buffer as you go
   leaks intermediate state to the client on the error path -
   and for a crypto TA, intermediate state is often the
   secret.                                                    */
The short-buffer protocol

GlobalPlatform's convention: if the output buffer is too small, set memref.size to the size you need and return TEE_ERROR_SHORT_BUFFER. The client sees the required size, reallocates and retries. Clients rely on this, so implement it — and note that it means writing to memref.size even on the error path, which is the one output write that is allowed before success.

Cache and coherency

Two worlds with different cache attributes looking at the same memory raises exactly the coherency questions the ARM track covered — and getting them wrong produces data that is correct on one side only.

/* Shared memory is Normal, cacheable memory on both sides, and
   the interconnect is coherent on any SoC that runs OP-TEE. So
   ordinarily NO cache maintenance is required.

   Where it does bite:

   1. CFG_CORE_UNMAP_CORE_AT_EL0 / different mapping
      attributes on the two sides. If OP-TEE maps SHM
      non-cacheable and Linux maps it cacheable, you have a
      mismatched-attribute alias (virtualisation chapter 07) and
      the behaviour is architecturally unpredictable.

   2. A non-coherent DMA master reading the buffer. Then
      whoever set it up must clean/invalidate:
          TEE_CacheClean(buf, len);
          TEE_CacheInvalidate(buf, len);
          TEE_CacheFlush(buf, len);
      These are OP-TEE extensions, available only if
      CFG_CACHE_API=y - they are not standard GlobalPlatform.

   3. Suspend/resume, where a cache may be powered down with
      dirty lines.

   The normal case needs nothing. If you find yourself adding
   cache maintenance to make a bug go away, you probably have
   an attribute mismatch instead - fix that.               */
