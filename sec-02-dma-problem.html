Why DMA breaks memory protection

The MMU sits between a CPU core and the interconnect. A DMA engine does not go through a CPU core. Every isolation guarantee built out of page tables therefore has a hole in it, and closing that hole is what the SMMU exists to do.

The gap

Every protection mechanism discussed so far applies to the processor. A device performing DMA is not the processor, and by default it addresses memory with nothing checking it at all — which quietly invalidates the memory protection you thought you had.

   WITHOUT AN SMMU

   CPU                              DMA-capable device
    |                                     |
    v                                     |
   +-------+                              |
   |  MMU  |  translate + check           |  raw PHYSICAL
   +-------+                              |  addresses,
    |                                     |  NO checks
    v                                     v
   +----------------------------------------------------+
   |            interconnect  ->  DRAM                   |
   +----------------------------------------------------+

  Every CPU access is translated and permission-checked
  (ARM chapters 12-14). Every DEVICE access is not checked at
  all — it goes straight onto the bus.

  So a device programmed with address X reads or writes physical
  address X. Any X. Including kernel memory, including the secure
  world's memory, including the page tables themselves.
What this means concretely

An attacker who can program a DMA engine — which on most systems means an attacker who has compromised the kernel, or who can plug in a Thunderbolt device — can:

  • Read kernel memory, including disk encryption keys held in RAM.
  • Overwrite kernel code or the page tables, escalating from device access to full control.
  • Overwrite another VM's memory, escaping the hypervisor.
  • Do all of this with the CPU's MMU perfectly configured, because the MMU was never involved.

Real attack classes

These are not hypothetical. Each class below has been demonstrated against shipping hardware, and several are the reason the mitigations later in this track exist at all.

Four problems, one solution

The problem has four distinct forms depending on whether the device is malicious, buggy, compromised or merely misconfigured. They need different defences, and conflating them leads to protecting against the least likely one.

The SMMU is usually described as a security feature. It solves
FOUR distinct problems, and only one is security:

  1. ISOLATION (security)
       constrain a device to the memory it was given
       -> the whole of this chapter

  2. VIRTUALISATION
       a guest programs a device with GUEST-physical addresses.
       Without translation, the device uses them as HOST-physical
       and scribbles over the host or another guest.
       -> stage 2 makes device passthrough possible at all

  3. SCATTER-GATHER
       a device wanting one large contiguous buffer forces the OS
       to find contiguous PHYSICAL memory, which fragments and
       eventually fails (OS chapter 11).
       -> with translation, physically scattered pages appear
          contiguous to the device

  4. ADDRESS WIDTH
       a legacy 32-bit device cannot reach memory above 4 GB.
       Without translation you need slow BOUNCE BUFFERS: copy the
       data down below 4 GB, DMA, copy back.
       -> with translation, any physical page can be mapped into
          the device's reachable range

  Problems 3 and 4 are why IOMMUs existed long before anyone
  worried about DMA attacks. The security benefit came later,
  and is now the main reason they are mandatory.

Putting an MMU in front of the device

The answer is to put a translation and permission check in front of the device, exactly as the MMU sits in front of the processor. That is what an SMMU is, and the next four chapters are how it works.

   WITH AN SMMU

   CPU                              DMA-capable device
    |                                     |
    v                                     v
   +-------+                        +-----------+
   |  MMU  |                        |   SMMU    |
   +-------+                        +-----------+
    |   translate + check            |   translate + check,
    |                                |   BY STREAMID
    v                                v
   +----------------------------------------------------+
   |            interconnect  ->  DRAM                   |
   +----------------------------------------------------+

  Same idea, same descriptor format, same permission bits. The
  difference is that the SMMU serves MANY devices through one
  block, so it needs the transaction to say WHO is asking.

  That identifier is the STREAMID, and it is the subject of the
  next chapter.

  Terminology: ARM calls it the SMMU (System MMU). The generic
  term is IOMMU. Intel's is VT-d, AMD's is AMD-Vi, and they
  differ in programming model but not in concept.

Why the MMU alone is not enough

An SMMU is necessary and not sufficient. Several attack paths route around it entirely, and knowing which ones is what stops you from declaring the problem solved prematurely.

/* A natural question: why not just have the device use virtual
   addresses through the CPU's MMU?

   Three reasons it cannot work:

   1. WHICH page tables? The CPU's MMU uses TTBR0/TTBR1 for the
      CURRENTLY RUNNING process. A device operates asynchronously
      — the process that started the transfer may not be running,
      may have exited, or may be on another core.

   2. The MMU is INSIDE the core. Physically, a device's
      transactions do not pass through it. Routing them there
      would mean routing all DMA through a CPU, which defeats the
      point of DMA entirely.

   3. Devices need their own POLICY. A device should be confined
      to the buffers it was given — not to whatever the process
      that programmed it can see. Those are different sets.

   Hence a separate translation unit, on the device side of the
   interconnect, with its own tables and its own notion of
   identity.                                                */

A second, separate problem

Isolation and coherency are different issues

DMA creates two problems and they are often confused:

  • Isolation — the device can reach memory it should not. Solved by the SMMU.
  • Coherency — the device and the CPU disagree about the contents of memory it legitimately reached. Solved by cache maintenance or by hardware coherency (ARM 18, ARM 19).

An SMMU does not make DMA coherent, and cache maintenance does not make it isolated. A driver needs to get both right, which is exactly why the DMA API exists to handle them together (chapter 07).

Where the SMMU sits

Not every master on an SoC is behind an SMMU, and finding out which are is a per-chip investigation rather than an assumption. The ones that are not are your remaining exposure.

Not every master goes through an SMMU. This is a SoC
INTEGRATION decision, and it is the first thing to establish
about any platform:

   +------+  +------+  +------+  +------+  +------+
   | GPU  |  | NPU  |  | DMA  |  | PCIe |  | PMU  |
   +--+---+  +--+---+  +--+---+  +--+---+  |micro-|
      |         |         |         |      |cntlr |
   +--v---------v---------v---------v--+   +--+---+
   |            SMMU                   |      |
   +-----------------+-----------------+      | NO SMMU
                     |                        | at all
   +-----------------v------------------------v-------------+
   |                    interconnect                         |
   +---------------------------------------------------------+

  The power-management microcontroller, a sensor hub, or a
  debug/test port may have direct memory access with nothing in
  front of it. Those masters are outside the SMMU's protection
  entirely, and can only be constrained by an interconnect
  FIREWALL (chapters 17-20).

  So the layered design of chapter 01 is not theoretical: some
  masters are covered by layer 2, some only by layer 4, and you
  must know which is which for your SoC.
# what does Linux think is behind an IOMMU?
ls /sys/kernel/iommu_groups/
ls -l /sys/kernel/iommu_groups/*/devices/

# is a specific device translated?
ls /sys/bus/pci/devices/0000:01:00.0/iommu_group
ls /sys/bus/platform/devices/*/iommu_group

# a device with NO iommu_group symlink is NOT behind an SMMU
for d in /sys/bus/platform/devices/*; do
  [ -e "$d/iommu_group" ] || echo "no IOMMU: $(basename $d)"
done

IOMMU groups

Devices that cannot be isolated from each other must be treated as one unit for security purposes. That grouping is forced by the hardware topology rather than chosen, and it constrains what you can safely pass through to a guest.

The SMMU can only distinguish devices whose transactions carry
DIFFERENT StreamIDs. Sometimes it cannot.

  A PCIe bridge that does not support Access Control Services
  may allow peer-to-peer traffic between devices behind it —
  traffic that never reaches the SMMU at all. Two such devices
  can DMA to each other regardless of what the SMMU says.

  Linux therefore groups devices that CANNOT be isolated from
  each other into one IOMMU GROUP, and treats the group as the
  smallest unit of assignment:

     /sys/kernel/iommu_groups/12/devices/
         0000:01:00.0      <- a GPU
         0000:01:00.1      <- its audio function

  CONSEQUENCE: you cannot pass one device of a group to a VM and
  keep the other on the host. VFIO refuses, because doing so
  would be a false isolation guarantee.

  This is a very common source of "why can't I pass through my
  GPU" — the answer is usually that its group contains something
  else, and the fix is a different slot, ACS support, or (with
  full understanding of the risk) an ACS override.

Bypass: the most common misconfiguration

An SMMU that is not configured protects nothing

A device whose StreamID has no valid Stream Table Entry can be handled in two ways: abort every transaction, or bypass translation entirely. Bypass means the device operates exactly as though no SMMU existed.

Bypass is convenient during bring-up and catastrophic in production. Several real systems have shipped with it enabled because a device did not work otherwise and someone turned it on to unblock testing.

# Linux kernel command line options that matter here
iommu.passthrough=1              # ALL devices bypass — debug only
arm-smmu-v3.disable_bypass=1     # abort unmatched streams (default
                                 # since 4.20, and the correct setting)
iommu.strict=1                   # invalidate TLBs synchronously on
                                 # unmap. strict=0 is faster and
                                 # leaves a window where a freed page
                                 # is still reachable by the device.

# check what is actually in force
cat /proc/cmdline
dmesg | grep -iE 'smmu|iommu'
#   arm-smmu-v3 2b400000.iommu: ias 48-bit, oas 48-bit (features 0x...)
#   arm-smmu-v3 2b400000.iommu: allocated 65536 entry cmdq
#   iommu: Default domain type: Translated

# "Default domain type: Passthrough" means devices are NOT
# being translated. On a production system that is a finding.

These costs are why bypass is tempting and why iommu.strict=0 exists. Both trade a real security property for measurable performance, and both should be a deliberate, documented decision rather than an accident.
