Error handling with Option and Result

No exceptions, no error codes to forget. Failure is in the return type, the compiler makes you handle it, and the ? operator makes propagation as terse as ignoring it would be in C.

Two types

Rust has no exceptions and no error return codes. It has two types, and the distinction between them is a modelling decision you make deliberately.

    enum Option<T> { Some(T), None }
    enum Result<T, E> { Ok(T), Err(E) }

/* THAT IS ALL THEY ARE - ordinary enums (chapter 05), with a
   great many convenience methods.

     Option    "a value, or nothing" - absence is not an error
     Result    "a value, or an error explaining why"

   USE Option WHEN: a lookup misses, a buffer is empty, a
   configuration field is unset, a conversion has one obvious
   failure mode.
   USE Result WHEN: the caller needs to know WHY, or wants to
   propagate.

/* THERE IS NO NULL. `Option<&T>` is the same size as `&T`
   (niche optimisation, chapter 05), so the safety is free -
   and the check is not optional:                          */

    fn find(&self, id: u32) -> Option<&Device>;

    let d = self.find(id);
    d.name();                   // COMPILE ERROR - it is an
                                // Option
    if let Some(d) = self.find(id) { d.name(); }

/* COMPARE C, where the null check is a convention nobody
   enforces, and C++, where std::optional is opt-in and the
   raw pointer remains available.

/* AND #[must_use]: Result is marked with it, so ignoring one
   is a warning: */
    write_register(0x10, 5);    // warning: unused
                                // `Result` that must be used
    let _ = write_register(0x10, 5);    // explicit "I am
                                        // ignoring this"  */

The ? operator

One operator does what pages of C error-propagation boilerplate do, and understanding exactly what it expands to is what stops it feeling like magic.

/* WITHOUT it, propagation is verbose: */
    fn read_config() -> Result<Config, Error> {
        let raw = match read_flash(CONFIG_ADDR) {
            Ok(v) => v,
            Err(e) => return Err(e),
        };
        let parsed = match parse(&raw) {
            Ok(v) => v,
            Err(e) => return Err(e),
        };
        Ok(parsed)
    }

/* WITH it: */
    fn read_config() -> Result<Config, Error> {
        let raw = read_flash(CONFIG_ADDR)?;
        let parsed = parse(&raw)?;
        Ok(parsed)
    }

/* `expr?` means: if Ok(v), evaluate to v; if Err(e), RETURN
   Err(e.into()) from the enclosing function.

   THE `.into()` IS THE IMPORTANT PART: the error is converted
   via the From trait (chapter 06), so a function returning
   `Result<_, MyError>` can use `?` on anything whose error
   type converts into MyError.                            */

    #[derive(Debug)]
    enum Error {
        Flash(FlashError),
        Parse(ParseError),
        Timeout,
    }

    impl From<FlashError> for Error {
        fn from(e: FlashError) -> Self { Error::Flash(e) }
    }
    impl From<ParseError> for Error {
        fn from(e: ParseError) -> Self { Error::Parse(e) }
    }
/* Now `?` converts automatically at every call site, and
   adding a new error source is one From impl.

/* `?` ALSO WORKS ON Option, inside a function returning
   Option: */
    fn first_even(v: &[i32]) -> Option<i32> {
        let x = v.iter().find(|x| *x % 2 == 0)?;
        Some(*x * 2)
    }

/* AND THE CHAIN, which is where it earns its keep: */
    fn handle(&mut self, cmd: &[u8]) -> Result<Response, Error> {
        let parsed = Command::parse(cmd)?;
        let result = self.execute(parsed)?;
        let encoded = result.encode()?;
        self.transmit(&encoded)?;
        Ok(Response::Ok)
    }
/* Four fallible operations, four characters of error
   handling, and not one of them can be forgotten.       */
Why this beats both alternatives

An error code can be ignored silently — and in C, routinely is. An exception cannot be ignored but is invisible in the signature and unwinds unpredictably (C++ chapter 12). Result is in the type, cannot be dropped without a warning, costs nothing at run time, and propagates in one character. It is the design C++23's std::expected is copying.

The methods worth knowing

Option and Result carry a large number of combinators. These are the ones that earn their place; the rest can be looked up.

/* --- EXTRACTING --- */
    opt.unwrap()                // PANICS on None
    opt.expect("msg")           // panics with your message
    opt.unwrap_or(default)
    opt.unwrap_or_else(|| compute())
    opt.unwrap_or_default()

    res.unwrap()                // panics, printing the Err
    res.expect("msg")
    res.unwrap_or(default)
    res.unwrap_err()            // panics if Ok

/* USE `expect` OVER `unwrap` - the message tells the next
   reader WHY you believed it could not fail:            */

        .expect("peripherals taken twice");

/* --- TRANSFORMING --- */
    opt.map(|v| v * 2)                  // Option<T> ->
                                        // Option<U>
    opt.and_then(|v| lookup(v))         // flat_map - avoids
                                        // Option<Option<T>>
    opt.filter(|v| *v > 0)
    opt.or(other)
    opt.take()                          // leaves None behind
    opt.replace(v)
    opt.get_or_insert_with(|| make())

    res.map(|v| v * 2)
    res.map_err(|e| Error::Wrapped(e))  // convert the ERROR
    res.and_then(|v| next_step(v))
    res.ok()                            // Result -> Option,
                                        // discarding the
                                        // error
    opt.ok_or(Error::Missing)           // Option -> Result
    opt.ok_or_else(|| Error::Missing)

/* --- INSPECTING --- */
    opt.is_some()  opt.is_none()
    res.is_ok()    res.is_err()
    opt.as_ref()                        // Option<T> ->

    opt.as_mut()
    res.as_ref()
    opt.iter()                          // 0 or 1 items

    let all: Result<Vec<u32>, E> = results.into_iter().collect();
/* Collects into Ok(vec) if EVERY element is Ok, or the FIRST
   Err. One line replaces a loop with an early return.

    opt.unwrap_or_else(|| expensive())  // only on None
/* The `_else` and `_with` suffixes always mean "lazy". On

Designing an error type

Designing an error type is where most of the real decisions are, and the right answer differs sharply between a library and an application.

/* --- FOR no_std / EMBEDDED: a small enum, Copy if
       possible --- */
    #[derive(Debug, Clone, Copy, PartialEq, Eq)]
    pub enum Error {
        Timeout,
        BusError,
        Nack,
        InvalidAddress(u8),
        BufferTooSmall { needed: usize, got: usize },
    }

    impl core::fmt::Display for Error {
        fn fmt(&self, f: &mut core::fmt::Formatter<'_>)
                -> core::fmt::Result {
            match self {
                Error::Timeout => write!(f, "timeout"),
                Error::Nack => write!(f, "not acknowledged"),
                Error::InvalidAddress(a) =>
                        write!(f, "invalid address {a:#x}"),
                Error::BufferTooSmall { needed, got } =>
                        write!(f, "buffer too small: need \
                                   {needed}, got {got}"),
                _ => write!(f, "bus error"),
            }
        }
    }

/* SIZE MATTERS on embedded: keep the variants small, and
   prefer Copy so the error can be returned without a move.
   `Result<(), Error>` with a Copy enum is typically one or
   two bytes.

/* --- THE thiserror CRATE removes the boilerplate (std or
       no_std with `core-error`): --- */
    #[derive(Debug, thiserror::Error)]
    pub enum Error {
        #[error("timeout after {0} ms")]
        Timeout(u32),

        #[error("SPI failure")]
        Spi(#[from] SpiError),           // generates the From
                                         // impl AND the
                                         // source chain
    }

/* --- FOR APPLICATIONS, anyhow: --- */
    fn main() -> anyhow::Result<()> {
        let cfg = read_config()
            .context("reading configuration")?;
        run(cfg).context("running")?;
        Ok(())
    }
/* anyhow::Error boxes any error and accumulates CONTEXT, so
   the final message is "running: reading configuration: file
   not found". Perfect for a binary; wrong for a library,
   because callers cannot match on the error.

/* THE RULE: LIBRARIES define a concrete enum so callers can
   match. APPLICATIONS use anyhow so they can report. Embedded
   firmware is a library in this sense - define the enum. */

Panics

Panics are Rust's mechanism for unrecoverable errors, and what they do on an embedded target is not what they do on Linux — which makes this section more important than it looks.

/* A panic is for a BUG, not a runtime failure - the same
   distinction as assert versus error return (C++ chapter 12).
*/

    panic!("invariant violated: {state:?}");
    assert!(index < LEN, "index {index} out of range");
    assert_eq!(a, b);
    debug_assert!(expensive_check());   // debug builds only
    unreachable!("state machine reached an impossible state");
    todo!()  unimplemented!()

/* WHAT HAPPENS: by default the stack UNWINDS, running Drop
   for every live value, then the thread dies. With
   `panic = "abort"` it terminates immediately.

/* THESE PANIC, and knowing which is important on embedded:
     unwrap() / expect() on None or Err
     array or slice indexing out of range
     integer division by zero
     INTEGER OVERFLOW in debug builds (release wraps)
     .unwrap() on a poisoned Mutex

/* AVOIDING PANICS in code that must not: */
    v.get(i)                    // Option, not a panic
    v.get_mut(i)
    a.checked_add(b)            // Option
    a.saturating_add(b)         // clamps
    a.wrapping_add(b)           // explicit wrap
    a.overflowing_add(b)        // (value, did_overflow)
    a.checked_div(b)            // None on zero

/* ON EMBEDDED (chapter 19): */
    #[panic_handler]
    fn panic(info: &PanicInfo) -> ! {
        // log it somewhere persistent, then reset
        write_panic_log(info);
        cortex_m::peripheral::SCB::sys_reset();
    }

    // in Cargo.toml
    [profile.release]
    panic = "abort"             // no unwinder - smaller
    overflow-checks = false     // or true, if you prefer the
                                // panic

/* AND THE panic-never TRICK: if you can prove no panic is
   reachable, the `panic-never` crate makes any residual panic
   a LINK ERROR. Combined with careful use of `get` and
   `checked_*`, that gives a build-time guarantee of no
   panics - which for safety-critical firmware is a strong
   property.                                              */

/* --- 2. RETRY WITH A BOUND --- */
    fn read_with_retry(&mut self, n: u8)
            -> Result<u16, Error>
    {
        let mut last = Error::Timeout;
        for _ in 0..n {
            match self.read() {
                Ok(v) => return Ok(v),
                Err(e) => last = e,
            }
        }
        Err(last)
    }

        Ok(())

How it shows up

SymptomCause and fix
"unused Result that must be used"Handle it, or write let _ = deliberately
"the ? operator can only be used in a function that returns Result"Change the return type, or handle it explicitly
"? couldn't convert the error"Missing From impl for that error type
"cannot use ? on an Option in a Result function"Use .ok_or(...)?
Panic: "called unwrap() on a None"Handle the case, or use expect with a reason
Panic: "index out of bounds"Use .get()
Panic in release but not debug, or vice versaInteger overflow — checked in debug, wrapping in release
Binary large because of panic machinerypanic = "abort", and avoid formatting in the handler
Cannot match on a library's errorsIt used anyhow — a library design mistake
Error type is large and copied everywhereBox the payload, or shrink the variants
