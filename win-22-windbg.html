WinDbg for driver developers

Setting up kernel debugging, reading a crash dump, and the two dozen commands that cover almost everything you will need. Unlike Linux, Windows expects you to use a real debugger — and the tooling is correspondingly good.

Setting up a connection

Kernel debugging needs two machines — or two virtual machines — because a debugger cannot usefully stop the kernel it is running on. Setting this up once is a prerequisite for everything else in the chapter.

# You need TWO machines: the HOST running WinDbg, and the
# TARGET running your driver. A VM is ideal.

# --- On the TARGET: choose a transport ---

# NETWORK (fastest, and the modern default):
    bcdedit /debug on
    bcdedit /dbgsettings net hostip:192.168.1.10 \
            port:50000 key:1.2.3.4.5.6.7.8
    ; the key can be anything; note it for the host
    shutdown /r /t 0

# SERIAL (works on anything, including physical boards):
    bcdedit /debug on
    bcdedit /dbgsettings serial debugport:1 baudrate:115200

# For a Hyper-V VM, the simplest option:
    bcdedit /dbgsettings serial debugport:1 baudrate:115200
    ; and configure the VM's COM1 as a named pipe:
    ;   \\.\pipe\mydebug

# BREAK INTO THE DEBUGGER AT BOOT, to catch DriverEntry:
    bcdedit /set bootdebug on

# --- On the HOST: connect ---
    windbg -k net:port=50000,key=1.2.3.4.5.6.7.8
    windbg -k com:pipe,port=\\.\pipe\mydebug,resets=0,reconnect

# --- SYMBOLS - do this first, always ---
    .sympath srv*C:\symbols*https://msdl.microsoft.com/download/symbols
    .sympath+ C:\myproject\x64\Debug
    .reload /f

    ; or set _NT_SYMBOL_PATH as an environment variable so
    ; every tool picks it up:
    setx _NT_SYMBOL_PATH "srv*C:\symbols*https://msdl.microsoft.com/download/symbols"

# WITHOUT SYMBOLS, every command prints hex addresses and you
# learn nothing. This is the single most common reason a
# newcomer finds WinDbg useless.

# --- Source-level debugging ---
    .srcpath C:\myproject\src
    l+t          ; source line mode
    .lines       ; enable line number information

Reading a crash dump

A crash dump is a snapshot of the machine at the moment it died. One command extracts most of what you need from it, and knowing what to read in its output is the highest-value debugging skill on Windows.

# CONFIGURE DUMPS on the target, before you need them:
#   System Properties -> Advanced -> Startup and Recovery
#   "Kernel memory dump" is the right choice for driver work -
#   a minidump often lacks the pool data you need.
#   -> C:\Windows\MEMORY.DMP

# Open it:
    windbg -z C:\Windows\MEMORY.DMP

# THE FIRST COMMAND, ALWAYS:
    !analyze -v

# It gives you:
#   the bugcheck code and its four parameters, decoded
#   the faulting module and function
#   the stack trace
#   often, a plain-English "PROCESS_NAME" and
#   "FAILURE_BUCKET_ID" that names the bug class
#   and a "MODULE_NAME" - which, if it is yours, is the answer

# THEN, IN ORDER:
    .bugcheck                 ; the code and parameters again
    kb                        ; the stack with arguments
    kv                        ; verbose - includes frame
                              ; pointers and trap frames
    kP                        ; with full parameter names
    lm                        ; loaded modules
    lmvm mydriver             ; details of yours - version,
                              ; timestamp, symbol status
    !irql                     ; the IRQL at the time
    !process                  ; the current process
    !thread                   ; the current thread
    r                         ; registers
    .trap <address>           ; switch to a trap frame's
                              ; context, from the kv output

# IF THE STACK IS CORRUPT:
    dps @rsp L100             ; dump the stack as symbols -
                              ; often reveals return addresses
                              ; the unwinder missed
    !stackusage
    .thread /r /p <ethread>   ; switch thread context
!analyze -v is right more often than you expect

It applies a large body of heuristics about known bug patterns and frequently names the exact module and reason. Read its whole output before doing anything else — including the "STACK_COMMAND" and "FOLLOWUP_NAME" lines, which tell you what it thinks and why. Then verify its conclusion rather than trusting it blindly; it is a very good first hypothesis, not a proof.

The commands worth memorising

WinDbg's command set is enormous and mostly irrelevant to any one debugging session — what actually matters is a small core you reach for constantly, organised around the questions you ask of a crash or a hang. Start every session with !analyze -v, which runs Microsoft's own heuristics over the crash and usually names the faulting driver and the likely cause outright; then use kb/kv to see how execution got there, and dt to inspect the actual structures involved once you have a suspect address. The !process/!thread/!irp/!devobj family answers a different kind of question — not "why did it crash" but "what is this system's state right now" — which is what you need for a hang rather than a bugcheck. ba w4 deserves special attention: setting a hardware breakpoint that fires the instant a specific address is written is frequently the only practical way to catch a memory-corruption bug, because it stops execution at the write itself rather than wherever the corrupted data is later read and misused.

The WDF extension

The framework's own debugger extension understands WDF objects, queues and requests, which the standard commands cannot see. For a KMDF driver this is usually where you should start rather than finish.

    .load wdfkd.dll
    !wdfkd.wdfhelp                  ; the full list

# THE ONES THAT MATTER:
    !wdfdriverinfo mydriver         ; everything: version,
                                    ; devices, queues
    !wdfdriverinfo mydriver 0xff    ; maximum verbosity
    !wdfdevicequeues <WDFDEVICE>    ; every queue and its
                                    ; pending requests
                                    ; (chapter 16)
    !wdfhandle <handle>             ; type, parent, context,
                                    ; refcount (chapter 14)
    !wdfobject <handle>
    !wdfrequest <WDFREQUEST>        ; state, owner, IRP
    !wdfqueue <WDFQUEUE>
    !wdfobjectdump                  ; the whole object tree

# AND THE MOST VALUABLE ONE:
    !wdflogdump mydriver
    !wdflogdump mydriver -d         ; include the IFR (in-flight
                                    ; recorder) detail

# The framework keeps a circular trace of every state
# transition, request, and error it detected - IN MEMORY, at
# all times, with no configuration. After a crash it usually
# tells you what the framework thought was happening, which is
# frequently the entire diagnosis.

# YOUR OWN TRACES appear there too, if you use WPP or
# TraceEvents - see below.

Tracing from your driver

Printing from a driver is expensive enough to change the timing you are trying to observe. WPP tracing solves that by compiling the message strings out of the binary entirely and emitting compact binary events instead.

/* THREE OPTIONS, in increasing order of quality: */

/* 1. DbgPrint / KdPrint - simplest, slowest */
        KdPrint(("MyRead: length %lu\n", length));
        /* compiled out in release builds */

        DbgPrintEx(DPFLTR_IHVDRIVER_ID, DPFLTR_INFO_LEVEL,
                   "MyRead: length %lu\n", length);

        /* enable output on the target: */
        ; registry: HKLM\SYSTEM\CCS\Control\Session Manager\Debug
        ;           Print Filter -> IHVDRIVER = 0xF
        ; or in WinDbg:
        ed nt!Kd_IHVDRIVER_Mask 0xF

/* DbgPrint IS SLOW - it serialises to the debugger connection
   and can take milliseconds with interrupts disabled. Never
   in a hot path or an ISR (chapter 11).                   */

/* 2. WPP TRACING - the standard for production drivers.
      Compiled to a binary format with a message GUID; the
      strings live in a PDB, not in the driver.            */

        /* trace.h */
        #define WPP_CONTROL_GUIDS \
            WPP_DEFINE_CONTROL_GUID( \
                MyDriverTraceGuid, \
                (A1B2C3D4,1234,5678,9ABC,DEF012345678), \
                WPP_DEFINE_BIT(TRACE_DEVICE)  \
                WPP_DEFINE_BIT(TRACE_QUEUE)   \
                WPP_DEFINE_BIT(TRACE_DPC)     \
                )

        /* in the driver: */
        WPP_INIT_TRACING(DriverObject, RegistryPath);
        ...
        TraceEvents(TRACE_LEVEL_INFORMATION, TRACE_QUEUE,
                    "Read request, length %lu", length);
        ...
        WPP_CLEANUP(DriverObject);

/* WPP IS FAST - a few dozen cycles per event, safe at any
   IRQL. And the messages land in the WDF log, so
   !wdflogdump shows them interleaved with the framework's
   own trace, which is exactly the correlation you want.  */

        /* capture live: */
        tracelog -start MyTrace -guid #A1B2C3D4-1234-5678-9ABC-DEF012345678 \
                 -f mytrace.etl -flag 0xF -level 5
        tracelog -stop MyTrace
        tracefmt -o output.txt mytrace.etl
        ; or traceview.exe for a GUI

/* 3. ETW TRACE EVENTS - for anything you want correlated with
      system-wide traces in WPA. More setup, best integration.
      Use it when latency or performance is the question
      rather than correctness.                            */

Live debugging techniques

Beyond post-mortem analysis, you can attach to a running machine and inspect or interrupt it. These are the techniques that matter most for a driver — breaking on your own load, catching a specific request, and stepping through a callback.

# --- Break in whenever you like ---
    Ctrl+Break in WinDbg, or on the target:
    ; SysRq equivalent: the debugger breaks on demand over the
    ; connection

# --- Break on your driver loading ---
    sxe ld mydriver.sys
    g
    ; stops the moment it loads, before DriverEntry

# --- Breakpoint on a function, with a condition ---
    bp mydriver!MyEvtIoRead ".if (@rdx == 0) {} .else {gc}"
    ; break only when the second argument is zero

# --- Breakpoint that just logs and continues ---
    bp mydriver!MyEvtIoRead "dt mydriver!_MY_CONTEXT @rcx; gc"

# --- BREAK ON MEMORY WRITE - the corruption finder ---
    ba w8 ffff8a0c12345678
    ; breaks when 8 bytes at that address are written.
    ; THE tool for "who is corrupting my structure?" - set it
    ; on the field that gets clobbered and the culprit
    ; identifies itself.
    ; Limited to four hardware breakpoints.

# --- Watch a value change over time ---
    .while (1) { dd mydriver!g_Counter L1; .sleep 1000; g }

# --- Call a function in the target ---
    .call mydriver!MyDumpState(0)
    g
    ; requires private symbols and a compatible calling
    ; convention. Powerful, and occasionally the fastest way
    ; to interrogate driver state.

# --- Scripting ---
    $$>a< C:\scripts\myscript.txt
    dx @$curprocess.Threads     ; the NatVis/dx data model
    dx -g @$curprocess.Threads.Where(t => t.Id > 100)

Diagnosing the common failures

A small number of failures account for the large majority of what you will actually encounter. Recognising each by its signature saves reconstructing the diagnosis from scratch every time.

# --- "My driver bugchecked" ---
    !analyze -v
    ; then verify its conclusion with kb and the bugcheck
    ; parameters (chapter 03 for 0xA/0xD1)

# --- "The system hangs, no bugcheck" ---
    Ctrl+Break
    !running                  ; what is each CPU doing?
    !stacks 2                 ; every thread
    !locks                    ; who holds what
    !deadlock                 ; if verifier's flag is on
    !irql                     ; are we stuck at high IRQL?

# --- "An application hangs on my device" ---
    !process 0 7              ; find the process and thread
    !thread <ethread>         ; what is it waiting on
    !irpfind -v 0 0 device <devobj>     ; which IRP is stuck
    !wdfdevicequeues <wdfdevice>        ; and which queue
                                        ; holds it

# --- "Memory is leaking" ---
    !poolused 2               ; sorted by non-paged usage
    !poolfind xMYD            ; your tag (chapter 07)
    !verifier 3 mydriver.sys  ; with stacks, if pool tracking
                              ; is enabled

# --- "Something is corrupting my structure" ---
    ba w8 <address of the field>
    ; or enable special pool and let it fault at the moment of
    ; the overrun (chapter 22)

# --- "The driver will not load" ---
    !devnode 0 1 mydriver
    ; and read setupapi.dev.log (chapter 20) and the
    ; CodeIntegrity event log (chapter 21) on the target

# --- "It works with the debugger attached" ---
    ; a timing bug. The debugger changes timing enormously.
    ; Use WPP tracing instead of breakpoints, and enable
    ; Driver Verifier - which perturbs timing differently and
    ; often makes the race deterministic.

Check yourself

  • Set up a network or serial kernel debugging connection to a VM.
  • Configure symbols so both Microsoft's and your own resolve.
  • Read a crash dump with !analyze -v and verify its conclusion.
  • Use fifteen of the core commands from memory.
  • Use the WDF extension to inspect queues, requests and the framework log.
  • Add WPP tracing and explain why it beats DbgPrint.
  • Set a conditional breakpoint and a data breakpoint.
  • Diagnose a hang using only !running, !stacks and !locks.
  • Find a hung application's stuck IRP and the queue holding it.
  • Locate a pool leak with !poolused and !verifier 3.
