The vCPU and the world switch

A vCPU is a data structure plus a promise: that whenever it runs, the physical CPU looks exactly the way that vCPU last left it. Keeping that promise is the world switch, and its length in instructions is the tax every guest pays on every exit.

What a vCPU is

A vCPU is a data structure and a thread, and being precise about what it does and does not contain explains most of what the switch code has to do.

   struct vcpu - conceptually, three groups of state:

   +-----------------------------------------------------------+
   |  GUEST CPU STATE - must be identical on resume            |
   |    x0-x30, SP_EL0, SP_EL1, PC (in ELR_EL2), PSTATE         |
   |    FP/SIMD/SVE register file                               |
   |    SCTLR_EL1 TTBR0_EL1 TTBR1_EL1 TCR_EL1 MAIR_EL1          |
   |    VBAR_EL1 ESR_EL1 FAR_EL1 ELR_EL1 SPSR_EL1 AMAIR_EL1     |
   |    CONTEXTIDR_EL1 TPIDR_EL0 TPIDRRO_EL0 TPIDR_EL1          |
   |    CPACR_EL1 PAR_EL1 CSSELR_EL1 ...                        |
   +-----------------------------------------------------------+
   |  VIRTUAL HARDWARE - state of the devices this vCPU owns    |
   |    vGIC CPU interface + list registers  (chapter 11)       |
   |    virtual timer: CNTV_CTL, CNTV_CVAL, CNTVOFF (chapter 13)|
   |    virtual PMU counters                                    |
   |    MPIDR / MIDR the guest should see (VMPIDR/VPIDR_EL2)    |
   +-----------------------------------------------------------+
   |  HYPERVISOR BOOKKEEPING - never seen by the guest          |
   |    pointer to the owning VM (and thus to VTTBR/VMID)       |
   |    exit reason, exit counters                              |
   |    pending interrupt injections                            |
   |    the host thread this vCPU is running on                 |
   |    run state: runnable / halted (WFI) / stopped            |
   +-----------------------------------------------------------+

   In KVM this structure lives in the host kernel and is
   reachable from user space through a per-vCPU file
   descriptor and a shared page (kvm_run).
A vCPU is a thread

In KVM, one vCPU is one host thread that spends its life in a loop: ioctl(vcpu_fd, KVM_RUN) enters the guest, returns when something needs handling, user space or the kernel handles it, repeat. Every consequence of that follows: vCPUs are scheduled by the ordinary Linux scheduler, they can be pinned with taskset, they show up in top, and a vCPU blocked in WFI is a thread blocked on a wait queue.

The run loop

The run loop is the heart of a hypervisor and is shorter than expected. Everything else in this track is an elaboration of one of its branches.

/* User space (QEMU, crosvm, cloud-hypervisor): one thread per vCPU */

void *vcpu_thread(void *arg)
{
        struct vcpu *v = arg;

        for (;;) {
                ioctl(v->fd, KVM_RUN, 0);     /* blocks in the guest */

                switch (v->kvm_run->exit_reason) {

                case KVM_EXIT_MMIO:
                        /* the guest touched an address we model  */
                        mmio_dispatch(v->kvm_run->mmio.phys_addr,
                                      v->kvm_run->mmio.data,
                                      v->kvm_run->mmio.len,
                                      v->kvm_run->mmio.is_write);
                        break;

                case KVM_EXIT_HYPERCALL:
                        handle_hypercall(v);
                        break;

                case KVM_EXIT_SYSTEM_EVENT:   /* PSCI shutdown/reset */
                        return handle_system_event(v);

                case KVM_EXIT_INTR:           /* a host signal       */
                        break;                /* just re-enter       */

                case KVM_EXIT_FAIL_ENTRY:
                        die("entry failed, hw error 0x%llx",
                            v->kvm_run->fail_entry.hardware_entry_failure_reason);
                }
        }
}

/* Note what is ABSENT from that list: stage-2 translation
   faults, timer interrupts, GIC accesses, WFI. Those never
   reach user space - the kernel handles them and re-enters the
   guest without ever returning from the ioctl. That is the
   difference between a "light exit" and a "heavy exit", and it
   is roughly a factor of ten.                                 */

The world switch itself

The switch itself is the most performance-critical code in the system, and every line of it exists because something must be saved or something must be restored.

   HOST context                                 GUEST context

   kvm_arch_vcpu_ioctl_run()
        |
        v
   +--------------------------------------+
   | 1. disable interrupts, preempt off   |
   | 2. flush pending vGIC state into the |
   |    list registers                    |
   | 3. save HOST unbanked state:         |
   |      callee-saved x19-x30, SP        |
   |      (host EL1 sysregs stay put in   |
   |       VHE; must be saved in nVHE)    |
   | 4. write VTTBR_EL2 = table | VMID    |
   | 5. write HCR_EL2 = guest flags       |
   | 6. restore GUEST sysregs             |
   | 7. restore GUEST x0-x30, SP_EL0      |
   | 8. write ELR_EL2 = guest PC          |
   |    write SPSR_EL2 = guest PSTATE     |
   | 9. ERET                              |
   +--------------------------------------+
        |
        +------------------------------------> guest runs
                                                    |
                                                    | trap
        <---------------------------------------+---+
        |
   +--------------------------------------+
   | 10. save GUEST x0-x30 immediately    |
   |     (you have no free registers -    |
   |      this is why TPIDR_EL2 holds the |
   |      per-CPU host context pointer)   |
   | 11. read ESR_EL2 - why are we here?  |
   | 12. save guest sysregs IF the exit   |
   |     will be long                     |
   | 13. restore host state               |
   | 14. return to C, handle the exit     |
   +--------------------------------------+

   Steps 6 and 12 are the expensive ones: roughly 30-40 MSR/MRS
   pairs, each with pipeline cost. The whole switch is a few
   thousand cycles.

Why TPIDR_EL2 matters

On entry from the guest, every general-purpose register belongs to the guest and must not be clobbered before it is saved. The handler therefore needs one register's worth of scratch and a way to find its own per-CPU data. TPIDR_EL2 is that anchor: it holds the address of this physical CPU's host context. Read it, stash a register, save the rest. Corrupt it and the hypervisor cannot find itself.

WFI, WFE and the idle guest

An idle guest is a scheduling opportunity, and how the hypervisor treats these two instructions decides whether the host can use it.

/* A guest with nothing to do executes WFI. On bare metal that
   parks the core until an interrupt arrives. Under a
   hypervisor that would waste a physical CPU, so HCR_EL2.TWI
   traps it.                                                  */

  guest: WFI
     -> trap to EL2, ESR_EL2.EC = 0x01
     -> KVM: kvm_vcpu_halt()
          the vCPU THREAD blocks on a wait queue.
          the physical CPU runs something else - another vCPU,
          a host process, or genuinely idles.

  later: a virtual interrupt becomes pending for this vCPU
     -> wake the thread
     -> re-enter the guest
     -> the guest's WFI "completes" and it takes the interrupt

/* WFE is different and subtler. A guest spinlock does:

       1: LDAXR w1, [x0]
          CBNZ  w1, 2f
          STXR  w2, w3, [x0]
          CBNZ  w2, 1b
          ... critical section ...
       2: WFE                 // sleep until someone SEVs
          B     1b

   If two vCPUs of the same guest are time-sharing ONE physical
   CPU, and the lock holder is descheduled, the waiter spins
   for its entire time slice waiting for a vCPU that cannot
   run. This is LOCK-HOLDER PREEMPTION, and it is the single
   worst pathology in overcommitted virtualisation.

   Trapping WFE turns the spin into a yield: KVM marks the vCPU
   as yielding and tries to schedule a sibling vCPU of the same
   VM - preferably the one holding the lock. That is
   kvm_vcpu_on_spin(), and it is why HCR_EL2.TWE is set.

   The real fix is not to overcommit vCPUs on a latency-
   sensitive workload. Paravirtualised queued spinlocks help
   on x86; on arm64 the WFE trap plus pinning is the practical
   answer.                                                    */

Bringing up a multi-vCPU guest

Bringing up secondary vCPUs involves a protocol between guest and hypervisor that is easy to overlook until a guest hangs waiting for CPUs that never arrive.

/* The guest cannot power on a CPU - there is no CPU to power
   on. It asks, via PSCI, and the hypervisor creates the
   illusion.                                                   */

  guest CPU0:  HVC  x0=PSCI_CPU_ON, x1=target MPIDR,
                    x2=entry point,  x3=context id
        |
        v
  EL2: find the vCPU whose VMPIDR_EL2 matches x1
       if it is already on          -> return ALREADY_ON
       set its PC = x2, x0 = x3
       set its state = runnable
       wake its host thread
       return SUCCESS
        |
        v
  guest CPU1 begins executing at x2, with x0 = context id,
  MMU off, at EL1.

/* Two details that bite:

   1. VMPIDR_EL2 is what the guest reads as MPIDR_EL1. YOU
      choose the affinity topology. If you hand out MPIDRs that
      imply 4 clusters of 1 CPU, the guest's scheduler builds
      its domains accordingly and may perform badly. Model a
      topology that matches reality, or a flat one.

   2. The PSCI conduit must match. The guest's device tree says
      method = "hvc" (under KVM) or "smc" (bare metal). A
      mismatch means CPU_ON sails past EL2 to EL3, where TF-A
      tries to power on a real core for a virtual request.
      Symptom: guest hangs with "CPU1: failed to boot: -110".  */

Measuring the switch

The cost of a world switch is a number you can measure rather than estimate, and having it makes the performance chapter concrete.

# How many exits, and how expensive?

$ sudo perf kvm --host stat live
# live per-exit-reason breakdown, updated continuously

$ sudo perf stat -e kvm:kvm_entry,kvm:kvm_exit -a sleep 10

# Time in the guest vs time in the host, per vCPU thread:
$ ps -T -p $(pgrep -f 'qemu.*mymachine') -o comm,pid,tid,pcpu
COMMAND          PID    TID %CPU
qemu-system-aar 4211   4211  3.1     # main/IO thread
CPU 0/KVM       4211   4219 74.2     # vCPU 0
CPU 1/KVM       4211   4220 71.8     # vCPU 1

# Pin them and watch the exit rate change:
$ taskset -cp 2 4219
$ taskset -cp 3 4220

# The microbenchmark that isolates switch cost: a guest loop
# that does nothing but trap.
#   guest:  1: hvc #0 ; b 1b
# Time N iterations, divide. On modern arm64 with VHE expect
# roughly 1-2 us per round trip if the hypercall is handled in
# the kernel, 10x that if it reaches user space.
