MIPI CSI-2 and camera interfaces

A 12-megapixel sensor at 30 frames per second produces about 5 gigabits every second. No bus in the preceding chapters is within two orders of magnitude of that, which is why camera interfaces are a different kind of engineering — and why the control path and the data path are separate buses.

Why cameras need their own interface

   THE ARITHMETIC:

     4000 x 3000 pixels x 10 bits x 30 fps
       = 3.6 Gbit/s of raw sensor data

   SPI at 100 Mbit/s would need 36 lanes.
   USB high speed at 480 Mbit/s cannot do it at all.

   THE OLD ANSWER - PARALLEL DVP (digital video port):

     D0-D7 (or D0-D11)   data
     PCLK                pixel clock
     HSYNC               line valid
     VSYNC               frame valid

     12-16 pins, and every one of them switching at the
     pixel clock. At VGA/30fps that is fine; at anything
     modern the pin count and the EMI are both unacceptable.
     Still common on small MCU-class sensors (OV7670 and
     similar) and worth recognising.

   THE MODERN ANSWER - MIPI CSI-2 over D-PHY:

     A clock lane plus 1-4 data lanes, DIFFERENTIAL, each
     lane carrying 1-2.5 Gbit/s.

     4 lanes x 2.5 Gbit/s = 10 Gbit/s on 10 wires.

   PLUS A SEPARATE I2C BUS (called CCI - camera control
   interface) for configuration. This split is the thing to
   internalise:

     CSI-2  = pixels, one direction, very fast
     I2C    = registers, bidirectional, slow

   You configure the sensor over I2C - resolution, exposure,
   gain, frame rate - and it then streams pixels over CSI-2.
   Two completely different buses to one chip, and bringing
   up a camera means getting both right independently.

D-PHY's two modes

   The physical layer switches between two electrical modes
   on the same wires, and this is what makes it efficient.

   HIGH-SPEED (HS) mode
     Differential, 200 mV swing around 200 mV common mode.
     Low voltage means low power and low EMI at gigabit
     rates. Used for the actual pixel burst.

   LOW-POWER (LP) mode
     Single-ended, 1.2 V, both wires used independently as
     two slow signals. Used between bursts for control,
     and to signal entry into HS mode.

     LP-11  both high    = stop state, the idle condition
     LP-01, LP-00        = the HS entry sequence
     LP-10  turnaround (for bidirectional lane 0)

   A FRAME LOOKS LIKE:

     LP-11 ... [HS burst: line 1] ... LP-11 ...
               [HS burst: line 2] ... LP-11 ...

   The link drops to low power between every LINE. On a
   battery device this matters enormously - the high-speed
   drivers are only active while pixels are actually moving.

   THIS IS WHY CSI-2 BRING-UP FAILS IN A CHARACTERISTIC WAY:
   if the lanes never leave LP-11, the sensor is not
   streaming at all - check the I2C configuration and the
   sensor's clock and reset pins. If you see HS bursts but
   no valid frames, the problem is packet-level: lane count,
   data type, or virtual channel mismatch.

The packet layer

/* CSI-2 carries SHORT and LONG packets, distinguished by
   the data type field.                                    */

/* SHORT PACKET - 4 bytes, synchronisation only:
     Frame Start (0x00), Frame End (0x01),
     Line Start (0x02),  Line End (0x03)

   +--------+--------+--------+--------+
   | DI     | frame number    | ECC    |
   +--------+--------+--------+--------+

   LONG PACKET - carries pixel data:

   +--------+-----------------+--------+=========+--------+
   | DI     | word count      | ECC    | payload |CRC-16  |
   +--------+-----------------+--------+=========+--------+
     header: 4 bytes                    variable   2 bytes

   DI (data identifier) = virtual channel (2 bits) +
                          data type (6 bits)

   DATA TYPES you will meet:
     0x2A  RAW8      0x2B  RAW10     0x2C  RAW12
     0x1E  YUV422 8-bit
     0x24  RGB888
     0x30-0x37  user defined

   THE ECC on the header is a Hamming code that corrects one
   bit error and detects two. The header must survive - a
   corrupted word count would desynchronise the whole
   stream - so it gets stronger protection than the payload,
   which only has a CRC.

   VIRTUAL CHANNELS let several image streams share one
   physical link: a sensor sending both full-resolution and
   a downscaled preview, or two sensors through an
   aggregator. The receiver demultiplexes by VC number.

   RAW FORMATS ARE PACKED. RAW10 puts four pixels in five
   bytes:

     byte 0: P0[9:2]
     byte 1: P1[9:2]
     byte 2: P2[9:2]
     byte 3: P3[9:2]
     byte 4: P3[1:0] P2[1:0] P1[1:0] P0[1:0]

   Software that assumes two bytes per pixel gets an image
   that looks correct but with wrong colours and a
   progressive horizontal skew - a very recognisable
   symptom once you have seen it.                          */
The sensor outputs Bayer, not colour

Almost every image sensor has a colour filter array — one red, one blue and two green filters per 2×2 group — so each pixel measures only one colour. Turning that into RGB is demosaicing, and it is one stage of an image signal processor pipeline that also does black level, lens shading, white balance, denoise, gamma and sharpening. On an application processor the ISP is dedicated hardware; on a microcontroller there is usually none, which is why MCU camera work uses sensors that output YUV or RGB directly and accept the sensor's own internal processing. The video track covers the pipeline properly.

Bringing up a camera

/* The order matters, and each step has a distinct failure
   signature. Work through them in this sequence.         */

/* 1. POWER AND CLOCKS. Sensors need several rails in a
      documented ORDER, and an external master clock
      (XCLK/MCLK, often 24 MHz) before they respond to
      anything.                                            */
gpio_set(SENSOR_PWDN, 0);       /* release power-down      */
delay_ms(5);
mclk_start(24000000);           /* usually a timer PWM     */
delay_ms(5);
gpio_set(SENSOR_RESET, 1);      /* release reset AFTER
                                   the clock is running    */
delay_ms(20);

/* 2. I2C PROBE. Read the chip ID register. If this fails,
      nothing else can work - stop here and fix it. This
      single check separates "camera problem" from "camera
      not even present".                                   */
uint16_t id = sensor_read16(0x300A);
if (id != EXPECTED_ID) { return -ENODEV; }

/* 3. CONFIGURE. Sensor vendors supply a register list -
      often hundreds of undocumented address/value pairs.
      This is normal and you will not be able to derive it;
      start from the vendor's list for a known mode.       */
sensor_write_array(mode_1920x1080_30fps);

/* 4. RECEIVER CONFIGURATION MUST MATCH EXACTLY:
        - number of lanes
        - data type (RAW10 vs RAW12 vs YUV422)
        - virtual channel
        - line length and frame height
        - D-PHY timing (t_HS-SETTLE especially)
      A mismatch in ANY of these gives you no frames, or
      corrupt ones, with no error message beyond a receiver
      error counter.                                        */

/* 5. CHECK THE RECEIVER'S ERROR COUNTERS FIRST when
      debugging. On Linux:
        $ dmesg | grep -i csi
        $ media-ctl -p          # the pipeline topology
        $ v4l2-ctl --list-formats-ext
      ECC and CRC error counts tell you immediately whether
      the problem is electrical (errors climbing) or
      configuration (no errors, no frames).                */

How it shows up

SymptomCause
Sensor does not respond on I2CMaster clock not running, or reset released before the clock
Lanes stay in LP-11Sensor not streaming — check I2C configuration and the mode
HS bursts present but no valid framesLane count, data type or virtual channel mismatch
Image skewed progressively across the frameLine length wrong, or packed RAW format unpacked as two bytes per pixel
Colours wrong and image looks stripedRAW10/RAW12 packing not handled
Image is greyscale mosaicBayer data not demosaiced — there is no ISP in the path
ECC errors climbingElectrical: lane length matching, impedance, or D-PHY timing
Works at low resolution, fails at highInsufficient lanes or bandwidth for the pixel rate
Frames arrive but tear or duplicateReceiver buffer bandwidth, or DMA not keeping up
Two sensors, only one worksSame virtual channel, or an I2C address collision on the control bus
