Templates and generic programming

Write one implementation, get a specialised copy for each type — with no runtime dispatch and no cost. Templates are how C++ achieves zero-overhead abstraction, and on embedded they are the mechanism for compile-time configuration.

Function and class templates

A template is not code; it is a recipe the compiler uses to generate code once per set of types you use it with. That single fact explains the compile times, the error messages and the code size.

template<typename T>
constexpr const T& max(const T& a, const T& b)
{
        return a > b ? a : b;
}

        max(1, 2);              /* T = int, deduced */
        max(1.0, 2.0);          /* T = double */
        max<long>(1, 2);        /* T explicit */
        max(1, 2.0);            /* ERROR - T cannot be both */

/* EACH INSTANTIATION IS A SEPARATE FUNCTION, generated at
   compile time, and inlined like any other. `max(1,2)`
   compiles to a single `csel` - identical to the macro,
   with type checking and no double-evaluation bug.       */

template<typename T, size_t N>
class RingBuffer {
        std::array<T, N> data_{};
        size_t head_ = 0, tail_ = 0;

public:
        static constexpr size_t capacity = N;

        bool push(const T& v)
        {
                size_t next = (head_ + 1) % N;
                if (next == tail_) return false;    /* full */
                data_[head_] = v;
                head_ = next;
                return true;
        }

        bool pop(T& out)
        {
                if (head_ == tail_) return false;   /* empty */
                out = data_[tail_];
                tail_ = (tail_ + 1) % N;
                return true;
        }

        size_t size() const { return (head_ - tail_ + N) % N; }
};

        RingBuffer<uint8_t, 64>   rx;
        RingBuffer<Message, 16>   queue;

/* N IS A COMPILE-TIME CONSTANT, so:
     · the storage is a fixed array - NO HEAP
     · `% N` with N a power of two becomes an AND
     · the size is known, so bounds are checkable at compile
       time
   This is the embedded container pattern: capacity as a
   template parameter, storage inline.                    */

/* NON-TYPE TEMPLATE PARAMETERS can be integers, enums,
   pointers, and since C++20 floating point and literal class
   types:                                                  */
        template<uint32_t BaseAddr>
        class Uart {
                static constexpr auto *regs =
                        reinterpret_cast<volatile UartRegs *>(
                                BaseAddr);
        public:
                static void put(char c) { regs->DR = c; }
        };
        using Uart0 = Uart<0x09000000>;
/* The address is a constant folded into every access - no
   pointer is stored, and no register is used to hold it. */

Specialisation

Sometimes the general recipe is wrong for one particular type. Specialisation lets you replace it, and there are two quite different mechanisms depending on whether it is a full or partial replacement.

/* Provide a different implementation for particular types. */

/* --- FULL SPECIALISATION --- */
template<typename T>
struct Serializer {
        static size_t write(uint8_t *buf, const T& v)
        {
                memcpy(buf, &v, sizeof(T));
                return sizeof(T);
        }
};

template<>
struct Serializer<std::string_view> {
        static size_t write(uint8_t *buf, std::string_view v)
        {
                buf[0] = static_cast<uint8_t>(v.size());
                memcpy(buf + 1, v.data(), v.size());
                return v.size() + 1;
        }
};

/* --- PARTIAL SPECIALISATION - CLASSES ONLY --- */
template<typename T>
struct Serializer<T*> {          /* any pointer */
        static size_t write(uint8_t *buf, T *p)
        {
                return Serializer<T>::write(buf, *p);
        }
};

/* FUNCTIONS CANNOT BE PARTIALLY SPECIALISED. Use overloading,
   or a class template with a static function - which is why
   the standard library's type traits are all classes.    */

/* --- TAG DISPATCH, the pre-concepts way to select an
       implementation --- */
        template<typename It>
        void advance_impl(It& it, int n,
                          std::random_access_iterator_tag)
                { it += n; }

        template<typename It>
        void advance_impl(It& it, int n,
                          std::forward_iterator_tag)
                { while (n--) ++it; }

        template<typename It>
        void advance(It& it, int n)
        {
                advance_impl(it, n,
                    typename std::iterator_traits<It>::
                        iterator_category{});
        }
/* Still worth recognising - the STL is full of it - but
   `if constexpr` and concepts have largely replaced it
   (below).                                                */

if constexpr

Choosing between code paths at compile time used to require elaborate tricks. A compile-time if replaced most of them, and the discarded branch is not even required to compile for the type in question.

/* C++17's most useful template feature: a branch that is
   DISCARDED at compile time, so the untaken side need not
   even be valid for that type.                            */

template<typename T>
size_t serialise(uint8_t *buf, const T& v)
{
        if constexpr (std::is_trivially_copyable_v<T>) {
                memcpy(buf, &v, sizeof(T));
                return sizeof(T);
        } else if constexpr (has_serialise_method_v<T>) {
                return v.serialise(buf);
        } else {
                static_assert(always_false_v<T>,
                              "type is not serialisable");
        }
}

/* WITH A PLAIN `if`, every branch must COMPILE for every T,
   even the ones that never run. With `if constexpr` only the
   taken branch is instantiated - which is what makes it
   usable for dispatching on type properties.

/* AND IN EMBEDDED CONFIGURATION CODE: */
template<bool UseDma>
class Transfer {
public:
        void run(const uint8_t *data, size_t n)
        {
                if constexpr (UseDma) {
                        dma_setup(data, n);
                        dma_start();
                } else {
                        for (size_t i = 0; i < n; i++)
                                poll_write(data[i]);
                }
        }
};
/* Transfer<false> contains NO dma code at all - it is not
   compiled, so it does not exist in the binary. That is how
   you build a configurable driver with no runtime cost and
   no #ifdef.                                              */
if constexpr replaces most #ifdef

An #ifdef hides code from the compiler entirely, so the disabled path is never type-checked and rots silently. if constexpr on a constexpr bool is fully parsed and type-checked in every configuration, discarded only at instantiation. Same generated code, far better maintenance — and it is one of the strongest arguments for C++ over C in configurable firmware.

Concepts

Templates traditionally fail with pages of errors deep inside the implementation. Concepts state the requirements up front, so a violation is reported at the call with a sentence rather than an essay.

/* C++20. Constrain a template, and get an error message that
   names the problem rather than a hundred lines of
   instantiation backtrace.                                */

template<typename T>
concept Serialisable = requires(const T& t, uint8_t *buf) {
        { t.serialise(buf) } -> std::convertible_to<size_t>;
        { T::size } -> std::convertible_to<size_t>;
};

template<Serialisable T>
void send(const T& msg) { ... }

        send(42);
/* ERROR: constraints not satisfied
     because '42' (of type int) does not satisfy
     'Serialisable': the required expression
     't.serialise(buf)' is invalid

   Compare the pre-concepts version, which reported a failure
   deep inside send()'s body across eight levels of
   instantiation.

/* THE STANDARD CONCEPTS worth knowing: */
        std::integral, std::floating_point
        std::same_as, std::convertible_to, std::derived_from
        std::copyable, std::movable, std::default_initializable
        std::invocable, std::predicate
        std::ranges::range, std::ranges::sized_range

/* THREE WAYS TO WRITE A CONSTRAINT, all equivalent: */
        template<std::integral T> void f(T);
        template<typename T> requires std::integral<T> void f(T);
        void f(std::integral auto x);           /* terse */

/* AND CONCEPTS PARTICIPATE IN OVERLOAD RESOLUTION, with the
   MORE CONSTRAINED overload preferred: */
        template<std::integral T>       void g(T);   /* 1 */
        template<typename T>            void g(T);   /* 2 */
        g(42);                  /* 1 - more constrained */
/* Which replaces the enable_if SFINAE machinery entirely, and
   is the main reason to move to C++20 where the toolchain
   allows.                                                 */

/* THE PRE-C++20 EQUIVALENT, which you will still meet: */
        template<typename T,
                 typename = std::enable_if_t<
                        std::is_integral_v<T>>>
        void f(T x);
/* "Substitution Failure Is Not An Error" - if the enable_if
   fails to substitute, the candidate is silently removed
   rather than causing a compile error. Powerful, and the
   source of C++'s worst error messages.                  */

Variadic templates

Templates taking any number of arguments are how type-safe wrappers around variadic C functions are built — giving you the flexibility of printf with actual type checking.

/* Any number of arguments, type-safe, with no varargs. */

template<typename... Args>
void log(const char *fmt, Args&&... args)
{
        format_to(buffer, fmt, std::forward<Args>(args)...);
}

/* FOLD EXPRESSIONS (C++17) - the readable way to process a
   pack: */
        template<typename... Args>
        auto sum(Args... args) { return (args + ...); }
                                        /* unary right fold */

        template<typename... Args>
        bool all_valid(Args... args) { return (args.valid() && ...); }

        template<typename... Args>
        void print_all(Args&&... args)
        {
                ((std::cout << args << ' '), ...);
                                        /* comma fold */
        }

        sizeof...(Args)         /* the number of arguments */

/* A PRACTICAL EMBEDDED USE - a compile-time register field
   builder: */
        template<typename... Fields>
        constexpr uint32_t make_reg(Fields... f)
        {
                return (f.value | ...);
        }
        constexpr auto ctrl = make_reg(Enable{1}, Mode{2},
                                       Prescale{7});
/* Computed entirely at compile time; the result is one
   immediate in the instruction stream.                    */

/* PRE-C++17 RECURSION, which you will still see: */
        void print() {}                         /* base case */
        template<typename T, typename... Rest>
        void print(T first, Rest... rest)
        {
                std::cout << first;
                print(rest...);                 /* recurse */
        }
/* Fold expressions are shorter and compile faster. Use them
   where available.                                        */

The costs

Templates are zero-cost at run time and distinctly not free at build time or in binary size, because each instantiation is separate code. That trade matters on a constrained target.

/* Templates are not free in every dimension. */

/* --- CODE BLOAT --- */
        RingBuffer<uint8_t, 16>
        RingBuffer<uint8_t, 32>
        RingBuffer<uint16_t, 16>
/* THREE COMPLETE COPIES of every member function. On a
   flash-constrained part this adds up quickly.

   MITIGATIONS:
     · factor the type-independent parts into a non-template
       base:                                              */
        class RingBufferBase {          /* no template */
        protected:
                size_t head_, tail_, cap_;
                bool advance(size_t& idx);   /* shared code */
        };
        template<typename T, size_t N>
        class RingBuffer : RingBufferBase { ... };

     /* · use fewer distinct instantiations - prefer one
          capacity where you can
        · -Wl,--icf=all folds byte-identical functions
          (compilers ch. 12)
        · MEASURE: nm --size-sort -S, or bloaty            */

/* --- COMPILE TIME --- */
/* Templates are instantiated in every translation unit that
   uses them, then deduplicated by the linker. Heavy template
   use is the main cause of slow C++ builds.

   MITIGATIONS:
     extern template class RingBuffer<uint8_t, 64>;
     /* in a header - suppress instantiation here */
     template class RingBuffer<uint8_t, 64>;
     /* in ONE .cpp - instantiate it once */
     · -ftime-trace (clang) + speedscope to see where the time
       goes
     · precompiled headers, or C++20 modules if available    */

/* --- ERROR MESSAGES --- */
/* Without concepts, an error inside a template reports at the
   point of failure, not the point of misuse - hundreds of
   lines deep. Use concepts, or static_assert early: */
        template<typename T>
        void f(T x) {
                static_assert(std::is_integral_v<T>,
                              "f requires an integral type");
                ...
        }
/* One clear message instead of a wall.                    */

/* --- DEBUGGING --- */
/* Template names in a debugger and in a backtrace are
   enormous. c++filt and `set print asm-demangle` help;
   type aliases help more:                                 */
        using RxBuffer = RingBuffer<uint8_t, 64>;

CRTP: static polymorphism

Inheriting from a template parameterised on the derived class gives you polymorphism resolved entirely at compile time — the pattern to reach for when virtual dispatch is too expensive.

/* Polymorphism with no vtable and no indirect call - the
   embedded alternative to virtual functions (chapter 11). */

template<typename Derived>
class SensorBase {
public:
        int read() {
                auto raw = self().read_raw();   /* dispatched
                                                   STATICALLY */
                return self().convert(raw);
        }

        void init() {
                self().configure();
                self().calibrate();
        }

private:
        Derived& self() { return static_cast<Derived&>(*this); }
};

class Thermistor : public SensorBase<Thermistor> {
public:
        uint16_t read_raw()          { return adc_read(CH0); }
        int      convert(uint16_t r) { return lookup(r); }
        void     configure()         { adc_init(CH0); }
        void     calibrate()         { }
};

        Thermistor t;
        int temp = t.read();

/* THE GENERATED CODE is fully inlined - read_raw and convert
   are called directly and usually vanish into the caller.
   NO vtable pointer in the object, NO indirect call, and the
   whole chain is optimisable.

/* THE COST: no runtime polymorphism. You cannot have a
   `std::vector<SensorBase*>` of mixed sensor types, because
   SensorBase<Thermistor> and SensorBase<Photodiode> are
   unrelated types.

/* WHEN TO USE WHICH:
     the set of types is KNOWN AT COMPILE TIME  -> CRTP
     the set varies at run time, or you need a
     heterogeneous container                    -> virtual
     you need both                              -> std::variant
                                                   (chapter 15)
*/
