Retrieval-augmented generation

A model knows what was in its training data and nothing else. Retrieval fixes that by putting the right documents into the context before the question — which turns a knowledge problem into a search problem, and moves every hard part of the system into the search.

The problem retrieval actually solves

It is worth being precise about which failure this addresses, because retrieval is routinely deployed against problems it cannot touch, and the disappointment that follows is entirely predictable.

   WHAT A MODEL'S WEIGHTS CANNOT CONTAIN:

     · anything after the training cutoff
     · your company's internal documents
     · this user's data
     · anything that changed since Tuesday

   THE ALTERNATIVES, AND WHY RETRIEVAL USUALLY WINS:

     RETRAIN          correct, and costs millions and months
     FINE-TUNE        teaches STYLE and FORMAT reliably;
                      teaches FACTS unreliably, and gives
                      you no way to cite or update them
     PUT IT IN THE    works, bounded by context length and
     PROMPT           by cost per token
     RETRIEVE THE     put only the RELEVANT part in the
     RELEVANT PART    prompt. This is RAG.

   ---------------------------------------------------------

   WHAT RETRIEVAL DOES NOT FIX, and this is the part people
   discover late:

     · reasoning failures. The right document in context
       does not make the model able to do arithmetic on it.
     · the model IGNORING what you retrieved and answering
       from its weights anyway.
     · questions whose answer is not in ANY document.
     · "summarise all 4000 of our tickets" - retrieval finds
       a handful of documents; it is not an aggregation
       engine. That is a database query.

   THE HONEST SUMMARY: RAG converts a knowledge problem into
   a SEARCH problem. If your search is bad, you have a bad
   system with extra steps and a confident tone.

The pipeline

Every RAG system, however it is dressed up, is these two phases. The offline phase is where the quality is decided; the online phase is where people spend their time.

   OFFLINE - once, or whenever the documents change

     documents
        │  1. PARSE          PDF/HTML/code -> clean text
        │  2. CHUNK          split into retrievable pieces
        │  3. EMBED          each chunk -> a vector (ch. 17)
        │  4. INDEX          store vectors + the original text
        ▼
     vector index

   ONLINE - per query

     question
        │  5. EMBED the question with the SAME model
        │  6. SEARCH for the k nearest chunks
        │  7. RERANK          optional, and usually the
        │                     single highest-value addition
        │  8. ASSEMBLE        chunks + question -> prompt
        ▼
     model  ->  answer + citations

   ---------------------------------------------------------

   STEP 5 HAS A TRAP WORTH NAMING NOW: the question and the
   documents must be embedded by the SAME model. Change the
   embedding model and you must re-index EVERYTHING - the
   old vectors live in a different space and comparing them
   to new ones produces plausible-looking nonsense rather
   than an error.

Chunking, which is where most systems are won or lost

Chunking gets the least attention and causes the most failures. The tension is simple and unavoidable: a chunk must be small enough to be a precise search result and large enough to be a useful answer.

# THE NAIVE APPROACH, and why it disappoints
#   split every 500 characters
#
#   - cuts sentences, tables and code blocks in half
#   - separates a heading from the text it describes
#   - produces chunks whose meaning depends on a
#     neighbouring chunk you did not retrieve

# THE APPROACH THAT ACTUALLY WORKS: split on STRUCTURE
# the document already has, then merge up to a size budget.

def chunk(doc, target=800, overlap=100):
    # 1. Split at the strongest natural boundary available:
    #      markdown headings, then paragraphs, then
    #      sentences. NEVER mid-sentence unless forced.
    units = split_on_headings(doc) or split_on_paragraphs(doc)

    # 2. Merge adjacent units up to the target size, so a
    #    chunk is a coherent passage rather than a fragment.
    chunks = merge_until(units, target)

    # 3. Overlap slightly, so a fact spanning a boundary
    #    survives in at least one chunk intact.
    return with_overlap(chunks, overlap)

# 4. THE STEP EVERYONE SKIPS: prepend the context a human
#    would need to make sense of the chunk on its own.
#
#    BAD  chunk:  "It must be called at PASSIVE_LEVEL."
#                 Retrieved alone, "it" refers to nothing.
#
#    GOOD chunk:  "[Driver Guide > Chapter 4 > WdfRequestSend]
#                  It must be called at PASSIVE_LEVEL."
#
#    The heading path costs a few tokens per chunk and
#    improves both retrieval and the answer, because the
#    chunk now embeds near the topic it belongs to.
The test that tells you your chunking is wrong

Take twenty chunks at random out of your index and read them with no other context, as if someone had handed you a page torn from a book. If you cannot tell what a chunk is about, neither can the embedding model — and a vector that does not represent a clear topic will not be retrieved for the query that needs it. This takes ten minutes and finds more problems than any amount of tuning the number of results you fetch.

Search: why vectors alone are not enough

Embedding search captures meaning and is startlingly bad at exact identifiers — which is precisely what technical questions are full of. The fix is to use both kinds of search rather than choosing.

Vector searchKeyword search (BM25)
FindsMeaning: "car" matches "automobile"Exact terms, including ones it has never seen
Strong onParaphrase, synonyms, questions asked in the user's own wordsError codes, API names, part numbers, rare words
Fails onSTATUS_INVALID_DEVICE_REQUEST — one embedding near every other error nameA question phrased with none of the document's vocabulary
NeedsA model, a GPU or an API, and re-indexing on changeAn inverted index and nothing else

The practical answer is hybrid search: run both, then combine the rankings. Reciprocal rank fusion — scoring each result by the sum of 1/(k + rank) across the two lists — is a few lines, needs no tuning, and is a large improvement over either alone. In a technical corpus full of identifiers, adding keyword search to a vector-only system is usually the biggest single win available.

   AND THEN RERANKING, which is the second-biggest win.

     RETRIEVAL   embeds the query and each document
                 SEPARATELY, then compares vectors. Fast,
                 because the documents were embedded
                 offline. Necessarily approximate, because
                 the document was embedded without knowing
                 the query.

     RERANKING   feeds (query, document) TOGETHER through a
                 smaller model that scores relevance
                 directly. Far more accurate. Far too slow
                 to run over a whole corpus.

   SO: retrieve 50 cheaply, rerank to the best 5, send those.

   THIS IS THE SAME SHAPE AS A CACHE HIERARCHY - a fast
   approximate filter in front of a slow accurate one - and
   it is worth recognising as such.

Assembling the prompt, and citations

Having retrieved well, the remaining job is to make the model answer from the retrieved text rather than around it — and to make it possible to check whether it did.

Answer the question using ONLY the sources below.
Cite the source id for every claim, as [1], [2].
If the sources do not contain the answer, say exactly:
"The provided sources do not answer this."

<sources>
[1] (driver-guide.md > Chapter 4 > WdfRequestSend)
    ...chunk text...

[2] (faq.md > IRQL)
    ...chunk text...
</sources>

Question: {question}

# FOUR DECISIONS ARE ENCODED ABOVE:
#
#  · "ONLY the sources" - reduces, though never eliminates,
#    answering from the weights instead.
#  · AN EXPLICIT REFUSAL STRING - gives the model a licence
#    to decline, and gives YOU something exact to detect.
#  · CITATIONS - the cheapest grounding check available.
#    An answer whose citations do not support it is
#    detectable automatically; an uncited answer is not.
#  · SOURCE IDs WITH PROVENANCE - so a user can go and read
#    the original, which is often the real product.

Debugging a RAG system

When the answer is wrong there are four distinct places it can have gone wrong, and they need completely different fixes. Almost all wasted effort in RAG comes from fixing the wrong one.

   ASK THE QUESTIONS IN THIS ORDER. Stop at the first NO.

   1. IS THE ANSWER IN THE CORPUS AT ALL?
        Search it by hand. If it is not there, no amount of
        retrieval tuning will help. Astonishingly often the
        answer is no.

   2. IS IT IN A SINGLE CHUNK, INTACT?
        Find the chunk. If the fact was split across a
        boundary, fix CHUNKING.

   3. DID RETRIEVAL RETURN THAT CHUNK?
        Log the retrieved ids for every query - if you do
        nothing else in this chapter, do this. If the chunk
        was not returned, fix SEARCH: add keyword search,
        add reranking, retrieve more candidates.

   4. DID THE MODEL USE IT?
        If the right chunk was in context and the answer is
        still wrong, it is a PROMPTING problem (ch. 28) -
        or the context was so long the chunk was ignored.

   ---------------------------------------------------------

   MEASURE 1-3 SEPARATELY FROM 4. "Retrieval recall" - was
   the right chunk in the top k - is a number you can track
   without involving the model at all, and it is the number
   that moves most when you improve the system.

   A SYSTEM WITH 60% RETRIEVAL RECALL HAS A CEILING OF 60%,
   and no prompt will raise it.
