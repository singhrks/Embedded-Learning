Intermediate representations and SSA

The form a compiler thinks in. Static Single Assignment makes data flow explicit, which is what turns most optimisations from difficult analyses into simple graph walks — and it is why modern compilers optimise as well as they do.

Why an IR at all

   Without an IR, supporting L languages on T targets needs
   L * T compilers.

   With one:   L front ends  +  1 optimiser  +  T back ends

   AND THE IR MUST BE:
     · LANGUAGE-NEUTRAL: no C-specific or Rust-specific
       concepts
     · TARGET-NEUTRAL: no x86 or ARM assumptions, at least
       until the back end
     · SIMPLE: few operation kinds, so a pass handles all of
       them
     · ANALYSABLE: data flow and control flow explicit
     · TYPED: enough to reason about sizes and aliasing

   THE LEVELS a compiler passes through:

     HIGH      close to the AST. Types, loops, structured
               control flow. GCC's GENERIC.
        |
     MID       three-address code, basic blocks, SSA.
               Most optimisation happens here.
               GCC's GIMPLE, LLVM IR.
        |
     LOW       close to machine code, but still virtual
               registers. GCC's RTL, LLVM's MachineIR.
        |
     MACHINE   real instructions, real registers.

Three-address code

/* SOURCE: */
        x = (a + b) * (c - d);

/* THREE-ADDRESS CODE - each instruction does ONE operation
   with at most three operands:                            */

        t1 = a + b
        t2 = c - d
        t3 = t1 * t2
        x  = t3

/* THE FORM: `result = operand1 op operand2`. Nested
   expressions become sequences of temporaries.

   WHY: every instruction is independently analysable and
   movable. A tree expression has to be walked; a flat list of
   simple operations can be reordered, deleted, or replaced
   one at a time.

/* THE OPERATION KINDS a mid-level IR needs, and it is a
   short list:
        arithmetic     add sub mul div rem
        bitwise        and or xor shl shr
        comparison     eq ne lt le gt ge
        memory         load store
        control        br  cond_br  ret  switch
        call
        conversion     trunc, extend, bitcast, int-to-float
        address        getelementptr / array_ref

   Everything in every source language reduces to these.  */

Basic blocks and the control flow graph

A BASIC BLOCK is a maximal straight-line sequence:
  - entered only at the first instruction
  - left only at the last

  SOURCE:
      if (a > 0)
              b = 1;
      else
              b = 2;
      c = b + 1;

  CFG:
                 +-------------+
                 | entry:      |
                 |  t = a > 0  |
                 |  br t, L1,L2|
                 +--+-------+--+
                    |       |
              true  |       |  false
                    v       v
            +-------+--+ +--+-------+
            | L1:      | | L2:      |
            |  b1 = 1  | |  b2 = 2  |
            |  br L3   | |  br L3   |
            +-------+--+ +--+-------+
                    |       |
                    +---+---+
                        v
                 +------+--------+
                 | L3:           |
                 |  b3 = phi(...)|
                 |  c = b3 + 1   |
                 +---------------+

  THE CFG IS THE FOUNDATION of every flow analysis:
  reachability, liveness, dominance, loop detection.

  KEY RELATIONSHIPS:
    PREDECESSORS / SUCCESSORS   the edges
    DOMINATES     A dominates B if EVERY path from entry to B
                  passes through A. This is what makes
                  "definition reaches use" decidable, and it is
                  what SSA construction is built on.
    POST-DOMINATES  the mirror image, used for sinking code
    LOOP          a back edge to a dominator
    NATURAL LOOP  a loop with a single entry (a header) -
                  which is what loop optimisations require
                  (chapter 07)

Static Single Assignment

/* THE RULE: every variable is assigned EXACTLY ONCE. Reassign
   and you get a new name.                                  */

/* NOT SSA: */
        x = 1;
        x = x + 1;
        y = x * 2;

/* SSA: */
        x1 = 1
        x2 = x1 + 1
        y1 = x2 * 2

/* WHY THIS IS TRANSFORMATIVE:

   Before SSA, "what value does x have here?" requires a
   dataflow analysis over the whole function - which
   assignments reach this use, along which paths.

   In SSA, x2 has exactly ONE definition, and it is right
   there. THE NAME IS THE ANSWER. Use-def chains become
   pointers rather than analyses.

   CONSTANT PROPAGATION becomes: look at the definition; if
   it is a constant, substitute.
   DEAD CODE ELIMINATION becomes: does this definition have
   any uses? No -> delete.
   VALUE NUMBERING becomes: do two definitions compute the
   same expression from the same operands? -> they are equal.

   Each of these was a whole-function analysis; in SSA they
   are local.                                              */

Phi nodes

/* THE PROBLEM: at a merge point, which definition applies? */

        if (cond)
                x = 1;
        else
                x = 2;
        y = x;          /* which x? */

/* THE SOLUTION: a PHI FUNCTION at the top of the merge
   block, selecting by which predecessor you came from.    */

   entry:
        br cond, L1, L2

   L1:
        x1 = 1
        br L3

   L2:
        x2 = 2
        br L3

   L3:
        x3 = phi [x1, L1], [x2, L2]
        y1 = x3

/* A PHI IS NOT A REAL INSTRUCTION. It is a notation meaning
   "the value depends on the incoming edge". The back end
   removes them by inserting COPIES at the end of each
   predecessor block - "phi elimination" - and then register
   allocation usually makes those copies free by assigning
   x1, x2 and x3 the same register (chapter 09).

/* PHIS ARE ALWAYS AT THE TOP of a block, and they all execute
   "simultaneously" - a phi may reference a value defined by
   another phi in the same block, and the semantics are that
   all read the OLD values. That matters for loop-carried
   dependencies:                                           */

   loop:
        i2 = phi [0, entry], [i3, loop]
        s2 = phi [0, entry], [s3, loop]
        s3 = s2 + i2
        i3 = i2 + 1
        c  = i3 < n
        br c, loop, exit

/* Read that and the loop's structure is completely explicit:
   two loop-carried values, their initial values, and their
   updates. That legibility is why loop optimisations
   (chapter 07) are practical.                            */
Where phi nodes go: the dominance frontier

A phi for variable x is needed in block B exactly when two different definitions of x can reach B along different paths. The precise answer is the iterated dominance frontier of the blocks that define x — the first blocks where a definition's dominance "runs out". Cytron's 1991 algorithm computes this efficiently, and it is what made SSA practical rather than merely elegant.

LLVM IR

; C source:
;     int sum(int *a, int n) {
;             int s = 0;
;             for (int i = 0; i < n; i++)
;                     s += a[i];
;             return s;
;     }

; clang -S -emit-llvm -O1 sum.c -o -

define i32 @sum(ptr noundef %a, i32 noundef %n) {
entry:
  %cmp = icmp sgt i32 %n, 0
  br i1 %cmp, label %loop.preheader, label %exit

loop.preheader:
  %wide.n = zext i32 %n to i64
  br label %loop

loop:
  %i    = phi i64 [ 0, %loop.preheader ], [ %i.next, %loop ]
  %s    = phi i32 [ 0, %loop.preheader ], [ %s.next, %loop ]
  %ptr  = getelementptr inbounds i32, ptr %a, i64 %i
  %v    = load i32, ptr %ptr, align 4
  %s.next = add nsw i32 %s, %v
  %i.next = add nuw nsw i64 %i, 1
  %done = icmp eq i64 %i.next, %wide.n
  br i1 %done, label %exit, label %loop

exit:
  %result = phi i32 [ 0, %entry ], [ %s.next, %loop ]
  ret i32 %result
}

/* READ THE ANNOTATIONS - they carry the optimiser's
   knowledge:

     i32, i64, ptr    explicit types on everything
     %name            an SSA value; %0, %1 for unnamed
     phi              the loop-carried values, explicit
     getelementptr    address computation, type-aware. It
                      knows the element size, so no manual
                      multiply appears.
     inbounds         "this address stays within the object" -
                      a PROMISE from the front end, derived
                      from C's rules. It licenses
                      optimisations that would otherwise be
                      illegal.
     nsw / nuw        "no signed/unsigned wrap" - i.e. signed
                      overflow is UB in C, so the optimiser
                      may assume it does not happen
                      (chapter 15). THIS IS WHERE UB ENTERS
                      THE IR.
     noundef          the argument is not undef or poison
     align 4          the load's alignment

   THE `nsw` FLAG IS THE ONE TO UNDERSTAND. It is how
   "signed overflow is undefined" travels from the C standard
   into the optimiser, and it is why `i + 1 > i` can be folded
   to `true` for signed i but not for unsigned.           */

Memory and the SSA boundary

/* SSA works for SCALARS in registers. Memory is different:
   two pointers might alias, so a store through one may
   change what a load through the other sees. SSA cannot
   express that with names alone.                          */

/* SO CLANG STARTS by putting everything in memory: */

define i32 @f(i32 %x) {
  %x.addr = alloca i32            ; a stack slot
  store i32 %x, ptr %x.addr
  %1 = load i32, ptr %x.addr
  %2 = add i32 %1, 1
  store i32 %2, ptr %x.addr
  %3 = load i32, ptr %x.addr
  ret i32 %3
}

/* ...and then the `mem2reg` (or SROA) pass PROMOTES stack
   slots whose address is never taken into SSA values:     */

define i32 @f(i32 %x) {
  %1 = add i32 %x, 1
  ret i32 %1
}

/* THIS IS WHY `&x` MATTERS FOR PERFORMANCE. Take the address
   of a local and pass it somewhere the compiler cannot see,
   and the variable can no longer be promoted - it must live
   in memory, be reloaded after every call that might modify
   it, and cannot participate in most optimisations.

   THE PRACTICAL RULE: do not take the address of a local
   unless you need to. `int i` in a loop is free; `int i;
   f(&i);` is not.

/* AND FOR MEMORY THAT STAYS IN MEMORY, the optimiser needs
   ALIAS ANALYSIS: can this store affect that load? The
   answers come from
     · type-based rules (strict aliasing - chapter 15)
     · `restrict`, which promises no aliasing
     · escape analysis: an object whose address never leaves
       the function cannot be touched from outside
   and the quality of those answers is most of what separates
   a good optimiser from a mediocre one.                  */

GCC's IRs

# GCC uses several, in sequence:

# GENERIC - a language-independent tree, close to the AST
    gcc -fdump-tree-original test.c

# GIMPLE - three-address, then SSA form
    gcc -fdump-tree-gimple test.c
    gcc -fdump-tree-ssa test.c
    gcc -fdump-tree-optimized test.c    ; after all tree passes

    ;; sum (int * a, int n)
    ;; basic block 3:
    ;;   # i_15 = PHI <0(2), i_11(3)>
    ;;   # s_16 = PHI <0(2), s_10(3)>
    ;;   _1 = (long unsigned int) i_15;
    ;;   _2 = _1 * 4;
    ;;   _3 = a_8(D) + _2;
    ;;   _4 = *_3;
    ;;   s_10 = s_16 + _4;
    ;;   i_11 = i_15 + 1;
    ;;   if (i_11 < n_9(D)) goto bb 3; else goto bb 4;

# NOTE the naming: `i_15` is version 15 of `i` - GCC keeps the
# source name, which makes GIMPLE dumps easier to relate back
# to code than LLVM's numbered values. `(D)` marks a default
# definition, i.e. a parameter.

# RTL - low level, close to machine instructions
    gcc -fdump-rtl-all test.c

# EVERY PASS, in order, with statistics:
    gcc -fdump-tree-all-details test.c
    gcc -fopt-info-all test.c

# THE PRACTICAL USE: when a loop does not optimise as you
# expect, dump `-fdump-tree-optimized` and look at what the
# middle end actually produced. It is frequently obvious in
# the dump and invisible in the assembly.

How it shows up

SymptomCause
A local variable is never in a registerIts address was taken — mem2reg could not promote it
A value is reloaded after every callThe compiler cannot prove the call does not modify it
A loop is not optimisedNot a natural loop, or a memory dependency it cannot disprove
i + 1 > i folds to true for intThe nsw flag — signed overflow is UB (ch. 15)
The same code is faster with restrictAlias analysis could not prove independence without it
Assembly does not match the source at allRead the IR dump — the transformation is visible there
Optimisation differs between GCC and ClangDifferent alias analysis and pass ordering, not a bug in either
Struct fields not kept in registersSROA could not split it — usually because its address escaped
