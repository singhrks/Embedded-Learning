Read it before an interview, before a bring-up, or whenever you come back to ARM after months away.

The eight rules that are never negotiable

Each of these is a rule the hardware enforces, not a style preference
  1. Never change a live translation-table entry in place. Break it, invalidate the TLB, then make the new one. Anything else risks the TLB holding two conflicting entries, which is architecturally unpredictable (ch. 15).
  2. A barrier after a system-register write that changes behaviour. Enabling the MMU, switching tables or changing a trap does not affect instructions already in flight until an ISB (ch. 21).
  3. Clean before the device reads; invalidate after the device writes. Both, in that order, for a bidirectional buffer. This is the whole of DMA correctness (ch. 18).
  4. Device memory is not Normal memory. Choosing a more permissive type than the hardware tolerates produces failures that appear only under load (ch. 11).
  5. Nothing between a load-exclusive and its store-exclusive except the few operations the architecture permits — and always a retry loop, because the reservation may be lost for reasons unrelated to you (ch. 22).
  6. The condition flags are only set when you ask. ADD does not touch them; ADDS does. That explicitness is what lets the compiler reorder freely (ch. 3, 5).
  7. Enable FP and SIMD before any code that might use them. The compiler emits them into code you did not think used floating point, and the trap fires before your console exists (ch. 35).
  8. Read the ID registers; never assume a feature. "ARM" is a family with enormous variation, and the processor will tell you exactly what it implements (ch. 1, 2).

The table to fix first: where code runs and what it may do

Privilege on AArch64 is a numbered ladder crossed with a security state, and almost every question about "can this code do that" resolves to a position in this grid. If you internalise one table on this page, make it this one.

EL2Hypervisor (or the host kernel under VHE)Secure partition manager, if presentStage-2 translation, traps on EL1 (ch. 16, 31)

Two orthogonal axes, not one ladder

Exception level is privilege: EL2 can trap what EL1 does. Security state is a separate bit deciding which copy of the world you are in — separate memory, separate peripherals, separate banked registers. Secure EL1 is not "more privileged than" non-secure EL1; it is the same privilege in a world the non-secure side cannot address at all.

Cache maintenance, reduced to two sequences

Almost all cache maintenance in real drivers is one of two sequences. Learn these two and the direction of each operation, and the rest of chapter 18 becomes reference material rather than something to reason through each time.

   CPU WROTE, DEVICE WILL READ:
        write the buffer
        DC CVAC   (clean to PoC - push it out)
        DSB
        start the device

   DEVICE WROTE, CPU WILL READ:
        start the device, wait for completion
        DC IVAC   (invalidate - discard stale lines)
        DSB
        read the buffer

   BIDIRECTIONAL: clean before, invalidate after.

   WROTE INSTRUCTIONS, WILL EXECUTE THEM:
        DC CVAU  → DSB → IC IVAU → DSB → ISB
        (the data and instruction sides are separate -
         ch. 18)

   AND THE ONE TO REMEMBER ABOUT SCOPE: VA operations
   broadcast to other cores; set/way operations do NOT.
   Set/way is for power-down sequences only, never for
   correctness.                                   (ch. 18)

The bring-up checklist

  • ID registers read, and no feature assumed that they do not report.
  • Vector table installed and VBAR_EL1 set before anything can fault.
  • MAIR and TCR configured before the MMU is enabled.
  • DSB + ISB after every change that alters how translation or trapping behaves.
  • Caches and MMU enabled in the right order, with the caches invalidated first.
  • FP and SIMD enabled — or the build restricted to general registers only.
  • Every live table edit uses break-before-make plus the correct TLB invalidation.
  • DMA buffers have the correct memory type, shareability, and maintenance on both sides.
  • Secondary cores started through PSCI, with their own stacks and translation set up.
  • A fault handler that prints ESR, FAR and ELR exists before you need it.
If you remember only one sentence from this track

The architecture guarantees what is correct, never what is fast — and it guarantees correctness only if you obey the rules about ordering, maintenance and invalidation that a strongly-ordered machine would have hidden from you. Almost every hard ARM bug is code that was correct on a machine that forgave it.
