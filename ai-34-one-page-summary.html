One page: the whole track, for revision

Thirty-three chapters reduced to the facts that change how you read everything else. If a line here does not immediately make sense, that is the chapter to reopen.

The chain, in one page

The track is built bottom-up, and every layer is a short step from the one below it. Being able to walk the chain in both directions is a good test of whether the material has landed.

   A VECTOR is a list of numbers with geometry attached.
   The DOT PRODUCT measures alignment.              (02)

   A MATRIX is a function. MATMUL composes them, and it is
   where all the compute goes.                      (03-04)

   A DERIVATIVE says how the output moves when an input
   moves. The CHAIN RULE composes derivatives, which makes
   BACKPROPAGATION possible on a graph of any size. (06-07)

   CROSS-ENTROPY measures how surprised your predicted
   distribution is by the true one. It is the loss.  (10)

   GRADIENT DESCENT walks downhill on that loss.     (11)

   A NEURAL NETWORK is stacked linear layers with a
   nonlinearity between them.                        (14)

   TOKENISATION turns text into integers. EMBEDDINGS turn
   integers into vectors with geometry.            (16-17)

   ATTENTION lets every position read every other position,
   weighted by content. O(1) path length, fully parallel,
   quadratic cost.                                   (19)

   A TRANSFORMER is attention + feed-forward + residual +
   normalisation, stacked.                        (20-22)

   PRETRAINING is next-token prediction on an enormous
   corpus. Everything the model can do emerges from that
   one objective.                                    (23)

   FINE-TUNING and PREFERENCE LEARNING turn a text
   predictor into an assistant.                      (24)

   INFERENCE is a loop: one forward pass per token, with a
   KV CACHE so the past is not recomputed.           (25)

   QUANTISATION and NPUs make it fit on hardware you can
   hold.                                          (26-27)

   PROMPTING, RETRIEVAL, TOOLS: everything you can change
   once the weights are frozen.                   (28-30)

   EVALUATION and SAFETY decide whether any of it should be
   allowed near a user.                           (31-32)

The numbers worth knowing

Approximate figures, held loosely, that let you sanity-check a claim or size a deployment without looking anything up.

QuantityRule of thumb
Memory for weightsParameters × bytes per parameter. 7B at 4-bit ≈ 3.5 GB; at fp16 ≈ 14 GB
Training memoryRoughly 4× the weights for optimiser state and gradients, before activations
Tokens per wordAbout 1.3 for ordinary English; far worse for code, rare words and non-Latin scripts
Attention costQuadratic in sequence length — doubling the context quadruples this part
Feed-forward costLinear in sequence length, and usually the larger share at short contexts
Parameter splitRoughly two-thirds feed-forward, one-third attention, in a standard block
KV cacheGrows linearly with context and with concurrent users — the usual limit on how many sessions fit
GenerationMemory-bandwidth bound, not compute bound — which is why batching helps so much

Misconceptions this track should have removed

Each of these is believed widely enough to be worth checking against explicitly.

The beliefWhat is actually trueCh.
The model looks things upIt samples a plausible continuation; there is no lookup and no store of known facts32
Confidence indicates correctnessFluency is a property of the model; correctness is not, and both are produced identically32
Lower temperature means more accurateIt means more deterministic. A confidently wrong answer becomes consistently wrong28
It can think longer about a hard tokenComputation per token is fixed; extra reasoning needs extra tokens28
Fine-tuning is how you add knowledgeIt teaches format and style reliably, facts unreliably. Use retrieval for facts29
The model calls the toolIt emits text; your code calls the tool and holds every privilege30
A prompt can stop injectionThe defence must be architectural — the model can always be out-argued in its own input32
Attention is the expensive partAt typical context lengths the feed-forward block usually dominates22
Models are bad at arithmetic because they cannot reasonTokenisation is a large part of it16
Benchmarks tell you if it worksThey compare base models. Only your own eval set says anything about your system31

Symptom to first move

The diagnostic order that finds problems fastest, whether the thing failing is a training run or a deployed application.

SymptomFirst move
Loss is NaNLearning rate too high, or a log of zero — check the loss implementation first
Loss does not moveOverfit a single batch deliberately. If that fails, the bug is in the model or the gradient, not the data
Trains well, generalises badlyOverfitting — regularise, or get more data
Shapes mismatchPrint every shape; do not reason about them
Model output is confidently wrongA facts problem: retrieval, not prompting
Output format keeps driftingShow an example rather than describing the format
Retrieval returns nothing usefulCheck the answer is in the corpus, then in one chunk, then in the top k — in that order
Exact identifiers never retrievedAdd keyword search to the vector search
Agent loops or overspendsNo budget limit; step limits alone are insufficient
Behaviour changed with no deploymentThe provider updated the model — pin the version
Inference is slower than the FLOPs suggestIt is memory bound; look at bandwidth, not compute
Model does not fit on the deviceDo the memory arithmetic before trying anything else

Where to go from here

This track deliberately stops at the point where the foundations are solid. These are the directions that actually reward the next stretch of effort, depending on what you want to do.

   IF YOU WANT TO BUILD PRODUCTS ON MODELS:
     chapters 28-32 are the whole job, and evaluation is
     the part that decides whether you improve. Build the
     twenty-case eval set before anything else.

   IF YOU WANT TO RUN MODELS ON HARDWARE:
     chapters 26-27, then the project (33), then the MCU
     and GPU tracks. The binding constraint is almost
     always memory bandwidth, and that is a systems problem
     you are already equipped for.

   IF YOU WANT TO TRAIN MODELS:
     chapters 23-24, then reimplement the project from
     scratch without looking. Then read papers - with the
     foundations in this track, the architecture sections
     are now readable.

   IF YOU WANT TO WORK ON THE SECURITY OF THESE SYSTEMS:
     chapter 32, then the isolation and TEE tracks. The
     interesting problems are at the boundary between an
     untrusted capable component and a privileged one,
     which those tracks have been describing all along.

   ---------------------------------------------------------

   AND THE HABIT THAT MATTERS MOST, whichever direction you
   pick: implement the thing. The gap between reading about
   backpropagation and writing one is the gap between
   knowing the words and knowing the subject, and it does
   not close by reading more.
