Intra prediction, inter prediction and partitioning

Everything a codec codes is a prediction error. The tools that generate the prediction — directional extrapolation from neighbours, motion vectors into other frames, and the block splitting that chooses where each applies — are where most of the gain from H.264 to AV1 actually came from.

Intra prediction: guessing from neighbours

   JPEG codes each 8x8 block independently. That wastes the
   fact that the pixels immediately above and to the left are
   ALREADY DECODED and are excellent predictors.

     A B C D E F G H     <- reconstructed row above
   I . . . .
   J . . . .             the 4x4 block to predict
   K . . . .
   L . . . .
   ^
   reconstructed column left

   H.264's 4x4 luma modes, all built from those 13 pixels:

     0 VERTICAL      copy A B C D straight down
     1 HORIZONTAL    copy I J K L across
     2 DC            fill with the average of all of them
     3 DIAGONAL DOWN-LEFT
     4 DIAGONAL DOWN-RIGHT
     5 VERTICAL-RIGHT
     6 HORIZONTAL-DOWN
     7 VERTICAL-LEFT
     8 HORIZONTAL-UP

   Nine modes for 4x4, four for 16x16.
   HEVC:  35 modes - DC, PLANAR, and 33 angles.
   AV1:   56 directional modes plus PAETH, SMOOTH, and
          intra block copy.

   PLANAR / SMOOTH deserves a mention: it interpolates a
   gradient across the block rather than copying a direction.
   Skies and soft shading are extremely common and a
   directional copy handles them badly, so planar is one of
   the most-selected modes in real content.

   THE ENCODER TRIES THEM ALL and picks by rate-distortion
   (chapter 6): the mode index costs a few bits, and the
   residual costs what it costs.

   WHY IT MATTERS: on a clean edge, the right directional mode
   makes the residual almost zero. This is the single biggest
   reason an H.264 I-frame is roughly HALF the size of an
   equivalent-quality JPEG.
Prediction uses reconstructed neighbours, not original ones

The encoder must predict from the same pixels the decoder will have — which are the quantised, reconstructed ones, not the source. So every encoder contains a complete decoder inside it, reconstructing each block before coding the next. Get that wrong and encoder and decoder diverge, which is drift: an error that compounds through every subsequent prediction until the picture visibly falls apart.

Partitioning: choosing the block size

   One size cannot fit both a flat wall and a face.

     LARGE blocks   fewer vectors, fewer mode decisions,
                    less overhead. Good on flat or uniformly
                    moving regions.
     SMALL blocks   follow detail and object boundaries.
                    Good at edges. Costs overhead per block.

   H.264   macroblock 16x16, split to 16x8, 8x16, 8x8, and
           8x8 further to 8x4, 4x8, 4x4.

   HEVC    QUADTREE. A 64x64 Coding Tree Unit recursively
           split into four, down to 8x8:

             +---------------+       +-------+-------+
             |               |       |       |   |   |
             |               |  ->   |       +---+---+
             |               |       |       |   |   |
             +---------------+       +---+---+-------+
                                     | | |   |       |
                                     +-+-+   |       |
                                     | | |   |       |
                                     +---+---+-------+

           Flat sky -> one 64x64 block, a handful of bits.
           Detailed foliage -> many 8x8 blocks.
           This alone is worth a large part of HEVC's gain
           over H.264, and it is why HEVC helps most at high
           resolutions - a 4K frame has far more area that is
           locally flat.

   AV1     quadtree PLUS 1:2, 2:1 and 1:4, 4:1 rectangular
           splits, 128x128 down to 4x4. Ten partition types
           per node.

   VVC     quadtree + binary + ternary splits, in any
           combination - the most flexible, and the most
           expensive to search.

   THE COST IS ENCODER TIME. Each additional partition type
   multiplies the search space, and the encoder must
   rate-distortion test them all. This is why HEVC encoding is
   roughly 5-10x slower than H.264 and AV1 slower again, for
   the same picture.

Inter prediction, in detail

/* The modes an encoder chooses between for each block. */

  SKIP / MERGE
      Take the motion vector from a neighbour, code NO
      residual and NO vector - just a flag.
      On static content this is most of the frame, and it is
      why a still shot costs almost nothing.
      HEVC's MERGE builds a candidate list from spatial and
      temporal neighbours; you code only the INDEX.

  INTER with MVD
      A merge candidate as the predictor, plus a coded motion
      vector DIFFERENCE. Coherent motion -> tiny differences.

  BI-PREDICTION
      Two references, averaged (chapter 9).

  INTRA, inside a P or B frame
      Sometimes prediction from a neighbour beats prediction
      from another frame - new content entering the shot,
      an occlusion boundary, a scene with a lot of noise.
      A "P-frame" is full of intra blocks at a scene cut.

/* THE CANDIDATE LIST IS THE INTERESTING PART. Coding a full
   motion vector costs 10-20 bits. Coding "use candidate 1"
   costs 1-2. So codecs spend real design effort on making the
   candidate list contain the right answer:

     spatial neighbours    left, above, above-right,
                           below-left, above-left
     temporal              the co-located block in a
                           previously coded frame
     history-based (AV1/VVC)  a rolling table of recently
                           used vectors anywhere in the frame
     pairwise average      the mean of two other candidates

   When the list is good, most blocks cost a few bits total.
   That is where modern codecs beat older ones far more than
   in the transform.                                        */

More tools means slower, not automatically better

AV1 has roughly ten times H.264's decision space. An encoder that searches it badly — a fast preset, or an immature implementation — can produce worse output than a well-tuned H.264 encoder at the same speed. The format sets the ceiling; the encoder's search decides how close you get. This is why "AV1 is 30% better" is only true at slow presets, and why x264 --preset veryslow beats SVT-AV1 --preset 12 at equal encoding time.
