Memory attributes and cacheability under virtualisation

Two independent pieces of software now describe the same byte of memory, and the hardware combines their opinions with a rule neither of them chose. Most "impossible" virtualisation bugs — a guest that boots but corrupts data, a device that reads zeroes, an exclusive that never succeeds — live here.

The combining rule

When two stages each specify a memory type, the hardware combines them by a fixed rule that always favours the more restrictive. A guest therefore cannot demand cacheability the hypervisor did not grant.

   For every access, the CPU has TWO opinions about the memory:

     stage 1 attribute   (guest's MAIR_EL1 + descriptor AttrIndx)
     stage 2 attribute   (hypervisor's descriptor MemAttr[3:0])

   and it must produce ONE. The rule is "most restrictive wins":

     TYPE           Device beats Normal
     CACHEABILITY   Non-cacheable beats Write-Through
                    Write-Through   beats Write-Back
     SHAREABILITY   Outer beats Inner beats Non-shareable
     DEVICE STRENGTH nGnRnE beats nGnRE beats nGRE beats GRE

   Worked cases:

     s1 Normal WB, s2 Normal WB      -> Normal WB       (good)
     s1 Normal WB, s2 Normal NC      -> Normal NC       (slow)
     s1 Normal WB, s2 Device-nGnRE   -> Device-nGnRE    (broken)
     s1 Device,    s2 Normal WB      -> Device          (fine)
     s1 Normal WB, s2 Device-nGnRnE  -> Device-nGnRnE   (very broken)

   The GUEST cannot escape upward. It can only make things
   stricter than the hypervisor allowed - never looser.

   Which means: if the hypervisor gets stage 2 wrong, the guest
   has NO WAY to compensate, and its own page tables will look
   completely correct while it misbehaves.
The asymmetry that matters

Isolation only requires stage 2 to restrict permissions. Restricting memory type is a side effect of the same mechanism, and it is almost never what you want for ordinary RAM. Map guest RAM as Normal, Inner-Shareable, Write-Back at stage 2 and let the guest decide. Anything else is a bug waiting for a workload.

An arm64 Linux guest whose RAM is Device at stage 2 will typically boot — early boot code is careful and aligned — and then die the moment the C library uses an optimised memcpy, or the moment futex takes an exclusive. The symptom looks like memory corruption or a scheduler hang, and nothing in the guest points at the real cause.

FWB: making the guest's opinion irrelevant

ARMv8.4-S2FWB ("stage-2 force write-back") changes the rule from combine to override. It exists because the combining rule made a whole class of hypervisor bugs unavoidable.

/* Without FWB, the hypervisor has a problem it cannot solve:

   The guest boots with its MMU OFF. All its accesses are
   therefore Device-nGnRnE (that is the architectural default
   when stage 1 is disabled). The hypervisor, meanwhile, has
   the page mapped Normal cacheable and has written the kernel
   image into it THROUGH THE CACHE.

   Guest reads with MMU off  -> Device -> bypasses the cache
                             -> reads STALE DRAM
                             -> reads garbage instead of the
                                kernel it was given.

   Historic fixes, both unpleasant:
     a) HCR_EL2.DC = 1: force the guest's stage-1-disabled
        accesses to be treated as Normal cacheable. Works, but
        it lies to a guest that genuinely wanted Device access
        to a real device before enabling its MMU.
     b) The hypervisor cleans the entire guest image to the
        point of coherency before every VM entry where the
        guest MMU is off. Correct and very slow.              */

/* With HCR_EL2.FWB = 1:

     stage 2 MemAttr is no longer combined - it WINS.

     s2 MemAttr = 0b0110  ->  Normal, Write-Back, whatever
                              stage 1 says. Including when
                              stage 1 is disabled.
     s2 MemAttr = 0b0101  ->  Normal, Non-Cacheable, forced
     s2 MemAttr = 0b0001  ->  Device-nGnRE, forced

   The hypervisor now states the truth once, in one place, and
   the guest's stage-1 attributes only affect ordering and
   sharing - not cacheability. KVM enables FWB whenever the
   silicon has it, and a large amount of cache-maintenance code
   becomes dead.                                              */

Who cleans the cache, and when

Cache maintenance under virtualisation is a question of division of labour, and the answer changes depending on who mapped the memory and how.

   Three participants, three different views of memory:

     the GUEST      writes through its cache
     the HYPERVISOR writes through its cache (a different
                    virtual mapping of the same physical page!)
     a DEVICE doing DMA  may or may not be coherent

   ALIASING: the hypervisor maps guest RAM into its own address
   space to load a kernel image, to emulate a device, or to
   migrate the VM. That is a SECOND virtual mapping of the same
   physical memory, potentially with different attributes. On
   ARM, mismatched attributes for the same physical address are
   architecturally UNPREDICTABLE - not merely slow.

   The rules that keep you safe:

   1. Hypervisor and guest should both use Normal WB Inner-
      Shareable for RAM. Then the coherent interconnect handles
      it and NO maintenance is needed.

   2. If the hypervisor writes guest memory while the guest's
      MMU is off (loading a kernel), it must either
        - clean to the Point of Coherency afterwards, or
        - rely on HCR_EL2.DC / FWB.

   3. If a NON-COHERENT device will read that memory, someone
      must clean it. Under passthrough this is the GUEST'S
      driver, and it works - the guest's DC CVAC operates on
      the right physical lines because stage 2 translated the
      address.

   4. Never map the same page as Device in one place and Normal
      in another. This is the mismatched-attribute rule, and
      the failure is silent and rare enough to reach
      production.
The mismatched-alias bug

A hypervisor maps a guest's framebuffer as Device (because it came from a PCI BAR) while the guest maps it Normal Non-Cacheable (because that is what framebuffers want). Both mappings are "reasonable"; together they are architecturally unpredictable. Symptoms: tearing, occasional wrong pixels, and behaviour that changes with CPU model. Fix the hypervisor mapping, not the guest.

HCR_EL2.DC and the boot window

One bit exists almost entirely for the window between reset and the guest enabling its MMU, and it causes confusing behaviour if you do not know it is there.

/* The window: from "hypervisor ERETs into the guest" to
   "guest sets SCTLR_EL1.M = 1". Perhaps a few thousand
   instructions, and every one of them is dangerous.        */

  HCR_EL2.DC = 1   effect while the guest's stage-1 MMU is OFF:

     the guest's accesses are treated as
         Normal, Inner-Shareable, Write-Back Read/Write-Allocate
     instead of
         Device-nGnRnE

     and stage 1 is forced to behave as if disabled anyway.

  WHY YOU WANT IT:
     the hypervisor wrote the kernel image through its cache;
     the guest can now read it coherently without anyone
     performing cache maintenance.

  WHY IT IS NOT FREE:
     a guest that legitimately wants to touch a real device
     before enabling its MMU now does so through the cache.
     For most guests this never happens. For a bare-metal
     payload that pokes a UART before MMU setup, it does -
     and the character never appears.

  KVM's actual policy (simplified):
     if FWB is available          -> use FWB, leave DC clear
     else if guest MMU is off     -> set DC
     else                         -> clear DC
   and it re-evaluates on every trap that could have changed
   SCTLR_EL1.M. That is one reason KVM traps SCTLR_EL1 writes
   on hardware without FWB, and does not on hardware with it. */

Checking what a guest really got

What a guest asked for and what it got can differ, and there are direct ways to find out which — worth doing before blaming a driver.

# From the HOST, dump KVM's stage-2 view. (Requires
# CONFIG_PTDUMP_DEBUGFS and a debug kernel; not all builds.)
$ sudo ls /sys/kernel/debug/kvm/
  1234-5/    # one directory per VM

# From the GUEST, look at what stage 1 asked for:
$ sudo cat /sys/kernel/debug/kernel_page_tables | head -20

# The practical test, from inside the guest - does it BEHAVE
# like Normal memory?

$ cat > attrtest.c <<'EOF'
#include <stdio.h>
#include <stdint.h>
int main(void) {
        static _Alignas(64) uint8_t buf[128];
        /* 1. unaligned access - faults on Device memory */
        volatile uint32_t *p = (uint32_t *)(buf + 1);
        *p = 0xdeadbeef;
        printf("unaligned ok: %08x\n", *p);

        /* 2. exclusives - never succeed on Device memory */
        uint32_t v = 0;
        int ok = __atomic_compare_exchange_n(&v, &(uint32_t){0}, 1,
                        0, __ATOMIC_SEQ_CST, __ATOMIC_SEQ_CST);
        printf("cas ok: %d\n", ok);
        return 0;
}
EOF
$ gcc attrtest.c -o attrtest && ./attrtest
unaligned ok: deadbeef
cas ok: 1

# A SIGBUS on test 1, or cas ok: 0 forever, means your RAM is
# not Normal memory. That is a stage-2 problem, in the host.

# Throughput is the blunt instrument that finds it fastest:
$ dd if=/dev/zero of=/dev/null bs=1M count=2000
# GB/s = Normal.  Tens of MB/s = Device. There is no middle.

Attributes for passed-through devices

A real device imposes attribute requirements of its own, and getting these wrong produces corruption rather than a fault.

/* When you assign a real device to a guest (chapter 17), its
   MMIO region must be Device at BOTH stages.               */

   stage 2: MemAttr = 0b0001  Device-nGnRE
            S2AP    = 0b11    read/write
            XN      = 1       never execute a device register

/* Getting this wrong in the permissive direction is the
   dangerous one: mapping a device region as Normal cacheable
   at stage 2 means

     - writes sit in the cache and reach the device late,
       out of order, or merged
     - the CPU may SPECULATIVELY READ device registers, which
       for many devices has side effects (clear-on-read status,
       FIFO pop). A speculative read can dequeue data nobody
       asked for.

   That last one is not theoretical. Speculatively reading a
   UART's RX FIFO loses characters that were never delivered to
   anyone. Always XN and always Device for MMIO.             */

/* And the reverse for the DMA buffers that device will use:
   they are ordinary RAM and must be Normal. A common bring-up
   mistake is to map an entire "device" range - registers AND
   the shared descriptor ring - as Device, then wonder why
   throughput is dreadful.                                   */
