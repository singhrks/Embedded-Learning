Boot, the Session Manager and services

By the time you see a desktop, four distinct processes — none of them called explorer.exe — have already done the work of turning firmware into a usable, multi-user operating system. This chapter is that sequence, and where a driver actually gets loaded along the way.

From firmware to desktop

Before you see a desktop, several programs have already run and handed control onward. This chain matters practically: when a machine fails to boot, where it stopped tells you which component failed, and each is diagnosed differently.

SMSS spawns a copy of itself for every new session, then exits

The Session Manager's role is easy to misread from Task Manager, where it appears not to be running at all after boot completes. What actually happens is that the master smss.exe spawns a child copy of itself to initialise each session — including Session 0 and every interactive session created afterward — and each child smss.exe exits once it has finished setting that session up, handing off to wininit.exe or csrss.exe as appropriate. So SMSS is not a long-running daemon; it is closer to a one-shot initialiser that runs once per session and then disappears, which is exactly why a memory dump taken well after boot rarely shows it.

Session 0 isolation: why services cannot show you a dialog box

This is the rule that surprises every developer who tries to make a service show a message box. Services run in a session that has no interactive desktop at all — and that isolation was introduced to close a real, exploited class of attack.

   BEFORE VISTA, SERVICES RAN IN SESSION 0 ALONGSIDE THE
   FIRST INTERACTIVE USER. A service could create a window
   or a dialog, and it would appear on the console session's
   desktop - the "shatter attack" surface this created (a
   lower-privileged interactive user sending window messages
   to a higher-privileged service's window) was a genuine,
   exploited security problem.

   SESSION 0 ISOLATION (Vista onward) makes Session 0
   NON-INTERACTIVE, permanently. Services still run there,
   but:

     - Session 0 has its own \BaseNamedObjects, its own
       \DosDevices (chapter 31) - so named objects a service
       creates do not collide with, or get confused with,
       identically-named objects a logged-on user's
       processes create
     - a service that tries to show a UI element gets
       redirected to an interactive services detection
       notification instead (on older systems) or is simply
       never seen at all (current systems) - it is NOT
       "shown but on a hidden desktop the user could switch
       to"; the isolation is a real, structural process and
       namespace boundary, not a display trick

   EVERY INTERACTIVE USER LOGS ON INTO SESSION 1 OR HIGHER
   - each with its own object namespace, its own instance of
   csrss.exe and winlogon.exe. This is also the exact
   mechanism that lets Remote Desktop and Fast User
   Switching give each simultaneously logged-on user a fully
   independent desktop and namespace on one machine.

The Service Control Manager: what a "service" actually is

A Windows service is not a special kind of program; it is an ordinary one supervised by another ordinary process, configured through exactly the same registry keys drivers use. Seeing that shared machinery makes both easier to reason about.

   SERVICES.EXE IS THE SCM - ITSELF AN ORDINARY WIN32
   PROCESS, running in Session 0, whose entire job is
   starting, stopping, and supervising OTHER processes and
   drivers according to the SAME registry service-key format
   drivers use (chapter 20's Start/Type values are literally
   shared with Win32 services - the two are more alike than
   most developers realise).

   HKLM\SYSTEM\CurrentControlSet\Services\<name>
        Type      1  = kernel driver
                  2  = file system driver
                  16 = own process (a normal Win32 service)
                  32 = shared process (svchost.exe hosting
                       several services together, the reason
                       Task Manager shows many svchost.exe
                       instances each hosting a different
                       group of services)
        Start     0  = Boot   (loaded by WINLOAD, before the
                              I/O manager is even fully up)
                  1  = System (loaded by the I/O manager
                              during its own init)
                  2  = Auto   (started by the SCM automatically
                              at boot)
                  3  = Demand (started on request - by the
                              SCM, or by a user, or by another
                              service depending on it)
                  4  = Disabled

   THE SCM PROCESSES DEPENDENCIES: a service listing another
   as a DependOnService will not be started until its
   dependency has started successfully - the same ordering
   problem a driver's own load order solves via the Start
   value, just one layer higher, among user-mode services
   rather than kernel drivers.
PS> Get-Service -Name mydriver | Select-Object *
PS> sc.exe qc mydriver              # query configuration:
                                    # Type, Start, dependencies
PS> sc.exe query mydriver           # current runtime state

Where a driver actually enters this timeline

A Plug-and-Play-enumerated driver (the overwhelming majority of hardware drivers, covered from chapter 06 onward) does not load at a fixed point in this boot sequence at all — it loads whenever the Plug and Play manager, itself started as part of the executive's initialisation, enumerates the bus and discovers the device that driver is bound to, which can happen during boot for built-in hardware or much later, on demand, the moment a USB device is plugged in. A Boot- or System-start driver, by contrast, is exactly the kind of driver that must exist before Plug and Play enumeration can even begin — a storage controller driver is the canonical example, since without it the disk holding the rest of the operating system cannot be read at all.
