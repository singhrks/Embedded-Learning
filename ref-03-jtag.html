JTAG, SWD and hardware debug

A side channel into the processor that works before any software runs. When the board is dead, the boot loops, or the fault handler fires before a single character reaches the UART, this is the only tool you have.

What the debug port is

   THE DEBUG PORT IS HARDWARE INSIDE THE CHIP, independent
   of the CPU's execution. It can:

     · HALT and RESUME the core
     · READ AND WRITE registers and memory - THROUGH THE
       BUS, so it works even when the CPU is halted or
       stuck
     · SET BREAKPOINTS in flash (hardware comparators)
     · SET WATCHPOINTS on data addresses
     · STEP single instructions
     · RESET the chip, and HALT BEFORE THE FIRST
       INSTRUCTION
     · program flash
     · and stream TRACE

   THAT LAST-BUT-ONE POINT IS THE IMPORTANT ONE: "connect
   under reset" lets you attach to a chip whose firmware
   immediately disables the debug pins, sleeps, or crashes.
   It is how you recover a board you have bricked with your
   own code.

   JTAG (IEEE 1149.1) - the original, 4-5 pins:
     TCK   clock
     TMS   mode select (drives a state machine)
     TDI   data in
     TDO   data out
     TRST  reset (optional)
   DAISY-CHAINABLE: several devices on one chain, which is
   why it is still used on FPGAs and multi-chip boards. It
   also does BOUNDARY SCAN - toggling and reading individual
   package pins to test solder joints, independently of the
   CPU.

   SWD (Serial Wire Debug) - ARM's 2-pin replacement:
     SWDIO  bidirectional data
     SWCLK  clock
     (+ SWO, optional, for trace output)

   SAME CAPABILITY, TWO PINS. Universal on Cortex-M, and
   what you will use in practice.

   THE CONNECTOR, and it matters when the board arrives:
     10-pin 1.27mm Cortex Debug     the modern standard
     20-pin 2.54mm ARM JTAG         older, bulky
     TC2050 "tag-connect"           no connector at all -
                                    spring pins on pads.
                                    COSTS NOTHING IN BOM
                                    AND SAVES YOU EVERY
                                    TIME.

   PUT A DEBUG CONNECTOR ON EVERY BOARD YOU DESIGN. Even
   production ones - use tag-connect pads, and disable the
   port in firmware for shipping units (see below).

Probes and the software stack

/* --- THE PROBES --- */
    SEGGER J-Link       the reference. Fast flash
                        programming, RTT (chapter 02),
                        excellent target support. The EDU
                        version is inexpensive for
                        non-commercial use.
    ST-LINK             on every Nucleo and Discovery
                        board. Fine for STM32.
    CMSIS-DAP / DAPLink open standard, on many dev boards.
                        Slower, universal.
    Black Magic Probe   runs the GDB SERVER ON THE PROBE -
                        connect GDB directly to a serial
                        port, no OpenOCD needed.
    Vendor probes       Lauterbach TRACE32 and iSYSTEM at
                        the high end: full instruction
                        trace, expensive, and worth it for
                        a team debugging hard timing
                        problems.

/* --- THE SOFTWARE STACK --- */

    GDB  <--TCP:3333-->  OpenOCD / JLinkGDBServer
                              |
                              v  (USB)
                            PROBE
                              |
                              v  (SWD/JTAG)
                            TARGET

    THE GDB SERVER translates GDB's remote protocol into
    probe commands. Understanding that there are three
    separate pieces is most of what makes connection
    failures diagnosable.

/* --- OPENOCD --- */
    $ openocd -f interface/stlink.cfg \
              -f target/stm32f4x.cfg

    Open On-Chip Debugger. Supports hundreds of targets and
    dozens of probes. Its telnet interface (port 4444) is
    useful on its own:

      $ telnet localhost 4444
      > reset halt
      > mdw 0x40021000 4       # read 4 words
      > mww 0x40020014 0x20    # write a word
      > flash write_image erase firmware.elf
      > reg                    # dump all registers

    READING AND WRITING PERIPHERAL REGISTERS BY HAND, with
    the CPU halted, is an extremely direct way to answer
    "is this peripheral configured the way I think?"

/* --- A CONNECTION THAT FAILS --- */
    "Error: init mode failed (unable to connect to the
     target)"

    THE CHECKLIST, in order:
      1. POWER. Is the target powered? Measure it.
      2. GROUND. Is the probe's ground connected? A missing
         ground is the most common cause.
      3. WIRING. SWDIO and SWCLK to the right pins, not
         swapped.
      4. RESET. Try "connect under reset" - firmware may be
         disabling the debug pins or entering sleep.
      5. PIN REUSE. Did your code reconfigure PA13/PA14 as
         GPIO? That kills SWD. Connect under reset and
         erase.
      6. LOW POWER MODE. Deep sleep gates the debug clock.
         Set the DBGMCU standby/stop bits to keep it alive.
      7. READOUT PROTECTION. If RDP is set, the port is
         disabled by design. A mass erase may be the only
         way back - and at RDP level 2, there is no way
         back.
      8. TARGET SPEED. Drop the adapter clock to 100 kHz
         and retry; long wires and slow crystals both
         matter.
      9. CLOCK. Is the target's crystal actually
         oscillating? Scope it.                          */

GDB, the parts you need

$ arm-none-eabi-gdb firmware.elf
(gdb) target extended-remote localhost:3333
(gdb) monitor reset halt     # "monitor" passes to OpenOCD
(gdb) load                   # flash the image
(gdb) break main
(gdb) continue

# ---- BREAKPOINTS ----
break main                   # by function
break i2c.c:214              # by file:line
break *0x08001234            # by address
break i2c_xfer if addr==0x50 # CONDITIONAL - and note it
                             # is evaluated by GDB, so it
                             # halts EVERY time and is slow
tbreak setup                 # temporary, one shot
info breakpoints
delete 2

# NOTE: A CORTEX-M HAS ONLY 4-8 HARDWARE BREAKPOINTS,
# because code is in flash and cannot be patched with a
# software trap. Exceed the limit and GDB reports a failure
# to set one. Delete the ones you are not using.

# ---- WATCHPOINTS: the most underused feature ----
watch g_state               # break when it is WRITTEN
rwatch g_config             # when READ
awatch g_flag               # either
watch *(uint32_t*)0x20001000

# "SOMETHING IS CORRUPTING THIS VARIABLE AND I CANNOT FIND
# WHAT" IS EXACTLY WHAT A WATCHPOINT IS FOR. Set it, run,
# and the debugger stops at the instruction that did it and
# shows you the backtrace. This turns a two-day bug into a
# two-minute one, and most people never use it.
#
# Hardware watchpoints are also limited (typically 4) and
# they watch an ADDRESS RANGE, so watching a whole struct
# may need several.

# ---- EXECUTION ----
continue / c
next / n           # step over calls
step / s           # step into
finish             # run until the current function returns
until 250          # run until line 250

# ---- STATE ----
print var
print/x reg                 # hex
print *ptr
print arr[0]@16             # ARTIFICIAL ARRAY: 16 elements
                            # from arr[0]. Extremely useful.
print sizeof(struct foo)
x/16xb 0x20000000           # 16 hex bytes
x/8xw 0x40021000            # 8 hex words - a peripheral
x/i $pc                     # the instruction at PC
x/20i $pc                   # disassemble forward
info registers
info locals
info args
backtrace / bt
bt full                     # with locals at each frame
frame 2                     # switch frames
set var x = 5               # MODIFY state and continue

# ---- WHEN THERE IS NO BACKTRACE ----
# After a hard fault the stack may be unwindable only
# manually. See chapter 06 for reading the fault registers
# and the stacked frame.

# ---- SCRIPTING: put this in .gdbinit ----
define reload
  monitor reset halt
  load
  monitor reset halt
end

define regs
  printf "PC=%08x LR=%08x SP=%08x\n", $pc, $lr, $sp
end

# ---- TUI ----
# Ctrl-X A, or start with `gdb -tui`. Source, registers and
# disassembly in one terminal. layout split, layout regs.
The three things a debugger does that nothing else can 
1. WATCHPOINTS. Catch the instruction that corrupts
   a variable, with a backtrace.
2. CONNECT UNDER RESET. Reach a chip whose firmware
   is hostile to debugging — including your own
   bricked board.
3. READ PERIPHERAL REGISTERS ON A HALTED CORE.
   Answer "is this actually configured?" directly,
   without trusting any code you wrote.

Trace, and what it buys

/* ARM CoreSight, the units and what each is for: */

    DWT   Data Watchpoint and Trace
            · a CYCLE COUNTER - free, precise timing
            · watchpoints
            · PC sampling for a statistical profile
            · exception tracing
    ITM   Instrumentation Trace Macrocell
            · software-generated messages, single-cycle
              cost (chapter 02)
    ETM   Embedded Trace Macrocell
            · FULL INSTRUCTION TRACE. Every instruction
              executed, reconstructible offline.
    TPIU  Trace Port Interface Unit
            · streams it out, over SWO (1 pin, slow) or a
              4-bit parallel TRACE port (fast, needs a
              proper probe)

/* --- THE CYCLE COUNTER: use this constantly --- */
    /* enable once */
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;

    /* measure anything */
    uint32_t t0 = DWT->CYCCNT;
    function_under_test();
    uint32_t cycles = DWT->CYCCNT - t0;
    /* the subtraction is correct across wraparound,
       for unsigned arithmetic (see the C track) */

    NANOSECOND-RESOLUTION TIMING, no probe required, a few
    lines of setup. IF YOU MEASURE ANYTHING ON A CORTEX-M,
    MEASURE IT WITH THIS.

/* --- FULL INSTRUCTION TRACE (ETM) --- */
    Records every branch, so a host tool can reconstruct the
    exact execution path - thousands of instructions before
    a crash, with no instrumentation and no timing
    perturbation.

    WHAT IT SOLVES THAT NOTHING ELSE DOES:
      · "how did we get to this address?"
      · a corrupted stack with no backtrace
      · a race whose interleaving you cannot otherwise see
      · code coverage on the real target
      · exact cycle-accurate profiling

    THE COST: a probe that supports it (J-Trace,
    Lauterbach, iSYSTEM) and a board that routes the trace
    pins. ROUTE THEM. Adding four pins at schematic time
    costs nothing; adding them after a failure costs a board
    spin.

/* --- ETW/perf EQUIVALENTS --- */
    On Linux and Windows you have perf and ETW instead
    (chapters 04, 05) - same idea, done in software with
    hardware performance counters.                       */

Debug ports and security

/* A DEBUG PORT IS COMPLETE ACCESS TO THE DEVICE. Read all
   memory, read the keys, modify execution, dump the
   firmware. On a shipped product that is a serious
   vulnerability, and leaving it open is one of the most
   common findings in any hardware teardown (see the
   cryptography track, chapter 21).

/* --- THE LIFECYCLE APPROACH --- */
    DEVELOPMENT   debug open, test keys only
    PRODUCTION    debug DISABLED via a one-way fuse or a
                  protection level, production keys
                  provisioned
    RMA           if debug can be re-enabled at all, THE
                  TRANSITION MUST ERASE ALL SECRETS FIRST

/* --- THE MECHANISMS, by vendor --- */
    STM32          RDP levels 0/1/2. Level 2 is PERMANENT -
                   there is no way back, and no way to
                   debug a returned unit.
    nRF            APPROTECT. Note that early revisions were
                   defeated by a voltage glitch, which is a
                   useful reminder that a protection bit is
                   only as strong as its enforcement
                   (cryptography chapter 19).
    ARMv8-M /
    TrustZone-M    debug authentication with SEPARATE
                   secure and non-secure permissions - you
                   can allow non-secure debug while keeping
                   the secure world closed. This is the
                   right model.
    ADAC           an ARM standard for AUTHENTICATED debug:
                   the port stays physically present but
                   requires a signed challenge-response to
                   unlock, so the vendor can debug a
                   returned unit and an attacker cannot.

/* --- AND THE PRACTICAL ADVICE --- */
      · DO put a debug connector on production boards -
        tag-connect pads cost nothing
      · DO disable the port in the production firmware
        configuration
      · DO verify on an actual production unit that it is
        disabled. "We set the fuse in the build script" is
        not evidence; probing a shipping unit is.
      · DO plan the RMA path before you ship, and make it
        erase
      · and prefer AUTHENTICATED debug over permanent
        lockout if the silicon supports it - a fleet you
        cannot diagnose is its own kind of problem.    */

How it shows up

SymptomCause
Cannot connect to the targetWork the nine-step checklist — ground and connect-under-reset first
Connects once, then never againFirmware reconfigured the SWD pins — connect under reset and erase
Connection drops when the device sleepsDebug clock gated — set the DBGMCU low-power bits
"Cannot set breakpoint"Hardware breakpoints exhausted — delete unused ones
Watchpoint has no effectWatching a range larger than the comparator covers
