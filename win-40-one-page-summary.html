The whole track compressed to what you actually need in your head. Nothing here teaches a concept for the first time — every line is a reminder with a chapter number attached, so the moment one stops making sense you know exactly where to go. Read it before an interview, before a code review, or whenever you return to driver work after months away.

The seven rules that are never negotiable

Break any of these and the machine, not your process, pays for it
  1. Know your IRQL before every call. It decides what you may touch, what you may allocate and whether you may block. Almost every rule below is a consequence of it (ch. 03).
  2. Match the pool to the IRQL. Anything a DPC, ISR or spinlock holder can reach must be non-paged. Paged memory touched at DISPATCH_LEVEL is an instant bugcheck (ch. 07).
  3. Never trust a user buffer. Validate every length, choose the buffering method deliberately, and never assume the user address space is even mapped when you run (ch. 08 · 09).
  4. Complete every request exactly once. Not zero times, not twice. Ownership between the completion and cancellation paths is exclusive (ch. 16).
  5. Check every NTSTATUS. Use NT_SUCCESS(), never a comparison against zero, and propagate rather than inventing a status (ch. 05).
  6. Undo in reverse, and test it. Unload and surprise removal are the least-exercised paths in any driver and the most likely to bugcheck (ch. 15).
  7. Your IOCTL codes and device interface are permanent. Applications in the field depend on them; internal kernel APIs, by contrast, are not stable (ch. 17).

The question to ask before every single call

"What IRQL am I at, and can this function be called there?" The documentation states a Maximum IRQL for every DDI, and a driver that consults it habitually writes very few of the bugs in this track. When you cannot tell what IRQL you are at, KeGetCurrentIrql() answers it, and Driver Verifier's IRQL checking answers it permanently.

The pre-review checklist

  • Every allocation's pool type matches the highest IRQL that touches it.
  • Every NTSTATUS checked with NT_SUCCESS(); failures propagate.
  • Every request completed exactly once, on every path including cancellation and error.
  • Every user-supplied length validated before it is used in arithmetic or a copy.
  • No paged memory or paged code reachable from a DPC, timer or ISR.
  • Locking documented: which lock protects which field, and at which IRQL it is taken.
  • Unload and surprise removal actually exercised, not just reasoned about.
  • Tested under verifier /standard plus special pool, not only a release build.
  • Every pool allocation uses your own four-character tag.
  • IOCTL codes use the correct buffering method and are treated as a permanent contract.
If you remember only one sentence from this track

Kernel code runs with no process boundary underneath it, at an IRQL that silently changes what you are allowed to do, in several contexts at once — so the discipline that feels excessive in an application (check every status, know your IRQL, own each request exactly once, unwind precisely) is not style here. It is the entire difference between a driver that ships and a machine that bugchecks.
