Native versus cross compilation

The Pi is fast enough to compile its own software, which is unusual for an embedded target and tempting for exactly that reason. It is still the wrong default for anything large — and knowing precisely where the boundary falls saves hours every week.

Three machines, and the words for them

   BUILD   the machine running the compiler
   HOST    the machine the output will RUN on
   TARGET  what the output itself compiles for
           (only meaningful when building a compiler)

   NATIVE          build == host        x86_64 -> x86_64
                                        Pi     -> Pi

   CROSS           build != host        x86_64 -> aarch64
                                        your laptop building
                                        for the Pi

   The triplet names them:  aarch64-linux-gnu
                            ^       ^     ^
                            arch    OS    libc/ABI

   Common ones you will meet:
     aarch64-linux-gnu       64-bit Pi, glibc      <- this
     arm-linux-gnueabihf     32-bit Pi, hard float
     aarch64-none-elf        bare metal, no OS     (ch 20)
     arm-none-eabi           Cortex-M              (mcu track)

   THE SUFFIX MATTERS. aarch64-none-elf has no libc and no
   syscalls; aarch64-linux-gnu assumes Linux and glibc.
   Using the bare-metal toolchain for a Linux program gives
   you a binary that links but cannot start.

Which to use

TaskUseWhy
A single .c file, a script, a quick testNativeCompile time is a second; setup cost of cross is not worth it
A userspace program with a few dependenciesNativeapt install lib…-dev and it just works. Dependency resolution is the hard part of cross
An out-of-tree kernel moduleEitherNative is far simpler; cross is faster once set up (chapter 16)
The kernelCross~10 min on a laptop against ~1–2 h native on a Pi 4 (chapter 15)
Anything in CICrossBuild machines are x86; reproducibility matters more than convenience
A full OS image (Yocto/Buildroot)CrossNative is not realistic at all
C++ with heavy templatesCrossThis is where the Pi's slower cores and limited RAM hurt most
The honest rule

Start native. It removes an entire class of problem — sysroots, library paths, ABI mismatches — while you are still learning what the code should do. Move to cross the moment build time becomes the thing you are waiting for, which in practice means when you start building kernels. Many experienced people develop userspace natively on the Pi for years and never regret it; nobody builds kernels natively twice.

Native, done well

# The Pi compiles its own userspace perfectly well. Two
# things make it noticeably better:

# 1. USE ALL FOUR CORES, but bound by RAM, not cores. Each
#    gcc process can take hundreds of megabytes; -j4 on a
#    1 GB Pi will invoke the OOM killer mid-build.
$ make -j$(nproc)                    # 4 GB+ board
$ make -j2                           # 1-2 GB board

# 2. GIVE IT SWAP if RAM is tight - on a USB SSD, never on
#    the SD card (write endurance, chapter 19):
$ sudo dphys-swapfile swapoff
$ sudo sed -i 's/^CONF_SWAPSIZE=.*/CONF_SWAPSIZE=2048/' \
      /etc/dphys-swapfile
$ sudo dphys-swapfile setup && sudo dphys-swapfile swapon

# 3. ccache turns a rebuild after a one-line change from
#    minutes into seconds:
$ sudo apt install ccache
$ export PATH="/usr/lib/ccache:$PATH"
$ ccache -M 5G

# 4. BUILD ON FAST STORAGE. An SD card is the bottleneck for
#    a large build far more often than the CPU. A USB 3 SSD
#    (or NVMe on a Pi 5) roughly halves real build times.

# -march: the Pi's own gcc already targets the right core,
# but be explicit when it matters:
#   Pi 4 (A72):  -mcpu=cortex-a72
#   Pi 5 (A76):  -mcpu=cortex-a76
# -mcpu=native works and is what most people use natively.
# Do NOT ship a binary built with -mcpu=native to a
# different Pi model; it may use instructions the older
# core lacks (chapter 02's feature table).

Cross, done properly

# On a Debian/Ubuntu host:
$ sudo apt install gcc-aarch64-linux-gnu g++-aarch64-linux-gnu

# The simple case - no external libraries - just works:
$ aarch64-linux-gnu-gcc -O2 -o blink blink.c
$ file blink
blink: ELF 64-bit LSB pie executable, ARM aarch64, ...
$ scp blink pi:~/

# THE HARD CASE is anything that links a library. The
# compiler needs the TARGET's headers and .so files, not
# your host's. That collection is a SYSROOT.

# Build one by copying the relevant parts off the Pi. The
# -L flag preserves symlinks as symlinks, which matters
# because libfoo.so -> libfoo.so.1.2.3 chains must survive:
$ mkdir -p ~/pi-sysroot
$ rsync -aL --info=progress2 \
    pi:/lib pi:/usr/include pi:/usr/lib \
    ~/pi-sysroot/

# Then point the compiler at it:
$ aarch64-linux-gnu-gcc \
    --sysroot=$HOME/pi-sysroot \
    -I$HOME/pi-sysroot/usr/include \
    -L$HOME/pi-sysroot/usr/lib/aarch64-linux-gnu \
    -Wl,-rpath-link=$HOME/pi-sysroot/usr/lib/aarch64-linux-gnu \
    -o sensor sensor.c -lgpiod

# THE SYSROOT MUST MATCH THE PI. If you apt upgrade the Pi
# and not the sysroot, you will link against headers for one
# libc version and run against another. The failures are
# subtle: a struct that changed size, a symbol version
# mismatch at load time. RE-SYNC THE SYSROOT whenever you
# update the board.

# CMake wants a toolchain file rather than flags:
cat > aarch64-pi.cmake <<'EOF'
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_SYSROOT $ENV{HOME}/pi-sysroot)
set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)
# Look for programs on the HOST, libraries and headers in
# the SYSROOT. Getting these four lines wrong is why
# cross-CMake finds your host's libraries and links a binary
# that cannot possibly run on the target.
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
EOF
$ cmake -B build -DCMAKE_TOOLCHAIN_FILE=aarch64-pi.cmake
The classic cross-compilation failure

The build succeeds, you copy the binary across, and it dies with cannot execute binary file or a missing shared object. Three causes, in order of likelihood: the toolchain was the bare-metal one (-none-elf) rather than the Linux one; CMake found host libraries because the FIND_ROOT_PATH_MODE lines were missing; or the sysroot is older than the Pi. Check with file on the host and ldd on the target before assuming anything about your code.

The third option: emulated native

# Run an aarch64 container on your x86 laptop, with qemu-
# user-static translating instructions. You get native-style
# builds - apt install works, dependencies resolve - with
# your laptop's storage and RAM.

$ docker run --rm --privileged \
      multiarch/qemu-user-static --reset -p yes
$ docker run --rm -it -v "$PWD":/src -w /src \
      arm64v8/debian:bookworm bash
# inside:
#   apt update && apt install -y build-essential libgpiod-dev
#   gcc -O2 -o sensor sensor.c -lgpiod

# WHEN THIS IS THE RIGHT ANSWER:
#   - a package with a tangled dependency tree that is
#     painful to sysroot
#   - reproducible builds in CI without a Pi in the loop
#   - you need the target's exact library versions

# WHEN IT IS NOT:
#   - emulation is 5-20x slower than native x86, so it is
#     no faster than building on the Pi itself for big
#     projects
#   - anything that touches real hardware obviously cannot
#     be tested here

# The comparison, roughly, for a medium userspace project:
#   cross on laptop      1x     (fastest, hardest setup)
#   emulated container   8x     (easy setup, slow)
#   native on Pi 5      10x     (easiest, needs the board)
#   native on Pi 4      20x
