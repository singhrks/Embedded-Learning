TrustZone: the two worlds and EL3

One bit splits the machine into two parallel software stacks, each with its own exception levels, page tables and interrupts. Between them sits EL3 — the only code that exists in both, and the most security-critical software on the chip.

The full picture

The complete arrangement — two worlds, four exception levels, and the monitor that switches between them — in one place. Everything else in this chapter is a detail hung off this structure.

   NORMAL WORLD (NS=1)              SECURE WORLD (NS=0)
   ===================              ===================

   EL0  applications                S-EL0  trusted applications
        browser, banking app               keymaster, DRM,
        games                              fingerprint matcher

        Linux, Windows                     OP-TEE, Trusty, QSEE

  EL3 belongs to NEITHER world. It is the gatekeeper.

Why put anything in the secure world

Before any mechanism, the design question: what belongs in a secure world at all. The answer is narrower than most projects assume, and putting too much there is itself a security problem.

ReasonConcretely
The rich OS is too big to trust30 M lines with a continuous CVE stream. Assume compromise; keep the secrets elsewhere.
Some secrets must survive kernel compromiseAttestation keys, disk encryption keys, DRM keys, biometric templates, payment credentials
Some operations need a trusted path"Confirm this payment" must display on a screen the normal world cannot fake and read input it cannot inject
Boot integrity needs an anchorSecure boot verification runs before the normal world exists at all
Certification requirementPayment, DRM and eSIM schemes mandate a certified TEE or secure element

What EL3 actually does

The secure monitor is the only software that sees both worlds, which makes it both the mechanism that makes TrustZone work and the most security-critical code on the device.

/* BL31 — the resident EL3 firmware — has four jobs and should
   have no others.                                            */

/* 1. WORLD SWITCHING. Save one world's state, flip SCR_EL3.NS,
      restore the other's, ERET. Chapter 11.                  */

/* 2. SMC DISPATCH. Decode the function ID and route it:
        PSCI            power management (ARM chapter 33)
        SiP             silicon-vendor-specific services
        Trusted OS      forward to S-EL1
        Standard        Arm-defined services (SDEI, RAS, TRNG)  */

/* 3. SECURE INTERRUPT ROUTING. SCR_EL3.{IRQ,FIQ,EA} decide
      which interrupts come to EL3 rather than the current
      world.                                                   */

/* 4. PLATFORM INITIALISATION that must happen once, at the
      highest privilege: TZASC regions, TZPC assignments, SMMU
      secure configuration — then LOCK them.                   */

/* What EL3 must NOT do:
     · parse untrusted input
     · implement a filesystem, a network stack, or crypto
       protocols beyond what boot verification needs
     · grow. TF-A's BL31 is tens of thousands of lines and that
       is a deliberate ceiling.

   Every line at EL3 can compromise BOTH worlds. It is the one
   place where "keep it small" is not a style preference.   */

SCR_EL3

BitNameEffect
0NSThe security state of the world below. 0 = Secure, 1 = Non-secure.
1IRQRoute IRQ to EL3
2FIQRoute FIQ to EL3 — normally set, so secure interrupts reach the monitor
3EARoute External Aborts and SError to EL3
7SMDDisable SMC entirely — it becomes undefined
8HCEEnable HVC. Cleared means no hypervisor calls.
10RWExecution state below: 1 = AArch64
11STAllow secure EL1 access to the secure timer
12/13TWI/TWETrap WFI/WFE to EL3
18SIFSecure Instruction Fetch: forbid the secure world fetching instructions from Non-secure memory
19EEL2Enable Secure EL2 (ARMv8.4+)
SCR_EL3.SIF is a defence worth knowing

Without it, secure software tricked into branching to a Non-secure address would execute normal-world code with secure privilege — total compromise from one corrupted function pointer. Setting SIF makes such a fetch fault. It is the secure world's equivalent of PXN on user pages (ARM 14), and it should always be set.

Who implements what

Several trusted OS implementations exist, differing in licensing, certification and scale. Which one a device uses is usually decided by the silicon vendor rather than by the product team.

Secure EL2 and partitions

Newer implementations add a hypervisor level inside the secure world, which allows several mutually distrusting secure partitions rather than one monolithic trusted OS.

The original design had ONE secure OS. That is a problem when
several vendors each want a trusted component:

   a payment applet from a bank
   a DRM component from a content provider
   a biometric matcher from the OEM
   an eSIM applet from a carrier

  With one S-EL1 OS, all four are mutually trusting. A bug in
  any one compromises the others — and the whole secure world.

  ARMv8.4's SECURE EL2 fixes this: a Secure Partition Manager at
  S-EL2 gives each component its own stage-2 translation, so
  they are isolated from each other exactly as VMs are.

   S-EL0   TA          TA          TA
   S-EL1   [partition A] [partition B] [partition C]
   S-EL2   Secure Partition Manager (Hafnium)
                stage-2 isolation between partitions
   EL3     monitor

  FF-A standardises the messaging between partitions and the
  normal world, replacing the vendor-specific SMC interfaces
  that came before.

  Practically: it is how a modern phone runs several vendors'
  trusted code without any of them reading the others' keys.

Shared memory: the interesting part

The two worlds must exchange data, and the region they share is the most security-sensitive memory on the device — it is the one place normal-world input reaches secure-world code.

/* The two worlds must exchange data. The pattern is always the
   same, and getting it wrong is the classic TEE vulnerability. */

/* 1. The NORMAL world allocates a buffer in NON-SECURE memory */
        shm = tee_shm_alloc(ctx, size, TEE_SHM_MAPPED | TEE_SHM_DMA_BUF);

/* 2. It passes the PHYSICAL ADDRESS in the SMC arguments      */

/* 3. The SECURE world maps it with NS=1 in its own page tables
      (chapter 08) and copies data in and out.                 */
Secure code must never trust a normal-world pointer

Before dereferencing an address supplied by the normal world, secure software must verify that the entire range lies inside non-secure memory. Otherwise the normal world hands the TEE a pointer to secure memory and has the TEE read or write it on its behalf.

That is a confused deputy attack, and it is behind a substantial number of real TEE CVEs. The check must cover the whole range and must handle integer overflow in base + length.

static bool ns_range_ok(paddr_t base, size_t len)
{
        paddr_t end;

        if (len == 0)                      return false;
        if (ADD_OVERFLOW(base, len, &end)) return false;  /* wrap! */
        if (!core_pbuf_is(CORE_MEM_NON_SEC, base, len))
                return false;              /* the WHOLE range */
        return true;
}
/* And the TOCTOU rule: COPY FIRST, then validate the copy.

   WRONG — validating shared memory in place: */
        if (req->len > MAX)  return TEE_ERROR_BAD_PARAMETERS;
        process(req->buf, req->len);
        /* the normal world can change req->len between the two
           reads, because it still has the memory mapped       */

/* RIGHT — one copy into secure memory, then validate: */
        struct req local;
        memcpy(&local, ns_req, sizeof local);   /* from NS memory */
        if (local.len > MAX)  return TEE_ERROR_BAD_PARAMETERS;
        process(local.buf, local.len);          /* the COPY       */

What a world switch costs

A world switch is a full context switch through the most privileged software on the chip, twice. Knowing roughly what it costs is what stops a design from putting a secure call in a hot path.

   SMC instruction                        ~20 cycles
   exception entry to EL3                 ~30 cycles
   save the outgoing world's state        ~200-1000 cycles
     X0-X30, FP/SIMD if used, any
     non-banked system registers
   dispatch the function ID               ~50 cycles
   restore the incoming world's state     ~200-1000 cycles
   ERET                                   ~20 cycles
   ---------------------------------------------------
   ONE WAY                                ~500-2000 cycles

   A round trip is 1,000-10,000 cycles, and on most designs the
   calling core is unavailable for the whole period.

  CONSEQUENCES for design:
     · never put an SMC in a hot path
     · BATCH work into one call rather than many small ones
     · never call from an interrupt handler or with a spinlock
       held
     · a TEE operation needed at high frequency is probably in
       the wrong place

  Compare: a system call is ~50-500 ns; a VM exit ~500-2000
  cycles. A world switch is the most expensive boundary
  crossing on the chip.

Interrupts across the boundary

Interrupts must be routed to the correct world, and an interrupt arriving while the other world is executing needs handling that neither world can subvert. That routing is part of the GIC's security model.

/* The GIC assigns every interrupt to a GROUP (ARM chapter 23),
   and the group plus SCR_EL3 routing decides where it lands.  */

   Group 0            -> FIQ, always to EL3
                         secure firmware's own interrupts
   Secure Group 1     -> IRQ in the secure world,
                         FIQ in the non-secure world
                         the trusted OS's interrupts
   Non-secure Group 1 -> IRQ
                         the normal OS's interrupts

/* THE KEY PROPERTY: a Non-secure OS clearing PSTATE.I cannot
   mask secure interrupts, because they arrive as FIQ and route
   to EL3. The secure world can ALWAYS preempt the normal world.

   That is what makes a TEE's timing guarantees meaningful.  */

/* The reverse case: a normal-world interrupt arriving while the
   SECURE world is running. The monitor must either
     · hold it until the secure operation completes — simple,
       but adds latency to the normal world, or
     · return to the normal world with an "operation preempted,
       call again" status, so long secure operations do not
       block the OS.

   OP-TEE does the latter, via RPC returns. That is why a TEE
   call can return a retry status the client must handle.   */

Running the whole stack on QEMU

All of this can be run without special hardware, which makes it far more approachable than its reputation suggests.

# A complete TrustZone system — TF-A at EL3, OP-TEE at S-EL1,
# Linux at EL1 — on your laptop, no hardware needed. The single
# best way to make this chapter concrete.

mkdir optee && cd optee
repo init -u https://github.com/OP-TEE/manifest.git -m qemu_v8.xml
repo sync -j8
cd build
make toolchains -j4
make run -j$(nproc)

# TWO consoles appear: the normal world (Linux) and the secure
# world (OP-TEE's log). Watch both.

# in the Linux console:
xtest                          # the OP-TEE conformance suite
optee_example_hello_world
optee_example_secure_storage
optee_example_acipher

# Watch the SECURE console while running these: the TA loading,
# the command dispatch, and the return, live.
Read optee_examples/hello_world/

About 150 lines split between a normal-world client (TEE Client API) and a Trusted Application (with TA_InvokeCommandEntryPoint). Tracing one command through both halves — client, ioctl, driver, SMC, monitor, trusted OS, TA, and back — teaches more than any amount of reading.
