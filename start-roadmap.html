The learning roadmap

599 chapters is a lot of map. This page is the route through it: what to read in what order, how long each stage honestly takes, and the test that tells you a stage is finished.

The organising principle

Every track on this site answers one of four questions, and they must be answered in this order:

QuestionTracksWhy it comes when it does
What is the machine?Computer architecture, ARMEvery abstraction above this is a lie told for convenience. You cannot debug a lie you do not know is one.
How do I express myself to it?C, C++, Rust, CompilersLanguages are how you address the machine; the compiler is the translator whose assumptions you must share.
Who manages the machine?Operating systems, Linux, WindowsAn OS is a set of policies over the hardware. Learn the hardware, then the policy.
How do I keep it safe?Isolation and security, CryptographyIsolation is meaningless before you understand what is being isolated from what.
What sits above the kernel?Virtualisation, OP-TEE, QEMUA hypervisor and a trusted OS both use a privilege level the kernel cannot reach, so they come after you know what a kernel does. QEMU is the board you develop both on.

The AI track sits outside this ordering. It teaches its own mathematics and depends on the rest of the site only where performance meets hardware — memory bandwidth, quantisation, accelerators.

Eight phases

Phase 0 — Prerequisites (0–4 weeks)

Take the self-assessment. If you fail the C section, do the C track first and nothing else. Everything on this site is written in C or described in terms of it.

Exit test: you can write a function that packs three bitfields into a 32-bit word using shifts and masks, and explain why the compiler might reorder your two writes to a hardware register.

Phase 1 — The machine (4–7 weeks)

Computer architecture, all 20 chapters. This is the biggest single jump in the whole curriculum, and skipping it is why most self-taught engineers plateau.

Exit test: explain why a program that touches an array with stride 64 runs several times slower than one with stride 1, in terms of cache lines and prefetchers.

Phase 2 — The language, properly (4–6 weeks)

C in full, then the first half of compilers (chapters 01–06). Do these together: the compiler track explains why the C track's rules exist.

Exit test: given a small C function, predict its assembly, then check with gcc -O2 -S and explain every difference.

Phase 3 — The ARM architecture (5–8 weeks)

ARM, all 39 chapters. Long, but each chapter is one concept and they build tightly. Do not skip the memory-model chapters (20–22); they are where the hard bugs live.

Exit test: given a 48-bit virtual address and a set of table base registers, trace by hand which bits index which level of the page table, and say what happens at each possible failure point.

Phase 4 — Operating systems (4–6 weeks)

Operating systems for the vendor-neutral concepts, then pick Linux or Windows as your primary and skim the other. Both end in a complete driver you build.

Exit test: your driver deadlocks under load. Describe the tools and the order you would use them in, without opening a debugger first.

Phase 5 — Isolation and security (4–6 weeks)

Isolation and security, then cryptography. This is the part most engineers never reach, and it is what separates a driver writer from a platform engineer.

Exit test: a device DMAs to an address and faults. Name five distinct layers that could have produced that fault and the register you would read in each case.

Phase 6 — The two worlds and the machine underneath (5–8 weeks)

Two tracks that both start from the same place — an exception level above EL1 — and go in opposite directions. Virtualisation uses EL2 to run several kernels that each believe they are alone; OP-TEE uses the secure world to run one thing that the kernel cannot touch. Read QEMU alongside either: it is the board you develop both on, and it is short.

The virtualisation track needs phase 5's SMMU material for device passthrough. The OP-TEE track needs phase 5's TrustZone material and a working grasp of cryptography before its projects.

Exit test: write a trusted application and the client that drives it, then explain — with the register that enforces it — why the normal world cannot read the key it holds.

Phase 7 — Breadth and depth (ongoing)

  • C++ or Rust, depending on where your industry is going. Rust if you want to be ahead of it.
  • The second half of compilers — linking, loading, debug info.
  • AI and LLMs, at any point; it is self-contained.
  • Read real driver source. Bring up a real board. Send a patch upstream.

These numbers assume you are building, not only reading

Reading a chapter takes fifteen minutes. Understanding it takes an hour of doing something with it — compiling the example, changing it until it breaks, and explaining the break. The timeline above assumes roughly one part reading to three parts hands-on. Halve the hands-on and you double the calendar time, because you will re-read everything.

Four ways people stall

Collecting boards

A Raspberry Pi, a BeagleBone and three dev kits in a drawer is not progress. One board, broken and recovered ten times, teaches more than five untouched ones. Everything here runs in QEMU anyway.

Reading the ARM ARM cover to cover

It is over 10,000 pages of reference material, not a textbook. Use it to answer a question you already have. That is what this site's ARM track is for: it gives you the questions.

Skipping the memory model

Barriers, coherency and cache maintenance feel like optional detail right up until you have a bug that only reproduces on four cores under load. That bug costs a week. Those chapters cost a day.

Writing drivers without reading drivers

The kernel already contains a near-exact template for whatever you are writing. Professionals find it and adapt it. Search drivers/ before you start typing.

Interview preparation runs alongside, not instead

The DSA interview prep track sits outside the seven phases deliberately. It is not a prerequisite for anything here, and nothing here is a prerequisite for it — it exists because getting the job and doing the job are measured differently, and the gap between them is real.

Start it when you have interviews booked, not before. Two to eight weeks is the usual window, and the track opens with a schedule for each. It shares the C track's assumptions about pointers and arrays and nothing else, so it can be read at any point.

The one genuine overlap is worth naming: the complexity reasoning in chapter 02 — amortised analysis, reading constraints backwards, knowing what an operation actually costs — is the same skill that tells you whether a driver's hot path is acceptable. That chapter earns its place regardless of whether you are interviewing.

Milestones worth naming

  • Junior: you can write a working driver by adapting an existing one, and debug it with prints and a datasheet.
  • Intermediate: you can read an unfamiliar subsystem and explain its locking, and you reach for the right tool before the debugger.
  • Senior: you can look at an unfamiliar SoC's technical reference manual and, in an hour, identify its interconnect topology, DMA masters, isolation blocks and boot flow.
  • Beyond: other people bring you the bugs nobody else could reproduce, and you have a method rather than a hunch.
