Building and installing the Pi kernel

Building your own kernel is the point at which the Pi stops being an appliance. You need it to enable a config option, to patch a driver, to add tracing, or simply to know that you can — and the Pi's build is unusually approachable because the tree, the config and the install path are all documented and small.

When you actually need to

GoalDo you need a kernel build?
Load your own moduleNo — kernel headers are enough (chapter 16)
Add a device tree overlayNo — dtc alone (chapter 10)
Enable a driver that is not builtYes, unless it is already a loadable module
Turn on a debug or tracing optionYes — most are compile-time
Patch a driver's sourceYes
Try PREEMPT_RTYes
Bisect a regressionYes, repeatedly — cross-compile

Check first whether the thing you want is already a module you can simply load: modprobe <name>, or look in /lib/modules/$(uname -r)/kernel/. A great many "I need to rebuild the kernel" problems are one modprobe away.

Getting the source

# The Raspberry Pi kernel is a FORK of mainline with
# board-specific drivers and patches. Use it, not
# kernel.org, unless you know precisely why not.

$ git clone --depth=1 --branch rpi-6.6.y \
      https://github.com/raspberrypi/linux

# MATCH THE BRANCH TO WHAT YOU ARE RUNNING, or your out-of-
# tree modules will not load against the running kernel:
$ uname -r
6.6.51+rpt-rpi-2712
$ zcat /proc/config.gz | head -5      # if CONFIG_IKCONFIG_PROC
$ cat /proc/version

# --depth=1 saves a large download. Drop it if you intend to
# bisect or read history.

# THE EXACT COMMIT your running kernel was built from:
$ zgrep "Linux version" /var/log/kern.log | head -1
# or, on Raspberry Pi OS:
$ dpkg -l | grep raspberrypi-kernel
# The firmware repo records kernel commit hashes per release
# if you need to reproduce a specific build exactly.

Cross-compiling, which is what you want

# On an x86 host: roughly 10-20 minutes with make -j16.
# Natively on a Pi 4: 1-2 hours. On a Pi 5: 40-60 minutes.
# The setup cost of cross is paid back on the first rebuild.

$ sudo apt install crossbuild-essential-arm64 \
      bc bison flex libssl-dev make libc6-dev libncurses5-dev

$ cd linux
$ export ARCH=arm64
$ export CROSS_COMPILE=aarch64-linux-gnu-

# THE DEFCONFIG IS PER BOARD:
$ make bcm2711_defconfig      # Pi 4, Pi 400, CM4
$ make bcm2712_defconfig      # Pi 5

# Using the wrong one produces a kernel that will not boot,
# usually with no output at all.

# START FROM YOUR RUNNING CONFIG instead, which is safer -
# it guarantees you keep every option the working kernel
# had:
$ scp pi:/proc/config.gz .
$ zcat config.gz > .config
$ make olddefconfig           # fill in new options with
                              # defaults, no prompts

# Change what you came for:
$ make menuconfig
#   '/' searches. Type the symbol name (e.g. FTRACE) and it
#   shows where it lives and what it depends on - which is
#   how you find out why an option is greyed out.

# BUILD. Image.gz is the compressed kernel; modules and
# dtbs are both needed.
$ make -j$(nproc) Image.gz modules dtbs

# Output:
#   arch/arm64/boot/Image.gz
#   arch/arm64/boot/dts/broadcom/*.dtb
#   arch/arm64/boot/dts/overlays/*.dtbo

Installing it without losing the board

# THE RULE: never overwrite the working kernel. Install
# alongside it and select with config.txt, so a bad build is
# a one-line edit from another machine rather than a
# reimage (chapter 09's recovery habit).

# --- install modules into a staging directory ---
$ make -j$(nproc) INSTALL_MOD_PATH=./staging modules_install
$ cd staging && tar czf ../modules.tar.gz lib && cd ..

# --- copy everything across ---
$ scp arch/arm64/boot/Image.gz pi:/tmp/kernel-test.img
$ scp arch/arm64/boot/dts/broadcom/bcm2712-rpi-5-b.dtb pi:/tmp/
$ scp arch/arm64/boot/dts/overlays/*.dtbo pi:/tmp/overlays/
$ scp modules.tar.gz pi:/tmp/

# --- on the Pi ---
$ sudo tar xzf /tmp/modules.tar.gz -C /
$ sudo cp /tmp/kernel-test.img /boot/firmware/
$ sudo cp /tmp/bcm2712-rpi-5-b.dtb /boot/firmware/
$ sudo cp /tmp/overlays/*.dtbo /boot/firmware/overlays/

# --- select it, WITHOUT removing the old one ---
$ sudo cp /boot/firmware/config.txt /boot/firmware/config.txt.good
$ echo "kernel=kernel-test.img" | sudo tee -a /boot/firmware/config.txt
$ sudo reboot

# --- verify ---
$ uname -a
$ dmesg | head

# --- IF IT DOES NOT BOOT ---
# Power off, pull the card, mount the FAT partition on your
# laptop, and either delete the kernel= line or restore
# config.txt.good. Ninety seconds, no reimage. This is why
# the "install alongside" rule matters.

# MODULE VERSION MUST MATCH. If /lib/modules/$(uname -r)
# does not exist for the new kernel, nothing loads and you
# get a barely-functional system. The modules_install step
# above is not optional.
Two settings that make a development kernel far more useful

While you are in menuconfig, turn on CONFIG_IKCONFIG and CONFIG_IKCONFIG_PROC so the running kernel carries its own configuration at /proc/config.gz — which means you can always reproduce a build from a board rather than guessing. Add CONFIG_DEBUG_INFO and CONFIG_DEBUG_INFO_DWARF5 if you intend to use kgdb or decode oops addresses precisely (chapter 17), accepting that the build gets much larger and slower.

Building on the Pi

# Slower, but simpler - no toolchain, no staging, no scp,
# and modules install straight into the running system.

$ sudo apt install git bc bison flex libssl-dev \
      libncurses5-dev
$ git clone --depth=1 --branch rpi-6.6.y \
      https://github.com/raspberrypi/linux
$ cd linux
$ make bcm2712_defconfig                # or bcm2711
$ make -j4 Image.gz modules dtbs        # 40 min - 2 h

$ sudo make -j4 modules_install
$ sudo cp arch/arm64/boot/Image.gz /boot/firmware/kernel-test.img
$ sudo cp arch/arm64/boot/dts/broadcom/*.dtb /boot/firmware/
$ sudo cp arch/arm64/boot/dts/overlays/*.dtbo /boot/firmware/overlays/

# BUILD ON FAST STORAGE. A kernel build is hundreds of
# thousands of small file operations; an SD card is the
# bottleneck long before the CPU is. USB 3 SSD or NVMe
# roughly halves the time, and spares the card's write
# endurance (chapter 19).

# ccache helps enormously on rebuilds after a small change:
$ sudo apt install ccache
$ make -j4 CC="ccache gcc" Image.gz modules

Options worth knowing about

# --- TRACING AND DEBUG (chapter 17) ---
CONFIG_FTRACE=y
CONFIG_FUNCTION_TRACER=y
CONFIG_DYNAMIC_DEBUG=y            # pr_debug at runtime
CONFIG_KPROBES=y
CONFIG_DEBUG_INFO=y
CONFIG_MAGIC_SYSRQ=y              # chapter 05's SysRq keys

# --- MEMORY BUG DETECTION - excellent for module work ---
CONFIG_KASAN=y                    # address sanitizer, in
                                  # the kernel. Slow and
                                  # memory-hungry, and it
                                  # will find your module's
                                  # buffer overrun on the
                                  # first run.
CONFIG_DEBUG_KMEMLEAK=y
CONFIG_PROVE_LOCKING=y            # lockdep: proves your
                                  # locking order is sound.
                                  # Turn this on before
                                  # writing chapter 21's
                                  # driver, not after.
CONFIG_DEBUG_ATOMIC_SLEEP=y       # catches sleeping in
                                  # atomic context - the
                                  # classic driver bug

# --- REAL TIME (chapter 13) ---
CONFIG_PREEMPT_RT=y               # needs the RT branch;
                                  # measure with cyclictest
                                  # before and after

# A DEBUG KERNEL IS SLOW - KASAN and lockdep together can
# halve throughput. That is the correct trade during
# development and the wrong one in production. Keep two
# kernels installed and switch with config.txt.
