ISRs, DPCs and work items

Windows splits interrupt handling into three tiers by IRQL: a tiny ISR at device level, a DPC at dispatch level, and a work item at passive level. Knowing which tier each piece of work belongs to is the core skill of interrupt-driven driver design.

The three tiers

Interrupt handling is split across three levels of urgency, and the split exists for one reason: the time spent in your interrupt handler is added directly to the worst-case latency of the entire machine. Each tier trades immediacy for freedom.

   device raises its interrupt
        |
        v
   ISR                              at DIRQL
     · acknowledge the hardware, stop it re-asserting
     · read the minimum state you need
     · queue a DPC
     · RETURN. Target: under a few microseconds.
     · CANNOT: touch paged memory, allocate paged pool,
       wait, block, call most APIs
        |
        v
   DPC                              at DISPATCH_LEVEL
     · the real work: parse data, complete requests, start
       the next transfer
     · CAN: complete IRPs, use spinlocks, allocate non-paged
       pool, queue work items
     · CANNOT: touch paged memory, wait, block
     · Target: tens of microseconds. Over ~100us and you are
       hurting system latency; the DPC watchdog fires at
       around 20ms.
        |
        v
   WORK ITEM                        at PASSIVE_LEVEL
     · anything that must sleep: registry access, file I/O,
       waiting on an event, sending a request to another
       driver, allocating paged pool
     · runs on a system worker thread, so it may be delayed
        |
        v
   done

  COMPARE LINUX (ch. 13):
     ISR        = the hard IRQ handler
     DPC        = a tasklet or softirq
     work item  = a workqueue item
     and WDF's passive-level interrupts = a threaded IRQ

  THE SAME DESIGN PRESSURE produces the same three tiers in
  both systems: something must be fast and constrained,
  something must be deferred but prompt, and something must be
  able to sleep.

The ISR

The interrupt service routine runs at device IRQL with interrupts of equal or lower priority masked on that processor. It should do the least possible work — and the list of things it may not do is longer than the list of things it may.

BOOLEAN
MyEvtInterruptIsr(_In_ WDFINTERRUPT Interrupt,
                  _In_ ULONG MessageID)
{
        PMY_CONTEXT ctx = MyInterruptGetContext(Interrupt);
        ULONG status;

        UNREFERENCED_PARAMETER(MessageID);

        /* WDF has ALREADY acquired the interrupt spinlock
           before calling us (chapter 10).                  */

        status = READ_REGISTER_ULONG(
                        (PULONG)(ctx->RegBase + REG_INT_STATUS));

        /* IS IT OURS? On a shared line this is mandatory -
           returning TRUE for someone else's interrupt breaks
           their driver.                                     */
        if ((status & INT_PENDING) == 0)
                return FALSE;

        /* ACKNOWLEDGE FIRST, so the device stops asserting */
        WRITE_REGISTER_ULONG(
                (PULONG)(ctx->RegBase + REG_INT_CLEAR), status);

        /* hand the minimum state to the DPC */
        ctx->LastStatus = status;

        /* queue the DPC and return */
        WdfInterruptQueueDpcForIsr(Interrupt);

        return TRUE;
}

/* THE RETURN VALUE:
     TRUE   this interrupt was mine and I handled it
     FALSE  not mine - let the next handler on the shared
            line try

   IF EVERY HANDLER RETURNS FALSE repeatedly, Windows
   eventually declares the interrupt unhandled and the system
   may bugcheck with 0x7A or hang in an interrupt storm - the
   equivalent of Linux's "nobody cared" (ch. 16).

/* WHAT NOT TO DO IN AN ISR:
     · a slow MMIO read (a PCIe config read can take
       microseconds - do it in the DPC)
     · a loop of unknown length
     · DbgPrint on a serial console (milliseconds!)
     · anything touching paged memory
     · acquiring any lock other than the interrupt lock     */

The DPC

The DPC is where the real work of an interrupt happens. It runs soon afterwards at DISPATCH_LEVEL, which buys you far more freedom than the ISR had while still forbidding anything that blocks.

VOID
MyEvtInterruptDpc(_In_ WDFINTERRUPT Interrupt,
                  _In_ WDFOBJECT AssociatedObject)
{
        PMY_CONTEXT ctx = MyInterruptGetContext(Interrupt);
        WDFREQUEST request;
        ULONG status;
        NTSTATUS s;

        UNREFERENCED_PARAMETER(AssociatedObject);

        /* read the state the ISR captured, under the
           interrupt lock (chapter 10) */
        WdfInterruptAcquireLock(Interrupt);
        status = ctx->LastStatus;
        ctx->LastStatus = 0;
        WdfInterruptReleaseLock(Interrupt);

        if (status & INT_ERROR) {
                ctx->Errors++;
                MyHandleError(ctx, status);
        }

        if (status & INT_DATA_READY) {
                /* complete a pending request (chapter 16) */
                s = WdfIoQueueRetrieveNextRequest(ctx->ReadQueue,
                                                  &request);
                if (NT_SUCCESS(s)) {
                        MyFillRequest(ctx, request);
                        WdfRequestCompleteWithInformation(
                                request, STATUS_SUCCESS, len);
                }
        }

        /* need PASSIVE_LEVEL? queue a work item */
        if (status & INT_NEEDS_RESET)
                WdfWorkItemEnqueue(ctx->ResetWorkItem);
}

/* DPC PROPERTIES worth knowing:

   · ONE DPC OBJECT runs at most once at a time, system-wide.
     Queueing it again while it is queued is a no-op - so a
     burst of interrupts produces ONE DPC run, not N. Your DPC
     must therefore handle "several things happened" in one
     pass, not assume a one-to-one mapping with interrupts.

   · It runs on the CPU that queued it, by default.
     WdfDpcCreate lets you request otherwise; on a
     multi-queue device, spreading DPCs across CPUs is how you
     scale.

   · It can be interrupted by any DIRQL interrupt, including
     your own ISR - so shared state still needs the interrupt
     lock.

   · DPCs from all drivers share one per-CPU queue. A long DPC
     delays everyone's. This is the single biggest source of
     system-wide latency spikes on Windows, and it is the
     direct analogue of the Linux argument for keeping
     softirqs short (ch. 11).                             */

/* A STANDALONE DPC, not tied to an interrupt: */
        WDF_DPC_CONFIG dpcConfig;
        WDF_OBJECT_ATTRIBUTES attr;

        WDF_DPC_CONFIG_INIT(&dpcConfig, MyDpcFunc);
        dpcConfig.AutomaticSerialization = TRUE;

        WDF_OBJECT_ATTRIBUTES_INIT(&attr);
        attr.ParentObject = device;

        status = WdfDpcCreate(&dpcConfig, &attr, &ctx->Dpc);
        ...
        WdfDpcEnqueue(ctx->Dpc);

        /* teardown - WAIT for it, like Linux's _sync forms */
        WdfDpcCancel(ctx->Dpc, TRUE);   /* TRUE = wait */
The DPC watchdog

Bugcheck 0x133 DPC_WATCHDOG_VIOLATION fires when a single DPC runs for roughly 20 ms, or when the system stays at DISPATCH_LEVEL for around 10 seconds. It exists because a long DPC is invisible in normal testing but destroys interactive latency in the field. If you hit it, the fix is never to raise the timeout — it is to move work into a work item or split it across several DPC invocations.

Work items

When the work genuinely must block — allocate paged memory, wait on an event, touch a file — even a DPC is too restrictive. A work item runs your code at PASSIVE_LEVEL on a system thread, where everything is permitted.

/* For anything needing PASSIVE_LEVEL. */

VOID
MyEvtWorkItem(_In_ WDFWORKITEM WorkItem)
{
        PMY_WORKITEM_CONTEXT wc = MyWorkItemGetContext(WorkItem);
        PMY_CONTEXT ctx = wc->DeviceContext;

        PAGED_CODE();     /* asserts PASSIVE_LEVEL */

        /* we may sleep here: registry, files, waiting */
        MyResetHardwareSlowly(ctx);
        MyReadConfigFromRegistry(ctx);
}

/* creating one, in EvtDeviceAdd: */
        WDF_WORKITEM_CONFIG workConfig;
        WDF_OBJECT_ATTRIBUTES attr;

        WDF_WORKITEM_CONFIG_INIT(&workConfig, MyEvtWorkItem);

        WDF_OBJECT_ATTRIBUTES_INIT_CONTEXT_TYPE(&attr,
                        MY_WORKITEM_CONTEXT);
        attr.ParentObject = device;

        status = WdfWorkItemCreate(&workConfig, &attr,
                                   &ctx->WorkItem);

        wc = MyWorkItemGetContext(ctx->WorkItem);
        wc->DeviceContext = ctx;

/* enqueue from a DPC or anywhere: */
        WdfWorkItemEnqueue(ctx->WorkItem);

/* teardown: */
        WdfWorkItemFlush(ctx->WorkItem);   /* WAIT for it */

/* THE SAME COALESCING RULE as DPCs: enqueueing an already
   queued work item is a no-op. If each event needs its own
   handling, either create several work items, or maintain
   your own queue of pending events and have one work item
   drain it.

   THAT SECOND PATTERN is usually the right one:
        DPC: push an event onto a list, enqueue the work item
        work item: drain the list until empty
   It handles bursts correctly and needs only one work item. */

/* SYSTEM WORKER THREADS are a shared, limited resource. A
   work item that blocks for a long time occupies one. Do not
   use work items for long-running loops - create a dedicated
   system thread instead (chapter 12).                    */

Passive-level interrupts

Some buses cannot be serviced at high IRQL at all, because reading the interrupt status itself requires a slow, blocking transaction. For those, the framework can run the whole interrupt handler at passive level.

/* Some devices are on a slow bus - I2C, SPI, or behind a
   USB transfer - where you CANNOT read the interrupt status
   register without sleeping. A DIRQL ISR cannot do that.

   WDF's answer: a passive-level interrupt.                */

        WDF_INTERRUPT_CONFIG config;

        WDF_INTERRUPT_CONFIG_INIT(&config,
                                  MyEvtInterruptIsr,
                                  MyEvtInterruptDpc);

        config.PassiveHandling = TRUE;    /* <-- the ISR runs
                                             at PASSIVE_LEVEL */
        config.AutomaticSerialization = FALSE;   /* required
                                                    with
                                                    passive   */

        status = WdfInterruptCreate(device, &config, &attr,
                                    &ctx->Interrupt);

/* NOW EvtInterruptIsr runs at PASSIVE_LEVEL, on a dedicated
   thread, and may sleep - so it can do an I2C read to find
   out what happened.

   This is EXACTLY Linux's threaded IRQ (ch. 15), including
   the reason it exists.

   CONSEQUENCES:
     · higher latency - a thread must be scheduled
     · the interrupt stays masked until your handler returns,
       so it is inherently one-shot
     · use WdfInterruptAcquireLock, which becomes a
       passive-level lock, not a spinlock
     · you may not need a DPC at all - do the work in the ISR

   USE IT for I2C/SPI/GPIO-connected devices, which on modern
   ARM64 Windows systems is most of them.                 */

Timers

Sometimes the trigger is time rather than an event: poll again shortly, or give up if the device has not answered. Windows offers timers at both levels, and the one you pick determines what the callback may do.

/* WDFTIMER - the callback runs at DISPATCH_LEVEL by default. */

        WDF_TIMER_CONFIG timerConfig;

        WDF_TIMER_CONFIG_INIT_PERIODIC(&timerConfig,
                                       MyEvtTimer,
                                       100);   /* ms period */
        /* or one-shot: */
        WDF_TIMER_CONFIG_INIT(&timerConfig, MyEvtTimer);

        timerConfig.AutomaticSerialization = TRUE;
        timerConfig.TolerableDelay = 50;   /* ms - lets the
                                              system coalesce
                                              timers and save
                                              power           */

        WDF_OBJECT_ATTRIBUTES_INIT(&attr);
        attr.ParentObject = device;

        status = WdfTimerCreate(&timerConfig, &attr,
                                &ctx->Timer);

        WdfTimerStart(ctx->Timer,
                      WDF_REL_TIMEOUT_IN_MS(100));

        WdfTimerStop(ctx->Timer, TRUE);   /* TRUE = WAIT for
                                             any running
                                             callback         */

VOID
MyEvtTimer(_In_ WDFTIMER Timer)
{
        WDFDEVICE device = WdfTimerGetParentObject(Timer);
        PMY_CONTEXT ctx = MyGetContext(device);

        /* DISPATCH_LEVEL - cannot sleep, cannot touch paged
           memory                                            */
        MyPollHardware(ctx);
}

/* FOR A PASSIVE-LEVEL TIMER CALLBACK: */
        WDF_OBJECT_ATTRIBUTES_INIT(&attr);
        attr.ExecutionLevel = WdfExecutionLevelPassive;

/* SHORT DELAYS without a timer: */
        KeStallExecutionProcessor(50);    /* BUSY-WAITS, in
                                             microseconds. Any
                                             IRQL. Keep it
                                             under ~50us.    */

        LARGE_INTEGER interval;
        interval.QuadPart = -10LL * 1000 * 20;   /* 20 ms */
        KeDelayExecutionThread(KernelMode, FALSE, &interval);
        /* SLEEPS. PASSIVE_LEVEL only. */

/* KeStallExecutionProcessor is Linux's udelay(); the delay
   thread is msleep(). The same advice applies: never busy-wait
   for milliseconds.                                        */

Teardown ordering

Interrupts, DPCs and work items can all be in flight when the device goes away. Stopping them in the right order is what separates a clean unload from a bugcheck seconds after the device is removed.

/* THE SAME RULE AS LINUX (ch. 13): stop the source first,
   then wait for what is already in flight.                */

NTSTATUS
MyD0Exit(_In_ WDFDEVICE Device,
         _In_ WDF_POWER_DEVICE_STATE TargetState)
{
        PMY_CONTEXT ctx = MyGetContext(Device);

        /* 1. stop the hardware generating interrupts.
              WDF disconnects the interrupt for us AFTER this
              callback, but the device must stop asserting
              first or we take a spurious one.             */
        WRITE_REGISTER_ULONG(
                (PULONG)(ctx->RegBase + REG_INT_ENABLE), 0);

        /* 2. wait for anything already queued */
        WdfDpcCancel(ctx->Dpc, TRUE);        /* TRUE = wait */
        WdfWorkItemFlush(ctx->WorkItem);
        WdfTimerStop(ctx->Timer, TRUE);      /* TRUE = wait */

        /* 3. now nothing can touch our state */
        return STATUS_SUCCESS;
}

/* THE "TRUE" ARGUMENTS ARE NOT OPTIONAL. Without them these
   calls return immediately, the callback may still be
   running, and it will touch your context after
   EvtDeviceReleaseHardware has unmapped the registers -
   producing a bugcheck at an address that no longer maps.

   This is the exact Windows counterpart of forgetting
   cancel_work_sync() on Linux, with the same symptom and the
   same fix.                                              */
