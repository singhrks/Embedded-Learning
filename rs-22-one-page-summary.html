The rules the compiler is enforcing

Almost every error message you will ever see is one of these being applied. Learning them verbatim converts the borrow checker from an obstacle into something predictable.

   OWNERSHIP                                        (ch. 02)
     1. Every value has exactly one owner.
     2. When the owner goes out of scope, the value is
        dropped.
     3. Ownership can be MOVED; assignment moves unless the
        type is Copy.

   BORROWING                                        (ch. 03)
     At any moment, for any value, you may have EITHER
       · any number of shared references  &T
       · OR exactly one mutable reference &mut T
     never both.

   LIFETIMES                                        (ch. 04)
     A reference may not outlive what it points at. The
     annotation NAMES that relationship; it never changes
     it.

   ---------------------------------------------------------

   WHAT THOSE THREE ELIMINATE, at compile time:
     use after free, double free, dangling pointers,
     iterator invalidation, data races.

   WHAT THEY DO NOT:
     logic errors, deadlocks, integer overflow in release,
     memory leaks, resource exhaustion, anything inside
     unsafe.

   BEING ABLE TO RECITE THE SECOND LIST is what separates
   understanding Rust from advocating for it.

Reading the error you are actually going to get

Rust's errors are long, and they have a fixed structure. Reading them in a fixed order makes them mechanical rather than intimidating.

   READ IN THIS ORDER, and stop as soon as it is obvious:

     1. THE LAST LINE. `help:` and `note:` frequently contain
        the literal fix. People read top-down and miss it.
     2. THE ERROR CODE. `rustc --explain E0502` gives a page
        with a worked example.
     3. THE SPANS. Which value, and which two places.

   ---------------------------------------------------------

   THE FIVE YOU WILL ACTUALLY MEET:

     E0382  use of moved value
            -> you moved it and used it again. Borrow, clone,
               or restructure so the move happens last.

     E0502  cannot borrow as mutable, already borrowed as
            immutable
            -> the two borrows overlap. Shorten one, or split
               the data (ch. 03).

     E0499  cannot borrow as mutable more than once
            -> same fix. split_at_mut is often the answer.

     E0597  borrowed value does not live long enough
            -> the referent dies first. Usually the struct is
               holding a reference where it should own the
               data (ch. 04).

     E0308  mismatched types
            -> ordinary. Check &T against T, and String
               against &str.

   ---------------------------------------------------------

   AND THE ONE PIECE OF ADVICE THAT SHORTENS THE FIRST WEEK
   MORE THAN ANY OTHER: when the checker refuses something
   you are sure is correct, it is usually right, and the code
   usually wants restructuring rather than a .clone(). Reach
   for clone to keep moving, then leave a TODO - but notice
   how often the restructured version is simply better.

The embedded half, in one block

The part of the track that distinguishes it from a general Rust tutorial, compressed.

   THE THREE LAYERS                                (ch. 19)
     core     always available. No allocator, no OS.
     alloc    adds Box, Vec, String. Needs a global
              allocator, which you opt into.
     std      adds files, threads, networking. Needs an OS.

   THE ECOSYSTEM STACK                             (ch. 20)
     PAC          generated from the vendor's SVD. Every
                  register, type-safe, unsafe confined here.
     HAL          chip-specific. Uses types to make invalid
                  pin configurations fail to compile.
     embedded-hal shared TRAITS. A driver written against
                  these runs on any chip.
     RTIC         interrupt-based concurrency, scheduling
                  analysed at compile time.
     Embassy      async/await for firmware.

   THE SIZE LEVERS                                 (ch. 18)
     panic = "abort", lto, opt-level = "z",
     codegen-units = 1, and defmt instead of core::fmt.

   THE KERNEL                                      (ch. 21)
     A restricted dialect: no std, no unwinding, fallible
     allocation. The value is in the safe abstractions over
     C APIs whose rules were previously only in comments.

Where to go from here

The track stops where the foundations are solid. These are the directions that reward the next stretch of effort.

   WRITE SOMETHING THAT IS NOT A TUTORIAL. A protocol
   parser, a small driver, a tool you actually wanted. The
   borrow checker only teaches you through your own code.

   THEN, DEPENDING ON WHERE YOU ARE HEADED:

     FIRMWARE      chapters 19-20, then a real board. The
                   MCU track covers the hardware side.
     KERNEL        chapter 21, then the Linux track's driver
                   chapters - the C you are wrapping is the
                   part that takes the time.
     TOOLING       chapters 12-13. Proc macros and testing
                   are where Rust's ergonomics are decided.
     FFI-HEAVY     chapters 14-15, and put it under Miri
                   from day one.

   ---------------------------------------------------------

   AND THE THING TO KEEP IN PROPORTION: Rust removes a
   specific and important class of bug. It does not remove
   the need to understand the hardware, the protocol or the
   problem - which is what the rest of this site is for.
