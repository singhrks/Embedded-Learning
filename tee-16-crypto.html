Cryptography inside a TA

The whole reason a TA exists is usually to hold a key. This chapter covers the algorithms OP-TEE offers, how keys are generated and derived so that raw material never crosses the boundary, where the hardware accelerator fits, and the handful of mistakes that turn a correct algorithm into a broken system.

The rule that shapes every design

One rule governs everything in this chapter: keys must not leave the secure world, even into shared memory. Everything else here is a consequence of holding that line.

   A key that crosses into the normal world is not protected.
   Design so it never has to.

   BAD                          GOOD

   client: generate key         client: "generate a key for me"
   client -> TA: here is the      TA: TEE_GenerateKey()
       key, please sign               store it persistently
   TA: sign with it                   return only a HANDLE/ID
   TA -> client: signature       client: "sign this, with key 7"
                                  TA: load key 7, sign, return
                                      the signature

   In the second design the key material exists only inside
   OP-TEE, from generation to destruction. There is no moment
   at which a compromised kernel could read it.

   The client's interface becomes:
       create_key()  -> key_id
       sign(key_id, digest) -> signature
       get_public_key(key_id) -> public key
       delete_key(key_id)

   That is exactly the shape of Android Keymint, of a PKCS#11
   token, and of the project in chapter 21. It is not a
   coincidence: it is the only shape that works.

Generating and keeping a key

Generating a key inside the secure world means it never existed anywhere else, which is a stronger property than importing one and worth preferring wherever possible.

/* An ECDSA P-256 signing key that is generated inside the TEE,
   stored persistently, and never exported.                  */

static TEE_Result create_signing_key(const char *id, size_t idlen)
{
        TEE_ObjectHandle key  = TEE_HANDLE_NULL;
        TEE_ObjectHandle pobj = TEE_HANDLE_NULL;
        TEE_Attribute    attr;
        TEE_Result       res;

        res = TEE_AllocateTransientObject(TEE_TYPE_ECDSA_KEYPAIR,
                                          256, &key);
        if (res) goto out;

        /* The curve must be given as a generation parameter. */
        TEE_InitValueAttribute(&attr, TEE_ATTR_ECC_CURVE,
                               TEE_ECC_CURVE_NIST_P256, 0);

        res = TEE_GenerateKey(key, 256, &attr, 1);
        if (res) goto out;

        /* Persist it AS AN OBJECT. */
        res = TEE_CreatePersistentObject(
                TEE_STORAGE_PRIVATE, id, idlen,
                TEE_DATA_FLAG_ACCESS_READ |
                TEE_DATA_FLAG_ACCESS_WRITE_META |
                TEE_DATA_FLAG_OVERWRITE,
                key, NULL, 0, &pobj);
out:
        TEE_FreeTransientObject(key);
        if (pobj != TEE_HANDLE_NULL)
                TEE_CloseObject(pobj);
        return res;
}

/* Exporting ONLY the public half - which is safe and
   necessary, because someone must verify the signatures.   */

static TEE_Result export_public(const char *id, size_t idlen,
                                uint8_t *x, size_t *xlen,
                                uint8_t *y, size_t *ylen)
{
        TEE_ObjectHandle pobj = TEE_HANDLE_NULL;
        TEE_Result res;
        uint32_t l;

        res = TEE_OpenPersistentObject(TEE_STORAGE_PRIVATE,
                                       id, idlen,
                                       TEE_DATA_FLAG_ACCESS_READ,
                                       &pobj);
        if (res) return res;

        l = *xlen;
        res = TEE_GetObjectBufferAttribute(pobj,
                        TEE_ATTR_ECC_PUBLIC_VALUE_X, x, &l);
        if (res) goto out;
        *xlen = l;

        l = *ylen;
        res = TEE_GetObjectBufferAttribute(pobj,
                        TEE_ATTR_ECC_PUBLIC_VALUE_Y, y, &l);
        if (res == TEE_SUCCESS)
                *ylen = l;
out:
        TEE_CloseObject(pobj);
        return res;
}

/* Asking for TEE_ATTR_ECC_PRIVATE_VALUE on a generated key
   returns TEE_ERROR_ACCESS_DENIED. That refusal is the
   guarantee: the private half is structurally unexportable,
   not merely undocumented.                                 */
Derive, do not store

A TA that needs many keys does not have to store many keys. Derive them from one root plus a label: key_i = HKDF(root, "purpose" || i). Storage holds one secret; the derived keys exist only while in use. Fewer persistent objects, no per-key storage failure, and rotating the root rotates everything at once.

Key derivation

Deriving keys from a root rather than storing them means a compromise of storage yields nothing usable, and it is how per-purpose keys are obtained without provisioning each one.

/* HKDF: the right tool for turning one secret into many. */

static TEE_Result derive(TEE_ObjectHandle root,
                         const char *label, size_t labellen,
                         TEE_ObjectHandle out)
{
        TEE_OperationHandle op = TEE_HANDLE_NULL;
        TEE_Attribute params[2];
        TEE_Result res;

        res = TEE_AllocateOperation(&op,
                        TEE_ALG_HKDF_SHA256_DERIVE_KEY,
                        TEE_MODE_DERIVE, 256);
        if (res) goto out;

        res = TEE_SetOperationKey(op, root);
        if (res) goto out;

        TEE_InitRefAttribute(&params[0], TEE_ATTR_HKDF_INFO,
                             label, labellen);
        TEE_InitRefAttribute(&params[1], TEE_ATTR_HKDF_SALT,
                             SALT, sizeof SALT);

        TEE_DeriveKey(op, params, 2, out);
out:
        TEE_FreeOperation(op);
        return res;
}

/* ECDH, and the mistake everyone makes: */

    /* WRONG: use the shared secret directly as an AES key.
       The X coordinate of an ECDH result is NOT uniformly
       distributed and has algebraic structure. */

    /* RIGHT: */
    TEE_AllocateOperation(&op, TEE_ALG_ECDH_DERIVE_SHARED_SECRET,
                          TEE_MODE_DERIVE, 256);
    TEE_SetOperationKey(op, my_keypair);
    TEE_InitRefAttribute(&p[0], TEE_ATTR_ECC_PUBLIC_VALUE_X,
                         peer_x, sizeof peer_x);
    TEE_InitRefAttribute(&p[1], TEE_ATTR_ECC_PUBLIC_VALUE_Y,
                         peer_y, sizeof peer_y);
    TEE_DeriveKey(op, p, 2, shared);       /* a GENERIC_SECRET */
    /* ...then run HKDF over `shared` to get the actual AES key */

The hardware unique key

The hardware unique key is the root of the whole chain: per-device, unreadable by software, and the reason data encrypted on one device is useless on another.

/* Every device has a different HUK (chapter 15). A TA can
   derive from it, which gives you a secret that:
     - is different on every device
     - never existed anywhere else
     - needs no storage at all                              */

#include <tee_internal_api_extensions.h>

    uint8_t key[32];
    TEE_Result res = TEE_GetHUKDerivedKey(
                        (const uint8_t *)"my-ta-purpose-v1", 16,
                        key, sizeof key);
    /* NOT standard GlobalPlatform - an OP-TEE extension,
       available when CFG_HUK_SUBKEY is enabled.            */

/* Uses:
     - encrypting something without a persistent key object
     - a device-binding value, so data cannot move devices
     - a per-device seed for a deterministic key

   Cautions:
     - the derivation label is part of the contract. Change it
       and every previously derived key is gone. Version it.
     - on QEMU the HUK is a fixed test value, so every
       "device" derives the same key. Do not conclude from a
       QEMU test that device binding works.
     - wipe the buffer when you are done:
           TEE_MemFill(key, 0, sizeof key);                 */

Hardware acceleration

Hardware acceleration matters here beyond speed — an accelerator that keeps the key in hardware means the key is never in memory at all, which closes an entire class of attack.

/* Most SoCs have a crypto accelerator. OP-TEE abstracts it
   behind the same API, so a TA does not change - but the
   performance difference is large.                         */

  core/drivers/crypto/
    caam/       NXP i.MX
    se050/      NXP secure element
    stm32/      ST
    hisilicon/  HiSilicon
    versal/     AMD/Xilinx
    aspeed/     ASPEED

  Enabled per platform, e.g.:
    CFG_NXP_CAAM=y
    CFG_NXP_CAAM_SHA_DRV=y
    CFG_NXP_CAAM_CIPHER_DRV=y

/* Rough figures - measure your own part:
     AES-256-GCM, software (libtomcrypt)   ~20-60 MB/s
     AES-256-GCM, CAAM/SAHARA             ~200-800 MB/s
     RSA-2048 sign, software              ~10-40 ms
     RSA-2048 sign, accelerator           ~1-5 ms
     ECDSA P-256 sign, software           ~2-10 ms

   The fixed cost of a TA invocation (chapter 5) is tens of
   microseconds, so for small operations the world switch
   dominates and the accelerator barely shows. For bulk data
   it is the whole story.

   The design consequence: BATCH. One invocation that signs 100
   digests beats 100 invocations that sign one each, by a large
   factor, regardless of the accelerator.                    */

The mistakes that matter

The recurring errors in trusted-application cryptography are rarely exotic algorithm choices. They are ordinary mistakes made in a context where the consequences are far larger.

MistakeWhy it is fatalDo this
Reusing a GCM nonce with the same keyRecovers the authentication key; forgeries become trivialCounter, or 96 bits of TEE_GenerateRandom, and never repeat
Comparing MACs with TEE_MemCompareTiming oracleTEE_MACCompareFinal, or a constant-time loop
Using an ECDH shared secret as a keyNot uniform; has structureRun it through HKDF
AES-ECBIdentical plaintext blocks give identical ciphertextGCM
RSA PKCS#1 v1.5 encryptionPadding-oracle attacksOAEP, or better, don't use RSA encryption
Decrypt-then-checkActing on unauthenticated plaintextAEAD, which does it in the right order for you
Key material in a local bufferLeft on the TA heap or stack after useKey objects, and TEE_MemFill(0) anything raw
Trusting TEE_GetREETime for expiryThe attacker sets the clockChapter 17
Logging a key with DHEXDUMPIt shipsNever; guard it out of release builds
Rolling your own primitiveYou will get it wrongUse the API; it is there
