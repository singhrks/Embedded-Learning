Trees: tries and prefix problems

A tree where the path spells the word. It makes prefix queries as cheap as exact lookups — something a hash map fundamentally cannot do.

The pattern

A trie stores strings by the path their characters trace, which is what makes prefix questions cheap and whole-string questions no better than a hash set. The picture makes the trade obvious.

   A TRIE (prefix tree) stores strings by CHARACTER PATH.
   Each edge is a character; each node is a prefix.

   Inserting "cat", "car", "dog":

              (root)
              /    \
            c        d
            |        |
            a        o
           / \       |
          t   r      g*
          *   *
                     * = end of a word

   THE KEY PROPERTY: WORDS SHARING A PREFIX SHARE A PATH.
   "cat" and "car" traverse the same first two nodes, so
   prefix questions are answered by a single descent.

   ---------------------------------------------------------
   THE NODE

     class TrieNode {
         children = new Map();   // char -> TrieNode
         isWord = false;         // does a word END here?
     }

     `isWord` IS ESSENTIAL AND SEPARATE FROM "has children".
     Without it you cannot distinguish the stored word "car"
     from the mere prefix "car" of "cart".

     Use a Map for arbitrary alphabets; a fixed
     `new Array(26)` is faster when the input is lowercase
     a-z only.

   ---------------------------------------------------------
   THE THREE OPERATIONS — all O(L), L = key length

     insert(word)     walk, creating nodes as needed, mark
                      the last node isWord = true
     search(word)     walk; return node exists AND isWord
     startsWith(pre)  walk; return the node merely EXISTS

     Search and startsWith differ by ONE LINE. That is the
     whole point of the structure.

   ---------------------------------------------------------
   WHY NOT A HASH SET?

     exact lookup       hash set O(L)     trie O(L)   — tie
     "any word with
      prefix 'app'?"    hash set O(n·L)   trie O(L)   — trie
     "all words with
      prefix 'app'"     hash set O(n·L)   trie O(L + k)
     wildcard '.'       hash set: no      trie: DFS branching
     autocomplete       hash set: no      trie: natural

   A HASH SET CANNOT ANSWER PREFIX QUESTIONS WITHOUT
   SCANNING EVERYTHING. That is the sentence to say when
   asked "why not just use a set?"

   COST: O(total characters) space — which can be large.
   The trade is memory for prefix speed.

When to reach for it

"Prefix", "starts with", autocomplete

The defining signal.

Wildcard or regex-lite matching

. matches any child — DFS over all branches.

Word search in a grid, many words

Build a trie of the dictionary and prune the DFS the moment a path leaves the trie.

Longest common prefix

Descend while there is exactly one child and no word ends.

Replace words / dictionary root matching

Walk the word until a stored root is hit.

Maximum XOR pair

A binary trie over bits — greedily take the opposite bit at each level.

Problems

SymptomCause

Memory blowup26-slot arrays at every node — use a Map for sparse alphabets
Deletion corrupts other wordsOnly unset isWord; prune a node only if it has no children
