Training: loss, initialisation and regularisation

The practical craft. Everything that determines whether a correct architecture actually learns anything — and the diagnostic procedure for when it does not.

Initialisation

Starting weights look like an implementation detail and are not: get them wrong and a deep network produces no usable gradient at all. The reasoning behind the standard schemes is short and worth following.

   THE PROBLEM: the initial weights determine whether
   signals and gradients survive their trip through the
   network.

   ALL ZEROS       every unit in a layer computes the same
                   thing, receives the same gradient, and
                   stays identical forever. THE NETWORK HAS
                   ONE EFFECTIVE UNIT PER LAYER. Symmetry
                   must be broken.

   TOO LARGE       activations grow layer by layer;
                   gradients explode; loss goes to nan
                   within a few steps.

   TOO SMALL       activations shrink to zero; gradients
                   vanish; nothing learns.

   THE RULE, derived from variance arithmetic in chapter 08:
   KEEP THE VARIANCE OF THE ACTIVATIONS ROUGHLY CONSTANT
   THROUGH DEPTH.

     XAVIER / GLOROT     Var(W) = 1 / n_in
                         (or 2/(n_in+n_out))
                         for tanh and sigmoid

     HE / KAIMING        Var(W) = 2 / n_in
                         for ReLU - the factor of 2
                         compensates for ReLU zeroing half
                         the outputs

     ORTHOGONAL          Q from a QR decomposition.
                         Preserves norms exactly
                         (chapter 03). Good for RNNs and
                         very deep stacks.

     BIASES              zero. Almost always.

   AND FOR TRANSFORMERS SPECIFICALLY:
     · a SMALL initialisation (std 0.02) on all weights
     · the RESIDUAL PROJECTIONS scaled down by
       1/sqrt(2*n_layers), so the residual stream does not
       grow with depth (chapter 22)
     · embeddings drawn from N(0, 0.02)

   THIS IS NOT FOLKLORE - it is the same variance argument,
   applied to a specific topology. GPT-2's initialisation
   scheme is three lines of code and it is load-bearing.
import numpy as np
import torch.nn as nn

# NUMPY
W = np.random.randn(n_in, n_out) * np.sqrt(2.0 / n_in)   # He

# PYTORCH - the defaults are reasonable but not optimal for
# every architecture, so set them explicitly:
def init_weights(m):
    if isinstance(m, nn.Linear):
        nn.init.normal_(m.weight, mean=0.0, std=0.02)
        if m.bias is not None:
            nn.init.zeros_(m.bias)
    elif isinstance(m, nn.Embedding):
        nn.init.normal_(m.weight, mean=0.0, std=0.02)

model.apply(init_weights)

# THE DIAGNOSTIC - run this ONCE before training. It takes
# thirty seconds and it has saved more debugging time than
# any other habit in this chapter:
def check_activations(model, x):
    acts = {}
    hooks = [m.register_forward_hook(
                lambda mod, i, o, n=n: acts.__setitem__(
                    n, o.detach()))
             for n, m in model.named_modules()]
    model(x)
    for name, a in acts.items():
        print(f"{name:30s} std={a.std():.4f} "
              f"mean={a.mean():+.4f} "
              f"dead={(a == 0).float().mean():.2%}")
    for h in hooks: h.remove()

# WHAT YOU WANT TO SEE: std roughly CONSTANT across layers,
# somewhere near 1 (or near 1 after each normalisation
# layer). A std that shrinks 10x per layer, or grows 10x,
# tells you the problem before you waste an hour on the
# loss curve.

Choosing the loss

The loss defines what the model is actually optimising, which is not always what you meant. Picking it is a modelling decision, not a default to accept.

TaskLossOutput layer
Binary classificationBCEWithLogitsLoss1 logit, no sigmoid
Multi-classCrossEntropyLossK logits, no softmax
Multi-labelBCEWithLogitsLossK logits
RegressionMSELossLinear
Regression with outliersHuberLoss / SmoothL1Linear
Language modellingCrossEntropyLossV logits per position
Ranking / retrievalContrastive, InfoNCE, tripletEmbeddings
Imbalanced classificationFocal loss, or class weightsLogits
 
/* THE "WithLogits" VARIANTS ARE NOT A CONVENIENCE. They
   fuse the activation and the loss to gain numerical
   stability and the clean gradient (chapter 06). Using the
   separated version is measurably worse and occasionally
   produces nan.

/* --- HANDLING IMBALANCE --- */
    class weights:
        w = torch.tensor([1.0, 10.0])       # 10x on the
                                            # rare class
        F.cross_entropy(logits, y, weight=w)

    FOCAL LOSS down-weights easy examples so training
    focuses on the hard ones:
        FL = -(1 - p_t)^gamma * log(p_t)      gamma = 2
    Designed for extreme imbalance in object detection;
    useful whenever the easy negatives swamp the signal.

    AND THE SIMPLER OPTIONS THAT OFTEN WIN: resample the
    data, or just move the decision threshold after training
    (chapter 13). Try those first.

/* --- AUXILIARY AND COMBINED LOSSES --- */
    loss = main_loss + 0.1 * auxiliary_loss

    THE WEIGHT MATTERS ENORMOUSLY and is a real
    hyperparameter. Check the MAGNITUDES of the terms - if
    one is 100x the other, the small one is decoration. Print
    both separately during training; a combined loss that
    only ever reflects one term is a common silent failure.

/* --- THE SANITY CHECK YOU SHOULD ALWAYS RUN --- */
    At step 0, before any learning:
      · K-way classification -> loss should be ~log(K)
        (10 classes -> 2.303; 50k vocabulary -> 10.82)
      · regression -> loss should be ~the variance of y

    IF THE INITIAL LOSS IS WRONG, THE BUG IS IN THE MODEL,
    THE LABELS OR THE LOSS - not in the training. Finding it
    now costs minutes; finding it after a day of training
    costs a day.                                          */

Regularisation

Every technique here exists to close the gap between training performance and real performance, and each attacks it differently. Knowing which lever to reach for is most of the practical skill.

/* --- MORE DATA. Always first, always best. --- */
    Nothing on this list comes close to the effect of
    doubling the dataset.

/* --- DATA AUGMENTATION: more data, for free --- */
    images  flips, crops, rotations, colour jitter,
            mixup, cutmix
    audio   time/pitch shift, noise, SpecAugment
    text    back-translation, synonym swap, token dropout -
            all much weaker than the vision equivalents,
            because language is less tolerant of
            perturbation
    sensor  jitter, scaling, window shifting, and SYNTHETIC
            FAULT INJECTION - which for embedded anomaly
            detection is often the only way to get positive
            examples at all

/* --- WEIGHT DECAY (L2) --- */
    opt = torch.optim.AdamW(params, weight_decay=0.1)
    A Gaussian prior on the weights (chapter 09). USE ADAMW,
    not Adam with L2 in the loss (chapter 11).

    AND EXCLUDE BIASES AND NORMALISATION PARAMETERS from
    decay - decaying a LayerNorm gain toward zero actively
    hurts:
        decay    = [p for n,p in model.named_parameters()
                    if p.dim() >= 2]
        no_decay = [p for n,p in model.named_parameters()
                    if p.dim() < 2]

/* --- DROPOUT --- */
    nn.Dropout(0.1)
    Randomly zero a fraction of activations during training;
    scale the rest by 1/(1-p) so the expected value is
    unchanged. At inference it is a no-op.

    THE INTUITION: units cannot rely on any particular other
    unit being present, so they learn redundant, distributed
    representations. Also approximately an ensemble over
    exponentially many sub-networks.

    RATES: 0.5 for old-style MLPs, 0.1 for transformers,
    OFTEN ZERO FOR LARGE-SCALE PRETRAINING - when the data
    is effectively unlimited and each example is seen once,
    there is nothing to overfit, and dropout only slows
    learning. It comes back for fine-tuning on small
    datasets.

    AND THE CLASSIC BUG: FORGETTING model.eval(). Dropout
    stays active, and your validation numbers are noisy and
    pessimistic. The same call switches BatchNorm to its
    running statistics.

/* --- EARLY STOPPING --- */
    best, patience, wait = inf, 10, 0
    for epoch in ...:
        val = validate()
        if val < best:
            best, wait = val, 0
            torch.save(model.state_dict(), "best.pt")
        else:
            wait += 1
            if wait >= patience:
                break
    Free, effective, and it also gives you the checkpoint.

/* --- LABEL SMOOTHING --- */
    Chapter 10. Prevents the model chasing infinite logits.

/* --- NORMALISATION LAYERS --- */
    BATCHNORM  normalise across the BATCH. Great for CNNs.
               DEPENDS ON BATCH SIZE, behaves differently in
               train and eval, and is awkward for sequences
               and for batch size 1 - which is exactly the
               embedded inference case.
    LAYERNORM  normalise across the FEATURES of each sample
               independently. NO BATCH DEPENDENCE, identical
               in train and eval. THE TRANSFORMER CHOICE
               (chapter 22).
    RMSNORM    LayerNorm without the mean subtraction.
               Cheaper, and what most recent LLMs use.

/* --- AND THE CHEAPEST WIN OF ALL: EMA OF THE WEIGHTS --- */
    ema = 0.999 * ema + 0.001 * weights
    Evaluate with the averaged weights. Costs one extra copy
    of the model and frequently gives a free accuracy
    improvement, because it lands in the middle of a basin
    rather than on its wall (chapter 11).                 */
The order to reach for these 
1. More data.
2. Data augmentation.
3. Early stopping (free, do it anyway).
4. Weight decay.
5. Dropout.
6. A smaller model.

And measure after each one. Stacking regularisers blindly is how you end up with a model that underfits and a hyperparameter search that cannot recover.

The debugging procedure

Training failures are unusually uninformative — the loss is simply wrong and nothing crashes. Working through a fixed checklist beats intuition here, and this is the order that finds problems fastest.

/* IN ORDER. Do not skip steps; each one rules out a whole
   class of bug and takes minutes.                        */

/* --- 1. OVERFIT A SINGLE BATCH --- */
    x, y = next(iter(dataloader))
    x, y = x[:8], y[:8]
    for i in range(500):
        loss = criterion(model(x), y)
        opt.zero_grad(); loss.backward(); opt.step()
        if i % 50 == 0: print(i, loss.item())

    THE LOSS MUST REACH APPROXIMATELY ZERO. If it does not,
    the bug is in the model, the data pipeline or the loss -
    NOT in the hyperparameters. Nothing else you do matters
    until this passes.

/* --- 2. CHECK THE INITIAL LOSS --- */
    ~log(K) for K classes. Wrong value -> wrong labels,
    wrong loss, or a broken output layer.

/* --- 3. VISUALISE THE INPUT AT THE MODEL BOUNDARY --- */
    Print or plot exactly what the model receives, after all
    preprocessing. Wrong normalisation, channels in the wrong
    order, off-by-one label indexing, and a shuffled
    label/feature correspondence are all VISIBLE HERE and
    invisible everywhere else.

/* --- 4. CHECK GRADIENT FLOW --- */
    for n, p in model.named_parameters():
        print(n, None if p.grad is None
                 else p.grad.norm().item())
    None -> disconnected from the loss.
    0.0  -> a non-differentiable operation upstream.
    1e-8 -> vanishing. 1e+8 -> exploding. (chapter 07)

/* --- 5. CHECK ACTIVATION STATISTICS --- */
    The hook from the top of this chapter.

/* --- 6. LR RANGE TEST --- */
    Chapter 11.

/* --- 7. ONLY NOW: TUNE --- */
    And tune ONE THING AT A TIME, with a fixed seed, logging
    everything.

/* ================= THE SYMPTOM TABLE ================= */

   LOSS IS nan
     -> lr too high; log(0); division by zero; bad input
        data; missing gradient clipping; fp16 overflow

   LOSS DOES NOT MOVE AT ALL
     -> lr too low; gradients not flowing; optimizer.step()
        never called; parameters not passed to the optimiser
        (a real and common mistake when a submodule is
        created after the optimiser)

   LOSS DECREASES THEN EXPLODES
     -> lr too high for the later, sharper region; add a
        schedule and clipping

   TRAIN LOSS DOWN, VAL LOSS UP
     -> overfitting. See the list above.

   BOTH LOSSES PLATEAU HIGH
     -> underfitting: more capacity, longer training, higher
        lr, or the features genuinely do not contain the
        signal

   VAL LOSS LOWER THAN TRAIN LOSS
     -> normal early on with dropout (train is measured with
        regularisation on); if persistent, suspect a data
        split problem

   RESULTS VARY WILDLY BETWEEN SEEDS
     -> the model is too small, the data too little, or the
        lr too high. Report a mean over seeds, not your best
        run.

   GREAT VALIDATION, POOR PRODUCTION
     -> leakage, or distribution shift (chapter 12)      */

How it shows up

SymptomCause
All units in a layer identicalZero initialisation — symmetry never broken
Activation std shrinks 10× per layerInitialisation scale too small
Loss nan at step 1Initialisation too large, or bad input data
Initial loss not log(K)Wrong labels, wrong loss, or a broken output layer
