Condition variables and waiting for a state

A mutex answers "may I touch this?". A condition variable answers "has it become what I need yet?" — without burning a core asking. It is the primitive people most often get wrong, and every mistake comes from forgetting that the condition variable itself holds no state at all.

The problem it solves

A mutex protects data but cannot express "wait until this becomes true". Polling in a loop while holding the lock is a deadlock; releasing and re-acquiring in a loop burns a core. Condition variables exist precisely for that gap.

   You want: "wait until the queue is non-empty."

   ATTEMPT 1 - spin
       while (queue_empty(q))
               ;
     Burns a core. On one core, may never progress.

   ATTEMPT 2 - spin with a lock
       for (;;) {
               lock(m);
               if (!queue_empty(q)) break;
               unlock(m);
       }
     Burns a core AND hammers the lock, so the producer
     cannot get in to add anything.

   ATTEMPT 3 - poll with a sleep
       for (;;) {
               lock(m);
               if (!queue_empty(q)) break;
               unlock(m);
               sleep_ms(1);
       }
     Works. Adds up to 1 ms of latency to every item and wakes
     up pointlessly all night. This is what people ship when
     they do not know about condition variables.

   WHAT YOU ACTUALLY WANT
       lock(m);
       while (queue_empty(q))
               cond_wait(cv, m);      /* atomically: unlock m,
                                         sleep, and relock m
                                         on wake              */
       take_item(q);
       unlock(m);

   Zero CPU while waiting, and wake-up latency measured in
   microseconds.
The atomicity that makes it work

cond_wait must release the mutex and begin waiting as one indivisible step. If there were any gap, a producer could add an item and signal in that gap — and the consumer would then go to sleep waiting for an event that already happened, for ever. This is the lost wake-up, and avoiding it is the entire reason the API takes the mutex as an argument rather than you unlocking it yourself.

The three rules

Condition variables have a small number of rules that look like ceremony and are each preventing a specific bug. The loop around the wait in particular is not optional, for a reason the section explains.

/* RULE 1: ALWAYS wait in a loop, never an if. */

        lock(m);
        while (!condition)          /* while, not if           */
                cond_wait(cv, m);
        /* condition is true here */
        unlock(m);

/* Three separate reasons, any one of which is sufficient:

   (a) SPURIOUS WAKE-UPS. POSIX explicitly permits cond_wait
       to return without any signal at all. This is not a bug
       in the implementation; it is licensed by the standard
       so that implementations can be fast (and it genuinely
       happens on signal delivery).

   (b) BARGING. Between the signaller's signal and your
       actually running, a THIRD thread may acquire the mutex
       and consume the item. You wake up, the queue is empty
       again. Most implementations are not FIFO handoff.

   (c) BROADCAST. If the signaller uses broadcast, every
       waiter wakes but only some can proceed.

   A codegen or review rule of "cond_wait is only ever called
   inside a while loop testing the predicate" catches almost
   every condition-variable bug there is.                    */


/* RULE 2: hold the mutex when you change the predicate. */

        lock(m);
        queue_push(q, item);        /* change the state ...    */
        unlock(m);
        cond_signal(cv);            /* ... then signal         */

/* Signalling inside or outside the lock are both correct.
   Outside avoids the waiter waking straight into a locked
   mutex ("hurry up and wait"), which some implementations
   optimise anyway. Inside is required if the condition
   variable or the predicate might be destroyed by a woken
   waiter - which is a real hazard on shutdown.

   THE THING THAT IS NEVER CORRECT is changing the predicate
   WITHOUT the mutex and then signalling: the waiter may test
   the predicate between your write and your signal, and
   sleep for ever.                                           */


/* RULE 3: one condition variable per predicate. */

/* WRONG - one cv for two different conditions */
        while (queue_full(q))  cond_wait(cv, m);   /* producer */
        while (queue_empty(q)) cond_wait(cv, m);   /* consumer */
/* signal() may wake a producer when you meant a consumer, and
   the woken thread goes straight back to sleep, having
   consumed the signal. Deadlock with a full queue.

   Either use TWO condition variables, or use broadcast and
   accept the thundering herd.                              */

The bounded buffer, written properly

The bounded producer-consumer queue is the canonical use and worth writing out in full, because getting both the full and empty cases right is the whole exercise.

/* The canonical example, and a good template. */

#define CAP 256

struct bbuf {
        pthread_mutex_t m;
        pthread_cond_t  not_empty;      /* two predicates,     */
        pthread_cond_t  not_full;       /* two variables       */
        void           *slot[CAP];
        size_t          head, tail, count;
        bool            closed;         /* for clean shutdown  */
};

int bbuf_put(struct bbuf *b, void *item)
{
        pthread_mutex_lock(&b->m);

        while (b->count == CAP && !b->closed)
                pthread_cond_wait(&b->not_full, &b->m);

        if (b->closed) {                       /* shutdown path */
                pthread_mutex_unlock(&b->m);
                return -EPIPE;
        }

        b->slot[b->tail] = item;
        b->tail = (b->tail + 1) % CAP;
        b->count++;
        pthread_mutex_unlock(&b->m);

        pthread_cond_signal(&b->not_empty);    /* exactly one
                                                  consumer can
                                                  proceed       */
        return 0;
}

void *bbuf_get(struct bbuf *b)
{
        pthread_mutex_lock(&b->m);

        while (b->count == 0 && !b->closed)
                pthread_cond_wait(&b->not_empty, &b->m);

        if (b->count == 0) {                   /* closed, empty */
                pthread_mutex_unlock(&b->m);
                return NULL;
        }

        void *item = b->slot[b->head];
        b->head = (b->head + 1) % CAP;
        b->count--;
        pthread_mutex_unlock(&b->m);

        pthread_cond_signal(&b->not_full);
        return item;
}

/* Shutdown. Note the BROADCAST: every waiter, on both
   variables, must be released - and `closed` is part of every
   predicate above precisely so they can be.                */
void bbuf_close(struct bbuf *b)
{
        pthread_mutex_lock(&b->m);
        b->closed = true;
        pthread_mutex_unlock(&b->m);
        pthread_cond_broadcast(&b->not_empty);
        pthread_cond_broadcast(&b->not_full);
}
// C++, where the predicate overload removes the loop from
// your code but not from the semantics.
#include <condition_variable>

std::mutex m;
std::condition_variable cv;
std::queue<int> q;
bool closed = false;

void producer(int v) {
    { std::lock_guard<std::mutex> g(m); q.push(v); }
    cv.notify_one();
}

std::optional<int> consumer() {
    std::unique_lock<std::mutex> lk(m);      // unique_lock, not
                                             // lock_guard: wait
                                             // must unlock it
    cv.wait(lk, [&]{ return !q.empty() || closed; });
    //           ^ this IS the while loop, written once
    if (q.empty()) return std::nullopt;
    int v = q.front(); q.pop();
    return v;
}

// With a timeout - note wait_for returns the predicate's value,
// so you can tell timeout from success without a second check:
if (!cv.wait_for(lk, std::chrono::seconds(5),
                 [&]{ return !q.empty(); }))
        return timeout();
wait needs unique_lock, and that is not arbitrary

std::lock_guard cannot unlock; cv.wait must. That is why the type differs, and why the compiler stops you. Similarly, waiting on a condition variable with a recursive_mutex locked twice releases it only once — so you sleep still holding it, and nobody can ever signal you. Another reason recursive mutexes cause trouble.

Signal or broadcast

signal / notify_onebroadcast / notify_all
WakesOne waiter (unspecified which)Every waiter
Correct whenEvery waiter waits for the same predicate and one item satisfies exactly oneWaiters have different predicates, or one event satisfies many
CostOne wake-upN wake-ups, N−1 of which relock, re-test and sleep again — the thundering herd
RiskWaking the wrong waiter if predicates differ, losing the signalOnly performance

The safe default when unsure is broadcast: it is never incorrect, only slower. Use signal when you can state, in one sentence, that every waiter on this variable is waiting for exactly the same thing and one event satisfies exactly one of them.
