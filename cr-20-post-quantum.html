Post-quantum cryptography

A sufficiently large quantum computer breaks RSA and every elliptic curve completely. It does not exist yet. For a product that will still be in the field in 2040, that is not a reason to wait.

What quantum computers actually break

A sufficiently large quantum computer would break RSA and elliptic curves completely, while affecting symmetric cryptography only mildly. Understanding that asymmetry is what makes the migration plan rational rather than panicked.

   SHOR'S ALGORITHM (1994)
     Solves FACTORING and DISCRETE LOGARITHM in polynomial
     time.

     BROKEN COMPLETELY:
       RSA           any key size (chapter 12)
       Diffie-Hellman, finite field          (chapter 13)
       ECDH, ECDSA, Ed25519, all curves      (14, 15)

     "Use a bigger key" does not help. A 15360-bit RSA key
     falls to the same algorithm as a 1024-bit one; it just
     needs a slightly larger machine.

   GROVER'S ALGORITHM (1996)
     Searches an unstructured space in O(sqrt(N)) instead of
     O(N).

     WEAKENED, NOT BROKEN:
       AES-128   -> effectively ~64-bit    -> UPGRADE
       AES-256   -> effectively ~128-bit   -> FINE
       SHA-256   -> ~128-bit preimage      -> FINE
       SHA-512, SHA-3                      -> FINE

     AND GROVER'S SPEEDUP IS HARD TO REALISE IN PRACTICE: it
     is inherently sequential, so it does not parallelise the
     way classical search does. The consensus is that
     doubling symmetric key sizes is sufficient and probably
     generous.

   SO THE SUMMARY IS SIMPLE:

     SYMMETRIC CRYPTO SURVIVES. Use AES-256, SHA-384/512,
     and 256-bit MACs.

     ALL DEPLOYED PUBLIC-KEY CRYPTO DIES. It must be
     replaced.

   WHEN? Nobody knows. Current machines have a few hundred
   noisy qubits; breaking RSA-2048 is estimated to need
   millions of physical qubits with error correction.
   Estimates for a cryptographically relevant machine range
   from "the 2030s" to "never". PLAN, DO NOT PANIC.
Harvest now, decrypt later

An adversary can record encrypted traffic today and decrypt it once a quantum computer exists. So the relevant question is not "when will quantum computers arrive?" but "how long must this data stay secret?" If the answer is more than about ten years — medical records, state secrets, long-lived device identities — the migration is already late. Signatures are less urgent, since a signature only needs to resist forgery while it is still being verified. But a firmware root key burned into a 2026 device that ships until 2035 and runs until 2050 is exactly the case that needs planning now.

   FASTER THAN X25519, and dramatically faster than RSA. The
   cost is bandwidth and memory, not cycles.             */

Key encapsulation, and why the shape changed

The replacement for key exchange works differently from Diffie-Hellman — it encapsulates a secret rather than deriving one jointly, which changes how protocols using it are structured.

/* PQ KEY EXCHANGE IS NOT DIFFIE-HELLMAN. There is no
   "raise the peer's value to my secret". The primitive is a
   KEM: KEY ENCAPSULATION MECHANISM.                      */

    KEYGEN()            -> (pk, sk)
    ENCAPS(pk)          -> (ciphertext, shared_secret)
    DECAPS(sk, ct)      -> shared_secret

/* THE FLOW:
     Alice generates (pk, sk), sends pk.
     Bob runs ENCAPS(pk), gets a random shared secret and a
       ciphertext. Sends the ciphertext.
     Alice runs DECAPS(sk, ct) and gets the same secret.

   ONE ROUND TRIP, same as DH, but ASYMMETRIC IN SHAPE - Bob
   chooses the secret rather than both contributing. That
   means SOME DH-BASED PROTOCOL PATTERNS DO NOT TRANSLATE
   DIRECTLY. Noise's DH-based patterns (chapter 13), for
   instance, needed a redesign; the PQNoise variants use KEMs
   explicitly.

/* --- HYBRID MODE: what everyone is actually deploying --- */

    shared_secret = KDF( X25519_output ‖ ML-KEM_output
                         ‖ transcript )

    THE POINT: THE RESULT IS SECURE IF *EITHER* PRIMITIVE IS
    SECURE.
      · if ML-KEM turns out to have a classical break - and
        it is a young algorithm; SIKE was broken in 2022 by a
        single laptop over a weekend, after reaching the
        final round - X25519 still protects you
      · if a quantum computer arrives, ML-KEM still protects
        you

    THIS IS THE RIGHT DEFAULT AND IT IS ALREADY DEPLOYED:
    X25519MLKEM768 is on by default in Chrome and Firefox,
    supported by OpenSSL 3.5+, and used by a large fraction
    of Cloudflare's traffic. If you are adding PQ to a
    product today, ADD IT AS A HYBRID.

/* --- THE CODE, liboqs --- */
    OQS_KEM *kem = OQS_KEM_new(OQS_KEM_alg_ml_kem_768);

    uint8_t pk[OQS_KEM_ml_kem_768_length_public_key];
    uint8_t sk[OQS_KEM_ml_kem_768_length_secret_key];
    OQS_KEM_keypair(kem, pk, sk);
    /* send pk (1184 bytes) */

    /* the peer: */
    uint8_t ct[OQS_KEM_ml_kem_768_length_ciphertext];
    uint8_t ss[OQS_KEM_ml_kem_768_length_shared_secret];
    OQS_KEM_encaps(kem, ct, ss, pk);
    /* send ct (1088 bytes) */

    /* back at the originator: */
    OQS_KEM_decaps(kem, ss, ct, sk);

    /* THEN HYBRID-COMBINE AND RUN IT THROUGH A KDF - never
       use a KEM output directly as a key (chapter 10): */
    hkdf(prk, x25519_ss ‖ ss, "myproto v2 hybrid", key, 32);

    OQS_KEM_free(kem);

/* NOTE: DECAPS NEVER FAILS. ML-KEM uses an implicit
   rejection construction - a malformed ciphertext produces a
   deterministic but WRONG shared secret rather than an
   error. That is deliberate: it removes a decryption oracle
   of exactly the Bleichenbacher shape (chapter 12). Your
   protocol finds out later, when the AEAD tag check fails.
   DO NOT ADD YOUR OWN "IS THIS CIPHERTEXT VALID" CHECK - you
   would be re-creating the oracle.                       */

Signatures, and the stateful option

The post-quantum signature schemes have substantially larger keys or signatures than what they replace, which has real consequences for constrained devices and for protocols with size limits.

/* --- ML-DSA (Dilithium): the general-purpose choice --- */
    Lattice-based, Fiat-Shamir with aborts. Fast, moderate
    sizes, no state. USE THIS unless you have a specific
    reason not to.

/* --- FN-DSA (Falcon): smaller, harder to implement --- */
    666-byte signatures - the smallest lattice option. But
    signing requires FLOATING-POINT GAUSSIAN SAMPLING, which
    is a side-channel minefield (chapter 19) and behaves
    differently across FPUs. VERIFICATION is easy and
    integer-only. A reasonable split: sign in the factory
    with a well-tested implementation, verify on-device.

/* --- SLH-DSA (SPHINCS+): the conservative choice --- */
    SECURITY RESTS ONLY ON HASH FUNCTIONS. No lattices, no
    new mathematical assumptions - if SHA-256 survives, this
    survives. Stateless.
    THE COST: 7-30 KB signatures and slow signing.
    USE FOR: a root of trust you cannot ever update. If your
    boot ROM's root key must be trustworthy for thirty years
    and you cannot patch it, the conservative assumption is
    worth the size.

/* --- LMS AND XMSS: STATEFUL, and read this carefully --- */
    Hash-based Merkle signature schemes. Small keys, moderate
    signatures, very conservative security.

    THE CATCH:

      EACH ONE-TIME KEY MAY BE USED EXACTLY ONCE.
      REUSING AN INDEX LEAKS THE PRIVATE KEY.

    So the signer must keep a COUNTER THAT NEVER GOES
    BACKWARDS - across crashes, backups, VM snapshots, and
    redundant signing servers. A restored backup is a key
    compromise. This is why NIST approved them ONLY for
    firmware signing (SP 800-208): a controlled,
    low-frequency, single-signer environment where the state
    can genuinely be managed.

    DO NOT USE THEM for anything with multiple signers or
    uncontrolled infrastructure.

/* --- THE PRACTICAL RECOMMENDATION TABLE ---
     TLS / session keys        hybrid X25519 + ML-KEM-768
     general signatures        ML-DSA-65 (hybrid with
                               Ed25519 during transition)
     firmware signing, updatable   ML-DSA-65 or LMS
     an unpatchable boot ROM root  SLH-DSA, or LMS with
                               rigorous state management
     symmetric everything      AES-256, SHA-384/512,
                               HMAC-SHA-384              */

Migrating a product

The practical concern is "harvest now, decrypt later": traffic recorded today could be decrypted once such a machine exists. That is why migration is beginning before the threat is present, and why hybrid schemes are used during it.

/* --- STEP 1: INVENTORY --- */
    Every place the product uses public-key cryptography:
      TLS to the cloud, firmware signature verification, the
      device identity certificate, secure boot, attestation,
      any licensing or pairing scheme, third-party SDKs.
    YOU CANNOT MIGRATE WHAT YOU HAVE NOT LISTED, and the
    third-party SDKs are the ones people forget.

/* --- STEP 2: CLASSIFY BY LIFETIME --- */
      confidentiality needed for > 10 years   -> URGENT,
                                                 harvest-now
      device identities lasting > 10 years    -> URGENT
      signatures verified only while current  -> can wait
      session data with short value           -> can wait

/* --- STEP 3: BUILD FOR CRYPTOGRAPHIC AGILITY --- */
    THIS IS THE HIGHEST-VALUE WORK, and it is useful even if
    quantum computers never arrive.

      · ALGORITHM IDENTIFIERS in every stored and transmitted
        format
      · KEY IDs, so keys can be rotated (chapter 18)
      · SIZE-AGNOSTIC BUFFERS AND FIELDS - a protocol with a
        fixed 64-byte signature field cannot ever carry a
        3 KB one. LENGTH-PREFIX EVERYTHING.
      · a NEGOTIATION mechanism, with a floor
      · no algorithm assumptions baked into wire formats or
        flash layouts
      · reserve space: OTP slots for multiple root key
        hashes, flash regions sized for larger manifests

/* --- STEP 4: DEPLOY HYBRIDS FIRST --- */
    Never a flag day. Support both, negotiate, measure, then
    deprecate.

/* --- AND THE HARDWARE QUESTION --- */
    Silicon designed today ships for years and lives for
    decades. If you are specifying an SoC now:
      · does the boot ROM support a PQ signature, or at
        least a second-stage loader that can?
      · is there enough OTP for larger key hashes and more
        slots?
      · enough RAM for lattice operations in the boot path?
      · a hash accelerator - SLH-DSA and LMS are almost
        entirely hashing
    A DEVICE WHOSE MASK-ROM ROOT OF TRUST IS RSA-2048 AND
    WHOSE ROM CANNOT BE UPDATED HAS A FIXED EXPIRY DATE.
    That is a business decision as much as a technical one,
    and it should be made deliberately rather than by
    default.                                             */
