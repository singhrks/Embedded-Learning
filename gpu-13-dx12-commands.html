DX12: command lists, allocators and queues

Nothing you call executes immediately. You record commands into a list, submit the list to a queue, and the GPU gets to it whenever it gets to it. The gap between "I recorded it" and "it ran" is where every DX12 lifetime bug lives.

Three objects, three jobs

   COMMAND ALLOCATOR
     the MEMORY the commands are written into. Grows as you
     record; never shrinks. You can only RESET it - which frees
     everything at once - and only when the GPU has finished
     executing every list ever recorded from it.

   COMMAND LIST
     the RECORDER. Cheap. Reset it to begin recording, Close
     it when done. A list may be reset and reused as soon as
     it is submitted - it does not own the memory.

   COMMAND QUEUE
     the SUBMISSION POINT. Lists execute in submission order
     within a queue. Different queues run CONCURRENTLY.

   THE LIFETIME RULE, and it is the whole chapter:

     allocator: reset only after the GPU is DONE with it
     list:      reset any time after Close + submit

   So you need ONE ALLOCATOR PER FRAME IN FLIGHT, and a fence
   to know when it is safe to reuse.

     frame 0 -> allocator A -> submit -> fence value 1
     frame 1 -> allocator B -> submit -> fence value 2
     frame 2 -> wait for fence >= 1, then reuse allocator A

   Reset an allocator the GPU is still reading and you get
   corruption or a device removal, usually several frames
   later and nowhere near the cause.
/* Creating the three. */

D3D12_COMMAND_QUEUE_DESC qd = {};
qd.Type  = D3D12_COMMAND_LIST_TYPE_DIRECT;
qd.Flags = D3D12_COMMAND_QUEUE_FLAG_NONE;
ComPtr<ID3D12CommandQueue> queue;
device->CreateCommandQueue(&qd, IID_PPV_ARGS(&queue));

/* One allocator per frame in flight. */
static const UINT kFrames = 3;
ComPtr<ID3D12CommandAllocator> alloc[kFrames];
for (UINT i = 0; i < kFrames; i++)
    device->CreateCommandAllocator(
        D3D12_COMMAND_LIST_TYPE_DIRECT, IID_PPV_ARGS(&alloc[i]));

/* One list is enough if you record single-threaded. */
ComPtr<ID3D12GraphicsCommandList> cmd;
device->CreateCommandList(0, D3D12_COMMAND_LIST_TYPE_DIRECT,
                          alloc[0].Get(), nullptr,
                          IID_PPV_ARGS(&cmd));
cmd->Close();     /* lists are created OPEN. Close it so the
                     frame loop's Reset is symmetrical. */

The frame loop

UINT64 fenceValue[kFrames] = {};
UINT64 nextFence = 1;
UINT   frame = 0;

void RenderFrame()
{
    /* 1. WAIT until the GPU has finished the frame that last
          used this allocator. THIS is what makes reuse safe. */
    if (fence->GetCompletedValue() < fenceValue[frame]) {
        fence->SetEventOnCompletion(fenceValue[frame], fenceEvent);
        WaitForSingleObject(fenceEvent, INFINITE);
    }

    /* 2. Reset the allocator (frees its memory), then the list
          (begins recording). Order matters: allocator first. */
    alloc[frame]->Reset();
    cmd->Reset(alloc[frame].Get(), initialPSO.Get());

    /* 3. Record. A freshly reset list has NO STATE - no
          descriptor heaps, no root signature, no viewport, no
          render targets. You set all of it, every frame. That
          is not overhead; it is what makes lists independent
          and recordable in parallel. */
    cmd->SetGraphicsRootSignature(rootSig.Get());
    ID3D12DescriptorHeap *heaps[] = { srvHeap.Get() };
    cmd->SetDescriptorHeaps(1, heaps);
    cmd->RSSetViewports(1, &viewport);
    cmd->RSSetScissorRects(1, &scissor);

    Transition(cmd.Get(), backBuffer[frame].Get(),
               D3D12_RESOURCE_STATE_PRESENT,
               D3D12_RESOURCE_STATE_RENDER_TARGET);

    cmd->OMSetRenderTargets(1, &rtv[frame], FALSE, &dsv);
    cmd->ClearRenderTargetView(rtv[frame], clearColour, 0, nullptr);
    /* ... draws ... */

    Transition(cmd.Get(), backBuffer[frame].Get(),
               D3D12_RESOURCE_STATE_RENDER_TARGET,
               D3D12_RESOURCE_STATE_PRESENT);

    /* 4. Close, then submit. A list must be Closed before
          ExecuteCommandLists or the runtime rejects it. */
    cmd->Close();
    ID3D12CommandList *lists[] = { cmd.Get() };
    queue->ExecuteCommandLists(1, lists);

    swapChain->Present(1, 0);

    /* 5. Signal a fence AFTER the submission, so we can later
          tell when this frame's work is done. */
    fenceValue[frame] = nextFence;
    queue->Signal(fence.Get(), nextFence++);

    frame = (frame + 1) % kFrames;
}
Frames in flight is a latency-versus-throughput dial

Two frames buffered keeps the GPU fed while the CPU records the next one. Three smooths hitches further but adds a frame of input latency. One means the CPU and GPU alternate, each idle half the time. Two or three is the normal range, and it must match your number of allocators and your swap-chain buffer count — mismatch them and you either stall or corrupt.

Queue types, and why they run concurrently

TypeCan doHardware
DIRECTEverything — draw, dispatch, copyThe main graphics engine
COMPUTEDispatch and copy, no drawsA separate async compute engine on most GPUs

BUNDLEA small pre-recorded set of draws, replayed into a direct listNot a queue. Rarely worth it on modern drivers
 
/* ASYNC COMPUTE: overlap work that uses different units.

   A shadow pass is geometry- and depth-bound; SSAO is
   ALU-bound. Run them on separate queues and they fill each
   other's gaps - typically 5-15% of frame time on a GPU that
   supports it well.                                        */

  graphics queue:  [ shadow maps ][ gbuffer ][ lighting ]
  compute queue:        [ SSAO ][ particle sim ]
                        ^                     ^
                        |                     |
                   both running at once, on different units

/* SYNCHRONISING BETWEEN QUEUES is done with fences, on the
   GPU - no CPU involvement: */

  computeQueue->ExecuteCommandLists(1, &ssaoList);
  computeQueue->Signal(sharedFence.Get(), 42);

  /* graphics queue WAITS for that, without stalling the CPU */
  graphicsQueue->Wait(sharedFence.Get(), 42);
  graphicsQueue->ExecuteCommandLists(1, &lightingList);

/* THE COPY QUEUE is the one everybody should use and few do.
   Uploading a texture on the direct queue serialises against
   your rendering. On the copy queue it happens in parallel,
   on a DMA engine that is otherwise idle:                  */

  copyQueue->ExecuteCommandLists(1, &uploadList);
  copyQueue->Signal(uploadFence.Get(), n);
  graphicsQueue->Wait(uploadFence.Get(), n);   /* use it after */

/* THE CAVEAT: resources have state (chapter 16), and the copy
   and compute queues support only a SUBSET of states. A
   resource used on a copy queue must be in COMMON state at
   the boundary. Getting this wrong is a classic multi-queue
   bug, and the debug layer catches it.                     */

Recording in parallel

/* The rules:
     - one ALLOCATOR per thread per frame in flight
     - one LIST per thread (lists are cheap to create)
     - lists EXECUTE in submission order, whatever order they
       were recorded in                                     */

struct ThreadCtx {
    ComPtr<ID3D12CommandAllocator>    alloc[kFrames];
    ComPtr<ID3D12GraphicsCommandList> list;
};
ThreadCtx ctx[kThreads];

void RecordChunk(int t, int frame, int first, int count)
{
    auto *c = &ctx[t];
    c->alloc[frame]->Reset();
    c->list->Reset(c->alloc[frame].Get(), pso.Get());

    /* every list sets up its own state - nothing is inherited */
    c->list->SetGraphicsRootSignature(rootSig.Get());
    c->list->SetDescriptorHeaps(1, heaps);
    c->list->RSSetViewports(1, &viewport);
    c->list->RSSetScissorRects(1, &scissor);
    c->list->OMSetRenderTargets(1, &rtv[frame], FALSE, &dsv);

    for (int i = first; i < first + count; i++)
        DrawObject(c->list.Get(), i);

    c->list->Close();
}

/* Then, on the main thread: */
  parallel_for(0, kThreads, [&](int t) {
      RecordChunk(t, frame, t * per, per);
  });

  ID3D12CommandList *all[kThreads];
  for (int t = 0; t < kThreads; t++) all[t] = ctx[t].list.Get();
  queue->ExecuteCommandLists(kThreads, all);   /* ONE submit   */

/* SUBMIT IN ONE CALL where you can: each
   ExecuteCommandLists has real driver overhead, so twenty
   calls of one list is measurably worse than one call of
   twenty.

   AND NOTE the barriers: resource transitions must be
   consistent across list boundaries. If list A leaves a
   resource in RENDER_TARGET and list B expects PIXEL_SHADER
   _RESOURCE, one of them must do the transition - and the
   runtime cannot check across lists at record time, only at
   execute time.                                            */
The two mistakes that produce delayed, confusing corruption

Resetting an allocator the GPU is still using. Symptoms appear frames later, in unrelated draws. Freeing or overwriting a resource that an in-flight command list still references. Same delay, same confusion. Both are solved the same way: a fence value per frame, and nothing is reused or released until the fence says that frame completed. Build that discipline into your allocator and upload helpers on day one rather than retrofitting it.
