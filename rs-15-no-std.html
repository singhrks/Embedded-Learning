no_std and bare-metal Rust

Rust without an operating system: what you lose, what you keep, and the boilerplate that turns a crate into a firmware image. Unlike C++, Rust was designed for this case from the start, and the result is genuinely comfortable.

The three layers

"No standard library" is really three separate questions, and separating them is what makes the rest of the chapter straightforward.

   core          ALWAYS AVAILABLE. No OS, no allocator.
                 Option, Result, Iterator, slices, str,
                 integers and floats, core::fmt, atomics,
                 mem, ptr, marker traits, panic machinery.
                 Most of the LANGUAGE lives here.

   alloc         needs a GLOBAL ALLOCATOR, nothing more.
                 Box, Vec, String, BTreeMap, Rc, Arc.
                 Opt in with `extern crate alloc;`.

   std           needs an OS. Files, sockets, threads,
                 processes, time, environment, HashMap
                 (because of random seeding).

   `#![no_std]` OPTS OUT OF std, keeping core. Add `alloc`
   back if you want heap collections and can supply an
   allocator.

   THE PRACTICAL POINT: `core` is not a cut-down subset -
   it contains iterators, the whole Option/Result API,
   formatting, atomics and the numeric traits. Idiomatic
   Rust works almost unchanged; what you lose is I/O,
   threads and heap collections.

   COMPARE C++ FREESTANDING (C++ chapter 15), where you must
   check header by header what is available and supply
   several runtime functions yourself.

A minimal firmware crate

The smallest firmware crate that builds and runs, with every line explained — because on a bare-metal target every one of them is doing something you would otherwise get from a runtime.

#![no_std]
#![no_main]

use panic_halt as _;            // supplies #[panic_handler]
use cortex_m_rt::entry;         // supplies the reset vector
use cortex_m::asm;

#[entry]
fn main() -> ! {                // NEVER returns
    let p = pac::Peripherals::take().unwrap();

    p.RCC.ahb1enr.modify(|_, w| w.gpiocen().set_bit());
    p.GPIOC.moder.modify(|_, w| w.moder13().output());

    loop {
        p.GPIOC.bsrr.write(|w| w.bs13().set_bit());
        asm::delay(8_000_000);
        p.GPIOC.bsrr.write(|w| w.br13().set_bit());
        asm::delay(8_000_000);
    }
}

/* `#![no_main]` because the C `main` signature and the
   pre-main runtime do not exist. `#[entry]` from
   cortex-m-rt provides the reset handler, which zeroes .bss,
   copies .data from flash, initialises the FPU, and calls
   your function (compilers chapter 12).

/* THE PANIC HANDLER is mandatory - core cannot provide one
   because the right behaviour is application-specific: */
    use panic_halt as _;        // spin forever
    use panic_reset as _;       // system reset
    use panic_probe as _;       // print over RTT, then halt
    use panic_persist as _;     // save the message to RAM
                                // across a reset

/* OR WRITE ONE, which is what a product does: */
    #[panic_handler]
    fn panic(info: &core::panic::PanicInfo) -> ! {
        // save the location for the next boot to report
        cortex_m::interrupt::disable();
        write_panic_record(info.location());
        cortex_m::peripheral::SCB::sys_reset();
    }

/* AND THE INTERRUPT HANDLERS: */
    use cortex_m_rt::exception;
    use stm32f4xx_hal::pac::interrupt;

    #[exception]
    fn SysTick() { TICKS.fetch_add(1, Ordering::Relaxed); }

    #[interrupt]
    fn USART1() { critical_section::with(|cs| { ... }); }

    #[exception]
    unsafe fn HardFault(ef: &ExceptionFrame) -> ! {
        // ef holds the stacked registers - log them
        log_fault(ef);
        loop {}
    }
/* The names are checked against the device's vector table by
   the PAC, so a typo is a compile error rather than an
   interrupt that never fires.                            */

Project layout

An embedded Rust project needs a few files that a hosted one does not, and each exists to answer a question the toolchain cannot infer.

# Cargo.toml
    [dependencies]
    cortex-m = "0.7"
    cortex-m-rt = "0.7"
    embedded-hal = "1.0"
    stm32f4xx-hal = { version = "0.21",
                      features = ["stm32f411"] }
    heapless = "0.8"
    defmt = "0.3"
    defmt-rtt = "0.4"
    panic-probe = { version = "0.3", features = ["print-defmt"] }
    critical-section = "1.1"

    [profile.release]
    opt-level = "z"
    lto = "fat"
    codegen-units = 1
    panic = "abort"
    debug = 2                   # symbols cost nothing in
                                # flash and defmt needs them
    overflow-checks = false

    [profile.dev]
    opt-level = 1               # -O0 firmware is often too
                                # slow to run

# .cargo/config.toml
    [build]
    target = "thumbv7em-none-eabihf"

    [target.thumbv7em-none-eabihf]
    runner = "probe-rs run --chip STM32F411RETx"
    rustflags = [
      "-C", "link-arg=-Tlink.x",        # from cortex-m-rt
      "-C", "link-arg=-Tdefmt.x",       # for defmt
      "-C", "linker=flip-link",         # STACK OVERFLOW
                                        # PROTECTION
    ]

# memory.x - the memory map, read by cortex-m-rt's link.x
    MEMORY
    {
      FLASH : ORIGIN = 0x08000000, LENGTH = 512K
      RAM   : ORIGIN = 0x20000000, LENGTH = 128K
    }

# build.rs copies memory.x into OUT_DIR (chapter 11).

# THEN:
    cargo run --release
# builds, flashes and runs on the target, streaming defmt
# logs back. One command.

/* flip-link IS WORTH SPECIAL MENTION: it moves the stack
   BELOW static memory, so a stack overflow hits an unmapped
   region and faults immediately instead of silently
   corrupting .bss. That is a free fix for the single worst
   embedded failure mode (Linux chapter 02 describes the same
   problem), and it costs nothing.                        */
The three tools that change the experience

probe-rs — flash, run, debug and stream logs with one command, no vendor IDE. defmt — deferred formatting: the format string stays in the ELF and only the arguments go over the wire, so a log line costs a few bytes and a handful of cycles. flip-link — stack overflow becomes a fault instead of corruption. Together they are why embedded Rust tooling is frequently better than the C equivalent, not merely comparable.

What you lose, and the replacement

Working out what you actually lose, and what replaces it, is the practical core of going no_std. Most of the replacements are better than expected.

/* MAKING A LIBRARY WORK BOTH WAYS - the convention every
   good crate follows: */

    #![cfg_attr(not(feature = "std"), no_std)]

    #[cfg(feature = "alloc")]
    extern crate alloc;

    #[cfg(feature = "alloc")]
    use alloc::vec::Vec;

    // Cargo.toml
    [features]
    default = ["std"]
    std = ["alloc"]
    alloc = []

/* AND THE CHECK: `cargo build --no-default-features` in CI,
   so a std-only dependency cannot creep in unnoticed.

/* USING A DEPENDENCY IN no_std: */
    serde = { version = "1", default-features = false,
              features = ["derive"] }
/* `default-features = false` is the crucial part - most
   crates enable std by default. If a crate does not support
   no_std, that is usually a hard blocker.               */

Adding a heap, if you must

A heap is available if you want one, and the decision to use it is a design decision with real consequences on a device with no memory protection.

    #![no_std]
    extern crate alloc;

    use embedded_alloc::LlffHeap as Heap;
    use alloc::{vec::Vec, string::String};

    #[global_allocator]
    static HEAP: Heap = Heap::empty();

    #[entry]
    fn main() -> ! {
        {
            use core::mem::MaybeUninit;
            const HEAP_SIZE: usize = 8 * 1024;
            static mut MEM: [MaybeUninit<u8>; HEAP_SIZE] =
                [MaybeUninit::uninit(); HEAP_SIZE];
            unsafe {
                HEAP.init(core::ptr::addr_of_mut!(MEM) as usize,
                          HEAP_SIZE)
            }
        }

        let mut v = Vec::new();
        v.push(42);
        ...
    }

/* HANDLING EXHAUSTION: */
    let mut v = Vec::new();
    v.try_reserve(100)?;                // Result, not a panic
    // otherwise allocation failure calls the OOM handler,
    // which by default panics

/* SHOULD YOU? Usually not.
     · fragmentation is unbounded over a long uptime
     · allocation time is not deterministic
     · failure handling is awkward
     · heapless gives you the same interfaces with a bounded
       failure mode (chapter 08)

   WHEN IT IS REASONABLE: a device with megabytes of RAM
   running a network stack or a filesystem, where the working
   set genuinely varies. On a 64 KB microcontroller, use
   heapless and static allocation.                        */

Controlling size

Binary size is a hard constraint rather than a preference on most microcontrollers, and Rust's defaults are not tuned for it. These settings are where the wins are.

# --- MEASURE FIRST ---
    cargo size --release -- -A
       .vector_table  1024
       .text         18432
       .rodata        2048
       .data           128
       .bss           4096

    cargo bloat --release -n 30
    cargo bloat --release --crates       # by dependency

# --- THE BIGGEST WINS, in order ---

# 1. THE PROFILE (chapter 11) - typically halves the binary:
    opt-level = "z", lto = "fat", codegen-units = 1,
    panic = "abort"

# 2. AVOID CORE::FMT. The formatting machinery is often the
#    single largest item in a small firmware:
    panic!("bad value: {}", x);         // pulls in fmt
    panic!("bad value");                // does not
    defmt::info!("value {=u32}", x);    // FORMATS ON THE
                                        // HOST - the string
                                        // never enters the
                                        // binary

# 3. defmt INSTEAD OF ANY OTHER LOGGING. It is the difference
#    between a few hundred bytes and several kilobytes.

# 4. PANICS. Every `unwrap`, every index, every slice
#    operation can panic, and each panic site carries a
#    location string. Use `get()`, `checked_*` and explicit
#    handling (chapter 07). Then:
    panic-never = "0.1"
#    makes any REACHABLE panic a LINK ERROR - which is a
#    build-time proof that no panic can occur.

# 5. build-std, to rebuild core with your profile:
    cargo +nightly build -Z build-std=core \
        -Z build-std-features=panic_immediate_abort \
        --target thumbv7em-none-eabihf --release
#    `panic_immediate_abort` removes the panic formatting
#    from core itself. Often several kilobytes.

# 6. --gc-sections is on by default via link.x, but check:
    cargo nm --release | sort -k1

# A REALISTIC RESULT: a blinky is around 2 KB; a firmware
# with a HAL, defmt logging and a USB stack is 30-60 KB.
# Comparable with C once the profile is right, and the
# difference is usually formatting rather than the language.

Testing and debugging

Testing code that cannot run on your development machine needs a different approach, and the standard answer splits the problem in two.

/* --- HOST TESTS for the portable logic (chapter 11) --- */
    #[cfg(test)]
    mod tests {
        use super::*;
        #[test]
        fn crc_matches_reference() {
            assert_eq!(crc32(b"hello"), 0x3610A686);
        }
    }
    // cargo test --target x86_64-unknown-linux-gnu
    // put the logic in a portable crate so this works

/* --- ON-TARGET TESTS --- */
    #[defmt_test::tests]
    mod tests {
        #[test]
        fn uart_loopback() {
            let mut u = setup_uart();
            u.write(b'x').unwrap();
            assert_eq!(u.read().unwrap(), b'x');
        }
    }
    // cargo test --target thumbv7em-none-eabihf
    // runs on the DEVICE, results streamed back over RTT

/* --- LOGGING --- */
    defmt::trace!("entering state {}", state);
    defmt::debug!("adc = {=u16}", raw);
    defmt::info!("ready");
    defmt::warn!("retry {=u8}/{=u8}", n, max);
    defmt::error!("fault: {}", e);
    defmt::assert!(x < 10, "x too large: {}", x);

    #[derive(defmt::Format)]        // like Debug, for defmt
    struct Reading { temp: i16, humidity: u8 }

    // filter at build time:
    DEFMT_LOG=info cargo run --release

/* --- DEBUGGING --- */
    probe-rs run --chip STM32F411RETx target/.../fw
    probe-rs attach --chip STM32F411RETx
    cargo embed                     # a TUI with RTT

    # GDB, when you need it:
    probe-rs gdb --chip STM32F411RETx
    (gdb) target remote :1337
    (gdb) monitor reset halt
    (gdb) break main
    (gdb) continue

/* --- AND THE HARD FAULT HANDLER, which is worth writing
       properly: */
    #[exception]
    unsafe fn HardFault(ef: &ExceptionFrame) -> ! {
        defmt::error!("HardFault at pc={=u32:#x} lr={=u32:#x}",
                      ef.pc(), ef.lr());
        // and the fault status registers (ARM chapter 29)
        let cfsr = (*SCB::PTR).cfsr.read();
        defmt::error!("CFSR = {=u32:#x}", cfsr);
        loop {}
    }
/* Which turns "it hangs" into "it faulted at this address
   because of an unaligned access" - the same diagnosis
   process as ARM chapter 29, with the registers named.  */

How it shows up

SymptomCause and fix
"can't find crate for std"A dependency needs std — set default-features = false
"#[panic_handler] function required"Add use panic_halt as _; or write one
"language item required: eh_personality"Set panic = "abort"
"undefined reference to memcpy"Needs a compiler_builtins or the target's runtime
Linker error about link.x or memory regionsmemory.x missing or not copied by build.rs
Binary far larger than expectedProfile not tuned, or core::fmt pulled in
Firmware hangs immediatelyStack overflow — use flip-link; or clocks not configured
Interrupt never firesNot unmasked in the NVIC, or the handler name is wrong
Panic with no messagepanic-halt — switch to panic-probe while developing
Peripherals::take() returns NoneCalled twice — by design (ch. 02)
Allocation fails at run timeHeap too small, or fragmented — prefer heapless
defmt output is garbledThe ELF and the running binary differ — reflash
