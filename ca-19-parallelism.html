Parallelism: ILP, SIMD, SMT and multicore

Clock speeds stopped rising around 2005. Everything since has come from doing more things at once. This chapter covers the four kinds of parallelism, which ones are free, which ones you must ask for, and why "add more cores" stops working.

Why parallelism became the only option

Processors stopped getting faster in the way they had for decades, and the reason was physics rather than engineering fashion. Understanding what stopped explains why every machine you buy now has many cores instead of one fast one.

Dynamic power in CMOS:      P ≈ C × V² × f

  Raising frequency f raises power linearly — and requires raising
  voltage V to keep switching fast enough, which raises power by the
  SQUARE. So a 20% clock increase can cost ~70% more power.

  ~2005: the "power wall". Air cooling caps a chip around 100-150 W.
  Frequencies flattened at 3-4 GHz and have stayed there for 20 years.

  Meanwhile transistor counts kept doubling. The only way to spend
  them was on MORE UNITS rather than FASTER ones:

     more execution units per core        -> ILP
     wider registers                      -> SIMD
     more thread contexts per core        -> SMT
     more cores                           -> multicore
     specialised units                    -> accelerators, NPUs

This is the entire shape of modern computing, and it is a
consequence of one equation.

What limits ILP, and what you can do about it

  TRUE DEPENDENCIES. A dependent chain cannot be parallelised at all.

     s = 0;
     for (i = 0; i < n; i++)
             s += a[i];        <- every add waits for the previous one
                                  4-cycle FP add latency = 4 cycles/element
                                  no matter how wide the core is

  Break the chain with accumulators — the single highest-value ILP
  optimisation available to a programmer:

     s0 = s1 = s2 = s3 = 0;
     for (i = 0; i < n; i += 4) {
             s0 += a[i];   s1 += a[i+1];      <- four INDEPENDENT chains
             s2 += a[i+2]; s3 += a[i+3];         now the 4-cycle latencies
     }                                           overlap
     s = (s0 + s1) + (s2 + s3);

  Typical result: ~4x faster, from an unchanged instruction count.

  Note the reassociation: this changes floating-point results
  (chapter 03), which is exactly why the compiler will NOT do it for
  you unless you pass -ffast-math. On integers it does it freely.

Beyond ~4-wide issue, ILP hits diminishing returns: real code simply does not contain enough independent work, and the hardware to find more grows quadratically. That is why cores stopped getting wider and started getting more numerous.

Data-level parallelism: SIMD

One instruction, several data elements. Cheap in hardware — one instruction fetch and decode drives many ALUs — but you or your compiler must express it.

   scalar                          SIMD (128-bit, 4 x float32)

   c[0] = a[0] + b[0];             ┌────┬────┬────┬────┐  a
   c[1] = a[1] + b[1];             ├────┼────┼────┼────┤
   c[2] = a[2] + b[2];             │ +  │ +  │ +  │ +  │  b
   c[3] = a[3] + b[3];             ├────┼────┼────┼────┤
                                   └────┴────┴────┴────┘  c
   4 instructions                  1 instruction

  ARM NEON      128-bit fixed        V0-V31
  ARM SVE/SVE2  128-2048, scalable   Z0-Z31 + predicates P0-P15
  x86 AVX2      256-bit
  x86 AVX-512   512-bit

SVE's key idea is VECTOR LENGTH AGNOSTIC code: the same binary runs
optimally on 128-bit and 512-bit implementations, because the loop is
written against a runtime length with predication for the tail.
No recompilation, no dispatch table.
/* Four ways to get SIMD, in order of preference */

/* 1. Let the compiler do it. Write clean, obviously independent loops. */
void add(float *restrict c, const float *a, const float *b, int n) {
        for (int i = 0; i < n; i++)
                c[i] = a[i] + b[i];
}
/* -O3 -march=armv8-a+simd emits NEON automatically.
   `restrict` is what makes it legal: it promises the arrays do not
   overlap, so the compiler may reorder the accesses. Without it the
   compiler must assume c may alias a, and vectorisation is unsafe. */

/* Check whether it actually happened - do not assume: */
//   gcc -O3 -fopt-info-vec-missed   (tells you WHY it did not)

/* 2. OpenMP, when the compiler needs permission */
#pragma omp simd
for (int i = 0; i < n; i++) c[i] = a[i] + b[i];

/* 3. Intrinsics: explicit, portable across compilers, readable */
#include <arm_neon.h>
for (int i = 0; i < n; i += 4) {
        float32x4_t va = vld1q_f32(a + i);
        float32x4_t vb = vld1q_f32(b + i);
        vst1q_f32(c + i, vaddq_f32(va, vb));
}

/* 4. Hand-written assembly. Rarely justified; hard to maintain. */
Why your loop did not vectorise

The compiler must prove the transformation is safe. Common blockers, roughly in order of frequency: possible pointer aliasing (fix with restrict); a loop-carried dependency; a data-dependent early exit or break; function calls that cannot be inlined; a non-contiguous or indirect access pattern (a[idx[i]]); floating-point reassociation that would change results; and a trip count unknown at compile time combined with expensive tail handling. Ask the compiler with -fopt-info-vec-missed rather than guessing — it will name the reason.

SIMD does not rescue a memory-bound loop

Vector add has an arithmetic intensity of about 0.08 FLOP/byte — far left of the roofline ridge (chapter 18). Making the arithmetic 4× faster changes nothing when you are waiting on DRAM. Vectorise things that are compute bound, or fix the memory behaviour first. This is the most common reason a carefully vectorised loop shows no improvement.

Thread-level parallelism on one core: SMT

Simultaneous multithreading keeps two or more architectural contexts in one physical core, so when one thread stalls the other uses the idle execution units.

Duplicated per threadShared between threads
Architectural registers, program counter, exception stateExecution units, caches, TLBs, branch predictors, memory bandwidth
 
Typical gain: 10-30%, for maybe 5% extra area. Excellent value —
when the threads stall a lot and do not fight over cache.

When SMT HURTS:
  · both threads are compute bound and already saturating the units
  · they have large, distinct working sets, so each halves the other's
    effective cache
  · latency matters: your thread now shares a core with an unknown
    neighbour, so worst-case timing becomes unpredictable
  · SECURITY: sharing caches and predictors is a side channel. Threads
    can observe each other. Cloud providers and hardened systems often
    disable SMT entirely for this reason.

ARM's application cores generally do NOT implement SMT — the design
choice has been more, simpler cores instead. Some Neoverse and
specialised ARM cores do. x86 calls it Hyper-Threading.

Multicore

Putting several processors on one chip sounds straightforward and raises a series of questions that do not arise with one: what they share, how they stay consistent, and whether they should even be identical to each other.

Homogeneous                     Heterogeneous (big.LITTLE, DynamIQ)

  4x identical cores              2x big  (wide, OoO, high power)
  simple scheduling               4x LITTLE (narrow, in-order, efficient)
                                  same ISA, very different performance

  Heterogeneity buys energy efficiency: run background work on the
  LITTLE cores at a fraction of the power, migrate to big under load.

  What it costs YOU:
    · benchmark results depend on which core you landed on
    · a thread can migrate mid-measurement
    · worst-case timing analysis must assume the slowest core
    · pin with taskset when measuring anything (chapter 18)

Why adding cores stops helping

LimitMechanismWhat to do
Amdahl's serial fractionThe sequential part never shrinksParallelise more of it, or accept the ceiling
Lock contentionThreads serialise on a shared lockFiner-grained locks, per-CPU data, lock-free structures, RCU
Memory bandwidthAll cores share one memory controllerImprove locality; reduce bytes moved (ch. 13)
Cache coherence trafficShared lines ping-pong between coresPad to line boundaries; avoid shared writes (ch. 15)
False sharingUnrelated variables in one cache lineAlign per-thread data to 64 bytes
Load imbalanceOne thread finishes last; the rest idleDynamic scheduling, work stealing, smaller chunks
Synchronisation overheadBarriers and joins cost more than the workCoarser tasks; fewer barriers
Power and thermalAll-core turbo is lower than single-core turboNothing — it is physics (ch. 20)
Negative scaling is a specific, diagnosable bug

If throughput decreases as you add threads, you are almost certainly looking at false sharing or lock contention — not at a fundamental limit. Confirm with perf c2c and lock profiling before concluding the problem is not parallelisable. Genuine bandwidth saturation flattens the curve; contention bends it downwards.

Parallel programming models

Hardware parallelism is only useful if software can express it. Each model below makes a different trade between how much control you get and how much of the difficulty it hides.

ModelShapeGood forHazard
Shared memory threadspthreads, std::threadFine-grained work on one machineRaces, deadlock, false sharing

Data parallel#pragma omp parallel forRegular loops over arraysLoad imbalance; false sharing at chunk edges
Message passingMPI, channels, actorsDistributed memory; no shared state by constructionMessage overhead; harder to load balance

/* the same loop, three ways */

/* data parallel */
#pragma omp parallel for schedule(dynamic, 64) reduction(+:sum)
for (int i = 0; i < n; i++)
        sum += heavy(a[i]);
/* `dynamic` handles imbalance when heavy() varies per element;
   `reduction` gives each thread a private accumulator and combines
   them at the end - which is exactly the false-sharing fix from
   chapter 15, done for you.                                       */

/* explicit threads with per-thread state, padded */
struct alignas(64) partial { double sum; };
std::vector<partial> parts(nthreads);        /* one cache line each */

/* pipeline */
stage1 -> queue -> stage2 -> queue -> stage3
/* throughput = 1 / max(stage time). Balance the stages, and size
   the queues to absorb jitter without adding needless latency.   */

Measuring parallel efficiency

Adding threads does not reliably make things faster, and the only way to know is to measure. These are the numbers that tell you whether parallelism is actually paying for itself.

speedup    S(n) = T(1) / T(n)
efficiency E(n) = S(n) / n          # 1.0 = perfect

# plot efficiency against thread count. The SHAPE is diagnostic:
#   flat near 1.0           -> scaling well, keep going
#   gradual decline         -> Amdahl's serial fraction, or bandwidth
#   sharp knee              -> a resource saturated: bandwidth or a lock
#   DECREASING below 1 core -> false sharing or contention. A bug.

perf stat -e cycles,instructions ./program           # per-thread IPC
perf c2c record ./program                            # false sharing
perf lock record ./program && perf lock report       # lock contention
perf record -e sched:sched_switch                    # migration, imbalance
