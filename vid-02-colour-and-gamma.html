Colour, gamma and colour spaces

The number 128 in a pixel does not mean "half as bright as 255". Almost every colour bug in software comes from that one fact, and from code that treats stored values as if they were light.

The single most important idea

   PIXEL VALUES ARE NOT LINEAR IN LIGHT.

   sRGB, roughly:      light = (value / 255) ^ 2.2

     value    relative light
       0        0.000
      64        0.052        <- a QUARTER of the value gives
     128        0.216           5% of the light
     192        0.528        <- HALF the value gives 22%
     255        1.000

   WHY IT IS DONE

     Human vision is roughly logarithmic: we distinguish
     dark tones far more finely than bright ones. Storing
     LINEAR light in 8 bits wastes most codes on highlights
     nobody can tell apart, and leaves visible banding in the
     shadows.

     A gamma curve spends the codes where the eye looks. It
     is perceptual compression, and it predates computers -
     CRT phosphors happened to have a response near 2.2, so
     the convention was free.

   THE CONSEQUENCE

     Any arithmetic that models LIGHT - averaging, blending,
     resizing, blurring, alpha compositing, lighting - must
     be done in LINEAR space. Doing it on stored values is
     mathematically wrong, and the error is visible.
/* THE CLASSIC DEMONSTRATION: average black and white.

   In sRGB values:      (0 + 255) / 2  = 128
   128 in sRGB is 21.6% of the light.

   In linear light:     (0.0 + 1.0) / 2 = 0.5
   0.5 linear encodes back to sRGB 188.

   So the "correct" mid-grey is 188, not 128. Averaging in
   the wrong space makes everything TOO DARK, and it is why
   badly-resized images look muddier than the original.   */

/* THE CORRECT SANDWICH */

float srgb_to_linear(float c)      /* decode */
{
        return (c <= 0.04045f) ? c / 12.92f
                               : powf((c + 0.055f) / 1.055f, 2.4f);
        /* the linear segment near zero avoids an infinite
           slope at 0 - it is why sRGB is "gamma 2.2-ish"
           rather than exactly 2.2                          */
}

float linear_to_srgb(float c)      /* encode */
{
        return (c <= 0.0031308f) ? c * 12.92f
                                 : 1.055f * powf(c, 1.0f / 2.4f) - 0.055f;
}

/* resize, blur, blend, light -> ALL between those two calls. */

/* AND THE FREE VERSION: let the hardware do it.
     GPU:  use a _SRGB texture format and an _SRGB render
           target. The sampler decodes on read and the ROP
           encodes on write, for nothing, and it filters in
           linear space which is also correct (GPU chapter 9).
     Display: a framebuffer declared sRGB gets the same
           treatment in the display controller.

   Doing the conversion in a shader is slower AND filters in
   the wrong space. Use the format.                       */
Alpha blending in sRGB is wrong, and everyone does it

Compositing 50% of a bright colour over a dark one with plain sRGB arithmetic gives a result that is too dark, with a characteristic dark fringe around anti-aliased edges — most visible on white text over a dark background. Browsers, UI toolkits and many game engines do this, partly for speed and partly because "fixing" it changes the appearance of every existing asset. Know that it is wrong, and know why your text looks thin.

What a colour space actually specifies

   THREE INDEPENDENT THINGS, and conflating them causes most
   colour-management confusion:

   1. PRIMARIES - which physical red, green and blue.
        Given as CIE xy coordinates. Two displays both
        "showing RGB(255,0,0)" emit different reds if their
        primaries differ. This defines the GAMUT: the set of
        colours representable at all.

   2. TRANSFER FUNCTION - how code values map to light.
        sRGB, BT.1886, PQ, HLG, linear, Log-C...
        This is "gamma", above.

   3. WHITE POINT - what RGB(255,255,255) means.
        D65 (6500 K) almost everywhere; D50 in print.

   A COLOUR SPACE = primaries + transfer + white point.
   Change any one and the same numbers mean a different
   colour.

   THE ONES YOU WILL MEET

     sRGB / BT.709    same primaries. The web and HD video.
                      Slightly different transfer functions,
                      which is a real and annoying subtlety.
     BT.601           SD video. DIFFERENT primaries, and a
                      different YCbCr matrix (chapter 3).
     DCI-P3           wider gamut. Apple displays, cinema.
     BT.2020          very wide. UHD and HDR.
     ACEScg, Rec.2100 working spaces for grading and HDR.

   THE CONVERSION between two RGB spaces is a 3x3 matrix,
   applied IN LINEAR LIGHT:

     decode transfer -> matrix (RGB_a -> XYZ -> RGB_b)
       -> gamut map if out of range -> encode transfer

   Skipping the decode is the same error as before, one level
   up.

Untagged data is the real problem

/* Pixel values alone are meaningless. They need METADATA
   saying which colour space they are in. When that metadata
   is missing, software GUESSES - and different software
   guesses differently.                                     */

  WHERE THE TAG LIVES
    images   ICC profile, or EXIF ColorSpace, or a PNG cHRM
             + gAMA chunk
    video    the "VUI" in the bitstream: colour_primaries,
             transfer_characteristics, matrix_coefficients,
             video_full_range_flag
    surfaces DXGI_COLOR_SPACE_*, VkColorSpaceKHR,
             drm_color_encoding / drm_color_range properties

/* THE FOUR VIDEO TAGS, and they are separate on purpose: */

  colour_primaries          1 = BT.709, 5 = BT.601 PAL,
                            6 = BT.601 NTSC, 9 = BT.2020
  transfer_characteristics  1 = BT.709, 16 = PQ, 18 = HLG
  matrix_coefficients       1 = BT.709, 6 = BT.601,
                            9 = BT.2020 non-constant
  video_full_range_flag     0 = LIMITED (16-235), 1 = FULL
                            (0-255)

/* THAT LAST ONE causes more visible bugs than the other
   three combined - see below. */

# Read what a file actually claims:
$ ffprobe -v error -select_streams v:0 \
    -show_entries stream=color_primaries,color_transfer,color_space,color_range \
    -of default=nw=1 input.mp4
color_range=tv
color_space=bt709
color_transfer=bt709
color_primaries=bt709

# "unknown" for any of them means the next tool will guess.
# The usual guess is: BT.601 below 720 lines, BT.709 at or
# above. Which is why an SD clip scaled to HD sometimes
# shifts colour.
Limited range versus full range

Broadcast video stores luma in 16–235, not 0–255, leaving headroom and footroom for filter overshoot. If a decoder outputs limited-range data and something downstream treats it as full range, blacks become dark grey and whites become light grey — a washed out image. Do the opposite and blacks clip to zero and highlights blow out — crushed. This is the single most common video colour bug, it is entirely a metadata problem, and both directions look like a broken display rather than a tagging error.

A correct pipeline, in order

   SOURCE (tagged: BT.709, limited range, 8-bit)
        |
        |  1. expand range 16-235 -> 0-1
        |  2. YCbCr -> RGB with the BT.709 matrix (chapter 3)
        v
   NON-LINEAR RGB, BT.709 primaries
        |
        |  3. decode the transfer function
        v
   LINEAR RGB, BT.709 primaries
        |
        |  4. ALL image maths happens HERE:
        |     resize, blur, blend, composite, colour grade
        |
        |  5. matrix to the DISPLAY's primaries
        v
   LINEAR RGB, display primaries
        |
        |  6. encode the display's transfer function
        |  7. dither to the output bit depth
        v
   DISPLAY

   SKIPPING STEP 3 is the commonest error and makes everything
   too dark.
   SKIPPING STEP 5 is the second, and makes wide-gamut content
   oversaturated on an sRGB screen - or sRGB content look flat
   on a P3 one.
   SKIPPING STEP 7 puts banding back after you paid for
   precision.
