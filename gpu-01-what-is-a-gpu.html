What a GPU is and why it exists

A CPU is built to finish one instruction stream as fast as possible. A GPU is built to have so much work outstanding that it never has to wait. Almost everything that seems strange about GPU programming follows from that one difference in objective.

Latency versus throughput

   THE SAME PROBLEM: memory is ~300 cycles away.

   A CPU SOLVES IT BY NOT WAITING
     huge caches                    keep data close
     out-of-order execution         run later instructions now
     branch prediction + speculation
     prefetchers
     deep pipelines, high clocks

     -> most of the transistor budget is spent on CONTROL and
        CACHE. Perhaps 1-5% is arithmetic.

   A GPU SOLVES IT BY HAVING SOMETHING ELSE TO DO
     thousands of threads resident at once
     a scheduler that switches between them EVERY CYCLE,
       at zero cost, because every thread's registers stay in
       the register file
     small caches, enormous register files
     in-order, simple cores, modest clocks

     -> most of the budget is ARITHMETIC. Latency is not
        reduced at all; it is HIDDEN behind other work.

   THE CONSEQUENCE, and it is the whole chapter:

     a CPU is fast at ONE thing.
     a GPU is fast only if you give it TEN THOUSAND things.

     A GPU running one thread is far slower than a CPU running
     one thread. There is no configuration in which a GPU wins
     on a serial problem.

The register file is the surprising number

A GPU SM has more register storage than L1 cache — commonly 256 KB of registers against 128 KB of L1. That inversion is the whole latency-hiding trick: every resident thread keeps its full register state live, so switching between them costs nothing. It also explains why "using too many registers" is a real performance problem (chapter 5): registers are the budget that decides how many threads fit.

How it became a general-purpose processor

   1990s   FIXED FUNCTION
             transform, light, rasterise, texture. All in
             silicon, configured by a few registers. You did
             not program it; you set state.

   2001    PROGRAMMABLE SHADERS
             vertex and pixel shaders. Tiny assembly programs,
             no branches, no loops, 128 instructions.

   2004    people notice the pixel shader is a parallel
             floating-point machine, and start smuggling
             physics and linear algebra through it as
             textures. "GPGPU" - genuinely by abusing the
             graphics API.

   2006    UNIFIED SHADERS. One pool of cores runs vertex,
             pixel and geometry work. The hardware stops
             caring which is which.

   2007    CUDA. You may now write C. The graphics API is no
             longer in the way.

   2010s   compute shaders in every graphics API; OpenCL;
             GPUs enter supercomputers.

   2017    TENSOR CORES. Fixed-function matrix-multiply units
             bolted back on - because the general machine was
             not fast enough for deep learning.

   2018    RT CORES. Fixed-function ray-triangle intersection,
             for the same reason.

   NOTE THE ARC: fixed function -> programmable -> general ->
   fixed function again, for the workloads that matter enough.
   That cycle is the most reliable pattern in hardware, and it
   is worth expecting the next turn of it.

The execution model, in one picture

   You write a KERNEL: one function, describing what ONE
   thread does. You then launch millions of them.

     __global__ void add(float *a, float *b, float *c, int n)
     {
             int i = blockIdx.x * blockDim.x + threadIdx.x;
             if (i < n) c[i] = a[i] + b[i];
     }
     add<<<(n + 255) / 256, 256>>>(a, b, c, n);

   THE HIERARCHY (CUDA names / portable names)

     thread          one lane. Has its own registers.
       |
     warp / wavefront    32 (NVIDIA) or 32-64 (AMD) threads
       |                 that execute IN LOCKSTEP. The real
       |                 unit of execution - chapter 2.
       |
     block / workgroup   up to 1024 threads. Share fast
       |                 on-chip memory and can barrier with
       |                 each other. Runs entirely on ONE SM.
       |
     grid / NDRange      all the blocks of one launch. Blocks
                         may run in ANY order, on any SM, and
                         cannot synchronise with each other.

   THE RULE THAT SHAPES EVERYTHING:
     threads within a block can cooperate.
     blocks cannot. If your algorithm needs global
     synchronisation, you need a SECOND KERNEL LAUNCH.

What it costs to use one

  kernel launch overhead ...............   5-20 us
  PCIe transfer, host to device ........   ~25 GB/s (PCIe 4 x16)
  PCIe latency, one way ................   1-2 us
  device memory bandwidth ..............   500-3000 GB/s
  device memory latency ................   400-800 cycles
  shared memory latency ................   ~20-30 cycles

/* THE ARITHMETIC THAT MATTERS

   Copying 1 MB to the GPU:      ~40 us
   Adding 1 MB of floats there:  ~2 us

   -> the transfer costs twenty times the compute. A kernel
      that is only worth running if the data is ALREADY on the
      device is the normal case, not the exception.

   THE COMPUTE-TO-COMMUNICATION RATIO is the first thing to
   estimate. Arithmetic intensity - FLOPs per byte moved -
   tells you whether you are compute-bound or bandwidth-bound
   before you write a line:

        vector add       0.08 FLOP/byte   hopelessly
                                          bandwidth-bound
        SGEMM (large)    ~50 FLOP/byte    compute-bound
        LLM inference,
          batch size 1   ~2 FLOP/byte     bandwidth-bound,
                                          which is why it is
                                          slow (AI chapter 25)

   Integrated GPUs (phones, Apple Silicon, consoles) share
   DRAM with the CPU, so there is no copy at all - but also no
   HBM, so bandwidth is much lower. Different trade, same
   analysis.                                                 */
Not everything belongs on a GPU

Good fits are uniform (every element does the same work), independent (no ordering between elements), arithmetic-heavy relative to bytes moved, and large (millions of items, not thousands). Bad fits: pointer chasing, branch-heavy logic, small problems where launch overhead dominates, anything sequentially dependent, and anything needing frequent CPU coordination. A "GPU rewrite" of an unsuitable algorithm typically lands between two and ten times slower.
