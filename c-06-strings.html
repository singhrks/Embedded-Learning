Strings and buffer safety

C has no string type. It has a convention — a byte array ending in a zero — and a library of functions that trust you to have got the sizes right. This chapter covers the convention, why the classic functions are dangerous, and what to use instead.

The convention

A C string is not a type. It is an array of characters with an agreement that a zero byte marks the end — and essentially every string vulnerability in history comes from that agreement being violated somewhere.

A C string is a contiguous sequence of characters terminated by '\0'.

   char s[] = "hello";

   index:   0    1    2    3    4    5
          +----+----+----+----+----+----+
          | h  | e  | l  | l  | o  | \0 |
          +----+----+----+----+----+----+
   size:  6 bytes.   length: 5 characters.

Every consequence of C string handling follows from this:

  · LENGTH IS NOT STORED. strlen() walks the array counting bytes,
    so it is O(n) and it must find a terminator or run off the end.
  · The terminator costs one byte that is easy to forget.
  · A string cannot contain a zero byte. Binary data needs a
    pointer + length, never a "string".
  · Nothing knows the CAPACITY of the buffer but you.
char a[6] = "hello";     /* exactly fits: 5 + terminator          */
char b[5] = "hello";     /* LEGAL C: no terminator. Not a string.  */
char c[]  = "hello";     /* size 6, deduced — prefer this          */
char d[10] = "hi";       /* remaining bytes zero-filled            */

sizeof("hello")          /* 6 — a compile-time array size         */
strlen("hello")          /* 5 — a runtime walk                    */

/* strlen on b runs past the end of the array: undefined behaviour,
   and in practice it returns whatever happens to follow in memory. */

   "safe strcpy" and using it as one creates bugs.                */

/* If you must use it, terminate explicitly: */
strncpy(dst, src, sizeof dst - 1);
dst[sizeof dst - 1] = '\0';

What to use instead

The classic string functions cannot be used safely in general, because they have no idea how large the destination is. These are the replacements, and the differences between them matter more than their similar names suggest.

snprintf — the portable workhorse

char buf[64];
int n = snprintf(buf, sizeof buf, "%s: %d", name, value);

/* snprintf ALWAYS terminates (when size > 0), and returns the length
   it WOULD have written. That return value is how you detect
   truncation — and it is why the return is not the bytes written.  */

if (n < 0)
        return -EIO;                    /* encoding error          */
if ((size_t)n >= sizeof buf)
        return -ENAMETOOLONG;           /* truncated               */

/* The classic bug: using the return value as a length blindly */
char buf[16];
int n = snprintf(buf, sizeof buf, "%s", long_string);
memcpy(other, buf, n);          /* n may EXCEED sizeof buf — overflow */

/* correct */
size_t len = (n < 0) ? 0 : ((size_t)n < sizeof buf ? (size_t)n : sizeof buf - 1);

strlcpy and strlcat — when available

/* From OpenBSD; in glibc since 2.38, and in the Linux kernel.
   They always terminate and return the length they TRIED to create,
   so truncation is detectable with one comparison.               */

size_t r = strlcpy(dst, src, sizeof dst);
if (r >= sizeof dst)
        return -ENAMETOOLONG;           /* truncated */

/* strscpy() is the kernel's preferred variant: it returns the
   number of bytes copied, or -E2BIG on truncation — an error code
   rather than a length you must compare.                        */
ssize_t r = strscpy(dst, src, sizeof dst);
if (r < 0)
        return r;

Parsing numbers correctly

Turning text into numbers is routine and full of traps: functions that cannot report failure, functions that report it ambiguously, and one that is almost always the right answer.

/* atoi has no error reporting whatsoever and is UB on overflow. */
int n = atoi(s);          /* returns 0 for "abc" AND for "0" */

/* strtol, used properly — this is the full, correct pattern */
#include <stdlib.h>
#include <errno.h>
#include <limits.h>

int parse_int(const char *s, int *out)
{
        char *end;
        errno = 0;                       /* MUST clear it first */

        long v = strtol(s, &end, 10);    /* explicit base: 10, never 0
                                            unless you want "0x" and
                                            octal to be accepted      */

        if (end == s)          return -EINVAL;   /* no digits at all  */
        if (*end != '\0')      return -EINVAL;   /* trailing garbage  */
        if (errno == ERANGE)   return -ERANGE;   /* out of long range */
        if (v < INT_MIN || v > INT_MAX) return -ERANGE;  /* out of int */

        *out = (int)v;
        return 0;
}

/* Note the four distinct failure modes. Any parser that does not
   distinguish them will accept input it should reject.           */

/* Kernel equivalents, which get this right for you: */
kstrtoint(s, 10, &val);
kstrtoul(s, 0, &val);

Bytes, characters and encodings

Beyond ASCII, a "character" stops being a byte, and code that assumes otherwise breaks on real-world input. This is what you need to know to handle that correctly without adopting a whole library.

A `char` is a BYTE. It is not a character.

  UTF-8 encodes a code point in 1 to 4 bytes:

    'A'   U+0041   -> 0x41                     1 byte
    'é'   U+00E9   -> 0xC3 0xA9                2 bytes
    '中'  U+4E2D   -> 0xE4 0xB8 0xAD           3 bytes
    '😀'  U+1F600  -> 0xF0 0x9F 0x98 0x80      4 bytes

  So for a UTF-8 string:
     strlen()  gives BYTES, not characters
     s[i]      indexes a byte, possibly mid-character
     toupper() on a byte of a multi-byte sequence is meaningless
     truncating at a byte boundary can produce invalid UTF-8

  What is still safe on UTF-8 without decoding:
     · comparing for equality (memcmp)
     · searching for an ASCII substring (UTF-8 is self-synchronising:
       a multi-byte sequence never contains an ASCII byte)
     · concatenation
     · sorting by byte order == sorting by code point order

  What is NOT safe: length in characters, indexing, case conversion,
  truncation, reversing, normalisation-sensitive comparison.
/* Practical advice for systems code:
     - treat text as opaque UTF-8 bytes and pass it through
     - validate UTF-8 at the boundary if you must interpret it
     - never truncate a UTF-8 string at an arbitrary byte offset
     - do not use wchar_t: it is 16-bit on Windows and 32-bit on
       Linux, which makes it useless for portable code
     - if you need real Unicode handling, use ICU or utf8proc     */

/* truncating UTF-8 safely: back up to a leading byte */
size_t utf8_truncate(const char *s, size_t max)
{
        size_t n = strnlen(s, max);
        while (n > 0 && (s[n] & 0xC0) == 0x80)   /* 10xxxxxx = continuation */
                n--;
        return n;
}

The ctype trap

The character classification functions have a genuine trap in their interface: passing them the wrong kind of value is undefined behaviour, and the natural way to call them does exactly that.

#include <ctype.h>

char c = get_byte();
if (isalpha(c))          /* UNDEFINED if c is negative */

/* The <ctype.h> functions take an int that must be representable as
   `unsigned char` or equal EOF. On platforms where plain char is
   signed (x86 Linux, Windows), byte 0xE9 becomes -23, and the
   implementation indexes a lookup table out of bounds.           */

if (isalpha((unsigned char)c))     /* correct — always cast */

/* Also: these are locale-dependent. In systems code that parses
   protocols, write explicit checks instead:                     */
static inline bool is_digit(char c)  { return c >= '0' && c <= '9'; }
static inline bool is_alpha(char c)  { return (c|32) >= 'a' && (c|32) <= 'z'; }

Handling secrets in buffers

Strings holding passwords or keys need handling ordinary strings do not, because the compiler is entitled to optimise away the cleanup you carefully wrote.

/* This does not work: */
void check_password(const char *input)
{
        char key[32];
        derive_key(key, input);
        use(key);
        memset(key, 0, sizeof key);   /* DEAD STORE — the compiler
                                         removes it, because key is
                                         never read again (chapter 01) */
}

/* Portable-ish fixes, in order of preference: */

memset_s(key, sizeof key, 0, sizeof key);      /* C11 Annex K, optional */
explicit_bzero(key, sizeof key);               /* BSD, glibc 2.25+      */
SecureZeroMemory(key, sizeof key);             /* Windows               */
memzero_explicit(key, sizeof key);             /* Linux kernel          */

/* If you have none of them, force it through a volatile pointer: */
static void *(*const volatile memset_ptr)(void *, int, size_t) = memset;
memset_ptr(key, 0, sizeof key);

/* And compare secrets in CONSTANT TIME — never with memcmp, which
   returns as soon as it finds a difference and thereby leaks how
   many bytes matched. See the cryptography track.               */
static int ct_memcmp(const void *a, const void *b, size_t n)
{
        const unsigned char *x = a, *y = b;
        unsigned char diff = 0;
        for (size_t i = 0; i < n; i++)
                diff |= x[i] ^ y[i];       /* no early exit */
        return diff;                        /* 0 == equal    */
}

Compiler and runtime hardening

Beyond writing careful code, the toolchain can detect a large fraction of string misuse automatically — at compile time, at run time, or both.

# FORTIFY_SOURCE: replaces str/mem functions with checked versions
# when the destination size is known at compile time. Nearly free.
gcc -O2 -D_FORTIFY_SOURCE=3 -Wall -Wextra

# stack canaries
gcc -fstack-protector-strong

# warn about format-string problems, including non-literal formats
gcc -Wformat=2 -Wformat-security

# catch overflows in testing
gcc -fsanitize=address -g

# static analysis
gcc -fanalyzer                 # GCC 10+, finds many string bugs
Format string vulnerabilities 
printf(user_input);              /* CATASTROPHIC */
/* If user_input contains %s the program reads an arbitrary pointer;
   %n WRITES to memory. This is a full compromise, not a crash.   */

printf("%s", user_input);        /* correct — the format is a literal */

/* -Wformat-security flags any call where the format is not a
   literal. Treat it as an error, not a warning.                  */
