USB device classes and writing a device

The single most valuable thing to know about USB is which standard class to claim, because claiming the right one means every operating system already has your driver. Getting this choice right is the difference between shipping a product and shipping a product plus three signed drivers.

The classes worth knowing

ClassDriver on Windows/macOS/LinuxUse for
CDC-ACM (serial)Built in everywhere; Windows needs an INF before 10A virtual COM port — debug consoles, legacy replacement
HIDBuilt in, no driver, no INF, everKeyboards, mice, and any low-rate custom data
MSC (mass storage)Built in everywhereExposing a filesystem — logs, firmware drop-in
Audio (UAC)Built in; UAC1 more compatible than UAC2Speakers, microphones
Video (UVC)Built in everywhereCameras
DFUNeeds WinUSB or a tool like dfu-utilFirmware update
Vendor-specificWinUSB via a WCID descriptor; libusb elsewhereHigh throughput custom protocols
 
   THE DECISION:

   Need a debug console?          -> CDC-ACM
   Custom data, under ~64 kB/s?   -> HID
   Custom data, high rate?        -> vendor-specific + WCID
   Exposing files?                -> MSC
   Firmware update?               -> DFU, or MSC drag-and-drop

   HID IS UNDERRATED FOR CUSTOM DATA. It needs no driver, no
   INF, no signing and no administrator rights on any
   operating system, and browsers can talk to it directly
   through WebHID. The cost is throughput: 64 KB/s at full
   speed, 24 MB/s at high speed but only with careful
   descriptor work.

   For a configuration tool, a dongle, or a sensor that
   reports a few kilobytes a second, HID removes an entire
   category of deployment problem. Reach for it before
   reaching for a vendor-specific interface.

Making a vendor-specific device driverless on Windows

/* Historically a vendor-specific device meant shipping a
   signed .inf and .cat. Microsoft OS descriptors (WCID)
   remove that: the device TELLS Windows to bind WinUSB.  */

/* Windows requests string descriptor 0xEE at enumeration.
   Return this magic string and it will follow up with
   vendor requests.                                       */
static const uint8_t msos_string[] = {
    0x12, 0x03,
    'M',0, 'S',0, 'F',0, 'T',0, '1',0, '0',0, '0',0,
    MSOS_VENDOR_CODE, 0x00
};

/* Then answer the compatible-ID request with "WINUSB". */
static const uint8_t msos_compat_id[] = {
    0x28,0,0,0,        /* dwLength = 40                    */
    0x00,0x01,         /* bcdVersion 1.0                   */
    0x04,0x00,         /* wIndex: compatible ID            */
    0x01,              /* one section                      */
    0,0,0,0,0,0,0,     /* reserved                         */
    0x00,              /* interface 0                      */
    0x01,              /* reserved                         */
    'W','I','N','U','S','B',0,0,   /* compatible ID        */
    0,0,0,0,0,0,0,0,               /* sub-compatible ID    */
    0,0,0,0,0,0                    /* reserved             */
};

/* Result: plug it in and Windows binds WinUSB with no
   driver install and no administrator rights. libusb then
   talks to it identically on Windows, macOS and Linux.

   ADD A DEVICE INTERFACE GUID via the extended properties
   descriptor and your application can find the device by
   GUID rather than enumerating everything.

   THIS IS THE MODERN ANSWER for custom USB devices, and
   it is much less widely known than it should be. TinyUSB
   and most stacks support it with a few lines of
   configuration.                                         */

A custom HID device

/* The HID report descriptor is a small stack-based language
   describing your data's structure. It is the fiddliest
   part of HID and the reason people avoid it - but a
   generic in/out report is a fixed template you can copy. */

static const uint8_t hid_report_desc[] = {
    0x06, 0x00, 0xFF,   /* Usage Page (vendor-defined)      */
    0x09, 0x01,         /* Usage (1)                        */
    0xA1, 0x01,         /* Collection (Application)         */

    0x09, 0x02,         /*   Usage (2) - input report       */
    0x15, 0x00,         /*   Logical Minimum (0)            */
    0x26, 0xFF, 0x00,   /*   Logical Maximum (255)          */
    0x75, 0x08,         /*   Report Size (8 bits)           */
    0x95, 0x40,         /*   Report Count (64 bytes)        */
    0x81, 0x02,         /*   Input (Data,Var,Abs)           */

    0x09, 0x03,         /*   Usage (3) - output report      */
    0x15, 0x00,
    0x26, 0xFF, 0x00,
    0x75, 0x08,
    0x95, 0x40,
    0x91, 0x02,         /*   Output (Data,Var,Abs)          */

    0xC0                /* End Collection                   */
};

/* 64 bytes in and 64 bytes out, opaque to the host. Now:  */

void tud_hid_set_report_cb(uint8_t itf, uint8_t id,
                           hid_report_type_t type,
                           uint8_t const *buf, uint16_t len)
{
    handle_command(buf, len);          /* host -> device   */
}

void send_reading(const reading_t *r)
{
    uint8_t rpt[64] = {0};
    memcpy(rpt, r, sizeof(*r));
    tud_hid_report(0, rpt, sizeof(rpt));   /* device -> host */
}

/* USE A DESCRIPTOR TOOL. The HID Descriptor Tool from
   USB-IF, or hidrd, will validate what you write. A subtly
   wrong report descriptor produces a device that enumerates
   successfully and then delivers reports the host silently
   discards - which is a miserable thing to debug by
   inspection.                                             */
Windows caches descriptors against VID/PID

During development, changing your descriptors and re-plugging often changes nothing, because Windows remembers the device from the first time it saw that VID/PID and does not re-read. Increment bcdDevice on every descriptor change, or delete the device from Device Manager with "delete the driver software" ticked, or use a different PID for each iteration. Hours are lost to this every year, and the symptom — "my change had no effect" — points at your code rather than the host.

Debugging USB

   IN ORDER OF WHAT YOU SHOULD REACH FOR:

   1. lsusb -v (Linux) / USB Tree View (Windows)
      Shows the descriptors as the host parsed them. If
      your device appears with the right VID/PID and the
      endpoints you expect, enumeration succeeded and the
      problem is above that layer.

   2. WIRESHARK WITH usbmon (Linux) or USBPcap (Windows)
      Every packet, free, no hardware. This shows you which
      control transfer failed, and it is the tool that
      answers "why does it not enumerate".

   3. dmesg (Linux)
      The kernel narrates enumeration failures in plain
      language: "device descriptor read/64, error -71".
      Often names the problem outright.

   4. A HARDWARE PROTOCOL ANALYSER
      Beagle, Ellisys and similar. Needed only for
      electrical or timing problems - a device that
      enumerates on one host and not another, or one that
      fails at high speed. Expensive, and rarely the first
      resort.

   5. GPIO + SCOPE inside your callbacks
      When the stack's behaviour itself is in question,
      toggling a pin in the endpoint callback tells you
      whether it is being called at all, and how often
      (mcu chapter 16).

   THE ORDER MATTERS. People reach for the analyser first
   and Wireshark last, when Wireshark answers the question
   nine times out of ten and costs nothing.
