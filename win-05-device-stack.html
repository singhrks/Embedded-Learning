The device stack and Plug and Play

Windows layers several drivers over one piece of hardware, and the PnP manager orchestrates their lifecycle. Understanding the stack explains filter drivers, why devices appear with a yellow bang, and what WDF is doing for you when it "just works".

One device, several drivers

A single piece of hardware is almost never served by a single driver. Several cooperate in a stack, each responsible for one layer of the problem, and knowing which role yours plays determines nearly everything else about it.

   For a single physical device:

   +------------------------------------+
   |  UPPER FILTER   (optional, several)|  encryption, tracing,
   |     e.g. a monitoring filter       |  policy
   +------------------------------------+
   |  FUNCTION DRIVER (FDO)             |  <-- YOURS. Knows
   |     the driver that knows the      |      how the hardware
   |     hardware                       |      works.
   +------------------------------------+
   |  LOWER FILTER   (optional, several)|
   +------------------------------------+
   |  BUS DRIVER (PDO)                  |  pci.sys, acpi.sys,
   |     enumerated this device,        |  usbhub.sys
   |     owns its resources             |
   +------------------------------------+

   NAMES YOU MUST KNOW:

     PDO   Physical Device Object. Created by the BUS driver
           to say "a device exists here". One per child.
     FDO   Functional Device Object. Created by YOUR driver
           and attached above the PDO.
     FiDO  Filter Device Object.

   An IRP enters at the TOP and travels down (chapter 05).
   Each layer may handle it, modify it, or pass it on.

   WHY THIS EXISTS: it makes filtering universal. A disk
   encryption filter, a keyboard logger, a USB analyser and a
   power policy owner all attach the same way, to any device,
   without the function driver knowing. Linux has no direct
   equivalent - filtering there is per-subsystem or done with
   stacked block devices.

   SEE A REAL ONE:
        WinDbg:  !devstack ffff8a0c12345678
        Device Manager -> device -> Details -> "Upper filters"

The PnP state machine

Plug and Play is a state machine, and your driver is expected to respond correctly at each transition. It is more elaborate than Linux's probe-and-remove pair because it must also handle a device being removed without warning while in use.

   BUS DRIVER enumerates hardware
        |  reports a new child in
        |  IRP_MN_QUERY_DEVICE_RELATIONS (BusRelations)
        v
   PnP MANAGER creates a PDO, reads its HARDWARE IDs
        |     PCI\VEN_1234&DEV_5678&SUBSYS_...&REV_01
        |     ACPI\VEN0001
        v
   matches against installed INFs (chapter 20)
        |
        v
   loads the driver, calls DriverEntry (once per driver)
        |
        v
   calls EvtDriverDeviceAdd / AddDevice (once PER DEVICE)
        |     you create the FDO and attach it to the stack
        v
   IRP_MN_QUERY_RESOURCE_REQUIREMENTS
        |     "what does this device need?"
        v
   PnP manager ASSIGNS resources (memory ranges, interrupts,
   DMA channels) - arbitrating between all devices
        |
        v
   IRP_MN_START_DEVICE                <-- the big one
        |     WDF: EvtDevicePrepareHardware  (map registers)
        |          EvtDeviceD0Entry          (power it up)
        |          interrupts connected
        v
   ===== DEVICE IS RUNNING; I/O flows =====
        |
        v
   IRP_MN_QUERY_REMOVE_DEVICE     "may I remove it?"
        |     you may VETO this if you are busy
        v
   IRP_MN_REMOVE_DEVICE
        |     WDF: EvtDeviceD0Exit
        |          EvtDeviceReleaseHardware
        |          EvtDeviceSelfManagedIoCleanup
        v
   device object deleted

   OTHER TRANSITIONS you must handle:
     IRP_MN_CANCEL_REMOVE_DEVICE   the remove was vetoed
     IRP_MN_QUERY_STOP / STOP      resource rebalance
     IRP_MN_SURPRISE_REMOVAL       the user yanked it out
     IRP_MN_QUERY_CAPABILITIES
     IRP_MN_QUERY_ID / QUERY_DEVICE_TEXT
Surprise removal is not an edge case

For anything on USB, PCIe hot-plug, or a removable bus, SURPRISE_REMOVAL is the normal path — the hardware is already gone when you are told. Every register read now returns 0xFFFFFFFF, every pending request must be completed with an error, and any code that waits for the hardware to respond will hang forever. Write the driver so that "the device vanished mid-operation" is a handled case from the first day, not something retrofitted after a bug report.

Doing it in raw WDM

Here is what the above costs in raw WDM. It is worth reading once, not because you should write it, but because it shows exactly how much work the framework in the next chapters is doing for you.

/* Shown so you can read legacy drivers and understand what
   WDF replaces. Do not write new code this way.           */

NTSTATUS
MyAddDevice(_In_ PDRIVER_OBJECT DriverObject,
            _In_ PDEVICE_OBJECT PhysicalDeviceObject)
{
        PDEVICE_OBJECT fdo;
        PMY_EXT ext;
        NTSTATUS status;

        status = IoCreateDevice(DriverObject, sizeof(MY_EXT),
                                NULL,      /* unnamed - PnP
                                              devices use
                                              interfaces     */
                                FILE_DEVICE_UNKNOWN,
                                FILE_DEVICE_SECURE_OPEN,
                                FALSE, &fdo);
        if (!NT_SUCCESS(status))
                return status;

        ext = fdo->DeviceExtension;
        RtlZeroMemory(ext, sizeof(*ext));
        ext->Self = fdo;
        ext->Pdo  = PhysicalDeviceObject;

        /* ATTACH to the stack - this returns the device
           DIRECTLY BELOW us, which may be a lower filter, not
           the PDO.                                          */
        ext->LowerDevice = IoAttachDeviceToDeviceStack(
                                fdo, PhysicalDeviceObject);
        if (!ext->LowerDevice) {
                IoDeleteDevice(fdo);
                return STATUS_DEVICE_REMOVED;
        }

        /* inherit the buffering method and power flags from
           below - getting this wrong breaks I/O in ways that
           are hard to trace (chapter 08)                    */
        fdo->Flags |= ext->LowerDevice->Flags &
                      (DO_BUFFERED_IO | DO_DIRECT_IO |
                       DO_POWER_PAGABLE);

        fdo->Flags &= ~DO_DEVICE_INITIALIZING;   /* LAST */

        return STATUS_SUCCESS;
}

/* AND THE PNP DISPATCH, which is where the real work is: */
NTSTATUS
MyPnp(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp)
{
        PMY_EXT ext = DeviceObject->DeviceExtension;
        PIO_STACK_LOCATION sp = IoGetCurrentIrpStackLocation(Irp);

        switch (sp->MinorFunction) {
        case IRP_MN_START_DEVICE:
                /* MUST send it down FIRST and WAIT: the lower
                   drivers must start before we touch the
                   hardware. This synchronous-forward pattern
                   is 40 lines of event and completion routine
                   in real code.                            */
                status = MyForwardAndWait(ext, Irp);
                if (NT_SUCCESS(status))
                        status = MyStartDevice(ext,
                                sp->Parameters.StartDevice.
                                   AllocatedResourcesTranslated);
                Irp->IoStatus.Status = status;
                IoCompleteRequest(Irp, IO_NO_INCREMENT);
                return status;

        case IRP_MN_REMOVE_DEVICE:
                MyStopDevice(ext);
                IoSkipCurrentIrpStackLocation(Irp);
                status = IoCallDriver(ext->LowerDevice, Irp);
                IoDetachDevice(ext->LowerDevice);
                IoDeleteDevice(DeviceObject);
                return status;
                /* NOTE: for REMOVE you forward it down and do
                   NOT complete it, then delete yourself. For
                   START you complete it. The rules differ per
                   minor function, and there are a dozen.   */

        default:
                IoSkipCurrentIrpStackLocation(Irp);
                return IoCallDriver(ext->LowerDevice, Irp);
        }
}

/* THERE ARE ROUGHLY 25 PNP MINOR FUNCTIONS, each with its own
   forwarding and completion rules, plus a state machine with
   about 15 states that you must implement correctly to pass
   certification. WDF implements all of it (chapter 15).

   THAT is why KMDF exists, and why a KMDF driver is typically
   a third the size of the WDM equivalent.               */

The same thing in KMDF

The same device, the same state machine, in KMDF. Compare the two directly — the framework handles the sequencing and leaves you with only the callbacks that are genuinely specific to your hardware.

NTSTATUS
MyEvtDeviceAdd(_In_ WDFDRIVER Driver,
               _Inout_ PWDFDEVICE_INIT DeviceInit)
{
        WDF_PNPPOWER_EVENT_CALLBACKS pnpPower;
        WDF_OBJECT_ATTRIBUTES attributes;
        WDFDEVICE device;
        PMY_CONTEXT ctx;
        NTSTATUS status;

        UNREFERENCED_PARAMETER(Driver);
        PAGED_CODE();

        WDF_PNPPOWER_EVENT_CALLBACKS_INIT(&pnpPower);
        pnpPower.EvtDevicePrepareHardware = MyPrepareHardware;
        pnpPower.EvtDeviceReleaseHardware = MyReleaseHardware;
        pnpPower.EvtDeviceD0Entry         = MyD0Entry;
        pnpPower.EvtDeviceD0Exit          = MyD0Exit;
        WdfDeviceInitSetPnpPowerEventCallbacks(DeviceInit,
                                               &pnpPower);

        WDF_OBJECT_ATTRIBUTES_INIT_CONTEXT_TYPE(&attributes,
                                                MY_CONTEXT);

        status = WdfDeviceCreate(&DeviceInit, &attributes,
                                 &device);
        if (!NT_SUCCESS(status))
                return status;

        ctx = MyGetContext(device);
        ctx->Device = device;

        /* publish a device interface, so user mode can find
           us without a hard-coded name (below)             */
        status = WdfDeviceCreateDeviceInterface(device,
                        &GUID_DEVINTERFACE_MYDEVICE, NULL);
        if (!NT_SUCCESS(status))
                return status;

        return MyQueueInitialize(device);
}

/* THAT IS THE WHOLE PNP IMPLEMENTATION. The framework:
     · creates the FDO and attaches it
     · implements every PnP minor function correctly
     · runs the state machine, including surprise removal,
       query-remove veto, and resource rebalance
     · calls your callbacks at the right time, at the right
       IRQL, in the right order
     · stops and restarts your queues around power transitions

   YOUR JOB reduces to four callbacks (chapter 15).      */

The four callbacks that matter

These four exist because "the device is present" and "the device is powered and usable" are separate events that WDF tracks independently — a laptop can suspend and resume the same device many times without ever revoking its resources, and Plug and Play can surprise-remove a device without ever powering it down cleanly first. PrepareHardware/ReleaseHardware bracket the period during which the device's memory-mapped registers and interrupt are validly assigned to you at all; D0Entry/D0Exit bracket the much more frequent power transitions that happen inside that period. The warning on ReleaseHardware is the one to take seriously: by the time it runs, the hardware may already be physically gone — a USB device unplugged, a PCIe card hot-removed — so any register access there risks touching memory that no longer maps to anything.

CallbackWhenDoIRQL
EvtDevicePrepareHardwareResources assignedMap registers, get the interrupt's resource descriptorPASSIVE
EvtDeviceD0EntryPowering upInitialise the hardware, restore statePASSIVE
EvtDeviceD0ExitPowering downQuiesce, save statePASSIVE
EvtDeviceReleaseHardwareResources revokedUnmap. Do not touch the hardware — it may be gonePASSIVE
 
NTSTATUS
MyPrepareHardware(_In_ WDFDEVICE Device,
                  _In_ WDFCMRESLIST ResourcesRaw,
                  _In_ WDFCMRESLIST ResourcesTranslated)
{
        PMY_CONTEXT ctx = MyGetContext(Device);
        ULONG i;

        PAGED_CODE();
        UNREFERENCED_PARAMETER(ResourcesRaw);

        /* Walk the TRANSLATED list - the raw one holds bus
           addresses, the translated one holds addresses the
           CPU can actually use (chapter 18).              */
        for (i = 0; i < WdfCmResourceListGetCount(ResourcesTranslated);
             i++) {
                PCM_PARTIAL_RESOURCE_DESCRIPTOR desc =
                        WdfCmResourceListGetDescriptor(
                                ResourcesTranslated, i);

                switch (desc->Type) {
                case CmResourceTypeMemory:
                        ctx->RegBase = MmMapIoSpaceEx(
                                desc->u.Memory.Start,
                                desc->u.Memory.Length,
                                PAGE_READWRITE | PAGE_NOCACHE);
                        if (!ctx->RegBase)
                                return STATUS_INSUFFICIENT_RESOURCES;
                        ctx->RegLength = desc->u.Memory.Length;
                        break;

                case CmResourceTypeInterrupt:
                        /* WDF connects it for you if you
                           created a WDFINTERRUPT object
                           (chapter 18) - nothing to do here  */
                        break;
                }
        }

        if (!ctx->RegBase)
                return STATUS_DEVICE_CONFIGURATION_ERROR;

        return STATUS_SUCCESS;
}

NTSTATUS
MyReleaseHardware(_In_ WDFDEVICE Device,
                  _In_ WDFCMRESLIST ResourcesTranslated)
{
        PMY_CONTEXT ctx = MyGetContext(Device);

        PAGED_CODE();
        UNREFERENCED_PARAMETER(ResourcesTranslated);

        /* DO NOT touch the hardware here. On surprise removal
           it is physically gone, and a register write may
           bugcheck or hang the bus. Quiesce in D0Exit, which
           runs while the device is still present.         */

        if (ctx->RegBase) {
                MmUnmapIoSpace(ctx->RegBase, ctx->RegLength);
                ctx->RegBase = NULL;
        }
        return STATUS_SUCCESS;
}

Device interfaces

A device needs a name that applications can find it by. Windows does this with a GUID rather than a fixed path, so that a program can enumerate every device of a given kind without knowing how many exist or what they are called.

/* A PnP device should NOT have a fixed name and symbolic link
   (chapter 04) - there may be several of them, and the name
   would collide. Instead it publishes a device INTERFACE: a
   GUID that says "I provide this kind of service".        */

/* 1. define a GUID, in a header shared with user mode: */
        // {A1B2C3D4-1234-5678-9ABC-DEF012345678}
        DEFINE_GUID(GUID_DEVINTERFACE_MYDEVICE,
                0xa1b2c3d4, 0x1234, 0x5678, 0x9a, 0xbc,
                0xde, 0xf0, 0x12, 0x34, 0x56, 0x78);

/* 2. publish it, in EvtDeviceAdd: */
        WdfDeviceCreateDeviceInterface(device,
                        &GUID_DEVINTERFACE_MYDEVICE,
                        NULL);   /* an optional reference
                                    string, to distinguish
                                    several interfaces on one
                                    device                   */

/* 3. USER MODE FINDS IT by GUID, not by name: */

        HDEVINFO info;
        SP_DEVICE_INTERFACE_DATA ifData = { sizeof(ifData) };
        PSP_DEVICE_INTERFACE_DETAIL_DATA_W detail;
        DWORD needed;
        HANDLE h;

        info = SetupDiGetClassDevsW(&GUID_DEVINTERFACE_MYDEVICE,
                        NULL, NULL,
                        DIGCF_PRESENT | DIGCF_DEVICEINTERFACE);

        SetupDiEnumDeviceInterfaces(info, NULL,
                        &GUID_DEVINTERFACE_MYDEVICE, 0, &ifData);

        SetupDiGetDeviceInterfaceDetailW(info, &ifData, NULL, 0,
                                         &needed, NULL);
        detail = malloc(needed);
        detail->cbSize = sizeof(*detail);
        SetupDiGetDeviceInterfaceDetailW(info, &ifData, detail,
                                         needed, &needed, NULL);

        h = CreateFileW(detail->DevicePath, GENERIC_READ |
                        GENERIC_WRITE, 0, NULL, OPEN_EXISTING,
                        FILE_ATTRIBUTE_NORMAL, NULL);

/* THE PATH looks like:
     \\?\pci#ven_1234&dev_5678#4&1a2b3c4d&0&00e0#{a1b2c3d4-...}

   WHY THIS IS BETTER than a symbolic link:
     · several identical devices coexist, each with its own
       path
     · user mode can enumerate ALL of them
     · arrival and removal can be watched with
       CM_Register_Notification / RegisterDeviceNotification,
       so an application reacts to hot-plug
     · no name collisions between vendors            */

Debugging the stack

When a device does not start, the debugger will tell you how far it got and which driver is where in the stack — which usually identifies the failing step immediately.

# --- Device Manager, first ---
#   View -> Show hidden devices
#   The device's Properties -> Details tab:
#       Hardware Ids           what the INF must match
#       Device Instance Path
#       Upper/Lower filters
#       "Problem code"         <-- the yellow bang's meaning
#
#   COMMON PROBLEM CODES:
#     Code 10  the driver failed IRP_MN_START_DEVICE
#     Code 12  resource conflict - PnP could not assign
#     Code 18  reinstall required
#     Code 28  no driver installed
#     Code 31  the driver failed to load
#     Code 39  driver corrupt or missing
#     Code 43  the driver reported a failure
#     Code 52  signature verification failed (chapter 21)

# --- WinDbg ---
    !devnode 0 1                    the whole PnP tree
    !devnode 0 1 mydriver           just yours
    !devstack ffff8a0c12345678      one device's stack
    !devobj  ffff8a0c12345678
    !drvobj \Driver\MyDriver 7

# --- The setup log, for install-time problems ---
    C:\Windows\INF\setupapi.dev.log
# It records every INF match attempt, every rank, and exactly
# why a driver was or was not selected. This is the file to
# read when a device shows Code 28.

# --- Live PnP tracing ---
    tracelog -start pnp -guid #B3A7...  -f pnp.etl
    # or use Windows Performance Recorder with the
    # "Device I/O" profile
