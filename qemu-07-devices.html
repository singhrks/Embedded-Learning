Devices, buses and the command line

QEMU's command line looks arbitrary until you see the object model underneath it. There are three layers — a backend that does real work, a frontend the guest sees, and a bus they plug into — and every confusing option is one of those three. Learn the shape and the syntax stops needing memorisation.

Backend, frontend, bus

   HOST SIDE                 GUEST SIDE
   "backend"                 "frontend" / device

   a file on disk    <---->  virtio-blk-device      on virtio-mmio
   a tap interface   <---->  virtio-net-pci         on PCIe
   your terminal     <---->  pl011 UART             on the SoC
   a unix socket     <---->  virtio-serial port     on virtio
   /dev/urandom      <---->  virtio-rng-device

   The command line names them SEPARATELY and joins them by id:

     -drive   file=disk.img,if=none,format=raw,id=hd0
              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  backend
                                          ^^^^  its name

     -device  virtio-blk-device,drive=hd0
              ^^^^^^^^^^^^^^^^^                 frontend
                                ^^^^^^^^^       the link

   Once you see that, every option follows:

     -netdev   TYPE,id=NAME,...        network backend
     -device   virtio-net-...,netdev=NAME
     -chardev  TYPE,id=NAME,...        character backend
     -device   ...,chardev=NAME
     -blockdev TYPE,node-name=NAME,... modern block backend
     -object   TYPE,id=NAME,...        memory, rng, crypto,
                                       tls credentials

   "if=none" means "do not auto-attach this backend to a
   default controller - I will attach it myself with -device".
   Forgetting it is the most common mistake, and the symptom is
   a disk that appears twice or not at all.

Which frontend for which bus

SuffixBusExampleNotes
-devicevirtio-mmiovirtio-blk-deviceThe 32 mmio slots on virt. Simple, no PCIe needed. Best for minimal guests
-pciPCIevirtio-blk-pciEnumerable, hotpluggable, supports MSI-X and multiqueue properly. Best for full guests
-ccws390 channelvirtio-blk-ccws390x only
 
# The same disk, three ways:

# 1. virtio-mmio - no PCIe involved
-drive file=d.img,if=none,format=raw,id=hd0 \
-device virtio-blk-device,drive=hd0

# 2. virtio-pci - needs the PCIe host bridge (virt has one)
-drive file=d.img,if=none,format=raw,id=hd0 \
-device virtio-blk-pci,drive=hd0

# 3. The shorthand, which auto-picks a controller.
#    Convenient, and it hides which bus you got.
-drive file=d.img,format=raw,if=virtio

# Prefer the explicit forms. When something does not appear in
# the guest, the explicit form tells you where to look.

# See what you actually built:
$ qemu-system-aarch64 -M virt ... -monitor stdio
(qemu) info qtree
(qemu) info pci
(qemu) info block

Character devices: where output goes

# Every serial port, console, monitor and debug channel is a
# chardev. This is the layer people fight with most.

# The simple forms:
-nographic                 # serial + monitor multiplexed to
                           # stdio. Ctrl-A c switches, Ctrl-A x
                           # quits.
-serial mon:stdio          # exactly what -nographic does
-serial null               # discard
-serial file:boot.log      # write to a file
-serial tcp::4444,server,nowait     # telnet to it
-serial unix:/tmp/sock,server,nowait
-serial pty                # QEMU prints "char device redirected
                           # to /dev/pts/5" - screen or minicom
                           # to it

# Named chardevs, so several devices can each have their own:
-chardev stdio,id=con0,mux=on \
-chardev file,id=log1,path=secure.log \
-chardev socket,id=dbg,path=/tmp/dbg.sock,server=on,wait=off \
-serial chardev:con0 \
-serial chardev:log1

# TWO UARTs, which the OP-TEE track needs (normal world on one,
# secure world on the other):
-serial mon:stdio -serial file:secure-world.log

# The order matters: the first -serial is ttyAMA0, the second
# is ttyAMA1, and so on. On virt only the first is in the
# generated device tree unless the machine adds more.

# Logging everything to a file while still watching it:
$ qemu-system-aarch64 ... -nographic 2>&1 | tee boot.log

# A virtio-serial channel, for a guest agent:
-device virtio-serial-device \
-chardev socket,path=/tmp/agent.sock,server=on,wait=off,id=ag \
-device virtserialport,chardev=ag,name=org.example.agent
# guest sees /dev/virtio-ports/org.example.agent
Ctrl-A is the escape key

Ctrl-A c toggles between the guest console and the QEMU monitor. Ctrl-A x quits. Ctrl-A h lists the rest. If your terminal multiplexer already uses Ctrl-A (screen does), change QEMU's with -echr 0x05 to use Ctrl-E instead.

A tour of devices worth knowing

# Storage
-device virtio-blk-device,drive=hd0            # the fast path
-device virtio-scsi-device -device scsi-hd,drive=hd0
-device nvme,drive=hd0,serial=deadbeef         # a real NVMe
                                               # controller model -
                                               # excellent for
                                               # driver work
-device usb-storage,drive=hd0

# Network
-device virtio-net-device,netdev=n0
-device e1000e,netdev=n0                       # Intel NIC model
-device rtl8139,netdev=n0                      # ancient, useful
                                               # for driver
                                               # teaching

# Console and input
-device virtio-serial-device
-device virtio-keyboard-device
-device virtio-tablet-device
-device usb-kbd -device usb-mouse

# Graphics
-device virtio-gpu-device
-device ramfb                                  # a dumb
                                               # framebuffer -
                                               # simplest possible
-device virtio-gpu-gl-device                   # with virgl

# Entropy - add this to every guest
-object rng-random,filename=/dev/urandom,id=rng0 \
-device virtio-rng-device,rng=rng0

# USB
-device qemu-xhci,id=xhci \
-device usb-host,hostbus=1,hostaddr=5          # pass a real
                                               # USB device
                                               # through!

# The one that matters most for this site:
-device loader,file=payload.bin,addr=0x40100000,force-raw=on
-device loader,addr=0x40100000,cpu-num=0       # set the PC
# Loads arbitrary blobs anywhere. This is how TF-A, OP-TEE and
# bare-metal payloads get placed.

# Ask what a device accepts:
$ qemu-system-aarch64 -device virtio-blk-device,help
$ qemu-system-aarch64 -device help | less

Hotplug

# PCIe devices can be added and removed while the guest runs.
# virtio-mmio devices cannot - the slots are fixed at startup.
# That alone is a reason to prefer -pci for a long-lived guest.

$ qemu-system-aarch64 -M virt -nographic -monitor stdio ...

(qemu) drive_add 0 if=none,file=extra.img,format=raw,id=hd1
(qemu) device_add virtio-blk-pci,drive=hd1,id=blk1
# guest: a new /dev/vdb appears

(qemu) device_del blk1
# guest: the device is unplugged (the guest must cooperate)

(qemu) info block
(qemu) info pci

# The same through QMP, which is what you would automate
# (chapter 10):
{"execute":"device_add",
 "arguments":{"driver":"virtio-blk-pci","drive":"hd1","id":"blk1"}}

# CPU hotplug on arm64 needs the machine to reserve slots:
$ qemu-system-aarch64 -M virt -smp 2,maxcpus=8 ...
(qemu) device_add cortex-a57-arm-cpu,id=cpu2,core-id=2

# Memory hotplug:
$ qemu-system-aarch64 -m 1G,slots=4,maxmem=8G ...
(qemu) object_add memory-backend-ram,id=m1,size=1G
(qemu) device_add pc-dimm,id=d1,memdev=m1

Making command lines survivable

# A real command line is 20 lines long. Do not retype it.

# 1. A shell script with a variable per concern:
#!/bin/sh
MACHINE="-M virt,gic-version=3,virtualization=on -cpu max -smp 4 -m 2G"
KERNEL="-kernel Image -append 'console=ttyAMA0 earlycon root=/dev/vda'"
DISK="-drive file=rootfs.ext4,if=none,format=raw,id=hd0
      -device virtio-blk-device,drive=hd0"
NET="-netdev user,id=n0,hostfwd=tcp::2222-:22
     -device virtio-net-device,netdev=n0"
DEBUG="-s -S -d guest_errors,unimp -D qemu.log"
exec qemu-system-aarch64 $MACHINE $KERNEL $DISK $NET -nographic "$@"

# 2. -readconfig, a config file QEMU parses itself:
$ cat vm.cfg
[machine]
  type = "virt"
  gic-version = "3"
[memory]
  size = "2G"
[drive "hd0"]
  file = "rootfs.ext4"
  format = "raw"
  if = "none"
[device "blk0"]
  driver = "virtio-blk-device"
  drive = "hd0"

$ qemu-system-aarch64 -readconfig vm.cfg -kernel Image -nographic

# 3. Dump the configuration QEMU derived, to see defaults:
$ qemu-system-aarch64 -M virt -writeconfig - -m 1G 2>/dev/null

# 4. -nodefaults, when you want NOTHING you did not ask for:
$ qemu-system-aarch64 -M virt -nodefaults \
    -serial mon:stdio -device virtio-blk-device,drive=hd0 ...
# Without it QEMU adds a default VGA, a default NIC, a default
# serial and a default parallel port. -nodefaults plus explicit
# devices is how you get a reproducible machine.
Defaults change between QEMU versions

A machine type is versioned (virt-8.2) precisely so that migration and reproducibility work, but -M virt means "the newest", which moves. For anything you want to reproduce in six months — CI, a bug report, a test baseline — pin the versioned machine type and use -nodefaults.

How it shows up

SymptomCause
Property 'drive' not foundFrontend name wrong for the bus — virtio-blk-device vs virtio-blk-pci
Disk appears twice in the guestMissing if=none, so QEMU auto-attached it as well as your -device
Drive 'hd0' is already in useSame, or two -device lines referencing one drive
Device configured but absent in the guestWrong bus for the machine, or the guest kernel lacks the driver. Check info qtree then guest dmesg
No console outputchardev routed elsewhere; check the -serial ordering and console=
Cannot escape QEMUTerminal multiplexer eating Ctrl-A; use -echr
Hotplug fails on virtDevice is on virtio-mmio, which is not hotpluggable — use -pci
Guest gets a NIC you did not ask forDefault devices; add -nodefaults
Command line works on one machine, not anotherDifferent QEMU version, different defaults
-device help lists a device that then failsPresent in the binary but not valid on this machine type
