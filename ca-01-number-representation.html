Binary, hex and number representation

A computer stores no numbers. It stores voltages, which we agree to read as bits, which we agree to group and interpret. Every bug in this chapter's territory comes from two pieces of code disagreeing about that interpretation.

The problem

A transistor is reliably good at one thing: being clearly on or clearly off. It is bad at holding "3.7 volts, meaning the digit 7". Noise, temperature and manufacturing variation smear analogue values; they barely touch a signal that only has to be distinguishably high or low.

So the machine gets two symbols. Everything else — integers, text, colours, machine instructions, your source code — is a convention layered on top of groups of those two symbols.

The central idea of this whole track

A pattern of bits has no inherent meaning. 0100 0001 is 65, or the letter A, or a fragment of an ARM instruction, or a pixel's red channel. What it means is decided entirely by the code that reads it. "Type" in a programming language is nothing more than a compiler-enforced agreement about which interpretation applies.

Positional notation, generalised

Decimal is positional: each digit is worth its face value times a power of ten. Binary is the same system with base two, and hex with base sixteen.

Decimal 205
    2 × 10²  +  0 × 10¹  +  5 × 10⁰   =  200 + 0 + 5      = 205

Binary 1100 1101
    1×2⁷ 1×2⁶ 0×2⁵ 0×2⁴ 1×2³ 1×2² 0×2¹ 1×2⁰
    128 + 64 +  0 +  0 +  8 +  4 +  0 +  1              = 205

Hex 0xCD
    C × 16¹  +  D × 16⁰   =  12×16 + 13                 = 205

Same value. Three notations. The machine only ever has the middle one.

Why hexadecimal exists

Hex is not a third number system the machine understands — it is a shorthand for humans, chosen because 16 = 2⁴. One hex digit is exactly four bits, always, with no carrying between them. That makes the conversion mechanical rather than arithmetic:

  1100 1101 0011 1010
  ─┬── ─┬── ─┬── ─┬──
   C    D    3    A     →  0xCD3A

Read four bits, write one hex digit. Never any arithmetic. This is why
every datasheet, debugger and hex dump uses hex and not decimal: you can
see the bits through it.

"Word" is not a fixed size

In ARM documentation a word is 32 bits, always. In x86 documentation a word is 16 bits (for historical reasons) and 32 bits is a "dword". In C, int is whatever the platform chose. Never rely on the word "word" across ecosystems — say the bit count.

KiB vs KB

KiB, MiB, GiB are powers of two (1024, 1048576, …). KB, MB, GB are strictly powers of ten (1000, 1000000, …). Memory is sold and addressed in powers of two; storage and network rates are usually quoted in powers of ten. This is why a "1 TB" disk shows as 931 GiB — nothing is missing, the units differ by 10%.

In practice: reading an address

Here is the skill this chapter is actually for. Given a peripheral base of 0x4001_0000 and a register at offset 0x0C:

  0x4001_0000     base of the GPIO block
+ 0x0000_000C     offset of the DATA register
─────────────
  0x4001_000C     the address you load from

Now read a value out of it:  0x0000_00A5

  0x A       5
    1010   0101
    ││││   ││││
    ││││   │││└─ bit 0 = 1
    ││││   ││└── bit 1 = 0
    ││││   │└─── bit 2 = 1
    ││││   └──── bit 3 = 0
    │││└──────── bit 4 = 1
    ││└───────── bit 5 = 0
    │└────────── bit 6 = 1
    └─────────── bit 7 = 0

  "Pins 0, 2, 5 and 7 are high."   ← the whole point

Notice how much harder that would be if the register had been printed as decimal 165. Hex is chosen precisely so bit positions are visible.

Writing literals in C

uint32_t a = 205;          /* decimal                                   */
uint32_t b = 0xCD;         /* hex — the default for anything hardware    */
uint32_t c = 0b11001101;   /* binary — C23; a GCC/Clang extension before */
uint32_t d = 0315;         /* OCTAL — a leading zero, almost never wanted */

/* digit separators, C23 and C++14, make long constants readable */
uint32_t page  = 0x0000'1000;
uint32_t mmio  = 0x4001'0080;
The leading-zero trap

int mode = 0755; is octal (493 decimal) — which is what you want for a Unix file mode and almost never what you want anywhere else. uint8_t id = 011; is 9, not 11. A leading zero silently changes the base. This has caused real outages in configuration parsing and in IP address handling.

The same bits, different meanings

To make the opening claim concrete, take the 32-bit pattern 0x41424344 and ask four different questions of it:

Nothing in the bits distinguishes these. The distinction lives entirely in the instruction you use to read them and the type your compiler believes they have.

Byte order, briefly

A 32-bit value occupies four consecutive byte addresses. Which byte goes at the lowest address is the machine's endianness.

Storing 0x12345678 at address 0x1000

  Little-endian (ARM in practice, x86 always)
    0x1000: 78   ← least significant byte first
    0x1001: 56
    0x1002: 34
    0x1003: 12

  Big-endian ("network byte order", some legacy and some MIPS/PowerPC)
    0x1000: 12   ← most significant byte first
    0x1001: 34
    0x1002: 56
    0x1003: 78

It matters the moment bytes cross a boundary: a network packet, a file format, a message to a different processor on the same chip. Within one program on one machine you never notice it. This is covered in depth in chapter 08 and again in the C track.
