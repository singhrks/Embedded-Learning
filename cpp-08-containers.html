The standard library: containers

What each container costs in memory, allocation and cache behaviour — and which of them belong in embedded code. The right answer is usually std::array, and knowing why the others are wrong is more useful than knowing their interfaces.

The pattern

Everything that stores its data inline is free and belongs in embedded code. Everything that owns heap memory is a decision. That single distinction covers the whole table, and it is why std::array, span, optional and variant are the four standard-library types worth adopting even in tightly constrained firmware.

std::array

A fixed-size array with a real type: it knows its own size, does not decay to a pointer, and costs exactly what a C array costs. For embedded work it is the container to reach for first.

#include <array>

        std::array<uint8_t, 64> buf{};          /* zeroed */
        std::array<int, 3> a{1, 2, 3};

        buf.size();             /* a compile-time constant */
        buf.data();             /* uint8_t* */
        buf[0];                 /* unchecked - same as C */
        buf.at(0);              /* THROWS if out of range -
                                   unusable with
                                   -fno-exceptions          */
        buf.front(); buf.back();
        for (auto& b : buf) { }
        std::fill(buf.begin(), buf.end(), 0);

/* IDENTICAL LAYOUT AND CODE to `uint8_t buf[64]`, plus:
     · it knows its size, so no separate length parameter
     · it does not decay to a pointer when passed
     · it can be returned by value, copied and compared
     · begin()/end() work with the algorithms

/* THE PASSING RULE: */
        void f(std::array<uint8_t, 64>& a);    /* one size
                                                  only     */
        void g(std::span<uint8_t> s);          /* ANY size -
                                                  prefer this */

/* CLASS TEMPLATE ARGUMENT DEDUCTION (C++17): */
        std::array a{1, 2, 3};          /* std::array<int,3> */

/* AND THE 2-D CASE: */
        std::array<std::array<float, 4>, 4> matrix{};
        matrix[1][2] = 3.0f;
/* Contiguous, no indirection - unlike float**.           */

std::span and string_view

A non-owning view over contiguous memory, carrying a pointer and a length together. It is the type that finally fixes C's "pointer and separate size parameter" convention.

#include <span>          /* C++20 */

/* A NON-OWNING view of contiguous memory: a pointer and a
   size. Replaces every (T *ptr, size_t len) pair.        */

        void process(std::span<const uint8_t> data)
        {
                for (auto b : data) { ... }
                if (data.size() < 4) return;
                auto header = data.first(4);
                auto body   = data.subspan(4);
        }

        std::array<uint8_t, 64> a;
        std::vector<uint8_t>    v;
        uint8_t                 c[32];

        process(a);             /* all three convert */
        process(v);             /* implicitly */
        process({c, 32});

/* WHY THIS MATTERS: it removes the commonest C bug shape -
   a pointer and a length passed separately, and one of them
   updated without the other.

/* FIXED-EXTENT SPANS carry the size in the type: */
        void f(std::span<uint8_t, 16> exactly16);
/* size() is then a compile-time constant, and passing the
   wrong size is a compile error.

/* string_view is the same idea for text: */
        void log(std::string_view msg);
        log("literal");                 /* no allocation, no
                                           strlen at run time -
                                           the size is known
                                           from the literal  */
        log(std::string{...});          /* also works */

/* THE LIFETIME HAZARD, and it is real: */
        std::string_view bad()
        {
                std::string s = build();
                return s;               /* DANGLING - s is
                                           destroyed         */
        }
        std::string_view sv = get_string();  /* if that returns
                                                by value,
                                                DANGLING     */
/* A view does not own. -Wdangling-gsl catches some cases;
   ASan catches the rest. Treat span and string_view as
   PARAMETERS, not as members or return values, unless you
   can see the owner's lifetime.                          */

std::vector, when you must

The default container in application C++ and the one most often banned in embedded code, because it allocates — and allocates again, unpredictably, as it grows.

        std::vector<int> v;
        v.reserve(100);         /* ONE allocation, up front */
        for (int i = 0; i < 100; i++)
                v.push_back(i); /* no reallocation */

/* GROWTH: capacity doubles (or ×1.5), which means:
     · amortised O(1) push_back
     · reallocation COPIES OR MOVES every element
     · ALL ITERATORS AND POINTERS ARE INVALIDATED
     · unpredictable timing - the reallocation is a latency
       spike exactly where you cannot afford one

        v.size()        elements
        v.capacity()    allocated space
        v.shrink_to_fit()   a non-binding REQUEST
        v.clear()       size 0, capacity UNCHANGED

/* THE ITERATOR INVALIDATION TRAP: */
        for (auto it = v.begin(); it != v.end(); ++it)
                if (*it == x)
                        v.erase(it);    /* it is now INVALID */
        /* correct: */
                it = v.erase(it);       /* erase returns the
                                           next valid one    */
        /* or, better: */
        std::erase(v, x);               /* C++20 */

/* WITH A CUSTOM ALLOCATOR, vector can use a fixed pool: */
        std::pmr::monotonic_buffer_resource pool{buffer,
                                                 sizeof buffer};
        std::pmr::vector<int> v{&pool};
/* Bounded, deterministic, no global heap. Worth knowing, and
   in practice a fixed-capacity container is simpler.

/* THE EMBEDDED ALTERNATIVE - a fixed-capacity vector: */
        etl::vector<Message, 32> queue;   /* ETL */
        /* or roll your own: */
template<typename T, size_t N>
class StaticVector {
        alignas(T) std::byte storage_[N * sizeof(T)];
        size_t size_ = 0;
public:
        bool push_back(const T& v)
        {
                if (size_ >= N) return false;   /* FAILS
                                                   rather than
                                                   allocating */
                new (&data()[size_]) T(v);
                size_++;
                return true;
        }
        T *data() { return reinterpret_cast<T *>(storage_); }
        size_t size() const { return size_; }
        ...
};
/* The interface of vector, the memory behaviour of an array,
   and a bounded failure mode instead of an allocation.  */

Maps, and what to use instead

The associative containers differ in their underlying structure, which decides their performance characteristics and whether they allocate per element. Those differences matter far more in systems code than the interface similarity suggests.

/* std::map is a red-black tree: one heap node per element,
   pointers everywhere, and a cache miss per level of the
   tree. std::unordered_map is buckets of nodes - the same
   problem plus a hash.

/* FOR A SMALL, FIXED SET, a sorted array beats both,
   dramatically: */

struct Entry { uint32_t key; Handler fn; };

inline constexpr std::array<Entry, 5> table{{
        {0x100, handle_status},
        {0x200, handle_config},
        {0x300, handle_data},
        {0x400, handle_reset},
        {0x500, handle_debug},
}};
static_assert(std::is_sorted(table.begin(), table.end(),
                [](auto& a, auto& b){ return a.key < b.key; }),
              "table must be sorted");

const Entry *lookup(uint32_t key)
{
        auto it = std::lower_bound(table.begin(), table.end(),
                        key,
                        [](const Entry& e, uint32_t k)
                                { return e.key < k; });
        return (it != table.end() && it->key == key)
                ? &*it : nullptr;
}

/* IN FLASH, no allocation, one cache line for the whole
   table, and the static_assert guarantees the sort order the
   binary search depends on.

/* FOR UP TO ABOUT 16 ENTRIES, a LINEAR SCAN is usually
   FASTER than a binary search - fewer branches, perfectly
   predictable, one cache line. Measure rather than assuming
   the asymptotically better algorithm wins at small N; on
   embedded it very often does not (CA chapter 14).

/* A FIXED HASH TABLE, when you need O(1) and have the space:
*/
template<typename K, typename V, size_t N>
class FlatMap {
        std::array<K, N> keys_{};
        std::array<V, N> vals_{};
        std::array<bool, N> used_{};
        /* open addressing, linear probing - no nodes, no
           allocation, contiguous                          */
};

/* AND FOR COMPILE-TIME LOOKUP, a perfect hash or simply a
   switch on a constexpr string hash (chapter 07) beats every
   container.                                              */

optional and variant

Types that represent "a value or nothing" and "a value or an error" remove a great deal of sentinel-value and out-parameter awkwardness, without any allocation.

#include <optional>

/* "a T, or nothing" - without a sentinel value or an
   out-parameter.                                           */

        std::optional<uint32_t> read_sensor()
        {
                if (!ready()) return std::nullopt;
                return raw_value();
        }

        if (auto v = read_sensor()) {
                use(*v);
        }
        uint32_t x = read_sensor().value_or(0);

/* LAYOUT: sizeof(T) + one bool + padding. INLINE, no
   allocation. Replaces:
     · a magic sentinel (0xFFFFFFFF meaning "no reading")
     · a bool out-parameter
     · a pointer that might be null
   all of which are error-prone in ways optional is not.

#include <variant>

/* "exactly one of these types" - a tagged union with the
   tagging done correctly.                                  */

        using Event = std::variant<ButtonPress, SensorReading,
                                   Timeout>;

        void handle(const Event& e)
        {
                std::visit([](const auto& ev) {
                        using T = std::decay_t<decltype(ev)>;
                        if constexpr (std::is_same_v<T,
                                                ButtonPress>)
                                on_button(ev);
                        else if constexpr (std::is_same_v<T,
                                                SensorReading>)
                                on_sensor(ev);
                        else
                                on_timeout(ev);
                }, e);
        }

/* LAYOUT: as large as the largest alternative, plus a small
   index. Inline, no allocation.

   VERSUS A RAW UNION: the variant knows which member is
   active, destroys the right one, and std::visit is
   EXHAUSTIVE - add an alternative and the code that does not
   handle it fails to compile. That last property is the
   whole value.

/* THE EXCEPTIONS CAVEAT: std::get and std::visit can throw
   std::bad_variant_access. With -fno-exceptions, use
   std::get_if, which returns a pointer or null:          */
        if (auto *p = std::get_if<SensorReading>(&e))
                on_sensor(*p);

/* AND std::expected (C++23) - a value or an error, which is
   what you actually want for a fallible operation
   (chapter 12):                                            */
        std::expected<Reading, Error> read();
        if (auto r = read())  use(*r);
        else                  log(r.error());

Measuring the cost

Container choice is easy to argue about and easy to measure. These are the numbers that actually decide it on a constrained target.

/* Do not guess. Measure the three things that matter. */

/* --- 1. SIZE, at compile time --- */
        static_assert(sizeof(std::array<uint8_t, 64>) == 64);
        static_assert(sizeof(std::span<int>) == 16);
        static_assert(sizeof(std::optional<uint32_t>) == 8);
        static_assert(sizeof(std::string_view) == 16);
        /* and on your target: */
        static_assert(sizeof(std::vector<int>) == 24);
        static_assert(sizeof(std::string) == 32);

/* --- 2. ALLOCATIONS, at run time --- */
        static size_t g_allocs = 0;
        void *operator new(size_t n) {
                g_allocs++;
                return malloc(n);
        }
        void operator delete(void *p) noexcept { free(p); }
/* Then assert the count is zero over your hot path. On bare
   metal, simply do not link an operator new - any
   accidental allocation becomes a LINK ERROR, which is the
   strongest guarantee available.

/* --- 3. CODE SIZE --- */
        nm --size-sort -S prog.elf | tail -20
        bloaty prog.elf -d symbols
/* Watch for std::__cxx11::basic_string and the iostream
   machinery appearing - each is tens of kilobytes.

/* --- AND THE STRUCTURAL CHECK --- */
        grep -rn 'std::string\|std::vector\|std::map\|iostream' src/
/* In a codebase with a documented subset (chapter 01), this
   grep should return nothing outside the places you decided
   to allow it. Automate it in CI.                        */
