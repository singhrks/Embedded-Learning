The memory map and the linker script

On a hosted system the linker script is a detail you never see. Here it is a design document: it decides what lives in flash, what lives in RAM, where the stack ends, and what happens when you run out. This chapter reads one line by line.

Why you cannot avoid this file

The compilers track covers linking in general: sections, symbols, relocation. What changes on bare metal is that nothing supplies a default that works. There is no loader to place your segments at run time, so the addresses baked in at link time are the addresses used forever. The linker script is where you state them.

   THE THREE JOBS OF A BARE-METAL LINKER SCRIPT

   1. Declare the physical memories and their sizes.
         "256 kB of flash at 0x08000000,
           64 kB of SRAM  at 0x20000000"

   2. Assign each input section to one of them.
         .text   -> flash
         .rodata -> flash
         .data   -> RAM, but its INITIAL VALUES in flash
         .bss    -> RAM, no initial values at all

   3. Export symbols so startup code can find the boundaries.
         _sdata, _edata, _sbss, _ebss, _estack, _sidata

   Job 3 is the one that surprises people: the linker script
   and the startup code (chapter 06) are two halves of one
   mechanism. Neither makes sense alone.

Load address versus virtual address

This is the concept the whole file turns on, and the one that makes .data comprehensible.

   A variable with an initial value:

       int counter = 42;

   It must be WRITABLE, so at run time it must live in RAM.
   But RAM is volatile - at power-on it contains garbage.
   So the value 42 has to be stored somewhere non-volatile.

   FLASH (what is programmed)      RAM (at run time)
   +---------------------+         +------------------+
   | .text  (code)       |         |                  |
   +---------------------+         |                  |
   | .rodata (consts)    |         |                  |
   +---------------------+         +------------------+
   | .data INITIALISERS  | ------> | .data  counter=42|
   |   the value 42      |  copy   +------------------+
   +---------------------+  at     | .bss   (zeroed)  |
                            boot   +------------------+

   VMA - Virtual Memory Address: where the code EXPECTS the
         variable to be. For .data, that is in RAM.
   LMA - Load Memory Address: where the value is STORED in
         the image. For .data, that is in flash.

   For .text and .rodata, VMA == LMA - they are used where
   they sit. For .data they differ, and the gap between them
   is exactly the copy loop in Reset_Handler.

   .bss has no LMA at all. It occupies no space in the image
   because its contents are known: zero. That is why a
   100 kB array of zeros adds nothing to your binary, and a
   100 kB array of ones adds 100 kB.

A complete linker script

/* GNU ld script for a Cortex-M4 with 256 kB flash, 64 kB SRAM.
   This is the whole file - they are shorter than their
   reputation suggests.                                       */

ENTRY(Reset_Handler)

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 256K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 64K
}

/* Stack and heap sizes, checked at link time below. */
_Min_Heap_Size  = 0x200;    /*  512 bytes */
_Min_Stack_Size = 0x800;    /* 2048 bytes */

SECTIONS
{
  /* Vector table FIRST, at the very base of flash.
     KEEP stops --gc-sections deleting it: nothing in C
     refers to it, so it looks like dead code.               */
  .isr_vector :
  {
    . = ALIGN(4);
    KEEP(*(.isr_vector))
    . = ALIGN(4);
  } >FLASH

  /* Code and read-only data. */
  .text :
  {
    . = ALIGN(4);
    *(.text)
    *(.text*)
    *(.glue_7)  *(.glue_7t)
    *(.eh_frame)
    KEEP(*(.init))
    KEEP(*(.fini))
    . = ALIGN(4);
    _etext = .;
  } >FLASH

  .rodata :
  {
    . = ALIGN(4);
    *(.rodata)
    *(.rodata*)
    . = ALIGN(4);
  } >FLASH

  /* THE IMPORTANT ONE.
     AT> FLASH sets the LMA; >RAM sets the VMA.
     _sidata is where the initialisers live in flash;
     _sdata.._edata is where they must end up in RAM.        */
  _sidata = LOADADDR(.data);

  .data :
  {
    . = ALIGN(4);
    _sdata = .;
    *(.data)
    *(.data*)
    . = ALIGN(4);
    _edata = .;
  } >RAM AT> FLASH

  /* Zero-initialised data. No AT> clause: no load address,
     no space in the image.                                  */
  .bss :
  {
    . = ALIGN(4);
    _sbss = .;
    __bss_start__ = _sbss;
    *(.bss)
    *(.bss*)
    *(COMMON)
    . = ALIGN(4);
    _ebss = .;
    __bss_end__ = _ebss;
  } >RAM

  /* Prove at LINK TIME that stack and heap still fit.
     Without this you discover the overflow at run time,
     as corruption. With it, the build fails.                */
  ._user_heap_stack :
  {
    . = ALIGN(8);
    PROVIDE ( end = . );
    . = . + _Min_Heap_Size;
    . = . + _Min_Stack_Size;
    . = ALIGN(8);
  } >RAM

  _estack = ORIGIN(RAM) + LENGTH(RAM);   /* top of RAM */

  /DISCARD/ : { libc.a ( * ) libm.a ( * ) libgcc.a ( * ) }
  .ARM.attributes 0 : { *(.ARM.attributes) }
}
The ._user_heap_stack section is the best line in the file

It allocates nothing and generates no code. Its only purpose is to make the linker fail if the remaining RAM cannot hold your declared minimum stack and heap. Without it, an over-large array links successfully and corrupts the stack at run time — a bug that presents as random misbehaviour weeks later. With it, you get region RAM overflowed by 312 bytes at build time. Trading a runtime mystery for a compile error is the whole art of embedded engineering, and this is the cheapest such trade available.

Putting specific things in specific places

/* Four placements you will actually need. */

/* 1. A buffer in a particular RAM bank - often required
      because only one bank is reachable by the DMA engine,
      or because a second bank is faster.                    */
__attribute__((section(".sram2")))
static uint8_t dma_buffer[1024];
/* with, in the script:
     RAM2 (rw) : ORIGIN = 0x2001C000, LENGTH = 16K
     .sram2 (NOLOAD) : { *(.sram2) } >RAM2                   */

/* 2. Data that must SURVIVE a reset - a crash log, a boot
      counter. Place it in a NOLOAD section so startup code
      never zeroes it.                                       */
__attribute__((section(".noinit")))
static uint32_t crash_count;
/*   .noinit (NOLOAD) : { *(.noinit) } >RAM
     NOLOAD means: reserve the address range, put nothing in
     the image. Combined with excluding it from the .bss
     zeroing loop, the value survives a warm reset.          */

/* 3. Code that must run FROM RAM - a flash-erase routine
      cannot execute from the flash it is erasing.           */
__attribute__((section(".ramfunc"), long_call, noinline))
void erase_sector(uint32_t addr) { /* ... */ }
/*   .ramfunc : { *(.ramfunc) } >RAM AT> FLASH
     Same LMA/VMA trick as .data - startup copies it.        */

/* 4. A fixed-address configuration block the bootloader and
      application both know about.                           */
__attribute__((section(".config"), used))
const struct config cfg = { .magic = 0xC0FFEE };
/*   .config 0x0801F000 : { KEEP(*(.config)) } >FLASH        */

Reading the output

$ arm-none-eabi-size -A firmware.elf
section          size      addr
.isr_vector       428   0x8000000
.text           28964   0x80001ac
.rodata          1832   0x8007270
.data             264  0x20000000     <- counts against BOTH
.bss             8192  0x20000108
._user_heap_stack 2560  0x20002108

/* FLASH used = .isr_vector + .text + .rodata + .data
              = 428 + 28964 + 1832 + 264 = 31488 of 262144

   RAM used   = .data + .bss + heap + stack
              = 264 + 8192 + 2560 = 11016 of 65536

   .data is counted TWICE - once in flash for the
   initialisers, once in RAM for the variables. This is the
   single most common arithmetic error when budgeting.      */

$ arm-none-eabi-nm --size-sort -S firmware.elf | tail -5
20000908 00000800 b uart_rx_ring
20001108 00001000 b sensor_history
/* --size-sort finds what is eating your RAM. 'b' is .bss,
   'd' is .data, 't' is .text. When the linker says RAM
   overflowed, this command names the culprit in seconds.   */

$ arm-none-eabi-objdump -h firmware.elf
/* Shows VMA and LMA side by side. If .data's LMA is not in
   flash, your AT> clause is wrong and the initialisers are
   not in the image at all - variables will hold garbage.   */
The map file is worth more than it looks

Pass -Wl,-Map=firmware.map and you get a file naming every symbol, its address, its size, and crucially which object file pulled it in. When a 4 kB printf implementation appears in a project that never calls printf, the map file's "referenced by" chain is what tells you it came in through assert. This is the single most under-used diagnostic in embedded development.

How it shows up

SymptomCause
region RAM overflowed by N bytesWorking as intended — use nm --size-sort to find the largest objects
Initialised globals contain garbage.data has no AT> clause, or startup does not run the copy loop
Globals are zero when they should be 42Section landed in .bss; check the map file
Vector table absent from the binaryMissing KEEP() — --gc-sections removed it
Binary far larger than expectedA large array initialised to non-zero values lives in flash as well as RAM
DMA transfers silently produce nothingBuffer in a RAM bank the DMA engine cannot reach — place it explicitly
Flash erase routine hangs the coreCode executing from the flash being erased; needs .ramfunc
Crash log cleared by the reset it recordedVariable in .bss, so startup zeroed it; needs .noinit
Linker succeeds, stack corrupts at run timeNo ._user_heap_stack check — add it
Unexplained 4 kB of code you never calledPulled in transitively; the map file's reference chain names it
