User buffers: buffered, direct and neither

Three ways the I/O manager can hand you a user's buffer, with completely different performance, safety and access rules. Choosing correctly is a design decision made once per interface — and choosing METHOD_NEITHER by accident is how drivers get CVEs.

The decision, in one line

Use METHOD_BUFFERED for control operations and small data. Use METHOD_OUT_DIRECT / METHOD_IN_DIRECT for bulk data and anything you will DMA. Use METHOD_NEITHER only when you have a specific, defensible reason — and then write the probing code with the care of someone who knows it is the most commonly botched thing in Windows drivers.

METHOD_BUFFERED

The safest of the three methods, and the right default for small transfers. The I/O manager copies the data for you, so your driver never touches a user address at all — which removes an entire category of bug at the cost of one copy.

   WRITE:
     user buffer --copy--> SystemBuffer (non-paged pool)
                              |
                              v
                          your driver reads it

   READ:
     your driver writes SystemBuffer
                              |
     user buffer <--copy-- SystemBuffer
     (the I/O manager copies back AT COMPLETION)

  ONE buffer serves BOTH directions in an IOCTL. It is sized
  max(InputBufferLength, OutputBufferLength), so:

     · your input is available when you start
     · you overwrite it with output
     · the I/O manager copies OutputBufferLength bytes back

  READ YOUR INPUT BEFORE WRITING YOUR OUTPUT. Writing output
  first destroys the input you have not read yet - a bug that
  works whenever input and output happen not to overlap, and
  fails when they do.

  THE SAFETY: the I/O manager probed the user buffer, copied
  it in kernel space in the CALLER'S context at PASSIVE_LEVEL,
  and the copy is in non-paged pool. So SystemBuffer is safe
  to touch at any IRQL, in any thread, at any time - which is
  exactly what you need for asynchronous completion from a
  DPC.

  THE COST: two copies. For a 4-byte control value that is
  irrelevant. For a 4 MB frame it is not.
NTSTATUS
MyDeviceControl(_In_ PDEVICE_OBJECT DeviceObject, _In_ PIRP Irp)
{
        PIO_STACK_LOCATION sp = IoGetCurrentIrpStackLocation(Irp);
        ULONG inLen  = sp->Parameters.DeviceIoControl.
                           InputBufferLength;
        ULONG outLen = sp->Parameters.DeviceIoControl.
                           OutputBufferLength;
        PVOID buffer = Irp->AssociatedIrp.SystemBuffer;
        NTSTATUS status;
        ULONG_PTR info = 0;

        switch (sp->Parameters.DeviceIoControl.IoControlCode) {
        case IOCTL_MY_SET_CONFIG: {
                MY_CONFIG cfg;

                if (inLen < sizeof(MY_CONFIG)) {
                        status = STATUS_BUFFER_TOO_SMALL;
                        break;
                }
                /* SystemBuffer is a kernel copy already, but
                   copy again into a local if you will write
                   output into the same buffer               */
                RtlCopyMemory(&cfg, buffer, sizeof(cfg));

                status = MyValidateAndApply(&cfg);
                break;
        }

        case IOCTL_MY_GET_STATS: {
                MY_STATS stats;

                if (outLen < sizeof(MY_STATS)) {
                        status = STATUS_BUFFER_TOO_SMALL;
                        Irp->IoStatus.Information = sizeof(MY_STATS);
                        break;          /* tell them the size */
                }
                MyGatherStats(&stats);
                RtlCopyMemory(buffer, &stats, sizeof(stats));
                info = sizeof(stats);
                status = STATUS_SUCCESS;
                break;
        }

        default:
                status = STATUS_INVALID_DEVICE_REQUEST;
                break;
        }

        Irp->IoStatus.Status = status;
        Irp->IoStatus.Information = info;
        IoCompleteRequest(Irp, IO_NO_INCREMENT);
        return status;
}

METHOD_DIRECT

For large transfers, copying is the dominant cost. Direct I/O avoids it: the I/O manager locks the user's pages in memory and hands you a description of them, so the data is never duplicated.

   The I/O manager:
     1. probes the user buffer
     2. builds an MDL describing its physical pages
     3. LOCKS those pages in memory
     4. hands you Irp->MdlAddress

   NO COPY happens. You either:
     · map the MDL to a kernel virtual address and touch it,
       or
     · hand the MDL straight to a DMA engine (chapter 19)

   METHOD_IN_DIRECT   the buffer is INPUT to the driver
                      (despite "IN" - the user WRITES it, the
                      driver READS it)
   METHOD_OUT_DIRECT  the buffer is OUTPUT from the driver

   THE NAMING IS GENUINELY CONFUSING. Remember it from the
   USER's point of view: OUT_DIRECT means data comes OUT of
   the driver to the user, so the driver writes it. That is
   the common case for a read.

   AND FOR IOCTLs: only the OUTPUT buffer is described by the
   MDL. The INPUT buffer of a DIRECT ioctl is still buffered,
   in SystemBuffer. So a DIRECT ioctl gives you BOTH:

        input  -> Irp->AssociatedIrp.SystemBuffer
        output -> Irp->MdlAddress

   That asymmetry catches everyone once.
        PVOID kva;
        ULONG length;

        if (Irp->MdlAddress == NULL) {
                status = STATUS_INVALID_PARAMETER;
                goto complete;
        }

        length = MmGetMdlByteCount(Irp->MdlAddress);

        /* map it to a kernel address valid in ANY context */
        kva = MmGetSystemAddressForMdlSafe(Irp->MdlAddress,
                        NormalPagePriority | MdlMappingNoExecute);
        if (kva == NULL) {
                status = STATUS_INSUFFICIENT_RESOURCES;
                goto complete;
        }

        RtlCopyMemory(kva, source, min(length, sourceLength));
        info = min(length, sourceLength);
        status = STATUS_SUCCESS;

/* NOTES:
     · MmGetSystemAddressForMdlSafe can FAIL under memory
       pressure - check it. The non-Safe variant bugchecks
       instead, which is why it is never the right call.
     · MdlMappingNoExecute is required on modern Windows;
       omitting it fails the mapping outright.
     · the I/O manager unlocks and frees the MDL at
       completion. Do NOT unlock it yourself.
     · for DMA you do not map at all - you pass the MDL to the
       DMA adapter (chapter 19). That is the real payoff:
       user pages go straight to the hardware with no copy and
       no kernel mapping.                                   */

METHOD_NEITHER

The third method hands you the raw user-mode addresses and gets out of the way. It is the fastest and by a wide margin the most dangerous, and it is where a large share of real driver vulnerabilities live.

/* You get the RAW USER POINTERS:
        input  -> sp->Parameters.DeviceIoControl.Type3InputBuffer
        output -> Irp->UserBuffer

   NOTHING has been probed, nothing copied, nothing locked.
   These addresses are valid ONLY:
        · in the calling process's context
        · at IRQL <= APC_LEVEL
        · until the user changes the memory, which another
          thread can do at any instant                      */

/* THE ONLY CORRECT WAY TO USE IT: */

        PVOID userIn  = sp->Parameters.DeviceIoControl.
                            Type3InputBuffer;
        PVOID userOut = Irp->UserBuffer;
        MY_CONFIG local;

        if (inLen < sizeof(MY_CONFIG))
                return STATUS_BUFFER_TOO_SMALL;

        __try {
                if (Irp->RequestorMode != KernelMode) {
                        ProbeForRead(userIn, inLen,
                                     __alignof(MY_CONFIG));
                        ProbeForWrite(userOut, outLen,
                                      __alignof(ULONG));
                }

                /* COPY IN. Never validate in place. */
                RtlCopyMemory(&local, userIn, sizeof(local));

        } __except (EXCEPTION_EXECUTE_HANDLER) {
                return GetExceptionCode();
        }

        /* validate the COPY, use only the COPY */
        if (local.Rate == 0 || local.Rate > MAX_RATE)
                return STATUS_INVALID_PARAMETER;

        status = MyApply(&local);

        __try {
                RtlCopyMemory(userOut, &result, sizeof(result));
        } __except (EXCEPTION_EXECUTE_HANDLER) {
                return GetExceptionCode();
        }
Why METHOD_NEITHER produces CVEs
  • No __try. A bad pointer becomes a bugcheck — a denial of service any user can trigger.
  • Probed, then used the original pointer. Another thread rewrites the buffer between the probe and the use. Classic TOCTOU (the same argument as isolation chapter 09).
  • Validated in place. Same problem: the value you checked is not the value you use.
  • Forgot RequestorMode. Probing is skipped for kernel callers — but if you never check, a user-mode caller's kernel-looking address is used unprobed.
  • Touched the pointer from a DPC or another thread. The address means nothing outside the caller's process context.
  • Trusted a length field inside the user buffer to bound a copy.

Every one of these has shipped in real drivers. If you cannot state why METHOD_BUFFERED or METHOD_DIRECT is unacceptable for your case, do not use METHOD_NEITHER.

Choosing it, per interface

The method is not a property of your driver — it is encoded in each individual IOCTL code, which means one driver can use different methods for different operations, choosing the right trade-off per request.

/* FOR READ/WRITE: the DEVICE OBJECT's flags decide, and it
   applies to every read and write on that device.        */

        /* WDM: */
        deviceObject->Flags |= DO_BUFFERED_IO;
        /* or */
        deviceObject->Flags |= DO_DIRECT_IO;
        /* neither flag set = METHOD_NEITHER */

        /* WDF: */
        WdfDeviceInitSetIoType(DeviceInit,
                               WdfDeviceIoBuffered);
        WdfDeviceInitSetIoType(DeviceInit,
                               WdfDeviceIoDirect);
        /* and per-queue, in newer versions: */
        WdfDeviceInitSetIoTypeEx(DeviceInit, &ioTypeConfig);

/* FOR IOCTLs: encoded in the CONTROL CODE itself
   (chapter 17), so it is per-operation: */

        #define IOCTL_MY_SET_CONFIG \
            CTL_CODE(FILE_DEVICE_UNKNOWN, 0x800, \
                     METHOD_BUFFERED, FILE_WRITE_ACCESS)

        #define IOCTL_MY_READ_BULK \
            CTL_CODE(FILE_DEVICE_UNKNOWN, 0x801, \
                     METHOD_OUT_DIRECT, FILE_READ_ACCESS)

/* SO A SINGLE DRIVER can use BUFFERED for its control IOCTLs
   and DIRECT for its bulk transfer IOCTL, which is exactly
   the right design: cheap safety where the data is small,
   zero copy where it is large.                            */

/* AND IN A FILTER DRIVER: inherit the method from the device
   below you, or reads and writes arrive in a form your lower
   driver does not expect:                                 */
        fdo->Flags |= lowerDevice->Flags &
                      (DO_BUFFERED_IO | DO_DIRECT_IO);

In WDF, it is simpler

KMDF removes most of the above. You ask for the buffer and the framework gives you a validated pointer and length regardless of which method the IOCTL used — which is one of the strongest practical arguments for the framework.

/* WDF hides the method behind one API. You ask for a buffer
   and the framework gives you a safe kernel pointer,
   whichever transfer method was used.                     */

VOID
MyEvtIoDeviceControl(_In_ WDFQUEUE Queue,
                     _In_ WDFREQUEST Request,
                     _In_ size_t OutputBufferLength,
                     _In_ size_t InputBufferLength,
                     _In_ ULONG IoControlCode)
{
        PVOID inBuf, outBuf;
        size_t inLen, outLen;
        NTSTATUS status;

        status = WdfRequestRetrieveInputBuffer(Request,
                        sizeof(MY_CONFIG),   /* MINIMUM size -
                                                checked FOR you */
                        &inBuf, &inLen);
        if (!NT_SUCCESS(status)) {
                WdfRequestComplete(Request, status);
                return;
        }

        status = WdfRequestRetrieveOutputBuffer(Request,
                        sizeof(MY_STATS), &outBuf, &outLen);
        ...

        WdfRequestCompleteWithInformation(Request, status,
                                          bytesWritten);
}

/* WdfRequestRetrieve*Buffer:
     · works for BUFFERED and DIRECT identically
     · CHECKS THE MINIMUM LENGTH and returns
       STATUS_BUFFER_TOO_SMALL if it is short - so the most
       common validation is done for you
     · for DIRECT, maps the MDL and handles the failure
     · refuses outright for METHOD_NEITHER unless you opted
       in

   AND for DMA, ask for the MDL instead:               */
        status = WdfRequestRetrieveOutputWdmMdl(Request, &mdl);

/* THIS IS THE ARGUMENT FOR WDF in miniature: the same code
   handles both transfer methods, the length check is not
   optional-and-forgotten, and METHOD_NEITHER is opt-in rather
   than the default you fall into.                        */
