Range queries: Fenwick and segment trees

Prefix sums answer range queries instantly and cannot survive an update. Sorting answers order questions and cannot survive an insert. When a problem interleaves updates with queries, both collapse — and this chapter is the two structures that do not.

Recognising the problem

These structures are heavy machinery, and reaching for them when a prefix sum would do is a mistake. There is a precise condition that tells you which tool the problem needs.

   ASK TWO QUESTIONS:

     Q1. Does anything CHANGE after the array is built?
     Q2. Are the queries over RANGES?

        Q1 no,  Q2 no   -> just scan it
        Q1 no,  Q2 yes  -> PREFIX SUMS      (chapter 06)
                           build O(n), query O(1)
        Q1 yes, Q2 no   -> a hash map or a heap
        Q1 yes, Q2 yes  -> THIS CHAPTER
                           update O(log n), query O(log n)

   WHY PREFIX SUMS DIE UNDER UPDATES: changing one element
   invalidates every prefix after it, so an update costs
   O(n). A thousand updates on a million elements is 10^9
   operations, which is the wall these structures exist to
   get past.

   ---------------------------------------------------------

   AND THE DISGUISE TO WATCH FOR. Many problems have no
   updates in the statement and become range-query problems
   once you decide to PROCESS THEM IN A DIFFERENT ORDER:

     "count inversions"
     "count smaller elements to the right"
     "how many earlier points are below and to the left"

   You sweep through the data inserting as you go, and each
   insertion is an update. The update was not in the problem;
   it came from your chosen order. Spotting that is the
   actual skill here.

The Fenwick tree

Also called a binary indexed tree. It is about fifteen lines, it does prefix sums with updates, and its whole behaviour comes from one bit trick that is worth understanding rather than memorising.

   THE IDEA: index i is responsible for a RANGE OF VALUES
   whose length is the lowest set bit of i.

     i = 6 = 110b   lowbit = 2   covers elements 5..6
     i = 8 = 1000b  lowbit = 8   covers elements 1..8
     i = 7 = 111b   lowbit = 1   covers element  7

   lowbit(i) = i & -i          <- two's complement; see
                                  chapter 17

   ---------------------------------------------------------

   PREFIX SUM of 1..i: walk DOWN, stripping the lowest bit.

     sum(7) = tree[7] + tree[6] + tree[4]
              111b  ->  110b  ->  100b  ->  0

     each step covers a disjoint chunk, and the chunks
     tile 1..7 exactly. At most one step per bit, so
     O(log n).

   POINT UPDATE at i: walk UP, adding the lowest bit.

     add(5) touches 5, 6, 8
            101b -> 110b -> 1000b

     these are exactly the indices whose range CONTAINS 5.

   ---------------------------------------------------------

   THE TWO LOOPS ARE MIRROR IMAGES, which is the thing to
   remember when the details fade:

     query: i -= i & -i        (down)
     update: i += i & -i       (up)

   ONE-BASED INDEXING IS NOT OPTIONAL. i & -i is 0 when
   i is 0, so a zero index makes both loops spin forever.
class Fenwick {
    constructor(n) {
        this.n = n;
        this.t = new Array(n + 1).fill(0);   /* 1-BASED */
    }
    /* add v at position i (1-based) */
    update(i, v) {
        for (; i <= this.n; i += i & -i) this.t[i] += v;
    }
    /* sum of positions 1..i */
    query(i) {
        let s = 0;
        for (; i > 0; i -= i & -i) s += this.t[i];
        return s;
    }
    /* sum of positions l..r */
    range(l, r) { return this.query(r) - this.query(l - 1); }
}

/* WHAT IT CANNOT DO, and this is the reason segment trees
   still exist: the subtraction in range() requires an
   INVERTIBLE operation. Sums and XORs invert. MINIMUM DOES
   NOT - knowing min(1..r) and min(1..l-1) tells you nothing
   about min(l..r). For those, use a segment tree.        */

The segment tree

More code, more memory, and far more general. The rule for what it can do is simple, and it is the thing to say when asked why you chose it over a Fenwick tree.

   EACH NODE STORES THE ANSWER FOR ONE RANGE. Children
   split the range in half.

                    [0..7]
              /                \
          [0..3]              [4..7]
         /      \            /      \
     [0..1]   [2..3]    [4..5]   [6..7]
      /  \     /  \      /  \     /  \
     0    1   2    3    4    5   6    7

   A QUERY over [l..r] decomposes into O(log n) nodes whose
   ranges tile it exactly. An UPDATE at a leaf recomputes
   the O(log n) nodes above it.

   ---------------------------------------------------------

   THE RULE FOR WHAT IT SUPPORTS: any ASSOCIATIVE operation.

     sum, min, max, gcd, "leftmost zero", matrix product

   ASSOCIATIVE IS ALL YOU NEED - no inverse required. That
   is precisely the difference from a Fenwick tree, and it
   is the answer to "why not just use a BIT?"

   ---------------------------------------------------------

   THE FLAT ITERATIVE VERSION, which is the one to write
   under time pressure: put the n leaves at t[n..2n-1] and
   every internal node at t[i] = op(t[2i], t[2i+1]).

     no recursion, no lazy propagation, about twelve lines,
     and it handles point update with range query - which is
     what almost every interview asks for.

   RANGE UPDATES need lazy propagation and roughly triple the
   code. Know that it exists, know the phrase, and do not
   attempt it in an interview unless it is clearly required.

   ---------------------------------------------------------

   CHOOSING BETWEEN THEM:

     FENWICK     shorter, ~2x faster, half the memory,
                 SUMS ONLY (or invertible ops)
     SEGMENT     longer, fully general, extends to lazy
                 propagation for range updates

   DEFAULT TO FENWICK IF THE OPERATION IS A SUM. Reach for a
   segment tree the moment it is a min, a max, or anything
   you cannot undo.
