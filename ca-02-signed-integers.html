Signed integers and two's complement

Negative numbers do not exist in hardware. What exists is a representation clever enough that the adder does not need to know about them — and understanding why it works explains a whole family of security bugs.

The problem

You have eight bits. That is 256 distinct patterns. You want some of them to mean negative numbers. The naïve approach — steal the top bit as a sign flag — seems obvious:

Sign-and-magnitude (the obvious idea, and wrong)

  0000 0101  =  +5
  1000 0101  =  -5     top bit = sign, rest = magnitude

Two problems:
  1. 0000 0000 = +0  and  1000 0000 = -0.  Two zeros. Every comparison
     against zero needs a special case.
  2. Addition needs a subtractor.  5 + (-5) through a plain binary adder
     gives 1000 1010 = -10.  Wrong. The hardware must inspect the signs
     and choose between adding and subtracting.

That second point costs real gates, real area and real time.

The mechanism: two's complement

The trick is to choose a representation where ordinary binary addition just works, with no sign inspection at all. Represent −n as the pattern that, added to n, produces zero after the carry out of the top bit is discarded.

Eight-bit two's complement: the number line wraps

  bit pattern   unsigned   signed
  0000 0000        0          0
  0000 0001        1         +1
  ...
  0111 1110      126       +126
  0111 1111      127       +127     ← largest positive
  1000 0000      128       -128     ← the wrap point
  1000 0001      129       -127
  ...
  1111 1110      254         -2
  1111 1111      255         -1     ← all ones is -1, always

The top bit still tells you the sign. But it is not a flag —
it carries a weight, and that weight is NEGATIVE:

  1111 1111  =  -128 + 64 + 32 + 16 + 8 + 4 + 2 + 1  =  -1
                 ─┬─
                  └── the only negative weight in the whole number
The one-sentence definition

In an n-bit two's complement number, the most significant bit has weight −2n−1 and every other bit has its usual positive weight. That is the entire system; everything else follows.

Why addition needs no special case

   5 + (-5), eight bits

     0000 0101      ( +5 )
   + 1111 1011      ( -5 )
   ───────────
   1 0000 0000
   ↑
   └── carry out of bit 7, discarded because the result is 8 bits

     result = 0000 0000 = 0   ✓

   7 + (-3)

     0000 0111      ( +7 )
   + 1111 1101      ( -3 )
   ───────────
   1 0000 0100  →  0000 0100 = +4   ✓

The adder never looked at a sign. Subtraction is just addition of the
negation, so the CPU needs ONE arithmetic unit for both — which is why
every processor built since the 1960s uses this representation.

How to negate

Two equivalent recipes. Both give the same answer; use whichever is faster for you.

Method 1: invert all bits, then add one

    +5   =  0000 0101
  invert    1111 1010
  add 1     1111 1011  =  -5

Method 2: copy bits from the right up to and including the first 1,
          then invert everything above it

    +12  =  0000 1100
                   ─┴┴  copy "100" unchanged
            1111 0100  =  -12
            ─────┘ invert the rest

Sanity check: negating twice must return the original.
    -5  = 1111 1011 → invert 0000 0100 → +1 → 0000 0101 = +5  ✓

The asymmetry that breaks code

There is one more negative number than positive. There are 128 negatives (−128…−1) and only 127 positives (1…127), because zero occupies a slot on the positive side.

The consequence: -INT_MIN is not representable. abs(INT_MIN) returns INT_MIN — still negative. In C this is undefined behaviour, and on ARM the instruction simply produces INT_MIN back. Code of the form if (abs(x) < limit) can therefore be defeated by passing INT_MIN, which has been the root of real vulnerabilities.

Sign extension

When a narrow value is widened, the new high bits must be filled. Filling them with zero is correct for unsigned values and catastrophic for negative signed ones.

Widening 8-bit 0xFF (-1 signed, 255 unsigned) to 32 bits

  ZERO extension    0x000000FF  =  255      correct for uint8_t
  SIGN extension    0xFFFFFFFF  =   -1      correct for int8_t

The rule: replicate the top bit of the source into every new bit.

This is why ARM has separate instructions:
  LDRB   Wd, [Xn]     load byte, zero-extend  → unsigned
  LDRSB  Wd, [Xn]     load byte, sign-extend  → signed
  LDRSW  Xd, [Xn]     load 32-bit word, sign-extend to 64

Picking the wrong load instruction is a silent, data-dependent bug:
it only misbehaves when the value happens to have its top bit set.
/* the classic surprise */
char c = -1;                      /* char may be signed or unsigned!      */
int  i = c;                       /* -1 if signed char, 255 if unsigned   */

/* getchar() returns int, not char, precisely because of this */
int ch;
while ((ch = getchar()) != EOF)   /* EOF is -1; a char cannot hold it     */
        ...                       /*   distinctly from the byte 0xFF      */

/* always be explicit in systems code */
int8_t  signed_byte   = -1;       /* guaranteed signed   */
uint8_t unsigned_byte = 0xFF;     /* guaranteed unsigned */

Mixing signed and unsigned: the biggest trap in C

When C compares a signed and an unsigned value of the same rank, the signed operand is converted to unsigned. The negative number becomes enormous.

int      i = -1;
unsigned u =  1;

if (i < u)                    /* FALSE. i converts to 4294967295 */
        puts("as expected");
else
        puts("surprise");     /* this branch runs */
The bug this causes, in the shape it actually appears 
/* a length check that does not check */
int copy_in(void *dst, const void *src, int len)
{
        if (len > MAX_LEN)            /* len = -1 passes: -1 > 1024 is false */
                return -EINVAL;
        memcpy(dst, src, len);        /* memcpy takes size_t — UNSIGNED.     */
        return 0;                     /* -1 becomes SIZE_MAX. Heap destroyed. */
}

This exact pattern — a signed length validated against an upper bound, then passed to an unsigned API — is one of the most common serious vulnerabilities in C code. The fix is to use an unsigned type for the length and check both ends of the range.

/* the fixed version */
int copy_in(void *dst, const void *src, size_t len)
{
        if (len == 0 || len > MAX_LEN)
                return -EINVAL;
        memcpy(dst, src, len);
        return 0;
}

Overflow

Overflow is what happens when the true answer will not fit in the bits available. The processor does not stop or warn — it simply gives you a wrong value, and in C the consequences differ sharply depending on whether the type was signed or unsigned.

Signed overflow, 8-bit:

    127 + 1  =  0111 1111 + 0000 0001  =  1000 0000  =  -128

The number line wraps from the largest positive straight to the most
negative. The carry INTO the top bit differs from the carry OUT of it —
that is exactly the hardware condition that sets the V (overflow) flag.

Unsigned overflow, 8-bit:

    255 + 1  =  1111 1111 + 0000 0001  = 1 0000 0000  →  0000 0000

Wraps to zero. Carry out of the top bit sets the C (carry) flag.

Why signed overflow being UB matters in practice 
if (x + 1 < x)          /* trying to detect signed overflow */
        handle();       /* GCC deletes this branch entirely at -O2:  */
                        /* signed overflow "cannot happen", so x+1 < x */
                        /* is always false.                            */

The check compiles to nothing. Detect overflow with the builtins instead: __builtin_add_overflow(a, b, &result) returns true on overflow and is a single instruction on ARM (it reads the V flag). The kernel wraps these as check_add_overflow().

The condition flags

Every arithmetic operation on ARM can set four flags, and their definitions come straight from this chapter:

FlagSet whenUsed for
N — negativeThe result's top bit is 1Signed comparisons
Z — zeroThe result is all zero bitsEquality tests
C — carryCarry out of the top bit (unsigned overflow)Unsigned comparisons, multi-word arithmetic
V — overflowCarry into the top bit ≠ carry out of itSigned overflow detection

This is why ARM has two families of conditional branches: B.HI/B.LO (unsigned, test C and Z) versus B.GT/B.LT (signed, test N and V). The comparison instruction is identical; only the interpretation differs — the same theme as chapter 01.
