The ARM64 boot flow

From power-on to the first line of C. This is where the ARM architecture track and the Linux track meet: exception levels, the MMU, the device tree and secure firmware all appear in the first few hundred instructions, and knowing the sequence is what makes bring-up tractable.

The whole sequence

Before a single line of Linux runs, three or four other programs have already executed and handed control onward, each one more capable than the last. This chain matters for a practical reason: when a board does not boot, where it stopped tells you which program failed, and each link in the chain is debugged with completely different tools.

  POWER ON
     |
     v
  BOOT ROM (BL1)            EL3, MMU off, caches off
     |  verifies and loads BL2 (isolation ch. 14)
     v
  BL2                       EL3 (or EL1S)
     |  initialises DRAM, loads BL31/BL32/BL33
     v
  BL31 - TF-A runtime       EL3, stays resident forever
     |  installs the SMC handlers, PSCI, the vectors
     |  drops to...
     +--> BL32 - OP-TEE     S-EL1  (isolation ch. 12)
     |
     v
  BL33 - U-Boot / UEFI      EL2 (usually) or EL1
     |  loads Image + DTB into DRAM
     |  may verify them (FIT signatures)
     v
  KERNEL, at its entry point           EL2 or EL1
     |
     +-- head.S:  primary_entry
     |      preserve x0 = DTB physical address
     |      record the EL we were entered at
     |      if EL2: init_kernel_el -> either stay for KVM,
     |              or drop to EL1
     |      __create_page_tables    build the initial mapping
     |      __primary_switch        turn the MMU ON
     |      set up the stack, clear BSS
     v
  start_kernel()            the first C function (chapter 05)
     |
     v
  ... subsystems, initcalls, drivers ...
     |
     v
  init process, PID 1

The boot protocol

The bootloader and the kernel have to agree, precisely, on the state the machine is in at the moment control passes over — which register holds what, whether caches are on, what is mapped. This is a real contract, written down in the kernel source, and the reason breaking it hurts so much is that it fails silently: no error, no panic, just a board that stops with nothing on the console.

/* Documentation/arch/arm64/booting.rst - the CONTRACT between
   the bootloader and the kernel. Violate any of it and you get
   a silent hang with no output at all.                      */

   THE BOOTLOADER MUST:

   1. Load the kernel Image to a 2 MB-aligned address, anywhere
      in the first usable DRAM. The Image header declares where
      it wants to go and how big it is.

   2. Set:
        x0 = physical address of the DEVICE TREE BLOB
        x1 = 0    (reserved)
        x2 = 0
        x3 = 0

   3. Enter at the first byte of the Image, in:
        EL2 (preferred - enables KVM) or EL1 (non-secure)
        AArch64
        MMU OFF
        D-cache OFF          <-- and this one matters
        I-cache on or off
        interrupts (DAIF) masked

   4. Have CLEANED the kernel image and DTB TO THE POINT OF
      COHERENCY. With the MMU off, the kernel's accesses are
      Device/non-cacheable and will NOT snoop dirty lines the
      bootloader left in the cache (ARM chapters 18 and 19).
      This is the single most common cause of "loads, jumps,
      dies instantly".

   5. Ensure all secondary CPUs are either in a WFE holding
      pen, or - much better - parked and brought up via PSCI
      (isolation ch. 11).

   6. Provide a valid DTB, itself in memory the kernel can
      reach, with /memory and /chosen nodes.

/* THE IMAGE HEADER, first 64 bytes of arch/arm64/kernel/head.S: */

        code0           /* executable code, or an MZ magic for
                           EFI so the same file boots as a PE  */
        code1
        text_offset     /* where to load, relative to 2 MB     */
        image_size      /* total size including BSS - use this
                           to know how much room to leave      */
        flags           /* endianness, page size, placement    */
        res2..res4
        magic           /* "ARM\x64"                           */
        res5            /* PE header offset                    */

/* Read it with: */
        head -c 64 arch/arm64/boot/Image | xxd
"It hangs before any output" — the four causes
  1. Caches not cleaned before jumping. The kernel reads stale memory.
  2. Entered at the wrong EL, or in AArch32, or with the MMU on.
  3. A bad DTB — wrong address in x0, corrupt magic, or a /memory node that does not describe real DRAM.
  4. The console is not where you think. The kernel is running fine and printing to a UART you are not watching. Try earlycon before assuming a crash.

head.S, in order

This is the first kernel code to execute, and it is assembly rather than C because a C environment does not exist yet — there is no stack, no page tables, and no memory map. Everything below exists to build that environment, and the moment it is ready the code jumps into C and never returns here.

/* arch/arm64/kernel/head.S. Read it once; it is only a few
   hundred lines and it demystifies the whole thing.        */

SYM_CODE_START(primary_entry)
        bl      record_mmu_state      /* were we entered with
                                         the MMU on? (EFI)    */
        bl      preserve_boot_args    /* stash x0..x3 - the
                                         DTB pointer!         */
        bl      create_idmap          /* an IDENTITY map: VA
                                         == PA, so we can keep
                                         executing across the
                                         MMU enable            */
        b       __primary_switch
SYM_CODE_END(primary_entry)

/* THE IDENTITY MAP TRICK - the central problem of MMU enable:

   Before:  PC = 0x40080000 (physical), MMU off
   After:   PC must be 0xffff800008080000 (virtual)

   You cannot change both at once. So:
     1. build a page table where VA 0x40080000 maps to
        PA 0x40080000 (the identity map), AND where the real
        kernel VA range maps to the same physical memory
     2. enable the MMU - the next instruction fetch at
        0x40080000 now translates through the identity map and
        finds the same code. Nothing appears to change.
     3. branch to the high virtual address
     4. tear down the identity map

   Same trick every OS uses, and the reason arm64 requires the
   kernel to be position-independent early on.             */

__primary_switch:
        adrp    x1, reserved_pg_dir
        adrp    x2, init_idmap_pg_dir
        bl      __enable_mmu          /* set SCTLR_EL1.M = 1   */
        bl      clear_page_tables
        bl      create_kernel_mapping /* the real mapping */
        ...
        bl      __primary_switched

__primary_switched:
        adr_l   x8, vectors           /* the exception table
                                         (ARM ch. 27)          */
        msr     vbar_el1, x8          /* now faults are
                                         survivable            */
        ...
        str_l   x21, __fdt_pointer, x5   /* save the DTB addr */
        bl      __pi_memset              /* clear BSS */
        ...
        b       start_kernel             /* into C */

Which exception level, and why it matters

ARM processors have several privilege levels, and the kernel can be started at more than one of them. Which one it got is decided by the bootloader before Linux has any say, and it permanently determines whether virtualisation will work on this boot. Chapter 44 covers the levels in full; what matters here is that the choice was already made for you.

/* The kernel records the EL it was entered at, and behaves
   differently:                                             */

   Entered at EL2:
        · KVM is possible. The kernel installs a hypervisor
          stub at EL2 and runs itself at EL1.
        · With VHE (ARMv8.1, FEAT_VHE), the kernel runs
          DIRECTLY at EL2 with EL2 registers behaving like EL1
          ones - this is the normal case on modern hardware.
        · dmesg says:  "CPU: All CPU(s) started at EL2"

   Entered at EL1:
        · no KVM. Everything else works.
        · dmesg says:  "CPU: All CPU(s) started at EL1"
        · usually means the bootloader dropped to EL1 itself,
          or a hypervisor is already running above you

/* CHECK IT FIRST when virtualisation does not work: */
        dmesg | grep "CPU(s) started at"
        dmesg | grep -i kvm

/* A bootloader that drops to EL1 before entering Linux
   silently disables KVM forever. On U-Boot this is
   CONFIG_ARMV8_SWITCH_TO_EL1 - leave it off.               */

The device tree arrives

One kernel binary runs on thousands of different boards, so it cannot have any particular board's hardware built into it. Instead it is told what exists, by a data structure the bootloader passes in — and that entire description arrives as a single pointer in one CPU register.

x0 at entry -> __fdt_pointer -> used in three phases:

  1. EARLY, before the MMU is fully set up:
       early_init_dt_scan()
         - /chosen  -> the kernel command line, initrd, stdout
         - /memory  -> how much DRAM, and where
         - reserved-memory -> carve-outs to keep out of the
           allocator (isolation ch. 18)
       These have to work with almost nothing available, so the
       early FDT code is a self-contained flat parser.

  2. UNFLATTENING, once memblock works:
       unflatten_device_tree() converts the flat blob into a
       tree of struct device_node objects with pointers.
       Now of_find_node_by_*() and friends work.

  3. DEVICE CREATION, much later, from an initcall:
       of_platform_populate() walks the tree and creates a
       struct platform_device for each node with a
       `compatible` - which is what your driver eventually
       binds to (chapter 19).

  So the DTB is consumed three times, in three different
  representations. Knowing which phase you are in explains why
  of_* APIs "do not work yet" in early code.

Getting output before the console exists

There is a long stretch of boot during which the kernel is running normally but everything it prints is invisible, because the driver for the serial port has not started yet. If a board hangs inside that window you see a blank screen and nothing else, which is why the technique below is the single most valuable skill in board bring-up.

# The single most useful bring-up skill. A normal console is
# only registered once the serial DRIVER probes - hundreds of
# initcalls in. Everything before that is invisible by default.

# EARLYCON - a minimal, direct-MMIO UART writer, available
# almost immediately:

    earlycon                    # use /chosen/stdout-path from DT
    earlycon=pl011,0x9000000    # or name it explicitly
    earlycon=uart8250,mmio32,0xff000000
    earlycon=uart,mmio32,0x1c020000,115200n8

# combine with:
    keep_bootcon    # do not switch away when the real console
                    # registers - you see BOTH, and the handover
    ignore_loglevel # print everything regardless of loglevel
    debug           # raise the loglevel
    initcall_debug  # print every initcall and its result -
                    # invaluable for "it hangs during boot"

# A good bring-up command line:
    earlycon keep_bootcon ignore_loglevel initcall_debug \
      console=ttyAMA0,115200 root=/dev/mmcblk0p2 rw

# And in the device tree:
    chosen {
        stdout-path = "serial0:115200n8";
        bootargs = "earlycon console=ttyAMA0,115200";
    };

# IF EARLYCON PRODUCES NOTHING:
#   the address is wrong; the UART is not clocked; the pin mux
#   is not set; or the driver name does not match. Try writing
#   a character directly from the bootloader to confirm the
#   UART works at all before blaming the kernel.

# LAST RESORT: CONFIG_DEBUG_LL / earlyprintk with a hard-coded
# address, compiled in. Ugly, and it works when nothing else
# does.
initcall_debug is the boot-hang debugger

It prints every initcall before and after it runs, with the time it took. A hang shows as a calling ... line with no matching initcall ... returned. That names the exact function, which names the driver, in one boot. Pair it with printk.time=1 and you also get a free boot-time profile.

Bringing up the other CPUs

Everything up to this point has run on one CPU. The others are still parked — held in reset, or spinning inside firmware — and starting them is a deliberate step that happens surprisingly late. The hardware does not do it for you.

/* Only CPU0 runs everything above. The rest are brought up
   much later, from smp_init(), using the method the device
   tree declares:                                           */

        cpus {
                cpu@0 {
                        device_type = "cpu";
                        compatible = "arm,cortex-a53";
                        reg = <0x0>;
                        enable-method = "psci";
                };
                cpu@1 { ... reg = <0x1>; enable-method = "psci"; };
        };

        psci {
                compatible = "arm,psci-1.0";
                method = "smc";          /* or "hvc" */
        };

/* PSCI path (isolation ch. 11):
        Linux issues SMC(CPU_ON, target_mpidr, entry_point)
        EL3 firmware powers the core and starts it at
        secondary_entry, which repeats the MMU setup and joins
        the scheduler.

   The older "spin-table" method has the bootloader park each
   secondary in a WFE loop watching a mailbox address. It works
   and it cannot power cores off - so PSCI is what you want.

/* SYMPTOM: only CPU0 online.
        cat /proc/cpuinfo          # one entry
        dmesg | grep -i psci
        dmesg | grep "CPU. failed to come online"
   Almost always: wrong `method` (smc vs hvc), missing PSCI
   node, wrong `reg` values (they must match MPIDR_EL1
   affinity), or firmware refusing CPU_ON. Check the TF-A
   console.                                                 */

How the kernel learns about memory

The kernel cannot ask the hardware how much RAM is fitted or where it lives in the address space; there is no standard way to probe for that. Like everything else about the board, it has to be described from outside.

        memory@80000000 {
                device_type = "memory";      /* REQUIRED */
                reg = <0x0 0x80000000 0x0 0x40000000>;  /* 1 GB */
        };

/* Consumed by early_init_dt_scan_memory() into MEMBLOCK - a
   simple early allocator that exists before the real page
   allocator (chapter 06).

   Then:
     reserved-memory nodes are removed from it
     the kernel image itself is reserved
     the initrd is reserved
     memblock hands the rest to the buddy allocator at
     mem_init()

   CHECK IT:
        dmesg | grep -i "Memory:"
          Memory: 892340K/1048576K available (...)
        cat /proc/iomem
        dmesg | grep -i memblock       (with memblock=debug)

   COMMON PROBLEMS:
     · device_type = "memory" omitted -> node ignored -> the
       kernel finds no RAM and hangs immediately
     · #address-cells/#size-cells mismatch -> the reg values
       are parsed wrong -> wildly wrong size, or an address of
       zero
     · memory described that does not physically exist -> a
       crash the first time the allocator hands out that range,
       long after boot
     · a secure carve-out NOT removed -> the kernel maps memory
       the TZASC denies -> an SError at an unpredictable moment
       (isolation ch. 18)                                    */
