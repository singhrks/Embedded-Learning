What a GPU driver actually does

Between your Draw call and the silicon sits several hundred thousand lines of someone else's code, split across a user-mode library and a kernel driver. Knowing what each half does closes the loop between this track and the Linux and Windows driver tracks — and explains most of the odd behaviour you have met along the way.

The two halves

   YOUR APPLICATION
        |  d3d12.dll / libvulkan.so
        v
   +--------------------------------------------------------+
   |  USER-MODE DRIVER  (UMD)                               |
   |    runs IN YOUR PROCESS, at your privilege             |
   |                                                        |
   |    * compiles DXIL/SPIR-V -> the GPU's real ISA        |
   |    * translates API calls into hardware COMMAND        |
   |      PACKETS, written into a buffer                    |
   |    * manages descriptors and their hardware layout     |
   |    * per-application workarounds and shader            |
   |      replacements, keyed on the executable name        |
   |                                                        |
   |    A CRASH HERE CRASHES YOUR APP, and nothing else.    |
   |    This is why most of the driver lives here.          |
   +--------------------------------------------------------+
        |  ioctl / DeviceIoControl  - the ONLY kernel entry
        v
   +--------------------------------------------------------+
   |  KERNEL-MODE DRIVER  (KMD)                             |
   |    ring 0. Shared by every process on the machine.     |
   |                                                        |
   |    * SUBMITS command buffers to the hardware rings     |
   |    * SCHEDULES between processes - your game and the   |
   |      compositor and the browser all want the GPU       |
   |    * manages GPU VIRTUAL MEMORY and page tables        |
   |    * handles interrupts and fence completion           |
   |    * power and clock management                        |
   |    * RESETS the GPU when something hangs (TDR)         |
   |                                                        |
   |    A CRASH HERE IS A BUGCHECK / KERNEL PANIC.          |
   +--------------------------------------------------------+
        |  MMIO, doorbells, DMA
        v
   THE GPU

   THE SPLIT IS DELIBERATE: everything that can be done at
   application privilege is, so that the enormous, fast-moving,
   game-specific part of the driver cannot take down the
   machine. Only the parts that genuinely need ring 0 -
   submission, memory mapping, interrupts, arbitration between
   processes - live in the kernel.
This is exactly the split you learned in the driver tracks

A GPU driver is the largest example of the same architecture: a user-mode component doing the complex, untrusted work, and a small kernel component owning the hardware, the address space and the arbitration. Compare Windows' WDM/KMDF/UMDF split and the Linux DRM/KMS design — the reasoning is identical, and GPU drivers are simply where it is pushed hardest.

How a draw actually reaches the GPU

/* Follow one Draw all the way down. */

  1. YOUR CODE
        cmd->DrawInstanced(3, 1, 0, 0);

  2. UMD, in your process
        appends a hardware command packet to the command
        allocator's memory. On AMD that is a PM4 packet; on
        NVIDIA a method write. Perhaps 20-100 bytes.
        NO SYSCALL. This is why DX12 draw calls are ~0.1 us.

  3. ExecuteCommandLists
        UMD builds a submission descriptor and calls into the
        KMD. ONE ioctl for the whole list - not one per draw.

  4. KMD
        * validates the buffer belongs to you
        * ensures every referenced resource is RESIDENT and
          mapped in this process's GPU page tables
        * places the submission in a hardware RING BUFFER
        * writes a DOORBELL register - an MMIO write that
          tells the GPU "there is work"

  5. GPU COMMAND PROCESSOR
        fetches from the ring, decodes packets, and feeds the
        front end. The GPU is now executing.

  6. COMPLETION
        the GPU writes a fence value to memory and raises an
        INTERRUPT. The KMD's ISR runs, signals the OS
        synchronisation object, and your WaitForSingleObject
        returns.

  NOTE how few kernel transitions there are: one per SUBMIT,
  not one per draw. That is the single biggest structural
  reason DX12 and Vulkan are faster than DX11 and OpenGL -
  the batching is explicit and under your control.        */

GPU virtual memory

   Modern GPUs have an MMU and per-process page tables, for
   the same reasons a CPU does.

     GPU virtual address
          |  GPU page tables, per process
          v
     physical: VRAM, or system RAM over PCIe, or migrated
               between them by the driver

   WHAT THIS BUYS
     * isolation: one process cannot read another's textures.
       Before per-process GPU page tables this was genuinely
       not true, and it was a real vulnerability class.
     * OVERSUBSCRIPTION: allocate more than VRAM and let the
       driver page. Slow, but it works instead of failing.
     * a stable address for a resource across residency
       changes - GetGPUVirtualAddress() stays valid even if
       the pages move.

   WHAT IT COSTS
     * a GPU page fault is enormously expensive - the whole
       wave stalls, and on older hardware the whole GPU
     * this is what a DRED page-fault report is telling you
       (chapter 12): a shader dereferenced a GPU VA that is
       not mapped, almost always a freed resource or a
       descriptor pointing at nothing

   IOMMU / SMMU applies here too: on a system with an IOMMU
   the GPU's DMA is itself translated, which is what makes
   GPU passthrough to a VM safe (virtualisation chapter 17).

Scheduling, preemption and TDR

/* THE GPU IS SHARED. Your game, the compositor, the browser
   playing video and Windows' own UI all submit work. The KMD
   arbitrates.                                              */

  PREEMPTION GRANULARITY - how quickly a running job can be
  interrupted:

    DRAW-LEVEL     between draw calls. Old hardware.
    PRIMITIVE      between triangles.
    PIXEL / WAVE   mid-draw. Modern hardware.
    INSTRUCTION    fully preemptible. Newest.

  Coarse preemption is why a single enormous draw or dispatch
  can make the whole desktop stutter: nothing else can run
  until it finishes.

/* TDR - TIMEOUT DETECTION AND RECOVERY

   If a submission does not complete within ~2 seconds,
   Windows assumes the GPU is hung:
     1. the KMD is asked to reset the GPU
     2. every application's device is marked REMOVED
     3. your app gets DXGI_ERROR_DEVICE_REMOVED with
        DXGI_ERROR_DEVICE_RESET (chapter 12)

   CAUSES, in order of likelihood:
     * an infinite loop in a shader
     * a compute dispatch that is genuinely too large - split
       it, or it will TDR on slower GPUs even though it works
       on yours
     * a barrier a group never reaches (chapter 18)
     * an actual driver or hardware fault

   THE REGISTRY KEY people reach for:
     HKLM\System\CurrentControlSet\Control\GraphicsDrivers
        TdrDelay = 60
   Raise it FOR DEBUGGING ONLY. Shipping software that needs
   it has a bug, and users will not have set it.

   Linux equivalents: amdgpu.lockup_timeout, and the
   GPU reset paths in i915/amdgpu. Same idea, same causes. */
Application profiles are real, and they explain a lot

Drivers ship per-executable profiles that change defaults, force settings, and in some cases substitute entire shaders with hand-optimised replacements. This is why renaming your executable can change performance, why a driver update can alter behaviour with no change on your side, and why benchmarking against a shipped game tells you about the profile as much as the hardware. When something behaves differently on one vendor for no reason you can find, this is a real candidate.

Mesa is the best code to read if you want to see this for real: src/amd/vulkan (RADV) is a complete, readable Vulkan driver, and drivers/gpu/drm/amdgpu is a complete kernel driver for the same hardware. Between them they contain every idea in this chapter, in code you can build and instrument — which is a rare thing for hardware this complex.

# Look at what the driver is doing on a Linux box.

$ lsmod | grep -E 'amdgpu|i915|nouveau'
$ dmesg | grep -i drm
[drm] amdgpu kernel modesetting enabled.
[drm] Initialized amdgpu 3.57.0 for 0000:03:00.0 on minor 0

# Every GPU client, and what it is using:
$ sudo cat /sys/kernel/debug/dri/0/clients
$ sudo cat /sys/kernel/debug/dri/0/amdgpu_gem_info
$ sudo cat /sys/kernel/debug/dri/0/amdgpu_vm_info    # page tables

# The ring buffers - the actual submission queues:
$ sudo cat /sys/kernel/debug/dri/0/amdgpu_ring_gfx | head

# A GPU hang, after the fact:
$ sudo cat /sys/kernel/debug/dri/0/amdgpu_gpu_recover
$ dmesg | grep -i 'ring gfx timeout\|GPU reset'

# Trace submissions as they happen:
$ sudo perf trace -e 'amdgpu:*' -a
$ sudo cat /sys/kernel/debug/tracing/events/amdgpu/available_filters

# And the disassembly of what your shader really became:
$ RADV_DEBUG=shaders ./app 2>shaders.txt
$ head -50 shaders.txt        # actual GCN/RDNA assembly

Where this track sits

You have gone from "a GPU hides latency instead of reducing it" to reading the assembly a driver generated for your shader. The natural continuations are Linux kernel and drivers if you want to work on the KMD side, compilers if the shader back end is the interesting part, concurrency because a GPU is the most parallel machine you will program, and AI and large language models for the workload that now drives most GPU design decisions.
