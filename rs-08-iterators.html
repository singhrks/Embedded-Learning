Collections, iterators and closures

Rust's iterators are lazy, composable and compile to the same loop you would write by hand — usually without bounds checks. On embedded they are the main reason idiomatic Rust is fast, and the main reason it needs no heap.

The Iterator trait

One trait with one required method, from which the entire iterator ecosystem is generated. Implementing it yourself once is the fastest way to stop finding iterators magical.

    trait Iterator {
        type Item;
        fn next(&mut self) -> Option<Self::Item>;

        // ...and about seventy provided methods, all built
        // on next()
    }

/* THAT IS THE WHOLE INTERFACE. Implement `next` and you get
   map, filter, zip, take, fold, sum and everything else for
   free.                                                    */

    struct Countdown(u32);

    impl Iterator for Countdown {
        type Item = u32;
        fn next(&mut self) -> Option<u32> {
            if self.0 == 0 { None }
            else { self.0 -= 1; Some(self.0 + 1) }
        }
    }

    for x in Countdown(3) { print!("{x} "); }   // 3 2 1
    let v: Vec<u32> = Countdown(3).collect();
    let s: u32 = Countdown(100).filter(|x| x % 3 == 0).sum();

/* THREE WAYS TO ITERATE A COLLECTION, and choosing wrongly
   is the commonest early mistake:                          */

    for x in &v      { }        // x: &T        - borrows
    for x in &mut v  { }        // x: &mut T    - borrows
                                //                mutably
    for x in v       { }        // x: T         - CONSUMES v

    v.iter()                    // -> &T
    v.iter_mut()                // -> &mut T
    v.into_iter()               // -> T, consumes

/* `for x in v` MOVES v. If you use v afterwards, the error
   is "use of moved value" and the fix is `&v`.          */

Adapters and consumers

Adapters are lazy and consumers are what actually drive the loop. That distinction explains both the performance and the surprises.

/* ADAPTERS are lazy - they build a new iterator and do
   nothing until consumed.                                  */

    .map(|x| x * 2)
    .filter(|x| *x > 0)
    .filter_map(|x| x.checked_mul(2))   // filter + map, on
                                        // Option
    .flat_map(|x| x.iter())
    .flatten()                          // Iterator<Iterator>
                                        // -> Iterator
    .take(5)  .skip(5)
    .take_while(|x| *x < 10)
    .skip_while(|x| *x < 10)
    .step_by(2)
    .chain(other)                       // concatenate
    .zip(other)                         // pairs; stops at the
                                        // shorter
    .enumerate()                        // (index, item)
    .rev()                              // needs
                                        // DoubleEndedIterator
    .peekable()                         // .peek() without
                                        // consuming
    .windows(3)   .chunks(4)            // on SLICES, not
                                        // iterators
    .scan(state, f)                     // stateful map
    .inspect(|x| println!("{x:?}"))     // debugging, no
                                        // effect

/* CONSUMERS drive the whole chain: */
    .collect::<Vec<_>>()
    .sum::<i32>()   .product()
    .count()  .last()  .nth(3)
    .min()  .max()  .min_by_key(|x| x.len())
    .fold(init, |acc, x| acc + x)
    .try_fold(init, |acc, x| acc.checked_add(x))
    .reduce(|a, b| a.max(b))            // fold with no init
    .any(|x| x > 0)   .all(|x| x > 0)   // SHORT-CIRCUIT
    .find(|x| pred(x))   .position(|x| pred(x))
    .for_each(|x| do_it(x))
    .partition(|x| pred(x))             // into two
                                        // collections
    .unzip()

                                                // happens
    let first = it.take(1).collect::<Vec<_>>(); // ONE call to
                                                // expensive
/* And short-circuiting consumers stop early:               */

/* COLLECT IS POLYMORPHIC in its target: */

    let s: String                = chars.collect();
    let m: HashMap<K, V>         = pairs.collect();
    let r: Result<Vec<i32>, E>   = results.collect();  // ch. 07

Why iterators beat index loops

An index loop needs a bounds check per access, and the compiler can only remove it if it can prove the index is in range. An iterator is the proof — it never produces an out-of-range index — so there is nothing to check. The result is that a.iter_mut().zip(b).for_each(|(x, y)| *x += y) vectorises and for i in 0..n { a[i] += b[i] } may not. On embedded this is the difference between idiomatic and fast, and it is the same code.

Closures

Closures are where ownership and borrowing meet iterators, and the three closure traits are exactly the three ways a closure can relate to what it captures.

    let add = |a, b| a + b;
    let double = |x: i32| -> i32 { x * 2 };

    let factor = 3;
    let scale = |x| x * factor;         // CAPTURES factor

/* THREE TRAITS, by what the closure does with its captures:

     FnOnce   consumes them - callable once
     FnMut    mutates them  - callable repeatedly, needs
              &mut
     Fn       only reads them - callable repeatedly, from &

   Every closure implements FnOnce; those that do not consume
   also implement FnMut; those that do not mutate also
   implement Fn. So `Fn: FnMut: FnOnce`.

    fn call_once<F: FnOnce()>(f: F) { f(); }
    fn call_many<F: FnMut()>(mut f: F) { f(); f(); }
    fn call_shared<F: Fn()>(f: &F) { f(); f(); }

/* CAPTURE MODE IS INFERRED - by reference if that suffices,
   by mutable reference if needed, by value if required.
   `move` forces capture by value:                        */

    let data = vec![1, 2, 3];
    let closure = move || println!("{data:?}");
    // data is MOVED into the closure - required for
    // thread::spawn (chapter 16), because the closure may
    // outlive this scope

/* A CLOSURE IS A STRUCT with one field per capture, plus an
   impl of the call trait - exactly like a C++ lambda
   (C++ chapter 09). A closure capturing nothing is
   zero-sized and coerces to a plain function pointer:    */

    let f: fn(i32) -> i32 = |x| x + 1;
    register_callback(f);       // usable as a C callback
                                // (chapter 15)

/* PASSING CLOSURES:
     fn f<F: Fn(u32)>(cb: F)            // generic - INLINED,
                                        // zero cost
     fn f(cb: &dyn Fn(u32))             // trait object - an
                                        // indirect call
     fn f(cb: Box<dyn Fn(u32)>)         // heap - avoid on
                                        // embedded

   The first is what you want. The same static-versus-dynamic
   trade as C++'s template parameter versus std::function
   (C++ chapter 14).                                       */

   the capacity in the type (chapter 06's const generics): */

    use heapless::Vec;

    let mut v: Vec<u8, 64> = Vec::new();
    v.push(1).unwrap();                 // Result - it can be
                                        // FULL
    v.extend_from_slice(&[2, 3])?;
    let s: &[u8] = &v;                  // derefs to a slice
    for x in &v { }                     // iterates like Vec

    let mut s: String<32> = String::new();
    write!(s, "value: {}", x).ok();     // core::fmt::Write

    use heapless::spsc::Queue;
    static mut Q: Queue<Event, 16> = Queue::new();
    let (mut prod, mut cons) = unsafe { Q.split() };
    // prod goes to the ISR, cons to the main loop -
    // lock-free, no critical section (chapter 16)

/* THE KEY DIFFERENCE FROM std: push returns Result, because
   a fixed-capacity container can be full. That is the
   BOUNDED FAILURE you want on embedded, instead of an
   allocation that might fail or a reallocation that costs
   unpredictable time.                                     */

Slices

Slices are the workhorse type of systems Rust — a pointer and a length, with bounds checking — and they are how you pass buffers around without copying them.

    let a = [1, 2, 3, 4, 5];
    let s: &[i32] = &a;
    let mid = &a[1..4];         // [2, 3, 4]
    let head = &a[..2];
    let tail = &a[2..];

/* A SLICE IS A FAT POINTER - a pointer and a length, 16
   bytes. Exactly std::span (C++ chapter 08), and the same
   advice: take &[T] in parameters, not &Vec<T>.

/* THE METHODS worth knowing: */
    s.len()  s.is_empty()  s.first()  s.last()
    s.get(i)                        // Option - NO PANIC
    s.split_at(mid)  s.split_at_mut(mid)
    s.chunks(n)  s.chunks_exact(n)  s.windows(n)
    s.iter().rev()
    s.contains(&x)  s.starts_with(&pre)
    s.binary_search(&x)             // Result<index,
                                    // insertion_point>
    s.sort()  s.sort_unstable()     // unstable does NOT
                                    // allocate - prefer it
    s.copy_from_slice(&other)       // lengths must MATCH
    s.fill(0)
    s.rotate_left(n)
    s.split_first()  s.split_last()

/* PARSING A BUFFER, zero-copy: */
    fn parse(buf: &[u8]) -> Option<(&[u8; 4], &[u8])> {
        let (h, rest) = buf.split_first_chunk::<4>()?;
        Some((h, rest))
    }
/* No allocation, no copying, and the lifetime ties the
   result to the buffer (chapter 04).

/* AND THE BYTE CONVERSIONS, which embedded code needs
   constantly: */
    u32::from_le_bytes(bytes.try_into().ok()?)

   memcpy-and-hope, or the pointer cast that is undefined

The generated code

The claim that iterator chains compile to the same code as a hand-written loop is testable, and worth testing rather than believing.

/* --- A CHAIN COMPILES TO ONE LOOP --- */
    fn sum_evens(v: &[i32]) -> i32 {
        v.iter().filter(|x| *x % 2 == 0).sum()
    }
/* -O2 aarch64: one loop, no closure objects, no
   intermediate collection - and it vectorises. The
   adapters are structs whose next() methods inline into
   one another completely.

/* --- BOUNDS CHECKS DISAPPEAR --- */
    fn add_indexed(a: &mut [i32], b: &[i32]) {
        for i in 0..a.len() { a[i] += b[i]; }
                                // b[i] IS bounds-checked -
                                // the compiler cannot prove
                                // b is long enough
    }
    fn add_iter(a: &mut [i32], b: &[i32]) {
        for (x, y) in a.iter_mut().zip(b) { *x += *y; }
                                // NO checks - zip stops at
                                // the shorter
    }
/* The second is shorter, safer AND faster. That combination
   is unusual and worth internalising.

/* --- VERIFY IT --- */
    cargo asm my_crate::sum_evens --rust
    cargo bloat --release -n 20
    # or godbolt with the Rust compiler

/* --- AND THE ONE THING TO WATCH --- */
    let v: Vec<i32> = it.collect();     // ALLOCATES
    let n = it.count();                 // does not
/* `collect` is where a chain stops being free. On embedded,
   collect into a heapless::Vec (which returns Result), or
   consume with fold/sum/for_each and never materialise the
   intermediate at all.                                    */
