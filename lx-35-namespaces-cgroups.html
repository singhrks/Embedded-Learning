Namespaces and cgroups: the mechanism behind containers

"Container" names a way of running software, not a kernel feature — there is no struct container anywhere in Linux. What actually exists, and what chapter 39's clone() flags already hinted at, are two independent, much older mechanisms: namespaces, which control what a process can see, and cgroups, which control how much of the machine it can use. Docker, Kubernetes and every other container runtime are built entirely out of these two primitives.

Namespaces: giving a process its own view of the world

A namespace takes something that is normally global to the whole machine — the list of processes, the network interfaces, the mount table — and gives a group of processes their own private copy of it. To the processes inside, it simply looks like they are alone on the machine.

   A NAMESPACE WRAPS ONE KIND OF GLOBAL KERNEL STATE AND
   MAKES IT PER-NAMESPACE INSTEAD OF SYSTEM-WIDE. A process
   inside a namespace sees ONLY that namespace's version of
   whatever it wraps - and, critically, has NO WAY TO EVEN
   OBSERVE that other versions exist, unless it has a
   privileged way to cross the boundary deliberately.

     PID       its own process tree - PID 1 inside the
               namespace is a real, ordinary process outside
               it, just with a different pid number on each
               side. A process cannot see or signal processes
               outside its own PID namespace at all.

     NET       its own network interfaces, routing table,
               firewall rules, port numbers. Two containers
               can both bind port 80 with zero conflict,
               because each has its OWN loopback and its own
               idea of "port 80" entirely.

     MNT       its own mount table. Mounting or unmounting a
               filesystem inside the namespace is invisible
               outside it - this is what makes a container's
               filesystem look self-contained even though it
               is, underneath, just directories and bind
               mounts on the host.

     UTS       its own hostname and NIS domain name -
               "UTS" is a historical name (Unix Timesharing
               System) for what `uname` reports.

     IPC       its own System V IPC objects and POSIX message
               queues - so two containers' semaphores or
               shared memory segments never collide by id.

     USER      its own mapping of user and group IDs - a
               process can be UID 0 (root) INSIDE the
               namespace while being an entirely unprivileged
               UID on the host - the single most important
               namespace for container SECURITY, since it
               means "root in the container" does not mean
               root on the machine.

     CGROUP    its own view of the cgroup hierarchy (below),
               so a process inside sees paths relative to its
               own cgroup root rather than the host's full
               tree.
A container is just a process with an unusual set of namespaces

There is no moment where a "container" is created as a distinct kernel object — a container runtime calls clone() with a combination of CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWUSER (the same flags chapter 39 introduced for threads, repurposed here for isolation instead of sharing), and the resulting process is what gets called a container. Everything that makes a container feel like a separate machine — its own process list, its own network stack, its own root filesystem — is a direct, mechanical consequence of which namespaces that one clone() call created.

Seeing namespaces from outside

Namespaces are not hidden. Every process advertises which ones it belongs to, and comparing two processes tells you immediately whether they share a given view — which is also exactly how the tooling enters a container.

# Every process's namespace membership is visible as symlinks:
ls -la /proc/PID/ns/
    pid -> pid:[4026532345]
    net -> net:[4026532210]
    mnt -> mnt:[4026531840]
    ...
# Two processes in the SAME namespace show the SAME inode
# number after the colon - that number, not the symlink text,
# is the namespace's real identity.

# Two processes are in the same PID namespace exactly when:
readlink /proc/PID1/ns/pid
readlink /proc/PID2/ns/pid
# ...print the same inode number.

# Enter an existing process's namespaces directly - this is
# literally how `docker exec` and `nsenter` work, no special
# container-aware API involved:
nsenter --target PID --pid --net --mount --uts -- /bin/bash

unshare --pid --net --mount --fork /bin/bash
# Creates a new set of namespaces for a fresh process directly
# from the shell - a minimal, dependency-free way to see
# namespace isolation without any container tooling installed.

cgroups: bounding how much a process may use

Namespaces control what a process can see, and that is only half of isolation. A process with a completely private view of the system can still consume all of its memory and CPU, so a second, entirely separate mechanism limits how much it may actually use.

   NAMESPACES ANSWER "WHAT CAN THIS PROCESS SEE." CGROUPS
   (control groups) ANSWER A COMPLETELY DIFFERENT QUESTION:
   "HOW MUCH OF THE MACHINE'S ACTUAL RESOURCES CAN IT USE."
   A process can be fully namespace-isolated and still starve
   every other process on the machine of CPU or memory
   without a cgroup limiting it - the two mechanisms are
   independent and a container runtime always uses both.

   CGROUPS ARE ORGANISED AS A HIERARCHY, mounted as a
   filesystem (cgroup v2, the current unified design):

     /sys/fs/cgroup/
       my-container/
         cgroup.procs        <- PIDs that are members
         memory.max           <- hard memory limit
         memory.current        <- current usage
         cpu.max               <- CPU quota, e.g. "50000 100000"
                                   (50ms of CPU per 100ms period
                                   - a two-CPU-core ceiling,
                                   expressed as a ratio, not a
                                   raw core count)
         io.max                <- per-device I/O bandwidth cap
         pids.max               <- maximum number of processes
                                   (prevents a fork-bomb)

   LIMITS ARE INHERITED DOWN THE TREE: a child cgroup can only
   be MORE restrictive than its parent, never less - the
   kernel enforces this structurally, so a runaway container
   cannot grant itself more resources than its own parent
   group was ever allowed.
# Create a cgroup and put the CURRENT shell into it:
mkdir /sys/fs/cgroup/my-limit
echo $$ > /sys/fs/cgroup/my-limit/cgroup.procs
echo "50M" > /sys/fs/cgroup/my-limit/memory.max

# Every process this shell now starts inherits the same
# cgroup automatically - and hitting the memory limit does
# NOT get -ENOMEM back the ordinary way; the kernel invokes
# its OOM killer scoped to just this cgroup, killing a
# process inside it specifically, leaving the rest of the
# machine untouched. This is the real mechanism behind a
# container being "OOM-killed" while its host keeps running
# normally.

cat /sys/fs/cgroup/my-limit/memory.events
    oom 1
    oom_kill 1

systemd-cgls              # see the whole cgroup tree, readable
systemd-cgtop              # live per-cgroup resource usage,
                           # roughly cgroup's answer to `top`

Namespaces plus cgroups equals what "container" means

A container runtime's actual job, stripped of all its tooling and image formats, is exactly two kernel calls worth of work: create a process with the right set of CLONE_NEW* namespace flags so it sees its own PID tree, network stack and filesystem, and place that process into a cgroup that bounds its CPU, memory and I/O. Everything else — image layers, networking bridges, orchestration — is built on top of, and ultimately reduces to, these two independent mechanisms working together on one ordinary Linux process.
