Building, signing and packaging a TA

A trusted application is delivered as a signed binary sitting in the normal world's filesystem, where an attacker can replace it at will. The signature is the only thing that makes that acceptable, and understanding the format, the build and the key management is what separates a demo from something shippable.

The project layout

A trusted application is a small project with a prescribed structure, and following it is what lets the supplied build machinery do the work.

   Copy optee_examples/hello_world and rename. Every OP-TEE
   project has this shape and there is no reason to invent
   another.

   my_project/
     Makefile              builds both halves
     host/
       Makefile
       main.c              the client (chapter 11)
     ta/
       Makefile            2 lines - includes the dev kit
       sub.mk              lists the source files
       user_ta_header_defines.h    flags, sizes, UUID (ch. 13)
       my_ta.c             the five entry points (ch. 12)
       include/
         my_ta.h           SHARED between host and TA:
                           the UUID and the command IDs
     README.md

   my_ta.h is the interface contract. Both sides include it, so
   a command ID can never drift between them:

     #define TA_MY_UUID \
        { 0x12345678, 0x1234, 0x1234, \
          { 0x12, 0x34, 0x12, 0x34, 0x12, 0x34, 0x12, 0x34 } }

     #define TA_CMD_SIGN     0
     #define TA_CMD_VERIFY   1
     #define TA_CMD_GEN_KEY  2
# Generate a UUID. Never invent one by hand, and never reuse
# an example's - two TAs with the same UUID cannot coexist.
$ uuidgen
7f2e9c1a-3b4d-4e5f-8a9b-0c1d2e3f4a5b

# In the C form OP-TEE wants:
$ python3 - <<'EOF'
import uuid
u = uuid.uuid4()
b = u.bytes
print(u)
print("#define TA_MY_UUID \\")
print("\t{ 0x%08x, 0x%04x, 0x%04x, \\" % (u.time_low, u.time_mid,
      u.time_hi_version))
print("\t  { " + ", ".join("0x%02x" % c for c in b[8:]) + " } }")
EOF

The makefiles

The build is driven by a few short files that hook into the main tree, and knowing which does what saves fighting the system when you add sources.

# ta/Makefile - genuinely this short. All the work is in the
# dev kit.
CFG_TEE_TA_LOG_LEVEL ?= 3
CPPFLAGS += -DCFG_TEE_TA_LOG_LEVEL=$(CFG_TEE_TA_LOG_LEVEL)

BINARY = 7f2e9c1a-3b4d-4e5f-8a9b-0c1d2e3f4a5b

-include $(TA_DEV_KIT_DIR)/mk/ta_dev_kit.mk

ifeq ($(wildcard $(TA_DEV_KIT_DIR)/mk/ta_dev_kit.mk), )
clean:
	@echo 'TA_DEV_KIT_DIR is not correctly defined' && false
endif

# BINARY must be the UUID. The output is $(BINARY).ta and
# OP-TEE looks it up by that name. A mismatch between BINARY
# and TA_UUID in the header means the file exists and is never
# found.


# ta/sub.mk
global-incdirs-y += include
srcs-y += my_ta.c
srcs-y += crypto_helpers.c
# cflags-my_ta.c-y += -Wno-unused-parameter


# host/Makefile
CC      ?= $(CROSS_COMPILE)gcc
CFLAGS  += -Wall -I../ta/include -I$(TEEC_EXPORT)/include
LDADD   += -lteec -L$(TEEC_EXPORT)/lib

BINARY = my_client
OBJS = main.o

.PHONY: all clean
all: $(BINARY)

$(BINARY): $(OBJS)
	$(CC) -o $@ $< $(LDADD)

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f $(OBJS) $(BINARY)


# Top-level Makefile
export V ?= 0
OUTPUT_DIR := $(CURDIR)/out

.PHONY: all
all: ta host

.PHONY: ta
ta:
	$(MAKE) -C ta CROSS_COMPILE=$(TA_CROSS_COMPILE) \
		LDFLAGS=""

.PHONY: host
host:
	$(MAKE) -C host CROSS_COMPILE=$(HOST_CROSS_COMPILE) \
		--no-builtin-variables

.PHONY: clean
clean:
	$(MAKE) -C ta clean
	$(MAKE) -C host clean
# Build it.
$ export TA_DEV_KIT_DIR=$HOME/optee/optee_os/out/arm-plat-vexpress/export-ta_arm64
$ export TEEC_EXPORT=$HOME/optee/optee_client/out/export/usr
$ export TA_CROSS_COMPILE=aarch64-linux-gnu-
$ export HOST_CROSS_COMPILE=aarch64-linux-gnu-
$ make

$ ls ta/*.ta host/my_client
ta/7f2e9c1a-3b4d-4e5f-8a9b-0c1d2e3f4a5b.ta
host/my_client

# Install into the image:
$ cp ta/*.ta   ~/optee/out-br/target/lib/optee_armtz/
$ cp host/my_client ~/optee/out-br/target/usr/bin/
$ cd ~/optee/build && make buildroot run-only

# package so it is rebuilt automatically. See

What a .ta file is

The output is not a plain binary but a signed container the loader can verify. Its structure explains what is authenticated and what is not.

   +--------------------------------------------------------+
   |  shdr - the signed header                              |
   |    magic       0x4f545348  "OTSH"                      |
   |    img_type    SHDR_TA / SHDR_BOOTSTRAP_TA /           |
   |                SHDR_ENCRYPTED_TA                       |
   |    img_size                                            |
   |    algo        e.g. RSASSA_PKCS1_PSS_MGF1_SHA256       |
   |    hash_size                                           |
   |    sig_size                                            |
   +--------------------------------------------------------+
   |  hash          SHA-256 of everything below             |
   +--------------------------------------------------------+
   |  signature     RSA/ECDSA over that hash                |
   +--------------------------------------------------------+
   |  (bootstrap TA only) the UUID and TA version           |
   +--------------------------------------------------------+
   |  the ELF - the actual TA, linked against the dev kit   |
   +--------------------------------------------------------+

   VERIFICATION, inside OP-TEE, before a single instruction of
   the TA runs:

     1. tee-supplicant delivers the file (chapter 9).
     2. OP-TEE reads shdr and checks magic and sizes.
     3. It hashes the ELF and compares with hash.
     4. It verifies the signature over that hash, using a
        public key COMPILED INTO OP-TEE.
     5. For a bootstrap TA, it checks the UUID inside matches
        the UUID that was requested - so a valid TA cannot be
        substituted for a different valid TA.
     6. Only then is the ELF loaded and mapped.

   Failure at any step: TEEC_ERROR_SECURITY (0xFFFF000F).

   NOTE WHAT IS NOT PROTECTED: confidentiality. A plain .ta is
   readable by anyone with the filesystem. If the TA's code is
   itself sensitive, you need SHDR_ENCRYPTED_TA.

Signing, and the key problem

The default signing key is a development key present in the public source tree, which means an unmodified build verifies nothing meaningful. Replacing it is a required production step.

# The default: every OP-TEE tree ships one key, and it signs
# every TA built in that tree.
$ ls -l optee_os/keys/default_ta.pem
-rw-r--r-- 1 user user 1704 default_ta.pem

# THIS KEY IS PUBLIC. It is in the git repository. A device
# whose OP-TEE trusts it will load any TA anyone builds.

# Use your own:
$ openssl genrsa -out my_ta_key.pem 2048
$ openssl rsa -in my_ta_key.pem -pubout -out my_ta_pub.pem

$ make -C optee_os TA_SIGN_KEY=$PWD/my_ta_key.pem ...
# OP-TEE embeds the PUBLIC half; the private half signs TAs.

# Sign an existing unsigned ELF by hand:
$ python3 optee_os/scripts/sign_encrypt.py sign \
    --key my_ta_key.pem \
    --uuid 7f2e9c1a-3b4d-4e5f-8a9b-0c1d2e3f4a5b \
    --in ta.elf --out ta.ta

# Inspect one you were given:
$ python3 optee_os/scripts/sign_encrypt.py display --in some.ta

# THE PRODUCTION PATTERN: the private key never leaves an HSM.
# sign_encrypt.py supports a two-step flow for exactly this:
#
#   1. produce the digest to be signed
$ python3 scripts/sign_encrypt.py digest \
    --key my_ta_pub.pem --uuid $UUID --in ta.elf --dig ta.dig
#   2. sign the digest elsewhere - HSM, signing service, an
#      air-gapped machine
$ openssl pkeyutl -sign -inkey my_ta_key.pem \
    -in ta.dig -out ta.sig \
    -pkeyopt digest:sha256 -pkeyopt rsa_padding_mode:pss \
    -pkeyopt rsa_pss_saltlen:digest
#   3. staple the signature on
$ python3 scripts/sign_encrypt.py stitch \
    --key my_ta_pub.pem --uuid $UUID \
    --in ta.elf --sig ta.sig --out ta.ta

# The build machine never holds the private key. This is the
# difference between a signing story and a signing key sitting
# in CI's environment variables.
Three ways TA signing goes wrong in the field

Shipping with the default key — anyone can load a TA. Key in the repository — same, once the repository leaks. No revocation plan — the public key is compiled into OP-TEE, which is in a signed boot image, so rotating it means a firmware update. Decide the rotation story before the first device ships, not after a key is compromised.

Encrypted TAs

Signing proves authenticity; it does not provide confidentiality. Encrypting a trusted application additionally protects its contents from inspection, which matters if the logic itself is sensitive.

# When the TA's own code is the secret - a proprietary
# algorithm, an anti-tamper routine, an obfuscated licence
# check.

$ make -C optee_os \
    CFG_ENCRYPT_TA=y \
    TA_ENC_KEY=0123456789abcdef0123456789abcdef

$ python3 scripts/sign_encrypt.py sign \
    --key my_ta_key.pem --enc-key $TA_ENC_KEY \
    --enc-key-type SHDR_ENC_KEY_DEV_SPECIFIC \
    --uuid $UUID --in ta.elf --out ta.ta

# Key types:
#   SHDR_ENC_KEY_DEV_SPECIFIC   derived from the device's
#                               hardware unique key. The .ta is
#                               then bound to ONE device and
#                               cannot be moved.
#   SHDR_ENC_KEY_CLASS_WIDE     a key shared by a product
#                               class. Convenient; one
#                               extracted key breaks the whole
#                               class.

# The TA is encrypted at rest and decrypted inside OP-TEE
# during load. It is still in cleartext in TA_RAM while
# running, so this defends against extraction from the
# filesystem, not against an attacker who has already
# compromised the secure world.

# Weigh it honestly: encryption complicates your build and
# your field-update story, and it protects only against
# reverse engineering. Most TAs do not need it. Signing is
# mandatory; encryption is a business decision.

Confirming it worked

Confirming that the device actually rejects an unsigned or wrongly-signed application is the test that proves the mechanism is switched on.

# On the target:
$ ls -l /lib/optee_armtz/
-rw-r--r-- 1 root root 24576 7f2e9c1a-3b4d-4e5f-8a9b-0c1d2e3f4a5b.ta

# Filename MUST equal the UUID. Check:
$ python3 sign_encrypt.py display --in /path/to/ta.ta
uuid: 7f2e9c1a-3b4d-4e5f-8a9b-0c1d2e3f4a5b
img_type: SHDR_BOOTSTRAP_TA
algo: TEE_ALG_RSASSA_PKCS1_PSS_MGF1_SHA256
size: 22016

# Run the client and watch the secure console:
D/TC:0 0 ree_fs_ta_open:...  TA 7f2e9c1a-... loaded
D/TC:0 0 shdr_verify_signature:...  OK
I/TA:  my TA started

# A signature failure looks like:
E/TC:0 0 shdr_verify_signature:...  Signature verification failed
E/TC:0 0 ree_fs_ta_open:...  TEE_ERROR_SECURITY
# and the client sees 0xFFFF000F.
