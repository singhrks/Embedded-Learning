Why DX12, Vulkan and Metal exist

The explicit APIs are harder to use than the ones they replaced, and that is the point. They exist because the old drivers were doing enormous amounts of guessing on your behalf — badly, on one thread, at unpredictable moments. This chapter is what they took away and what they gave back.

What the old drivers were doing

   DX11 / OpenGL: you call a function, and the driver decides
   everything.

     ctx->PSSetShaderResources(0, 1, &srv);
     ctx->Draw(3, 0);

   Behind that Draw the driver must:

     * check every piece of state you set and work out whether
       a new pipeline compile is needed. If so, COMPILE A
       SHADER, right now, mid-frame. -> a stutter you cannot
       predict or control.
     * track the lifetime of every resource you have ever
       bound, to know when it is safe to free or overwrite.
     * insert synchronisation between GPU operations by
       guessing your intent from the order of calls.
     * VALIDATE everything, every call, in the shipping
       driver.
     * do all of this on ONE THREAD, because the context is
       not thread-safe.

   THE RESULT
     * a driver thread that is the bottleneck on a 16-core
       machine
     * frame-time spikes with no visible cause
     * per-vendor "optimisations" that recognise specific
       games and substitute different shaders - genuinely, by
       executable name
     * ~1-2 us of CPU per draw call, capping you at a few
       thousand draws per frame

   THE EXPLICIT APIs' ANSWER: you already know your intent.
   Say it up front, once, and the driver stops guessing.

The trade, stated honestly

You get predictable frame times, multi-threaded submission, and roughly ten times the draw calls. You pay with perhaps five times the code for a first triangle, whole new bug classes (a missed barrier is a race between GPU stages), and the obligation to do your own memory management. For a small project or a tool, DX11 or OpenGL is still the right choice. For anything shipping at scale, the explicit APIs won for good reasons.

The five concepts they all share

   Learn these once; the three APIs differ mainly in spelling.

   1. DEVICE and QUEUES
        the device is the GPU. Queues are where work goes -
        typically GRAPHICS, COMPUTE and COPY, which run
        concurrently on separate hardware engines.

   2. COMMAND LISTS / BUFFERS
        you RECORD commands into a list, on any thread, and
        SUBMIT it later. Recording touches no GPU state, so
        eight threads can record eight lists at once.
        (chapter 13)

   3. PIPELINE STATE OBJECTS
        every piece of state that could affect shader
        compilation - shaders, blend, depth, rasteriser,
        vertex layout, render-target formats - baked into one
        immutable object, created at load time.
        (chapter 15)

   4. DESCRIPTORS and DESCRIPTOR HEAPS
        a descriptor is a small opaque struct describing a
        resource. They live in heaps; shaders index into them.
        Binding becomes "point at an offset" instead of "tell
        the driver about this texture".
        (chapter 14)

   5. EXPLICIT SYNCHRONISATION
        FENCES     CPU waits for GPU
        BARRIERS   GPU waits for GPU, and transitions a
                   resource between usages
        This is the part that is genuinely hard, and the part
        the debug layer will save you on.
        (chapter 16)

This track uses DX12 from here on. It is the middle of the three in complexity, it pairs with the Windows track, and its concepts map onto Vulkan and Metal almost one-to-one. Where they diverge in a way that matters, the chapters say so.

What multi-threading actually buys

/* THE OLD MODEL - one thread does everything. */

  main thread:  cull -> for each object: set state, Draw
                     -> the DRIVER thread then translates all
                        of that into GPU commands, serially

  On a 16-core machine you are using 2 of them, and the
  driver thread is the wall.

/* THE NEW MODEL - record in parallel, submit once. */

  thread 0: record shadow pass       -> command list A
  thread 1: record opaque, part 1    -> command list B
  thread 2: record opaque, part 2    -> command list C
  thread 3: record transparent + UI  -> command list D

  main:     queue->ExecuteCommandLists(4, {A, B, C, D});

/* THE RULES that make it safe:
     * one COMMAND ALLOCATOR per thread per frame-in-flight.
       Allocators are not thread-safe and cannot be reset
       while the GPU is still reading them.
     * command lists are recorded independently but EXECUTE
       IN THE ORDER YOU SUBMIT THEM.
     * resource state transitions must be consistent across
       list boundaries - the debug layer checks this, and it
       is where multi-threaded recording actually goes wrong.

   THE HONEST CAVEAT: parallel recording helps only if you
   are CPU-bound on draw submission. Many titles are GPU-bound
   and gain nothing. Measure which you are before building
   the machinery - and note that the draw-call ceiling rising
   from ~5,000 to ~50,000 changes what art can do, which is
   often the real benefit rather than frame time.          */
The debug layer is not optional

The explicit APIs removed validation from the shipping driver, so an error usually produces a device removal, a hang, or corrupted output with no message at all. The debug layer (DX12), validation layers (Vulkan) or Metal's API validation give you precise diagnostics for every mistake in this track. Develop with them on, always; the performance cost is irrelevant during development and they will save you days.

// Turn it on before creating the device - order matters.
#if defined(_DEBUG)
    ComPtr<ID3D12Debug1> dbg;
    if (SUCCEEDED(D3D12GetDebugInterface(IID_PPV_ARGS(&dbg)))) {
        dbg->EnableDebugLayer();
        dbg->SetEnableGPUBasedValidation(TRUE);   // slower,
                                                  // catches far
                                                  // more
    }
#endif

// And make errors stop the debugger where they happen:
ComPtr<ID3D12InfoQueue> iq;
if (SUCCEEDED(device.As(&iq))) {
    iq->SetBreakOnSeverity(D3D12_MESSAGE_SEVERITY_CORRUPTION, TRUE);
    iq->SetBreakOnSeverity(D3D12_MESSAGE_SEVERITY_ERROR,      TRUE);
}
