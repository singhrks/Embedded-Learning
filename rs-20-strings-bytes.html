Strings, bytes and the conversions between them

C has one string type and it is a lie — a pointer that might be NUL-terminated, might be valid, might be UTF-8. Rust has eight, each encoding a different guarantee, and the apparent complexity is the C ambiguity made explicit. Learn the table once and the rest of the language stops arguing with you.

The types, and what each one guarantees

Every one of these exists because a different caller needs a different promise. The owned/borrowed split will already be familiar from chapter 02 — it is the same distinction as Vec<T> against &[T], applied four times.

String&strValid UTF-8Text. The default
Vec<u8>&[u8]Nothing — arbitrary bytesBuffers, protocol frames, files, anything from hardware
CString&CStrNUL-terminated, no interior NULCrossing the FFI boundary (chapter 15)

   WHY OsStr EXISTS, which is the one that looks like
   over-engineering and is not:

     ON LINUX a filename is a sequence of bytes that is not
     required to be valid UTF-8. You can create one with
     `touch $'\xff\xfe'`. It is a legal filename.

     ON WINDOWS a filename is a sequence of 16-bit units
     that is not required to be well-formed UTF-16.

   NEITHER FITS IN String. A language that insisted on UTF-8
   for filenames would be unable to open files that exist.
   C "solves" this by not having the problem, because char*
   promises nothing - which is why C programs mangle such
   filenames silently.

   ---------------------------------------------------------

   AND THE ONE THAT IS NOT A STRING AT ALL:

     char  is a UNICODE SCALAR VALUE, four bytes, not a byte.
           'a' as u32 == 97, but 'é' is one char and TWO
           bytes of UTF-8.

     b'a'  is a u8 byte literal.
     b"ab" is a &[u8; 2] byte-string literal.
     c"ab" is a &CStr literal, NUL included.

   ON EMBEDDED TARGETS you will mostly want b"..." and
   &[u8], because you are moving bytes rather than text.

Why you cannot index a string

s[0] does not compile, and the reason is the single most useful thing to understand about Rust strings — it is not an ergonomic oversight, it is the encoding refusing to lie to you.

let s = "héllo";

s.len()            // 6  - BYTES, not characters
s.chars().count()  // 5  - scalar values. O(n), not O(1).

// s[0]            // does not compile. What would it return?
//                 //   a byte?      you probably meant a character
//                 //   a char?      cannot be found in O(1)

s.as_bytes()[0]    // 104 - you asked for a byte, explicitly
s.chars().next()   // Some('h') - you asked for a character

// SLICING WORKS, and panics if you cut a character in half:
&s[0..1]           // "h"  fine
// &s[0..2]        // PANIC: byte index 2 is not a char boundary
&s[0..3]           // "hé" fine - 'é' occupies bytes 1..3

/* THE THREE DIFFERENT "LENGTHS", and they are all correct
   answers to different questions:

     "héllo".len()                      6   bytes
     "héllo".chars().count()            5   scalar values
     grapheme clusters                  5   what a human
                                            would call
                                            characters

   THEY DIVERGE FURTHER THAN THAT. "é" can be written as one
   scalar value or as 'e' followed by a combining accent -
   two chars, one grapheme, and they look identical. If you
   need what a user would call a character, you need a
   crate; std deliberately does not guess.                */

/* THE RULE THAT AVOIDS ALL OF THIS: do not index into text.
   Iterate it, split it, or parse it. If you find yourself
   reaching for a byte offset in a string, you are almost
   always working with DATA rather than TEXT - so use
   &[u8] and say so.                                     */

The conversion map

Most string friction in Rust is not knowing which call goes which way. This is the whole map; the arrows that can fail are the interesting ones, because each failure corresponds to a guarantee being checked.

   &str  ──── .to_string() / .to_owned() ────>  String
   String ─── .as_str() / &s ────────────────>  &str

   &str  ──── .as_bytes() ───────────────────>  &[u8]
   &[u8] ──── str::from_utf8()  -> Result ───>  &str     (*)
   Vec<u8> ── String::from_utf8() -> Result >  String   (*)
   &[u8] ──── String::from_utf8_lossy() ─────>  Cow<str>

   &str  ──── CString::new() -> Result ──────>  CString  (**)
   &CStr ──── .to_str() -> Result ───────────>  &str     (*)
   &CStr ──── .to_bytes() ───────────────────>  &[u8]

   &str  ──── .into() / OsString::from() ────>  OsString
   &OsStr ─── .to_str() -> Option ───────────>  &str     (*)
   &Path ──── .to_str() -> Option ───────────>  &str     (*)

   (*)  fails if the bytes are not valid UTF-8
   (**) fails if there is an INTERIOR NUL byte

   ---------------------------------------------------------

   THE PATTERN: every arrow INTO a str-like type returns a
   Result or an Option, because that arrow is where a
   guarantee is being CHECKED. Every arrow out is
   infallible, because you are discarding a guarantee rather
   than acquiring one.

   THAT IS THE WHOLE DESIGN, and once you see it you can
   predict the signature of a conversion you have never used.

   ---------------------------------------------------------

   from_utf8_lossy IS THE PRAGMATIC ESCAPE HATCH: it replaces
   every invalid sequence with U+FFFD and cannot fail. Right
   for logging and diagnostics. WRONG for anything you will
   later compare, hash, or write back out - it silently
   changes the data.
The FFI mistake that compiles, runs, and corrupts

This line is wrong, and it is the single most common Rust FFI bug:

let p = CString::new(name).unwrap().as_ptr();   // DANGLING
unsafe { c_function(p) };

The CString is a temporary. It is dropped at the end of the statement, before c_function is ever called, so p points at freed memory. It usually appears to work, because the allocator has not yet reused the block — which is exactly what makes it dangerous. Bind the CString to a variable that outlives the call:

let owned = CString::new(name).unwrap();        // lives on
unsafe { c_function(owned.as_ptr()) };

The borrow checker cannot catch this because as_ptr returns a raw pointer, and raw pointers carry no lifetime. This is precisely the class of bug chapter 14 means when it says the guarantees stop at the unsafe boundary.

Choosing the types in your own signatures

The type you accept is an interface decision, and the wrong choice forces every caller to allocate. There are three rules and they cover almost everything.

// 1. TAKE &str, NOT &String. &String forces the caller to
//    have allocated one; &str accepts a literal, a slice of
//    a larger string, and a &String by deref coercion.
fn parse(input: &str) -> Result<Config, Error>      // yes
fn parse(input: &String) -> Result<Config, Error>   // no

// Same rule, same reason, for the whole family:
//    &[T] not &Vec<T>        &Path not &PathBuf

// 2. RETURN String when you built it; return &str when you
//    are handing back a piece of something the caller owns.

// 3. WHEN IT MIGHT BE EITHER, use Cow - "clone on write".
//    Borrow when nothing changed, allocate only when it did.
use std::borrow::Cow;

fn normalise(s: &str) -> Cow<'_, str> {
    if s.contains('\r') {
        Cow::Owned(s.replace('\r', ""))   // had to allocate
    } else {
        Cow::Borrowed(s)                  // no allocation
    }
}
// The common case - input is already clean - costs nothing.

// AND FOR MAXIMUM FLEXIBILITY AT AN API BOUNDARY:
fn open(path: impl AsRef<Path>) { /* ... */ }
// accepts &str, String, &Path, PathBuf, &OsStr - which is
// how std::fs::File::open works, and why it always "just
// takes what you have".

On embedded targets

Without an allocator, String, CString and OsString do not exist — they are all heap types. What remains is enough, and the constraint tends to improve the code.

   WHAT SURVIVES IN core:
     &str, str, char, &[u8], &CStr
     all the parsing and formatting on &str
     write! into anything implementing fmt::Write

   WHAT YOU REACH FOR INSTEAD OF String:
     heapless::String<N>   fixed capacity, on the stack,
                           push returns Err when full
     &mut [u8] + a cursor  the zero-dependency option
     core::write!          formatting into a fixed buffer

   ---------------------------------------------------------

   AND THE HABIT WORTH FORMING: on a microcontroller you are
   almost never handling text. You are handling FRAMES - a
   length, a command byte, a payload, a checksum. Model them
   as &[u8] and structs, not as strings, and the type system
   stops fighting you because you have finally told it the
   truth about the data.
