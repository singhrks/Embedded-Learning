TLS

Every primitive so far, assembled into a working secure channel. TLS 1.3 is the reference design for how to combine them — and the thirty years of attacks on its predecessors are the reference list of how not to.

The two layers

TLS is where nearly every primitive in this track is assembled into one protocol, which makes it the best worked example available — and the reason its failures are so instructive.

   HANDSHAKE PROTOCOL
     · negotiate the version and the cipher suite
     · exchange keys (ECDHE - chapter 13)
     · authenticate the peer (certificates - chapter 16)
     · derive the traffic keys (HKDF - chapter 10)
     · confirm the whole transcript matched

   RECORD PROTOCOL
     · fragment the byte stream into records
     · protect each with an AEAD (chapter 09)
     · number them implicitly, so reordering, deletion and
       replay are all detected

   TLS 1.3 HANDSHAKE, one round trip:

   CLIENT                                   SERVER
     ClientHello
       + supported_versions
       + key_share (X25519 pubkey)
       + signature_algorithms
       + server_name (SNI)         ------>
                                            ServerHello
                                              + key_share
                         <=== both sides now derive the
                              handshake keys; EVERYTHING
                              BELOW IS ENCRYPTED ===>
                                            {EncryptedExtensions}
                                            {Certificate}
                                            {CertificateVerify}
                                            {Finished}
                                   <------
     {Finished}                    ------>
     [Application Data]            <----->  [Application Data]

     {} = handshake-key encrypted   [] = traffic-key encrypted

   WHAT EACH MESSAGE IS FOR:
     key_share            ephemeral DH, so FORWARD SECRECY is
                          not optional
     Certificate          the server's identity
     CertificateVerify    a SIGNATURE OVER THE TRANSCRIPT -
                          this is what binds the certificate
                          to this exchange, and stops the
                          man in the middle
     Finished             a MAC over the whole transcript,
                          from both sides - this is what kills
                          downgrade attacks

What TLS 1.3 removed

The current version removed a great deal, and what it removed is as informative as what it kept: nearly every option deleted had been the basis of a practical attack.

/* The most important design work in TLS 1.3 was DELETION.
   Each removal closed a family of attacks.               */

   REMOVED                        ATTACK IT ENABLED
   ---------------------------------------------------------
   RSA key transport              no forward secrecy;
                                  Bleichenbacher/ROBOT
                                  (chapter 12)
   Static DH / static ECDH        no forward secrecy
   CBC mode ciphersuites          BEAST, Lucky13, padding
                                  oracles (chapter 05)
   RC4                            biased keystream (ch. 06)
   3DES                           SWEET32 birthday bound
   MD5, SHA-1 signatures          collisions (chapter 07)
   Compression                    CRIME, BREACH
   Renegotiation                  the 2009 renegotiation
                                  injection flaw
   Custom DH groups               Logjam (chapter 13)
   Export ciphersuites            FREAK, Logjam
   Non-AEAD ciphers               everything above

   WHAT REMAINS: FIVE cipher suites, all AEAD, all forward
   secret.
       TLS_AES_128_GCM_SHA256
       TLS_AES_256_GCM_SHA384
       TLS_CHACHA20_POLY1305_SHA256
       TLS_AES_128_CCM_SHA256          <-- for constrained
       TLS_AES_128_CCM_8_SHA256            devices

   THE LESSON GENERALISES: A PROTOCOL'S SECURITY IS BOUNDED
   BY ITS WEAKEST NEGOTIABLE OPTION. Every algorithm you keep
   "for compatibility" is an algorithm an attacker will try
   to force you into. Delete, do not deprecate.

/* AND ON THE KEY SCHEDULE: TLS 1.3 derives every key with
   HKDF, with a distinct label for each purpose:
       "c hs traffic", "s hs traffic",
       "c ap traffic", "s ap traffic",
       "exp master",   "res master"
   Textbook key separation (chapter 10), including separate
   keys per direction (chapter 08).                      */

The record layer

Beneath the handshake, the record layer is what actually carries data — and its framing has been the source of vulnerabilities independent of the cryptography it protects.

/* Each record is protected with the negotiated AEAD.     */

    struct {
        ContentType type;          /* always 23
                                      "application_data" on
                                      the wire in 1.3 - the
                                      real type is INSIDE
                                      the encrypted body */
        uint16 legacy_version;     /* always 0x0303 */
        uint16 length;
        opaque encrypted_record[length];
    } TLSCiphertext;

/* THE NONCE IS NOT TRANSMITTED. It is derived:
        nonce = static_iv XOR sequence_number
   The sequence number is implicit and increments per record.

   THIS IS AN ELEGANT PIECE OF DESIGN, and it does three
   things at once:
     · guarantees nonce uniqueness without state on the wire
       (chapter 09's cardinal rule, enforced structurally)
     · makes REPLAY impossible - a replayed record decrypts
       under the wrong nonce and fails the tag check
     · makes REORDERING and DELETION detectable for free

/* RECORD SIZE AND THE KEY UPDATE:
     max 2^14 bytes of plaintext per record.
     KeyUpdate messages rotate the traffic keys mid-session,
     so the AEAD limits (chapter 09) never bite on a
     long-lived connection.

/* PADDING: TLS 1.3 lets you append zero bytes inside the
   encrypted body to hide the true length. Nobody uses it,
   and TRAFFIC ANALYSIS remains a real leak - the size and
   timing of your records still describe what you are doing.
   For a device that sends distinguishable commands, pad to a
   fixed size.                                            */
0-RTT is not free

TLS 1.3 lets a resuming client send application data in its first flight. That data has no forward secrecy against a compromise of the resumption secret, and it can be replayed by an attacker who captured it. Only send idempotent requests in early data, and only enable it if the latency actually matters to your product.

DTLS, and TLS on constrained devices

Running TLS over an unreliable transport requires solving problems TCP otherwise hides, which matters for embedded and real-time systems that cannot afford a stream protocol.

/* --- DTLS 1.3: TLS over UDP --- */
    Needed because TLS assumes a reliable ordered stream, and
    UDP gives neither.
      · explicit sequence numbers in the record header
      · a REPLAY WINDOW (a sliding bitmap) instead of a strict
        counter
      · retransmission and reassembly of handshake messages
      · a HELLORETRYREQUEST COOKIE, so the server does no work
        and holds no state until the client proves it can
        receive at its claimed address - AMPLIFICATION DDOS
        PROTECTION

    USED BY: CoAP over DTLS, WebRTC, QUIC's ancestor, and
    most constrained-device IoT stacks.

/* --- WHAT TLS COSTS ON AN MCU --- */
    mbedTLS, ECDHE-ECDSA-AES128-GCM, Cortex-M4:
      code                 ~60-100 KB flash
      RAM per connection   ~20-40 KB   <-- usually the
                                           binding constraint
      handshake            ~300-800 ms in software
      record throughput    a few hundred KB/s

    THE RAM IS THE PROBLEM. Two 16 KB record buffers plus the
    certificate chain plus the session state. On a part with
    64 KB of SRAM, one TLS connection may be all you get.

/* --- HOW TO MAKE IT FIT --- */
    · MBEDTLS_SSL_MAX_CONTENT_LEN 2048  - the single biggest
      saving. Requires the max_fragment_length extension and
      a server that honours it.
    · MBEDTLS_SSL_KEEP_PEER_CERTIFICATE off - free the chain
      after verification
    · compile out every cipher suite you do not use; the
      default config includes dozens
    · use RAW PUBLIC KEYS (RFC 7250) instead of certificates
      where both ends are yours - no ASN.1, no chain, 32
      bytes
    · or use PSK, below
    · SESSION RESUMPTION to avoid repeated handshakes - one
      handshake per boot instead of one per message

/* --- PSK MODE: when public-key crypto will not fit --- */
    TLS_PSK_WITH_AES_128_CCM_8, or 1.3's psk_ke:
      a symmetric key provisioned per device at manufacture.
      TINY: no certificates, no ECC, a few kilobytes total.

    THE TRADE-OFFS, and they are serious:
      · NO FORWARD SECRECY in pure PSK mode (use psk_dhe_ke
        if you can afford one ECDH)
      · the server must hold every device's key - a database
        breach is a fleet compromise
      · key rotation is hard
      · if the key is not per-device, ONE EXTRACTED DEVICE
        BREAKS EVERYTHING. This is the classic IoT failure:
        a single symmetric key in every unit of a product.

    USE PSK ONLY WITH PER-DEVICE KEYS, stored in a secure
    element (chapter 18), and prefer psk_dhe_ke.

/* --- THE CLIENT CODE, mbedTLS, with the checks that
       matter --- */
    mbedtls_ssl_config_defaults(&conf,
            MBEDTLS_SSL_IS_CLIENT,
            MBEDTLS_SSL_TRANSPORT_STREAM,
            MBEDTLS_SSL_PRESET_DEFAULT);

    /* 1. VERIFICATION IS MANDATORY, NOT OPTIONAL */
    mbedtls_ssl_conf_authmode(&conf,
            MBEDTLS_SSL_VERIFY_REQUIRED);

    /* 2. OUR PINNED ROOT ONLY - not a system CA bundle */
    mbedtls_ssl_conf_ca_chain(&conf, &vendor_root, NULL);

    /* 3. FLOOR THE VERSION */
    mbedtls_ssl_conf_min_tls_version(&conf,
            MBEDTLS_SSL_VERSION_TLS1_2);

    /* 4. THE HOSTNAME - sets SNI *AND* enables name
          verification. FORGETTING THIS MEANS ANY VALID
          CERTIFICATE FROM ANY SERVER IS ACCEPTED. */
    mbedtls_ssl_set_hostname(&ssl, "api.example.com");

    /* 5. our device certificate, for mutual TLS */
    mbedtls_ssl_conf_own_cert(&conf, &dev_cert, &dev_key);

    ret = mbedtls_ssl_handshake(&ssl);
    if (ret != 0) { /* FAIL CLOSED. No retry without TLS. */ }

    /* 6. AND CHECK THE RESULT EXPLICITLY */
    uint32_t flags = mbedtls_ssl_get_verify_result(&ssl);
    if (flags != 0) { abort_connection(); }

/* STEP 4 IS THE ONE THAT GETS OMITTED, and it silently
   disables hostname verification. It is the embedded
   equivalent of the mobile TrustManager bug from
   chapter 16.                                           */

The attack history, and what it teaches

TLS's attack history is the best available case study in applied cryptography, because each break exploited something that looked reasonable at the time. The lessons generalise well beyond TLS.

AttackYearMechanismGeneral lesson
Bleichenbacher1998PKCS#1 v1.5 decryption oracleError messages are an oracle
BEAST2011Predictable CBC IVIVs must be unpredictable
CRIME2012Compression before encryptionNever compress secrets with attacker data
Lucky132013MAC-then-encrypt timingEncrypt-then-MAC; use an AEAD
Heartbleed2014Missing length checkMemory safety is crypto security
goto fail2014Duplicated statement skipped a checkTest the rejection paths
POODLE2014SSLv3 padding, reached by downgradeRemove old versions entirely
FREAK / Logjam2015Downgrade to export gradeDelete weak options, don't deprecate
DROWN2016SSLv2 on a server sharing a keyKey reuse across protocols is fatal
SWEET32201664-bit block birthday boundBlock size limits data per key
ROBOT2017Bleichenbacher, againRemoved attacks come back if the code stays
Raccoon2020DH timing side channelConstant time, everywhere
 
/* WHAT THE LIST ACTUALLY SAYS:

   · ALMOST NONE OF THESE BROKE A CIPHER. AES is fine. RSA is
     fine. The failures are in COMPOSITION, NEGOTIATION,
     ERROR HANDLING, PARSING and IMPLEMENTATION.

   · Half of them are DOWNGRADE or LEGACY-OPTION attacks. The
     old code you kept for compatibility is the attack
     surface.

   · Several are TIMING. Constant-time code is not paranoia
     (chapter 19).

   · One is a plain buffer over-read. MEMORY SAFETY IS PART
     OF CRYPTOGRAPHY, which is a large part of why Rust is
     appearing in this space (see the Rust track).

   · AND THE META-LESSON: USE A MAINTAINED LIBRARY AND KEEP
     IT UPDATED. Every one of these was fixed centrally, and
     every device that never got an update is still
     vulnerable. YOUR UPDATE MECHANISM IS A SECURITY CONTROL
     (chapter 15).                                        */
