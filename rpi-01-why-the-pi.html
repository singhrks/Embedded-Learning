Why a Pi, and what it hides from you

A Raspberry Pi is the cheapest way to get a real ARM Cortex-A system with real peripherals on your desk, and it is the board most of this curriculum can actually run on. It is also a board that solves several hard problems for you silently — and knowing which ones is what stops it teaching you bad habits.

What you are actually holding

   A Pi is not a microcontroller board. It is a small
   computer, and the difference is the whole point.

   +-------------------------------------------------+
   |  Pi 4 (BCM2711) / Pi 5 (BCM2712)                |
   |                                                 |
   |   4x Cortex-A72 @1.8GHz  /  4x Cortex-A76 @2.4  |
   |   ARMv8-A, 64-bit, MMU, four exception levels   |
   |   L1 + L2 caches, branch prediction, SMP        |
   |                                                 |
   |   1-8 GB LPDDR4  /  4-16 GB LPDDR4X             |
   |   GPU, video decode, ISP                        |
   |                                                 |
   |   Boots Linux. Runs systemd. Has a package      |
   |   manager, a filesystem, and 30 million lines   |
   |   of kernel underneath you.                     |
   +-------------------------------------------------+

   COMPARE WITH THE MCU TRACK'S TARGET:
     Cortex-M4 @100 MHz, 64 kB SRAM, no MMU, no OS.

   These are different universes, and both are "embedded".
   The Pi is where the ARM, Linux, virtualisation and
   security tracks become touchable; the MCU track's
   material does not apply to it and never will.

What it is genuinely good for

The single best argument for it

Every other way of learning this material either emulates the hardware (so you never meet cache coherency, signal integrity, thermal throttling, or a peripheral that lies about its state) or costs ten times as much and comes with a vendor toolchain you must fight. A Pi is real silicon, with a mainline-adjacent kernel, public schematics, and a community that has already hit whatever you are about to hit.

What it hides, and why that matters

   THE PI SOLVES THESE FOR YOU. On a real product you would
   solve them yourself, and not knowing that is the risk.

   1. BOOT AND FIRMWARE
      A closed-source firmware blob brings up DRAM, clocks
      and the PMIC before your kernel sees anything. On a
      custom board that is YOUR problem: DDR training,
      power sequencing, a bootloader you port.
      -> chapter 03 shows you what it is doing.

   2. POWER MANAGEMENT
      Regulators, sequencing and rails are done. You will
      never brown-out a Pi by enabling a peripheral wrongly.

   3. THE DEVICE TREE
      A correct, complete, tested device tree ships with the
      OS. On a new board, writing it is weeks of work.
      -> chapter 10 makes you edit it, which is the useful
         half of that experience.

   4. THE DISTRIBUTION
      Raspberry Pi OS has drivers, firmware, a package
      manager and an update path. A product needs Yocto or
      Buildroot and someone to own it.

   5. THERMAL AND MECHANICAL
      A heatsink and a known-good PCB. No EMC testing, no
      layout review, no enclosure.

   6. STORAGE
      An SD card that you can reimage in 90 seconds. A
      product has eMMC or NAND, wear levelling, and a
      power-fail-safe update scheme.

   NONE OF THIS MAKES THE PI A BAD TEACHER. It makes it a
   teacher of the SOFTWARE half. Just do not conclude from a
   working Pi that you know how to bring up a board.

Where the Pi is genuinely misleading

/* Three habits the Pi encourages that will hurt you on a
   real product.                                            */

/* 1. "JUST WRITE TO /dev/mem"
      Plenty of Pi tutorials poke peripheral registers
      directly from userspace by mmap-ing /dev/mem. It works,
      it is fast to write, and it is wrong: no locking
      against the kernel's own driver for that peripheral, no
      portability, requires root, and on the Pi 5 the
      addresses moved entirely (chapter 14).

      Use the kernel interfaces. If none exists, write a
      driver - which is what chapter 21 is for.             */

/* 2. "sudo EVERYTHING"
      Most Pi documentation runs as root because it is
      simpler. On a product, a userspace process with
      CAP_SYS_RAWIO is an attack surface. Learn the group
      permissions (gpio, i2c, spi, dialout) instead - they
      exist precisely so you do not need root.             */

/* 3. "IT IS FAST ENOUGH"
      A 2.4 GHz quad-core with 8 GB of RAM forgives
      inefficiency that a real target will not. Code
      developed on a Pi and deployed to a 500 MHz
      single-core part with 256 MB is routinely 20x too
      slow. If the Pi is a STAND-IN for a smaller target,
      constrain it deliberately: taskset to one core, cap
      the clock, cgroup the memory.                        */
A Pi is not a real-time system, and no amount of tuning makes it one

Linux on a Pi will give you millisecond-scale latency most of the time and tens of milliseconds occasionally — a page fault, a thermal event, an SD card retry, a rogue interrupt. Even with PREEMPT_RT the tail is bounded far more loosely than a Cortex-M's twelve cycles. If a deadline matters, the answer is a microcontroller alongside the Pi (which is exactly the architecture of most real products, and what chapter 22 builds). Do not try to bit-bang a protocol from a Linux userspace thread and expect it to hold timing.
