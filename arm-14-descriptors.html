Translation table descriptors, decoded

Sixty-four bits per mapped page, and almost every bit does something you can observe. This is the reference chapter — learn to read a descriptor and you can diagnose any permission, attribute or protection question from a raw hex value.

The leaf descriptor

A leaf descriptor is a 64-bit word in which nearly every bit means something. This is the reference for all of them, and the sections that follow take the ones that matter most in turn.

The L3 inversion is repeated here because it is worth learning twice: it is the most common bare-metal MMU bug (chapter 13).

AP[2:1] — access permissions

Two bits decide read and write permission for both privileged and unprivileged access simultaneously, which is why the encoding is less obvious than a simple read/write flag would be.

   AP    EL1 (and above)    EL0        typical use
   ───────────────────────────────────────────────────────────
   00    read/write          none       kernel data
   01    read/write          read/write shared with userspace —
                                        rare, and a red flag
   10    read only           none       kernel rodata, code
   11    read only           read only  shared constants, vDSO

  Note what is NOT expressible: "EL0 read/write, EL1 no access".
  Privilege is strictly nested — EL1 can always do at least what
  EL0 can. That is a property of the architecture, not a gap.

  So how does PAN stop the kernel touching user pages? Not through
  AP. PAN is a PSTATE bit that makes any EL1 access to an
  EL0-ACCESSIBLE page fault (chapter 05). It works precisely
  BECAUSE AP cannot express the restriction.

Execute-never

Marking memory non-executable is what stops injected data from being run as code. There are separate bits for privileged and unprivileged execution, and using both correctly is a standard hardening measure.

   UXN  bit 54    Unprivileged eXecute Never — EL0 may not execute
   PXN  bit 53    Privileged   eXecute Never — EL1+ may not execute

/* W^X, the fundamental exploit mitigation, is these two bits: */

   kernel code       AP=10 (RO), PXN=0, UXN=1
   kernel data       AP=00 (RW), PXN=1, UXN=1
   kernel rodata     AP=10 (RO), PXN=1, UXN=1
   user code         AP=11 (RO), PXN=1, UXN=0
   user data         AP=01 (RW), PXN=1, UXN=1

/* Note user data has PXN=1. Without it, an attacker who redirects
   kernel execution into a user-controlled buffer wins — the
   classic ret2usr attack. PXN on all user pages closes it, and
   is the ARM equivalent of x86's SMEP.                       */

/* SCTLR_EL1.WXN makes this automatic: any writable page becomes
   execute-never regardless of the descriptor. A cheap global
   hardening switch.                                          */

AttrIndx[2:0] — the memory type

This is the field that connects a mapping to the memory types from chapter 11 — three bits selecting one of eight definitions, rather than encoding the type directly.

/* Three bits selecting one of eight MAIR_EL1 slots
   (chapter 11).                                              */

        pte |= PTE_ATTR(IDX_NORMAL_WB);      /* bits [4:2] */

/* Which slot means what is entirely a software convention —
   whatever you put in MAIR. Linux's arm64 convention:

     0  Device-nGnRnE
     1  Device-nGnRE
     2  Normal Non-cacheable
     3  Normal Write-Back
     4  Normal Write-Through
     5  Normal Tagged (MTE)

   Reading a raw descriptor therefore requires reading MAIR too.
   A descriptor alone does not tell you the memory type.     */

SH[1:0] — shareability

SHDomainUse for
00Non-shareableMemory only this core touches; no coherency maintained
10Outer ShareableShared with masters beyond the CPU cluster — some DMA
11Inner ShareableThe normal choice for all SMP kernel and user memory

Shareability only has meaning for Normal cacheable memory — it is ignored for Device and for Non-cacheable. It determines how far coherency is maintained, and therefore how far a DMB ISH or a TLBI ...IS propagates (chapter 19). Marking SMP memory Non-shareable produces exactly the coherency bugs of CA chapter 15.

AF — the access flag

The bit everyone forgets

If AF is 0, any access takes an Access Flag fault — even though the mapping is otherwise perfect. In hand-written boot tables this presents as "the MMU does not work at all", with a fault code that beginners misread as a translation fault.

Its purpose is page-usage tracking: the OS clears AF, and a later fault tells it the page was touched. That is how LRU approximation works (OS chapter 12). With TCR.HA the hardware sets it for you and the fault disappears. In static tables that never move, just set it and forget it.

nG — not global

A global mapping survives a context switch; a non-global one is tagged with an ASID. Getting this bit wrong means either unnecessary flushing or, far worse, one process seeing another's translations.

   nG = 0    GLOBAL: the TLB entry matches under ANY ASID
   nG = 1    non-global: tagged with the current ASID

/* Kernel mappings (TTBR1) are Global — they are identical in
   every process, so a context switch need not disturb them.
   User mappings (TTBR0) are non-Global, so several processes'
   entries coexist in the TLB (chapter 15).

   Getting this backwards is a memorable bug: mark a user page
   Global and process B sees process A's memory. Mark a kernel
   page non-Global and it is flushed on every switch, costing
   performance but not correctness.                          */

NS — the security bit

One bit in the descriptor decides which security world a mapping belongs to. It is the page-table half of the TrustZone mechanism the isolation track covers in depth.

   NS = 0    this mapping generates SECURE accesses
   NS = 1    this mapping generates NON-SECURE accesses

/* Only meaningful in the Secure translation regime. Secure
   software can create a mapping that issues Non-secure accesses
   — which is how a trusted OS reads a buffer shared with the
   normal world.

   Non-secure software's descriptors have no NS bit that matters:
   its accesses are always NS=1, enforced by hardware.

   In TABLE descriptors there is a separate NSTable bit (bit 63)
   which forces every entry below it to be Non-secure regardless
   of what those entries say — a way to delegate a whole subtree
   safely. Security track, chapter 08.                       */

The contiguous hint

Telling the processor that several adjacent entries map a contiguous region lets it use a single TLB entry for all of them. It is a pure optimisation, with one strict requirement that makes it easy to get wrong.

   Ct  bit 52

/* Asserts: "this entry and its 15 aligned neighbours map a
   contiguous, aligned physical region with identical attributes."
   The TLB may then allocate ONE entry covering all 16 — a 64 KB
   mapping built from 4 KB pages, without needing a block.

   Benefit: 16x the TLB reach for the same table structure.

   Danger: if the claim is FALSE, the TLB uses one translation for
   16 different pages. Accesses silently go to the wrong memory.
   There is no fault. This is the worst kind of bug — silent,
   data-dependent corruption.

   Requirements: all 16 entries valid, physically contiguous,
   16-page aligned in both VA and PA, identical attributes and
   permissions. Changing any one of them requires clearing the
   hint on all 16 first, with break-before-make.            */

DBM and hardware dirty tracking

Dirty bit management lets hardware mark a page as written rather than requiring a fault and a software update. It is a significant performance feature and it changes the meaning of the permission bits slightly.

   DBM  bit 51    Dirty Bit Modifier

/* With TCR.HD enabled, a descriptor with DBM=1 and AP=read-only
   is upgraded to writable BY HARDWARE on the first write, and
   the hardware records the page as dirty by clearing AP[2].

   Without it, the OS must map the page read-only, take a
   permission fault on the first write, record "dirty" in
   software, and remap writable. One fault per page.

   Reading a descriptor: if DBM is set and AP[2] is CLEAR, the
   page has been written. If AP[2] is SET, it is clean.
   Linux's pte_dirty() checks exactly this.                  */

Software-defined bits

Several bits are ignored by hardware entirely and reserved for the operating system's own bookkeeping. Knowing which they are tells you which bits in a real descriptor are Linux's rather than the architecture's.

/* Bits 58:55 (and bits 62:59 in some configurations) are
   IGNORED by hardware. The OS owns them.                     */

/* Linux arm64 uses them for: */
#define PTE_DIRTY       (_AT(pteval_t, 1) << 55)
#define PTE_SPECIAL     (_AT(pteval_t, 1) << 56)
#define PTE_DEVMAP      (_AT(pteval_t, 1) << 57)
#define PTE_PROT_NONE   (_AT(pteval_t, 1) << 58)

/* And for SWAP ENTRIES: when a page is swapped out, the
   descriptor is invalid (bit 0 = 0), so the hardware ignores the
   whole thing — and the OS reuses the other 63 bits to store the
   swap device and offset. That is how the page table doubles as
   the swap map with no extra storage.                       */

Decoding a real descriptor

Here is the payoff: taking a real 64-bit descriptor value and reading off exactly what it permits. Doing this fluently is what turns a fault address into an explanation.

/* Given: 0x0060000098765743                                  */

   0x0060000098765743
   = 0000 0000 0110 0000 0000 ... 1001 1000 0111 0110 0101 0111 0100 0011

   bit  0     = 1        VALID
   bit  1     = 1        → at L3: PAGE   (at L1/L2: TABLE)
   bits [4:2] = 0b000    AttrIndx = 0 → MAIR slot 0
   bit  5     = 1        NS — non-secure
   bits [7:6] = 0b01     AP = 01 → RW at EL1 and EL0
   bits [9:8] = 0b11     SH = Inner Shareable
   bit  10    = 1        AF set — accessed
   bit  11    = 0        nG = 0 → GLOBAL
   bits[47:12]= 0x98765  output address → PA base 0x98765000
   bit  53    = 1        PXN — kernel may not execute here
   bit  54    = 1        UXN — user may not execute here

   Conclusion: a global, inner-shareable, read/write,
   non-executable page at PA 0x98765000, memory type = whatever
   MAIR slot 0 holds. Global + user-writable together is unusual
   and worth questioning.

/* A decoder worth keeping in your toolbox: */
static void decode_pte(uint64_t pte, int level)
{
        if (!(pte & 1)) { pr_info("INVALID (%016llx)\n", pte); return; }

        pr_info("PA=%09llx %s %s AP=%llu SH=%llu %s%s%s%s AttrIdx=%llu\n",
                pte & 0x0000FFFFFFFFF000ULL,
                (pte & 2) ? (level == 3 ? "page" : "table") : "block",
                (pte & (1UL << 10)) ? "AF"  : "!AF",
                (pte >> 6) & 3, (pte >> 8) & 3,
                (pte & (1UL << 11)) ? "nG "  : "G ",
                (pte & (1UL << 53)) ? "PXN " : "",
                (pte & (1UL << 54)) ? "UXN " : "",
                (pte & (1UL << 52)) ? "CONT " : "",
                (pte >> 2) & 7);
}

Stage-2 descriptors differ

Descriptors used by a hypervisor's translation are laid out differently from the ones covered above, because they answer to a different set of questions. Confusing the two while debugging is a common trap.

Stage-2 (guest IPA → PA, chapter 16) uses a DIFFERENT layout:

   S2AP[7:6]     00 none, 01 read-only, 10 write-only, 11 read/write
                 — absolute permissions, NOT split by EL, because
                   stage 2 applies to the whole guest

   MemAttr[5:2]  the memory type DIRECTLY encoded, with no MAIR
                 indirection — because the guest owns MAIR and
                 the hypervisor cannot rely on it

   XN[54:53]     execute-never, two bits in newer revisions

  The final memory type is the COMBINATION of stage 1 and stage 2,
  and the rule is "the more restrictive wins": if either stage
  says Device, the access is Device; if either says read-only,
  it is read-only. A hypervisor can therefore force a guest's
  mapping to be non-cacheable regardless of what the guest asked
  for — which is how it emulates devices safely.

How Linux names these bits

Linux gives these architectural bits its own names, and mapping between the two vocabularies is necessary as soon as you read kernel page-table code.

/* arch/arm64/include/asm/pgtable-hwdef.h — worth reading once */

#define PTE_VALID       (_AT(pteval_t, 1) << 0)
#define PTE_TYPE_PAGE   (_AT(pteval_t, 3) << 0)
#define PTE_TABLE_BIT   (_AT(pteval_t, 1) << 1)
#define PTE_USER        (_AT(pteval_t, 1) << 6)   /* AP[1] */
#define PTE_RDONLY      (_AT(pteval_t, 1) << 7)   /* AP[2] */
#define PTE_SHARED      (_AT(pteval_t, 3) << 8)   /* SH[1:0] */
#define PTE_AF          (_AT(pteval_t, 1) << 10)
#define PTE_NG          (_AT(pteval_t, 1) << 11)
#define PTE_CONT        (_AT(pteval_t, 1) << 52)
#define PTE_PXN         (_AT(pteval_t, 1) << 53)
#define PTE_UXN         (_AT(pteval_t, 1) << 54)

/* and the composed protections */
#define PAGE_KERNEL       __pgprot(PROT_NORMAL)
#define PAGE_KERNEL_RO    __pgprot(PROT_NORMAL | PTE_RDONLY | PTE_PXN)
#define PAGE_KERNEL_EXEC  __pgprot(PROT_NORMAL & ~PTE_PXN)

/* Reading these definitions is the fastest way to connect the
   architecture to a real kernel's use of it.               */
