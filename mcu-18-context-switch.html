The context switch, PendSV and the scheduler core

Twenty instructions separate "a program" from "an operating system". This chapter builds the switch itself: why it must run in PendSV, why PendSV must be the lowest priority in the system, and what the hardware does for you at each end.

The whole idea in one picture

   A "context" is just a stack with registers saved on it.
   Switching tasks means changing which stack PSP points at.

   TASK A's STACK              TASK B's STACK
   +--------------+            +--------------+
   |   xPSR       | \          |   xPSR       | \
   |   PC         |  |         |   PC         |  |  hardware
   |   LR         |  | pushed  |   LR         |  |  pushes
   |   R12        |  | by HW   |   R12        |  |  and pops
   |   R3         |  |         |   R3         |  |  these 8
   |   R2         |  |         |   R2         |  |
   |   R1         |  |         |   R1         |  |
   |   R0         | /          |   R0         | /
   +--------------+            +--------------+
   |   R11        | \          |   R11        | \
   |   R10        |  |         |   R10        |  |  YOU push
   |   R9         |  | pushed  |   R9         |  |  and pop
   |   R8         |  | by YOU  |   R8         |  |  these 8
   |   R7         |  |         |   R7         |  |
   |   R6         |  |         |   R6         |  |
   |   R5         |  |         |   R5         |  |
   |   R4         | /          |   R4         | /
   +--------------+ <- saved   +--------------+ <- saved
        PSP_A         in TCB        PSP_B         in TCB

   THE SWITCH:
     1. hardware pushed 8 registers onto A's stack already
     2. push R4-R11 onto A's stack
     3. save PSP into A's TCB
     4. pick the next task
     5. load PSP from B's TCB
     6. pop R4-R11 from B's stack
     7. BX to EXC_RETURN - hardware pops B's 8 registers

   Step 7 returns to whatever B was doing, because B's PC is
   in the frame the hardware just popped. There is no jump
   to task B; you simply return from an interrupt into it.

Why PendSV

   PendSV is an exception whose ONLY purpose is deferring
   work to the lowest priority. Set its priority to 0xFF -
   the lowest possible - and it runs only when no other
   exception is active.

   WITHOUT PendSV, switching directly in SysTick:

     SysTick fires -> switch to task B -> return
     But an interrupt was PREEMPTED by SysTick and is still
     ACTIVE. Returning into task B while that interrupt's
     frame is on the stack corrupts the exception nesting,
     and the core takes a UsageFault (INVPC) or worse.

   WITH PendSV:

   time -->
     UART IRQ  |=====================|
     SysTick        |==|  (sets PendSV pending, returns)
     PendSV                          |=====|  switch here
     task B                                 |=========

     Every other exception drains first. PendSV runs last,
     with a clean nesting state, and the switch is safe.

   THE RULE: PendSV must be the LOWEST priority exception in
   the system. If anything is lower, it can be preempted by
   the switch and the same corruption returns.

     NVIC_SetPriority(PendSV_IRQn, 0xFF);
     NVIC_SetPriority(SysTick_IRQn, 0xFE);

   This is why every Cortex-M RTOS port uses PendSV. It is
   not a convention; it is the only correct place.

The switch, in full

/* This is a complete, working PendSV handler for ARMv7-M.
   'naked' because we must control every instruction - a
   compiler prologue would corrupt the frame we are building. */

__attribute__((naked)) void PendSV_Handler(void)
{
    __asm volatile (
    /* --- SAVE the outgoing task ------------------------- */
    "   mrs   r0, psp              \n"  /* current task SP   */
    "   cbz   r0, restore          \n"  /* first switch: no  */
                                        /* task to save      */
    "   subs  r0, r0, #32          \n"  /* room for R4-R11   */
    "   stm   r0, {r4-r11}         \n"

    "   ldr   r1, =current_tcb     \n"
    "   ldr   r2, [r1]             \n"  /* r2 = current TCB  */
    "   str   r0, [r2]             \n"  /* TCB->sp = r0      */
                                        /* sp is at offset 0 */

    /* --- CHOOSE the next task --------------------------- */
    "restore:                      \n"
    "   push  {lr}                 \n"  /* EXC_RETURN        */
    "   bl    scheduler_next       \n"  /* C function        */
    "   pop   {lr}                 \n"

    /* --- RESTORE the incoming task ---------------------- */
    "   ldr   r1, =current_tcb     \n"
    "   ldr   r2, [r1]             \n"
    "   ldr   r0, [r2]             \n"  /* r0 = TCB->sp      */
    "   ldm   r0, {r4-r11}         \n"
    "   adds  r0, r0, #32          \n"
    "   msr   psp, r0              \n"

    "   isb                        \n"
    "   bx    lr                   \n"  /* EXC_RETURN ->     */
                                        /* hardware unstacks */
    );
}

/* Points worth dwelling on:

   - scheduler_next() is ordinary C. It reads the ready list
     and writes current_tcb. All the policy lives there; the
     assembly is pure mechanism.

   - LR must be preserved across the call, hence push/pop.
     It holds EXC_RETURN, and losing it means you cannot
     return from the exception at all.

   - 'sp' is deliberately the FIRST member of the TCB, so
     the offset is zero and the assembly needs no knowledge
     of the struct layout. Every RTOS does this.

   - This code does NOT save the FP registers. On a part
     with an FPU where two tasks use float, add:

         tst   lr, #0x10          @ EXC_RETURN bit 4
         it    eq
         vstmdbeq r0!, {s16-s31}  @ save if FP frame present

     and the mirror on restore. Omitting it is the classic
     bug that only appears when a second task uses float
     (chapter 02).                                          */

Manufacturing the first stack frame

A task that has never run has no saved context. You fabricate one that looks exactly like a real switch, so the first restore starts it at its entry point.

uint32_t *task_stack_init(uint32_t *stack_top,
                          void (*entry)(void *), void *arg)
{
    /* 8-byte alignment is required by AAPCS. */
    uint32_t *sp = (uint32_t *)((uint32_t) stack_top & ~7u);

    /* --- the frame the HARDWARE will pop, in its order --- */
    *(--sp) = 0x01000000u;            /* xPSR: THUMB BIT SET */
    *(--sp) = (uint32_t) entry & ~1u; /* PC                  */
    *(--sp) = (uint32_t) task_exit;   /* LR: where a task    */
                                      /* goes if it returns  */
    *(--sp) = 0x12121212u;            /* R12                 */
    *(--sp) = 0x03030303u;            /* R3                  */
    *(--sp) = 0x02020202u;            /* R2                  */
    *(--sp) = 0x01010101u;            /* R1                  */
    *(--sp) = (uint32_t) arg;         /* R0 = first argument */

    /* --- the registers WE pop --------------------------- */
    *(--sp) = 0x11111111u;            /* R11                 */
    *(--sp) = 0x10101010u;            /* R10                 */
    *(--sp) = 0x09090909u;            /* R9                  */
    *(--sp) = 0x08080808u;            /* R8                  */
    *(--sp) = 0x07070707u;            /* R7                  */
    *(--sp) = 0x06060606u;            /* R6                  */
    *(--sp) = 0x05050505u;            /* R5                  */
    *(--sp) = 0x04040404u;            /* R4                  */

    return sp;                        /* store in TCB->sp    */
}

/* THREE THINGS THAT MUST BE RIGHT:

   1. xPSR MUST have bit 24 (T) set. Clear it and the core
      faults with INVSTATE the instant the task starts
      (chapter 02). This is the single most common bug when
      writing a scheduler from scratch.

   2. The PC entry must have bit 0 CLEAR here, even though
      function pointers carry it set. The hardware takes the
      T state from xPSR, not from the PC, and a set bit 0 in
      the stacked PC is architecturally unpredictable.

   3. LR should point at a function that handles a task
      returning. A task that falls off the end otherwise
      branches to whatever 0x0E0E0E0E-style filler you put
      there. Make it explicit:                              */

static void task_exit(void)
{
    task_delete(current_tcb);
    for (;;) { }        /* never reached; the switch away
                           happens inside task_delete       */
}

/* The recognisable filler values are a debugging gift: in a
   fault dump, seeing 0x07070707 in R7 tells you instantly
   that this task has never actually run.                   */

Starting the scheduler

/* Getting from main() - running on MSP, privileged - into
   the first task on PSP is a one-time bootstrap.          */

void scheduler_start(void)
{
    NVIC_SetPriority(PendSV_IRQn,  0xFF);   /* lowest       */
    NVIC_SetPriority(SysTick_IRQn, 0xFE);

    current_tcb = scheduler_highest_ready();

    /* Point PSP at the first task's frame, skipping the 8
       registers the hardware will pop for us.              */
    __set_PSP((uint32_t) current_tcb->sp + 32);

    /* Switch Thread mode to PSP. */
    __set_CONTROL(0x02);
    __ISB();                    /* MANDATORY (chapter 03)   */

    systick_init(1000);         /* 1 kHz tick               */

    /* Jump to the task entry. From here the only way back
       into main() is a bug.                                */
    void (*entry)(void *) = current_tcb->entry;
    entry(current_tcb->arg);
}

/* THE TICK. SysTick does no switching itself - it accounts
   for time and, if that changed who should run, requests a
   PendSV. That request is a single register write:        */

void SysTick_Handler(void)
{
    g_ticks++;
    if (scheduler_tick()) {                  /* returns 1 if
                                                a switch is
                                                needed      */
        SCB->ICSR = SCB_ICSR_PENDSVSET_Msk;  /* request it  */
    }
}

/* Any code, including any ISR, can request a switch with
   that one store. A UART handler that unblocks a waiting
   task does exactly this, which is how a task becomes
   runnable "immediately" rather than at the next tick.    */
Mechanism and policy are cleanly separated

The assembly above is the entire mechanism, and it never changes. Round-robin, fixed-priority preemptive, rate-monotonic, or EDF are all just different implementations of scheduler_next() — ordinary C, testable on a host, with no assembly involved. When you read FreeRTOS or Zephyr, this is the seam to look for first: port.c holds the twenty instructions, and everything else is policy on top.
