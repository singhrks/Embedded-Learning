Why concurrency exists, and what it costs

Concurrency is not a feature you add for speed. It is a structural decision that buys you three specific things and charges you in a currency — correctness you can no longer verify by reading the code — that most teams underestimate until the first bug that only reproduces in production.

The three reasons, and only three

"Concurrency" is used for three genuinely different goals, and confusing them is why people adopt threads and get no benefit. Naming which one you actually want decides everything that follows — including whether threads are the right tool at all.

   1. LATENCY HIDING - something is slow and not the CPU

        thread A: read from disk .................. 10 ms
        thread B: meanwhile, do actual work

      This is why servers are threaded. It has nothing to do
      with having more cores; a single core wins here too,
      because the alternative is a CPU sitting idle.

   2. THROUGHPUT - the work genuinely divides

        8 cores, 8 independent chunks -> up to 8x

      This is the only reason that needs multiple cores, and
      the only one where Amdahl's law bites.

   3. STRUCTURE - the problem IS concurrent

        a UI that must stay responsive while working
        a device that raises interrupts whenever it likes
        ten clients that arrive independently

      Here concurrency is not an optimisation. Modelling these
      sequentially produces worse code, not faster code.

   IF YOUR REASON IS NOT ON THIS LIST, do not add threads.
   "It felt like it should be faster" is not a reason, and
   parallel code that is slower than the serial version is the
   single most common outcome of a first attempt.
Concurrency is not parallelism

Concurrency is a way to structure a program: several independent activities, whose execution may interleave. Parallelism is executing several things at literally the same instant, which needs hardware. A single-core machine can be highly concurrent and not at all parallel. Reasons 1 and 3 above are concurrency; reason 2 is parallelism. Confusing them is why people expect a thread pool to speed up a program that was waiting on a network socket.

What the speed-up is actually bounded by

This is the arithmetic that sets a hard ceiling on what parallelism can achieve, and it is far lower than intuition suggests. A program that is 95% parallelisable cannot go more than twenty times faster no matter how many cores you add.

/* Amdahl's law. If a fraction p of a program can be
   parallelised and the rest cannot:                        */

        speedup(N) = 1 / ( (1 - p) + p/N )

   p = 0.95, N = 8   ->  5.9x     (not 8x)
   p = 0.95, N = 32  ->  12.5x
   p = 0.95, N = INF ->  20x      <-- the ceiling, for ever

   p = 0.50, N = INF ->  2x

/* The 5% you did not parallelise caps you at 20x no matter
   how many cores you buy. And "the rest" includes things
   people forget to count:

     - process startup and teardown
     - reading the input, writing the output
     - the lock everyone contends on
     - the memory allocator
     - the one std::cout in the inner loop

   Gustafson's law is the optimistic counterpart: if you scale
   the PROBLEM with the machine rather than fixing it, the
   serial fraction shrinks in relative terms and the ceiling
   moves. Both are true. Amdahl describes making a fixed job
   faster; Gustafson describes doing a bigger job in the same
   time. Know which one you are actually doing.                */

The bill

Threads are not free, and the costs arrive in several distinct forms — some paid once, some on every switch, some only when threads actually contend. Knowing which is which explains why adding threads sometimes makes a program slower.

CostWhat it looks like
Correctness stops being localA function that is correct on its own can be wrong when two threads call it. You can no longer verify code by reading it in isolation, which is the single biggest cost and the hardest to price
Bugs become non-deterministicA race that fires once in 10⁸ iterations appears weekly in production and never on your laptop. "Cannot reproduce" becomes a normal state
Tests stop proving thingsA passing test means "this interleaving worked", not "the code is correct". See chapter 20 for what to do instead
Memory traffic multipliesTwo threads writing near each other can be slower than one thread doing all the work — false sharing
Synchronisation is not freeAn uncontended mutex is ~20 ns; a contended one that sleeps is ~1–10 µs. Lock a mutex per element of a million-element loop and you have written something slower than the serial version by an order of magnitude
Latency gets a tailAverage throughput improves; the 99.9th percentile gets worse, because now there is queueing and there are lock convoys
Debugging tools stop helpingA breakpoint changes the timing and the bug goes away. printf is a memory barrier and a syscall
 
/* Rough costs on a modern out-of-order core. Ratios, not
   measurements - benchmark your own platform.               */

  an L1 cache hit ..........................   ~1 ns
  an uncontended atomic increment ..........   ~5-20 ns
  an uncontended mutex lock + unlock .......   ~20 ns
  a cache line bouncing between two cores ..   ~50-200 ns
  a contended mutex that must sleep ........   ~1-10 us
  a thread context switch ..................   ~1-5 us
  creating a thread ........................   ~10-100 us
  a condition-variable wake-up .............   ~5-50 us

/* The two lines worth memorising:

   * creating a thread costs about as much as 10,000 mutex
     operations. This is why thread POOLS exist (chapter 17).

   * moving a cache line between cores costs more than a
     hundred arithmetic operations. This is why data layout
     decides parallel performance more often than algorithm
     choice does (chapter 16).                               */
The most common first mistake

Taking a loop, splitting it across eight threads, and finding it runs slower. Almost always one of three causes: the threads are contending on a shared counter or allocator; they are writing to adjacent memory and bouncing a cache line; or the work per item is smaller than the synchronisation cost. All three are covered later in this track, and all three are invisible in the source code.

The embedded case is not optional

Even a bare-metal program with no threads is concurrent: an interrupt can fire between any two instructions, and the handler shares memory with the code it interrupted. Everything in this track about races, atomicity and memory ordering applies, minus the scheduler. If you have ever written volatile hoping it would fix something, chapters 11 and 12 are for you.

Why it is hard, specifically

Concurrency is difficult for reasons that are structural rather than a matter of care. Each one below defeats a technique that works perfectly for sequential code, which is why experience with sequential debugging transfers so poorly.

   Two threads run this. `counter` starts at 0.

       counter = counter + 1;

   One line. It compiles to three operations:

       LDR  w0, [counter]      // read
       ADD  w0, w0, #1         // modify
       STR  w0, [counter]      // write

   An interleaving that loses an increment:

     thread A          thread B          counter
     --------          --------          -------
     LDR  -> 0                              0
                       LDR  -> 0            0
     ADD  -> 1                              0
                       ADD  -> 1            0
     STR                                    1
                       STR                  1     <-- should be 2

   Now note three things that make this worse than it looks:

   1. This interleaving is RARE. The window is nanoseconds.
      Your test passes ten million times and fails in
      production.

   2. The compiler may keep `counter` in a register across the
      whole loop, so the write happens ONCE, at the end.

   3. The hardware may reorder your loads and stores relative
      to other variables entirely (chapter 12).

   Points 2 and 3 mean you cannot reason about concurrency by
   reading the source at all. You are reasoning about a
   contract between you, the compiler and the CPU - and that
   contract is the memory model.

Rules that survive contact with real systems

  1. Do not share what you can copy. The cheapest synchronisation is the kind you deleted. Give each thread its own data and merge at the end.
  2. Do not communicate by sharing memory; share memory by communicating. Go's slogan, and it is right far more often than shared-mutable-state advocates admit.
  3. Immutable data needs no locks. If nothing writes after publication, every reader is safe for free.
  4. One lock, one clearly named invariant. If you cannot state in a sentence what a lock protects, nobody can use it correctly, including you in six months.
  5. Measure before and after. Parallel code that is not faster is strictly worse than serial code, and you will not know which you have without a number.
  6. Prefer coarse locking first. One big lock that is correct beats fine-grained locking that is subtly wrong. Make it correct, measure, then split only what the profile demands.

What this track assumes and what it adds

The operating systems track already introduced threads, synchronisation primitives and deadlock as OS concepts. The C++ and Rust tracks cover their respective language models. This track is the practitioner's version: what the hardware really does, which primitive to reach for and why, the failure modes that only appear under load, and how to find them deliberately rather than by waiting.
