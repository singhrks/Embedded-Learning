Interrupt handling in Linux

From the GIC delivering an exception to your handler being called: the number spaces, the device-tree description, the registration API, and the handful of mistakes that produce interrupt storms and missed events.

The path from wire to handler

Between a wire changing voltage and your C function running, a surprising amount happens: hardware signals a controller, the controller decides which CPU should take it, the CPU switches privilege level and vectors into the kernel, and only then is your handler looked up and called. Knowing the path matters because an interrupt that never arrives can be lost at any point along it.

   device asserts its interrupt line
        |
        v
   GIC distributor -> redistributor -> CPU interface
        |  (ARM ch. 23-24: priority, targeting, grouping)
        v
   CPU takes an IRQ exception -> VBAR_EL1 + 0x280
        |  (ARM ch. 27-28)
        v
   arch/arm64/kernel/entry.S  el1_irq / el0_irq
        |
        v
   handle_arch_irq  ->  gic_handle_irq()
        |
        |  read GICC_IAR / ICC_IAR1_EL1 -> the hardware INTID
        v
   irq_find_mapping(domain, hwirq)  ->  the LINUX IRQ NUMBER
        |
        v
   generic_handle_irq(virq)
        |
        v
   handle_level_irq() / handle_edge_irq()   the FLOW HANDLER
        |    mask, ack, or eoi as the type requires
        v
   for each action on this irq:
        your_handler(irq, dev_id)
        |
        v
   IRQ_HANDLED / IRQ_WAKE_THREAD / IRQ_NONE
        |
        v
   EOI to the GIC, return from exception

  TWO NUMBER SPACES, and confusing them wastes hours:

     HWIRQ    the hardware number. SPI 42, or "bit 3 of GPIO
              controller 2". Meaningful only to that
              controller. This is what the DEVICE TREE says.

     VIRQ     the Linux irq number. A global integer allocated
              by the kernel. What you pass to request_irq().
              What /proc/interrupts shows.

  The IRQ DOMAIN maps between them, per controller. That is
  what makes nested controllers work: a GPIO chip is an
  interrupt controller whose own interrupt comes from the GIC,
  and each of its pins gets a virq of its own.

Describing an interrupt in the device tree

Your driver does not choose which interrupt line it gets — that is a property of how the chip is wired to the board, so like everything else about the board it comes from the device tree. Getting this description wrong is the single most common reason a handler never fires.

/* GIC SPI, the common case: */

        my_device: device@1c000000 {
                compatible = "vendor,my-device";
                reg = <0x0 0x1c000000 0x0 0x1000>;
                interrupts = <GIC_SPI 42 IRQ_TYPE_LEVEL_HIGH>;
                interrupt-parent = <&gic>;   /* often inherited */
        };

/* THREE CELLS for a GICv2/v3:
     cell 1: GIC_SPI (0) or GIC_PPI (1)
     cell 2: the interrupt number WITHIN that type.
             SPI n in DT = INTID (n + 32) in the GIC.
             THIS OFF-BY-32 CATCHES EVERYONE. The TRM says
             "INTID 74"; the device tree says 42.
     cell 3: the trigger type:
                IRQ_TYPE_EDGE_RISING     1
                IRQ_TYPE_EDGE_FALLING    2
                IRQ_TYPE_LEVEL_HIGH      4
                IRQ_TYPE_LEVEL_LOW       8

/* NAMED interrupts, when a device has several - always prefer
   this over relying on index order: */
        interrupts = <GIC_SPI 42 IRQ_TYPE_LEVEL_HIGH>,
                     <GIC_SPI 43 IRQ_TYPE_LEVEL_HIGH>;
        interrupt-names = "tx", "rx";

/* A GPIO used as an interrupt - a NESTED controller: */
        interrupt-parent = <&gpio2>;
        interrupts = <7 IRQ_TYPE_EDGE_FALLING>;
        /* two cells here, because that is what gpio2's
           #interrupt-cells says. Every controller defines its
           own cell format - check its binding.            */

/* GETTING THE VIRQ IN YOUR DRIVER: */
        irq = platform_get_irq(pdev, 0);           /* by index */
        irq = platform_get_irq_byname(pdev, "rx"); /* by name  */
        if (irq < 0)
                return irq;      /* it already logged the error
                                    and may be -EPROBE_DEFER  */

/* platform_get_irq() does the whole domain translation for
   you. Never hard-code a number.                          */
The SPI off-by-32

GIC interrupt IDs 0–15 are SGIs, 16–31 are PPIs, and SPIs start at 32. The device tree's GIC_SPI n means INTID n + 32. A datasheet quoting "interrupt 74" almost always means INTID 74, which you write as GIC_SPI 42. Getting this wrong gives you a driver whose interrupt never fires, or — worse — one that steals another device's.

Registering a handler

Registering is where you tell the kernel which function to call, and — just as importantly — what kind of handler it is. The choice you make here determines what your code is allowed to do when it runs.

/* The managed form. Use it. */

        ret = devm_request_irq(&pdev->dev, irq,
                               my_handler,
                               0,                 /* flags */
                               dev_name(&pdev->dev),
                               d);                /* dev_id */
        if (ret)
                return dev_err_probe(&pdev->dev, ret,
                                     "cannot request irq %d\n",
                                     irq);

/* Or threaded (chapter 15), which is usually what you want: */
        ret = devm_request_threaded_irq(&pdev->dev, irq,
                                        my_hardirq, my_thread,
                                        IRQF_ONESHOT,
                                        dev_name(&pdev->dev), d);

/* THE FLAGS:
     IRQF_SHARED       the line is shared with other devices
     IRQF_ONESHOT      keep masked until the thread finishes
     IRQF_TRIGGER_*    override the DT trigger type. Do not -
                       fix the device tree instead.
     IRQF_NO_SUSPEND   keep enabled across suspend
     IRQF_PERCPU       a per-CPU interrupt (a PPI)
     IRQF_NOBALANCING  exclude from irqbalance

/* dev_id MUST be unique and non-NULL for a shared interrupt -
   it is how free_irq() knows which action to remove, and it
   is what your handler receives. Pass your device struct.

/* THE HANDLER: */
static irqreturn_t my_handler(int irq, void *dev_id)
{
        struct my_dev *d = dev_id;
        u32 status;

        status = readl(d->base + REG_STATUS);

        /* ON A SHARED LINE THIS CHECK IS MANDATORY: */
        if (!(status & d->irq_mask))
                return IRQ_NONE;        /* not mine */

        writel(status, d->base + REG_STATUS);   /* ack */
        ... handle ...

        return IRQ_HANDLED;
}

/* RETURN VALUES:
     IRQ_HANDLED       it was mine and I dealt with it
     IRQ_NONE          not mine. On a shared line, essential.
     IRQ_WAKE_THREAD   run the threaded handler

   IF EVERY handler on a line returns IRQ_NONE repeatedly, the
   kernel disables the interrupt and prints:
        "irq 42: nobody cared (try booting with irqpoll)"
        "Disabling IRQ #42"
   which is the spurious-interrupt protection saving your
   system from a livelock. It means the interrupt is asserted
   and nobody is clearing it.                              */

Edge versus level: the failure modes differ

Interrupts signal in one of two ways: a momentary change, or a level held until you clear it. This sounds like a hardware detail with no software consequence, and it is in fact the difference between a lost interrupt and an interrupt storm.

LEVEL-TRIGGERED: the line stays asserted until the device is
serviced.

  · If your handler does not CLEAR the condition in the
    device, the interrupt fires again immediately, forever.
    -> interrupt storm, system livelock, "nobody cared".
  · Cannot be missed: if it is still asserted, it will be
    taken.
  · Safe with sharing.
  · Needs IRQF_ONESHOT with a threaded handler.

EDGE-TRIGGERED: a transition latches a pending bit.

  · CAN BE MISSED. The classic race:

       handler reads STATUS       -> sees event A
       ... device raises event B, edge occurs ...
       handler clears STATUS      -> clears BOTH
       handler returns
       -> event B is lost, and no further edge will come
          because the device is now waiting for you

    THE FIX - loop until the device is genuinely idle:

       do {
               status = readl(d->base + REG_STATUS);
               if (!status)
                       break;
               writel(status, d->base + REG_STATUS); /* ack */
               handle(status);
       } while (1);

    Bound the loop if the hardware might never settle.

  · Also: clear the condition BEFORE re-enabling, or you
    latch your own acknowledgement.

  THE SYMPTOM of getting edge handling wrong is a device that
  works fine and then stops responding forever under load -
  one lost edge and it waits for an event that will never be
  re-signalled.

Controlling interrupts

Occasionally a driver needs to stop an interrupt from firing while it manipulates shared state. There are several ways to do that, they differ in how much of the system they affect, and reaching for the heaviest one by reflex is a common cause of latency problems.

        disable_irq(irq);          /* waits for handlers to
                                      finish. NOT from inside
                                      the handler - deadlock. */
        disable_irq_nosync(irq);   /* returns immediately */
        enable_irq(irq);           /* must MATCH the number of
                                      disables - they nest    */

        /* from within the handler, to mask your own line: */
        disable_irq_nosync(irq);

        /* wake-up capability, for suspend (chapter 32): */
        enable_irq_wake(irq);
        disable_irq_wake(irq);

/* LOCAL interrupt control - almost never right in a driver: */
        local_irq_disable();       /* this CPU only */
        local_irq_enable();
        local_irq_save(flags);
        local_irq_restore(flags);

/* Use spin_lock_irqsave() instead (chapter 12). Bare
   local_irq_disable() in a driver is a red flag: it does not
   protect against other CPUs, it hurts system latency, and it
   is almost always a lock in disguise.                    */

/* AFFINITY (chapter 11): */
        irq_set_affinity_hint(irq, cpumask_of(2));

Reading /proc/interrupts

The kernel keeps a running count of every interrupt, per line and per CPU. This one file answers most "is it firing at all?" questions immediately, and comparing two readings a second apart tells you the rate.

$ cat /proc/interrupts
            CPU0       CPU1       CPU2       CPU3
   3:      12043      11982          0          0  GICv3  30 Level arch_timer
  42:       8471          0          0          0  GICv3  74 Level 1c000000.my-device
  43:          0          0          0          0  GICv3  75 Edge  1c000000.my-device
  56:     102394          0          0          0  GICv3  88 Level eth0
 IPI0:      4821       5102       4993       4877  Rescheduling interrupts

# COLUMN BY COLUMN:
#   42        the LINUX irq (virq)
#   counts    per CPU. This is the useful part.
#   GICv3     the controller
#   74        the HWIRQ - note 42 in DT became INTID 74
#   Level     the trigger type ACTUALLY configured
#   name      what you passed to request_irq

# WHAT TO LOOK FOR:
#   count is ZERO         -> the interrupt never fires. Wrong
#                            number, wrong trigger type, device
#                            not enabled, or pin not muxed.
#   count climbs wildly   -> a storm; the condition is not
#                            being cleared.
#   count on one CPU only -> normal unless you expected
#                            balancing.
#   your device missing   -> request_irq never succeeded.
#   trigger type differs from your DT -> something overrode it
#                            with IRQF_TRIGGER_*.

# Watch it live:
    watch -d -n1 'grep my-device /proc/interrupts'

When the interrupt does not fire

An interrupt that does not arrive is one of the more frustrating bring-up problems, because there is no error message — nothing happens at all. Working through the path in order turns it from guesswork into a short checklist.

# Work down this list. It is almost always one of these.

# 1. Does the count in /proc/interrupts move at all?
#    No -> the interrupt is not reaching the CPU.

# 2. Is the device actually enabled?
    devmem 0x1c000004        # read the interrupt-enable reg
#    Many devices need BOTH a global enable and a per-source
#    unmask, and drivers commonly set only one.

# 3. Is the pin muxed as an interrupt?
    cat /sys/kernel/debug/pinctrl/*/pinmux-pins | grep ...
#    A GPIO-based interrupt with the pin in the wrong function
#    is silent.

# 4. Is the number right?
    cat /sys/kernel/debug/irq/domains/*        # the mappings
    cat /sys/kernel/debug/irq/irqs/42          # this one
#    Compare hwirq against the TRM, remembering the +32.

# 5. Is the trigger type right?
#    A level-high device described as edge-rising fires once
#    at most. Check the "Level"/"Edge" column.

# 6. Is it masked at the GIC?
    cat /sys/kernel/debug/irq/irqs/42
      handler:  handle_level_irq
      status:   0x00000000
      istate:   0x00000000
      ddepth:   1                 <-- DISABLED. Someone called
                                      disable_irq and did not
                                      re-enable.
      wdepth:   0

# 7. Is the clock to the device running? An unclocked
#    peripheral cannot assert anything.

# TRACING, once it does fire:
    echo 1 > /sys/kernel/tracing/events/irq/enable
    cat /sys/kernel/tracing/trace_pipe
      irq_handler_entry: irq=42 name=1c000000.my-device
      irq_handler_exit:  irq=42 ret=handled
