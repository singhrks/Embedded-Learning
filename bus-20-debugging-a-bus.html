Debugging a bus with a scope and a logic analyser

Every bus in this track eventually fails in a way that source code cannot explain. The difference between an hour and a week is knowing which instrument answers which question, and having a procedure rather than a hunch.

Which instrument

InstrumentAnswersCannot answer
Logic analyser (~$20 clone + sigrok/PulseView)What bytes were sent, protocol decode, timing between events, long capturesAnything about signal shape — it only sees above or below a threshold
OscilloscopeEdge shape, ringing, overshoot, noise, actual voltage levelsLong captures; decoding many bytes is painful
Protocol analyser (USB, CAN)Full protocol semantics, errors, timing, at speedCosts real money; unnecessary for simple buses
GPIO probe pinWhat your software was doing when the bus event happenedAnything about the bus itself
 
   THE DECISION IS ONE QUESTION:

     "Is the DATA wrong, or is the SIGNAL wrong?"

   DATA WRONG  (wrong bytes, wrong sequence, missing ACK,
                wrong address, protocol violation)
     -> LOGIC ANALYSER. It decodes, it captures for
        seconds, and a $20 one is entirely sufficient.

   SIGNAL WRONG (works at low speed, intermittent, one
                 board in ten, errors when a motor runs)
     -> OSCILLOSCOPE. You need to see the shape.

   BUY THE LOGIC ANALYSER FIRST. An 8-channel USB clone
   with PulseView decodes UART, SPI, I2C, CAN, 1-Wire and
   dozens more, captures at 24 MHz, and costs less than an
   hour of your time. There is no reason to debug a serial
   bus without one.

The procedure

/* Work in this order. Each step rules out a layer, and
   skipping ahead is how days are lost.                    */

/* 1. IS ANYTHING HAPPENING AT ALL?
      Probe the clock. No clock means the problem is
      configuration - peripheral clock, pin alternate
      function, or the peripheral never enabled (chapter
      01). Zero point debugging protocol logic when nothing
      is being transmitted.                                */

/* 2. IS THE IDLE STATE CORRECT?
      UART   idle HIGH
      I2C    both lines HIGH (if not: no pull-ups, or a
             stuck bus - chapter 07)
      SPI    CS high, SCLK at its CPOL level
      CAN    ~2.5 V on both lines, 0 V differential

      A wrong idle state is a wiring or configuration fault
      and nothing above it can work.                        */

/* 3. IS THE TIMING RIGHT?
      Measure one bit. Not the average - one bit, with
      cursors.
        UART 115200 -> 8.68 us
        SPI 1 MHz   -> 1.00 us
        I2C 400 kHz -> 2.50 us
      A 10% error here is the whole bug (chapter 02).       */

/* 4. ARE THE LEVELS RIGHT?
      VOH should be near VDD, VOL near 0. If a "high" is
      2.0 V on a 3.3 V system, you have a pull-up fighting
      a driver, a level-shifter problem, or a short.        */

/* 5. DECODE IT.
      Now turn on protocol decoding and read the bytes.
      Compare against what your code intended to send. This
      is where you discover the address was shifted, the
      register number was wrong, or the byte order was
      reversed.                                             */

/* 6. CORRELATE WITH SOFTWARE.
      Add a GPIO probe pin toggled in your driver, captured
      on a spare analyser channel. Now you can see "the
      driver entered the ISR here, and the bus glitched
      there" on one timeline. This is the technique that
      solves the genuinely hard ones.                       */

Triggering is the whole skill

   A fault that happens once an hour cannot be found by
   watching. You must arm the instrument to catch it.

   TRIGGER ON THE ERROR, NOT THE TRAFFIC:

   I2C     trigger on a NACK. PulseView and most scopes
           support this directly, and it catches exactly
           the transaction that failed.

   UART    trigger on a specific byte value, or on a
           framing error if the scope supports it.

   SPI     trigger on a CS edge, then look at what came
           after.

   CAN     trigger on an error frame.

   THE UNIVERSAL TECHNIQUE - SOFTWARE-TRIGGERED CAPTURE:

     When your driver detects the error, toggle a GPIO.
     Trigger the analyser on that pin. You now capture
     precisely the failing event, with your own code
     deciding what counts as a failure.

       if (i2c_status & NACKF) {
           TRIGGER_PIN_HIGH();     /* arm the capture */
           TRIGGER_PIN_LOW();
           stats.nack++;
       }

     Set the analyser to capture with 90% PRE-TRIGGER, so
     you see everything that led up to the failure rather
     than what followed it. The cause is always before the
     symptom.

   This one technique - your software telling the
   instrument when to look - turns an intermittent fault
   into a reproducible capture, and it works for every bus
   in this track.
Capture the working case first

Before capturing a failure, capture a success and save it. Half of bus debugging is noticing a difference, and you cannot see a difference without a reference. It also validates your instrument setup — if you cannot capture and decode a transaction that definitely works, then a failed capture tells you nothing about the bus, only about your probe placement or threshold setting.

Recognisable pictures

   WHAT YOU SEE                     WHAT IT MEANS

   Clean edges, wrong bytes         Software: wrong register,
                                    wrong address, wrong
                                    byte order

   Slow rounded rising edges,       Pull-up too weak, or
   sharp falling edges              too much capacitance
   (open-drain buses)               (chapter 07)

   Ringing after each edge          Reflection; slew rate too
                                    fast or missing series
                                    termination (chapter 19)

   Signal never reaches VDD         Pull-up fighting a driver,
                                    or a level-shifter fault

   Bits present but one extra       Ringing crossing the
   clock counted                    threshold twice

   Correct data, no ACK             Device not there,
                                    unpowered, or the address
                                    is shifted (chapter 06)

   Everything correct, device       Timing violation: setup,
   ignores it                       hold or valid delay
                                    (chapter 18)

   is transmitting                  fail-safe bias (RS-485,

   Traffic stops after N frames     Descriptor or buffer
                                    ownership not returned
                                    (chapter 17)
