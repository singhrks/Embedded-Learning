Why Rust for systems programming

Rust's claim is specific: memory safety and data-race freedom, proved at compile time, with no garbage collector and no runtime cost. This chapter is about what that claim actually covers, what it does not, and why the Linux kernel accepted it.

The claim, precisely

Rust's central promise is narrower and more precise than the marketing suggests, and knowing exactly what it does and does not cover is what stops the rest of the track feeling like advocacy.

   IN SAFE RUST, the following are IMPOSSIBLE:

     use after free            dangling pointers
     double free               buffer overflow
     null pointer dereference  uninitialised memory reads
     data races                iterator invalidation

   Not "unlikely", not "caught by tools" - REJECTED BY THE
   COMPILER. The program does not build.

   WHAT IS STILL POSSIBLE, and this matters:
     · memory LEAKS (safe, just wasteful)
     · deadlocks
     · integer overflow (panics in debug, wraps in release -
       both defined)
     · logic errors
     · panics, which abort or unwind
     · resource exhaustion
     · anything inside an `unsafe` block

   THE COST: none at run time. No GC, no runtime, no hidden
   allocation. Rust compiles through LLVM to the same
   instructions C would (chapter 06 of the compilers track),
   and often better - because its aliasing rules are stronger
   than C's, so LLVM can optimise more aggressively.

   WHERE THE COST IS PAID: at COMPILE TIME, in your head. The
   borrow checker rejects programs that are actually correct
   but that it cannot prove correct, and learning to write in
   a shape it accepts takes weeks.

Why the industry moved

Language preference rarely moves an industry. What moved this one was a small number of concrete, measurable facts about where serious bugs actually come from.

/* THE DATA, which is what changed minds:

   · MICROSOFT: ~70% of CVEs assigned each year are memory
     safety issues. Consistent across a decade.
   · GOOGLE (Chrome): ~70% of serious security bugs are
     memory safety.
   · GOOGLE (Android): memory-safety vulnerabilities fell
     from 76% of the total to 24% as the proportion of new
     code written in Rust and Java grew - WITHOUT rewriting
     the old code.
   · THE US GOVERNMENT (ONCD, 2024) recommended memory-safe
     languages for new critical software.

   THE ANDROID RESULT IS THE IMPORTANT ONE: the drop came
   from NEW code being memory-safe. Vulnerability density is
   highest in new code, so replacing the growth edge rather
   than rewriting the base is the effective strategy - which
   is exactly the position an existing C codebase is in.

/* AND THE COUNTER-ARGUMENTS, stated fairly:
     · the learning curve is real, and steeper than any
       mainstream language
     · compile times are slow
     · the embedded ecosystem is younger than C's by three
       decades
     · vendor SDKs, HALs and certified toolchains are C
     · safety-certification stories (ISO 26262, DO-178C) are
       emerging but not yet routine
     · `unsafe` is required for hardware access, so the
       guarantee is only as good as the audit of those
       blocks                                              */

The mechanism, in one page

The whole safety story rests on one idea applied consistently. If you take nothing else from this chapter, take this page — everything in chapters 02 to 04 is an elaboration of it.

/* Three rules do almost all the work. Chapters 02-04 cover
   each properly; this is the shape.                        */

/* --- 1. OWNERSHIP: every value has exactly one owner --- */
        let s = String::from("hello");
        let t = s;              // MOVED. `s` is no longer
                                // usable.
        println!("{}", s);      // COMPILE ERROR

/* When the owner goes out of scope, the value is dropped.
   Exactly once, automatically, on every path. This is C++'s
   RAII with the copy-that-double-frees made impossible
   (C++ chapter 03).

/* --- 2. BORROWING: many readers XOR one writer --- */
        let mut v = vec![1, 2, 3];

        let a = &v;             // shared borrow
        let b = &v;             // another - fine
        println!("{:?} {:?}", a, b);

        let m = &mut v;         // exclusive borrow
        let n = &v;             // ERROR - cannot borrow while
                                // mutably borrowed

/* THIS ONE RULE eliminates data races AND iterator
   invalidation AND aliasing bugs, because all three are the
   same underlying problem: two references to one thing, one
   of them writing.

/* --- 3. LIFETIMES: a reference cannot outlive its
       referent --- */
        let r;
        {
                let x = 5;
                r = &x;
        }                       // x dropped
        println!("{}", r);      // ERROR - r outlives x

/* THE COMPILER TRACKS THIS ACROSS FUNCTION BOUNDARIES, which
   is what makes returning a reference safe.

/* AND THE PAYOFF, in one example - this C bug: */
        char *f(void) {
                char buf[64];
                sprintf(buf, "hi");
                return buf;             /* DANGLING */
        }
/* is, in Rust, not a bug you have to find. It does not
   compile.                                                */
The trade, stated honestly

The borrow checker rejects some programs that are correct. Learning Rust is largely learning which program shapes it can prove correct, and restructuring toward them. That is a real cost, paid up front, in exchange for a class of bug that never reaches production. Whether that trade is worth it depends on how expensive your bugs are — which for firmware, kernels and anything network-facing is usually "very".

Rust on embedded

The obvious objection to a safe language on a microcontroller is cost, and it is worth answering with specifics rather than reassurance.

/* THE PARTS THAT FIT EMBEDDED WELL:

   · no_std - the core language and `core` with no OS, no
     allocator, no runtime (chapter 19). Rust was designed for
     this from the start.
   · ZERO-COST ABSTRACTIONS, verified the same way as C++'s
     (C++ chapter 14) - and the compiler is LLVM, so the
     optimiser is the same one.
   · TYPE-STATE: encode hardware state in the type system, so
     "configure the pin before using it" is checked at
     compile time rather than documented.
   · No hidden allocation. If it allocates, you can see it.
   · Cargo, which after CMake and vendor IDEs is a relief.
   · Excellent cross-compilation: rustup target add
     thumbv7em-none-eabihf, and it works.

/* THE PARTS THAT DO NOT FIT YET:
   · vendor HALs and SDKs are C - so every project has an FFI
     layer (chapter 15), and that layer is `unsafe`
   · certified toolchains (Ferrocene exists; the ecosystem
     around it is young)
   · debugging and trace tooling is thinner than for C
   · binary size can be larger without care - though
     opt-level="z", LTO and panic=abort close most of the gap
   · the async story on bare metal is excellent but recent
     (Embassy - chapter 20)

/* WHERE IT IS ALREADY IN PRODUCTION:
     Android (Binder, Keystore, the Bluetooth stack, parts of
       the kernel)
     Windows (parts of the kernel and font parsing)
     the LINUX KERNEL (chapter 21)
     AWS Firecracker, Cloudflare's proxy, Discord, Dropbox
     Oxide Computer's firmware (Hubris - an entire embedded OS)
     Espressif, Nordic and STM32 HALs

/* THE HONEST RECOMMENDATION for a 2026 embedded team:
     · a NEW project on a well-supported chip: seriously
       consider it
     · an EXISTING C codebase: consider Rust for new
       components with a clean interface, not a rewrite
     · a project constrained by a vendor SDK or certification:
       C or C++, and revisit in two years
     · and LEARN IT REGARDLESS - the ideas improve how you
       write C++, and the kernel now accepts it            */

Getting started

The toolchain is one of the genuinely good parts of the language, and getting to a running program takes about two minutes. This is the whole setup.

# --- INSTALL ---
    curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
    rustup update
    rustup component add rust-src rustfmt clippy
    rustup target add aarch64-unknown-linux-gnu
    rustup target add thumbv7em-none-eabihf   # Cortex-M4F

# --- A HOSTED PROJECT ---
    cargo new hello
    cd hello
    cargo run
    cargo build --release
    cargo test
    cargo clippy -- -D warnings         # the linter. Use it.
    cargo fmt                           # one formatting
                                        # standard, no debate

# --- CROSS-COMPILE ---
    cargo build --target aarch64-unknown-linux-gnu --release

# --- THE FILES ---
    Cargo.toml          dependencies, metadata, profiles
    Cargo.lock          exact versions - COMMIT this for a
                        binary, not for a library
    src/main.rs         the binary crate root
    src/lib.rs          the library crate root

# --- A FIRST PROGRAM, showing the shape ---
fn main() {
    let data = vec![3, 1, 4, 1, 5, 9, 2, 6];

    let sum: i32 = data.iter().sum();
    let max = data.iter().max().expect("non-empty");

    let mut sorted = data.clone();
    sorted.sort();

    println!("sum={sum} max={max} sorted={sorted:?}");

    match find_first_even(&data) {
        Some(x) => println!("first even: {x}"),
        None    => println!("no even numbers"),
    }
}

fn find_first_even(v: &[i32]) -> Option<&i32> {
    v.iter().find(|&&x| x % 2 == 0)
}

/* THINGS TO NOTICE ALREADY:
     `&[i32]`      a SLICE - a pointer and a length, like
                   std::span (C++ chapter 08)
     Option<&i32>  "a reference or nothing" - and the compiler
                   forces you to handle both cases
     `match`       exhaustive: forget a case and it does not
                   compile
     no semicolon  on the last expression of a function - it
                   is the return value
     `{sum}`       inline format arguments                 */

Reading Rust as a C programmer

Rust syntax looks alien for about a week and most of that is a handful of unfamiliar sigils. This is the translation table that shortens the week.

    fn name(arg: Type) -> Ret { }       // function
    let x = 5;                          // immutable BY
                                        // DEFAULT
    let mut y = 5;                      // mutable
    const MAX: u32 = 100;               // compile-time
    static GLOBAL: u32 = 0;             // a static

    &T          a shared reference       (const T* that cannot
                                         be null)
    &mut T      an exclusive reference   (T* that cannot be
                                         null, and is the ONLY
                                         one)
    *const T    a raw pointer           (needs unsafe to
                                         deref)
    Box<T>      an owned heap value      (unique_ptr)
    Vec<T>      a growable array        (vector)
    &[T]        a slice                 (span)
    &str        a string slice          (string_view)
    String      an owned string
    Option<T>   Some(T) or None         (optional)
    Result<T,E> Ok(T) or Err(E)         (expected)

    struct S { a: u32 }                 // a struct
    enum E { A, B(u32), C { x: u8 } }   // a TAGGED UNION -
                                        // variants carry data
    impl S { fn method(&self) {} }      // methods, defined
                                        // separately
    trait T { fn f(&self); }            // an interface
    impl T for S { fn f(&self) {} }     // implementing it

    match x {                           // exhaustive
        0 => a(),
        1..=9 => b(),
        _ => c(),
    }

    if let Some(v) = opt { }            // match one pattern
    while let Some(v) = it.next() { }

    v.iter().map(f).filter(g).sum()     // iterator chains -
                                        // lazy, fused, zero
                                        // cost

/* THE TWO THINGS THAT LOOK STRANGEST AT FIRST:
     1. `impl` blocks separate from the struct - which means a
        type can have methods added by anyone who imports the
        trait
     2. no `return` on the last expression - the value of the
        final expression IS the return value. `return` exists
        for early exits.                                    */
