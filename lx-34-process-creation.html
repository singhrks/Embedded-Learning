Process creation internals: fork, exec and clone

Chapter 10 covered task_struct once it exists. This chapter is where it comes from — why Unix split "create a process" and "run a program" into two separate calls, what a thread actually is at the kernel level, and the single system call underneath all of it.

fork(): copy first, ask questions later

Unix creates a new process by duplicating an existing one, which strikes most people as a strange choice. The result is a second process identical to the first in every respect except one — and that single difference is how each side knows which it is.

   fork() CREATES A NEW PROCESS THAT IS, AT THE INSTANT IT
   IS CREATED, A NEAR-EXACT COPY OF THE CALLER:

     BEFORE fork()                 AFTER fork()

     PARENT                        PARENT           CHILD
     pid 100                       pid 100          pid 101
     memory: A, B, C                memory: A,B,C    memory: A,B,C
     fds: 3, 4, 5                   fds: 3,4,5       fds: 3,4,5
     return value: -                return: 101      return: 0

   BOTH PROCESSES RESUME EXECUTION AT THE SAME POINT, right
   after the fork() call - the ONLY difference visible to the
   program is fork()'s return value, which is how each side
   knows which one it is. Everything else - open file
   descriptors, memory contents, signal handlers, the current
   working directory - starts out identical and then
   DIVERGES independently from that moment on.
Copy-on-write: fork() does not actually copy memory

Duplicating an entire address space on every fork() — potentially gigabytes — would make it unusably slow, and in the overwhelmingly common case (fork() immediately followed by exec(), replacing the memory anyway) all of that copying would be wasted work. Instead the kernel marks every page in both processes' page tables read-only and lets them share the same physical pages. The first write by either process — parent or child — triggers a page fault (the same fault mechanism the Windows internals chapter on memory describes, and Linux's own page-fault path works the same way), the kernel copies just that one page, and each process gets its own private copy from that point on. This is copy-on-write, and it is why fork() is fast regardless of how much memory the parent holds: the cost is proportional to how much memory actually gets modified afterward, not to the process's total size.

exec(): the same process, entirely new content

Creating a process and running a program are two separate operations in Unix. This is the second one, and unlike fork it creates nothing: it replaces the contents of the process that calls it.

/* exec() does NOT create a new process. It REPLACES the
   calling process's memory image, in place, with a new
   program - the pid stays the same, but code, data, heap and
   stack are all discarded and rebuilt from the new binary.  */

execve("/bin/ls", argv, envp);
/* If this returns AT ALL, it failed - success means the
   calling code has been replaced and execution resumes at
   the NEW program's entry point, not at the line after
   execve().                                                */

/* THE CLASSIC PATTERN, and why fork/exec are two calls
   instead of one "spawn" call: */

pid_t pid = fork();
if (pid == 0) {
        /* CHILD: free to do things ONLY the child should do
           before the new program starts - redirect stdin/out,
           close inherited file descriptors, change directory,
           drop privileges, set up a new process group -
           because it is still running the PARENT'S code and
           can still call ordinary functions.                */
        dup2(pipe_fd, STDOUT_FILENO);
        execve("/bin/ls", argv, envp);
        _exit(127);   /* only reached if execve() itself failed */
} else {
        /* PARENT: continues immediately, pid holds the
           child's pid for waitpid() later.                  */
        waitpid(pid, &status, 0);
}
Why not one combined "spawn" call?

The gap between fork() and execve() is not an implementation accident — it is the whole point of splitting process creation this way. Every shell feature that looks like it needs special support from the kernel — I/O redirection (>), pipes (|), changing the working directory for one command only, running a command as a different user — is implemented entirely in that gap, using nothing but ordinary system calls the child process runs on itself before replacing its own image. Windows, by contrast, has no equivalent split — CreateProcess combines both steps into one call and has to expose each of those behaviours as an explicit parameter instead.

clone(): the one real syscall underneath both

Neither of the calls above is really a system call. Both are thin wrappers around a single, more general one, and what it produces — a separate process or a thread sharing everything — depends entirely on the flags you give it.

   NEITHER fork() NOR pthread_create() IS ITS OWN SYSTEM
   CALL. BOTH ARE LIBRARY WRAPPERS AROUND ONE UNDERLYING
   SYSCALL: clone(). What clone() actually creates - a
   process that looks completely separate, or a thread that
   shares almost everything with its creator - is controlled
   entirely by a set of FLAGS passed to it.

     fork()  is roughly:
        clone(SIGCHLD, 0)
        - shares NOTHING extra: new address space, new file
          descriptor table (a COPY, not shared), new signal
          handler table (a copy)

     pthread_create()  is roughly:
        clone(CLONE_VM | CLONE_FS | CLONE_FILES |
              CLONE_SIGHAND | CLONE_THREAD | ..., stack)
        - CLONE_VM:      SHARE the address space - this is
                         what makes it a thread rather than a
                         process; a write by one is
                         immediately visible to the other,
                         with no copy-on-write involved at all
        - CLONE_FILES:   SHARE the file descriptor table -
                         close(fd) in one thread closes it for
                         every thread
        - CLONE_SIGHAND: SHARE signal handlers
        - CLONE_THREAD:  put it in the same thread GROUP, so
                         getpid() returns the SAME value for
                         every thread (chapter 10's pid/tid
                         distinction is exactly this: what
                         getpid() reports for a thread is its
                         thread GROUP's id, not the value the
                         scheduler tracks it under)

   THE CONSEQUENCE: at the kernel level, a THREAD IS SIMPLY A
   task_struct THAT HAPPENS TO SHARE ITS mm_struct, file table
   and signal handlers WITH ANOTHER task_struct. There is no
   separate "thread" data structure in the scheduler at all -
   chapter 10's task_struct and chapter 11's scheduler treat
   every runnable thing identically, whether a userspace
   thread calls it a thread or a process.

What CLONE_* flags actually control

FlagShared instead of copiedSet by
CLONE_VMThe entire address spacepthread_create()
CLONE_FILESThe open file descriptor tablepthread_create()
CLONE_FSCurrent working directory, root, umaskpthread_create()
CLONE_SIGHANDSignal disposition table (requires CLONE_VM)pthread_create()
CLONE_THREADThread group membership — same getpid()pthread_create()
CLONE_NEWNS/NEWPID/NEWNET/...Nothing shared — a new, isolated namespace instead (chapter 40)Container runtimes
None of the aboveNothing — an ordinary, independent processfork()

Reading this table is the fastest way to understand a genuinely confusing piece of Linux terminology: a "process" and a "thread" are not two different kernel object types, they are the same task_struct-based mechanism used with a different combination of sharing flags. Everything else — how much isolation you get, whether a crash in one takes down the other, whether kill() targets one or all of them — follows directly from which resources that particular clone() call chose to share.

Observing it

All of this is visible from outside. Being able to see which flags a program actually used, and which tasks share what, turns the process/thread distinction from a definition into something you can check.

strace -f -e trace=clone,fork,execve ./myprogram
# -f follows children; the clone() line's flags argument
# shows exactly which CLONE_* bits a given fork() or
# pthread_create() call actually used underneath.

ps -eLf              # -L shows every THREAD as its own row,
                     # with a shared PID and a distinct LWP
                     # (light-weight process) id - the
                     # kernel's actual per-thread identifier

cat /proc/PID/status | grep -i threads
cat /proc/PID/task/   # one directory per thread, each with
                      # its own /proc/PID/task/TID/stack etc.
