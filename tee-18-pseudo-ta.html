Pseudo TAs and core drivers

A pseudo TA is a service compiled into OP-TEE itself, running at S-EL1 with the trusted OS's full privilege and none of its isolation. Sometimes that is the only way to do the job. Usually it is not, and the difference is worth being precise about before you write one.

Where a pseudo TA sits

Code can live inside the trusted OS itself rather than as a loadable application, and the two options differ in isolation, privilege and update path.

   S-EL0   +----------+  +----------+
           | user TA  |  | user TA  |   isolated from each
           |          |  |          |   other and from the core
           +----------+  +----------+   by the MMU
                 |             |
                 |  SVC        |
                 v             v
   S-EL1   +--------------------------------------------+
           |  OP-TEE CORE                               |
           |   scheduler, MMU, crypto, drivers          |
           |                                            |
           |   +------------------------------------+   |
           |   |  PSEUDO TA                         |   |
           |   |  same privilege as the core.       |   |
           |   |  same address space as the core.   |   |
           |   |  can call ANY core function.       |   |
           |   |  a bug here is a bug in the        |   |
           |   |  trusted OS.                        |   |
           |   +------------------------------------+   |
           +--------------------------------------------+

   A user TA that dereferences a wild pointer: that TA panics,
   its session dies, the system continues.

   A pseudo TA that dereferences a wild pointer: the trusted OS
   panics, or worse, silently corrupts another TA's memory or
   its own key material.

   The privilege is the same as writing kernel code. Treat it
   that way.

When it is actually right

The choice is not a matter of convenience. Running inside the OS removes a protection boundary, so it needs a reason beyond avoiding the build steps.

ReasonValid?
You need a core API not exposed to S-EL0 — direct hardware access, a core driver, internal stateYes. This is the main reason
You must work before the normal world can load anything — early boot, before tee-supplicantYes — though an early TA may serve, and keeps S-EL0 isolation
You are implementing a service other TAs will callSometimes. A user TA can also be called by another TA
You need to service an interrupt in the secure worldYes — as a core driver, not really as a TA
"It is faster"No. You save one privilege transition, tens of nanoseconds, against a call that costs tens of microseconds
"It is simpler than packaging a .ta"No. That is an hour of build setup against a permanent expansion of the trusted computing base
"It avoids depending on tee-supplicant"Use an early TA instead — same benefit, keeps isolation

Writing one

Writing one looks similar to a normal trusted application with a different registration mechanism — and the similarity is slightly deceptive given the different privilege.

/* core/pta/my_service.c */

#include <kernel/pseudo_ta.h>
#include <kernel/user_access.h>
#include <mm/core_memprot.h>
#include <string.h>
#include <trace.h>

#define PTA_MY_SERVICE_UUID \
        { 0x7c1a9e30, 0x4d6b, 0x4f21, \
          { 0x9a, 0x3c, 0x11, 0x22, 0x33, 0x44, 0x55, 0x66 } }

#define TA_NAME  "my_service.pta"

#define PTA_CMD_READ_REG    0
#define PTA_CMD_WRITE_REG   1

static TEE_Result read_reg(uint32_t ptypes, TEE_Param params[4])
{
        uint32_t exp = TEE_PARAM_TYPES(TEE_PARAM_TYPE_VALUE_INPUT,
                                       TEE_PARAM_TYPE_VALUE_OUTPUT,
                                       TEE_PARAM_TYPE_NONE,
                                       TEE_PARAM_TYPE_NONE);
        vaddr_t base;
        uint32_t off;

        if (ptypes != exp)
                return TEE_ERROR_BAD_PARAMETERS;

        off = params[0].value.a;

        /* WHITELIST. A pseudo TA can read ANY address in the
           system. The client must never choose one. */
        if (off >= MY_DEVICE_SIZE || (off & 3))
                return TEE_ERROR_BAD_PARAMETERS;

        base = (vaddr_t)phys_to_virt_io(MY_DEVICE_BASE,
                                        MY_DEVICE_SIZE);
        if (!base)
                return TEE_ERROR_GENERIC;

        params[1].value.a = io_read32(base + off);
        return TEE_SUCCESS;
}

static TEE_Result invoke_command(void *sess __unused,
                                 uint32_t cmd,
                                 uint32_t ptypes,
                                 TEE_Param params[4])
{
        switch (cmd) {
        case PTA_CMD_READ_REG:  return read_reg(ptypes, params);
        case PTA_CMD_WRITE_REG: return write_reg(ptypes, params);
        default:                return TEE_ERROR_NOT_SUPPORTED;
        }
}

static TEE_Result open_session(uint32_t ptypes __unused,
                               TEE_Param params[4] __unused,
                               void **sess __unused)
{
        /* WHO may call this? A pseudo TA can and should
           restrict its callers. */
        struct ts_session *s = ts_get_calling_session();

        if (!s || !is_user_ta_ctx(s->ctx)) {
                /* called from the normal world directly */
                return TEE_ERROR_ACCESS_DENIED;
        }
        return TEE_SUCCESS;
}

pseudo_ta_register(.uuid  = PTA_MY_SERVICE_UUID,
                   .name  = TA_NAME,
                   .flags = PTA_DEFAULT_FLAGS,
                   .open_session_entry_point = open_session,
                   .invoke_command_entry_point = invoke_command);

/* Flags:
     TA_FLAG_SINGLE_INSTANCE     always, for a PTA
     TA_FLAG_MULTI_SESSION
     TA_FLAG_INSTANCE_KEEP_ALIVE
     TA_FLAG_CONCURRENT          allow concurrent invocations -
                                 you must then be thread safe
     PTA_DEFAULT_FLAGS = SINGLE_INSTANCE | MULTI_SESSION |
                         INSTANCE_KEEP_ALIVE                 */
# core/pta/sub.mk
srcs-$(CFG_MY_SERVICE_PTA) += my_service.c

# core/pta/pta.mk  (or the platform's conf.mk)
CFG_MY_SERVICE_PTA ?= y

$ make CFG_MY_SERVICE_PTA=y
# It is now inside tee.elf. No .ta file, no signing, no
# tee-supplicant, and no way to update it without replacing
# OP-TEE.
Two rules that are not optional in a pseudo TA

Validate every address. A user TA that dereferences a client-supplied pointer faults harmlessly at S-EL0. A pseudo TA reads or writes whatever is there — another TA's key, the core's own state, a device register. Whitelist offsets against a known region; never accept an address.

Copy client data before using it. The double-fetch rule from chapter 7 applies with much worse consequences here. Use copy_from_user/copy_to_user when the caller is a user TA, and never act on shared memory in place.

The pseudo TAs that ship

Several ship as part of the OS and provide core services. Knowing what they are tells you what is already available before you write anything.

Early TAs: the middle option

Some services must exist before the filesystem does, which is one of the few genuinely compelling reasons to build code into the OS rather than load it.

/* An early TA is an ORDINARY user TA, at S-EL0, with full MMU
   isolation - but its binary is linked into tee.elf rather
   than loaded from the normal world.

   You get:
     + available before tee-supplicant, before Linux
     + no dependency on the normal-world filesystem
     + full S-EL0 isolation - a bug is contained
     + no separate signing/installation step
   You lose:
     - it cannot be updated without replacing OP-TEE
     - it occupies TEE_RAM permanently

   This is almost always the right answer when the reason you
   were reaching for a pseudo TA was "it must work early" or
   "I do not want to depend on the supplicant".            */

$ make CFG_EARLY_TA=y \
       EARLY_TA_PATHS="path/to/7f2e9c1a-....ta"

/* The TA is still signed, still verified, and still runs at
   S-EL0 - it is simply carried inside the OP-TEE image
   instead of fetched at runtime.                          */

TA-to-TA calls

Trusted applications can call each other, which allows a service to be factored out — and introduces the question of how the callee authenticates the caller.

/* A user TA can open a session to another TA. Often this is
   what you actually wanted when you considered a pseudo TA -
   a shared service, without giving it core privilege.      */

    TEE_TASessionHandle sess = TEE_HANDLE_NULL;
    TEE_UUID other = OTHER_TA_UUID;
    uint32_t origin;
    TEE_Param params[4] = {0};
    TEE_Result res;

    res = TEE_OpenTASession(&other, TEE_TIMEOUT_INFINITE,
                            0, params, &sess, &origin);
    if (res) return res;

    res = TEE_InvokeTACommand(sess, TEE_TIMEOUT_INFINITE,
                              CMD_DO_THING,
                              TEE_PARAM_TYPES(
                                  TEE_PARAM_TYPE_MEMREF_INPUT,
                                  TEE_PARAM_TYPE_NONE,
                                  TEE_PARAM_TYPE_NONE,
                                  TEE_PARAM_TYPE_NONE),
                              params, &origin);

    TEE_CloseTASession(sess);

/* The callee sees the caller's identity as
   TEE_LOGIN_TRUSTED_APP, with the caller's UUID - so it can
   authorise. Two S-EL0 TAs, isolated from each other, with an
   authenticated channel between them.

   CAUTION: the calling TA's thread is held for the duration
   (chapter 5), so a chain of TA-to-TA calls consumes one
   thread, not several - but a CYCLE deadlocks immediately.
   Keep the call graph acyclic and shallow.                */

How it shows up

SymptomCause
The whole TEE panics when a client misbehavesA pseudo TA dereferencing a client-supplied address
One TA's data appears in anotherA pseudo TA writing outside its intended region — no isolation to stop it
Pseudo TA works, cannot be updated in the fieldBy design: it is inside a signed OP-TEE image
Intermittent corruption under concurrencyTA_FLAG_CONCURRENT set without making the code thread safe
Normal-world client can reach an internal serviceNo caller check in open_session
TA-to-TA call hangs for everA cycle in the call graph, or the callee blocked
Service needed before tee-supplicantUse an early TA rather than a pseudo TA
Security review rejects a pseudo TAUsually correctly. Justify the privilege or move it to S-EL0
