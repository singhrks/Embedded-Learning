Porting OP-TEE to new hardware

Everything so far ran on QEMU, where the platform port already existed and the secure memory was imaginary. Bringing OP-TEE up on real silicon is a different kind of work: a few hundred lines of platform code, one console, one memory carve-out that must be enforced by hardware, and a long list of questions only the SoC's security manual can answer.

What a port actually is

Bringing OP-TEE to a new SoC is a defined piece of work rather than an open-ended one, and knowing its shape up front makes it tractable.

   OP-TEE is mostly platform-independent. A port is a
   directory:

     core/arch/arm/plat-<yours>/
       conf.mk            what the platform has and wants
       main.c             console, early init, hardware setup
       platform_config.h  addresses and sizes
       sub.mk             which files to build
       kern.ld.S          only if your layout is unusual

   Plus decisions made OUTSIDE OP-TEE, which are the hard part:

     TF-A            must load OP-TEE as BL32 and pass a
                     correct boot argument (chapter 2)
     TZASC / XPU     must actually FENCE the secure DRAM
                     (chapter 6) - firmware's job, not
                     OP-TEE's
     device tree     Linux must be told OP-TEE is there
     fuses / keys    the HUK, the TA signing key, secure boot

   Rough effort on a well-supported SoC whose vendor already
   ships TF-A:

     console up ................ half a day
     first TA runs ............. two days
     xtest passing ............. one to two weeks
     RPMB, HUK, secure boot .... weeks, and mostly paperwork

   The middle number is small and the last one is not. Budget
   accordingly: the port is easy, the PLATFORM SECURITY is
   not.
The question that decides everything

Can the hardware make a region of DRAM inaccessible to the non-secure world, and can that configuration be locked before non-secure code runs? If yes, a port is worth doing. If no — no TZASC, no XPU, no lockable firewall — then OP-TEE will run and provide no isolation at all, because normal-world Linux can read secure DRAM directly. Answer this before writing a line of code.

The information you need first

Most porting difficulty comes from missing information rather than difficult code. This is what to obtain from the silicon vendor before starting.

Is there a TZASC/TZC-400, or a vendor XPU?SoC security manualWithout it there is no secure memory (chapter 6)

The four files

A port is a small set of platform files, and knowing which does what tells you where each piece of board-specific knowledge belongs.

# core/arch/arm/plat-acme/conf.mk

PLATFORM_FLAVOR ?= acme_evk

include core/arch/arm/cpu/cortex-armv8-0.mk

$(call force,CFG_TEE_CORE_NB_CORE,4)
$(call force,CFG_ARM64_core,y)          # 64-bit TEE core
$(call force,CFG_GIC,y)
$(call force,CFG_ARM_GICV3,y)
$(call force,CFG_PL011,y)               # console driver
$(call force,CFG_SECURE_TIME_SOURCE_CNTPCT,y)
$(call force,CFG_WITH_ARM_TRUSTED_FW,y) # TF-A loads us as BL32

CFG_SHMEM_START   ?= 0x0f000000
CFG_SHMEM_SIZE    ?= 0x00200000         # 2 MB

CFG_DRAM0_BASE    ?= 0x00000000
CFG_DRAM0_SIZE    ?= 0x80000000

CFG_CORE_DYN_SHM      ?= y   # dynamic shared memory (ch. 7)
CFG_CORE_ASLR         ?= y

# CFG_RPMB_FS         ?= y
# CFG_RPMB_WRITE_KEY  ?= n     # NEVER y in production images

/* core/arch/arm/plat-acme/platform_config.h */

#ifndef PLATFORM_CONFIG_H
#define PLATFORM_CONFIG_H

#include <mm/generic_ram_layout.h>

/* Cache line size - wrong value here corrupts data silently
   through partial cache maintenance.                       */
#define CACHELINE_LEN           64
#define STACK_ALIGNMENT         64

/* GIC */
#define GICD_BASE               0x2f000000
#define GICR_BASE               0x2f100000

/* Console: the UART OP-TEE owns. Must be firewalled to the
   secure world, or normal-world Linux will also drive it and
   the output interleaves into nonsense.                    */
#define CONSOLE_UART_BASE       0x1c090000
#define CONSOLE_BAUDRATE        115200
#define CONSOLE_UART_CLK_IN_HZ  24000000

#endif /* PLATFORM_CONFIG_H */
/* core/arch/arm/plat-acme/main.c - the whole platform port. */

#include <console.h>
#include <drivers/gic.h>
#include <drivers/pl011.h>
#include <kernel/boot.h>
#include <kernel/panic.h>
#include <mm/core_memprot.h>
#include <platform_config.h>

static struct pl011_data console_data;

/* Tell the memory manager these physical ranges exist and how
   they may be mapped. MISSING ONE OF THESE IS THE COMMONEST
   PORTING BUG: the driver writes to an address that was never
   mapped and the core panics with a translation fault.     */
register_phys_mem_pgdir(MEM_AREA_IO_SEC,
                        CONSOLE_UART_BASE, PL011_REG_SIZE);
register_phys_mem_pgdir(MEM_AREA_IO_SEC, GICD_BASE, GIC_DIST_REG_SIZE);
register_phys_mem_pgdir(MEM_AREA_IO_SEC, GICR_BASE, GIC_RDIST_REG_SIZE);

/* Normal-world DRAM: OP-TEE must know which memory is NOT
   secure, so it can refuse a TA that hands it a pointer into
   secure RAM (chapter 20).                                 */
register_ddr(CFG_DRAM0_BASE, CFG_DRAM0_SIZE);

void console_init(void)
{
        pl011_init(&console_data, CONSOLE_UART_BASE,
                   CONSOLE_UART_CLK_IN_HZ, CONSOLE_BAUDRATE);
        register_serial_console(&console_data.chip);
}

void boot_primary_init_intc(void)
{
        gic_init(GICD_BASE, GICR_BASE);
}

void boot_secondary_init_intc(void)
{
        gic_init_per_cpu();
}

/* Optional: platform-specific early setup - clocks, a crypto
   accelerator, the fuse controller that supplies the HUK.  */
static TEE_Result acme_late_init(void)
{
        IMSG("ACME platform init");
        return TEE_SUCCESS;
}
service_init(acme_late_init);

The TF-A side

The secure world does not boot itself; EL3 firmware must load and dispatch it. That integration is a separate piece of work from the OS port.

/* OP-TEE cannot load itself. TF-A's BL2 loads it as BL32 and
   BL31 hands control over. Two things must agree.        */

/* 1. TF-A must be built to know about it: */
$ make -C arm-trusted-firmware \
      PLAT=acme \
      SPD=opteed \                    # the OP-TEE dispatcher
      BL32=~/optee_os/out/arm-plat-acme/core/tee-header_v2.bin \
      BL32_EXTRA1=.../tee-pager_v2.bin \
      BL32_EXTRA2=.../tee-pageable_v2.bin \
      BL33=u-boot.bin \
      ARM_TSP_RAM_LOCATION=dram \
      all fip

/* 2. The boot argument. TF-A passes OP-TEE a device tree
   pointer (or a legacy argument) in x0/x2 at entry. Getting
   this wrong gives you a hang with no output at all, which
   is the single most demoralising failure in this chapter.

   Debug it by putting a character out of the UART as the
   VERY FIRST instruction of OP-TEE's entry point:

       core/arch/arm/kernel/entry_a64.S, at _start:

           mov  x20, x0            // save the real arg first!
           ldr  x1, =0x1c090000    // UART DR
           mov  w2, #'0'
           str  w2, [x1]

   If '0' appears, TF-A reached you and the problem is later.
   If it does not, the problem is the load address, the
   entry point, or the TZASC fencing you off from your own
   code.                                                   */

The part that is not software

The memory partition between the worlds must be established by hardware, and on a new platform that means configuring the specific enforcement blocks that chip provides.

/* The carve-out must be enforced by HARDWARE, before any
   non-secure code runs, and the configuration must be
   LOCKED. This is TF-A's BL2/BL31 job.                    */

/* TZC-400 example, from a platform's BL2:                  */

void plat_acme_security_setup(void)
{
        tzc400_init(TZC400_BASE);
        tzc400_disable_filters();

        /* Region 0 is the background: everything not covered
           by another region. Make it NON-SECURE by default,
           so a region you forget to configure is at least not
           silently secure.                                 */
        tzc400_configure_region0(TZC_REGION_S_NS_RDWR, 0);

        /* Region 1: the OP-TEE carve-out. SECURE ONLY.
           No non-secure master - CPU or DMA - may touch it. */
        tzc400_configure_region(TZC_FILTERS_ALL, 1,
                TZDRAM_BASE,
                TZDRAM_BASE + TZDRAM_SIZE - 1,
                TZC_REGION_S_RDWR,      /* secure only       */
                0);                     /* no NSAID access   */

        tzc400_set_action(TZC_ACTION_ERR);  /* fault, do not
                                               silently drop */
        tzc400_enable_filters();

        /* And lock it, if the hardware supports locking.
           An unlocked TZASC can be reprogrammed by the
           normal world later, which defeats the whole
           exercise.                                        */
}

/* VERIFY IT. Do not assume. From Linux, as root:          */

$ devmem2 0x0e100000 w
/dev/mem opened.
Memory mapped at address 0xffff...
Bus error                      <-- CORRECT. The fence works.

# If instead you see:
Value at address 0x0E100000: 0x14000000
# then you are reading OP-TEE's own code from the normal
# world, and there is no isolation. Everything else in this
# track is theatre until this reads "Bus error".

# Also check DMA, which is the harder half: program a DMA
# engine to read the same address. The TZASC must block the
# device too, and on some SoCs devices are governed by a
# DIFFERENT firewall (an XPU) that you must configure
# separately.
The two mistakes that void the whole port

First: configuring the TZASC but never locking it, so normal-world firmware can widen the window later. Second: fencing the CPU but not the DMA masters — the SMMU and the peripheral firewall are separate blocks with separate configuration, and a passthrough-capable DMA engine that is not covered can read secure DRAM on the guest's behalf. Test both paths explicitly; a passing xtest proves neither.

Telling Linux

The normal world has to be told a TEE exists, which is a device-tree change — and one of the more common reasons a fresh port appears to do nothing.

/ {
        firmware {
                optee {
                        compatible = "linaro,optee-tz";
                        method = "smc";
                };
        };

        reserved-memory {
                #address-cells = <2>;
                #size-cells = <2>;
                ranges;

                /* The carve-out, so Linux never allocates
                   here. The TZASC would fault it anyway, but
                   a fault at a random later moment is far
                   worse than never touching it.           */
                optee@0e100000 {
                        reg = <0x0 0x0e100000 0x0 0x00f00000>;
                        no-map;
                };
        };
};

What separates a port from a product

A development port is not a shippable one. These are the things that must change before a device goes out, and each is easy to forget precisely because nothing fails without it.

/* A port that passes xtest is a development port. Shipping
   requires all of the following, and none of them is code you
   write in OP-TEE.                                         */

  1. A REAL HUK.
     The default is often zeros or a build-time constant. Then
     every device derives the same storage key and secure
     storage protects nothing (chapter 16). Wire
     tee_otp_get_hw_unique_key() to fuses or a key ladder,
     and prove two boards produce different values.

  2. A REAL TA SIGNING KEY.
     The default key ships in the source tree. Anyone can sign
     a TA for your device. Generate one, keep the private half
     in an HSM, and pass TA_SIGN_KEY= at build time
     (chapter 14).

  3. SECURE BOOT, enabled and fused.
     A verified boot chain that is not enforced by fuses is a
     boot chain an attacker replaces.

  4. RPMB, with the key programmed at manufacture.
     CFG_RPMB_WRITE_KEY=y is a development convenience that
     programs a one-time-writable key. Shipping it lets the
     first attacker claim the RPMB.

  5. LOGGING TURNED DOWN.
     CFG_TEE_CORE_LOG_LEVEL=1, CFG_TEE_TA_LOG_LEVEL=0. Debug
     output from the secure world is an information leak, and
     DMSG in a hot path is a timing side channel.

  6. CFG_CORE_ASLR=y, and no CFG_TEE_CORE_DEBUG.

  7. A DOCUMENTED THREAT MODEL.
     Which attacks is this defending against? Bus probing?
     A malicious app? A compromised kernel? Physical
     decapping? The answer decides whether the port is
     adequate, and it is the question an auditor asks first.
