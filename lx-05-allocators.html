Kernel memory allocators

Five allocators, layered on one another, each solving a problem the one below it cannot. Choosing wrongly costs you memory, performance, or — with DMA — a driver that silently corrupts data.

The stack of allocators

The kernel does not have one malloc. It has five allocators layered on top of each other, and each exists because the one beneath it could not solve a particular problem. Seeing them as a stack — rather than as five unrelated functions — is what makes choosing between them straightforward.

   +---------------------------------------------------------+
   |  devm_kmalloc()     device-managed. Freed on unbind.    |
   |                     USE THIS IN DRIVERS. (chapter 33)   |
   +---------------------------------------------------------+
   |  kmalloc() / kmem_cache_alloc()          SLAB / SLUB    |
   |     small objects, PHYSICALLY CONTIGUOUS                |
   |     8 bytes .. a few pages                              |
   +---------------------------------------------------------+
   |  vmalloc()                                              |
   |     large, VIRTUALLY contiguous only                    |
   |     builds page tables; physically scattered            |
   +---------------------------------------------------------+
   |  alloc_pages() / __get_free_pages()      BUDDY ALLOCATOR|
   |     power-of-two page runs, physically contiguous       |
   |     the foundation everything above sits on             |
   +---------------------------------------------------------+
   |  memblock                                               |
   |     boot only, before the buddy allocator exists        |
   +---------------------------------------------------------+
   |  PHYSICAL MEMORY, from the device tree                  |
   +---------------------------------------------------------+

   And, off to the side but important for drivers:

   dma_alloc_coherent()   physically contiguous, DMA-mapped,
                          cache-coherent. (chapter 30)
   CMA                    a reserved pool that can serve large
                          contiguous allocations at runtime

The buddy allocator

Everything above is ultimately built on this one. The buddy allocator hands out whole pages, always in power-of-two runs, and it is the layer that actually owns physical memory. You will rarely call it directly, but its behaviour — especially the way it fragments — leaks upward into every allocator above it.

/* The foundation: allocates 2^order contiguous PAGES.       */

struct page *alloc_pages(gfp_t gfp, unsigned int order);
void         __free_pages(struct page *page, unsigned int order);

unsigned long __get_free_pages(gfp_t gfp, unsigned int order);
void          free_pages(unsigned long addr, unsigned int order);

        order 0  =  1 page   =  4 KB
        order 1  =  2 pages  =  8 KB
        order 2  =  4 pages  = 16 KB
        ...
        order 10 = 1024 pages = 4 MB    (MAX_ORDER limit,
                                         configurable)

/* HOW IT WORKS: free memory is kept in 11 lists, one per
   order. To satisfy an order-2 request with only order-4
   blocks free, it splits an order-4 into two order-3s, takes
   one, splits it into two order-2s, takes one. On free, if
   the adjacent "buddy" block is also free, they merge back.

   CONSEQUENCE - FRAGMENTATION. After hours of uptime, plenty
   of memory can be free while no high-order block exists.
   An order-0 allocation succeeds; an order-4 fails. This is
   why:

     · high-order allocations must ALWAYS be error-checked
     · a driver that needs 4 MB contiguous at runtime should
       use CMA, or allocate at probe time and keep it
     · "it works after reboot, fails after a week" is often
       exactly this

   SEE THE STATE:
        cat /proc/buddyinfo
   Node 0, zone   Normal   1432  882  341  102   43  12  3 0 0 0 0
                           ^order0                        ^order10
   Lots of low-order, nothing high-order = fragmented.   */

kmalloc and the slab allocator

kmalloc is the one you will type most, and it is the closest thing the kernel has to ordinary malloc. Underneath, it is not a general-purpose heap at all: it keeps pools of fixed-size blocks and rounds your request up to the nearest one, which has consequences worth knowing before you size a structure.

void *kmalloc(size_t size, gfp_t flags);
void *kzalloc(size_t size, gfp_t flags);        /* zeroed */
void *kcalloc(size_t n, size_t size, gfp_t f);  /* n*size,
                                                   OVERFLOW-
                                                   CHECKED   */
void *krealloc(const void *p, size_t new, gfp_t f);
void  kfree(const void *p);
size_t ksize(const void *p);       /* what you ACTUALLY got */

/* kmalloc serves from a set of fixed-size caches:
        8, 16, 32, 64, 96, 128, 192, 256, 512, 1024,
        2048, 4096, 8192 ... up to KMALLOC_MAX_SIZE

   ROUNDING UP MATTERS: kmalloc(100) consumes 128 bytes.
   kmalloc(129) consumes 192. In a driver allocating one
   object per packet, choosing 128 over 129 is a 33% memory
   saving. Check with ksize().

   PROPERTIES:
     · PHYSICALLY CONTIGUOUS - so it is DMA-able (with the
       right GFP flags), and virt_to_phys() works on it
     · fast: per-CPU freelists, usually no locking
     · above ~2 pages it falls back to the page allocator, and
       becomes subject to fragmentation

   ALWAYS CHECK THE RETURN:
        p = kmalloc(n, GFP_KERNEL);
        if (!p)
                return -ENOMEM;
   Even GFP_KERNEL can fail. "Small allocations never fail" is
   almost true and entirely unsafe to rely on.             */

/* SIZE ARITHMETIC - use the checked helpers: */
        p = kmalloc(n * size, GFP_KERNEL);      /* CAN OVERFLOW */
        p = kmalloc_array(n, size, GFP_KERNEL); /* checked      */
        p = kcalloc(n, size, GFP_KERNEL);       /* checked+zero */
        p = kmalloc(struct_size(obj, items, n), GFP_KERNEL);
                        /* checked, for flexible array members */

Your own slab cache

If your driver allocates thousands of copies of one particular structure, you can ask the slab allocator for a pool dedicated to exactly that size. This costs a few lines of setup and buys you three things — tighter memory use, faster allocation, and a named line in the kernel's own statistics that makes a leak in your driver immediately visible.

/* When you allocate many objects of ONE type, a dedicated
   cache is tighter and faster than kmalloc's rounding.     */

static struct kmem_cache *my_cache;

static int __init my_init(void)
{
        my_cache = kmem_cache_create("my_request",
                                     sizeof(struct my_request),
                                     __alignof__(struct my_request),
                                     SLAB_HWCACHE_ALIGN, /* flags */
                                     NULL);              /* ctor */
        if (!my_cache)
                return -ENOMEM;
        return 0;
}

        obj = kmem_cache_alloc(my_cache, GFP_KERNEL);
        kmem_cache_free(my_cache, obj);

static void __exit my_exit(void)
{
        kmem_cache_destroy(my_cache);   /* WARNS loudly if
                                           objects are still
                                           allocated - which is
                                           a free leak detector */
}

/* USEFUL FLAGS:
     SLAB_HWCACHE_ALIGN   align to a cache line - avoids false
                          sharing between CPUs (CA ch. 15)
     SLAB_POISON          fill freed objects with a pattern
     SLAB_RED_ZONE        guard bytes around each object
     SLAB_ACCOUNT         charge to the memory cgroup

/* WHY BOTHER:
     · exact sizing: 100-byte objects cost 100 bytes, not 128
     · a NAMED line in /proc/slabinfo, so leaks are visible
       and attributable to your driver
     · kmem_cache_destroy() warning is a built-in leak test

   INSPECT:
        sudo cat /proc/slabinfo | grep my_request
        sudo slabtop -s c            # sorted by cache size  */

vmalloc

Sometimes you need a large buffer and do not care where the physical pages are. vmalloc stitches scattered pages into one contiguous virtual range, which lets it satisfy allocations the buddy allocator would refuse — at a cost, and with one restriction that causes serious, hard-to-find bugs when ignored.

void *vmalloc(unsigned long size);
void *vzalloc(unsigned long size);
void  vfree(const void *addr);

/* Allocates SCATTERED physical pages and maps them into a
   contiguous VIRTUAL range by building page tables.

   USE IT FOR: large buffers where only the CPU touches the
   memory. Firmware images, big lookup tables, module text.

   DO NOT USE IT FOR:
     · DMA. The pages are not physically contiguous, and
       virt_to_phys() DOES NOT WORK on vmalloc addresses.
       This is a top-three driver bug: DMA "works" on a
       machine with little fragmentation, then corrupts
       random memory on a busy one.
     · anything in atomic context - vmalloc can sleep.
     · small allocations - the page-table overhead and TLB
       cost dominate.

   COMPARE:
                     kmalloc         vmalloc
     contiguous      physical+virt   virtual only
     max size        ~4 MB           very large
     speed           fast            slow (page tables, TLB)
     DMA-safe        yes             NO
     can sleep       depends on GFP  always
     virt_to_phys    works           BROKEN

   For a vmalloc buffer you must reach page by page:
        struct page *p = vmalloc_to_page(addr);            */
The DMA rule, stated once

Memory for DMA must be obtained from dma_alloc_coherent(), or from kmalloc/alloc_pages and then mapped with dma_map_single(). Never vmalloc. Never a stack buffer (it may not be DMA-able and its physical address is meaningless to a device). Never a module-static array without mapping it. Chapter 30 covers this properly, but the rule is worth learning before you need it.

Choosing

The right allocator is determined entirely by two questions — does this memory need to be physically contiguous for a device to use it, and what context (process, atomic, driver-lifetime) is it allocated and freed in — and almost every wrong choice in real driver code traces back to skipping one of those two questions rather than to not knowing an API existed.

CMA — contiguous memory at runtime

Some hardware genuinely requires a large, physically contiguous buffer — a camera or a video codec may need tens of megabytes in one unbroken run. After a few hours of uptime, ordinary allocation cannot deliver that at any price, so the kernel needs a way to reserve the memory in advance without wasting it in the meantime.

/* THE PROBLEM: a camera or video codec needs 32 MB physically
   contiguous, at runtime, after hours of uptime. The buddy
   allocator cannot deliver that - fragmentation guarantees it.

   THE SOLUTION: reserve a region at boot, but let MOVABLE
   pages (page cache, anonymous memory) use it meanwhile. When
   a contiguous allocation arrives, migrate them out.       */

        reserved-memory {
                #address-cells = <2>;
                #size-cells = <2>;
                ranges;

                cma_pool: linux,cma {
                        compatible = "shared-dma-pool";
                        reusable;          /* <-- makes it CMA */
                        size = <0x0 0x8000000>;   /* 128 MB */
                        alignment = <0x0 0x400000>;
                        linux,cma-default;
                };
        };

        my_codec: codec@1c000000 {
                compatible = "vendor,codec";
                reg = <0x0 0x1c000000 0x0 0x10000>;
                memory-region = <&cma_pool>;
        };

/* Then in the driver, dma_alloc_coherent() transparently comes
   from CMA:                                                */
        of_reserved_mem_device_init(dev);
        buf = dma_alloc_coherent(dev, SZ_32M, &dma, GFP_KERNEL);

/* CAVEATS worth knowing before you rely on it:
     · migration can FAIL if a page is pinned - so CMA
       allocation can still fail, just much less often
     · migration takes time; a large allocation can stall for
       tens of milliseconds
     · `reusable` is what allows the memory to be borrowed. A
       carve-out without it is simply removed from the kernel's
       view entirely - which is what you want for a security
       boundary (isolation ch. 18), and not what you want for
       a codec buffer.

   MONITOR:
        cat /proc/meminfo | grep Cma
        CmaTotal:  131072 kB
        CmaFree:    98304 kB                                */

Finding leaks and overruns

Memory bugs in the kernel rarely crash at the point of the mistake; they corrupt something and the machine dies later, somewhere unrelated. The tools below exist to convert those delayed, unreproducible failures into an immediate message naming the exact line — and they are the difference between a bug found in an afternoon and one hunted for a week.

# KASAN - the one that finds real bugs. Enable it in
# development and leave it on.
    CONFIG_KASAN=y
    CONFIG_KASAN_INLINE=y
# Catches: use-after-free, out-of-bounds read and write,
# double-free, use-after-scope. Reports with two backtraces -
# where it was allocated and where it was freed. ~2-3x slower
# and ~1/8 more memory, and worth every bit of it.

# KFENCE - a sampling version, cheap enough for production:
    CONFIG_KFENCE=y
    CONFIG_KFENCE_SAMPLE_INTERVAL=100
# Catches a small fraction of the same bugs at near-zero cost.

# kmemleak - finds objects nothing points to any more:
    CONFIG_DEBUG_KMEMLEAK=y
    echo scan > /sys/kernel/debug/kmemleak
    cat /sys/kernel/debug/kmemleak
# Reports false positives; read them, do not just believe them.

# Slab poisoning and red zones, without full KASAN:
    slub_debug=FZPU              # on the command line
    slub_debug=FZPU,my_request   # or just your cache

# Where memory went:
    cat /proc/meminfo
    sudo slabtop -s c
    cat /proc/vmallocinfo
    cat /proc/buddyinfo
    cat /proc/pagetypeinfo
The allocation-failure message is a diagnosis, not just an error

When an allocation fails the kernel dumps the order requested, the GFP flags, the zone state and a full backtrace. The order tells you whether you hit real exhaustion (order 0 failing) or fragmentation (order 0 fine, order 4 failing) — and those have completely different fixes. Read the dump before concluding you are out of memory.
