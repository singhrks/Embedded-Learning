Floating point and IEEE 754

Floating point trades exactness for range. Understanding the trade precisely is what separates "why is my total off by a cent" from a correct design — and it is unavoidable knowledge for the AI track, where the entire performance story is about shrinking these formats.

The problem

Integers are exact but their range is fixed by their width. A 32-bit integer cannot hold the mass of an electron and the mass of the sun. Scientific notation solves this for humans:

   6.022 × 10²³        significand × base^exponent
   ─┬───   ──┬──
    │        └── move the point this many places
    └─────────── the significant digits

The insight: store the digits and the exponent separately. The point
"floats" to wherever the exponent puts it. Precision stays constant
(a fixed number of significant digits) while range becomes enormous.

IEEE 754 is that idea in binary, standardised in 1985 so every machine produces bit-identical results. Before it, the same program gave different answers on different hardware.

The format

A floating-point number is not one value but three fields packed into a word, in the same way scientific notation has a sign, a mantissa and an exponent. Every quirk of floating-point behaviour follows from how those three are encoded.

Single precision (float, 32 bits)

  31  30      23 22                                    0
 ┌───┬──────────┬──────────────────────────────────────┐
 │ S │ exponent │            fraction                  │
 └───┴──────────┴──────────────────────────────────────┘
   1      8                     23 bits

Double precision (double, 64 bits)

  63  62         52 51                                 0
 ┌───┬─────────────┬────────────────────────────────────┐
 │ S │  exponent   │            fraction                │
 └───┴─────────────┴────────────────────────────────────┘
   1       11                     52 bits

value = (-1)^S  ×  1.fraction  ×  2^(exponent - bias)

  bias = 127 for float, 1023 for double

The three parts

  • Sign (S) — one bit, 0 for positive. Unlike integers, this is a plain flag, which is why floating point has both +0.0 and -0.0.
  • Exponent — stored with a bias rather than as two's complement, so that comparing two positive floats as if they were integers gives the right answer. A stored 130 with bias 127 means an actual exponent of +3.
  • Fraction (mantissa) — the digits after an implied leading 1. Since any normalised binary number starts with 1, storing that bit would waste it. This "hidden bit" buys one extra bit of precision for free.

Worked example: encoding −6.25

1. Sign:  negative  →  S = 1

2. Convert the magnitude to binary
     6.25 = 110.01₂          (4 + 2 + 0.25)

3. Normalise: shift until there is exactly one 1 before the point
     110.01  =  1.1001 × 2²

4. Exponent: actual 2, stored = 2 + 127 = 129 = 1000 0001₂

5. Fraction: the bits after the leading 1, padded to 23 bits
     1001 0000 0000 0000 0000 000

6. Assemble
     1 | 1000 0001 | 100 1000 0000 0000 0000 0000
     = 0xC0C80000

Check it:  printf("%#x\n", *(uint32_t*)&(float){-6.25f});

NaN poisons everything downstream

Any arithmetic involving a NaN produces a NaN. A single bad sample in a signal-processing chain, or one uninitialised weight in a neural network, silently turns an entire output tensor into NaNs with no error raised anywhere. This is why "loss went to NaN" is the most common training failure in machine learning — see AI chapter 15.

Why bfloat16 beat float16 for machine learning

Both are 16 bits. FP16 spends 10 bits on precision and only 5 on exponent; bfloat16 spends 7 on precision and 8 on exponent — exactly FP32's exponent field. Training cares far more about range (gradients spanning many orders of magnitude, which underflow to zero in FP16) than about the third decimal place. bfloat16 also converts to and from FP32 by truncating or padding, with no arithmetic at all.

The thing that surprises everyone

Binary fractions can only represent sums of negative powers of two. 0.5, 0.25 and 0.75 are exact. 0.1 is not — in binary it is a repeating fraction, exactly as 1/3 is in decimal.

0.1 in binary =  0.0001100110011001100110011...  (repeating "0011")

Stored as the nearest float:
    0.100000001490116119384765625

Stored as the nearest double:
    0.1000000000000000055511151231257827021181583404541015625

Therefore:
    0.1 + 0.2  ==  0.30000000000000004     not 0.3
    (0.1 + 0.2) == 0.3   →   FALSE
/* NEVER compare floats for equality */
if (a == b)                                   /* wrong */

/* absolute tolerance — fine when the scale is known */
if (fabs(a - b) < 1e-9)

/* relative tolerance — correct in general */
if (fabs(a - b) <= 1e-9 * fmax(fabs(a), fabs(b)))

/* money: do not use floating point at all */
int64_t cents = 1999;                         /* store the smallest unit  */

Precision is not uniform

Because the exponent scales the whole value, the gap between representable numbers grows with magnitude. This is the most under-appreciated property of the format.

Around this value (float)Gap to the next representable number
1.0≈ 1.2 × 10⁻⁷
1,000≈ 6.1 × 10⁻⁵
1,000,000≈ 0.0625
16,777,216 (2²⁴)2.0 — consecutive integers stop being representable
10⁹≈ 64
 
float x = 16777216.0f;      /* 2^24 */
x = x + 1.0f;               /* x is STILL 16777216.0f — the +1 vanishes */

/* the same effect in a loop: this never terminates */
for (float f = 0; f != 20000000.0f; f += 1.0f)
        ;                   /* increments stop having any effect        */
Absorption and catastrophic cancellation

Absorption: adding a small number to a large one loses the small one entirely, as above. Summing a million small values into a running total therefore loses accuracy progressively — sum smallest first, or use Kahan summation.

Cancellation: subtracting two nearly equal numbers destroys the significant digits. (1.0000001f - 1.0f) keeps almost no meaningful precision, and any subsequent division amplifies the error. Rearranging the algebra to avoid the subtraction is the fix.

Floating point in hardware

An FPU is a large, power-hungry block. Whether one exists, and whether you may use it, is a real design decision:

ContextSituation
Cortex-A (application)FPU and NEON always present; freely usable in user space
Cortex-M0/M3No FPU. Floating point is emulated in software — hundreds of cycles per operation.
Cortex-M4F / M7Single-precision FPU; double precision still emulated
Linux kernelFloating point is effectively forbidden. FP registers are not saved on kernel entry, so using them corrupts user-space state. kernel_fpu_begin() exists but is heavyweight and reserved for special cases.
Interrupt handlersAvoid. FP context save/restore adds latency to every interrupt.
 
# ARM ABI variants — a mismatch produces link errors or silent corruption
arm-none-eabi-gcc -mfloat-abi=soft      # no FPU; library calls, FP args in integer regs
arm-none-eabi-gcc -mfloat-abi=softfp    # uses the FPU, but passes FP args in integer regs
arm-none-eabi-gcc -mfloat-abi=hard      # uses the FPU and passes FP args in FP registers

# deterministic-behaviour flags worth knowing
-ffast-math          # allows reassociation; BREAKS IEEE semantics. Read before enabling.
-ffp-contract=off    # stop the compiler fusing a*b+c into one FMA (changes results)
Fixed point: the usual embedded answer

When there is no FPU, represent fractions as scaled integers. In Q16.16 format, a 32-bit integer holds 16 integer bits and 16 fraction bits — the value is simply the integer divided by 65,536. Addition is plain integer addition; multiplication needs a shift afterwards. It is exact, fast, and deterministic, which is why audio, motor control and DSP code often uses it even on chips that do have an FPU.

typedef int32_t q16;
#define Q16(x)      ((q16)((x) * 65536.0))
#define Q16_MUL(a,b) ((q16)(((int64_t)(a) * (b)) >> 16))
#define Q16_ADD(a,b) ((a) + (b))
