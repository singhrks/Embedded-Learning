Hardware resources and interrupts in WDF

How your driver learns where its registers are and which interrupt is its own, how to map and access them safely, and the WDF interrupt object that connects the ISR and DPC from chapter 11 to real silicon.

The resource list

Your driver does not choose its own registers or interrupt line; the PnP manager assigns them and hands you a list at start-up. Reading that list correctly — and not assuming its contents — is the first step of talking to real hardware.

/* PnP assigns resources and hands you two lists in
   EvtDevicePrepareHardware (chapter 15):

     ResourcesRaw         bus-relative addresses, as the
                          device sees them
     ResourcesTranslated  system addresses the CPU can use

   USE THE TRANSLATED LIST for mapping. Use the RAW list only
   when you must program a bus-relative value into the device
   itself - which is rare on modern systems.              */

NTSTATUS
MyPrepareHardware(_In_ WDFDEVICE Device,
                  _In_ WDFCMRESLIST ResourcesRaw,
                  _In_ WDFCMRESLIST ResourcesTranslated)
{
        PMY_CONTEXT ctx = MyGetContext(Device);
        ULONG i, count;

        PAGED_CODE();
        UNREFERENCED_PARAMETER(ResourcesRaw);

        count = WdfCmResourceListGetCount(ResourcesTranslated);

        for (i = 0; i < count; i++) {
                PCM_PARTIAL_RESOURCE_DESCRIPTOR desc =
                        WdfCmResourceListGetDescriptor(
                                ResourcesTranslated, i);

                switch (desc->Type) {

                case CmResourceTypeMemory:
                case CmResourceTypeMemoryLarge:
                        /* desc->u.Memory.Start   PHYSICAL_ADDRESS
                           desc->u.Memory.Length  ULONG          */
                        if (ctx->RegBase == NULL) {
                                ctx->RegLength =
                                        desc->u.Memory.Length;
                                ctx->RegBase = (PUCHAR)
                                        MmMapIoSpaceEx(
                                          desc->u.Memory.Start,
                                          desc->u.Memory.Length,
                                          PAGE_READWRITE |
                                          PAGE_NOCACHE);
                                if (!ctx->RegBase)
                                        return STATUS_INSUFFICIENT_RESOURCES;
                        }
                        break;

                case CmResourceTypePort:
                        /* legacy I/O ports - x86 only */
                        ctx->PortBase =
                                (PUCHAR)(ULONG_PTR)
                                desc->u.Port.Start.QuadPart;
                        break;

                case CmResourceTypeInterrupt:
                        /* the WDFINTERRUPT created in
                           EvtDeviceAdd is matched to this
                           automatically - nothing to do   */
                        ctx->InterruptVector =
                                desc->u.Interrupt.Vector;
                        break;

                case CmResourceTypeDma:
                        break;      /* chapter 19 */

                case CmResourceTypeConnection:
                        /* a GPIO, I2C or SPI connection, on
                           ACPI-enumerated ARM64 systems.
                           u.Connection.IdLowPart /
                           IdHighPart form a resource hub ID
                           you open with a target
                           (chapter 13's WDFIOTARGET).      */
                        ctx->ConnectionId.LowPart =
                                desc->u.Connection.IdLowPart;
                        ctx->ConnectionId.HighPart =
                                desc->u.Connection.IdHighPart;
                        break;
                }
        }

        if (ctx->RegBase == NULL)
                return STATUS_DEVICE_CONFIGURATION_ERROR;

        return STATUS_SUCCESS;
}

/* NEVER ASSUME THE ORDER OR COUNT of descriptors. A device
   with two memory ranges may report them in either order on
   different firmware. Match on what you find, and fail
   cleanly if something expected is absent - that is what
   turns a mysterious later crash into a clear Code 10 at
   install time.                                            */

Register access

Device registers are not memory. They must be accessed with specific functions that prevent the compiler and processor from caching, reordering or combining the accesses, all of which would be catastrophic.

/* Use the READ_/WRITE_REGISTER_* macros, not raw pointer
   dereferences - the same argument as Linux's readl/writel
   (ch. 25): they guarantee width, ordering and no compiler
   reordering.                                              */

        UCHAR  b = READ_REGISTER_UCHAR (ctx->RegBase + 0x00);
        USHORT w = READ_REGISTER_USHORT((PUSHORT)(ctx->RegBase + 0x02));
        ULONG  l = READ_REGISTER_ULONG ((PULONG)(ctx->RegBase + 0x04));
        ULONG64 q= READ_REGISTER_ULONG64((PULONG64)(ctx->RegBase + 0x08));

        WRITE_REGISTER_ULONG((PULONG)(ctx->RegBase + 0x04), value);

        /* bulk, for FIFOs: */
        READ_REGISTER_BUFFER_ULONG((PULONG)(ctx->RegBase + FIFO),
                                   buffer, count);
        WRITE_REGISTER_BUFFER_ULONG((PULONG)(ctx->RegBase + FIFO),
                                    buffer, count);

/* FOR LEGACY I/O PORTS: */
        READ_PORT_ULONG(), WRITE_PORT_ULONG(), and the
        _BUFFER_ variants.

/* MEMORY BARRIERS, when ordering matters beyond a single
   access: */
        KeMemoryBarrier();           /* full */
        MemoryBarrier();
        _ReadWriteBarrier();         /* compiler only */

/* AND THE DMA CASE: after filling a buffer and before the
   doorbell write, you need the data visible to the device
   first. On Windows the DMA API's flush routines handle this
   (chapter 19); for a common buffer, KeMemoryBarrier() before
   the doorbell is the portable form.                     */

/* A HELPER PAIR worth writing, because it makes every call
   site readable: */
static FORCEINLINE ULONG
MyRd(PMY_CONTEXT ctx, ULONG reg)
{
        return READ_REGISTER_ULONG((PULONG)(ctx->RegBase + reg));
}

static FORCEINLINE VOID
MyWr(PMY_CONTEXT ctx, ULONG reg, ULONG val)
{
        WRITE_REGISTER_ULONG((PULONG)(ctx->RegBase + reg), val);
}

Creating the interrupt object

Creating the interrupt object is what connects your ISR to the hardware line the resource list named. It also establishes the lock that protects data shared between your ISR and everything else.

/* In EvtDeviceAdd - BEFORE resources are assigned. WDF
   matches it to the interrupt descriptor later.           */

        WDF_INTERRUPT_CONFIG interruptConfig;
        WDF_OBJECT_ATTRIBUTES attributes;

        WDF_INTERRUPT_CONFIG_INIT(&interruptConfig,
                                  MyEvtInterruptIsr,
                                  MyEvtInterruptDpc);

        /* optional enable/disable callbacks, called around
           power transitions (chapter 15) */
        interruptConfig.EvtInterruptEnable  = MyIntEnable;
        interruptConfig.EvtInterruptDisable = MyIntDisable;

        WDF_OBJECT_ATTRIBUTES_INIT_CONTEXT_TYPE(&attributes,
                                        MY_INTERRUPT_CONTEXT);

        status = WdfInterruptCreate(device, &interruptConfig,
                                    &attributes,
                                    &ctx->Interrupt);

/* THE ENABLE/DISABLE CALLBACKS run at DIRQL with the
   interrupt lock held, and are the right place to touch the
   device's interrupt-enable register: */

NTSTATUS
MyIntEnable(_In_ WDFINTERRUPT Interrupt, _In_ WDFDEVICE Device)
{
        PMY_CONTEXT ctx = MyGetContext(Device);

        MyWr(ctx, REG_INT_ENABLE, INT_ALL);
        return STATUS_SUCCESS;
}

NTSTATUS
MyIntDisable(_In_ WDFINTERRUPT Interrupt, _In_ WDFDEVICE Device)
{
        PMY_CONTEXT ctx = MyGetContext(Device);

        MyWr(ctx, REG_INT_ENABLE, 0);
        return STATUS_SUCCESS;
}

/* WDF calls Enable after connecting the interrupt and Disable
   before disconnecting it - which is exactly the ordering
   that avoids a spurious interrupt with no handler
   (chapter 15).                                            */

Message-signalled interrupts

Modern buses do not use dedicated interrupt wires. They signal by writing to a special memory address, which allows many more interrupt vectors per device and removes the sharing problems that plagued line-based interrupts.

/* MSI/MSI-X: a PCIe device signals by WRITING to a special
   address rather than asserting a line.

   ADVANTAGES:
     · no sharing, so no "is it mine?" check needed
     · several messages per device, each with its own ISR -
       one per queue, one per channel
     · inherently ordered with respect to the DMA writes that
       preceded them, which removes a whole class of
       "interrupt arrived before the data" races           */

/* THE INF requests them: */
        [MyDevice_AddReg]
        HKR,"Interrupt Management",,0x00000010
        HKR,"Interrupt Management\MessageSignaledInterruptProperties",,0x00000010
        HKR,"Interrupt Management\MessageSignaledInterruptProperties",\
            MSISupported,0x00010001,1
        HKR,"Interrupt Management\MessageSignaledInterruptProperties",\
            MessageNumberLimit,0x00010001,4

/* AND THE DRIVER creates one WDFINTERRUPT PER MESSAGE: */
        for (i = 0; i < MY_NUM_MESSAGES; i++) {
                WDF_INTERRUPT_CONFIG_INIT(&interruptConfig,
                                MyEvtInterruptIsr,
                                MyEvtInterruptDpc);

                status = WdfInterruptCreate(device,
                                &interruptConfig, &attributes,
                                &ctx->Interrupts[i]);
                if (!NT_SUCCESS(status))
                        return status;

                ictx = MyGetInterruptContext(ctx->Interrupts[i]);
                ictx->MessageIndex = i;
        }

/* The ISR receives the message id: */
BOOLEAN
MyEvtInterruptIsr(_In_ WDFINTERRUPT Interrupt,
                  _In_ ULONG MessageID)
{
        /* With MSI, MessageID identifies WHICH message fired -
           so you often need no status-register read at all,
           which makes the ISR dramatically cheaper.       */
        ...
}

/* IF FEWER MESSAGES ARE GRANTED than you asked for, the
   remaining ones map onto message 0. Handle that: check
   WdfInterruptGetInfo() for what you actually got, and do not
   assume the count.                                       */

        WDF_INTERRUPT_INFO info;

        WDF_INTERRUPT_INFO_INIT(&info);
        WdfInterruptGetInfo(ctx->Interrupts[0], &info);
        /* info.MessageSignaled, info.MessageNumber,
           info.Vector, info.Irql, info.TargetProcessorSet  */
MSI removes the shared-line problem

A line-based interrupt may be shared, so every ISR must read a status register to ask "is this mine?" — and that read can cost microseconds on PCIe. An MSI is by definition yours, and the message number tells you what happened. On any device where you control the hardware design or the interrupt count, MSI-X with one message per queue is both faster and simpler.

Synchronising with the ISR

Data touched by an ISR cannot be protected by an ordinary lock, because the ISR runs above the level such a lock raises to. The framework provides a way to run a small piece of code at the ISR's own level instead.

/* Data shared between the ISR and everything else needs the
   interrupt lock (chapter 10).                            */

/* Option 1: acquire it around a section */
        WdfInterruptAcquireLock(ctx->Interrupt);
        ctx->SharedState = newValue;
        MyWr(ctx, REG_CONFIG, newValue);
        WdfInterruptReleaseLock(ctx->Interrupt);

/* Option 2 - PREFERRED: run a small function at DIRQL with
   the lock held: */
static BOOLEAN
MySetEnableSync(_In_ WDFINTERRUPT Interrupt,
                _In_ WDFCONTEXT Context)
{
        PMY_CONTEXT ctx = (PMY_CONTEXT)Context;

        ctx->Enabled = TRUE;
        MyWr(ctx, REG_INT_ENABLE, INT_ALL);
        return TRUE;
}

        WdfInterruptSynchronize(ctx->Interrupt,
                                MySetEnableSync, ctx);

/* WHY OPTION 2 IS BETTER: the critical section is a named
   function whose entire body is visible, so it is obvious it
   is short and does nothing forbidden at DIRQL. An
   Acquire/Release pair invites someone to add a line in the
   middle later.                                            */

/* NOTE: with a PASSIVE-LEVEL interrupt (chapter 11), the
   interrupt "lock" is a passive-level lock and you MAY sleep
   inside it. WdfInterruptSynchronize still works and still
   serialises correctly.                                   */

Interrupt affinity and policy

On a multiprocessor machine you can influence which processors service your interrupt. This matters for latency-sensitive devices, and like most such controls it makes things worse about as easily as better.

/* Which CPU handles the interrupt, and at what priority.
   Set from the INF, not from code - it is a system policy
   decision, and the administrator may override it.        */

        [MyDevice_AddReg]
        HKR,"Interrupt Management\Affinity Policy",\
            DevicePolicy,0x00010001,5    ; IrqPolicySpreadMessagesAcrossAllProcessors
        HKR,"Interrupt Management\Affinity Policy",\
            DevicePriority,0x00010001,3  ; IrqPriorityHigh

/* THE POLICIES:
     0  MachineDefault
     1  AllCloseProcessors
     2  OneCloseProcessor
     3  AllProcessorsInMachine
     4  SpecifiedProcessors
     5  SpreadMessagesAcrossAllProcessors   <-- for MSI-X

/* SPREADING MSI-X MESSAGES across CPUs is what lets a
   multi-queue device scale: each message's DPC runs on a
   different core, so DPC processing is parallel rather than
   serialised on one CPU (chapter 11).

/* FROM CODE, if you must: */
        WdfInterruptSetPolicy(ctx->Interrupt,
                        WdfIrqPolicySpecifiedProcessors,
                        WdfIrqPriorityNormal,
                        1 << 2);        /* CPU 2 */

/* And read what you got: */
        WdfInterruptGetInfo(interrupt, &info);
        /* info.TargetProcessorSet */

Debugging resources and interrupts

When an interrupt never fires, the debugger can show you what the PnP manager actually assigned and whether your ISR is connected — which distinguishes a driver bug from a firmware or INF problem.

# --- Device Manager ---
#   Properties -> Resources tab: exactly what was assigned.
#   If a range or IRQ you expect is missing, the problem is in
#   the firmware or the INF, not your driver.

# --- WinDbg ---
    !devnode 0 1 mydriver           the PnP node
    !devobj ffff8a0c...             the device object
    !arbiter 4                      the resource arbiters -
                                    who owns which ranges
    !idt                            the interrupt dispatch
                                    table: which vector goes
                                    where
    !wdfkd.wdfdriverinfo mydriver 0x10   WDF's view of the
                                    interrupt objects

# --- Is my interrupt firing at all? ---
#   Add a counter in the ISR and expose it in a debug IOCTL or
#   read it with WinDbg. If it never increments:
#     · the device is not enabled - check REG_INT_ENABLE
#     · the interrupt was never connected - check the
#       WdfInterruptCreate return
#     · the resource descriptor was absent - check
#       PrepareHardware
#     · the device is not clocked or not out of reset
#     · MSI was requested but not granted, and you assumed it
#
#   THE SAME CHECKLIST as Linux chapter 16, in a different
#   dialect.

# --- ETW tracing of interrupts and DPCs ---
    wpr -start GeneralProfile -start DeviceIO
    ... reproduce ...
    wpr -stop trace.etl
    wpa trace.etl
# The "DPC/ISR" graph shows every ISR and DPC with durations.
# It is the tool for "why is this system's latency bad", and
# it will show your DPC's cost next to everyone else's.
