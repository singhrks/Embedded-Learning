Performance: measuring, and where Rust is not free

"Zero-cost abstractions" is true and routinely misquoted. It means you could not have written it faster by hand — not that everything is free. This chapter is about the abstractions that genuinely cost nothing, the ones that cost something, and how to tell which is which on your code rather than in the abstract.

What the claim actually says

The phrase has a precise meaning and a common misreading, and the gap between them explains most disappointment about Rust performance.

   THE CLAIM: "What you don't use, you don't pay for. What
   you do use, you could not hand-code any better."

   IT IS A CLAIM ABOUT THE ABSTRACTION, not about the
   program. An iterator chain compiles to the loop you would
   have written. It does NOT promise that the loop you would
   have written was a good idea.

   ---------------------------------------------------------

   GENUINELY FREE, after optimisation:

     · iterator chains          -> the equivalent loop
     · generics                 -> monomorphised, inlined
     · Option<&T>               -> one pointer. The niche
                                   optimisation uses the
                                   null value as None, so
                                   it is the same size as
                                   &T
     · newtype wrappers         -> nothing at all
     · Result in a hot path     -> a tag and a branch, the
                                   same as a C error return
     · bounds checks IN A LOOP  -> usually hoisted or
                                   eliminated when the
                                   compiler can prove the
                                   range

   NOT FREE, and each one is a real decision:

     · dyn Trait                -> an indirect call that
                                   cannot be inlined
     · Box, Rc, Arc             -> allocation; Arc adds
                                   atomic refcount traffic
     · RefCell                  -> a runtime flag check, and
                                   a panic path
     · bounds checks the compiler CANNOT prove away
     · .clone() and .to_string() -> exactly what they say
     · Mutex                    -> a real lock
     · format! / println!       -> allocation plus the
                                   formatting machinery,
                                   which is surprisingly
                                   large on embedded

   ---------------------------------------------------------

   THE HONEST HEADLINE: idiomatic Rust and careful C land in
   the same place for most systems work. Where Rust tends to
   win is that the SAFE version is fast enough that nobody
   reaches for the unsafe one - and where it tends to lose is
   an interface that forced an allocation or a clone that C
   would have handled with a pointer.

Measure first, and measure properly

Every instinct in this chapter is worth less than one measurement, and microbenchmarks are unusually easy to get wrong in a language that optimises this aggressively.

// The trap, in full:
fn bench_bad() {
    let start = Instant::now();
    for _ in 0..1_000_000 {
        checksum(&data);          // result unused
    }
    println!("{:?}", start.elapsed());
}
// The compiler can see the result is never used, and delete
// the call. You have measured an empty loop. The giveaway
// is a suspiciously round, suspiciously small number.

// The fix is to hide the value from the optimiser:
use std::hint::black_box;

for _ in 0..1_000_000 {
    black_box(checksum(black_box(&data)));
}
// black_box on the INPUT too, or constant folding may
// compute the answer once at compile time.

/* WHAT TO USE INSTEAD OF HAND-ROLLING THIS:

     criterion    the standard benchmarking crate. Warms up,
                  runs to a statistical confidence, and
                  reports whether a change is a real
                  regression or noise - which is the part
                  you cannot eyeball.

     cargo bench  built in, nightly only for the harness.

   AND FOR FINDING WHAT TO OPTIMISE, rather than confirming
   a guess:

     perf / VTune         where the time goes
     cargo-flamegraph     the same, readable in one picture
     cargo-bloat          where the BINARY SIZE goes, which
                          is the metric that matters on a
                          microcontroller
     cargo-llvm-lines     which generic got monomorphised
                          three hundred times                */
Always measure a release build, and know what changes

A debug build is routinely ten to fifty times slower than release, and the difference is not uniform — it falls hardest on exactly the abstractions this chapter is about, because none of them are inlined yet. Debug builds also insert integer-overflow checks that release builds omit. Timing a debug build tells you almost nothing, and the conclusions people draw from it ("iterators are slow", "Rust is slower than C") are artefacts of the profile rather than facts about the language.

Where the wins usually are

In practice the same handful of things account for most of the difference between slow and fast Rust, and none of them require unsafe.

ProblemFixTypical effect
Allocating in a loopHoist the buffer out and clear() it, or use with_capacityOften the largest single win
clone() to silence the borrow checkerRestructure so a borrow works — chapter 03's techniquesRemoves a copy per call
collect() into a temporary that is immediately iteratedKeep the iterator lazyRemoves an allocation and a pass
Bounds checks in a hot loopIterate rather than index, or slice once up front so the compiler can prove the rangeReal, but smaller than people assume
dyn Trait on a hot pathGenerics, or an enum of the known implementationsEnables inlining, which is the actual win
Arc where Rc or a borrow would doUse the cheapest that compilesRemoves atomic traffic between cores
Hashing short keys with the default hasherA faster hasher where DoS resistance is not neededNoticeable in map-heavy code
Generic code instantiated for many typesAn inner non-generic function doing the workCuts compile time and binary size

Notice the pattern: almost every row is about memory traffic rather than instruction count. That is the same lesson as the matmul chapter in the AI track and the cache chapters in the ARM track — on modern hardware, the interesting variable is usually what you moved, not what you computed.

Size, which is the embedded metric

On a microcontroller the binding constraint is flash and RAM rather than cycles, and Rust's defaults are not tuned for it. The settings below routinely move a firmware image by a large factor.

# Cargo.toml - the release profile for firmware
[profile.release]
opt-level     = "z"     # optimise for size ("s" is milder)
lto           = true    # link-time optimisation, across crates
codegen-units = 1       # one unit: slower build, smaller output
panic         = "abort" # no unwinding machinery at all
strip         = true    # drop symbols from the final binary
debug         = false

# THE BIGGEST SINGLE WIN IS USUALLY panic = "abort". Unwinding
# drags in the landing-pad tables and the whole panic
# formatting path, and on a device with no operating system
# there is nothing meaningful to unwind TO.

# THE SECOND BIGGEST IS AVOIDING core::fmt. One println!-style
# formatting call pulls in the formatting machinery, which can
# be tens of kilobytes. Use defmt instead: it sends the format
# STRING INDEX and the arguments over the wire and does the
# formatting on the host. The strings never enter the binary.

# FIND OUT WHERE IT WENT rather than guessing:
#   cargo bloat --release -n 30        biggest functions
#   cargo bloat --release --crates     biggest crates
#   cargo size --release -- -A         section sizes

When reaching for unsafe is not the answer

The temptation, on finding a bounds check in a profile, is to remove it with get_unchecked. This is almost always a bad trade, and it is worth knowing why before you make it.

   THE ARITHMETIC:

     A BOUNDS CHECK is a compare and a predictable branch.
     The branch predictor gets it right essentially every
     time, because it never fires. On a superscalar core it
     is frequently FREE - it fits in an issue slot that was
     otherwise idle.

     WHAT IT COSTS INSTEAD is that it can block
     vectorisation, which IS significant - but the fix for
     that is usually to give the compiler the information
     it needs, not to remove the check.

   ---------------------------------------------------------

   THE ORDER TO TRY THINGS:

     1. ITERATE INSTEAD OF INDEXING. An iterator has no
        bounds check to eliminate, because it cannot go out
        of bounds by construction.

     2. SLICE ONCE, UP FRONT.
          let a = &a[..n];  let b = &b[..n];
          for i in 0..n { a[i] + b[i] }
        The compiler now proves the range once and drops
        the per-iteration checks.

     3. USE zip, chunks_exact, windows. chunks_exact in
        particular tells the optimiser the length is a
        multiple of N, which is frequently what unlocks
        vectorisation.

     4. MEASURE AGAIN. Usually you are done.

     5. ONLY THEN consider get_unchecked - and if you do,
        write down the invariant that makes it sound, and
        put the crate under Miri (chapter 12).

   ---------------------------------------------------------

   THE POINT: every step before 5 keeps the guarantee. Step 5
   trades a permanent safety property for a performance gain
   you have not yet demonstrated. Demonstrate it first.
