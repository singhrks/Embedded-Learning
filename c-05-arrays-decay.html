Arrays, decay and pointer arithmetic

"Arrays are pointers" is the most repeated falsehood in C teaching. Arrays and pointers are different types with different sizes and different semantics. They are connected by one specific rule — decay — and understanding exactly where it applies and where it does not resolves nearly every array confusion.

Arrays are not pointers

The single most consequential misconception in C is that arrays and pointers are the same thing. They are not — they have different sizes, different addresses of a sort, and different behaviour — and the places where they appear identical are exactly where the confusion starts.

int a[10];
int *p = a;

sizeof(a)      /* 40 — the whole array          */
sizeof(p)      /* 8  — one pointer              */

&a             /* type int(*)[10] — pointer to array of 10 int */
&p             /* type int**                                    */

&a + 1         /* advances 40 bytes — past the whole array      */
&p + 1         /* advances 8 bytes                              */

a = p;         /* ERROR: an array is not assignable             */
p = a;         /* fine: decay                                    */
The decay rule, stated exactly

In most expression contexts, an expression of type "array of T" is converted to "pointer to T", pointing at the first element.

The four exceptions — the only places an array stays an array:

  1. Operand of sizeof
  2. Operand of & (address-of)
  3. Operand of _Alignof
  4. A string literal used to initialise a character array

Everywhere else — assignment, arithmetic, comparison, function arguments — the array decays.

char s[] = "hello";      /* exception 4: initialises the array,
                            so s is 6 bytes and MUTABLE          */
char *t  = "hello";      /* decay: t points at a string LITERAL,
                            which you must not modify            */

s[0] = 'H';              /* fine                                 */
t[0] = 'H';              /* UNDEFINED — literals may be in ROM,
                            and on many targets they are         */

/* Declare pointers to literals as const to make the compiler help: */
const char *t = "hello";
t[0] = 'H';              /* now a compile error, as it should be  */

Array parameters are a lie

This is where the illusion becomes most misleading: an array parameter is silently rewritten by the language into a pointer, so the size information you appear to have written is discarded entirely.

These four declarations are IDENTICAL. The compiler rewrites all of
them to the last one.

    void f(int a[10]);
    void f(int a[100]);
    void f(int a[]);
    void f(int *a);        <- what the compiler actually sees

Consequences you must internalise:

  · sizeof(a) inside f is sizeof(int*), NOT the array size
  · the bound in the declaration is documentation, nothing more
  · the compiler will NOT check that you passed 10 elements
  · you must pass the length separately. Always.
/* the bug this causes, constantly */
void process(int a[10])
{
        size_t n = sizeof(a) / sizeof(a[0]);   /* 8/4 = 2, not 10 */
        for (size_t i = 0; i < n; i++)          /* processes 2 elements */
                ...
}
/* -Wsizeof-pointer-div warns about exactly this. Enable it. */

/* the correct signature */
void process(int *a, size_t n);
void process(size_t n, int a[n]);    /* C99: documents intent, and
                                        some compilers can check it */

/* C99 static array parameters — a promise of a minimum size.
   GCC and Clang will warn if you pass fewer or pass NULL.        */
void process(int a[static 10]);      /* "at least 10 elements"    */

Multidimensional arrays

Multidimensional arrays in C are genuinely two-dimensional, not arrays of pointers — and the difference in memory layout matters both for performance and for what you can legally pass to a function.

C has no 2-D arrays. It has arrays OF arrays, stored contiguously
in row-major order.

    int m[3][4];

    memory layout, 48 bytes, one contiguous block:
    +--------------+--------------+--------------+
    | m[0][0..3]   | m[1][0..3]   | m[2][0..3]   |
    +--------------+--------------+--------------+
     ^              ^
     m[0]           m[1]        each is an int[4]

    m           type int(*)[4] after decay — pointer to a ROW
    m[0]        type int[4], decays to int*
    m[0][0]     type int
    *(*(m+1)+2) == m[1][2]

    sizeof(m)      48    the whole thing
    sizeof(m[0])   16    one row
    sizeof(m[0][0]) 4    one element

  The address computation the compiler emits for m[i][j]:
      base + (i * 4 + j) * sizeof(int)
  The COLUMN COUNT is baked into the type. That is why it cannot be
  omitted in a parameter declaration.
/* passing a 2-D array: all but the FIRST bound are required */
void f(int m[3][4]);      /* rewritten to int (*m)[4]  */
void f(int m[][4]);       /* same                       */
void f(int (*m)[4]);      /* what it really is          */
void f(int **m);          /* WRONG — a different type entirely */

/* C99 VLA parameters make it general and self-documenting */
void f(size_t rows, size_t cols, int m[rows][cols])
{
        m[i][j] = 0;      /* indexing works naturally */
}

/* the portable pre-C99 alternative: flatten it yourself */
void f(int *m, size_t rows, size_t cols)
{
        m[i * cols + j] = 0;
}
int ** is not a 2-D array

An int[3][4] is one contiguous 48-byte block. An int ** is a pointer to an array of pointers, each pointing to a separately allocated row — four allocations, scattered in memory, and an extra dereference per access. They are incompatible types and behave differently for cache locality (CA ch. 13). Passing one where the other is expected is a type error that a cast will silence and then crash.

Allocating arrays

Allocating a two-dimensional array dynamically can be done in two quite different ways, with different memory layouts, different performance and different cleanup requirements.

/* 1-D: straightforward. Note `sizeof *a` rather than `sizeof(int)`. */
int *a = malloc(n * sizeof *a);
if (!a) return -ENOMEM;

/* Guard the multiplication — n * size can overflow (chapter 02) */
if (n > SIZE_MAX / sizeof *a) return -EOVERFLOW;
int *a = malloc(n * sizeof *a);
/* or */
int *a = calloc(n, sizeof *a);     /* calloc checks internally, and zeroes */

/* 2-D contiguous — ONE allocation, best locality, index arithmetic */
int (*m)[COLS] = malloc(rows * sizeof *m);
m[i][j] = 0;                        /* natural syntax, contiguous storage */
free(m);

/* 2-D "jagged" — N+1 allocations, worse locality, but rows may differ
   in length and can be reallocated independently                     */
int **m = malloc(rows * sizeof *m);
for (size_t i = 0; i < rows; i++)
        m[i] = malloc(cols * sizeof **m);
/* ...and you must free every row before freeing m */

/* Flat with manual indexing — one allocation, works pre-C99,
   and the shape is a runtime value                                */
int *m = malloc(rows * cols * sizeof *m);
#define M(i, j) m[(i) * cols + (j)]

Variable-length arrays

Arrays whose size is decided at run time look convenient and carry risks that make them banned in much systems code — most importantly that the size often comes from somewhere you do not control.

void f(size_t n)
{
        int a[n];          /* C99 VLA: size determined at runtime */
        ...
}                          /* automatically freed at scope exit    */

/* Attractive, and largely a trap in systems code: */
ProblemDetail
Stack overflowA large or attacker-controlled n silently blows the stack. No error, no diagnostic — just corruption or a crash. Kernel stacks are 8–16 KB.
No failure pathUnlike malloc, there is no way to detect that allocation failed
OptionalMade optional in C11; MSVC has never supported them
Hidden costPrevents some optimisations; the frame size becomes dynamic
BannedThe Linux kernel removed all VLAs in 2018 and builds with -Wvla. MISRA C forbids them.
 
/* Use them only for VLA PARAMETERS, which are pure documentation
   and generate no allocation:                                    */
void matmul(size_t n, size_t m, double a[n][m]);   /* good use     */

/* Otherwise: a fixed bound with a check, or heap allocation */
if (n > MAX_ITEMS) return -EINVAL;
int a[MAX_ITEMS];
/* or */
int *a = malloc(n * sizeof *a);

Flexible array members

A structure ending in an array of unspecified size lets you allocate a header and its variable-length payload as one block. It is the standard idiom for packets and messages, and it has one arithmetic trap.

/* The idiomatic way to allocate a header plus a variable-length
   payload in ONE allocation. C99 standardised it.               */
struct packet {
        uint32_t len;
        uint8_t  type;
        uint8_t  data[];        /* flexible array member — must be LAST,
                                   and cannot be the only member       */
};

struct packet *p = malloc(sizeof *p + payload_len);
p->len = payload_len;
memcpy(p->data, payload, payload_len);
/* one allocation, one free, contiguous, cache-friendly */

/* sizeof(struct packet) does NOT include data[] — it is 8 here.
   Guard the addition against overflow:                          */
if (payload_len > SIZE_MAX - sizeof *p) return -EOVERFLOW;

/* Linux provides helpers that do this correctly: */
p = kmalloc(struct_size(p, data, payload_len), GFP_KERNEL);

/* The old pre-C99 hack you will still meet, and should not copy: */
uint8_t data[1];        /* "struct hack" — technically UB to index past [0] */
uint8_t data[0];        /* GNU extension, same idea                          */

Bounds are never checked

C does not check array bounds, so overrunning one is not an error the language will report — it simply corrupts whatever is next. These are the practical ways to get checking back.

int a[10];
a[10] = 0;        /* one past the end — undefined, and usually silent */
a[-1] = 0;        /* also undefined                                    */
a[1000000] = 0;   /* also undefined; may or may not fault              */

/* C performs NO bounds checking, ever. `a[i]` is defined as
   `*(a + i)` and that is all the compiler does.

   This is the root of the buffer overflow, which remains one of the
   most exploited vulnerability classes in existence — because on the
   stack, writing past an array reaches the saved return address.   */
Stack layout during a classic overflow

   higher addresses
   +---------------------+
   | saved return address|  <-- overwrite this and you control the PC
   +---------------------+
   | saved frame pointer |
   +---------------------+
   | char buf[64]        |  <-- gets(buf) writes as much as it is given
   +---------------------+
   lower addresses

Mitigations, none of which are a substitute for correct code:

  stack canaries    -fstack-protector-strong   detect on return
  non-executable stack                          make the payload harder
  ASLR                                          make addresses unknown
  FORTIFY_SOURCE    -D_FORTIFY_SOURCE=2        compile/run-time checks
  ASan              -fsanitize=address          catch it in testing
/* the discipline */
#define ARRAY_SIZE(a)  (sizeof(a) / sizeof((a)[0]))    /* on real arrays only */

for (size_t i = 0; i < ARRAY_SIZE(a); i++)   /* never a hardcoded bound */
        use(a[i]);

/* validate every index that came from outside */
if (idx >= ARRAY_SIZE(table))
        return -EINVAL;
return table[idx];

/* pass length with pointer, always */
void process(const uint8_t *data, size_t len);

/* and in security-sensitive code, mask rather than branch, so the
   check survives speculation (see CA chapter 12): */
idx = array_index_nospec(idx, ARRAY_SIZE(table));

Arrays of characters versus strings

C strings are just arrays with a convention, which means every rule above applies to them, plus one more: the terminator has to be there, and nothing enforces that it is.

/* A "string" in C is a convention, not a type: a char array whose
   contents end with '\0'.                                        */

char a[6] = "hello";      /* 5 chars + terminator — exactly fits  */
char b[5] = "hello";      /* legal in C! No terminator. NOT a string.
                             Passing b to strlen() runs off the end. */
char c[]  = "hello";      /* size 6, deduced — prefer this        */

sizeof("hello")   /* 6 — includes the terminator */
strlen("hello")   /* 5 — does not               */

/* This distinction is the source of a large fraction of C's
   buffer bugs. Chapter 06 covers string handling in full.     */
