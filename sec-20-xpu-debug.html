Debugging access-control failures

The last chapter of the track, and the one you will actually use. Something is being refused, or worse, silently ignored. Here is how to find out what, who, and why — starting from the two symptoms that look nothing like an access-control problem.

The two faces of a denial

Access-control failures rarely announce themselves as permission errors. They appear as a device that does not work, a read that returns zeros, or a hang — which is why they are so often misattributed.

  LOUD: an abort.

     Linux:  "Synchronous External Abort" / "SError Interrupt"
     TF-A:   an EL3 crash dump
     DMA:    a channel error, a device timeout
     SMMU:   an event in the event queue (chapter 06)

     Annoying, but honest. You get an address and often a
     master.

  SILENT: reads return 0, writes vanish.

     "The device isn't present."
     "The ID register reads 0x00000000."
     "DMA completes but the buffer is unchanged."
     "It works on the dev board."

     THIS is the one that costs a week. There is no error
     anywhere in the system, and every layer reports success.
     The driver author reasonably concludes the hardware is
     broken or the address is wrong.

  THE TELL for the silent case:

     an MMIO read returning EXACTLY 0x00000000 or 0xFFFFFFFF
     from a register that should have a fixed non-zero value -
     an ID, a version, a revision - is an access problem until
     proven otherwise. Real hardware that is present and
     clocked almost never reads back all-zeros from its ID
     register.

     0x00000000  usually: RAZ/WI denial, or the block is in
                 reset, or unclocked
     0xFFFFFFFF  usually: nothing decodes this address at all,
                 or the bus returned an error that got
                 swallowed

Triage: five questions in order

Given an unexplained failure, a short ordered set of questions distinguishes an access-control denial from an ordinary driver bug quickly.

/* Work down this list. Each step is cheap and eliminates a
   large class.                                              */

1. IS THE BLOCK POWERED, CLOCKED, AND OUT OF RESET?
      By far the most common cause of all-zero reads, and it is
      not an access-control problem at all.
      -> check the clock and reset drivers, /sys/kernel/debug/clk,
         and the power domain state. Enable the clock by hand
         and read again.

2. IS THE ADDRESS RIGHT?
      Compare the DT reg property against the TRM. Check you
      are reading the right instance - SoCs have four UARTs and
      three of them are wired to nothing.
      -> devmem2 / busybox devmem from userspace, on a
         neighbouring register you know the value of.

3. IS THIS ACCESS DENIED?
      Now the interesting question. Read the XPU fault
      registers, the SMMU event queue, the TZASC fail status.
      -> details below.

4. WHICH MASTER, AND WHICH REGION?
      A fault register usually gives you both. If not,
      bisect - see "when there is no fault register".

5. IS THE POLICY WRONG, OR IS THE CODE WRONG?
      A denial is often CORRECT: the driver really is touching
      something it should not, using the wrong buffer, or
      running on the wrong master. Fix the code before you
      widen the policy. Widening is the last resort, not the
      first.                                                */
The instinct to resist

When a denial appears, the fastest way to make it go away is to open the region. That is almost always the wrong fix, and it is how policies rot (chapter 19). Ask first: why is this master touching this address? Half the time the honest answer reveals a bug — a stale pointer, a buffer allocated from the wrong pool, a DMA descriptor never updated — and the XPU has just done you a large favour.

Decoding a CPU abort

When the processor is the blocked master, the fault arrives through the ordinary exception path — and decoding it is the ARM track's syndrome register work applied here.

Unhandled fault: synchronous external abort (0x96000010)
  at 0xffff800008a01000
[0000000000000000] ESR = 0x96000010

/* ESR_EL1 = 0x96000010, decoded (ARM chapter 29):

     EC   = 0b100101 (0x25)  Data Abort, same EL
     ISV  = 0                no instruction syndrome
     DFSC = 0b010000 (0x10)  SYNCHRONOUS EXTERNAL ABORT,
                             not on a translation table walk

   DFSC 0x10 means: the MMU translated it fine, the transaction
   went out to the bus, AND SOMETHING OUT THERE SAID NO.

   That "something" is an XPU, a TZASC, a peripheral that does
   not decode the address, or a slave in reset. The CPU cannot
   tell you which - it only knows the bus said no.

   FAR_EL1 holds the virtual address. Convert it to physical:
        virt_to_phys(), or read the translation with AT S1E1R
        and TTBR-walk it, or just look at the ioremap that
        produced it.                                         */

/* SYNCHRONOUS vs ASYNCHRONOUS - and this matters a lot:

   Synchronous external abort (DFSC 0x10)
        the faulting instruction is in ELR. Device memory
        (nGnRnE/nGnRE) accesses fault synchronously, so MMIO
        denials point straight at the offending line.

   SError / asynchronous
        a WRITE to Normal memory was posted and completed long
        ago from the CPU's point of view. The abort arrives
        whenever the write finally reached the denier - which
        may be thousands of instructions later, in unrelated
        code, on a different task.
        -> the reported PC IS NOT THE CULPRIT. Do not spend a
           day analysing it.

   TAMING AN SError: insert `dsb sy` after the suspect writes to
   force them to complete, and the abort becomes synchronous
   enough to localise. Or bisect by disabling one master at a
   time.                                                     */

Reading XPU fault registers

When a non-CPU master is blocked, the access control unit itself records what happened. Finding and reading that record is the equivalent of reading an SMMU event.

/* Every XPU worth using latches the FIRST fault. Read it. */

void xpu_dump_fault(uintptr_t xpu)
{
        uint32_t st = mmio_read32(xpu + XPU_ERR_STATUS);
        uint64_t addr;

        if (!(st & XPU_ERR_VALID)) {
                INFO("xpu: no fault latched\n");
                return;
        }

        addr  = (uint64_t)mmio_read32(xpu + XPU_ERR_ADDR_HI) << 32;
        addr |= mmio_read32(xpu + XPU_ERR_ADDR_LO);

        ERROR("XPU FAULT\n"
              "  address   : 0x%016llx\n"
              "  master ID : 0x%02x (%s)\n"
              "  direction : %s\n"
              "  security  : %s\n"
              "  privileged: %s\n"
              "  multiple  : %s\n",
              addr,
              mmio_read32(xpu + XPU_ERR_MASTER),
              master_name(mmio_read32(xpu + XPU_ERR_MASTER)),
              (st & XPU_ERR_WRITE)  ? "write" : "read",
              (st & XPU_ERR_NS)     ? "non-secure" : "secure",
              (st & XPU_ERR_PRIV)   ? "privileged" : "unprivileged",
              (st & XPU_ERR_OVF)    ? "yes - more faults occurred"
                                    : "no");

        mmio_write32(xpu + XPU_ERR_CLEAR, 1);   /* re-arm */
}

/* THE OVERFLOW BIT MATTERS. Only the first fault is latched;
   later ones set overflow and are lost. So:

     · clear the fault as soon as you have logged it
     · if overflow is set, you are seeing one of many - fix
       that one, re-run, and look again
     · a repeating fault at 60 Hz is a display or DMA loop;
       one fault at boot is a probe.

/* WIRE THE INTERRUPT UP. An XPU fault interrupt handled in EL3
   that prints this block is worth more than any amount of
   after-the-fact analysis. Do it once, at the start of a
   project, and every subsequent access bug takes minutes.  */

The other reporters

Several other blocks on an SoC can also report a denied access, and knowing which reporters exist on your platform saves searching the wrong log.

BlockWhere the evidence is
SMMUThe event queue: StreamID, SubstreamID, IOVA, fault reason. See chapter 06 — richest source on the SoC.
TZC-400FAIL_ADDRESS_LOW/HIGH, FAIL_CONTROL (direction, NS, privilege), FAIL_ID (master), per filter unit.
InterconnectSome NoCs have error probes logging the initiator, target, opcode and a timestamp — check whether yours does before building a bisect harness.
TF-AIts exception handlers print an EL3 crash dump with all the ESR/FAR context.
Linuxdmesg: external aborts, SErrors, arm-smmu fault lines, rcu stalls if the secure world hung.
The DMA enginePer-channel error status, often with the descriptor address that failed — which tells you the buffer, not just the address.

When there is no fault register

The hardest case: a denial that reports nothing at all, because the hardware was configured to return zeros silently. This is how to find those.

/* RAZ/WI denials with no logging. You have no evidence, so
   MANUFACTURE some.                                         */

/* TECHNIQUE 1: switch to error responses.
   Most blocks can be told to abort instead of ignoring, even
   if production ships quiet. One build flag turns a
   week-long mystery into a stack trace.                    */
        mmio_write32(xpu + XPU_CTRL, ctrl | XPU_CTRL_ERR_RESP);

/* TECHNIQUE 2: probe from a known-good master.
   Read the same address from EL3 firmware, which is usually
   allowed everything. If EL3 sees the right value and Linux
   sees zeros, it is a policy question, not a hardware one. */

/* TECHNIQUE 3: bisect the policy.
   Open regions one at a time until it works. The one that
   fixes it names the resource; the failing master follows from
   which driver you were exercising. Crude, always works.   */

/* TECHNIQUE 4: bisect the masters.
   Hold subsystems in reset, or disable their DT nodes, one at
   a time. When the corruption stops, the last one you disabled
   is the culprit. This is the standard way to find a rogue
   DMA writer with no XPU at all.                           */

/* TECHNIQUE 5: a canary region.
   Fill a page with a pattern, deny everyone, and scan it
   periodically. If it changes, something is writing where it
   must not - and now you know it exists, which is most of the
   battle.                                                   */

/* TECHNIQUE 6: read a neighbour.
   If register 0x00 reads zero, read 0x04, 0x08, an adjacent
   block's ID register. All zero across a whole peripheral ->
   clock, reset or a whole-block denial. Only one register
   zero -> that register really is zero, and this was never an
   access problem.                                          */

A worked example

A complete investigation from symptom to root cause, tying together the triage, the registers and the policy — which is what the chapter has been building toward.

# SYMPTOM
#   New video decoder driver. probe() succeeds, but every
#   decode returns an empty frame. No errors anywhere.

# 1. clocked and out of reset?
   cat /sys/kernel/debug/clk/clk_summary | grep vdec
     vdec_core   1  1  0  300000000        -> yes, enabled

# 2. address right? read the ID register from userspace:
   devmem 0x1c000000
     0x00000000                             -> suspicious.
   devmem 0x1c000004
     0x00000000
   devmem 0x1c000008
     0x00000000                             -> the whole block.
#  TRM says ID should read 0x56444543. So: not present, not
#  clocked (but clk says it is), or DENIED.

# 3. any faults latched? From the TF-A debug console:
   tfa> xpu_dump 0
     XPU FAULT
       address   : 0x000000001c000000
       master ID : 0x04 (CPU_NS)
       direction : read
       security  : non-secure
     -> DENIED. The CPU, non-secure, may not read the decoder's
        registers.

# 4. why? Check the policy:
   grep -A4 vdec platform_policy.yaml
     - name: vdec_regs
       base: 0x1C000000
       access: { secure: rw }
     -> the decoder was classified as a SECURE resource,
        because an earlier product used it for DRM.

# 5. policy wrong, or code wrong?
#  Talk to the team. Conclusion: this product decodes
#  non-protected content on the AP, so the AP legitimately
#  needs the registers - but the PROTECTED OUTPUT BUFFER must
#  still be unreadable by the AP. So the fix is to split the
#  resource, not to open it:

     - name: vdec_regs
       base: 0x1C000000
       access: { ap: rw, secure: rw }       # control plane
     - name: vdec_protected_out
       base: 0xC8000000
       access: { media: w, secure: rw }     # data plane:
                                            # codec writes,
                                            # AP never reads

# 6. regenerate, rebuild firmware, re-run.
#    AND add the negative test:
     { "AP reads protected video output", M_CPU_NS,
       PROT_VIDEO, false },
#    so the day someone widens this by accident, CI says so.
Notice what step 5 did

The lazy fix — access: { ap: rw } on the whole subsystem — would have worked, shipped, and quietly handed the application processor read access to protected video. Splitting control plane from data plane took ten extra minutes and preserved the property the policy existed for. That distinction, between "make the error go away" and "understand what the error was protecting", is the whole skill.

The toolkit

The tools and register views worth having to hand before you need them, since several are only accessible from firmware or a debugger rather than from Linux.

ToolUse
devmem / devmem2Poke physical addresses from userspace. First thing to reach for.

The negative test suiteNot a debugging tool — a tool for knowing the bug never comes back.
