What a hypervisor actually is

A hypervisor is an operating system whose processes are operating systems. Everything else in this track — EL2, stage-2 translation, the vGIC, virtio — is a consequence of that one sentence, because a process that believes it owns the machine needs lying to in ways an ordinary process does not.

The problem it solves

An operating system is written on the assumption that it is alone. It sets up page tables at a physical address it chose. It programs the interrupt controller. It reads a timer and believes the value. It writes to a UART at 0x0900_0000 because the manual says the UART is there.

Now run two of them on one chip. Both want to be alone. Both chose physical addresses. Both programmed the interrupt controller. Neither will tolerate the other, and neither can be modified — that is the whole point, because if you were willing to rewrite the guest you would not need virtualisation, you would need a library.

That last row is the interesting one. A process asks for a service by executing SVC: it knows it is asking. A guest kernel writes to what it believes is a hardware register: it does not know it is asking. The hypervisor must intercept an operation the guest thought was a plain memory store, work out what the guest meant by it, do something equivalent, and resume the guest as if the store had simply happened.

The definition worth memorising

A hypervisor gives each guest the illusion of a whole machine: its own physical address space, its own CPU, its own interrupt controller, its own timer, and its own devices. Every chapter in this track is one of those illusions, and how the hardware helps you build it.

Type 1 and type 2

The textbook split is between hypervisors that run on bare metal and hypervisors that run inside a host OS. It is a useful first cut and a poor final one, because the interesting systems sit in between.

KVM is the case that breaks the taxonomy, and it is the one you will meet most. The Linux kernel gains the ability to enter EL2 and run a guest; a user-space process (QEMU, crosvm, cloud-hypervisor) supplies the device models and the policy. The scheduler scheduling your vCPU is the ordinary Linux scheduler, and the vCPU is an ordinary thread. That design decision — a vCPU is a thread — explains most of KVM's behaviour, good and bad.

Three ways to virtualise

TechniqueHowCostWhere you see it
Trap and emulateRun the guest directly; privileged operations trap to the hypervisor, which emulates themOne trap per privileged operation — cheap if rare, ruinous if hotThe base mechanism everywhere
Binary translationRewrite the guest's instruction stream before running it, replacing awkward instructionsTranslation time, cache pressure, enormous complexityVMware on pre-2006 x86; QEMU's TCG today
ParavirtualisationModify the guest to call the hypervisor deliberatelyYou must be able to change the guestvirtio, Xen PV, PSCI, pvclock, KVM's hypercalls

Real systems use all three at once. An arm64 KVM guest runs natively (trap-and-emulate) for ordinary code, is trapped for GIC and timer access, and deliberately calls the hypervisor for power management via PSCI and for I/O via virtio. Paravirtualisation is not a compromise you make when the hardware is weak — it is the right answer whenever the interface you are emulating is a bad interface. Emulating a 1990s IDE controller register-by-register is possible and pointless; a virtqueue is better in every way.

Why virtio exists at all

Emulating a real device means one trap per register access, and real device drivers touch a lot of registers per operation. A virtio device is designed so that the guest can queue many requests into shared memory and then trap once to say "there is work". The unit of expensive interaction becomes the batch, not the register. Hold that thought — it recurs in chapter 14.

Why this matters in embedded, not just in the cloud

Server virtualisation is about consolidation and billing. Embedded virtualisation is about isolation with mixed criticality, and the shape of the problem is different.

   A typical automotive or industrial SoC today:

   +----------------------+  +---------------+  +--------------+
   |  Infotainment        |  |  Instrument   |  | Safety /     |
   |  Android or Linux    |  |  cluster      |  | control      |
   |  huge, updated often |  |  Linux, must  |  | RTOS, ASIL-B |
   |  low trust           |  |  never blank  |  | hard realtime|
   +----------------------+  +---------------+  +--------------+
   +-------------------------------------------------------------+
   |  hypervisor - and its job is NOT consolidation, it is:       |
   |   * the RTOS must meet its deadline even when Android melts  |
   |   * a compromise in Android must not reach the CAN bus       |
   |   * the cluster must keep rendering during an infotainment   |
   |     restart                                                  |
   +-------------------------------------------------------------+

   Consequences you will not meet in a cloud hypervisor:
     - static partitioning is often preferred over scheduling
     - device PASSTHROUGH is the norm, not the exception
     - the hypervisor must be small enough to CERTIFY
     - "overcommit" may be forbidden outright

This is why the track covers Jailhouse and static partitioning alongside KVM. In a data centre a hypervisor that cannot overcommit memory is useless; in a car a hypervisor that can is a hazard.

What virtualisation actually costs

The honest answer is "almost nothing, except at the boundaries, where it is enormous". Guest instructions that do not trap run at native speed — there is no interpreter and no overhead. The cost is concentrated entirely in exits.

The classic embedded surprise

Code that "works fine on the board" and is unusably slow in the VM is almost always doing register polling. On hardware each read is ~100 ns; under a hypervisor each read is a trap. The fix is not a faster hypervisor — it is to stop polling, or to pass the device through (chapter 17).
