Inheritance, virtual functions and the vtable

How runtime polymorphism is implemented, exactly what it costs, and the four alternatives that give you the same flexibility without an indirect call. On embedded the answer is often "not virtual" — but you need to know the mechanism to make that judgement.

The vtable

Virtual dispatch is not magic: it is a hidden pointer in the object leading to a table of function pointers. Seeing the layout explains its cost, its memory overhead, and why it defeats inlining.

   class Shape {
   public:
           virtual ~Shape() = default;
           virtual int area() const = 0;
           virtual void draw() const = 0;
   };

   class Circle : public Shape {
           int r_;
   public:
           int area() const override { return 3 * r_ * r_; }
           void draw() const override { ... }
   };

   OBJECT LAYOUT of a Circle on AArch64:

      +0   __vptr    -----------+   8 bytes, ALWAYS FIRST
      +8   r_                   |   4 bytes (+ 4 padding)
      = 16 bytes total          |
                                v
      Circle's VTABLE (one per CLASS, in .rodata):
         [0]  offset-to-top   0
         [1]  typeinfo ptr    -> Circle's type_info (RTTI)
         [2]  &Circle::~Circle          (complete)
         [3]  &Circle::~Circle          (deleting)
         [4]  &Circle::area
         [5]  &Circle::draw

   A CALL:
        shape->area();
   compiles to:
        ldr  x8, [x0]           ; load the vptr
        ldr  x8, [x8, #32]      ; load the slot
        blr  x8                 ; indirect call

   THREE INSTRUCTIONS AND TWO DEPENDENT LOADS, versus one
   `bl` for a direct call.

   THE COSTS, precisely:
     · 8 bytes per OBJECT for the vptr
     · one vtable per CLASS in .rodata
     · two dependent loads before the call - a potential
       cache miss each
     · an INDIRECT branch, which the predictor must learn
       (CA chapter 12)
     · NO INLINING, unless the compiler can prove the dynamic
       type - which blocks every downstream optimisation

   THAT LAST POINT IS USUALLY THE LARGEST COST. The call
   itself is a few cycles; the lost inlining can be a factor
   of two on small functions.

The rules that matter

Several rules around virtual functions exist to prevent specific, silent bugs — most importantly a destructor that fails to run and an override that silently becomes an overload.

/* --- 1. A POLYMORPHIC BASE NEEDS A VIRTUAL DESTRUCTOR --- */
        class Base { public: ~Base(); };        /* NOT virtual */
        Base *p = new Derived;
        delete p;               /* ~Derived NEVER RUNS -
                                   UNDEFINED BEHAVIOUR       */

        class Base { public: virtual ~Base() = default; };
/* -Wnon-virtual-dtor / -Wdelete-non-virtual-dtor catch this.
   Enable them.

   THE EXCEPTION: if a base is never deleted through a base
   pointer, a PROTECTED non-virtual destructor is correct and
   cheaper:                                                */
        class Interface {
        protected:
                ~Interface() = default;         /* cannot
                                                   delete
                                                   through
                                                   this      */
        public:
                virtual void run() = 0;
        };

/* --- 2. ALWAYS WRITE `override` --- */
        class Derived : public Base {
                void draw() const override;     /* checked */
                void draw();                    /* silently a
                                                   NEW
                                                   function -
                                                   const
                                                   mismatch  */
        };
/* -Wsuggest-override, -Winconsistent-missing-override.
   `override` turns a silent bug into a compile error, and
   costs one word.

/* --- 3. `final` enables DEVIRTUALISATION --- */
        class Circle final : public Shape { ... };
        void f(Circle& c) { c.area(); }   /* the compiler KNOWS
                                             the type -> a
                                             DIRECT, INLINABLE
                                             call            */
/* Mark leaf classes and non-overridden virtuals `final`. It
   is free and it recovers the inlining.

/* --- 4. NEVER CALL A VIRTUAL FROM A CONSTRUCTOR --- */
/* During Base's constructor the vptr points at BASE's vtable
   (chapter 03). The override is not called. Use two-phase
   init.

/* --- 5. SLICING --- */
        void f(Shape s);        /* BY VALUE - only the Shape
                                   part is copied           */
        Circle c;
        f(c);                   /* SLICED - r_ is lost, and
                                   the vptr is Shape's      */
/* Always pass polymorphic types by reference or pointer.
   Making the base abstract prevents it entirely, because
   `Shape s` will not compile.                            */

/* --- 6. DEFAULT ARGUMENTS ARE STATICALLY BOUND --- */
        class Base    { virtual void f(int x = 1); };
        class Derived { void f(int x = 2) override; };
        Base *p = new Derived;
        p->f();                 /* calls Derived::f(1) - the
                                   DEFAULT came from Base   */
/* Do not use default arguments on virtual functions.      */

Multiple and virtual inheritance

Inheriting from several bases complicates the object layout considerably, and the virtual case introduces a pointer adjustment that surprises people reading disassembly.

/* MULTIPLE INHERITANCE from interfaces is fine and cheap: */
        class Readable  { public: virtual int read() = 0; };
        class Writable  { public: virtual int write(int) = 0; };
        class Port : public Readable, public Writable { ... };

/* LAYOUT: TWO vptrs, one per base. And a `Writable*` obtained
   from a `Port*` is at a NON-ZERO OFFSET, so:            */
        Port p;
        Writable *w = &p;       /* w != (void*)&p ! */
/* The compiler adjusts the pointer. Casting back and forth
   with reinterpret_cast rather than static_cast breaks
   silently - which is one reason C-style casts are dangerous
   in C++.

/* AND THE THUNK: calling through Writable* needs `this`
   adjusted before entering Port's function, so the vtable
   entry points at a small thunk that does the subtraction.
   You will see these in disassembly as tiny functions named
   `non-virtual thunk to Port::write`.

/* VIRTUAL INHERITANCE - the diamond: */
        class Base { int x; };
        class A : virtual public Base {};
        class B : virtual public Base {};
        class D : public A, public B {};    /* ONE Base */

/* THE COST is substantial: a virtual base pointer per
   subobject, an extra indirection to reach Base's members,
   and complicated construction ordering (the most-derived
   class constructs the virtual base).

   ON EMBEDDED: avoid virtual inheritance entirely. If you
   need the diamond, you almost certainly want composition or
   pure interfaces with no data.                          */

/* THE INTERFACE RULE that avoids all of this:
     a class with virtual functions has NO DATA MEMBERS
     a class with data members has NO VIRTUAL FUNCTIONS and is
     not inherited from
   Then multiple inheritance is only ever from interfaces, and
   the diamond cannot arise.                              */
Prefer composition to inheritance

Inheritance couples the derived class to the base's implementation, its layout, and its future changes. Composition — holding a member and forwarding — couples only to the interface. The C++ Core Guidelines put it as: use inheritance for substitutability (an interface), and composition for reuse. Almost every "share this code between classes" problem is composition, not inheritance.

The four alternatives

Run-time polymorphism is not the only kind. Several techniques give you the same flexibility resolved entirely at compile time, which matters when the dispatch is in a hot path or the memory overhead is unacceptable.

/* --- 1. TEMPLATES: static polymorphism (chapter 06) --- */
template<typename Sensor>
void sample_loop(Sensor& s)
{
        while (running)
                log(s.read());          /* resolved at COMPILE
                                           time, INLINED     */
}
/* ZERO cost, full inlining. The type set must be known at
   compile time, and each instantiation is a separate copy of
   the code.

/* --- 2. CRTP (chapter 06) --- */
template<typename D>
class SensorBase {
        D& self() { return static_cast<D&>(*this); }
public:
        int read() { return self().convert(self().read_raw()); }
};
/* An interface with shared implementation, statically
   dispatched.

/* --- 3. std::variant + std::visit (chapter 08) --- */
        using AnySensor = std::variant<Thermistor, Photodiode,
                                       Hall>;

        std::array<AnySensor, 4> sensors;

        for (auto& s : sensors)
                std::visit([](auto& sensor)
                        { log(sensor.read()); }, s);

/* A HETEROGENEOUS CONTAINER with no heap and no vtable. The
   dispatch is a jump table on the variant's index - one
   indirect branch, but the target is a known small set and
   the functions CAN be inlined into the visitor.

   THE TRADE: the type list is closed. Adding a sensor type
   means recompiling, which for firmware is fine and for a
   plugin system is not.

/* --- 4. A FUNCTION POINTER TABLE: the C way, still good --- */
        struct DriverOps {
                int  (*read)(void *ctx);
                int  (*write)(void *ctx, int v);
                void (*close)(void *ctx);
        };
        struct Driver {
                const DriverOps *ops;
                void *ctx;
        };
        d.ops->read(d.ctx);
/* Exactly a hand-rolled vtable - and this is precisely what
   the Linux kernel's file_operations is (Linux chapter 22).
   It is explicit, has no language machinery behind it, and
   costs the same indirect call.

/* CHOOSING:

     types known at compile time, one type per call site
          -> TEMPLATES
     interface with shared implementation, static
          -> CRTP
     small closed set, heterogeneous container, no heap
          -> VARIANT
     open set, runtime plugins, ABI boundary
          -> VIRTUAL (or an ops table)

   AND THE HONEST NOTE: virtual functions are not expensive
   in absolute terms. If the function does meaningful work,
   the indirect call is noise. The cost that matters is lost
   inlining on SMALL functions called in a loop - and that is
   the case where an alternative pays.                    */

Measuring the cost

The overhead of virtual dispatch is often quoted and rarely measured. These are the actual costs, and which of them dominates depends on the situation rather than on the call itself.

RTTI

Run-time type information supports dynamic casts and type queries, and it is switched off in most embedded builds. Knowing what you lose tells you whether that is acceptable.

#include <typeinfo>

        Shape *s = get_shape();

        if (Circle *c = dynamic_cast<Circle *>(s)) {
                use(*c);                /* it was a Circle */
        }
        Circle& r = dynamic_cast<Circle&>(*s);   /* THROWS
                                                    on failure */

        if (typeid(*s) == typeid(Circle)) { ... }
        const char *name = typeid(*s).name();   /* MANGLED */

/* THE COST: a typeinfo object per polymorphic class, plus a
   runtime walk of the inheritance graph for dynamic_cast -
   which is not constant time with multiple inheritance.

/* AND -fno-rtti REMOVES IT ENTIRELY, which is what embedded
   builds do. Then dynamic_cast and typeid are compile
   errors.

/* THE ALTERNATIVE when you need to recover the concrete type:
   put a tag in the base and use static_cast:              */
        class Shape {
        public:
                enum class Kind { Circle, Square };
                Kind kind() const { return kind_; }
                virtual ~Shape() = default;
        protected:
                explicit Shape(Kind k) : kind_(k) {}
        private:
                Kind kind_;
        };

        if (s->kind() == Shape::Kind::Circle)
                auto *c = static_cast<Circle *>(s);

/* This is LLVM's own idiom - its `isa<>` and `dyn_cast<>`
   are exactly this, built on a kind field, and LLVM is
   compiled with -fno-rtti for the reason above.

/* AND THE BETTER ANSWER, usually: if you are asking what
   concrete type something is, the interface is probably
   missing a virtual function that would let you avoid
   asking.                                                 */
