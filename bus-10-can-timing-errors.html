CAN: bit timing, error states and bus-off

Two things distinguish a CAN node that works from one that mostly works: a sample point set where the standard wants it, and an understanding of the error counters that decide whether a misbehaving node is allowed to keep talking.

The bit, divided

   A CAN bit is divided into TIME QUANTA (tq), and the
   division is what you configure - not a baud rate divisor.

   |<--------------- one bit time ------------------>|
   +--------+------------------+--------------------+
   |  SYNC  |    PROP + PS1    |        PS2         |
   |  1 tq  |                  |                    |
   +--------+------------------+--------------------+
                               ^
                          SAMPLE POINT

   SYNC_SEG   always 1 tq. Edges are expected here.
   PROP_SEG   compensates for the physical propagation
              delay to the far end of the bus and back.
   PHASE_SEG1 buffer, can be LENGTHENED to resync.
   PHASE_SEG2 buffer, can be SHORTENED to resync.

   SAMPLE POINT = (SYNC + PROP + PS1) / total, as a
   percentage of the bit.

   TARGET: 75-80% for most rates; CANopen and DeviceNet
   specify 87.5%. LATE, not in the middle - because
   arbitration requires the signal to have propagated to
   the far end AND BACK before anyone samples (chapter 09).

   THIS IS THE SINGLE MOST COMMON CAN CONFIGURATION ERROR.
   A sample point at 50% works perfectly on a short bench
   bus and fails on a long vehicle harness, because the
   round trip no longer fits. The symptom is a bus that
   works until the cable gets longer.

   SJW (SynchronisationJumpWidth): how many tq the resync
   may adjust by, 1-4. It absorbs the accumulated difference
   between two nodes' oscillators. Set it to 1 for tight
   clocks, higher if you must tolerate sloppy ones.

Calculating it

/* GOAL: 500 kbit/s from a 42 MHz peripheral clock, sample
   point at 87.5%.                                         */

/*  tq per bit is chosen first. More tq gives finer control
    of the sample point; fewer allows higher bit rates.
    8-25 is the usual range; 16 is a good default.

    prescaler = f_clk / (bitrate * tq_per_bit)
              = 42e6 / (500000 * 16)
              = 5.25            -> NOT AN INTEGER.

    Try tq = 14:
              = 42e6 / (500000 * 14) = 6      -> exact.

    Now divide 14 tq to place the sample point:
      SYNC = 1
      TSEG1 (prop + ps1) = 11
      TSEG2 (ps2)        = 2
      total = 1 + 11 + 2 = 14
      sample = (1 + 11) / 14 = 85.7%     -> close enough

    Registers hold "value minus one" (mcu chapter 11):     */

CAN1->BTR = ((6u - 1u)  << 0)      /* BRP  = 6            */
          | ((11u - 1u) << 16)     /* TS1  = 11 tq        */
          | ((2u - 1u)  << 20)     /* TS2  = 2 tq         */
          | ((1u - 1u)  << 24);    /* SJW  = 1 tq         */

/* VERIFY BY MEASUREMENT, not by arithmetic. Put a scope on
   CANH and measure one bit's width: it must be 2.00 us for
   500 kbit/s. An error of even 1% will cause errors on a
   long bus with a node at the tolerance limit.

   EVERY NODE ON THE BUS MUST USE THE SAME BIT RATE, and
   should use a similar sample point. They need NOT use the
   same tq count or prescaler - only the resulting bit time
   and a compatible sample point matter.

   ONLINE CALCULATORS EXIST and are worth using: the
   constraint set (integer prescaler, tq range, sample point
   target, SJW) is genuinely fiddly and errors are silent. */
Bit timing can only be changed in initialisation mode

The BTR register is writable only while the peripheral is in initialisation mode, and writes are silently ignored otherwise. Code that configures timing after starting the controller produces a node running at whatever the reset default was — usually wrong, and usually diagnosed as a wiring problem. Set timing before leaving init, and read the register back to confirm it took.

Error confinement

   CAN assumes nodes will fail, and contains them
   automatically. Two counters per node:

     TEC - transmit error counter
     REC - receive error counter

   ROUGHLY: an error while transmitting adds 8 to TEC; an
   error while receiving adds 1 to REC; a SUCCESS subtracts
   1 from the relevant counter.

   The 8:1 asymmetry is deliberate: a node that is itself
   broken accumulates errors eight times faster than the
   innocent nodes that merely witness them. The faulty node
   is therefore confined first, and the bus survives.

   THREE STATES:

   ERROR ACTIVE      TEC < 128 and REC < 128
     Normal. Transmits ACTIVE error frames (6 dominant
     bits), which destroy the offending frame for everyone.

   ERROR PASSIVE     TEC >= 128 or REC >= 128
     Still communicates, but transmits PASSIVE error frames
     (6 RECESSIVE bits) which do not disturb others. It
     also waits 8 extra bit times before transmitting,
     yielding to healthy nodes.

   BUS-OFF           TEC >= 256
     Disconnected. Transmits nothing, ACKs nothing, has no
     effect on the bus at all.

   +---------------+  TEC or REC >= 128   +----------------+
   | ERROR ACTIVE  |--------------------> | ERROR PASSIVE  |
   |               | <------------------- |                |
   +---------------+  both < 128          +----------------+
                                                   |
                                        TEC >= 256 |
                                                   v
                                          +----------------+
                                          |    BUS-OFF     |
                                          +----------------+
                                                   |
                          128 x 11 recessive bits, |
                          and software permission  |
                                                   v
                                            ERROR ACTIVE

   RECOVERY FROM BUS-OFF requires observing 128 occurrences
   of 11 consecutive recessive bits - i.e. the bus being
   idle - which takes at least 128 x 11 bit times. At
   500 kbit/s that is about 2.8 ms.

Handling bus-off in software

/* Whether recovery is automatic is a configuration choice,
   and the right answer depends on the product.            */

/* AUTOMATIC (ABOM): the hardware recovers as soon as the
   128x11 condition is met. Convenient, and it hides the
   fault - a node with a broken transceiver will cycle
   in and out of bus-off forever, and nobody notices.      */
CAN1->MCR |= CAN_MCR_ABOM;

/* MANUAL: software decides. Preferred in anything that
   must report faults, because it lets you count and
   rate-limit.                                             */
void CAN1_SCE_IRQHandler(void)
{
    uint32_t esr = CAN1->ESR;

    if (esr & CAN_ESR_BOFF) {
        stats.bus_off_count++;
        stats.last_lec = (esr >> 4) & 7u;   /* last error code */

        if (stats.bus_off_count < 5) {
            can_restart();                  /* try again    */
        } else {
            /* Repeated bus-off is a HARDWARE fault: a
               shorted bus, a missing terminator, a wrong
               bit rate, or a dead transceiver. Retrying
               forever hides it. Report and stay off.      */
            fault_latch(FAULT_CAN_BUS);
        }
    }
}

/* THE LAST ERROR CODE names the cause, and it is genuinely
   diagnostic:

     1 STUFF   more than 5 identical bits -> noise, or a
               node at the wrong bit rate
     2 FORM    a fixed-form field was wrong -> bit rate or
               a node speaking a different protocol
     3 ACK     nobody acknowledged -> you are alone on the
               bus, or the others are bus-off, or CANH/CANL
               are swapped
     4 BIT1    sent recessive, read dominant -> another
               node is stuck dominant, or a short to ground
     5 BIT0    sent dominant, read recessive -> your
               transceiver is not driving; check its
               standby pin and supply
     6 CRC     corruption in transit -> noise or termination

   ACK error on a bench setup with one node is normal and
   expected (chapter 09). ACK error in a running vehicle
   means everyone else has gone quiet.                     */

Acceptance filters

/* A busy bus carries thousands of frames per second, and
   most are not yours. Filtering in HARDWARE is essential -
   waking the CPU for every frame would dominate the load. */

/* MASK MODE: check only the bits the mask selects.
     accept if (received_id & mask) == (filter_id & mask)  */

/* Accept 0x100-0x10F: the low nibble is "don't care".     */
CAN1->sFilterRegister[0].FR1 = (0x100u << 21);   /* id      */
CAN1->sFilterRegister[0].FR2 = (0x7F0u << 21);   /* mask    */

/* LIST MODE: accept exactly these identifiers, no mask.
   Use when you want a handful of unrelated IDs.           */

/* DESIGN CONSEQUENCE: assign IDs so that the messages one
   node cares about share a bit pattern. If a node needs
   0x101, 0x205 and 0x3C2, no single mask captures them and
   you burn three filter banks. If those messages were
   numbered 0x110, 0x111, 0x112 one filter does it.

   This is why CAN ID allocation is a system design task
   done up front, in a spreadsheet, balancing:
     - priority (lower = more urgent, chapter 09)
     - filterability (group by consumer)
     - room to grow

   Retrofitting an ID scheme after the software is written
   is genuinely painful, which is why standard higher-layer
   protocols - CANopen, J1939 - specify one for you.       */
