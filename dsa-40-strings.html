Strings: matching, palindromes and rolling hashes

Most string problems are array problems wearing a disguise, and the patterns you already have solve them. The three that are genuinely their own thing — prefix-function matching, expanding around a centre, and rolling hashes — are the subject of this chapter, and each is short once you see what it is counting.

First, check it is not a problem you can already solve

Reaching for KMP when a hash map would do is a common and costly mistake in interviews. Before learning anything new, run the string through the patterns from earlier chapters.

The prefix function, and what it actually counts

KMP is usually taught as a matching algorithm with a confusing skip rule. It is easier to learn the other way round: build one table, understand what its numbers mean, and matching falls out of it for free.

   THE TABLE. For a string s, pi[i] is the length of the
   LONGEST PROPER PREFIX of s[0..i] that is also a SUFFIX
   of s[0..i].

     s   =  a  b  a  b  a  c  a
     pi  =  0  0  1  2  3  0  1
                     ^
                     "aba" ends here; its longest
                     prefix-that-is-also-a-suffix is "a",
                     length 1

   READ pi[i] AS: "if I have matched i+1 characters and the
   next one fails, how many characters can I keep?"

   ---------------------------------------------------------

   WHY THAT MAKES MATCHING LINEAR:

     text    a b a b a b a c a
     pattern a b a b a c
                       ^ mismatch at pattern index 5

     A NAIVE algorithm restarts the pattern at the next text
     position, re-reading characters it has already seen.

     KMP knows that "abab" - the part already matched - has
     a prefix "ab" that is also its suffix. So it can slide
     the pattern so that "ab" lines up, and CONTINUE from
     text position where it was. The text pointer NEVER
     MOVES BACKWARDS, which is exactly why it is O(n + m).

   ---------------------------------------------------------

   THE PART WORTH MEMORISING is that the table is built with
   the SAME loop that uses it - you match the string against
   itself.
/* The prefix function. Six lines, and the only string
   algorithm in this chapter worth memorising verbatim.  */
function prefixFunction(s) {
    const pi = new Array(s.length).fill(0);
    for (let i = 1; i < s.length; i++) {
        let j = pi[i - 1];
        while (j > 0 && s[i] !== s[j]) j = pi[j - 1];
        if (s[i] === s[j]) j++;
        pi[i] = j;
    }
    return pi;
}

/* THE while LOOP LOOKS QUADRATIC AND IS NOT. j increases by
   at most 1 per iteration of the outer loop, so it can
   decrease at most n times in total across the whole run.
   Amortised O(n) - the same argument as the monotonic stack
   in chapter 23.                                         */

/* TWO FACTS THAT SOLVE MOST PREFIX-FUNCTION PROBLEMS:

   1. The shortest repeating unit of s has length
        n - pi[n-1]
      and s is built from whole copies of it exactly when
      that length divides n.

   2. To search for a pattern p in a text t, run the prefix
      function over  p + '\u0000' + t  and look for values
      equal to p.length. The separator stops matches from
      straddling the join.                                */

Expand around centre

The palindrome problems have their own trick, and it is simpler than the DP solution people usually reach for first. The only thing to get right is how many centres there are.

   A PALINDROME IS DEFINED BY ITS CENTRE, so enumerate
   centres rather than substrings.

   HOW MANY CENTRES? 2n - 1, not n:

     a b a       odd centres:  a, b, a        (3)
     ^ ^ ^       even centres: a|b, b|a       (2)
      v v                                     ---
                 total                         5

   FORGETTING THE EVEN CENTRES is the single most common bug
   in this problem, and it passes "aba" and fails "abba".

   ---------------------------------------------------------

   for (let c = 0; c < n; c++) {
       expand(c, c);        // odd  length
       expand(c, c + 1);    // even length
   }

   EACH EXPANSION IS O(n), SO THIS IS O(n²) - which is the
   expected answer. Manacher's algorithm does it in O(n) and
   is almost never required; mention that you know it exists
   and move on.

Rolling hashes, and the one thing that will bite you

A rolling hash turns "are these two substrings equal" into an O(1) question. It is the right tool when you need many such comparisons — and it is the one technique in this chapter that can be wrong.

   THE IDEA: treat the string as a number in base B, modulo
   a large prime M.

     h(s[0..k]) = s[0]*B^k + s[1]*B^(k-1) + ... + s[k]

   Precompute prefix hashes and powers of B, then the hash
   of any substring is one subtraction and one multiply:

     hash(l, r) = h[r] - h[l-1] * B^(r-l+1)     (mod M)

   ---------------------------------------------------------

   THE THING THAT WILL BITE YOU: COLLISIONS.

   Two different substrings CAN hash the same. With one
   modulus around 10^9 and enough comparisons, this stops
   being theoretical - the birthday bound means roughly
   10^4.5 comparisons give you a real chance of a collision,
   and adversarial inputs make it a certainty.

   THREE DEFENCES, in increasing order of effort:
     · verify a hash match with a real character comparison
       (cheap if matches are rare - this is what you should
        usually do)
     · use TWO moduli and compare both
     · choose the base at random at run time, so no fixed
       input can be constructed to break you

   SAY THIS OUT LOUD IN AN INTERVIEW. "Hashes can collide,
   so I will verify" is the sentence that distinguishes
   someone who has used the technique from someone who has
   read about it.

   ---------------------------------------------------------

   AND NOTE: in JavaScript, B * h overflows the 53-bit safe
   integer range for realistic moduli. Use BigInt, or pick a
   modulus below 2^26 or so, or use the prefix function
   instead - which has no collision problem at all.
