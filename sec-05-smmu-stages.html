SMMU: stages, queues and invalidation

Two translation stages with two different owners, three queues connecting software to hardware, and an invalidation discipline that mirrors the CPU's exactly. Plus the advanced features — ATS, PRI and SVA — that let a device share a process's address space directly.

Two stages, two owners

Like the processor's MMU, the SMMU can translate twice — and crucially the two stages have different owners. That split is what lets a hypervisor contain a device that an untrusted guest is driving.

Guest can change it?Yes — it is the guest's ownNo — that is the point
 
   BARE-METAL OS, stage 1 only

     device --> IOVA --[ stage 1, OS tables ]--> PA

   DEVICE PASSED THROUGH TO A VM, stage 2 only

     device --> IPA ---[ stage 2, hypervisor ]--> PA
                ^ the guest programs the device with its own
                  "physical" addresses, and cannot escape

   NESTED — a guest with its own IOMMU driver, both stages

     device --> IOVA --[ stage 1, GUEST ]--> IPA
                        --[ stage 2, HYPERVISOR ]--> PA

  Exactly the structure of CPU two-stage translation
  (ARM chapter 16), with the same walk-multiplication cost: each
  stage-1 table access itself needs a stage-2 translation, so a
  full nested walk can be up to 24 memory accesses.

  Mitigations are the same too: SMMU TLBs caching the combined
  IOVA -> PA translation, walk caches for intermediate
  descriptors, and huge pages at stage 2 (a 1 GB block for the
  guest's RAM is standard).

The three queues

The SMMU communicates with software through memory-based queues rather than registers alone: commands in one direction, events in the other. Understanding that structure is essential to reading a fault.

Software and the SMMU communicate through circular buffers in
memory, each with producer and consumer indices in registers.

   COMMAND QUEUE          software  ->  SMMU
      CMDQ_BASE, CMDQ_PROD (software writes), CMDQ_CONS (SMMU)
      invalidate a cached STE, CD or TLB entry; synchronise;
      prefetch; respond to a page request

   EVENT QUEUE            SMMU  ->  software
      EVENTQ_BASE, EVENTQ_PROD (SMMU writes), EVENTQ_CONS
      fault records: bad StreamID, translation fault, permission
      fault, external abort. An interrupt signals arrival.

   PRI QUEUE              SMMU  ->  software
      PRIQ_BASE, PRIQ_PROD, PRIQ_CONS
      page requests from a device that supports PRI — "please
      map this address for me". Optional.

  Same design as the GIC's ITS command queue (ARM chapter 23),
  and as virtio and io_uring (OS chapter 08): a shared ring plus
  a doorbell. Recognise the pattern.

  Queue memory attributes must match SMMU_CR1's configuration,
  for the same reason STE memory does (chapter 04).

The invalidation rule, exactly as for the CPU

Anything you change in memory — an STE, a CD, a page table entry — is invisible to the SMMU until you issue the matching invalidate command and a CMD_SYNC. This mirrors the CPU's write → DSB → TLBI → DSB → ISB sequence (ARM 15), and omitting it produces exactly the same class of "works sometimes" bug.

/* Unmapping a page, correctly: */

        /* 1. clear the descriptor */
        *pte = 0;

        /* 2. make the write visible to the SMMU, which is a
              separate observer reading memory directly       */
        dsb(ishst);

        /* 3. invalidate the SMMU's TLB entry */
        cmdq_issue(CMD_TLBI_NH_VA, asid, iova);

        /* 4. if ATS is in use, invalidate the DEVICE's cache too,
              and WAIT for the device to acknowledge            */
        cmdq_issue(CMD_ATC_INV, sid, ssid, iova, size);

        /* 5. wait for all of it to complete */
        cmdq_issue(CMD_SYNC);
        wait_for_sync_completion();

        /* 6. ONLY NOW is it safe to free or reuse the page */
        free_page(page);

/* Skipping step 5 and freeing immediately leaves a window in
   which the device can still write to a page that now belongs
   to something else. That is a use-after-free with DMA, and it
   is precisely what iommu.strict=0 trades away for speed.  */

Strict versus deferred invalidation

Whether an invalidation must complete before a mapping is reused is a genuine trade between safety and throughput, and Linux exposes it as a setting that people change without appreciating what they are giving up.

   iommu.strict=1   (the default)
        every unmap issues an invalidate and waits for CMD_SYNC
        before the IOVA is reused or the page freed.
        SAFE. Costs a command-queue round trip per unmap, which
        on a high-rate NIC is a measurable fraction of the
        packet budget.

   iommu.strict=0   ("lazy" / DMA-FQ)
        unmapped IOVAs go on a flush queue and are invalidated
        in BATCHES, typically every 10 ms or when the queue
        fills. Far fewer syncs.
        UNSAFE WINDOW: between unmap and the batched invalidate,
        the device can still translate and access the page. If
        the page has been freed and reallocated, a malicious or
        buggy device writes to whatever now lives there.

   Which to choose:
      · trusted, on-SoC devices, throughput-critical -> strict=0
        may be a reasonable, documented decision
      · anything hot-pluggable, or any device you do not
        control -> strict=1, always

   cat /sys/kernel/iommu_groups/*/type
   #   DMA      strict
   #   DMA-FQ   deferred (flush queue)
   #   identity bypass

ATS: caching translations in the device

A device can cache its own translations, which removes the SMMU from the critical path and moves trust into the device. That is a significant security decision disguised as a performance feature.

A PCIe device can ask the SMMU to translate an address in
advance and cache the result in its own ADDRESS TRANSLATION
CACHE (ATC), then issue PRE-TRANSLATED transactions.

   device --> ATS Translation Request --> SMMU
          <-- translated address       <--
   device caches it in the ATC
   device --> transaction marked "already translated" --> memory
                                       (SMMU not consulted)

  BENEFIT: removes the SMMU from the data path entirely. On a
  device doing millions of transfers per second this is a large
  win.

  COST 1 — a new correctness obligation. When software unmaps a
  page it must send CMD_ATC_INV and WAIT for the device's
  response. If the device is slow, buggy, or has been
  hot-unplugged, that wait can stall. Linux has a timeout and
  will report:
       arm-smmu-v3: ATC invalidation timed out

  COST 2 — a TRUST problem. A pre-translated transaction bypasses
  the SMMU's checks entirely. You are trusting the device to
    (a) only use translations it was legitimately given, and
    (b) honour invalidations.
  A malicious device that ignores both has unrestricted access.

  Hence PCIe ACS and the "translation blocking" controls, and
  hence: enable ATS only for devices you trust. Linux will not
  enable it for a device without the appropriate ACS
  capabilities upstream.

PRI: page faults for devices

If a device can tolerate a fault and retry, it can use memory that is not currently resident — which is what makes shared virtual memory between a CPU and an accelerator workable.

/* Normally, a device touching an unmapped address gets an abort.
   With PRI, it can instead REQUEST that the page be mapped:  */

   device --> Page Request (via the PRI queue) --> software
   software pages the memory in, maps it
   software --> CMD_PRI_RESP (success) --> SMMU --> device
   device retries the access

/* This requires STALL mode: STE.S1STALLD = 0, so a faulting
   transaction is HELD rather than terminated. The device's
   pipeline stalls until the response arrives.

   What it enables: DEMAND PAGING for devices. A GPU can be
   given a pointer to memory that is swapped out, and it will
   fault it in exactly as a CPU would.

   What it costs: a stalled transaction occupies device
   resources. A storm of page requests can deadlock a device
   whose queues fill. And it only works if the device supports
   it — most do not.                                       */

/* Check support: */
        SMMU_IDR0.PRI          /* SMMU supports PRI          */
        SMMU_IDR0.STALL_MODEL  /* can it stall, or only
                                  terminate?                 */

SVA: sharing a process's address space

The payoff of the identical descriptor format

Because the SMMU uses exactly the CPU's translation table format (ARM 14), the OS can point a device's Context Descriptor at a user process's own page tables, with the same ASID. The device then dereferences precisely the pointers the application uses — no dma_map, no IOVA allocation, no copying.

   WITHOUT SVA                      WITH SVA

   app allocates a buffer           app allocates a buffer
   dma_map_single()                 (nothing)
     -> allocate an IOVA
     -> build SMMU page tables
     -> invalidate
   pass the dma_addr_t to the       pass the ORDINARY POINTER
     device                           to the device
   device DMAs                      device DMAs, translating
   dma_unmap_single()                 through the process's own
     -> tear it all down              page tables
                                     (nothing)

  Requirements, all three:
     1. the device supports ATS and PRI, because process memory
        can be swapped out or moved at any time
     2. the SMMU supports SubstreamIDs, so each process gets its
        own CD
     3. the OS wires the process's mm to a CD and keeps the ASID
        in sync, including on TLB invalidation

  Linux API:
        handle = iommu_sva_bind_device(dev, mm);
        pasid  = iommu_sva_get_pasid(handle);
        /* pass pasid to the device; it now sees the process's
           address space */
        iommu_sva_unbind_device(handle);

  Used by: GPU compute, smart NICs, accelerators — anywhere the
  marshalling cost of dma_map dominates the actual work.

Performance

Address translation for devices costs the same kinds of thing it costs for the processor: table walks, TLB pressure, and invalidation. These are the numbers and the knobs that affect them.

CostMitigation
Translation on every transactionSMMU TLBs; huge pages at both stages
Walk on a TLB miss (up to 24 accesses nested)Walk caches; cacheable table walks in the CD/STE
Map/unmap page-table editsPersistent mappings; larger buffers; scatter-gather in one call

The Linux picture

The kernel's IOMMU layer presents all of the above through a small number of APIs, and knowing which kernel concept maps to which hardware structure is what makes kernel SMMU code readable.
