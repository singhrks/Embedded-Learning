Entropy coding: Huffman, arithmetic and CABAC

The last stage of every codec, and the only lossless one. It takes the quantised symbols and writes them in as few bits as their statistics allow — and the gap between "as few as Huffman allows" and "as few as information theory allows" is worth about 15% of your bitrate.

Huffman: one integer number of bits per symbol

   Build a binary tree, most frequent symbols nearest the
   root. Symbol probabilities:

     A 0.45   B 0.25   C 0.15   D 0.10   E 0.05

                    (1.0)
                   /     \
                 A(.45)  (.55)
                        /     \
                     B(.25)   (.30)
                             /     \
                          C(.15)   (.15)
                                  /     \
                               D(.10)  E(.05)

     A = 0        1 bit
     B = 10       2 bits
     C = 110      3 bits
     D = 1110     4 bits
     E = 1111     4 bits

   Average = .45(1) + .25(2) + .15(3) + .10(4) + .05(4) = 2.00
   Entropy = 2.04... wait, entropy here is 1.98 bits.

   So Huffman costs 2.00 where the floor is 1.98. Close - on
   THIS distribution.

   THE FUNDAMENTAL LIMIT: a Huffman code must use a WHOLE
   NUMBER of bits per symbol. When one symbol is very likely,
   that rounding is brutal:

     P(zero) = 0.95  ->  ideal cost = -log2(0.95) = 0.074 bits
                         Huffman must spend      = 1 bit
                         THIRTEEN TIMES too many.

   And "mostly zeros" is exactly what a quantised transform
   block looks like (chapter 7). This is why JPEG's entropy
   coder leaves real compression on the table, and why every
   codec after it moved to arithmetic coding.

   THE WORKAROUND JPEG USES: code (RUN, SIZE) PAIRS rather
   than individual coefficients, so one symbol covers many
   zeros. It helps, and it is still not enough.

Arithmetic coding: fractional bits

/* The whole message becomes ONE number in [0,1). Each symbol
   narrows the interval in proportion to its probability. */

  Alphabet: A=0.6  B=0.3  C=0.1
  Encode "ABA":

  start                 [0.0000, 1.0000)   width 1.0
  'A' -> first 60%      [0.0000, 0.6000)   width 0.6
  'B' -> next 30% of it [0.3600, 0.5400)   width 0.18
  'A' -> first 60%      [0.3600, 0.4680)   width 0.108

  Transmit ANY number in the final interval - say 0.4.
  Bits needed = -log2(0.108) = 3.21 bits.

  Huffman on this alphabet: A=1 bit, B=2, C=2 -> "ABA" = 4 bits.

/* THE KEY PROPERTY: a symbol of probability p costs
   -log2(p) bits, and that number need not be an integer.
   A symbol with p = 0.95 genuinely costs 0.074 bits, because
   it barely narrows the interval at all.

   THE PRACTICAL PROBLEMS, and their solutions:

   1. Infinite precision is impossible.
      -> RENORMALISATION: as the interval narrows, the leading
         bits stop changing. Emit them and rescale. The
         encoder keeps a fixed-width register.

   2. The E3 / straddle condition: the interval sits across
      0.5 so no leading bit is settled.
      -> count the pending bits and emit them once the
         ambiguity resolves.

   3. Division is expensive in hardware.
      -> MULTIPLICATION-FREE variants using lookup tables.
         This is exactly what CABAC's M-coder does.

   4. It was patented until the mid-2000s.
      -> which is why JPEG has an arithmetic mode that
         nobody implemented, and why H.264 shipped CAVLC as
         well as CABAC.                                     */
Coding is only half of it; modelling is the other half

An arithmetic coder achieves -log2(p) bits — but only if your p is right. A coder with a perfect model and a mediocre engine beats a perfect engine with a bad model, every time. That is why modern codecs spend enormous effort on context modelling: not "how do I write this bit cheaply", but "given everything the decoder already knows, how likely is this bit to be 1?"

CABAC: context-adaptive binary arithmetic coding

   H.264's entropy coder, and the shape of every one since.
   THREE STAGES:

   1. BINARISATION
        Every syntax element becomes a string of bits.
        A motion vector difference of 5 becomes, say,
        "1 1 1 1 1 0" in a unary-ish code. Now the coder only
        ever handles BINARY decisions, which makes the
        arithmetic tractable in hardware.

   2. CONTEXT MODELLING
        Each bin is coded with a probability chosen from a
        CONTEXT selected by neighbouring data:

          coding "is this block's coefficient non-zero?"
            context depends on how many neighbours were
            non-zero
          coding a motion vector
            context depends on the neighbours' motion vectors
          coding a skip flag
            context depends on whether the blocks above and
            left were skipped

        H.264 has ~460 contexts. Each holds a 6-bit
        probability state and an MPS (most probable symbol)
        flag.

   3. BINARY ARITHMETIC CODING
        The M-coder: multiplication-free, table-driven,
        4 x 64 entries. Two paths:
          REGULAR    uses and updates a context
          BYPASS     assumes p = 0.5, no context, much faster
                     - used for sign bits and the tails of
                     long values, which really are random

   ADAPTATION: after coding each bin, the context's state
   moves toward what actually happened. The model tracks the
   content as it changes, with no side information - the
   decoder performs the identical update.

   THE RESULT: 10-15% smaller than CAVLC at the same quality,
   for free at the decoder. AV1's multi-symbol coder and
   VVC's CABAC are refinements of the same idea.
/* The decoder side, simplified, to show the shape. */

typedef struct { uint8_t state; uint8_t mps; } ctx_t;

static int decode_bin(cabac_t *c, ctx_t *ctx)
{
        /* Look up the sub-interval width for this state. */
        int qIdx  = (c->range >> 6) & 3;
        int rLPS  = rangeTabLPS[ctx->state][qIdx];
        c->range -= rLPS;

        int bin;
        if (c->offset >= c->range) {          /* LPS path      */
                c->offset -= c->range;
                c->range   = rLPS;
                bin        = 1 - ctx->mps;
                if (ctx->state == 0)
                        ctx->mps ^= 1;        /* flip MPS      */
                ctx->state = transIdxLPS[ctx->state];
        } else {                              /* MPS path      */
                bin        = ctx->mps;
                ctx->state = transIdxMPS[ctx->state];
        }

        renormalise(c);          /* shift in bits until range
                                    is back in range          */
        return bin;
}

/* NOTE WHAT THIS COSTS: the next decision depends on the
   updated state, which depends on this decision. CABAC is
   INHERENTLY SERIAL - one bin at a time, with a loop-carried
   dependency.

   That single property is why:
     * CABAC decode is the hardest part of a video decoder to
       accelerate, and often the bottleneck at high bitrates
     * hardware decoders have a dedicated CABAC engine, and
       its throughput sets the maximum bitrate the chip
       supports
     * H.264 levels specify a maximum bin rate, not just a
       bitrate
     * SLICES and TILES exist partly so several CABAC engines
       can run in parallel - each slice resets the contexts
       and can be decoded independently. WPP (wavefront
       parallel processing) in HEVC is the refined version.  */

Entropy coding is where bitstream corruption becomes catastrophic

Because arithmetic coding has no byte alignment and the context state is carried forward, a single flipped bit desynchronises the decoder for the rest of the slice — you do not get one wrong pixel, you get garbage until the next resynchronisation point. That is why streams have start codes, slices and IDR frames, and why a dropped packet on a long GOP produces seconds of smearing rather than one bad frame (chapter 10).
