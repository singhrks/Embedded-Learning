Performance monitoring and the PMU

Every ARM core contains counters that measure what the microarchitecture is actually doing. This is ground truth rather than inference — and knowing which events to count turns performance work from guessing into measurement.

What the PMU provides

The performance monitoring unit counts hardware events — cycles, cache misses, branch mispredictions — with no overhead, which is what makes measurement possible rather than merely estimation.

   PMCCNTR_EL0        a dedicated 64-bit CYCLE counter
   PMEVCNTR0-30_EL0   general counters, 32-bit (64-bit in
                      ARMv8.5), each programmable to count one
                      event
   PMEVTYPER0-30_EL0  which event each counter counts, plus
                      filters (count at EL0? EL1? EL2? secure?)

   PMCR_EL0           enable, reset, and how many counters exist
   PMCNTENSET_EL0     enable individual counters
   PMOVSSET_EL0       overflow status — the interrupt source
   PMINTENSET_EL1     enable overflow interrupts
   PMUSERENR_EL0      may EL0 access these directly?

  The NUMBER of counters is implementation defined — typically
  4 to 6 on a small core, 6 to 8 on a large one. Read it:

        mrs     x0, pmcr_el0
        ubfx    x0, x0, #11, #5         /* N field */

  This is why perf multiplexes: ask for more events than there
  are counters and it time-slices them, scaling the results.
  The scaling factor appears in perf's output, and heavily
  multiplexed measurements are correspondingly noisy.

Reading the numbers

Counters are just registers, and reading them is straightforward. The subtlety is in knowing what each event actually counts on the specific core you are running on.

START with IPC. It tells you which world you are in:

   IPC = INST_RETIRED / CPU_CYCLES

     < 0.5   STALLED. Find out on what.
     0.5-1.5 mixed
     > 2.0   compute bound — further gains need a better
             ALGORITHM, not micro-optimisation

THEN split the stalls:

   STALL_FRONTEND high  → INSTRUCTION supply
        · I-cache misses, ITLB misses, branch mispredicts
        · fixes: code layout, PGO, fewer/more predictable
          branches, smaller hot code

   STALL_BACKEND high   → DATA supply or execution
        · D-cache misses, dependency chains, divides
        · fixes: data layout, blocking, more ILP (CA ch. 19)

THEN the specific rates:

   L1D miss rate    = L1D_CACHE_REFILL / L1D_CACHE
   LLC miss rate    = LL_CACHE_MISS_RD / LL_CACHE_RD
   branch miss rate = BR_MIS_PRED_RETIRED / BR_RETIRED
                      > 2% is worth investigating
   TLB walks/insn   = DTLB_WALK / INST_RETIRED
                      high → try huge pages

AND the speculation waste:

   INST_SPEC vs INST_RETIRED
     a large gap means work was executed and thrown away —
     heavy misprediction (CA chapter 12)

Using perf

In practice you will use the kernel's tooling rather than the registers directly, because it handles multiplexing, scaling and symbolisation for you.

# the standard first look
perf stat ./program
#   12,405,281,113  cycles                    #  2.98 GHz
#   18,204,113,782  instructions              #  1.47  insn per cycle
#    3,201,554,231  branches
#       62,119,882  branch-misses             #  1.94% of all branches

# ARM-specific, by architected name
perf stat -e cycles,instructions,\
l1d_cache,l1d_cache_refill,\
l2d_cache_refill,ll_cache_miss_rd,\
dtlb_walk,itlb_walk,\
br_retired,br_mis_pred_retired,\
stall_frontend,stall_backend ./program

# by raw event number, when the kernel does not know the name
perf stat -e r0011,r0008 ./program        # cycles, instructions

# WHICH function, and which instruction?
perf record -g ./program && perf report
perf record -e l1d_cache_refill ./program && perf annotate

# system-wide
perf stat -a sleep 10
perf top

# what does this kernel expose?
perf list | grep -i arm
ls /sys/bus/event_source/devices/

Sampling versus counting

Counting tells you how much of something happened; sampling tells you where. They answer different questions and the distinction determines which one you should be running.

COUNTING       program a counter, run, read the total.
               Exact. No overhead beyond the counter itself.
               → perf stat

SAMPLING       program the counter to OVERFLOW after N events,
               and take an interrupt. The handler records the PC.
               → perf record

  Sampling gives you attribution — WHICH code caused the misses —
  at the cost of overhead and of SKID: the PC recorded at the
  overflow interrupt is not exactly the instruction that caused
  the event, because the pipeline had moved on.

  Skid is why perf annotate sometimes blames the instruction
  AFTER the real culprit. Two mitigations:

    SPE — Statistical Profiling Extension (ARMv8.2). Hardware
          samples individual OPERATIONS and records the PC, the
          data address, the latency and the source of the data,
          into a memory buffer. No skid, and vastly richer.

          perf record -e arm_spe// -- ./program
          perf report --sort=symbol,srcline

    BRBE — Branch Record Buffer Extension (ARMv9). A hardware
           branch history, giving exact taken/not-taken paths.

  If your core has SPE, use it. It answers "which load missed,
  and where did the data come from" directly, which counting
  never can.

Access control

User space cannot read these counters unless it is allowed to, and the control is deliberate — the counters leak timing information that has been used in real attacks.

/* By default EL0 cannot touch the PMU. PMUSERENR_EL0 gates it: */

   PMUSERENR_EL0[0]  EN     allow EL0 access to all PMU registers
                [1]  SW     allow EL0 writes to PMSWINC
                [2]  CR     allow EL0 to read the CYCLE counter
                [3]  ER     allow EL0 to read event counters

/* Enabling direct EL0 access removes the syscall from the
   measurement path — essential for microbenchmarks: */
        msr     pmuserenr_el0, #0xF

/* Linux exposes this as a sysctl: */
//   /proc/sys/kernel/perf_user_access   (arm64, 5.17+)

/* Why it is off by default: a cycle counter readable from
   userspace is a high-resolution TIMING SIDE CHANNEL, useful for
   cache-timing attacks. The same reasoning applies to
   CNTVCT_EL0, which hardened configurations sometimes also
   disable (chapter 32).                                    */

/* And the general perf gate: */
//   /proc/sys/kernel/perf_event_paranoid
//     -1  everything
//      0  no CPU events for unprivileged users
//      1  no tracepoints            (common default)
//      2  no kernel profiling       (hardened default)
//      3  no perf at all

Reading counters directly

For very tight measurement loops, going through the kernel adds more overhead than the thing being measured. Reading the registers directly is possible, with caveats.

/* For a tight microbenchmark, the perf syscall overhead can
   exceed what you are measuring. Read the counter yourself: */

static inline uint64_t read_cycles(void)
{
        uint64_t v;
        asm volatile("isb");                    /* order it */
        asm volatile("mrs %0, pmccntr_el0" : "=r"(v));
        return v;
}

/* Setup, from EL1: */
static void pmu_enable(void)
{
        /* enable the PMU and reset the cycle counter */
        write_sysreg(BIT(0) | BIT(2), pmcr_el0);   /* E | C  */
        /* enable the cycle counter */
        write_sysreg(BIT(31), pmcntenset_el0);
        /* do not divide by 64 */
        write_sysreg(read_sysreg(pmcr_el0) & ~BIT(3), pmcr_el0);
        /* allow EL0 access */
        write_sysreg(0xF, pmuserenr_el0);
        isb();
}

/* Programming an event counter: */
static void pmu_count_event(int counter, uint32_t event)
{
        write_sysreg(counter, pmselr_el0);      /* select        */
        isb();
        write_sysreg(event, pmxevtyper_el0);    /* which event   */
        write_sysreg(BIT(counter), pmcntenset_el0);
        isb();
}

/* The ISBs matter: without them the counter read can be
   reordered relative to the code being measured, giving results
   that vary with unrelated changes (chapter 21).          */
Microbenchmarking traps
  • Frequency scaling. Cycles are a stable unit; seconds are not. Either pin the governor (cpupower frequency-set -g performance) or measure cycles.
  • Core migration. On big.LITTLE the same code runs at very different speeds. Pin with taskset.
  • The counter is per-core. If the thread migrates mid-measurement, the delta is meaningless.
  • Cold caches. The first iteration measures the miss, not the code. Warm up, then measure.
  • Dead code elimination. If the result is unused the compiler deletes the work (C ch. 01). Consume it.

The PMU under virtualisation

Counters inside a virtual machine may or may not reflect reality, depending on how the hypervisor configured them — which matters a great deal before trusting a measurement taken in a guest.

/* MDCR_EL2 controls guest PMU access: */
   MDCR_EL2.TPM    trap all PMU register access to EL2
   MDCR_EL2.TPMCR  trap PMCR_EL0 only
   MDCR_EL2.HPMN   how many counters the guest may use — the
                   rest are reserved for the hypervisor

/* So a hypervisor can:
     · give the guest a virtual PMU (KVM emulates it)
     · partition the counters between host and guest
     · deny access entirely, which is common in cloud
       environments because a cycle counter is a side channel

   Which is why `perf` inside a VM often reports nothing, or
   reports host-visible events that do not correspond to the
   guest's own execution. Check:                            */
//   dmesg | grep -i 'kvm.*pmu'
//   perf stat ./prog     → "not supported" means the PMU is
//                          not exposed to this guest

Beyond the core

Events outside the core — at the interconnect, the memory controller, the caches shared between clusters — need their own counters, and they are where memory bandwidth problems become visible.

/* Many SoCs expose additional PMUs outside the CPU: */

   DSU PMU        the DynamIQ Shared Unit — the cluster's L3
   CMN PMU        the coherent mesh interconnect (chapter 25)
   SMMU PMU       translation and TLB behaviour of DMA masters
   DDR / memory controller PMU
   GPU, NPU, and other accelerator counters

perf list | grep -iE 'arm_dsu|arm_cmn|smmu|ddr'
perf stat -e arm_cmn_0/hnf_cache_miss/ -a sleep 10
perf stat -e arm_dsu_0/bus_access/ ./prog

/* These answer questions the core PMU cannot:
     · is the interconnect saturated, or is DRAM the limit?
     · which agent is consuming memory bandwidth?
     · are SMMU TLB misses hurting a DMA-heavy workload?

   On a system where several masters share bandwidth (OS
   chapter 19), these are the only way to attribute the
   contention.                                              */

A workflow

Tools matter less than method. This is the order that finds the real bottleneck fastest, rather than confirming whichever theory you started with.

  1. MEASURE the thing you actually care about, end to end.
     If it is not repeatable, stop and fix that first.

  2. perf stat — get IPC.
        low  → continue to 3
        high → the algorithm is the problem; stop measuring
               microarchitecture

  3. Split the stalls: frontend or backend?

  4. Drill into the specific rate — cache, TLB, branch.

  5. perf record on THAT event → which function, which line.

  6. Fix the largest contributor, and ONLY that one.

  7. Re-measure. Did the predicted gain appear? If not, the
     model was wrong — that is information.

  8. Re-profile. The bottleneck has moved.

  Never skip step 1, and never optimise anything perf has not
  shown you. CA chapter 18 has the arithmetic that makes this
  worth doing in this order.

SymptomCause
