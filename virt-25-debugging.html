Debugging in practice: four failures, hunted down

Hypervisor bugs are unpleasant because the symptom appears in the guest and the cause is in the host, with a hardware boundary in between that hides most of your usual tools. These are four real shapes of failure, followed from the symptom to the line, with the reasoning shown rather than the answer announced.

The instruments, and what each one can see

Before the cases, it is worth being clear about which side of the boundary each tool sits on — because the commonest mistake is spending an hour with a tool that structurally cannot observe the thing you are looking for.

The single most useful habit is to establish, in the first minute, which side is running. A guest that is not being entered at all is a completely different investigation from a guest that is running and producing nothing, and one perf kvm stat distinguishes them.

Case 1: the guest boots to silence

A new board port. The hypervisor starts the guest, and nothing appears on the guest console — no kernel banner, no panic, nothing at all.

   SYMPTOM   no output, no crash, no host error.

   FIRST QUESTION: is it running at all?

     $ perf kvm stat live
     ... exits accumulating steadily, mostly MMIO ...

   SO IT IS RUNNING. That eliminates half the possibilities
   immediately - the vCPU is being entered, the stage-2
   tables are good enough to fetch instructions, and it is
   not stuck in the host.

   A guest that were NOT running would show zero exits, and
   the investigation would go to the entry path instead.

   ---------------------------------------------------------

   SECOND QUESTION: what is it touching?

     $ trace-cmd record -e kvm:kvm_mmio -e kvm:kvm_exit
     $ trace-cmd report | head

       kvm_exit: reason DABT_LOW ... ipa 0x09000000
       kvm_mmio: mmio write len 4 gpa 0x9000000 val 0x58
       kvm_exit: reason DABT_LOW ... ipa 0x09000000
       kvm_mmio: mmio write len 4 gpa 0x9000000 val 0x59

   IT IS WRITING CHARACTERS. 0x58 is 'X', 0x59 is 'Y'. The
   guest is printing happily to 0x09000000 and something
   downstream is dropping it.

   ---------------------------------------------------------

   THIRD QUESTION: who owns 0x09000000?

     In the device model: the UART is registered at
     0x09000000. Good.
     In the device tree handed to the guest: also
     0x09000000. Good.

   So both ends agree - and yet nothing comes out. The
   remaining possibility is that the write is REACHING the
   model and the model is discarding it.

     static void uart_write(u64 off, u32 val) {
         if (off == UART_DR)
             putchar(val);
     }

   AND THE TRACE SAID: gpa 0x9000000, which is the BASE.
   What offset did the model compute?

     off = gpa - base;       /* 0 - correct */

   ... unless base was never initialised for this platform,
   in which case off is 0x9000000, UART_DR is 0x00, the
   comparison fails, and every character is silently
   dropped.

   ---------------------------------------------------------

   THE BUG   a per-platform base address left at zero.
   THE FIX   one line.
   THE LESSON  "no output" made this look like a serious
   bring-up problem. Two traces showed the guest was fine
   and the fault was three layers above the hardware. ASK
   WHETHER IT IS RUNNING BEFORE ASSUMING IT IS NOT.

Case 2: the guest hangs under load, and only sometimes

A guest that has been stable for weeks starts hanging during heavy I/O, roughly once a day, with no panic. Attaching a debugger shows every vCPU idle in WFI, waiting for an interrupt that never comes.

   SYMPTOM   intermittent hang; all vCPUs in WFI; the device
             says it completed the work.

   "AN INTERRUPT WENT MISSING" is the diagnosis, and it is
   almost always one of three things (chapter 11):

     A. never injected       - the hypervisor did not do it
     B. injected and lost    - a list register was reused
     C. injected, guest got it, guest never EOI'd

   DISTINGUISHING THEM IS THE WHOLE JOB, and the vGIC state
   answers it directly.

   ---------------------------------------------------------

     $ trace-cmd record -e kvm:kvm_vgic\* -e kvm:kvm_entry

   On the hang, the last records show:

     vgic_update_irq_pending  irq=42 level=1
     kvm_entry                (no injection recorded)

   SO IT WAS MARKED PENDING AND NEVER PLACED IN A LIST
   REGISTER. That eliminates B and C, and points at the code
   that chooses which pending interrupts to inject.

   ---------------------------------------------------------

   THE LIST REGISTERS ARE A FIXED, SMALL RESOURCE - four on
   many implementations. If more interrupts are pending than
   there are registers, the hypervisor must:

     1. inject as many as fit,
     2. enable a MAINTENANCE INTERRUPT so it is told when
        one is consumed,
     3. inject the rest then.

   Step 2 is the one that gets forgotten, because under
   light load there are never more than four pending and the
   code path never runs. Under heavy I/O it does, and the
   surplus interrupt waits forever for a hypervisor that is
   not going to be woken.

   ---------------------------------------------------------

   THE BUG   the underflow maintenance interrupt was enabled
             only on the first overflow, not re-armed.
   THE LESSON  "intermittent, only under load" is very often
   a FIXED-SIZE RESOURCE being exhausted for the first time.
   Ask what is finite, and what is supposed to happen when
   it runs out - then check that path has ever executed.

Case 3: virtio corrupts data, rarely, on one core type

A virtio-blk implementation passes every test on the development machine and corrupts occasional sectors on the target — a big.LITTLE SoC, and only when the workload migrates between clusters.

   SYMPTOM   rare corruption; reproduces on target hardware,
             never on x86; correlates with migration between
             cores.

   THAT CORRELATION IS THE ENTIRE CLUE. A bug that appears
   on a weakly ordered machine and not on a strongly ordered
   one is a MEMORY ORDERING bug until proven otherwise
   (chapter 15).

   ---------------------------------------------------------

   THE VIRTQUEUE PROTOCOL has a strict publication order.
   The driver must:

     1. write the descriptor
     2. BARRIER
     3. write the available-ring index
     4. BARRIER
     5. notify

   Step 2 is the load-bearing one: it guarantees the device
   cannot observe the new index before the descriptor it
   refers to. Without it, on a weakly ordered core, the two
   stores can become visible in either order.

   SO THE DEVICE READS AN INDEX POINTING AT A DESCRIPTOR
   THAT HAS NOT LANDED YET, and processes whatever was in
   that slot before - stale addresses, stale lengths.

   ---------------------------------------------------------

   WHY x86 NEVER SHOWED IT: on a strongly ordered machine,
   stores become visible in program order anyway. The
   barrier is a no-op there, so omitting it is invisible.
   THE CODE WAS ALWAYS WRONG. Only the hardware changed.

   ---------------------------------------------------------

   FINDING IT, when the trace tells you nothing:

     · REVIEW THE BARRIERS AGAINST THE SPECIFICATION. The
       virtio spec states the required order explicitly, and
       this is one of the rare bugs where reading is faster
       than measuring.
     · LOG THE DESCRIPTOR the device consumed alongside the
       index. A mismatch confirms it in one run.
     · Under emulation, ordering bugs USUALLY DISAPPEAR -
       which is itself evidence, and a reason not to trust a
       clean run under QEMU as proof.

   THE LESSON  "works on one machine, not another" plus
   "rare" plus "shared memory" is a memory-model bug. Do not
   start by suspecting the device.

Case 4: a ten-line change made everything three times slower

A guest that ran acceptably now runs at a third of the speed. The change was small and looked harmless, and nothing in the guest was touched.

   SYMPTOM   large uniform slowdown after a small host-side
             change. The guest is unmodified.

   THE FIRST MEASUREMENT IS ALWAYS THE SAME (chapter 23):

     $ perf kvm stat live

       BEFORE    ~4,000 exits/sec
       AFTER     ~900,000 exits/sec, almost all SYSREG

   AN EXIT STORM, and the reason field names the culprit
   class immediately. This is why exits are step one: the
   answer is usually in the first command.

   ---------------------------------------------------------

   WHICH REGISTER?

     $ trace-cmd record -e kvm:kvm_sys_access
     $ trace-cmd report | awk '{print $NF}' | sort | uniq -c | sort -rn

       871204 CNTV_CTL_EL0
          312 ...

   The guest is touching a timer register constantly and
   trapping every time.

   ---------------------------------------------------------

   WHY? The change enabled a trap bit "for observability" -
   a debugging aid that was meant to be temporary and was
   committed. The guest's idle loop reads that register on
   every tick, and each read is now a full world switch:
   roughly two microseconds instead of a few nanoseconds
   (chapter 08).

   A REGISTER READ MADE A THOUSAND TIMES MORE EXPENSIVE, in
   the hottest loop the guest has.

   ---------------------------------------------------------

   THE LESSON, and it generalises past this bug:

     TRAPS ARE A POLICY DECISION WITH A PRICE TAG (chapter
     04). Enabling one is cheap to write and can be
     catastrophic to run, and NOTHING WARNS YOU - the system
     stays correct, it just becomes slow.

     So: after any change to trap configuration, count the
     exits. It is one command, and it is the difference
     between shipping this and finding it in the field.

The method underneath all four

The cases differ; the procedure does not. Working in this order is what stops an investigation wandering.

   1. WHICH SIDE IS RUNNING?
        Zero exits means the guest is not executing - look
        at entry, stage-2, or the host. Exits accumulating
        means the guest is fine and something it depends on
        is not.

   2. COUNT BEFORE YOU TRACE.
        perf kvm stat is one command and frequently names
        the problem. Tracing everything first buries the
        signal.

   3. NARROW BY EXIT REASON, then by address or register.
        Every case above was solved by "which reason, and
        which specific thing".

   4. ASK WHAT IS FINITE.
        Intermittent, load-dependent failures are usually a
        fixed-size resource - list registers, queue slots,
        shared-memory regions - overflowing for the first
        time.

   5. ASK WHAT THE HARDWARE GUARANTEES.
        "Works on one machine, not another" is a memory
        model or a feature-detection problem, not a logic
        problem.

   6. CHANGE ONE THING AND RE-MEASURE.
        With exit counts as the metric, a regression is
        visible in seconds rather than arguable for days.

How it shows up

SymptomLikely cause

Check yourself

  • Say which tool answers "is the guest running at all", and what its two answers mean.
  • Explain why "no output" does not imply the guest failed to start.
  • Name the three ways an interrupt can go missing, and how the vGIC state distinguishes them.
  • Explain why list-register exhaustion only appears under load.
  • Say why a virtio ordering bug never reproduces on x86.
  • Give the required publication order for a virtqueue and the load-bearing barrier.
  • Explain why a clean run under emulation is weak evidence for an ordering bug.
  • Describe how one trap bit tripled the cost of a workload.
  • State what you should measure after any trap-configuration change.
  • Give the six steps of the method, in order.
