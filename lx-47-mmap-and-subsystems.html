Exposing a driver properly: mmap and subsystem registration

Two things this track has told you to do without ever showing you how. Chapter 23 argued that you should use an existing subsystem instead of inventing an interface — this chapter registers with one. And chapter 22 covered every file operation except the one that matters most for moving real data: mmap.

Part 1 — mmap: letting userspace touch the buffer directly

Everything so far has moved data by copying it between the kernel and user space. For small transfers that is exactly right; for large ones the copying becomes the dominant cost, and there is a way to avoid it entirely.

   WITH read()/write(), EVERY BYTE IS COPIED:

     device buffer (kernel)  --copy_to_user-->  user buffer
                                   ^
                          one full copy of the data,
                          every single transfer

   For a temperature sensor sending 2 bytes a second, that
   copy costs nothing and read() is the right answer.

   For a camera sending 60 frames a second at 8 MB a frame -
   480 MB/s - that copy is roughly half your memory bandwidth
   spent achieving nothing.

   WITH mmap(), THERE IS NO COPY AT ALL:

     the SAME physical pages appear in the process's address
     space. Userspace reads the buffer the device DMA'd into,
     directly.

     user virtual address ----+
                              |  page tables point at
     kernel virtual address --+--> THE SAME PHYSICAL PAGES
                              |
     device DMA writes here --+

   THIS IS WHY EVERY HIGH-BANDWIDTH SUBSYSTEM USES IT: V4L2
   for video, ALSA for audio, DRM for graphics. They all
   expose buffers by mmap and pass around buffer INDICES,
   never the data itself.
/* THE TWO CASES, and using the wrong one is the classic bug. */

/* CASE 1: mapping a DMA buffer (the common one).
   dma_alloc_coherent gave you memory; dma_mmap_coherent maps
   THAT SAME memory to userspace, and it knows about the
   architecture's cache and attribute requirements - which
   you would otherwise have to get right by hand.          */

static int my_mmap(struct file *file, struct vm_area_struct *vma)
{
        struct my_dev *d = file->private_data;
        size_t size = vma->vm_end - vma->vm_start;

        /* VALIDATE. vm_pgoff and the length come straight from
           userspace and are entirely under its control - this
           check is the whole security boundary of mmap.     */
        if (size > d->dma_size)
                return -EINVAL;
        if (vma->vm_pgoff != 0)          /* we only offer the
                                            one buffer, at 0  */
                return -EINVAL;

        return dma_mmap_coherent(d->dev, vma,
                                 d->dma_virt,   /* kernel addr */
                                 d->dma_handle, /* dma addr    */
                                 size);
}

/* CASE 2: mapping device REGISTERS or a physical region.
   remap_pfn_range installs page-table entries pointing at a
   physical page frame number directly.                     */

static int my_mmio_mmap(struct file *file,
                        struct vm_area_struct *vma)
{
        struct my_dev *d = file->private_data;
        size_t size = vma->vm_end - vma->vm_start;

        if (size > d->reg_size || vma->vm_pgoff != 0)
                return -EINVAL;

        /* Registers are NOT normal memory: they must not be
           cached, and the CPU must not reorder or combine
           accesses to them.                                 */
        vma->vm_page_prot = pgprot_noncached(vma->vm_page_prot);

        return remap_pfn_range(vma,
                               vma->vm_start,
                               d->reg_phys >> PAGE_SHIFT,
                               size,
                               vma->vm_page_prot);
}

static const struct file_operations my_fops = {
        .owner   = THIS_MODULE,
        .open    = my_open,
        .release = my_release,
        .mmap    = my_mmap,
};
An unvalidated mmap hands the whole machine to any process that can open your device

vma->vm_pgoff and the mapping length are supplied entirely by userspace. If you pass them to remap_pfn_range() without bounds-checking, a caller chooses any physical address and your driver maps it into their process — kernel memory, another device's registers, another process's pages. This is not a theoretical concern; it is a recurring class of real CVEs in vendor drivers. Check the length against your buffer's actual size, and either reject a non-zero vm_pgoff or validate it against a range you own. There is no framework doing this for you.

/* THE USERSPACE SIDE, so you can test it: */

        int fd = open("/dev/mydev", O_RDWR);
        size_t len = 4096;

        void *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
                       MAP_SHARED,      /* SHARED, not PRIVATE -
                                           PRIVATE would give a
                                           copy-on-write copy and
                                           the device would never
                                           see your writes      */
                       fd, 0);
        if (p == MAP_FAILED) { perror("mmap"); return 1; }

        /* p now points at the device's buffer. No copies. */
        printf("first word: 0x%08x\n", ((uint32_t *)p)[0]);

        munmap(p, len);
        close(fd);

Part 2 — registering with a subsystem instead of inventing an interface

Chapter 27's temperature sensor exposed a file called temp containing a number. It works, but it invented a private interface: no existing tool knows that file exists, nobody knows what unit the number is in, and every program wanting the reading must be taught about your specific driver. Registering with hwmon instead takes about the same amount of code and produces an interface that sensors, Prometheus exporters and every monitoring agent already understand.

/* The same sensor from chapter 27, done properly. */

#include <linux/hwmon.h>

/* 1. Declare WHAT you have: one temperature channel, which
      can be read, and which has a label.                   */
static const struct hwmon_channel_info *tmp102_info[] = {
        HWMON_CHANNEL_INFO(chip, HWMON_C_REGISTER_TZ),
        HWMON_CHANNEL_INFO(temp, HWMON_T_INPUT),
        NULL
};

/* 2. Say which of those are actually accessible, and how. */
static umode_t tmp102_is_visible(const void *data,
                                 enum hwmon_sensor_types type,
                                 u32 attr, int channel)
{
        return 0444;            /* read-only, to everyone */
}

/* 3. One read function for every channel. The core has
      already told you WHICH value it wants.               */
static int tmp102_read(struct device *dev,
                       enum hwmon_sensor_types type,
                       u32 attr, int channel, long *val)
{
        struct tmp102 *t = dev_get_drvdata(dev);
        int milli, ret;

        if (type != hwmon_temp || attr != hwmon_temp_input)
                return -EOPNOTSUPP;

        ret = tmp102_read_millicelsius(t, &milli);
        if (ret)
                return ret;

        *val = milli;    /* hwmon's UNIT IS FIXED: temperatures
                            are millidegrees Celsius, always.
                            That fixed convention is the whole
                            point - no tool has to ask.       */
        return 0;
}

static const struct hwmon_ops tmp102_hwmon_ops = {
        .is_visible = tmp102_is_visible,
        .read       = tmp102_read,
};

static const struct hwmon_chip_info tmp102_chip_info = {
        .ops  = &tmp102_hwmon_ops,
        .info = tmp102_info,
};

/* 4. Register, in probe(). One call replaces the whole
      attribute-group machinery of chapter 27.             */
        hwmon = devm_hwmon_device_register_with_info(dev,
                        "tmp102", t, &tmp102_chip_info, NULL);
        if (IS_ERR(hwmon))
                return PTR_ERR(hwmon);

The rule, stated plainly

Search drivers/ for a subsystem matching your device class before you write a line of interface code. A subsystem gives you a documented ABI, working tools on day one, less code to maintain, and a far easier path upstream — chapter 45 lists "a new custom char device where a subsystem exists" as the single most common reason a driver is asked to be rewritten. The char device is the right answer only when nothing fits, and then the burden of documenting and supporting that interface forever is yours (chapter 02's ABI rule).
