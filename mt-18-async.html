Asynchronous models: events, coroutines, async/await

A thread blocked on a socket costs a megabyte of stack and a scheduler slot to do nothing. Asynchronous models remove that cost by making waiting explicit — and charge you in a different currency: your code turns inside out, and the function colour problem arrives.

The problem with a thread per connection

Threads are an expensive way to wait. When a program's concurrency is dominated by waiting for I/O rather than by computation, a different model handles far more concurrent operations with far fewer threads.

   10,000 concurrent connections, one thread each:

     10,000 x 8 MB reserved stack   = 80 GB of address space
     10,000 kernel task structures
     a run queue the scheduler must reason about
     context switches whenever any of them wakes

   Most of those threads are doing NOTHING - waiting for a
   packet. The work is tiny; the waiting is everything.

   THE ASYNC ALTERNATIVE

     one thread (or a few), and a readiness list:

       for (;;) {
               events = wait_for_readiness(all_fds);
               for (e : events)
                       handle(e);      /* never blocks */
       }

     10,000 connections =  ~10,000 small state objects,
     a few hundred bytes each, and one thread.

   THE TRADE

     you may NEVER BLOCK inside a handler. One blocking call -
     a DNS lookup, a disk read, a mutex - stalls every other
     connection on that thread. In a threaded model it stalls
     only itself.

     That single rule is what makes async both fast and
     hostile to write.

Readiness versus completion

Two fundamentally different models for asynchronous I/O, and the distinction determines the shape of your whole program. One tells you when you may act; the other tells you when the work is already done.

Kernel tells you"you can read now""your read is done, here is the data"
You thenCall read(), which returns immediatelyNothing — the buffer is already filled

WhereLinux, BSD, macOSWindows (IOCP) since the 1990s, Linux (io_uring) since 5.1
 
/* The readiness loop, which is what most async runtimes wrap. */

int ep = epoll_create1(0);

struct epoll_event ev = {
        .events = EPOLLIN | EPOLLET,     /* edge-triggered     */
        .data.ptr = conn,
};
epoll_ctl(ep, EPOLL_CTL_ADD, conn->fd, &ev);

for (;;) {
        struct epoll_event out[64];
        int n = epoll_wait(ep, out, 64, -1);
        for (int i = 0; i < n; i++)
                handle(out[i].data.ptr);
}

/* LEVEL vs EDGE triggered - the classic epoll bug:

     LEVEL (default): reports while data remains. Forgiving.
     EDGE  (EPOLLET): reports only on a CHANGE. Fewer wake-ups,
                      and you MUST read until EAGAIN or you
                      will never be told again - the connection
                      simply goes silent and stays silent.

   With EPOLLET the loop is:
        while ((n = read(fd, buf, sizeof buf)) > 0) consume();
        if (n < 0 && errno != EAGAIN) error();

   Forget the loop and you get a hang that appears only when a
   message spans two reads.                                  */

Callbacks, and why they became coroutines

The traditional way to express "do this when that finishes" nests badly and scatters related logic. Knowing why is what motivates the alternatives that followed.

/* CALLBACK STYLE - the control flow is inside out. */

read_async(sock, buf, [](int n) {
        parse_async(buf, n, [](Request r) {
                db_query_async(r, [](Row row) {
                        render_async(row, [](string html) {
                                write_async(sock, html, [](int) {
                                        /* five levels deep, and
                                           now try adding error
                                           handling to each   */
                                });
                        });
                });
        });
});

/* PROBLEMS
     * error handling at every level, or errors vanish
     * no try/catch, no RAII scope - the stack is gone by the
       time the callback runs
     * lifetimes are manual: who owns `buf` across five
       callbacks? Use-after-free is the default outcome
     * a loop becomes a recursive callback chain
     * debugging: the stack trace shows the event loop, not
       how you got there                                     */


/* ASYNC/AWAIT - the same machine, written as straight code. */

async Task<void> serve(Socket sock) {
        try {
                auto n    = co_await read_async(sock, buf);
                auto req  = parse(buf, n);
                auto row  = co_await db_query_async(req);
                auto html = render(row);
                co_await write_async(sock, html);
        } catch (const IoError &e) {          /* works again    */
                log(e);
        }
}   /* destructors run. RAII works. Loops are loops. */

/* WHAT THE COMPILER DOES: splits the function at every await
   into a state machine, and heap-allocates the locals that
   live across a suspension point. `co_await` is "return to
   the caller, and resume here when the awaited thing
   completes".                                              */
Stackless versus stackful

Stackless coroutines (C++20, Rust, C#, JavaScript) store only the variables that survive a suspension — tens of bytes, and the compiler computes the size. You can only suspend inside a coroutine, which is why await is contagious. Stackful coroutines and goroutines get a real (growable) stack, so any function can yield — no colouring — at the cost of kilobytes each and a runtime that manages stacks. Go chose stackful; almost everyone else chose stackless.

The function colour problem

Asynchronous functions tend to infect their callers, so that one async call at the bottom forces every function above it to become async too. That property has real design consequences and is worth naming explicitly.

/* An async function can only be awaited from an async
   function. So async spreads up the call graph until it
   reaches main.                                            */

        int compute(int x);                    /* "red"  - sync */
        async Task<int> fetch(int x);          /* "blue" - async */

        /* calling fetch from compute: impossible without
           blocking, which defeats the purpose             */

/* CONSEQUENCES

   1. TWO ECOSYSTEMS. Rust has `Read` and `AsyncRead`,
      `Mutex` and `tokio::Mutex`. Python has requests and
      aiohttp. Libraries get written twice.

   2. THE BRIDGE IS DANGEROUS. block_on() from inside an async
      context deadlocks the executor - the thread that would
      run the future is the one blocked waiting for it.

   3. sleep() IS A BUG. std::thread::sleep in an async task
      blocks the whole executor thread and every other task on
      it. Every runtime ships its own: tokio::time::sleep.

   4. A LOCK HELD ACROSS AN AWAIT is held for an unbounded
      time, and in a work-stealing executor may be released
      on a different thread than took it - which is undefined
      for many mutex implementations.

   THE RULE: never hold a std mutex across an await. Either
   scope it so it is released first, or use the runtime's
   async-aware mutex.                                       */

        /* WRONG */
        let g = mutex.lock().unwrap();
        let v = fetch().await;              /* held across await */

        /* RIGHT */
        let v = fetch().await;
        { let mut g = mutex.lock().unwrap(); *g = v; }

        /* OR, when you genuinely must hold it: */
        let mut g = async_mutex.lock().await;
        let v = fetch().await;              /* fine: this mutex
                                               yields properly  */

Async is for I/O concurrency, not for speed

An async runtime does not make anything compute faster; it removes the cost of waiting. If your bottleneck is CPU, async adds state-machine overhead and buys nothing — you want a thread pool. If your bottleneck is ten thousand idle sockets, async is transformative. Diagnosing which you have, before rewriting, saves a great deal of regret.
