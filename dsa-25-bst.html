Trees: binary search trees

A binary tree with an ordering invariant, which turns search into a descent. Two facts do most of the work: comparison tells you which way to go, and an inorder traversal comes out sorted.

The pattern

The BST invariant is routinely misremembered in a way that passes small examples and fails real ones, so it is worth stating precisely before anything else.

   THE BST INVARIANT, stated correctly:

     for EVERY node, ALL values in its left subtree are
     smaller, and ALL values in its right subtree are larger.

   NOT "left child < node < right child". That weaker
   condition is the source of the most common bug in this
   chapter:

              5
             / \
            1   7          7 > 5 ✓, 4 < 7 ✓ locally
               / \         BUT 4 < 5 and it is on the
              4   8        RIGHT of 5 -> NOT A BST

   ---------------------------------------------------------
   THE TWO FACTS TO EXPLOIT

   1. COMPARISON GIVES DIRECTION
        target < node.val  ->  go LEFT
        target > node.val  ->  go RIGHT
      Search, insert and delete are all O(h) descents.

   2. INORDER TRAVERSAL IS SORTED
        left, node, right  ->  ascending order
      So "kth smallest", "validate", "find the two swapped
      nodes" and "convert to a sorted list" are all inorder
      walks (chapter 27).

   ---------------------------------------------------------
   THE COST IS THE HEIGHT, NOT log n

     balanced   h = log n   -> O(log n)
     SKEWED     h = n       -> O(n), no better than a list

     Inserting sorted data into a plain BST produces exactly
     the skewed case. Real implementations self-balance —
     AVL, red-black — which is why std::map and TreeMap are
     O(log n) guaranteed. Interviews rarely ask you to
     implement balancing, but DO ask you to state that a
     plain BST degrades.

   ---------------------------------------------------------
   VALIDATION — pass bounds DOWN

     function valid(node, lo, hi) {
         if (!node) return true;
         if (node.val <= lo || node.val >= hi) return false;
         return valid(node.left,  lo, node.val)
             && valid(node.right, node.val, hi);
     }
     valid(root, -Infinity, Infinity);

     Each recursion NARROWS the allowed range. Going left
     tightens the upper bound; going right tightens the
     lower bound. That is how a distant ancestor still
     constrains a deep descendant.

   ---------------------------------------------------------
   DELETION — the only fiddly operation

     0 children   remove it
     1 child      replace it with that child
     2 children   replace its value with the INORDER
                  SUCCESSOR (the smallest value in the right
                  subtree), then delete that successor from
                  the right subtree — it has at most one
                  child, so the recursion terminates.

When to reach for it

Sorted order from a tree

Inorder traversal. Kth smallest, sorted output, validation.

Search / insert / delete by key

Descend by comparison. O(h).

Lowest common ancestor in a BST

Much easier than the general tree — the first node between the two values is the LCA.

Range queries

Prune whole subtrees using the bounds.

Need order and fast lookup

A hash map gives O(1) lookup but no order; a balanced BST gives both at O(log n).

Build a balanced BST from sorted data

Recursive midpoint selection.

Problems

How it shows up

SymptomCause
Invalid tree acceptedOnly compared with the parent — must pass a range down
Duplicates break validationDecide whether equal values are allowed, and use <= or < consistently
Overflow with extreme valuesUse null bounds rather than INT_MIN/MAX sentinels
Kth smallest scans the whole treeStop early — an inorder walk can return as soon as k is reached
Operations degrade to O(n)Skewed tree from sorted insertions — mention self-balancing
Deletion loses a subtreeTwo-child case must reattach via the inorder successor
LCA wrong in a BSTUsed the general-tree algorithm and ignored the ordering
