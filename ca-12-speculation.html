Branch prediction and speculation

A modern processor guesses. It guesses which way branches go, executes hundreds of instructions past the guess, and throws the work away when wrong. This is why sorted data can be faster than unsorted, and it is the mechanism behind Spectre.

The problem

Chapter 11 left us with control hazards. A branch's direction is not known until several stages after it is fetched, but the front end must fetch something every cycle.

Cost of getting it wrong, by design depth

  pipeline    branch resolved at    flush penalty
  ─────────────────────────────────────────────────
  5-stage     stage 3               ~2 cycles
  10-stage    stage 7               ~7 cycles
  15-stage    stage 11              ~15 cycles
  Pentium 4   stage ~20             ~30 cycles

Branches are ~15-25% of instructions in typical code.

  With a 15-cycle penalty and NO prediction:
      CPI = 1 + 0.20 × 15 = 4.0
  With 95% prediction accuracy:
      CPI = 1 + 0.20 × 0.05 × 15 = 1.15

Prediction is not an optimisation. Without it, deep pipelines are
pointless — you would spend all your speed on flushes.

Static prediction

The cheapest approach: decide from the instruction alone, with no history.

HeuristicRationaleAccuracy
Always not-takenSimplest; just keep fetching sequentially~40%
Always takenMost branches in loops are taken~60%
Backward taken, forward not-takenA backward branch is almost always a loop; a forward branch is usually an error path~70%
Compiler hintProfile-guided, encoded in the instruction or in layout~80%
 
/* Linux and GCC let you supply the hint explicitly */
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

if (unlikely(ptr == NULL))          /* error path: moved out of line     */
        return -EINVAL;             /* so the fall-through is the common */
                                    /* case and stays in the I-cache     */

/* what this actually does: the compiler reorders basic blocks so the
   likely path is contiguous. On modern cores the dynamic predictor
   outperforms the hint within a few iterations — the real benefit is
   INSTRUCTION CACHE LAYOUT, not the prediction itself. */
Where hints still genuinely matter

On a small in-order core (Cortex-M, Cortex-A53) with a weak or absent dynamic predictor, and on the very first execution of any branch before history exists. In hot loops on a big core, remove them — they add noise and the hardware already knows better. Profile before adding one.

Dynamic prediction

One-bit predictor

Remember what the branch did last time. Keep a table of bits indexed by branch address.

   predict = last outcome

   for (i = 0; i < 10; i++) { ... }

   iterations:  T T T T T T T T T N       (N = the final exit)
   prediction:  ? T T T T T T T T T
   correct:     ✗ ✓ ✓ ✓ ✓ ✓ ✓ ✓ ✓ ✗

   Two mispredicts per loop execution: the exit, and then the first
   iteration of the NEXT execution, because the table now says "not taken".

   For a nested loop run many times, that doubling is significant.

Two-bit saturating counter

Require two consecutive surprises before changing the prediction. This is the fundamental unit of nearly every real predictor.

           taken            taken            taken
    ┌──────────────►┌──────────────►┌──────────────►┐
  ┌─┴──┐         ┌──┴─┐         ┌───┴┐         ┌────┴┐
  │ 00 │         │ 01 │         │ 10 │         │ 11  │
  │ SN │◄────────│ WN │◄────────│ WT │◄────────│ ST  │
  └────┘  n-taken└────┘ n-taken └────┘ n-taken └─────┘
  strongly       weakly          weakly         strongly
  NOT taken      NOT taken       TAKEN          TAKEN

  predict TAKEN if the high bit is 1.

  Same loop:  T T T T T T T T T N
  now the single N moves ST → WT, still predicting taken.
  Next execution starts correct. ONE mispredict per loop, not two.

Correlating and tournament predictors

Two-bit counters cannot capture patterns. Real code has branches that depend on other branches:

if (x < 5)  a = 1;      /* branch A */
if (y < 3)  b = 1;      /* branch B */
if (a && b) c = 1;      /* branch C — fully determined by A and B */

A global history register shifts in the outcome of every branch, forming a pattern. Indexing the counter table by (branch address XOR global history) lets the predictor learn "when the last few branches went TNT, this one is taken".

PredictorIdeaTypical accuracy
2-bit bimodalCounter per branch address~85%
gshareIndex by address XOR global history~93%
TournamentRun a local and a global predictor, plus a meta-predictor that learns which to trust per branch~95%
TAGESeveral tables with different history lengths; the longest matching one wins~97–99%
Perceptron / neuralA weighted sum over a long history vector~97–99%

Modern cores use TAGE or perceptron variants with thousands of entries and history lengths in the hundreds. The predictor can be several percent of core area — it is that valuable.

Predicting the target, not just the direction

Knowing a branch is taken is useless without knowing where. Three structures handle this:

StructureHandlesHow
BTB — branch target bufferDirect branchesCache mapping branch address → last target. Available during fetch, before decode.
Indirect predictorBR Xn — virtual calls, switch tables, function pointersHistory-indexed target table; harder, since the target varies
RAS — return address stackRETA hardware stack: BL pushes, RET pops. Near-perfect, because calls and returns nest.
Two ways software breaks the return address stack

The RAS assumes calls and returns are balanced. Break that assumption and you lose a near-100% predictor:

  • Unbalanced call/return. setjmp/longjmp, C++ exception unwinding, coroutine switches and hand-written context switches all return to somewhere the RAS did not predict. The stack stays misaligned for several subsequent returns, so the cost is more than one mispredict.
  • Using BL as a plain jump, or RET as an indirect branch. Some hand-written assembly does this to save an instruction; it corrupts the RAS. ARM added BLR target hints and RETAA partly to keep these paths honest.

Speculation: acting on the guess

Prediction only helps if the processor proceeds on it. Modern cores execute far past unresolved branches, and beyond that, speculate on more than branch direction:

KindGuessRecovery when wrong
Control speculationWhich way a branch goesFlush and refetch
Memory dependence speculationThat a load does not alias an earlier pending storeReplay the load and everything after it
Value predictionThe result of a long-latency operationRare in shipping designs
Prefetch speculationWhich cache lines will be neededNo correctness impact — just wasted bandwidth
 
How a core stays correct while guessing

  ┌──────────┐   ┌────────┐   ┌────────────┐   ┌──────────┐
  │  fetch   │──►│ rename │──►│  execute   │──►│  RETIRE  │
  │(predicted)│  │        │   │(out of     │   │(in order)│
  └──────────┘   └────────┘   │  order)    │   └──────────┘
                              └────────────┘         │
                                                     ▼
                                        architectural state updated
                                        ONLY here, and only in
                                        program order

  The reorder buffer holds results until retirement. A mispredicted or
  faulting instruction is discarded before it ever retires, so the
  ARCHITECTURAL state is always exactly correct.

  But microarchitectural state — caches, TLBs, predictor tables —
  was already changed and is NOT rolled back.

Spectre and Meltdown

That last line is the whole vulnerability class. Speculation is architecturally invisible and microarchitecturally loud.

Spectre variant 1 — bounds check bypass

  if (index < array1_size)          ← attacker trains this to predict TAKEN
          y = array2[array1[index] * 4096];

  1. Attacker calls the function repeatedly with valid indices.
     The predictor learns: this branch is taken.

  2. Attacker calls with index far out of bounds, having evicted
     array1_size from cache so the check is SLOW to resolve.

  3. The core speculates "taken", reads array1[index] — memory it
     must not read — and uses that secret byte to index array2.
     A cache line in array2 is loaded, chosen by the secret value.

  4. The check resolves. Speculation is discarded. y is never written.
     Architecturally, nothing happened.

  5. Attacker times reads across array2. One line is fast.
     Its index reveals the secret byte.

The bounds check was CORRECT. It was simply evaluated too late.

/* the Linux kernel's Spectre-v1 mitigation, and how to read it */
if (index < size) {
        index = array_index_nospec(index, size);
        /* Expands to a data dependency that forces index to 0 when out
         * of bounds — a mask computed WITHOUT a branch, so speculation
         * cannot bypass it. On arm64:
         *     cmp   x1, x2
         *     csel  x1, x1, xzr, lo     ; a mux, not a branch
         *     csdb                      ; speculation barrier
         */
        val = array[index];
}

/* ARM's speculation control instructions */
    CSDB    // consumption of speculative data barrier
    SSBB    // speculative store bypass barrier
    SB      // full speculation barrier (ARMv8.5)

Making your code predictable

Branch prediction is hardware you cannot program directly, but you can write code that is easy or hard for it to predict — and the difference is often several times the execution speed. These are the patterns that matter in practice.

/* The famous case: this loop is ~6x faster when the data is sorted */
for (i = 0; i < n; i++)
        if (data[i] >= 128)
                sum += data[i];

/* Sorted:   the branch goes one way for a long run — near-perfect prediction.
   Unsorted: 50/50 random — the predictor cannot do better than chance,
             and every other iteration costs a full flush.

   The fix that makes sorting irrelevant: remove the branch. */

for (i = 0; i < n; i++) {
        int mask = -(data[i] >= 128);   /* 0 or -1 (all ones) */
        sum += data[i] & mask;          /* a MUX, chapter 05  */
}
/* compiles to CSEL/CSINC on AArch64 — no branch, constant time */
GuidelineWhy
Prefer predictable branches over clever onesA branch taken 99% of the time is nearly free; a 50/50 branch is very expensive
Hoist unpredictable conditions out of hot loopsSplit the loop into two predictable loops rather than one unpredictable one
Use branchless selection for random conditionsCSEL, arithmetic masks, min/max
Prefer switch over long else if chainsA jump table is one indirect branch instead of many conditional ones
Avoid virtual calls in the hottest loopsIndirect branches are the hardest to predict; devirtualise or batch by type
In cryptographic code, never branch on secretsTiming and predictor state leak the secret — see crypto chapter 19
