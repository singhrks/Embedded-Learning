Multi-head attention and positional encoding

Two details that the previous chapter glossed over, and both matter more than their size suggests. One gives attention its expressive power; the other is the only thing telling the model that word order exists.

Multi-head attention

Running attention several times in parallel with different projections sounds redundant and turns out to be essential, for a reason that is easy to state once the single-head version is clear.

   ONE ATTENTION HEAD PRODUCES ONE WEIGHTED AVERAGE. But a
   token often needs several unrelated things at once:

     "The bank by the river was steep."

     · what is the SUBJECT of "was"?          -> "bank"
     · which sense of "bank" is this?         -> "river"
     · what is the previous token?            -> "was"

   THREE DIFFERENT QUESTIONS, THREE DIFFERENT WEIGHTINGS.
   One softmax-weighted average cannot express all of them -
   whatever it emphasises, it de-emphasises the rest.

   THE SOLUTION: RUN h ATTENTION OPERATIONS IN PARALLEL,
   EACH IN A LOWER-DIMENSIONAL SUBSPACE, AND CONCATENATE.

        d_head = d_model / h

     x --> [W_Q1,W_K1,W_V1] --> attention --> head_1 \
       --> [W_Q2,W_K2,W_V2] --> attention --> head_2  \
       --> ...                                         >-- concat --> W_O --> out
       --> [W_Qh,W_Kh,W_Vh] --> attention --> head_h  /

   THE PARAMETER COUNT IS UNCHANGED. Splitting 768
   dimensions into 12 heads of 64 costs exactly the same as
   one head of 768 - you are reshaping, not adding.

   WHAT YOU BUY: h INDEPENDENT ATTENTION PATTERNS instead
   of one. Empirically this matters a great deal; ablating
   to a single head degrades models badly.

   AND THE OUTPUT PROJECTION W_O IS NOT DECORATION. The
   concatenated heads are just stacked subspaces; W_O mixes
   them back into the residual stream and decides how each
   head's contribution is written. Interpretability work
   often factors attention as (W_Q W_K^T) for "where to
   look" and (W_V W_O) for "what to write".

   TYPICAL: d_head is 64 or 128, essentially always. Models
   grow by adding HEADS and LAYERS, not by widening heads.
import torch
import torch.nn as nn
import torch.nn.functional as F

class MultiHeadAttention(nn.Module):
    def __init__(self, d_model, n_head, dropout=0.1):
        super().__init__()
        assert d_model % n_head == 0
        self.n_head = n_head
        self.d_head = d_model // n_head
        # ONE fused projection for Q, K, V (chapter 04:
        # one big matmul beats three small ones)
        self.qkv  = nn.Linear(d_model, 3 * d_model,
                              bias=False)
        self.proj = nn.Linear(d_model, d_model, bias=False)
        self.dropout = dropout

    def forward(self, x, is_causal=True):
        B, T, C = x.shape
        q, k, v = self.qkv(x).chunk(3, dim=-1)

        # THE RESHAPE THAT MAKES HEADS WORK:
        # (B, T, C) -> (B, n_head, T, d_head)
        # The head dimension becomes a BATCH dimension, so
        # one batched matmul runs every head simultaneously.
        def split(t):
            return t.view(B, T, self.n_head,
                          self.d_head).transpose(1, 2)
        q, k, v = split(q), split(k), split(v)

        y = F.scaled_dot_product_attention(
                q, k, v, is_causal=is_causal,
                dropout_p=self.dropout if self.training
                          else 0.0)

        # (B, n_head, T, d_head) -> (B, T, C)
        y = y.transpose(1, 2).contiguous().view(B, T, C)
        return self.proj(y)

# THE .contiguous() IS NOT OPTIONAL. transpose() returns a
# VIEW with permuted strides; view() requires contiguous
# memory. Omitting it raises an error - and if you use
# reshape() instead, it silently copies, which works but
# hides the cost.

# --- GROUPED-QUERY ATTENTION (chapter 19) ---
class GQA(nn.Module):
    """n_head query heads, n_kv_head key/value heads.
       n_kv_head = n_head    -> standard MHA
       n_kv_head = 1         -> multi-query
       in between            -> GQA, what Llama uses"""
    def __init__(self, d_model, n_head, n_kv_head):
        super().__init__()
        self.n_head, self.n_kv_head = n_head, n_kv_head
        self.d_head = d_model // n_head
        self.q = nn.Linear(d_model, n_head * self.d_head,
                           bias=False)
        self.k = nn.Linear(d_model, n_kv_head * self.d_head,
                           bias=False)
        self.v = nn.Linear(d_model, n_kv_head * self.d_head,
                           bias=False)
        self.proj = nn.Linear(d_model, d_model, bias=False)

    def forward(self, x):
        B, T, C = x.shape
        q = self.q(x).view(B, T, self.n_head,
                           self.d_head).transpose(1, 2)
        k = self.k(x).view(B, T, self.n_kv_head,
                           self.d_head).transpose(1, 2)
        v = self.v(x).view(B, T, self.n_kv_head,
                           self.d_head).transpose(1, 2)

        # REPEAT the KV heads to match the query heads.
        # No extra parameters, and the CACHE only stores
        # n_kv_head copies - which is the entire point.
        rep = self.n_head // self.n_kv_head
        k = k.repeat_interleave(rep, dim=1)
        v = v.repeat_interleave(rep, dim=1)

        y = F.scaled_dot_product_attention(q, k, v,
                                           is_causal=True)
        y = y.transpose(1, 2).contiguous().view(B, T, C)
        return self.proj(y)

Why position must be added

Attention is blind to order, which means a transformer without positional information cannot distinguish a sentence from its own shuffling. How that information is injected has become a design decision with real consequences.

/* ATTENTION IS PERMUTATION-EQUIVARIANT.

   Shuffle the input tokens and the outputs shuffle
   identically - the VALUES do not change. Look at the
   equation (chapter 19): it is a set of dot products and a
   weighted sum. NOTHING IN IT REFERS TO POSITION.

   So without positional information:

        "dog bites man"  ==  "man bites dog"

   The model literally cannot distinguish them. POSITION
   MUST BE INJECTED EXPLICITLY, and how you do it turns out
   to determine how far the model can extrapolate beyond its
   training length.                                       */

/* --- 1. LEARNED ABSOLUTE (GPT-2, BERT) --- */
    self.wpe = nn.Embedding(max_len, d_model)
    x = self.wte(idx) + self.wpe(positions)

    A lookup table, one vector per position, learned like
    any other parameter.
      + simple, and it works
      - HARD LIMIT at max_len. Position 1025 has no
        embedding. Cannot extrapolate at all.
      - positions are learned independently, so nothing
        forces position 5 and position 6 to be related

/* --- 2. SINUSOIDAL (the 2017 paper) --- */
    PE(pos, 2i)   = sin(pos / 10000^(2i/d))
    PE(pos, 2i+1) = cos(pos / 10000^(2i/d))

    Different dimensions oscillate at different frequencies -
    a binary-counter-like encoding in continuous form. The
    intended property: PE(pos+k) is a LINEAR FUNCTION of
    PE(pos), so relative offsets are learnable.
      + no parameters, defined for any position
      - extrapolation is poor in practice despite the theory

/* --- 3. ROPE: ROTARY POSITION EMBEDDING. THE STANDARD. --- */

    THE IDEA: do not ADD anything to the embeddings. ROTATE
    the query and key vectors by an angle proportional to
    their position.

      Treat each pair of dimensions as a 2-D vector and
      rotate it by (position * theta_i), with theta_i
      decreasing across dimension pairs.

    WHY IT IS ELEGANT: after rotation, the dot product
    between a query at position m and a key at position n
    depends only on (m - n).

        q_m · k_n  =  f(q, k, m - n)

    RELATIVE POSITION FALLS OUT OF THE ARITHMETIC. No
    relative-position bias table, no extra parameters, and
    it applies to Q and K only - the values and the residual
    stream are untouched.

    · used by Llama, Mistral, Gemma, Qwen, and essentially
      every recent open model
    · extrapolates better than the alternatives
    · and CONTEXT EXTENSION IS POSSIBLE AFTER TRAINING by
      scaling the frequencies - "NTK-aware" scaling, YaRN,
      position interpolation. This is how an 8k model
      becomes a 128k model with modest fine-tuning, and it
      is the main reason context lengths grew so fast.

def rope(x, positions, base=10000.0):
    """x: (B, n_head, T, d_head), d_head even."""
    B, H, T, D = x.shape
    half = D // 2
    freqs = 1.0 / (base ** (torch.arange(0, half,
                    device=x.device).float() / half))
    angles = positions[:, None].float() * freqs[None, :]
    cos, sin = angles.cos(), angles.sin()      # (T, half)

    x1, x2 = x[..., :half], x[..., half:]
    return torch.cat([x1 * cos - x2 * sin,
                      x1 * sin + x2 * cos], dim=-1)

# APPLY TO Q AND K ONLY, NOT V:
#     q = rope(q, pos);  k = rope(k, pos)

/* --- 4. ALiBi --- */
    Add a linear penalty to the attention scores based on
    distance, with a different slope per head:
        score = q·k - m_head * |i - j|
    No embeddings at all. Extrapolates well; nearer tokens
    are simply favoured. Used by BLOOM and MPT.

/* --- 5. NoPE --- */
    And a genuinely surprising result: DECODER-ONLY models
    with NO POSITIONAL ENCODING AT ALL still learn position,
    because the causal mask itself is positional information
    - position i can see exactly i+1 tokens, and that count
    is recoverable. Performance is competitive at small
    scale. A good reminder that architectural "necessities"
    deserve testing.                                       */
What to use 
new model, any size        -> RoPE
need long extrapolation    -> RoPE with frequency
                              scaling, or ALiBi
reproducing GPT-2/BERT     -> learned absolute
encoder for fixed-length
  classification           -> learned absolute is fine
tiny embedded model,
  short sequences          -> learned absolute; it is one
                              small table and the cheapest
                              to run

What the heads do

Individual heads can be inspected, and some of them turn out to do recognisable, nameable jobs. This is among the more concrete results in interpretability.

/* HEADS SPECIALISE, without being told to. The patterns
   from chapter 19, seen through the multi-head lens:

     · POSITIONAL heads   attend to the previous token, or
                          n back. Early layers.
     · SYNTACTIC heads    subject-verb, adjective-noun,
                          matching brackets
     · COREFERENCE heads  pronoun to antecedent
     · INDUCTION heads    copy a pattern seen earlier in
                          context. Requires TWO heads
                          working together across layers -
                          one to record "what followed this
                          token last time", one to use it.
                          Their formation coincides with
                          in-context learning appearing.
     · SINK heads         dump attention on token 0

/* --- HEAD REDUNDANCY --- */
    A well-known result: MANY HEADS CAN BE PRUNED with
    little loss. Some layers work fine with a single head.
    Others have one critical head whose removal breaks a
    capability entirely.

    THIS IS PRACTICALLY USEFUL: head pruning is a real
    compression technique (chapter 26), and it is structured
    - removing a whole head removes whole rows and columns,
    which actually speeds up the matmul, unlike unstructured
    sparsity (chapter 03).

How it shows up

SymptomCause
Word order has no effect on outputNo positional encoding
Crash at sequence length above the trained maximumLearned absolute positions — no embedding exists
Quality collapses beyond the training lengthPoor extrapolation — use RoPE with scaling or ALiBi
view size is not compatibleMissing .contiguous() after transpose
Heads produce identical patternsInitialisation or a reshape bug collapsing the head dimension
Output is scrambled across headsWrong reshape order — check (B, T, H, D) then transpose
