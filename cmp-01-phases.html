What a compiler is and its phases

Between your source file and a running instruction there are about a dozen distinct transformations. Knowing which one is responsible for a given behaviour is what lets you answer "why did it do that?" instead of guessing.

The pipeline

   hello.c
      |
      v
   PREPROCESSOR              #include, #define, #if
      |                      -> a single translation unit
      v  hello.i
   LEXER                     characters -> TOKENS
      |                      (chapter 02)
      v
   PARSER                    tokens -> a PARSE TREE
      |                      (chapter 03)
      v
   SEMANTIC ANALYSIS         types, scopes, name resolution
      |                      -> an annotated AST (chapter 04)
      v
   IR GENERATION             AST -> an INTERMEDIATE
      |                      REPRESENTATION (chapter 05)
      v
   ===== THE MIDDLE END: machine-independent =====
      |
   OPTIMISATION PASSES       constant folding, dead code,
      |                      inlining, loop transforms
      |                      (chapters 06-07)
      v
   ===== THE BACK END: machine-specific =====
      |
   INSTRUCTION SELECTION     IR -> target instructions
      |                      (chapter 08)
      v
   SCHEDULING                reorder for the pipeline
      |
      v
   REGISTER ALLOCATION       virtual -> physical registers
      |                      (chapter 09)
      v
   ASSEMBLY EMISSION
      |
      v  hello.s
   ASSEMBLER                 text -> an OBJECT FILE
      |                      (chapter 11)
      v  hello.o
   LINKER                    objects + libraries -> an
      |                      executable (chapter 12)
      v  a.out
   LOADER                    map it, relocate, resolve
                             (chapter 13)

   THE SPLIT THAT MATTERS: front end (language-specific),
   middle end (neither), back end (target-specific). It is why
   GCC supports many languages on many targets with N+M
   components rather than N*M.

Watching each phase

# --- Preprocessor only ---
    gcc -E hello.c -o hello.i
    ; expands includes and macros. When a macro misbehaves,
    ; look here FIRST - the answer is always visible.
    gcc -E -P hello.c | less     ; -P drops line markers

# --- Tokens ---
    gcc -E -dD hello.c           ; with all macro definitions
    clang -cc1 -dump-tokens hello.c

# --- The parse tree / AST ---
    clang -Xclang -ast-dump -fsyntax-only hello.c
    gcc -fdump-tree-original-raw hello.c

# --- The IR ---
    clang -S -emit-llvm hello.c -o hello.ll   ; LLVM IR
    gcc -fdump-tree-all hello.c               ; GIMPLE, every
                                              ; pass
    gcc -fdump-rtl-all hello.c                ; RTL

# --- Assembly ---
    gcc -S hello.c -o hello.s
    gcc -S -O2 -fverbose-asm hello.c          ; with comments

# --- Object file ---
    gcc -c hello.c -o hello.o
    objdump -d hello.o
    readelf -a hello.o

# --- The whole thing, with every step shown ---
    gcc -v hello.c
    ; prints the actual cc1, as and ld command lines - which
    ; is how you find out what flags your build system is
    ; really passing.

/* WHY THE SPLIT PAYS: LLVM has one optimiser. Rust, Swift,
   Julia, Zig, clang and a dozen others all feed it LLVM IR
   and inherit every optimisation anyone writes.

   AND WHY IT LEAKS: the middle end optimises the IR under the
   assumption that the source program has NO UNDEFINED
   BEHAVIOUR. That assumption is what makes aggressive
   optimisation legal, and it is why UB has effects that look
   insane at the source level (chapter 15).                */

GCC and LLVM

/* You will use both. The differences that matter in
   practice:                                                */

   GCC
     · the default for the Linux kernel and most embedded
       Linux toolchains
     · GIMPLE (tree-based) then RTL (low-level) IR
     · a monolithic program
     · often marginally better code on some targets,
       especially with -O2 on ARM
     · inline assembly and __attribute__ syntax are the de
       facto standard that Clang copies

   LLVM/CLANG
     · a LIBRARY, so tools are built on it: clangd, clang-tidy,
       clang-format, sanitizers, static analysers
     · LLVM IR: typed, SSA, human-readable, stable enough to
       write tools against
     · far better diagnostics - error messages that point at
       the right thing
     · the sanitizers (ASan, UBSan, TSan, MSan) originate here
     · what Rust, Swift and Zig use

/* IN EMBEDDED WORK you will typically compile the kernel and
   the BSP with GCC (because that is what the vendor
   supports), and use Clang's tooling - clangd for navigation,
   clang-tidy and the sanitizers for analysis - alongside it.
   The Linux kernel now builds with either.

   AND FOR LEARNING: read Clang's LLVM IR output. It is far
   more legible than GIMPLE and the optimisation passes are
   individually observable.                                */

-O2The standard. Inlining, vectorisation, most passesAlmost everything
-O3-O2 plus aggressive inlining and vectorisationMeasured hot paths; can be slower from cache pressure

/* WHY -O0 IS NOT "SAFE":

   · the kernel REQUIRES optimisation. Inline assembly
     constraints, __builtin_constant_p, and many macros only
     work when constants fold. Linux does not build at -O0.
   · unoptimised code is 3-10x slower and much larger, which
     on an embedded target may not fit or may miss deadlines.
   · a BUG THAT ONLY APPEARS AT -O2 is usually undefined
     behaviour in your code (chapter 15), not a compiler bug.
     Turning optimisation off hides it; it does not fix it.

/* THE RIGHT DEBUG BUILD is -Og -g, or -O2 -g with the
   understanding that variables may be optimised out. Modern
   DWARF and gdb handle -O2 far better than they used to
   (chapter 14).                                            */

Flags worth knowing

# --- Warnings: turn them on, all of them ---
    -Wall -Wextra              ; the baseline. Not optional.
    -Werror                    ; in CI
    -Wshadow                   ; a shadowed variable is
                               ; almost always a bug
    -Wconversion               ; implicit narrowing
    -Wsign-conversion
    -Wcast-align               ; important on ARM
    -Wpointer-arith
    -Wvla                      ; variable-length arrays
    -Wframe-larger-than=1024   ; stack usage (Linux ch. 02)
    -Wstack-usage=1024

# --- Standards ---
    -std=c11 / -std=gnu11 / -std=c17
    -pedantic                  ; reject GNU extensions

# --- Code generation ---
    -fno-strict-aliasing       ; the kernel uses this; see
                               ; chapter 15
    -fno-common
    -fstack-protector-strong
    -fno-omit-frame-pointer    ; makes profiling and
                               ; backtraces work

                               ; (chapter 12)

    -march=armv8-a+crc+crypto
    -mtune=cortex-a53

    -ffreestanding -nostdlib -nostdinc
    -fno-builtin

Translation units and the build

   foo.c  bar.c  baz.c
     |      |      |
     |  each compiled SEPARATELY, knowing nothing about the
     |  others - this is the C model
     v      v      v
   foo.o  bar.o  baz.o
     \      |      /
      \     |     /
       LINKER  +  libc.a, libm.so
          |
          v
       a.out

  CONSEQUENCES OF SEPARATE COMPILATION:

    · the compiler cannot inline across files, or prove
      anything about a function it has not seen
      -> which is why `static` matters: a static function has
         no external callers, so the compiler may inline it,
         specialise it, or delete it entirely
      -> and why LTO exists (chapter 12): defer optimisation
         to link time, when everything IS visible

    · a declaration mismatch between files is NOT caught by
      the compiler - only by the linker, and only sometimes
      -> which is what header files are for, and why a
         function should be declared in exactly one header
         that both the definition and the callers include

    · build times scale with the number of translation units
      times the size of the headers each pulls in
      -> which is why include hygiene matters on large
         projects, and why C++ modules were invented
