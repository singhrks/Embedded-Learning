Project: a firmware TPM as a trusted application

A TPM is a small state machine with keys, counters and measurement registers, spoken to over a byte-stream protocol. That description does not require a chip — it requires isolation, and the secure world provides it. Microsoft's fTPM does exactly this, ships on real products, and is the most instructive TA in existence.

Why a TPM in software is a reasonable idea

Discrete TPM (dTPM)Firmware TPM (fTPM)
Where it runsA separate chip on the SPI or LPC busA trusted application in the secure world
Bill of materialsA part, a footprint, routingNothing
Bus interceptionPossible — the SPI bus is on the board and can be probedNot applicable; there is no bus
Physical attack on the partHard — the chip is hardened, often certifiedAs hard as attacking the SoC, which is usually less hard
Shares fate with the CPUNoYes — an SoC compromise is a TPM compromise
CertificationCommon Criteria, FIPSPossible but harder
UpdatableRarelyYes, with the firmware
PerformanceSlow bus, slow partFast — it is the application processor

The honest summary: an fTPM removes bus-probing attacks and costs nothing, at the price of sharing its fate with the SoC. For a phone or a laptop where the SoC is already the root of trust, that trade is clearly right — which is why Windows on ARM, most Android devices and AMD's fTPM all take it. For a system where the threat model includes an attacker with unlimited physical access and the CPU is not hardened, a discrete part still wins.

What a TPM actually is

A firmware TPM implements in software, inside the secure world, what is normally a discrete chip on the board. Understanding what that buys and what it gives up is the point of the project.

   Strip away the specification and a TPM 2.0 is four things:

   1. PCRs - Platform Configuration Registers
        24 registers, each holding a hash. You cannot WRITE
        them; you can only EXTEND them:

            PCR[i] = SHA256( PCR[i] || new_measurement )

        One-way and order-dependent. Reset to zero only on
        reboot. So the value of PCR[4] after boot is a
        fingerprint of exactly which bootloader ran, in which
        order - and no software can fake a value it did not
        actually reach.

   2. A KEY HIERARCHY
        Primary keys derived from persistent SEEDS:
          Endorsement Seed  -> the device's identity, set at
                               manufacture, never changes
          Storage Seed      -> the owner's key hierarchy
          Platform Seed     -> firmware's own hierarchy
        Child keys are created under a parent and stored
        OUTSIDE the TPM as encrypted blobs, loaded back on
        demand. That is how a TPM with 64 KB of storage
        manages thousands of keys.

   3. NV STORAGE
        A few kilobytes of indexed, attribute-controlled
        space. Certificates, counters, policy data.
        Monotonic counters live here.

   4. POLICY
        A session-based language for "this key may be used
        only if...". Conditions include PCR values, a
        password, a signature, a time, or a counter.
        This is what makes SEALING work.

   SEALING, the flagship use, in one line:

     encrypt a secret so that it can only be decrypted when
     PCR[0..7] have exactly the values they had at seal time

   which means: "decrypt only if the machine booted the same
   software it did when I sealed this". That is BitLocker,
   and it is the reason PCRs exist.

The fTPM stack

The arrangement has more layers than the previous project, spanning a reference implementation, the trusted OS and the normal-world stack. Fixing the picture first makes the rest navigable.

   NORMAL WORLD                        SECURE WORLD

   tpm2-tools, systemd-cryptenroll,
   Windows, Clevis, ...

                                |  secure storage (ch. 15)  |
                                |  and its RNG onto         |
                                |  TEE_GenerateRandom       |
                                +---------------------------+

   THE KEY INSIGHT: the TA's interface is ONE command that
   takes an opaque byte string and returns another. All the
   complexity is inside, and the TEE boundary carries a
   protocol that was already designed to cross an untrusted
   bus.

   That is why the fTPM is such a good TA: the TPM 2.0 command
   protocol was designed on the assumption that the transport
   is hostile. Every command is self-contained, sessions are
   authenticated, and nothing depends on the caller being
   trustworthy. A TEE is exactly that transport.
The design lesson worth taking away

A good TA interface is narrow and self-authenticating. The fTPM has one command and the payload carries its own authorisation. Compare a TA with forty commands, each with pointer parameters and implicit state — every one is an attack surface needing its own validation (chapter 20). If you can express your service as a protocol rather than an API, do it.

The TA interface, in full

The TPM has a standardised command interface, and the trusted application's job is to carry those commands across the world boundary without interpreting them.

/* fTPM/ftpm_ta.c - the entire command surface.             */

#define TA_FTPM_SUBMIT_COMMAND   (0)
#define TA_FTPM_EMULATE_PPI      (1)   /* physical presence   */

TEE_Result TA_InvokeCommandEntryPoint(void *sess_ctx __unused,
                                      uint32_t cmd_id,
                                      uint32_t param_types,
                                      TEE_Param params[4])
{
        switch (cmd_id) {
        case TA_FTPM_SUBMIT_COMMAND:
                return ftpm_submit_command(param_types, params);
        case TA_FTPM_EMULATE_PPI:
                return ftpm_emulate_ppi(param_types, params);
        default:
                return TEE_ERROR_BAD_PARAMETERS;
        }
}

static TEE_Result ftpm_submit_command(uint32_t param_types,
                                      TEE_Param params[4])
{
        uint32_t exp_param_types =
                TEE_PARAM_TYPES(TEE_PARAM_TYPE_MEMREF_INPUT,
                                TEE_PARAM_TYPE_MEMREF_INOUT,
                                TEE_PARAM_TYPE_NONE,
                                TEE_PARAM_TYPE_NONE);
        uint8_t  *cmd_buf;
        uint32_t  cmd_len;
        uint8_t  *resp_buf;
        uint32_t  resp_len;

        if (param_types != exp_param_types)
                return TEE_ERROR_BAD_PARAMETERS;

        cmd_len  = params[0].memref.size;
        cmd_buf  = params[0].memref.buffer;
        resp_len = params[1].memref.size;
        resp_buf = params[1].memref.buffer;

        if (cmd_len > MAX_COMMAND_SIZE ||
            resp_len < MAX_RESPONSE_SIZE)
                return TEE_ERROR_BAD_PARAMETERS;

        /* Copy the command into TA memory - one fetch
           (chapter 20). The reference implementation then
           works entirely on its own buffers.               */
        memcpy(pCommandBuffer, cmd_buf, cmd_len);

        /* THE WHOLE TPM. One call into the reference code. */
        _plat__RunCommand(cmd_len, pCommandBuffer,
                          &respLen, &respBuf);

        if (respLen > resp_len)
                return TEE_ERROR_SHORT_BUFFER;

        memcpy(resp_buf, respBuf, respLen);
        params[1].memref.size = respLen;
        return TEE_SUCCESS;
}

/* That is it. One entry point, one memcpy in, one call, one
   memcpy out. Forty thousand lines of TPM behind a twenty-line
   function.                                                */

The platform layer: where the porting work is

The reference implementation expects a set of platform services — storage, entropy, time — that must be mapped onto what the secure world actually provides.

/* The reference implementation calls out to a platform layer
   for everything the specification leaves to the
   implementer. Porting a TPM to a new environment IS writing
   this layer, and OP-TEE makes it short.                   */

/* --- NV STORAGE: the TPM's persistent state ------------- */
/* platform/NVMem.c                                         */

int _plat__NvCommit(void)
{
        /* The TPM's entire NV image is one blob, written back
           to OP-TEE secure storage (chapter 15).           */
        return NvFileCommit();   /* -> TEE_WriteObjectData   */
}

void _plat__NvMemoryRead(unsigned int startOffset,
                         unsigned int size, void *data)
{
        memcpy(data, &s_NV[startOffset], size);
}

/* The whole NV area is held in RAM and flushed on commit.
   Consequences:
     - a power cut between a state change and the commit loses
       that change. The TPM specification anticipates this and
       defines which operations must be committed
       synchronously.
     - the NV area is a few tens of kilobytes, so this is
       affordable.
     - REE FS gives no rollback protection. An fTPM that
       matters should be built with CFG_RPMB_FS=y, or its NV
       counters can be rewound (chapter 17). THIS IS THE
       SINGLE MOST IMPORTANT DEPLOYMENT DECISION HERE.     */

/* --- ENTROPY -------------------------------------------- */
int32_t _plat__GetEntropy(unsigned char *entropy, uint32_t amount)
{
        TEE_GenerateRandom(entropy, amount);
        return (int32_t)amount;
        /* Backed by the platform's TRNG where one exists.
           On QEMU it is not a real TRNG, which is one more
           reason the QEMU build is for development only. */
}

/* --- TIME ----------------------------------------------- */
uint64_t _plat__TimerRead(void)
{
        TEE_Time t;
        TEE_GetSystemTime(&t);      /* MONOTONIC, secure -
                                       not TEE_GetREETime.
                                       The TPM's clock must
                                       not be attacker-
                                       controlled (ch. 17). */
        return (uint64_t)t.seconds * 1000 + t.millis;
}

/* --- UNIQUE VALUES: where the seeds come from ------------ */
/* The Endorsement Primary Seed is the device's identity. It
   must be:
     - different on every device
     - stable for the life of the device
     - never derivable from outside the secure world

   Options, best first:
     1. TEE_GetHUKDerivedKey with a fixed label - derived from
        fuses, per-device, needs no storage (chapter 16).
     2. generated once with TEE_GenerateRandom and persisted
        to RPMB.
     3. provisioned at manufacture from an HSM, along with an
        EK certificate signed by your CA.

   Option 3 is what a product does, because an Endorsement Key
   is only useful for attestation if a relying party can chain
   it to a manufacturer they trust.

   The QEMU/development build uses a FIXED seed. Every
   "device" then has the same EK, which is fine for testing
   and completely useless for attestation.               */

/* --- PHYSICAL PRESENCE ---------------------------------- */
/* On a PC this is a person pressing a key during POST. In a
   TA there is nobody to ask, so the platform layer decides -
   usually by asserting presence for operations the platform
   owner is allowed to perform, and refusing otherwise.
   Getting this wrong lets the normal world clear the TPM.  */

Size is the first thing that will bite you

The fTPM is by far the largest TA most people will deploy: a 400 KB binary with a 2 MB heap. On QEMU with 48 MB of secure DRAM that is comfortable. On a real SoC with 4 MB of secure SRAM and a pager (chapter 5) it is a genuine engineering problem, and it is why the paged build exists. Budget the memory before you promise the feature.

A minimal TPM, if you want to understand rather than integrate

Before the full implementation, a minimal version that answers one command proves the plumbing works — which is the right place to stop and verify.

/* Building the real fTPM teaches you integration. Writing a
   tiny one teaches you what a TPM IS. This implements four
   commands in about 200 lines, and it is a genuinely useful
   exercise before chapter 23.                             */

#define TPM_ST_NO_SESSIONS   0x8001
#define TPM_RC_SUCCESS       0x0000
#define TPM_RC_COMMAND_CODE  0x0143
#define TPM_CC_PCR_Extend    0x00000182
#define TPM_CC_PCR_Read      0x0000017E
#define TPM_CC_GetRandom     0x0000017B
#define TPM_CC_Startup       0x00000144

#define NUM_PCR   24
#define PCR_LEN   32

static uint8_t g_pcr[NUM_PCR][PCR_LEN];   /* zeroed at reset */

/* Big-endian helpers - TPM structures are all big-endian. */
static uint32_t be32(const uint8_t *p)
{
        return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
               ((uint32_t)p[2] << 8)  |  (uint32_t)p[3];
}
static void put_be32(uint8_t *p, uint32_t v)
{
        p[0] = v >> 24; p[1] = v >> 16; p[2] = v >> 8; p[3] = v;
}
static void put_be16(uint8_t *p, uint16_t v)
{
        p[0] = v >> 8; p[1] = v;
}

/* PCR_Extend: PCR[i] = SHA256(PCR[i] || digest)           */
static TEE_Result pcr_extend(uint32_t idx, const uint8_t *digest)
{
        TEE_OperationHandle op = TEE_HANDLE_NULL;
        uint8_t  out[PCR_LEN];
        uint32_t outlen = sizeof out;
        TEE_Result res;

        if (idx >= NUM_PCR)
                return TEE_ERROR_BAD_PARAMETERS;

        res = TEE_AllocateOperation(&op, TEE_ALG_SHA256,
                                    TEE_MODE_DIGEST, 0);
        if (res != TEE_SUCCESS)
                return res;

        TEE_DigestUpdate(op, g_pcr[idx], PCR_LEN);
        res = TEE_DigestDoFinal(op, digest, PCR_LEN,
                                out, &outlen);
        if (res == TEE_SUCCESS)
                TEE_MemMove(g_pcr[idx], out, PCR_LEN);

        TEE_FreeOperation(op);
        return res;
}

/* The command dispatcher. Every TPM command has this header:
     uint16 tag | uint32 commandSize | uint32 commandCode
   and every response has:
     uint16 tag | uint32 responseSize | uint32 responseCode  */

static uint32_t tpm_dispatch(const uint8_t *cmd, uint32_t cmdlen,
                             uint8_t *rsp, uint32_t *rsplen)
{
        uint32_t cc, size;
        uint32_t rc = TPM_RC_SUCCESS;
        uint32_t body = 0;      /* bytes of response payload  */

        if (cmdlen < 10)
                return TPM_RC_COMMAND_CODE;

        size = be32(cmd + 2);
        cc   = be32(cmd + 6);

        /* Never trust the caller's length. */
        if (size != cmdlen)
                return TPM_RC_COMMAND_CODE;

        switch (cc) {
        case TPM_CC_Startup:
                break;                          /* no payload  */

        case TPM_CC_GetRandom: {
                uint16_t want;
                if (cmdlen < 12) { rc = TPM_RC_COMMAND_CODE; break; }
                want = (cmd[10] << 8) | cmd[11];
                if (want > 64) want = 64;
                put_be16(rsp + 10, want);
                TEE_GenerateRandom(rsp + 12, want);
                body = 2 + want;
                break;
        }

        case TPM_CC_PCR_Extend: {
                uint32_t idx;
                if (cmdlen < 10 + 4 + PCR_LEN) {
                        rc = TPM_RC_COMMAND_CODE; break;
                }
                idx = be32(cmd + 10);
                if (pcr_extend(idx, cmd + 14) != TEE_SUCCESS)
                        rc = TPM_RC_COMMAND_CODE;
                break;
        }

        case TPM_CC_PCR_Read: {
                uint32_t idx;
                if (cmdlen < 14) { rc = TPM_RC_COMMAND_CODE; break; }
                idx = be32(cmd + 10);
                if (idx >= NUM_PCR) {
                        rc = TPM_RC_COMMAND_CODE; break;
                }
                TEE_MemMove(rsp + 10, g_pcr[idx], PCR_LEN);
                body = PCR_LEN;
                break;
        }

        default:
                rc = TPM_RC_COMMAND_CODE;
        }

        put_be16(rsp, TPM_ST_NO_SESSIONS);
        put_be32(rsp + 2, 10 + body);
        put_be32(rsp + 6, rc);
        *rsplen = 10 + body;
        return rc;
}

/* Wire it to the single SUBMIT_COMMAND entry point exactly as
   the real fTPM does, and you have a TPM you can drive from
   Linux. It will not pass the TCG test suite, but it will
   extend and read PCRs, which is enough to understand what
   chapter 23 is doing.                                    */
