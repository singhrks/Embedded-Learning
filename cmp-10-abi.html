Calling conventions and the ABI

The contract that lets separately compiled code work together: where arguments go, who saves what, how the stack is laid out. Violate it and you get corruption that looks like a hardware fault — and every language's foreign function interface is built on it.

What an ABI covers

   An API is a source-level contract: function names, types,
   semantics. An ABI is a BINARY contract:

     · sizes and alignments of every type
     · struct layout and padding rules
     · where arguments are passed, and in what order
     · where return values come back
     · which registers are preserved across a call
     · stack frame layout, alignment, and direction
     · the stack unwinding format, for exceptions
     · name mangling (C++)
     · object file format, relocations, symbol visibility
     · dynamic linking: PLT, GOT, TLS model
     · system call numbering and convention

   THE RELEVANT DOCUMENT for ARM 64-bit is:
     "Procedure Call Standard for the Arm 64-bit Architecture"
     (AAPCS64), plus the ELF ABI supplement.

   TWO OBJECT FILES AGREE ON AN ABI OR THEY DO NOT WORK. This
   is why you cannot link an armhf library into an aarch64
   binary, why C++ objects from different compilers may not
   link, and why the kernel's syscall interface is frozen
   forever (Linux chapter 02).

/* THE v8-v15 RULE IS A REAL TRAP: only the LOW 64 BITS are
   callee-saved. A function that uses the full 128-bit v8 and
   restores only the low half has corrupted its caller's
   upper half. Hand-written SIMD assembly must save the whole
   register if it uses the whole register.               */

/* AND x18: on Linux it is usually free, but on Windows on
   ARM and on Darwin it holds the TEB/TLS pointer, and with
   -fsanitize=shadow-call-stack it holds the shadow stack
   pointer. Compile with -ffixed-x18 if you are writing code
   that must be portable across those. Never allocate it in
   hand-written assembly.                                 */

Argument passing

/* THE ALGORITHM, simplified but accurate for the common
   cases:

   NGRN = next general register number (starts at 0)
   NSRN = next SIMD register number (starts at 0)
   NSAA = next stacked argument address

   For each argument, in order:
     · integer or pointer, fits in 8 bytes
           -> x[NGRN++], if NGRN < 8; else stack
     · 16-byte integer (__int128)
           -> an even-numbered register PAIR
     · float, double, or a short vector
           -> v[NSRN++], if NSRN < 8; else stack
     · HFA/HVA - a struct of 1-4 identical float/vector
       members
           -> consecutive v registers, one per member
     · other struct, <= 16 bytes
           -> passed in 1 or 2 general registers, by value
     · other struct, > 16 bytes
           -> a COPY is made, and its ADDRESS is passed in a
              register. The callee may modify the copy.
     · variadic arguments after the named ones
           -> on the stack, on most platforms (Darwin differs)
*/

/* WORKED EXAMPLE: */
        struct Small { int a, b; };            /* 8 bytes  */
        struct Big   { int a[10]; };           /* 40 bytes */
        struct Vec3  { float x, y, z; };       /* an HFA    */

        void f(int a, double b, struct Small c,
               struct Big d, struct Vec3 e, int f);

/*      a -> w0
        b -> d0
        c -> x1              (8 bytes, packed into one reg)
        d -> x2 = &copy_of_d (too large - by reference)
        e -> s1, s2, s3      (HFA - one register per member)
        f -> w3                                            */

/* THE HFA RULE IS WHY a 3-float vector type is efficient on
   ARM and a 3-int one is not: floats get three registers,
   ints get packed and spilled. It is also why graphics and
   DSP code on ARM tends to use float structs.           */

/* VARIADIC FUNCTIONS: the named arguments follow the normal
   rules, everything after goes on the stack in a defined
   layout, and va_arg walks it. THIS IS WHY:
     · printf("%d", someFloat) is UB - the float was passed in
       a v register or promoted to double on the stack, and
       %d reads an integer slot
     · a function must have a prototype in scope: without it,
       the compiler cannot know whether an argument is named
       or variadic                                        */

Return values

        int f(void);                    -> w0
        long f(void);                   -> x0
        void *f(void);                  -> x0
        float f(void);                  -> s0
        double f(void);                 -> d0
        __int128 f(void);               -> x0, x1
        struct Small f(void);           -> x0 (and x1 if 9-16
                                           bytes)
        struct Vec3 f(void);            -> s0, s1, s2 (HFA)

        struct Big f(void);
/* THE CALLER allocates space, passes its address in x8, and
   the callee writes the result there. So:            */

        struct Big result = f();
   compiles to:
        add   x8, sp, #16          ; where to put it
        bl    f
        ; f writes 40 bytes at [x8]

/* WHICH IS WHY returning a large struct by value is not as
   expensive as people assume - there is one copy, into a
   destination the caller chose, not two. And why NAMED RETURN
   VALUE OPTIMISATION matters in C++ (C++ chapter 05): if the
   callee builds the result directly at [x8], there is no copy
   at all.                                                */

The stack frame

   higher addresses
   +---------------------------+
   |  caller's frame           |
   +---------------------------+  <- sp on entry, 16-aligned
   |  stacked arguments        |     (arguments 9+)
   +---------------------------+
   |  x29 (saved FP)           |  <- x29 points HERE
   |  x30 (saved LR)           |
   +---------------------------+
   |  other callee-saved regs  |
   |  x19-x28, v8-v15          |
   +---------------------------+
   |  local variables          |
   |  spill slots (chapter 09) |
   +---------------------------+
   |  outgoing arguments for   |
   |  calls this function makes|
   +---------------------------+  <- sp, always 16-aligned
   lower addresses

   THE STANDARD PROLOGUE:
        stp   x29, x30, [sp, #-48]!   ; push FP and LR,
                                      ; allocate 48 bytes
        mov   x29, sp                 ; establish the frame
        stp   x19, x20, [sp, #16]     ; save callee-saved
        str   x21, [sp, #32]

   THE EPILOGUE, exactly reversed:
        ldr   x21, [sp, #32]
        ldp   x19, x20, [sp, #16]
        ldp   x29, x30, [sp], #48     ; pop and deallocate
        ret                           ; = br x30

   THE FRAME POINTER CHAIN: each x29 points at the previous
   x29, forming a linked list. That is how a backtrace works
   without debug information - walk the chain, read the saved
   x30 at each level. -fomit-frame-pointer breaks it, which is
   why profilers and the kernel build with
   -fno-omit-frame-pointer.

   16-BYTE ALIGNMENT IS MANDATORY at every public interface.
   Misalign the stack and you get a fault the first time
   something executes a 128-bit SIMD load/store relative to
   sp - typically deep inside memcpy, far from the cause.

Type layout

/* SIZES AND ALIGNMENTS on AArch64 Linux (LP64): */

        char            1    align 1
        short           2    align 2
        int             4    align 4
        long            8    align 8      <- 4 on Windows!
        long long       8    align 8
        pointer         8    align 8
        float           4    align 4
        double          8    align 8
        long double    16    align 16     <- 8 on some ABIs
        bool            1    align 1

/* THE `long` DIFFERENCE is the classic portability bug:
     LP64  (Linux, macOS):  long = 8
     LLP64 (Windows):       long = 4
   Use int64_t/uint64_t/intptr_t and the question does not
   arise.                                                  */

/* STRUCT LAYOUT: members in declaration order, each at the
   next offset satisfying its alignment; the struct's
   alignment is the maximum of its members'; the size is
   rounded up to that.                                     */

        struct A {              /* 24 bytes */
                char  a;        /* offset 0            */
                                /* 7 bytes PADDING     */
                long  b;        /* offset 8            */
                char  c;        /* offset 16           */
                                /* 7 bytes TAIL PADDING*/
        };

        struct B {              /* 16 bytes - REORDERED */
                long  b;        /* offset 0            */
                char  a;        /* offset 8            */
                char  c;        /* offset 9            */
                                /* 6 bytes padding     */
        };

/* SORTING MEMBERS LARGEST-FIRST is the simplest layout
   optimisation available, and it costs nothing. On an array
   of a million elements, 24 versus 16 bytes is 8 MB and a
   third more cache lines (CA chapter 14).

   SEE THE LAYOUT:
        pahole -C A prog.o
        clang -Xclang -fdump-record-layouts -c prog.c        */

/* PACKING, and why it is dangerous: */
        struct __attribute__((packed)) Wire {
                uint8_t  type;
                uint32_t value;         /* offset 1 -
                                           MISALIGNED */
        };
/* On ARM, an unaligned access to Normal memory works but may
   be slower; to DEVICE memory it FAULTS (ARM chapter 11).
   And taking a POINTER to a packed member and dereferencing
   it is undefined behaviour - the compiler warns with
   -Waddress-of-packed-member for exactly this reason.

   FOR WIRE FORMATS, prefer explicit serialisation:      */
        static void encode(uint8_t *buf, const struct Msg *m)
        {
                buf[0] = m->type;
                put_le32(buf + 1, m->value);
        }
/* Slower to write, correct everywhere, and endian-explicit. */
The C++ additions

C++ layers name mangling (so overloads and templates get distinct symbols), vtable layout, RTTI representation, exception unwinding tables, and the rules for empty base optimisation on top of the C ABI. The Itanium C++ ABI is what GCC and Clang both implement on Linux and ARM, which is why their objects interoperate — and MSVC's differs entirely, which is why they do not on Windows.

Inline assembly and the ABI

/* Writing assembly means obeying the ABI yourself. */

static inline uint64_t read_cntvct(void)
{
        uint64_t val;

        __asm__ volatile("mrs %0, cntvct_el0"
                         : "=r" (val)     /* output */
                         :                /* no inputs */
                         : "memory");     /* clobbers */
        return val;
}

/* THE CONSTRAINT LETTERS you need on AArch64:
     "r"    a general register
     "w"    a SIMD/FP register
     "m"    a memory operand
     "i"    an immediate constant
     "I"    a 12-bit immediate valid for add/sub
     "0"    same as operand 0 (tied)
     "+r"   read AND written
     "=r"   write only

/* THE CLOBBER LIST is where mistakes happen:
     · list EVERY register you modify that is not an output
     · "memory" means "this may read or write memory the
       compiler does not know about" - it prevents the
       compiler from caching loads across the asm and from
       reordering memory operations around it
     · "cc" means the condition flags are modified

/* FORGETTING A CLOBBER produces the worst class of bug: the
   compiler keeps a value in a register you overwrote, and the
   corruption appears somewhere unrelated, only at -O2, only
   sometimes.

/* AND `volatile` on the asm means "do not delete this even if
   its outputs are unused, and do not move it". Required for
   anything with a side effect - an MMIO access, a barrier, a
   system register write.                                 */

/* A COMPLETE EXAMPLE with input, output and clobbers: */
static inline void write_ttbr0(uint64_t val)
{
        __asm__ volatile("msr ttbr0_el1, %0\n"
                         "isb"
                         :
                         : "r" (val)
                         : "memory");
}

/* FOR A WHOLE FUNCTION IN ASSEMBLY, the ABI is entirely
   yours: save x19-x28 if you use them, keep sp 16-aligned,
   return through x30, put the result in x0. Get any of it
   wrong and the failure appears in the CALLER.          */
