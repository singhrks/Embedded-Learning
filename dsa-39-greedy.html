Greedy: when the local choice is the right one

Greedy solutions are three lines long and almost impossible to believe. The work is never the code — it is the argument that taking the best-looking option right now cannot cost you later. This chapter is mostly about how to build that argument, because without it you are guessing.

The pattern

Every greedy algorithm has the same two parts: a rule for choosing, and a reason the rule is safe. Most people write the rule and skip the reason, which is exactly why greedy problems feel like luck.

   THE SHAPE:

     repeat:
        pick the option that looks best BY SOME RULE
        commit to it - never reconsider
     until done

   THE PART THAT MATTERS is why "never reconsider" is safe.
   There is one standard argument and it is worth knowing by
   name:

   THE EXCHANGE ARGUMENT
     Take any optimal solution O. Show that if O disagrees
     with the greedy choice, you can SWAP the greedy choice
     into O without making it worse. Repeat, and O turns
     into the greedy solution while staying optimal.
     Therefore greedy is optimal too.

   IF YOU CANNOT MAKE THAT SWAP, greedy is probably wrong,
   and the answer is DP.

   ---------------------------------------------------------

   GREEDY vs DP, THE ONE-LINE TEST:

     Can an early choice ever be REGRETTED - can a locally
     worse choice lead to a globally better answer?

        NO   -> greedy
        YES  -> DP (you must keep both options alive)

   COIN CHANGE MAKES THIS CONCRETE:
     coins [1, 5, 10, 25], amount 30
        greedy: 25 + 5 = 2 coins        CORRECT
     coins [1, 3, 4], amount 6
        greedy: 4 + 1 + 1 = 3 coins
        optimal: 3 + 3     = 2 coins    GREEDY IS WRONG

   SAME PROBLEM. DIFFERENT COIN SET. The algorithm's
   correctness depends on the INPUT STRUCTURE, not the
   problem statement - which is why "it worked on the
   example" proves nothing.

The four rules that cover most problems

Greedy problems look wildly different and reuse a surprisingly small set of choice rules. Recognising which one applies is most of the work, and each comes with its own exchange argument.

RuleUse whenWhy the swap works
Earliest finishing timeMaximise the count of non-overlapping thingsFinishing earliest leaves the most room for everything after it, so swapping it in never blocks anything
Sort by a ratio or a differenceTwo competing costs per itemCompare two adjacent items: if swapping them improves the total, your sort key is the one that ordering implies
Always take the current extremeA heap is available and the best item now stays bestNothing you do later can make a smaller item preferable
Track the best reachable so farReachability and coverage problemsYou never need to know how you reached a point, only how far you can get

The second rule is the one worth practising, because it is mechanical: when a problem says "order these to minimise something", compare exactly two adjacent items, write down the condition under which swapping them is an improvement, and that condition is your comparator. It turns an intuition problem into algebra.

The three shapes in code

Almost every greedy solution you will write is one of these, and they are short enough to recognise by silhouette.

/* 1. SORT, THEN ONE PASS - by far the most common. */
items.sort(byTheRightKey);
let result = 0, state = initial;
for (const item of items) {
    if (compatible(item, state)) {
        result++;
        state = update(state, item);
    }
}

/* 2. HEAP - when "the best remaining" changes as you go. */
const heap = new MinHeap(items);
while (!heap.isEmpty()) {
    const best = heap.pop();
    /* using best may create new candidates */
    heap.push(derived(best));
}

/* 3. ONE PASS, NO SORT - when the order is already given
      and you only track a running frontier.             */
let reach = 0;
for (let i = 0; i < n; i++) {
    if (i > reach) return false;      /* unreachable     */
    reach = Math.max(reach, i + jump[i]);
}

/* THE THIRD IS THE ONE PEOPLE MISS. It looks too simple to
   be an algorithm, and it is O(n) where the DP solution is
   O(n²).                                               */

How to tell yourself you are wrong, quickly

The cheapest thing you can do in an interview is spend two minutes trying to break your own greedy rule before you spend fifteen implementing it. There is a standard way to do this.

   TRY TO BUILD A COUNTEREXAMPLE IN THIS ORDER:

   1. THE SMALLEST ADVERSARIAL CASE
        two items where the rule's choice is clearly bad.
        Most wrong greedies die at n = 2 or n = 3.

   2. A TIE
        two items the rule rates equally. Does it matter
        which you take? If yes, your rule is incomplete.

   3. AN EXTREME
        zero, one item, all identical, everything negative.

   4. BRUTE FORCE AGAINST IT
        if you have five minutes and a doubt, write the
        exhaustive version and compare on random small
        inputs. This finds the counterexample you could not
        think of, and it is the technique that separates
        "I believe it" from "I checked".

   SAY THIS OUT LOUD IN AN INTERVIEW. "Let me try to break
   this before I write it" is exactly the instinct being
   tested, and finding your own counterexample scores far
   better than having one found for you.

Problems

How it shows up

SymptomCause
Passes the examples, fails hidden testsThe classic greedy failure — the rule is wrong and the examples did not expose it
Correct on small inputs, wrong on largeUsually a tie-break the rule does not specify
Off by one in the count of intervals keptComparing < against <= on touching intervals
Works forwards, fails backwardsThe choice rule is not symmetric; state which direction you scan and why
Sort comparator gives inconsistent resultsA comparator that is not a strict weak ordering — common when sorting by a ratio with equal values
Greedy is right but too slowRe-scanning for the best item each step instead of using a heap
Answer is optimal but the reconstruction is wrongYou tracked the value but not the choices
Cannot justify it when askedNo exchange argument — which in an interview counts as not having solved it

Check yourself

  • State the exchange argument in your own words.
  • Give the one-line test that distinguishes greedy from DP.
  • Show a coin set where greedy change-making fails, and one where it works.
  • Name the four common choice rules and a problem for each.
  • Derive a comparator by considering two adjacent items.
  • Explain why "earliest finishing time" is safe for activity selection.
  • List the four things you try when hunting a counterexample.
  • Explain why the jump-game one-pass is O(n) where the DP is O(n²).
  • Say what you would tell an interviewer before implementing a greedy solution.
