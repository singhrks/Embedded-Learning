HCR_EL2: choosing what traps

One 64-bit register decides, bit by bit, which operations a guest may perform for itself and which must be brought to the hypervisor for adjudication. Every design decision about isolation, fidelity and performance in an ARM hypervisor is ultimately expressed here.

The idea

One register decides most of what a guest may do unsupervised. Reading it as a list of policy decisions rather than a bit field is what makes the rest of this chapter straightforward.

   guest at EL1 executes:  MSR SCTLR_EL1, x0

        HCR_EL2.TVM == 0                 HCR_EL2.TVM == 1
        ----------------                 ----------------
        the write happens.               EXCEPTION to EL2.
        No exception. Full speed.        ESR_EL2.EC = 0x18
                                         (trapped MSR/MRS)
                                         ISS encodes the register,
                                         the direction and Rt.

                                         hypervisor decides what
                                         "writing SCTLR_EL1" should
                                         mean for THIS guest, then
                                         ERETs.

   That is the entire mechanism. HCR_EL2 has about forty such
   bits; each one moves a class of operation from "free" to
   "mediated". Your hypervisor's personality is the bit pattern
   you choose.

What a real hypervisor sets

The difference between what a hypervisor could trap and what it actually traps is the difference between correct and usable. This is a realistic configuration.

/* Close to what KVM/arm64 programs for a normal 64-bit guest.
   Compare arch/arm64/include/asm/kvm_arm.h.                 */

  HCR_GUEST_FLAGS =
        HCR_TSC          /* trap SMC: EL2 sees and filters them   */
      | HCR_TSW          /* trap set/way cache ops - a guest doing
                            "clean by set/way" would operate on
                            the WHOLE cache, including other VMs  */
      | HCR_TWE          /* trap WFE  -> yield the pCPU           */
      | HCR_TWI          /* trap WFI  -> block the vCPU thread    */
      | HCR_VM           /* stage-2 ON                            */
      | HCR_PTW          /* protected table walk                  */
      | HCR_TID3         /* trap ID regs: show a sanitised CPU    */
      | HCR_FMO | HCR_IMO /* physical FIQ/IRQ come to EL2, and
                             virtual FIQ/IRQ become available     */
      | HCR_AMO          /* same for SError                       */
      | HCR_RW           /* AArch64 guest                         */
      | HCR_FB           /* broadcast the guest's TLBI/cache ops  */
      | HCR_BSU_IS       /* barriers upgrade to inner-shareable   */
      | HCR_TACR         /* trap ACTLR_EL1                        */
      | HCR_TIDCP;       /* trap impl-defined registers           */

/* Notice what is DELIBERATELY ABSENT:

     no TVM   - the guest may write TTBR0_EL1/SCTLR_EL1 freely.
                Stage-2 makes that safe, and trapping every page
                table change would destroy performance.

     no TTLB  - the guest may invalidate its own TLB entries.
                VMID tagging means it can only hit its own.

     no TRVM  - reads of VM registers are harmless.

   Each absent bit is a decision that the HARDWARE already
   provides the isolation, so software should stay out of the
   way. That is the whole art.                                */
The rule of thumb

Trap when you must maintain state the guest cannot be allowed to own, or when the guest would otherwise observe the truth. Do not trap when stage-2 or VMID tagging already contains the damage. Every unnecessary trap bit is a permanent tax on every guest, for ever.

A worked example: why TSW exists

One bit is worth working through in full, because the reason it exists is not obvious and the reasoning generalises to half the other bits.

/* AArch64 cache maintenance comes in two flavours:      */

    DC CIVAC, x0     /* clean+invalidate by VIRTUAL ADDRESS.
                        Goes through stage 1 and stage 2, so it
                        can only ever touch memory this guest
                        actually owns.  SAFE - do not trap.   */

    DC CISW,  x0     /* clean+invalidate by SET AND WAY.
                        Addresses a physical cache location by
                        geometry. There is no address, so there
                        is nothing for stage 2 to constrain.

                        A guest looping over every set and way -
                        which is exactly what Linux does when it
                        turns its MMU off during boot or kexec -
                        would clean and invalidate lines
                        belonging to OTHER VMs and to the
                        hypervisor.                            */

/* Hence HCR_EL2.TSW. The guest traps, and the hypervisor does
   something equivalent-but-safe. KVM's historical answer was to
   flush the guest's own stage-2 mappings instead; modern KVM
   mostly just makes the operation a no-op after ensuring the
   guest's memory is coherent, because a guest with stage-2
   enabled has no legitimate need for set/way operations.

   This is the general shape of every trap handler you will
   write: the guest asked for something that means one thing on
   bare metal and something dangerous under virtualisation, and
   you must supply the SPIRIT of the request, not the letter. */

Decoding a trap when it arrives

A trap arrives as an exception with the details spread across three registers. Decoding it in a fixed order turns a hex dump into a sentence.

/* Every trap to EL2 leaves the reason in ESR_EL2. */

    ESR_EL2[31:26]  EC   exception class
    ESR_EL2[25]     IL   instruction length (1 = 32-bit)
    ESR_EL2[24:0]   ISS  class-specific syndrome

  EC values you will meet constantly:

    0x01  trapped WFI/WFE                 (HCR.TWI/TWE)
    0x03  trapped MCR/MRC cp15            (AArch32 guest)
    0x07  trapped SVE/FP/SIMD             (CPTR_EL2)
    0x16  HVC from AArch64                (deliberate hypercall)
    0x17  SMC from AArch64                (HCR.TSC)
    0x18  trapped MSR/MRS/system insn     (HCR.TVM, TID*, TACR...)
    0x20  instruction abort, lower EL     (stage-2 fetch fault)
    0x24  data abort, lower EL            (stage-2 data fault)

/* For EC=0x18 the ISS names the register precisely: */

    ISS[21:20] Op0   ISS[19:17] Op2   ISS[16:14] Op1
    ISS[13:10] CRn   ISS[9:5]   Rt    ISS[4:1]   CRm
    ISS[0]     Direction: 0 = write (MSR), 1 = read (MRS)

/* So a handler looks like: */

static int handle_sysreg_trap(struct vcpu *v)
{
        u64 esr  = read_sysreg(esr_el2);
        u32 iss  = esr & 0x1ffffff;
        int rt   = (iss >> 5) & 0x1f;
        bool is_read = iss & 1;

        const struct sysreg_desc *d = find_desc(iss);
        if (!d)
                return inject_undefined(v);   /* guest gets UNDEF */

        if (is_read)
                vcpu_set_reg(v, rt, d->get(v));
        else
                d->set(v, vcpu_get_reg(v, rt));

        /* ALWAYS advance past the trapping instruction, or you
           will execute it again, for ever.                    */
        vcpu_skip_instr(v);
        return 1;
}
Forgetting vcpu_skip_instr

The guest re-executes the same instruction, traps again, and the VM appears to hang while burning 100% of a physical CPU. It is the single most common bug when hand-writing a trap handler, and it looks like a livelock rather than a crash. If a guest is stuck, check the exit counter — a constant, enormous exit rate with no progress is this bug.

Watching traps on a live system

All of this can be watched on a running system rather than reasoned about, and doing so once is worth more than reading the section twice.

# Every exit KVM takes is counted and typed.

$ sudo perf stat -e 'kvm:*' -a sleep 5
        12,043  kvm:kvm_entry
        12,043  kvm:kvm_exit
         8,911  kvm:kvm_mmio
           520  kvm:kvm_wfx_arm64
            17  kvm:kvm_hvc_arm64

$ sudo perf record -e kvm:kvm_exit -a -- sleep 5
$ sudo perf script | head
# the ESR_EL2 value is in the event, so you can bucket exits by EC

# Or read the per-VM counters directly:
$ sudo cat /sys/kernel/debug/kvm/*/vcpu0/*exits* 2>/dev/null

# A healthy compile-in-a-VM: a few thousand exits per second,
# nearly all MMIO to virtio queues.
# A sick one: hundreds of thousands, dominated by kvm_wfx or by
# MMIO to an emulated legacy device.
