Storage and block devices

QEMU's block layer is a stack of filters — format drivers, protocol drivers, caches, throttling, snapshots — that you compose. The command line hides this behind -drive, which is convenient until you need a snapshot chain or an overlay, at which point knowing the real structure saves you.

The block stack

   guest driver  (virtio-blk, nvme, ahci ...)

   host storage

   -drive collapses all of this into one option. -blockdev
   exposes each layer as a named node you can wire together,
   which is what libvirt and any serious automation uses.

Overlays: the workflow that saves the most time

# Build a golden image once. Never boot it directly again.
# Every experiment gets a disposable overlay on top.

$ qemu-img create -f qcow2 -b golden.qcow2 -F qcow2 work.qcow2
Formatting 'work.qcow2', fmt=qcow2 backing_file=golden.qcow2 ...

$ ls -lh
-rw-r--r-- 2.1G golden.qcow2
-rw-r--r--  196K work.qcow2        # writes go here only

$ qemu-system-aarch64 ... -drive file=work.qcow2,if=none,id=hd0 \
    -device virtio-blk-device,drive=hd0

# Broke it? Throw the overlay away, make a new one. Two seconds.
$ rm work.qcow2 && qemu-img create -f qcow2 -b golden.qcow2 \
    -F qcow2 work.qcow2

# Even quicker, for a single throwaway run - no overlay file at
# all, all writes go to a temporary file QEMU deletes on exit:
$ qemu-system-aarch64 ... -snapshot -drive file=golden.qcow2,...

# Commit an overlay back into its backing file, when the change
# was one you wanted to keep:
$ qemu-img commit work.qcow2

# Chains are allowed, and useful:
#   base.qcow2  <- installed.qcow2  <- configured.qcow2  <- run.qcow2
$ qemu-img info --backing-chain run.qcow2

# Flatten a chain into one image:
$ qemu-img convert -O qcow2 run.qcow2 flattened.qcow2
The single habit worth forming

Keep one read-only golden image per project and always boot an overlay. Experiments become free, "it worked yesterday" becomes recoverable, and you stop being afraid of rm -rf inside a guest. The whole trick is one qemu-img create -b command.

Cache modes: a correctness setting

   Three caches sit between the guest and the platter:

     guest page cache -- guest's own, always present
     HOST page cache  -- controlled by cache=
     disk write cache -- controlled by whether flushes reach it

   cache=writeback   (default)
       host page cache USED. Guest flushes are honoured
       (fdatasync). Fast, and SAFE - provided the guest issues
       flushes and your device model implements them.

   cache=none
       O_DIRECT: bypass the host page cache. The guest's own
       cache is the only one. Predictable, avoids double
       caching, required for some migration setups. Needs
       aligned I/O, so it fails on some filesystems (tmpfs).

   cache=writethrough
       every write goes to stable storage before completing.
       Very slow. Safe even for a guest that never flushes.

   cache=unsafe
       FLUSHES ARE IGNORED. Fastest by far. A host crash loses
       arbitrary amounts of guest data, including data the
       guest was told was durable.

   cache=directsync
       O_DIRECT plus writethrough.

   Choose:
     building/throwaway images, CI        -> unsafe   (10x on
                                             installs)
     day-to-day development               -> writeback
     anything holding work you care about -> writeback, and
                                             verify flushes
     production, shared storage           -> none
# The full modern form. aio=native needs cache=none or
# directsync; aio=io_uring is better where available.
-drive file=disk.qcow2,if=none,id=hd0,format=qcow2,\
cache=none,aio=io_uring,discard=unmap,detect-zeroes=unmap \
-device virtio-blk-device,drive=hd0

#   discard=unmap        guest TRIM shrinks the host image
#   detect-zeroes=unmap  writes of zeroes become holes
#   Together these keep a long-lived image from growing without
#   bound. Add them to every qcow2 you keep.

# Throttling, to simulate slow storage - genuinely useful for
# finding timeout bugs in a driver:
-drive file=disk.img,if=none,id=hd0,\
throttling.iops-total=100,throttling.bps-total=1048576

# Fault injection, to test error paths:
-drive file=blkdebug::disk.img,if=none,id=hd0
# with a config file that fails the Nth read, or corrupts a
# write, or returns EIO after a delay.

Reading and writing images from the host

# raw, single filesystem - simplest:
$ sudo mount -o loop rootfs.ext4 /mnt

# raw, partitioned:
$ LOOP=$(sudo losetup -Pf --show sd.img)
$ sudo mount ${LOOP}p2 /mnt
$ ... ; sudo umount /mnt ; sudo losetup -d $LOOP

# qcow2 - via NBD:
$ sudo modprobe nbd max_part=8
$ sudo qemu-nbd --connect=/dev/nbd0 disk.qcow2
$ sudo fdisk -l /dev/nbd0
$ sudo mount /dev/nbd0p1 /mnt
$ ... ; sudo umount /mnt ; sudo qemu-nbd --disconnect /dev/nbd0

# WITHOUT ROOT, and without mounting - libguestfs. This is the
# right tool for scripting:
$ sudo apt install libguestfs-tools
$ virt-ls -a disk.qcow2 /etc
$ virt-cat -a disk.qcow2 /etc/hostname
$ virt-copy-out -a disk.qcow2 /var/log/messages ./
$ virt-copy-in -a disk.qcow2 mydriver.ko /lib/modules/
$ virt-customize -a disk.qcow2 \
      --root-password password:secret \
      --install openssh-server \
      --run-command 'systemctl enable serial-getty@ttyAMA0'
$ guestfish -a disk.qcow2 -i        # an interactive shell

# NEVER mount an image read-write while a guest is using it.
# Two writers on one filesystem corrupts it immediately and
# the corruption may not show for hours.

Snapshots

# INTERNAL snapshots - stored inside a qcow2, include RAM if
# taken from the monitor. This is save-state/load-state.

(qemu) savevm before-experiment
(qemu) info snapshots
ID   TAG                 VM SIZE  DATE               VM CLOCK
1    before-experiment     512MiB 2026-08-22 10:14   00:02:31
(qemu) loadvm before-experiment      # instant time travel
(qemu) delvm before-experiment

# Offline:
$ qemu-img snapshot -l disk.qcow2
$ qemu-img snapshot -c mytag disk.qcow2
$ qemu-img snapshot -a mytag disk.qcow2
$ qemu-img snapshot -d mytag disk.qcow2

# EXTERNAL snapshots - a new overlay, taken live via QMP. This
# is how backups are done without pausing the guest:
{"execute":"blockdev-snapshot-sync",
 "arguments":{"device":"hd0","snapshot-file":"snap1.qcow2",
              "format":"qcow2"}}

# savevm/loadvm is the most underused debugging tool in QEMU.
# Reproducing a bug that takes ten minutes of setup? Snapshot
# just before it, then loadvm as many times as you need. It
# turns a ten-minute iteration into a one-second one.
# (It requires all devices to support migration state; a
# passed-through device will refuse.)

How it shows up

SymptomCause
Guest filesystem corrupt after a host crashcache=unsafe, or a device model that ignores FLUSH
Image grows until the host disk fillsNo discard=unmap; deleted guest data still occupies clusters
Could not open backing fileOverlay moved away from its backing file — the path is stored inside the overlay. Use qemu-img rebase
Guest sees a smaller disk than the fileImage resized but the guest partition and filesystem were not
cache=none fails to openFilesystem does not support O_DIRECT (tmpfs, some network filesystems)
aio=native rejectedRequires cache=none or cache=directsync
Both host and guest wrote to an image; it is wreckedTwo writers. There is no recovery; restore from the golden image
savevm refusesA device without migration support — commonly a passed-through device or a non-migratable model
Guest boots from the wrong diskOrdering; set bootindex= on the device
Terrible install performanceUse cache=unsafe for the install, then switch back
