Timer virtualisation

Time is the illusion hardest to maintain, because a guest can measure it against the outside world. ARM's answer is a single 64-bit offset register that shifts a guest's view of the counter, plus a dedicated virtual timer per exception level — and a set of compromises about what happens while a vCPU is not running.

One counter, several views

There is one physical counter and several views of it, and the offset between views is the whole mechanism of timer virtualisation.

   There is exactly ONE physical counter in the system: a
   free-running, always-on, fixed-frequency counter, shared by
   every core. Software reads it through several windows.

   CNTPCT_EL0   physical count   = the counter, raw
   CNTVCT_EL0   virtual count    = CNTPCT_EL0 - CNTVOFF_EL2

                                              ^^^^^^^^^^^
                             ONE register, per vCPU, 64-bit,
                             writable only at EL2. That is the
                             entire mechanism.

   Timers (comparators) come in matching flavours:

     EL1 physical timer   CNTP_CTL_EL0  CNTP_CVAL_EL0  CNTP_TVAL_EL0
     EL1 virtual timer    CNTV_CTL_EL0  CNTV_CVAL_EL0  CNTV_TVAL_EL0
     EL2 hypervisor timer CNTHP_CTL_EL2 CNTHP_CVAL_EL2
     EL2 virtual timer    CNTHV_*_EL2   (VHE)
     EL3 secure timer     CNTPS_*_EL1

   Each has its own interrupt (a PPI):
     30  EL1 physical timer
     27  EL1 virtual timer     <-- the one a KVM guest uses
     26  EL2 hypervisor timer
     29  EL3 secure timer

   A guest kernel under KVM is told, via its device tree, to use
   the VIRTUAL timer. It then reads CNTVCT_EL0 with no trap at
   all, and gets a value shifted by CNTVOFF_EL2.
Why the offset must exist

A guest that boots two hours after the host expects its counter to start near zero, not at the host's uptime. More importantly, a guest that is suspended and resumed, or migrated to another machine, must not see time jump backwards or leap forwards — its scheduler, its watchdogs and its TCP stack all assume monotonic, roughly-real time. CNTVOFF_EL2 lets the hypervisor rebase the guest's clock without touching a single guest instruction.

What the hypervisor does with CNTVOFF

One register lets the hypervisor lie to a guest about what time it is, which is exactly what is needed to hide the time a guest spent not running.

/* At VM creation: */
    vcpu->cntvoff = read_cntpct();      /* guest time starts at 0 */

/* On every guest entry: */
    write_sysreg(vcpu->cntvoff, cntvoff_el2);

/* All vCPUs of one VM MUST share the same offset, or the guest
   sees different cores disagreeing about the time - which
   breaks its scheduler, its clocksource watchdog and any
   lock-free algorithm using timestamps.

   KVM enforces this: CNTVOFF is per-VM, not per-vCPU.       */

/* On resume from a host suspend: */
    /* The physical counter kept running (or did not - it is
       "always on" but the SoC may have powered it). Either way
       the guest must not observe a jump. Adjust:            */
    vcpu->cntvoff += (now - suspend_started);

/* On live migration: */
    /* The destination machine's counter has a completely
       different value AND possibly a different frequency.
       CNTFRQ_EL0 is not writable per-guest, which is a real
       architectural gap - migration between machines with
       different counter frequencies is not supported. Check
       CNTFRQ on both ends before you promise migration.     */

Several timers exist at once and they belong to different owners. Confusing them is a common source of guests that either never wake or wake constantly.

   instead of the virtual one produces a guest that works but
   traps on every timer programming operation. Symptom: high
   exit count with EC=0x18 on CNTP registers.               */

The hard part: time while you are not running

The genuinely hard problem: a guest's timer can expire while it is not scheduled, and what the hypervisor does about that is a design decision with visible consequences.

   A guest sets a timer for 1 ms from now, then its vCPU is
   descheduled for 20 ms because the host is busy.

   The virtual timer fires - in hardware - while the vCPU is
   not resident. Who notices?

   ANSWER: the hypervisor must arrange to notice. KVM does this
   by putting the guest's timer deadline into a HOST timer
   (an hrtimer) whenever the vCPU is descheduled:

     vCPU blocks / is preempted
        |
        v
     read guest CNTV_CVAL, convert to host time
     arm a host hrtimer for that instant
     save and DISABLE the guest's timer in hardware
        |
        ... host runs other things ...
        |
     hrtimer fires -> mark virtual PPI 27 pending for that vCPU
                   -> wake the vCPU thread
        |
        v
     vCPU is scheduled again
        |
        v
     restore guest timer state, inject the pending interrupt

   The guest observes: "my 1 ms timer fired after 20 ms".
   That is LATE, not WRONG - and lateness is unavoidable when
   you overcommit. But it must never be EARLY, and it must
   never be LOST.
The RTOS problem

An RTOS guest with a 100 µs deadline cannot tolerate 20 ms of scheduling delay, and no amount of hypervisor cleverness fixes it — the physical CPU was genuinely doing something else. The answer is not a better timer path; it is to stop sharing that CPU: pin the vCPU, isolate the core (isolcpus, nohz_full), give it a real-time scheduling class, or use a partitioning hypervisor that never time-shares in the first place.

Steal time: telling the guest the truth

Rather than hiding lost time, a hypervisor can report it — which lets a cooperative guest schedule sensibly instead of being confused.

/* A guest's own accounting is a lie under overcommit: it
   thinks it used 100 ms of CPU when 60 ms of that was spent
   descheduled. Its load average, its CPU-frequency governor
   and its scheduler all draw wrong conclusions.

   The paravirtual fix: the hypervisor publishes, in a shared
   page, how much time this vCPU spent NOT running.        */

  struct pvclock_vcpu_stolen_time {
          __le32 revision;
          __le32 attributes;
          __le64 stolen_time;      /* nanoseconds, monotonic  */
          /* padded to 64 bytes                              */
  };

/* Discovered via SMCCC:
     HV_PV_TIME_FEATURES  -> is it there?
     HV_PV_TIME_ST        -> give me the IPA of my structure   */

/* In the guest: */
$ cat /proc/stat | head -2
cpu  1204 0 388 90112 22 0 8 1877 0 0
                                 ^^^^
                                 steal time, in USER_HZ

$ vmstat 1

                                                        ^^
                                            31% stolen - this
                                            guest is starved

/* st consistently above a few percent means the host is
   oversubscribed. It is the single most useful number for
   diagnosing "the VM is slow" complaints, and it points at the
   host, not the guest.                                      */

Checking the timer setup

Timer configuration is checkable from inside the guest, and doing so resolves most "the clock is wrong" reports quickly.

# Guest: which timer is it actually using?
$ cat /proc/interrupts | grep timer
  3:      12045      11982   GICv3  27 Level  arch_timer
                                    ^^ 27 = VIRTUAL timer. Good.
                                    30 would be the physical one.

$ cat /sys/devices/system/clocksource/clocksource0/current_clocksource
arch_sys_counter

$ dmesg | grep -i arch_timer
[    0.000000] arch_timer: cp15 timer(s) running at 54.00MHz (virt).
[    0.000000] clocksource: arch_sys_counter: mask: 0xff...
                                                         ^^^^^^
# "(virt)" is what you want. "(phys)" means the guest is on the
# physical timer and every access traps.

# Host: what frequency does the hardware run at?
$ dmesg | grep -i 'arch_timer.*MHz'
# Must match on both ends of a live migration.

# Prove the offset works - guest uptime should not be host uptime:
$ uptime            # in the guest
$ ssh host uptime   # on the host

# Measure timer accuracy inside the guest:
$ cyclictest -t1 -p 80 -n -i 1000 -l 10000
T: 0 ( 1234) P:80 I:1000 C:  10000 Min:     12 Act:   28 Avg:   35 Max:    9812
                                                                       ^^^^^^^
# 9.8 ms worst case = the vCPU was descheduled. Pin it and
# re-run; on an isolated core this should drop to tens of us.
