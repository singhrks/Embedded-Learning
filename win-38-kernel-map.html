The Windows kernel map: layers, components and where a driver sits

Every other chapter in this track explains one piece. This one is the whole picture in a single diagram — every layer from your application down to the hardware, every executive component named, and your driver's place among them marked. Read it early to know where you are, and come back whenever a chapter feels like it is describing something in isolation.

The whole system, on one page

Nothing in this diagram is new; it is the rest of the track arranged spatially. The single most useful thing it shows is that your driver is not "inside the kernel" as one undifferentiated blob — it sits in a specific place, called by one specific component, with everything else either above it or beneath it.

What each layer is actually responsible for

The distinction that matters most is between the layers that decide what should happen and the layers that make it happen on real silicon. Confusing the two is why people expect the kernel layer to be large and the executive to be small, when it is firmly the other way round.

Reading the map from a function name

This is the practical payoff of the diagram, and it works in reverse: because every kernel function carries its component's prefix, any unfamiliar name in a stack trace or a header tells you immediately which box above it belongs to — which is usually most of what you need to know about it.

   THE TWO-LETTER PREFIX IS A MAP REFERENCE:

     IoCallDriver          Io  -> the I/O manager
     ObReferenceObject     Ob  -> the object manager
     MmProbeAndLockPages   Mm  -> the memory manager
     PsCreateSystemThread  Ps  -> the process manager
     KeAcquireSpinLock     Ke  -> the kernel layer
     ExAllocatePool2       Ex  -> executive support
     SeAccessCheck         Se  -> the security reference monitor
     CmRegisterCallback    Cm  -> the configuration manager
     PoStartNextPowerIrp   Po  -> the power manager
     HalGetBusData         Hal -> the HAL
     ZwCreateFile          Zw  -> the native API, called from
                                  kernel mode (previous mode set
                                  to kernel, so access checks are
                                  skipped - see below)
     NtCreateFile          Nt  -> the same routine, entered from
                                  USER mode, where the caller's
                                  arguments are untrusted

   THE Nt/Zw DISTINCTION IS NOT COSMETIC and it is the most
   commonly misunderstood pair in the whole API. Calling the Nt
   form from a driver leaves "previous mode" as whatever the
   caller was, so your own kernel pointers may be validated as
   if they came from user space - or worse, a user-supplied
   pointer may be trusted. From kernel code you almost always
   want the Zw form. (Chapter 08 covers the buffer side of the
   same problem.)

One ReadFile, all the way down and back

The clearest way to see the layers cooperating is to follow a single ordinary operation through every one of them. Almost every question this track answers later — about IRQL, buffers, IRPs, completion or cancellation — is a question about one specific step in this sequence.

   ReadFile(hDevice, buf, len, &got, NULL)     USER MODE

        |  kernel32 forwards to ntdll

   NtReadFile              ntdll, still user mode
        |  syscall instruction - the ONLY way across

        |  FILE_OBJECT pointer, and checks the access that
        |  handle was granted when it was opened (chapter 04)

        |  builds an IRP: major function IRP_MJ_READ, the
        |  buffer described according to your device's
        |  buffering method (chapter 08), one stack location
        |  per driver in the stack (chapter 05)
        v
   IoCallDriver(topOfStack, irp)
        |
        v
   UPPER FILTER        may inspect, modify, or pass down
        v
   YOUR FUNCTION DRIVER        <-- where this track lives
        |  KMDF turns the IRP into a WDFREQUEST and delivers
        |  it to one of your queues (chapter 16)
        |
        |  you program the hardware, and RETURN - usually
        |  STATUS_PENDING, because the device is not finished
        v

        |

        v
   ReadFile returns TRUE, `got` holds the byte count
The one asymmetry worth remembering

The request travels down the stack in the calling thread's context, at PASSIVE_LEVEL, where you may block, allocate paged memory and touch user buffers. It usually completes upward in a completely different context — a DPC at DISPATCH_LEVEL, on whichever CPU took the interrupt, with no relationship to the original thread at all. Almost every rule in chapter 03 exists because of that asymmetry, and most driver bugs are code that assumed it was still in the first situation when it had reached the second.

How it shows up

SymptomWhere on the map to look
A function name in a crash you have never seenRead its two-letter prefix — that names the component and usually the chapter
A user buffer is valid on entry and garbage at completionCompletion runs in a different thread; the user address space is no longer mapped
