Cache organisation and policies

Chapter 13 said caches work. This chapter opens one up: how an address finds its line, why associativity exists, what happens on a write, and why two arrays exactly 4 KB apart can destroy your performance.

The problem

A cache holds a small subset of a huge address space. Two questions must be answered on every access, in about one cycle:

  1. Given an address, where would that line be if it were cached?
  2. Is it actually there, or is this a different address that maps to the same place?

Searching every entry would be correct and far too slow. The answer is to make the location a function of the address, and store enough extra bits to confirm identity.

Cache lines

Caches do not store individual bytes. The unit of transfer and tracking is a line, almost universally 64 bytes on ARM and x86.

Why 64 bytes and not 4?

  Larger lines:  + exploit spatial locality — fetch neighbours for free
                 + fewer tags to store (less overhead)
                 - more wasted bandwidth if you use only part of it
                 - more false sharing between cores (chapter 15)

  64 bytes is the empirical sweet spot, and it has consequences you
  can measure:

    · a 64-byte struct fits exactly one line — align it and every
      access touches one line instead of two
    · reading 1 byte costs the same as reading 64
    · two variables in the same line are, for coherency purposes,
      THE SAME VARIABLE

Address decomposition

An address is split into three fields. This is the whole mechanism.

   ┌──────────────┬────────────┬──────────────┐
   │     TAG      │    INDEX   │    OFFSET    │
   └──────────────┴────────────┴──────────────┘
      identity       which set     byte within
                     to look in     the line

  OFFSET = log2(line size)          64-byte line  → 6 bits
  INDEX  = log2(number of sets)
  TAG    = everything left over

Worked example: 32 KB, 8-way set-associative, 64-byte lines

  lines total = 32768 / 64        = 512
  sets        = 512 / 8           = 64 sets
  offset bits = log2(64)          = 6
  index bits  = log2(64)          = 6
  tag bits    = 48 - 6 - 6        = 36   (for a 48-bit address)

   47                    12 11    6 5    0
  ┌────────────────────────┬───────┬──────┐
  │          TAG           │ INDEX │OFFSET│
  └────────────────────────┴───────┴──────┘

The lookup

  1. Extract INDEX from the address    → select one set
  2. Read all N ways of that set in parallel
  3. Compare each way's stored TAG against the address's TAG,
     and check its VALID bit
  4. Any match → HIT. Use OFFSET to pick bytes from that line.
     No match  → MISS. Choose a victim, evict it, fetch the line.

Steps 2 and 3 happen simultaneously across all ways — that is what
associativity costs in hardware: N comparators and N tag reads per access.

Associativity

A direct-mapped cache is simple but has an obvious weakness: two addresses that map to the same slot evict each other endlessly, even when the rest of the cache is empty. Associativity is the fix, and it is a spectrum rather than a switch.

OrganisationWhere a line may goCostWeakness
Direct-mapped (1-way)Exactly one placeOne comparator; fastest, smallestTwo hot addresses with the same index thrash forever, even with the cache 99% empty
N-way set-associativeAny of N ways in one setN comparators, a replacement policyStill possible to conflict with N+1 hot lines
Fully associativeAnywhereOne comparator per line — only feasible for tiny structuresImpractical above a few dozen entries; used for TLBs and victim caches
 
Direct-mapped thrashing, made concrete

  32 KB direct-mapped, 64-byte lines → 512 sets
  index = bits [14:6], so addresses 32 KB apart share an index.

  float a[8192], b[8192];        /* 32 KB each, adjacent in memory */
  for (i = 0; i < 8192; i++)
          a[i] += b[i];

  a[i] and b[i] are exactly 32768 bytes apart → SAME SET, every i.
  Each iteration evicts the other. 100% miss rate.
  Padding b by one line makes the miss rate ~6%.

This is a CONFLICT MISS: the cache is nearly empty and still missing.
The power-of-two stride trap

This is not a historical curiosity — it bites constantly in numerical and image code. Any array whose row stride is a large power of two makes column traversal land on the same few sets.

float m[1024][1024];              /* row stride = 4096 bytes */
for (j = 0; j < 1024; j++)
        for (i = 0; i < 1024; i++)
                sum += m[i][j];   /* every access strides 4096 bytes */

/* With a 4096-byte set span, all 1024 accesses in the inner loop map
   to the same set. An 8-way cache holds 8 of them. Miss rate ≈ 100%.

   Fix: pad the row.  */
float m[1024][1024 + 16];         /* stride is now 4160 — indices spread */

The same effect explains why FFT and matrix libraries pad their leading dimensions, and why a benchmark can slow down 5× when you round an array size up to a power of two.

How much associativity is enough?

Empirically, an N-way cache of size S has about the same miss rate as a direct-mapped cache of size 2S, with diminishing returns past 8 ways. Typical modern designs: L1 4- or 8-way (latency-sensitive), L2 8- to 16-way, L3 16-way or more.

Replacement policy

PolicyIdeaNote
LRUEvict the least recently used wayGood, but exact LRU needs log2(N!) bits per set — only practical for small N
Pseudo-LRUA binary tree of "which half was used more recently"N−1 bits per set; nearly as good. The common real choice.
RandomPick a way at randomCheap, and immune to pathological patterns. Used in some ARM L1s.
RRIP / DRRIPPredict re-reference interval; insert streaming data as "evict soon"Handles scans that would otherwise flush the whole cache
Why LRU fails on scans

Stream an array larger than the cache and LRU evicts everything useful in favour of data you will never touch again. This is why madvise(MADV_DONTNEED), non-temporal stores (STNP on AArch64) and RRIP-style policies exist: they let a bulk copy pass through without destroying the working set of everything else.

Write policies

Two independent decisions, giving four combinations — and the choice is directly visible in your page tables.

DecisionOptions
On a write hitWrite-back: update the line, mark it dirty, write to memory only on eviction. Write-through: update the line and memory every time.
On a write missWrite-allocate: fetch the line first, then write into it. No-write-allocate: send the write straight to memory.
 
Write-back + write-allocate   ← the standard pairing, and the default
                                for Normal memory on ARM
  + far less memory traffic (repeated writes coalesce in the cache)
  + a write miss followed by more writes to the same line is cheap
  - memory is stale until eviction → this is exactly why DMA needs
    cache maintenance (chapter 15, and the SMMU chapter)
  - a dirty line must be written out on eviction, adding latency

Write-through + no-write-allocate
  + memory is always current → simple for DMA and for coherency
  + no dirty bits to track
  - every store goes to memory; needs a write buffer to be tolerable

The DIRTY bit is the whole difference. It is why a cache flush is
sometimes a no-op and sometimes writes megabytes to DRAM.
/* On ARM this is not a fixed property of the cache — it is chosen
   per page, via the AttrIndx field of the translation descriptor
   indexing into MAIR_EL1. See ARM chapters 11 and 14.            */

MAIR slot 0 = 0xFF   /* Normal, Inner+Outer Write-Back, read+write allocate */
MAIR slot 1 = 0x00   /* Device-nGnRnE — never cached at all                 */
MAIR slot 2 = 0x44   /* Normal, Non-cacheable                               */

/* So "is this memory write-back cached?" is a software decision made
   in a page table, not a hardware constant. Getting it wrong for a
   DMA buffer or an MMIO region is a classic driver bug.            */

Virtual versus physical indexing

The cache lookup needs an address — but which one, the virtual address the program used or the physical address after translation? Waiting for the MMU adds latency to every access.

SchemeIndex / TagProperty
PIPTPhysical / PhysicalSimplest to reason about; no aliasing. But the TLB lookup is on the critical path.
VIVTVirtual / VirtualFastest, but must be flushed on every context switch and suffers aliasing. Largely abandoned.
VIPTVirtual / PhysicalThe standard. Index with the virtual address (available immediately) while the TLB produces the physical tag in parallel. Both finish together.
 
Why VIPT works, and its constraint

  Page offset bits are IDENTICAL in the virtual and physical address —
  translation only changes the page number.

   47                     12 11        0
  ┌─────────────────────────┬───────────┐
  │      page number        │  offset   │   ← offset is untranslated
  └─────────────────────────┴───────────┘
                             └────┬────┘
                                  │ if INDEX+OFFSET fit inside here,
                                  │ indexing with the VA is identical
                                  │ to indexing with the PA

  Constraint:  (cache size / associativity) ≤ page size

  4 KB pages, 64-byte lines → index+offset ≤ 12 bits
  32 KB cache: needs 8-way to keep each way at 4 KB.

This is precisely why L1 caches are "32 KB, 8-way" so consistently.
It is not a tuning choice — it is forced by the 4 KB page size.
Going to a 64 KB L1 requires 16 ways, or larger pages, or accepting
aliasing and handling it in software.

Inspecting a real machine

Cache sizes and geometry are not something you have to look up in a datasheet — the machine will tell you, and knowing the actual numbers for the hardware in front of you makes the preceding sections concrete.

# Linux exposes the full cache topology
lscpu -C
#  NAME ONE-SIZE ALL-SIZE WAYS TYPE        LEVEL SETS
#  L1d       64K     512K    4 Data            1  256
#  L1i      128K       1M    4 Instruction     1  512
#  L2         4M      32M    8 Unified         2 8192
#  L3        16M      16M   16 Unified         3 16384

# or directly
cat /sys/devices/system/cpu/cpu0/cache/index0/{level,type,size,ways_of_associativity,coherency_line_size}

getconf -a | grep CACHE

/* the constant every performance-sensitive program needs */
#include <unistd.h>
long line = sysconf(_SC_LEVEL1_DCACHE_LINESIZE);   /* usually 64 */

/* C++17 gives it portably at compile time */
#include <new>
alignas(std::hardware_destructive_interference_size) struct counter { ... };

/* Linux kernel */
struct foo {
        int hot;
} ____cacheline_aligned;
