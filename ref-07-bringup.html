The board bring-up checklist

A new board arrives and nothing works. This is the order to attack it in — strictly bottom up, verifying each layer before trusting anything above it.

The principle

   BRING UP IN LAYERS. VERIFY EACH ONE BEFORE MOVING UP.

     7  APPLICATION
     6  DRIVERS AND PERIPHERALS
     5  CONSOLE / STDIO
     4  RAM AND THE C RUNTIME
     3  CLOCKS
     2  DEBUG CONNECTION
     1  POWER
     0  THE PHYSICAL BOARD

   THE MISTAKE EVERYONE MAKES: flashing the full application
   onto a brand-new board and wondering why nothing happens.
   You have just introduced seven layers of possible failure
   at once, with no way to distinguish them.

   START AT LAYER 0. GET A BLINKING LED BEFORE ANYTHING
   ELSE.

   A BLINKING LED PROVES A REMARKABLE AMOUNT:
     · power is present and stable enough
     · the clock configuration works
     · reset released correctly
     · the vector table is where the CPU expects it
     · the C runtime initialised
     · main() was reached
     · GPIO configuration works
     · your build and flash toolchain are correct

   That is layers 0 through 4 in one test, and it takes ten
   minutes. NEVER SKIP IT.

   AND THE SECOND PRINCIPLE: ON A NEW BOARD, DO NOT TRUST
   THE SCHEMATIC OR THE ASSEMBLY. Both contain mistakes.
   Measure.

Layers 0-2: power and access

/* --- 0. BEFORE APPLYING POWER --- */
  [ ] VISUAL INSPECTION under magnification: solder
      bridges, tombstoned parts, missing components,
      COMPONENTS FITTED THE WRONG WAY AROUND (check pin 1
      on every polarised part)
  [ ] CHECK FOR SHORTS with a meter: every supply rail to
      ground, and rail to rail. A short here saves the
      board.
  [ ] verify the assembly matches the BOM - wrong-value
      resistors in a divider are common and invisible
  [ ] confirm the input polarity and voltage before
      connecting anything

/* --- 1. POWER --- */
  [ ] apply power through a CURRENT-LIMITED SUPPLY. Set the
      limit to a little above the expected draw. If it
      immediately limits, power down and find the short.
  [ ] MEASURE EVERY RAIL with a meter. Tolerance, typically
      +-5%.
  [ ] check the POWER SEQUENCING if the datasheet requires
      an order - many SoCs do, and violating it can damage
      the part or leave it wedged
  [ ] SCOPE EVERY RAIL, AC-coupled, at a fast timebase.
      Ripple, and any dip at start-up. A multimeter will
      not show a 2 microsecond brownout that resets your
      MCU.
  [ ] check the current draw against expectation. Far too
      high means a short or a mis-stuffed part; far too low
      means something is not powered at all.
  [ ] check thermals - anything unusually hot after a
      minute is wrong

/* --- 2. THE DEBUG CONNECTION --- */
  [ ] RESET pin: is it released? Scope it at power-up. A
      held reset is a very common cause of "the board is
      dead".
  [ ] BOOT MODE pins: strapped correctly for the boot
      source you intend?
  [ ] connect the probe. Ground first (chapter 03).
  [ ] read the CHIP ID register. This proves SWD/JTAG
      works, the core is alive, and the part is what you
      think it is.
        > mdw 0xE0042000       # DBGMCU_IDCODE on STM32
  [ ] if it will not connect, work the nine-step checklist
      in chapter 03. Try "connect under reset" early.
  [ ] MASS ERASE the part. Factory-programmed content and
      leftover test firmware both cause confusing
      behaviour.

/* AT THIS POINT YOU HAVE A CONNECTION TO A LIVE CHIP. Every
   remaining problem is now diagnosable, which is a
   qualitatively different situation from ten minutes
   ago.                                                   */

Layers 3-5: clocks, RAM, console

/* --- 3. CLOCKS --- */
  [ ] FIRST, RUN FROM THE INTERNAL OSCILLATOR. It always
      works. Do not configure the PLL yet.
  [ ] blink an LED with a crude delay loop. THE FIRST
      MILESTONE.
  [ ] now switch to the external crystal, ONE STEP AT A
      TIME:
        · is the crystal oscillating? Scope it with a 10x
          probe - a 1x probe's capacitance can stop a
          crystal, which is a genuinely confusing failure
        · are the load capacitors the value the crystal
          datasheet specifies?
        · does the ready flag set? DO NOT SPIN FOREVER
          WAITING:
              uint32_t to = 100000;
              while (!(RCC->CR & RCC_CR_HSERDY) && --to)
                      ;
              if (!to) fall_back_to_internal_osc();
          A firmware that hangs in a clock wait loop looks
          exactly like a dead board.
  [ ] configure the PLL. CHECK THE FLASH WAIT STATES FIRST
      - at a higher core clock the flash needs more wait
      states, and setting the clock before the wait states
      is an instant hard fault.
  [ ] VERIFY THE ACTUAL FREQUENCY. Output the system clock
      on the MCO pin and measure it, or time a known delay
      loop against a stopwatch. DO NOT ASSUME THE
      CONFIGURATION WORKED - a wrong clock makes every
      subsequent baud rate and timer wrong, and the symptom
      is "the UART outputs garbage".

/* --- 4. RAM AND THE C RUNTIME --- */
  [ ] internal RAM: the startup code has already used it if
      you reached main()
  [ ] EXTERNAL RAM (SDRAM/DDR), if fitted, needs its
      controller configured, and then TESTED:
        · walking ones and walking zeros - catches stuck
          and shorted data lines
        · an address test (write the address to itself) -
          catches ADDRESS line faults, which present as
          aliasing rather than corruption
        · a pattern test over the full range
        · AND TEST AT TEMPERATURE. Marginal timing passes
          at 25C and fails at 70C.
  [ ] check the LINKER SCRIPT regions match the actual
      memory map
  [ ] check .data was copied and .bss was zeroed - a global
      that is unexpectedly nonzero means the startup code
      is wrong
  [ ] SET UP STACK PAINTING NOW, while it is easy:
        fill the stack with 0xA5 at boot; a later
        high-water-mark check tells you the real usage
        (chapter 06)

/* --- 5. THE CONSOLE --- */
  [ ] configure the UART and print something
  [ ] IF IT IS GARBAGE, THE CLOCK IS WRONG. Garbled output
      at a consistent wrong rate is almost always a system
      clock that is not what you configured. Go back to
      step 3.
  [ ] if there is nothing at all: check the pin mux, check
      TX and RX are not swapped, check the peripheral clock
      is enabled, and scope the TX pin to see whether
      anything is coming out at all.
  [ ] print the clock frequencies, the reset reason, and
      the build ID at boot. YOU WILL WANT ALL THREE
      CONSTANTLY.
  [ ] install a fault handler that prints the fault
      registers (chapter 06) - do this before you have
      faults, not after

/* NOW YOU HAVE A CONSOLE. Everything from here is ordinary
   debugging.                                             */
The three milestones 
1. THE CHIP ID READS BACK.
   Power, reset and debug access all work.

2. AN LED BLINKS.
   Clocks, reset, vector table, C runtime, GPIO and
   your entire toolchain work.

3. THE CONSOLE PRINTS.
   You now have observability, and every remaining
   problem is a normal debugging problem.

Do not attempt anything else until all three pass. Every
hour spent trying to debug an application on a board that
has not reached milestone 2 is wasted.

Layer 6: peripherals

/* ONE AT A TIME. Never bring up two peripherals at once -
   you will not know which one is failing.               */

/* --- THE UNIVERSAL SEQUENCE FOR ANY PERIPHERAL --- */
  1. ENABLE ITS CLOCK. Then read a register back. If it
     reads zero or the reset value and writes do not stick,
     the clock is off. (chapter 06 - the most common bug in
     this whole chapter.)
  2. CONFIGURE THE PINS: mux, direction, speed, pull,
     open-drain where required.
  3. CONFIGURE THE PERIPHERAL, in the ORDER THE REFERENCE
     MANUAL SPECIFIES. Some registers can only be written
     while the peripheral is disabled.
  4. READ BACK EVERY CONFIGURATION REGISTER and compare it
     to what you wrote. Reserved bits, write-protected
     registers and clock-gated writes all silently discard.
  5. THE SIMPLEST POSSIBLE TRANSACTION. One byte. Polled,
     not interrupt-driven, not DMA.
  6. SCOPE IT. Confirm the signal is physically present and
     correct.
  7. ONLY THEN add interrupts.
  8. ONLY THEN add DMA.

/* --- GPIO --- */
  [ ] output: set a pin, measure it. Toggle it, scope it.
  [ ] input: tie the pin high and low, read it. CHECK THE
      PULL CONFIGURATION - a floating input reads randomly.

/* --- I2C --- */
  [ ] pull-ups fitted? Value appropriate for the bus
      capacitance? (2.2k-10k typically; too weak gives
      slow rising edges and a bus that half-works)
  [ ] SCAN THE BUS - address every device from 0x08 to
      0x77 and see who ACKs. This immediately proves
      wiring, pull-ups and addressing.
  [ ] SCOPE SDA AND SCL. Look at the RISE TIME - a slow
      rise is the classic weak-pull-up signature. Look for
      the ACK bit.
  [ ] check the address: 7-bit versus 8-bit conventions
      differ between datasheets and APIs, and a factor-of-
      two address error is the most common I2C mistake.
  [ ] a stuck bus (SDA held low by a confused slave)
      recovers by clocking SCL manually nine times

/* --- SPI --- */
  [ ] MODE: CPOL and CPHA must match the slave. Four
      combinations, and the wrong one gives plausible
      garbage rather than nothing.
  [ ] chip select polarity and timing
  [ ] MOSI/MISO not swapped
  [ ] read a known register - most devices have an ID
      register, and that is your test
  [ ] scope all four signals together

/* --- UART --- */
  [ ] baud rate, and therefore the clock (step 3)
  [ ] TX/RX crossed correctly
  [ ] voltage levels - 3.3V versus 5V versus RS-232, which
      is inverted and bipolar
  [ ] flow control configuration matching both ends

/* --- ADC --- */
  [ ] reference voltage present and correct
  [ ] measure a known voltage; check the reading matches
  [ ] sampling time long enough for the source impedance -
      too short reads low and the error scales with
      impedance

/* --- FLASH / STORAGE --- */
  [ ] read the JEDEC ID first
  [ ] write and read back a page
  [ ] erase and confirm it reads all 0xFF
  [ ] check timing at the temperature extremes

/* --- USB / ETHERNET --- */
  [ ] clock accuracy - USB needs 0.25%, so the internal RC
      oscillator is usually not good enough
  [ ] termination, and the magnetics for Ethernet
  [ ] enumerate; check the descriptors with a host tool
  [ ] and a PROTOCOL ANALYSER is worth its cost here - USB
      problems are almost undiagnosable without one     */

Record what you find

/* A BRING-UP LOG IS A DELIVERABLE, NOT A PERSONAL NOTE.

   FOR EACH BOARD REVISION, RECORD:
     · every measured rail voltage and current
     · the actual clock frequencies measured
     · every deviation from the schematic - blue wires,
       lifted pins, changed resistor values, DNF parts
     · which peripherals were verified and how
     · every errata that applied and the workaround used
     · every mistake found in the schematic or layout, with
       enough detail for the next revision to fix it
     · photographs of any rework

   WHY IT MATTERS:
     · the next revision's fixes come from this list
     · when board #7 behaves differently from board #1, the
       log tells you what is different
     · a colleague debugging at 2am can read it
     · and PRODUCTION NEEDS TO KNOW which reworks are
       required on which units

/* --- AND THE THINGS TO BUILD INTO THE FIRMWARE NOW --- */
     · a BOOT BANNER printing the build ID, the git hash,
       the measured clock frequencies and the reset reason
     · a RESET REASON DECODER - power-on, watchdog,
       software, brownout, pin. When a unit reboots in the
       field this is the first thing you will want.
     · a FAULT HANDLER that prints the fault registers and
       the stacked frame (chapter 06)
     · STACK PAINTING and a high-water-mark report
     · a SELF-TEST command that exercises every peripheral
       and prints pass/fail - which then doubles as the
       production test
     · a persistent TRACE BUFFER surviving reset
       (chapter 02)

   ALL OF THIS COSTS A DAY DURING BRING-UP AND SAVES WEEKS
   OVER THE PRODUCT'S LIFE. It is also far harder to
   retrofit later, because by then the board is "working"
   and nobody wants to touch the startup code.          */

How it shows up

SymptomCause
Board completely deadReset held, no power, or a short — measure before assuming
Supply limits immediatelyShort — power down and find it
Debugger will not connectChapter 03's checklist; try connect-under-reset
LED blinks at the wrong rateClock is not what you configured
Hangs before mainSpinning in a clock-ready loop, or flash wait states wrong
UART prints garbageClock wrong — go back to layer 3
UART prints nothingPin mux, TX/RX swapped, or peripheral clock off
Peripheral registers read zeroClock not enabled
Configuration register reads back differentWrite-protected, reserved bits, or written while enabled
I2C never ACKsPull-ups, address convention, or wiring — scan the bus
SPI returns plausible garbageWrong CPOL/CPHA mode
External RAM fails only when warmMarginal timing — test at temperature
Works on board 1, not board 7Rework difference — read the bring-up log
Crystal will not startWrong load capacitors, or a 1× scope probe stopping it

Check yourself

  • List the eight layers and explain why bring-up is strictly bottom up.
  • Say what a blinking LED proves — all eight things.
  • Give the pre-power checks, in order.
  • Explain why a rail must be scoped as well as measured.
  • Say why reading the chip ID is the right first debug step.
  • Explain why you start on the internal oscillator.
  • Write a clock-ready wait with a timeout and say why the timeout matters.
  • Explain why flash wait states must be set before raising the clock.
  • Describe how to verify the actual clock frequency.
  • Give the three memory tests for external RAM and what each catches.
  • Give the eight-step universal peripheral bring-up sequence.
  • Say why garbled UART output points at the clock.
  • List the six things to build into the firmware during bring-up.
