Hash functions

A fixed-size fingerprint of arbitrary data, with three security properties that are routinely confused. Hashes underpin signatures, MACs, key derivation, secure boot and blockchains — and the property you need determines which is safe to use.

The three properties

A hash function is judged by three properties, and they are not equally hard to break. Knowing which one a given use actually depends on is what tells you whether a deprecated hash is fatal there or merely untidy.

   H : {0,1}* -> {0,1}^n

   PREIMAGE RESISTANCE
     given h, infeasible to find m with H(m) = h
     "one-way"
     cost to break: 2^n

   SECOND PREIMAGE RESISTANCE
     given m1, infeasible to find m2 != m1 with
     H(m2) = H(m1)
     cost to break: 2^n

   COLLISION RESISTANCE
     infeasible to find ANY m1 != m2 with H(m1) = H(m2)
     cost to break: 2^(n/2)     <-- THE BIRTHDAY BOUND

   THE FACTOR OF TWO IS THE POINT. For SHA-256:
     preimage      2^256   - unreachable
     collision     2^128   - unreachable
   For SHA-1 (160 bits):
     preimage      2^160   - still unreachable
     collision     2^80    - REACHED IN 2017 (SHAttered)

   WHICH IS WHY SHA-1 IS BROKEN FOR SIGNATURES AND
   CERTIFICATES but not yet for HMAC: signatures need
   collision resistance (a forger picks BOTH messages), while
   HMAC's security rests on the key and needs only much
   weaker properties. The distinction matters when you are
   deciding whether a legacy system must be changed
   immediately.

   AND THE BIRTHDAY PARADOX, since it is the whole reason:
   among 23 people two share a birthday with probability
   > 1/2, because there are 253 PAIRS. Collisions come from
   pairs, so n/2 bits of work suffices - and any protocol
   whose security depends on collisions needs twice the
   output length you might expect.

What hashes are for

Hashes appear in more places than any other primitive, and in several of those the property being relied on is not the obvious one. This is what each use actually requires.

/* --- LEGITIMATE --- */
    integrity checking       compare H(file) with a known
                             value
    digital signatures       sign H(m), not m (chapter 15)
    MACs                     HMAC (chapter 08)
    key derivation           HKDF (chapter 10)
    commitment schemes       publish H(x), reveal x later
    Merkle trees             efficient verification of a
                             large set
    deduplication            content-addressed storage
    proof of work            find m with H(m) < target
    secure boot              measure each stage before
                             executing it
                             (isolation chapter 14)

/* --- NOT LEGITIMATE, and each is a real mistake --- */

    PASSWORD STORAGE with a plain hash
        Hashes are FAST - billions per second on a GPU. That
        is the wrong property here. Use Argon2id
        (chapter 10).

    A MAC AS H(key ‖ message)
        LENGTH EXTENSION (below) lets an attacker append data
        and produce a valid tag WITHOUT the key. Use HMAC.

    ENCRYPTION
        A hash is not reversible. "Hashing" data does not
        protect it if the input space is small - an attacker
        enumerates. H(email) is not anonymisation; H(phone
        number) is trivially reversible.

    RANDOM NUMBER GENERATION from a low-entropy input
        H(timestamp) has as much entropy as the timestamp
        (chapter 02).

    COMPARING SECRETS with memcmp
        Early-exit comparison leaks how many bytes matched
        (chapter 19). Use a constant-time compare.        */

How they are built

How a hash processes arbitrary-length input using a fixed-size operation determines its properties — including one structural weakness that surprised people and that newer designs deliberately avoid.

   MERKLE-DAMGARD - MD5, SHA-1, SHA-2

     message -> pad -> split into blocks
     IV -> [f] -> [f] -> [f] -> ... -> output
            ^      ^      ^
            m0     m1     m2

     A compression function f applied iteratively to a
     chaining value. If f is collision resistant, so is the
     whole hash - which is the construction's theorem and the
     reason it was used.

     AND ITS FLAW: the output IS the final chaining value.
     So an attacker who knows H(m) can CONTINUE HASHING from
     that state:

        H(m ‖ padding ‖ extra)

     computed without knowing m - only its length. That is
     LENGTH EXTENSION, and it is why H(key ‖ message) is not
     a MAC.

   SPONGE - SHA-3, ASCON, BLAKE3's tree mode

     a large state, split into RATE and CAPACITY:

       ABSORB:  XOR message blocks into the rate, permute
       SQUEEZE: read output from the rate, permute

       state  [ rate | capacity ]
                 ^        ^
              message   never touched directly by
              goes in   the message or the output

     THE CAPACITY IS NEVER EXPOSED, so length extension is
     impossible. Output can be ANY LENGTH - which gives
     SHAKE128/256, the extendable-output functions used by
     the post-quantum schemes (chapter 20).

   AND THE PRACTICAL CONSEQUENCE: SHA-3, BLAKE2 and BLAKE3
   are all immune to length extension by construction, and
   SHA-512/256 is immune because it truncates. SHA-256 is
   not.

   Interoperability required (TLS, signatures, standards)
        -> SHA-256, or SHA-384 where the standard says so

   64-bit CPU, performance matters
        -> SHA-512/256 or BLAKE2b - both faster than SHA-256
           because they work on 64-bit words

   Microcontroller with a SHA accelerator
        -> whatever it accelerates, usually SHA-256

   Microcontroller without one, code size matters
        -> BLAKE2s (~1 KB) or SHA-256 (~2 KB)

   Hashing very large amounts of data
        -> BLAKE3, which parallelises across cores and SIMD

   Need arbitrary-length output
        -> SHAKE128/256, or BLAKE2X, or BLAKE3

   Need a keyed hash
        -> BLAKE2's keyed mode, or HMAC (chapter 08)

   Hash table keys, attacker-controlled
        -> SipHash with a per-process random key

/* AND CRC IS NOT A HASH. It is linear, so an attacker can
   compute exactly what to change to preserve it. It detects
   accidental corruption, which is a completely different
   job. Using CRC32 for integrity against an adversary is a
   finding, and it appears in shipped firmware regularly. */
SHA-256 is not always the fastest choice

SHA-256 uses 32-bit operations; SHA-512 uses 64-bit ones and does fewer rounds per byte. On any 64-bit CPU without SHA hardware extensions, SHA-512/256 is roughly 1.5x faster than SHA-256 and gives the same 256-bit output — plus immunity to length extension. It is under-used simply because the name is unfamiliar.

Length extension, concretely

A property of the classic construction that lets an attacker extend a hash without knowing the input. It is the reason naively hashing a key with a message does not produce a secure authentication code.

/* THE VULNERABLE CONSTRUCTION: */
        tag = SHA256(secret_key ‖ message)

/* THE ATTACK: the attacker knows `message` and `tag`, and
   the LENGTH of the key - not the key itself.

   1. SHA-256's output IS its internal state after the final
      block.
   2. Load that state into a fresh SHA-256 context.
   3. Continue hashing arbitrary `extra` data.
   4. The result is a valid tag for:

        secret_key ‖ message ‖ padding ‖ extra

   The attacker has forged a tag for a message they chose,
   without ever learning the key.

/* A REAL EXAMPLE, and this shape appears constantly: */
        /* the server checks: */
        tag == SHA256(key ‖ "user=alice&admin=false")

        /* the attacker produces a valid tag for: */
        "user=alice&admin=false" ‖ 0x80 00 ... len ‖
                                          "&admin=true"

   If the parser takes the LAST occurrence of a duplicated
   parameter - which many do - the attacker is now an
   administrator. This has broken Flickr's API, several
   payment gateways, and a long list of others.

/* THE FIXES, in order of preference:
     1. USE HMAC (chapter 08). It is designed for this and
        the nesting defeats the attack.
     2. Use a hash that is immune: SHA-3, BLAKE2/3,
        SHA-512/256.
     3. Use an AEAD, which authenticates as part of
        encryption (chapter 09).

   H(message ‖ key) is also weak - it reduces the forgery to
   finding a collision in H. HMAC exists precisely so that
   nobody has to reason about this.                       */

Using them

Hashing correctly is mostly about what you hash rather than which function you use — in particular, how you handle structure so that two different inputs cannot produce the same byte sequence.

/* --- INCREMENTAL HASHING, which every API supports --- */
    #include <mbedtls/sha256.h>

    mbedtls_sha256_context ctx;
    uint8_t digest[32];

    mbedtls_sha256_init(&ctx);
    mbedtls_sha256_starts(&ctx, 0);         /* 0 = SHA-256 */
    while ((n = read_chunk(buf, sizeof buf)) > 0)
            mbedtls_sha256_update(&ctx, buf, n);
    mbedtls_sha256_finish(&ctx, digest);
    mbedtls_sha256_free(&ctx);
