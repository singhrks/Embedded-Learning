Reading compiler output like a professional

The practical skill this whole track exists to give you: look at generated AArch64 assembly and understand what the compiler did and why. It is the only way to settle a performance argument, and it is faster than you expect once you know the patterns.

The workflow

# --- godbolt.org, for anything small ---
# Source left, assembly right, colour-matched by line. Set the
# compiler to "ARM64 gcc" or "armv8-a clang", flags to -O2.
# Nothing else comes close for exploring a question.

# --- Locally, for real code ---
    gcc -S -O2 -fverbose-asm prog.c -o prog.s
    ; -fverbose-asm annotates each instruction with the
    ; variable names involved

    objdump -dS --demangle prog.o | less
    ; disassembly INTERLEAVED with source (needs -g)

    objdump -d --no-show-raw-insn --demangle prog.o

# --- One function only ---
    objdump -d prog | awk '/<myfunc>:/,/^$/'
    gdb -batch -ex 'disassemble /s myfunc' prog

# --- With performance data attached ---
    perf record ./prog
    perf annotate myfunc
    ; shows the percentage of samples on each instruction -
    ; which turns "this function is slow" into "this load is
    ; slow"

# --- Cycle-level analysis ---
    llvm-mca -mcpu=cortex-a53 -timeline prog.s
    ; a pipeline simulation with the bottleneck named

# --- ALWAYS COMPILE WITH THE FLAGS YOU SHIP. Reading -O0
# output tells you nothing about your release build, and
# reading -O2 output while shipping -Os tells you almost as
# little.

Recognising the skeleton

; int add(int a, int b) { return a + b; }
add:
        add     w0, w0, w1              ; args in w0,w1;
        ret                             ; result in w0

; A LEAF FUNCTION: no prologue, no stack, no calls. If you see
; this shape, the function is as cheap as it can be.

; ---------------------------------------------------------
; int call_it(int x) { return helper(x) + 1; }
call_it:
        stp     x29, x30, [sp, #-16]!   ; PROLOGUE: save FP,LR
        mov     x29, sp
        bl      helper                  ; the call
        add     w0, w0, #1
        ldp     x29, x30, [sp], #16     ; EPILOGUE
        ret

; A NON-LEAF FUNCTION. The stp/ldp pair is the giveaway.
; ---------------------------------------------------------
; A function needing callee-saved registers:
big:
        stp     x29, x30, [sp, #-64]!
        mov     x29, sp
        stp     x19, x20, [sp, #16]     ; more saves ->
        stp     x21, x22, [sp, #32]     ; more simultaneous
        str     x23, [sp, #48]          ; live state
        ...
; THE PROLOGUE SIZE IS A PRESSURE GAUGE (chapter 09). Five
; saved registers and a 64-byte frame means the function is
; carrying a lot at once - a candidate for splitting.

A worked example

/* SOURCE: */
int count_set_bits(const uint32_t *data, int n)
{
        int count = 0;

        for (int i = 0; i < n; i++)
                count += __builtin_popcount(data[i]);

        return count;
}

; aarch64 gcc -O2 -mcpu=cortex-a72
count_set_bits:
        cmp     w1, #0
        b.le    .Lreturn_zero           ; guard: n <= 0
        mov     x2, #0                  ; i
        mov     w3, #0                  ; count
.Lloop:
        ldr     w4, [x0, x2, lsl #2]    ; data[i] - scaled
        fmov    s0, w4                  ; move to a SIMD reg
        cnt     v0.8b, v0.8b            ; popcount per BYTE
        addv    b0, v0.8b               ; sum the bytes
        fmov    w4, s0                  ; back to a GP reg
        add     x2, x2, #1
        add     w3, w3, w4
        cmp     x2, x1, sxtw
        b.lt    .Lloop
        mov     w0, w3
        ret
.Lreturn_zero:
        mov     w0, #0
        ret

/* WHAT THIS TELLS YOU:

   1. __builtin_popcount became `cnt` + `addv` on the SIMD
      unit, because AArch64 has no scalar population count.
      Four instructions including the register moves.

   2. THE fmov PAIR IS THE COST. Moving between general and
      SIMD registers has real latency (typically 3-5 cycles
      each way on an A72), and it happens EVERY iteration.

   3. IT DID NOT VECTORISE. Processing four words at once
      would amortise the moves, and it did not - because the
      reduction plus the per-element move confused the
      vectoriser.

   4. THE FIX, and this is the point of reading the output:
      restructure so the popcount stays in the vector domain: */

int count_set_bits_v2(const uint32_t *data, int n)
{
        uint32x4_t acc = vdupq_n_u32(0);
        int i;

        for (i = 0; i <= n - 4; i += 4) {
                uint8x16_t v = vreinterpretq_u8_u32(
                                    vld1q_u32(data + i));
                uint8x16_t c = vcntq_u8(v);
                acc = vaddq_u32(acc,
                        vpaddlq_u16(vpaddlq_u8(c)));
        }

        int count = vaddvq_u32(acc);

        for (; i < n; i++)              /* the tail */
                count += __builtin_popcount(data[i]);

        return count;
}
/* Four words per iteration, no domain crossing in the loop,
   one horizontal reduction at the end. Typically 3-4x faster.

   YOU WOULD NOT HAVE KNOWN TO DO THIS without reading the
   assembly. The source looked fine.                      */
What reading assembly is actually for

Not to hand-optimise — the compiler usually wins at that. It is to answer three questions no other tool answers: did the optimisation I expected happen?, what is this loop actually doing per iteration?, and is the cost where I think it is? Every performance investigation that gets past guesswork goes through this step.

The questions to ask

/* Work down this list on any hot function: */

1. IS IT A LEAF? No stp/ldp prologue means no calls, no
   frame. Good.

2. HOW BIG IS THE FRAME? `sub sp, sp, #N` or the stp
   immediate. Large frames mean spilling or large locals.

3. WHAT IS IN THE LOOP BODY? Count the instructions between
   the label and the backward branch. That is your per-
   iteration cost, roughly.

4. ANY STACK TRAFFIC IN THE LOOP? str/ldr to [sp, #n] means
   spilling. Reduce pressure (chapter 09).

5. ANY CALLS IN THE LOOP? `bl` prevents most optimisation
   across it and clobbers the caller-saved registers.

6. DID IT VECTORISE? Look for v registers and q loads. If not,
   ask why with -fopt-info-vec-missed (chapter 07).

7. ARE THE ADDRESSING MODES BEING USED? `[x0, x1, lsl #2]`
   good; a separate lsl then add means something prevented
   folding.

8. ARE THERE REDUNDANT MOVES? A `mov` between two registers
   that could have been the same one suggests a coalescing
   failure or a domain crossing.

9. ANY BARRIERS OR ATOMICS? dmb/ldaxr are expensive and often
   unintended - a stray volatile or an atomic where a plain
   variable would do.

10. IS THE HOT PATH THE FALL-THROUGH? A taken branch on the
    common path costs more than a not-taken one. PGO fixes
    this (chapter 06); __builtin_expect hints it.

11. WHAT DOES perf annotate SAY? The instruction with the
    samples on it is often a load - i.e. the problem is
    memory, not code (CA chapter 14), and no amount of
    instruction tuning will help.

Comparing two versions

# The most productive use of all: does my change help?

    gcc -O2 -S before.c -o before.s
    gcc -O2 -S after.c  -o after.s
    diff -u before.s after.s

# Or count instructions in the hot loop:
    objdump -d prog | awk '/\.Lloop/,/b\.lt/' | wc -l

# Or measure sizes:
    size -A before.o after.o
    nm --size-sort -S prog | tail

# AND THEN MEASURE THE ACTUAL PROGRAM, because instruction
# count is a proxy, not the answer:
    perf stat -r 10 ./prog
      cycles, instructions, IPC, branch-misses,
      cache-misses, stalled-cycles

# THE THREE NUMBERS THAT DIAGNOSE MOST THINGS:
#   IPC low + high cache-misses    -> memory bound
#   IPC low + high branch-misses   -> branchy code
#   IPC high but slow              -> genuinely doing too much
#                                     work; look at the
#                                     algorithm

# A CHANGE THAT REMOVES INSTRUCTIONS AND DOES NOT REMOVE TIME
# means the bottleneck is elsewhere. That is worth
# discovering before spending a day on it.

A practice routine

# Twenty minutes, and it teaches more than reading about it.

# 1. Open godbolt.org, set ARM64 gcc, -O2.

# 2. Type each of these and read the output:
    int f(int x) { return x * 2; }          ; lsl
    int f(int x) { return x / 2; }          ; the signed
                                            ; correction
    unsigned f(unsigned x) { return x / 2; } ; one lsr
    int f(int x) { return x % 7; }          ; magic-number
                                            ; division
    int f(int a, int b) { return a > b ? a : b; }  ; csel
    int f(int *p) { return p ? *p : 0; }
    int f(void) { int a[4] = {1,2,3,4};
                  return a[0]+a[1]+a[2]+a[3]; }    ; folded?

# 3. Then a loop, and check whether it vectorises:
    void f(float *a, float *b, int n) {
            for (int i = 0; i < n; i++) a[i] += b[i];
    }
    ; add `restrict` and watch the alias check disappear

# 4. Then something from your own codebase.

# THE HABIT TO BUILD: whenever you wonder "is this fast?" or
# "did that help?", spend two minutes looking rather than
# reasoning. It is almost always faster than the argument,
# and it is always more reliable.

Check yourself

  • Get from a source file to annotated assembly three different ways.
  • Recognise a leaf function, a non-leaf, and a register-pressured one at a glance.
  • Identify fifteen AArch64 patterns and say what each implies.
  • Work the eleven diagnostic questions on a real hot function.
  • Spot spilling, vectorisation and idiom recognition in output.
  • Diff two versions of a function and quantify the change.
  • Use perf stat to decide whether you are memory or compute bound.
  • Name seven traps that make assembly misleading, and how to avoid each.
  • Find a real optimisation opportunity in your own code by reading its output.
  • Explain what reading assembly is for, and what it is not for.
