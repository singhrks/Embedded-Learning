Security architecture

Security questions in a design round are testing whether you reason from a threat model or from a checklist. The strongest answers start by asking who the attacker is and what they gain — and are willing to conclude that a given measure is not worth its cost.

Start with the threat model

   FOUR QUESTIONS, and none of them is "which algorithm".

   1. WHAT ARE THE ASSETS?
        a signing key, a per-device identity, user data,
        the firmware itself (IP), the ability to actuate
        something physical, access to the network the
        device sits on.

   2. WHO IS THE ATTACKER, AND WHAT ACCESS DO THEY HAVE?
        remote, over the network
        local network / same LAN
        physical, casual (has the device, a laptop)
        physical, funded (decapping, side channels)
        INSIDER (a factory, a service technician)

   3. WHAT DO THEY GAIN?
        This is the question that sizes everything. If
        compromising one device gains one device's data,
        that is very different from a key that unlocks the
        whole fleet.

   4. WHAT IS THE COST OF THE DEFENCE, AND OF THE FAILURE?
        A secure element is a part, a bus and provisioning
        complexity. If the answer to (3) is "nothing much",
        say so and spend the money elsewhere.

   THE SCALING PROPERTY THAT MATTERS MOST:
     does compromising ONE device compromise ALL of them?
   A shared key across the fleet turns one extraction into
   a total loss. Per-device keys make an attack cost
   proportional to the number of devices attacked, which
   is usually the single most valuable design decision.

The properties, and what provides each

PropertyMeansProvided by
IntegrityThe data or code has not been alteredHash, MAC, or a signature
AuthenticityIt came from who it claimsMAC (shared key) or signature (public key)
ConfidentialityNobody else can read itEncryption — AES-GCM, ChaCha20-Poly1305
FreshnessIt is not a replay of an old valid messageNonce, counter, or timestamp
AvailabilityIt keeps workingWatchdogs, rate limits, resource bounds
 
THE ONE PEOPLE FORGET IS FRESHNESS. A signed message is
authentic forever - so an attacker who captures a valid
"unlock" command can replay it tomorrow. Every command
protocol needs a counter or nonce, and the receiver must
reject anything not strictly newer. On a device that loses
power, that counter must be persistent, which is a storage
design decision (chapter 08) and a good reason to reach
for FRAM.

USE AUTHENTICATED ENCRYPTION, NOT ENCRYPTION.
  AES-GCM or ChaCha20-Poly1305 give confidentiality AND
  integrity in one construction. Encrypting without
  authenticating (AES-CBC alone) allows an attacker to
  flip bits in the plaintext without detection, and
  "encrypt then MAC it yourself" is a construction people
  get wrong. Do not invent it.

AND NEVER WRITE YOUR OWN CRYPTO. Use the vendor's hardware
engine, mbedTLS, or libsodium. Constant-time
implementation matters more than the algorithm choice: a
comparison that returns early on the first differing byte
leaks the correct value one byte at a time.
The honest answer is sometimes "we do not need this"

A design round question about security is partly a test of proportionality. A sensor in a locked plant room reporting temperature over a wired network to a local server, in a fleet of 200, does not need a secure element, remote attestation or firmware encryption — and proposing all three signals that you are reciting rather than reasoning. What it probably does need is signed firmware updates (so the update path is not a backdoor) and no default passwords. Being able to say "here is where I would spend the security budget, and here is what I would not do and why" is a stronger answer than a longer list.

The attack surface of a typical device

   NETWORK          the obvious one. Every listening port,

                    A protocol parser is the most likely
                    place a remote attacker gets code

                    stored there is public unless
                    encrypted, and encrypted-at-rest needs
                    the key somewhere else.

   THE SUPPLY CHAIN a compromised build machine, an
                    unvetted third-party library, a
                    contract manufacturer with your signing
                    key.

   SIDE CHANNELS    timing, power analysis. Relevant only
                    against a funded physical attacker -
                    but that IS the threat model for
                    payment and access control.

   THE HUMAN PATH   default passwords, a support tool that
                    works on every unit, a recovery mode
                    with a universal code.

   IN PRACTICE, RANKED BY WHAT ACTUALLY GETS EXPLOITED:
     1. default or shared credentials
     2. an unsigned or unverified update path
     3. an unauthenticated network service
     4. a memory-safety bug in a parser
     5. debug interfaces left enabled
   Address those five before considering anything
   exotic.

Questions

How do you approach "make this device secure"?Mid

By refusing the question as stated and building a threat model instead. What are the assets — a key, user data, the ability to actuate something, network access? Who is the attacker, and what access do they have: remote, on the same network, physically holding the device, or an insider at the factory? What do they gain? And what does the defence cost against what the failure costs?

The property I would establish first is whether compromising one device compromises the fleet. Per-device keys instead of a shared key is usually the single highest-value decision, because it makes an attack cost proportional to the number of devices attacked.

Then I would rank by what actually gets exploited: default credentials, an unsigned update path, an unauthenticated network service, memory-safety bugs in parsers, and debug ports left enabled. Those five cover the overwhelming majority of real compromises, and I would want all of them addressed before discussing anything more exotic.

Listening forThreat model first, and prioritising by real-world exploitation rather than by sophistication.
Why is an unsigned firmware update path the worst vulnerability?Mid

Because it converts any other access into total, persistent control. An attacker who can push firmware owns the device completely and permanently — they can disable every other defence, exfiltrate every key, and survive a reboot and a factory reset. Every other vulnerability is bounded; this one is not.

It also scales: if the update path is remote and unsigned, one compromise of the update server or a man-in-the-middle position compromises the entire fleet at once.

The fix is signature verification anchored in an immutable root of trust — ROM plus fuses, not flash — with the private key in an HSM in a controlled build environment. And the failure path must refuse to boot, not log a warning and continue, or the check is decorative.

Worth adding: signing gives authenticity and integrity, not confidentiality. If firmware confidentiality matters (to protect IP or to hide a vulnerability until devices are patched), that is a separate decision with its own key management problem.

Listening for"Persistent and total" as the reason, and separating signing from encryption.
An attacker has physical access to the device. What can you actually protect?Senior

Less than people hope, and the honest framing is that physical access with sufficient funding beats almost any defence — so the goal is to raise cost above the value of the attack, and to contain the blast radius.

What you can reasonably protect: keys, if they live in a secure element or an MCU key store where they are usable but not readable, so extraction requires decapping and microprobing rather than a debugger. The fleet, if keys are per-device — then a successful physical attack yields one device.

What you largely cannot: firmware confidentiality against a determined attacker (readout protection on many MCUs has known bypasses via voltage glitching); data in external flash unless encrypted with a key held elsewhere; and anything against a funded lab.

What to do regardless: disable debug in production, enable readout protection, encrypt external storage, use per-device keys, and design so that compromise of one unit is detectable and revocable — the ability to revoke a device's certificate limits the damage more than trying to make extraction impossible.

Listening forRealism about what is achievable, and containment plus revocation as the strategy.
What is a replay attack, and how do you prevent it in an embedded protocol?Mid

An attacker records a legitimate, correctly-authenticated message and re-sends it later. A signature proves the message was genuine when created; it says nothing about when, so a captured "unlock" or "start motor" command remains valid forever.

Prevention needs freshness: a monotonic counter in every message, with the receiver rejecting anything not strictly greater than the last accepted value; or a challenge-response, where the receiver supplies a random nonce the sender must include; or a timestamp, which requires synchronised clocks and a tolerance window.

The embedded-specific difficulty: the counter must survive power loss, or a reboot resets it and every old message becomes valid again. That means persistent storage written on every message — which is exactly the frequently-written-small-value case that argues for FRAM rather than flash. Challenge-response avoids the persistence problem entirely, at the cost of a round trip, which is why it is often the better fit for a low-power device.

Listening forThe persistence problem for counters, and challenge-response as the way around it.
Should firmware be encrypted?Senior

It depends what you are protecting and it is often the wrong priority. Signing is essential — it prevents running attacker code. Encryption protects confidentiality, which buys you two things: making reverse engineering harder (protecting IP), and preventing an attacker from studying a patch to find the vulnerability it fixes before devices have updated.

The costs: the decryption key must be on every device, which means it either lives in a secure element or is derivable — and if it is the same key everywhere, one extraction publishes all firmware forever. It complicates the boot chain, the build process and debugging. And it provides no protection at all against someone who simply runs the device and observes it.

My default: sign always; encrypt only when there is a specific, articulated reason — a genuine IP concern with a real competitor, or a regulated environment that requires it. And if encrypting, use per-device or per-batch key derivation rather than one global key, so extraction is contained.

Listening forPrioritising signing over encryption, and the shared-key failure mode.
How do you handle the tension between locking a device down and being able to diagnose it?Senior

Replace the open debug port with an authenticated one. The device keeps a diagnostic capability, but entering it requires proving possession of a key — a challenge-response where the device issues a nonce and the service tool returns a signature over it, verified against a public key in the firmware.

That gives you: no permanently open door; no shared secret that leaks once and works forever; per-technician or per-tool credentials that can be revoked; and an audit trail if the device logs unlock attempts.

Supporting design: build the observability in so that most diagnosis does not need an unlock at all — persistent crash logs, error counters, reset causes, and a read-only status interface. If ninety percent of returns can be diagnosed from data the device volunteers, the unlock path is rarely needed.

And a practical detail: keep the physical test pads even when the port is disabled, because a factory or a repair centre with the right credentials still needs them, and adding them later is impossible.

Listening forAuthenticated unlock rather than a shared code, and reducing the need for it through observability.
What is the risk of a third-party library in embedded firmware?Mid

You inherit its vulnerabilities and its maintenance obligation, in code that runs with full privilege because most MCU firmware has no privilege separation at all. A memory-safety bug in a vendor's BLE stack or a JSON parser is a bug in your device with no sandbox around it.

Concretely, what I would want: an inventory of every third-party component and its version — a software bill of materials — so that when a CVE is published you can answer "are we affected?" in minutes rather than weeks. A process for tracking advisories. An assessment of which components parse untrusted input, because those are the ones that matter most. And where possible, isolation — running a parser in an unprivileged context with an MPU region, so a bug is contained.

The supply-chain dimension: pin versions and verify hashes, so a compromised upstream or a typosquatted package does not silently enter the build. And prefer components with an active maintainer and a security contact, because an unmaintained library is a liability with a ten-year field life.

Listening forThe SBOM as a concrete practice, and prioritising components that parse untrusted input.
Where does TrustZone-M fit in a security design?Senior

It provides isolation on a single chip: the silicon partitions memory, peripherals and interrupts into secure and non-secure worlds, with transitions only through defined entry points. So a bug in the application — a buffer overflow in a protocol parser, say — cannot read the key or bypass the crypto, because the non-secure world has no access to that memory at all.

What it is good for: keeping keys and crypto operations, secure boot verification, and a small trusted services layer away from a large, frequently-changed application. It also shrinks the code that must be carefully audited to a small secure-world binary.

Its limits: it is only as strong as your secure-world code — a bug there compromises everything, so the secure side must be small and reviewed. It does not resist physical attack: the key is still in the same die and voltage glitching or fault injection may bypass the boundary. And it requires designing the partition up front, which is architectural work, not a switch you flip.

Compared with a secure element: TrustZone-M is cheaper (a core feature, no extra part) and weaker against physical attack. If the threat is remote software attack, it is proportionate; if the attacker holds the device and extraction compromises more than that unit, a secure element is warranted.

Listening for"Only as strong as the secure-world code", and the comparison against a secure element on physical-attack resistance.
A device is compromised in the field. What should your design let you do?Senior

Detect, contain, and recover — and all three need designing in before deployment.

Detect: the device reports its firmware version and a measurement of its own state, so a server can notice a device running unexpected firmware. Anomalous behaviour — unusual traffic volume, unexpected endpoints, failed authentication attempts — should be visible in telemetry.

Contain: per-device credentials, so revoking one certificate removes exactly one device from the fleet. Server-side authorisation limits on what any single device can do, so a compromised sensor cannot issue commands. Network segmentation, so a compromised device cannot reach anything it should not.

Recover: an update path that a compromised device cannot block — which is difficult, because malicious firmware can refuse updates. The realistic answer is that recovery may require physical access, so the design should make that possible: a hardware-enforced recovery mode entered by a button combination or a pin, which the ROM honours regardless of what the application firmware wants.

And a key rotation plan, so a compromised signing key can be retired without replacing hardware.

Listening forThe recognition that a compromised device may refuse recovery, and a hardware-enforced path around it.
What security requirements might regulation impose, and how does that change the design?Senior

I would be careful not to overstate what I know about specific regimes, but the recurring themes across consumer IoT and industrial standards are consistent enough to design against: no universal default passwords; a documented vulnerability disclosure process; a stated minimum support period during which security updates are provided; secure storage of credentials; and secure, authenticated update mechanisms.

The design consequences are mostly architectural rather than cryptographic. A per-device credential established at manufacture rather than a shared default. An update mechanism that will still function years later, which means key management and build reproducibility. A software bill of materials so you can answer whether a published vulnerability affects your product. And logging sufficient to demonstrate compliance, because these regimes generally require evidence rather than assertion.

The practical point for a design round: these requirements mostly reinforce things that are good practice anyway, and the cost of retrofitting them is much higher than designing them in. If a product is destined for a regulated market, the specific standard should be identified early and read — I would not want to guess at clause-level detail.

Listening forNaming the recurring themes confidently while being appropriately careful about specific regulatory detail.
