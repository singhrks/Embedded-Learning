Stream ciphers

A pseudorandom keystream XORed with the plaintext — the one-time pad made practical. Fast, simple, constant-time by construction, and unforgiving of nonce reuse. ChaCha20 is the one to use.

The model

A stream cipher generates a keystream that is combined with the plaintext, which makes it structurally the one-time pad with a generated pad rather than a truly random one. Every property follows from that.

   key, nonce ---> KEYSTREAM GENERATOR ---> k0 k1 k2 k3 ...
                                              |
   plaintext  p0 p1 p2 p3 ...  ---------- XOR |
                                              v
   ciphertext c0 c1 c2 c3 ...

   ENCRYPTION AND DECRYPTION ARE THE SAME OPERATION - one
   implementation serves both, which halves the code on a
   constrained device.

   PROPERTIES INHERITED FROM THE ONE-TIME PAD (chapter 03):
     + no padding - encrypt any length
     + no block alignment
     + can start encrypting before the length is known
     + a bit error in transit corrupts exactly one bit
     - NONCE REUSE IS CATASTROPHIC: c1 XOR c2 = p1 XOR p2
     - NO INTEGRITY: flipping a ciphertext bit flips the
       plaintext bit

   AND THE TWO FAMILIES:

     SYNCHRONOUS       the keystream depends only on the key
                       and nonce, not on the data. ChaCha20,
                       RC4, AES-CTR.
     SELF-SYNCHRONISING the keystream depends on previous
                       ciphertext. CFB mode. Recovers from
                       insertions and deletions, at the cost
                       of error propagation. Rarely used.

   NOTE THAT CTR MODE (chapter 05) IS A STREAM CIPHER built
   from a block cipher. The distinction between "stream
   cipher" and "block cipher in a streaming mode" is about
   construction, not about the properties you get.

ChaCha20

The modern default, and the one to reach for when hardware AES is unavailable. It is fast in software on almost anything, which is why it appears throughout mobile and embedded systems.

/* Daniel Bernstein, 2008. A refinement of Salsa20, and the
   modern default for software encryption.                */

/* THE STATE: 16 words of 32 bits = 512 bits, 4x4 */

        c c c c          c = constants "expand 32-byte k"
        k k k k          k = the 256-bit key
        k k k k
        b n n n          b = 32-bit block counter
                         n = 96-bit nonce

/* THE QUARTER-ROUND, the entire nonlinear core: */
    #define QR(a, b, c, d)                     \
        a += b;  d ^= a;  d = rotl32(d, 16);   \
        c += d;  b ^= c;  b = rotl32(b, 12);   \
        a += b;  d ^= a;  d = rotl32(d,  8);   \
        c += d;  b ^= c;  b = rotl32(b,  7);

/* ADD, ROTATE, XOR - an "ARX" cipher. No S-boxes, no tables,
   NO DATA-DEPENDENT MEMORY ACCESS, and no data-dependent
   branches. CONSTANT TIME BY CONSTRUCTION, on every
   platform, with no special effort (chapter 19).

/* THE BLOCK FUNCTION: 20 rounds, alternating column and
   diagonal quarter-rounds, then add the original state. */

    void chacha20_block(const uint32_t in[16], uint32_t out[16])
    {
        uint32_t x[16];
        memcpy(x, in, sizeof x);

        for (int i = 0; i < 10; i++) {      /* 10 double
                                               rounds = 20  */
            /* column rounds */
            QR(x[0], x[4], x[ 8], x[12]);
            QR(x[1], x[5], x[ 9], x[13]);
            QR(x[2], x[6], x[10], x[14]);
            QR(x[3], x[7], x[11], x[15]);
            /* diagonal rounds */
            QR(x[0], x[5], x[10], x[15]);
            QR(x[1], x[6], x[11], x[12]);
            QR(x[2], x[7], x[ 8], x[13]);
            QR(x[3], x[4], x[ 9], x[14]);
        }

        for (int i = 0; i < 16; i++)
            out[i] = x[i] + in[i];      /* the feed-forward
                                           makes it
                                           non-invertible  */
    }

/* THE FINAL ADDITION MATTERS: without it the block function
   would be an invertible permutation and an attacker could
   run it backwards. Adding the input makes it one-way.

/* WHY IT IS THE DEFAULT NOW:
     · 3-4x faster than software AES on a CPU without AES-NI
     · constant time with no effort - which software AES
       requires bitslicing to achieve (chapter 04)
     · a 20-round design with a large margin; the best attack
       reaches 7 rounds
     · small: a few hundred bytes of code, 64 bytes of state
     · vectorises well - SSE, AVX2 and NEON implementations
       process several blocks at once
     · no patents, a public-domain reference implementation

/* XCHACHA20: extends the nonce to 192 bits by hashing the
   key and the first 128 nonce bits through the same
   permutation (HChaCha20) to derive a subkey. A 192-bit
   nonce is large enough that RANDOM nonces never collide -
   removing the nonce management problem entirely
   (chapter 05). Prefer XChaCha20-Poly1305 wherever it is
   available.                                              */
ChaCha20 or AES?

Hardware AES available (any modern Arm application core, any x86): AES-GCM is faster — around 1 cycle/byte versus 3-4. No hardware AES (most microcontrollers, older cores): ChaCha20-Poly1305 wins on speed, code size and side-channel resistance simultaneously. TLS 1.3 negotiates between exactly these two for exactly this reason, and mobile clients without AES acceleration end up on ChaCha20.

RC4 — the cautionary tale

Once ubiquitous and now thoroughly broken. It is worth knowing about because it still appears in legacy systems and because the way it failed is instructive.

/* Designed 1987, leaked 1994, ubiquitous for two decades,
   comprehensively broken. Worth understanding because every
   one of its failures illustrates a general principle. */

    /* the key schedule */
    for (i = 0; i < 256; i++) S[i] = i;
    for (i = j = 0; i < 256; i++) {
        j = (j + S[i] + key[i % keylen]) & 0xFF;
        swap(S[i], S[j]);
    }
    /* the keystream */
    i = j = 0;
    while (n--) {
        i = (i + 1) & 0xFF;
        j = (j + S[i]) & 0xFF;
        swap(S[i], S[j]);
        *out++ = S[(S[i] + S[j]) & 0xFF];
    }

/* Beautifully small - which is why it spread. And:

   1. THE SECOND OUTPUT BYTE is 0 with probability 2/256
      instead of 1/256. There are biases throughout the first
      few thousand bytes.
      -> the RC4 NOMORE and Bar-Mitzvah attacks recovered
         plaintext from TLS and WPA-TKIP.

   2. THE KEY SCHEDULE IS WEAK. Related keys - a per-message
      IV concatenated with a fixed key - leak the key.
      -> THIS IS WEP. Concatenating a 24-bit IV with the
         shared key produced related keys, and WEP was broken
         to the point of key recovery in minutes.

   3. IT USES A KEY-DEPENDENT LOOKUP TABLE, so software
      implementations have a cache-timing side channel
      (chapter 19).

   PROHIBITED in TLS since RFC 7465. Removed from every
   modern library.

/* THE GENERAL LESSONS:
     · a cipher can be "unbroken" for years and then fall to
       accumulated statistical work
     · KEY SCHEDULES MATTER as much as the round function
     · concatenating an IV with a key is not a nonce
       mechanism - use a construction designed for it
     · small and elegant is not the same as secure         */

The others

A few other stream ciphers appear in specific niches, particularly where hardware cost is the dominant constraint. Several are broken, which matters if you meet them in existing designs.

   outputs have held.                                     */

Using one correctly

Stream ciphers have one absolutely rigid rule about key and nonce reuse, and violating it is not a weakening but a complete break. This is how to use them without doing that.

/* --- THE ONLY CORRECT WAY: use the AEAD, not the raw
       cipher --- */

    /* libsodium, and this is the recommendation */
    #include <sodium.h>

    unsigned char nonce[crypto_aead_xchacha20poly1305_ietf_NPUBBYTES];
    randombytes_buf(nonce, sizeof nonce);   /* 192 bits -
                                               random is safe */

    crypto_aead_xchacha20poly1305_ietf_encrypt(
            ciphertext, &ct_len,
            plaintext, pt_len,
            aad, aad_len,
            NULL, nonce, key);

    /* decryption FAILS CLOSED if the tag does not verify */
    if (crypto_aead_xchacha20poly1305_ietf_decrypt(
            decrypted, &pt_len, NULL,
            ciphertext, ct_len, aad, aad_len,
            nonce, key) != 0) {
            /* FORGED OR CORRUPTED - discard everything */
            return -1;
    }

/* --- THE RAW CIPHER, only inside a construction you are
       building deliberately --- */
    crypto_stream_chacha20_ietf_xor(out, in, len, nonce, key);
/* No authentication. If you call this directly you are
   responsible for the MAC, and you should probably not be.

/* --- THE NONCE RULES, restated because they are what
       fails --- */
    ChaCha20 (IETF)   96-bit nonce, 32-bit counter
                      -> 256 GB max per (key, nonce)
                      -> random nonces collide at ~2^32
                         messages: USE A COUNTER
    XChaCha20         192-bit nonce
                      -> RANDOM NONCES ARE SAFE, always.
                         This is why it is preferable.

/* --- SEEKING WITHIN A STREAM, which stream ciphers make

/* --- ON A MICROCONTROLLER --- */
    /* Monocypher: ~2 KB of code for the whole AEAD */
    crypto_aead_lock(ciphertext, mac, key, nonce,
                     aad, aad_len, plaintext, pt_len);

    if (crypto_aead_unlock(plaintext, mac, key, nonce,

   size.                                                   */

How it shows up

SymptomCause
