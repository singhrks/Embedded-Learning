Function pointers and dispatch tables

Function pointers are how C does polymorphism, callbacks, plugins and state machines. Every driver interface in Linux and Windows is a struct of function pointers. Once the declaration syntax stops being frightening, the patterns are straightforward — and they are everywhere.

Declaration syntax

Function pointer declarations are famously unreadable, and the reason is that C's declarator syntax nests rather than reads left to right. There is a mechanical way to decode them, and a way to avoid ever having to.

   int  f(int);            a function taking int, returning int
   int (*p)(int);          a POINTER to such a function
   int *g(int);            a function returning int*  — different!

The parentheses around *p are mandatory, because () binds tighter
than *. Without them you get "function returning a pointer".

   int (*fns[4])(int);     an array of 4 such pointers
   int (*(*p)[4])(int);    a pointer to such an array
   int (*f(void))(int);    a function returning a function pointer

At the third line, stop and use a typedef. Everyone does.
/* Two ways to name the type. Learn to read both. */
typedef int  handler_t(int);       /* the FUNCTION type      */
typedef int (*handler_ptr_t)(int); /* the POINTER type       */

handler_ptr_t p = my_func;
handler_t    *q = my_func;         /* equivalent, and arguably clearer */

/* Modern style prefers naming the function type and adding * at use,
   because it keeps the pointer-ness visible:                       */
typedef int compare_fn(const void *, const void *);
void sort(void *base, size_t n, size_t sz, compare_fn *cmp);

Taking and calling

With the syntax handled, using them is straightforward — and one detail surprises people: several different-looking ways of taking and calling a function pointer are all exactly equivalent.

int add(int a, int b) { return a + b; }

int (*op)(int, int) = add;      /* the & is optional...   */
int (*op)(int, int) = &add;     /* ...both are identical  */

int r = op(2, 3);               /* call: the * is optional */
int r = (*op)(2, 3);            /* ...both are identical   */

/* A function name in an expression decays to a pointer, exactly
   like an array name (chapter 05). That is why both spellings
   work. Pick one and be consistent; `op(2,3)` is more common.  */

/* Comparison and null are meaningful */
if (op == add)  ...
if (op != NULL) op(1, 2);

/* But arithmetic is NOT. You cannot do op + 1, and sizeof on a
   function type is undefined.                                  */
Function pointers are not object pointers

The standard guarantees conversion between void * and object pointers only. Converting a function pointer through void * is not guaranteed by ISO C — on architectures where code addresses have a different size or format it genuinely breaks. POSIX requires it to work so that dlsym() can exist, which is why that API is a documented wart. Keep function pointers in function-pointer types, and use a union or a POSIX-blessed cast if you truly must.

Callbacks

The callback is the single most common use, and the part that needs care is not the pointer but the context: a callback with nowhere to carry caller state forces the caller into global variables.

/* The standard library's own example */
int cmp_int(const void *a, const void *b)
{
        int x = *(const int *)a, y = *(const int *)b;
        return (x > y) - (x < y);       /* avoids overflow of x - y */
}
qsort(arr, n, sizeof arr[0], cmp_int);

/* THE design rule for callback APIs: always carry a user context.
   Without it, callers are forced into global state.            */

/* BAD — no context */
void for_each(int *a, size_t n, void (*fn)(int));

/* GOOD — an opaque pointer threaded through */
void for_each(int *a, size_t n, void (*fn)(int, void *), void *ctx)
{
        for (size_t i = 0; i < n; i++)
                fn(a[i], ctx);
}

struct acc { long total; };
static void add_to(int v, void *ctx) { ((struct acc *)ctx)->total += v; }

struct acc a = {0};
for_each(arr, n, add_to, &a);

/* This is why qsort_r/qsort_s exist: plain qsort has no context
   parameter, so comparators that need extra state must use a
   global — which is not reentrant or thread safe.             */

Dispatch tables: polymorphism in C

A struct full of function pointers is how C does polymorphism, and it is exactly what C++ generates for you invisibly. Seeing it written out explicitly demystifies both.

/* A struct of function pointers IS a vtable. This is exactly how
   C++ virtual functions are implemented, written out by hand.  */

struct file_ops {
        int     (*open)(struct file *);
        ssize_t (*read)(struct file *, void *, size_t);
        ssize_t (*write)(struct file *, const void *, size_t);
        int     (*close)(struct file *);
};

struct file {
        const struct file_ops *ops;     /* the vtable pointer */
        void *private_data;             /* the "derived" state */
};

/* Each implementation supplies its own table. Designated
   initialisers mean unimplemented operations are NULL.       */
static const struct file_ops disk_ops = {
        .open  = disk_open,
        .read  = disk_read,
        .write = disk_write,
        .close = disk_close,
};
static const struct file_ops socket_ops = {
        .open  = sock_open,
        .read  = sock_read,
        /* .write and .close are NULL */
};

/* Generic code dispatches without knowing the type: */
ssize_t file_read(struct file *f, void *buf, size_t n)
{
        if (!f->ops->read)
                return -ENOSYS;         /* ALWAYS check for NULL */
        return f->ops->read(f, buf, n);
}

/* Note `const struct file_ops *` — the table lives in .rodata,
   so it cannot be corrupted by a stray write, and it is shared
   by every instance rather than copied per object.           */
Why this is the shape of every OS driver interface

   struct file                struct file_ops (in .rodata)
   +----------------+         +---------------------------+
   | ops  ----------|-------> | open   -> disk_open        |
   | private_data   |         | read   -> disk_read        |
   +----------------+         | write  -> disk_write       |
                              | close  -> disk_close       |
   struct file                +---------------------------+
   +----------------+
   | ops  ----------|-------> (socket_ops)
   | private_data   |
   +----------------+

  One generic VFS layer, many implementations, no switch statement,
  and new implementations can be added without touching the core.

  Linux: struct file_operations, struct net_device_ops,
         struct platform_driver
  Windows: the WDF EvtIo* callbacks and the WDM MajorFunction array
  Both are this pattern.

Jump tables and state machines

Replacing a long switch with an array of function pointers can be clearer and faster — or slower and harder to read. Which one it is depends on facts worth knowing before making the change.

/* Replacing a long switch with a table — O(1), and data-driven */

typedef void (*cmd_fn)(const char *args);

struct command {
        const char *name;
        cmd_fn      handler;
        const char *help;
};

static const struct command commands[] = {
        { "read",  cmd_read,  "read a register"  },
        { "write", cmd_write, "write a register" },
        { "dump",  cmd_dump,  "dump memory"      },
};

static int dispatch(const char *name, const char *args)
{
        for (size_t i = 0; i < ARRAY_SIZE(commands); i++)
                if (strcmp(commands[i].name, name) == 0) {
                        commands[i].handler(args);
                        return 0;
                }
        return -EINVAL;
}
/* Adding a command is one table row. The help text, the parser and
   the dispatcher all stay unchanged — this is the main practical
   benefit over a switch.                                        */
/* A state machine as a table of transitions */
typedef enum { S_IDLE, S_RUNNING, S_ERROR, S_COUNT } state_t;
typedef enum { E_START, E_STOP, E_FAULT, E_COUNT } event_t;

typedef state_t (*transition_fn)(void *ctx);

static const transition_fn table[S_COUNT][E_COUNT] = {
        [S_IDLE]    = { [E_START] = on_start,  [E_FAULT] = on_fault },
        [S_RUNNING] = { [E_STOP]  = on_stop,   [E_FAULT] = on_fault },
        [S_ERROR]   = { [E_STOP]  = on_reset },
};

state_t step(state_t s, event_t e, void *ctx)
{
        transition_fn fn = table[s][e];
        return fn ? fn(ctx) : s;        /* NULL = ignore the event */
}
/* The table IS the specification. It can be reviewed against a
   state diagram directly, which nested switches cannot.        */

Weak symbols and optional hooks

A function pointer that can be changed at run time is how tracing, plugins and test doubles are built in C — and, for the same reason, it is a target for attackers, which is why hardened systems make such tables read-only.

/* Firmware pattern: provide a default that the application may
   override, with no function pointer and no runtime cost.     */

__attribute__((weak)) void board_init(void) { /* default: nothing */ }

int main(void)
{
        board_init();          /* calls the app's version if it
                                  defined one, else the default   */
}

/* The linker resolves this at link time: a strong definition
   anywhere replaces the weak one. Used heavily in CMSIS and
   vendor SDKs for interrupt vectors:                         */
__attribute__((weak)) void TIM1_IRQHandler(void) { default_handler(); }

Safety and security

Function pointers are an attack surface

An attacker who can overwrite a function pointer controls the program counter. This is why:

  • Keep vtables in .rodata — declare them const. A read-only page cannot be corrupted by a heap or stack overflow.
  • Always NULL-check before calling through a pointer. A partially initialised struct is a jump to address 0.
  • Validate indices into dispatch tables before use, and mask rather than branch in security-sensitive paths (CA ch. 12).
  • Modern mitigations exist: ARM Pointer Authentication (PACIASP/ AUTIASP) signs return addresses and can sign function pointers; Branch Target Identification (BTI) requires indirect branch targets to be marked; Control Flow Integrity (-fsanitize=cfi) checks that the target has the right type.
/* Build with the hardening on, on aarch64: */
gcc -mbranch-protection=standard    /* PAC + BTI */
clang -fsanitize=cfi -flto -fvisibility=hidden

/* Defensive dispatch */
static int call_op(struct file *f, int op_index)
{
        if (op_index < 0 || (size_t)op_index >= ARRAY_SIZE(f->ops->table))
                return -EINVAL;                    /* bounds check    */
        cmd_fn fn = f->ops->table[op_index];
        if (!fn)
                return -ENOSYS;                    /* NULL check      */
        return fn(f);
}

The real cost is usually not the branch — it is that an indirect call is an optimisation barrier. The compiler cannot inline it, cannot propagate constants through it, and must assume it clobbers memory. In a hot inner loop, hoisting the dispatch outside the loop, or specialising the loop per implementation, is often a large win.

/* dispatch per element — the pointer blocks all optimisation */
for (size_t i = 0; i < n; i++)
        ops->process(&a[i]);

/* dispatch once — now each branch can be inlined and vectorised */
if (ops->process == fast_process)
        for (size_t i = 0; i < n; i++) fast_process(&a[i]);
else
        for (size_t i = 0; i < n; i++) ops->process(&a[i]);
