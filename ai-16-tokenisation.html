Tokenisation

Text becomes integers before a model sees any of it. This unglamorous preprocessing step is the origin of a surprising number of the strange behaviours people attribute to the model itself.

The problem

Before a model can process text at all, the text must become integers, and every way of doing that involves a trade nobody is happy with. Understanding the trade explains a surprising amount of model behaviour.

   A NEURAL NETWORK CONSUMES NUMBERS. Text is a string. Some
   mapping is required, and the choice has consequences.

   OPTION 1 - CHARACTERS
     "hello" -> [104, 101, 108, 108, 111]
     + tiny vocabulary (~256 with bytes)
     + NO out-of-vocabulary words, ever
     - LONG sequences: attention is quadratic in length
       (chapter 19), so 5x longer input is 25x the attention
       cost
     - the model must learn spelling before it learns
       meaning

   OPTION 2 - WORDS
     "hello world" -> [4821, 923]
     + short sequences, semantically meaningful units
     - HUGE vocabulary: 500k+ for English, and the output
       layer is (d_model x vocab) - the largest matrix in a
       small model
     - out-of-vocabulary words become <UNK> and their
       information is DESTROYED
     - "run", "runs", "running", "ran" are four unrelated
       entries
     - and it is not even well-defined for Chinese, Japanese
       or Thai, which do not delimit words with spaces

   OPTION 3 - SUBWORDS. WHAT EVERYONE USES.
     "tokenisation" -> ["token", "isation"]
     "unhappiness"  -> ["un", "happiness"]
     "GPT-4"        -> ["G", "PT", "-", "4"]

     · common words stay whole
     · rare words split into meaningful pieces
     · NO out-of-vocabulary case at all - anything
       decomposes to bytes in the worst case
     · vocabulary of 30k-200k: a workable output layer
     · morphology is partially captured for free

   THE PRACTICAL RATIO FOR ENGLISH: about 4 CHARACTERS PER
   TOKEN, or roughly 0.75 words per token. 1,000 tokens is
   about 750 words. This is the arithmetic behind every
   context-length and pricing calculation you will do.

Byte-pair encoding

Byte-pair encoding is the algorithm behind nearly every modern tokeniser, and it is simple enough to implement in an afternoon. The training procedure is the part worth following closely.

"""BPE, the dominant algorithm. Originally a 1994
   compression method, repurposed for NLP in 2015.

   TRAINING: start from individual bytes, repeatedly merge
   the most frequent adjacent pair, until the vocabulary
   reaches the target size."""

from collections import Counter

def train_bpe(corpus_words, num_merges):
    # start: every word as a tuple of bytes/characters
    vocab = {tuple(w): c for w, c in
             Counter(corpus_words).items()}
    merges = []

    for _ in range(num_merges):
        # 1. COUNT ADJACENT PAIRS, weighted by word frequency
        pairs = Counter()
        for word, freq in vocab.items():
            for i in range(len(word) - 1):
                pairs[(word[i], word[i+1])] += freq
        if not pairs:
            break

        # 2. MERGE THE MOST FREQUENT PAIR
        best = max(pairs, key=pairs.get)
        merges.append(best)

        new_vocab = {}
        for word, freq in vocab.items():
            w, i = [], 0
            while i < len(word):
                if (i < len(word) - 1 and
                        (word[i], word[i+1]) == best):
                    w.append(word[i] + word[i+1])
                    i += 2
                else:
                    w.append(word[i])
                    i += 1
            new_vocab[tuple(w)] = freq
        vocab = new_vocab

    return merges

def encode(word, merges):
    """Apply the learned merges IN THE ORDER THEY WERE
       LEARNED. That ordering is the model - it is why the
       merge list, not just the vocabulary, must be
       shipped."""
    tokens = list(word)
    for a, b in merges:
        i = 0
        while i < len(tokens) - 1:
            if tokens[i] == a and tokens[i+1] == b:
                tokens[i:i+2] = [a + b]
            else:
                i += 1
    return tokens

# WORKED, on a corpus of "low low lower newest widest":
#   merge 1: ('e','s') -> 'es'      (in newest, widest)
#   merge 2: ('es','t') -> 'est'
#   merge 3: ('l','o') -> 'lo'
#   ...
# Frequent substrings become single tokens; rare ones stay
# split.

/* --- THE VARIANTS YOU WILL MEET --- */
    BPE            merge by FREQUENCY. GPT-2/3/4, Llama,
                   most models.
    BYTE-LEVEL BPE Operate on RAW BYTES, not Unicode
                   characters. 256 base tokens covers
                   EVERYTHING - every language, every emoji,
                   every binary blob - with no unknown
                   token possible. GPT-2 onwards.
    WORDPIECE      merge by LIKELIHOOD GAIN rather than
                   raw frequency. BERT. Marks continuations
                   with "##".
    UNIGRAM / SentencePiece
                   start LARGE and prune tokens that cost
                   least likelihood. Handles languages
                   without spaces natively, and is
                   REVERSIBLE - it encodes whitespace as a
                   visible marker, so decode(encode(x)) == x
                   exactly. T5, Llama, Gemma.

/* --- USING ONE --- */
from tokenizers import Tokenizer
tok = Tokenizer.from_pretrained("gpt2")

ids = tok.encode("Hello, world!").ids   # [15496, 11, 995, 0]
tok.decode(ids)                          # "Hello, world!"

/* NOTE THE FOUR TOKENS FOR THREE WORDS AND TWO PUNCTUATION
   MARKS. And note that " world" (with the leading space)
   is a DIFFERENT TOKEN from "world". The space belongs to
   the following token in GPT-style tokenisers, which is the
   source of a whole family of surprises below.          */

Why models behave strangely

Several famous model failures — arithmetic, spelling, counting letters — are not reasoning failures at all. They are tokenisation artefacts, and they become obvious once you can see the token boundaries.

/* A large fraction of "the model is bad at X" is really
   "the tokeniser makes X hard", and knowing which is which
   saves a great deal of confusion.                       */

/* --- 1. COUNTING LETTERS --- */
    "How many r's in strawberry?"
    The model sees ["str", "aw", "berry"]. IT NEVER SEES
    INDIVIDUAL LETTERS. Asking it to count characters is
    like asking you to count the pixels in a word you read.
    It can sometimes do it by memorised association; it has
    no direct access.

/* --- 2. ARITHMETIC --- */
    Numbers tokenise inconsistently:
        "1234"  might be one token, or ["12","34"],
                or ["1","234"]
        "1235"  might split completely differently
    Digit-position alignment - which is what column
    arithmetic requires - is destroyed. THE FIX, used by
    several recent models: force digits to tokenise
    individually, or in fixed groups of three. It measurably
    improves arithmetic, which is strong evidence the
    tokeniser was the problem.

/* --- 3. REVERSING STRINGS, RHYMING, WORDPLAY --- */
    All require character-level access. Same cause.

/* --- 4. WHITESPACE SENSITIVITY --- */
    "hello" and " hello" are different tokens with different
    embeddings. A prompt ending in a trailing space puts the
    model in a strange state, because it now expects a
    continuation of a token rather than a new word. THIS IS
    A REAL SOURCE OF DEGRADED OUTPUT and it is invisible
    when you read the prompt.

/* --- 5. NON-ENGLISH TEXT COSTS MORE --- */
    Tokenisers are trained on corpora dominated by English.
        English   ~4 characters per token
        Chinese   ~1-1.5 characters per token
        Thai, Burmese, many African languages: sometimes
        1 token PER BYTE
    So the same document costs 2-5x more tokens, fits in
    less context, and costs more money. This is a genuine
    equity issue in deployed systems, not a curiosity.

/* --- 6. GLITCH TOKENS --- */
    " SolidGoldMagikarp" and a handful of others appeared in
    GPT-2's tokeniser training data (scraped from Reddit
    usernames) but were almost absent from the model's
    training data. Their embeddings were never meaningfully
    trained, so they sit at essentially random positions in
    embedding space, and prompting with them produced
    bizarre, evasive or nonsensical output.

    THE GENERAL LESSON: A TOKEN THAT EXISTS IN THE VOCABULARY
    BUT NOT IN THE TRAINING DATA IS AN UNTRAINED PARAMETER
    SITTING IN YOUR MODEL. Tokeniser and model must be
    trained on consistent data.

/* --- 7. CODE --- */
    Indentation matters in Python, and a tokeniser trained
    mostly on prose splits whitespace poorly. Code-focused
    models add explicit tokens for runs of 2, 4, 8, 16
    spaces - a small change with a large effect on code
    quality and on token count.                          */
The rule

The tokeniser and the model are a matched pair. Changing the tokeniser invalidates every embedding and requires retraining from scratch. Vocabulary size, digit handling and whitespace treatment are architectural decisions made before pretraining and effectively permanent afterwards — which is why tokeniser choices from 2019 are still shaping model behaviour today.

Practical matters

The details that matter when you are working with a real tokeniser rather than reading about one, including the ones that cost money.

/* --- SPECIAL TOKENS --- */
    <|endoftext|>    document boundary; also used as
                     padding and as BOS in GPT-2
    [CLS] [SEP]      BERT's classification and separator
    <|im_start|>
    <|im_end|>       chat message boundaries in
                     instruction-tuned models
    <PAD>            padding, and it MUST BE MASKED OUT of
                     both attention and loss
    <|fim_prefix|>   fill-in-the-middle, for code models

    THE CHAT TEMPLATE MATTERS. An instruction-tuned model
    was fine-tuned on a specific format, and using a
    different one degrades it substantially:

        tok.apply_chat_template(messages, tokenize=False)

    USE THE LIBRARY FUNCTION rather than assembling the
    string yourself - this is a common and silent source of
    poor results.

/* --- VOCABULARY SIZE: THE TRADE-OFF --- */
    LARGER vocabulary
      + shorter sequences -> cheaper attention (quadratic!)
      + more semantics per token
      - a bigger embedding table and output projection
      - each token is seen less often during training
      - and a slower softmax over the vocabulary

    TYPICAL: 32k (Llama 2), 50k (GPT-2), 100k (GPT-4),
    128k-256k (Llama 3, Gemma). THE TREND IS UPWARD,
    because attention cost dominates and multilingual
    coverage matters.

/* --- COUNTING TOKENS, which you will do constantly --- */
    ids = tok.encode(text).ids
    n = len(ids)

    RULES OF THUMB FOR ENGLISH:
        1 token   ~= 4 characters ~= 0.75 words
        1,000 tokens ~= 750 words ~= 1.5 pages
    ALWAYS MEASURE for other languages and for code.

/* --- BATCHING AND PADDING --- */
    Sequences in a batch must be the same length.
      PAD to the longest in the batch (dynamic padding),
        not to the model maximum - padding to 2048 when your
        longest sample is 100 tokens wastes 95% of the
        compute
      MASK the padding in attention
      IGNORE it in the loss:
          F.cross_entropy(logits, targets,
                          ignore_index=PAD_ID)
      SORT BY LENGTH into buckets to minimise padding
      AND FOR PRETRAINING, don't pad at all: concatenate
        documents with a separator and slice into fixed
        blocks. Zero waste, and it is what every large
        pretraining run does.

/* --- FOR EMBEDDED DEPLOYMENT (chapter 27) --- */
    The tokeniser must ship with the model and run on the
    device. A 128k-entry vocabulary with its merge list is
    a few megabytes of data and needs a real string
    implementation.

    ON A CONSTRAINED DEVICE, CONSIDER:
      · a SMALL DOMAIN-SPECIFIC VOCABULARY trained on your
        actual data - 1-4k tokens is often plenty for a
        command or intent model, and shrinks the embedding
        table dramatically
      · CHARACTER-LEVEL, if sequences are short. No
        vocabulary file at all.
      · doing tokenisation on the HOST and sending IDs, if
        the device is not the entry point.
    The output projection is proportional to vocabulary
    size, so on an MCU this is frequently the single
    largest layer in the model.                          */
