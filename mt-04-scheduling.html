How the scheduler decides who runs

You do not control when your threads run. Understanding the policy that does — and the four or five knobs you are actually allowed to turn — is the difference between tuning a system and superstitiously adding sleep(0) until the symptom moves.

The state machine

A thread is not simply running or not running. The distinctions within "not running" are exactly what you need when diagnosing something that appears stuck, because each state implies a different cause.

                    +-------------+
        create ---> |   READY     | <--------------+
                    +------+------+                |
                           | scheduler picks it    | timeslice
                           v                       | expires, or
                    +-------------+                | preempted by
                    |   RUNNING   | ---------------+ a higher
                    +--+-------+--+                  priority
                       |       |
        blocks on I/O, |       | exits
        a mutex, a     |       v
        condvar, sleep |    +--------+
                       |    | DEAD   |
                       v    +--------+
                +-------------+
                |   BLOCKED   |
                +------+------+
                       | the thing it waited for happened
                       +--------------------------> READY

   THE ONLY TRANSITION YOU CONTROL is RUNNING -> BLOCKED, and
   you control it by calling something that blocks. Everything
   else is the scheduler's decision.

   A thread in BLOCKED costs nothing. A thread spinning in
   READY/RUNNING costs a whole core. That is the entire
   argument for blocking primitives over spinning ones in
   general-purpose code (chapter 6).

Policies you can actually choose

Most threads use the default policy and should. The alternatives exist for work with genuine timing requirements, and reaching for them without that requirement usually makes the whole system worse.

PolicyBehaviourUse it when
SCHED_OTHER / CFSFair-share by weight. Every runnable thread makes progress; nice adjusts the shareDefault. Almost always right
SCHED_FIFOReal-time. Runs until it blocks or yields. A higher-priority FIFO thread preempts instantly and never gives the CPU back on its ownHard deadlines, and only with a bounded work loop
SCHED_RRFIFO plus a timeslice among equal prioritiesSeveral equal-priority real-time threads
SCHED_DEADLINEYou declare (runtime, deadline, period); the kernel admits you or refusesPeriodic real-time work where you can state the budget
SCHED_IDLERuns only when nothing else wants the CPUBackground scrubbing, prefetch
SCHED_BATCHCFS, but assumed non-interactive; fewer preemptionsLong compute jobs where throughput beats latency
 
/* Setting a real-time policy. Needs CAP_SYS_NICE or root, and
   a rlimit (RLIMIT_RTPRIO) that allows it.                   */

#include <pthread.h>
#include <sched.h>

int make_realtime(pthread_t t, int prio)
{
        struct sched_param p = { .sched_priority = prio };
        /* prio 1..99 for FIFO/RR; higher number = higher
           priority, the opposite of `nice`.                  */
        return pthread_setschedparam(t, SCHED_FIFO, &p);
}

/* THE FOOTGUN, and it is a big one:

   A SCHED_FIFO thread that busy-loops on a single-core system
   locks the machine. Nothing else - not your shell, not the
   watchdog - will ever run. Linux ships a safety valve:

     /proc/sys/kernel/sched_rt_runtime_us  = 950000
     /proc/sys/kernel/sched_rt_period_us   = 1000000

   which caps all real-time threads at 95% of each second so
   you can still get a shell. Turn that off (set runtime to -1)
   only if you are certain, and keep a serial console.

   THE RULE FOR SCHED_FIFO: the loop body must be bounded and
   must end in a blocking call. If it can spin, it will.     */
Priority is not urgency

Raising a thread's priority does not make it faster; it makes it starve everything below it. On a loaded system that is usually how you turn a latency problem into an unresponsive machine. Before reaching for priorities, check whether the thread is actually runnable — a thread blocked on I/O gains nothing from being important. And a high-priority thread that takes a lock a low-priority thread holds gets priority inversion, which is worse than the original problem.

Affinity, and why the scheduler moves you

Pinning a thread to specific cores trades the scheduler's flexibility for predictability. It is occasionally exactly right and more often a way to make things slower in a manner that is hard to attribute.

/* By default a thread may run on any CPU, and the scheduler
   WILL move it to balance load. That migration costs you:
   cold L1, cold L2, cold TLB, and possibly a different NUMA
   node from your memory.                                    */

#define _GNU_SOURCE
#include <sched.h>

void pin_to(int cpu)
{
        cpu_set_t set;
        CPU_ZERO(&set);
        CPU_SET(cpu, &set);
        sched_setaffinity(0, sizeof set, &set);   /* 0 = self  */
}

# From the shell:
$ taskset -c 2,3 ./myapp          # start pinned
$ taskset -cp 2 1234              # pin a running thread
$ numactl --cpunodebind=0 --membind=0 ./myapp

# See where threads actually ran:
$ ps -eLo pid,tid,psr,comm | grep myapp
$ perf stat -e migrations,context-switches ./myapp

/* WHEN PINNING HELPS
     - real-time threads that must not be migrated
     - one thread per core, no oversubscription, cache-heavy
     - NUMA: keeping a thread on the node holding its memory
     - isolating a latency-critical thread with isolcpus /
       nohz_full so the kernel stops interrupting it

   WHEN IT HURTS
     - you pinned two hot threads to SMT siblings of one core
       and they now fight over one L1
     - you pinned everything and the scheduler can no longer
       balance a load you did not predict
     - a pinned thread blocks and its core idles while another
       core has a run queue three deep

   Measure. Pinning is one of the few tuning knobs that is
   just as likely to hurt as help.                           */

Yielding, sleeping, and spinning

Voluntarily giving up the processor sounds like a polite way to share, and is almost always the wrong tool — it is a hint with no defined effect, and code that depends on it is depending on luck.

/* Four ways to give up the CPU, and only two are usually right. */

  sched_yield()           "I am still ready; run someone else."
                          Under CFS this often means the
                          scheduler picks YOU again immediately,
                          because you still have the most
                          credit. As a synchronisation tool it
                          is a coin flip. Legitimate use: a
                          spin-wait's back-off path, and little
                          else.

  nanosleep(1ms)          Genuinely blocks. Precise to the
                          timer resolution, which under CFS
                          means "at least 1ms, possibly 4ms".
                          Fine for polling something slow.
                          Terrible inside a lock.

  a blocking wait         futex / condvar / poll. The thread
                          leaves the run queue entirely and is
                          woken by the event itself. THIS IS
                          THE RIGHT ANSWER for waiting on
                          another thread.

  a spin loop             Burns a core to save a few hundred
                          nanoseconds of wake-up latency. Right
                          only when the wait is provably shorter
                          than a context switch (~1-5 us), and
                          only with a pause instruction:

                              while (locked)
                                      __builtin_ia32_pause();  /* x86 */
                              /* or on ARM: */
                              __asm__ volatile("yield");
                              /* or WFE, which actually sleeps
                                 the core until an event       */

/* The pause/yield hint matters more than it looks: it stops
   the core speculating down the loop, frees the SMT sibling's
   execution units, and cuts the power draw of the spin by a
   large factor.                                              */
The scheduler is not your synchronisation primitive

Code that works because "thread A is higher priority so it runs first" is not synchronised; it is lucky. Add a core, change a kernel version, run under a hypervisor where your vCPU is descheduled (virtualisation chapter 08), and the assumption evaporates. If order matters, express it with a primitive that guarantees it.

Watching it happen

Scheduler behaviour is fully observable, which turns "my thread isn't running often enough" from a complaint into a measurement showing exactly when it ran and what preempted it.

# Is my thread running, blocked, or fighting for a core?
$ ps -eLo pid,tid,stat,psr,pcpu,comm | grep myapp
#   R = running/ready   S = interruptible sleep
#   D = uninterruptible (usually disk)   T = stopped

# How often is it being switched out, and voluntarily?
$ cat /proc/$(pidof myapp)/status | grep ctxt_switches
voluntary_ctxt_switches:     4821    # it blocked - good
nonvoluntary_ctxt_switches:  91024   # it was preempted - it
                                     # wants more CPU than it
                                     # is getting

# Where did the time actually go?
$ perf sched record -- ./myapp
$ perf sched latency --sort max
# per-task: runtime, number of switches, and worst-case delay
# between "became runnable" and "actually ran"

# Scheduling latency for a real-time thread:
$ cyclictest -t1 -p 80 -i 1000 -l 100000 -m
T: 0 (1234) P:80 I:1000 C: 100000 Min: 8 Act: 12 Avg: 14 Max: 71

# A high nonvoluntary count plus high `perf sched latency` max
# means oversubscription: you have more runnable threads than
# cores. No amount of priority tuning fixes that - reduce the
# thread count.
